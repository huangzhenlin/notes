## 持久化

`persist` middleware 可以把部分状态写入 `localStorage`、`sessionStorage` 或自定义存储。它适合主题、用户偏好、草稿、购物车这类可恢复状态。

```typescript
import { create } from "zustand";
import { persist } from "zustand/middleware";

type PreferenceStore = {
  theme: "light" | "dark";
  fontSize: number;
  themeChanged: (theme: "light" | "dark") => void;
};

export const usePreferenceStore = create<PreferenceStore>()(
  persist(
    (set) => ({
      theme: "light",
      fontSize: 14,
      themeChanged: (theme) => set({ theme }),
    }),
    {
      name: "preference-store",
      partialize: (state) => ({
        theme: state.theme,
        fontSize: state.fontSize,
      }),
    },
  ),
);
```

`partialize` 很重要。不是所有状态都应该持久化，加载状态、错误信息、临时弹窗、敏感凭证都不适合长期保存。凭证存储还要结合 [[1.6.8 敏感信息|敏感信息]] 和鉴权策略一起判断。

持久化还要考虑版本迁移。用户本地 storage 可能长期存在，Store 字段改名或结构调整后，旧数据如果不迁移，应用可能恢复出一份不合法状态。

```typescript
persist(
  (set) => ({
    theme: "light",
    setTheme: (theme: "light" | "dark") => set({ theme }),
  }),
  {
    name: "preference-store",
    version: 2,
    migrate: (state, version) => {
      if (version === 1) {
        return { theme: "light" };
      }

      return state;
    },
  },
);
```

能持久化的状态应满足两个条件：刷新后仍有意义，泄露后不会造成严重风险。临时 loading、错误、弹窗、请求缓存通常不符合这个条件。

## 订阅增强

`subscribeWithSelector` 可以让组件外订阅更精确，只监听某个字段或派生结果。

```typescript
import { subscribeWithSelector } from "zustand/middleware";

const useStore = create(
  subscribeWithSelector((set) => ({
    count: 0,
    increment: () => set((state) => ({ count: state.count + 1 })),
  })),
);

const unsubscribe = useStore.subscribe(
  (state) => state.count,
  (count, previousCount) => {
    console.log(count, previousCount);
  },
);
```

它适合组件外逻辑、调试、WebSocket、请求层同步等场景。组件内仍然优先用 `useStore(selector)`。

组件外订阅必须关注清理。入口文件里注册一次的长期订阅可以保留；测试、热更新、临时模块里的订阅如果不 unsubscribe，就可能重复执行。

```typescript
const unsubscribe = useStore.subscribe(
  (state) => state.count,
  (count) => console.log(count),
);

unsubscribe();
```

## 调试辅助

`devtools` 可以把 Zustand 状态变化接入 Redux DevTools，方便查看 action 和 state diff。

```typescript
import { devtools } from "zustand/middleware";

export const useCartStore = create<CartStore>()(
  devtools(
    (set) => ({
      items: {},
      itemAdded: (product) =>
        set(
          (state) => ({
            items: {
              ...state.items,
              [product.id]: { product, quantity: 1 },
            },
          }),
          false,
          "cart/itemAdded",
        ),
    }),
    { name: "cart-store" },
  ),
);
```

第三个参数是 action 名称。给关键 action 命名后，调试时能更快看出状态变化来源。

如果 action 名称缺失，DevTools 里只会看到匿名更新或难以理解的默认名称。Zustand 不强制 action type，所以越是复杂 Store，越应该在关键 `set` 调用里补上业务化名称。

## immer

`immer` 适合处理嵌套更新，但它不应该成为复杂状态结构的借口。

```typescript
import { immer } from "zustand/middleware/immer";

export const useTodoStore = create<TodoStore>()(
  immer((set) => ({
    items: [],
    toggleTodo: (id) =>
      set((state) => {
        const todo = state.items.find((item) => item.id === id);

        if (todo) {
          todo.done = !todo.done;
        }
      }),
  })),
);
```

如果更新路径很深，先检查状态是否可以归一化或拆分。工具可以降低写法成本，但不能消除错误的建模边界。

Immer 适合嵌套结构不可避免的场景，例如编辑器文档树、复杂配置、表单 schema。普通列表按 id 更新时，扁平结构通常比深层对象更清楚。不要因为有 Immer 就接受任意深的状态树。

## 组合顺序

多个中间件可以组合，但顺序会影响类型推导和运行行为。组合越多，调试成本越高。

```typescript
export const useStore = create<State>()(
  devtools(
    persist(
      immer((set) => ({
        count: 0,
        increment: () =>
          set((state) => {
            state.count += 1;
          }),
      })),
      { name: "counter-store" },
    ),
  ),
);
```

优先为明确问题引入中间件，而不是在每个 store 上套一整组默认能力。

组合顺序还会影响调试和持久化行为。比如 persist 的恢复动作是否被 devtools 记录、immer 的草稿是否包住所有更新，都和包裹顺序有关。团队最好形成固定模板，不要每个 Store 都随意排列。

## 使用边界

Zustand middleware 是增强 Store 行为的方式，但不应该把所有能力都靠中间件堆出来。

| 能力 | 适合中间件 |
| --- | --- |
| 持久化用户偏好 | 适合 |
| 接入调试工具 | 适合 |
| 精确订阅变化 | 适合 |
| 深层不可变更新 | 可用 immer |
| 复杂业务编排 | 不优先 |
| 服务端缓存系统 | 不优先 |

复杂业务流程仍然应该回到清晰的状态设计。缓存、重试、失效这类服务端状态问题，不要强行塞进 middleware。

中间件解决横切能力，不解决业务归属。持久化、调试、订阅、不可变更新是横切能力；结算、登录后初始化、切换项目清理缓存是业务流程。后者更适合 action、组合函数或流程层。
