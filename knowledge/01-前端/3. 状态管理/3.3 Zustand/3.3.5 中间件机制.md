## persist 示例

持久化中间件常用于保存登录态、主题、语言、低频配置等状态。

```typescript
const useSettingStore = create(
  persist(
    (set) => ({
      theme: "light",
      setTheme: (theme: string) => set({ theme }),
    }),
    {
      name: "settings",
      partialize: (state) => ({ theme: state.theme }),
    }
  )
);
```

`partialize` 很重要，它可以控制只持久化真正需要的字段，避免把 token、临时表单、接口缓存等不该保存的内容写进本地存储。

持久化最容易踩的坑是“恢复时机”。页面初次渲染时，持久化状态可能还没有恢复完成；如果 UI 立刻根据默认值渲染，可能出现闪烁或错误判断。对登录态、主题、语言这类状态，要明确是否需要等待恢复后再渲染关键内容。

## immer 示例

如果状态层级较深，可以用 immer 中间件降低不可变更新的书写成本。

```typescript
const useTodoStore = create(
  immer((set) => ({
    todos: [],
    toggleTodo: (id: string) =>
      set((state) => {
        const todo = state.todos.find((item) => item.id === id);
        if (todo) todo.done = !todo.done;
      }),
  }))
);
```

这种写法看起来像直接修改，但实际会生成新的状态。它适合复杂嵌套更新，不适合掩盖混乱的数据结构。

Immer 能降低嵌套更新样板，但它不是状态建模替代品。如果每个 action 都需要改四五层深的对象，先考虑是否应该把状态扁平化或按 id 存储。

## 排查方法

中间件问题可以按这个顺序排查：

1. 去掉所有 middleware，确认基础 Store 是否正确。
2. 只恢复一个 middleware，观察行为变化。
3. 检查增强顺序是否改变了 `set`、`get` 或订阅行为。
4. 检查持久化恢复时机是否影响页面初始渲染。

这个顺序比直接猜“哪个中间件坏了”更稳定。

中间件叠加后，问题可能来自顺序而不是单个中间件。例如 devtools 包在 persist 外面和里面，看到的 action、恢复过程和调试信息都可能不同。排查时要把组合顺序也当成变量。
## 中间件位置

Zustand 中间件包裹 Store 创建函数，用来增强 `set`、`get`、订阅、持久化或调试能力。

```ts
const useStore = create<State>()(
  devtools(
    persist(
      (set, get) => ({
        count: 0,
        increment: () => set({ count: get().count + 1 }),
      }),
      { name: "counter-store" },
    ),
  ),
);
```

中间件改变的是 Store 能力，不应该承载具体业务规则。业务规则仍然优先写在 action 或纯函数里。

中间件越底层，越应该通用。persist 管存储，devtools 管调试，immer 管更新写法，subscribeWithSelector 管订阅。把“下单后清空购物车”写成中间件逻辑，通常不如写在业务流程或 action 里清楚。

## persist 生命周期

`persist` 的关键不是“写入 storage”，而是完整处理保存、恢复、筛选字段和版本迁移。

```ts
persist(
  (set) => ({
    token: "",
    theme: "light",
    setTheme: (theme: "light" | "dark") => set({ theme }),
  }),
  {
    name: "app-preference",
    partialize: (state) => ({ theme: state.theme }),
    version: 2,
    migrate: (persistedState, version) => {
      if (version === 1) {
        return { theme: "light" };
      }

      return persistedState;
    },
  },
);
```

`partialize` 用来避免把不该保存的字段写入 storage。`version` 和 `migrate` 用来处理状态结构升级。

持久化数据就是一份长期存在的外部数据，结构升级必须考虑兼容。改字段名、改枚举值、拆分对象后，如果没有 migrate，老用户本地 storage 可能让应用进入异常状态。

## devtools Action 名称

使用 `devtools` 时，可以给 `set` 传入 action 名称，让调试时间线更清晰。

```ts
const useCartStore = create<CartStore>()(
  devtools((set) => ({
    items: [],
    addItem: (product) =>
      set(
        (state) => ({ items: [...state.items, product] }),
        false,
        "cart/addItem",
      ),
  })),
);
```

如果 action 名称缺失，DevTools 里只能看到匿名更新，排查复杂流程时会很吃力。

DevTools action 名称最好和业务动作一致。`cart/addItem`、`editor/contentChanged` 比 `setState` 更容易定位问题。Zustand 不强制 action type，所以更需要团队自觉命名。

## subscribeWithSelector

`subscribeWithSelector` 可以订阅某个状态片段，而不是监听整个 Store。

```ts
const useAuthStore = create(
  subscribeWithSelector((set) => ({
    token: "",
    setToken: (token: string) => set({ token }),
  })),
);

useAuthStore.subscribe(
  (state) => state.token,
  (token, previousToken) => {
    if (token !== previousToken) {
      apiClient.setToken(token);
    }
  },
);
```

它适合组件外同步外部系统，例如请求客户端、WebSocket、日志模块。组件内渲染仍然优先用 selector。

组件外订阅要记得清理。模块级订阅如果没有 unsubscribe，可能在测试、热更新或多实例场景中重复执行。

## 组合成本

中间件越多，类型、调试和行为理解成本越高。引入前可以先判断它解决的是不是明确问题。

| 中间件 | 解决问题 | 典型代价 |
| --- | --- | --- |
| persist | 跨刷新保留 | 恢复、迁移、敏感字段控制 |
| devtools | 调试状态变化 | action 命名和调试配置 |
| immer | 简化嵌套更新 | 状态结构问题可能被掩盖 |
| subscribeWithSelector | 精细订阅 | 订阅清理和外部副作用管理 |

中间件选择的原则是先有问题，再引入能力。需要跨刷新保留再上 persist，需要调试时间线再上 devtools，嵌套更新确实痛苦再上 immer。Zustand 本来轻，别让中间件把轻量优势吃掉。
