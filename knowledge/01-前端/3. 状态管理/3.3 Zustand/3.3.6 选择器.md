## 状态选择

选择器用于从 Store 取出组件真正需要的值。相比订阅整个对象，选择具体字段能减少无关更新带来的渲染。

选择器是 Zustand 性能的核心之一。它决定了组件到底订阅多大范围的数据，也决定了状态变化会不会把整棵组件树一起拖着重渲染。

```typescript
const userName = useUserStore((state) => state.user.name);
```

如果组件写成 `const store = useUserStore()`，Store 中任何字段变化都会让组件重新渲染。小组件问题不大，但列表项、复杂面板和高频状态里会很快变成性能问题。

所以在 Zustand 里，默认应该先想“我到底需要哪几个字段”，再写 selector，而不是先把整个 Store 拿下来再慢慢挑。

选择器设计和 Store 设计是互相影响的。如果 Store 把生命周期不同的状态全塞在一起，选择器再精细也会越来越难写；如果 Store 边界清楚，selector 通常很短。

所以 selector 问题很多时候不是读取层单独的问题，而是 store 设计的回声。订阅范围总是太大、返回值总是不稳定，往往说明状态本身已经混得过重了。

## 最小订阅

组件应该只订阅自己渲染必需的数据，不订阅“顺手拿到”的整个业务对象。

```tsx
function UserName() {
  const name = useUserStore((state) => state.profile.name);

  return <span>{name}</span>;
}
```

最小订阅能让 Zustand 的轻量模型真正发挥作用。否则 Store 越大，组件越容易被无关字段拖着渲染。

这对长列表和高频交互尤其重要。组件订阅得越少，后面你越不需要靠额外 memo 去补救。

最小订阅还能降低心智负担。组件读 `profile.name`，就只关心名字；组件读整个 `profile`，后续头像、权限、偏好任何字段变化都可能影响它。

这条原则对长列表尤其重要。列表项只要订阅了多余字段，就会在无关更新时被批量带着重渲染。Zustand 的性能优势很多时候不是“框架更快”，而是你能不能把订阅读得足够小。

## 多字段选择

组件需要多个字段时，可以分别订阅，也可以返回对象并配合浅比较。

```tsx
import { shallow } from "zustand/shallow";

function Toolbar() {
  const { keyword, setKeyword, reset } = useSearchStore(
    (state) => ({
      keyword: state.keyword,
      setKeyword: state.setKeyword,
      reset: state.reset,
    }),
    shallow,
  );

  return (
    <form>
      <input
        value={keyword}
        onChange={(event) => setKeyword(event.target.value)}
      />
      <button type="button" onClick={reset}>
        重置
      </button>
    </form>
  );
}
```

返回对象时每次都会创建新引用，浅比较可以避免字段没变但对象引用变化导致的重渲染。字段很少时，拆成多个 selector 也很清楚。

如果字段少，拆成多个 selector 往往比返回对象更直观；如果字段多且总是一起使用，配合浅比较可以减少重复订阅带来的样板。

不要为了少写几行，把不相关字段塞进同一个对象 selector。比如一个组件同时读 `keyword` 和 `theme`，如果它们没有业务关系，通常应该分开订阅。

选择器是否该合并，不应只看代码行数，而要看这些字段是否总是一起消费、一起影响同一块 UI。字段关系越松，越适合拆开；字段关系越紧，再考虑合并加浅比较。

## 浅比较

浅比较只比较对象第一层字段是否相同，不会深度比较嵌套对象。

```typescript
const result = useStore(
  (state) => ({ name: state.name, role: state.role }),
  shallow,
);
```

如果 selector 返回的嵌套对象每次都新建，浅比较也救不了。此时要重新检查状态结构或派生方式。

也就是说，选择器只能优化订阅边界，不能替你修状态结构。如果状态层本身设计得太重，还是要回头拆。

浅比较只看第一层引用。如果 selector 返回 `{ user: state.user }`，而 `user` 每次都被 reducer/action 重建，浅比较仍然会认为变化。真正稳定要从更新路径和状态结构一起看。

这也是为什么 `shallow` 不是万能开关。它能避免简单对象包装带来的无意义更新，但不能替代稳定的引用和合理的状态结构。真正的根因如果在 store 更新方式，比较函数只能暂时掩盖现象。

## 派生选择

Selector 可以直接做派生计算，但要注意返回引用的稳定性。

```typescript
const completedCount = useTodoStore(
  (state) => state.todos.filter((todo) => todo.done).length,
);
```

返回数字、字符串、布尔值通常很稳定。返回数组或对象时，如果每次都创建新引用，组件更容易重渲染。

```typescript
const completedTodos = useTodoStore(
  (state) => state.todos.filter((todo) => todo.done),
);
```

这段代码能工作，但当 `todos` 较大或组件较多时，可以把筛选条件拆小，或用 `useShallow`、外部记忆化方案控制引用变化。

派生 selector 适合轻量计算，不适合重查询。筛选、排序、分页如果已经开始影响体验，通常就要回头考虑状态结构或服务端缓存。

如果派生结果是数组或对象，并且多个组件依赖它，可以把派生逻辑抽成独立 selector 函数，配合记忆化库或手动缓存。不要在很多组件里重复写同一段过滤规则。

派生选择器最好仍然保持轻量。只要排序、筛选、分组已经开始明显消耗性能，就值得回头想：这是不是应该前移到服务端状态层、缓存层，或者先把基础状态结构整理好，而不是把所有计算都压给组件订阅阶段。

## 外部读取

Zustand Store 可以在组件外读取和订阅，适合请求层、事件总线、WebSocket 回调等非 React 场景。

```typescript
const token = useAuthStore.getState().token;

useAuthStore.subscribe((state, previousState) => {
  if (state.token !== previousState.token) {
    apiClient.setToken(state.token);
  }
});
```

组件外读取不是响应式渲染，只是拿当前快照或监听变化。不要把它和组件里的 selector 混为一谈。

组件外读取适合和网络层、WebSocket、定时器等代码集成，但它不应该替代组件订阅。一个是业务外部接入，一个是 React 渲染订阅，职责不一样。

组件外读取尤其要小心旧快照。`const token = useAuthStore.getState().token` 只读取当下值，后续 token 变化不会自动更新这个变量。需要持续同步时，应使用 subscribe。

这类外部读取最适合接请求客户端、WebSocket 管理器、路由守卫或定时器协调层，但不适合拿来替代 React 内部状态驱动。一个是外部系统接入点，一个是界面渲染订阅点，两者要分清。

## 渲染控制

选择器设计直接影响渲染范围。页面卡顿时，排查顺序通常是：

1. 组件是否订阅了过大的状态对象。
2. selector 是否每次创建新引用。
3. 列表是否把无关状态传给大量子项。
4. Store 是否把生命周期不同的状态放在一起。

很多性能问题不是 Zustand 本身慢，而是订阅边界太粗。

如果页面卡顿，先看 selector，再看状态结构，最后才看是否需要拆 Store。多数问题都能在“订阅范围是否过大”这一步找到答案。

排查时可以在组件里临时计数渲染次数，或用 React DevTools Profiler 看哪些组件被无关状态带动。不要一开始就把问题归因给 Zustand，很多时候只是 selector 写得太宽。

如果一个组件总在“明明没变的数据”下反复渲染，优先检查三件事：它订阅是不是太宽，selector 返回的引用是不是总在变，store 更新是不是每次都顺手重建了很多字段。通常问题就藏在这三处里。
