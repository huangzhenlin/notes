## Store

Zustand 的 Store 是一个独立状态容器，可以在 React 组件中通过 Hook 使用，也可以在组件外读取和更新。

```javascript
import { create } from "zustand";

const useCounterStore = create((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
}));
```

Zustand 的特点是 API 小、样板代码少，不强制你使用 Action 类型、Reducer 或 Provider。

这种轻量感是它的优势，也是它的风险。工具不强制你建立流程约束，团队就更需要自己约定 Store 命名、Action 边界、选择器粒度和副作用位置。

Zustand 的 Store 默认是模块级单例。这个特性让跨组件共享非常简单，但在 SSR、测试、多实例编辑器和多账号切换场景里要格外小心。浏览器单页应用里单例通常没问题；服务端渲染时，如果把用户相关状态放进全局单例，就可能出现请求之间状态串扰。

## 订阅更新

组件使用 Store 中的状态时，会订阅对应数据变化。状态变化后，相关组件重新渲染。

```javascript
function Counter() {
  const count = useCounterStore((state) => state.count);
  return <span>{count}</span>;
}
```

如果组件直接订阅整个 Store，任何字段变化都可能触发重新渲染。因此选择器很重要。

Zustand 的性能不是自动来的，而是依赖你订阅得足够精确。组件只读 `count`，就不要订阅整个 store；组件只需要 `user.name`，也不要把完整用户对象传来传去。

```tsx
// 订阅过粗
const state = useCounterStore();

// 订阅精确
const count = useCounterStore((state) => state.count);
```

订阅越接近使用点，状态变化影响越小。Zustand 不需要你写 reducer，但仍然需要你认真设计读取边界。

## 选择器

选择器决定组件关心 Store 的哪一部分。

```javascript
const count = useCounterStore((state) => state.count);
```

组件只订阅自己需要的数据，状态拆分和渲染控制才会更稳定。Zustand 的轻量感很大程度上来自这种直接选择状态的方式。

选择器返回对象或数组时，要注意引用稳定。每次返回新对象，组件就可能重新渲染。可以拆成多个 selector，或者配合浅比较工具。

```tsx
const count = useCounterStore((state) => state.count);
const increment = useCounterStore((state) => state.increment);
```

简单场景下分别订阅字段最直观；确实需要组合读取时，再考虑 shallow 比较。

## Store 即 Hook

Zustand 的核心模型很轻：创建 store 后得到的就是一个 React Hook。组件调用这个 Hook 读取状态，也可以从中拿到 action。

```ts
import { create } from "zustand";

type CounterStore = {
  count: number;
  increment: () => void;
  reset: () => void;
};

export const useCounterStore = create<CounterStore>((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
  reset: () => set({ count: 0 }),
}));
```

```tsx
function CounterButton() {
  const count = useCounterStore((state) => state.count);
  const increment = useCounterStore((state) => state.increment);

  return <button onClick={increment}>点击 {count}</button>;
}
```

Zustand 不要求 Provider，也不要求 reducer/action type。它适合中小型全局状态、跨组件共享状态和局部复杂模块，但也因此更依赖团队自己维护 Store 边界。

如果项目本身状态规则简单，Zustand 能让代码非常直接；如果业务流程非常复杂，则需要额外补上测试、命名规范和 action 约束，否则 Store 很容易变成随手修改的全局对象。

Zustand 的自由度很高，所以 action 命名要自觉贴近业务。`addItem`、`toggleTodo`、`resetEditor` 比 `setData`、`update` 更容易调试。轻量工具不等于随意工具，越少约束越需要团队约定。

## set 与 get

`set` 负责写入状态，`get` 负责读取当前状态。同步 action 通常只需要 `set`，依赖当前状态或多个 action 联动时会用到 `get`。

```ts
type CartStore = {
  items: Array<{ id: string; price: number; quantity: number }>;
  totalPrice: () => number;
  clearIfEmpty: () => void;
};

export const useCartStore = create<CartStore>((set, get) => ({
  items: [],
  totalPrice: () =>
    get().items.reduce(
      (sum, item) => sum + item.price * item.quantity,
      0,
    ),
  clearIfEmpty: () => {
    if (get().items.length === 0) {
      set({ items: [] });
    }
  },
}));
```

派生值可以写成函数，也可以放到组件 selector 里计算。不要为了方便把 `totalPrice` 这类可以稳定计算出来的值重复保存成状态，否则会引入同步问题。

`get` 适合在 action 内读取当前快照，但不要把它当成跨 Store 随意访问的万能入口。读取越多，依赖越隐蔽，后续拆分 Store 时越痛苦。

## 更新方式

Zustand 的 `set` 默认是浅合并对象，因此更新嵌套数据时仍然要注意不可变更新。

```ts
const useProfileStore = create((set) => ({
  profile: {
    name: "Ada",
    address: { city: "Shanghai" },
  },
  cityChanged: (city: string) =>
    set((state) => ({
      profile: {
        ...state.profile,
        address: {
          ...state.profile.address,
          city,
        },
      },
    })),
}));
```

如果嵌套层级很深，可以考虑调整状态结构，或配合 immer 中间件。优先让状态形状简单，而不是让更新工具替复杂建模兜底。

状态结构最好先服务于更新路径。经常按 id 更新的集合更适合字典结构，经常按顺序展示的列表才更适合数组。结构选对了，action 会简单很多。

## 适用边界

| 场景 | Zustand 是否合适 | 判断 |
| --- | --- | --- |
| 弹窗、侧边栏、当前选中项 | 合适 | 跨组件共享但业务流程不复杂 |
| 购物车、本地草稿、编辑器状态 | 合适 | 客户端状态为主，action 边界清楚 |
| 大型后台的复杂领域流程 | 视情况 | 需要严格约束 store 拆分和测试 |
| 服务端缓存、分页、失效、轮询 | 不优先 | 更适合 TanStack Query 或 RTK Query |
| 强审计、强时间旅行调试 | 不优先 | Redux DevTools 与 action 约束更成熟 |

Zustand 的核心适用场景是“客户端业务状态清楚、组件共享真实存在、团队愿意维护边界”。如果状态主要来自服务端，优先考虑服务端状态工具；如果需要强流程约束，再考虑 Redux。

可以把 Zustand 放在“组件状态”和“强约束 Redux”之间：它比组件 state 更适合跨组件共享，比 Redux 更轻；但它不天然提供严格 action 流、时间旅行和服务端缓存模型。选它时，要确认你需要的是轻量共享状态，而不是完整数据获取层或强流程审计。
