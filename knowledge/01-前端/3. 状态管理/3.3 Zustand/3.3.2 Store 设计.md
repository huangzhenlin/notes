## 状态切分

Store 设计的第一步不是写代码，而是决定哪些状态应该放在同一个 Store 中。

```javascript
const useUserStore = create((set) => ({
  user: null,
  setUser: (user) => set({ user }),
}));
```

同一业务域、生命周期相近、经常一起更新的状态更适合放在一起；无关状态硬塞进一个 Store，会让选择器和更新逻辑都变复杂。

Zustand 很容易创建 Store，所以更要先想清楚边界。不是每个字段都值得单独成 Store，也不是所有字段都应该塞进一个总 Store。

设计 Store 时可以先写出“状态事实”和“允许动作”。如果只能列出字段，却说不出动作，说明这个 Store 可能只是把变量挪到了全局。

```text
购物车 Store
  状态：items、coupon、status
  动作：addItem、removeItem、changeQuantity、applyCoupon、reset
```

这个方法的好处在于，它会强迫你先把业务语言说清楚。字段只是事实快照，action 才真正体现这个 Store 存在的价值。如果一个 Store 只有数据，没有清晰动作，它往往更像被动仓库，而不是稳定状态边界。

## 动作组织

Zustand 通常把状态和修改状态的函数放在同一个 Store 中。

```javascript
const useCartStore = create((set) => ({
  items: [],
  addItem: (item) => set((state) => ({ items: [...state.items, item] })),
}));
```

这种写法很直接，但也要避免 Store 变成“万能服务对象”。动作应该围绕状态本身组织，而不是把所有业务流程都塞进去。

如果 action 名称越来越像 `handleSubmit`、`onClick`、`doSomething`，通常说明它已经开始贴近组件事件，而不是业务动作。更好的 action 名称应该表达业务结果。

组件事件和 Store action 要分层。组件事件可以叫 `handleClick`，Store action 应该叫 `addItem`、`submitDraft`、`resetSelection`。前者描述交互入口，后者描述状态变化或业务动作。

这层分离能直接提升可维护性。组件换了交互方式，Store action 往往不需要变；但如果 action 一开始就贴着组件命名，后续组件一重构，Store 语义也会跟着漂移。

## 组合边界

大型项目可以按业务域拆多个 Store，也可以用 slice 模式组合 Store。

| 方式 | 适合场景 | 风险 |
| --- | --- | --- |
| 单 Store | 小应用、状态少 | 逐渐膨胀 |
| 多 Store | 业务域清晰 | 跨 Store 协调增多 |
| Slice 组合 | 大 Store 下分模块 | 类型和组合逻辑更复杂 |

选择哪种方式，取决于状态是否真的共享，而不是目录看起来是否整齐。

多 Store 的好处是边界清楚，坏处是跨 Store 流程会增多。Slice 组合的好处是集中创建一个大 Store，坏处是类型和组合函数更复杂。不要为了“架构完整”提前引入 slice 模式，先让业务域边界稳定更重要。

很多 Zustand 项目的设计难点，不在 API，而在“什么时候该拆、什么时候该合”。一个稳妥原则是先按业务域拆，再根据共享程度决定是否需要组合；不要一开始就因为目录好看而提前抽象。

## 业务域拆分

Zustand 的 Store 可以很小，也可以很大。更稳定的拆分方式是围绕业务域，而不是围绕组件层级。

```txt
stores/
  useUserStore.ts
  useCartStore.ts
  useEditorStore.ts
```

用户信息、购物车、编辑器状态分别有自己的生命周期和 action。它们可以在页面中组合使用，但不需要塞进一个巨大的 `useAppStore`。

拆分以后，每个 Store 都应该能回答三个问题：它保存什么事实，它允许哪些动作，它什么时候被清理或重置。答不上来，就说明边界还不够稳。

尤其要补上“什么时候被清理或重置”这个问题。很多状态在登录切换、项目切换、页面退出、提交完成后都应该重置；如果设计时没想清楚，后面很容易出现旧状态残留和跨流程污染。

## 状态与 Action 共置

Zustand 常见写法是把状态和修改状态的 action 放在同一个 store 中。组件只调用 action，不直接拼复杂的 `set` 逻辑。

```ts
type TodoStore = {
  items: Array<{ id: string; title: string; done: boolean }>;
  addTodo: (title: string) => void;
  toggleTodo: (id: string) => void;
};

export const useTodoStore = create<TodoStore>((set) => ({
  items: [],
  addTodo: (title) =>
    set((state) => ({
      items: [
        ...state.items,
        { id: crypto.randomUUID(), title, done: false },
      ],
    })),
  toggleTodo: (id) =>
    set((state) => ({
      items: state.items.map((todo) =>
        todo.id === id ? { ...todo, done: !todo.done } : todo,
      ),
    })),
}));
```

这样组件不需要知道 todo 是数组还是字典，也不需要知道切换完成状态的具体更新规则。后续状态结构调整时，影响范围会更小。

这也是状态和 action 共置的真正价值：组件只表达意图，Store 负责细节。只要 action 入参和语义稳定，内部数据结构可以逐步演进。

共置还能让测试更聚焦。你可以直接对 store action 做断言，而不是通过 UI 间接验证状态更新。对于表单、编辑器、选择器这种交互密集的状态，收益会非常明显。

## Store 粒度

Store 太大时，容易出现命名拥挤、action 互相调用混乱和无关订阅；Store 太小时，跨 store 协作会变得频繁。

| 粒度 | 表现 | 调整方向 |
| --- | --- | --- |
| 过大 | 一个 store 包含用户、购物车、权限、页面 UI | 按业务域拆分 |
| 适中 | 一个 store 负责一个稳定业务域 | 保持 action 清晰 |
| 过小 | 每个字段一个 store | 合并生命周期相同的状态 |

判断粒度时可以看生命周期：一起加载、一起重置、一起持久化、一起测试的状态，更适合放在同一个 store。

如果一个 Store 需要同时处理登录、主题、购物车、弹窗、编辑器，它通常已经过大；如果一个 Store 只有一个布尔值，却要跨很多地方协调，它也可能过小。

判断粒度时还可以看“谁会一起订阅、谁会一起持久化、谁会一起清空”。这三件事如果经常同时发生，通常说明它们可以放在一个 Store；如果几乎从不一起发生，硬塞在一起只会增加订阅和重置复杂度。

## 跨 Store 协作

跨 store 调用要克制。偶尔读取另一个 store 的快照可以接受，但如果两个 store 长期互相依赖，说明边界可能划错了。

```ts
const useCheckoutStore = create((set) => ({
  submit: async () => {
    const user = useUserStore.getState().profile;
    const items = useCartStore.getState().items;

    await checkoutApi.submit({ userId: user.id, items });
    set({ status: "success" });
  },
}));
```

结算流程读取用户和购物车是合理的；但如果购物车 action 经常修改用户 store，用户 action 又经常修改购物车 store，就应该考虑抽出更高层的业务流程或重新划分 store。

跨 Store 协作越频繁，越应该考虑“流程层”是否缺失。结算、登录后初始化、项目切换这类流程，往往不属于单个 Store，而属于更高层业务编排。

流程层可以是页面 action、服务函数、组合 hook 或专门的业务编排函数。它负责读取多个 store、调用接口、处理跳转，再把结果写回各自 Store。这样 Store 仍然保持单一职责，不会互相缠绕。

一旦某个 Store 里开始频繁出现“先读 A Store，再改 B Store，再判断 C Store”的逻辑，就值得停下来重看边界。很多时候不是 Zustand 不适合，而是流程层和状态层被混写了。
