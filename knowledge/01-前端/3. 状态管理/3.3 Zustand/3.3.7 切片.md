## 切片动机

Zustand 没有强制模块系统。Store 变大后，可以用 Slice Pattern 把不同业务域拆成可组合的创建函数。

Slice Pattern 解决的是“大 Store 不好维护”，不是“我想把所有东西拼成一个巨型 Store”。只有在确实需要组合时，它才比独立 Store 更有价值。

```txt
createUserSlice
createCartSlice
createCheckoutSlice
        ↓
useAppStore
```

切片解决的是“大 Store 难维护”的问题。它不是为了把所有小 Store 强行合并，而是在确实需要一个组合 Store 时保持边界清楚。

切片模式适合“业务域不同，但希望共享同一个 Store 实例和中间件能力”的场景。比如多个 slice 都需要 persist、devtools，或者流程层需要在同一 store 内读取多个域。若模块之间几乎没有关系，独立 Store 通常更简单。

换句话说，slice 解决的是“同一棵状态树内部怎么分工”，不是“所有状态最终都要进同一个 app store”。如果模块天然独立，强行切片再组合，反而会增加类型和依赖负担。

## Slice 定义

每个 slice 返回自己负责的状态和 action。

```ts
type UserSlice = {
  user: User | null;
  setUser: (user: User | null) => void;
};

const createUserSlice: StateCreator<
  UserSlice & CartSlice,
  [],
  [],
  UserSlice
> = (set) => ({
  user: null,
  setUser: (user) => set({ user }),
});
```

slice 的类型会有一点复杂，因为最终 Store 是多个 slice 的交集。类型写清楚后，跨 slice 调用和组件使用都会更稳。

切片的复杂度主要体现在 TypeScript 上，所以它更适合团队已经熟悉 Zustand 且愿意承担一定类型组织成本的项目。

每个 slice 都应该只返回自己的字段和 action。不要让 `createUserSlice` 顺手创建 cart 字段，也不要让 `createCartSlice` 修改 user 字段。类型交叉只是组合方式，不代表职责可以混用。

这条约束非常关键。slice 一旦开始越权，就会很快失去模块意义，最后虽然文件看起来拆开了，实际逻辑仍然纠缠在一起。真正的好处不是“文件更多了”，而是边界更清楚了。

## 组合 Store

组合时把多个 slice 展开到同一个 Store 中。

```ts
type AppStore = UserSlice & CartSlice & CheckoutSlice;

export const useAppStore = create<AppStore>()((...args) => ({
  ...createUserSlice(...args),
  ...createCartSlice(...args),
  ...createCheckoutSlice(...args),
}));
```

组合后的组件使用方式仍然是普通 Zustand selector。

对组件来说，切片后的使用方式不应该变复杂。组件仍然只关心自己读什么、触发什么，不需要知道状态是怎么拼起来的。

```tsx
const user = useAppStore((state) => state.user);
const addItem = useAppStore((state) => state.addItem);
```

如果组件开始需要知道“这个字段来自哪个 slice”，说明组合层可能泄露了实现细节。切片应该是维护层内部组织，对组件最好保持透明。

对组件而言，最理想的体验是：它只知道自己要读哪个字段、调哪个 action，而不用在意底层是单 store、多 slice 还是怎样组合出来的。实现细节越少泄漏，后续重构空间越大。

## 跨 Slice 调用

跨 slice 调用可以通过 `get` 完成，但要控制依赖方向。

```ts
const createCheckoutSlice: StateCreator<AppStore, [], [], CheckoutSlice> = (
  set,
  get,
) => ({
  status: "idle",
  submit: async () => {
    const user = get().user;
    const items = get().items;

    if (!user || items.length === 0) return;

    set({ status: "submitting" });
    await checkoutApi.submit({ userId: user.id, items });
    set({ status: "success" });
  },
});
```

结算 slice 读取用户和购物车是合理的，因为它代表更高层流程。反过来，如果 user、cart、checkout 互相频繁调用，就说明切片边界需要重新设计。

跨 slice 调用最好只向上汇总，不要向下互相掺杂。越像流程编排的 slice，越适合放在上层；越像基础事实的 slice，越应该保持单一职责。

跨 slice 流程最好有清晰方向：checkout 可以读取 user 和 cart，因为它是更高层流程；user slice 不应该反过来知道 checkout 细节。依赖方向一旦互相循环，切片就会变成隐形耦合。

判断依赖方向时，可以把 slice 分成“基础事实”和“流程汇总”两类。基础事实 slice 尽量少依赖别人，流程型 slice 可以读取基础事实做组合决策。只要基础层开始反向依赖流程层，边界通常就乱了。

## 命名边界

组合 Store 中所有字段会落到同一层，命名冲突要提前避免。

```ts
// 容易冲突
status
error
reset

// 更清楚
checkoutStatus
checkoutError
resetCheckout
```

如果多个 slice 都有 `status`，组件读取时很难判断语义。可以通过命名前缀、嵌套对象或拆成多个 Store 来保持清晰。

命名冲突是切片最常见的隐患之一。它不一定马上出 bug，但会慢慢侵蚀可读性，所以最好在一开始就约定好命名风格。

也可以用嵌套对象减少命名冲突，例如 `checkout.status`、`editor.status`，但这样 selector 会稍长。扁平命名和嵌套命名没有绝对优劣，关键是同一个 Store 内保持一致。

命名一致性比命名风格本身更重要。只要一个 store 里一半字段是扁平前缀、一半字段是深层嵌套，组件和 selector 很快就会变得难读。先选一种对当前项目最顺手的方式，再稳定执行，比来回摇摆更重要。

## 使用边界

Slice Pattern 适合一个业务模块确实需要共享 Store 能力的场景。简单项目可以直接多个独立 Store；过早使用 slice 会增加类型和组织成本。

| 场景 | 是否适合切片 |
| --- | --- |
| 一个 Store 已经包含多个稳定业务域 | 适合 |
| 多个 slice 需要共享中间件和持久化 | 适合 |
| 每个模块几乎互不依赖 | 不一定，独立 Store 更简单 |
| 只是为了“看起来架构化” | 不适合 |

如果一个项目还处于快速变化期，过早切片会增加维护成本。先用更直白的独立 Store 跑通边界，真的需要共享实现时再切片，通常更稳。

切片不是 Zustand 的必修课。小项目和中等项目用多个独立 Store 往往已经够清楚；只有当单 Store 变大且业务域稳定时，再引入 Slice Pattern，收益才会超过类型成本。

所以引入切片前，最好先确认痛点到底是什么。是一个 Store 已经装不下，还是其实只是命名混乱、action 语义不清、selector 订阅过宽。如果根因不是规模，而是边界本身没想清楚，切片只会把问题分散到更多文件里。
