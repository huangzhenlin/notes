## 异步 Action

Zustand 不需要额外中间件才能写异步。Action 可以直接是 `async` 函数，请求完成后调用 `set` 更新状态。

这使得异步流程写起来非常直接，但也意味着你要自己负责加载状态、错误状态、竞态和取消策略，不像专门的服务端状态工具那样内建那么多能力。

```typescript
type UserStore = {
  user: User | null;
  status: "idle" | "loading" | "success" | "error";
  error: string | null;
  loadUser: (id: string) => Promise<void>;
};

export const useUserStore = create<UserStore>((set) => ({
  user: null,
  status: "idle",
  error: null,
  loadUser: async (id) => {
    set({ status: "loading", error: null });

    try {
      const user = await userApi.getUser(id);
      set({ user, status: "success" });
    } catch (error) {
      set({
        status: "error",
        error: error instanceof Error ? error.message : "加载失败",
      });
    }
  },
}));
```

这种写法适合客户端业务状态里夹带少量请求，例如加载当前用户、提交本地草稿、同步编辑器配置。

如果异步请求只是业务动作的一部分，比如保存草稿、同步设置、提交表单，Zustand 很合适；如果请求本身已经是一个完整的数据缓存系统，就不该勉强用它顶上。

异步 action 的优势是直观，缺点是所有策略都要自己写：什么时候 loading，失败是否回滚，旧请求是否忽略，成功后是否失效其他数据。简单流程很舒服，复杂服务端状态会越来越像手写 Query 工具。

## 加载状态

异步 action 通常要显式维护加载和错误状态。不要只把数据写进 Store，却不告诉界面当前请求处在哪个阶段。

```typescript
type RequestStatus = "idle" | "loading" | "success" | "error";
```

请求状态越复杂，越应该用明确枚举或判别联合建模，而不是几个布尔值互相组合。

只用 `loading`、`error` 两个布尔值，往往不够表达真实业务。像首次加载、刷新中、提交中、重试中、已过期这些状态，最好都有清晰命名。

如果一个 Store 同时有读取和提交，最好把读取状态和提交状态分开。列表刷新中的 `isFetching` 不应该禁用提交按钮；提交中的 `isSubmitting` 也不一定要清空列表。

## 错误处理

错误不应该只写进控制台。界面通常需要知道错误类型、是否可重试、是否需要回退旧数据。

```typescript
type StoreError = {
  message: string;
  retryable: boolean;
};
```

Zustand 适合管理客户端状态和轻量异步流程；一旦需求变成“接口缓存系统”，就不应该硬把所有逻辑塞进 Store。

这条边界一旦超过，最容易出现的就是重复请求、缓存失效、旧数据覆盖新数据。那时把异步逻辑交给 Query 工具通常更省力。

错误对象最好结构化。只保存字符串会让组件无法判断是否可重试、是否需要登录、是否要回滚。

```ts
type StoreError = {
  message: string;
  type: "network" | "auth" | "business";
  retryable: boolean;
};
```

## 组件触发

组件触发异步 action 时，仍然要处理依赖变化和重复触发。

```tsx
function UserProfile({ userId }: { userId: string }) {
  const user = useUserStore((state) => state.user);
  const status = useUserStore((state) => state.status);
  const loadUser = useUserStore((state) => state.loadUser);

  useEffect(() => {
    loadUser(userId);
  }, [loadUser, userId]);

  if (status === "loading") return <Spinner />;
  if (status === "error") return <ErrorView onRetry={() => loadUser(userId)} />;

  return <ProfileCard user={user} />;
}
```

如果 `loadUser` 是从 Store 中稳定创建的 action，放入依赖数组通常不会造成重复请求。真正需要关注的是 `userId` 变化后旧请求是否会覆盖新请求。

所以异步状态管理不只是“发请求”，还包括“怎么处理请求之间的先后关系”。如果这一点不处理好，页面会时不时显示旧结果。

组件触发异步 action 时，还要考虑卸载和参数变化。Zustand action 本身不会因为组件卸载自动取消请求，所以请求是否取消、结果是否仍可写入，需要在 Store 或调用方设计。

## 竞态控制

多次请求同一资源时，可以在 Store 中记录当前请求编号，只接受最新结果。

```typescript
export const useSearchStore = create((set, get) => ({
  keyword: "",
  results: [],
  requestId: 0,
  status: "idle",
  search: async (keyword: string) => {
    const requestId = get().requestId + 1;

    set({ keyword, requestId, status: "loading" });

    const results = await searchApi.search(keyword);

    if (get().requestId === requestId) {
      set({ results, status: "success" });
    }
  },
}));
```

搜索、自动补全、路由快速切换都容易遇到旧请求晚返回的问题。只接受最新请求，是最常用也最容易理解的防线。

如果有取消能力，也可以在请求发起时同时记录 abort controller 或请求序号。核心目标都是避免旧结果覆盖新结果。

`AbortController` 适合浏览器 fetch，可以主动取消旧请求；requestId 适合任何 Promise，可以忽略过期结果。两者可以同时使用：取消减少网络和服务端压力，请求序号保证状态不会被旧结果覆盖。

## 旧数据保留

刷新数据时不一定要清空旧内容。很多页面可以保留旧数据，同时展示局部刷新状态。

```typescript
set({ isRefreshing: true });
```

首次加载、刷新、重试、提交中应该拆开表达，用户体验会更细。

如果旧数据要保留，最好把“刷新中”单独展示出来，而不是让用户看到整页空白。这样异步体验会更像渐进更新，而不是反复闪烁。

旧数据保留也要看风险。公开列表可以保留旧数据，权限、账号、支付状态这类高敏数据失败时不一定适合继续展示旧结果。体验和正确性要按业务分级。

## 与服务端状态工具

Zustand 可以发请求，但不等于应该用它管理所有服务端状态。

| 需求 | Zustand | TanStack Query / RTK Query |
| --- | --- | --- |
| 简单提交动作 | 合适 | 也可以 |
| 接口缓存复用 | 需要手写 | 内置 |
| 分页与参数缓存 | 需要手写 | 内置 |
| 自动重试与失效 | 需要手写 | 内置 |
| 客户端业务状态 | 合适 | 不适合替代 |

边界可以这样划：数据如果主要来自服务端，并且需要缓存、刷新、失效、轮询，就交给服务端状态工具；数据如果主要由前端交互产生，并且只是偶尔同步接口，就可以留在 Zustand。

也就是说，Zustand 负责“客户端自己生成和维护的状态”，Query 工具负责“服务端来的数据生命周期”。这个分工清楚后，异步部分就不会混成一锅粥。

一种常见组合是：Zustand 保存筛选草稿、当前选中项、编辑器状态；TanStack Query 或 RTK Query 根据提交后的查询参数拉取服务端数据。这样客户端交互和服务端缓存各归各位。
