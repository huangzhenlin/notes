## 请求生命周期

异步状态通常至少要表达四个阶段：未请求、请求中、成功、失败。

这四个阶段不是为了写得完整，而是为了让 UI 能明确知道自己处在什么时刻。请求还没发、正在发、已经成功、已经失败，对应的交互和提示都不同。

```javascript
const initialState = {
  status: "idle",
  data: null,
  error: null,
};
```

只存一个 `data` 往往不够，因为界面还需要知道是否正在加载、是否可以重试、是否应该展示错误提示。

如果只靠 `data === null` 判断状态，很容易混淆“还没请求”“请求失败”“请求成功但为空”这几种情况。状态字段越清楚，组件分支越稳定。

请求状态最好和业务数据分开表达。`data` 是服务端返回的内容，`status` 是请求过程，`error` 是失败原因。三者相关，但职责不同。只要混在一起，UI 分支就会靠猜。

## 成功失败分支

请求成功和失败不是两个简单布尔值，而是两条不同的 UI 路径。

```javascript
if (status === "loading") return <Spinner />;
if (status === "failed") return <ErrorState />;
if (!data) return <EmptyState />;
```

如果成功和失败逻辑被写成同一个分支，后续很容易把错误展示、重试按钮和空状态混在一起。

空状态和错误状态尤其要分开。空状态表示请求成功但没有数据，错误状态表示请求没有得到可信结果，用户下一步动作完全不同。

成功分支里也要区分“有数据”和“空数据”。空列表不是错误，通常应该给用户下一步建议，例如调整筛选、新建内容或清空搜索条件。

## 取消与竞态

异步请求经常会遇到竞态：新请求还没回来，旧请求先返回并覆盖了新结果。

```javascript
let requestId = 0;

async function load() {
  const currentId = ++requestId;
  const data = await fetchData();
  if (currentId === requestId) {
    dispatch(setData(data));
  }
}
```

取消、忽略旧请求、只接受最新结果，是异步状态管理里非常常见的防线。

Redux Toolkit 的 `createAsyncThunk` 会为每次请求生成 `requestId`，也支持通过 `signal` 处理取消。复杂搜索和分页场景，可以利用这些元信息避免旧请求覆盖新请求。

```ts
export const searchUsers = createAsyncThunk(
  "users/search",
  async (keyword: string, { signal }) => {
    const response = await fetch(`/api/users?q=${keyword}`, { signal });
    return response.json();
  },
);
```

## createAsyncThunk 示例

Redux Toolkit 常用 `createAsyncThunk` 描述一次异步请求，再在 slice 中处理 `pending`、`fulfilled`、`rejected` 三个阶段。

```ts
import { createAsyncThunk, createSlice } from "@reduxjs/toolkit";

export const fetchUser = createAsyncThunk(
  "user/fetchUser",
  async (userId: string, { rejectWithValue }) => {
    const response = await fetch(`/api/users/${userId}`);

    if (!response.ok) {
      return rejectWithValue({ message: "用户加载失败" });
    }

    return response.json();
  },
);

const userSlice = createSlice({
  name: "user",
  initialState: {
    entity: null,
    status: "idle",
    error: null,
  },
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchUser.pending, (state) => {
        state.status = "loading";
        state.error = null;
      })
      .addCase(fetchUser.fulfilled, (state, action) => {
        state.status = "success";
        state.entity = action.payload;
      })
      .addCase(fetchUser.rejected, (state, action) => {
        state.status = "error";
        state.error = action.payload ?? action.error;
      });
  },
});
```

这类写法的重点不是把请求“塞进 Redux”，而是把请求生命周期变成可观察、可复现、可测试的状态变化。组件只负责派发 `fetchUser(id)` 与根据 `status` 渲染界面。

`pending`、`fulfilled`、`rejected` 三个阶段天然对应请求流转。这样你在 DevTools 里看到的不只是最终数据，而是一次异步过程完整发生了什么。

处理 `rejected` 时要区分 `rejectWithValue` 和真实异常。前者适合服务端返回的业务错误，后者更像网络错误、代码异常或未知失败。状态里最好保留足够信息，让 UI 能决定展示字段错误、全局错误还是重试入口。

## 错误类型

异步失败不只是一种错误。把错误类型区分清楚，界面和重试策略会更稳定。

| 类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 网络错误 | 断网、超时 | 提供重试入口 |
| 鉴权错误 | 401、登录过期 | 跳转登录或刷新凭证 |
| 权限错误 | 403、无访问权限 | 展示无权限说明 |
| 业务错误 | 库存不足、状态不允许 | 展示业务提示，不一定重试 |
| 校验错误 | 表单字段不合法 | 回填字段级错误 |

如果所有错误都只保存成 `"请求失败"`，组件就无法判断该展示“重新加载”、 “重新登录”还是“修改表单后再提交”。

错误建模越粗，界面越只能给通用提示。业务越复杂，越应该把错误类型、是否可重试、是否需要登录、是否要回滚旧数据这些信息保存清楚。

可以把错误建模成结构化对象，而不是简单字符串。

```ts
type RequestError = {
  type: "network" | "unauthorized" | "forbidden" | "validation" | "business";
  message: string;
  retryable: boolean;
};
```

这样组件不需要靠匹配文案判断下一步动作。

## 重试与刷新

重试不应该绕过 Redux 状态流。组件可以复用同一个 thunk，并根据当前状态控制按钮文案与禁用逻辑。

```tsx
function UserPanel({ userId }: { userId: string }) {
  const dispatch = useAppDispatch();
  const { entity, status, error } = useAppSelector((state) => state.user);

  useEffect(() => {
    dispatch(fetchUser(userId));
  }, [dispatch, userId]);

  if (status === "loading") return <Spinner />;

  if (status === "error") {
    return (
      <ErrorView
        error={error}
        onRetry={() => dispatch(fetchUser(userId))}
      />
    );
  }

  return <UserProfile user={entity} />;
}
```

自动重试要谨慎：适合网络抖动，不适合权限错误或业务错误。通常可以把“是否可重试”作为错误对象的一部分，而不是让组件猜测。

如果请求会修改服务端状态，比如提交订单、支付、领取权益，重试还要配合幂等键。否则一次用户动作可能被重复执行，状态管理再清楚也兜不住业务风险。

异步状态还要和缓存失效连接。创建、修改、删除成功后，相关列表和详情应该刷新或失效。只更新当前 slice 的 `status`，但不处理服务端状态缓存，页面仍可能展示旧数据。

```text
提交成功
  -> mutation 状态 success
  -> 失效列表缓存
  -> 刷新详情或跳转
```
