## 中间件链路

Redux middleware 位于 dispatch 和 reducer 之间。它可以拦截 action、读取当前 state、派发新 action、记录日志、处理异步、上报错误或阻止某些 action 继续向下传递。

```ts
const logger = (store) => (next) => (action) => {
  console.log("before", store.getState());
  const result = next(action);
  console.log("after", store.getState());
  return result;
};
```

Reducer 必须保持纯净，不应该请求接口、读写存储、操作路由或上报埋点。副作用应该放在 middleware、thunk、listener、组件事件或独立数据层里。

中间件的能力来自它能看到 action 进入 reducer 前后的过程。它可以在 action 到达 reducer 前记录日志、改写、拦截，也可以在 reducer 更新后继续派发其他 action。越靠近 dispatch 的逻辑，越要保持可解释，否则数据流会变得隐式。

这也是为什么 Redux 中间件既强大又需要克制。它处在状态流的关键位置，很适合承接横切逻辑；但一旦每个业务都想在这里“顺手处理一下”，最后 dispatch 链路就会越来越难读懂。

## Thunk 模型

Thunk 允许 action creator 返回函数，而不是普通 action。这个函数可以执行异步逻辑，并在不同阶段 dispatch 普通 action。

```ts
export const loadUser =
  (userId: string) => async (dispatch, getState) => {
    const state = getState();
    if (state.users.entities[userId]) return;

    dispatch(userLoading(userId));

    try {
      const user = await api.getUser(userId);
      dispatch(userLoaded(user));
    } catch (error) {
      dispatch(userLoadFailed({ userId, error }));
    }
  };
```

Thunk 适合简单请求、条件判断和少量流程编排。它的优点是直观，缺点是当缓存、去重、重试、失效、并发控制变多时，手写 thunk 会越来越散。

Thunk 最适合表达“一次用户意图触发一段流程”。比如保存表单、登录、提交订单前校验、根据当前 state 决定是否请求。它能读取 `getState`，但不要让 thunk 到处读取状态树细节，否则它会变成另一个耦合点。

好的 thunk 通常有一个比较清晰的开始和结束：因为什么动作触发、过程中会派发哪些 action、失败后如何收尾。只要一个 thunk 已经开始同时处理缓存、重试、并发、轮询、订阅和跨模块联动，就说明职责有点过重了。

## createAsyncThunk

Redux Toolkit 的 `createAsyncThunk` 用于规范异步请求的生命周期。它会生成 pending、fulfilled、rejected 三类 action，适合把请求状态写进 slice。

```ts
export const fetchUserById = createAsyncThunk(
  "users/fetchById",
  async (userId: string) => {
    return api.getUser(userId);
  },
);
```

```ts
const usersSlice = createSlice({
  name: "users",
  initialState,
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchUserById.pending, (state) => {
        state.status = "loading";
      })
      .addCase(fetchUserById.fulfilled, (state, action) => {
        state.status = "succeeded";
        state.entities[action.payload.id] = action.payload;
      })
      .addCase(fetchUserById.rejected, (state) => {
        state.status = "failed";
      });
  },
});
```

它适合“请求结果要进入 Redux 状态”的场景。如果只是点击后调用接口再跳转，不一定需要把所有中间状态都放进 Store。

`createAsyncThunk` 生成的 action 会带有 `meta`，包括参数、requestId 和请求状态。排查竞态时，`meta.requestId` 很有价值，可以判断当前返回是否还对应最新请求。

它的另一个好处是把异步生命周期标准化。团队里不同人写的请求逻辑，只要都通过 pending、fulfilled、rejected 进入状态层，页面处理加载、成功和失败就会更一致，不容易每个模块一套风格。

## 条件与取消

异步 action 要处理重复请求和过期结果。`createAsyncThunk` 支持 `condition`，可以在发起前根据当前状态决定是否跳过。

```ts
export const fetchUserOnce = createAsyncThunk(
  "users/fetchOnce",
  async (userId: string) => api.getUser(userId),
  {
    condition: (userId, { getState }) => {
      const state = getState() as RootState;
      return !state.users.entities[userId];
    },
  },
);
```

请求取消、并发覆盖、旧结果回写都是异步状态常见坑。用户快速切换页面或筛选条件时，旧请求返回后不应该覆盖新结果。复杂服务端状态更适合交给 RTK Query、TanStack Query 这类工具管理。

`condition` 适合请求前跳过重复任务，`AbortSignal` 适合请求中取消任务，requestId 适合请求后忽略过期结果。三者解决的是不同阶段的问题，不要混为一谈。

把这三者拆开理解很重要。很多异步 bug 表面看都是“结果不对”，但真正根因可能分别发生在发起前、进行中或返回后。阶段分清以后，处理策略也会自然很多。

## Listener Middleware

Listener middleware 适合表达“当某个 action 发生后，再做另一件事”。它比在组件里到处写副作用更集中，也比把流程塞进 reducer 更符合 Redux 边界。

```ts
import { createListenerMiddleware } from "@reduxjs/toolkit";

const listenerMiddleware = createListenerMiddleware();

listenerMiddleware.startListening({
  actionCreator: userLoggedIn,
  effect: async (action, listenerApi) => {
    await listenerApi.dispatch(fetchUserProfile(action.payload.userId));
    track("login_success");
  },
});
```

它适合埋点、同步本地存储、联动刷新、WebSocket 消息处理、路由相关副作用。不要把所有业务流程都迁进 listener，否则会变成另一种隐式事件总线。

Listener middleware 的优势是“响应 action”。比如登录成功后加载权限、登出后清空缓存、订单提交成功后跳转或上报。它比在多个组件里重复写 effect 更集中，但也要避免链式监听过深。

如果多个 listener 开始相互依赖、互相派发、形成长链，就要小心它正在演化成隐式流程引擎。listener 适合承接清晰的“某动作发生后做某件事”，不适合替代整个业务编排层。

## RTK Query

如果主要问题是服务端数据获取、缓存、去重、失效、重试和加载状态，RTK Query 通常比手写 thunk 更合适。它把 API 声明、缓存 key、请求状态和数据订阅整合起来。

```ts
export const apiSlice = createApi({
  reducerPath: "api",
  baseQuery: fetchBaseQuery({ baseUrl: "/api" }),
  endpoints: (builder) => ({
    getUser: builder.query<User, string>({
      query: (id) => `/users/${id}`,
    }),
  }),
});
```

Thunk 更像“我来编排一段流程”，RTK Query 更像“我声明服务端资源如何读取和缓存”。选择时要看问题类型，而不是把所有异步都塞进同一种方案。

如果一个接口数据会被多个组件读取、需要保留旧数据、需要自动刷新和失效，就优先考虑 RTK Query。手写 thunk 可以做到这些，但代码会逐渐变成自制查询缓存系统。

这也是 Redux 现代实践里很重要的分工：客户端业务流程继续用 thunk 或 listener，服务端资源缓存优先交给 RTK Query。把两类问题拆开，异步层通常会清爽很多。

## 错误处理

异步错误要区分用户可恢复错误、权限错误、网络错误、服务端错误和代码异常。Store 中不要直接保存不可序列化 Error 对象，最好保存可展示、可判断的错误结构。

```ts
type RequestError = {
  code: string;
  message: string;
  retryable: boolean;
};
```

错误处理也不应该完全分散在组件里。接口层负责规范错误，异步 action 负责转换状态，组件负责展示和重试入口。这样错误语义能在项目里保持一致。

中间件还适合做全局错误上报，但不要让它吞掉业务错误。业务错误需要进入状态，让页面能展示；技术异常可以上报监控；权限错误可能还要触发登出或跳转。不同错误有不同去向。

错误一旦没有分层，页面层就很容易只剩一句“请求失败”。真正可维护的异步系统，通常会把“用户能否恢复”“是否需要重试”“是否需要跳登录”“是否只需记录监控”这些分支提前区分开。

## 选择边界

Redux 异步方案可以按复杂度选择。简单按钮请求可以放组件事件；请求结果需要进入 Store 可以用 thunk 或 `createAsyncThunk`；服务端缓存用 RTK Query；横切副作用用 listener middleware；日志和调试用普通 middleware。

```text
组件事件：局部一次性动作
createAsyncThunk：请求生命周期进入 Store
RTK Query：服务端状态和缓存
Listener Middleware：action 驱动副作用
Middleware：日志、监控、拦截
```

这和 [[3.1.8 服务端状态|服务端状态]] 的边界直接相关：服务端数据不是普通客户端状态，缓存、失效、并发和重试都需要专门模型。Redux 工具链提供了多个层次，关键是把副作用放到合适位置。

判断异步逻辑放哪里，可以问：它是否只属于当前组件，是否需要写入 store，是否是服务端资源缓存，是否响应某个 action，是否是横切日志监控。答案不同，落点就不同。把所有异步都放进 thunk，和把所有状态都放进 store 一样，短期统一，长期变重。

最终目标不是把所有异步都统一进一个工具，而是让每种异步都待在最合适的位置。局部动作放组件，流程型动作放 thunk，资源型缓存放 RTK Query，横切副作用放 listener 或 middleware。边界一清楚，Redux 异步链路就会好维护得多。
