## API Slice

RTK Query 把一组接口相关的查询和变更集中在一个 API Slice 里管理。它的目标不是再写一层普通请求封装，而是把请求缓存、失效、自动重试和状态派生统一起来。

```javascript
const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: "/api" }),
  endpoints: (builder) => ({
    getPosts: builder.query({
      query: () => "/posts",
    }),
  }),
});
```

## 请求缓存

RTK Query 会按查询键缓存请求结果，同一组参数的请求可以复用缓存，减少重复网络开销。

缓存不是永久有效。RTK Query 会根据订阅情况、缓存生命周期和失效规则决定数据何时保留、何时重新获取。

API Slice 通常按后端服务域或业务资源组织。一个大型项目可以有多个 API Slice，但不要为每个接口都建一个 slice。过度拆分会让 middleware、reducerPath 和 tag 管理变复杂。

## 缓存失效

当某个变更发生后，相关缓存需要被标记失效，随后自动重新获取。

```javascript
invalidatesTags: ["Posts"];
```

这让“数据变了，哪些页面要跟着更新”变得显式。

缓存失效是 RTK Query 的核心价值。写操作成功后，不需要组件手动找到所有列表和详情刷新，而是通过 tag 让相关查询自动失效。这样数据依赖关系集中在 API 定义里。

## Query 与 Mutation

RTK Query 把服务端状态的读取、缓存、请求状态和失效规则放在一个 API slice 中。Query 用来读取，Mutation 用来修改。

```ts
import { createApi, fetchBaseQuery } from "@reduxjs/toolkit/query/react";

type Post = {
  id: string;
  title: string;
  content: string;
};

export const postsApi = createApi({
  reducerPath: "postsApi",
  baseQuery: fetchBaseQuery({ baseUrl: "/api" }),
  tagTypes: ["Post"],
  endpoints: (builder) => ({
    getPosts: builder.query<Post[], void>({
      query: () => "/posts",
      providesTags: ["Post"],
    }),
    addPost: builder.mutation<Post, Pick<Post, "title" | "content">>({
      query: (body) => ({
        url: "/posts",
        method: "POST",
        body,
      }),
      invalidatesTags: ["Post"],
    }),
  }),
});

export const { useGetPostsQuery, useAddPostMutation } = postsApi;
```

读取接口写成 Query，修改接口写成 Mutation，缓存语义才清楚。Query 会根据参数建立缓存条目；Mutation 通常通过 tag 让相关 Query 失效。

Query 不应该承担状态变更语义，Mutation 也不应该被当成普通查询使用。语义清楚后，缓存、重试、loading 状态和失效规则都会更自然。

## 组件调用

组件使用自动生成的 hooks，不需要自己维护 `loading`、`error`、`data` 三件套。

```tsx
function PostList() {
  const { data = [], isLoading, isError, refetch } = useGetPostsQuery();
  const [addPost, addPostState] = useAddPostMutation();

  if (isLoading) return <Spinner />;
  if (isError) return <ErrorView onRetry={refetch} />;

  return (
    <>
      <button
        disabled={addPostState.isLoading}
        onClick={() => addPost({ title: "新文章", content: "正文内容" })}
      >
        新建文章
      </button>

      {data.map((post) => (
        <article key={post.id}>
          <h2>{post.title}</h2>
          <p>{post.content}</p>
        </article>
      ))}
    </>
  );
}
```

这里的组件只表达订阅数据和触发提交。请求去重、缓存复用、请求状态和刷新入口交给 RTK Query 管。

RTK Query hooks 返回的状态比 `loading/error/data` 更细，例如 `isLoading`、`isFetching`、`isSuccess`、`isError`。首次加载和后台刷新应该区别展示，避免每次刷新都把页面打回骨架屏。

## 缓存标签

粗粒度 tag 适合入门，细粒度 tag 适合减少不必要的刷新。

```ts
getPost: builder.query<Post, string>({
  query: (id) => `/posts/${id}`,
  providesTags: (result, error, id) => [{ type: "Post", id }],
}),
updatePost: builder.mutation<Post, Partial<Post> & { id: string }>({
  query: ({ id, ...patch }) => ({
    url: `/posts/${id}`,
    method: "PATCH",
    body: patch,
  }),
  invalidatesTags: (result, error, arg) => [{ type: "Post", id: arg.id }],
}),
```

列表页通常提供列表 tag，详情页提供实体 tag。创建或删除会影响列表，更新单个实体优先让对应详情失效，必要时再让列表失效。

tag 可以设计成“列表 tag + 实体 tag”的组合。列表查询提供 `Post/LIST` 和每个实体 id，创建删除失效列表，更新实体失效对应 id。这样能减少不必要刷新。

```ts
providesTags: (result) =>
  result
    ? [
        { type: "Post", id: "LIST" },
        ...result.map((post) => ({ type: "Post" as const, id: post.id })),
      ]
    : [{ type: "Post", id: "LIST" }]
```

## 查询参数

Query 的参数会参与缓存 key。筛选、分页、排序条件应该显式放进参数中，而不是藏在组件闭包里。

```ts
getProducts: builder.query<
  Product[],
  { keyword: string; page: number; category?: string }
>({
  query: ({ keyword, page, category }) => ({
    url: "/products",
    params: { keyword, page, category },
  }),
});
```

如果两个组件传入相同参数，它们可以共享缓存；如果参数不同，它们应该拥有不同缓存。这个规则比手写请求缓存更稳定，也更容易调试。

参数对象要保持语义稳定。`{ page: 1, keyword: "" }` 和 `{ keyword: "", page: 1 }` 在序列化策略下通常能处理，但团队仍应统一默认值和字段命名，避免同一查询条件出现多种表达。

## 使用边界

RTK Query 适合管理服务端状态，不适合替代本地 UI 状态。弹窗开关、表单输入、临时筛选条件仍然应由组件状态、普通 slice 或表单库管理。

| 状态 | 更合适的位置 | 原因 |
| --- | --- | --- |
| 文章列表接口结果 | RTK Query | 来自服务端，需要缓存、刷新和失效 |
| 弹窗是否打开 | 组件状态 | 生命周期局部，没必要进入全局 store |
| 搜索框输入中内容 | 组件状态 | 高频变化，提交后才变成查询参数 |
| 当前登录用户资料 | RTK Query 或普通 slice | 取决于是否需要缓存失效和跨页复用 |
| 购物车草稿 | 普通 slice | 更偏客户端业务状态 |

RTK Query 不适合管理纯客户端状态，也不适合承载复杂领域事务。比如结算流程里的步骤、优惠券输入草稿、弹窗状态更适合普通 slice 或组件状态；订单提交接口和订单详情缓存才适合 RTK Query。

如果项目已经有 RTK Query，就不要再把同一份服务端列表复制到普通 slice 里。普通 slice 可以保存 UI 选择、筛选草稿、当前编辑 id，接口结果仍由 RTK Query 管理。
