## Action 追踪

Redux DevTools 最实用的能力之一，是可以看到每次 Action 的名称、参数和触发顺序。

这意味着你不必只靠 `console.log` 去猜状态为什么变了，而是可以直接看动作链路。

```text
user/loginStarted -> user/loginSucceeded -> permissions/loaded
```

这种链路特别适合排查“页面为什么进入了某个状态”。

Action 轨迹越接近业务语言，DevTools 越像一份可回放的操作日志。它能把“用户做了什么”和“状态怎么变”连起来。

使用 DevTools 时，不要只看最后一个 action。复杂 bug 往往来自前面某个 action 把状态改到临界值，后续 action 只是把问题暴露出来。沿着时间线找第一个异常 diff，定位会快很多。

这也是为什么 Redux 调试往往比单纯看组件日志更高效。组件日志看到的是某个时刻的局部结果，而 DevTools 能把动作顺序、状态差异和业务事件连成一条完整链路，特别适合排查“到底是哪一步开始偏了”。

## 状态快照

每次状态变化都能形成快照，方便对比前后差异。  
状态树一旦变复杂，快照比肉眼扫代码更能快速定位变化点。

快照能帮助你判断是 Action 参数错了，还是 Reducer 处理错了。

```text
before: user.profile = null
after:  user.profile = { id: 1, name: "Ada" }
```

快照对比适合检查“这个字段到底在哪次更新里变了”，尤其适合排查权限、表单和多步骤流程。

当状态树很大时，快照差异比打印整个对象有用得多。它能让你快速确认是哪个 action 改动了哪个字段。

快照差异还能帮助判断是否有无关更新。如果点击一个筛选按钮，却看到用户权限、购物车、主题都发生变化，说明 reducer 或重置逻辑可能影响过大。

很多性能问题也能从快照里看出端倪。如果一次很小的交互总是带来大面积状态变化，组件层即使订阅正确，也很可能因为上游状态更新范围过大而产生不必要的重渲染。

## 时间旅行

时间旅行调试允许你在过去的状态之间回退和前进。  
它的价值不是“好玩”，而是能让复杂交互的状态转移变得可回放、可验证。

如果回退到某个 Action 前状态正常，执行它后状态异常，问题范围就会被大幅缩小。

时间旅行最适合验证 reducer 是否纯、状态转移是否可重复。只要同一串 action 每次得到不同结果，就说明 reducer 或中间过程里混入了外部不确定性。

时间旅行对异步副作用有限制。它能回放 state 变化，但不会可靠地回放网络请求、localStorage 写入、路由跳转和埋点上报。所以副作用越分散，DevTools 越只能看到结果，看不到真实原因。

因此 DevTools 最擅长回答的是“状态为什么变成这样”，而不是“外部世界为什么这么做”。网络、存储、路由和埋点这些副作用仍然要结合请求日志、浏览器面板或服务端日志一起看。

## 调试边界

DevTools 能告诉你状态如何变化，但不能替你判断业务规则是否正确。  
如果 Action 命名混乱、状态结构不清晰、Reducer 同时做太多事，调试工具只能暴露问题，不能自动解决问题。

DevTools 是放大镜，不是整理器。它会把状态流暴露得更清楚，但如果状态设计本身混乱，看到的也只是一条更清楚的混乱链路。

换句话说，DevTools 的上限取决于状态设计质量。action 命名清楚、reducer 职责单一、selector 结构稳定时，工具会非常强；如果所有东西都揉在一起，工具也只能帮你更快看见混乱。

## Action 命名

Redux DevTools 的时间线本质上是一份业务行为日志。Action 名称越接近业务事件，排查问题时越容易直接读懂流程。

```txt
cart/itemAdded
cart/itemQuantityChanged
checkout/paymentSubmitted
checkout/submitRejected
user/sessionExpired
```

如果时间线里都是 `setData`、`update`、`change`，就必须反复展开 payload 才知道发生了什么。更清晰的命名会让 action type 自带上下文。

好的命名应该说明领域和动作，比如 `cart/itemAdded` 比 `add` 清楚，`checkout/submitRejected` 比 `error` 清楚。调试时少猜一个词，定位就快一截。

命名还应避免过度技术化。`modal/setOpen` 也许能表达状态变化，但 `checkout/addressDialogOpened` 更能表达业务上下文。越关键的业务流程，action 越应该像业务事件。

命名稳定后，团队成员在 review、联调和线上排障时也能更快对齐上下文。DevTools 看到的不只是技术细节，更像是一份带业务语义的操作轨迹。

## 状态差异

DevTools 可以查看 action 前后的 state 差异。定位问题时先确认状态是否已经正确更新，再决定继续看 selector、组件渲染还是接口数据。

```txt
cart/itemQuantityChanged
before: items.p1.quantity = 1
after:  items.p1.quantity = 3
```

如果 action 后 state 已经正确，但页面显示不对，下一步看 selector 或组件订阅；如果 state 已经错误，就回到 reducer、middleware 或接口返回值。

这个分流很重要。状态正确但 UI 不对，是读取和渲染问题；状态本身就错，是更新链路问题。不要混在一起排查。

排查顺序可以固定为：action payload 是否正确，reducer diff 是否正确，selector 输出是否正确，组件是否订阅正确。这个顺序能避免一开始就在 UI 层乱改。

这套顺序一旦固定下来，很多问题会明显更容易分层。payload 错了看事件和请求层，diff 错了看 reducer，selector 错了看派生逻辑，UI 错了看组件订阅和渲染。不要跳着查，否则容易在错误层里做无效修改。

## 复现路径

复杂问题可以先在 DevTools 中整理出最短 action 序列，再把它变成测试用例。

```txt
user/loginFulfilled
cart/itemAdded
cart/itemQuantityChanged
checkout/couponApplied
checkout/submitRejected
```

这条序列比“我点了很多次然后页面错了”更容易复现。对于偶发问题，可以比较成功路径和失败路径的 state diff，先找第一个产生分歧的 action。

一旦找到最短 action 序列，就可以把它沉淀成 reducer 或 store 测试。这样下次重构时，DevTools 里的经验就变成了自动化保护。

对于线上偶发问题，如果有能力记录脱敏后的 action 序列和关键 state diff，也可以大幅降低复现成本。但要严格过滤敏感字段，不能把用户隐私和 token 一起上传。

这也是 DevTools 最大的工程价值之一：它不只是临时排障工具，还能帮你把“偶发问题的复现路径”提炼成稳定测试。只要一个问题能被压缩成一串 action，它通常就已经接近可自动化验证了。

## 时间旅行前提

时间旅行依赖 reducer 的可预测性。Reducer 如果读取当前时间、随机数、localStorage 或外部可变对象，回到历史 action 时就不一定能得到同样结果。

```ts
const slice = createSlice({
  name: "order",
  initialState,
  reducers: {
    orderSubmitted(state) {
      state.submittedAt = Date.now();
    },
  },
});
```

上面这类写法应该改成由 action payload 传入时间，时间的产生放在组件事件、thunk 或中间件中。

```ts
dispatch(orderSubmitted({ submittedAt: Date.now() }));
```

这样 reducer 只处理确定输入，DevTools 的回放、测试和日志复现都会更可靠。

同理，随机数、当前用户环境、localStorage 读取都应该在 action 创建阶段或 thunk 里完成，再把结果作为 payload 传给 reducer。Reducer 越纯，工具越有用。

如果必须在 reducer 中记录时间，也应该由 action payload 传入。这样测试可以固定时间，DevTools 回放也能得到一致结果。

时间旅行是否可靠，本质上取决于状态变化是否可重演。只要 reducer 依赖了环境变量、系统时间、随机数或外部可变对象，回放价值就会明显下降。所以让 reducer 保持纯，既是在保护架构，也是在保护调试能力。

## 敏感数据

不要因为 DevTools 好用，就把 token、密码、完整身份证号等敏感信息放进 Redux。开发期插件、日志上报和错误快照都可能接触 store。

更稳妥的做法是只保存必要的非敏感状态，例如 `isAuthenticated`、`userId`、权限列表或脱敏后的用户资料。真正的凭证应交给更合适的安全存储与请求层处理。

如果状态快照需要上传到监控平台，还要额外做脱敏和字段过滤。DevTools 带来的可见性很强，越强就越不能忽视数据边界。

开发环境也要注意团队共享屏幕、录屏和日志导出。Redux store 往往包含用户资料、权限、业务数据和请求结果，任何调试工具都可能扩大可见面。状态设计时少放敏感信息，调试时再做脱敏，会比事后清理更安全。

如果团队会把调试截图、录屏或状态快照发到群里排查问题，这条边界就更重要。DevTools 越强，信息暴露面越广；状态里放的东西越克制，后续协作和排障就越安全。
