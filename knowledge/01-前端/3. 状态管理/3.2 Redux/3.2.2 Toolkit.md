## createSlice

`createSlice` 会把状态片段、Reducer 和 Action 创建逻辑放在一起，减少样板代码。

```javascript
import { createSlice } from "@reduxjs/toolkit";

const counterSlice = createSlice({
  name: "counter",
  initialState: { value: 0 },
  reducers: {
    increment(state) {
      state.value += 1;
    },
  },
});
```

它让“写 Redux 很啰嗦”这类老问题明显缓解，但本质上仍然遵循 Redux 的状态流和纯函数约束。

`createSlice` 会根据 `name` 和 reducers 自动生成 action type 和 action creator。这样 action 命名、reducer 逻辑和导出方法天然放在一起，减少手写字符串出错。

```ts
export const { increment } = counterSlice.actions;
export default counterSlice.reducer;
```

## 配置 Store

`configureStore` 用来创建 Store，并默认帮你接上常见中间件、DevTools 和更合理的默认配置。

```javascript
import { configureStore } from "@reduxjs/toolkit";

const store = configureStore({
  reducer: {
    counter: counterSlice.reducer,
  },
});
```

在现代 Redux 项目里，`configureStore` 基本是首选。

`configureStore` 还会默认组合 reducer、添加 thunk、启用开发期检查和 Redux DevTools。相比手写 `createStore`，它更接近官方推荐的生产默认配置。

## 异步辅助

Redux Toolkit 提供了一些异步相关辅助能力，例如 `createAsyncThunk`，方便把请求流程拆成 pending、fulfilled、rejected。

```javascript
import { createAsyncThunk } from "@reduxjs/toolkit";

export const fetchUser = createAsyncThunk("user/fetch", async (id) => {
  const res = await fetch(`/api/users/${id}`);
  return res.json();
});
```

异步逻辑可以放进 thunk，但真正的请求状态、缓存和失效，如果越来越复杂，通常更适合交给 RTK Query。

`createAsyncThunk` 适合“一个动作触发一次请求，并把生命周期写进 slice”。如果请求需要缓存 key、自动重试、数据失效、多个组件共享同一请求结果，RTK Query 往往更合适。
## Slice 文件组织

Redux Toolkit 的核心价值是把“状态形状、同步修改、异步生命周期、导出 action”集中到一个业务域里。一个 slice 通常围绕业务概念组织，而不是围绕页面组织。

```txt
features/
  cart/
    cartSlice.ts
    cartSelectors.ts
    cartApi.ts
  user/
    userSlice.ts
    userSelectors.ts
  checkout/
    checkoutSlice.ts
```

页面可以组合多个业务域，例如结算页会读取 `user`、`cart`、`checkout`。如果按页面切 slice，后续复用同一购物车状态时就容易出现重复建模。

业务域 slice 要避免过度庞大。一个 `appSlice` 里塞用户、购物车、订单、权限、弹窗，很快会变成小型数据库。按领域拆分后，action 命名、selector 和测试都会更清楚。

## Payload 类型

Action 的 payload 应该体现业务意图，而不是把一整块组件数据原样丢给 reducer。

```ts
import { createSlice, PayloadAction } from "@reduxjs/toolkit";

type CartState = {
  items: Record<string, { productId: string; quantity: number }>;
};

const cartSlice = createSlice({
  name: "cart",
  initialState: { items: {} } satisfies CartState,
  reducers: {
    itemQuantityChanged(
      state,
      action: PayloadAction<{ productId: string; quantity: number }>,
    ) {
      const item = state.items[action.payload.productId];

      if (item) {
        item.quantity = action.payload.quantity;
      }
    },
  },
});
```

`itemQuantityChanged` 比 `setCart` 更容易在 DevTools 中理解，也更容易测试。好的 action 像“发生了什么”，而不是“把状态改成什么”。

payload 也要保持最小充分。组件里完整的表单对象、DOM 事件、路由对象不应该直接丢进 reducer。Reducer 只需要完成状态变化所需的数据。

```ts
dispatch(itemQuantityChanged({ productId, quantity }));
```

这比传整个商品卡片 props 更稳定，也更符合序列化要求。

## Immer 写法

Toolkit 内部使用 Immer，因此 reducer 可以写成“直接修改”的样子，但实际仍然会生成不可变更新。

```ts
const todoSlice = createSlice({
  name: "todo",
  initialState: {
    items: [] as Array<{ id: string; title: string; done: boolean }>,
  },
  reducers: {
    todoToggled(state, action: PayloadAction<string>) {
      const todo = state.items.find((item) => item.id === action.payload);

      if (todo) {
        todo.done = !todo.done;
      }
    },
  },
});
```

这种写法减少了浅拷贝样板代码，但不要在 reducer 里做副作用。请求、时间、随机数、localStorage、埋点仍然应该放在 thunk、中间件或组件事件里。

Immer 草稿只能在 reducer 同步执行期间使用。不要把 `state` 或草稿对象保存到异步回调里，也不要在 reducer 中混用“修改草稿”和“返回新对象”两种风格。保持一种写法更容易读。

## extraReducers

`extraReducers` 用来响应 slice 外部定义的 action，最常见场景是处理 `createAsyncThunk` 产生的请求生命周期。

```ts
const userSlice = createSlice({
  name: "user",
  initialState: {
    entity: null,
    status: "idle",
  },
  reducers: {
    userCleared(state) {
      state.entity = null;
      state.status = "idle";
    },
  },
  extraReducers: (builder) => {
    builder
      .addCase(fetchUser.pending, (state) => {
        state.status = "loading";
      })
      .addCase(fetchUser.fulfilled, (state, action) => {
        state.status = "success";
        state.entity = action.payload;
      })
      .addCase(fetchUser.rejected, (state) => {
        state.status = "error";
      });
  },
});
```

同步业务动作放在 `reducers`，外部事件或异步生命周期放在 `extraReducers`。这样 slice 的主动行为和被动响应会更清楚。

`extraReducers` 也适合响应其他 slice 的 action，比如登出后清空购物车、切换组织后重置项目缓存。它让 slice 可以对外部业务事件做出反应，而不需要让其他 slice 直接修改自己。

```ts
builder.addCase(userLoggedOut, (state) => {
  state.items = {};
});
```

## Store 配置

`configureStore` 默认启用 thunk、开发期不可变检查、序列化检查和 Redux DevTools。大多数项目只需要补充 reducer 与少量中间件。

```ts
import { configureStore } from "@reduxjs/toolkit";
import { listenerMiddleware } from "./listenerMiddleware";
import { postsApi } from "./postsApi";

export const store = configureStore({
  reducer: {
    cart: cartReducer,
    user: userReducer,
    [postsApi.reducerPath]: postsApi.reducer,
  },
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware()
      .prepend(listenerMiddleware.middleware)
      .concat(postsApi.middleware),
});

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

只有在确认 payload 或 state 中确实存在非序列化对象，并且这件事无法调整建模时，才考虑关闭序列化检查。否则调试、持久化和时间旅行都会变得更难。

Store 配置还要导出类型化 hooks，避免组件里到处重复写 `RootState` 和 `AppDispatch`。

```ts
export const useAppDispatch = useDispatch.withTypes<AppDispatch>();
export const useAppSelector = useSelector.withTypes<RootState>();
```

类型化 hooks 能让 thunk dispatch、selector 返回值和组件读取更稳定，是 TypeScript Redux 项目的基础设施。
