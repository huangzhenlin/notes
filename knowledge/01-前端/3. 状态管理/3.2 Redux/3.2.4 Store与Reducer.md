## 状态树

Redux Store 通常是一棵由多个 slice 组成的状态树。每个 slice 负责一个业务域，而不是随意把所有字段平铺在一起。

```typescript
type RootState = {
  user: {
    profile: UserProfile | null;
    permissions: string[];
  };
  cart: {
    items: Record<string, CartItem>;
  };
  order: {
    currentId?: string;
  };
};
```

状态树越清晰，selector 越容易写，局部更新也越容易控制。组件不应该直接依赖整棵树的所有细节，而应该通过 selector 读取需要的部分。

状态树设计要围绕业务域，而不是组件树。组件树经常变，业务域相对稳定。比如购物车、用户、订单、权限可以长期存在；某个页面上的某个按钮状态通常不应该进入 Redux 状态树。

## Reducer 职责

Reducer 的职责是描述状态如何转移，而不是描述 UI 怎么更新。

```typescript
type CartState = {
  items: Array<{ id: string; count: number }>;
};

type CartAction =
  | { type: "cart/add"; payload: { id: string } }
  | { type: "cart/remove"; payload: { id: string } };

function cartReducer(state: CartState = { items: [] }, action: CartAction) {
  switch (action.type) {
    case "cart/add":
      return {
        ...state,
        items: [...state.items, { id: action.payload.id, count: 1 }],
      };
    case "cart/remove":
      return {
        ...state,
        items: state.items.filter((item) => item.id !== action.payload.id),
      };
    default:
      return state;
  }
}
```

Reducer 不关心按钮在哪里，也不关心接口怎么请求，它只关心“某个业务事件发生后，状态应该变成什么”。

Reducer 的输入 action 应该足够表达业务事件。比如 `orderSubmitted`、`itemRemoved`、`profileUpdated`，这些动作让 reducer 不需要知道事件来源，就能做状态转移。

## 纯函数约束

Reducer 必须是纯函数：同样的输入，永远得到同样的输出，不读取外部可变状态，不直接修改入参，不产生副作用。

| 行为 | 不应放在 reducer 的原因 |
| --- | --- |
| 发起请求 | 结果不可预测，无法同步返回新状态 |
| 读取当前时间 | 时间旅行和测试不稳定 |
| 生成随机数 | 回放 action 时结果不同 |
| 写 localStorage | 状态更新混入 IO |
| 修改外部变量 | 破坏可预测性 |

这些逻辑应放在 thunk、中间件、组件事件或服务层中。Reducer 保持纯粹，状态回放和单元测试才可靠。

纯函数约束也意味着 reducer 不能偷偷依赖当前用户、当前路由或本地缓存。需要这些信息时，把它们作为 action payload 传进来，或者在 thunk/action creator 中读取后再 dispatch。

## 不可变更新

传统 Redux reducer 需要返回新对象，不能直接修改旧 state。

```typescript
function cartReducer(state = initialState, action: CartAction) {
  switch (action.type) {
    case "cart/itemQuantityChanged":
      return {
        ...state,
        items: state.items.map((item) =>
          item.id === action.payload.id
            ? { ...item, quantity: action.payload.quantity }
            : item,
        ),
      };
    default:
      return state;
  }
}
```

Redux Toolkit 内部使用 Immer，因此 slice reducer 可以写成“直接修改”的样子，但原则仍然是不可变更新。

```typescript
itemQuantityChanged(state, action) {
  const item = state.items.find((item) => item.id === action.payload.id);

  if (item) {
    item.quantity = action.payload.quantity;
  }
}
```

这段代码看似修改 state，实际由 Immer 生成新状态。

不可变更新的目的不是形式主义，而是让 Redux 能通过引用变化判断状态是否更新，也让 DevTools 能记录每一步状态差异。直接修改旧对象会让订阅、selector 和调试都失去可靠基础。

## Reducer 组合

大型应用通常会把多个 reducer 组合成根 reducer。

```typescript
import { combineReducers } from "redux";

const rootReducer = combineReducers({
  user: userReducer,
  cart: cartReducer,
  order: orderReducer,
});
```

每个 reducer 只接收自己负责的 slice state。`userReducer` 不应该直接修改 `cart`，`cartReducer` 也不应该直接修改 `user`。跨域流程通过 action、thunk 或中间件编排。

跨 slice 协作时，优先通过共享 action 或 thunk 编排，而不是让 reducer 互相调用。比如登出后多个 slice 都需要清理，可以让它们都响应 `auth/loggedOut`。

## Store 订阅

Store 除了保存状态，还负责订阅和通知。

```typescript
const unsubscribe = store.subscribe(() => {
  console.log(store.getState());
});

store.dispatch({ type: "cart/add", payload: { id: "sku_1" } });
unsubscribe();
```

在 React 项目里，通常不直接手写订阅，而是通过 React Redux 的 hooks 把订阅和组件更新连接起来。

```tsx
const items = useAppSelector(selectCartItems);
```

订阅越粗，重渲染范围越大；selector 越精确，组件越容易保持稳定。

React Redux 的 `useSelector` 会根据 selector 返回值判断是否需要重新渲染。返回新对象、新数组时要特别注意，否则每次 store 更新都可能让组件重新渲染。

```tsx
const userName = useAppSelector((state) => state.user.profile?.name);
```

简单读取优先返回基础值；复杂组合再考虑 memoized selector。

## 状态重置

登出、切换租户、清空项目时，经常需要重置部分或全部状态。重置逻辑要显式设计。

```typescript
const appReducer = combineReducers({
  user: userReducer,
  cart: cartReducer,
});

export function rootReducer(
  state: ReturnType<typeof appReducer> | undefined,
  action: { type: string },
) {
  if (action.type === "auth/logoutFulfilled") {
    return appReducer(undefined, action);
  }

  return appReducer(state, action);
}
```

全量重置适合登出，局部重置适合清空购物车、关闭编辑器、切换项目。不要靠刷新页面来解决状态残留。

重置还要考虑持久化状态。如果 store 有部分字段写进 localStorage，登出时只重置内存不清理持久化，刷新后旧状态可能又回来。状态重置要覆盖内存、持久化和服务端缓存。

## 拆分边界

Reducer 拆分要按业务状态边界，而不是按页面文件边界。`user`、`cart`、`order` 是比较稳定的业务域；`HomePageReducer`、`ButtonReducer` 这类命名通常会让状态和 UI 耦合过深。

```text
更推荐：
features/cart/cartSlice.ts
features/user/userSlice.ts
features/order/orderSlice.ts

谨慎：
pages/Home/homeReducer.ts
components/Button/buttonReducer.ts
```

如果某段状态需要被多个页面复用，就更应该按业务域放进 Store；如果只服务一个组件局部交互，放进 Redux 反而会增加复杂度。

拆分边界可以用三个问题判断：这份状态的业务名称是什么，谁有权修改它，离开当前页面后是否还需要存在。如果说不清业务名称，通常不适合进 Redux；如果只在一个页面短暂存在，通常应留在页面或组件状态里。
