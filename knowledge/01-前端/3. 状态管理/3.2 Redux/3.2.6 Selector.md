## 状态读取

Selector 是从 Store 中读取所需状态的函数。它把组件和状态树结构隔开，让组件关心“需要什么数据”，而不是“数据存在 state 的哪条路径”。

```typescript
const selectCartItems = (state: RootState) => state.cart.items;
const selectCurrentUser = (state: RootState) => state.user.profile;
```

如果组件到处写 `state.cart.items`，Store 结构一调整就会影响大量组件。Selector 是状态结构变化时的缓冲层。

Selector 还能让组件更像“消费视图数据”，而不是直接依赖状态树内部结构。状态树可以为了更新效率而变化，组件不应该被这种内部变化反复牵动。

Selector 是 Redux 里非常重要的“读取边界”。写入通过 action/reducer 收口，读取通过 selector 收口。这样状态树内部可以重构，组件仍然面向稳定的业务视图。

很多 Redux 项目到后期难维护，不是因为 reducer 太多，而是因为组件已经把状态树路径写死在各个角落。selector 的真正价值，就是把“读什么”与“怎么存”分开，让状态树还能继续演进。

## 派生计算

当视图需要的数据不是原始状态，而是原始状态计算后的结果时，Selector 很适合承载派生逻辑。

```typescript
const selectCompletedTodos = (state: RootState) =>
  state.todos.items.filter((todo) => todo.done);
```

组件只关心“拿到已完成列表”，不关心过滤规则怎么写。这样多个组件复用同一规则时，结果也会保持一致。

派生逻辑集中以后，测试也更容易。你可以直接测试 selector 输入和输出，而不用通过 UI 间接验证过滤规则。

派生 selector 也能避免多个组件各自实现一套规则。比如“当前用户是否能编辑订单”这种权限判断，如果散在组件里，规则变更时很难保证一致。

```typescript
export const selectCanEditOrder = (state: RootState, orderId: string) => {
  const order = state.orders.entities[orderId];
  const permissions = state.user.permissions;

  return Boolean(order && permissions.includes("order:edit"));
};
```

派生逻辑一旦进入 selector，页面代码通常会明显变轻。组件只表达“我要显示什么”，至于“这个结果怎么算出来”，则由 selector 统一维护。规则越容易变，越值得收口到 selector。

## 实体结构

列表数据较多时，Store 中常用实体结构保存，Selector 再负责转成组件需要的数组或单项。

```typescript
type UsersState = {
  ids: string[];
  entities: Record<string, User>;
};

const selectUserEntities = (state: RootState) => state.users.entities;
const selectUserIds = (state: RootState) => state.users.ids;

const selectUsers = createSelector(
  [selectUserIds, selectUserEntities],
  (ids, entities) => ids.map((id) => entities[id]),
);
```

实体结构适合按 id 更新、删除和查找。组件如果需要数组，就让 selector 负责组装，避免组件知道内部存储细节。

这种写法对大型列表很有用。Store 内部按 id 管理可以降低更新成本，组件侧仍然拿到自己需要的数组或单项，不必知道内部是怎么存的。

Redux Toolkit 的 `createEntityAdapter` 可以帮助管理实体结构，减少手写 ids/entities 的样板。它适合大量按 id 增删改查的列表状态，但不是所有数组都必须实体化。小型静态列表直接数组更简单。

是否实体化可以看三个信号：是否频繁按 id 查找，是否经常局部更新单项，是否有多个页面共用同一批实体。三个信号都明显时，实体结构通常更划算；否则继续保持数组往往更直观。

## 参数化读取

参数化 selector 用于按 id、分类、路由参数读取数据。

```typescript
const selectUserById = (state: RootState, userId: string) =>
  state.users.entities[userId];

function UserCard({ userId }: { userId: string }) {
  const user = useSelector((state: RootState) =>
    selectUserById(state, userId),
  );

  if (!user) return null;

  return <span>{user.name}</span>;
}
```

参数化读取能避免组件先取全量列表再 `find`。如果多个组件都需要按 id 读取，selector 也能保持写法统一。

参数化 selector 还适合路由详情页。页面拿到 `id` 后直接通过 selector 读取对应实体，如果不存在再决定请求或展示缺省状态。

参数化 selector 要注意缓存行为。普通 selector 只有一个缓存槽时，不同参数轮流调用可能互相覆盖缓存；大量组件实例使用不同参数时，可以考虑 selector 工厂或更细粒度读取。

这类问题在列表页很常见。比如每个列表项都按自己的 id 读取统计结果，如果直接复用一个依赖参数的 memoized selector，缓存很容易被下一个组件实例顶掉。缓存策略和使用场景要一起看，不是只要 `createSelector` 就万事大吉。

## 记忆化

如果 selector 的计算成本较高，或者返回数组、对象这类引用值，可以使用 `createSelector` 记忆化结果。

```typescript
const selectVisibleTodos = createSelector(
  [
    (state: RootState) => state.todos.items,
    (state: RootState) => state.todos.filter,
  ],
  (items, filter) => items.filter((item) => item.status === filter),
);
```

只要输入 `items` 和 `filter` 没变，`selectVisibleTodos` 会返回上一次结果。这样组件不会因为每次读取都得到新数组而重渲染。

记忆化不是为了“所有 selector 都更高级”，而是为了解决引用稳定和昂贵计算。简单字段读取不需要 `createSelector`，否则只是增加样板。

只要 selector 每次返回新对象或新数组，使用它的组件就可能重新渲染。要么返回基础值，要么拆成多个 selector，要么用 `createSelector` 缓存派生结果。

```typescript
const selectUserView = createSelector([selectCurrentUser], (user) =>
  user ? { id: user.id, name: user.name } : null,
);
```

这类 selector 只有在输入 user 没变时才复用返回对象。

判断是否值得记忆化，可以先看两个问题：计算是否昂贵，返回引用是否会导致无意义重渲染。只要两个答案都不明显，普通 selector 往往就够用了。不要把记忆化当成默认姿势。

## Selector 工厂

当每个组件实例都需要独立缓存时，可以创建 selector 工厂。

```typescript
const makeSelectTodosByProject = () =>
  createSelector(
    [
      (state: RootState) => state.todos.items,
      (_state: RootState, projectId: string) => projectId,
    ],
    (items, projectId) =>
      items.filter((todo) => todo.projectId === projectId),
  );
```

它适合列表中多个组件实例同时按不同参数派生数据的场景。普通场景下先使用普通 selector，不要一开始就引入工厂函数。

如果一个 selector 依赖组件自己的 props，并且多个组件实例会同时使用不同参数，工厂函数能避免缓存互相挤掉。否则普通 selector 更简单。

selector 工厂常用于列表项复杂派生、每个卡片独立统计、按项目 id 聚合任务等场景。它的代价是每个组件实例创建自己的 selector，需要注意创建时机，避免每次渲染都新建。

因此 selector 工厂通常更适合和组件实例生命周期绑定，例如在组件外定义工厂、在组件初始化时创建一次，而不是每次 render 都重新生成。否则你以为自己在做缓存，实际却一直在新建缓存。

## 失效场景

记忆化 selector 依赖输入引用。如果 reducer 每次都创建无关的新数组，selector 仍然会重新计算。

```typescript
const selectTodoTitles = createSelector([selectTodos], (todos) =>
  todos.map((todo) => todo.title),
);
```

上面这个 selector 每次返回新数组。如果 `todos` 没变，`createSelector` 会复用上一次结果；如果 reducer 在无关 action 中也重建了 `todos`，缓存就会失效。

常见排查顺序是先看 reducer 是否只更新必要字段，再看 selector 输入是否稳定，最后才考虑给组件增加比较函数。不要把所有问题都交给 `shallowEqual`，否则会掩盖状态建模不合理的问题。

很多 selector 失效其实不是 selector 写错，而是 reducer 每次都重建了太多引用。先保证状态更新精确，再优化 selector 才有效。

如果 reducer 对无关 action 也返回新数组、新对象，所有依赖它的 selector 都会重新计算。Redux 性能优化很多时候要从 reducer 更新范围开始，而不是从组件层硬压。

这也是为什么 selector 优化不能孤立看。读取层是否稳定，取决于写入层是否精确；写入层每次都大范围重建，读取层再怎么 memo 也只能被动失效。Redux 的性能问题往往是整条状态流共同决定的。

## 重渲染控制

Selector 性能问题通常来自三个地方：订阅范围太大、返回引用不稳定、reducer 无关更新太多。

| 问题 | 表现 | 调整 |
| --- | --- | --- |
| 订阅整个 slice | 无关字段变化也渲染 | 拆小 selector |
| 每次返回新对象 | 组件频繁重渲染 | `createSelector` 或拆字段 |
| reducer 重建大数组 | 缓存频繁失效 | 只更新必要字段 |
| 组件内重复派生 | 多处逻辑不一致 | 抽成 selector |

不要把所有渲染问题都交给比较函数。先检查状态更新是否精确、selector 输入是否稳定，再考虑 `shallowEqual`。

Selector 的好坏会直接决定 Redux 代码是否可维护。好的 selector 让组件读起来像业务，差的 selector 会把状态树结构泄漏到每个角落。

好的 selector 命名应该表达业务结果，例如 `selectVisibleTodos`、`selectCartTotal`、`selectCanCheckout`，而不是 `selectData1`。组件里读到这些名字时，应该能直接看懂页面需要什么数据。

从长期维护看，selector 就像状态层的公开读取 API。只要这个 API 稳定，底层 slice 怎么拆、字段怎么迁、实体怎么规范化，都还有重构空间；一旦组件直接读深层 state 路径，后续每次改结构都会牵一大片。
