## 服务端状态是什么

服务端状态来自接口和缓存，核心不是“存在浏览器里”，而是“数据由服务器权威决定”。它经常表现为列表、详情、搜索结果、权限、统计和配置。

服务端状态和本地状态最大的差异，在于它的真实性不由前端说了算。前端可以决定什么时候展示、什么时候缓存、什么时候刷新，但不能决定这份数据本身是否仍然有效。

```text
特点：
1. 来源外部
2. 需要同步
3. 可能失效
4. 常被多个组件共享
```

服务端状态和本地 UI 状态不同。前者强调数据新鲜度、失效、同步、去重和重试；后者更适合弹窗开关、输入框、展开收起和局部交互。

如果把服务端状态当成本地状态维护，页面很快就会出现“请求回来后又改了一次”“列表页和详情页不是同一份数据”“刷新后状态丢失”之类的问题。

```ts
type ServerState<T> = {
  data?: T;
  updatedAt?: number;
  stale: boolean;
};
```

这个模型提醒我们：服务端状态不只是 `data`，还要知道数据什么时候来的、能不能继续用。

所以服务端状态一般都需要附带元信息，例如更新时间、是否过期、是否正在加载、是否曾经失败。只有这样，页面才知道应该展示旧数据、重新请求还是直接报错。

服务端状态还要面对“多个组件同时需要同一份数据”的问题。如果每个组件各自请求，页面会产生重复请求、竞态和不一致。服务端状态工具的核心价值之一，就是用相同 key 复用同一份缓存和请求过程。

这也是为什么服务端状态不应该只被理解成“把接口结果存下来”。真正难的是围绕这份结果继续管理时间、新鲜度、并发、失效和共享。少了这些信息，它就只是一个临时对象，还谈不上稳定的数据层。

## 服务端状态边界

如果一个值来自接口，又会被缓存、分页、搜索、刷新、共享，就基本是服务端状态，不要混到普通组件 state 里。

这条判断很实用。凡是用户切路由、刷新页面、切换筛选条件后仍然要恢复的值，通常都不该只靠局部 state；凡是会影响多个页面的一致性的数据，更应该交给服务端状态层。

服务端状态适合交给专门的数据层工具管理，因为它经常需要处理去重、缓存、失效、重试和并发。

服务端状态不要随意复制到客户端 store 里长期保存。比如用户列表已经由查询缓存管理，再复制一份到 Redux/Zustand/Pinia，后续修改用户时就要同时更新两份。除非有明确原因，否则让查询层继续做权威缓存更稳定。

判断边界时可以先问：这份数据的真实来源是不是服务器，它会不会因为时间、权限、筛选条件或用户身份改变而失效，它是不是会被多个页面共享。如果这些答案大多是“会”，那它就更像服务端状态，而不是普通本地 state。

## 缓存键

服务端状态通常依赖请求 key。

```ts
["user", id]
["posts", { page, tag }]
```

key 要把影响结果的参数全都包含进去。分页、搜索词、排序、筛选、登录用户都可能影响最终数据。

key 设计得太粗，会把不同查询复用成一份缓存；key 设计得太细，又会让缓存命中率过低。合适的 key 应该既能区分结果，又不过度拆碎。

缓存 key 应该包含所有影响结果的输入：资源类型、资源 id、分页、筛选、排序、当前用户或租户。遗漏任何一个输入，都可能把 A 用户或 A 条件下的数据复用到 B 场景。

```ts
["orders", { userId, page, status, sort }]
```

对象型 key 要保持稳定结构，避免同一语义用不同字段名或默认值表达，否则缓存会被无意义拆碎。

缓存 key 的本质是“这份数据的身份”。身份定义得不准，后续所有缓存复用、失效和乐观更新都会跟着出问题。很多服务端状态 bug 表面上像渲染异常，根因其实是数据身份没定义清楚。

## 新鲜度

新鲜度决定能不能直接复用旧数据。

```text
数据没变 -> 直接用
数据可能变了 -> 重新拉
```

新鲜度不是绝对时间，而是业务判断。库存、价格、权限数据通常更敏感；文章、字典、地区列表通常更稳定。

这也解释了为什么同样是“列表”，有的可以长缓存，有的必须频繁刷新。数据本身的变化频率、错误代价和用户感知都要一起考虑。

| 数据 | 新鲜度要求 |
| --- | --- |
| 库存、价格 | 高 |
| 用户权限 | 高 |
| 文章详情 | 中 |
| 省市区字典 | 低 |

新鲜度不是简单的“多久刷新一次”，还包括用户是否能接受看到旧数据。文章列表旧一分钟可能没问题，支付状态旧一秒都可能造成误解。服务端状态策略要跟业务风险绑定。

这也是为什么不能给所有接口套同一套缓存时间。真正合理的策略往往和业务语义相关，而不是和接口名称相关。只要页面里有“用户会据此做决定”的数据，新鲜度要求通常就会更高。

## 重新验证

常见重新验证时机包括手动刷新、窗口聚焦、路由切换和修改后失效。

```ts
async function revalidateUser(id: string) {
  const user = await fetch(`/api/users/${id}`).then((r) => r.json());
  cache.set(["user", id], user);
}
```

重新验证不一定要清空旧数据。很多页面可以先展示旧数据，再在后台刷新，这样体验会更稳。

对列表页、详情页和仪表盘来说，这种“先旧后新”的策略通常更友好。用户不会因为每次刷新都先看到空白态而觉得页面卡顿。

重新验证通常有两种体验：清空后加载，或者保留旧数据并后台刷新。前者适合数据不应继续展示的场景，后者适合旧数据仍有参考价值的场景。

```text
保留旧数据：文章列表、商品详情、仪表盘
清空旧数据：切换账号、权限变化、敏感数据
```

是否保留旧数据，本质上是体验和正确性的取舍。

很多页面体验差，不是因为没有重新验证，而是重新验证方式太粗暴。每次切换筛选都先清空、每次窗口聚焦都先闪 skeleton、每次提交成功都整页重置，这些都会让用户感到系统不稳定。服务端状态的成熟度，往往就体现在这些刷新细节上。

## 乐观更新

修改类操作可以先更新 UI，再等服务端确认。

```ts
async function toggleTodo(todo: Todo) {
  const previous = cache.get(["todos"]);

  cache.set(["todos"], (todos: Todo[]) =>
    todos.map((item) =>
      item.id === todo.id ? { ...item, done: !item.done } : item,
    ),
  );

  try {
    await fetch(`/api/todos/${todo.id}`, { method: "PATCH" });
  } catch {
    cache.set(["todos"], previous);
  }
}
```

乐观更新适合点赞、收藏、勾选这类失败率低、反馈敏感的操作。

如果操作本身有较高风险，比如支付、提交订单、删除关键数据，就不适合简单乐观更新。那些场景更需要明确确认和服务端最终结果。

乐观更新必须有回滚策略。更新前保存旧缓存，请求失败后恢复；请求成功后最好用服务端返回结果校正一次，避免前端假设和真实业务规则不一致。

```text
保存旧值
  -> 先更新 UI
  -> 请求服务端
  -> 成功后用服务端结果校正
  -> 失败后回滚旧值
```

它适合失败率低、用户反馈敏感、冲突代价低的操作。风险越高，越要让服务端结果先回来。

如果页面里存在多个相关查询，比如列表、详情、统计数、筛选结果，乐观更新还要考虑它会影响哪些缓存。只改一处而漏掉其他相关查询，用户看到的就会是“局部更新了，但全局还没变”，体验反而更混乱。

## 服务端边界

服务端状态一旦需要去重、缓存、失效、重试和并发控制，就不该混进普通组件 state。组件本地 state 更适合局部 UI，比如弹窗开关、输入草稿和临时筛选。

服务端状态和本地状态最好不要互相冒充。谁负责数据真实性、谁负责展示交互、谁负责失效恢复，一开始就分开，后面工程会轻很多。

服务端状态设计可以围绕四个问题展开：key 怎么定义，新鲜度怎么判断，写操作后失效哪些缓存，失败时展示旧数据还是错误态。只要这四件事清楚，数据层就不会沦为一堆 `loading/data/error` 的重复代码。

从工程视角看，服务端状态层真正的目标是把“请求的复杂性”抽到统一位置。页面不该重复思考同一份数据怎么缓存、何时过期、失败后保不保留旧值、提交后让哪些查询失效。只要这些规则被稳定沉淀下来，页面代码会轻很多。
