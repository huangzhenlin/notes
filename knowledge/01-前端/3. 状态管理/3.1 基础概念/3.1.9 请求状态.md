## 请求状态模型

请求状态至少要表达：未开始、加载中、成功、失败。有时还要加上重试、空数据、取消中。

```ts
type RequestState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: string };
```

这种判别联合比 `loading/error/data` 三个松散字段更安全，因为每个状态只携带自己合法的数据。

松散字段最容易产生不合法组合，比如 `loading=true` 同时有 `error`，或者 `data` 已经存在但状态仍是 `idle`。判别联合把状态组合收紧，适合复杂请求、表单提交和关键业务流程。

请求状态建模的意义，不只是为了类型好看，而是为了逼着我们把“不同时刻到底发生了什么”说清楚。状态越模糊，UI 越容易同时出现互相矛盾的提示；状态越清晰，页面分支就越稳定。

## 状态组合

一个请求不只关心数据，还关心是否首次加载、是否正在刷新、是否出错。

```ts
type QueryState<T> = {
  data?: T;
  error?: string;
  isLoading: boolean;
  isFetching: boolean;
};
```

`isLoading` 更偏首次加载，`isFetching` 更偏正在请求。这个差异会直接影响 skeleton、局部 loading 和旧数据保留策略。

请求状态还可以拆出 `isSubmitting`、`isRefreshing`、`isRetrying`。它们都表示异步中，但用户体验完全不同：提交中要防重复点击，刷新中可以保留旧数据，重试中要提示正在恢复。

这也是为什么“一个全局 loading 布尔值”通常撑不起复杂页面。搜索、提交、上传、刷新、分页、背景同步虽然都算异步，但用户对它们的预期完全不同。把它们压成同一个状态，最后 UI 往往只能做出粗糙反馈。

## 首次加载

首次加载和刷新应该区别对待。

```tsx
function UserList({ state }: { state: QueryState<User[]> }) {
  if (state.isLoading) {
    return <Skeleton />;
  }

  if (state.error && !state.data) {
    return <ErrorView message={state.error} />;
  }

  return (
    <>
      {state.isFetching && <small>正在刷新...</small>}
      <List users={state.data ?? []} />
    </>
  );
}
```

首次加载没数据时更适合骨架屏；刷新时已有旧数据，通常更适合局部提示。

首次加载和刷新混在一起，会导致每次后台刷新都把页面打回 skeleton。用户正在阅读列表时突然空白，会比看到一条“正在刷新”更糟糕。

一个更稳的思路是：把“有没有可展示的数据”和“现在是不是正在请求”分开。前者决定页面主体呈现什么，后者决定是否显示局部进度提示。这样加载体验通常会自然很多。

## 错误保留

失败时要不要保留旧数据，取决于业务。

```text
有些页面：失败时保留旧内容
有些页面：失败时清空并提示
```

列表刷新失败通常可以保留旧列表，表单提交失败通常要保留输入，权限校验失败则可能要清空敏感数据并跳转。

错误保留要按风险判断。公开列表刷新失败可以继续展示旧内容；个人隐私、权限、支付状态失败时，保留旧数据可能误导用户，甚至造成安全风险。

所以错误态设计不是简单地决定“失败了要不要 toast 一下”，而是要先判断：此时继续展示旧数据会不会比报错更危险。不同业务场景的选择可能完全相反。

## 竞态保护

连续发起多个请求时，要避免旧请求覆盖新请求。

```ts
let latestRequestId = 0;

async function search(keyword: string) {
  const id = ++latestRequestId;
  const result = await fetch(`/api/search?q=${encodeURIComponent(keyword)}`)
    .then((response) => response.json());

  if (id !== latestRequestId) {
    return;
  }

  setResult(result);
}
```

输入搜索、筛选切换、分页翻页都容易出现竞态。更稳的做法是配合 `AbortController` 取消旧请求。

竞态不仅发生在搜索，也发生在路由切换和组件卸载。旧页面请求晚回来后，如果还更新全局状态或缓存，可能污染新页面。请求状态管理要么取消旧请求，要么用 request id 确认最新请求。

只要一个场景允许用户快速连续触发请求，就应该默认存在竞态风险。搜索框、筛选器、分页、切标签、切路由、重复点击提交按钮，这些都值得提前设计取消或去重策略，而不是等线上偶发错乱后再补。

## 重试策略

重试适合网络波动，不适合参数错误、权限失败或业务校验失败。

```ts
async function retry<T>(task: () => Promise<T>, times = 3): Promise<T> {
  let lastError: unknown;

  for (let index = 0; index < times; index += 1) {
    try {
      return await task();
    } catch (error) {
      lastError = error;
    }
  }

  throw lastError;
}
```

重试最好带退避，而不是立刻连续打三次。对移动网络和临时服务波动，短暂延迟后重试更友好；对 400、401、403 这类确定性错误，重试只会浪费资源。

重试策略最好和错误分类绑在一起，而不是做成“任何失败都自动重试”。真正有价值的重试，是在用户不必参与的情况下帮他恢复临时故障；如果错误本身需要用户登录、修改参数或补全权限，重试只会制造噪音。

## 失败分类

| 失败类型 | 处理方式 |
| --- | --- |
| 网络闪断 | 可重试 |
| 接口 500 | 可重试或提示 |
| 参数错误 | 不重试 |
| 权限失败 | 跳转或提示 |
| 空结果 | 视业务展示空状态 |

请求状态管理的目标不是把所有情况都塞成 `loading/success/error`，而是让用户知道系统现在发生了什么，以及下一步能做什么。

好的请求状态应该能指导 UI：什么时候显示骨架，什么时候禁用按钮，什么时候允许重试，什么时候保留旧数据，什么时候跳转登录。请求状态不是接口调用的附属品，而是用户体验的一部分。

从工程层面看，请求状态如果建得足够清楚，很多页面逻辑都会变简单。因为组件不再需要自己猜“当前到底算不算加载中”“失败后该不该清空”“旧数据能不能继续展示”，而是可以直接根据状态模型做稳定分支。
