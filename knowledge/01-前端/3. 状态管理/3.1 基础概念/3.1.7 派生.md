## 计算来源

派生状态是从已有状态计算出来的结果，例如总价、过滤后的列表、按钮是否可点击。

```javascript
const completedTodos = todos.filter((todo) => todo.done);
const canSubmit = username.trim() !== "" && password.length >= 8;
```

如果一个值能稳定从其他状态计算出来，优先计算而不是额外保存。额外保存派生状态会引入同步风险。

派生状态的关键是“没有独立事实来源”。总价来自购物车项，按钮可用性来自表单输入和校验规则，过滤列表来自原始列表和筛选条件。只要源状态变了，它就应该立即跟着变。

## 缓存价值

有些派生计算成本较高，或者会造成不必要的重复渲染，这时可以考虑缓存计算结果。

```javascript
const visibleTodos = useMemo(() => {
  return todos.filter((todo) => todo.text.includes(keyword));
}, [todos, keyword]);
```

缓存派生结果的前提是依赖清晰。依赖不清晰时，缓存会变成另一个隐藏状态，反而更难维护。

缓存派生结果不是保存另一份事实，而是避免重复计算。React 的 `useMemo`、Vue 的 `computed`、Redux selector 的 memoization 都属于这个思路。缓存要由依赖失效驱动，而不是手动到处同步。

## 同步风险

最危险的做法是同时保存源状态和派生状态，却没有严格同步。

```javascript
setItems(nextItems);
setTotal(nextItems.reduce((sum, item) => sum + item.price, 0));
```

如果中间任何一次更新漏掉 `total`，界面就会显示矛盾数据。状态设计时要优先避免这种“双份事实”，只有在性能、交互或外部 API 明确需要时，才把派生结果落成状态。

同步风险常常不是马上出现，而是在新增字段、新增分支、新增异步流程后暴露。比如购物车新增优惠券后，原来的 `total` 同步逻辑忘了考虑折扣，页面就会出现“商品总价”和“支付金额”不一致。
## 表单派生示例

表单里最常见的派生状态是校验结果、按钮状态和提示文案。源状态只需要保存用户输入，其他结果在渲染时计算即可。

```tsx
function LoginForm() {
  const [form, setForm] = useState({ email: "", password: "" });

  const errors = {
    email: form.email && !form.email.includes("@") ? "邮箱格式不正确" : "",
    password:
      form.password && form.password.length < 8 ? "密码至少需要 8 位" : "",
  };

  const canSubmit =
    form.email.includes("@") &&
    form.password.length >= 8 &&
    !errors.email &&
    !errors.password;

  return (
    <form>
      <input
        value={form.email}
        onChange={(event) =>
          setForm((current) => ({ ...current, email: event.target.value }))
        }
      />
      <input
        value={form.password}
        onChange={(event) =>
          setForm((current) => ({ ...current, password: event.target.value }))
        }
      />
      <button disabled={!canSubmit}>登录</button>
    </form>
  );
}
```

如果把 `canSubmit` 也放进 state，就需要在每次输入变化时同步更新它；一旦漏掉某个字段或某个校验分支，就会出现“输入已经正确但按钮仍不可点”的不同步问题。

表单派生还要区分“校验结果”和“用户是否看过错误”。错误内容可以派生，但 `touched`、`dirty`、`submitted` 这类交互状态通常需要保存，因为它们代表用户行为历史。

```ts
const errors = validate(values);
const canSubmit = Object.keys(errors).length === 0;
```

校验结果来自输入，是否展示错误来自交互状态。两者不要混成一份。

## 列表派生示例

列表页面通常会同时受到搜索词、筛选条件、排序规则和分页影响。源状态保存原始列表与条件，展示列表通过派生函数得到。

```ts
type Product = {
  id: string;
  name: string;
  price: number;
  category: string;
  available: boolean;
};

function getVisibleProducts(
  products: Product[],
  filters: { keyword: string; category: string; onlyAvailable: boolean },
) {
  return products
    .filter((product) => {
      const matchKeyword = product.name
        .toLowerCase()
        .includes(filters.keyword.toLowerCase());
      const matchCategory =
        !filters.category || product.category === filters.category;
      const matchAvailable = !filters.onlyAvailable || product.available;

      return matchKeyword && matchCategory && matchAvailable;
    })
    .sort((a, b) => a.price - b.price);
}
```

这个函数可以放在组件内、Selector 内或独立工具函数里。关键是不要同时维护 `products` 和 `visibleProducts` 两份状态，除非 `visibleProducts` 来自服务端分页结果或需要被用户手动编辑。

列表派生最好保持纯函数。给同样的原始列表和筛选条件，就返回同样的结果。这样它可以被测试、缓存，也可以在不同框架里复用。

## 落成状态的条件

派生值并不是永远不能保存。它可以落成独立状态，但需要满足明确条件：它已经不再只是本地计算结果，而是具备自己的生命周期。

| 场景 | 是否适合保存 | 原因 |
| --- | --- | --- |
| `cartItems.length` | 不适合 | 完全由购物车数组决定 |
| `filteredUsers` | 通常不适合 | 可由用户列表和筛选条件计算 |
| 服务端返回的 `searchResultIds` | 适合 | 结果代表一次查询快照，可能与本地全量列表不同 |
| 用户手动调整后的排序结果 | 适合 | 排序结果已经包含用户意图，不再只是规则计算 |
| 昂贵计算的缓存结果 | 视情况 | 可以缓存，但要明确失效条件 |

判断时可以问一个问题：如果源状态变化，这个值是否必须立即随之变化？如果答案是“必须”，它大概率应该保持派生；如果答案是“不一定，它有自己的提交、撤销、刷新或过期规则”，它才更像独立状态。

派生落成状态的典型情况，是结果已经成为新的业务事实。比如用户手动拖拽排序后的顺序，不再只是按规则排序，而是用户提交的意图；服务端返回的搜索结果 id 列表，也不是本地全量列表能稳定算出的结果。此时它们可以成为独立状态，但要明确生命周期和失效条件。
