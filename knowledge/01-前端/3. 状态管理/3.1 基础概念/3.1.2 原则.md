## 单一来源

同一事实最好只有一个权威来源。多个来源彼此写入，很容易导致同步地狱。

单一来源并不意味着“只能有一个 store”，而是同一份业务事实不要同时在多个地方各自维护一份副本。可以有多个状态容器，但同一事实最好只有一个读写主入口。

```text
错误示例：
1. 用户名同时存在于组件 state 和 store
2. 总价既存结果，又能从列表算出
```

一旦状态有两个写入点，就很难判断谁先更新、谁应该覆盖谁。很多“偶发 bug”其实都是同一份事实被写了两次。

如果状态确实要跨层共享，也应该尽量让写入口集中，比如统一 action、统一 store 方法、统一服务层，而不是每个页面都直接改底层对象。这样回溯问题时，路径会清楚很多。

例如购物车数量既由接口返回又被局部组件手动加减，最后就很容易出现“页面显示和服务端不一致”。这种问题很难靠临时补丁彻底消掉，通常只能回到单一来源。

单一来源并不排斥缓存和副本，但缓存必须知道自己是副本。比如接口数据可以被缓存到客户端，但服务端仍然是权威；表单可以从用户资料初始化，但编辑中的草稿是另一份临时状态。只要两者的权威关系明确，就不会互相冒充。

```text
用户资料：服务端权威
编辑草稿：表单本地权威
提交成功：服务端返回结果重新成为权威
```

很多状态 bug 的根因，是草稿和权威数据没有分清，导致页面一会儿展示草稿，一会儿展示缓存，一会儿又被接口结果覆盖。

## 可预测更新

状态修改应该尽量显式、可追踪、可复现。

```ts
setCount((value) => value + 1);
```

```ts
dispatch({ type: "cart/add", payload: item });
```

不要在很多地方直接改同一个对象的深层字段。统一入口能让日志、调试和回放都更容易。

显式更新还有一个好处：变更路径更短。你能清楚知道是哪个动作触发了修改，也更容易在 DevTools 或日志里还原过程。

可预测更新要求“动作”和“结果”之间关系清楚。比如 `cart/add` 表示加入购物车，`user/logout` 表示退出登录，`filters/reset` 表示重置筛选。动作名越具体，日志越有意义。

```ts
dispatch({ type: "filters/setKeyword", payload: "phone" });
dispatch({ type: "filters/reset" });
```

如果所有动作都叫 `setState`，短期方便，长期排查会很痛苦。状态管理工具提供的 DevTools 只有在动作语义清楚时才真正有价值。

## 近处优先

状态应该尽量放在离使用它最近的地方。

这条原则并不是鼓励“到处都放本地状态”，而是提醒你先从最小可行范围开始。范围越小，影响面越小，定位问题也越快。

```text
局部状态 -> 最近组件
页面状态 -> 页面层
共享状态 -> Context / store
```

状态放得越远，和它无关的组件越容易跟着重渲染。先局部、后共享，通常比一开始全局化更稳。

这条原则和“全局化越早越好”正好相反。多数项目出问题，不是因为状态不够全，而是因为状态离使用者太远，导致更新范围、依赖关系和清理时机都变复杂了。

近处优先也不是永远局部。局部状态一旦出现明确共享需求，就应该上移到最近公共父级；上移后如果继续跨多个路由或业务域共享，再考虑 store。它是一条迁移路径，而不是单点答案。

```text
组件 state
  -> 页面 state
  -> Context / provide
  -> Store
  -> 服务端状态层
```

每提升一层，都要确认收益大于成本：共享更方便了，但更新范围、测试复杂度和清理责任也变大了。

## 副作用分离

请求、订阅、存储、日志等副作用要和纯状态更新分开。

```text
改数据：状态层
做请求：副作用层
```

把“改数据”和“做外部交互”混在一起，状态系统会越来越难推理。好的状态管理能让更新逻辑尽量纯，让副作用尽量边界化。

比如请求失败后重试、存储同步、埋点上报都更适合放到状态更新之外。状态负责描述结果，副作用负责和外部世界打交道，这样职责才不会混。

如果副作用必须和状态联动，最好也把它们的触发条件写清楚。比如“状态从 pending 变成 success 后再保存缓存”，而不是在很多地方散落地写副作用调用。

状态更新最好保持纯粹，副作用最好集中在事件处理器、异步 action、中间件、effect 或数据请求层里。不同工具名字不一样，但原则相同：状态层描述事实变化，副作用层处理外部世界。

```text
用户点击提交
  -> 副作用层发请求
  -> 成功后派发状态更新
  -> 失败后记录错误状态
```

这样即使请求失败，状态仍然能表达清楚当前处境，而不是半途中被改坏。

## 派生优先

能从现有状态算出来的值，优先派生，不要重复存储。

```ts
const total = items.reduce((sum, item) => sum + item.price, 0);
```

派生值应该是结果，不是事实来源。只要它能从别的状态算出，就别再多放一份。

如果派生值被重复保存，后续就会出现“原始状态变了，派生值忘了更新”的问题。很多表单总价、筛选计数、选中数量 bug，本质都是派生值被手动维护了。

派生优先还有一个实际好处：减少同步成本。你只要改事实来源，相关结果就会自动重新计算，不需要手工去找所有副本逐一更新。

派生值可以缓存，但缓存不等于事实来源。比如筛选后的列表可以用 `useMemo`、`computed` 或 selector 缓存计算结果，但它仍然应该由原始列表和筛选条件推导出来。

```ts
const visibleItems = items.filter((item) => item.name.includes(keyword));
```

只有当派生结果来自昂贵计算，并且计算输入稳定时，缓存才有意义。不要为了“省计算”把派生结果变成另一份需要手工维护的状态。

## 失效明确

状态一旦依赖外部数据，就要考虑什么时候失效、由谁失效、失效后怎么恢复。

```text
修改数据后
  -> 对应缓存失效
  -> 触发重新获取
  -> 保留或清空旧数据
```

不明确失效边界，缓存和状态就容易互相污染。

失效原则最好提前和接口、缓存、表单提交一起设计。什么时候清掉旧值、什么时候保留旧值、什么时候强制重新拉取，这些都应该在状态设计阶段先想明白。

如果业务中存在“提交成功后回到列表”“重新登录后刷新权限”“切换账号后清空草稿”这类场景，失效规则就更不能含糊。状态管理最怕的不是没有数据，而是不知道旧数据什么时候该退场。

失效要明确触发源。常见触发源包括：用户主动刷新、窗口重新聚焦、路由切换、写操作成功、权限变化、登出、切换组织或账号。每一种触发源都可能对应不同范围的状态清理。

```text
登出 -> 清空用户、权限、私有缓存、草稿
修改资料 -> 失效当前用户信息和用户详情
切换组织 -> 失效组织相关列表和权限
```

如果失效规则写得太粗，页面会频繁空白和重拉；写得太细，又容易漏掉旧数据。状态原则的目标不是绝对正确，而是在体验和一致性之间找到可解释的平衡。
