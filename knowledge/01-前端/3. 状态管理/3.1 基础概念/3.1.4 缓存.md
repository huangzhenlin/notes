## 缓存是什么

缓存本质上是在“数据还没过期”时复用结果。它解决的不是有没有数据，而是能不能暂时不重新算、不重新请求。

```text
请求 -> 命中缓存 -> 直接复用
请求 -> 缓存过期 -> 重新拉取
```

缓存和状态很像，但不是同一件事。状态更关注当前 UI 的真实值，缓存更关注这份值能不能暂时复用。

缓存一定要回答两个问题：这份数据是谁产生的，什么时候还能继续相信。前端缓存常见于接口结果、图片资源、字典配置、列表详情和计算结果。它的目标不是“永远少请求”，而是在正确性允许的范围内减少重复工作。

```text
缓存命中
  -> 判断是否足够新
  -> 可用则直接展示
  -> 不够新则重新验证
```

## 缓存与状态

缓存解决的是复用，状态解决的是表达当前事实。

```ts
const key = ["users", page, keyword];
```

如果一个值是可复用的请求结果，就更像缓存；如果一个值是当前表单、当前开关、当前页面选中项，就更像状态。

缓存可以被状态读取，但缓存本身不一定是当前事实。比如用户详情缓存里有旧昵称，表单草稿里有正在编辑的新昵称，服务端数据库里有最终昵称。三者都可能存在，但权威来源不同。

```text
服务端数据 -> 查询缓存 -> 页面展示
用户编辑 -> 表单状态 -> 提交后失效缓存
```

缓存和状态混在一起时，最容易出现提交成功后页面仍显示旧数据。写操作后要明确失效哪些缓存。

## 缓存键

缓存键要稳定且完整。

```ts
["user", id]
["users", { page: 1, sort: "name" }]
```

键如果漏了参数，就可能把 A 页的数据错发给 B 页。缓存设计最怕“看起来命中率很高，实际上结果已经串了”。

缓存键要包含所有影响结果的因素：资源类型、id、分页、排序、筛选、搜索词、当前用户、租户或语言。如果用户身份会影响结果，却没有进入 key，就可能把一个用户的数据复用给另一个用户。

```ts
["orders", { userId, page, status, sort }]
["i18n", locale]
```

key 也不要包含每次都变的临时对象，否则会导致缓存无法命中。对象型 key 要保持字段稳定、默认值统一。

## 新鲜度

缓存要区分“还能不能直接用”和“还在不在内存里”。

```text
fresh = 结果够不够新
retention = 缓存对象还在不在
```

有些缓存还在，但已经不新了；有些缓存不新，但仍可先展示再后台刷新。工程上经常要同时看这两个维度。

可以把缓存分成三种体验：新鲜数据直接展示，过期数据先展示再刷新，不可信数据清空后重新加载。不同业务适合不同策略。

```text
字典配置：长时间 fresh
文章详情：可先旧后新
账号权限：过期后谨慎复用
支付结果：优先重新确认
```

## 重新验证

缓存不是永远正确，重要数据要重新验证。

```text
重新验证方式：
1. 过期自动刷新
2. 手动失效
3. 聚焦时刷新
4. 修改后失效
```

重新验证不是清空一切，而是在不打断体验的前提下尽量保证数据新鲜。

重新验证要考虑触发范围。修改一条用户详情后，可能只需要失效 `["user", id]`；修改用户角色后，还可能要失效用户列表、权限缓存和当前会话信息。范围太小会漏旧数据，范围太大又会造成无谓刷新。

## 缓存对象

能被缓存的对象通常是列表、详情、字典、配置、权限、统计等可重复读取的数据。

| 数据 | 新鲜度要求 |
| --- | --- |
| 库存、价格 | 高 |
| 用户权限 | 高 |
| 文章详情 | 中 |
| 省市区字典 | 低 |

数据变化越频繁，缓存收益越小；数据越稳定，缓存越有价值。

除了变化频率，还要看错误代价。省市区字典即使旧一点也没关系；库存价格旧一点可能影响下单；权限旧一点可能导致越权入口。缓存策略应该先按业务风险分级，再考虑性能收益。

## 乐观更新

修改类操作可以先更新 UI，再等服务端确认。

```ts
// optimistic update
```

```ts
async function toggleTodo(todo: Todo) {
  const previous = cache.get(["todos"]);

  cache.set(["todos"], (todos: Todo[]) =>
    todos.map((item) =>
      item.id === todo.id ? { ...item, done: !item.done } : item,
    ),
  );

  try {
    await fetch(`/api/todos/${todo.id}`, { method: "PATCH" });
  } catch {
    cache.set(["todos"], previous);
  }
}
```

乐观更新适合成功率高、反馈要快的操作，不适合高风险写操作。

乐观更新要有三个动作：保存旧值、立即更新、失败回滚。成功后也最好用服务端返回结果校正一次，因为服务端可能有权限、库存、排序、审计字段等额外规则。

```text
点赞、收藏、勾选 -> 适合乐观
支付、删除、提交订单 -> 谨慎或不适合
```

## 失效策略

缓存失效可以手动，也可以自动。

```text
常见触发：
1. 修改数据后
2. 登出后
3. 权限变化后
4. 过期后
```

缓存如果只会加不会失效，就会逐渐变成旧数据制造机。

失效策略可以按事件组织：写操作成功后失效相关查询，登出后清空私有缓存，切换组织后清空组织域数据，窗口聚焦后刷新高敏数据。缓存不是独立系统，它必须和业务事件连接起来。

## 使用边界

缓存最适合“访问频繁但变化不快”的数据；不适合每次都必须最新的强实时数据，也不适合纯本地临时输入。判断时要同时看命中率、失效成本和一致性要求。

不要为了“有缓存”而缓存一切。缓存会带来失效、内存、串数据和调试成本。一个好的缓存设计，应该能说清 key、fresh 时间、保留时间、失效触发、失败时是否保留旧数据。说不清这些，缓存就很可能变成隐藏状态。
