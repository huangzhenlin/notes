## 共享事实

状态提升解决的是“多个组件需要读写同一份事实”的问题。做法是把状态从子组件移到它们最近的共同父组件，再通过 Props 下发数据，通过回调上报变更。它不依赖状态库，是组件化开发中最基础的共享方式。

```tsx
function Accordion() {
  const [activeId, setActiveId] = useState<string | null>(null);

  return (
    <>
      <Panel id="a" activeId={activeId} onActiveChange={setActiveId} />
      <Panel id="b" activeId={activeId} onActiveChange={setActiveId} />
    </>
  );
}
```

如果两个面板各自维护 `isActive`，它们无法自然做到“展开一个时关闭另一个”。把状态提升到共同父组件后，父组件拥有唯一事实来源，两个子组件只是展示这个事实。

状态提升的本质是把“多个局部事实”合并成“一份共享事实”。它不是为了让父组件更大，而是为了避免两个子组件各自猜测对方状态。

## 最近父级

状态不是越往上放越好。应该放到需要它的组件的最近共同父级。放太低，其他组件拿不到；放太高，上层组件会承载过多细节，导致无关更新和难以维护。

```text
Page
  SearchPanel
    KeywordInput
    CategorySelect
  ResultList
```

如果 `KeywordInput`、`CategorySelect` 和 `ResultList` 都依赖筛选条件，状态可以放在 `Page` 或专门的 `SearchContainer`。如果只有输入框内部需要“输入中”状态，就不必提升。

最近父级可以是页面组件，也可以是专门的容器组件。容器组件的价值是承接共享状态和事件，让页面文件不至于被细碎 props 和 handler 塞满。

```tsx
function SearchContainer() {
  const [filters, setFilters] = useState(defaultFilters);

  return (
    <>
      <FilterPanel value={filters} onChange={setFilters} />
      <ResultList filters={filters} />
    </>
  );
}
```

## 数据下行

状态提升后，数据通过 Props 从父组件传给子组件。子组件不需要知道数据来自本地状态、URL、Store 还是接口，只需要根据输入渲染。

```tsx
function ResultSummary({ keyword, count }: { keyword: string; count: number }) {
  return (
    <p>
      “{keyword}” 找到 {count} 条结果
    </p>
  );
}
```

数据下行让渲染结果更可预测。相同 Props 应该得到相同 UI，这也是组件测试和复用的基础。

数据下行还可以让子组件不知道状态来源。今天数据来自本地 state，明天来自 URL，后天来自 store，只要 props 契约不变，子组件就不需要改。

## 事件上行

子组件不能直接修改父组件状态，只能通过回调表达用户意图。父组件收到事件后决定是否更新状态、如何校验、是否同步 URL 或触发请求。

```tsx
function KeywordInput({
  value,
  onChange,
}: {
  value: string;
  onChange: (value: string) => void;
}) {
  return <input value={value} onChange={(event) => onChange(event.target.value)} />;
}
```

这种“数据下行、事件上行”和 [[3.1.6 数据流|数据流]] 是同一套思想。它让子组件保持简单，也让父组件集中处理状态变更。

事件上行最好表达用户意图，而不是暴露父组件内部实现。比如 `onSelect(id)` 比 `setSelectedId(id)` 更抽象，子组件只知道“用户选择了某项”，不知道父组件如何保存。

## 派生状态

状态提升时要避免复制派生状态。能从已有状态计算出来的值，不应该再存一份，否则两份状态可能不一致。

```tsx
function CartSummary({ items }: { items: CartItem[] }) {
  const total = items.reduce((sum, item) => sum + item.price * item.count, 0);

  return <span>合计：{total}</span>;
}
```

购物车总价可以从商品列表计算，不需要单独存 `total`。只有当计算成本很高、需要缓存，或者值来自用户输入且尚未确认时，才考虑保存额外状态。

状态提升时尤其容易把派生值也一起提升。比如父组件保存了 `items`，又保存 `selectedCount`、`totalPrice`、`hasError`，这些值大多可以从源状态计算。提升状态前要先删掉能派生的部分，否则父组件会迅速膨胀。

## 受控组件

状态提升经常会把子组件变成受控组件。父组件掌握值，子组件通过事件请求修改。这在表单、筛选器、弹窗、分页和选中状态中非常常见。

```tsx
function FilterPage() {
  const [page, setPage] = useState(1);

  return (
    <Pagination page={page} onPageChange={setPage} />
  );
}
```

受控组件更灵活，但调用成本更高。基础组件可以同时支持受控和非受控，业务组件则应尽量选择清晰状态模型。这里可以和 [[4.1.5 受控模式|受控模式]] 一起理解。

受控模式适合父组件需要统一协调的场景，例如表单、筛选器、分页器、弹窗开关。它的代价是调用方必须传值和变更回调，所以基础组件要设计清楚默认模式，不要让调用方猜状态归谁。

## 过度提升

状态提升也会带来问题。状态放得过高，可能导致父组件变胖、Props 传递过长、无关组件重复渲染、业务逻辑集中在一个大组件里。

```text
过度提升信号：
父组件只负责转发大量 props
很多子组件收到自己不用的数据
一个状态变更导致大片区域重渲染
页面容器里充满细碎事件处理
```

遇到这些信号时，可以考虑拆容器组件、使用 Context、引入局部 Store，或者把状态下沉。状态提升不是终点，它只是找到单一事实来源的一种方式。

过度提升时，常见修复不是立刻上全局 store，而是重新划分局部区域。比如把搜索条件放在 `SearchContainer`，把表格选中状态放在 `TableContainer`，把弹窗内部草稿放回弹窗组件。状态向上移动和向下回收都应该服务于边界清晰。

## 状态库边界

不是所有共享状态都需要状态库。只在一个局部组件树内共享的状态，优先用状态提升；跨页面、跨布局、跨业务模块共享的状态，再考虑 Context、Pinia、Redux、Zustand 等方案。

```text
局部共享：状态提升
跨层级但范围有限：Context
跨页面或模块：Store
服务端缓存：Query 类工具
```

状态管理的核心不是选择工具，而是确定每份状态的归属。状态提升让这个判断保持具体：先问“谁真的需要它”，再决定放在哪里。

可以把状态提升当成第一阶段方案：当共享范围清楚且还在一个局部树内时，用它最简单；当 props 传递过深但范围仍有限时，再用 Context；当跨页面、跨模块或需要调试/持久化时，再考虑 store。工具越强，边界越要清楚。
