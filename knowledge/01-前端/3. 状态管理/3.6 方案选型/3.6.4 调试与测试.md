## 调试入口

状态问题调试时，先确定错误发生在数据流的哪一段。

这一步其实是在定位责任边界。是事件没触发、action 没执行、state 没更新，还是 selector/getter 算错了，先分清层级，排查就会快很多。

```txt
事件是否触发
Action 参数是否正确
State 是否按预期变化
Selector/Getter 是否派生正确
组件是否订阅正确
```

这个顺序能避免一上来就怀疑框架。很多问题来自参数传错、状态重复保存、派生计算不稳定或组件订阅范围过大。

如果你能把状态流按这条链路走通，很多“偶发性 UI 错乱”其实都能在很早的位置被发现，而不是等到页面表现异常才去猜。

排查时最好固定一个最小复现路径，然后沿状态流逐层打点。比如“点击加入购物车后数量没变”，不要一上来改渲染代码，而是先看事件是否触发、action 是否收到商品、Store 是否更新、selector/getter 是否算对、组件是否订阅了正确字段。

```text
点击按钮
-> addItem(product) 是否调用
-> items 是否新增或数量递增
-> itemCount getter 是否更新
-> Badge 是否读取 itemCount
```

这条链路能把问题从“页面不对”缩小到某一层，而不是在组件、Store、接口之间来回猜。

## DevTools

Redux、Pinia、Zustand 都可以借助 DevTools 或日志观察状态变化。调试重点不是“看到状态”，而是看到状态为什么变化。

具名动作和状态变化记录越清楚，回放问题就越容易。调试不是看“值是什么”，而是看“是谁把值改成这样的”。

```txt
cart/itemAdded
cart/itemQuantityChanged
checkout/submitRejected
```

具名 action 能让时间线更接近业务流程。`setData`、`update` 这类泛化名称很难帮助复现问题。

DevTools 的价值在于还原时间线。Redux 可以看到 action 序列，Pinia 可以看到 Store 和 action，Zustand 通常需要接入 devtools 中间件后才能更清楚地观察状态变化。

```ts
const useCartStore = create(
  devtools((set) => ({
    items: [],
    addItem: (product) =>
      set((state) => ({ items: addItem(state.items, product) }), false, "cart/addItem"),
  })),
);
```

调试命名要贴近业务动作，不要只写 `set`、`update`、`change`。当线上用户反馈“提交后购物车清空异常”时，清晰时间线能直接告诉你是 `checkout/submitSuccess` 清空的，还是某个初始化逻辑误触发。

## Reducer 与 Action 测试

纯状态更新逻辑适合写单元测试。输入旧状态和 action，断言新状态。

```ts
it("adds product to cart", () => {
  const state = cartReducer(undefined, itemAdded({ id: "p1", price: 10 }));

  expect(state.items.p1.quantity).toBe(1);
  expect(state.totalPrice).toBe(10);
});
```

测试越靠近纯函数，越稳定。复杂 UI 测试前，先把状态更新规则测清楚。

这类测试特别适合检查边界条件，比如空数组、重复添加、删除最后一项、状态回滚。把这些先测住，后面的 UI 改动就不容易把核心规则带偏。

Reducer 或纯函数测试应该覆盖正常路径和边界路径。状态管理 bug 很少出在“第一次添加一条数据”这种最顺场景，更多出在重复操作、删除最后一项、失败回滚、非法输入、旧数据迁移。

```ts
it("merges quantity when adding same product", () => {
  const state = cartReducer(
    { items: { p1: { id: "p1", quantity: 1, price: 10 } } },
    itemAdded({ id: "p1", price: 10 }),
  );

  expect(state.items.p1.quantity).toBe(2);
});
```

把核心规则抽成纯函数，测试会比挂完整 UI 更稳定。UI 测试看用户路径，状态测试看业务规则，两者不要互相替代。

## Store Action 测试

Zustand、Pinia 这类 Store action 可以通过创建 Store、调用 action、读取状态来测试。

```ts
it("toggles todo", () => {
  const store = useTodoStore.getState();

  store.addTodo("学习状态管理");
  const todo = useTodoStore.getState().todos[0];

  store.toggleTodo(todo.id);

  expect(useTodoStore.getState().todos[0].done).toBe(true);
});
```

测试之间要重置 Store，避免上一个用例的状态污染下一个用例。持久化中间件和全局订阅也要在测试中隔离。

如果 Store 里有持久化、订阅或跨实例共享，测试环境里最好显式清理，否则用例之间的状态残留会让结果看起来像“偶尔失败”。

Pinia 测试通常要为每个用例创建新的 Pinia 实例；Zustand 测试要重置 store state；Redux 测试可以创建新的 store。核心原则是每个用例都有干净初始状态。

```ts
beforeEach(() => {
  setActivePinia(createPinia());
});
```

如果 Store action 依赖 API，可以 mock service，而不是 mock Store 本身。直接 mock Store 会绕过真实状态更新，测试通过也不代表业务流真的正确。

## 异步测试

异步状态要测试加载、成功、失败和竞态。

```ts
it("stores user after loading", async () => {
  server.use(
    http.get("/api/users/1", () => HttpResponse.json({ id: "1", name: "Ada" })),
  );

  await store.dispatch(fetchUser("1"));

  expect(store.getState().user.status).toBe("success");
  expect(store.getState().user.entity.name).toBe("Ada");
});
```

接口层推荐使用 Mock Service Worker 或测试框架提供的 mock 能力。不要让单元测试依赖真实网络，否则速度和稳定性都会变差。

异步测试里最容易忽略的就是竞态。两个请求先后返回时，谁该覆盖谁、旧请求要不要丢弃，这些都值得在测试里明确下来。

异步测试要覆盖四类状态：请求前、请求中、请求成功、请求失败。对有并发保护的 action，还要测试“旧请求后返回不覆盖新结果”。

```ts
it("keeps latest search result", async () => {
  const first = store.search("old");
  const second = store.search("new");

  await second;
  await first;

  expect(store.keyword).toBe("new");
  expect(store.results).toEqual(newResults);
});
```

这类测试看起来比普通成功用例麻烦，但它能覆盖真实用户快速输入、切换筛选、重复点击时最容易出现的问题。

## 回归用例

线上或测试环境出现过的状态问题，最好沉淀成回归用例。

```txt
复现路径 -> 最小 action 序列 -> 测试用例 -> 修复验证
```

如果一个问题只能靠人工点击复现，下一次仍然容易漏。把它转成 action 序列或 Store 测试，才算真正降低了再次发生的概率。

状态问题最值得沉淀成测试的，通常是“有固定输入、有固定流程、有固定结果”的那一类。这样测试一旦建立，后续改动就能更放心。

回归用例可以从线上日志或缺陷单里提炼成最小 action 序列。比如用户路径是“登录 -> 加入购物车 -> 应用优惠券 -> 切换账号 -> 返回购物车”，测试不一定要完整打开浏览器页面，可以先用 Store action 序列复现关键状态变化。

```ts
await authStore.login(userA);
cartStore.addItem(product);
await cartStore.applyCoupon("SUMMER");
await authStore.login(userB);

expect(cartStore.items).toEqual([]);
```

如果这个测试失败，就说明账号切换时购物车清理规则不完整。把这类路径固化下来，比靠人工回忆“上次怎么点出来的”可靠得多。

调试和测试的最终目标不是追求覆盖率数字，而是让状态变化可解释、可复现、可验证。只要能把关键状态流变成可运行的用例，后续重构 Store、换工具或拆分模块时，心里就有底。
