## 状态切分

状态切分要围绕业务边界，而不是围绕文件数量。  
同一生命周期、同一业务域、经常一起更新的数据适合放在一起；无关状态不要为了“集中管理”放进同一个 Store。

复杂度控制的目标不是拆得越碎越好，而是让同一份事实尽量只在一个地方说清楚。边界太碎会增加协调成本，边界太大又会让同步成本失控。

如果两个状态总是一起读取、一起更新、一起失效，它们大概率属于同一个边界。  
如果只是因为“都在首页用到”就放在一起，后续页面变化时会很难拆。

很多复杂度问题其实来自错误分组。按页面位置分组，常常会把不相关的数据绑在一起；按业务边界分组，后续重构和迁移就会容易得多。

切分时不要只看“字段像不像”，要看“变化是否同频”。用户资料和权限字段类型不一样，但经常在登录、刷新、退出时一起变化；商品列表和弹窗开关都出现在购物车页面，但生命周期完全不同。

```text
适合放一起：profile、permissions、sessionExpiredAt
不适合放一起：cartItems、isCouponDialogOpen、hoveredSkuId
```

如果一个 Store 里有很多字段只被一个页面使用，并且离开页面就应该销毁，这些字段大概率不属于全局业务状态。

## 共享边界

共享边界越明确，状态越容易维护。  
不需要跨页面共享的状态，就不要全局化；不需要缓存和失效的数据，就不要放进服务端状态层。

```text
组件状态 -> 父级共享 -> 模块 Store -> 应用 Store -> 服务端缓存
```

这条链路越往右，能力越强，维护成本也越高。

共享状态要尽量少而稳定。短生命周期的 UI 状态一旦进入全局 Store，常常会造成页面离开后状态残留、返回页面后状态不符合预期。

共享边界可以用“影响半径”来判断。组件状态影响当前组件，页面状态影响当前路由，业务 Store 影响多个页面，服务端缓存影响所有读取同一接口数据的位置。影响半径越大，修改入口就越要收口。

```text
影响半径小：直接写
影响半径中：父组件或页面 composable
影响半径大：Store action
影响远端事实：API / Query 工具
```

控制复杂度不是把状态藏起来，而是让每次修改都只影响它应该影响的范围。

## 维护成本

维护成本通常来自三个地方：状态同步、依赖扩散和调试难度。

| 问题 | 表现 |
| --- | --- |
| 状态同步 | 多份数据互相覆盖 |
| 依赖扩散 | 一个字段变化引发大量组件更新 |
| 调试困难 | 不知道是谁改了状态 |

状态越多，不代表架构越好；状态越难说清来源，问题就越多。

真正该优先控制的，是写入口数量和状态来源的清晰度。状态来源越单一，后续调试和测试就越轻松。

复杂度控制的目标不是“少用状态库”，而是让每一份状态都有明确的来源、归属和销毁时机。

维护成本还会来自“隐式同步”。比如 URL 上有筛选条件，Store 里也有筛选条件，组件本地又维护一份输入值，如果没有明确谁是事实来源，很快就会出现刷新、返回、分享链接时状态不一致。

```text
筛选输入框草稿：组件本地
已提交筛选条件：URL
接口结果缓存：Query
```

同一个业务看起来有三份状态并不一定错，关键是它们分别处在不同阶段。草稿、已提交条件、接口结果不是同一份事实；如果把它们混成一个字段，反而更难表达流程。
## 唯一事实来源

复杂度失控最常见的原因，是同一份事实被保存到多个地方。

```ts
// 容易失控：items 和 total 同时保存
set({
  items: nextItems,
  total: nextItems.reduce((sum, item) => sum + item.price, 0),
});
```

如果 `total` 完全由 `items` 得到，就应该派生计算。只有当它来自服务端快照、用户手动调整或有独立生命周期时，才适合保存。

把派生值当事实存储，短期看省事，长期会把同步问题一点点积累起来。统计、数量、汇总这类字段尤其要谨慎。

唯一事实来源不是说“只能有一个变量”，而是说同一层语义的事实只能有一个权威位置。购物车商品是事实，总价是派生；分页参数是事实，列表结果是服务端缓存；表单草稿是事实，提交按钮是否可用是派生。

```ts
const canSubmit = computed(() => {
  return form.name.trim().length > 0 && !submitting.value;
});
```

如果派生值被保存成 state，就要承担同步责任。除非这个值来自服务端快照或有独立修改规则，否则优先派生计算。

## Action 收口

组件不应该到处拼状态更新。复杂业务状态应该通过 action 收口。

```ts
const useCartStore = create((set) => ({
  items: {},
  addItem: (product) =>
    set((state) => ({
      items: addProductToCart(state.items, product),
    })),
  applyCoupon: (code) =>
    set((state) => validateAndApplyCoupon(state, code)),
}));
```

当状态更新规则变复杂时，把规则放进 action 或纯函数里，组件只表达用户意图。这样同一个业务动作从不同入口触发时，行为仍然一致。

组件自己拼更新逻辑，最常见的后果就是这里改了一处，那里漏了一处。把规则收口后，状态变化就更像正式业务动作，而不是散落的赋值语句。

Action 收口不等于所有字段都要有 setter。过多 `setXxx` 只是在 Store 外面套了一层壳，仍然无法表达业务意图。更好的 action 应该描述场景。

```ts
// 不如这样
setCouponCode(code);
setDiscount(discount);
setStatus("ready");

// 更像业务动作
applyCoupon(code);
```

当 action 命名能被产品或测试理解时，状态流通常就更健康。比如 `submitOrder`、`cancelSelection`、`restoreDraft` 比 `updateData` 更容易定位问题。

## 状态分层

不要把所有状态都塞进一个层级。局部状态、页面状态、全局业务状态、服务端状态应有边界。

| 层级 | 示例 | 控制复杂度的方法 |
| --- | --- | --- |
| 组件局部 | 输入中内容、展开状态 | 靠近使用处 |
| 页面状态 | 筛选条件、当前 tab | 页面内收口 |
| 全局业务 | 用户、购物车、权限 | Store action 管理 |
| 服务端状态 | 列表、详情、分页 | Query 工具管理 |

层级混乱时，任何小需求都可能牵动全局 Store。状态分层清楚，改动范围才容易预测。

分层其实是在控制影响半径。局部层出问题，只影响局部；全局层出问题，才需要更谨慎地设计失效和恢复。

状态分层还要和文件分层配合。服务函数不应该直接依赖组件，Store 不应该到处读取 DOM，组件不应该拼接一堆接口协议。每层只知道必要的下一层，复杂度才不会反向扩散。

```text
Component -> Store Action -> Service -> API
Component -> Query Hook -> API
```

如果组件、Store、service 之间互相 import，说明边界已经开始倒流。状态管理复杂度很多时候不是库的问题，而是依赖方向没有管住。

## 副作用隔离

请求、缓存、storage、埋点、路由跳转都属于副作用。副作用混进状态更新，会让逻辑难以复现。

```ts
async function submitOrder() {
  set({ status: "submitting" });

  try {
    const order = await orderApi.submit(get().draft);
    set({ status: "success", order });
  } catch (error) {
    set({ status: "error", error });
  }
}
```

这段代码把副作用放在 action 中，状态更新仍然清楚。如果副作用横跨多个 Store 或所有 action，再考虑中间件、插件或服务层。

副作用越多，越要确保它们不会悄悄改写别的状态。一个副作用最好只做一件事，并有明确的触发和清理位置。

副作用还需要可取消、可重试、可观测。请求可以取消，定时器要清理，storage 写入要容错，埋点失败不应该影响主流程。把这些都塞进组件点击事件里，代码会很快变长。

```ts
actions: {
  async refresh() {
    this.status = "loading";

    try {
      this.data = await api.load();
      this.status = "success";
    } catch (error) {
      this.status = "error";
      this.error = normalizeError(error);
    }
  },
}
```

副作用隔离的目标是让页面能读懂“发生了什么”，而不是让每个页面都重新处理请求细节。

## 增量重构

状态管理不需要一次性设计到完美。更现实的路线是从局部开始，随着共享关系和业务规则变明确再提升。

```txt
组件 state -> 状态提升 -> Context/Store -> 服务端状态工具
```

过早全局化会让简单状态背上复杂工具；过晚抽象会让重复逻辑散落各处。判断时看重复是否真实出现、规则是否稳定、是否有多个入口必须保持一致。

状态管理的成熟，不是一次性设计完美，而是能在问题真的出现时，把状态移动到更合理的位置。这个节奏比追求架构感更重要。

增量重构最好先加测试或最小回归用例。比如先用测试固定“添加商品会合并数量”“应用优惠券会更新折扣和应付金额”，再把组件散落逻辑收口到 Store。这样迁移过程中更容易发现行为漂移。

```text
补测试 -> 收口写入口 -> 移动状态 -> 删除旧同步 -> 复查调用方
```

如果没有测试，也至少先列出关键用户路径：首次进入、刷新、返回、切换账号、失败重试、重复点击。状态管理的复杂度通常就在这些路径里暴露。
