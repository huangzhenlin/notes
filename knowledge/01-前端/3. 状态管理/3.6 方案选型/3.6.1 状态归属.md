## 本地状态

本地状态适合只在当前组件或局部交互里使用的数据。它的优点是简单、局部、易读。

本地状态不是“层级最低”的代名词，而是“最接近使用者”的代名词。只要它还没真正跨出当前组件，就尽量别急着往外推。

```jsx
const [open, setOpen] = useState(false);
```

弹窗开关、局部 tab、临时输入值都优先放本地，不需要为了“统一管理”而上全局 Store。

如果一个状态只是为了让一个按钮亮起来、一个弹窗打开或者一个输入框显示临时值，就没有必要额外上状态库。把简单问题留在局部，往往会更清楚。

如果本地状态不断通过 Props 传给远处组件，才说明它可能需要上移或进入 Store。

本地状态还可以包括“编辑中的草稿”。比如用户资料已经存在 Store 中，但弹窗里正在修改的输入值不一定要立刻写回 Store。可以先在组件里维护草稿，点击保存后再调用 action。

```tsx
function ProfileEditor({ profile }: { profile: UserProfile }) {
  const [draft, setDraft] = useState({
    name: profile.name,
    email: profile.email,
  });

  async function handleSave() {
    await userStore.updateProfile(draft);
  }

  return <button onClick={handleSave}>保存</button>;
}
```

这样 Store 里保存的是“已确认事实”，组件里保存的是“编辑中状态”。两者职责不同，不需要强行合并。

## 全局状态

全局状态适合多个组件、多个页面共享的数据。它的优点是统一来源，缺点是依赖面变大。

登录用户、主题、权限、购物车这类状态通常具备全局性。  
但只要共享范围还能靠 [[3.1.5 状态提升|状态提升]] 解决，就不必急着全局化。

全局状态最怕被当成“方便传值工具”。一旦 Store 里混入大量临时 UI 状态，后续很难判断哪些状态应该持久、哪些应该随页面销毁。

全局状态要有明确的写入入口。比如登录用户可以被很多组件读取，但不应该允许任何组件随意 `setUser`。更好的做法是暴露 `login`、`refreshProfile`、`logout` 这类动作，让状态变化走业务流程。

```ts
const authStore = {
  user: null,
  async login(params) {
    const user = await authApi.login(params);
    set({ user });
  },
  logout() {
    set({ user: null });
  },
};
```

如果一个全局状态只有读取价值，没有跨模块写入需求，也可以考虑 Context、provide/inject 或只读配置对象，不一定非要进 Store。

## 服务端状态

服务端状态适合接口数据、列表缓存、详情信息和需要重新验证的数据。它的核心问题通常不是“怎么同步到全局”，而是“怎么缓存、何时失效、如何重试”。

选状态归属时，优先看生命周期、共享范围和数据来源，而不是先选 Redux、Zustand 或 Pinia。

| 判断问题 | 更可能的归属 |
| --- | --- |
| 只影响当前组件吗 | 本地状态 |
| 多个页面都要读写吗 | 全局状态 |
| 来自接口且会过期吗 | 服务端状态 |
| 能从已有状态算出来吗 | 派生状态 |

服务端状态的典型特征是：它有远端权威来源，会过期，可能需要重新请求，可能被多个页面共享缓存，还可能遇到加载、失败、重试、后台刷新。把这些全塞进普通 Store，往往会重复造一个不完整的 Query 工具。

```tsx
const projectsQuery = useQuery({
  queryKey: ["projects", { page, keyword }],
  queryFn: () => projectApi.list({ page, keyword }),
  staleTime: 30_000,
});
```

Store 仍然可以保存“当前选中的项目 id”“用户设置的筛选偏好”这类客户端事实，而列表数据本身交给服务端状态工具管理。这样前端状态和远端缓存不会混成一团。
## 局部优先

状态归属的第一原则是局部优先。状态只被一个组件使用，就放在这个组件里；只有出现真实共享、复用或生命周期外溢时，才向外移动。

```tsx
function RenameDialog() {
  const [name, setName] = useState("");
  const [open, setOpen] = useState(false);

  return <Dialog open={open}>...</Dialog>;
}
```

弹窗开关、输入中内容、hover、焦点、临时展开状态，都不需要一开始就进全局 Store。全局状态越多，项目越难判断谁能修改它。

局部优先不是拒绝抽象，而是避免过早扩大影响范围。一个状态一旦进入全局 Store，任何组件都有机会读取它，很多人也会默认它应该长期存在。这个语义成本比写一行 `useState` 或 `ref` 高得多。

```vue
<script setup lang="ts">
const activePanel = ref<"base" | "advanced">("base");
</script>
```

如果 `activePanel` 只是当前页面面板状态，留在页面里最清楚；如果它要影响 URL、跨页面恢复或被多个模块读取，再考虑上移。

## 最近归属

多个组件共享状态时，先找最近公共父级；跨层级或跨页面时，再考虑 Context 或 Store。

这样做的核心是先缩短数据路径，再决定是否需要全局化。路径越短，出错点越少，状态更新也越可预测。

```txt
单组件使用 -> 组件 state
兄弟组件共享 -> 最近公共父级
深层稳定依赖 -> Context
跨页面业务状态 -> Store
服务端数据缓存 -> Query 工具
```

这个顺序能避免把所有问题都交给 Store。Store 应该承载稳定业务事实，而不是临时 UI 细节。

最近归属也适合解决“兄弟组件通信”。如果两个兄弟组件共享筛选条件，先把筛选条件放到共同父组件，再通过 props 和事件传递；只有当共享范围继续扩大，才引入 Store。

```tsx
function ProductPage() {
  const [filter, setFilter] = useState({ keyword: "", category: "all" });

  return (
    <>
      <ProductFilter value={filter} onChange={setFilter} />
      <ProductList filter={filter} />
    </>
  );
}
```

这比为了两个组件通信就上全局 Store 更轻。等到筛选条件需要同步 URL、跨页面保留、被顶部导航读取时，再提升也不迟。

## 生命周期判断

状态应该放在哪里，关键看它跟谁同生共死。

| 生命周期 | 典型状态 | 推荐位置 |
| --- | --- | --- |
| 组件卸载即消失 | 输入中内容、展开面板 | 组件 state |
| 页面内多个区域共享 | 筛选条件、选中项 | 页面父组件 |
| 应用级稳定存在 | 当前用户、主题、权限 | Context 或 Store |
| 来自服务端且会刷新 | 列表、详情、分页结果 | Query 工具 |
| 需要跨刷新保留 | 偏好、草稿 | Store + 持久化 |

如果一个状态的生命周期说不清，通常说明它的归属还没想清楚。先写局部状态，等共享关系变真实后再提升，往往比提前全局化更稳。

状态归属的判断顺序最好是：先局部，后父级，再 Context，最后 Store。这样能避免一上来就把本来很小的问题放进重工具里。

还要看销毁时机。搜索页的筛选条件可能离开页面就清空，也可能需要通过 URL 保留；订单草稿可能关闭弹窗后还在，也可能必须立即丢弃。状态归属如果不包含销毁规则，只决定“放哪里”是不够的。

```text
打开弹窗生成 -> 关闭弹窗丢弃：组件状态
页面筛选切换 -> 刷新后保留：URL 或 Store + 持久化
服务端详情 -> 返回页面可复用：Query 缓存
```

生命周期决定了状态的清理策略。很多“状态残留”问题，本质上是状态放到了比它生命周期更长的位置。

## 修改权边界

状态归属不只是“放在哪里”，还包括“谁有资格修改”。能读不代表能写。

```ts
type AuthStore = {
  user: User | null;
  login: (params: LoginParams) => Promise<void>;
  logout: () => void;
};
```

组件可以读取 `user`，但登录态的修改应该通过 `login`、`logout` 这类 action 完成。不要把 `setUser` 暴露给所有组件，否则任何地方都可能绕过鉴权流程直接改登录态。

修改权和读取权分开以后，状态就更接近“受控资源”而不是“公共变量”。这在权限、登录、购物车和草稿类状态里尤其重要。

修改权边界还能减少并发问题。比如订单提交时，组件不应该直接改 `status`，否则多个按钮、快捷键或自动保存可能互相覆盖。由 action 统一处理，就可以在内部判断是否正在提交、是否允许重复触发。

```ts
async function submitOrder() {
  if (get().submitStatus === "submitting") return;

  set({ submitStatus: "submitting" });
  // ...
}
```

状态归属最终要落到“谁读、谁写、何时销毁、谁是事实来源”这四件事。只决定工具，而不决定这些边界，状态仍然会乱。

## 重构信号

状态归属需要随着项目演进调整。出现下面信号时，可以考虑移动状态。

| 信号 | 可能问题 | 调整 |
| --- | --- | --- |
| props 连续传三四层 | 状态位置太低或依赖太深 | 提升、Context、Store |
| 多个页面复制同一请求逻辑 | 服务端状态没有收口 | Query 工具或 API 层 |
| 组件里出现复杂业务流程 | 组件承担过多 | action 或领域服务 |
| Store 里塞满弹窗开关 | 全局状态过度使用 | 回收到页面或组件 |
| 同一事实保存多份 | 状态归属冲突 | 保留唯一事实来源 |

如果状态迁移时发现自己总是在“删字段、补字段、补同步”，通常就是归属早期没想清楚。那时与其继续补丁，不如重新找最近的归属点。

迁移状态时要小步进行：先收敛写入口，再调整读取位置，最后删除旧状态。直接把字段从组件搬到 Store，容易出现新旧两套状态并存。

```text
第一步：把所有写入改成同一个函数或 action
第二步：让读取方逐步改读新的状态来源
第三步：删除旧字段和同步逻辑
```

这个顺序可以降低回归风险。状态管理重构最怕同时换工具、换数据结构、换调用方式，那样出了问题很难定位是哪一层引入的。
