## 插件入口

Pinia 插件用于给所有 Store 增加统一能力，例如持久化、日志、埋点、权限上下文或调试信息。插件通过 `pinia.use()` 注册。

```ts
import { createPinia } from "pinia";

const pinia = createPinia();

pinia.use(({ store }) => {
  store.$onAction(({ name, args }) => {
    console.log(`[pinia action] ${store.$id}/${name}`, args);
  });
});

app.use(pinia);
```

插件适合横切能力。只服务于一个 Store 的逻辑，优先写在这个 Store 的 action 或订阅里，不需要抽成全局插件。

插件函数会在 Store 被创建时执行，可以拿到当前 Store、Pinia 实例、app 和配置上下文。也就是说，插件不是应用启动时“一次性跑完”的工具，而是每个 Store 创建时都会参与 Store 扩展。

```ts
pinia.use(({ app, pinia, store, options }) => {
  console.debug("install plugin for", store.$id, {
    hasApp: Boolean(app),
    hasPinia: Boolean(pinia),
    options,
  });
});
```

理解这个执行时机后，就能解释很多现象：插件注册太晚时，已经创建过的 Store 不一定被扩展；插件里做重逻辑时，每个 Store 都会付出成本；插件依赖外部实例时，要确保这些实例在 Store 创建前已经准备好。

所以插件的第一原则通常不是“能不能做”，而是“值不值得让每个 Store 都经历一次”。一段逻辑只要不具备全局公共价值，就不应该为了复用感硬塞进插件入口。

## 扩展 Store

插件可以给 Store 增加属性或方法，例如统一注入创建时间、重置方法或外部服务。

```ts
pinia.use(({ store }) => {
  const createdAt = new Date().toISOString();

  return {
    createdAt,
    resetState() {
      store.$reset();
    },
  };
});
```

扩展能力要保持克制。全局增加的方法越多，Store 的隐式能力越多，新成员越难判断某个属性来自哪里。

如果扩展的是 router、i18n、analytics client 这类外部实例，最好用 `markRaw()` 避免被 Vue 转成响应式代理。外部类实例通常不需要响应式，强行代理可能带来性能和行为问题。

```ts
import { markRaw } from "vue";

pinia.use(() => {
  return {
    analytics: markRaw(createAnalyticsClient()),
  };
});
```

插件返回对象会被合并到 Store 上，因此命名要尽量避开业务字段。比如 `$analytics`、`$resetToInitialState` 这类带前缀的名字，比 `client`、`reset` 更不容易和 Store 自身属性冲突。

命名带前缀还有一个好处：读代码时能立刻看出“这不是业务 state，而是插件注入的能力”。可见性越强，团队越不容易把插件能力误认成 Store 自身的字段。

## Action 监听

`$onAction` 可以监听 action 开始、成功和失败，适合做日志、性能统计和错误上报。

```ts
pinia.use(({ store }) => {
  store.$onAction(({ name, after, onError }) => {
    const startedAt = performance.now();

    after(() => {
      reportActionTiming({
        store: store.$id,
        action: name,
        duration: performance.now() - startedAt,
      });
    });

    onError((error) => {
      reportActionError({
        store: store.$id,
        action: name,
        error,
      });
    });
  });
});
```

这类逻辑放在插件里比散落在每个 action 中更合适，因为它关注的是所有 Store 的统一行为。

`after` 只在 action 成功完成后触发，`onError` 只在 action 抛错或返回 rejected Promise 时触发。它们适合做“观察”，不适合改变 action 的业务结果。比如记录耗时、上报错误很合理，但在插件里悄悄重试订单提交就会让数据流变得隐蔽。

```ts
store.$onAction(({ name, after, onError }) => {
  after((result) => {
    reportSuccess(store.$id, name, result);
  });

  onError((error) => {
    reportFailure(store.$id, name, error);
  });
});
```

如果日志里包含 action 参数，要注意过滤密码、token、手机号、身份证、支付信息等敏感字段。状态管理插件经常能看到很多上下文，越是全局工具越不能无差别采集。

插件越靠近全局，越要小心它带来的隐式成本。日志、上报、持久化、权限辅助这些能力确实适合统一做，但也意味着它们更容易接触到全站状态和动作，所以默认策略应该偏保守，而不是默认全量记录。

## 使用边界

| 能力 | 是否适合插件 | 原因 |
| --- | --- | --- |
| action 日志 | 适合 | 横切所有 Store |
| 错误上报 | 适合 | 统一处理更稳定 |
| 单个购物车折扣逻辑 | 不适合 | 属于业务 Store 自身 |
| 持久化策略 | 视情况 | 多 Store 统一策略适合插件 |
| 权限上下文注入 | 视情况 | 需要清楚安全边界 |

插件是 Pinia 的扩展点，不是业务逻辑仓库。只要逻辑带有明确业务含义，就优先留在具体 Store 里。

插件的一个实用判断标准是：如果这段逻辑删掉后，业务流程还能跑，只是少了日志、持久化、调试或通用能力，它适合插件；如果删掉后业务本身就不成立，它应该属于 Store、service 或页面流程。
## 插件边界

Pinia 插件用来给 Store 增加横切能力，例如持久化、日志、权限、埋点、调试辅助和外部服务注入。它的核心价值不是“再写一层 Store 逻辑”，而是把所有 Store 都需要的公共能力集中管理。

```ts
pinia.use(({ store }) => {
  store.createdAt = Date.now();
});
```

插件适合处理公共能力，但不适合承载每个 Store 的核心业务流程。真正的状态结构、action 分工和请求策略，仍然应该写在对应 Store 里。

## 扩展属性

插件可以给 Store 注入属性或方法，例如路由器、弹窗管理器、持久化方法、重置函数等。注入后，Store 的使用方就可以直接访问这些能力。

```ts
import { markRaw } from "vue";
import { router } from "./router";

pinia.use(({ store }) => {
  return {
    router: markRaw(router),
    createdAt: new Date().toISOString(),
  };
});
```

外部实例最好用 `markRaw()` 包起来，避免被 Vue 递归响应式转换。注入越稳定，Store 就越像一个可扩展的领域对象，而不是一堆散乱字段的容器。

## 生命周期

插件只对安装之后创建的 Store 生效，且要在 `app.use(pinia)` 之前正确注册。这个顺序很重要，否则插件可能看起来写了，但实际上没有挂到已有 Store 上。

```ts
const pinia = createPinia();
pinia.use(myPlugin);
app.use(pinia);
```

如果项目里有 Nuxt、微前端或延迟加载场景，还要确认 Pinia 实例与插件安装时机。插件逻辑如果依赖 app、router 或外部服务，要保证这些对象已经可用。

## 订阅增强

插件内部可以调用 `$subscribe`、`$onAction`，给每个 Store 统一加日志、统计、持久化或异常上报。

```ts
pinia.use(({ store }) => {
  store.$subscribe((mutation) => {
    console.log(`[pinia] ${store.$id}`, mutation.type);
  });

  store.$onAction(({ name, after, onError }) => {
    const started = performance.now();
    after(() => console.log(name, performance.now() - started));
    onError((error) => console.error(name, error));
  });
});
```

这类代码很适合放在插件里，因为它属于横切关注点。但如果某个逻辑只服务单个 Store，继续放进插件反而会增加隐式性。

## 持久化插件

Pinia 插件最常见的用途之一是持久化。插件可以统一监听 Store 变化，把需要保存的字段同步到本地存储或其他介质。

```ts
pinia.use(({ store }) => {
  const key = `pinia:${store.$id}`;

  store.$subscribe((_mutation, state) => {
    localStorage.setItem(key, JSON.stringify(state));
  });
});
```

持久化插件要控制范围，不要把整个 Store 无脑保存。敏感字段、临时状态和不可序列化对象都不适合直接落盘。更好的做法是允许按 Store 白名单或字段白名单配置。

```ts
type PersistOptions = {
  key?: string;
  paths?: string[];
};

declare module "pinia" {
  export interface DefineStoreOptionsBase<S, Store> {
    persist?: boolean | PersistOptions;
  }
}
```

通过 Store 选项声明持久化规则，比在插件里硬编码 Store id 更容易维护。这样每个 Store 可以自己表达“哪些字段可以保存”，插件只负责执行通用同步逻辑。

## 类型扩展

插件给 Store 注入新属性时，TypeScript 也要知道这些扩展。否则虽然运行时可用，类型上却会一直报错或失去提示。

```ts
declare module "pinia" {
  export interface PiniaCustomProperties {
    createdAt: string;
    router: Router;
  }
}
```

类型扩展越明确，团队就越容易知道哪些属性来自插件，哪些属性来自 Store 自身。这样也能避免把临时挂载当成 Store 原生能力。

如果插件新增的是 state 字段，还需要考虑 DevTools、SSR 序列化和持久化是否能正确识别。很多插件能力适合作为普通属性，而不是 state，因为它们只是工具能力，不应该参与视图渲染。

## 使用原则

插件应当服务稳定公共能力，而不是把 Store 逻辑整体搬过去。可以把它理解为“Store 的基础设施层”。

```text
适合插件：
持久化
日志
埋点
权限辅助
外部服务注入

不适合插件：
核心业务流程
复杂请求编排
页面专属逻辑
跨域名定制规则
```

一旦插件开始依赖大量业务前提，就应该重新评估：这到底是插件，还是一个被误放进全局的业务层。

Pinia 插件最好的形态是“小而稳定”：注册顺序清楚，扩展能力有限，类型声明完整，副作用可开关，生产环境不会泄露敏感数据。它应该让 Store 更容易治理，而不是让每个 Store 多一层猜不透的隐式逻辑。

从长期维护看，插件更像基础设施，而不是业务抽象层。基础设施应当稳定、可预期、低惊喜；一旦插件开始承载太多“只有某个业务才懂”的逻辑，它就不再是在帮项目减负，而是在全局放大复杂度。
