## 派生读取

Getter 是 Pinia 中的派生状态。它从 state 计算结果，组件像读取普通属性一样读取它。

它更像“Store 内部的计算视图”，不是新的事实来源。只要它依赖的 state 没变，getter 的结果就应该保持稳定。

```ts
import { defineStore } from "pinia";

export const useCartStore = defineStore("cart", {
  state: () => ({
    items: [] as Array<{ id: string; price: number; quantity: number }>,
  }),
  getters: {
    totalPrice: (state) =>
      state.items.reduce((sum, item) => sum + item.price * item.quantity, 0),
    itemCount: (state) =>
      state.items.reduce((sum, item) => sum + item.quantity, 0),
  },
});
```

`totalPrice` 和 `itemCount` 都不需要重复保存进 state。只要购物车项变化，getter 会根据依赖重新计算。

Getter 适合表达“从事实状态得到的稳定结果”。它让组件不用知道具体计算过程，也避免多个组件各算各的，最后因为算法略有差异出现展示不一致。

```vue
<script setup lang="ts">
const cartStore = useCartStore();
</script>

<template>
  <p>共 {{ cartStore.itemCount }} 件，合计 {{ cartStore.totalPrice }} 元</p>
</template>
```

如果页面上有多个位置展示总价，统一从 getter 读取，比每个组件自己 reduce 更安全。价格、权限、筛选、格式化这类规则一旦变化，只需要改 Store。

Getter 真正统一的是“读取规则”。状态事实只有一份，但从事实推导出什么业务结果、以什么口径展示，如果散在多个组件里，后面改口径时就很容易出现一半页面已更新、一半页面还停留在旧规则。

## 纯计算

Getter 最重要的原则是纯。它应该只根据已有 state 计算结果，不读写外部变量，不发请求，不操作路由，不写存储。

```text
适合 Getter：
总数
统计
过滤
格式化
提交条件

不适合 Getter：
异步请求
副作用
写 localStorage
触发埋点
修改其他 Store
```

如果一个 getter 写起来越来越像 action，通常说明职责已经偏了。

一个很好用的判断方式是：getter 里如果开始出现请求、定时器、路由、存储写入，那它基本已经跑出边界了。

```ts
// 不推荐：getter 里出现副作用
getters: {
  currentUser(state) {
    localStorage.setItem("lastUserId", state.user?.id ?? "");
    return state.user;
  },
}
```

副作用放进 getter 的问题在于触发时机不稳定。组件读取、DevTools 展开、测试断言都可能触发 getter，最后你很难判断 storage 是什么时候被写入的。需要记录或同步时，应该放到 action、订阅或插件里。

这一点和计算属性的原则完全一致：getter 应该像读取结果，而不是像执行动作。只要一次读取会悄悄改变外部世界，它就不再是安全的派生状态，而会把调试和测试都弄得很别扭。

## 访问其他 Getter

需要访问同一个 Store 内的其他 getter 时，可以使用普通函数写法，通过 `this` 读取。

```ts
export const useCartStore = defineStore("cart", {
  state: () => ({
    items: [] as CartItem[],
    discount: 0,
  }),
  getters: {
    totalPrice: (state) =>
      state.items.reduce((sum, item) => sum + item.price * item.quantity, 0),
    payablePrice(): number {
      return Math.max(this.totalPrice - this.discount, 0);
    },
  },
});
```

使用 `this` 时，TypeScript 通常需要显式标注返回类型，这样 getter 之间的类型推导会更稳定。

箭头函数 getter 更适合只依赖 `state` 的场景；普通函数 getter 更适合访问同 Store 的其他 getter。不要为了统一风格强行全用箭头函数，否则一旦需要 `this`，类型推导会变得别扭。

```ts
getters: {
  subtotal: (state) => state.items.reduce(sumItem, 0),
  tax(): number {
    return this.subtotal * 0.06;
  },
  total(): number {
    return this.subtotal + this.tax;
  },
}
```

Getter 之间可以组合，但组合层级不要太深。`total` 依赖 `tax` 和 `subtotal` 很自然；如果一个 getter 需要串起十几个 getter，可能说明状态模型需要重新拆分。

组合 getter 的目标是复用稳定的小规则，而不是堆出一条很长的依赖链。层级一深，定位性能问题和业务口径问题都会变难，所以更好的方式通常是保留几层关键派生，而不是无限继续往上叠。

## 参数化读取

Getter 本身像计算属性，不直接接收参数。需要按参数查找时，可以让 getter 返回一个函数。

```ts
export const useUserStore = defineStore("user", {
  state: () => ({
    users: [] as Array<{ id: string; name: string; role: string }> ,
  }),
  getters: {
    getUserById: (state) => {
      return (id: string) => state.users.find((user) => user.id === id);
    },
    usersByRole: (state) => {
      return (role: string) => state.users.filter((user) => user.role === role);
    },
  },
});
```

这类 getter 适合封装读取规则，但不要把复杂查询都塞进 getter。大量筛选、排序、分页如果依赖服务端参数，应放到请求层或页面查询逻辑中。

参数化 getter 适合“当前 Store 内部的查找规则”，不适合替代真正的数据查询层。数据量一大、条件一多，还是该回到服务端或专门的数据层。

还要注意，返回函数的 getter 在使用上更像“带 Store 上下文的查询函数”，它的参数本身不参与 Pinia 的 getter 缓存。也就是说，`getUserById("1")` 和 `getUserById("2")` 不是分别缓存两个结果。

```ts
const user = userStore.getUserById(route.params.id as string);
```

如果同一个参数会被大量重复查询，可以考虑把 state 组织成字典，而不是每次都在数组里 `find`。

```ts
state: () => ({
  userMap: {} as Record<string, User>,
}),
getters: {
  getUserById: (state) => (id: string) => state.userMap[id],
}
```

这说明 getter 的性能很多时候取决于底层 state 结构。与其在 getter 层反复优化查找，不如先把状态组织成更适合读取的形式。Pinia 的 getter 擅长表达读取规则，但不应该替状态结构设计兜底。

## 缓存行为

Getter 会缓存计算结果，只有依赖变化时才重新计算。这意味着派生逻辑可以放在 getter 里，但前提是它足够纯，且没有副作用。

```ts
getters: {
  totalPrice: (state) =>
    state.items.reduce((sum, item) => sum + item.price * item.quantity, 0),
}
```

如果一个派生值特别重，可以先考虑拆分 state、把计算挪到更上层，或者让组件自己按需计算。Getter 适合读多写少的纯计算，不适合承担 IO、请求和状态修改。

当 getter 的依赖太多、计算太重时，它就不再是“轻量派生”，而会开始影响渲染性能。这个时候宁可回头简化 state，也不要硬把所有计算都堆在 getter 里。

缓存并不等于免费。Getter 依赖的响应式字段越多，任何一个依赖变化都可能触发重新计算。大列表筛选、复杂排序、树结构递归统计这类逻辑，如果每次渲染都参与计算，仍然可能成为性能热点。

```ts
getters: {
  visibleItems: (state) =>
    state.items
      .filter((item) => item.visible)
      .sort((a, b) => a.priority - b.priority),
}
```

如果 `items` 很大且变化频繁，可以考虑把筛选条件下沉到服务端、维护索引结构，或在 action 更新时预处理必要字段。Getter 适合表达结果，不适合弥补数据结构设计问题。

缓存行为也提醒我们：getter 虽然有缓存，但不是“任何重计算都能无脑放进去”。只要依赖变化频繁、数据量很大、派生逻辑又重，就应该回到数据模型本身看问题，而不是希望 getter 单独扛住所有开销。

## 读取方式

Getter 在组件里像普通属性一样读取即可。

```ts
const cartStore = useCartStore();

console.log(cartStore.totalPrice);
console.log(cartStore.itemCount);
```

如果组件只需要少量派生字段，优先读 Getter，不要把整个 Store 都传来传去。这样可以减少无关字段变化导致的重渲染。

在 `<script setup>` 中如果要解构 getter，仍然使用 `storeToRefs`。Getter 在 Store 上表现为响应式属性，直接解构会拿到当前值快照。

```ts
const cartStore = useCartStore();
const { totalPrice, itemCount } = storeToRefs(cartStore);
```

如果只是事件里即时读取，例如提交前检查一次 `cartStore.canCheckout`，直接访问 Store 属性即可。长期展示用 ref，即时判断读属性，这样代码更自然。

这一点和组件使用方式直接相关。长期渲染关注响应式连接，即时判断关注当前快照，二者语境不同。把这层语境分清后，Getter 在模板和事件里的用法就不会混乱。

## 选择边界

| 场景 | 推荐 |
| --- | --- |
| 总数、统计、格式化 | Getter |
| 提交条件 | Getter |
| 纯筛选、排序 | Getter |
| 发请求、改状态 | Action |
| 复杂业务流程 | Action 或服务层 |

Getter 的作用是让 Store 更像“状态 + 结果”，而不是“状态 + 一堆计算脚本”。

如果 getter 里有大量业务条件分支，也可以考虑先抽成更小的派生函数，再让 getter 去组合它们。这样既保留响应式，又不会让一个 getter 过于臃肿。

```ts
function calculatePayablePrice(items: CartItem[], discount: number) {
  const subtotal = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  return Math.max(subtotal - discount, 0);
}

getters: {
  payablePrice: (state) => calculatePayablePrice(state.items, state.discount),
}
```

这样写还有一个好处：复杂计算可以脱离 Pinia 单独测试。Getter 只负责把 Store state 接到纯函数上，业务算法本身可以用普通单元测试覆盖。

这也是复杂 getter 很值得采用的写法。把业务算法抽到纯函数后，Pinia 只负责响应式接线，算法本身可以独立验证、独立复用，也更不容易因为 Store 结构变化而牵连整段逻辑。
