## 状态分区

Store 组织的第一步不是写代码，而是决定哪些状态应该放在同一个 Store 中。

这一步其实是在画业务边界。Store 不是按页面名来切，也不是按组件名来切，而是按“同一份事实是否经常一起变化”来切。

```ts
const useUserStore = defineStore("user", {
  state: () => ({
    user: null,
  }),
});
```

同一业务域、生命周期相近、经常一起更新的状态更适合放在一起；无关状态硬塞进一个 Store，会让 getter 和 action 都变复杂。

比如用户信息、权限、登录态天然互相关联，而把用户信息和编辑器光标放一起通常就不合理。越能一起复用、一起失效的状态，越适合放进同一个 Store。

更具体地说，同一个 Store 内的状态最好满足“同源、同生命周期、同修改入口”这三个特征。用户资料和权限通常同源于登录接口，退出登录时一起失效，也经常由登录、刷新用户信息这些 action 更新，所以适合放在一个用户 Store 中。购物车、编辑器、工作区则属于另一个生命周期，不应该因为“页面上同时出现”就合并。

```ts
export const useSessionStore = defineStore("session", {
  state: () => ({
    profile: null as UserProfile | null,
    permissions: [] as string[],
    tokenExpiredAt: 0,
  }),
  getters: {
    isLoggedIn: (state) => Boolean(state.profile),
  },
});
```

如果拆分时拿不准，可以先问一句：当这个 Store 需要重置时，里面的字段是否应该一起清空？如果答案经常是否定的，说明边界可能太大。

## 命名原则

Store 命名最好直接对应业务域，而不是页面或技术细节。

```text
更好：
user
cart
editor

不太好：
homePage
buttonState
pageStore
```

清晰命名能让路由、目录和文档更容易对齐。

命名清晰以后，调试时也更容易定位。看到 `useCartStore` 就知道它和购物车有关，而不是得先翻目录猜它到底管什么。

Pinia 的 Store 名称通常有两层：文件导出的 composable 名，例如 `useCartStore`；`defineStore` 的 id，例如 `"cart"`。前者服务代码阅读，后者服务 Pinia 内部标识、DevTools、插件和持久化。两者最好保持一致。

```ts
// stores/cart.ts
export const useCartStore = defineStore("cart", {
  // ...
});
```

不要频繁修改 Store id。项目里一旦接入持久化插件、日志平台或错误上报，Store id 往往会成为外部数据的一部分，随意改名会造成缓存失效或历史日志难以追踪。

## 职责边界

Pinia Store 里适合放共享状态、派生读取和业务动作，不适合放所有东西。

如果把临时 UI 状态也塞进 Store，久而久之 Store 会越来越像“全局垃圾桶”。那样虽然数据都能找到，但真正有价值的业务边界反而看不清了。

```text
适合：
1. 登录信息
2. 购物车
3. 当前工作区
4. 编辑器内容

不适合：
1. 单个输入框光标位置
2. 临时弹窗开关
3. 与页面无关的纯计算函数
```

更容易失控的是“看起来方便”的公共 Store。比如 `useAppStore` 可以保存主题、全局 loading、用户信息、当前菜单、弹窗、工作区、缓存参数，短期很省事，长期会让所有模块都依赖它。公共 Store 不是不能有，但应该只放真正全局且稳定的状态，例如主题、语言、布局偏好。

```text
useAppStore 可以放：
主题
语言
全局布局偏好

不建议继续塞：
用户权限
商品筛选
编辑器内容
某个页面的弹窗状态
```

Store 的职责边界越像业务语言，越容易和产品、接口、测试用例对齐。反过来，如果 Store 只能用“这里存一些公共状态”来解释，通常就是需要继续拆分的信号。

## 业务域拆分

更稳定的拆分方式是围绕业务域，而不是围绕组件层级。

```txt
stores/
  useUserStore.ts
  useCartStore.ts
  useEditorStore.ts
```

用户信息、购物车、编辑器状态分别有自己的生命周期和 action。它们可以在页面中组合使用，但不需要塞进一个巨大的 `useAppStore`。

把 Store 按业务域拆开以后，每个域的测试、持久化、失效和调试也能独立演进。出了问题时，你不用先排查整个应用状态树。

一个更接近工程项目的目录可以这样组织：

```text
src/
  stores/
    session.ts
    cart.ts
    workspace.ts
    editor.ts
```

如果某个业务域继续变复杂，可以再在目录内拆实现文件，但对外仍然暴露一个 Store 入口。

```text
src/
  stores/
    cart/
      index.ts
      pricing.ts
      normalize.ts
```

这里的 `pricing.ts`、`normalize.ts` 可以是纯函数或服务封装，不一定都要变成 Store。Pinia Store 负责状态边界，业务计算可以拆出去，以免 action 越写越长。

## 组合方式

大型项目可以按业务域拆多个 Store，也可以用较小 Store 组合出页面能力。

| 方式 | 适合场景 | 风险 |
| --- | --- | --- |
| 单 Store | 小应用、状态少 | 逐渐膨胀 |
| 多 Store | 业务域清晰 | 跨 Store 协调增多 |
| 按页面拆分 | 只适合临时页面逻辑 | 可复用性差 |

选择哪种方式，取决于状态是否真的共享，而不是目录看起来是否整齐。

如果某个 Store 的职责还在变化，先保持小而明确通常比一次性设计得很大更稳。后面真的长起来了，再按业务域继续拆也不迟。

实际项目里常见的是“业务 Store + 页面局部状态”组合。比如订单详情页会同时使用用户 Store、订单 Store、权限 Store，但展开面板、当前激活 Tab、临时筛选关键字仍然可以留在组件或页面 composable 中。

```vue
<script setup lang="ts">
const orderStore = useOrderStore();
const permissionStore = usePermissionStore();

const activeTab = ref("detail");
const isRemarkEditorOpen = ref(false);
</script>
```

这能避免把页面交互细节污染到业务 Store，也能让 Store 更容易在别的页面复用。

## 跨 Store 协作

跨 Store 调用要克制。偶尔读取另一个 Store 的快照可以接受，但如果两个 Store 长期互相依赖，说明边界可能划错了。

```ts
const useCheckoutStore = create((set) => ({
  submit: async () => {
    const user = useUserStore.getState().profile;
    const items = useCartStore.getState().items;

    await checkoutApi.submit({ userId: user.id, items });
    set({ status: "success" });
  },
}));
```

结算流程读取用户和购物车是合理的；但如果购物车 action 经常修改用户 Store，用户 action 又经常修改购物车 Store，就应该考虑抽出更高层的业务流程或重新划分 Store。

跨 Store 协作最好保留“只读快照”思路。读取别的 Store 没问题，但修改对方状态要很谨慎，否则边界会越来越模糊。

Pinia 中跨 Store 调用应该使用 Pinia 的写法，而不是混入其他库的 API。比如结算 Store 可以在 action 内调用用户 Store 和购物车 Store：

```ts
export const useCheckoutStore = defineStore("checkout", {
  state: () => ({
    submitting: false,
  }),
  actions: {
    async submit() {
      const userStore = useUserStore();
      const cartStore = useCartStore();

      this.submitting = true;
      try {
        await checkoutApi.submit({
          userId: userStore.profile!.id,
          items: cartStore.items,
        });
        cartStore.clear();
      } finally {
        this.submitting = false;
      }
    },
  },
});
```

跨 Store 修改不是禁忌，但要表达清楚谁是流程的发起者。上面的结算 Store 负责结算流程，购物车 Store 只暴露 `clear` 这样的明确动作，这比直接在外部改 `cartStore.items = []` 更稳。

## 协作信号

当 Store 之间出现以下情况时，通常意味着该重新整理边界：

1. 互相调用太频繁。
2. action 命名开始含糊。
3. 某个 Store 逐渐变成万能容器。
4. 页面调试时很难判断状态归属。

Pinia 的轻量并不代表可以把所有状态混在一起。边界清楚，Store 才能长期可维护。

如果一个 Store 的名字越来越像“misc”“common”“app”，通常就是边界开始失控了。那时最该做的往往不是继续加字段，而是重新分区。

还有一种信号是测试开始变难。一个 action 为了测试需要准备五六个无关字段，或者必须同时 mock 多个不相关接口，通常说明 Store 承担的职责过宽。好 Store 的测试前置条件应该和业务动作直接相关，而不是被大量全局状态拖住。
