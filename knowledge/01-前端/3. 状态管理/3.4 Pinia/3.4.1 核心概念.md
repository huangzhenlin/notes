## Store

Pinia 的 Store 是 Vue 应用中的状态容器。每个 Store 通常对应一个业务域，例如用户、购物车、权限或编辑器。

它的价值不只是“集中存状态”，而是把业务域里的事实、派生值和动作放到同一个可追踪的单元里。对读代码的人来说，Store 往往就是这一块业务的入口。

```ts
import { defineStore } from "pinia";

export const useUserStore = defineStore("user", {
  state: () => ({
    profile: null as User | null,
  }),
});
```

Store 接入了 Vue 的响应式系统，组件读取后会在状态变化时自动更新。

这意味着 Store 不是一个普通对象，而是一个会驱动视图更新的响应式边界。理解这一点后，组件里就不该随意改深层字段，而应该通过 action 或明确的方法收口。

`defineStore` 的第一个参数是 Store 的唯一标识，通常会出现在 DevTools、持久化 key、日志和调试输出里。这个标识不只是一个随手写的字符串，它应该稳定、简短，并且和业务域一致。

```ts
// 好：能直接看出业务域
defineStore("cart", { /* ... */ });

// 不好：和页面或实现细节绑定过深
defineStore("homePageRightPanelCartState", { /* ... */ });
```

Pinia 的轻量感容易让人把它当成“全局变量增强版”，但更准确的理解是：每个 Store 都是一块业务域状态的边界。边界清楚时，组件只需要知道“我要调用哪个 Store 的哪个动作”；边界混乱时，任何页面都可能绕过规则直接改状态，后期排查会变得很像追线团。

所以使用 Pinia 的第一步通常不是“先建一个 stores 目录”，而是先问清楚：这块业务到底有哪些稳定事实、有哪些明确动作、哪些状态应该共享、哪些只属于组件。Store 不是为了统一存放变量，而是为了统一业务语义。

## State

State 保存 Store 的基础事实。Option Store 中的 `state` 必须写成函数，返回初始状态对象。

```ts
export const useCartStore = defineStore("cart", {
  state: () => ({
    items: [] as CartItem[],
    couponCode: "",
  }),
});
```

State 里应该放“需要保存的事实”，不要把总价、过滤结果、按钮是否可点击这类派生值重复放进去。

如果一个值能从 state 直接算出来，通常就该留给 getter；如果它只和当前组件短暂交互有关，就不该硬塞进 Store。Store 越像事实库，后续更新就越简单。

判断一个字段是否该进 state，可以看它是否满足三个条件：是否需要被多个位置读取，是否需要跨组件或跨页面保持一致，是否无法从其他字段稳定推导出来。比如购物车商品列表是事实，总价是推导；当前用户权限列表是事实，“是否能进入管理页”通常是推导。

```ts
state: () => ({
  // 事实：来自用户选择或服务端返回
  items: [] as CartItem[],
  couponCode: "",

  // 不推荐：可以从 items 计算出来
  // totalPrice: 0,
})
```

State 越少，更新路径越短；State 越多，越容易出现“两个字段表达同一件事，但没有同步更新”的问题。Pinia 不会自动替你判断事实和派生，这个边界需要在建模时先想清楚。

很多 Store 后期难维护，不是因为字段多，而是因为事实和派生混在一起。比如同时存 `items`、`selectedItems`、`selectedCount`、`canSubmit`，一旦其中几项本来就可以从别的字段算出来，后续就很容易出现同步遗漏。

## Getter

Getter 是基于 state 的派生读取，类似 Vue 的 computed。

```ts
export const useCartStore = defineStore("cart", {
  state: () => ({
    items: [] as CartItem[],
  }),
  getters: {
    totalPrice: (state) =>
      state.items.reduce((sum, item) => sum + item.price * item.quantity, 0),
  },
});
```

Getter 让组件读取结果，而不是在每个组件里重复写计算逻辑。复杂计算收口后，也更容易测试。

对于购物车、筛选面板、权限判断、提交按钮可用状态这类“读多写少”的结果，getter 尤其合适。它让组件更专注于展示，而不是到处重复业务计算。

Getter 应尽量保持纯计算：只读取 state 或其他 getter，不发请求、不写 storage、不改路由、不触发埋点。这样它才像 Vue 的 `computed` 一样可预测。需要副作用时，应该把逻辑放进 action。

```ts
getters: {
  canCheckout: (state) =>
    state.items.length > 0 && state.items.every((item) => item.stock > 0),
}
```

如果 getter 需要接收参数，可以返回一个函数，但这只适合 Store 内部的小规模查找。复杂筛选、分页、搜索如果本质上依赖服务端数据，就不应该用 getter 假装成本地查询系统。

这条边界很重要。getter 擅长本地派生，不擅长替代完整数据层。只要一个结果已经依赖分页、筛选、缓存失效、后台刷新，那它就更接近服务端状态问题，而不只是“从 state 里算个值”。

## Action

Action 负责修改状态和编排业务流程。它可以是同步函数，也可以是异步函数。

```ts
export const useUserStore = defineStore("user", {
  state: () => ({
    profile: null as User | null,
    status: "idle" as "idle" | "loading" | "success" | "error",
  }),
  actions: {
    async loadProfile() {
      this.status = "loading";

      try {
        this.profile = await userApi.getProfile();
        this.status = "success";
      } catch {
        this.status = "error";
      }
    },
  },
});
```

组件应该调用 `loadProfile` 这样的 action，而不是在组件里拼接口请求和状态修改。这样多个入口触发同一流程时，行为能保持一致。

把请求和状态修改放进 action，最大的好处是流程稳定。无论是页面首次进入、手动刷新还是别的组件触发，都走同一套入口，后面修 bug 也只需要改一处。

Action 不是只能“改一个字段”的 setter，它更适合表达一段业务动作。一个好的 action 名字通常描述用户或系统动作，例如 `login`、`submitOrder`、`refreshProfile`、`applyCoupon`。如果 action 名字全是 `setXxx`，Store 可能只是被当成了可写对象，而没有承担流程收口。

```ts
actions: {
  async applyCoupon(code: string) {
    this.status = "checking";

    const coupon = await couponApi.validate(code);
    this.couponCode = coupon.code;
    this.discount = coupon.discount;
    this.status = "ready";
  },
}
```

异步 action 要明确处理 loading、错误和重复触发。尤其是按钮连点、路由切换、请求返回顺序不稳定这些情况，组件里临时处理往往会散，放进 action 才能统一约束。

Action 是否设计得好，往往决定了 Store 最终是“状态边界”还是“全局变量集合”。好的 action 让组件只表达意图，不必关心底层请求、异常和收尾；差的 action 则只是把 `store.xxx = value` 包了一层名字。

## 组件集成

在 Vue 组件中，Store 可以直接调用。解构 state 和 getter 时用 `storeToRefs` 保持响应式。

```vue
<script setup lang="ts">
import { storeToRefs } from "pinia";
import { useUserStore } from "@/stores/user";

const userStore = useUserStore();
const { profile, status } = storeToRefs(userStore);
const { loadProfile } = userStore;
</script>
```

Action 是方法，可以直接解构；state 和 getter 是响应式数据，长期解构时要通过 `storeToRefs`。

这点在大型组件里很关键。很多 Pinia 的响应式丢失问题，不是 Store 设计错了，而是把 state 直接解构后当成普通变量用了。

```ts
const userStore = useUserStore();

// 不推荐：profile 会失去和 store 的响应式连接
const { profile } = userStore;

// 推荐：profile 仍然是 ref
const { profile } = storeToRefs(userStore);

// action 可以直接解构
const { loadProfile } = userStore;
```

在模板里长期展示 state 和 getter 时，优先用 `storeToRefs`；在事件处理或普通函数里只读取一次时，直接访问 `userStore.profile` 更清晰。两种写法没有绝对优劣，关键是不要把响应式值误解成普通快照。

这也是 Pinia 和普通对象最容易混淆的地方。Store 看起来像对象，但读法其实分“要不要持续响应式”两种语境。长期展示和联动用 `storeToRefs`，一次性读取和动作调用直接访问实例，思路会更清楚。

## 与 Vue 组件状态

Pinia 适合管理跨组件、跨页面共享的业务状态。组件内部的展开状态、hover 状态、局部输入草稿，不一定要放进 Pinia。

如果所有状态都进 Store，调试入口虽然统一了，但局部组件会变得更难复用。

更稳的做法是先让局部状态留在组件里，等它真的需要跨组件共享、跨页面复用或重启恢复时，再把它提升到 Store。这样不会把简单组件过早卷进全局状态。

```vue
<script setup lang="ts">
const isOpen = ref(false); // 只影响当前下拉框，留在组件内即可

const userStore = useUserStore(); // 登录用户会影响多个页面，放在 Pinia 更合理
</script>
```

服务端状态也不要一股脑塞进 Pinia。接口列表、分页缓存、重试、失效、后台刷新这类问题，本质上更接近 [[3.1.8 服务端状态|服务端状态]]。Pinia 可以保存当前选中的业务上下文，但不一定要自己承担完整的数据缓存系统。

换句话说，Pinia 更适合做“当前用户是谁”“当前组织是哪个”“当前筛选条件是什么”“当前表单草稿是什么”这类应用级或业务级共享状态；而“接口列表如何缓存、何时失效、是否保留旧数据”则应当交给更专门的数据层模型。

## 与 Vuex

Pinia 可以理解为 Vuex 的现代替代方案。它移除了 mutation 概念，让 action 可以直接修改 state，同时提供更好的 TypeScript 推导和组合式 API 体验。

```text
Vuex: state -> getter -> mutation -> action
Pinia: state -> getter -> action
```

概念减少不代表边界可以放松。大型项目仍然需要清晰的 Store 命名、action 设计、持久化策略和测试。

Pinia 的“轻”只是 API 层面更轻，不代表项目治理可以更轻。Store 越多，命名、职责、失效和订阅越要统一，否则它很快也会变成另一种混乱的中心。

从 Vuex 迁移到 Pinia 时，不需要机械保留 mutation 思维。原来 `commit("setUser")` 加 `dispatch("loadUser")` 的组合，可以收敛成一个 action；原来过度拆散的 mutation，也可以直接变成 action 内部的状态赋值。

```ts
// Pinia 更鼓励把动作写成业务流程
await userStore.loadProfile();
```

不过，少了 mutation 并不意味着所有组件都应该直接写 `store.xxx = value`。对外暴露 action，内部再决定怎么改 state，仍然是更容易维护和测试的方式。

Pinia 把概念做轻了，但并没有取消边界本身。少了 mutation，并不等于少了设计要求；相反，越轻的 API 越需要团队主动保持命名、职责和更新入口的一致性。
