## 持久化范围

Pinia 本身不强制提供持久化方案，项目里通常通过插件或手写订阅把状态同步到 `localStorage`、`sessionStorage` 或其他存储中。持久化前先确定哪些字段真的需要跨刷新保留。

| 状态 | 是否适合持久化 | 原因 |
| --- | --- | --- |
| 主题、语言、布局偏好 | 适合 | 用户偏好需要长期保留 |
| 购物车草稿 | 视业务而定 | 未登录购物车常需要保留 |
| 表单临时草稿 | 视业务而定 | 长表单、编辑器适合保存 |
| loading、error | 不适合 | 属于瞬时 UI 状态 |
| token、密码、敏感信息 | 不适合 | 存储泄漏风险高 |

持久化不是“把整个 Store 存起来”，而是选择有长期价值、可恢复、低敏感的字段。

选择字段时，要先区分“刷新后还应该存在”和“刷新后应该重新计算”。主题、语言、草稿属于用户预期会保留的状态；loading、错误提示、接口临时结果通常应该在刷新后重新开始。把瞬时状态持久化下来，反而会让用户刷新后看到过期错误或卡在 loading。

```ts
type PersistedSetting = {
  theme: "light" | "dark" | "system";
  locale: "zh-CN" | "en-US";
};
```

持久化字段越少，恢复越可靠。尤其是 Store 里有 Date、Map、Set、File、AbortController、函数或类实例时，直接 `JSON.stringify` 会丢信息或失败，应该只保存可序列化的数据。

## 持久化位置

常见持久化介质包括本地存储、会话存储和后端同步。保存位置越靠近浏览器，读取越方便，但安全和一致性越要谨慎。

```text
优先级不是绝对的：
1. 用户偏好 -> 本地存储
2. 草稿 -> 本地或后端草稿
3. 关键交易数据 -> 后端
```

`localStorage` 生命周期长，适合主题、语言、布局偏好；`sessionStorage` 随标签页会话结束而清理，更适合一次会话内的临时步骤；IndexedDB 适合较大、结构更复杂的数据，但接入成本更高。无论选哪种浏览器存储，都不能把它当成安全存储。

```text
localStorage：小体积、长期偏好
sessionStorage：一次会话内状态
IndexedDB：较大结构化离线数据
服务端：关键业务事实
```

如果数据和账号强绑定，例如地址、订单、会员权益，最终权威来源应该是服务端。本地持久化最多用于提升体验，不能替代服务端事实。

## 订阅写入

可以通过 `$subscribe` 监听 Store 变化，再把必要字段写入 storage。

```ts
const cartStore = useCartStore();

cartStore.$subscribe((mutation, state) => {
  localStorage.setItem(
    "cart",
    JSON.stringify({
      items: state.items,
      updatedAt: Date.now(),
    }),
  );
});
```

这种方式简单直接，但要注意写入频率。高频输入、拖拽、编辑器状态最好做节流，避免每次微小变化都写 storage。

实际写入时更推荐保存白名单字段，而不是整个 state。这样 Store 后续新增临时字段时，不会被持久化插件自动写入。

```ts
cartStore.$subscribe((_mutation, state) => {
  const snapshot = {
    version: 1,
    items: state.items.map((item) => ({
      id: item.id,
      quantity: item.quantity,
    })),
  };

  localStorage.setItem("cart", JSON.stringify(snapshot));
});
```

如果状态变化很频繁，可以在订阅回调里做防抖或节流。对编辑器、拖拽排序这类场景，按固定间隔保存比每次输入都保存更稳。

## 恢复时机

恢复通常发生在应用初始化阶段。恢复太晚，组件可能已经读取过默认值，再被持久化数据覆盖，造成闪动或状态错乱。

```ts
const store = useSettingStore();
store.$patch(loadFromStorage());
```

浏览器存储只能在客户端读取，SSR 场景里不能假设初始化时一定可用。

恢复前要先做解析和校验，不能默认 `localStorage` 里的 JSON 一定合法。用户可能手动改 storage，旧版本可能留下不兼容结构，浏览器也可能因为隐私模式或配额限制导致读写异常。

```ts
function loadSetting(): Partial<SettingState> {
  try {
    const raw = localStorage.getItem("setting");
    if (!raw) return {};

    const parsed = JSON.parse(raw) as unknown;
    if (!isPersistedSetting(parsed)) return {};

    return parsed;
  } catch {
    return {};
  }
}
```

恢复动作最好尽早发生，但不要早到依赖对象还不可用。比如需要读取 `window` 的逻辑只能在客户端执行；需要用户 id 作为 key 的缓存，也要等账号上下文明确以后再恢复。

## 版本迁移

状态结构变化后，旧缓存可能无法直接使用。可以在持久化数据里保存版本号。

```ts
type PersistedCartV2 = {
  version: 2;
  items: CartItem[];
};
```

```ts
function migrateCart(raw: unknown): PersistedCartV2 {
  if (isCartV2(raw)) return raw;

  if (isCartV1(raw)) {
    return {
      version: 2,
      items: raw.products.map((product) => ({
        id: product.id,
        price: product.price,
        quantity: product.count,
      })),
    };
  }

  return { version: 2, items: [] };
}
```

没有迁移策略时，最保守的做法是清空旧缓存并重新初始化。对用户关键数据，例如草稿、购物车、编辑器内容，迁移比清空更合适。

版本迁移最好只处理“已知旧版本”。遇到未知版本时，不要强行猜结构。比如从 v1 到 v2 可以迁移 `count` 到 `quantity`，但如果拿到 v99，说明缓存可能来自未来版本或异常数据，此时清空或提示重新加载更安全。

```ts
function migrate(raw: unknown): PersistedCartV2 {
  if (isV2(raw)) return raw;
  if (isV1(raw)) return migrateV1ToV2(raw);

  return {
    version: 2,
    items: [],
  };
}
```

迁移代码也属于业务逻辑，不能只在插件里随便写几行。草稿、购物车、离线编辑这类用户会感知的数据，迁移失败会直接影响体验。

## 失效处理

持久化数据也会过期。登录态、权限、主题偏好、草稿状态的失效规则都可能不同，不能一股脑长期保留。

```text
需要重新处理的情况：
1. 切换账号
2. 修改密码
3. 服务端版本升级
4. 本地缓存结构升级
```

持久化不是安全边界。敏感 Token、权限判断和服务端校验结果，都不应该因为“本地还存着”就被默认信任。

账号切换是最容易遗漏的失效点。A 用户的本地草稿、购物车、筛选条件不一定能直接给 B 用户使用。缓存 key 至少要考虑用户维度，退出登录时也要明确清理哪些数据。

```ts
const key = userId ? `cart:${userId}` : "cart:guest";
```

如果权限、会员等级、价格规则来自服务端，本地持久化只能保存展示偏好或草稿，不能保存最终授权结论。安全判断仍然要回到服务端，前端最多做体验层面的预判断。

## 使用边界

Pinia 持久化最适合的是“可恢复、低敏感、用户明确预期会保留”的状态。

| 场景 | 建议 |
| --- | --- |
| 用户偏好 | 持久化 |
| 长表单草稿 | 视情况持久化 |
| 服务端缓存 | 不优先 |
| 登录凭证 | 不直接持久化 |
| 瞬时 UI 状态 | 不持久化 |

持久化只是状态生命周期的一段，不是状态管理的全部。 

使用第三方持久化插件时也要先看清它的默认行为：是否默认保存整个 Store，是否支持字段白名单，是否支持自定义 storage，是否支持 SSR，是否支持 before/after restore 钩子。默认配置越“省事”，越要小心无意中保存了不该保存的字段。

Pinia 持久化可以让体验更顺滑，但它带来的问题也很实在：缓存污染、旧版本迁移、敏感信息泄露、跨账号串数据、恢复时机不稳定。只要这些边界提前设计好，持久化才会从“偶尔制造玄学 bug 的工具”变成可靠的体验增强。
