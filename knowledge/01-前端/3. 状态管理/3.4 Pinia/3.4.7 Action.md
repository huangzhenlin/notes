## 同步 Action

Action 是 Pinia 中修改 state 和表达业务动作的主要入口。同步 action 适合处理本地状态变化。

Action 的意义不只是“能改状态”，而是把“怎么改”收口成统一入口。对外看，组件调用的是业务动作；对内看，Store 负责具体更新细节。

```ts
export const useCartStore = defineStore("cart", {
  state: () => ({
    items: [] as CartItem[],
  }),
  actions: {
    addItem(product: Product) {
      const item = this.items.find((current) => current.id === product.id);

      if (item) {
        item.quantity += 1;
      } else {
        this.items.push({
          id: product.id,
          name: product.name,
          price: product.price,
          quantity: 1,
        });
      }
    },
  },
});
```

组件调用 `addItem(product)`，不需要知道购物车是数组、字典还是其他结构。Action 把状态更新规则收口起来。

这样做的好处是，购物车怎么存、商品怎么合并、数量怎么累加，都能集中调整，不用改一堆页面。Action 本质上就是状态写入的业务接口。

同步 action 也适合做数据归一化。组件传入的是后端商品、搜索结果或表单数据，Store 可以在 action 里把它转换成内部状态结构。

```ts
actions: {
  addItem(product: Product) {
    const cartItem: CartItem = {
      id: product.skuId,
      title: product.title.trim(),
      price: Number(product.price),
      quantity: 1,
    };

    this.mergeItem(cartItem);
  },
  mergeItem(input: CartItem) {
    const item = this.items.find((current) => current.id === input.id);
    if (item) item.quantity += input.quantity;
    else this.items.push(input);
  },
}
```

这样组件不需要知道 Store 内部到底按 `skuId`、`id` 还是组合 key 管理商品。内部结构变化时，组件调用方式也能保持稳定。

这就是 action 作为“写入边界”的意义。组件只负责表达业务意图，Store 决定内部怎么落地。只要写入边界稳定，后续无论是数组改字典、增加字段校验，还是补充统计逻辑，影响范围都会小很多。

## 业务流程封装

Action 很适合封装一个完整业务流程，而不是只写单个字段修改。比如提交表单时，页面不应该同时关心 loading、请求、错误和成功后的状态收敛，这些可以放进 Store 的 action 里统一处理。

```ts
export const useProfileStore = defineStore("profile", {
  state: () => ({
    form: { name: "", email: "" },
    submitting: false,
    errorMessage: "",
  }),
  actions: {
    async submitProfile() {
      this.submitting = true;
      this.errorMessage = "";

      try {
        await updateProfile(this.form);
      } catch (error) {
        this.errorMessage = "保存失败，请稍后重试";
        throw error;
      } finally {
        this.submitting = false;
      }
    },
  },
});
```

页面侧只需要调用 `submitProfile`，不用重复维护请求过程中的状态。

把完整流程放进 action 后，页面就可以更轻地专注于表单展示、按钮禁用和结果跳转。复杂流程集中到 store，页面就不会长成“半个服务层”。

业务流程 action 要注意“事务感”。虽然前端没有数据库事务，但可以通过明确的状态顺序减少半成功状态。比如先校验，再进入 loading，请求成功后一次性更新关键 state，请求失败时回滚或保留草稿。

```ts
actions: {
  async saveDraft() {
    if (!this.form.name.trim()) {
      this.errorMessage = "名称不能为空";
      return false;
    }

    this.submitting = true;
    try {
      const saved = await profileApi.save(this.form);
      this.profile = saved;
      this.dirty = false;
      return true;
    } finally {
      this.submitting = false;
    }
  },
}
```

这里 action 返回布尔值给页面判断是否关闭弹窗，但状态更新仍然由 Store 自己完成。

这种“Store 负责状态，组件根据返回值决定下一步交互”的分工通常很稳。页面只关心要不要跳转、要不要关闭弹窗、要不要展示 toast，而不需要再参与底层状态收敛。

## 异步 Action

Pinia action 可以直接写成异步函数，适合封装请求、提交和流程编排。

```ts
export const useProfileStore = defineStore("profile", {
  state: () => ({
    profile: null as UserProfile | null,
    status: "idle" as "idle" | "loading" | "success" | "error",
    error: "",
  }),
  actions: {
    async loadProfile() {
      this.status = "loading";
      this.error = "";

      try {
        this.profile = await profileApi.getProfile();
        this.status = "success";
      } catch (error) {
        this.status = "error";
        this.error = error instanceof Error ? error.message : "加载失败";
      }
    },
  },
});
```

这种写法适合“请求结果会影响 Store 状态”的场景。如果只是按钮点击后局部提交，且结果不需要跨组件共享，组件内处理也可以更简单。

异步 action 最适合和服务端状态、请求状态一起看。它负责发起动作、更新状态、收敛结果，而不是单纯当成一个 fetch 包装器。

异步 action 还要处理并发返回顺序。用户快速切换筛选条件时，旧请求可能比新请求更晚返回，如果不做保护，旧数据会覆盖新数据。

```ts
actions: {
  async loadUsers(keyword: string) {
    const requestId = ++this.latestRequestId;
    this.status = "loading";

    const users = await userApi.search(keyword);

    if (requestId !== this.latestRequestId) return;

    this.users = users;
    this.status = "success";
  },
}
```

如果请求工具支持取消，也可以结合 `AbortController`。关键是 action 要对“重复触发”有预期，而不是假设请求永远按发起顺序返回。

对于搜索、筛选、自动保存和切页加载这类高频动作，这一点尤其重要。Pinia action 虽然写起来简单，但只要涉及异步，就应该默认存在并发和竞态，不要等到 UI 出现“旧结果覆盖新结果”才回头补保护。

## 返回值

Action 可以返回结果。返回值适合表达调用方需要立即知道的结果，例如提交是否成功、创建后的 id、服务端返回的详情。

```ts
actions: {
  async createProject(input: CreateProjectInput) {
    const project = await projectApi.create(input);

    this.projects.push(project);

    return project.id;
  },
}
```

组件可以根据返回值跳转页面，但不要让组件重复修改 Store。

如果 action 已经负责更新 Store，组件就只负责用返回值做下一步，比如跳转、提示或关闭弹窗。职责分开后，后续排错更容易。

```ts
const projectId = await projectStore.createProject(form);
router.push(`/projects/${projectId}`);
```

Action 更新 Store，组件处理路由跳转，这样职责更清楚。

返回值不应该变成另一套状态来源。比如 action 返回了创建后的项目，同时也写入 `this.projects`，组件就不要再自己 `projects.push(project)`。否则一个流程会产生两条写入路径。

```ts
const projectId = await projectStore.createProject(form);
router.replace({ name: "project-detail", params: { id: projectId } });
```

如果调用方只需要知道成功与否，返回 `true / false` 或直接抛错都可以；如果调用方需要下一步参数，返回 id 或精简对象更合适。不要把完整响应对象随意暴露给组件，让组件继续依赖后端返回结构。

返回值设计得越克制，组件和后端的耦合就越低。action 更适合返回“下一步所需信息”，而不是把原始接口响应整包暴露出去，否则组件很快又会开始依赖接口字段细节。

## 错误处理

Action 里可以处理业务错误，但不要把所有异常都吞掉。界面需要知道是校验失败、接口失败还是网络失败，才能给出正确反馈。

```ts
actions: {
  async submitOrder() {
    this.submitStatus = "submitting";

    try {
      const order = await orderApi.submit(this.draft);
      this.submitStatus = "success";
      return order;
    } catch (error) {
      this.submitStatus = "error";
      this.submitError = normalizeError(error);
      throw error;
    }
  },
}
```

如果页面需要展示 Store 中的错误，action 内要写入 `submitError`；如果错误只影响当前按钮或弹窗，也可以由调用方捕获处理。

错误处理最怕“吞了又没提示”。action 可以决定是把错误留给调用方，还是在 Store 里保留一个可展示的错误状态，但不能让错误悄悄消失。

可以把错误分成两类：可展示错误和不可恢复异常。表单校验失败、库存不足、权限不足通常需要给用户明确提示；代码异常、未知响应结构更应该上报，并给出兜底反馈。

```ts
actions: {
  async submitOrder() {
    try {
      return await orderApi.submit(this.draft);
    } catch (error) {
      const normalized = normalizeOrderError(error);
      this.submitError = normalized.message;

      if (normalized.shouldReport) {
        reportError(error);
      }

      throw normalized;
    }
  },
}
```

Action 抛错并不等于没处理。它可以先记录 Store 状态，再把错误交给组件决定是否弹 toast、关闭弹窗或停留当前页面。

可以把 action 的错误处理理解成两层：第一层是把 Store 自己需要记录的状态收好，比如 `status`、`errorMessage`、回滚结果；第二层才是决定要不要把异常继续抛给页面，让页面做交互层反馈。

## 跨 Store 调用

Action 中可以使用其他 Store，但要保持依赖方向清楚。

```ts
actions: {
  async submitCheckout() {
    const userStore = useUserStore();
    const cartStore = useCartStore();

    await checkoutApi.submit({
      userId: userStore.profile.id,
      items: cartStore.items,
    });

    cartStore.clear();
  },
}
```

结算 action 调用用户和购物车是合理的业务流程。如果多个 Store 互相调用越来越多，应该考虑抽出更明确的流程 Store 或服务层。

当一个 action 里面已经开始像编排器一样组织多个 Store、多个接口和多个步骤时，它就不只是“状态修改”，而是业务流程控制了。这时候抽服务层往往更合适。

跨 Store 调用最好保持单向依赖。比如 checkout 读取 user 和 cart 很合理，但 user Store 不应该反过来频繁调用 checkout Store。依赖方向清楚，测试和调试都会简单很多。

```text
推荐方向：
checkout -> user
checkout -> cart

危险方向：
user <-> checkout
cart <-> checkout
```

如果两个 Store 互相调用是因为它们共同参与同一个流程，通常可以抽出一个流程 action 或领域服务，让两个 Store 各自只暴露清晰动作。

Store 之间长期互调，往往说明“流程层”缺位了。Pinia 很适合表达业务域状态，但不一定适合直接承载所有跨域编排。把复杂流程抽到 service 或更高层 action，通常能让单个 Store 更干净。

## 与组件职责

Action 不应该把所有组件行为都接管。适合放进 Action 的是业务状态流转，例如登录、保存、加载列表、切换业务状态；不适合放进去的是纯 UI 临时状态，例如弹窗 hover、输入框本地草稿、一次性动画状态。

一个简单判断是：如果这个状态离开当前组件仍然有业务意义，就可以考虑放进 Store；如果只服务当前组件显示，留在组件内部更清晰。

这条判断对 action 也成立。只有真的需要跨组件复用或统一处理的动作，才值得进入 Store；纯页面级交互不要硬上升。

一个常见拆法是：组件负责展示和局部交互，action 负责业务状态流转，service 负责接口和领域计算。

```text
组件：收集用户输入、展示状态、触发动作
Action：校验流程、更新 Store、处理状态收敛
Service：调用接口、封装协议、处理非响应式业务函数
```

这样 Store 不会被接口细节污染，组件也不会到处直接改全局状态。

最终目标不是让所有逻辑都进 action，而是让“真正需要被复用和统一管理的状态流转”进入 action。动作越有业务语义、边界越稳定，Store 越像领域入口，而不是一堆到处可调的修改函数。

## 使用边界

Action 的目标是收口状态变化，而不是把所有逻辑塞进 Store。

| 场景 | 推荐 |
| --- | --- |
| 本地计数、切换 | 同步 Action |
| 提交表单 | 异步 Action |
| 需要返回结果 | Action 返回值 |
| 复杂流程编排 | Action 或服务层 |
| 纯 UI 细节 | 不必放进 Action |

Action 越稳定，Store 越像业务流程入口，而不是一堆散乱的修改函数。

如果 action 名字能直接说清业务意图，比如 `submitOrder`、`loadProfile`、`clearCart`，通常就比 `setData`、`doSomething` 更好维护。

Pinia 允许直接修改 state，也允许使用 `$patch` 批量更新。单字段更新直接赋值最清晰；多个字段表示同一次状态转移时，`$patch` 能让 DevTools 里更容易看出这是一次整体变化。

```ts
this.$patch({
  status: "success",
  profile,
  error: "",
});
```

不要为了“显得统一”给每个字段都写 `setXxx` action。真正值得成为 action 的，是有业务含义、需要复用、需要测试或需要收口副作用的状态变化。

一个很好用的判断标准是：如果这个状态变化离开当前组件仍然有业务意义，或者多个入口都会触发它，它通常值得成为 action；如果只是某个局部输入框的一次性中间态，就没必要强行全局化。
