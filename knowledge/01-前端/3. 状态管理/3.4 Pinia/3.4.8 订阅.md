## 状态订阅

Pinia 的 `$subscribe` 用于监听 Store 状态变化。它适合持久化、日志、调试和状态快照同步。回调会拿到 mutation 信息和变更后的 state，可以判断变更类型、Store ID 和 `$patch` 载荷。

它更像“状态变化观察点”，不是业务入口。也就是说，订阅适合看结果，不适合承载核心逻辑。

```ts
const cartStore = useCartStore();

const unsubscribe = cartStore.$subscribe((mutation, state) => {
  localStorage.setItem("cart", JSON.stringify(state.items));
});
```

订阅关注的是“状态最终变成什么”，不关心是谁触发了变化。如果需求是记录用户行为或 action 耗时，应该优先考虑 `$onAction`。

这一区分很重要，因为很多人会拿 `$subscribe` 去做本该由 action 处理的事情。结果一旦状态变化来源变多，订阅就会越来越像隐式事件总线。

`mutation` 信息可以帮助你区分是直接赋值、`$patch` 对象还是 `$patch` 函数触发的变化。调试时它很有用，但业务逻辑不要过度依赖 mutation 类型，因为 Store 内部更新方式可能会重构。

```ts
cartStore.$subscribe((mutation, state) => {
  console.debug(mutation.storeId, mutation.type);
  console.debug("items", state.items.length);
});
```

订阅最适合做“状态变化后的同步”，例如保存偏好、输出调试日志、同步到外部非响应式系统。它不适合决定业务下一步，因为它只知道状态变了，不一定知道用户为什么触发了变化。

## 触发时机

`$subscribe` 底层基于 Vue 的 `watch`，可以传入类似 watch 的选项，例如 `flush`。默认时机适合大多数场景；如果要同步写入存储或立即响应某些变更，可以调整触发时机。

```ts
cartStore.$subscribe(
  (mutation, state) => {
    localStorage.setItem("cart", JSON.stringify(state.items));
  },
  { flush: "sync" },
);
```

同步订阅要谨慎。持久化数据较大、回调里做复杂计算、频繁状态变更时，同步执行会影响交互性能。持久化可以做节流，或者只保存必要字段。

如果只是偏好设置、主题、语言这种轻量数据，同步写入通常还能接受；但如果 Store 很大，最好只保存必要字段，避免每次状态变化都写整份对象。

`flush` 的选择要和副作用成本匹配。同步写入适合非常小的关键偏好；默认异步时机适合普通日志和持久化；如果回调依赖 DOM 更新后的状态，才考虑更晚的触发时机。多数业务不需要主动改 `flush`。

```text
轻量偏好：可以同步
大对象持久化：默认时机 + 字段白名单
高频输入：默认时机 + 节流
DOM 相关读取：优先放组件生命周期，不优先放订阅
```

订阅回调越重，越应该从主交互链路里拿开。比如编辑器草稿保存可以延迟写入，而不是每按一个键都同步 `localStorage`。

## Action 订阅

`$onAction` 用于监听 action 开始、成功和失败。它适合埋点、日志、性能统计、错误上报和统一调试。和 `$subscribe` 不同，它更接近“发生了什么业务动作”。

```ts
const unsubscribe = cartStore.$onAction(({ name, args, after, onError }) => {
  const startedAt = performance.now();

  after(() => {
    console.log(`${name} success`, {
      args,
      duration: performance.now() - startedAt,
    });
  });

  onError((error) => {
    console.error(`${name} failed`, error);
  });
});
```

如果要统计“用户点击加入购物车后接口是否成功”，`$onAction` 比 `$subscribe` 更合适；如果要把购物车最终内容写入本地存储，`$subscribe` 更直接。

订阅和 action 订阅的区别，本质上是“看状态变化”还是“看业务动作”。这两个层次分清以后，日志和持久化都更容易放对地方。

`$onAction` 的 `after` 可以拿到 action 返回值，`onError` 可以拿到抛出的错误。它特别适合统一统计 action 耗时和失败率。

```ts
store.$onAction(({ name, args, after, onError }) => {
  const startedAt = performance.now();

  after((result) => {
    trackAction({
      storeId: store.$id,
      name,
      duration: performance.now() - startedAt,
      success: true,
      resultType: typeof result,
    });
  });

  onError((error) => {
    trackActionError(store.$id, name, args, error);
  });
});
```

如果 action 参数里可能有敏感数据，日志函数要做脱敏。状态管理订阅天然容易拿到用户上下文，不能因为调试方便就把所有参数原样上报。

## 生命周期绑定

在组件 `setup()` 中创建订阅时，默认会和组件生命周期绑定，组件卸载后订阅会被移除。全局订阅或插件订阅则要明确只安装一次，避免重复监听。

```ts
onMounted(() => {
  const stop = cartStore.$subscribe((mutation, state) => {
    console.log(state.items.length);
  });

  onUnmounted(() => {
    stop();
  });
});
```

如果确实希望组件卸载后订阅仍然存在，可以使用 detached 订阅。但 detached 订阅更接近全局副作用，要放在应用初始化或明确的模块安装函数里管理。

全局订阅越多，越要注意是否重复安装。否则开发时 HMR、页面重进或多次初始化时，很容易出现重复写存储、重复打日志的情况。

```ts
cartStore.$subscribe(callback, { detached: true });
```

在普通组件里，大多数订阅都不需要 `detached`。一旦 detached，订阅生命周期就不再跟组件走，必须由应用初始化、插件或明确的清理函数负责管理。

```ts
export function installCartPersistence() {
  const cartStore = useCartStore();

  return cartStore.$subscribe(saveCartSnapshot, {
    detached: true,
  });
}
```

这种函数应该只在应用入口调用一次。如果每次进入页面都调用，就会产生重复订阅，表现为同一份缓存被写多次、日志重复输出、性能逐渐变差。

## 持久化

订阅最常见的用途是持久化，但不要把整个 Store 无脑写入本地存储。敏感信息、临时状态、服务端缓存、错误对象都不一定适合保存。

```ts
userStore.$subscribe((mutation, state) => {
  localStorage.setItem(
    "user-preferences",
    JSON.stringify({
      theme: state.theme,
      language: state.language,
    }),
  );
});
```

持久化要考虑版本迁移。旧版本存储的数据结构可能和新版本 Store 不一致，读取时要提供默认值和迁移逻辑，而不是直接 `JSON.parse` 后塞回状态。

如果持久化数据是用户偏好或草稿，升级时最好预留一个迁移层。这样即便字段改名、结构调整，也不会把用户以前保存的数据直接弄丢。

持久化订阅还要避免循环更新。比如订阅里写 storage 通常没问题，但如果订阅里又 `$patch` 同一个 Store，就可能触发下一轮订阅。确实需要修正状态时，最好放在 action 或恢复阶段处理，不要在订阅回调里做复杂写入。

```ts
// 不推荐：订阅内继续修改同一个 Store，容易形成隐式循环
store.$subscribe((_mutation, state) => {
  if (state.items.length > 100) {
    store.items = state.items.slice(0, 100);
  }
});
```

这类边界约束应该放进 action，例如 `addItem` 时就限制数量，而不是等状态已经变化后再由订阅“纠正”。

## 调试日志

订阅可以帮助排查状态变化，但日志要控制范围。开发环境可以记录详细 mutation，生产环境只记录关键行为或异常上下文，避免泄露用户数据和拖慢页面。

```ts
if (import.meta.env.DEV) {
  store.$subscribe((mutation) => {
    console.debug("[pinia]", mutation.storeId, mutation.type);
  });
}
```

调试日志最好不要成为业务逻辑的一部分。订阅回调如果修改同一个 Store，可能引起循环更新；如果触发请求，可能让状态变化产生隐式副作用。

日志越想“全量”，越应该警惕它侵入业务流程。最好的订阅日志通常是轻量、只读、可开关的，而不是和业务状态互相纠缠。

开发日志可以更详细，生产日志应该聚焦关键动作和异常上下文。尤其是用户资料、表单内容、订单信息、token、手机号等字段，默认不应该进入日志。

```ts
if (import.meta.env.DEV) {
  store.$subscribe((mutation) => {
    console.debug("[pinia mutation]", mutation.storeId, mutation.type);
  });
}
```

生产环境如果需要排查复杂状态问题，更推荐记录 action 名称、耗时、错误码、请求 id，而不是整份 state。这样既能定位问题，也能降低隐私和体积风险。

## 插件封装

多个 Store 都需要持久化或日志时，可以封装成 Pinia 插件，而不是在每个组件里重复订阅。插件适合处理横切能力，但要提供清晰配置。

```ts
export function persistPlugin({ store }) {
  const key = `pinia:${store.$id}`;

  store.$subscribe((mutation, state) => {
    localStorage.setItem(key, JSON.stringify(state));
  });
}

pinia.use(persistPlugin);
```

插件封装要保留排除能力，例如某些 Store 不持久化、只保存部分字段、不同 Store 使用不同存储介质。否则全局插件会把所有状态都变成隐式副作用。

如果多个 Store 的持久化规则不一样，最好让插件配置显式接受白名单或黑名单，而不是默认把所有 Store 都处理掉。全局自动化越强，越要保留退出机制。

```ts
type PersistConfig = {
  enabled: boolean;
  paths?: string[];
  storage?: Storage;
};
```

插件封装后，订阅逻辑就变成基础设施。基础设施越通用，配置就越要显式，默认行为越要保守。最安全的默认值通常是“不持久化”，由 Store 主动声明可持久化字段。

## 使用边界

订阅适合横切逻辑，不适合承载核心业务流程。核心流程应该写在 action、service 或页面逻辑里，订阅只负责观察和同步。

```text
适合订阅：
持久化偏好设置
记录 action 耗时
开发环境调试日志
同步少量外部状态

不适合订阅：
替代业务 action
触发复杂请求链
维护关键交易流程
隐式修改其他 Store
```

当订阅越来越多时，要重新审视状态边界。过多订阅往往意味着状态变化正在被当作事件总线使用，这会让数据流变得隐蔽。

如果一个项目里订阅逻辑已经多到难以追踪，通常不是“监听器写得好”，而是状态边界开始漂了。那时最该做的往往是回头整理 Store，而不是继续加订阅。

订阅的最终原则是“观察，不主导”。它可以把状态变化同步到外部世界，但不应该反过来成为业务流程的主要驱动。真正的业务入口仍然应该是 action，真正的数据事实仍然应该是 state。
