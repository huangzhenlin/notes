## 定义方式

Pinia 的 Store 定义以 `defineStore` 为入口。可以用选项式写法，也可以用组合式写法。

`defineStore` 的本质是把一块状态区域注册成可复用的 store 实例。你可以把它理解为“给业务域起一个可调用的状态工厂名”。

```typescript
export const useTodoStore = defineStore("todo", {
  state: () => ({ items: [] }),
});
```

`defineStore` 返回的是一个 `useXxxStore` 函数，而不是立即创建出来的全局对象。组件、composable 或其他 Store 调用这个函数时，才会拿到当前 Pinia 实例下对应的 Store。

```ts
const todoStore = useTodoStore();
```

这种设计让 Store 能够跟随应用实例工作，尤其适合测试、SSR 和多应用挂载场景。不要把 Store 当成普通单例随意在模块顶层执行复杂副作用，真正依赖运行时上下文的逻辑应该放进 action 或组件生命周期里。

这条原则看起来抽象，实际很重要。只要在定义阶段就执行依赖环境的逻辑，比如直接读浏览器对象、直接发请求、直接注册长期订阅，后面测试、SSR 和多实例场景都会变得很难控。

## 选项式写法

选项式写法把 state、getter、action 分块写清楚，结构稳定，适合简单到中等复杂度的 Store。

```typescript
export const useCounterStore = defineStore("counter", {
  state: () => ({ count: 0 }),
  getters: {
    double: (state) => state.count * 2,
  },
  actions: {
    increment() {
      this.count++;
    },
  },
});
```

它的优点是结构直观，新人阅读成本低。

选项式写法特别适合刚开始上 Pinia 的团队，因为 state、getter、action 的边界很明确，文档和代码也容易对照着看。

选项式写法里，`state` 是事实，`getters` 是派生读取，`actions` 是修改和流程。这个分区很适合团队统一规范，也方便测试时分别验证初始状态、计算结果和业务动作。

```ts
const counter = useCounterStore();

counter.increment();
expect(counter.count).toBe(1);
expect(counter.double).toBe(2);
```

需要注意的是，action 内部通过 `this` 访问 Store，因此不要把 action 写成箭头函数。箭头函数会破坏 `this` 绑定，导致类型和运行时行为都变得不稳定。

选项式写法的优势就在这里：状态、派生、动作分区非常清楚。对于团队协作来说，这种显式结构往往能减少阅读成本，尤其适合业务域明确、规则相对稳定的 Store。

## 组合式写法

组合式写法更适合需要复用 composable、调用其他 Hook 或组织复杂逻辑的场景。

```typescript
export const useSearchStore = defineStore("search", () => {
  const keyword = ref("");
  const results = ref([]);
  return { keyword, results };
});
```

如果团队以组合式 API 为主，组合式 Store 更容易复用逻辑；如果 Store 结构比较固定，选项式写法更利于快速定位 state、getter 和 action。

两种写法不应该混成一锅粥。团队最好先约定某类 Store 用哪种写法，否则同一项目里不同文件写法差太多，阅读体验会掉得很快。

组合式 Store 返回的 `ref` 相当于 state，`computed` 相当于 getter，普通函数相当于 action。所有要暴露给组件、DevTools 或插件识别的状态都应该返回。

```typescript
export const useCounterStore = defineStore("counter", () => {
  const count = ref(0);
  const double = computed(() => count.value * 2);

  function increment() {
    count.value++;
  }

  return { count, double, increment };
});
```

组合式写法更灵活，也更容易把外部 composable、监听器、异步流程混进来。灵活不是坏事，但要小心把 Store 写成“隐藏了很多副作用的 composable”。如果需要 watch、定时器或外部订阅，最好清楚说明创建和清理时机。

所以组合式写法更适合“真的需要组合式能力”的场景，而不是单纯因为语法更新就全部切过去。灵活度越高，越需要靠约定来保护结构，否则同一项目里不同 Store 的风格会越来越散。

## TypeScript 推导

Pinia 的类型推导通常足够好，但空数组、空对象和 getter 之间互相访问时，需要显式标注类型。

```typescript
type User = {
  id: string;
  name: string;
  role: "admin" | "member";
};

export const useUserStore = defineStore("user", {
  state: () => ({
    users: [] as User[],
  }),
  getters: {
    adminUsers: (state): User[] =>
      state.users.filter((user) => user.role === "admin"),
  },
});
```

类型标注的目标不是让代码显得复杂，而是避免空数组被推成 `never[]`、复杂 getter 返回值不稳定、action 参数含义不清。

Pinia 的类型推导已经很好，但“足够好”不等于“完全不用管”。一旦 Store 状态开始承载真实业务数据，类型边界清楚会比事后补断言省心得多。

对于复杂 state，可以先定义状态类型，再让 `state` 返回这个类型。这样空数组、空对象、联合状态都会更稳。

```ts
type RequestStatus = "idle" | "loading" | "success" | "error";

type UserState = {
  users: User[];
  selectedId: string | null;
  status: RequestStatus;
};

export const useUserStore = defineStore("user", {
  state: (): UserState => ({
    users: [],
    selectedId: null,
    status: "idle",
  }),
});
```

Action 参数也值得显式标注。状态管理里的类型问题很多不是出在 state，而是出在“传进来什么都行”的 action。参数类型清楚以后，组件调用 Store 时会更早暴露错误。

类型最值得优先补的位置，通常是边界输入输出，而不是实现细枝末节。Store state、getter 返回值、action 参数这三个位置一旦稳定下来，后续重构和协作都会轻很多。

## SSR 注意

`state` 必须是函数，这样每个应用实例都能得到独立状态。SSR 场景下尤其重要，否则不同请求之间可能共享同一份状态。

这个规则在服务端渲染里尤其关键，因为 Store 实例可能在多个请求之间复用。把初始状态写成函数，就是避免请求互相污染的基础做法。

```ts
state: () => ({
  items: [] as CartItem[],
})
```

组合式 Store 在 SSR 中还要注意返回完整状态，不要让私有 `ref` 藏在闭包里却参与服务端渲染。未返回的响应式状态不会被 Pinia 正确序列化和恢复，容易出现服务端和客户端状态不一致。

```ts
export const useAuthStore = defineStore("auth", () => {
  const token = ref("");
  const profile = ref<UserProfile | null>(null);

  // 如果 profile 会影响页面渲染，就必须返回
  return { token, profile };
});
```

另外，Store 定义文件里不要直接读取 `window`、`localStorage` 这类浏览器对象。SSR 或构建阶段执行到这些代码时，它们可能不存在。需要读取浏览器环境时，放到客户端初始化或 action 中处理。

同样地，和当前请求、当前路由、当前用户上下文强绑定的逻辑，也不要在定义阶段直接展开。Store 定义阶段更适合描述结构，真正依赖运行时条件的动作应该推迟到实例被使用以后再执行。

## 组件使用

组件里调用 Store 和普通 composable 很像。需要解构 state 或 getter 时使用 `storeToRefs`，action 可以直接解构。

```vue
<script setup lang="ts">
import { storeToRefs } from "pinia";
import { useTodoStore } from "@/stores/todo";

const todoStore = useTodoStore();
const { items, completedCount } = storeToRefs(todoStore);
const { addTodo, toggleTodo } = todoStore;
</script>

<template>
  <button @click="addTodo('学习 Pinia')">新增</button>
  <p>已完成 {{ completedCount }} 个</p>
  <button
    v-for="item in items"
    :key="item.id"
    @click="toggleTodo(item.id)"
  >
    {{ item.title }}
  </button>
</template>
```

不要直接从 Store 解构 state 后长期使用，因为它会丢失响应式连接。`storeToRefs` 更适合模板中长期使用的 state 和 getter。

如果只是短时间读取一次，直接访问没问题；但一旦要把值交给模板长期展示，或者要在多个地方响应式联动，就应该优先用 `storeToRefs`。

组件里还要避免“复制一份 Store 状态再维护”。比如把 `store.items` 拷贝到本地 ref 后又手动同步，常常会制造两个事实来源。只有在编辑草稿、确认后提交这类场景，才适合把 Store 数据复制成局部表单状态。

```ts
const draft = reactive({
  name: userStore.profile?.name ?? "",
});

function save() {
  userStore.updateProfile({ name: draft.name });
}
```

这里的 `draft` 是表单草稿，不是新的全局事实。保存前可以独立编辑，保存后再通过 action 写回 Store。

这个区分很关键。局部草稿的存在是为了给用户一个“可编辑但未提交”的缓冲区，而不是为了把 Store 再复制一遍。只要复制后的数据还想长期和 Store 双向同步，通常就说明状态归属已经开始模糊。

## 创建边界

Store 定义时先决定它是业务域容器，还是组合逻辑容器。

| 目标 | 更适合 |
| --- | --- |
| 明确的业务域 | 选项式 |
| 复用 composable | 组合式 |
| 结构稳定 | 选项式 |
| 逻辑较多 | 组合式 |

写法不是重点，关键是 Store 的职责要清楚，不要把定义写成“把所有状态塞进去”的通用模板。

Store 定义清楚以后，后续的 action、getter、订阅和测试才有落点。定义阶段其实就是在给后面所有用法定边界。

选择定义方式时可以用一个简单规则：团队需要一致阅读体验时优先选项式；Store 需要大量复用组合式逻辑时选择组合式。不要因为“组合式更现代”就把所有 Store 都改成组合式，也不要因为选项式清晰就拒绝必要的逻辑复用。

一个健康的 Store 定义通常具备这些特征：id 稳定，state 是最小事实集合，getter 是纯派生，action 描述业务动作，组件使用时不会绕过 action 大量直接改字段。做到这些，Pinia 的 API 才能真正保持轻。

最终要选的不是“更现代的写法”，而是“更适合当前团队长期维护的写法”。只要定义方式和职责边界都稳定，Pinia 的轻量 API 才会成为优势，而不是变成结构发散的借口。
