## 拆分目标

Chunk 拆分的目标是让资源加载更符合用户路径和缓存策略。它不是把文件拆得越碎越好，而是在首屏体积、缓存命中、请求数量、执行成本之间找到平衡。

```text
入口 HTML
  -> Runtime
  -> 首屏页面 Chunk
  -> 公共依赖 Chunk
  -> 低频路由 Chunk
  -> 重型功能 Chunk
```

用户首次进入页面时，最重要的是首屏可交互；用户二次访问时，最重要的是缓存命中；用户切换路由时，最重要的是延迟可接受。Chunk 策略要同时服务这三个阶段。

Chunk 拆分的难点是平衡。主包太大首屏慢，拆太碎请求多，公共包太大缓存差，公共包太少重复代码多。

所以 Chunk 拆分从来不是“越多越好”或“越少越好”，而是围绕用户路径、缓存稳定性和运行时调度做平衡。

## 拆分边界

常见拆分边界包括路由、业务模块、第三方依赖、重型组件和运行时代码。每种边界都有适用场景。

| 边界 | 适合内容 | 风险 |
|---|---|---|
| 路由 | 页面级代码 | 路由切换时加载等待 |
| 业务模块 | 后台模块、营销模块 | 模块依赖交叉会变复杂 |
| 第三方依赖 | Vue、React、图表库 | vendor 过大或缓存失效 |
| 重型组件 | 编辑器、地图、图表 | 首次打开组件时延迟 |
| Runtime | 打包运行时代码 | 需要保持缓存稳定 |

判断一个模块是否适合拆分，可以问三个问题：是否首屏必需，体积是否明显，访问频率是否足够低。

如果一个模块既大又低频，就很适合拆；如果它小而高频，单独拆出去通常收益不大。

拆分边界最好跟真实业务路径一致。只有当用户访问路径和 chunk 组织大致一致时，拆分才能真正转化成下载和缓存收益。

## manualChunks

在 Vite/Rollup 中，可以通过 `manualChunks` 手动控制部分依赖的拆分。它适合处理特别大的第三方库或希望长期缓存的基础依赖。

```typescript
// vite.config.ts
import { defineConfig } from 'vite';

export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        manualChunks(id) {
          if (id.includes('node_modules')) {
            if (id.includes('echarts')) return 'vendor-echarts';
            if (id.includes('lodash-es')) return 'vendor-lodash';
            return 'vendor';
          }
        },
      },
    },
  },
});
```

不要一上来把每个依赖都拆成独立 chunk。请求过多会增加调度成本，HTTP 缓存也不一定能抵消首屏等待。手动拆分应该基于真实包体积分析。

`manualChunks` 适合解决明确问题，例如某个图表库污染首屏、某个编辑器只在低频页面使用。它不是默认要写得越细越好。

手动拆分的价值在于显式表达策略，而不是接管所有拆分。大多数情况下，先让默认拆分工作，再对明确异常点做干预，会更稳。

## Vendor 策略

单一 vendor chunk 配置简单，但容易变成巨大文件。某个依赖升级会让整个 vendor hash 改变，导致用户重新下载大量未变化代码。

```text
vendor.js
  -> vue
  -> router
  -> pinia
  -> echarts
  -> dayjs
  -> utils
```

更细的策略可以把框架核心、UI 库、图表库、编辑器分别拆开：

```text
vendor-framework
vendor-ui
vendor-chart
vendor-editor
```

拆分后要看两件事：首屏是否真的变小，缓存是否真的更稳定。如果用户每次进首页仍然要下载图表库，那拆分没有达到目标。

Vendor 策略要关注变化频率。框架核心变化少，适合稳定缓存；业务工具变化频繁，放进 vendor 反而可能拖累缓存。

如果 vendor 每次发布都大面积变 hash，就说明它并没有真正承担“稳定缓存层”的角色，反而可能成了一个不断膨胀的公共入口。

## 公共模块

打包工具会把多个异步 chunk 共享的模块抽成公共 chunk。公共模块能减少重复代码，但也可能制造额外请求，甚至让低频页面的依赖影响高频页面。

```text
PageA -> util/date
PageB -> util/date
PageC -> util/date
        -> common-date chunk
```

公共模块是否值得抽取，要看重复体积和加载路径。一个 1KB 工具函数被抽成单独请求可能得不偿失；一个 300KB 图表库被多个页面复用则值得单独缓存。

公共模块抽取要避免“为了去重而制造请求”。重复一点小代码，有时比多一次网络请求更划算。

这类取舍尤其要结合移动端和弱网环境看。在请求成本高的环境里，过度细碎的公共 chunk 很容易把理论优化变成实际负担。

## 缓存稳定

Chunk 拆分要配合文件 hash 和长期缓存。稳定依赖应该尽量保持 hash 不变，业务代码频繁变化则可以单独更新。

```http
Cache-Control: public, max-age=31536000, immutable
```

HTML 不能长期强缓存，因为它引用最新资源清单；带 hash 的 JS/CSS 可以长期缓存。发布时要保留旧 chunk 一段时间，避免用户加载旧 HTML 后请求不到旧资源。

这个问题和 [[5.9.6 版本追踪|版本追踪]] 强相关：如果线上出现 chunk 404，需要知道用户加载的是哪个 HTML、哪个 release、哪个资源 hash。

发布系统要保留旧 chunk，并让 HTML 控制版本切换。否则用户停留在旧页面时，异步加载新路由就可能请求不到旧资源。

Chunk 拆分和部署系统天然耦合。拆得越细，就越需要稳定的版本保留、清理策略和追踪能力。

## 预加载与预取

拆分后的 chunk 可以通过 preload、prefetch 或业务预测提前加载。预加载适合当前页面马上需要的关键资源；预取适合用户可能稍后访问的低优先级资源。

```html
<link rel="modulepreload" href="/assets/order-detail.abc123.js" />
<link rel="prefetch" href="/assets/report-page.def456.js" />
```

预加载用错会抢占首屏资源。比如首页还没渲染，就预加载十几个低频页面 chunk，反而会拖慢关键资源。预取更适合空闲阶段和高概率下一步路径。

拆分越多，预加载策略越需要克制。真正关键的少数资源可以提前，低概率资源应该等用户路径更明确后再加载。

否则很容易出现“为了拆分而拆分，拆完又把它们全都 preload 回来”的情况，等于把复杂度加上了，却没有留下收益。

## 监控指标

Chunk 策略要用数据验证。只看构建产物大小不够，还要看真实用户下载、缓存命中、执行耗时和错误率。

| 指标 | 说明 |
|---|---|
| 首屏 JS 下载量 | 首次进入需要下载多少 JS |
| JS 执行耗时 | 下载后解析和执行是否阻塞 |
| chunk 请求数 | 是否拆得过细 |
| 缓存命中率 | 二次访问是否复用资源 |
| chunk 404 | 发布缓存策略是否出问题 |
| 路由切换耗时 | 异步 chunk 是否加载太晚 |

Chunk 拆分和 [[6.4.2 代码分割|代码分割]] 是同一个主题的两个层面：代码分割决定“哪里异步加载”，Chunk 拆分决定“打包产物如何组织和缓存”。

最终要用真实数据判断策略是否有效：首屏 JS 是否减少、缓存命中是否提升、chunk 404 是否下降、路由切换是否可接受。

Chunk 策略是否健康，可以重点看：

| 观察点 | 说明 |
| --- | --- |
| 首屏入口是否足够轻 | 下载收益 |
| 二次访问是否更能命中缓存 | 缓存收益 |
| 请求数量是否被控制在合理范围 | 调度成本是否可控 |
| 发布后是否容易出现 chunk 404 | 部署耦合成本是否过高 |
