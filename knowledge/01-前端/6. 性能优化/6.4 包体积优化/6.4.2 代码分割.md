## 动态 import

浏览器和打包工具都支持动态 `import()`。它返回 Promise，可以在用户交互、路由进入或条件满足时加载模块。

```javascript
async function openEditor() {
  const { createEditor } = await import('./rich-editor.js');
  const editor = createEditor(document.querySelector('#editor'));
  editor.focus();
}

document.querySelector('#edit-button').addEventListener('click', openEditor);
```

这段代码把富文本编辑器从首屏包中拆出去，只有用户点击编辑时才加载。适合延迟加载的模块通常具有“体积大、低频、非首屏必需”的特征。

动态导入适合把成本从“所有用户都承担”变成“真正使用的人才承担”。这对编辑器、图表、导出、地图这类重功能特别有效。

代码分割在包体积优化里的意义，不只是让构建报告更好看，而是把“下载时机”从首屏挪到真正需要的时刻。

## 路由分割

单页应用最常见的分割边界是路由。用户进入首页时，不应该同时下载后台设置页、报表页和低频活动页。

```tsx
import { lazy, Suspense } from 'react';

const Dashboard = lazy(() => import('./pages/Dashboard'));
const Settings = lazy(() => import('./pages/Settings'));

export function AppRoutes() {
  return (
    <Suspense fallback={<PageSkeleton />}>
      <Routes>
        <Route path="/" element={<Dashboard />} />
        <Route path="/settings" element={<Settings />} />
      </Routes>
    </Suspense>
  );
}
```

路由分割要配合合理的 loading 状态。否则虽然首屏包变小了，但用户切换页面时会看到突兀空白。

路由分割的目标是减少首屏负担，同时保证切换体验可接受。只拆不设计 loading，会把性能问题从首屏转移到跳转时。

所以代码分割之后一定要看真实用户路径。首页是不是更轻了，用户常走的下一步是不是还能接受，才是判断是否成功的关键。

## 组件分割

低频重组件也适合单独拆分，例如图表、地图、代码编辑器、富文本编辑器、3D 预览、复杂表格。

```tsx
const ChartPanel = lazy(() => import('./ChartPanel'));

function ReportPage({ showChart }) {
  return (
    <section>
      <ReportSummary />
      {showChart ? (
        <Suspense fallback={<div>图表加载中...</div>}>
          <ChartPanel />
        </Suspense>
      ) : null}
    </section>
  );
}
```

组件分割不要把基础按钮、输入框、普通卡片都拆出去。这些组件使用频率高、体积小，拆分反而增加运行时开销。

组件分割更适合“重且低频”的组件，而不是所有组件。拆分粒度越小，运行时调度成本和请求管理成本越高。

如果一个组件很小但到处都用，把它强行拆出去通常没有意义；如果一个组件很重但只有少数用户会打开，拆出去往往收益明显。

## 预加载策略

分割后的代码如果加载时机太晚，会造成交互卡顿。可以在用户即将需要时预加载，例如鼠标悬停、链接进入视口、路由预测、空闲时间。

```javascript
const preloadSettings = () => import('./pages/Settings');

document.querySelector('a[href="/settings"]').addEventListener('mouseenter', () => {
  preloadSettings();
}, { once: true });
```

预加载不是越早越好。它会占用网络和主线程资源，应优先用于高概率、短时间内会访问的路径。

鼠标悬停、链接进入视口、用户完成上一步流程，都是比较可靠的预加载时机。空闲时间预加载则要防止抢占关键资源。

预加载时机越接近真实行为，收益越稳定。越依赖主观猜测，越容易把带宽花在用户最后根本不会进入的路径上。

## 公共依赖

打包工具会把多个入口共享的依赖抽成公共 chunk。公共 chunk 有利于缓存，但如果把太多内容塞进 vendor，也会让首屏加载变重。

| 拆分方式 | 优点 | 风险 |
|---|---|---|
| 单一 vendor | 缓存稳定、配置简单 | 初始包过大 |
| 按库拆分 | 命中缓存更精细 | 请求数量增加 |
| 按业务拆分 | 更贴合用户路径 | 配置和维护成本高 |

公共依赖拆分要结合 [[6.4.5 依赖分析|依赖分析]] 看真实体积。不要只看 chunk 数量，要看首屏实际下载、解析和执行了多少 JavaScript。

公共依赖如果变化频繁，会拖累缓存命中。稳定的大依赖适合独立，频繁变化的业务公共代码要谨慎抽太大。

公共依赖策略最终要服务缓存，而不是只服务去重。重复一点小代码，有时比让所有页面都依赖一个大公共包更划算。

## 失败兜底

代码分割引入了新的失败模式：chunk 文件 404、网络中断、CDN 缓存不一致、用户加载旧 HTML 但新 chunk 已被删除。生产项目必须处理动态加载失败。

```tsx
function reloadOnChunkError(error: unknown) {
  const message = String(error);
  if (message.includes('Loading chunk') || message.includes('Failed to fetch dynamically imported module')) {
    location.reload();
  }
  throw error;
}

const Settings = lazy(() => import('./pages/Settings').catch(reloadOnChunkError));
```

更稳妥的做法是发布时保留旧版本静态资源一段时间，让旧 HTML 仍能加载对应 chunk。代码分割和 [[5.9.6 版本追踪|版本追踪]]、CDN 缓存策略是连在一起的。

分割后一定要验证弱网、旧页面停留、发布切换和 CDN 同步这些场景。否则 chunk 加载失败会成为线上白屏来源。

代码分割是否值得保留，可以重点看：

| 观察点 | 说明 |
| --- | --- |
| 首屏 JS 是否明显下降 | 入口收益 |
| 高概率下一步是否仍足够顺畅 | 路径收益 |
| 是否引入了更多 chunk 加载失败风险 | 发布和缓存成本 |
| 是否真的减少了所有用户承担的平均成本 | 总体价值 |
