## Polyfill 边界

Polyfill 用来在旧环境中补齐新 API 或新语法相关能力。它解决的是“目标浏览器缺少某个运行时能力”的问题，不是所有兼容问题都能靠 Polyfill 解决。

| 类型 | 示例 | Polyfill 是否适合 |
|---|---|---|
| 新内置 API | `Promise`、`Array.prototype.includes` | 适合 |
| 新 Web API | `IntersectionObserver`、`ResizeObserver` | 部分适合 |
| 新语法 | optional chaining、class fields | 需要编译转换，不是 Polyfill |
| CSS 特性 | `gap`、容器查询 | 通常需要降级样式或 PostCSS |
| 浏览器 bug | 某版本实现异常 | 需要规避或特定修复 |

Polyfill 和转译要区分：Babel/SWC 把新语法转成旧语法；Polyfill 补运行时缺失的对象、方法和接口。`?.` 这类语法不能靠运行时补丁解决。

很多兼容问题其实不是 Polyfill 问题。语法、API、CSS、浏览器 bug、WebView 行为差异，要分别处理。

把所有兼容问题都往 Polyfill 上归，会让产物越来越重，也会掩盖真正应该改在语法、样式或运行环境适配层的问题。

## 目标环境

Polyfill 策略必须从目标环境开始。面向现代浏览器、企业旧浏览器、移动 WebView、小程序 WebView、桌面 Electron 的策略都不一样。

```text
目标用户
  -> 浏览器与版本分布
  -> Browserslist 配置
  -> 编译目标
  -> Polyfill 注入
  -> 产物验证
```

```text
> 0.5%
last 2 versions
not dead
not IE 11
```

Browserslist 不应该凭感觉写。更好的方式是结合产品真实用户统计、业务所在地区、B 端客户环境和容器内核版本。目标环境越保守，Polyfill 成本越高。

目标环境越旧，现代用户也可能被迫下载更多兼容代码。所以支持范围要有业务依据，而不是长期沿用默认模板。

Polyfill 策略本质上是在做兼容成本分配。支持谁、放弃谁、让所有人多下多少代码，都应该是有业务依据的决定。

## 按需注入

现代构建通常使用按需 Polyfill，依据代码用到的 API 和目标浏览器决定注入内容。这样可以避免把完整 `core-js` 打进所有用户的首屏包。

```javascript
// babel.config.js
module.exports = {
  presets: [
    ['@babel/preset-env', {
      useBuiltIns: 'usage',
      corejs: '3.37',
      targets: '> 0.5%, last 2 versions, not dead',
    }],
  ],
};
```

`usage` 会根据代码中用到的特性注入对应 Polyfill；`entry` 则要求在入口显式引入 Polyfill，再按目标环境裁剪。

```javascript
import 'core-js/stable';
import 'regenerator-runtime/runtime';
```

`usage` 更省心，但对构建工具和依赖扫描有要求；`entry` 更可控，但容易引入过多内容。项目越复杂，越需要结合包体积分析验证实际结果。

按需注入不是绝对精准。第三方依赖、动态代码和构建配置都会影响结果，最终仍然要看产物里实际包含了哪些 polyfill。

因此“配置看起来对了”并不代表最终结果就对。兼容策略一定要回到产物和真实目标环境验证，而不是停在 Babel 配置层。

## 条件加载

有些 Polyfill 可以通过特性检测条件加载，只让缺少能力的浏览器下载。

```javascript
async function ensureIntersectionObserver() {
  if ('IntersectionObserver' in window) return;

  await import('intersection-observer');
}

await ensureIntersectionObserver();
startLazyLoad();
```

条件加载适合体积较大、使用范围明确、缺失环境较少的 API。它的代价是首次使用前多一次异步加载，所以要放在不阻塞首屏的路径上。

条件加载的关键是特性检测要准确，加载失败要有兜底。否则旧浏览器可能在真正使用功能时才暴露错误。

条件加载适合让现代用户少背负兼容成本，但它把一部分风险转移到了运行时，所以检测和失败处理必须做扎实。

## 差异化产物

差异化产物是为现代浏览器和旧浏览器提供不同构建结果。现代浏览器加载更小、更少转译的代码，旧浏览器加载兼容包。

```html
<script type="module" src="/assets/app.modern.js"></script>
<script nomodule src="/assets/app.legacy.js"></script>
```

这种方案能明显降低现代浏览器的兼容成本，但会增加构建、测试和发布复杂度。要确保 modern 和 legacy 产物功能一致，监控上也能区分不同产物的错误。

差异化产物适合访问量大、兼容范围跨度大的项目。小项目如果维护成本过高，可能不如单一产物更稳。

这种方案的收益通常来自“让现代浏览器不再为极少数旧浏览器付费”，但代价是构建、测试、发布和监控都要成倍更谨慎。

## 第三方依赖

Polyfill 策略不能只看业务代码。第三方依赖可能使用较新的语法或 API，也可能默认不被 Babel 转译。

| 问题 | 处理 |
|---|---|
| 依赖发布了现代语法 | 配置需要转译的依赖 |
| 依赖使用新 API | 手动补对应 Polyfill |
| 依赖体积过大 | 替换依赖或按需加载 |
| 依赖内置 Polyfill | 避免重复注入 |

包体积异常时，要结合 [[6.4.5 依赖分析|依赖分析]] 看 Polyfill 是否被重复打包。常见情况是多个库各自引入兼容层，导致现代用户也下载大量旧环境代码。

第三方依赖是否被转译、是否自带 polyfill、是否发布现代语法，都应该进入依赖评估。兼容成本不只来自业务代码。

很多包体积异常最后并不是业务手写了太多兼容代码，而是第三方依赖把自己的兼容层一起带进来了。

## 污染与隔离

Polyfill 通常会修改全局对象或原型，例如给 `Array.prototype` 添加方法。这种方式兼容性好，但也会改变全局环境。对于库作者，污染全局尤其要谨慎。

```javascript
// 应用项目可以接受全局 Polyfill
import 'core-js/features/array/at';

// 库项目更应避免默认污染用户环境
export function at<T>(items: T[], index: number) {
  return index < 0 ? items[items.length + index] : items[index];
}
```

应用项目可以根据目标环境统一注入 Polyfill；库项目则应该尽量不替使用者修改全局环境，除非文档明确说明。

库作者默认污染全局，会让使用者很难控制兼容策略。更好的做法是提供说明或独立入口，让应用自己决定是否注入。

全局污染的代价，不只是体积和行为风险，还包括后续排查困难。一旦多个库都在补全局，问题会变得非常难追。

## 验证方式

Polyfill 策略必须验证。构建能通过不代表旧浏览器能运行，现代浏览器能运行也不代表企业 WebView 能运行。

| 验证项 | 说明 |
|---|---|
| 产物体积 | Polyfill 是否显著增加首屏包 |
| 目标浏览器 | 真实旧版本或云真机验证 |
| 异步加载 | 缺失能力时能否成功加载 Polyfill |
| 错误监控 | 是否能识别兼容包错误 |
| 回归路径 | 新 API 引入后是否更新兼容策略 |

Polyfill 策略和 [[6.4.2 代码分割|代码分割]] 可以配合：低频能力的 Polyfill 不一定要进首屏包，缺失环境按需加载往往更合理。

每次引入新 API，都应该问目标环境是否支持、是否需要补齐、补齐成本是否值得。兼容策略也需要持续维护。

Polyfill 策略是否健康，可以重点看：

| 观察点 | 说明 |
| --- | --- |
| 现代浏览器是否背了过多兼容代码 | 兼容成本是否过重 |
| 旧环境是否真的被成功覆盖 | 策略是否有效 |
| 第三方依赖是否引入了重复兼容层 | 依赖治理是否到位 |
| 兼容代码是否和目标环境保持同步 | 策略是否持续维护 |
