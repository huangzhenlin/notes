## 摇树目标

Tree Shaking 用来移除最终产物中没有被使用的代码。它依赖打包工具对模块依赖关系和导入导出关系做静态分析。

```text
源码模块
  -> 静态依赖分析
  -> 标记使用导出
  -> 删除未使用代码
  -> 生成更小产物
```

Tree Shaking 的目标不是让源码变少，而是让用户下载和执行的代码变少。它本质上是一种构建期裁剪能力，不是运行时优化。

因此，Tree Shaking 的收益必须看构建产物，而不是看源码是否拆得漂亮。源码组织只是为打包器创造可分析条件。

它解决的是“已经被引进来的代码里，哪些其实并没有被用到”。如果本来就不该进首屏的重依赖被引进来了，Tree Shaking 也未必能救回来。

## ESM 静态结构

ES Module 的 `import` / `export` 是静态结构，打包工具可以在运行前分析。

```javascript
// math.js
export function add(a, b) {
  return a + b;
}

export function multiply(a, b) {
  return a * b;
}
```

```javascript
import { add } from './math.js';

console.log(add(1, 2));
```

如果 `multiply` 没有被使用，就有机会从产物中移除。CommonJS 的动态 `require` 更难静态分析，因此摇树效果通常不如 ESM。

这也是现代库越来越重视 ESM 产物的原因。静态导入导出越清楚，工具越容易判断哪些代码可以删除。

所以摇树优化和模块设计是绑在一起的。导出越清楚、职责越单一、副作用越少，打包器越容易做正确裁剪。

## 副作用

模块副作用是 Tree Shaking 最容易失效的地方。比如模块一加载就改全局变量、注册样式、执行初始化逻辑，打包器就不敢轻易删除它。

```javascript
console.log('module loaded');
window.appConfig = {};
Array.prototype.first = function () {};
```

有副作用的模块不能随便删除，因为即使没有导出被使用，导入它也可能影响运行结果。库作者要特别注意：样式注入、全局注册、国际化初始化都可能成为保留理由。

副作用最好集中在明确入口里，不要和纯函数、组件导出混在一起。这样消费方才能只引入自己需要的部分。

## sideEffects

`package.json` 中的 `sideEffects` 字段可以告诉打包工具哪些文件有副作用。

```json
{
  "sideEffects": false
}
```

如果只有样式文件有副作用，可以写成数组：

```json
{
  "sideEffects": [
    "*.css"
  ]
}
```

错误标记 `sideEffects: false` 会导致必要代码被删除。库作者必须确认模块顶层没有副作用，应用项目也要留意第三方包声明是否可靠。

如果样式文件、polyfill 或注册逻辑被误删，产物体积可能变小，但页面会出问题。摇树优化后必须跑测试和冒烟验证。

Tree Shaking 最危险的地方就在这里：看起来像纯构建优化，实际上它直接影响运行结果。体积小了不代表一定正确。

## 常见误区

- 以为用了 ESM 就一定会自动瘦身
- 组件库整包引入却期待摇树生效
- 忽略样式文件、副作用导入、polyfill 导入带来的保留结果

`Tree Shaking` 更像是一种“给打包器创造删除条件”的工程设计，而不是一个独立开关。

如果代码结构不利于静态分析，打开再多构建选项也不会有明显收益。

很多“为什么摇不掉”的问题，最后都不是构建器能力不足，而是代码本身把纯导出、副作用和聚合入口混在了一起。

## 失效场景

真正的项目里，`Tree Shaking` 失效往往不是因为工具坏了，而是模块设计天然不利于静态删除。常见情况包括：

- 入口文件顺手导出整组能力，导致引用一项却把整组都带进来
- 工具模块里混入初始化逻辑、样式导入或全局注册
- 组件库入口顺带导入主题、图标、语言包
- 通过动态路径加载模块，让构建阶段无法确定真实依赖

如果一个模块同时承担“导出工具”和“执行副作用”两种职责，打包器通常只能保守保留。

把初始化逻辑、样式导入和纯导出拆开，通常比调复杂配置更有效。

这也是为什么性能优化经常会反过来推动代码结构更清晰。越容易被分析的模块，往往也越容易被维护和测试。

## 模块设计

想让 `Tree Shaking` 更稳定，模块本身要尽量满足几个特点：

| 设计方式 | 对摇树的影响 |
| --- | --- |
| 单个文件只导出单类能力 | 更容易删除未使用导出 |
| 副作用和纯函数分离 | 更容易判定可删部分 |
| 使用 `lodash-es` 这类 ESM 版本 | 更利于静态分析 |
| 避免聚合入口过重 | 减少“引用一处带入全部” |

这也是为什么很多库明明功能没变，发布成 ESM 后体积表现会好很多。

库作者应该尽量提供清晰的 ESM 入口、子路径导出和类型声明，让使用者项目继续摇树。

对应用开发者来说，最重要的是确认“这个库有没有给我摇树空间”；对库作者来说，最重要的是“别在入口里顺手做副作用”。

## 导入方式

导入方式会影响摇树效果。命名导入通常更利于工具识别使用范围。

```javascript
import { debounce } from 'lodash-es';
```

不合理的导入可能把整个库拉进来：

```javascript
import _ from 'lodash';
```

是否能摇掉未使用代码，还取决于库的发布格式、打包工具配置和依赖本身是否有副作用。

导入方式要和库的推荐用法一致。有些库支持命名导入，有些库必须从子路径导入才能避免全量带入。

## Barrel 文件

Barrel 文件是统一出口文件，例如 `index.ts`。它方便导入，但也可能让依赖关系变粗。

```typescript
export * from './Button';
export * from './Modal';
export * from './Table';
```

如果这些模块顶层有副作用，或者工具无法正确分析，就可能导致未使用组件也进入产物。组件库设计时要让子模块保持纯净，并验证实际构建结果。

Barrel 文件不是不能用，而是不能让它顺手执行初始化逻辑。统一出口应该尽量只做导出，不做运行时代码。

## 动态引用

动态属性访问、反射式导出和运行时拼接路径都可能降低 Tree Shaking 效果。

```javascript
const utils = {
  add,
  multiply,
};

utils[methodName](1, 2);
```

工具无法在构建时确定 `methodName` 的值，就很难删除未使用成员。性能敏感库更适合保持导出清晰。

动态引用越多，打包器越保守。可读、显式的导入导出，往往也是更好的性能结构。

因此动态模式虽然灵活，但性能敏感模块里越显式通常越有利。真正需要动态的地方，再用动态，不要把整个模块设计都做成黑盒。

## 验证方式

Tree Shaking 是否生效不能靠猜，要看构建报告和产物。

| 检查项 | 判断 |
|---|---|
| 未使用函数是否还在产物 | 搜索构建文件 |
| 包体积是否下降 | 对比 gzip/brotli |
| 第三方库是否整体进入 | 看依赖分析报告 |
| sideEffects 是否误删 | 跑测试和冒烟 |

Tree Shaking 和 [[6.4.1 包体积分析|包体积分析]]、[[5.3.4 Rollup|Rollup]] 紧密相关。它是包体积优化的一种手段，不是替代代码分割和依赖治理的万能钥匙。

验证 Tree Shaking 时，最好同时看未使用代码是否还在产物里、gzip/brotli 是否下降、功能是否仍然正常。只看构建日志不够。

Tree Shaking 是否真的值得继续优化，可以看几个问题：

| 问题 | 说明 |
| --- | --- |
| 未使用代码是否明显还残留在产物里 | 是否还有优化空间 |
| 清理后体积变化是否足够大 | 收益是否明显 |
| 模块结构是否因此更清晰 | 工程价值是否同步存在 |
