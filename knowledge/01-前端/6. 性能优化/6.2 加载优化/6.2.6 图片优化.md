## 格式选择

不同图片格式解决的问题不同：

| 格式 | 适合场景 | 特点 |
| --- | --- | --- |
| `JPEG` | 照片类内容 | 压缩率高，兼容性强 |
| `PNG` | 透明图、边缘清晰图 | 体积通常更大 |
| `WebP` | 通用 Web 图片 | 体积更优，兼容较好 |
| `AVIF` | 更高压缩比场景 | 体积更小，但编码和兼容要评估 |

图片优化不是盲目追新格式，而是结合兼容性、生成成本和收益判断。

格式选择要看内容类型。照片更适合有损压缩，图标和透明图要考虑透明通道，首屏主图还要优先考虑解码速度和兼容性。

图片优化最常见的误区，是把所有图片都按同一种策略处理。真正有效的做法通常是按内容类型、展示位置和业务价值分层。

## 首屏主图

首屏主图不要机械懒加载。它往往就是 `LCP` 元素，更适合：

- 优先发现
- 必要时 `preload`
- 明确尺寸，避免布局跳动

如果主图直到滚动进入视口才开始下载，首屏性能很容易被自己拖慢。

首屏主图如果是 LCP 元素，就应该尽早被浏览器发现。它可以通过 HTML 直接出现、预加载、提高优先级等方式进入关键路径。

如果主图被埋在 CSS 背景、轮播组件或异步渲染逻辑后面，即使图片文件本身不大，也可能因为发现太晚而拖慢 LCP。
## 尺寸匹配

图片优化的第一原则是按展示尺寸加载。不要在 200px 宽的卡片里加载 2000px 的原图。

```html
<img
  src="/images/product-400.jpg"
  width="200"
  height="200"
  alt="商品图"
/>
```

明确 `width` 和 `height` 可以减少图片加载后的布局偏移。图片尺寸如果未知，浏览器需要等资源回来后才知道占位大小，容易影响 CLS。

图片尺寸匹配是收益最高的基础优化之一。很多页面图片体积大，并不是格式不先进，而是实际展示很小却加载了原图。

所以图片优化往往应该先做尺寸治理，再考虑更复杂的格式和编码策略。尺寸错了，再先进的格式也只是“稍微没那么浪费”。

## 响应式图片

使用 `srcset` 和 `sizes` 可以让浏览器根据设备像素比和布局宽度选择合适图片。

```html
<img
  src="/images/banner-800.jpg"
  srcset="
    /images/banner-400.jpg 400w,
    /images/banner-800.jpg 800w,
    /images/banner-1200.jpg 1200w
  "
  sizes="(max-width: 600px) 100vw, 800px"
  alt="活动横幅"
/>
```

浏览器会结合 `sizes` 判断图片显示宽度，再从 `srcset` 中选择合适资源。移动端尤其能减少不必要的流量。

`sizes` 写错会让浏览器选错图。比如移动端显示 100vw，却写成固定大尺寸，就可能继续下载过大的图片。

响应式图片的收益建立在布局信息准确的前提上。只要 `sizes` 和真实展示宽度偏差很大，浏览器的选择就可能持续不理想。

## picture

`picture` 适合根据格式或媒体条件选择不同图片。

```html
<picture>
  <source srcset="/hero.avif" type="image/avif" />
  <source srcset="/hero.webp" type="image/webp" />
  <img src="/hero.jpg" alt="首页主图" />
</picture>
```

AVIF、WebP 通常比 JPEG/PNG 更小，但要考虑浏览器兼容和图片类型。照片、插画、透明图、图标适合的格式不同。

`picture` 的价值是让浏览器自己选择最合适的可支持格式，而不是让业务代码判断浏览器能力。

它特别适合格式回退场景，但并不意味着所有图片都必须用 `picture`。简单图片如果没有复杂格式需求，直接 `img + srcset` 往往更清晰。

## 懒加载

非首屏图片可以使用原生懒加载。

```html
<img
  src="/images/product.jpg"
  loading="lazy"
  alt="商品图"
/>
```

首屏关键图片不要懒加载，否则会拖慢 LCP。懒加载适合列表下方、详情页后半段、相关推荐等非关键图片。

懒加载要配合占位尺寸。否则图片虽然晚加载了，但加载后把页面挤开，CLS 会变差。

图片懒加载优化的是流量和首屏压力，不应该以牺牲布局稳定性为代价。尺寸预留是这类优化的基本前提。

## LCP 图片

首屏最大内容图片常常是 LCP 元素，要优先加载。

```html
<link
  rel="preload"
  as="image"
  href="/images/hero.webp"
  imagesrcset="/images/hero-800.webp 800w, /images/hero-1200.webp 1200w"
  imagesizes="100vw"
/>
```

如果 LCP 是主视觉图片，要避免被 JS 延迟插入、CSS 背景隐藏、懒加载或低优先级请求拖慢。

CSS 背景图作为 LCP 主图时，浏览器通常发现得更晚。能用 `<img>` 表达的关键图片，通常更利于优先级和响应式处理。

只有当图片确实只是装饰背景时，才更适合放在 CSS 里。真正承载主内容的图片，优先让浏览器在 HTML 里直接看到它。

## 占位与解码

图片加载期间可以使用占位色、骨架图或低质量占位图。

```css
.image-box {
  aspect-ratio: 4 / 3;
  background: #f3f4f6;
}
```

`aspect-ratio` 能提前保留空间，减少布局跳动。大量图片列表中，稳定布局比花哨占位更重要。

低质量占位图、主色占位和骨架图都可以改善等待感，但不要让占位本身比图片还重。

占位优化的目标是减少感知空白，而不是再引入一层新的加载负担。越简单、越稳定，通常越适合大规模使用。

## CDN 参数

图片 CDN 通常支持裁剪、压缩、格式转换和质量控制。

```txt
/product.jpg?width=400&format=webp&quality=75
```

CDN 参数要和组件展示尺寸匹配。前端组件如果知道卡片尺寸，就应请求对应尺寸图片，而不是把原图交给浏览器缩放。

图片 CDN 最好和组件规范一起设计。例如卡片图、头像、横幅、详情图都定义固定尺寸档位，避免每个业务随意拼参数。

如果尺寸档位统一，图片治理就会轻松很多。构建、缓存、CDN 和组件都能基于同一套尺寸约定协同工作。

图片优化是否有效，最终最好回到这些问题：

| 问题 | 用来判断什么 |
| --- | --- |
| LCP 主图是否更早出现 | 首屏收益 |
| 列表和长页面是否减少了无谓流量 | 加载收益 |
| 图片加载是否引起布局跳动 | 稳定性风险 |
| 低端网络下是否仍然可读可看 | 真实用户收益 |
