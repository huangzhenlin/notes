## 子集化

字体通常不需要下载全部字形。按语言、字符集或使用范围做子集化可以显著减小体积。

```css
@font-face {
  font-family: 'BrandFont';
  src: url('/fonts/brand-latin.woff2') format('woff2');
  unicode-range: U+000-5FF;
}
```

如果页面主要是中文，不要把纯拉丁子集当作唯一字体资源。根据实际内容拆分字体资源，才能真正减包。

中文字体体积通常远大于拉丁字体，完整下载成本很高。实际项目里常见做法是只对子集化的品牌字、标题字或数字字使用自定义字体，正文优先系统字体。

字体子集化要基于真实内容，而不是凭感觉裁剪。品牌标题、数字、英文 Logo、少量运营字形适合独立子集；大段中文正文如果强行自定义字体，下载成本通常会非常高。

字体优化最重要的不是“把字体技术栈弄得很复杂”，而是判断哪些文字真的值得自定义字体，哪些地方直接用系统字体更划算。

## font-display

`font-display` 控制字体加载时文本如何显示。

| 值 | 行为 |
|---|---|
| `swap` | 先用回退字体，后替换 |
| `fallback` | 短暂阻塞后回退 |
| `optional` | 网络慢时直接用回退字体 |
| `block` | 先阻塞再显示 |

```css
@font-face {
  font-family: 'BrandFont';
  src: url('/fonts/brand.woff2') format('woff2');
  font-display: swap;
}
```

`swap` 适合希望尽快显示内容的页面；`optional` 适合品牌字体不是强核心的场景；`block` 风险较高，一般不建议直接用于普通内容页。

字体加载策略会影响 FOUT 和 FOIT：前者是先显示回退字体再替换，后者是等待字体导致文字暂时不可见。内容型页面通常更怕文字不可见。

如果页面以内容阅读为主，优先保证文字尽快可见；如果页面以品牌视觉为主，可以接受短暂替换，但要控制布局抖动。字体策略要服务页面目标。

换句话说，字体策略不是全站统一最佳解。资讯页、活动页、品牌页、后台页的优先级完全可能不同。

## 预加载

首屏主字体可以预加载，减少字体到达时间。

```html
<link rel="preload" href="/fonts/brand.woff2" as="font" type="font/woff2" crossorigin />
```

预加载适合少量关键字体，不适合把所有字重和语言包都提前加载。字体预加载过多会抢占其他更关键的资源。

如果一个页面只用到了常规字重，就不要把 bold、medium、italic 全部预加载。字体资源也要进入首屏预算。

预加载字体要配合 `crossorigin` 和正确 MIME，否则浏览器可能重复下载或预加载失效。预加载不是越多越好，关键字体才值得抢优先级。

如果一个页面根本不依赖品牌字体完成首屏阅读，就没必要急着预加载它。把资源优先级留给真正影响首屏的内容通常更重要。

## 回退栈

字体回退应该符合品牌和可读性。常见做法是定义字体栈，而不是只写一个字体名。

```css
body {
  font-family:
    'BrandFont',
    'PingFang SC',
    'Microsoft YaHei',
    sans-serif;
}
```

回退字体的字面高度、字宽和字重都可能和品牌字体不同，页面设计要为这种差异留余量，否则字体切换后容易 CLS。

选择回退字体时要尽量接近目标字体的字宽和行高。这样即使发生替换，布局变化也更小。

字体回退还会影响设计验收。不同系统默认字体差异很大，Windows、macOS、Android、iOS 上的字宽和渲染都不完全一样，关键页面需要跨平台看一遍。

字体回退不是“退一步就行”，而是实际布局的一部分。只要回退字体差异明显，设计稿里本来稳定的版面就可能在真实设备上抖动。

## 可变字体

可变字体可以在一个文件里承载多个字重和轴变化，适合减少多个独立字体文件的体积。

```css
@font-face {
  font-family: 'BrandVariable';
  src: url('/fonts/brand-variable.woff2') format('woff2');
  font-weight: 100 900;
}
```

可变字体不是所有项目都需要。只有当你真的用到了多个字重或字形变体时，它的体积收益才更明显。

如果页面只用一个字重，可变字体可能比单独字体更重。是否使用可变字体，要看实际使用的字重数量和字体文件大小。

可变字体适合设计系统和品牌站，但对普通后台页面不一定必要。判断时看两个指标：是否真的用到多个轴，以及替换后总字体体积是否下降。

可变字体更像一种能力，不是默认答案。只有在多个字重、多个变体和统一设计语言都确实存在时，它的收益才会比较明确。

## 性能验证

字体优化要看 FCP、LCP、CLS 和实际可读体验。很多时候，最优方案不是坚持某个品牌字体，而是允许关键路径先用回退字体，再逐步替换。

| 问题 | 对策 |
|---|---|
| 文本空白 | `font-display: swap` |
| 布局抖动 | 更接近的回退字体 |
| 字体包过大 | 子集化、减少字重 |
| 首屏慢 | 预加载关键字体 |

字体优化和 [[1.1.2 常用标签|常用标签]]、[[1.1.3 语义化|语义化]]、[[6.1.2 性能指标采集|性能指标采集]] 都有关。它不是单独的视觉问题，而是性能和可读性同时要平衡的部分。

验证字体优化时，要同时看文本是否尽快可读、布局是否稳定、字体文件是否减少、LCP/FCP 是否改善。只看字体包体积不够。

字体优化的最终判断应该回到用户体验：首屏文字是否更快出现、页面是否少抖动、低端网络下是否仍可读。品牌和性能之间不是只能二选一，但要明确优先级。

字体优化是否做对了，可以重点看：

| 观察点 | 说明 |
| --- | --- |
| 首屏文字是否更早可见 | 可读性收益 |
| 字体切换后是否明显跳动 | 布局稳定性 |
| 自定义字体是否真的减少了总体资源成本 | 体积收益 |
| 不同系统和网络下效果是否一致可接受 | 真实场景可用性 |
