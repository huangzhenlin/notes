## 图片懒加载

HTML 原生支持图片懒加载：

```html
<img src="/cover.jpg" alt="封面图" loading="lazy" />
```

`loading="lazy"` 适合首屏外图片、长列表图片和资讯流内容。它让浏览器在图片接近视口时再请求资源，减少初始网络压力。

对于需要优先展示的首屏主图，不要盲目加 lazy，否则会拖慢 LCP。

懒加载的核心不是“晚一点加载”，而是“把当前不需要的东西延后”，让首屏先集中资源。这个思路既适合图片，也适合脚本、iframe 和重型功能。

判断是否适合懒加载，先看它是否属于首屏关键路径。如果用户一打开页面就必须看到或必须操作的内容，就不该懒；如果用户大概率先不会用到，懒加载通常就很划算。

懒加载真正的价值，不是“把东西都拖后”，而是把用户当前不会立刻感知到的成本挪开，让关键路径更干净。

## iframe 懒加载

iframe 是最值得懒加载的资源之一，因为它通常包含独立页面、广告、地图、播放器或第三方嵌入内容。

```html
<iframe
  src="https://example.com/map"
  title="地图"
  loading="lazy"
></iframe>
```

MDN 说明，iframe 的懒加载只在 JS 启用时生效，这和隐私与反追踪策略有关。也就是说，不能把 `loading="lazy"` 当成绝对可靠的“永远不请求”机制。

iframe 往往比图片更重，因为它包含独立页面、脚本和第三方逻辑。能懒加载的 iframe，通常都应该懒加载。

如果 iframe 里的内容对 SEO 或首屏可见性很重要，就不能单纯依赖 lazy。需要先区分它是业务关键内容，还是只是嵌入组件。

但 iframe 懒加载也要注意用户感知。如果用户进入页面后马上就会滚到这个区域，过晚开始加载也可能让体验变差，所以最好结合真实滚动路径判断提前量。

## 交互懒加载

重型功能常常在用户交互后才需要，例如富文本编辑器、图表、地图和代码高亮。动态 `import()` 可以把这类模块延后到交互时再加载。

```javascript
button.addEventListener('click', async () => {
  const { openEditor } = await import('./editor.js');
  openEditor();
});
```

这种懒加载特别适合“用户只会使用一小部分高级功能”的页面。它能明显缩小首屏包，但要配合加载中状态，否则用户点击后会觉得卡住。

如果交互触发后才加载模块，按钮态最好立刻反馈“正在加载”，这样用户不会误以为点击失效。

交互懒加载特别适合低频重功能，但要避免把一次点击变成两次等待。点击后立即有反馈、模块下载期间保持可交互、加载完成后再切换状态，体验会更稳。

如果某个功能虽然不在首屏，但用户高频且快速地会触发，就可以考虑“懒加载 + 预取”组合，而不是纯粹等用户点击后再开始下载。

## 视口判断

对不支持原生懒加载的环境，可以用 Intersection Observer 监听元素进入视口。

```javascript
const observer = new IntersectionObserver((entries) => {
  for (const entry of entries) {
    if (!entry.isIntersecting) continue;
    loadImage(entry.target);
    observer.unobserve(entry.target);
  }
});

document.querySelectorAll('[data-src]').forEach((img) => observer.observe(img));
```

这种方式比滚动事件更高效，因为浏览器可以自己决定何时观察和回调。兼容性较差时，再退回滚动/resize 事件兜底。

视口判断的目标是减少不必要的请求，而不是把所有资源都拖到最后一刻。对于首屏可能马上进入视野的元素，应该适度提前。

视口懒加载要注意占位尺寸。元素高度如果事先不确定，进入视口时才补高度，容易触发 CLS。懒加载前先固定空间，体验会更好。

## 骨架体验

懒加载不是让用户看到空白，而是让用户看到可接受的占位状态。骨架屏、低清预览、模糊占位和默认背景都能减少等待感。

占位状态做得好，用户会觉得“内容马上就来了”；做不好，就会显得像卡死或空白页。懒加载的体验质量，往往取决于占位设计。

```html
<div class="skeleton-card" aria-hidden="true"></div>
```

```css
.skeleton-card {
  aspect-ratio: 16 / 9;
  background: linear-gradient(90deg, #eee, #f5f5f5, #eee);
}
```

懒加载和 [[6.1.2 性能指标采集|性能指标采集]] 相关，因为加载策略变化后，LCP、INP 和 CLS 都可能变化。懒加载不是单看请求数，而是要看体验是否真的更好。

如果懒加载导致关键内容延后出现，那就要重新判断是否真的值得。不是所有资源都适合懒，首屏和关键路径上的内容应该优先保证。

真正值得懒的，通常是“重但低频”的东西。比如长列表外的图片、用户很少打开的编辑器、地图、图表和第三方嵌入。把这些延后，收益通常比把基础按钮延后大得多。

懒加载的边界也可以这样判断：

| 更适合懒加载 | 不适合懒加载 |
| --- | --- |
| 首屏外图片 | LCP 主图 |
| 低频重型功能 | 用户一进入就要操作的模块 |
| 下半页 iframe | 首屏核心内容 |
| 低概率下一步流程 | 当前路径必需逻辑 |

## 失败兜底

懒加载会引入新的失败场景：资源还没到、用户已经滚到了、动态模块加载失败、图片地址 404、网络慢导致空位太久。

```javascript
async function loadModule() {
  try {
    return await import('./heavy-module.js');
  } catch {
    showFallback();
    throw new Error('lazy_load_failed');
  }
}
```

好的懒加载会有可见反馈、有降级路径、能在失败后重试，而不是把问题隐藏到用户点击之后才暴露。

懒加载最怕“加载时机晚了，但失败也晚了”。所以失败兜底和重试入口要尽量和触发点放在一起。

懒加载做完后，要观察两个结果：首屏是否变快，以及用户第一次触发时是否可接受。如果用户点开后等太久，说明懒得太过了，需要加预取或调整边界。

一个成熟的懒加载策略，最终要同时满足三件事：首屏压力更小、第一次触发可接受、失败时也不会让用户完全失去路径。
