## 分割目标

代码分割的目标不是让文件数量变多，而是减少首屏必须下载、解析和执行的 JavaScript。首屏只保留当前路径立即需要的能力，低频页面、重型组件和第三方库延后加载。

```text
首屏必需：路由框架、页面骨架、关键交互
延后加载：图表、编辑器、地图、导出工具、管理后台
```

如果分割后主包变小，但首屏新增大量阻塞请求，体验未必会变好。判断分割是否成功，要同时看体积、请求数量、加载时机和用户路径。

代码分割的本质是把“当前必需”和“未来才需要”的代码分开，而不是机械切文件。

如果没有这层判断，代码分割很容易变成“把问题从一个大包拆成很多小等待”，体积变小了，体验却未必变好。

## 动态 import

动态 `import()` 会创建异步 chunk。它可以用于组件，也可以用于普通模块。

```ts
async function openEditor() {
  const { Editor } = await import("./Editor");
  renderEditor(Editor);
}
```

它也适合非组件模块，例如算法库、导出工具、文件解析器。

动态导入的真正价值在于按需加载，不一定非要和 React/Vue 组件绑定。

```ts
async function exportExcel(rows: Row[]) {
  const XLSX = await import("xlsx");
  const workbook = XLSX.utils.book_new();
  // 只在用户点击导出时加载 xlsx
}
```

低频能力不要放进主包。否则用户即使从来不用导出、地图或富文本编辑器，也要为它们付出下载和解析成本。

如果模块很重但只在少数流程出现，拆出去几乎总是划算的。关键是给它配上可接受的加载状态和失败处理。

低频大模块最怕被默认打进主包，因为这会让所有用户都为少数用户的场景付费。把这种成本后移，通常是代码分割最直观的收益来源。

## 路由分割

路由分割是最常见、收益最稳定的分割方式。用户进入首页时，不应该同时下载设置页、报表页和后台管理页。

```tsx
const Dashboard = lazy(() => import("./pages/Dashboard"));
const Settings = lazy(() => import("./pages/Settings"));

function App() {
  return (
    <Suspense fallback={<PageSkeleton />}>
      <Routes>
        <Route path="/" element={<Dashboard />} />
        <Route path="/settings" element={<Settings />} />
      </Routes>
    </Suspense>
  );
}
```

路由分割要配合加载状态，否则只是把“首屏慢”变成“跳转时白屏”。骨架屏、局部 loading、错误重试要和异步 chunk 一起设计。

在路由分割里，用户的感知很大程度取决于切换时是否有顺畅反馈。一个可控的 loading 往往比沉默等待更容易被接受。

路由分割之后，如果切页等待明显增加，就要考虑是不是需要给常走路径做预取，或者把路由边界和共享 chunk 再调一轮。

## 公共依赖

构建工具会把公共依赖拆成 vendor 或 shared chunk。

```text
react vendor
chart vendor
common utils
route chunks
```

公共 chunk 太大，会影响所有页面；拆得太细，又会增加请求调度成本。要结合 Network 和 bundle analyzer 判断。常见策略是：稳定的大型依赖独立出来，业务公共代码不要过早拆成巨大共享包。

理想的公共 chunk 是稳定、复用高、变化少的部分。经常变化的业务逻辑不适合放进稳定共享包，否则缓存命中会变差。

公共 chunk 过大时，往往说明“共享”做得太宽了。把所有代码都抽成公共模块，短期看起来减少重复，长期却会让每个页面都背上过重首包。

## 预加载与预取

代码分割后，可以对高概率下一步访问的 chunk 做预取。

```html
<link rel="prefetch" href="/assets/settings.chunk.js" />
```

预取适合“用户可能马上去”的资源，例如登录成功后的控制台。低概率资源不要预取，避免浪费带宽。预加载和预取的边界可以结合 [[6.2.3 预加载|预加载]] 判断：首屏关键资源才用高优先级提示，下一步资源通常用低优先级预取。

预取更适合用户路径上下一步极有可能进入的页面，不适合纯猜测式提前下载。

如果下一步概率并不高，预取反而会浪费带宽，尤其对移动端用户不友好。所以分割后的预取最好依据真实路径和行为数据，而不是开发者主观判断。

## 加载失败

异步 chunk 可能加载失败。原因包括网络中断、CDN 边缘节点未同步、用户打开旧 HTML 后资源已被清理。

```tsx
<Suspense fallback={<PanelSkeleton />}>
  <ChartPanel />
</Suspense>
```

真实项目里要给异步组件准备错误边界和重试入口，尤其是后台系统、低网速环境和发布频繁的应用。

当 chunk 加载失败时，最好能明确提示用户并提供重试，而不是让页面静默失效。

```tsx
function reloadPage() {
  window.location.reload();
}
```

如果发布系统会删除旧 chunk，用户停留在旧页面再点击新路由时，就可能请求不存在的资源。静态资源部署要保留旧版本一段时间，避免“刚发版就白屏”。

这类问题说明代码分割不只是前端构建问题，还和部署保留策略、版本切换和缓存一致性紧密相关。

## 分割边界

| 适合分割 | 不适合分割 |
| --- | --- |
| 低频路由 | 首屏核心组件 |
| 大型第三方库 | 小工具函数 |
| 富文本编辑器 | 每次都立即需要的代码 |
| 图表地图 | 强依赖主流程的模块 |
| 管理后台 | 极小组件 |

代码分割会减少初始体积，但也会引入异步加载成本。判断标准是：这段代码是否当前页面立刻需要、是否足够大、是否能提供可靠加载体验。

分割不是越细越好。频繁使用的小模块、基础工具库、极小组件往往不值得单独切出去。

是否值得分割，可以看三个问题：它够不够大、用得够不够晚、拆出去后用户第一次使用时是否还能接受等待。三者同时成立时，收益通常最明显。

## 验证方法

```text
查看首屏 JS 体积是否下降
检查新增 chunk 请求数量
确认懒加载时机
验证弱网下加载状态
用 Coverage 看未使用代码
用 Bundle Analyzer 看依赖归属
```

分割之后要复测首屏和交互。只看到主包变小还不够，用户路径上的总体体验也要变好。

如果分割后路由切换变慢、预取失效或缓存碎片化，就要重新调整 chunk 边界。

代码分割成功与否，最终还是要看用户路径：首屏是不是更轻了，常用下一步是不是还能顺畅，缓存是不是更稳定，而不是只看构建报告里的文件数。
