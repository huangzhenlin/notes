## JavaScript 加载

脚本会影响 HTML 解析和主线程执行。普通脚本会阻塞解析，`defer` 和 `async` 可以调整加载执行时机。

```html
<script src="/app.js" defer></script>
<script src="/analytics.js" async></script>
```

`defer` 保持执行顺序，并在 HTML 解析完成后执行，适合业务脚本；`async` 下载完就执行，适合独立第三方脚本，但可能打断解析。

如果页面依赖多个脚本协作，优先考虑 `defer`。如果只是独立埋点、统计或广告脚本，才考虑 `async`。脚本策略选错时，首屏卡顿和脚本竞态经常一起出现。

如果脚本还依赖 DOM 结构，最稳妥的方式通常是把主业务脚本放到 `defer`，再把不影响首屏的统计和广告脚本延后到交互之后。这样既能保住页面骨架，又不会让第三方脚本过早抢占主线程。

资源加载优化首先要看请求链路。页面打开后，HTML、CSS、JS、字体、图片和第三方脚本会按不同优先级进入网络层和渲染层。真正拖慢首屏的，通常不是“资源多”，而是“关键资源被非关键资源挡住了”。

网络层和渲染层的关系很关键。比如 CSS 会影响首次绘制，JS 可能会阻塞解析，字体会影响文本可见性，首屏图片又可能影响 LCP。资源加载优化通常要先保证“关键 CSS 和关键 JS 到位”，再考虑图片、字体和第三方资源的提前加载。

优化时可以先用 Network 瀑布图把资源分成三类：首屏必须、首屏相关但可延后、首屏无关。首屏必须资源要尽早到达，首屏无关资源则不要抢带宽和主线程。这个分类比简单数文件数量更有用。

资源加载优化最怕“所有资源都觉得自己很重要”。一旦每个模块都要求自己预加载、提前执行、优先下载，最终就会把真正关键的资源淹没。

## 代码拆分

按路由、组件或能力拆分 JS，可以减少首屏加载体积。

```ts
const SettingsPage = lazy(() => import("./SettingsPage"));
```

拆分不是越细越好。过多小 chunk 会增加请求和调度成本。优先拆低频、重依赖、非首屏模块，例如图表、编辑器、地图、管理后台。

```text
适合拆分：
1. 首屏后才会用到的页面
2. 体积大的独立能力
3. 用户操作后才进入的流程

不适合过度拆分：
1. 频繁切换的小组件
2. 到处都要用的基础库
3. 互相依赖很强的逻辑
```

代码拆分要和缓存一起看。稳定的第三方依赖适合拆成 vendor chunk，业务页面适合按路由拆分，低频重组件适合交互触发后再加载。

如果拆分后出现大量并发请求，可以再结合 `preload`、`prefetch` 或者路由级预取做平衡。拆分不是目的，减少首屏阻塞、提高可缓存性，才是拆分真正要达到的效果。

代码拆分完成后，要观察两件事：首屏入口是否变小，路由切换是否变慢。如果首屏快了但用户进入下一页明显等待，就需要给高概率路径加预取或把拆分边界调粗一点。

所以资源加载优化永远是平衡题：首屏更快，下一跳会不会更慢；下载更少，运行时会不会更碎；第三方更晚，业务是否还能接受首次使用等待。

## 字体加载

字体可能影响首屏文本显示和布局稳定性。

```css
@font-face {
  font-family: "Brand";
  src: url("/fonts/brand.woff2") format("woff2");
  font-display: swap;
}
```

`font-display: swap` 可以先用系统字体显示，再替换为自定义字体。字体文件要使用 woff2，按字重拆分，避免一次加载全量字族。字体优化的重点不是“字体要不要美观”，而是“首屏能不能先稳住”。

很多页面的字体优化收益并不来自“字体文件更小”，而是来自“文本尽快可见”。如果业务对品牌字体要求没那么高，优先保证可读性通常比执着于完全一致的视觉更重要。

字体资源也要避免和首屏主图、关键 CSS 竞争。品牌字体如果不是 LCP 关键内容，可以选择延后或使用更接近的系统字体兜底，减少首屏空白和布局抖动。

## 第三方资源

第三方资源常常不受本项目构建控制，但会影响首屏和交互。

| 资源 | 优化 |
| --- | --- |
| 监控 SDK | 延迟初始化，采样 |
| 客服组件 | 用户需要时加载 |
| 地图 SDK | 进入地图模块再加载 |
| 广告脚本 | 隔离和预算 |
| A/B 实验 | 控制阻塞和闪烁 |

第三方脚本必须进入性能预算。不能因为它来自外部，就不计算成本。对第三方资源最重要的不是“接入成功”，而是“不会把主流程拖慢”。

如果第三方资源过重，常见做法是延迟加载、交互后加载、按路由加载，甚至把它放到独立容器里做失败隔离。能不让它出现在首屏关键路径上，就尽量不要让它出现在首屏关键路径上。

第三方资源还要设置失败兜底。客服、地图、广告、实验 SDK 加载失败时，页面主流程不应该跟着失败。第三方越不受控，越要隔离在非关键路径上。

对第三方资源来说，最理想的状态通常是“加载成功会增强体验，加载失败也不破坏主流程”。做不到这一点的第三方资源，就不应处在关键路径上。

## 优先级提示

浏览器会自动分配资源优先级，也可以通过资源提示辅助。

```html
<link rel="preconnect" href="https://cdn.example.com" />
<link rel="preload" as="image" href="/hero.webp" />
<link rel="prefetch" href="/next-page.js" />
```

`preconnect` 用来提前建立连接，`preload` 用来提前加载当前页关键资源，`prefetch` 更适合下一跳资源。三者不是同一个东西，错用会直接抢占带宽。

资源提示要少而准。预加载过多会让浏览器把带宽用在非关键资源上，反而拖慢真正的首屏资源。尤其在弱网移动端，错误的 `preload` 比不用还糟。

资源提示是手动干预浏览器优先级的手段，使用前最好先确认浏览器默认调度是否真的出了问题。不是所有页面都需要主动提示。

## 优化顺序

```txt
分析 Network 瀑布图
识别首屏关键资源
压缩和缓存静态资源
拆分非首屏逻辑
控制第三方脚本
验证首屏指标
```

资源加载优化要先找关键路径，再找大资源，再找可拆分点。只改一个 `preload` 就期待全局变快，通常是不现实的。

资源加载优化要看实际瀑布图。只减少文件数量或只压缩体积，都可能没有击中真正瓶颈。最有效的优化往往是先找到“谁在阻塞谁”，再决定是拆分、延后还是预加载。

优化完成后要重新对比 LCP、FCP、资源瀑布和主线程任务。加载优化不只看下载速度，还要看资源到达后是否真的让页面更快可见。

判断资源加载优化是否有效，可以重点看：

| 观察点 | 说明 |
| --- | --- |
| 关键资源是否更早进入瀑布图 | 发现时机更合理 |
| 首屏必须资源是否少被非关键资源抢占 | 优先级调整有效 |
| LCP / FCP 是否真的改善 | 用户体验获得收益 |
| 第三方和低频资源是否成功移出关键路径 | 策略命中重点 |
