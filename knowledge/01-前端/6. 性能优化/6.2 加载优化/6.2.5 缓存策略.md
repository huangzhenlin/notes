## 强缓存

静态资源通常使用长缓存，尤其是带 hash 的 JS、CSS 和图片。

```http
Cache-Control: public, max-age=31536000, immutable
```

文件名带内容 hash 时，内容变化会生成新 URL，因此可以放心长缓存。

```txt
app.8f3a1.js
style.91c2e.css
```

不要给没有 hash 的入口 HTML 设置超长缓存，否则用户可能长期拿到旧入口。

强缓存命中时，浏览器可以不向服务器发起请求，收益最大。它适合内容不可变、URL 会随内容变化的资源，不适合入口 HTML 和用户相关接口。

实际项目里，最常见的策略是把“入口短缓存 + 静态资源长缓存”组合起来。这样用户每次打开页面时都能先看到最新入口，再让入口去引用正确版本的静态资源。

这是前端缓存策略里最值得优先建立的基本盘。只要入口和静态资源的职责分清，很多版本错位问题都会少很多。

## 协商缓存

协商缓存通过 `ETag` 或 `Last-Modified` 判断资源是否变化。

```http
ETag: "abc123"
Cache-Control: no-cache
```

`no-cache` 不是“不缓存”，而是每次使用前都要向服务器确认。入口 HTML 常用这种策略，保证能及时发现新版本。

协商缓存仍然需要一次网络往返，但如果资源没变，服务端可以返回 `304 Not Modified`，浏览器继续使用本地副本。它适合“可能变化，但想避免重复传输”的资源。

协商缓存的收益通常比强缓存小，但它在入口 HTML、接口响应和需要快速感知更新的资源上非常有用。尤其是更新频繁但内容体积不大时，协商缓存能在新鲜度和传输成本之间取得平衡。

从体验角度看，强缓存更像“尽量别再问服务器”，协商缓存更像“可以先问一下有没有更新”。两者服务的目标不同，不应该混着用。

## HTML 与静态资源

常见策略是 HTML 短缓存或协商缓存，带 hash 静态资源长缓存。

| 资源 | 策略 |
| --- | --- |
| `index.html` | `no-cache` 或短缓存 |
| `app.[hash].js` | 长缓存 + immutable |
| `style.[hash].css` | 长缓存 + immutable |
| 图片资源 | 按 hash 或 CDN 策略 |
| API 响应 | 按业务新鲜度 |

这个组合可以做到：用户访问 HTML 时发现新版本，新 HTML 再引用新的 hash 资源。

如果 HTML 也被长缓存了，就容易出现“明明发布了新版本，用户却还是进旧页面”的问题。很多发布事故不是静态资源没缓存好，而是入口文件缓存过长。

因此入口 HTML 通常应该被视为版本切换控制点，而不是普通静态资源。它的缓存策略要优先考虑新鲜度，而不是最大化缓存命中。

## 失效方式

缓存真正难的地方不是“存下来”，而是“什么时候失效”。

```text
1. 版本号变化
2. 文件名变化
3. 响应头变化
4. 手动清理
5. 服务端下发失效信号
```

如果没有明确失效机制，缓存就会从性能优化变成数据污染。

失效机制最好和版本号、构建产物和发布流程绑定在一起，而不是靠人工记忆。人工手动清缓存这件事，越到大项目越不可靠。

一旦需要经常人工指导“你清一下缓存再试”，就说明缓存设计已经在把成本转移给用户和排障人员。

## CDN 缓存

CDN 缓存要考虑刷新、预热、版本回滚和区域一致性。

```text
发布新资源 -> 上传带 hash 文件 -> 更新 HTML -> CDN 刷新入口
```

尽量避免覆盖同名静态资源。覆盖后即使服务器变了，用户浏览器或 CDN 边缘节点仍可能保留旧内容。

发布时更稳妥的顺序是先上传带 hash 的静态资源，再更新入口 HTML。这样即使用户在发布过程中访问页面，也不容易拿到“新 HTML 引用旧资源不存在”的半发布状态。

CDN 预热和刷新也要考虑顺序。入口文件先刷新，资源还没上齐，容易 404；资源先上齐，再切入口，风险就小得多。

缓存发布策略和资源部署策略必须是一体的。只改服务器头、不改发布顺序，或者只改发布顺序、不改缓存头，都很难真正稳定。

## Service Worker 缓存

Service Worker 可以自定义缓存策略，但也带来版本复杂度。

```js
self.addEventListener("activate", (event) => {
  event.waitUntil(cleanOldCaches());
});
```

如果旧缓存没有清理，用户可能长期使用旧 JS。PWA 或离线应用必须设计安装、激活、更新提示和缓存清理流程。

Service Worker 比普通 HTTP 缓存更强，也更危险。它可以拦截请求、返回缓存、后台更新资源，但一旦更新策略写错，用户可能长时间停留在旧版本。

因此，Service Worker 更适合能接受复杂发布和缓存治理的场景，比如 PWA、离线优先应用或强控制的内部系统。普通网站如果没有成熟的更新提示和缓存清理流程，通常不建议把它用得太激进。

Service Worker 最大的问题不是“会不会快”，而是“版本治理是否会因此变复杂”。如果团队还没有准备好处理更新提示、旧缓存清理和离线回退，先谨慎一些更稳。

## 接口缓存

接口缓存要围绕数据新鲜度设计，不能照搬静态资源策略。

| 数据 | 缓存策略 |
| --- | --- |
| 用户资料 | 短缓存或手动刷新 |
| 商品详情 | 可缓存但需失效 |
| 库存价格 | 新鲜度要求高 |
| 字典配置 | 可长缓存 + 版本 |
| 支付结果 | 不应使用旧缓存判断 |

接口缓存要和服务端状态、请求状态、版本追踪一起看。用户关键决策数据不能因为缓存导致错误，尤其是价格、权限、库存和支付结果。

## 使用边界

缓存不是越激进越好。它真正解决的是“重复请求”和“无意义等待”，不是“所有数据都别变”。

```text
适合缓存：静态资源、字典、配置、可延迟更新的数据
谨慎缓存：价格、库存、权限、订单状态
```

如果某条数据变更会直接影响用户决策，就要优先考虑失效机制、版本号、手动刷新或短缓存，而不是一味延长过期时间。

缓存排查时可以按层级逐个确认：浏览器是否命中、CDN 是否命中、服务端是否返回旧数据、应用层是否复用了旧状态。不要只看 Network 面板里“from disk cache”，就认为全部缓存策略都正确。

一个实用判断标准是：静态资源优先追求长期稳定，业务数据优先追求新鲜度。前者看 hash 和长缓存，后者看失效和同步。把两者混在一起，缓存策略就很容易失控。

缓存策略是否成熟，可以看这些现象：

| 现象 | 说明 |
| --- | --- |
| 发布后用户能较快拿到新入口 | 入口缓存策略较合理 |
| 很少出现 chunk 404 和版本错位 | 资源缓存和部署顺序较稳 |
| 很少需要人工指导用户清缓存 | 失效机制较健康 |
| 关键业务数据不会长期停留旧值 | 动态数据缓存边界较清楚 |
