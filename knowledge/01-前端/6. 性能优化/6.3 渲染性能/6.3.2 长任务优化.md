## 长任务定义

浏览器主线程上执行时间超过 50ms 的任务通常被视为 Long Task。长任务会阻塞输入响应、渲染和其他脚本执行。

```txt
用户点击 -> 主线程忙于 JS -> 事件处理延迟 -> 交互变慢
```

长任务与 INP、TBT 等指标关系密切。用户感受到的“点了没反应”，很多时候就是主线程被长任务占住。

长任务优化的目标不是追求主线程完全没有长任务，而是让关键交互路径不要被持续阻塞。首屏初始化、点击、输入、滚动的优先级最高。

## 常见来源

长任务常来自大 JS 包解析执行、复杂同步计算、一次性渲染大量 DOM、低效循环、JSON 解析、第三方脚本。

| 来源 | 示例 |
| --- | --- |
| JS 初始化 | 大型框架和业务包启动 |
| 同步计算 | 大数组排序、过滤、加密 |
| DOM 操作 | 一次插入大量节点 |
| JSON 处理 | 大响应同步解析 |
| 第三方脚本 | 监控、广告、客服组件 |

优化长任务要找到真实来源，而不是盲目拆代码。

长任务来源不同，优化手段也不同。业务计算可以切片，第三方脚本要延迟或预算约束，渲染量太大则要减少 DOM 或虚拟化。

所以“长任务优化”并不等于“把函数拆短一点”。真正要做的，是先确认这段阻塞到底属于计算、渲染、解析还是第三方脚本，再选对应手段。

## 任务切片

大计算可以拆成多个小任务，让浏览器有机会处理输入和渲染。

```js
async function processItems(items) {
  const chunkSize = 500;

  for (let index = 0; index < items.length; index += chunkSize) {
    const chunk = items.slice(index, index + chunkSize);
    processChunk(chunk);

    await new Promise((resolve) => {
      setTimeout(resolve, 0);
    });
  }
}
```

这段代码把一个大任务拆成多段。它不会减少总计算量，但能降低单次阻塞时间，让页面更有响应性。

任务切片适合可以分批完成的工作，例如批量处理列表、分块渲染、非关键数据转换。不能切片的同步关键逻辑，要考虑移到 Worker 或服务端。

切片之后也要看用户体验是否真的改善。理论上每段更短了，但如果任务太多、调度太碎，整体响应不一定会明显变好。

## 空闲调度

低优先级任务可以放到空闲时间执行。

```js
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 0 && queue.length > 0) {
    process(queue.shift());
  }
});
```

`requestIdleCallback` 适合日志整理、缓存预热、非关键计算。关键渲染路径和用户立即需要的结果不应该完全依赖空闲回调。

空闲回调不是实时调度。页面繁忙时可能很久都没有空闲时间，所以只能放低优先级任务。

因此空闲调度更适合“晚做没关系”的任务，比如日志整理、缓存预热和非关键计算，而不是用户已经在等待结果的主流程。

## Web Worker

CPU 密集任务可以放到 Worker 中，避免阻塞主线程。

```js
const worker = new Worker(new URL("./worker.js", import.meta.url), {
  type: "module",
});

worker.postMessage({ type: "parse", payload: largeText });

worker.onmessage = (event) => {
  renderResult(event.data);
};
```

Worker 适合大 JSON 处理、搜索索引、图片处理、加密压缩等。它不适合直接操作 DOM，且数据传输也有成本。

如果传输数据很大，要考虑结构化克隆成本。能使用 Transferable 对象时，可以减少复制开销。

Worker 能解决的是主线程阻塞，不是所有性能问题。对于小任务或高频来回通信的任务，Worker 本身的调度和传输成本也要一并评估。

## 渲染拆分

一次性渲染大量内容也会形成长任务。列表、表格、树形控件要考虑分页、虚拟滚动或渐进渲染。

```tsx
function ProductList({ products }) {
  return (
    <VirtualList
      items={products}
      itemHeight={72}
      renderItem={(product) => <ProductRow product={product} />}
    />
  );
}
```

虚拟列表的价值是减少同一时刻参与渲染的节点数量。节点越多，布局、绘制和事件处理成本越高。

渲染拆分要配合用户体验。一次渲染少了，但如果滚动时不断抖动或高度估算不准，体验仍然会变差。

## 第三方脚本

第三方脚本是长任务高发来源。它们常常在主线程执行，并且不受业务代码直接控制。

```html
<script async src="https://example.com/analytics.js"></script>
```

能延后加载的第三方脚本不要阻塞首屏；能按需加载的组件不要全站加载。对监控、客服、广告、AB 实验脚本要做性能预算。

第三方脚本最难控制，所以更需要可观测性。至少要知道它什么时候加载、耗时多少、是否影响 INP 和长任务数量。

如果一个第三方脚本已经反复出现在长任务里，就应该把它当成真正的性能依赖来治理，而不是继续把问题归给“浏览器偶尔卡”。

## 定位流程

```txt
Performance 录制交互
查找超过 50ms 的任务
展开 Bottom-Up / Call Tree
确认脚本来源和函数栈
判断是拆分、延迟、Worker 还是删除
```

长任务优化不是把所有函数都改短，而是保护用户关键交互路径。首屏、点击、输入、滚动这些路径优先级最高。

优化后要用 Performance 面板和线上 INP 数据复测。代码看起来拆开了，不代表用户真的更流畅。

长任务优化是否有效，最终要回到两个判断：

| 判断 | 说明 |
| --- | --- |
| 关键交互后的阻塞是否明显下降 | 用户体感是否改善 |
| INP / TBT / 长任务数量是否同步变化 | 指标层是否验证成功 |
