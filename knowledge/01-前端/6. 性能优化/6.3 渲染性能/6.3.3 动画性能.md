## 帧预算

动画流畅度通常以帧率衡量。60fps 下每帧预算约 16.67ms，120fps 下每帧预算约 8.33ms。

```txt
输入处理 + JS + 样式计算 + 布局 + 绘制 + 合成 <= 一帧预算
```

任何阶段超时都可能掉帧。动画性能优化的目标是减少每帧工作量，让浏览器能稳定按时交付画面。

帧预算并不是全部留给业务代码。浏览器还要处理输入、样式、布局、绘制和合成，所以动画中的 JavaScript 应尽量轻。

动画性能优化最容易掉进的误区，就是只看“动画有没有动起来”，却不看它是不是在持续吞掉主线程和绘制预算。

## 合成友好属性

高频动画优先使用 `transform` 和 `opacity`。

```css
.card {
  transition: transform 180ms ease, opacity 180ms ease;
}

.card:hover {
  transform: translateY(-4px);
  opacity: 0.96;
}
```

这类属性通常可以在合成阶段处理，避免频繁触发布局和大面积绘制。

合成友好属性适合高频动画，例如滑动、淡入淡出、弹层位移和列表项过渡。它们能减少主线程压力，但仍要控制图层数量。

选择动画属性时，核心不是“哪种写法更酷”，而是“这段变化会不会让浏览器反复布局、绘制或上传图层”。属性选对了，很多动画问题会天然少一半。

## 布局属性

动画 `width`、`height`、`top`、`left` 可能触发布局。

```css
/* 更容易触发布局 */
.box {
  transition: left 200ms ease;
}

/* 更适合动画 */
.box {
  transition: transform 200ms ease;
}
```

如果视觉上只是移动元素，优先用 `transform: translate()`。如果确实要改变布局，例如展开内容区域，则要控制频率和范围。

布局型动画并非完全不能做，但要意识到它本身就是更贵的选择。只有在视觉收益明确时才值得承担这部分成本。

展开收起这类动画如果必须影响布局，可以考虑只在开始和结束更新布局，中间过程用 transform 或 max-height 谨慎模拟。

## 绘制成本

某些属性不会触发布局，但绘制成本高。

| 属性 | 风险 |
| --- | --- |
| `box-shadow` | 大面积阴影绘制 |
| `filter` | 模糊和滤镜成本高 |
| `backdrop-filter` | 背景采样昂贵 |
| 大面积渐变 | 绘制成本可能高 |
| border-radius + overflow | 可能增加裁剪成本 |

动效中使用这些属性时，要在真实设备上测试。桌面上流畅，不代表移动 WebView 也流畅。

绘制成本高的效果并非不能用，而是不要在大面积、高频、长时间动画中滥用。尤其是毛玻璃、阴影和滤镜，要优先真机验证。

这类效果在静态状态下看起来成本不高，但一旦叠到滚动、弹层、长列表或持续动画里，代价就会迅速放大。

## will-change

`will-change` 可以提前提示浏览器某个属性将变化。

```css
.drawer {
  will-change: transform;
}
```

它适合即将动画的少量元素。不应长期给大量元素添加 `will-change`，否则会造成图层和显存压力。

`will-change` 更像“提前热身”，不是永久优化。长期挂着可能让浏览器一直保留额外资源。

只有当你明确知道某个元素即将开始高频变化时，`will-change` 才有价值。默认给一堆元素常驻这个属性，通常得不偿失。

## JS 动画

JS 驱动动画应使用 `requestAnimationFrame`。

```js
function update() {
  element.style.transform = `translateX(${x}px)`;
  requestAnimationFrame(update);
}

requestAnimationFrame(update);
```

`requestAnimationFrame` 会和浏览器刷新节奏对齐。不要用 `setInterval` 驱动视觉动画，它和帧渲染不同步。

如果动画状态来自滚动、拖拽或输入，最好把 DOM 写入收敛到 `requestAnimationFrame` 中，避免同一帧内多次更新。

动画和交互最怕“事件来了就立刻改 DOM”。事件频率远高于刷新频率时，不做节流和对齐，很容易在一帧内重复更新。

## 手势动画

拖拽、滑动、跟手动画要尽量减少主线程工作。

```js
const handleMove = rafThrottle((x) => {
  panel.style.transform = `translateX(${x}px)`;
});
```

事件中不要做复杂计算、同步请求、频繁读写布局。需要读布局时，先批量读，再批量写，避免布局抖动。

手势动画要求“跟手”，所以要优先保证响应而不是一次算完所有内容。复杂计算可以延后、缓存或交给 Worker。

如果每次拖动都还要顺便计算复杂布局、筛选数据或更新大量组件，再漂亮的动画曲线也救不回来。

## 降级偏好

尊重用户减少动态效果的系统设置。

```css
@media (prefers-reduced-motion: reduce) {
  .modal {
    transition: none;
    animation: none;
  }
}
```

对于视差、缩放、大范围移动等效果尤其重要。可访问性也是性能体验的一部分。

减少动态效果不仅是照顾敏感用户，也能在低性能设备上减少不必要的动画成本。

## 定位流程

```txt
Performance 录制动画过程
查看 FPS 和掉帧
检查 Main 线程长任务
查看 Layout/Paint 是否频繁
确认动画属性
检查 Layers 是否过多
低端设备复测
```

动画卡顿不一定是 CSS 问题。JS 长任务、图片解码、主线程忙、图层过多都可能导致掉帧。

优化动画前先确认瓶颈在哪。只把 `left` 改成 `transform`，如果真正问题是 JS 长任务，卡顿仍然会存在。

动画优化是否有效，可以重点看：

| 观察点 | 说明 |
| --- | --- |
| FPS 是否更稳定 | 帧交付是否改善 |
| Main 线程长任务是否减少 | 脚本是否更轻 |
| Layout / Paint 是否下降 | 属性和视觉效果是否更合理 |
| 真机跟手感是否变好 | 最终用户体验是否改善 |
