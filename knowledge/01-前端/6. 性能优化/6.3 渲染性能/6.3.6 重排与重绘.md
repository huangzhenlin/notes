## Layout

Layout 负责计算元素在页面中的几何信息，包括宽高、位置、换行、滚动区域等。修改几何属性通常会触发布局。

| 修改 | 可能触发 |
|---|---|
| `width` / `height` | Layout |
| `margin` / `padding` | Layout |
| `top` / `left` | Layout |
| `font-size` | Layout |
| `display` | Layout |

布局成本和 DOM 规模、CSS 复杂度、布局模型复杂度有关。节点越多，依赖关系越复杂，布局越容易影响 INP。

Layout 的危险在于它常常牵一发动全身。一个容器尺寸变化，可能让内部文本换行、子元素位置和滚动区域全部重新计算。

这也是为什么布局优化经常优先从“缩小影响范围”入手，而不是只盯着单个属性本身。改动发生在越高层，波及通常越大。

## Paint

Paint 负责把元素绘制成像素。修改不影响几何位置的视觉属性，通常会触发重绘。

| 修改 | 可能触发 |
|---|---|
| `color` | Paint |
| `background` | Paint |
| `box-shadow` | Paint |
| `border-color` | Paint |

重绘不一定便宜。大面积阴影、滤镜、渐变和复杂背景会增加绘制成本，尤其在低端移动设备上更明显。

Paint 问题在静态页面里不一定明显，但在滚动、动画和频繁状态变化时会放大。

绘制问题往往带有明显场景性。静止状态下不一定看得出来，一旦进入滚动、悬停、过渡或持续刷新，代价就会快速暴露。

## Composite

合成是把不同图层组合到屏幕上。`transform` 和 `opacity` 通常可以在合成层处理，避免重新布局和绘制。

```css
.card {
  transition: transform 200ms ease;
}

.card:hover {
  transform: translateY(-4px);
}
```

动画优先使用 `transform` 和 `opacity`，而不是 `top`、`left`、`width`、`height`。这也是很多性能优化建议反复强调的点。

合成友好的属性可以减少布局和绘制，但仍要控制图层数量。性能优化总是在成本之间转移，不是把成本变没。

所以“把所有动画都改成 transform”不是最终答案。只要图层过多、JS 太重或绘制太复杂，整体卡顿依然会存在。

## 强制同步布局

强制同步布局发生在 JavaScript 修改样式后，马上读取布局信息，浏览器不得不提前计算最新布局。

```javascript
box.classList.add('expanded');
console.log(box.offsetHeight);
```

常见会触发布局读取的属性包括 `offsetWidth`、`offsetHeight`、`clientWidth`、`scrollTop`、`getBoundingClientRect()` 等。不是不能读，而是要避免读写交错。

如果必须读取布局信息，尽量集中读取，再统一写入样式。这样浏览器可以减少被迫同步计算。

很多强制同步布局其实并不是业务必须，而是代码组织方式导致的。把读布局和写样式拆开，往往就是很高收益的修复。

## 布局抖动

布局抖动是多次读写交错造成的连续强制布局。

```javascript
// 不推荐
for (const item of items) {
  item.style.width = `${container.offsetWidth}px`;
}
```

更好的方式是先读后写：

```javascript
const width = container.offsetWidth;

for (const item of items) {
  item.style.width = `${width}px`;
}
```

web.dev 对 Layout Thrashing 的建议也强调：先批量读取旧布局值，再批量写入样式，避免 read-write-read-write 循环。

布局抖动往往出现在循环里，一次很小的读写交错，乘以大量节点就会变成明显卡顿。

列表、表格、瀑布流和批量更新场景里尤其要留意这种模式。单次看似无害，循环后就会放大成真实交互卡顿。

## 图层控制

`will-change` 可以提示浏览器某个属性即将变化，但不能滥用。过多图层会增加内存和合成成本。

```css
.dragging {
  will-change: transform;
}
```

`will-change` 适合短时间内即将发生的动画或拖拽，不适合作为全局默认样式。动画结束后可以移除提示。

如果一个元素长时间没有动画，却一直保留 `will-change`，浏览器可能一直为它保留额外资源。

`will-change` 更像短期提示，而不是长期样式设计的一部分。越是公共组件，越要警惕把它默认写死在基础样式里。

## 排查路径

排查重排重绘要结合 DevTools Performance 面板，看 Layout、Paint、Composite、Long Task 和交互延迟。

| 现象 | 可能原因 |
|---|---|
| 点击后卡顿 | 事件回调触发大量 Layout |
| 滚动掉帧 | DOM 太多、Paint 太重 |
| 动画不流畅 | 使用几何属性动画 |
| INP 高 | 主线程布局和渲染压力大 |

重排重绘和 [[1.3.10 DOM|DOM]]、[[6.1.1 核心性能指标|核心性能指标]] 是一条线：DOM 操作影响渲染链路，渲染链路最终会反映到用户指标上。

排查时先看现象：点击卡、滚动卡、动画卡，对应的瓶颈可能完全不同。不要所有问题都用同一种优化套路。

重排重绘优化是否有效，可以重点验证：

| 观察点 | 说明 |
| --- | --- |
| Layout / Paint 时间是否下降 | 主要瓶颈是否被击中 |
| 点击和滚动是否更流畅 | 用户体感是否改善 |
| 是否减少了强制同步布局 | 代码组织是否更合理 |
| 是否引入了新的图层或内存问题 | 优化是否只是转移成本 |
