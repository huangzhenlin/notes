## 渲染窗口

虚拟列表用于处理大量列表项渲染。它不会一次性把所有 DOM 节点渲染出来，而是只渲染视口附近的一小段窗口。

```text
总列表：100000 条
实际 DOM：可见 20 条 + 缓冲 10 条
```

虚拟列表解决的是 DOM 数量过多带来的渲染、布局和内存压力。它不减少数据量本身，也不自动解决接口分页问题。

所以虚拟列表通常要和分页、懒加载、图片懒加载一起设计。只做虚拟渲染，不处理数据量和图片解码，仍然可能卡。

虚拟列表不是“数据一多就上”的默认答案，而是当 DOM 数量和渲染量真的成为瓶颈时的一种结构化手段。

## 固定高度

固定高度列表最简单，因为每一项高度一致，可以通过索引直接计算位置。

```tsx
import { FixedSizeList } from 'react-window';

function Row({ index, style }) {
  return (
    <div style={style}>
      第 {index} 行
    </div>
  );
}

export function LargeList() {
  return (
    <FixedSizeList
      height={500}
      width={400}
      itemCount={100000}
      itemSize={36}
    >
      {Row}
    </FixedSizeList>
  );
}
```

`style` 必须挂到行元素上，因为虚拟列表依赖绝对定位控制每一行的位置。漏掉它，列表会全部堆在一起。

固定高度列表性能最好，因为滚动位置和 item 位置都可以直接计算。能统一行高的场景，优先统一行高。

固定高度的收益不仅是快，还包括心智简单、滚动稳定和调试成本低。设计上如果能接受统一高度，往往会让整套虚拟化方案轻松很多。

## 动态高度

动态高度列表更复杂，因为每一项高度不同，需要知道或测量每个 item 的尺寸。

```tsx
import { VariableSizeList } from 'react-window';

function getItemSize(index: number) {
  return index % 2 === 0 ? 48 : 72;
}

<VariableSizeList
  height={500}
  width={400}
  itemCount={items.length}
  itemSize={getItemSize}
>
  {Row}
</VariableSizeList>
```

真实业务中，动态高度可能来自文本换行、图片加载、折叠展开和异步内容。高度变化后要通知列表重新计算，否则滚动位置会错。

动态高度列表最容易出现跳动和定位不准。设计上如果能限制内容高度、固定图片比例或折叠长文本，虚拟化会稳定很多。

所以动态高度列表往往不只是前端实现问题，也需要设计和产品配合收敛内容边界。没有边界的自由排版，会显著增加虚拟化复杂度。

## 缓冲区

虚拟列表通常会在视口上下额外渲染一部分缓冲项，避免用户快速滚动时看到空白。

```tsx
<FixedSizeList
  height={500}
  width={400}
  itemCount={items.length}
  itemSize={40}
  overscanCount={5}
>
  {Row}
</FixedSizeList>
```

缓冲太小会闪白，缓冲太大又会增加 DOM 数量。移动端低端机更需要谨慎调试，因为滚动速度、主线程压力和内存都更敏感。

缓冲区不是固定答案。内容轻、滚动快可以适当加大；内容重、设备弱则要控制缓冲，避免一次渲染太多。

缓冲区调参时要在“空白闪现”和“渲染过重”之间找平衡。不同设备、不同列表复杂度下，合适值可能差别很大。

## 数据加载

虚拟列表只负责渲染窗口，不负责远程分页。无限滚动场景需要结合分页加载。

```tsx
function onItemsRendered({ visibleStopIndex }) {
  if (visibleStopIndex > items.length - 10 && hasMore && !loading) {
    loadMore();
  }
}
```

数据加载要处理重复请求、加载中状态、没有更多、请求失败和重试。只根据滚动位置触发请求，很容易在快速滚动时重复加载。

无限滚动还要注意滚动恢复。用户进入详情再返回列表时，如果无法恢复位置和数据，会严重影响体验。

这类体验问题经常比纯性能问题更容易被用户感知。虚拟列表如果让用户丢滚动位置、选中状态或已加载数据，再快也会让体验打折。

## 键与状态

虚拟列表会复用 DOM 节点。如果行内组件保存局部状态，必须保证 key 和 item 数据对应稳定。

```tsx
<FixedSizeList
  itemKey={(index) => items[index].id}
  itemCount={items.length}
  itemSize={40}
>
  {Row}
</FixedSizeList>
```

不要用默认索引 key 处理可排序、可插入、可删除的列表，否则滚动后可能出现状态错位。

虚拟列表复用 DOM，key 不稳定会让输入框、选中状态、展开状态错位。数据 id 应该优先作为 itemKey。

状态错位是虚拟列表里非常典型的隐性 bug。它不一定总是报错，但会在滚动、插入、排序后悄悄出现错误交互。

## 可访问性

虚拟列表会让 DOM 中只存在部分列表项，这可能影响浏览器查找、读屏器和页面内搜索。需要根据场景评估可访问性。

| 场景 | 建议 |
|---|---|
| 后台大表格 | 虚拟列表合适 |
| 普通短列表 | 不需要虚拟化 |
| 文档阅读 | 谨慎虚拟化 |
| 可搜索内容 | 提供服务端搜索或全局搜索 |

不是所有长列表都要虚拟化。如果列表只有几百项、渲染内容简单，分页或普通懒加载可能更简单。

虚拟化会牺牲部分原生页面能力，例如浏览器查找、完整 DOM 选择、读屏连续阅读。内容型长文档要谨慎使用。

所以是否启用虚拟列表，不能只看性能收益，还要看业务是否依赖这些原生能力。后台表格和文档阅读页，对虚拟化的接受度完全不同。

## 性能边界

虚拟列表减少 DOM 数量，但不会消除行组件本身的渲染成本。如果每一行都有复杂图表、图片、富文本和大量事件，仍然会卡。

```text
虚拟列表优化：
1. DOM 节点数量
2. 布局压力
3. 内存占用

不能自动优化：
1. 单行渲染复杂度
2. 数据计算成本
3. 图片解码成本
```

虚拟列表和 [[6.3.6 重排与重绘|重排与重绘]]、[[6.2.2 懒加载|懒加载]] 经常一起使用：列表负责少渲染，图片负责晚加载，样式负责少触发布局。

判断是否需要虚拟列表，可以先用 Performance 面板看 DOM 数量、Layout 耗时和内存。如果瓶颈不是 DOM 数量，虚拟化未必是正确解法。

虚拟列表是否真的值得，最终可以看三个问题：

| 问题 | 用来判断什么 |
| --- | --- |
| DOM 数量是否已经成为主要成本 | 是否命中瓶颈 |
| 启用后滚动和交互是否更稳 | 真实体验收益 |
| 是否引入了可接受的复杂度和限制 | 工程取舍是否合理 |
