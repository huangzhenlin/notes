## Core Web Vitals

核心 Web 指标关注用户能否快速看到、快速交互、页面是否稳定。

| 指标 | 含义 | 关注点 |
|---|---|---|
| LCP | 最大内容绘制 | 首屏主体内容出现速度 |
| INP | 交互到下一次绘制 | 交互响应延迟 |
| CLS | 累计布局偏移 | 页面视觉稳定性 |
| FCP | 首次内容绘制 | 页面开始有内容 |
| TTFB | 首字节时间 | 服务端和网络响应 |

LCP 常受图片、字体、接口、SSR、CDN 影响；INP 常受长任务、事件回调、渲染压力影响；CLS 常受图片尺寸、广告、字体替换和异步插入内容影响。

## PerformanceObserver

浏览器提供 `PerformanceObserver` 监听性能条目。它可以采集 paint、resource、navigation、longtask、layout-shift 等数据。

```javascript
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.name, entry.startTime, entry.duration);
  }
});

observer.observe({
  type: 'resource',
  buffered: true,
});
```

`buffered: true` 可以读取观察器创建前已经产生的条目，避免脚本加载较晚时漏掉早期指标。

## LCP 采集

LCP 表示视口内最大的内容元素完成绘制的时间。它通常对应首屏大图、标题、视频封面或主要文本块。

```javascript
let lcpEntry;

const observer = new PerformanceObserver((list) => {
  const entries = list.getEntries();
  lcpEntry = entries[entries.length - 1];
});

observer.observe({
  type: 'largest-contentful-paint',
  buffered: true,
});

window.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden' && lcpEntry) {
    reportMetric('LCP', lcpEntry.startTime, {
      element: lcpEntry.element?.tagName,
      url: lcpEntry.url,
    });
  }
});
```

LCP 要在页面隐藏或用户离开时上报，因为最大元素可能随着加载继续变化。采集时记录元素类型和 URL，有助于判断瓶颈是图片、字体还是服务端。

如果只记一个数值而不记上下文，后续定位会很吃力。尤其是 LCP，知道是图片、标题还是视频封面，排查方向会完全不同。

## CLS 采集

CLS 衡量页面意外布局偏移。用户主动交互后的布局变化通常不算入问题，真正要关注的是“用户没操作，页面突然跳了”。

```javascript
let cls = 0;

new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (!entry.hadRecentInput) {
      cls += entry.value;
    }
  }
}).observe({
  type: 'layout-shift',
  buffered: true,
});
```

CLS 上报时最好带上发生偏移的页面区域、元素信息和版本号。布局偏移往往和广告位、图片宽高、字体加载和骨架屏替换有关。

CLS 还要注意聚合方式。单次偏移可能不明显，但多次小偏移加起来也会形成真实体验问题，所以采集时要保证能还原会话内的累计情况。

## INP 采集

INP 衡量页面交互响应。它关注用户点击、键盘输入、触摸之后，到下一次页面绘制之间的延迟。INP 取页面生命周期中较差的交互，而不是第一次交互。

```javascript
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    reportMetric('interaction', entry.duration, {
      name: entry.name,
      startTime: entry.startTime,
    });
  }
}).observe({
  type: 'event',
  buffered: true,
  durationThreshold: 40,
});
```

INP 问题通常要结合长任务、主线程占用和具体交互事件定位。只知道 INP 高还不够，还要知道用户点了什么、当时哪些任务在执行。

对于关键交互，最好额外记录交互类型、目标区域和当时的页面状态。比如是在搜索、下拉筛选、弹窗打开还是列表切换，这些信息会直接影响定位效率。

## 资源指标

资源指标能帮助判断 JS、CSS、图片、字体、接口和第三方脚本的加载成本。

```javascript
const resources = performance
  .getEntriesByType('resource')
  .filter((entry) => entry.initiatorType === 'script')
  .map((entry) => ({
    name: entry.name,
    duration: entry.duration,
    transferSize: entry.transferSize,
  }));
```

资源指标和 [[6.4.1 包体积分析|包体积分析]] 可以互相验证：构建报告告诉你产物有多大，真实资源指标告诉你用户实际下载了多少、缓存是否命中、CDN 是否稳定。

很多时候构建产物看起来不算大，但真实资源耗时仍然很高，原因可能是缓存没命中、网络质量差、优先级不对或第三方域名响应慢。采集的价值就在于把这些差异看出来。

## 上报策略

性能数据量很大，不应该全量无脑上报。常见策略是采样、合并、延迟发送和页面隐藏时发送。

```javascript
function reportMetric(name, value, detail = {}) {
  const payload = JSON.stringify({
    name,
    value,
    detail,
    path: location.pathname,
    release: window.__APP_RELEASE__,
    time: Date.now(),
  });

  navigator.sendBeacon('/metrics', payload);
}
```

`sendBeacon` 适合页面卸载或隐藏时发送轻量数据。指标上报要带页面、版本、设备、网络、浏览器和采样信息，否则后续聚合分析会失真。

上报策略还要考虑失败容忍。性能数据丢一点通常可接受，但不能因为上报逻辑本身再给页面增加明显负担，所以采集脚本本身也要尽量轻。

## 数据解释

性能指标要看分位数，不要只看平均值。平均值容易被少量极端值影响，也掩盖长尾用户体验。

| 统计方式 | 价值 |
|---|---|
| P50 | 典型用户体验 |
| P75 | Web Vitals 常用判断点 |
| P95 | 长尾问题 |
| 按页面分组 | 定位慢页面 |
| 按版本分组 | 发现发布退化 |
| 按设备分组 | 发现低端机问题 |

采集到数据只是开始。性能优化要形成闭环：发现指标异常，定位原因，发布优化，继续观察同一指标是否改善。

真正成熟的采集体系，还会把数据按页面、版本、设备、网络、人群分层展示。这样团队不是只看“全站平均变慢”，而是能看到“哪个页面、哪次发布、哪类用户在变慢”。
