## 预算含义

性能预算就是在项目还没变慢之前，先给它设定可接受上限。它的价值不在于写一份表，而在于把“别太慢”变成可执行规则。

常见预算对象包括：

- 页面级指标预算，如 `LCP`、`INP`、`CLS`
- 资源体积预算，如 JS、CSS、图片总大小
- 构建产物预算，如首屏关键 chunk 大小
- 请求数量预算，如首页初始请求数、第三方脚本数量

## 预算落地

预算要能进流水线，否则只是口号。一个常见落点是构建或 CI：

```json
{
  "homepage": {
    "js": "180kb",
    "css": "40kb",
    "lcp": "2500ms"
  }
}
```

然后在构建脚本里读取这份预算，超过阈值就报警或失败。这样预算才会和 [[5.7 CI-CD/5.7.3 构建验证|构建验证]]、[[5.7 CI-CD/5.7.5 灰度发布|灰度发布]] 连起来。

预算只有进入日常流程，才会真的改变行为。否则团队知道“最好别太大”，但每次需求上线时仍然会优先让功能通过，性能成本也就会持续累积。

## 预算层次

预算不要只设一层。更实用的做法是分成三档：

| 档位 | 含义 | 处理方式 |
| --- | --- | --- |
| 目标值 | 理想体验 | 日常优化朝这个值靠近 |
| 警戒值 | 开始退化 | 阻止继续放大问题 |
| 阻断值 | 已不可接受 | CI 失败或发布阻断 |

这样团队不会因为一次轻微波动就寸步难行，也不会等到页面明显变慢了才发现。

三档预算的好处，是既能保留工程弹性，也能让问题在真正变严重之前被看见。它比单一硬阈值更适合长期治理。

## 预算对象

性能预算是给页面性能设定可量化上限。它不是“优化建议”，而是发布前必须检查的约束。

```txt
JS 总量 <= 250KB gzip
首屏图片 <= 300KB
LCP <= 2.5s
INP <= 200ms
CLS <= 0.1
```

预算可以约束资源体积、请求数量、关键指标、第三方脚本、构建产物。它的价值在于防止性能在每次需求迭代中悄悄变差。

## 资源预算

资源预算最容易落地，适合放进构建和 CI。

```json
{
  "budget": {
    "javascript": "250kb",
    "css": "80kb",
    "image": "500kb",
    "thirdParty": "150kb"
  }
}
```

资源预算要按页面类型设置。营销首页、后台列表、移动端活动页的预算不应完全相同。移动端页面尤其要限制 JS 和图片体积。

资源预算和设备特性也要匹配。桌面后台和移动 H5 即使用的是同一套技术栈，预算上限也不应该一样。

## 指标预算

指标预算关注真实用户体验。

| 指标 | 常见预算 | 关注点 |
| --- | --- | --- |
| LCP | 2.5s 内 | 首屏最大内容加载 |
| INP | 200ms 内 | 交互响应 |
| CLS | 0.1 内 | 布局稳定性 |
| TTFB | 800ms 内 | 服务端响应 |
| FCP | 1.8s 内 | 首次内容出现 |

指标预算应区分实验室数据和真实用户数据。Lighthouse 分数好看，不代表真实低端机和弱网用户体验一定好。

实验室预算更适合做回归比较，真实用户预算更适合做上线判断。两者一起用，才能同时兼顾可重复性和真实性。

## 页面分级

不同页面承担不同业务价值，预算也应分级。

```txt
核心转化页：预算最严格
高频访问页：严格控制
后台低频页：关注交互和稳定性
活动页：关注首屏和图片体积
```

例如电商的商品详情、结算页、登录页应该有更严格预算；内部配置页可以稍宽，但也不能无限制引入依赖。

## 第三方预算

第三方脚本常常是性能预算失控的来源。

| 类型 | 风险 |
| --- | --- |
| 监控 SDK | 初始化和上报成本 |
| 客服组件 | 大 JS 包和样式 |
| 广告脚本 | 长任务、布局变化 |
| A/B 实验 | 阻塞渲染、闪烁 |
| 地图/图表 | 体积大、运行成本高 |

第三方脚本也要有负责人和预算。不能因为它“不在业务仓库里”就不计入页面性能成本。

很多项目的性能失控，并不是因为业务代码写得差，而是因为第三方一点点叠加进来却没人负责。只要没人对第三方体积和运行成本负责，它就会持续膨胀。

## CI 检查

性能预算可以通过构建分析、Lighthouse CI、bundle analyzer 等工具自动检查。

```txt
构建产物超过预算 -> CI 失败
Lighthouse 指标低于阈值 -> 阻止合并
新增第三方脚本 -> 需要说明收益和成本
```

CI 不一定一开始就卡所有指标。可以先从 JS/CSS 体积、关键页面 Lighthouse、第三方脚本清单开始，逐步提高约束。

预算落地最怕“一刀切过严”。如果团队一开始就被大量失败门禁卡住，最终更可能绕开预算，而不是认真治理。

## 预算调整

预算不是永远不变。新增关键能力可能需要提高预算，但必须说明收益、成本和替代方案。

```txt
为什么增加体积
增加多少
影响哪些页面
是否可按需加载
是否有更轻方案
是否有回滚计划
```

性能预算的目标不是阻止业务，而是让性能成本被看见、被讨论、被控制。

预算是否健康，可以看几个问题：

| 问题 | 理想状态 |
| --- | --- |
| 新增功能是否会显式暴露性能成本 | 会 |
| 性能退化是否能在 PR 或发布前被发现 | 能 |
| 团队是否知道哪些页面预算最严格 | 知道 |
| 超预算后是否有清楚处理方式 | 有 |
