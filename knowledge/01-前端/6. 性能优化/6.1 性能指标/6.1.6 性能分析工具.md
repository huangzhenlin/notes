## DevTools

Chrome DevTools 更适合定位根因。看性能录制时，优先关注：

- Main 线程是否有连续长任务
- 是否存在频繁 Layout、Recalculate Style、Paint
- 首屏关键资源是不是下载太晚
- 交互操作后是否有异常脚本峰值

如果你已经知道“慢”，DevTools 更适合回答“为什么慢”。

## 线上监控

线上监控负责回答三件事：

1. 这次发布有没有让真实用户变慢。
2. 变慢影响的是哪个页面、哪个区域、哪类设备。
3. 问题是偶发，还是稳定回归。

如果只有本地分析工具，没有线上指标，你会知道“理论上变快了”；如果只有线上监控，没有性能录制，你会知道“真的变慢了”，却不容易找根因。

性能分析工具最怕被孤立使用。单一工具通常只能回答一部分问题，只有把实验室、线上、构建和运行时工具串起来，团队才能既看到现象，也找到根因。
## 工具分层

性能分析工具可以分为实验室工具、真实用户监控、构建分析、运行时 Profiling。

| 类型 | 工具 | 作用 |
| --- | --- | --- |
| 实验室 | Lighthouse、WebPageTest | 可重复测试 |
| 真实用户 | RUM、PerformanceObserver | 线上体验 |
| 构建 | Bundle Analyzer | 资源体积 |
| 运行时 | Chrome DevTools Performance | 定位长任务和渲染 |
| 框架 | React Profiler、Vue Devtools | 组件渲染 |

没有一个工具能回答所有问题。加载慢、交互慢、包体大、渲染卡顿，需要不同工具组合判断。

所以在使用工具之前，先把问题分类往往更重要。是加载问题、交互问题、构建问题，还是线上特定人群问题，不同分类会直接决定工具优先级。

## Lighthouse

Lighthouse 适合快速检查页面的性能、可访问性、最佳实践、SEO。

```txt
Performance
Accessibility
Best Practices
SEO
```

它提供的是实验室环境结果，适合回归对比和发现明显问题。不要只看总分，要看 LCP、TBT、CLS、资源瀑布和诊断建议。

Lighthouse 最适合做“标准化体检”，不适合直接代表所有真实用户。它能帮助团队快速发现明显退化，但不能代替真实用户监控。

## Performance 面板

Chrome DevTools Performance 面板适合定位运行时问题。

```txt
录制用户操作
查看 Main 线程
查找 Long Task
展开 Call Tree
查看 Layout / Paint / Composite
```

交互卡顿、滚动掉帧、动画不流畅、输入延迟，都应该用 Performance 面板录制具体操作，而不是凭感觉改代码。

Performance 面板的价值，在于能把“感觉卡”拆成脚本、布局、绘制、合成等具体阶段。只有看到主线程时间线，很多隐藏的阻塞才会暴露出来。

## Network 面板

Network 面板适合分析资源加载。

```txt
请求数量
资源大小
缓存命中
阻塞时间
优先级
瀑布图
```

首屏慢时，先看 HTML、CSS、JS、字体、LCP 图片的加载顺序。关键资源是否被晚发现、是否被低优先级加载，常常比单个文件大小更重要。

Network 瀑布图特别适合回答“为什么它这么晚才开始下载”这类问题。很多首屏问题不是资源太大，而是发现太晚、优先级不对或被其他请求抢占了。

## Coverage

Coverage 可以查看 JS 和 CSS 的未使用比例。

```txt
DevTools -> More tools -> Coverage
```

它适合发现首屏加载了大量当前页面不用的代码。发现未使用代码后，再考虑路由级拆包、组件按需加载、CSS 拆分、第三方库替换。

Coverage 很适合做“当前页面到底真的用了多少”的快速验证，尤其对首页、营销页和复杂后台首屏很有帮助。

## Bundle Analyzer

构建分析工具用于查看产物组成。

```txt
哪个依赖最大
是否重复打包
是否引入了整个工具库
是否存在多语言包
是否能拆到异步 chunk
```

包体优化要从依赖图入手。看到 JS 大，不要只压缩代码，先看是否引入了不必要依赖或没有做按需加载。

构建分析工具更像“静态解剖”，它能帮助你发现产物组成，却不直接告诉你真实用户是否因此变慢。所以最好总是和真实指标结合看。

## PerformanceObserver

线上指标可以通过 PerformanceObserver 采集。

```js
new PerformanceObserver((entryList) => {
  for (const entry of entryList.getEntries()) {
    console.log(entry.name, entry.startTime, entry.duration);
  }
}).observe({ type: "largest-contentful-paint", buffered: true });
```

真实用户监控能看到不同设备、网络、地区、浏览器下的表现。实验室数据用于定位，RUM 数据用于判断真实影响范围。

线上监控最重要的价值，是帮助你确认某次优化到底有没有真的改善目标用户，而不是只在开发机或 CI 环境里变好看。

## 工具选择

| 问题 | 优先工具 |
| --- | --- |
| 首屏慢 | Lighthouse、Network、WebPageTest |
| 点击慢 | Performance、INP 监控 |
| JS 包大 | Bundle Analyzer、Coverage |
| 列表卡顿 | Performance、React Profiler |
| 布局跳动 | Layout Shift 调试、Performance |
| 线上用户慢 | RUM、日志、指标平台 |

先明确问题，再选工具。工具输出很多，关键是把它们对应到用户体验和具体代码路径。

一个比较稳的分析顺序通常是：

```text
先用线上数据确认问题是否真实存在
  -> 再用实验室工具复现
  -> 再用运行时工具定位根因
  -> 最后回到构建和依赖层做治理
```

这样能避免团队在没有确认用户影响前就陷入细碎调参，也能减少“优化了半天但方向不对”的情况。
