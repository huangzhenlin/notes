## 指标含义

长任务是指主线程上持续执行超过 50ms 的任务。浏览器在任务执行期间无法及时处理输入、渲染和其他回调。

```txt
Main Thread: |--------- 120ms JS Task ---------|
用户点击:                 等待任务结束后才处理
```

长任务越多，页面越容易出现点击延迟、输入卡顿、动画掉帧。它和 TBT、INP 这类交互体验指标关系很近。

## 50ms 阈值

浏览器把超过 50ms 的任务视为 Long Task。超过部分会计入阻塞时间。

```txt
任务耗时 80ms
阻塞时间 80 - 50 = 30ms
```

这个阈值来自用户感知：如果主线程长时间不让出控制权，用户输入就会明显变慢。优化目标不是让所有任务都消失，而是减少关键交互路径上的阻塞。

50ms 不是绝对魔法值，但它是一个很实用的经验边界。任务超过这个时间，用户大概率已经开始感到迟钝。

长任务之所以重要，不是因为某个数字本身，而是因为它直接占住了主线程，让浏览器没机会及时响应用户和更新界面。

## 常见来源

| 来源 | 表现 |
| --- | --- |
| 大 JS 初始化 | 首屏主线程长时间忙碌 |
| 大数组计算 | 搜索、排序、过滤卡顿 |
| JSON 解析 | 大接口响应后页面卡住 |
| 一次性渲染 | 大列表、大表格创建慢 |
| 第三方脚本 | 业务代码之外的阻塞 |
| 复杂样式计算 | 大量 DOM 和选择器 |

长任务往往不是单个语句的问题，而是一段流程一次做了太多事情。

所以定位长任务时，不要盯着一行代码，而要看整段流程是否能被切开、延后或转移到后台。

一个长任务通常意味着“太多事情在同一时刻被同步完成”。优化时真正要做的，往往不是把其中某一小步写得更快，而是重新安排这段工作的时机和位置。

## Performance 定位

Chrome DevTools Performance 面板可以直接看到 Long Task。

```txt
录制页面加载或交互
查看 Main 线程上的红色三角
展开任务调用栈
看 Bottom-Up 中耗时函数
定位到具体脚本或第三方资源
```

定位时要区分业务脚本、框架运行时、构建产物、第三方脚本。第三方脚本造成的长任务，也需要进入性能预算和加载策略。

如果长任务来自框架更新，可能要减少状态范围；如果来自第三方脚本，可能要延迟或隔离；如果来自业务逻辑，就要拆任务、分页或挪到 Worker。

因此长任务分析最好总是和交互上下文一起看。某次长任务发生在首屏初始化、输入联想、筛选列表还是动画过程中，优化方式通常完全不同。

## Long Tasks API

浏览器提供 PerformanceObserver 观察长任务。

```js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log("long task", entry.startTime, entry.duration);
  }
}).observe({ type: "longtask", buffered: true });
```

线上监控可以采集长任务数量、耗时和页面路径，用来发现真实用户环境中的主线程阻塞。

把长任务数据和版本、设备、网络一起看，才知道是所有用户都慢，还是只有低端机或某个版本慢。

线上长任务数据特别适合发现“本地机器看不出来”的问题。高性能开发机上顺滑的操作，放到低端手机上可能早就被长任务拖垮了。

## 拆分任务

大任务可以拆成小块，让浏览器有机会处理输入和渲染。

```js
async function renderChunks(items) {
  const size = 200;

  for (let index = 0; index < items.length; index += size) {
    render(items.slice(index, index + size));

    await new Promise((resolve) => setTimeout(resolve, 0));
  }
}
```

拆分任务不会减少总工作量，但能降低单次阻塞时间。对用户来说，“能持续响应”比“一口气做完但卡住”更重要。

任务切片适合大循环、列表渲染和批量处理。它不是把代码变复杂，而是让浏览器有机会插空处理输入和绘制。

任务切片也要注意粒度。切得过粗仍然会卡，切得过碎又可能增加调度成本，所以要围绕用户交互节奏做权衡。

## 后台线程

CPU 密集任务可以交给 Web Worker。

```js
const worker = new Worker(new URL("./search-worker.js", import.meta.url), {
  type: "module",
});

worker.postMessage({ keyword, items });
worker.onmessage = (event) => {
  updateResult(event.data);
};
```

Worker 适合搜索索引、复杂计算、压缩、加密、大 JSON 处理。它不能直接操作 DOM，数据传输也要控制体积。

如果任务更偏计算而不是 UI，Worker 往往是最有效的手段之一。它把 CPU 密集工作从主线程挪走，能明显改善交互。

但 Worker 不是免费午餐。数据序列化、消息传递和结果同步也有成本，所以更适合真正重计算、可异步处理的任务。

## 优化判断

| 问题 | 优化方向 |
| --- | --- |
| 启动长任务 | 代码拆分、延迟非关键脚本 |
| 交互长任务 | 任务切片、减少同步计算 |
| 列表长任务 | 虚拟列表、分页渲染 |
| 第三方长任务 | 延迟加载、移除、预算约束 |
| 大数据处理 | Worker、服务端处理 |

长任务优化要优先保护用户正在操作的路径。后台预热任务可以慢一点，但点击、输入、滚动不能被长时间阻塞。

最好的长任务优化，不是“把所有事情拆得极碎”，而是把真正影响用户感知的那几段阻塞先压下去。

判断长任务治理是否有效，可以看：

| 观察点 | 说明 |
| --- | --- |
| 关键交互后的卡顿是否明显减少 | 用户体感改善 |
| INP 或 TBT 是否同步下降 | 指标层验证 |
| 低端设备收益是否更明显 | 优化命中痛点 |
