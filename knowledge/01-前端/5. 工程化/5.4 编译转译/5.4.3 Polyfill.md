## 能力补齐

Polyfill 的作用，是补齐运行时缺失的 API 或行为。它不是语法转换，而是把目标环境没有的能力加回来。

```text
语法转换：把写法改掉
Polyfill：把能力补回来
```

这两个概念经常被混在一起。比如箭头函数、解构、可选链属于语法层，靠 Babel、SWC 这类转译工具处理；Promise、Map、Set、fetch 这类能力则要看运行时是否存在，缺了就要用 polyfill 补。

如果只做语法降级，不补运行时能力，代码在老环境里仍然可能报错。

Polyfill 的目标不是“让所有旧环境都完全等价于现代浏览器”，而是让项目在明确支持范围内稳定运行。很多现代特性可以不补，因为业务根本不会在旧环境走到那条路径；但如果核心流程依赖某个 API，就不能赌运行时一定有。

所以 polyfill 不是越全越好，而是越贴近真实兼容边界越好。工程里真正需要回答的问题通常不是“这个 API 能不能补”，而是“这个场景值不值得为它补”。如果只为了极小比例的用户把所有现代能力全量带上，最终受影响的是所有用户的下载和执行成本。

## 使用方式

现在更常见的做法，是按需引入，而不是整包注入。

```ts
import "core-js/stable";
```

```text
更推荐：
1. 只引入需要的能力
2. 结合目标浏览器决定
3. 避免全量 polyfill
```

按需引入的前提，是先明确目标浏览器范围。比如项目只面向现代浏览器和少量移动端内置 WebView，可能根本不需要大面积补齐；如果还要兼容旧内网环境或老旧终端，就要认真评估 polyfill 的范围。

按需引入还要和构建工具联动。很多工程会用 `@babel/preset-env`、`core-js` 或类似方案按目标浏览器注入必要能力。做法不同，控制粒度也不同，但核心原则都是“只补目标环境真的缺少的东西”。

如果项目存在多入口、多端或多运行环境，还要注意不同入口未必需要同样的 polyfill。登录页、活动页、后台系统和嵌入式 WebView 页面，兼容压力可能完全不同，统一塞入一整套补丁往往不是最优解。

## 适用场景

| 场景 | 是否需要 |
| --- | --- |
| Promise / Map / Set | 可能需要 |
| 箭头函数 / 解构 | 不属于 polyfill |
| 老浏览器兼容 | 常需要 |
| 现代浏览器内网项目 | 可能不需要 |

不同能力的兼容策略也不一样。像 Promise、URL、URLSearchParams、Array.prototype.includes 这类基础能力，通常更常见；而更复杂的国际化、加密、流媒体、文件处理能力，往往不适合靠 polyfill 硬补到底。

```text
先问：
1. 目标环境是否原生支持
2. 是否真会走到该代码路径
3. 补齐后体积是否可接受
```

实际判断时还可以再加两步：

```text
4. 是否存在更轻的降级写法
5. 是否可以直接调整支持范围
```

有些问题未必要靠 polyfill 解决。比如只是为了一个小特性而引入整套运行时补丁，很多时候不如改写业务代码或直接声明“不支持该旧环境”。

## 体积成本

Polyfill 会直接增加运行时代码体积，所以需要和目标浏览器一起决策，而不是默认全开。

```text
成本包括：
1. 包体积
2. 首屏加载
3. 全局污染
4. 维护复杂度
```

Polyfill 的体积成本经常被低估，因为它会和应用代码一起进入首屏。项目如果只是为了兼容极少数老浏览器，却给所有用户都加了大量补齐代码，整体收益通常不划算。

```text
常见误区：
1. 把 polyfill 当成兼容万能药
2. 不看目标环境直接全量引入
3. 把语法转译和运行时补齐混为一谈
4. 忽略体积和首屏影响
```

除了下载体积，polyfill 还有执行成本。很多补丁会在页面启动阶段立刻运行，修改全局对象、安装方法或做环境判断。移动端低性能设备上，这些初始化成本也可能变成真实卡顿。

## 全局污染

有些 polyfill 会修改全局对象或原型链，这在库开发里通常要特别谨慎。

```text
应用项目：
可接受部分全局补齐
库项目：
尽量避免污染全局
```

对于库项目来说，更好的策略通常是把兼容责任交给消费方。库如果主动改写全局原型，可能会和宿主应用、其他库或运行时环境冲突，排查起来会很痛。

库开发还有一个问题：不同消费方的目标浏览器不一样。如果库自己强行带上 polyfill，可能会和宿主应用已有的补齐策略重复甚至冲突。所以库更适合保持纯净，让应用决定兼容层。

如果确实要在库里提供兼容能力，通常也应该是显式、可选、文档化的方案，而不是默认偷偷注入。这样消费方才能根据自己的目标环境决定是否启用。

## 选型原则

如果只是应用兼容，按需补齐最稳；如果是库，尽量让消费方自己决定是否加载 polyfill。polyfill 的核心不是“越多越好”，而是“补到刚好够用”。

在工程里，polyfill 最好和 browserslist、构建配置、目标平台说明一起管理。这样团队在新增浏览器支持范围时，能同步更新兼容策略，而不是到线上出错后再回头补。

如果项目有明显的兼容边界，最好把它写成明确规范，比如“仅支持近两年主流浏览器”和“旧内网浏览器不在支持范围内”。支持范围越清楚，polyfill 策略越容易稳定。

更稳妥的实践，是把 polyfill 当成一项“兼容预算”来管理：支持范围扩大了，体积和测试成本也会扩大；支持范围收窄了，产物就有机会更轻、更快。只有把它放到产品、前端和测试共同能理解的语境里，polyfill 才不会沦为出问题时临时乱加的一层补丁。
