## 工具定位

Babel 是 JavaScript 编译器，常用于语法转换、JSX 转换、插件式代码转换和兼容旧环境。它最强的地方是插件生态。

```text
源码
  -> parser
  -> AST
  -> transform plugins
  -> generator
  -> 输出代码
```

Babel 通常不做类型检查。TypeScript 项目仍需要 `tsc --noEmit` 或其他类型检查流程。

Babel 的核心流程是“解析源码得到 AST，再由插件修改 AST，最后生成新代码”。这使它特别适合做语法转换、框架语法支持、兼容性降级和一些工程侧代码改写。

Babel 最大的价值不只是“能转”，而是“能精细控制怎么转”。很多历史项目、组件库、框架定制能力和埋点注入逻辑，最后都落在 Babel 插件体系上。这也是为什么即使出现了更快的工具，Babel 仍然没有完全退出工程链路。

## Preset

Preset 是一组插件集合。常见 preset 包括 `@babel/preset-env`、`@babel/preset-react`、`@babel/preset-typescript`。

```javascript
module.exports = {
  presets: [
    ['@babel/preset-env', {
      targets: '> 0.5%, not dead',
    }],
    '@babel/preset-react',
    '@babel/preset-typescript',
  ],
};
```

Preset 解决的是常见场景配置，不需要为每个语法手动配置插件。

Preset 本质上是插件组合。项目越大，越要避免多个 preset 重复处理同一类语法，否则会增加构建耗时，也可能让转换结果变得难以预测。

比较稳妥的做法，是让 preset 承担通用转换，把项目个性化需求放到少量明确的 plugin 里。这样既能复用社区方案，也方便后续升级 Babel 或切换构建器时定位影响范围。

## Plugin

Plugin 是 Babel 的最小转换单元，可以转换语法、注入代码、移除调试语句、按需导入组件等。

```javascript
module.exports = {
  plugins: [
    '@babel/plugin-transform-runtime',
  ],
};
```

插件顺序会影响转换结果。遇到奇怪编译问题时，要检查插件顺序、重复配置和框架默认配置。

插件适合处理非常具体的转换。例如按需导入组件、移除调试代码、转换实验语法、复用 helper。插件越底层，越要谨慎，因为它直接改变 AST，可能影响 sourcemap、调试栈和产物可读性。

在团队协作里，Babel 插件数量最好可控。插件一多，常见问题会变成：

| 现象 | 常见原因 |
| --- | --- |
| 构建结果和预期不一致 | 插件顺序冲突 |
| 调试定位困难 | AST 改写过多，sourcemap 质量下降 |
| 升级困难 | 依赖历史插件或私有转换逻辑 |
| 迁移成本高 | 新工具无法完全兼容旧插件 |

所以 Babel 很强，但也更容易积累历史包袱。能用 preset 解决的，就不要急着写自定义插件；能在业务代码里明确表达的，也不要都丢给编译阶段偷偷改写。

## preset-env

`@babel/preset-env` 会根据目标环境决定需要转换哪些语法。

```javascript
['@babel/preset-env', {
  targets: {
    chrome: '100',
  },
}]
```

目标环境通常来自 Browserslist。目标越旧，转换越多，产物越大。

`preset-env` 的价值在于“按目标环境决定是否转换”，而不是无脑把所有语法都降到最低版本。支持范围越现代，Babel 可以保留更多原生语法，产物通常更小，运行时也更接近源码。

这也是为什么 `targets` 必须和实际用户环境对齐。目标设得太保守，会导致过度转译；目标设得太激进，又可能让低版本设备直接报错。`preset-env` 的正确用法，不是追求“最全兼容”，而是追求“和支持范围一致的兼容”。

## Polyfill

Babel 转语法，不自动完整补运行时 API。`useBuiltIns` 和 `core-js` 可以按需注入 polyfill。

```javascript
['@babel/preset-env', {
  useBuiltIns: 'usage',
  corejs: 3,
}]
```

Polyfill 策略要和 [[6.4.6 Polyfill 策略|Polyfill 策略]] 一起看。盲目引入会增加包体积。

`useBuiltIns: "usage"` 会根据源码中用到的 API 尝试按需注入 polyfill，`entry` 则更适合在入口统一导入。两者都要配合明确的 `core-js` 版本，否则容易出现重复注入或缺失补丁。

应用项目和库项目对待 polyfill 的方式也不一样。应用可以更主动地补齐运行时能力，因为它能控制最终执行环境；库则更适合减少全局副作用，把兼容责任交给宿主应用。

## transform-runtime

`@babel/plugin-transform-runtime` 可以复用 Babel helper，避免每个文件重复注入辅助函数。

```javascript
module.exports = {
  plugins: ['@babel/plugin-transform-runtime'],
};
```

库项目尤其适合使用它，减少产物重复代码，也避免污染全局。

应用项目可以接受 Babel helper 被打进产物里，但库项目更应该避免重复 helper 和全局污染。因为库会被别人的应用消费，任何隐式修改全局环境的行为都会扩大影响面。

`transform-runtime` 还有一个很现实的意义，就是让编译输出更稳定。多个文件重复塞入辅助函数，不仅会增大体积，还会让产物 diff、缓存命中和 sourcemap 阅读都变差。

## TypeScript

Babel 可以移除 TypeScript 类型并输出 JavaScript，但不会做完整类型检查。

```typescript
const value: number = 1;
```

输出后类型会被擦除。TypeScript 检查仍应由 `tsc` 或框架专用工具负责。

Babel 处理 TypeScript 时，主要是“去掉类型语法并输出 JS”。它不会判断 `string` 能不能赋值给 `number`，也不会完整执行 TypeScript 的类型系统推导，所以应用项目通常需要单独的 `typecheck` 命令。

如果项目里已经有 `tsc --noEmit`、`vue-tsc` 或框架级类型检查，就不要再误把 Babel 当成类型系统的一部分。Babel 负责的是“让代码能输出”，不是“证明类型正确”。

## SWC 对比

SWC 速度更快，Babel 插件生态更成熟。现代框架常默认使用 SWC，但遇到复杂 Babel 插件时仍可能保留 Babel。

| 场景 | 判断 |
|---|---|
| 需要成熟插件生态 | Babel |
| 追求构建速度 | SWC |
| Next 默认编译 | SWC |
| 自定义语法转换 | Babel 更灵活 |

Babel 和 [[5.4.4 SWC|SWC]] 都是编译转译工具，选择时要看速度、生态和项目已有配置。

如果项目依赖大量历史 Babel 插件，强行迁移到 SWC 可能会遇到兼容问题。如果项目只是做常规 TS/JSX 转译和压缩，SWC 或 esbuild 的速度优势会更明显。

选择 Babel 的典型信号包括：需要稳定的插件生态、需要细粒度 AST 改写、需要兼容多年积累的工程配置。反过来，如果项目只是标准 React/Vue/TS 应用，没有太多定制转换逻辑，Babel 的灵活性未必能换来足够收益，反而会增加构建复杂度。
