## 编译目标

TypeScript 编译的核心任务是把 `.ts`、`.tsx` 中的类型语法移除，并按配置输出 JavaScript、声明文件和 source map。

```text
TypeScript 源码
  -> 类型检查
  -> 类型擦除
  -> JS 输出
  -> d.ts 输出
```

TypeScript 类型只存在编译期，运行时不会自动校验类型。

这意味着 TypeScript 编译解决的是“开发阶段更早发现问题”，不是“运行时自动变安全”。如果接口返回数据不可信，仍然需要运行时校验、兜底和错误处理。

很多团队在引入 TypeScript 后，会下意识把“类型通过”等同于“逻辑安全”。这是一个常见误区。TypeScript 只能证明静态约束成立，无法保证接口响应、用户输入、第三方脚本和运行时环境一定符合预期。

## tsc

`tsc` 是 TypeScript 官方编译器。它既能类型检查，也能输出 JavaScript 和声明文件。

```bash
tsc
tsc --noEmit
```

前端应用项目常用 `tsc --noEmit` 做类型检查，把转译交给 Vite、SWC、esbuild 等工具。库项目更常用 `tsc` 生成声明文件。

应用项目追求构建速度，所以常把类型检查和产物输出拆开；库项目要发布给外部使用，所以声明文件质量非常重要。两类项目使用 `tsc` 的重点并不一样。

这也是为什么前端项目里常见两条命令并存：

```bash
pnpm build
pnpm typecheck
```

前者关注“能否生成产物”，后者关注“类型边界是否稳定”。把两者混在一起虽然看似省步骤，但在大型项目里往往会拖慢反馈速度，也不利于定位问题。

## tsconfig

`tsconfig.json` 控制编译行为。

```json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "strict": true,
    "declaration": true,
    "sourceMap": true
  },
  "include": ["src"]
}
```

`target` 控制输出 JavaScript 语法版本，`module` 控制模块格式，`strict` 控制类型严格度。

`tsconfig` 也是团队类型约定的中心。`strict`、`noImplicitAny`、`skipLibCheck`、`isolatedModules` 这些配置会明显影响类型质量和构建速度。不要只复制模板，要理解它们对项目的影响。

例如：

| 选项 | 更适合关注的问题 |
| --- | --- |
| `strict` | 是否真的建立了类型约束 |
| `skipLibCheck` | 构建速度和第三方声明兼容 |
| `isolatedModules` | 是否兼容单文件转译链 |
| `noImplicitAny` | 是否在默默放过类型空洞 |

真正稳定的 `tsconfig`，不是选项越多越好，而是能和团队当前代码质量、框架工具链、构建方式保持一致。

## noEmit

`noEmit` 表示只检查，不输出文件。

```json
{
  "compilerOptions": {
    "noEmit": true
  }
}
```

这适合应用项目，因为构建工具会负责产物输出。这样可以把类型检查和构建速度解耦。

CI 中常见做法是 `pnpm build` 和 `pnpm typecheck` 分开跑。这样构建工具可以快速出产物，类型检查可以独立失败并给出清晰错误。

如果项目使用 SWC、esbuild、Vite 这类更快的转译链，`noEmit` 往往是更合理的默认值。因为这些工具负责编译输出，`tsc` 只需要做它最擅长的静态检查。

## declaration

`declaration` 会生成 `.d.ts` 文件，适合库项目。

```json
{
  "compilerOptions": {
    "declaration": true,
    "emitDeclarationOnly": true
  }
}
```

如果只想生成类型声明，不生成 JavaScript，可以使用 `emitDeclarationOnly`。组件库和 SDK 发布时尤其需要保证声明文件正确。

声明文件要和实际导出保持一致。否则用户可能运行时能导入，类型却找不到；或者类型显示可用，运行时却没有对应导出。这类问题在组件库和工具库里非常常见。

对于库项目，声明文件不是附属产物，而是 API 的一部分。它直接决定使用者在编辑器里的自动提示、重构体验和错误暴露时机。很多“这个库不好用”的反馈，本质上都和声明文件质量有关。

## sourceMap

`sourceMap` 用于把编译后代码映射回源码。

```json
{
  "compilerOptions": {
    "sourceMap": true
  }
}
```

开发环境通常开启 source map。生产环境是否上传或公开，要结合监控和源码保护策略。

TypeScript source map 通常还会和构建工具的 source map 串起来。如果中间某一层映射丢失，线上错误可能只能定位到编译后的文件，而无法回到真实 `.ts` 或 `.tsx` 源码。

因此 source map 不只是一个“开发环境方便调试”的选项，在真实项目里，它还影响线上错误定位效率、监控平台可读性和回滚判断速度。

## moduleResolution

模块解析策略决定 TypeScript 如何理解 import。

```json
{
  "compilerOptions": {
    "moduleResolution": "bundler"
  }
}
```

现代前端项目使用 Vite、Webpack、Next 等打包工具时，`bundler` 模式更贴近构建工具解析方式。Node 库则可能使用 `node16` 或 `nodenext`。

模块解析策略会影响 package exports、路径别名、类型声明和 ESM/CJS 互操作。前端应用通常更关注和打包工具一致，Node 库则更关注和 Node 运行时一致。

如果这里配错，最常见的现象就是“编辑器里没问题，运行起来却找不到模块”或者“测试能跑，构建时报路径错误”。这些问题看起来像构建器问题，根因往往是 TypeScript 对模块的理解和运行时不一致。

## 路径别名

TypeScript 可以通过 `paths` 配置路径别名。

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

注意 TS 路径别名只影响类型解析，不一定自动影响运行时或打包工具。Vite/Webpack/Node 也要有对应配置。

这类问题很隐蔽：编辑器能跳转、类型不报错，但运行时找不到模块。路径别名必须让 TypeScript、构建工具、测试工具和运行环境都认识。

也就是说，路径别名从来不是 TypeScript 自己的配置问题，而是整个工程链路的一致性问题。只改 `tsconfig` 往往不够，还要同步检查 Vite、Webpack、Jest/Vitest、Node 执行器和 IDE 插件。

## 项目引用

大型项目和 monorepo 可以使用 Project References。

```json
{
  "references": [
    { "path": "../ui" },
    { "path": "../utils" }
  ]
}
```

它能提升增量构建效率，也能让包之间类型边界更明确。TypeScript 编译和 [[5.5.4 TypeScript检查|TypeScript检查]]、[[1.5.11 声明文件|声明文件]] 是一条线：检查保证正确，声明提供外部类型。

Project References 更适合包边界清楚的 monorepo。如果包之间随意跨目录引用内部文件，即使用了项目引用，也很难形成稳定的类型边界。

实际排查 TypeScript 编译问题时，可以优先按下面的顺序判断：

```text
报错出现
  -> 先看是类型问题还是模块解析问题
  -> 再看是 tsconfig 配置冲突还是工具链职责重叠
  -> 再看声明文件、路径别名、项目引用是否一致
  -> 最后才考虑是否需要调整转译器或构建器
```

这个顺序能避免把 TypeScript 问题一股脑甩给构建工具，也能帮助团队更快找到真正的配置边界。
