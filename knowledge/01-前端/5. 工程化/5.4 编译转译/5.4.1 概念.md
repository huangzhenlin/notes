## 转译职责

编译转译的作用，是把现代语法和特性转换成目标环境能理解的形式。它解决的是“代码写得出来”与“目标平台能不能运行”之间的落差。

```text
源码
  -> 解析语法
  -> 转换语法形态
  -> 补齐必要特性
  -> 输出目标代码
```

如果只做语法转换，不处理运行时缺失，页面仍然可能在老环境里报错；如果盲目补齐所有特性，又会把包体积和运行成本抬高。

转译的目标不是“把源码变旧”，而是“把输出变成目标环境能稳定执行的形态”。这意味着它要同时考虑语法版本、模块格式、浏览器能力和构建产物的可调试性。

## 编译与转译

工程里常把“编译”与“转译”混着说，但它们关注点并不完全一样。

| 概念 | 关注点 |
| --- | --- |
| 编译 | 从一种输入形式得到另一种输出形式 |
| 转译 | 保持语义前提下做语法或特性降级 |
| 打包 | 组织模块、资源和依赖关系 |

在前端里，很多工具既做转译，也做打包，还顺手做压缩和资源处理，所以边界看起来会很模糊。

真正做工程决策时，最好把这几个概念拆开理解。比如“页面在旧浏览器打不开”，根因可能是语法没有降级，也可能是运行时 API 没补齐，还可能是模块格式和宿主环境不匹配。如果把所有问题都归到“编译没配好”，排查会越来越乱。

## 兼容目标

转译前必须先明确目标环境。

```text
目标决定：
1. 语法降级到哪一级
2. 是否需要 polyfill
3. 是否保留现代模块语法
4. 是否输出多份构建产物
```

比如同一份源码，面向现代浏览器可以保留更高版本语法；面向旧浏览器则需要更激进的降级。没有目标环境，转译策略就只是在“猜”。

有些团队会把目标环境写进 `browserslist`，再由 Babel、Autoprefixer、构建器读取同一份配置。这样 JavaScript、CSS 和部分运行时补齐策略就不会各自为政，避免出现“JS 已经降级了，CSS 前缀却没跟上”这种不一致问题。

兼容目标本质上是产品决策，而不是单纯技术配置。一个面向新版本 Chrome 的内部系统，和一个必须兼容老 WebView 的 To C 活动页，转译策略一定不同。先明确“要支持谁”，再决定“要降到哪里”，比直接套模板可靠得多。

## 工具分工

编译转译链里常见工具包括 Babel、SWC、TypeScript 编译器和各类构建器内置转译流程。

```text
常见链路：
源码 -> 解析 AST -> 转换 AST -> 生成代码 -> 输出 sourcemap
```

| 工具 | 作用 |
| --- | --- |
| Babel | 语法转换和插件生态 |
| SWC | 更快的 Rust 实现转译器 |
| TypeScript 编译器 | 类型检查 + 语法输出 |
| 构建器内置转译 | 与打包流程整合 |

不同工具的重点不同。Babel 的优势是生态和可配置性，SWC 的优势是速度，TypeScript 编译器适合类型系统与输出同步处理。

在真实工程里，转译链路通常还要和压缩、摇树、Sourcemap、资源处理一起工作。也就是说，转译不是孤立的一步，而是构建链中的一环。链路越复杂，越要明确“谁做语法降级、谁做类型检查、谁做最终输出”。

在大项目里，这些工具经常不是二选一，而是组合使用。比如 TypeScript 负责类型检查和部分语法输出，Babel 负责更灵活的插件转换，构建器负责把这些步骤串进统一流程。判断工具时，重点不是名字，而是“谁负责检查、谁负责降级、谁负责生成最终产物”。

如果职责不清，就会出现同一份源码被重复处理的问题。常见情况包括：

| 重复处理 | 风险 |
| --- | --- |
| `tsc` 和 Babel 都在做语法输出 | 构建慢，产物来源不清楚 |
| Babel 和 SWC 都做 JSX/TS 转换 | sourcemap 变差，调试困难 |
| 多个工具各自读取不同兼容目标 | 产物行为不一致 |

工程里越是多工具组合，越要把“检查”和“输出”拆开看。类型检查可以单独跑，语法输出也可以交给更快的构建链，不必让一个工具包办所有职责。

## 语法与特性

语法转换和特性补齐不是一回事。

```text
语法转换：箭头函数、解构、类、可选链
特性补齐：Promise、Map、Set、Array.prototype.includes
```

```js
const title = user?.profile?.name ?? "匿名";
```

上面的代码如果目标环境不支持可选链，转译器可以把语法改写成更老的判断表达式。但如果目标环境没有 `Promise` 或 `Map`，转译器只改语法并不能凭空提供 API。

这也是为什么“只升 Babel 配置”不一定能解决兼容问题。语法降级和运行时补齐要一起考虑，且要和目标浏览器范围绑定，否则很容易出现包体积暴涨但兼容收益并不明显的情况。

转译和 polyfill 不是一回事。

| 场景 | 处理方式 |
| --- | --- |
| 只是语法不兼容 | 只做转译 |
| API 不存在 | 需要 polyfill |
| 方法存在但行为不同 | 可能需要兼容处理 |
| 现代浏览器 | 尽量少补齐 |

polyfill 解决的是“缺什么补什么”，不是把所有旧 API 都硬塞进去。越精准的补齐，包体积和副作用越小。

常见的 polyfill 方案会尽量按需注入，而不是一次性把整套 ES 标准都塞进去。这样既能覆盖缺失能力，又能避免现代浏览器白白背上额外成本。

除了“有没有”之外，还要考虑“行为是否一致”。有些 API 即使存在，具体实现也可能和现代环境不完全一致，尤其是旧 WebView、定制内核或历史浏览器。遇到这类问题时，单纯语法降级往往帮不上忙，需要结合真实设备验证。

## 选择边界

| 问题 | 决策 |
| --- | --- |
| 只是旧语法问题 | 转译即可 |
| 旧环境缺 API | 需要 polyfill |
| 兼容范围窄 | 保留更多现代特性 |
| 兼容范围广 | 降级更充分 |

编译转译的目标不是把所有代码都写成“最旧的形式”，而是在兼容、体积、速度和可维护性之间找平衡。

现代项目常见的做法，是先用 Browserslist 明确目标，再由 Babel、SWC 或构建工具读取这份目标配置。这样转译策略、polyfill 策略和 CSS 前缀策略就能保持一致。

如果目标环境经常变化，最好把兼容范围写成可维护配置，而不是分散在多个工具里手动改。否则一次修改 browserslist，可能就要同步改 Babel、Autoprefixer、polyfill 和测试策略，特别容易遗漏。

如果目标设备主要是现代浏览器，就没必要为了极少数旧环境把所有特性都打回去；如果业务必须覆盖很旧的设备，也不能只靠某一个转换工具硬扛，通常还要配合运行时检测、降级页面和兼容说明一起设计。

从排查顺序看，兼容问题通常可以按下面的路径判断：

```text
页面报错或白屏
  -> 先看是否是语法解析失败
  -> 再看是否缺失运行时 API
  -> 再看模块格式、资源加载或平台限制
  -> 最后再调转译和 polyfill 配置
```

这样做的好处是能尽快缩小问题范围，不会一上来就改 Babel 配置，结果把真正的问题埋掉。
