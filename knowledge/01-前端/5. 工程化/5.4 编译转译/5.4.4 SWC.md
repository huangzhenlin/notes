## 工具定位

SWC 是用 Rust 编写的 JavaScript/TypeScript 编译器，常用于转译、压缩、React/Next 编译和构建加速。它的优势是速度快，适合替代部分 Babel 和 Terser 场景。

```text
TypeScript / JSX
  -> SWC parse
  -> transform
  -> emit JavaScript
```

SWC 负责语法转换，不等于完整类型检查。TypeScript 类型质量仍需要 `tsc` 或 `vue-tsc`。

SWC 的定位更偏“高速编译基础设施”。它常被框架或构建工具包在内部使用，开发者不一定直接感知它，但会感受到启动、刷新和生产构建速度的变化。

从工程视角看，SWC 的核心价值不是“多一个转译器”，而是把原本比较重的编译环节做轻。对于大型项目、monorepo、组件库联调和频繁热更新场景，这种速度收益会非常明显。

## 转译能力

SWC 可以把现代 JavaScript、TypeScript、JSX 转换成目标环境可运行的代码。

```json
{
  "jsc": {
    "parser": {
      "syntax": "typescript",
      "tsx": true
    },
    "target": "es2020",
    "transform": {
      "react": {
        "runtime": "automatic"
      }
    }
  }
}
```

这类配置决定源码语法如何被解析、目标语法输出到哪个版本。

配置中的 `parser` 决定 SWC 能不能读懂源码，`target` 决定输出语法版本，`transform.react` 决定 React JSX 的转换方式。三个配置分别解决“怎么读”“怎么写”“框架语法怎么转”。

这也说明 SWC 不是装上就一定快。目标版本设得过低、转换链过长、同时叠加其他转译器，仍然会把收益吃掉。提速来自职责清晰和链路收敛，而不是单纯把 Babel 名字换成 SWC。

## 压缩能力

SWC 也可以用于压缩 JavaScript，常用于构建阶段替代 Terser 以提升速度。

```json
{
  "minify": true,
  "jsc": {
    "minify": {
      "compress": true,
      "mangle": true
    }
  }
}
```

压缩策略要结合产物体积和构建速度评估。更快不一定总是更适合，如果某些压缩选项影响兼容或调试，就需要调整。

压缩不是越狠越好。变量混淆、删除调试语句、合并表达式都有可能影响调试体验和边缘兼容。生产环境要用真实产物对比体积、构建耗时和线上错误情况。

如果项目从 Terser 切到 SWC 压缩，最好至少对比三件事：构建耗时、gzip/br 体积、错误监控的可读性。速度提升很容易看见，但压缩后调试变差、堆栈变乱、边缘 bug 变多，也是真实成本。

## Next 集成

Next.js 默认深度使用 SWC，用于编译、压缩、Fast Refresh 和部分优化。开发者通常不需要手动配置太多。

```text
Next 源码
  -> SWC 编译
  -> 路由与打包
  -> 产物输出
```

如果项目从 Babel 插件迁移到 SWC，要确认是否存在 SWC 不支持的 Babel 插件能力。不是所有 Babel 插件都能无缝替换。

Next 这类框架把 SWC 深度集成进默认链路，能减少用户手写配置。但一旦项目依赖特殊 Babel 插件，例如宏转换、私有语法转换或内部埋点插件，就要确认框架是否仍允许回退或扩展。

这类迁移最怕“表面替换成功，细节能力悄悄丢失”。所以从 Babel 迁到 SWC 时，不只是看构建能不能过，还要核对埋点、按需导入、装饰器、宏、测试编译和 source map 是否都保持可用。

## Babel 对比

Babel 插件生态更成熟，SWC 速度更快。选择时要看项目需要的是生态兼容还是构建性能。

| 维度 | SWC | Babel |
|---|---|---|
| 速度 | 快 | 较慢 |
| 插件生态 | 较少 | 丰富 |
| 类型检查 | 不负责 | 不负责 |
| Next 集成 | 默认 | 可选 |

很多项目不是“SWC 或 Babel 二选一”，而是在主要编译链用 SWC，特殊插件场景保留 Babel。

这种混合方案的关键是边界清楚。常规语法转译交给 SWC，复杂自定义转换交给 Babel，类型检查交给 TypeScript。不要让多个工具重复处理同一份源码。

如果边界不清，就会出现“构建快了，但问题更难查”的情况。因为一旦产物和源码不一致，你很难判断是 SWC 的输出、Babel 的二次转换，还是构建器的后处理造成的结果。

## 类型边界

SWC 会移除 TypeScript 类型并输出 JavaScript，但不会验证类型是否正确。

```typescript
const count: number = '1' as any;
```

这段代码可能被成功转译，但类型质量并不可靠。工程里应该单独配置 `pnpm typecheck`。

如果团队把“构建通过”当成“类型正确”，就会漏掉很多问题。SWC 编译成功只能说明语法可以输出，类型约束是否成立仍然要靠 TypeScript 工具链。

这也是为什么很多项目会把 `build` 和 `typecheck` 分开跑。SWC 负责快，TypeScript 负责准，两者配合起来才是完整的工程反馈链路。

## sourcemap

SWC 支持生成 source map，用于调试和线上错误定位。

```json
{
  "sourceMaps": true
}
```

生产 source map 要和监控平台、版本追踪、权限控制一起考虑。不要为了排查方便直接暴露敏感源码。

使用 SWC 后也要确认 sourcemap 是否能被错误监控平台正确解析。构建速度提高了，但如果线上报错无法映射回源码，排障成本会被转移到运行阶段。

特别是在 React、Next 这类依赖快速迭代的项目里，source map 质量几乎和构建速度同样重要。编译再快，如果线上错误栈看不懂，收益很容易在排障阶段被抵消。

## 选择边界

SWC 适合构建提速、现代框架默认编译、TS/JSX 转译和压缩。复杂宏、老 Babel 插件、特殊代码转换仍可能需要 Babel。

| 场景 | 判断 |
|---|---|
| Next 项目 | 默认使用 SWC |
| 大型构建慢 | 可评估 SWC |
| 依赖 Babel 插件 | 谨慎迁移 |
| 类型检查 | 仍用 tsc/vue-tsc |

SWC 和 [[5.4.1 概念|编译转译概念]] 的关系很直接：它是具体工具，而编译转译概念解释为什么需要这些转换。

选择 SWC 时可以先做一轮对比：构建耗时、产物体积、sourcemap 可用性、框架插件兼容、类型检查流程是否完整。只有这些都稳定，速度收益才是真收益。

适合优先尝试 SWC 的场景，通常包括：

| 场景 | 原因 |
| --- | --- |
| 标准 React/TypeScript 应用 | 转换路径常规，迁移阻力小 |
| 构建明显偏慢的大型项目 | 提速收益直观 |
| 框架已默认集成 SWC | 生态成本低 |
| 自定义 Babel 插件较少 | 兼容风险可控 |

反过来，如果项目严重依赖 Babel 历史插件、私有 AST 转换或一些实验特性，SWC 更适合作为渐进替换对象，而不是一口气完全迁移。
