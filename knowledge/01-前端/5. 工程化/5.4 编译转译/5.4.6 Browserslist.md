## 工具定位

Browserslist 用来声明项目支持哪些浏览器和版本。Babel、Autoprefixer、PostCSS、eslint-plugin-compat、打包工具和 polyfill 工具都可能读取它。

```text
Browserslist
  -> Babel 转译目标
  -> Autoprefixer 前缀
  -> Polyfill 策略
  -> 构建产物大小
```

它不是浏览器检测工具，而是工程目标环境配置。

这点非常重要：Browserslist 不会在用户访问页面时判断浏览器，它只是在构建阶段告诉工具“我们准备支持哪些环境”。最终产物会根据这个目标发生变化。

因此 Browserslist 看起来只是几行配置，实际上决定的是整条前端交付链的兼容策略。它会影响 JavaScript 是否降级、CSS 是否加前缀、polyfill 是否注入，最终还会影响包体积、调试体验和测试范围。

## 查询语法

Browserslist 使用查询语法描述目标环境。

```text
> 0.5%
last 2 versions
not dead
not IE 11
```

这些规则会合并成最终支持范围。`dead` 通常表示官方不再维护或使用量极低的浏览器。

查询条件越宽，支持范围越大，构建工具需要做的兼容处理越多。范围越窄，产物越现代，但低版本用户可能无法正常使用。

很多项目一开始直接复制社区通用配置，后面就再也不管了。这样做的问题在于，项目的真实用户环境会变，框架默认策略会变，浏览器市场份额也会变，旧配置未必一直合理。

## 配置位置

可以在 `package.json` 中配置：

```json
{
  "browserslist": [
    "> 0.5%",
    "last 2 versions",
    "not dead"
  ]
}
```

也可以使用 `.browserslistrc`：

```text
> 0.5%
last 2 versions
not dead
```

团队应统一配置位置，避免多个配置源造成理解偏差。

如果仓库里同时存在 `package.json`、`.browserslistrc` 和工具局部配置，就要确认到底哪个生效。配置分散会让 Babel、PostCSS 和 polyfill 产生不一致结果。

团队协作时，最好让兼容目标有一个单一来源。否则 A 以为项目不支持旧浏览器，B 又在某个子工具里偷偷加了兼容配置，最后构建结果会变得不可预测。

## 环境分组

Browserslist 支持按环境区分，例如 production 和 development。

```json
{
  "browserslist": {
    "production": [
      "> 0.5%",
      "not dead"
    ],
    "development": [
      "last 1 chrome version"
    ]
  }
}
```

开发环境可以更现代，提升构建速度；生产环境根据真实用户范围决定。

开发环境通常只需要覆盖开发者正在使用的现代浏览器，因此可以减少转译和 polyfill。生产环境要面向真实用户，不能只按开发者电脑上的 Chrome 来决定。

环境分组的价值，在于把“开发体验”和“线上兼容”分开管理。开发环境更现代，可以换来更快的编译和更接近源码的调试体验；生产环境更真实，才能反映最终用户会拿到什么产物。

## 真实数据

目标浏览器不应只凭默认配置。最好结合产品真实访问数据、地区、业务客户环境和 WebView 内核版本。

| 项目 | 目标判断 |
|---|---|
| C 端活动页 | 看真实流量分布 |
| B 端系统 | 看客户浏览器要求 |
| 移动 H5 | 看 WebView 版本 |
| 内部工具 | 可更激进 |

支持越旧，转译和 polyfill 越多，产物越大，测试成本也越高。

如果产品有真实访问统计，Browserslist 应该跟统计数据对齐。比如移动 H5 要看 App WebView 和系统浏览器，B 端系统要看客户内网浏览器限制，海外业务要看目标地区浏览器分布。

这也是为什么 Browserslist 不能只由前端单方面拍脑袋决定。它同时受产品定位、用户分布、商务约束、终端形态和测试投入影响，本质上是技术实现和业务现实之间的折中。

## 转译影响

Browserslist 会影响语法转换。例如目标包含旧浏览器时，现代语法会被转换得更多。

```javascript
const name = user?.profile?.name ?? '匿名';
```

目标环境越现代，保留的新语法越多，产物通常更小、更接近源码。

这也会影响调试体验。保留现代语法时，构建产物更接近源码；大量降级后，调试栈和 sourcemap 更依赖工具链质量。

所以当你发现“构建后代码突然变得很难读”或者“体积明显变大”时，不一定是业务代码写多了，也可能是 Browserslist 扩大了支持范围，导致更多语法被转换。

## CSS 前缀

Autoprefixer 会根据 Browserslist 添加必要 CSS 前缀。

```css
.box {
  user-select: none;
}
```

可能生成：

```css
.box {
  -webkit-user-select: none;
  user-select: none;
}
```

不需要手写大量历史前缀，让工具根据目标环境生成更可靠。

手写前缀容易过时，也容易漏掉必要情况。让 Autoprefixer 根据 Browserslist 生成，可以让 CSS 兼容策略和项目目标环境保持一致。

这类统一的价值很大。否则就会出现 JavaScript 已经按现代浏览器输出，但 CSS 仍在为更老环境添加前缀，或者反过来 CSS 很现代而 JS 过度降级，整条链路的兼容成本难以解释。

## Polyfill 关系

Browserslist 也会影响 polyfill 注入。目标越旧，需要补的运行时能力越多。

```text
目标浏览器
  -> 缺失 API
  -> core-js polyfill
  -> 产物体积变化
```

Browserslist 和 [[6.4.6 Polyfill 策略|Polyfill 策略]] 必须一起看。盲目扩大支持范围，会直接增加用户下载成本。

如果目标里包含很多旧浏览器，polyfill 可能成为包体积的重要来源。优化时不能只看业务代码大小，也要看兼容目标带来的运行时补齐成本。

这也是性能优化里经常被忽略的一点：用户下载的不只是业务代码，还有为了兼容目标环境付出的额外成本。支持范围每扩一层，通常都意味着更多转译、更多补丁和更多测试。

## 维护策略

Browserslist 应定期复查。浏览器市场份额、业务用户环境和框架默认目标都会变化。

```bash
npx browserslist
```

这个命令可以查看当前配置解析出的目标浏览器。修改 Browserslist 后，要重新验证构建产物、兼容性和包体积。

建议在升级框架、调整市场策略、放弃旧浏览器支持或发现包体积异常时复查 Browserslist。它看起来只是一段配置，实际会影响转译、CSS、polyfill 和最终用户下载成本。

一个比较实用的复查思路是：

```text
升级依赖或框架
  -> 检查 Browserslist 是否仍符合用户环境
  -> 对比构建体积和语法输出变化
  -> 验证 CSS 前缀和 polyfill 是否同步变化
  -> 复查测试设备矩阵是否需要调整
```

把 Browserslist 当成“前端兼容基线”会更容易维护。只要它发生变化，就要意识到受影响的不是单个工具，而是整条前端工程链路。
