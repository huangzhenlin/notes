## 变量边界

环境变量用于把代码和环境差异分开，例如接口地址、运行模式、版本号、功能开关和监控配置。前端环境变量有一个特殊风险：构建进浏览器的变量，本质上都是公开信息。

```text
构建时变量
  -> 被打进 JS 产物
  -> 用户可查看
```

因此，前端环境变量不能存放数据库密码、服务端密钥、私有 token、云服务 Secret 等敏感信息。

只要变量被打进前端产物，就可以通过 DevTools、源码映射、网络请求或构建产物看到。前端变量只能放“可以公开但需要按环境切换”的信息。

环境变量最容易出问题的地方，是大家以为“名字叫 env 就都安全”。实际上，前端变量只是构建输入的一种，不是密钥存储系统。

前端变量治理的重点从来不是“怎么放进去”，而是“哪些内容绝不能进去、进去之后如何校验、不同环境如何保持一致”。

## 暴露前缀

多数构建工具要求只有特定前缀的变量才会暴露给浏览器。例如 Vite 使用 `VITE_`，Next 使用 `NEXT_PUBLIC_`。

```bash
VITE_API_BASE=https://api.example.com
VITE_APP_RELEASE=1.8.0
```

```typescript
const apiBase = import.meta.env.VITE_API_BASE;
```

```bash
NEXT_PUBLIC_API_BASE=https://api.example.com
```

前缀不是安全机制，而是防误暴露机制。加了公开前缀，就要假设用户能看到。

这类前缀的意义是减少意外暴露，比如没有前缀的变量默认不进浏览器。但一旦加了前缀，就必须按公开信息处理。

前缀机制也适合帮助团队统一认知。哪些变量是前端可见、哪些只能服务端使用，一眼就能从命名上区分出来。

但前缀只能减少误操作，不能替代审查。真正高风险的仍然是变量内容本身，而不是变量名长什么样。

## 构建时变量

前端变量通常在构建时被替换，而不是运行时动态读取。

```typescript
if (import.meta.env.MODE === 'production') {
  enableMonitor();
}
```

这意味着同一份构建产物不能随意在多个环境中复用，除非项目做了运行时配置注入。否则 staging 构建可能带着 staging API 发布到生产。

构建时变量适合决定编译结果，例如是否开启调试代码、监控 release、构建模式。运行时经常变化的配置，不适合强绑在构建产物里。

如果项目经常需要换接口地址、切换租户或更新运行时开关，运行时配置会比重新构建更合适。反过来，如果配置会影响编译结果，最好还是留在构建时。

是否选构建时变量还是运行时配置，本质上是在权衡“构建是否与环境绑定”。前者更简单，后者更灵活，但也更依赖配置分发和缓存治理。

## 运行时配置

如果需要同一份产物部署到多个环境，可以在 HTML 或外部配置文件中注入运行时配置。

```html
<script>
  window.__APP_CONFIG__ = {
    apiBase: 'https://api.example.com',
    release: '1.8.0'
  };
</script>
```

运行时配置适合容器化部署、静态资源统一发布、多租户和环境动态切换。它也要注意缓存，配置文件不能被长期强缓存。

如果使用外部配置文件，建议短缓存或协商缓存，并带版本字段。这样可以在不重新构建的情况下切换接口地址、功能开关或灰度配置。

运行时配置一旦被长期缓存，就会出现“代码是新版本，配置还是旧版本”的错位问题。所以它虽然灵活，也需要像入口 HTML 一样认真管理缓存。

## 类型声明

TypeScript 项目应该为环境变量补类型，避免拼错变量名。

```typescript
interface ImportMetaEnv {
  readonly VITE_API_BASE: string;
  readonly VITE_APP_RELEASE: string;
}

interface ImportMeta {
  readonly env: ImportMetaEnv;
}
```

类型能帮助开发阶段发现错误，但不能保证运行时变量真的存在。构建前仍应做环境校验。

类型声明解决的是“代码里写没写错变量名”，环境校验解决的是“构建时有没有提供变量”。两者缺一不可。

环境变量校验最好在启动或构建入口尽早执行，避免等页面跑到一半才发现配置缺失。

校验失败应尽量早失败，而不是默默给默认值继续运行。对关键变量来说，错误地继续运行往往比直接失败更危险。

## 密钥隔离

真正的密钥必须留在服务端。前端如果需要访问第三方服务，应通过服务端代理、BFF 或短期签名完成。

```text
浏览器
  -> 自家服务端
  -> 第三方服务
```

不要把云存储 Secret、支付密钥、短信密钥放进前端。即使变量名没有公开前缀，只要进入前端产物，就不再是秘密。

如果浏览器确实需要访问第三方资源，应由服务端生成短期凭证、签名 URL 或代理请求。不要把长期密钥交给浏览器。

这类代理设计不仅保护密钥，也有助于后续做权限控制、频率限制和审计。很多“为了前端方便直连第三方”的做法，最后都会把安全和运维成本转移回来。

密钥隔离也能防止误配置。哪怕只是预发环境，也不应该因为“临时方便”把服务端 Secret 暴露给前端。

## 环境矩阵

环境变量要按环境管理：本地、测试、预发、生产各自有明确配置。

| 环境 | 常见变量 |
|---|---|
| local | 本地 API、mock 开关 |
| test | 测试 API、调试日志 |
| staging | 预发 API、监控测试环境 |
| production | 生产 API、正式监控 |

变量治理和 [[5.1.4 环境配置|环境配置]] 是同一个体系：环境变量是输入，环境配置是如何组织、校验和使用这些输入。

环境矩阵最好文档化并纳入 CI 校验。每个环境需要哪些变量、哪些变量可公开、哪些变量必须来自密钥系统，都应该清楚。

环境矩阵清楚后，部署和排障都会轻松很多。看到某个 release 时，团队能立刻知道它拿的是哪套变量，而不是靠猜。

一个成熟的环境变量体系，通常能回答这些问题：

| 问题 | 理想状态 |
| --- | --- |
| 哪些变量会暴露给前端 | 明确 |
| 哪些变量只允许服务端使用 | 明确 |
| 每个环境缺变量时会不会立即失败 | 会 |
| 同一份产物是否能跨环境复用 | 有清楚规则 |
