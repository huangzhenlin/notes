## 资源类型

前端静态资源通常包括 HTML、JavaScript、CSS、图片、字体、source map、manifest 和运行时配置。不同资源的缓存策略不同，不能一刀切。

| 资源 | 特点 | 缓存策略 |
|---|---|---|
| HTML | 入口文件，引用资源清单 | 短缓存或协商缓存 |
| JS/CSS | 带 hash 的构建产物 | 长缓存 |
| 图片字体 | 可 hash 或版本化 | 长缓存 |
| source map | 排查用，需权限控制 | 不公开或受控 |
| runtime config | 环境配置 | 短缓存 |

静态资源部署的核心问题是：用户拿到的 HTML 和资源文件必须匹配。

前端静态资源不像服务端接口那样每次都执行最新代码。浏览器、CDN、代理和 Service Worker 都可能缓存资源，所以部署设计要优先保证“入口和资源版本一致”。

静态资源部署最核心的心智，不是“把文件传上去”，而是“让不同缓存层最终都稳定收敛到同一套资源关系”。只要入口和资源有机会错位，线上就会出现白屏、chunk 404 或样式丢失。

## 文件指纹

JS/CSS 通常使用内容 hash 作为文件名。内容变化，文件名变化；内容不变，文件名稳定。

```text
main.abc123.js
style.f91a20.css
```

这让浏览器可以长期缓存资源，而不用担心拿到旧代码。HTML 引用新的 hash 文件后，用户才会加载新版本。

文件指纹的前提是内容不可变。发布后不要覆盖同名 hash 文件，否则缓存会失去可信度，也会让问题排查变得非常困难。

一旦选择了 hash 文件名，就应该把它当成内容身份。相同文件名永远对应相同内容，这样浏览器和 CDN 的长期缓存才真正可靠。

## 缓存头

HTML 和带 hash 的静态资源应该使用不同缓存头。

```http
index.html
Cache-Control: no-cache

assets/main.abc123.js
Cache-Control: public, max-age=31536000, immutable
```

`no-cache` 不等于不缓存，而是每次使用前要和服务器确认是否更新。带 hash 的资源可以使用 `immutable`，因为文件名已经代表内容版本。

HTML 是版本切换入口，不能像 JS/CSS 一样长期强缓存。否则用户可能长期拿着旧 HTML，永远不会引用新版本资源。

如果项目有运行时配置文件，它和 HTML 一样也应按入口对待。因为配置变化会影响页面实际拿到哪个接口地址、灰度开关或版本标识。

## 发布顺序

静态资源发布要注意顺序。通常先上传新资源，再切换 HTML 或资源清单，避免 HTML 先指向还不存在的 chunk。

```text
1. 上传新 JS/CSS/图片
2. 校验资源可访问
3. 上传或切换 HTML
4. 清理 CDN HTML 缓存
5. 保留旧资源
```

如果顺序反了，用户可能拿到新 HTML，但请求不到对应资源。

这个问题常见于异步发布：资源上传还没完成，入口已经切换；或者 CDN 刷新了 HTML，但边缘节点还没有拿到新 chunk。发布顺序必须把这种窗口期考虑进去。

部署系统如果支持原子切换，会比逐文件覆盖安全得多。先把整套资源准备好，再一次性切换入口，是减少窗口期最稳的方式之一。

## 旧资源保留

发布后不要立即删除旧资源。用户浏览器、CDN、代理和 Service Worker 可能仍持有旧 HTML。

```text
保留最近 N 个版本资源
或保留最近 7-30 天资源
```

旧资源保留能降低 chunk 404，也能让回滚更快。清理策略要基于流量、存储成本和回滚窗口设计。

保留旧资源不是浪费，而是给缓存世界留缓冲。只要旧 HTML 可能存在，就要允许它引用的旧 chunk 继续可访问。

保留策略要和真实流量行为匹配。高频站点可能几天就足够，低频后台系统或长会话产品则可能需要更长保留窗口。

## CDN 刷新

CDN 缓存能提升访问速度，但也会带来更新一致性问题。HTML 通常需要刷新或短缓存，hash 资源不需要频繁刷新。

| 操作 | 适合对象 |
|---|---|
| 刷新文件 | HTML、配置 |
| 不刷新 | hash 资源 |
| 预热 | 大型 JS、字体、图片 |

CDN 操作要可追踪。发布时清了哪些路径、何时生效、是否失败，都应该有记录。

CDN 刷新适合入口和配置，不适合频繁刷新 hash 资源。hash 资源应通过新 URL 自然生效，入口文件负责切换版本。

如果每次发布都大范围刷新所有静态资源，说明缓存策略可能没有真正利用起 hash 带来的优势，也会增加 CDN 成本和传播延迟。

## 跨域与 MIME

静态资源部署还要确保 MIME 类型、CORS、字体跨域和压缩配置正确。

```http
Content-Type: text/javascript
Content-Encoding: br
Access-Control-Allow-Origin: *
```

字体文件如果跨域加载，需要正确 CORS；JS/CSS MIME 错误会导致浏览器拒绝执行或加载。

部署后如果出现“本地能跑、线上白屏”，MIME、CORS、压缩和 public path 是最值得先查的几类问题。

尤其是子路径部署、跨域静态资源托管和字体资源加载，往往最容易在这些细节上出问题。部署环境一旦和本地根路径假设不同，问题会更明显。

## 部署验证

部署完成后要验证入口、资源、缓存和版本。

```text
验证项：
1. HTML 可访问
2. JS/CSS 资源 200
3. 缓存头符合预期
4. release 信息正确
5. 旧资源仍可访问
```

静态资源部署和 [[5.7.6 回滚策略|回滚策略]]、[[6.4.4 Chunk 拆分|Chunk 拆分]] 强相关。资源组织不好，回滚和缓存都会变脆。

部署验证最好自动化。人工点开首页不够，还要检查核心 chunk、CSS、字体、manifest、source map 权限和缓存头是否符合预期。

静态资源部署是否成熟，可以看几个信号：

| 信号 | 说明 |
| --- | --- |
| 小流量用户很少遇到 chunk 404 | 入口和资源匹配较稳 |
| 发布后不同地区很快收敛到同一版本 | CDN 切换较稳定 |
| 回滚时能快速切回旧入口 | 旧资源保留和版本管理较好 |
| 问题出现后能追到具体资源和缓存层 | 追踪链路完整 |
