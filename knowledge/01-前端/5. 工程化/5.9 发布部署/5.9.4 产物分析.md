## 长期趋势

单次分析只能看到当前状态，长期趋势能看到包体是否持续膨胀。

```text
记录：
每次构建总大小
最大 chunk
依赖变化
gzip / brotli 后大小
```

如果每次发布只增加一点点体积，单次不明显，几个月后就可能变成性能问题。趋势记录能让优化更早发生。

长期趋势尤其适合放进 CI 报告或发布报告。只要某次 PR 让主 chunk、vendor chunk 或总下载体积明显增长，就应该提醒开发者解释原因。

趋势的价值在于把“慢慢变大”的问题提早暴露出来。很多性能退化单次看并不明显，但长期累积后会变成真实用户的加载和执行成本。
## 分析对象

产物分析关注的是构建结果里到底包含了什么，以及这些内容是如何被浏览器加载和执行的。它不是只看文件大小，还要看入口、chunk、hash、source map 和静态资源引用。

```text
构建产物
  -> HTML
  -> JS chunk
  -> CSS
  -> 图片字体
  -> source map
```

产物分析通常在发布前做，也可以在 CI 中自动执行，帮助发现构建退化。

分析对象不仅是“文件大不大”，还包括“为什么大”“谁引入的”“是否影响首屏”“是否能被缓存”。没有这些判断，产物分析就只剩截图报表。

因此产物分析最好和依赖分析、路由分析、缓存策略一起看。单看一个包体数字，很难真正指导优化动作。

## 入口清单

先看入口是否合理。多页应用、单页应用和库的产物结构差异很大。

| 产物 | 关注点 |
|---|---|
| HTML | 是否引用正确资源 |
| JS | 初始 chunk 是否过大 |
| CSS | 是否拆分合理 |
| 静态资源 | 是否被正确 hash |
| source map | 是否能用于排查 |

如果 HTML 引用了错误的资源版本，就会出现旧页面加载新 chunk 失败的情况，这和 [[5.9.6 版本追踪|版本追踪]]、[[6.4.4 Chunk 拆分|Chunk 拆分]] 都有关。

入口清单要和部署产物一一对应。发布前能确认入口引用的每个资源都存在，能提前拦住很多线上 404。

对多入口应用来说，这一步尤其重要。一个管理后台入口正常，不代表营销页、子应用或嵌入页入口也都正常。

## chunk 结构

看 chunk 结构时，要关注业务代码、公共代码、第三方依赖和运行时代码各占多少。

```text
main
vendor
route-home
route-admin
runtime
```

理想的结构不是“越少越好”，而是高频入口小、低频功能延迟、公共依赖稳定、hash 变化可控。

如果 vendor chunk 过大，要看是不是把低频依赖也放进去了；如果 route chunk 过大，要看是不是路由里同步导入了编辑器、图表或地图 SDK。

chunk 分析不只是为了拆包，更是为了理解加载路径。某个依赖大并不一定是问题，问题在于它是不是出现在了不该出现的加载阶段。

## hash 稳定

hash 稳定性直接影响缓存命中。公共依赖改动一次会让过大范围的 hash 变化，进而降低缓存价值。

| 现象 | 说明 |
|---|---|
| 小改动导致很多 hash 变化 | chunk 组织不稳定 |
| HTML 长缓存 | 容易引用旧资源 |
| 资源 404 | 旧 HTML 失配 |

分析时要看文件名变化是否合理，而不是只看体积是否变小。体积小但 hash 到处变，也可能导致缓存收益很差。

稳定 hash 能让用户复用缓存。小改动导致大量文件 hash 变化，说明 chunk 边界可能不稳定，或者运行时代码影响了过多产物。

这类问题会直接影响用户重复访问成本。文件没有明显变大，但每次发版都让大量缓存失效，用户仍然会付出额外下载代价。

## source map

source map 是调试和错误定位的重要产物，但不应随意公开到无权限环境。它能帮助把线上堆栈映射回源码。

```text
错误堆栈
  -> source map
  -> 源码位置
```

source map 的发布策略通常要和错误监控、权限和版本追踪一起设计。公开过多会增加源码泄露风险。

source map 可用性也要验证。上传到了监控平台不代表一定能正确解析，release、文件路径和产物 hash 都要对齐。

source map 分析的重点不是“有没有生成”，而是“线上报错能不能真的映射回来”。只有和 release、部署路径、错误监控一起验证，source map 才算真正可用。

## 性能关系

产物分析不只是发布前检查，它也能反推性能瓶颈。例如首屏太慢，可能是入口 chunk 太大、CSS 太多、字体阻塞或脚本执行太重。

| 问题 | 可能来源 |
|---|---|
| 首屏白屏 | JS 过大、主线程阻塞 |
| 首屏文字慢 | 字体加载 |
| 交互卡顿 | 运行时代码过多 |
| 路由切换慢 | 某个 route chunk 过重 |

产物分析和 [[6.1.2 性能指标采集|性能指标采集]] 配合后，能把“包很大”转成“哪些用户真的慢”。

产物体积只是潜在风险，真实性能还要结合设备、网络、浏览器和用户路径。一个大 chunk 如果不在首屏加载，影响就和首屏大包不同。

这也是为什么产物分析最好和真实性能监控一起看。构建产物告诉你“理论风险在哪”，线上指标告诉你“这些风险是否真的影响了用户”。

## 发布检查

发布前最好检查：

| 检查项 | 目的 |
|---|---|
| 入口 HTML | 引用正确 |
| 资源清单 | 文件完整 |
| chunk 体积 | 没有异常膨胀 |
| source map | 可用但受控 |
| 缓存头 | 与资源策略一致 |

产物分析的最终目标不是生成报表，而是让发布前能提前发现回滚风险。

如果分析发现入口资源缺失、chunk 异常膨胀、source map 不匹配或缓存头错误，应该阻止发布，而不是等线上监控报警。

一个成熟的产物分析，不只会产出图表，还会推动决策：哪些问题只是观察项，哪些问题已经严重到需要阻断发布。
