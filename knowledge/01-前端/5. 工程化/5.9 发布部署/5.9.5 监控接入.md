## 监控目标

前端监控的目标是让线上问题可发现、可定位、可归因。它不是简单收集错误，而是把错误、性能、资源、用户行为、版本和环境信息串起来。

```text
用户访问
  -> 错误 / 性能 / 资源 / 行为
  -> 上报
  -> 聚合
  -> 告警
  -> 定位版本和用户影响
```

没有监控的发布，只能等用户反馈。监控接入越早，发布风险越可控。

监控不是上线后的装饰，而是发布体系的一部分。没有监控，就无法判断灰度是否稳定、回滚是否生效、问题影响了哪些用户。

监控接入最重要的不是埋点数量，而是“出了问题能不能快速看懂”。错误、性能、资源、版本、用户上下文如果不能串起来，监控再多也只是数据堆积。

监控系统本质上是在为发布和排障服务。团队真正需要的不是更多事件，而是更少的猜测。

## 错误采集

前端错误包括运行时异常、Promise 未捕获、资源加载失败和框架错误边界。

```javascript
window.addEventListener('error', (event) => {
  reportError({
    type: 'error',
    message: event.message,
    filename: event.filename,
    lineno: event.lineno,
    colno: event.colno,
  });
});

window.addEventListener('unhandledrejection', (event) => {
  reportError({
    type: 'unhandledrejection',
    reason: String(event.reason),
  });
});
```

资源错误和脚本错误不完全一样，图片、CSS、JS 加载失败要单独捕获。React/Vue 组件树中的错误也应接入框架级错误处理。

资源错误通常不会冒泡到普通 `window.onerror`，需要在捕获阶段处理。chunk 404、CSS 加载失败、字体失败都可能造成页面异常。

错误采集最好区分可恢复错误和不可恢复错误。可恢复错误适合提示和重试，不可恢复错误则要尽快上报并给出兜底页面。

错误采集也要注意去重和聚合。相同错误如果因为字段过杂而被拆成很多条，告警和分析都会失真。

## 性能采集

性能监控应覆盖 LCP、INP、CLS、FCP、TTFB、资源耗时和长任务。

```javascript
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    reportMetric(entry.name, entry.startTime);
  }
}).observe({
  type: 'paint',
  buffered: true,
});
```

性能数据要带页面、版本、设备、网络、浏览器和采样率。否则很难判断问题影响的是全量用户还是某类设备。

性能指标要看分位数，而不是平均值。P75 或 P95 更能反映真实用户中的慢体验，平均值容易被少量极端值或大量快用户掩盖。

性能采集最好和页面类型绑定。首页、表单页、列表页、编辑页的指标关注点不一样，监控口径也不应该完全相同。

性能监控最有价值的地方，在于它能帮助区分“代码确实退化了”还是“某类设备、某类网络用户特别慢”。只有加上上下文，指标才有解释力。

## 版本关联

监控必须关联 release。错误没有版本号，就很难判断是哪个发布引入的问题。

```javascript
initMonitor({
  release: window.__APP_RELEASE__,
  commit: window.__GIT_COMMIT__,
  environment: import.meta.env.MODE,
});
```

source map 也要按 release 上传。错误堆栈能映射回源码，排查效率会高很多。source map 发布要控制权限，避免源码泄露。

如果 release 和 source map 不匹配，监控看起来接入了，实际定位仍然会失败。每次发布都应该确认 source map 与线上资源对应。

版本关联也能帮助识别回归。只要某个 release 的错误率明显高于前一版，团队就能更快判断是新增问题还是长期问题。

发布后的监控面板最好默认就能按 release 切分，否则一旦连续多次发布叠在一起，问题来源会迅速变模糊。

## 用户上下文

监控上下文可以帮助定位影响范围，但要注意隐私和脱敏。

| 上下文 | 用途 |
|---|---|
| userId | 判断影响用户 |
| route | 定位页面 |
| release | 定位版本 |
| device | 判断设备问题 |
| network | 判断弱网问题 |
| featureFlag | 判断灰度问题 |

不要上报密码、token、身份证、手机号明文、详细地址等敏感信息。监控数据也属于生产数据的一部分。

用户上下文要遵循最小必要原则。能用匿名 ID 解决的问题，不要上报明文个人信息；必须上报时也要脱敏和限制权限。

上下文字段最好标准化，否则不同团队上报的字段名不一致，后续聚合和分析会非常痛苦。

标准化还可以减少后续接平台、换平台和跨系统对齐时的成本。字段一开始就乱，后面只会越来越难整理。

## 采样策略

错误通常可以高比例采集，性能和行为数据通常要采样。采样策略要保证代表性。

```javascript
function shouldSample(rate) {
  return Math.random() < rate;
}
```

采样率要随页面价值和流量调整。低流量核心链路可以提高采样，高流量普通页面可以降低采样。

采样要保证代表性。不能只采样成功用户，也不能漏掉低端设备、弱网和特定地区，否则监控会低估真实问题。

采样策略应和业务目标一致。关键链路可以更高采样，普通页面可以低采样，但总体上要能保留趋势和异常。

采样不是为了省事，而是在成本、精度和可操作性之间找平衡。越关键的页面和链路，越应该优先保证样本质量。

## 告警规则

告警应关注趋势和阈值，而不是每个错误都报警。否则团队会很快对告警麻木。

| 告警 | 触发依据 |
|---|---|
| 错误率升高 | release 后异常增长 |
| 白屏率升高 | 首屏超时或无内容 |
| LCP 退化 | P75 变差 |
| chunk 404 | 静态资源失配 |
| 接口失败率升高 | API 或网络异常 |

监控接入和 [[5.9.3 部署策略|部署策略]] 是配套的：发布策略负责控制风险，监控负责告诉你风险是否真的发生。

告警规则要可行动。收到告警后应该知道该暂停灰度、回滚、联系后端还是继续观察，而不是只知道“有错误”。

监控接入最终要落到行动。只有当告警能推动发布停止、回滚或排查时，监控才真正有价值。

监控体系是否健康，可以看这些问题能否快速回答：

| 问题 | 理想状态 |
| --- | --- |
| 新版本是不是引入了新错误 | 能快速看出 |
| 哪类用户或设备受影响最大 | 能快速筛到 |
| 问题是否和某个资源、路由或灰度批次有关 | 能 |
| 回滚后指标是否恢复 | 能及时确认 |
