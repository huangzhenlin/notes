## 用户反馈定位

用户反馈进入排查流程时，版本信息能显著缩短定位时间。

```text
反馈：页面打不开
  -> 查看用户访问版本
  -> 对应 release
  -> 查看该版本错误和资源加载
  -> 判断回滚或修复
```

前端页面可以在隐藏调试面板、监控上下文或构建信息接口里暴露版本号，方便客服、测试和研发统一沟通。

用户反馈如果没有版本信息，就只能靠时间和猜测反推发布范围。版本信息越容易获取，跨角色沟通越顺。

这一点对客服、测试、运维和研发协作尤其重要。越接近一线的人越不应该被要求理解复杂构建细节，但他们应该能轻松拿到足够的版本标识。
## 追踪对象

版本追踪的目标是回答三个问题：线上用户正在运行哪个版本，这个版本来自哪次代码提交，这个版本出现问题时如何定位和回滚。前端发布如果只记录“部署成功”，遇到线上异常时会很难判断影响范围。

| 对象 | 示例 | 作用 |
|---|---|---|
| 源码版本 | Git commit SHA | 追溯具体代码 |
| 构建版本 | CI build id | 追溯构建环境和产物 |
| 应用版本 | `1.8.0` | 面向产品和用户沟通 |
| 资源版本 | chunk hash / manifest | 定位静态资源 |
| 发布批次 | rollout id | 灰度、回滚和分流 |

这些版本信息应该在构建时写入产物，而不是靠人工记忆。线上页面、监控日志和错误上报都应该能读到同一组版本标识。

版本追踪的关键是“一致”。页面展示、监控上报、错误日志、灰度系统和产物仓库看到的 release 应该是同一个。

一旦这些系统里的版本号不一致，排查就会迅速陷入混乱。有人看的是应用版本，有人看的是构建号，有人看的是 commit，结果每个人都像在说不同的系统。

## 构建注入

前端项目可以在构建阶段注入版本信息，例如 Git SHA、构建时间、分支、环境和应用版本。

```typescript
export const releaseInfo = {
  version: import.meta.env.VITE_APP_VERSION,
  commit: import.meta.env.VITE_GIT_COMMIT,
  buildTime: import.meta.env.VITE_BUILD_TIME,
  environment: import.meta.env.MODE,
};
```

```bash
VITE_GIT_COMMIT=$(git rev-parse --short HEAD) \
VITE_BUILD_TIME=$(date -u +%Y-%m-%dT%H:%M:%SZ) \
pnpm build
```

版本信息可以暴露在调试面板、错误上报上下文和监控埋点中。不要把密钥、内部 token、私有地址等敏感信息一起注入前端产物。

构建注入要尽量自动化。commit、build id、构建时间和分支不应该靠人工填写，否则发布忙乱时很容易漏掉或写错。

自动注入的另一个好处，是能保证同一批构建产物里的所有位置都拿到同样的 release 信息，而不是某个页面显示一套、监控上报另一套。

## 错误关联

错误监控要能把异常关联到 release。只有这样，才能判断某个错误是新版本引入的，还是老版本长期存在的。

```typescript
import * as Sentry from '@sentry/browser';

Sentry.init({
  dsn: 'https://examplePublicKey@o0.ingest.sentry.io/0',
  release: `${releaseInfo.version}+${releaseInfo.commit}`,
  environment: releaseInfo.environment,
});
```

如果使用 source map，还要确保上传的 source map 与线上资源版本一一对应。否则错误堆栈会映射到错误源码，定位反而更混乱。

错误关联最好能看到“首次出现版本”和“最近出现版本”。这样可以判断问题是新引入，还是历史长期存在。

这类时间维度非常有价值。很多问题不是“今天第一次发生”，而是“今天开始放大”，两者在发布决策上的意义并不一样。

## 资源映射

现代前端构建会生成带 hash 的 JS 和 CSS 文件。版本追踪需要保存 manifest，把入口、chunk、hash 和 release 关联起来。

```json
{
  "release": "1.8.0+abc1234",
  "assets": {
    "main": "/assets/main.9f2a1c.js",
    "vendor": "/assets/vendor.24a87b.js"
  }
}
```

当用户报告某个页面异常时，可以通过页面上的 release 和资源 hash 判断他加载的是新资源、旧缓存还是混合版本。混合版本问题常见于 CDN 缓存、HTML 缓存和 chunk 文件清理策略不一致。

资源映射也能帮助排查 chunk 404。如果用户请求的 chunk 不在当前 manifest 中，就要判断他是否持有旧 HTML 或 Service Worker 缓存。

资源映射最好能在出问题时快速反查。给出 release、页面 URL、chunk 名称时，团队应该能较快知道它属于哪次构建、哪套入口和哪组静态资源。

## 灰度标识

灰度发布时，版本追踪还要记录用户属于哪个批次、命中了哪个实验、使用了哪些远程配置。否则线上指标异常时，很难判断是全量问题还是某个灰度策略造成的。

```typescript
analytics.track('page_view', {
  release: releaseInfo.version,
  commit: releaseInfo.commit,
  rollout: window.__ROLLOUT_ID__,
  experiment: window.__EXPERIMENT_ID__,
});
```

灰度标识要贯穿埋点、错误、接口日志和用户反馈。只在前端日志里记录不够，服务端也要能看到同一用户请求来自哪个前端版本。

灰度标识如果只存在前端，排查接口失败时会断链。把 rollout、experiment、release 放进请求上下文，后端日志才能一起关联。

灰度追踪越完整，问题定位就越精确。否则一旦只有部分用户出问题，团队就很难判断到底是版本问题、配置问题还是实验分组问题。

## 回滚判断

版本追踪的最终价值是帮助做发布决策。新版本上线后，如果错误率、白屏率、接口失败率或关键转化出现异常，就要能快速判断是否回滚。

| 信号 | 可能动作 |
|---|---|
| 新 release 错误率显著升高 | 暂停灰度或回滚 |
| 某个 chunk 404 | 恢复资源或修复缓存策略 |
| 某个实验组转化异常 | 关闭实验 |
| 单平台白屏升高 | 平台定向回滚或降级 |

回滚前要确认问题是否只影响某个批次。盲目全量回滚可能影响无问题用户，而不回滚又会扩大事故。版本追踪就是为了让这个判断更有证据。

版本追踪越完整，回滚就越精确。可以只回滚某个灰度批次、某个平台、某个区域，而不是一出问题就全量撤回。

这种精确回滚能力，本质上依赖的就是版本和批次追踪的粒度。没有细粒度追踪，很多时候只能用最大代价换取最快止血。

## 用户反馈

用户反馈入口也应该携带版本信息。截图、设备信息、系统版本、浏览器版本、前端 release、用户 ID 和时间戳组合起来，才能把“我这里打不开”转成可排查的问题。

```typescript
function createFeedbackPayload(message: string) {
  return {
    message,
    release: releaseInfo,
    userAgent: navigator.userAgent,
    url: location.href,
    time: new Date().toISOString(),
  };
}
```

版本追踪不要等事故发生后补。它应该是发布部署的基础设施，和构建产物、监控、灰度、回滚一起设计。

反馈入口、客服工具、测试环境和监控平台都应展示同一套版本信息。这样“用户说出问题”才能快速变成“哪个版本、哪个资源、哪个灰度批次出了问题”。

一个成熟的版本追踪体系，通常能回答这些问题：

| 问题 | 理想状态 |
| --- | --- |
| 当前用户看到的是哪个 release | 能快速得知 |
| 这个 release 来自哪个 commit 和构建批次 | 能 |
| 它对应了哪些静态资源和 source map | 能 |
| 它是否属于某个灰度批次或实验 | 能 |
