## 测试目标

组件测试验证组件在给定 props、状态和用户交互下是否正确渲染和响应。

```txt
输入 props
渲染组件
模拟用户操作
断言界面结果
```

它介于单元测试和 E2E 测试之间：比纯函数测试更接近用户界面，比浏览器端到端测试更快、更稳定。

组件测试最适合验证“组件自己的行为”。例如 props 变化后显示是否正确、用户点击后状态是否变化、接口返回后 UI 是否更新、错误态是否出现。它不适合承担完整登录、路由跳转和后端链路验证。

可以把组件测试理解为“把组件放进一个尽量真实但仍然可控的小环境里观察行为”。它比单元测试更接近实际界面，但又不会像整站 E2E 那样受太多外部因素影响。

## 用户视角

组件测试应优先从用户能看到和操作的内容断言。

```tsx
render(<LoginForm />);

await user.type(screen.getByLabelText("邮箱"), "ada@example.com");
await user.click(screen.getByRole("button", { name: "登录" }));

expect(await screen.findByText("登录成功")).toBeInTheDocument();
```

不要优先断言内部 state、组件实例或实现细节。组件重构后，只要用户行为不变，测试就不应该失败。

这也是 Testing Library 一类工具强调用户视角的原因。测试越接近用户行为，越不容易因为内部实现重构而失效。

用户视角还有一个附带收益：它会逼着组件暴露出更清晰的可访问语义。按钮要有名字、输入框要有关联标签、错误信息要能被找到，这些既提升测试稳定性，也提升产品可用性。

## 渲染工具

React 常用 Testing Library，Vue 常用 Vue Test Utils 或 Testing Library。

```tsx
import { render, screen } from "@testing-library/react";

render(<Button>保存</Button>);

expect(screen.getByRole("button", { name: "保存" })).toBeInTheDocument();
```

查询元素时优先使用 role、label、text，这也能推动组件具备更好的可访问性。

如果一个元素很难通过 role 或 label 找到，通常也意味着真实用户，尤其是依赖辅助技术的用户，也很难理解它。组件测试会反向推动语义和无障碍质量。

只有在确实没有自然语义的情况下，才建议退回到 `data-testid`。比如图表画布、拖拽句柄、复杂虚拟滚动区域，这些地方测试 ID 更像一份显式契约，而不是偷懒。

## 交互模拟

交互应使用接近真实用户的工具，例如 `user-event`。

```tsx
const user = userEvent.setup();

await user.click(screen.getByRole("button", { name: "删除" }));
```

`fireEvent` 更偏底层事件触发，适合特殊场景。普通输入、点击、键盘操作优先使用 user-event。

`user-event` 会更接近真实交互过程，比如输入时触发 focus、keydown、input、change 等事件序列。组件依赖真实交互链时，它比直接触发单个事件更可靠。

这点在表单、键盘操作、受控组件、组合输入和弹层交互里尤其明显。直接 `fireEvent.change` 有时能让测试通过，但并没有真正模拟用户过程，后续一旦实现变化，测试的保护力会下降。

## 异步组件

组件中有请求、定时器、懒加载时，要使用异步断言。

```tsx
render(<UserProfile userId="u1" />);

expect(screen.getByText("加载中")).toBeInTheDocument();
expect(await screen.findByText("Ada")).toBeInTheDocument();
```

不要用固定 `setTimeout` 等待。使用 `findBy`、`waitFor` 让测试等待真实条件。

固定等待会让测试又慢又不稳定。条件式等待能表达“等到界面出现某个状态”，失败时也更容易看出到底哪个状态没出现。

异步组件测试里比较值得重点覆盖的，通常不只是成功态，还包括：

| 状态 | 典型表现 |
| --- | --- |
| 加载中 | skeleton、loading、禁用按钮 |
| 成功 | 数据渲染、提示出现 |
| 失败 | 错误提示、重试按钮 |
| 空态 | 无数据提示、引导操作 |
| 慢响应 | 中间态是否稳定 |

## Mock 接口

组件测试中的网络请求推荐使用 Mock Service Worker。

```ts
server.use(
  http.get("/api/users/u1", () => {
    return HttpResponse.json({ id: "u1", name: "Ada" });
  }),
);
```

这样组件仍然按真实方式发请求，只是响应由测试环境控制。比直接 mock 请求函数更接近真实集成。

接口 Mock 要覆盖成功、失败、空态、权限不足和慢响应。组件测试不应该只验证 happy path，否则很多真实 UI 状态都不会被保护。

如果一个组件依赖多个请求，最好也把请求之间的顺序、并发、取消和失败组合考虑进去。很多复杂 UI 的 bug，不在单个接口成功与否，而在多个异步状态交织时的表现。

## 断言边界

| 应该断言 | 不优先断言 |
| --- | --- |
| 用户可见文本 | 内部 state |
| 按钮是否可用 | 私有方法调用 |
| 错误提示 | 组件文件结构 |
| 请求结果渲染 | CSS 类名细节 |
| 交互后的界面变化 | 实现中的临时变量 |

样式类名可以在设计系统组件中测试，但普通业务组件更应关注用户结果。

业务组件的测试最好关注“用户能不能完成任务”，设计系统组件才更需要关注类名、ARIA、状态样式和受控行为这类底层契约。

也就是说，越接近业务，越应该从结果断言；越接近基础组件，越可以适当补充契约断言。两类组件的测试关注点并不完全相同。

## 组件测试与 E2E

组件测试适合覆盖状态分支和交互细节，E2E 适合覆盖真实路由、登录、后端集成和关键业务链路。

```txt
组件测试：表单校验、弹窗交互、列表状态
E2E：登录下单、权限跳转、支付流程
```

不要用 E2E 覆盖所有小分支，也不要指望组件测试发现所有集成问题。两者分工清楚，测试体系才稳定。

如果组件测试写得很重，说明它可能承担了太多集成职责；如果 E2E 很多且不稳定，说明有些状态分支应该下沉到组件测试。

组件测试是否设计得合理，可以用这几个信号判断：

| 信号 | 说明 |
| --- | --- |
| 本地执行速度可接受 | 说明没有承担过多整站职责 |
| 失败信息能直接映射到某个组件状态 | 说明定位成本低 |
| 组件重构后只要行为不变测试就不需要大改 | 说明没有绑死实现细节 |
