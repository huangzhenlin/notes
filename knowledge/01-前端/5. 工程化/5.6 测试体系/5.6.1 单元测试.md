## 测试结构

常见单元测试由准备、执行、断言三部分组成。

```typescript
import { describe, expect, it } from 'vitest';
import { formatPrice } from './formatPrice';

describe('formatPrice', () => {
  it('格式化人民币金额', () => {
    const result = formatPrice(1299);

    expect(result).toBe('¥12.99');
  });
});
```

测试名称应该表达业务行为，而不是重复函数名。好的测试失败后，读名称就能知道哪个行为坏了。

单元测试真正测试的是“一个小单元在某个输入下是否表现符合预期”。它更适合函数、纯逻辑、数据转换、状态计算和可控副作用，而不是依赖真实浏览器、真实网络和复杂页面交互的场景。

判断一个场景是否适合单元测试，可以先问两个问题：这个逻辑能不能脱离页面独立运行？这个结果是否可以只靠输入和输出判断？如果答案大多是“可以”，那它通常就适合先用单元测试保护。

## 纯函数

纯函数最适合单元测试，因为相同输入总能得到相同输出，没有外部副作用。

```typescript
export function calculateDiscount(price: number, rate: number) {
  if (rate < 0 || rate > 1) {
    throw new Error('invalid_rate');
  }

  return Math.round(price * (1 - rate));
}
```

```typescript
it('计算折扣后价格', () => {
  expect(calculateDiscount(1000, 0.2)).toBe(800);
});

it('拒绝非法折扣', () => {
  expect(() => calculateDiscount(1000, 2)).toThrow('invalid_rate');
});
```

如果一个函数很难测试，通常说明它混合了太多职责：计算、请求、时间、随机数、DOM、全局状态都绑在一起。

所以很多时候，写测试不是最后一步，而是帮助你反过来拆分代码。把副作用边界抽出来后，测试会更简单，代码也更容易维护。

这也是为什么单元测试和设计质量经常是联动的。依赖注入、纯函数、明确输入输出、收敛副作用，这些既让测试更好写，也会让代码本身更容易复用和重构。

## Mock

Mock 用于隔离外部依赖，例如网络、时间、随机数、存储和第三方 SDK。Mock 的目标是让测试稳定，而不是伪造一整个系统。

```typescript
import { vi } from 'vitest';

vi.stubGlobal('fetch', vi.fn(async () => ({
  ok: true,
  json: async () => ({ id: 'u1', name: 'Ada' }),
})));
```

时间相关逻辑可以使用 fake timers：

```typescript
vi.useFakeTimers();

const callback = vi.fn();
setTimeout(callback, 1000);

vi.advanceTimersByTime(1000);
expect(callback).toHaveBeenCalled();
```

Mock 过多会让测试只验证“Mock 是否按预期工作”。能通过传参注入依赖时，优先让函数更可测试，而不是在测试里强行劫持全局环境。

一个简单原则是：能测纯函数就不要先去测全局，能注入依赖就不要强行 mock 运行时。这样测试更像在验证业务行为，而不是在模拟框架内部细节。

Mock 的粒度也要控制。Mock 太粗，会让测试和真实行为差得太远；Mock 太细，又会把实现细节绑死。更稳的做法通常是 mock 边界依赖，而不是 mock 被测单元内部的每一步。

## 异步测试

异步逻辑要等待 Promise 完成，再做断言。

```typescript
it('加载用户信息', async () => {
  const user = await loadUser('u1');

  expect(user.name).toBe('Ada');
});
```

不要写“看起来异步但没有等待”的测试：

```typescript
// 不稳定：测试可能在 Promise 完成前结束
loadUser('u1').then((user) => {
  expect(user.name).toBe('Ada');
});
```

异步测试失败时，先确认是否真正等待了结果，再看 Mock、超时和错误分支。

异步测试最常见的问题不是断言错，而是忘了等待。Promise、定时器、事件回调和网络请求都要确保测试在结果真正到达后再断言。

如果异步测试偶发失败，还要检查是否存在共享状态、未清理的定时器、并发污染或上一个测试留下的全局 mock。很多看起来像“偶发网络问题”的失败，其实是测试隔离没有做好。

## 覆盖率

覆盖率能帮助发现未测试区域，但不能代表测试质量。高覆盖率可能只是执行到了代码，未必验证了关键行为。

| 覆盖指标 | 含义 |
|---|---|
| Statements | 语句是否执行 |
| Branches | 分支是否覆盖 |
| Functions | 函数是否调用 |
| Lines | 行是否执行 |

更有价值的是覆盖关键分支：成功、失败、边界、空值、异常、权限不足、过期数据。覆盖率是信号，不是目标本身。

如果只追求覆盖率，测试很容易变成“为了覆盖而覆盖”。更应该关注的是关键分支、异常路径、边界条件和用户真正会遇到的行为。

单元测试里更值得优先保护的，通常包括：

| 场景 | 原因 |
| --- | --- |
| 金额、折扣、权限等规则计算 | 容易因为重构被破坏 |
| 空值、异常、默认值分支 | 线上高频出错点 |
| 状态机或状态切换逻辑 | 分支多，人工容易漏 |
| 数据转换与格式化 | 输入组合多，回归隐蔽 |

## 测试组织

测试文件可以和源码放在一起，也可以集中放在 `__tests__`。选择哪种方式不如保持一致重要。

```text
src
├─ utils
│  ├─ formatPrice.ts
│  └─ formatPrice.test.ts
└─ stores
   ├─ cart.ts
   └─ cart.test.ts
```

单元测试应该尽量快，适合在本地提交前和 CI PR 阶段运行。慢测试、依赖浏览器的测试、真实链路测试应该放到其他层级。

这也是测试分层的意义：单元测试跑得快、失败原因清晰，适合高频执行；更重的测试留给组件测试、E2E 或预发验证，避免本地开发被拖慢。

单元测试理想状态下应该能在开发者本地高频运行。它越快，团队越愿意在改动后顺手跑一遍；一旦变慢，就会逐渐被推迟到“有空再测”，保护价值也会下降。

## 可测试设计

可测试代码通常有几个特征：输入输出清晰，副作用可注入，时间和随机数可控制，外部依赖集中封装。

```typescript
export function createOrderNo(now = new Date()) {
  return `ORDER_${now.getFullYear()}_${now.getTime()}`;
}
```

测试时可以传入固定时间：

```typescript
expect(createOrderNo(new Date('2026-01-01'))).toContain('2026');
```

单元测试和 [[5.6.3 E2E测试|E2E测试]] 是互补关系：单元测试快速确认逻辑正确，E2E 测试确认用户链路真的可用。

如果一个模块的单元测试写起来特别痛，通常不是测试工具的问题，而是模块边界、依赖方式或副作用设计有待调整。

实际排查单元测试问题时，可以优先按下面顺序判断：

```text
先看是否测了太大的东西
  -> 再看依赖是否难以隔离
  -> 再看断言是否绑定实现细节
  -> 最后再看测试工具和运行环境
```

大多数“单元测试难写、不稳、很慢”的根因，最终还是会落回代码边界本身，而不是测试框架。
