## 覆盖目标

覆盖率用于衡量测试执行到了哪些代码。它能帮助发现未被测试触达的区域，但不能证明代码行为一定正确。

```text
测试执行
  -> 收集覆盖信息
  -> 生成报告
  -> 找出未覆盖区域
```

覆盖率是信号，不是目标本身。真正要关注的是关键业务分支是否被验证。

高覆盖率只能说明代码被执行过，不代表断言有效。一个没有断言的测试也能提高覆盖率，但不能保护真实行为。

因此覆盖率报告更适合被当成“风险雷达”，而不是“成绩单”。它能提醒你哪些区域可能完全没人测，但不能替你判断这些测试是不是测到了关键业务点。

## 覆盖维度

常见覆盖率维度包括语句、分支、函数和行。

| 指标 | 含义 |
|---|---|
| Statements | 语句是否执行 |
| Branches | 条件分支是否覆盖 |
| Functions | 函数是否调用 |
| Lines | 行是否执行 |

分支覆盖通常比行覆盖更能暴露问题，因为很多 bug 出现在异常、空值、权限和边界路径里。

如果只能优先看一个指标，通常先看分支覆盖。因为业务里真正出问题的地方，往往不是主路径，而是失败、空值、边界和异常路径。

同样 80% 的覆盖率，含义可能完全不同。一个项目如果主要覆盖的是 happy path，另一个项目覆盖了大量失败分支、空态和异常路径，后者通常更有保护价值。

## 阈值设置

覆盖率阈值可以防止测试质量持续下降。

```typescript
// vitest.config.ts
export default {
  test: {
    coverage: {
      provider: 'v8',
      reporter: ['text', 'html'],
      thresholds: {
        statements: 80,
        branches: 70,
        functions: 80,
        lines: 80,
      },
    },
  },
};
```

阈值要循序渐进。老项目可以先设置当前基线，再逐步提高，避免一次性把团队卡死。

新项目可以从较高阈值开始，老项目更适合“只要求新代码不下降”。覆盖率治理应该是持续改进，不是一次性运动。

覆盖率阈值真正有用的前提，是团队愿意长期维护它。如果阈值一开始定得过高，大家只会想办法规避；如果太低，又起不到约束作用。能持续执行，比一次性理想化更重要。

## 报告阅读

覆盖率报告通常会标出未覆盖行和未覆盖分支。阅读报告时优先看核心模块，而不是追求把所有工具和边缘代码都补满。

| 未覆盖区域 | 判断 |
|---|---|
| 支付逻辑 | 优先补 |
| 权限分支 | 优先补 |
| 错误处理 | 优先补 |
| 简单类型声明 | 可忽略 |
| 框架胶水代码 | 视情况 |

不要为了覆盖率写没有断言的测试。执行到代码但没有验证结果，覆盖率会好看，质量不会提高。

读报告时还要区分“值得补”和“不值得补”。核心业务、复杂分支、权限逻辑优先补；简单入口、类型声明、自动生成代码则不必强求。

一个常见误区是看到红色未覆盖行就立刻想补测试，但更重要的是先判断这段代码是否值得被测。覆盖率治理本质上也是资源分配，不是机械填空。

## 排除规则

有些文件不适合计入覆盖率，例如类型文件、生成代码、入口文件、配置文件。

```typescript
coverage: {
  exclude: [
    'src/**/*.d.ts',
    'src/generated/**',
    'src/main.ts',
  ],
}
```

排除规则要克制。不能因为某个模块难测就把它排除，否则覆盖率会失去约束意义。

合理排除能让覆盖率更真实，滥用排除会让数字变漂亮但质量变差。排除列表最好定期复查。

特别要警惕“因为难测所以排除”。难测的地方往往恰恰说明边界复杂、职责混乱或业务关键，更应该先思考是否能重构出更可测的结构，而不是直接把它从报告里抹掉。

## 变更覆盖率

大型项目更关注变更覆盖率：本次 PR 改动的代码是否有测试覆盖。它比全仓库覆盖率更贴近日常协作。

```text
全局覆盖率 75%
本次变更覆盖率 95%
```

这适合老项目渐进治理。即使历史债务很多，也可以要求新代码质量不继续下降。

变更覆盖率比全局覆盖率更适合日常 PR。它把注意力放在本次改动上，能避免历史包袱拖住当前质量门禁。

在老项目里，这种策略尤其现实。历史覆盖率可能一时提不上去，但至少可以确保新改动不继续制造新的测试盲区。

## 质量边界

覆盖率无法判断断言是否正确，也无法覆盖真实浏览器行为、样式回归和完整用户链路。

| 覆盖率能发现 | 覆盖率发现不了 |
|---|---|
| 哪些代码没跑到 | 断言是否有意义 |
| 哪些分支没覆盖 | UI 是否好看 |
| 测试盲区 | 真实链路是否成功 |

覆盖率和 [[5.6.1 单元测试|单元测试]] 是配套的，但还需要 [[5.6.3 E2E测试|E2E测试]] 和视觉回归补充真实用户视角。

最终判断测试质量时，要看失败时是否能定位问题、是否覆盖关键业务风险、是否能长期稳定运行，而不是只看一个百分比。

如果要把覆盖率真正用在工程治理里，更推荐这套顺序：

```text
先看关键模块有没有明显盲区
  -> 再看本次改动是否被覆盖
  -> 再看全局阈值是否在稳步提升
  -> 最后才看总体百分比好不好看
```

这样覆盖率才会服务质量，而不是反过来把团队带到“为了好看而补测试”的方向上。
