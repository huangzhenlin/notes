## 回归目标

视觉回归测试用于发现 UI 视觉差异，例如布局错位、字体变化、颜色错误、组件溢出和响应式断点异常。它关注“看起来有没有变”，不是业务逻辑是否正确。

```text
生成截图
  -> 与基线对比
  -> 计算差异
  -> 人工确认
  -> 更新基线或修复问题
```

视觉回归适合设计系统、组件库、营销页、核心页面和复杂布局，不适合替代功能测试。

它特别适合发现“功能没坏但界面变了”的问题。比如按钮高度变了、布局挤压了、字体 fallback 了、响应式断点错了，这些都不一定会让普通测试失败。

视觉回归最适合放在 UI 变化成本高的地方。比如组件库、设计系统、首页、关键表单、支付流程、数据看板，这些区域一旦样式回归，用户很容易感知，但普通单元测试又很难覆盖。

可以把视觉回归理解为“给界面建立一份可比对的视觉契约”。逻辑测试保护的是行为，视觉回归保护的是呈现结果，两者并不互相替代。

## 截图基线

基线截图是视觉回归的参照物。第一次运行生成基线，后续运行与基线对比。

```typescript
import { test, expect } from '@playwright/test';

test('首页视觉稳定', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveScreenshot('home.png');
});
```

基线截图应该进入版本控制，变更时通过 code review 确认。否则视觉变化会悄悄进入主干。

更新基线不是机械确认，而是一次视觉审查。差异如果符合预期，就更新基线；如果不符合预期，就修复样式或布局问题。

基线更新应该和需求变更绑定。只有视觉变化是预期的一部分，才应该更新基线；如果只是依赖升级、浏览器差异或样式泄漏导致截图变化，就应该先找原因，而不是一键接受所有差异。

如果团队把“截图红了就直接更新基线”当成默认流程，视觉回归很快就会失去意义。它的价值恰恰在于逼着大家确认：这次视觉变化到底是不是预期。

## 稳定页面

截图前必须让页面稳定。动态时间、随机数据、动画、广告、异步图片和骨架屏都会造成误报。

```typescript
await page.goto('/dashboard');
await page.getByText('加载完成').waitFor();
await expect(page).toHaveScreenshot();
```

必要时可以冻结时间、mock 接口、禁用动画、固定浏览器尺寸和字体。

视觉测试越依赖动态内容，误报越多。稳定截图环境比提高截图次数更重要。

```css
* {
  animation: none !important;
  transition: none !important;
}
```

页面稳定还包括字体、时区、滚动位置和数据顺序。截图环境如果每次机器、字体或数据都不同，视觉回归会变成噪音制造机。稳定性优先级要高于覆盖数量。

因此视觉回归的核心能力，不只是截图，而是环境治理。字体包、浏览器版本、屏幕尺寸、时区、语言环境、动画状态、接口数据，这些都必须尽量固定。

## 对比阈值

视觉对比通常允许少量像素差异，以适配字体抗锯齿、系统渲染和平台差异。

```typescript
await expect(page).toHaveScreenshot({
  maxDiffPixelRatio: 0.01,
});
```

阈值不能设置过大。过大阈值会把真实问题吞掉，过小阈值又会制造大量噪音。应根据页面类型和运行环境调试。

对设计系统组件，阈值通常要更严格；对包含图片、图表或复杂字体渲染的页面，可以适当放宽，但要避免吞掉真实回归。

阈值最好按页面类型设置。组件库截图应尽量严格，因为它保护的是基础视觉契约；业务页面可以稍微宽松，但不能宽松到布局错位也通过。

阈值策略也应该和场景价值匹配。越是基础组件、越是像素级敏感的区域，越应该严格；越是动态图表、复杂图片、外部资源多的页面，越需要在可接受误差和误报成本之间找平衡。

## 组件截图

组件库更适合做组件级视觉回归。每个组件在不同状态下生成截图，例如默认、hover、disabled、error、loading。

```text
Button
  -> default
  -> disabled
  -> loading
  -> danger
```

组件级截图能更早发现设计系统回归，也比整页截图更容易定位差异来源。

组件库最好按状态组织截图：默认、禁用、加载、错误、聚焦、hover、选中。这样视觉回归不只是“看一张图”，而是保护组件契约。

复杂组件还可以按主题、尺寸和方向组织截图。比如按钮要看不同 variant，表单要看错误和禁用，弹窗要看不同宽度，表格要看空态和长文本。这样比只截一个默认状态更有保护价值。

组件级视觉回归最怕只截“默认状态”。真正容易在改版中出问题的，往往是 hover、disabled、error、selected、dark mode、长文本、极窄宽度这些边缘状态。

## 响应式截图

响应式页面要在多个 viewport 下截图。

```typescript
test.use({ viewport: { width: 390, height: 844 } });
```

常见尺寸包括移动端、小屏桌面、大屏桌面。不要只在开发者自己的浏览器宽度下验证。

响应式问题经常只在特定宽度出现。选择 viewport 时应覆盖业务真实设备，而不是随便选几个整数宽度。

响应式截图还要覆盖临界断点附近。很多布局不是在 375 或 1440 这类常见宽度坏掉，而是在断点刚切换的几像素范围内错位，所以关键页面可以多测断点前后。

如果页面主要面向移动端、平板或大屏，还应把真实设备分布纳入截图策略，而不是只用开发机常见尺寸。视觉回归越接近真实终端，发现的问题越有价值。

## 误报治理

视觉回归的难点不是截图，而是降低误报。误报太多，团队很快会失去信任。

| 误报来源 | 处理 |
|---|---|
| 动画 | 禁用动画 |
| 时间 | 冻结时钟 |
| 随机数据 | mock 数据 |
| 字体差异 | 固定字体和运行环境 |
| 图片异步 | 等待资源稳定 |

视觉回归和 [[5.6.3 E2E测试|E2E测试]] 互补：E2E 验证用户流程，视觉回归验证流程中的界面是否保持一致。

误报治理做不好，团队会逐渐不信任视觉测试。稳定数据、固定环境、明确基线更新流程，是视觉回归能长期运转的关键。

视觉回归的维护成本要提前承认。它不是加上截图断言就万事大吉，而是要配合稳定环境、评审规则和基线管理。只有团队相信差异报告有意义，视觉回归才会真正进入质量体系。

实际落地视觉回归时，可以优先遵循这条顺序：

```text
先挑少量高价值页面或组件
  -> 先把环境稳定下来
  -> 再收紧阈值和状态覆盖
  -> 最后再扩大截图范围
```

这样更容易建立团队信任。否则一开始就大面积接入，误报很多，大家往往会先学会“忽略红图”，而不是利用它发现问题。
