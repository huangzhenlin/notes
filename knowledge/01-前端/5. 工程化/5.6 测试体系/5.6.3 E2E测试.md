## 测试对象

E2E 测试从用户视角验证完整业务链路：打开页面、执行操作、等待反馈、确认结果。它不关心某个函数怎么实现，而关心用户能否完成真实任务。

```text
用户目标
  -> 页面加载
  -> 表单输入
  -> 点击提交
  -> 接口返回
  -> 页面反馈
  -> 数据可见
```

适合 E2E 覆盖的不是所有细节，而是高价值路径：登录、注册、下单、支付、搜索、提交表单、权限拦截、关键配置保存。普通工具函数和组件内部逻辑更适合单元测试或组件测试。

端到端测试最贵，所以每一条都应该有明确业务价值。一个好的 E2E 用例，通常都能回答一个产品层问题，例如“用户是否还能成功登录”“订单是否还能提交流转”“权限控制是否仍然生效”。

## 用户行为

E2E 测试应优先使用用户能感知的选择器，例如角色、文本、标签、占位符和测试 ID，而不是依赖 CSS 类名、DOM 层级或内部实现。

```typescript
import { test, expect } from '@playwright/test';

test('用户可以提交登录表单', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('邮箱').fill('ada@example.com');
  await page.getByLabel('密码').fill('correct-password');
  await page.getByRole('button', { name: '登录' }).click();

  await expect(page.getByText('欢迎回来')).toBeVisible();
});
```

`getByRole`、`getByLabel`、`getByText` 这类定位方式同时推动页面可访问性变好。用户能理解的控件，测试也更容易稳定定位。

如果一段页面只能靠很深的 CSS 选择器或 XPath 才能稳定定位，往往说明界面语义不够清晰，或者测试在依赖实现细节。短期能跑，长期维护成本通常会很高。

## 定位策略

稳定的定位策略会显著降低 E2E 脆弱性。CSS 类名经常因为样式重构变化，DOM 层级会因为布局调整变化，而用户可见语义通常更稳定。

| 优先级 | 定位方式 | 示例 |
|---|---|---|
| 高 | 角色与名称 | `getByRole('button', { name: '保存' })` |
| 高 | 表单标签 | `getByLabel('手机号')` |
| 中 | 可见文本 | `getByText('订单已提交')` |
| 中 | 测试 ID | `getByTestId('order-card')` |
| 低 | CSS / XPath | `.layout > div:nth-child(2)` |

测试 ID 适合没有自然语义的复杂区域，例如图表、虚拟列表、拖拽画布。它应该是测试契约，不应该绑定样式类名。

测试 ID 的命名也应该稳定、可读、面向业务。例如 `checkout-submit`、`profile-avatar` 往往比 `btn-1`、`box-right` 更适合长期维护。

## 自动等待

现代 E2E 工具会在点击、输入和断言时自动等待元素可操作。测试里不应该到处写固定时间等待，因为固定等待既慢又不稳定。

```typescript
// 不稳定：接口快时浪费时间，接口慢时仍可能失败。
await page.waitForTimeout(3000);

// 更稳定：等待用户真正能看到的结果。
await expect(page.getByText('保存成功')).toBeVisible();
```

断言也应该使用会重试的 Web 优先断言：

```typescript
await expect(page.getByRole('button', { name: '提交' })).toBeEnabled();
await expect(page.getByText('订单已创建')).toBeVisible();
```

E2E 的稳定性很大程度来自“等待正确的信号”。正确的信号通常是用户可见状态，而不是某个内部变量。

这也是为什么固定睡眠几乎总是坏味道。等待“某个可见结果”既更贴近真实用户，也更容易在失败时说明问题到底卡在哪一步。

## 数据隔离

每个 E2E 用例都应该能独立运行，不依赖前一个测试留下的登录态、数据库记录或本地缓存。否则一个测试失败可能拖垮整套测试。

```typescript
test.beforeEach(async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('邮箱').fill('test@example.com');
  await page.getByLabel('密码').fill('password');
  await page.getByRole('button', { name: '登录' }).click();
});
```

更高效的方式是把登录态作为测试夹具提前生成：

```typescript
// playwright.config.ts
export default defineConfig({
  use: {
    storageState: 'playwright/.auth/user.json',
  },
});
```

数据准备要和环境匹配。测试可以调用后端测试接口创建订单、用户、权限数据，但要能清理或使用隔离命名，避免污染共享环境。

如果测试依赖共享账号、共享订单或共享配置，很快就会出现并行冲突、脏数据污染和偶发失败。E2E 环境越接近真实，就越要重视数据隔离。

## 网络控制

E2E 测试应避免依赖不可控的第三方服务。支付、地图、广告、外部 OAuth、统计脚本都可能因为网络或弹窗导致测试不稳定。可以通过 mock、stub 或测试环境替身控制外部依赖。

```typescript
await page.route('**/api/recommendations', async (route) => {
  await route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify({
      items: [{ id: 'p1', title: '测试商品' }],
    }),
  });
});
```

对自己控制的后端接口，端到端测试可以走真实服务；对第三方服务，应该用可控响应替代。这样测试验证的是你的业务集成逻辑，而不是第三方今天是否稳定。

这里可以把依赖分成两类：核心链路依赖尽量真实，外部不可控依赖尽量替身化。这样既不会把所有东西都 mock 掉，也不会让第三方不稳定性拖垮整个测试体系。

## Page Object

Page Object 可以把页面操作封装成语义化方法，减少重复代码。但不要过度封装到看不见测试意图。

```typescript
class LoginPage {
  constructor(private page: Page) {}

  async open() {
    await this.page.goto('/login');
  }

  async login(email: string, password: string) {
    await this.page.getByLabel('邮箱').fill(email);
    await this.page.getByLabel('密码').fill(password);
    await this.page.getByRole('button', { name: '登录' }).click();
  }
}

test('登录成功后进入首页', async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.open();
  await loginPage.login('ada@example.com', 'password');

  await expect(page.getByText('首页')).toBeVisible();
});
```

Page Object 应封装稳定业务动作，而不是封装每一个按钮点击。测试读起来仍然应该像用户故事。

如果 Page Object 抽象过度，测试文件里会只剩一堆看不见细节的方法调用，失败时也更难判断问题到底出在页面、测试还是封装层。抽象的目标是减少重复，不是隐藏意图。

## CI 稳定性

E2E 在 CI 上更容易暴露问题：机器慢、网络慢、浏览器版本不同、并行执行、环境数据竞争。稳定性治理要靠配置和流程，而不是无限加超时。

```typescript
export default defineConfig({
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 2 : undefined,
  use: {
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },
});
```

失败时 trace 比普通截图更有价值，因为它能看到动作时间线、DOM 快照、网络请求和控制台日志。E2E 测试和 [[5.7.1 流水线|流水线]] 要配合：PR 阶段跑关键路径，夜间或发布前跑完整矩阵。

在 CI 中，E2E 最重要的不是“全部跑完”，而是“失败后能快速看懂为什么失败”。trace、video、console、network log 这些产物，本质上是在为排障买时间。

## 维护边界

E2E 测试越多，维护成本越高。不要把所有 UI 分支都塞进 E2E。更合理的测试金字塔是：大量单元测试覆盖逻辑，适量组件测试覆盖交互，少量 E2E 覆盖关键用户链路。

| 测试层级 | 适合内容 |
|---|---|
| 单元测试 | 工具函数、状态转换、纯逻辑 |
| 组件测试 | 表单、弹窗、复杂组件交互 |
| E2E 测试 | 登录、下单、支付、核心业务流 |

E2E 的价值不在数量，而在信心。每个 E2E 用例都应该回答一个清晰问题：如果它失败，是否意味着用户真的无法完成某个重要任务。

排查 E2E 不稳定时，可以优先看：

```text
是否等待了错误的信号
  -> 是否依赖共享数据
  -> 是否绑定了脆弱选择器
  -> 是否把第三方不稳定性带进来了
  -> 是否在 CI 资源不足时并发过高
```

只要这些基础问题不解决，单纯加超时和重试通常只会把问题藏起来。
