## Mock 目的

Mock 数据用于在真实依赖不可用、成本高或不稳定时，提供可控输入。

```txt
接口未完成 -> Mock API
测试边界场景 -> Mock 数据
第三方服务不稳定 -> Mock 服务
错误场景难复现 -> Mock 错误响应
```

Mock 的目标不是“造假”，而是让开发和测试能稳定覆盖预期场景。

Mock 最重要的价值是稳定可控。真实接口可能受网络、权限、发布节奏和后端实现影响，而测试需要的是可重复、可预测、可覆盖边界的输入。

Mock 的本质是把不稳定因素从测试里拿掉。这样测试关注的就不是网络会不会抖、后端今天有没有上线，而是组件和页面在给定输入下是否表现正确。

但 Mock 不能脱离真实世界太远。它一旦和真实接口、真实状态流或真实错误形态长期漂移，测试覆盖再多，也可能只是把一套“假场景”跑得很绿。

## 数据工厂

测试中推荐用工厂函数生成数据，而不是复制大段对象。

```ts
function createUser(overrides: Partial<User> = {}): User {
  return {
    id: "u1",
    name: "Ada",
    role: "admin",
    ...overrides,
  };
}

const guest = createUser({ role: "guest" });
```

工厂函数能减少重复，也能让每个测试只突出自己关心的字段。

工厂函数比直接复制 JSON 更适合长期维护，因为默认值集中在一处，字段变化时只要改一个地方。测试用例只需要覆盖自己关心的差异即可。

工厂函数也适合表达层级关系。比如列表、分页、详情、错误响应可以建立在同一个基础实体上，这样测试数据不会到处散落成互相矛盾的 JSON 片段。

一个成熟的数据工厂，通常会把“默认值 + 覆盖点 + 语义场景”结合起来。这样测试写起来既简洁，也能快速构造出管理员、游客、空列表、异常订单、过期会话这类明确场景。

## 接口 Mock

前端接口 Mock 常用 Mock Service Worker 这类拦截网络请求的方案。

```ts
http.get("/api/users/:id", ({ params }) => {
  return HttpResponse.json(
    createUser({ id: String(params.id) }),
  );
});
```

这种方式比 mock 请求函数更接近真实行为，因为组件仍然发出正常网络请求，只是响应被测试环境拦截。

网络拦截式 Mock 的优势在于它保留了真实请求链路，所以更容易发现请求路径、请求方法、请求头和状态处理方面的问题。

如果项目有请求封装层，MSW 这类方案还能顺手验证拦截器、鉴权头、错误码处理和重试逻辑。相比直接 mock 函数，它更接近真实浏览器环境。

因此在前端工程里，越接近组件和页面层，越推荐用网络层 Mock；越接近纯逻辑层，越可以直接 mock 函数或模块。这样每一层的 mock 成本和真实性更平衡。

## 场景覆盖

Mock 不应只覆盖成功数据，还要覆盖异常、空态、权限、边界值。

| 场景 | 示例 |
| --- | --- |
| 成功 | 有完整列表 |
| 空态 | 列表为空 |
| 加载慢 | 延迟响应 |
| 服务错误 | 500 |
| 权限错误 | 403 |
| 字段缺失 | 兼容旧数据 |
| 大数据量 | 长列表性能 |

优秀的 Mock 数据能推动 UI 状态完整，而不是只让 happy path 跑通。

如果只写成功数据，组件往往只验证“有数据时能渲染”，但无法覆盖空态、错误态、延迟态和权限态，而这些恰恰是线上常见问题。

场景覆盖最好和组件状态对应。比如列表页至少要有空态、加载态、错误态、分页态和超长文本态；表单页至少要有校验失败、提交失败、字段缺失和服务端回填。这样 Mock 不是为了凑数量，而是为了补齐真实状态。

当你不知道该补哪些 Mock 场景时，可以直接反推页面状态图：页面可能出现哪些状态，用户可能看到哪些分支，后端可能返回哪些异常，这些就应该映射成一组明确的 mock 数据。

## 契约一致

Mock 数据要和真实接口契约保持一致。接口字段变更后，Mock 也要更新。

```ts
type UserDTO = {
  id: string;
  displayName: string;
};
```

如果 Mock 和真实接口长期漂移，测试越多越容易制造虚假信心。最好从 OpenAPI、类型定义、后端契约生成或共享 DTO 中获得数据结构。

Mock 和契约不一致时，最危险的不是测试报错，而是测试全绿但线上挂。越是接口频繁变更的团队，越要让 Mock 数据来源尽量贴近真实契约。

契约一致最好由工具或共享类型兜底，而不是靠人工记忆。只要接口字段变动，Mock 也应同步更新，否则测试会对“旧世界”一直绿灯。

如果前后端有 OpenAPI、共享 DTO、schema 或接口生成工具，最好尽量把 Mock 建立在这些来源之上。这样契约变化时，问题会尽早暴露，而不是等到上线后才发现真实接口已经不一样了。

## 随机数据

随机数据适合生成大量样本，但测试断言要保持稳定。

```ts
const user = createUser({
  id: "fixed-id",
  name: faker.person.fullName(),
});
```

快照测试、精确文本断言、排序测试不适合完全随机。需要随机时，应固定 seed 或只随机不影响断言的字段。

随机数据适合扩展覆盖面，不适合取代稳定断言。真正要测的仍然是行为是否正确，而不是随机内容本身长什么样。

随机化最适合做“扩大样本多样性”的补充，而不是作为主要测试基础。主测试仍应尽量使用可预测数据，保证失败后能稳定复现。

如果测试对随机数据有断言依赖，最好固定 seed，或者只让随机字段出现在非关键区域。否则测试会出现偶发失败，很难定位。

## 环境隔离

开发 Mock、单元测试 Mock、E2E Mock 要区分。

| 环境 | Mock 方式 |
| --- | --- |
| 本地开发 | Mock 服务或 MSW |
| 单元测试 | 函数、模块、网络拦截 |
| 组件测试 | MSW + 数据工厂 |
| E2E 测试 | 测试后端或网络拦截 |
| 预发环境 | 尽量真实服务 |

越接近上线，越应该减少 Mock，使用真实服务或稳定测试环境验证集成问题。

如果到了预发还依赖大量 Mock，说明测试层级和真实集成之间还缺了一层。Mock 适合开发与边界测试，不适合长期替代真实集成验证。

对外部服务依赖重的项目，Mock 还可以作为“服务降级演练”的工具。比如支付、短信、地图、上传这类能力，在开发和测试里最好能显式模拟成功、失败和超时，避免只测顺利路径。

这类失败场景往往在真实环境里很难稳定复现，Mock 反而能帮助团队更早发现交互和容错设计是否完整。

## 维护边界

Mock 数据也需要维护。过多手写 JSON 文件会变成第二套后端。

```txt
基础工厂少而通用
场景数据围绕测试命名
接口契约自动同步
错误场景显式定义
不用的 Mock 及时删除
```

Mock 的价值在于稳定和可控，不在于模拟整个世界。

维护 Mock 时要记得同步清理废弃场景，否则第二套数据会慢慢长成另一套“假后端”。

长期维护时，Mock 最好和测试命名绑定。每个场景数据都能看出它服务哪类测试，这样清理和排查都更快。否则 Mock 文件一多，就会变成另一个难维护的资料仓库。

判断 Mock 设计是否健康，可以看几个信号：

| 信号 | 说明 |
| --- | --- |
| 新增测试时能快速复用已有工厂 | 数据组织合理 |
| 接口字段变化时 Mock 能及时暴露问题 | 契约没有漂移太远 |
| 很少需要复制整段 JSON | 维护成本可控 |
| 出错时能迅速定位是哪类场景数据导致 | 命名和分层清晰 |
