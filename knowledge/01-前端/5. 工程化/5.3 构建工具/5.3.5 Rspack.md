## 工具定位

Rspack 是基于 Rust 编写的前端打包工具，目标是提供接近 Webpack 生态的能力，同时提升构建性能。

```txt
Webpack 生态兼容思路
Rust 实现提升性能
面向大型前端项目构建
```

它适合希望保留 Webpack 配置心智、但构建速度遇到瓶颈的项目。新项目也可以直接选择 Rspack，但要确认团队和生态依赖是否匹配。

Rspack 的核心价值不是“换一个更快的名字”，而是在尽量复用 Webpack 心智的前提下，用 Rust 实现降低构建耗时。对大型历史项目来说，这比完全迁移到另一套工具链更容易控制风险。

它最适合的场景通常不是“从零选一个最轻工具”，而是“Webpack 体系已经很深，但构建速度开始拖团队后腿”。这时 Rspack 的价值在于迁移路径更平滑，而不是心智完全重建。

## 基础配置

Rspack 配置结构与 Webpack 接近。

```ts
import { defineConfig } from "@rspack/cli";

export default defineConfig({
  entry: {
    main: "./src/main.tsx",
  },
  output: {
    filename: "[name].[contenthash].js",
    clean: true,
  },
  module: {
    rules: [
      {
        test: /\.tsx?$/,
        loader: "builtin:swc-loader",
      },
    ],
  },
});
```

熟悉 Webpack 的团队迁移成本相对低，但不能假设所有 loader/plugin 都完全兼容。

迁移时不要一次性照搬完整配置。更稳妥的方式是先跑通最小入口，再逐步加入 CSS、图片、别名、环境变量、插件和生产优化。每加一类能力，就对比一次产物。

Rspack 配置看起来像 Webpack，但“像”不等于“完全等价”。特别是一些边缘 loader、自研 plugin、模板生成和复杂资源链路，最好单独做兼容清单，不要默认可以直接复制。

## SWC 编译

Rspack 常结合内置 SWC 能力处理 JavaScript、TypeScript、React。

```ts
{
  test: /\.[jt]sx?$/,
  loader: "builtin:swc-loader",
  options: {
    jsc: {
      parser: {
        syntax: "typescript",
        tsx: true,
      },
      transform: {
        react: {
          runtime: "automatic",
        },
      },
    },
  },
}
```

SWC 编译速度快，但类型检查不是它的职责。TypeScript 项目仍需要 `tsc --noEmit` 或独立类型检查流程。

这一点和很多现代构建工具一样：为了速度，转译和类型检查往往被拆开。构建成功只能说明产物生成了，不代表类型一定正确。

这也意味着脚本命令要分层。`build` 负责产物，`typecheck` 负责类型，`lint` 负责静态规则，CI 再把它们统一收口。把所有责任都压到构建器本身，往往会让速度和边界都变模糊。

## 开发服务

Rspack 提供开发服务和 HMR 能力。

```ts
export default defineConfig({
  devServer: {
    port: 3000,
    hot: true,
    historyApiFallback: true,
  },
});
```

SPA 项目通常需要 `historyApiFallback` 支持刷新路由。代理、HTTPS、Mock、跨域等也应在 devServer 中统一配置。

开发服务不仅是本地启动页面。它还负责模拟部署环境的一部分能力，比如接口代理、资源路径、跨域、HTTPS、WebSocket 和 HMR。如果开发服务和真实部署差异太大，上线前才会暴露路径和跨域问题。

对于历史 Webpack 项目来说，开发服务迁移尤其要验证代理、history fallback、静态资源目录和环境变量行为。很多项目构建能过，但开发环境的细节没对齐，团队日常使用反而更难受。

## 代码分割

Rspack 支持动态 import 和 splitChunks。

```ts
const AdminPage = lazy(() => import("./pages/AdminPage"));
```

```ts
optimization: {
  splitChunks: {
    chunks: "all",
  },
}
```

代码分割要结合路由和业务模块，不要只依赖默认策略。图表、编辑器、地图、后台低频页面都适合拆分。

对于从 Webpack 迁移来的项目，拆包策略尤其要复查。默认策略即使能构建成功，也可能改变 chunk 命名、公共依赖抽取和缓存稳定性，导致线上缓存命中率变化。

构建速度提升不应该靠牺牲产物稳定换来。迁移前后除了对比耗时，还要对比 chunk 数量、vendors 拆分、hash 稳定性和路由级懒加载行为。

## 生态兼容

Rspack 兼容大量 Webpack 配置，但不是百分百等价。

| 项目 | 关注点 |
| --- | --- |
| loader | 是否支持或有替代 |
| plugin | 是否兼容 Rspack |
| Module Federation | 版本和能力差异 |
| CSS 处理 | PostCSS、Sass、CSS Modules |
| 资源处理 | 图片、字体、SVG |

迁移前应列出当前 Webpack 配置中所有 loader/plugin，逐项确认兼容性。

兼容性评估最好分成三类：完全兼容、需要替换、暂时不支持。不要等迁移到最后一天才发现某个核心插件无法替代，例如模块联邦、特殊模板处理、老式 CSS 提取或内部自研插件。

## 迁移策略

```txt
建立最小 Rspack 配置
跑通开发服务
跑通生产构建
对比产物和路由
验证 CSS、静态资源、环境变量
补类型检查和测试
对比构建耗时
```

迁移构建工具不能只看构建成功。还要检查产物路径、缓存策略、Source Map、动态导入、部署环境和线上监控。

迁移前后最好保留同一套验证脚本：构建耗时、产物体积、chunk 数量、核心页面截图、路由刷新、错误上报、source map 解析。这样才能证明迁移带来了真实收益，而不是只换了工具。

## 使用边界

Rspack 的价值主要在构建性能和 Webpack 迁移体验。如果项目本身很小，Vite 已经足够快，迁移收益可能不明显。大型多页应用、Webpack 历史项目、模块联邦项目更值得评估。

如果项目依赖大量 Webpack 生态，同时构建耗时已经影响日常开发和 CI，Rspack 值得优先评估。如果项目本身是现代轻量 SPA，团队又没有 Webpack 历史包袱，直接使用 Vite 可能更简单。

Rspack 更像“性能导向的 Webpack 路线”，而不是所有项目的默认答案。选它的理由应该是：历史迁移成本可控、团队能复用既有心智、构建耗时问题真实存在，而不是单纯因为它更新。
