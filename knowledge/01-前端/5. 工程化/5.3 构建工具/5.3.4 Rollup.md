## 构建定位

Rollup 是一个面向 JavaScript 模块的打包工具，尤其适合构建库、SDK、组件包和需要清晰产物格式的项目。它以 ES 模块为基础，擅长 tree shaking 和输出多种模块格式。

```text
源码模块
  -> 依赖图
  -> Tree Shaking
  -> 插件转换
  -> 输出 ESM / CJS / UMD
```

应用开发中常通过 Vite 间接使用 Rollup；库开发中则经常直接配置 Rollup。

Rollup 的优势不是“什么都能做”，而是“把模块关系分析得更干净”。当你希望发布一个可被别人复用、可摇树、格式清晰的包时，Rollup 的心智通常比应用型打包器更直接。

这也是为什么 Rollup 在库开发里长期很稳。应用构建更关心开发服务器、HTML 入口、路由和环境变量；库构建更关心输出格式、tree shaking、external 和类型声明。Rollup 刚好把重点放在后者。

## 输入输出

Rollup 配置通常包含入口、输出格式和插件。

```javascript
// rollup.config.js
import typescript from '@rollup/plugin-typescript';

export default {
  input: 'src/index.ts',
  output: [
    {
      file: 'dist/index.mjs',
      format: 'es',
      sourcemap: true,
    },
    {
      file: 'dist/index.cjs',
      format: 'cjs',
      sourcemap: true,
    },
  ],
  plugins: [typescript()],
};
```

库项目通常同时输出 ESM 和 CJS，方便不同生态消费。浏览器直接使用的库还可能输出 IIFE 或 UMD。

输出格式要和使用场景匹配。现代构建器更喜欢 ESM，Node 历史生态中仍有大量 CJS，浏览器直接通过 `<script>` 引入时才需要 IIFE 或 UMD。不要为了“兼容所有场景”无脑输出所有格式，格式越多，测试和发布成本越高。

一个实用策略是：先明确谁消费这个包。给现代前端应用使用，通常 ESM 优先；给老 Node 环境使用，再补 CJS；只有明确存在 script 标签直连需求时，才考虑 IIFE 或 UMD。

## Tree Shaking

Rollup 的 tree shaking 会删除未被使用的导出。它依赖 ES 模块的静态结构，因此命名导出通常比动态对象导出更利于摇树。

```javascript
export function used() {}
export function unused() {}
```

如果消费方只导入 `used`，`unused` 有机会被移除。副作用会影响摇树结果，例如模块顶层执行 DOM 操作、注册全局变量、修改原型等。

```javascript
// 有副作用，不能随意移除
console.log('init');
```

库作者应尽量让模块保持纯净，并在 `package.json` 中正确声明 `sideEffects`。

Tree Shaking 的关键不是“工具有没有开”，而是代码结构是否能被静态分析。命名导出、纯函数、无顶层副作用、清晰入口都会让消费方更容易移除无用代码。

库作者如果经常在入口文件里顺手执行注册、打日志、修改全局对象，就会直接削弱摇树效果。Rollup 很擅长分析模块关系，但不会替你修复带副作用的代码结构。

## 外部依赖

库构建通常不应该把 peer dependency 打进产物。例如 Vue 组件库不应把 Vue 打包进去，而应该让使用者项目提供 Vue。

```javascript
export default {
  input: 'src/index.ts',
  external: ['vue'],
  output: {
    file: 'dist/index.mjs',
    format: 'es',
  },
};
```

`external` 能减少产物体积，也避免多个 Vue/React 实例造成运行时问题。应用构建和库构建的依赖处理策略不同，这是 Rollup 配置里最重要的判断之一。

通常 `dependencies` 里的小型运行时工具可以按需打进包里，`peerDependencies` 里的框架、渲染库、状态库应该 external。否则用户项目可能同时存在两份 React 或 Vue，导致上下文、Hooks、响应式实例等出现诡异问题。

external 配置还要和 `package.json` 对齐。声明为 peer 的包通常也应该 external；如果某个包 external 了，但类型、文档和安装说明里没写清楚，使用方会遇到“运行时报错找不到包”的问题。

## 插件系统

Rollup 通过插件处理 TypeScript、CommonJS、Node resolve、JSON、CSS、别名、压缩等能力。

```javascript
import resolve from '@rollup/plugin-node-resolve';
import commonjs from '@rollup/plugin-commonjs';
import terser from '@rollup/plugin-terser';

export default {
  plugins: [
    resolve(),
    commonjs(),
    terser(),
  ],
};
```

插件顺序会影响结果。一般先解析模块，再转换 CommonJS，再处理语言转换和压缩。遇到构建异常时，先缩小插件范围定位是哪一步引入问题。

Rollup 插件也可能参与模块解析、加载、转换和产物生成。插件组合越复杂，越要把职责拆清楚：解析依赖交给 resolve，兼容 CJS 交给 commonjs，语法处理交给 TypeScript 或 Babel，压缩放在最后。

Rollup 配置看起来通常比 Webpack 短，但不代表问题更少。库构建最常见的问题往往是输出格式不匹配、external 漏配、CSS 处理策略不清、声明文件入口不一致。这些都需要在发布前用真实消费项目验证。

## 代码分割

Rollup 支持多入口和动态导入产生代码分割。库项目可以通过多入口保留模块结构，应用项目则常通过动态 `import()` 拆分异步 chunk。

```javascript
export default {
  input: {
    index: 'src/index.ts',
    button: 'src/button.ts',
  },
  output: {
    dir: 'dist',
    format: 'es',
  },
};
```

库项目保留 ESM 模块结构，有利于消费方继续 tree shaking。不要为了“文件少”把所有模块强行打成一个大包。

组件库尤其适合保留模块边界。比如用户只使用 Button，就不应该把 Table、DatePicker、Upload 的实现全部带进去。产物文件多一些不一定是坏事，只要入口、导出和类型声明保持清晰。

多入口输出还适合做子路径导出，例如 `@acme/ui/button`、`@acme/ui/table`。这类产物设计能明显提升消费方的按需引入体验，但前提是入口命名、类型路径和样式路径都保持一致。

## 类型产物

Rollup 本身不专注生成声明文件，TypeScript 库通常需要配合 `tsc` 或声明文件插件生成 `.d.ts`。

```json
{
  "scripts": {
    "build:js": "rollup -c",
    "build:types": "tsc --emitDeclarationOnly"
  }
}
```

类型产物和运行时代码必须保持入口一致，否则用户导入正常但类型报错。这个问题可以和 [[1.5.11 声明文件|声明文件]] 一起理解。

库作者最好把“JS 构建”和“类型构建”分开对待，再在 CI 中同时验证。很多包运行时代码没问题，真正出问题的是类型入口和 exports 配置不一致。

## 构建边界

Rollup 更适合“可复用包”的清晰产物构建；复杂应用开发、开发服务器、HMR、环境变量和 HTML 入口通常交给 Vite 这类上层工具更顺手。

| 场景 | 选择 |
|---|---|
| 组件库 | Rollup / Vite library mode |
| 工具库 | Rollup |
| Web 应用 | Vite |
| 多页面应用 | Vite / Webpack |
| Node SDK | Rollup / tsup |

选择工具时不要只看流行度。库构建关注产物格式和摇树，应用构建关注开发体验、资源处理和部署链路。

如果项目主要目标是发布可复用包，Rollup 往往是很稳的答案；如果主要目标是开发和部署 Web 应用，再硬把 Rollup 当主应用构建器，通常会让团队自己补很多本该由上层工具处理的能力。
