## 源码映射

Source Map 的作用，是把压缩后、合并后、转译后的代码映射回源码，方便调试和定位问题。

```text
源码 -> 构建产物 -> 浏览器调试映射
```

前端生产代码通常会经过 TypeScript、Babel、压缩、Tree Shaking、代码分割等步骤，最终浏览器执行的代码和源码差异很大。没有 Source Map 时，线上报错可能只剩下压缩后的文件名、行号和列号，很难定位到真实业务代码。

Source Map 本质上是一张映射表，记录构建产物里的位置对应源码里的哪个文件、哪一行、哪一列。它不是为了让用户下载源码，而是为了让开发者和监控平台能还原错误位置。

如果项目同时使用 TypeScript、Babel 和压缩器，Source Map 还要保证链路连续。中间某一步没有正确传递 map，最终还原出来的位置就会偏移，表现为“能看到源码文件，但行号不准”。

这也是为什么 Source Map 问题不能只看最后一层工具。TypeScript、Babel、SWC、压缩器、打包器任何一层 map 丢失或偏移，最终结果都会不准。排查时要沿整条构建链路看，而不是只怪监控平台。

## 调试价值

有了 Source Map，线上报错、断点调试和性能分析都更容易对回真实源码。

```text
适合：
1. 生产排查
2. 本地调试
3. 性能分析
4. 远程错误上报
```

线上错误监控通常会把压缩后的堆栈上传到平台，再用对应版本的 Source Map 还原源码位置。这里的关键是“版本对应”：如果产物和 Source Map 不是同一次构建生成的，还原出来的位置就可能完全不准。

调试价值还包括性能分析。浏览器 Performance 面板或监控平台如果能映射回源码，就能知道耗时函数来自哪个模块，而不是只看到压缩后的匿名函数。

Source Map 对线上排查最有价值的地方，是把“用户真实遇到的问题”重新连接到“开发者能修改的源码”。没有这层映射，排查经常会停在压缩文件和不可读堆栈上。

除了错误排查，Source Map 对回归验证也有帮助。升级构建链或压缩器后，如果监控平台突然出现“堆栈无法还原”或“行号明显偏移”，往往说明 map 链路被破坏了。

## 风险边界

Source Map 也会暴露源码结构、接口路径和注释，因此不能无脑公开。

| 风险 | 表现 |
| --- | --- |
| 代码暴露 | 源码结构可见 |
| 路径泄露 | 内部目录和接口名可见 |
| 注释泄露 | 实现细节外泄 |

风险的重点不是 Source Map 本身“不安全”，而是公开方式是否合适。把 `.map` 文件直接放到公开 CDN 上，任何人都可能下载并还原源码结构；上传到受控监控平台，则只有授权人员能用于排查。

如果项目包含敏感算法、内部接口路径、测试开关或注释里的业务信息，生产 Source Map 的访问权限就更要严格控制。

生产环境还要注意 map 文件是否被 CDN 自动同步。如果构建产物上传脚本没有区分 `.js` 和 `.map`，很容易把映射文件一起发布出去。

这也是部署流程要区分“浏览器产物”和“排障资产”的原因。`.js`、`.css` 给用户访问，`.map` 给监控平台或内部排障使用，两者不应该默认走同一公开路径。

## 部署策略

常见做法是把 Source Map 上传到受控平台，而不是直接公开在静态目录里。

```text
策略：
1. 生产保留
2. 受控上传
3. 监控系统使用
4. 不公开散发
```

部署时要保证 Source Map 和产物版本绑定。常见做法是使用 release id、commit hash 或构建号关联产物和 map 文件。这样线上错误发生时，监控平台能找到同一版本的映射文件。

```text
构建产物：app.8f3a2c.js
映射文件：app.8f3a2c.js.map
发布版本：web@2026.07.29-001
```

如果部署时只上传最新 map，旧版本用户仍然访问旧缓存产物时，错误堆栈就可能还原失败。

旧版本 Source Map 保留多久，要和缓存策略、灰度窗口和回滚策略一起定。用户可能因为 CDN、Service Worker 或浏览器缓存继续运行几天前的产物，如果老版本 map 已经被清掉，错误就会失去可读性。

版本绑定最好和发布流程自动化。手动上传 map 很容易漏版本、传错环境或覆盖旧文件；把它放进 CI/CD 流程里，才能保证每次发布都有对应映射。

## 开关选择

| 场景 | 策略 |
| --- | --- |
| 开发环境 | 全量开启 |
| 预发环境 | 开启 |
| 生产环境 | 受控开启 |
| 高敏感项目 | 只内部可见 |

构建工具通常提供不同 Source Map 类型。开发环境适合使用更完整、更快的映射；生产环境则要平衡定位能力、构建速度、体积和泄露风险。不是所有场景都需要完整源码级映射。

```text
开发：更关注断点体验
预发：更关注真实构建还原
生产：更关注受控排查和安全边界
```

Source Map 策略最好成为环境约定的一部分，而不是临时开关。比如开发默认开启、预发默认开启、生产只生成并上传到内部平台，这样团队不会在排障时临时补配置。

## 验证方法

上线后要确认 Source Map 是否真的可用，并且没有被错误暴露给外部用户。真正好的策略，不是“要不要 Source Map”，而是“给谁看、看到什么程度”。

验证可以从两边做：一边制造测试错误，确认监控平台能还原到源码文件和行号；另一边访问线上 `.map` 地址，确认外部用户不能直接下载。如果这两件事都成立，Source Map 策略才算真正可用。

```bash
curl -I https://cdn.example.com/assets/app.js.map
```

如果返回公开可访问的 `200`，就要确认这是否符合预期。多数生产项目更希望 map 文件只在内部平台可见。

验证 Source Map 时不要只看是否生成文件，还要看是否能被实际错误使用。最稳的方式是在预发环境触发一次测试异常，确认监控平台显示源码路径、行号、版本号都正确。

上线后如果错误平台还原失败，排查顺序通常是：当前错误对应的 release 是否正确、该 release 的 map 是否上传成功、产物 hash 是否匹配、map 文件是否被压缩或重写、构建链中是否有某一步丢失了 map 信息。
