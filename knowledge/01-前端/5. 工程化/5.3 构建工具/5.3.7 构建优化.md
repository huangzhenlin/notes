## 优化目标

构建优化要同时关注开发体验、CI 耗时、产物质量和缓存稳定。它不是只追求构建命令更快，也不是只追求产物更小。

```text
开发构建速度
  -> 本地反馈
生产构建速度
  -> CI 成本
产物结构
  -> 加载性能
缓存稳定
  -> 用户体验
```

优化前要先知道瓶颈在哪里：依赖预构建、TypeScript 检查、压缩、source map、图片处理、插件链或单个大包。

构建优化最怕“凭感觉优化”。如果没有构建耗时统计、产物分析和 CI 日志，很容易把时间花在收益很小的地方。先量化，再改动，是构建优化的基本顺序。

优化目标最好拆成两个维度：开发阶段和生产阶段。开发阶段看冷启动、HMR、测试反馈；生产阶段看 CI 耗时、产物体积、缓存稳定和部署速度。两者目标不同，优化手段也不同。

## 依赖预构建

Vite 等工具会在开发阶段预构建依赖，减少浏览器需要处理的模块数量。依赖变化会触发重新预构建。

```typescript
export default defineConfig({
  optimizeDeps: {
    include: ['lodash-es'],
    exclude: ['some-problematic-lib'],
  },
});
```

预构建配置适合解决开发服务启动慢、依赖解析异常、某些包无法被正确处理的问题。不要无脑 include 全部依赖。

依赖预构建的收益主要出现在开发阶段。它能把复杂依赖提前处理成更适合浏览器消费的形式，但如果依赖频繁变化或配置过度，也会导致缓存反复失效。

预构建优化时不要只看“更快”，还要看“更稳”。某些依赖被强行 include 后虽然启动快了一点，但如果热更新、路径解析或 monorepo 链接变得更脆，整体收益未必成立。

## 插件成本

构建插件会影响构建时间。每个插件都可能读取文件、转换代码、生成资源或做额外分析。

| 插件类型 | 可能成本 |
|---|---|
| 转译插件 | CPU |
| 图片压缩 | CPU 和 IO |
| 产物分析 | 额外扫描 |
| 类型检查 | 大量计算 |
| legacy/polyfill | 增加产物和构建时间 |

优化时可以临时关闭插件定位瓶颈。开发环境和生产环境也可以使用不同插件组合。

很多插件只应该出现在生产环境，例如压缩、产物分析、legacy polyfill、图片深度压缩。开发环境如果也全部开启，反馈速度会被明显拖慢。

插件成本最好通过二分法定位：先关掉一半插件看时间变化，再继续缩小范围。大型项目里，真正拖慢构建的往往不是“所有插件都一点点慢”，而是某个插件或某段扫描逻辑异常重。

## 并行与缓存

构建优化离不开缓存。常见缓存包括包管理器缓存、构建工具缓存、任务缓存和 CI 缓存。

```text
依赖缓存
  -> node_modules / pnpm store
构建缓存
  -> vite cache / babel cache
任务缓存
  -> Turborepo / Nx
```

缓存要和输入绑定。配置、锁文件、环境变量变化时，缓存应该失效。错误缓存比没有缓存更糟。

CI 缓存尤其要小心。锁文件、Node 版本、包管理器版本、构建配置、环境变量都可能影响最终结果。如果缓存 key 设计得太粗，构建会快，但产物可能不可信。

缓存不是越多越好。缓存命中要建立在输入一致的前提下，否则“快但错”比“慢但对”更危险。构建优化里，可靠性永远比局部加速更重要。

## 类型检查拆分

生产构建可以把类型检查和转译拆开。构建工具负责快速出产物，`tsc` 或 `vue-tsc` 在独立任务中做类型检查。

```json
{
  "scripts": {
    "build": "vite build",
    "typecheck": "vue-tsc --noEmit"
  }
}
```

这样能让职责更清晰，也方便 CI 并行执行。不能因为构建能过，就认为类型一定没问题。

在 Vite、Rspack、esbuild 这类快构建链路里，类型检查拆分非常常见。推荐把 `build`、`typecheck`、`lint` 分成独立任务，再由 CI 并行执行并统一收口。

拆分以后也要保证本地和 CI 有统一入口。比如本地可以单跑 `typecheck`，CI 则跑 `verify` 聚合。否则任务拆开后，团队反而更容易漏掉某一步。

## source map 策略

source map 有助于线上排查，但会增加构建时间和产物管理成本。

```typescript
export default defineConfig({
  build: {
    sourcemap: true,
  },
});
```

生产 source map 是否公开，要看安全策略。常见做法是上传到监控平台，不直接暴露到公网。

source map 的选择要同时看排障价值和信息泄露风险。内部系统可以更开放，公网项目则更适合上传到错误监控平台，并限制外部访问。

Source Map 还会显著影响构建时间和上传体积。对大型项目来说，全量生产 map 可能需要明显更长的构建与发布时间，所以要把排障收益和发布成本一起算。

## 压缩策略

压缩能减少产物体积，但也会增加构建时间。现代工具常用 esbuild、terser、swc 等压缩器。

```typescript
export default defineConfig({
  build: {
    minify: 'esbuild',
  },
});
```

如果需要更强的压缩效果，可以评估 terser；如果更关注速度，esbuild 往往更合适。选择要基于构建耗时和产物体积对比。

压缩也有边界。为了减少极少量体积而显著增加 CI 时间，通常不划算。更有效的体积优化往往来自依赖替换、按需加载和减少无用代码，而不是无限调压缩参数。

压缩策略最好用真实数据比较。比如 esbuild 压缩和 terser 压缩分别耗时多少、gzip 后体积差多少、首屏和缓存是否真的改善。没有对比数据，很容易在“感觉更专业”的压缩配置上投入过多。

## 产物优化

构建优化最终要体现在产物结构上：合理 chunk、稳定 hash、按需加载、去除重复依赖和控制 polyfill。

| 目标 | 手段 |
|---|---|
| 首屏小 | 代码分割 |
| 缓存稳 | chunk 策略 |
| 依赖少 | 依赖分析 |
| 兼容准 | polyfill 策略 |

构建优化和 [[6.4.1 包体积分析|包体积分析]]、[[6.4.4 Chunk 拆分|Chunk 拆分]] 是连续流程：先分析，再拆分，再验证。

构建优化完成后要看两个结果：开发和 CI 是否真的更快，线上加载是否真的更稳。前者看构建耗时和缓存命中，后者看产物体积、chunk 命中率、LCP、JS 执行时间和错误率。

优化后的结果最好沉淀成基线。比如记录一次构建耗时、首屏 JS 体积、关键页面 chunk 数量、CI 总时长。没有基线，下一次性能回退时就很难判断是从什么时候开始变差的。
