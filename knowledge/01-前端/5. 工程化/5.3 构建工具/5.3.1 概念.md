## 构建本质

构建工具的核心任务，是把源码变成“更适合交付给浏览器、App 容器或静态托管平台”的产物。它不只做打包，还会处理依赖图、语法转换、资源引用、压缩拆分、注入环境变量和产物分析。

```text
源码
  -> 解析依赖图
  -> 转换语法与资源
  -> 生成 chunk / bundle
  -> 输出可部署产物
```

构建的结果通常不是“更少的代码”，而是“更可控的交付形态”。同一份源码，经过不同构建策略，可能产出面向开发、测试、预发和生产的不同版本。

构建工具的价值还体现在“把杂事收口”。资源引用、环境变量、代码分割、CSS 提取、图片处理、压缩、分析这些工作如果都散在业务代码里，后期就会很难维护。构建层把这些事情统一处理，业务层才能专注写功能。

构建工具真正解决的是“交付约束”。浏览器只认识有限的运行时能力，而业务代码往往用了 TypeScript、JSX、CSS Module、SVG 组件化、环境变量和按需加载。构建层把这些开发期语法和资源组织成浏览器能接收的结果。

## 入口与输出

构建流程通常从入口开始，再把依赖一路递归拉平。入口决定从哪里开始看，输出决定最后把什么交给浏览器。

```text
Entry -> Dependency Graph -> Bundle / Chunk -> Output
```

单页应用常用一个主入口，再通过路由动态导入拆出异步 chunk；多页应用可能有多个入口，每个入口对应一个 HTML 页面。入口太粗会导致首屏加载太多无关代码，入口太碎又会增加公共依赖抽取和缓存管理成本。

输出不只是文件目录。它还包括文件名规则、资源公共路径、hash 策略、chunk 命名和静态资源引用方式。很多构建问题本质上都能回到入口和输出配置是否清楚。

一个常见判断方式是：如果页面打开后，第一屏就要用到的代码越多，入口就越应该精细拆分；如果多个页面共享大量基础能力，公共依赖就要抽出来，避免每个入口重复打包。构建层的“入口”和“输出”不是文档术语，而是直接影响首构速度、缓存命中和部署回滚的真实配置项。

入口和输出还会影响监控和回滚。比如输出文件名里带 hash 更利于 CDN 长缓存，但也要求 HTML 入口始终指向最新资源；多入口应用则要确认每个入口的公共依赖是否稳定，不然一次小改动也会让所有页面 chunk 一起失效。

## 转换能力

构建工具常常和转译工具一起工作，但职责不同。构建工具更关注资源组织，转译工具更关注语法降级和兼容处理。

| 能力 | 例子 |
| --- | --- |
| 模块解析 | `import`、`require`、动态导入 |
| 语法转换 | TS、JSX、ESNext |
| 资源处理 | CSS、图片、字体、SVG |
| 优化输出 | 压缩、分包、Tree Shaking、缓存 |

这些能力经常被打包在一起，但它们解决的问题不一样。资源处理解决“文件怎么进来”，优化解决“文件怎么出去”，开发体验解决“人怎么高效改代码”。

这也是为什么构建配置常常看起来“不是一件事”。同一个配置文件里，既有路径别名，也有 CSS 处理，也有产物拆分，因为构建工具就是在做一系列相连但职责不同的工作。

## 开发体验

现代构建工具通常还负责开发服务器、热更新和预览体验。

```text
开发阶段：
1. 快速启动
2. 按需编译
3. 热更新
4. 错误定位
5. 本地代理
```

开发体验越好，前端团队的反馈回路就越短。Vite 这类工具利用浏览器原生 ESM 提升开发启动速度，Webpack 这类工具则依靠成熟的 loader、plugin 和 HMR 机制支撑复杂项目。

开发态和生产态不能混为一谈。开发阶段追求快反馈，生产阶段追求稳定、体积、缓存和兼容。一个工具开发时快，不代表生产产物一定好；一个工具生产能力强，也不代表团队每天开发会舒服。

如果团队经常遇到“改一行等半天”，通常是开发侧优化没跟上；如果线上经常出现缓存污染、旧包残留、回滚困难，通常是生产产物和发布策略没设计好。构建工具的价值就在于把这两个问题分别处理，而不是只盯住其中一边。

构建工具也决定了工程边界是否清晰。比如是否支持多入口、是否方便注入环境变量、是否能配合 SSR、是否容易做产物分析，这些都会影响团队后续怎么组织项目。

```text
工程里最常见的构建判断：
1. 开发是否快
2. 生产是否稳
3. 插件是否够用
4. 迁移是否可控
```

开发体验也要和团队规模结合看。个人项目更在意“开箱就跑”，团队项目更在意“约定统一、错误可复现、CI 能对齐”。同一个构建工具，在不同团队里的价值点不完全一样。

## 产物职责

构建后的产物通常会同时承担浏览器兼容、缓存友好、资源拆分和部署适配责任。

```text
产物要解决：
1. 浏览器能执行
2. 资源能缓存
3. 路由能按需加载
4. 错误能定位
5. 部署能回滚
```

生产产物里常见的 `assets/app.[hash].js`、`assets/style.[hash].css`，本质上是在服务缓存策略。hash 文件可以长缓存，入口 HTML 则保持短缓存或协商缓存。

除了文件名，构建产物还经常承担“环境隔离”的职责。比如测试环境、预发环境和生产环境可能会注入不同的接口地址、埋点开关、日志级别和功能开关。这些都不是业务代码本身写死的，而是交给构建阶段去决定。

产物职责还包括部署适配。例如单页应用部署到子路径下时，需要正确处理静态资源前缀；多页应用部署到 CDN 时，需要保证 HTML 和资源版本对应；SSR 应用则要同时考虑客户端产物和服务端产物的匹配。

## 选型视角

| 视角 | 更关注 |
| --- | --- |
| 开发体验 | 启动速度、热更新 |
| 生产优化 | 包体积、分包、缓存 |
| 多页站点 | 入口管理、资源复用 |
| 单页应用 | 按需加载、动态路由 |
| 组件库 | 输出格式、Tree Shaking、类型声明 |

工具不是越新越好，也不是越强越好。选型时更重要的是团队熟悉度、已有生态、插件支持和迁移成本。

如果是新项目，通常可以优先考虑开发体验更好的工具；如果是老项目，往往先看现有 loader、plugin、微前端方案和构建约定能不能延续。很多选型失败，不是工具不行，而是忽略了项目本身已经沉淀下来的工程边界。

选型时最好把“迁移成本”和“长期收益”一起算。一个新工具也许能把开发速度提升很多，但如果项目现有插件链、微前端容器、历史模板和构建约定全都要重写，收益未必能覆盖成本。构建工具不是越新越好，而是越适配项目当前阶段越好。
