## 工具定位

Webpack 是经典的模块打包工具，核心能力是从入口出发构建依赖图，把 JavaScript、CSS、图片、字体等资源都视为模块，再通过 Loader 和 Plugin 完成转换与扩展。

Webpack 的优势是生态成熟、可定制能力强、适合复杂构建链路。它的缺点是配置和性能优化成本较高，尤其在大型项目中需要更细的缓存、并行和拆包策略。

Webpack 更像一套可编程的构建平台，而不只是一个打包命令。它适合处理“项目很复杂，但每一步都想控制”的场景，例如多入口、多端产物、微前端、老项目迁移、复杂静态资源处理和深度定制发布链路。

Webpack 的价值通常不是“默认最快”，而是“边界最可塑”。当项目历史长、插件多、遗留格式多、资源处理复杂时，它往往比更轻的工具更容易把老约定继续接住。

## 核心概念

#### Entry

Entry 是构建入口，Webpack 从这里开始分析依赖。

```js
export default {
  entry: "./src/main.ts",
};
```

多入口适合多页面应用或需要生成多个独立 bundle 的项目。

入口设计会影响首屏体积和缓存复用。一个入口过大，所有页面都会背上公共成本；入口过多，又可能让公共依赖重复进入多个包。多页项目通常要配合 `splitChunks` 抽取共享依赖。

多入口项目里，还要考虑 HTML 模板、公共资源和运行时脚本如何分配。Webpack 灵活的同时，也意味着入口设计一旦失控，后期排查“为什么这个页面带了不该带的代码”会很痛苦。

#### Output

Output 控制产物输出位置、文件名和资源路径。

```js
export default {
  output: {
    path: new URL("./dist", import.meta.url).pathname,
    filename: "[name].[contenthash].js",
    clean: true,
  },
};
```

生产环境通常使用 `contenthash` 配合 CDN 缓存。

`publicPath` 也很关键，它决定运行时资源从哪里加载。静态资源部署到 CDN、子路径部署、微前端动态加载时，`publicPath` 配错会直接导致 chunk 404。

#### Module

Module 表示被依赖图管理的模块。Webpack 原生理解 JavaScript 和 JSON，其他资源通常通过 Loader 转换。

在 Webpack 的心智里，CSS、图片、字体都可以成为模块。这也是为什么可以在 JavaScript 中 `import "./style.css"` 或 `import logo from "./logo.png"`，因为它们都会进入统一的依赖图。

#### Chunk

Chunk 是代码分割后的构建单元。一个入口会形成初始 chunk，动态导入会形成异步 chunk。

```js
import("./admin").then((mod) => mod.mount());
```

动态导入会让 Webpack 生成异步 chunk。用户真正进入对应功能时才加载这部分代码，常用于后台页面、弹窗编辑器、图表面板和低频业务流。

#### Dependency Graph

依赖图描述模块之间的引用关系。Webpack 的很多优化，如 Tree Shaking、代码分割、缓存命中，都依赖对依赖图的分析。

依赖图越清晰，优化越有效。循环依赖、隐式全局副作用、动态拼接路径和过度聚合导出，都会让优化空间变小。

Webpack 对依赖图的掌控很强，但前提是代码结构愿意配合。很多“Webpack 优化没效果”的根因并不是配置少了一行，而是代码本身充满动态行为，工具很难静态分析。

## Loader

#### 执行顺序

Loader 用于把非标准或需要处理的资源转换成模块。多个 Loader 从右到左、从下到上执行。

```js
export default {
  module: {
    rules: [
      {
        test: /\.scss$/,
        use: ["style-loader", "css-loader", "sass-loader"],
      },
    ],
  },
};
```

这里先执行 `sass-loader`，再执行 `css-loader`，最后执行 `style-loader`。

Loader 本质上是“把一种资源转换成 Webpack 能继续处理的模块”。如果某个文件无法被识别，通常不是 Webpack 不支持，而是缺少对应 loader 或 loader 配置范围不正确。

这也是 Webpack 容易变复杂的地方。每多一种资源处理方式，就可能多一条 loader 链；loader 链一长，构建速度、缓存命中和调试复杂度都会上升。所以 loader 配置应该尽量只命中真正需要处理的目录和文件。

#### Pitch 阶段

Loader 有 pitch 阶段和 normal 阶段。pitch 阶段从左到右执行，normal 阶段从右到左执行。大多数日常使用不需要写 pitch，但理解它有助于看懂复杂 Loader。

#### Normal 阶段

Normal 阶段负责真正转换资源内容。比如把 Sass 转成 CSS，把 TypeScript 转成 JavaScript，把图片转成资源引用。

日常业务开发更常遇到 normal 阶段，因为大多数 loader 都是在这里处理资源。排查 loader 问题时，可以先确认匹配规则、执行顺序、输入输出和是否命中缓存。

#### Loader Context

Loader 可以通过上下文访问文件路径、配置、依赖收集、产物输出等能力。自定义 Loader 时要避免引入不可缓存的隐式状态。

## Plugin

#### Tapable

Webpack 插件基于 Tapable 事件机制。构建过程中会暴露大量 Hook，插件通过注册 Hook 参与流程。

如果说 Loader 处理“某个文件怎么变”，Plugin 处理的就是“整个构建过程怎么运转”。HTML 生成、CSS 提取、资源复制、产物分析、环境变量注入都更适合交给 Plugin。

#### Compiler

Compiler 表示一次完整的 Webpack 配置和构建环境。插件通常在 `apply(compiler)` 中注册逻辑。

```js
class DemoPlugin {
  apply(compiler) {
    compiler.hooks.done.tap("DemoPlugin", () => {
      console.log("build done");
    });
  }
}
```

自定义插件要特别注意副作用范围。插件能改构建全局状态，能力强，也更容易制造难排查的问题。

#### Compilation

Compilation 表示一次具体构建过程，包含模块、chunk、asset 等信息。增量构建中，一个 Compiler 可能对应多次 Compilation。

理解 Compiler 和 Compilation 的区别，有助于看懂插件为什么有些逻辑只执行一次，有些逻辑每次增量构建都会执行。

#### 生命周期

Plugin 适合做构建流程级能力，例如生成 HTML、提取 CSS、复制静态资源、注入环境变量、分析产物、压缩资源。它和 Loader 的区别是：Loader 处理单个模块，Plugin 参与整个构建流程。

## 性能优化

#### 构建速度

构建速度优化包括缓存、缩小处理范围、减少 Loader 成本、并行处理、升级工具链。

大型项目里，构建慢通常不是单点问题，而是 loader 链过长、类型检查阻塞、source map 过重、插件重复扫描、缓存没有命中叠加在一起。优化前最好先用 profile 或构建分析工具定位瓶颈。

```text
只处理 src
开启 filesystem cache
避免重复 Babel 转译 node_modules
减少不必要插件
```

#### 产物体积

产物体积优化包括 Tree Shaking、代码分割、依赖替换、图片压缩、移除调试代码。

体积优化要防止“看起来拆了，实际更慢”。如果拆出太多小 chunk，用户可能面对更多请求和运行时调度成本。拆包应该围绕访问路径、缓存稳定性和首屏关键资源来设计。

Webpack 优化最容易变成“配置越来越多，但没人知道为什么”。如果项目已经有十几处 `optimization`、`cacheGroups`、自定义 runtime chunk 策略，最好配套构建报告和说明，否则下一次改动会非常危险。

#### 缓存策略

Webpack 5 支持持久化缓存，可以显著提升二次构建速度。

```js
export default {
  cache: {
    type: "filesystem",
  },
};
```

#### 代码分割

代码分割可以通过动态导入和 `optimization.splitChunks` 实现。拆包目标是减少首屏体积、提升缓存复用，而不是盲目拆得越细越好。

```js
export default {
  optimization: {
    splitChunks: {
      chunks: "all",
      cacheGroups: {
        vendors: {
          test: /[\\/]node_modules[\\/]/,
          name: "vendors",
          priority: -10,
        },
      },
    },
  },
};
```

这类配置要结合产物分析一起看。拆包后如果公共依赖频繁变化，反而会降低缓存命中率。

Webpack 在复杂项目里仍然很强，但也意味着团队要愿意维护更重的构建认知。如果项目并不需要这些高自由度，Vite 或更轻的方案通常会更省心。
