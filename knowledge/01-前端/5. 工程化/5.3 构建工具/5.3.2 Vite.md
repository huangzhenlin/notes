## 开发机制

Vite 的核心特点是开发时更快。它利用浏览器原生 ESM 和按需编译，减少了传统打包器在开发阶段的预打包成本。

```text
开发模式：
浏览器请求模块
  -> Vite 只处理当前需要的文件
  -> 按需转换并返回
```

这和传统“先整体打包再启动”的模式差别很大。传统方案在开发时往往要先做一轮完整构建，项目越大，等待越明显；Vite 的思路更接近“按请求工作”，所以更适合模块化程度高、改动频繁的前端项目。

它快的前提是浏览器能够直接处理原生 ESM，或者至少可以接受开发阶段的按需转换。换句话说，Vite 的快不是凭空来的，而是把很多原来提前做的工作后移了。

这个机制决定了 Vite 的开发体验和项目结构有强关联。模块拆分越清晰、依赖越现代化，Vite 的体验通常越好；如果项目里大量依赖旧式 CommonJS、特殊 loader 或非常重的历史插件，优势会被打折。

Vite 的优势通常首先体现在开发阶段，而不是生产构建阶段。很多团队感受到的“Vite 很快”，本质上是 dev server、HMR 和依赖预构建更轻；真正上线后的 chunk 结构、缓存策略和部署行为，仍然要认真配置和验证。

## 预构建

Vite 会对依赖做预构建，减少大量小模块带来的请求和解析成本。

```text
预构建目的：
1. 提升冷启动
2. 兼容 CJS 依赖
3. 减少重复处理
```

预构建主要针对第三方依赖。很多包的发布形态并不适合直接让浏览器逐个请求源文件，预构建可以把它们整理成更少的请求、更稳定的入口和更快的开发启动。

当依赖包更新频繁或者存在解析异常时，预构建配置也会影响开发体验。`include` 和 `exclude` 不是“越多越好”，而是用来修正实际问题的。

预构建也会影响调试和依赖兼容。某些依赖如果导入方式混乱，开发阶段可能会出现重复请求、循环依赖或无法热更新的问题，这时就需要通过 `optimizeDeps.include` / `optimizeDeps.exclude` 精细调节，而不是盲目关闭预构建。

遇到“某个依赖开发模式能跑但热更新异常”时，优先检查它是否被正确预构建、是否同时存在 ESM 和 CJS 入口、是否在 monorepo 里被链接成本地包。很多 Vite 问题最后都能回到依赖解析和预构建边界。

## 配置入口

Vite 配置通常围绕入口、别名、插件和构建输出。

```ts
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [],
});
```

这个配置只是入口骨架，实际项目里通常还会继续补别名、代理、端口、构建产物目录、环境变量和插件顺序。Vite 配置的好坏，很多时候会直接决定团队的调试效率。

```ts
export default defineConfig({
  resolve: {
    alias: {
      "@": "/src",
    },
  },
  server: {
    proxy: {
      "/api": "http://localhost:3000",
    },
  },
});
```

这类配置看似简单，但如果没有统一约定，团队里不同项目会出现路径写法不一致、代理分散、插件顺序混乱等问题。

Vite 配置最好集中表达常见工程约定：别名、代理、端口、环境变量暴露规则、构建目录、基础路径。这样项目一多时，不需要每次从头摸索一遍。

## 插件体系

插件是 Vite 扩展能力的主要方式。常见用途包括 React / Vue 支持、路径别名、SVG 处理和打包优化。

```text
插件可处理：
1. 转换源码
2. 注入配置
3. 改写产物
4. 扩展开发体验
```

Vite 插件通常沿用 Rollup 的插件思路，既能参与开发阶段，也能参与生产构建。React、Vue、SVG、路径别名、HTML 注入这些能力，都可以通过插件串起来。

插件数量一多，问题定位就会变复杂，所以遇到 HMR 异常、构建慢、产物不对时，先排插件链是很有效的思路。

插件体系的价值在于可组合，但也带来“谁先谁后”的问题。很多 Vite 异常本质上不是插件坏了，而是插件顺序、处理范围或与框架插件的协作方式不对。遇到问题时，先简化插件列表通常比盲调配置更高效。

插件越多，越要控制职责。React/Vue 官方插件负责框架语法，SVG 插件负责资源转换，路径插件负责解析，分析插件负责构建报告。一个插件同时承担太多事情，后期定位问题会很痛苦。

## 构建输出

生产构建时，Vite 会把源码输出成静态资源，并结合 Rollup 完成分块和优化。

```bash
vite build
```

构建阶段更关注产物体积、chunk 划分、静态资源引用和浏览器兼容，而不是开发时那种极速响应。

在生产构建里，Vite 仍然要处理代码分割、资源指纹、静态资源复制、CSS 提取和 sourcemap 这些事情。开发快不代表生产就简单，真正上线时还是要看 chunk 是否稳定、资源路径是否正确、CDN 是否能正确缓存。

生产构建还要看部署路径。如果应用不是部署在域名根路径下，就要正确设置 `base`，否则静态资源引用、路由刷新和懒加载 chunk 都可能出问题。

```ts
export default defineConfig({
  base: "/admin/",
});
```

这个配置在本地可能感知不强，但一旦部署到子路径或 CDN 前缀下，立刻会影响静态资源是否 404。

## 适用场景

| 场景 | 适合程度 |
| --- | --- |
| 单页应用 | 很适合 |
| 中型项目 | 很适合 |
| 组件库 | 也适合 |
| 极复杂传统多页历史工程 | 视情况 |

Vite 最强的是“开发快、配置轻、生态成熟”。如果项目已经有重度定制链路，迁移时要评估插件兼容和构建约束。

它特别适合现代 SPA、管理后台、组件库和中型业务项目。对于大量依赖 Webpack loader/plugin、复杂多页模板、模块联邦或历史包袱很重的工程，迁移前最好先做最小原型验证。

最值得先验证的通常不是页面能不能打开，而是开发服务、生产构建、路由刷新、环境变量和部署路径这几件事能不能对齐。很多迁移问题，都是在这些地方暴露的。

Vite 迁移老项目时，最常见的难点通常不是主框架，而是历史插件链、CommonJS 依赖、路径注入方式、全局样式处理、构建后资源路径以及某些只在 Webpack 下成立的 loader 约定。样板页验证时最好把这些都放进去，而不是只启动一个空首页。

如果项目需要做组件库或多应用复用，还要额外验证库的输出格式、CSS 注入、externals 和类型产物。Vite 很适合现代项目，但并不意味着所有构建诉求都可以无脑照搬默认模板。
