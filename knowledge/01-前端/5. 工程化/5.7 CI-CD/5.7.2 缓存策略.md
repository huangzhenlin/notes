## 缓存目标

CI 缓存的目标是减少重复下载、重复构建和重复计算。常见缓存对象包括依赖、构建产物、测试缓存、任务缓存。

```txt
依赖缓存 -> 减少 install 时间
构建缓存 -> 减少 build 时间
测试缓存 -> 减少 test 时间
工具缓存 -> 减少环境准备时间
```

缓存不是越多越好。错误缓存会导致构建不稳定、测试误判和线上产物污染。

CI 缓存的核心不是“能缓存就缓存”，而是“缓存命中后结果仍然可信”。任何会影响输出的输入，都应该参与缓存 key 或任务输入声明。

缓存策略应该从最确定的对象开始，比如包管理器缓存和构建工具明确声明的输出。对依赖外部服务、时间、随机数据或本机状态的任务，不要轻易缓存结果。

缓存越深入流程，收益和风险通常都会一起变大。依赖缓存相对容易控，构建缓存需要更强的输入声明，测试缓存则必须非常清楚哪些结果真的可重复。

## 依赖缓存

依赖缓存通常根据 lockfile 生成 key。

```yaml
key: pnpm-${{ hashFiles('pnpm-lock.yaml') }}
```

lockfile 变化说明依赖图变化，缓存应该更新。不要只用分支名作为依赖缓存 key，否则依赖升级后可能继续使用旧缓存。

依赖缓存还要考虑 Node 版本和包管理器版本。相同 lockfile 在不同 Node 或 pnpm 版本下，安装结果也可能不同。

依赖缓存命中后仍然要执行安装命令。缓存只提供加速，不应该替代包管理器根据 lockfile 校正依赖。跳过安装看似更快，但会让依赖状态变得不可验证。

依赖缓存更像“提前把材料运到现场”，不是“直接假定工程已经完工”。只要最终安装步骤还在，lockfile 和包管理器才能把状态校正回可信结果。

## node_modules

是否缓存 `node_modules` 要看包管理器和 CI 环境。pnpm 更常见的是缓存 pnpm store。

```yaml
- name: Get pnpm store path
  run: pnpm store path
```

直接缓存 `node_modules` 可能体积大、跨平台不稳定、容易受 postinstall 影响。缓存包管理器 store 通常更稳。

pnpm 的 store 可复用性更好，`node_modules` 则包含项目链接结构和平台相关产物。跨操作系统或跨 Node 版本复用 `node_modules`，更容易出现隐蔽问题。

如果缓存 `node_modules`，要确认 CI 机器系统、Node 版本、包管理器版本和原生依赖编译环境稳定一致。否则某些 native package 可能在缓存恢复后才暴露问题。

一般来说，越依赖原生模块、postinstall 脚本和平台差异，越不适合粗暴缓存 `node_modules`。这类项目更应该优先缓存包管理器的底层 store。

## 构建缓存

构建缓存需要考虑输入文件、环境变量、依赖版本和构建配置。

```txt
源码
lockfile
tsconfig
vite/webpack 配置
环境变量
Node 版本
```

如果某个输入没有进入缓存 key，可能出现“源码变了但复用旧产物”的问题。任务缓存工具通常会自动建模这些输入，但仍要配置好边界。

构建缓存尤其要关注环境变量。前端构建经常把 `VITE_*`、`NEXT_PUBLIC_*` 这类变量注入产物，如果缓存没有感知变量变化，就可能发布出错误环境的包。

构建缓存最好配合产物校验。缓存命中后仍要确认入口 HTML、chunk、环境标识和 release 信息正确，避免把旧环境的产物带到新环境。

这也是为什么构建缓存不能只看源码目录。很多“我明明改了配置，为什么构建没变”的问题，根因都是环境变量、构建配置或上游输入没有进入缓存判断。

## Monorepo 缓存

Monorepo 中常使用 Turborepo、Nx 等工具做任务缓存。

```json
{
  "tasks": {
    "build": {
      "outputs": ["dist/**"]
    },
    "test": {
      "outputs": ["coverage/**"]
    }
  }
}
```

每个任务要声明输入和输出。没有输出的任务无法有效缓存；输出声明过宽会缓存不该缓存的文件。

任务缓存适合可重复、输入输出明确的任务，例如 build、test、lint。对于依赖真实外部服务、时间或随机数据的任务，要谨慎缓存。

Monorepo 缓存还要看包依赖图。修改底层工具包时，依赖它的上层应用也应重新执行相关任务。只看当前包文件变化，可能会漏掉跨包影响。

跨包缓存最难的地方在于“影响面不是平铺的”。一个底层包看似只改了几行工具代码，实际上可能影响多个应用和组件库的构建、测试和类型检查。

## 缓存恢复

CI 通常支持 restore key，用于找相近缓存。

```yaml
restore-keys: |
  pnpm-
```

恢复相近缓存能提高命中率，但要确保后续 install 会校正依赖。缓存命中不是跳过校验的理由。

restore key 更像“拿一个接近的起点”，不是最终可信状态。依赖安装命令仍然必须执行，让包管理器根据 lockfile 修正差异。

restore key 适合依赖下载这类可修正缓存，不适合构建产物这类强一致输出。构建产物一旦错用相近缓存，就可能让 CI 通过但线上实际运行的是旧代码。

因此 restore key 更像“保守加速器”，不是“广义兜底逻辑”。能修正的缓存可以模糊匹配，不能修正的缓存最好严格命中，否则宁可重新生成。

## 失效策略

缓存失效要可控。

| 缓存 | 失效依据 |
| --- | --- |
| 依赖 | lockfile、Node 版本 |
| 构建 | 源码、配置、环境变量 |
| 测试 | 源码、测试配置 |
| 浏览器二进制 | 工具版本 |
| Docker 层 | Dockerfile、依赖文件 |

缓存 key 太宽会命中旧结果，太窄会几乎不命中。要按“哪些输入影响输出”来设计。

缓存策略可以先保守再优化。先保证正确，再逐步扩大命中率，比一开始追求极致速度更安全。

缓存失效规则要能被人理解。一个缓存如果只有少数人知道为什么命中或失效，出现问题时就会很难排查。清晰的 key 命名和日志输出能减少很多猜测。

一个实用的做法，是在 CI 日志里明确打印缓存 key、命中状态和关键输入。这样当构建结果异常时，团队至少能先判断问题是不是来自缓存复用。

## 安全边界

不要缓存敏感信息。

```txt
不要缓存 .env.production
不要缓存私钥
不要缓存登录态
不要把 token 写入构建产物缓存
```

开源仓库、fork PR、多人协作环境尤其要注意缓存污染和凭证泄漏。缓存目录应只包含可重复生成的文件。

如果缓存里混入 token、私有配置或生产环境变量，泄漏风险会非常高。缓存目录应该像构建产物一样可重建、可丢弃、可审查。

缓存清理也要有策略。依赖缓存和构建缓存长期不清理，会占用大量存储；但清理太激进，又会让 CI 频繁冷启动。合理做法是按分支、时间和重要性设置保留周期。

判断缓存策略是否健康，可以看这些现象：

| 现象 | 可能说明 |
| --- | --- |
| 命中率高且结果稳定 | 缓存边界较合理 |
| 偶发出现“清缓存就好了” | 输入声明可能不完整 |
| 冷启动过慢 | 基础缓存还可以优化 |
| 缓存目录巨大且难以解释 | 清理策略不足 |
