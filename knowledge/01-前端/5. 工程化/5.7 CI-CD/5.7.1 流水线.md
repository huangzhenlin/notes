## 流程目标

流水线的目标是把代码从提交到交付的关键步骤自动化，让质量检查、构建产物、部署发布和回滚路径都可重复、可追踪。

流水线本质上是在把“人工上线经验”固化成可执行流程。它最重要的不是命令多，而是每一步都有明确输入、输出和失败责任。

```text
代码提交
  -> 安装依赖
  -> 质量检查
  -> 测试
  -> 构建
  -> 产物上传
  -> 部署
  -> 验证
```

流水线不是为了“跑一堆命令”，而是为了让每次变更都有一致的验证路径。

如果流程设计得好，同一个变更在本地、预发和生产会走相似的检查路径，减少“本地没问题，线上出事故”的概率。

流水线设计时最重要的是把“快反馈”和“高可信”分开。PR 阶段应该尽快拦住明显问题，发布阶段则要更完整地验证产物、环境和回滚能力。把所有检查都塞进一个阶段，既慢又难维护。

一个健康的流水线，不是“所有事都自动化”，而是“该自动化的路径稳定自动化，不该自动化的高风险步骤有清楚的人工边界”。这样既能减少机械劳动，也不会把高风险动作藏进无人理解的脚本里。

## 触发条件

流水线可以由 push、pull request、tag、手动按钮、定时任务或上游流水线触发。

| 触发方式 | 适合场景 |
| --- | --- |
| Pull Request | 代码合并前验证 |
| Push | 分支提交后验证 |
| Tag | 版本发布 |
| Manual | 灰度、回滚、补发 |
| Schedule | 定期扫描、依赖检查 |

触发条件要和风险匹配。PR 阶段适合跑快速检查，发布阶段才需要完整构建和部署。

触发方式不同，适合承载的任务也不同。PR 阶段更关注反馈速度，tag 和 manual 更适合发版、回滚和补发，定时任务则适合依赖扫描、过期检查和环境巡检。

触发条件还可以和分支策略结合。比如主分支只允许受控发布，特性分支只做校验，tag 只做正式发版。这样能避免“任何分支都能触发生产部署”的风险。

触发条件最好还能体现环境意图。比如同样是 `main` 分支，有的仓库只允许部署预发，有的则通过 tag 才能进生产。把“什么代码能去哪一层环境”写进规则里，会比靠口头约定稳得多。

## 阶段拆分

流水线阶段应按职责拆分，而不是把所有命令写进一个巨大 job。

```text
install -> lint -> typecheck -> test -> build -> deploy
```

阶段拆开后，失败位置更清楚，也更容易做缓存和并行。

如果所有命令都堆在一个 job 里，失败后很难知道是 lint、测试还是构建出了问题。拆分阶段后，日志、缓存和重试都更容易做。

阶段拆分还便于并行。比如 lint、typecheck、unit test 可以并行跑，构建则放在它们之后。只要阶段边界清楚，流水线就能在速度和可定位性之间找到更好的平衡。

阶段拆分还有助于复用。很多仓库最后都会形成“校验模板”“构建模板”“部署模板”这类可复用 job，如果一开始就把所有逻辑糊在一起，后续抽象和迁移成本会很高。

## 任务依赖

任务之间要表达依赖关系。构建依赖安装和检查，部署依赖构建产物，发布依赖环境审批。

```yaml
jobs:
  build:
    needs: [lint, test]
  deploy:
    needs: [build]
```

依赖关系越明确，流水线越容易维护。不要让部署任务在质量检查失败时仍然运行。

任务依赖还能避免重复耗时。比如构建前先做安装和校验，部署前先保证构建产物存在，发布前再做环境审批，这样流程就不会互相踩踏。

依赖关系最好写成显式配置，而不是靠执行顺序“碰运气”。一旦任务被拆到不同 job、不同 worker 或不同流水线，显式依赖才是保证流程正确的唯一方式。

显式依赖还能帮助控制失败传播。比如部署只依赖构建和必要验证，不应该因为某个低价值报告任务失败而被阻塞；反过来，核心测试失败时，也绝不能让部署继续往前。

## 质量门禁

质量门禁通常包括 lint、类型检查、单元测试、组件测试、E2E、构建验证和安全扫描。

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

门禁要分层：本地 hooks 跑快任务，PR 跑核心检查，发布前跑完整验证。

不同层级承担不同风险。本地负责拦最便宜的错误，PR 负责阻止明显质量下降，发布前负责兜住真实交付风险。

门禁最好和失败策略一起设计。哪些失败允许重试，哪些失败必须人工处理，哪些失败会直接阻止发布，这些规则越清楚，团队越不容易在流水线失败后乱猜。

门禁本质上是在做风险分层。语法错误、类型错误、核心测试失败这类问题应该直接阻断；网络抖动、缓存拉取失败、偶发第三方扫描超时这类问题，则可以设计有限重试或降级策略。

## 缓存策略

流水线缓存可以显著减少耗时，但必须和输入绑定。

```text
缓存输入：
1. lockfile
2. package manager version
3. build config
4. environment variables
```

错误缓存比没有缓存更糟。锁文件、构建配置、环境变量变化时，缓存应该失效。

流水线缓存适合加速依赖安装、构建中间产物和任务重复执行，但前提是输入稳定。缓存键如果设计不准确，可能让错误产物被重复复用。

缓存命中率不是唯一指标。错误命中会比低命中更危险，所以缓存策略应先保证正确，再逐步提升命中率。构建工具、依赖版本、环境变量和源码变动都应该进入缓存判断。

很多 CI 变快的优化，最终都会落回缓存设计。但缓存是一个典型的“调快很容易，调对很难”的领域。命中率漂亮不代表可信，关键还是产物和验证结果是否真的对应当前输入。

## 产物发布

流水线应该明确产物是什么、放在哪里、如何追踪版本。

```text
前端产物：
1. HTML
2. JS/CSS
3. Source Map
4. 构建元信息
```

构建产物最好带上 commit、版本号、构建时间和环境信息，方便线上问题追踪。

产物信息不只是给人看，也方便监控和回滚系统识别当前线上到底是哪一版。没有元信息的构建产物，排查起来会很被动。

产物发布最好同时保留清单和校验信息。这样回滚时可以确认“这次发出去的到底是不是同一份包”，而不是只能凭文件名猜。

对于前端项目，产物里最好还保留 release、commit、构建时间、环境和 source map 对应关系。这样线上错误一出现，团队就能快速把报错映射回具体发布批次。

## 失败处理

流水线失败时，要让开发者知道失败在哪、为什么失败、如何重试。

```text
失败信息应包含：
1. 阶段名称
2. 错误日志
3. 关联提交
4. 重试方式
```

不要把多个无关任务塞在同一个脚本里，否则失败日志会很难定位。

好的失败信息应该让人一眼知道“在哪一步失败、失败原因是什么、下一步怎么处理”。如果失败后还要翻半天日志，那流水线就没有发挥价值。

失败处理也可以自动化一部分。比如依赖安装失败先重试一次，缓存失效则重新拉取，测试失败则保留日志和截图。能自动恢复的错误，就不要都交给人工排查。

但自动恢复也要克制。真正的代码错误、类型错误、产物错误不应该靠“多试几次”掩盖；重试只适合处理那些明显受外部网络、平台波动影响的问题。

## 回滚机制

发布流水线必须有回滚路径。前端回滚可能是切换静态资源版本、回退配置、停止灰度或重新部署旧产物。

```text
回滚要素：
1. 旧产物仍然可用
2. 配置可以恢复
3. CDN 缓存可处理
4. 版本能被监控识别
```

流水线和 [[5.7.6 回滚策略|回滚策略]]、[[5.9.6 版本追踪|版本追踪]] 是一条链路：能发布，也要能定位和撤回。

这条链路越完整，发布就越像可控实验，而不是一次性赌博。自动化的意义就在于让发布变成可验证、可恢复、可追踪的过程。

如果流水线已经能覆盖安装、检查、构建、发布和回滚，后续最值得做的优化通常不是继续加命令，而是提升每一步的可读性、可观察性和恢复能力。

判断流水线是否成熟，可以看几个信号：

| 信号 | 说明 |
| --- | --- |
| 失败后能迅速定位具体阶段和原因 | 可维护性较好 |
| 发布和回滚路径都可重复执行 | 交付稳定 |
| 新人能看懂主要阶段职责 | 可读性足够 |
| 速度优化没有牺牲正确性 | 工程取舍健康 |
