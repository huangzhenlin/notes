## 验证目标

构建验证用于确认代码在进入部署前能生成正确、完整、可运行的产物。它不只是执行 `build`，还要检查类型、测试、资源、环境、产物和运行时入口。

```text
安装依赖
  -> 静态检查
  -> 类型检查
  -> 单元测试
  -> 构建
  -> 产物检查
  -> 冒烟验证
```

构建验证越早暴露问题，发布阶段越少惊喜。它是 CI/CD 的核心门禁之一。

构建验证的目标是让“能不能发”有证据，而不是靠开发者经验判断。它应该在部署前把依赖、类型、测试、资源和运行入口都检查一遍。

构建验证的重点不是多跑几个命令，而是保证输出能真正被用户打开、被浏览器执行、被监控识别。只要产物无法运行，再漂亮的构建成功日志都没有意义。

它本质上是在回答一个非常实际的问题：这次提交生成的东西，是否真的达到了“可以交付”的标准。这个标准不只包括语法正确，还包括依赖稳定、环境完整、入口可访问和关键功能可冒烟验证。

## 依赖一致

构建前要确保依赖安装可复现。CI 应使用锁文件冻结模式。

```bash
pnpm install --frozen-lockfile
yarn install --immutable
npm ci
```

不要在 CI 中使用会自动修改锁文件的安装方式。构建环境应该消费已确认的依赖图，而不是临时解析新版本。

依赖不一致是 CI 偶发失败和线上产物差异的重要来源。锁文件冻结能保证每次构建都从同一份依赖图开始。

如果构建环境经常变化，最好把 Node、包管理器和关键工具版本也固定下来。构建验证要检查的不是“能不能跑一次”，而是“每次都能跑出同样的结果”。

可复现性是构建验证的底线。一次偶然成功、一次偶然失败，都说明交付链路还不够稳。只有输入足够固定，验证结果才值得信任。

## 类型检查

类型检查应该独立于构建执行。很多构建工具为了速度不会做完整类型检查。

```bash
pnpm typecheck
```

Vue 项目常用 `vue-tsc --noEmit`，React/TS 项目常用 `tsc --noEmit`。类型检查失败应该阻止合并或部署。

构建工具为了速度常常只做转译，不做完整类型检查。把 typecheck 独立出来，能避免“产物生成成功但类型已经坏了”的情况。

类型检查失败应该尽早中止流程，避免后面的测试和构建都在错误前提上白跑。构建验证的目标是尽量早失败，而不是等最后一步才一起爆。

这也是为什么很多团队会把 lint、typecheck、unit test 放到构建前面。越便宜的问题越应该越早暴露，后面的构建资源要留给更接近交付的验证。

## 测试门禁

构建验证通常至少跑单元测试和关键集成测试。E2E 可以按项目规模拆成快速冒烟和完整回归。

```bash
pnpm test:unit
pnpm test:e2e --grep @smoke
```

PR 阶段可以跑快速集，发布前跑完整集。关键是每一层验证职责清晰，不要把所有风险都压到最后一步。

测试门禁也要控制耗时。PR 阶段跑核心测试，发布前跑完整回归，既能保证反馈速度，也能守住上线质量。

如果测试太慢，团队会倾向于跳过；如果测试太少，构建验证就失去意义。最稳的办法通常是把验证分层，并把最关键的核心链路放在最快的那层。

构建验证里最值得优先保留的，通常是那些“失败就真的不能发”的检查。辅助报告可以延后生成，但核心风险不应该被压缩掉。

## 产物完整

构建成功后要检查产物是否完整：HTML、JS、CSS、图片、字体、manifest、source map 是否存在且引用正确。

```text
dist/
  index.html
  assets/*.js
  assets/*.css
```

可以用脚本检查入口 HTML 是否引用了存在的资源，避免上传后才发现 chunk 缺失。

产物完整性还包括文件大小异常、source map 是否生成、manifest 是否存在、资源路径是否以正确 public path 开头。构建成功不代表产物一定能部署。

产物检查最好脚本化。比如检查入口 HTML 是否指向存在的 chunk、是否有重复引用、是否有缺失的 CSS 或字体资源。人工看一眼很容易漏，脚本能把重复劳动变成稳定门禁。

有条件的话，还可以在构建后比对包体积、关键 chunk 数量和入口资源变化。这样不仅能发现“不能运行”的问题，也能提前发现明显的构建退化和拆包异常。

## 产物运行

构建产物应在本地或 CI 中启动一个静态服务做冒烟验证。

```bash
pnpm build
pnpm preview
```

冒烟验证可以访问首页、登录页、核心路由和静态资源，确认不是“构建成功但页面打不开”。

前端项目尤其需要验证路由刷新和静态资源路径。SPA 在本地能打开，不代表部署到子路径或 CDN 后也能正常加载。

冒烟验证可以再往前走一步，直接访问核心路由、表单页和静态资源，并确认 release 标识、错误监控和接口配置都符合预期。这样能更接近真实上线状态。

对 SPA、SSR、静态站点和多入口应用来说，冒烟验证的重点也会不同。比如 SPA 更要关注路由刷新和 public path，SSR 更要关注首屏渲染和服务端数据注入，多入口应用则要确认各入口都能独立打开。

## 环境校验

构建验证要确认必需环境变量存在，且没有把服务端密钥打进前端产物。

```typescript
const required = ['VITE_API_BASE', 'VITE_APP_RELEASE'];

for (const key of required) {
  if (!process.env[key]) {
    throw new Error(`missing env ${key}`);
  }
}
```

环境变量校验和 [[5.9.2 环境变量|环境变量]] 是一组：前者保证构建输入正确，后者定义哪些变量可以暴露给浏览器。

构建验证还应检查是否混入了不该暴露的密钥。一个常见的失误是变量名没问题，但某个服务端 Secret 通过错误前缀被打进了前端产物。

环境校验还要区分构建时变量和运行时变量。构建时变量进入静态产物，运行时变量可以由配置文件或 HTML 注入，二者混用会增加发布风险。

一旦环境边界不清，就容易出现“预发包带了生产地址”“生产包读到了测试变量”这类高风险问题。构建验证要尽量在部署前就把这些问题拦下来。

## 质量报告

构建验证最好输出报告：测试结果、覆盖率、包体积、产物清单、source map 状态和构建耗时。

| 报告 | 价值 |
|---|---|
| 测试报告 | 判断功能风险 |
| 覆盖率 | 判断测试盲区 |
| 包体积 | 判断性能退化 |
| 产物清单 | 判断发布完整性 |
| 构建耗时 | 判断工程效率 |

报告不是为了存档好看，而是为了让 PR 和发布决策有依据。

如果构建验证输出了包体积变化、测试失败详情、覆盖率趋势和构建耗时，团队就能更早发现性能退化和工程效率问题。

报告最好能给出趋势而不是只有单次结果。这样团队才能知道某次 PR 只是波动，还是工程质量真的在下降。

一个成熟的构建验证，不只是告诉你“这次过没过”，还会告诉你“这次和之前相比变差了没有”。只有这样，它才真正具备工程治理价值。
