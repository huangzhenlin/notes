## 回滚目标

回滚策略用于在发布后出现异常时，把影响范围快速收住。它不是失败后的临时操作，而是发布前就应该设计好的安全网。

```text
发布新版本
  -> 监控发现异常
  -> 暂停放量
  -> 切回稳定版本
  -> 保留现场
  -> 修复并重新发布
```

回滚的目标不是“回到过去”这么简单，而是让用户尽快恢复可用，同时保留足够证据分析根因。

回滚策略越提前设计，事故中越不需要临时决策。真正危险的不是回滚本身，而是发现问题后不知道该切哪一版、怎么切、切完怎么验证。

回滚策略应该和发布策略一起评审。只要某次发布改变了入口资源、接口协议、缓存结构或数据写入方式，就要同步确认对应回滚路径，而不是等异常发生后再补。

很多回滚失败不是因为工具不够，而是因为发布时根本没有把“回退可能性”当成设计约束。越是牵涉缓存、协议和数据结构的变更，越要提前评估回滚复杂度。

## 触发条件

回滚需要明确触发条件，避免线上事故时靠情绪判断。

| 信号 | 可能动作 |
|---|---|
| 白屏率显著升高 | 立即暂停灰度或回滚 |
| JS 错误率升高 | 按 release 判断回滚 |
| chunk 404 增多 | 恢复旧资源或切回旧 HTML |
| 核心转化下降 | 暂停放量并排查 |
| 接口失败率升高 | 判断前端兼容或后端异常 |

触发条件要和监控指标绑定。没有监控，就没有客观回滚依据。

触发条件最好提前写清阈值和负责人。例如错误率超过某个比例、白屏率持续上升、核心链路失败超过窗口阈值，就进入暂停或回滚流程。

触发条件也要区分自动和人工。白屏率、chunk 404、核心接口失败可以设置自动告警；业务转化下降、用户反馈异常则可能需要人工判断。两类信号都要进入同一套响应流程。

一套好的回滚触发条件，既不能模糊到完全靠感觉，也不能机械到一点正常波动就自动切回。阈值、观察窗口和人工确认点都需要结合业务特征设计。

## 静态资源回滚

静态前端最常见回滚方式是切回上一版 HTML 或资源清单。带 hash 的 JS/CSS 通常可以长期保留，HTML 决定用户加载哪组资源。

```text
v2 index.html -> v2 chunks
回滚
v1 index.html -> v1 chunks
```

前提是旧资源仍然存在。如果发布时删除了旧 chunk，用户持有旧 HTML 时就可能加载失败。静态资源部署必须配合保留策略。

静态资源回滚的核心是入口切换。只要旧入口和旧 chunk 都还在，回滚通常可以很快完成；如果旧资源已经被清理，回滚会变成重新构建和重新发布。

静态资源回滚时要特别关注 CDN 生效时间。入口 HTML 切回旧版后，还要确认边缘节点已经更新，否则不同地区用户可能同时访问新旧入口。

如果项目采用多级缓存或多地域 CDN，回滚后的验证也要覆盖多个入口点，而不是只在某一台机器上看到恢复就认为全网已经恢复。

## 配置回滚

很多问题可以通过配置回滚解决，例如关闭新入口、禁用功能开关、降低灰度比例、切回旧接口。

```typescript
if (featureFlags.newCheckout) {
  renderNewCheckout();
} else {
  renderLegacyCheckout();
}
```

配置回滚比重新部署更快，但要求代码里提前保留旧路径。没有旧路径，开关只是摆设。

功能开关要避免只控制入口展示，而不控制真实执行路径。否则界面隐藏了新功能，底层请求或数据写入仍然可能走新逻辑。

配置回滚最适合处理“功能开关可控”的问题。如果代码路径已经被移除，或者新版本已经改写数据结构，配置回滚就不够用了，需要资源回滚或服务端协同。

因此功能开关最好从一开始就围绕“可关闭、可旁路、可恢复”来设计，而不是只为了上线阶段方便展示某个新按钮。

## 数据兼容

回滚最危险的是数据不兼容。新版本如果写入了旧版本无法识别的数据结构，回滚后可能继续出错。

| 风险 | 处理 |
|---|---|
| 新字段旧代码不识别 | 旧代码忽略未知字段 |
| 数据迁移不可逆 | 发布前设计反向迁移 |
| 接口协议变更 | 服务端保持兼容窗口 |
| 本地缓存结构变化 | 加版本号和迁移逻辑 |

前端回滚也要考虑 LocalStorage、IndexedDB、缓存数据和服务端接口协议。只回滚 JS 不一定能解决数据层问题。

数据兼容是回滚里最容易被低估的风险。新版本如果已经写入新结构，旧版本必须能忽略未知字段或有迁移兜底，否则回滚后仍然会坏。

涉及数据写入的前端发布，最好采用“先兼容、再切换、后清理”的节奏。先让旧版本能接受新字段，再放出新版本，最后等稳定后再清理旧逻辑，这样回滚空间更大。

这种兼容窗口虽然会让代码短期更复杂，但它换来的是更高的发布安全性。尤其是支付、订单、配置中心、本地缓存升级这类场景，回滚空间比短期整洁更重要。

## 回滚演练

回滚流程要演练。没有演练过的回滚，在事故中很容易变成新的事故。

```text
演练内容：
1. 找到上一稳定版本
2. 执行回滚命令
3. 验证页面可用
4. 检查监控恢复
5. 记录耗时和问题
```

演练不需要等真实事故发生。核心业务上线前，应该至少确认回滚路径可用。

演练要记录耗时、操作步骤和卡点。回滚如果只能由某一个人完成，就是隐性风险。

回滚演练不一定要影响真实用户，可以在预发环境、灰度环境或影子入口里执行。关键是验证流程和工具，而不是制造一次真实事故。

演练的目标也不只是证明“能回去”，还要看恢复速度是否达标、监控是否能及时反映恢复效果、操作步骤是否足够清晰，是否存在单点知识依赖。

## 现场保留

回滚前后要保留现场：release、commit、构建产物、错误日志、用户反馈、监控截图、灰度比例和操作时间。

```text
事故记录
  -> 发生时间
  -> 影响范围
  -> 触发版本
  -> 回滚动作
  -> 恢复时间
```

回滚不是结束，复盘才是把事故变成项目能力的关键。它和 [[5.9.5 监控接入|监控接入]]、[[5.9.6 版本追踪|版本追踪]] 必须形成闭环。

复盘里要分清“发布问题”“监控问题”“回滚问题”和“流程问题”。只有把这些分别改掉，下一次发布才会更稳。

现场保留要注意顺序。先止血，但不要覆盖证据；先恢复用户可用，再整理根因。事故中的操作记录越完整，复盘越不容易变成猜测。

判断回滚体系是否成熟，可以看几个问题：

| 问题 | 理想状态 |
| --- | --- |
| 能否在几分钟内确定回滚目标 | 能 |
| 回滚后能否快速验证恢复效果 | 能 |
| 是否保留了足够现场信息 | 能 |
| 是否有人之外的流程文档和脚本可依赖 | 能 |
