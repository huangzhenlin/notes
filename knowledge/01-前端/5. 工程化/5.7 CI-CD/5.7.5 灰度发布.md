## 灰度一致性

灰度要保证同一个用户在一段时间内稳定命中同一版本或同一功能状态。

```text
不稳定灰度：
刷新前是新功能
刷新后变回旧功能

稳定灰度：
按用户 ID 或组织 ID 固定分桶
```

稳定性对有表单、流程、缓存的功能尤其重要。用户在流程中途切换版本，可能导致状态不一致。

灰度一致性不仅影响体验，也影响数据分析。如果同一个用户反复进入不同版本，错误率、转化率和性能指标都很难解释。
## 灰度目标

灰度发布用于让新版本先影响一小部分用户，通过真实指标判断是否继续放量。它的价值是降低事故半径，而不是让发布流程看起来更复杂。

```text
内部验证
  -> 白名单
  -> 小流量
  -> 分阶段放量
  -> 全量
```

灰度需要配合监控、版本追踪、回滚和稳定分流。缺少这些能力，灰度很容易变成“慢速全量”。

灰度发布的本质是小范围验证真实环境，而不是把发布流程拖慢。它必须能观察、能暂停、能回滚，才算真正降低风险。

灰度最怕两件事：分桶不稳定，以及指标看不清。前者会让同一用户反复切换版本，后者会让团队不知道该不该继续放量。

灰度如果不能回答“现在谁在用新版本”“这些用户表现如何”“如果出问题怎么立刻停”，那它就只是一层更复杂的发布形式，而不是风险控制能力。

## 分流维度

常见灰度维度包括用户 ID、设备 ID、组织、地域、渠道、版本和账号白名单。

| 维度 | 适合场景 |
|---|---|
| 用户 ID | C 端稳定分桶 |
| 组织 ID | B 端企业灰度 |
| 设备 ID | 未登录用户 |
| 地域 | 地区性业务 |
| 白名单 | 内测和验收 |

分流维度要稳定。同一个用户反复切换新旧版本，会造成体验混乱，也会污染监控数据。

选择分流维度时要看业务身份是否稳定。登录用户适合按用户 ID，B 端适合按组织 ID，未登录场景可以考虑设备 ID 或匿名 ID。

如果业务里存在会话切换、账号切换或多租户切换，灰度维度就要避免跟着会话乱跳。灰度应该尽量绑定稳定身份，而不是临时请求状态。

选择灰度维度时，还要考虑指标归因。能稳定归因到用户、组织或设备的维度，更适合长期观察；过于临时的维度虽然实现简单，但很难解释后续数据。

## 稳定分桶

稳定分桶通常通过哈希实现。给定同一个用户 ID 和灰度比例，结果应保持一致。

```javascript
function hash(input) {
  let value = 0;
  for (const char of input) {
    value = (value * 31 + char.charCodeAt(0)) >>> 0;
  }
  return value;
}

function inGray(userId, percent) {
  return hash(userId) % 100 < percent;
}
```

灰度比例从 10% 增加到 30% 时，原来的 10% 用户应继续留在灰度内，这样数据更稳定。

稳定分桶还要保证扩容时只新增用户，不把原有灰度用户踢出去。否则同一批用户的行为前后无法连续观察。

灰度算法最好有可解释性和可复现性。出了问题时，团队应该能根据用户 ID 和规则重算他属于哪个桶，而不是靠外部平台的黑盒结果猜。

如果灰度规则涉及多个条件叠加，比如白名单、实验平台、地区、账号等级和版本过滤，更要注意优先级和冲突处理，否则用户命中结果会越来越难判断。

## 版本标识

灰度用户必须带上版本、分桶、实验和配置标识。否则指标异常时，很难判断是哪个灰度造成的。

```javascript
analytics.track('page_view', {
  release: window.__APP_RELEASE__,
  rollout: window.__ROLLOUT_ID__,
  bucket: window.__GRAY_BUCKET__,
});
```

错误监控、性能监控、接口日志和业务埋点都应该能看到同一套灰度标识。

如果只有前端埋点知道灰度信息，而后端日志不知道，排查跨端链路时仍然会断开。灰度标识最好贯穿请求头、日志和监控。

灰度标识还能帮助做实验分析。只要 release、rollout、experiment 都能统一，后续排查“是版本问题还是策略问题”会快很多。

标识体系越统一，越容易把前端、后端、监控、埋点和客服反馈串起来。没有统一标识时，灰度问题很容易变成“每个系统都知道一点，但谁也说不清全貌”。

## 放量节奏

放量节奏要根据业务风险决定。低风险改动可以快速放量，高风险改动要观察更久。

```text
1% 观察 30 分钟
10% 观察 1 小时
50% 观察半天
100% 全量
```

观察指标包括错误率、白屏率、接口失败率、核心转化、性能指标和用户反馈。指标稳定再继续，不稳定就暂停。

放量节奏不应该只看时间，还要看样本量和业务周期。低流量页面可能需要观察更久，高峰期发布则要更谨慎。

放量过程里，最好预留人工暂停入口。自动规则可以挡住大多数问题，但在指标抖动、外部事件或突发故障时，人工兜底很重要。

放量节奏还要结合业务时段。高峰期、营销活动期、财务结算期这类时间窗口，通常不适合激进扩量；低峰期更适合验证高风险变更。

## 缓存影响

前端灰度最容易被缓存影响。HTML、CDN、Service Worker、本地缓存都可能让用户实际拿到的版本和分流结果不一致。

| 缓存层 | 风险 |
|---|---|
| CDN HTML | 用户拿到旧入口 |
| 浏览器缓存 | 资源清单滞后 |
| Service Worker | 拦截请求 |
| 本地配置缓存 | 灰度开关不更新 |

灰度策略要明确哪些内容可缓存、缓存多久、灰度变化后如何刷新。

前端灰度尤其要注意入口 HTML 和配置缓存。如果配置已经切回旧版本，但用户本地仍缓存旧灰度配置，回滚就不会立即生效。

灰度缓存问题常见于 CDN、Service Worker 和本地存储同时存在的项目。发布策略要明确哪个层级负责切换，哪个层级负责失效，否则很容易“明明回滚了，用户还看见新版本”。

前端灰度和缓存系统一旦耦合，就必须把缓存命中当成灰度路径的一部分来设计，而不是只看服务器端怎么分流。

## 回滚灰度

灰度回滚通常比全量回滚简单：暂停放量、把比例降为 0、关闭功能开关或切回旧资源。

```text
发现异常
  -> 停止扩大
  -> 比例降为 0
  -> 观察指标恢复
  -> 分析原因
```

灰度发布和 [[5.7.6 回滚策略|回滚策略]] 是配套的。灰度的意义，就是让回滚更早、更小、更可控。

如果灰度阶段发现异常，应优先暂停放量并保留现场，而不是立刻继续尝试修补。先把影响范围收住，再分析根因。

灰度规则最好和监控阈值、回滚动作写成一套预案。这样一旦指标异常，值班同学能按规则执行，不需要临时决定。

一个成熟的灰度发布，通常会提前定义：

| 内容 | 目的 |
| --- | --- |
| 分桶规则 | 保证命中稳定 |
| 指标看板 | 让异常可观察 |
| 扩量节奏 | 控制风险暴露速度 |
| 暂停条件 | 出问题时能快速止损 |
| 回滚动作 | 把恢复路径前置 |
