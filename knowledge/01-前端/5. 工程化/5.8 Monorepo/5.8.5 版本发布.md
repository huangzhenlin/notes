## 发布单元

Monorepo 的版本发布首先要明确发布单元：是整个仓库统一一个版本，还是每个包独立版本。选择不同，版本号、变更记录、依赖更新和回滚方式都会不同。

| 模式 | 特点 | 适合场景 |
|---|---|---|
| 固定版本 | 所有包共用同一个版本号 | 强耦合套件、统一交付产品 |
| 独立版本 | 每个包独立升级 | 组件库、工具包、SDK 集合 |
| 分组版本 | 部分包绑定版本 | 核心包联动、插件包独立 |

固定版本简单，但小改动也会让所有包升级；独立版本灵活，但需要处理包之间依赖版本同步。组件库、工具库 Monorepo 通常更适合独立版本或分组版本。

发布单元要和使用者感知一致。如果外部使用者把一组包当作一个整体，统一版本更好理解；如果每个包独立消费，独立版本能减少无意义升级。

发布单元还要考虑内部协作。如果多个包经常一起变动、一起验证，分组版本可能比完全独立版本更省心；如果包之间耦合松，独立版本更灵活。

这一步如果选错，后面所有发布体验都会受影响。版本模式不是越灵活越好，而是越贴近真实协作和消费方式越好。

## 变更记录

Monorepo 发布不能只在发布当天补 changelog。更稳定的方式是在每个 PR 或每个功能变更时记录“哪个包发生了什么级别的变化”。Changesets 就是常用方案之一。

```bash
pnpm add -D @changesets/cli
pnpm changeset init
pnpm changeset
```

一次 changeset 通常包含三类信息：受影响的包、版本升级类型和变更说明。

```markdown
---
"@acme/button": minor
"@acme/theme": patch
---

Button 增加 loading 状态，theme 修复暗色模式变量。
```

变更记录的价值不只是生成日志，还能把“这个改动是否影响发布”前置到开发阶段。不是所有提交都需要 changeset，例如文档、测试和内部重构如果不改变对外行为，就可以不产生发布记录。

changeset 的好处是把发布判断放到 PR 阶段。写代码的人最清楚变更影响，让他在当时说明版本级别，比发布当天再补日志可靠得多。

变更记录最好尽量短而明确，说明“改了什么、影响哪个包、应该升什么版本”。冗长描述反而不利于发布审查。

一个好的 changeset 不是把实现细节全写进去，而是让发布审查者和使用者快速理解这次变化的外部影响。

## 版本计算

发布前需要把积累的 changeset 消费掉，计算每个包的新版本，并同步更新内部依赖范围。

```bash
pnpm changeset version
```

这个步骤通常会修改：

| 文件 | 变化 |
|---|---|
| `package.json` | 更新包版本和内部依赖版本 |
| `CHANGELOG.md` | 写入本次发布说明 |
| `.changeset/*.md` | 已消费的 changeset 被移除 |

执行版本计算后要审查 diff，重点看版本级别是否合理、内部依赖是否同步、changelog 是否能被使用者读懂。版本计算不是机械步骤，它是发布前最后一次确认对外影响。

如果版本计算结果和预期不一致，通常说明 changeset 写错、内部依赖范围不合理，或者某些包边界没有设计好。

版本计算阶段其实也是一次边界体检。只要一算版本就出现大面积联动，往往说明包划分、依赖范围或版本模式还需要重新审视。

版本计算后最好检查内部依赖是否都被正确提升。否则某些包看起来发布成功了，但实际消费方仍然拿着旧依赖范围。

## 发布执行

版本计算通过后，才进入真正发布。发布前通常要完成构建、测试、类型检查、包内容检查和 npm 权限校验。

```bash
pnpm install --frozen-lockfile
pnpm test
pnpm build
pnpm changeset publish
```

发布命令会把版本高于 registry 当前版本的包发布出去。对于首次发布的 scoped public 包，需要确保 `publishConfig.access` 或 changeset 配置正确。

```json
{
  "name": "@acme/button",
  "version": "0.1.0",
  "publishConfig": {
    "access": "public"
  }
}
```

不要把 npm token 暴露在日志和普通配置文件里。CI 发布应使用仓库密钥、最小权限 token 或可信发布机制。

发布权限应尽量收敛到 CI，而不是每个开发者都在本地手动发布。这样能减少环境差异、权限泄露和不可追踪发布。

发布执行最好同时保留 dry-run 和正式发布。先在干跑里检查包内容和版本号，确认没问题后再走正式发布，能减少很多低级事故。

真正危险的不是“发版多按了一次命令”，而是“没有统一发布入口”。一旦每个人都能在各自本地环境里直接发包，后续版本追踪和故障排查会非常困难。

## 包内容检查

Monorepo 中最容易出现“本地能用，发布后不能用”的问题，因为包发布到 npm 后只包含 `files`、`.npmignore` 和默认规则允许的内容。发布前应检查最终 tarball。

```bash
pnpm --filter @acme/button pack --pack-destination ./tmp
npm pack --dry-run
```

需要重点确认：

| 检查项 | 说明 |
|---|---|
| 入口文件 | `main`、`module`、`types` 指向真实文件 |
| 类型文件 | `.d.ts` 是否随包发布 |
| 样式文件 | CSS、主题变量是否包含 |
| 产物格式 | CJS、ESM、类型声明是否符合约定 |
| 多余内容 | 测试、源码私密文件是否被排除 |

包内容检查比“构建成功”更接近真实用户体验，因为用户安装的不是你的源码目录，而是发布后的包。

很多包发布事故都发生在这里：本地引用源码没问题，npm 包却漏了 CSS、类型声明或入口文件。发布前 `pack --dry-run` 很值得做。

对组件库来说，这一步尤其关键。一个按钮组件本地开发正常，不代表发到 npm 后样式、主题变量、类型声明和副作用配置都还完整。

包内容检查也适合和发布清单一起看。哪些包会发布、哪些只是内部使用、哪些需要额外样式和声明文件，最好都能一眼看清。

## 依赖联动

独立版本 Monorepo 要处理内部依赖更新。例如 `@acme/button` 依赖 `@acme/theme`，theme 发布新版本后，button 是否需要同步升级，取决于依赖范围和构建产物。

```json
{
  "dependencies": {
    "@acme/theme": "workspace:^"
  }
}
```

`workspace:^` 能在发布时转换成合适的 semver 范围。内部依赖如果没有同步，用户可能安装到不兼容组合；如果同步过度，又会造成无意义版本膨胀。

依赖联动要看运行时是否真的受影响。类型包、主题包、组件包之间的关系不同，发布时不能一律同步，也不能完全不管。

如果内部依赖的兼容范围经常变化，可以考虑配合自动化提 PR 更新下游包，减少人工找依赖的时间。

依赖联动最怕两种极端：一种是什么都不联动，结果消费者拿到不兼容组合；另一种是什么都跟着升，结果版本噪音很大。中间的平衡要靠清楚的兼容策略。

## 自动化发布

成熟的 Monorepo 通常把版本计算和发布接入 CI。常见流程是：PR 合并后由机器人创建 Version PR，人工审查变更日志和版本号，合并 Version PR 后发布。

```text
功能 PR
  -> 添加 changeset
  -> 合并到 main
  -> 自动生成 Version PR
  -> 审查版本和 changelog
  -> 合并 Version PR
  -> 发布 npm 包并打 tag
```

这个流程比“本地手动发布”更稳定，因为它把发布权限、构建环境和版本记录统一到流水线中。它也和 [[5.7.1 流水线|流水线]]、[[5.9.6 版本追踪|版本追踪]] 形成闭环：发布出去的每个包都应该能追溯到提交、构建和变更说明。

自动化发布不是为了省一次命令，而是为了让版本、tag、changelog、npm 包和构建记录保持一致。只要其中一环靠人工，就容易出现追踪断点。

自动化发布完成后，还要把版本信息回写到监控、文档和调试入口里，这样发布链路才真正闭环。

判断版本发布体系是否成熟，可以看几个问题：

| 问题 | 理想状态 |
| --- | --- |
| 哪些包会在这次发布中变化 | 一眼能看清 |
| 为什么升 major / minor / patch | 有明确记录 |
| 发布后能否追到对应 commit 和 changelog | 能 |
| 回滚或补发时是否仍有统一流程 | 有 |
