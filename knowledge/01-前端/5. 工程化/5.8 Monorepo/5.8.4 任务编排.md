## 编排目标

Monorepo 任务编排解决的是“多个包之间按依赖关系高效执行脚本”的问题。它不仅是批量运行命令，还要处理依赖拓扑、缓存、并行、增量和失败传播。

```text
packages/ui
packages/utils
apps/admin
apps/mobile

utils -> ui -> admin
utils -> mobile
```

如果 `admin` 依赖 `ui`，那么构建 `admin` 前应该先构建 `ui`。任务编排工具就是把这种关系自动化。

任务编排的价值在于把“人脑记依赖顺序”变成“工具按依赖图执行”。仓库越大，这个价值越明显。

当仓库里同时存在多个应用、组件库、工具包和配置包时，单靠 `pnpm -r` 全量执行很快就会变慢。任务编排真正带来的，不只是自动排序，还有“只做必要工作”的能力。

## 拓扑顺序

拓扑执行会根据包之间的依赖关系决定顺序。依赖先执行，被依赖者后执行。

```bash
pnpm -r --sort build
```

```text
utils build
  -> ui build
    -> admin build
```

没有拓扑顺序时，应用可能在依赖包尚未生成产物时就开始构建，造成偶发失败。这个问题在 CI 并行环境里尤其明显。

拓扑顺序还能让失败更可解释。如果底层包构建失败，上层应用就不该继续构建，否则只会产生更多噪音日志。

拓扑顺序本质上是在保护依赖链。越底层的问题越应该越早失败，避免把错误放大到一串无意义的后续任务里。

## 过滤执行

大型 Monorepo 不应该每次都全量构建。过滤执行可以只运行某个包、某个目录或受影响范围。

```bash
pnpm --filter admin build
pnpm --filter "...admin" test
pnpm --filter "admin..." lint
```

过滤语义通常要区分“当前包”“依赖当前包的包”“当前包依赖的包”。用错过滤范围，会导致遗漏必要构建或跑太多无关任务。

过滤执行不是为了偷懒少跑，而是为了精准跑。真正安全的过滤要覆盖变更包及其影响范围。

过滤如果只看“我改了哪个包”，往往还不够。还要看谁依赖它、谁消费它、哪些测试和构建会被它的变化间接影响。

## 任务缓存

任务缓存会把输入文件、依赖版本、环境变量和命令输出作为缓存键。如果输入没变，就复用上次结果。

```json
{
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": []
    }
  }
}
```

缓存的前提是任务可复现。构建输出如果依赖当前时间、随机数、未声明环境变量或外部服务，缓存就可能不可靠。

任务缓存要和输入输出绑定。输入声明少了，会复用错误结果；输出声明少了，会命中缓存但缺少产物；输出声明太宽，又可能把无关文件缓存进去。

任务编排工具再强，也无法替你猜出真正的输入边界。脚本设计越不透明，缓存和编排越容易失真。

## 并行执行

没有依赖关系的任务可以并行执行，提高 CI 速度。

```text
utils lint ─┐
ui lint    ├─ 并行
admin lint ┘
```

并行不是越多越好。机器资源有限时，过高并发会导致内存不足、测试抖动、构建变慢。CI 中通常需要限制 workers 或并发数。

并行执行适合无依赖任务。对于有共享资源的任务，比如同时启动多个浏览器测试、写同一个缓存目录，就要控制并发，避免互相干扰。

并行带来的问题往往不是“会不会更快”，而是“会不会互相污染”。浏览器测试、临时目录、端口占用、本地服务启动这些场景，都要特别注意共享资源冲突。

## 增量范围

增量构建要知道“这次变更影响了哪些包”。影响范围不仅包括被修改包，还包括依赖它的上游包。

```text
修改 packages/utils
  -> 需要测试 utils
  -> 需要测试依赖 utils 的 ui
  -> 需要测试依赖 ui 的 admin
```

只测试修改包是不够的，因为破坏可能出现在使用方。受影响范围计算是 Monorepo 提升效率同时保证质量的关键。

影响范围计算越准确，CI 越快也越安全。计算过窄会漏测，计算过宽则失去提速意义。

所以受影响范围检测不应该被当成“可有可无的小优化”，它其实是 Monorepo CI 是否能既快又可信的关键能力之一。

## 远程缓存

远程缓存让团队和 CI 共享任务结果。开发者本地、PR CI、主干 CI 都可以复用同一份构建缓存。

```text
本地构建
  -> 上传缓存
CI 构建
  -> 命中缓存
  -> 跳过重复任务
```

远程缓存要注意权限和安全。缓存里可能包含构建产物、日志、source map 或环境相关内容，不应该把敏感信息写入输出目录。

远程缓存还要防止不可信分支污染缓存。开源仓库或 fork PR 场景下，要格外注意缓存读写权限。

远程缓存越强，越要重视权限和隔离。否则一个不可信分支写进了错误缓存，问题就可能在整个团队和多条流水线之间扩散。

## 任务设计

好的任务编排依赖好的脚本设计。脚本应该输入明确、输出明确、可重复执行。

| 任务 | 输出 | 是否适合缓存 |
|---|---|---|
| `build` | `dist/**` | 适合 |
| `typecheck` | 无产物 | 适合缓存结果 |
| `lint` | 无产物 | 适合缓存结果 |
| `test` | coverage | 视情况 |
| `dev` | 长进程 | 不适合 |

任务编排和 [[5.7.1 流水线|流水线]] 是配套的：本地靠编排提速，CI 靠编排减少无效工作，同时保持依赖顺序和质量门禁。

脚本设计越稳定，编排收益越大。一个任务如果每次输出不确定、依赖隐式环境、或会修改源码，就不适合作为可缓存任务。

任务编排是否健康，可以看这些迹象：

| 迹象 | 说明 |
| --- | --- |
| 只改小包时 CI 明显变快 | 影响范围计算有效 |
| 失败任务定位清楚 | 拓扑和职责划分合理 |
| 缓存命中后产物仍可信 | 输入输出声明较完整 |
| 很少出现“全量跑才能放心” | 编排体系开始成熟 |
