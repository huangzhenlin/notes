## 基本模型

Monorepo 是把多个项目或 package 放在同一个代码仓库中管理。

```txt
repo/
  apps/
    web/
    admin/
  packages/
    ui/
    utils/
    config/
```

它不是简单的“一个大仓库”，而是一种共享代码、统一工程标准、集中协作的组织方式。

Monorepo 的关键不是“放在一起”，而是“放在一起之后还能保持边界清楚、任务高效、发布可控”。如果只是把多个项目搬进一个仓库，却没有 workspace、任务缓存、边界约束和发布规范，就只是目录变大了。

Monorepo 解决的不是“能不能放一起”，而是“放一起之后怎么协作”。真正有价值的，是共享代码、统一规范、跨包重构和依赖图驱动的任务执行。

所以 Monorepo 从来不是单纯目录调整，而是一套协作方式的升级。它要求团队愿意接受更强的一致性，也要求工程工具能把这种一致性真正落地。

## 适用场景

Monorepo 适合多个项目之间存在稳定共享关系的团队。

| 场景 | 是否适合 |
| --- | --- |
| 多个前端应用共享组件库 | 适合 |
| 应用和 SDK 同步开发 | 适合 |
| 前后端强契约共享类型 | 视情况 |
| 完全无关项目 | 不适合 |
| 团队很小且只有单应用 | 不一定需要 |

如果项目之间几乎没有共享代码、发布节奏完全不同、权限边界强，强行 Monorepo 可能只会增加复杂度。

适不适合 Monorepo，取决于协作关系是否真实存在。如果多个项目经常一起改、一起验证、共享组件和工具，那么同仓库会提高效率；如果项目彼此无关，单独仓库反而更清爽。

判断是否适合时，可以先看这三个问题：是否经常共享代码、是否需要跨包原子修改、是否愿意维护统一工程规范。只要这三条里有两条不成立，就不一定要上 Monorepo。

另一个很现实的判断角度，是团队是否已经感受到多仓库协作成本。例如组件库改一次要跨多个仓库提 PR、类型变更要手动同步多个项目、CI 重复跑相同任务。如果这些问题已经很明显，Monorepo 的收益会更容易体现。

## 价值

Monorepo 的价值主要体现在共享和一致性。

```txt
统一依赖版本
统一 lint/test/build 配置
本地联调共享包
跨包重构一次完成
代码搜索更完整
CI 可基于依赖图执行
```

例如 UI 组件库和多个业务应用放在同仓库中，修改组件 API 时可以同时修改所有调用方并跑测试。

这种“跨包原子修改”是 Monorepo 的核心收益之一。组件 API、工具函数、类型定义变化时，可以在同一个 PR 里同时更新依赖方，避免先发布包、再等应用逐个升级。

Monorepo 的另一个好处是让代码搜索和重构更完整。以前散在多个仓库里的依赖关系，在同一个仓库里更容易被发现，也更容易一次性修改和验证。

这对于前端基础设施、设计系统、共享 SDK、类型定义和构建配置尤其有价值。因为这些能力天然是跨项目共享的，把它们放在一个仓库中治理，往往比跨仓库同步更稳定。

## 成本

Monorepo 也会带来工程成本。

| 成本 | 表现 |
| --- | --- |
| 仓库变大 | clone、安装、索引变慢 |
| CI 复杂 | 需要变更检测和缓存 |
| 权限边界 | 不同团队代码在同仓库 |
| 发布复杂 | 多包版本和 changelog |
| 依赖治理 | 循环依赖、幽灵依赖 |

没有工具支撑的 Monorepo 很容易变成“巨大目录”。Workspace、任务缓存、边界检查、发布工具都很重要。

成本也不是一次性成本。仓库变大后，依赖安装、编辑器索引、CI 调度、权限控制和发布流程都会变复杂，需要持续治理。

如果没有自动化支持，Monorepo 很容易把原来的简单协作变成“一个大仓库里的人工流程”。所以它通常不是单独引入，而是和 workspace、缓存、任务编排、变更检测一起落地。

很多团队踩坑的原因，不是 Monorepo 本身不好，而是只做了“合仓”，没有同步补上工具链和规则层。结果共享和一致性没拿到，复杂度却先上来了。

## 包边界

Monorepo 中每个 package 应有清晰职责。

```txt
@repo/ui      -> UI 组件
@repo/utils   -> 通用工具
@repo/config  -> ESLint/TS/Vite 配置
@repo/web     -> Web 应用
```

包不是越多越好。只有当代码有独立职责、复用价值、构建边界或发布需求时，才值得拆包。

拆包过细会让开发者在多个 package 之间来回跳，也会增加构建、发布和版本管理成本。拆包过粗则会让复用和缓存失效，所以包边界需要随着业务演进调整。

包边界最好围绕职责和变化频率，而不是围绕目录名。一个包如果经常被一起修改、一起发布、一起测试，那它们可能更适合同属一个边界；如果一个包的变化很少却被很多地方依赖，就要格外谨慎。

边界不是一次划完就永远不变。随着业务演进，某些包会变得过大、过碎或角色模糊，这时就需要重新调整，而不是把最初的拆分方式当成永久真理。

## 依赖图

Monorepo 的任务执行应基于依赖图。

```txt
utils -> ui -> web
config -> web
```

如果只修改 `utils`，需要测试依赖它的 `ui` 和 `web`；如果只修改 `web` 页面，不一定要构建所有包。依赖图能让 CI 更快，也能降低漏测风险。

依赖图也是缓存和任务编排的基础。没有依赖图，CI 只能全量跑；有了依赖图，才知道这次改动真正影响哪些包。

依赖图还决定了哪些包可以并行、哪些包必须串行。理解依赖图之后，很多 CI 优化其实就变成了“把独立的任务并行执行，把受影响的任务按图重跑”。

依赖图如果长期没人维护，就会逐渐偏离真实情况。显式声明包依赖、避免跨目录偷引用、把边界规则自动化，都是保证依赖图可信的前提。

## 发布模式

Monorepo 常见发布模式有统一版本和独立版本。

| 模式 | 特点 |
| --- | --- |
| 统一版本 | 所有包共用版本号，管理简单 |
| 独立版本 | 每个包独立发版，更灵活 |
| 应用不发布 | apps 部署，packages 发布或内部使用 |

组件库、工具库对外发布时，需要版本策略；纯应用仓库更关注部署和构建缓存。

发布模式没有绝对优劣。统一版本简单、心智负担低；独立版本灵活，但 changelog、依赖联动和发布流程会更复杂。

如果仓库里既有应用又有库，发布模式也可以分层：应用按部署发布，内部库按版本发布。这样能避免把部署和发包混成一个流程。

这类分层模式在前端仓库里很常见。应用关注的是上线和回滚，库关注的是版本和兼容；如果强行用同一套发布心智管理它们，团队通常会越来越混乱。

## 判断问题

决定是否使用 Monorepo 前，可以问：

```txt
是否有多个项目共享代码
是否需要跨项目原子修改
是否愿意维护统一工程规范
CI 是否能按变更范围执行
权限和发布边界是否能接受
团队是否理解包边界
```

Monorepo 是协作和工程治理选择，不是目录结构潮流。它解决共享和一致性问题，同时要求更强的工具和规范。

如果团队规模还不大，也可以先从 workspace 和少量共享包开始，不必一上来就把所有项目都塞进同一套复杂治理里。

如果团队还没有稳定的包边界、CI 缓存和发布流程，先从 workspace 和少量共享包做起，比一次性“大一统”更稳。

一个更稳妥的推进路径通常是：

| 阶段 | 重点 |
| --- | --- |
| 初期 | 先建立 workspace 和共享包 |
| 中期 | 接入任务编排、缓存和边界约束 |
| 后期 | 优化版本发布、变更检测和治理规则 |

这样 Monorepo 才会逐步长成工程能力，而不是一开始就把复杂度全部压到团队身上。
