## 工作区定位

Workspace 是包管理器提供的多包协作能力，用来在一个仓库中管理多个 package。它解决的不是“怎么写业务代码”，而是“怎么让多个包在同一仓库里可靠协作”。

```text
repo/
  package.json
  pnpm-workspace.yaml
  packages/
    ui/
    utils/
  apps/
    web/
    admin/
```

Monorepo 是仓库组织方式，Workspace 是依赖安装、包链接和脚本执行的基础设施。没有 Workspace，也可以手动维护多包，但依赖关系、本地联调和发布流程都会更脆弱。

可以把 Workspace 理解成 Monorepo 的“依赖底座”。它负责发现包、链接内部包、统一安装依赖，让多个 package 像一个整体一样协作。

底座一旦不稳，上层所有能力都会受影响。任务编排、缓存、版本发布、边界约束本质上都依赖 workspace 对包关系的正确识别。

## 包发现

不同包管理器有不同 Workspace 配置方式。pnpm 常用 `pnpm-workspace.yaml`。

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

npm 和 Yarn 也可以在根 `package.json` 中声明 workspaces。

```json
{
  "private": true,
  "workspaces": ["apps/*", "packages/*"]
}
```

根包通常应设置 `private: true`，避免误把整个仓库发布到 npm。这个约束看起来小，但在多人协作仓库里非常重要。

包发现规则要尽量简单清晰。过度复杂的 glob 容易让包被遗漏，或者把不该纳入 workspace 的目录纳入进来。

如果某个目录只是示例代码、脚本、临时实验或生成产物，就不应该轻易纳入 workspace。被纳入之后，它就会参与依赖安装、脚本执行和任务编排，反而会增加噪音。

## 本地链接

Workspace 最大的便利是本地包自动链接。应用依赖内部包时，可以直接引用 workspace 包。

```json
{
  "dependencies": {
    "@company/ui": "workspace:*"
  }
}
```

这样开发 `@company/ui` 时，`apps/admin` 可以立即使用本地版本，不需要先发布到 registry。对组件库、工具库、设计系统来说，这会让联调速度快很多。

本地链接也会暴露边界问题。比如 `ui` 是否需要先构建、是否输出类型声明、是否能被应用直接引用源码，都需要提前定规则。

如果内部包只提供源码入口，应用构建工具要能处理这些源码；如果内部包依赖 `dist`，就要保证开发时有 watch build 或任务编排。两种方式都可以，但要统一。

源码直连更方便调试，dist 依赖更接近发布形态。前者强调开发效率，后者强调边界清晰和构建稳定，选哪一种要看仓库规模和工具链能力。

## 依赖安装

Workspace 会在根目录统一安装依赖，并根据包之间关系建立链接。pnpm 还会通过内容寻址存储和严格依赖隔离减少幽灵依赖。

```bash
pnpm install
```

不要依赖“某个包没有声明依赖但因为根目录装了所以能用”的行为。每个 package 应声明自己真实使用的依赖，否则发布、构建和 CI 都可能出现环境差异。

幽灵依赖是 Workspace 里最常见的问题之一。本地可能因为根目录或兄弟包安装过依赖而正常运行，但发布到外部或独立构建时就会失败。

这类问题最难排查的地方在于“本地好像一直都没问题”。只有到 CI、独立打包或外部消费时才暴露，所以越早通过严格依赖模型把它拦下来越好。

## 脚本执行

Workspace 可以按包执行脚本，也可以按依赖图范围执行脚本。

```bash
pnpm --filter @repo/web dev
pnpm --filter @repo/ui build
pnpm -r test
```

`--filter` 适合只运行某个包，或者只运行某个变更范围内的任务。大型仓库中，所有任务都全量执行会非常慢，所以通常会和缓存、变更检测、任务编排一起使用。

过滤执行要理解方向。运行某个包自身任务、运行它依赖的包、运行依赖它的包，是三种不同范围，选错会导致漏测或浪费时间。

一旦团队开始大量使用过滤执行，就要把过滤语义写清楚并形成约定。否则每个人都按自己的理解写命令，最终很容易出现“本地跑过了，CI 还是漏了”的情况。

## 版本协议

`workspace:*`、`workspace:^`、`workspace:~` 用于表达本地包依赖关系。

| 协议 | 含义 |
| --- | --- |
| `workspace:*` | 使用工作区版本，发布时替换为具体版本 |
| `workspace:^` | 发布时使用兼容版本范围 |
| `workspace:~` | 发布时使用补丁兼容范围 |

应用包如果不会发布，使用 `workspace:*` 很常见；库包要发布到 npm 时，需要考虑版本范围对外部消费者的影响。

发布时 workspace 协议会被替换成实际 semver 范围。库包如果对外发布，版本范围要考虑兼容性；内部应用包则更关注本地联调便利。

这也意味着 workspace 协议不是“只在本地有效的小语法”，它会直接影响最终发布结果。对外发包的仓库尤其要理解这层转换关系。

## 根依赖与包依赖

根目录适合放工程工具，子包应声明运行所需依赖。

```txt
根依赖：eslint、typescript、turbo、prettier
包依赖：react、vue、lodash、业务 SDK
```

测试工具、格式化工具、构建编排工具可以放根目录统一管理。真正被代码 import 的依赖，应放在对应 package 的 `dependencies` 或 `devDependencies` 中。

判断依赖放哪里，可以问一句：这个包单独构建或发布时是否需要它。如果需要，就应该写在这个包自己的 `package.json` 里。

根依赖更像仓库级工具依赖，包依赖则是运行或构建这个包时真正不能少的东西。把两者混在一起，会让边界越来越模糊。

## 常见问题

| 问题 | 原因 | 处理 |
| --- | --- | --- |
| 本地包改了应用没更新 | 构建产物未刷新或入口指向 dist | 使用源码入口或 watch build |
| CI 能过本地不过 | 包管理器版本不一致 | 固定 packageManager |
| 发布后缺依赖 | 子包未声明依赖 | 补齐 package.json |
| 循环依赖 | 包边界设计不清 | 抽公共包或重划职责 |
| 全量任务太慢 | 未过滤任务范围 | 使用 filter 和缓存 |

Workspace 解决的是多包管理基础问题。真正的大型 Monorepo 还需要任务编排、缓存、版本发布和边界约束配合。

Workspace 做好后，Monorepo 才有继续上 Turborepo、Changesets、边界检查的基础。否则上层工具会被底层依赖混乱拖住。

Workspace 是否健康，可以看几个现象：

| 现象 | 说明 |
| --- | --- |
| 单个包独立构建时很少缺依赖 | 依赖声明较完整 |
| 本地联调不需要频繁手工 link | 工作区链接正常 |
| CI 和本地结果一致性较高 | 包管理基础稳定 |
| 新增包能快速接入统一脚本 | workspace 结构清晰 |
