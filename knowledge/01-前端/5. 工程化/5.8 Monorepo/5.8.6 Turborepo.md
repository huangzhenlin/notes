## 工具定位

Turborepo 是面向 JavaScript/TypeScript Monorepo 的任务编排和缓存工具。它不替代 pnpm、yarn 或 npm，也不替代构建工具，而是负责让多个包的任务按依赖关系高效执行。

```text
包管理器：安装依赖
构建工具：生成产物
Turborepo：编排任务和缓存结果
```

它适合包数量较多、构建测试任务重复、CI 时间变长的前端仓库。

Turborepo 最适合解决“重复执行太多”的问题。如果仓库只有一个应用、任务很少、CI 也很快，引入它的收益可能不如维护成本高。

它的价值通常不是在第一天就很明显，而是在仓库逐渐变大、任务越来越多时被放大出来。应用、组件库、工具包越多，重复任务越多，编排和缓存的收益就越明显。

## 任务声明

Turborepo 通过 `turbo.json` 描述任务关系、输入、输出和缓存策略。

```json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": []
    },
    "lint": {
      "outputs": []
    }
  }
}
```

`^build` 表示先执行依赖包的 `build`。这让任务顺序来自包关系，而不是靠脚本作者手动记住。

任务声明越准确，执行越稳定。`dependsOn` 管顺序，`outputs` 管产物，`inputs` 和环境变量管缓存正确性。

很多 Turborepo 问题表面看像“缓存有 bug”，根因其实是任务声明不完整。工具只会严格按声明工作，不会替项目猜测隐式依赖。

## 缓存输入

任务缓存依赖输入。输入包括源码、配置、锁文件、环境变量和命令本身。输入没变，输出可以复用。

```json
{
  "tasks": {
    "build": {
      "inputs": ["$TURBO_DEFAULT$", ".env.production"],
      "outputs": ["dist/**"]
    }
  }
}
```

如果构建依赖环境变量，但没有声明，缓存可能复用错误结果。缓存快是一把好刀，但输入边界必须准确。

对于前端构建，环境变量尤其敏感。API 地址、release 标识、feature flag 都可能进入产物，漏声明就可能跨环境复用错误缓存。

所以在前端项目里，缓存输入不仅要看源码文件，还要看构建配置、环境变量和框架约定。越靠近产物注入层，越不能省略输入声明。

## 输出目录

`outputs` 告诉 Turborepo 哪些文件是任务产物。构建任务通常有输出，lint 和 typecheck 通常没有稳定产物。

| 任务 | outputs |
|---|---|
| build | `dist/**`、`.next/**` |
| test | `coverage/**` 或空 |
| lint | 空 |
| typecheck | 空 |

声明输出能让缓存恢复真实产物。漏声明输出，会出现“任务命中缓存但产物不存在”的问题。

对于 Next、Vite、库构建，输出目录不同，要按项目实际配置。不要照抄示例里的 `dist/**`，否则缓存命中也可能没有恢复正确文件。

输出声明错了会直接影响开发体验。最常见的现象就是“日志显示命中缓存，但运行时目录里什么都没有”，这通常不是工具失效，而是 outputs 配置没写对。

## 远程缓存

远程缓存让 CI 和开发者共享任务结果。一个人或一条流水线构建过的结果，其他环境可以复用。

```text
开发者 A build
  -> 上传远程缓存
CI build
  -> 命中缓存
  -> 跳过重复构建
```

远程缓存适合大仓库，但要注意安全：不要把密钥、私有配置、未脱敏 source map 或敏感日志写入输出目录。

团队协作时，远程缓存能显著减少重复构建；但它也意味着产物会在多人和 CI 之间共享，所以输出目录必须保持干净。

远程缓存越好用，团队越要建立“输出目录只放可共享产物”的习惯。日志、密钥、局部临时文件一旦混进去，风险就会被放大。

## 过滤执行

Turborepo 支持按包和影响范围过滤任务。

```bash
turbo run build --filter=web
turbo run test --filter=...[HEAD^]
```

过滤能减少无关任务，但不能破坏依赖关系。受影响范围计算要覆盖被修改包和依赖它的上游包。

过滤命令要在真实 PR 上验证。看似少跑了很多任务，如果遗漏了依赖方测试，节省下来的时间会在事故里还回来。

过滤策略最好配合实际改动路径做几轮验证，确认“只改文档”“只改共享包”“只改应用页面”这几类常见场景下，受影响任务是否符合预期。

## 环境变量

环境变量会影响缓存正确性。Turborepo 提供配置让任务知道哪些变量参与缓存键。

```json
{
  "globalEnv": ["NODE_ENV"],
  "tasks": {
    "build": {
      "env": ["NEXT_PUBLIC_API_BASE"]
    }
  }
}
```

如果不同环境构建结果不同，就必须把对应变量纳入缓存输入。否则 staging 的产物可能被 production 复用。

生产和预发环境最怕缓存混用。环境变量进入产物时，要么纳入缓存键，要么让构建产物与环境无关，把运行时配置拆出去。

如果项目选择运行时注入配置，那么 Turborepo 层的缓存就可以更稳定；如果选择构建时注入配置，就必须更谨慎地建模环境变量输入。

## 适用边界

Turborepo 解决任务编排和缓存，不解决代码架构。包边界混乱、循环依赖严重、脚本不可复现，即使用了 Turborepo 也只是更快地暴露问题。

| 适合 | 不适合 |
|---|---|
| 多包构建 | 单包小项目强行引入 |
| CI 提速 | 替代包管理器 |
| 缓存重复任务 | 修复架构混乱 |
| 统一任务入口 | 替代测试和构建工具 |

Turborepo 和 [[5.8.4 任务编排|任务编排]]、[[5.8.3 包边界|包边界]] 是一套体系：先有清晰包边界，再用工具把执行效率提上来。

工具无法替代架构治理。包边界乱、脚本不可复现、依赖声明不完整时，Turborepo 只会更快地暴露这些问题。

判断 Turborepo 是否发挥了正向价值，可以看这些现象：

| 现象 | 说明 |
| --- | --- |
| 本地和 CI 的重复任务明显减少 | 编排和缓存生效 |
| 小改动不再触发大面积全量构建 | 过滤和依赖图合理 |
| 缓存命中后产物仍可直接使用 | outputs 声明较准确 |
| 很少再靠“重跑一次试试”解决问题 | 输入边界开始稳定 |
