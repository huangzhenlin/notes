## 边界目标

Monorepo 的包边界用于控制依赖关系、发布粒度和协作范围。包不是目录的高级写法，而是一个可以独立构建、测试、版本化和被其他包消费的单元。

```text
apps/admin
packages/ui
packages/utils
packages/config
```

边界清晰的包能降低耦合；边界混乱的包会让 monorepo 变成“大泥球仓库”。

包边界的价值在于让代码依赖关系可理解、可构建、可测试、可发布。边界不是为了多建目录，而是为了控制变化影响范围。

边界越清楚，团队越容易回答几个关键问题：这个能力应该放在哪个包、这个改动会影响哪些下游、这次发布会动到哪些消费者。反过来，边界一旦模糊，Monorepo 的协作成本会迅速上升。

## 职责划分

每个包应该有明确职责。常见类型包括应用包、组件包、工具包、配置包、领域包和 SDK 包。

| 包类型 | 示例 | 职责 |
|---|---|---|
| 应用包 | `apps/web` | 面向用户的完整应用 |
| UI 包 | `packages/ui` | 通用组件 |
| 工具包 | `packages/utils` | 无业务工具函数 |
| 配置包 | `packages/eslint-config` | 共享工程配置 |
| SDK 包 | `packages/api-client` | 接口客户端 |

不要把业务页面放进通用 UI 包，也不要让工具包依赖具体业务。

包职责越底层，越应该稳定、通用、少依赖业务。越靠近应用层，越可以承载具体业务规则和页面逻辑。

职责划分还要考虑变化节奏。变化频率完全不同的代码，如果被强行放在同一个包里，后续发布、缓存和测试往往都会变重。

## 依赖方向

包之间要有稳定依赖方向。应用包可以依赖 UI、utils、SDK；底层包不应该反向依赖应用。

```text
apps -> features -> ui / sdk -> utils
```

如果底层包需要调用业务能力，通常说明抽象方向错了。更好的方式是通过参数、回调、接口或事件把业务能力注入进去。

依赖方向稳定后，构建顺序、缓存命中和发布影响都更容易判断。反向依赖会让底层包被业务变化牵着走。

如果底层包频繁因为上层业务变化而改动，通常说明依赖方向已经出现了侵蚀。比起继续补例外，更值得先回头看抽象方向是不是反了。

## 公开入口

包应该通过公开入口导出能力，外部不要直接依赖内部文件。

```typescript
// packages/ui/src/index.ts
export { Button } from './Button';
export { Modal } from './Modal';
```

```typescript
import { Button } from '@acme/ui';
```

深层导入会破坏包边界：

```typescript
// 不推荐
import { Button } from '@acme/ui/src/Button';
```

一旦外部依赖内部路径，包就很难重构目录和拆分实现。

公开入口相当于包的契约。内部文件怎么组织可以变，但对外导出的 API 要尽量稳定，否则调用方会被实现细节绑住。

对外入口越稳定，内部就越有重构空间。反之，一旦大家都在深层路径里各自 import，任何目录调整都会变成大规模破坏性改动。

## 版本边界

包边界也决定发布边界。独立版本的包需要更严格的 semver、changelog 和兼容策略；内部应用包则可以更灵活。

| 包 | 发布要求 |
|---|---|
| 公共 npm 包 | 语义化版本、变更日志、类型稳定 |
| 内部共享包 | 兼容策略、迁移说明 |
| 应用包 | 以部署版本为主 |

包越公共，破坏性变更成本越高。对外暴露的 API 要克制。

内部包也不代表可以随意破坏。只要被多个应用依赖，它就需要迁移说明、兼容窗口或统一改动。

这也是为什么“内部包”不等于“低标准包”。只要它承载共享职责，就同样需要边界、版本和兼容意识。

## 循环依赖

包级循环依赖比文件级循环更危险，因为它会影响构建顺序、缓存和发布。

```text
packages/a -> packages/b -> packages/a
```

解决方式通常是抽出共同依赖、合并过度拆分的包、反转依赖方向，或者把共享协议放到独立包。

循环依赖往往说明两个包边界没有切对。不要只靠工具绕过循环，而要重新看职责是不是需要合并或抽象。

有些循环依赖其实是“过早拆包”的信号。两个包如果总是需要互相调用、互相等待构建、互相共享类型，可能本来就不应该分得那么开。

## 约束工具

包边界可以通过 ESLint、TypeScript path、包管理器约束和 monorepo 工具校验。

```json
{
  "dependencies": {
    "@acme/utils": "workspace:*"
  }
}
```

依赖要写在使用它的包自己的 `package.json` 中，不能依赖根目录或其他包“顺手带上”的依赖。

边界约束最好自动化。靠 code review 记住所有依赖规则很难，ESLint、包管理器约束和任务检查可以把规则变成可执行门禁。

边界规则越重要，越应该自动化。否则团队规模一大，review 很难长期靠人脑稳定守住所有 import 和依赖方向。

## 拆包判断

拆包要有明确收益，不要为了 monorepo 而 monorepo。

| 适合拆包 | 不适合拆包 |
|---|---|
| 多应用复用 | 只被一个页面使用 |
| 需要独立发布 | 变化频繁且强耦合 |
| 构建可独立缓存 | 边界还没稳定 |
| 团队独立维护 | 只是目录太长 |

包边界和 [[5.8.6 Turborepo|Turborepo]]、[[5.8.4 任务编排|任务编排]] 是配套关系。工具能提速，但前提是包边界本身清楚。

如果包边界不清楚，任务缓存可能复用错误结果，发布范围可能判断错误，团队协作也会变成互相踩目录。

一个实用的判断标准是：当某个包需要改动时，团队能否快速说清它的输入、输出、依赖方向和消费者。如果说不清，通常说明边界还不够稳定。
