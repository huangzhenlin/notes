## 结构目标

项目结构的目标是让代码位置和职责对应起来。好的结构能让团队快速判断一个文件应该放在哪里、模块之间能否互相依赖、页面和公共能力如何协作。

```text
src
├─ app
├─ pages
├─ features
├─ entities
├─ shared
└─ assets
```

结构不是越复杂越好。小项目需要清晰，大项目需要边界，过早分层会增加理解成本。

项目结构首先服务查找和修改。一个新人接到“改订单列表筛选条件”的任务，应该能比较快判断去哪里找页面、接口、状态、组件和测试。结构如果只在架构图上漂亮，但实际修改要全仓库搜索，就没有真正降低复杂度。

## 按类型组织

按类型组织是把组件、工具、样式、接口分别放到对应目录。

```text
src
├─ components
├─ hooks
├─ utils
├─ api
└─ styles
```

这种方式适合小项目、页面少、业务边界不复杂的应用。缺点是业务增长后，同一个功能散落在多个目录里，修改一个功能要来回跳。

按类型组织的优势是上手快，因为目录名和技术角色直接对应。它适合原型、小型后台、页面数量少的项目。等业务模块变多后，可以先在 `features` 或 `modules` 下按业务局部聚合，不一定要一次性重构全项目。

## 按业务组织

按业务组织把同一业务能力相关的页面、组件、接口和状态放在一起。

```text
src
├─ features
│  ├─ order
│  │  ├─ api
│  │  ├─ ui
│  │  └─ model
│  └─ user
└─ shared
```

它适合中大型项目。优点是业务聚合，缺点是需要提前定义公共层和业务层依赖方向。

按业务组织时，模块内部可以继续按类型分层。比如 `features/order/api`、`features/order/ui`、`features/order/model`。这样既能聚合业务，又不至于把所有文件混在一个目录里。

```text
features/order
├─ api
├─ model
├─ ui
└─ index.ts
```

## 分层边界

常见分层可以分为应用入口、页面、业务功能、业务实体、共享能力。

| 层 | 职责 |
|---|---|
| app | 应用启动、路由、全局配置 |
| pages | 路由页面组合 |
| features | 业务功能单元 |
| entities | 业务实体模型 |
| shared | 通用组件、工具、请求、样式 |

低层不应该依赖高层。例如 shared 不应该依赖某个具体 page，utils 不应该依赖业务页面。

分层边界还要配合导入规则。只靠目录约定不够，最好用 ESLint import rules、TypeScript path alias 或包边界工具限制反向依赖。否则结构会随着业务压力慢慢被绕开。

## 公共目录

公共目录最容易变成垃圾场。不是所有复用都应该放进 shared。只有通用、稳定、无业务绑定的能力才适合放公共层。

| 适合 shared | 不适合 shared |
|---|---|
| 基础按钮 | 某个订单弹窗 |
| 请求客户端 | 某个活动接口 |
| 日期格式化 | 临时业务规则 |
| 主题变量 | 页面专属样式 |

公共代码一旦被很多地方依赖，修改成本会很高。抽公共之前要确认它真的稳定。

公共目录里的名字要尽量具体。`shared/utils/index.ts` 这种大杂烩入口很容易变成所有东西的出口；更好的方式是按能力拆分，例如 `shared/date`、`shared/request`、`shared/ui`、`shared/config`。

## 入口文件

模块入口文件用于暴露公开 API，隐藏内部结构。

```typescript
// features/order/index.ts
export { OrderList } from './ui/OrderList';
export { useOrderQuery } from './model/useOrderQuery';
```

外部通过入口导入：

```typescript
import { OrderList } from '@/features/order';
```

不要让外部直接依赖内部深层路径，否则模块就无法自由重构。

入口文件也不应该暴露所有内部细节。它是模块的公开 API，而不是目录索引。只导出外部真正需要的组件、类型、hook 或 service，内部实现保持私有。

## 命名约定

命名约定要稳定。目录名、组件名、hook/composable、工具函数和测试文件都应有一致风格。

```text
UserCard.tsx
useUserQuery.ts
formatPrice.ts
formatPrice.test.ts
```

命名的目标是可搜索。不要大量使用 `common`、`base`、`helper` 这种含义过宽的名字。

命名还要表达层级。比如 `UserCard` 是业务组件，`BaseButton` 是基础组件，`useUserQuery` 是请求 hook，`formatPrice` 是纯工具函数。名字能表达职责，调用方就少看一层实现。

## 演进策略

项目结构应该随复杂度演进。早期可以简单，业务变复杂后再引入分层和包边界。

```text
小项目：按类型组织
中项目：按业务组织
大项目：业务分层 + monorepo 包边界
```

项目结构和 [[5.1.6 模块化|模块化]]、[[5.8.3 包边界|包边界]] 是连续关系：先有目录边界，再有模块边界，最后才需要包边界。

演进时不要一次性大搬家。可以先从高频业务域试点，把新结构跑通后，再逐步迁移其他模块。结构重构最怕同时改目录、改导入、改命名、改逻辑，这样回归成本会很高。
