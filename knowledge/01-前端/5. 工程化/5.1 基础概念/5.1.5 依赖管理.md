## 版本范围

语义化版本把版本号拆成主版本、次版本、补丁版本，但版本范围不是可靠性的全部。`^` 允许次版本和补丁版本升级，`~` 主要允许补丁版本升级，精确版本最可控但维护成本更高。

| 写法 | 含义 | 适合场景 |
| --- | --- | --- |
| `1.2.3` | 固定到具体版本 | 核心依赖、问题复现 |
| `~1.2.3` | 允许补丁升级 | 风险较低的修复 |
| `^1.2.3` | 允许次版本升级 | 常规应用依赖 |
| `>=1.2.0` | 宽范围匹配 | 库的 peer 兼容声明 |

项目真正的可复现安装依赖锁文件。`package.json` 表达意图，`package-lock.json`、`pnpm-lock.yaml` 或 `yarn.lock` 固定解析结果。CI 中应该使用锁文件安装命令，例如 `npm ci` 或 `pnpm install --frozen-lockfile`，避免构建时偷偷解析到新版本。

依赖管理不只是“装包”和“升级”，还包括版本范围控制、重复依赖排查、私有源管理和安全治理。一个前端项目一旦依赖变多，真正难的往往不是引入某个包，而是让这些包在团队里长期可控。

```text
先看四件事：
1. 依赖从哪里来
2. 版本怎么锁定
3. 是否存在重复和冲突
4. 升级时怎么回滚
```

依赖引入前也应该有判断。不要因为一个小函数就引入一个长期依赖，尤其是运行时依赖。可以先看包是否维护、体积是否合理、是否有 ESM、是否有类型、是否有安全历史和替代方案。

## 锁文件

锁文件记录直接依赖和间接依赖的实际版本、下载地址、完整性校验和依赖树结构。它不是“自动生成就不用管”的文件，而是保障多人协作、CI 构建和线上回滚一致性的核心资产。

```text
package.json      描述需要哪些依赖和允许范围
lockfile          描述本次解析出来的完整依赖图
node_modules      安装后的物理结果
```

锁文件冲突不能随手删掉重装。正确做法是确认双方改动的依赖意图，再用包管理器重新解析并运行测试。尤其是安全修复和框架升级同时出现时，锁文件变化可能很大，但真正需要关注的是核心包、构建工具和重复安装的版本。

如果依赖没有治理，常见问题会很快出现：本地能跑、CI 失败、线上包冲突、某个小版本升级后样式和逻辑一起变。这些问题大多不是代码本身写错，而是依赖边界没有设清楚。

锁文件应该提交到仓库，并由 CI 使用 frozen install 校验。如果锁文件和 `package.json` 不一致，CI 应该失败，而不是自动帮你重新解析依赖。

## 安装来源

依赖可以来自 npm registry、私有 registry、Git 仓库、本地路径和 tarball。来源越不标准，越需要考虑可追溯性和 CI 可用性。

```json
{
  "dependencies": {
    "@company/ui": "1.4.0",
    "local-kit": "file:../local-kit",
    "remote-kit": "github:org/remote-kit#main"
  }
}
```

生产项目不建议长期依赖 Git 分支或本地路径。分支会移动，本地路径在 CI 上可能不存在，tarball 难以审计。临时联调可以这样做，但发布前要回到明确版本和稳定源。

私有 registry 也要治理。比如内部组件库、工具包和业务 SDK 要有明确版本、发布记录和权限控制。否则内部依赖也会变成“谁都能发、谁都不敢升”的风险源。

## 重复依赖

前端项目常见体积问题不是“某个包很大”，而是同类包和多版本包重复存在。例如项目同时引入 `moment`、`dayjs`、`date-fns`，或者组件库和应用各自带了一份不同版本的工具库。

```bash
pnpm why lodash
npm ls react
```

排查重复依赖时，先确认是不是运行时重复，再确认是否能通过升级、依赖提升、peer 声明或替换方案解决。不要为了减少一个依赖而引入更复杂的封装层，依赖治理的目标是降低整体维护成本。

重复依赖不是一定要清零。构建工具依赖的内部版本通常不影响首屏；真正要优先处理的是进入浏览器产物的重复运行时依赖，比如多个日期库、多个图标库、多个样式运行时。

## 升级策略

依赖升级要按风险分批。补丁版本可以自动化但仍要测试；次版本需要关注默认行为变化；主版本要阅读迁移说明并在独立分支验证。框架、构建工具、路由、状态管理、测试框架这类核心依赖，不应该和几十个普通依赖混在一个提交里升级。

```text
推荐批次：
1. 安全补丁
2. 类型声明与开发工具
3. 普通运行时依赖
4. 构建工具与框架
5. 主版本迁移
```

如果升级后出现异常，批次越小越容易定位。依赖升级和 [[5.2.5 依赖版本|依赖版本]] 是同一个问题的两个层面：前者关注过程，后者关注版本表达和解析规则。

升级策略最好配合自动化工具，但不能完全交给自动化。Dependabot、Renovate 这类工具可以提出升级 PR，团队仍然要根据依赖类型、风险等级和测试结果决定是否合并。

## 安全治理

依赖安全不等于运行一次 `audit`。`audit` 能发现已公开漏洞，但无法判断包是否停止维护、是否被恶意接管、是否引入过宽权限、是否在安装脚本里做危险操作。前端依赖链很长，真正需要的是持续治理。

```bash
npm audit
pnpm audit
```

安全修复也要判断边界：开发依赖漏洞不一定影响生产运行，但构建链漏洞可能影响产物；间接依赖漏洞需要看是否真的可达；强行升级可能引入破坏性变更。这里和 [[1.6.7 依赖安全|依赖安全]] 相连，安全判断不能只停留在包管理器提示。

安全治理还要关注安装脚本。某些包在 `postinstall` 阶段会下载二进制或执行脚本，供应链风险不只发生在运行时，也可能发生在安装和构建阶段。

## CI 安装

CI 应该追求确定性、缓存友好和失败可定位。确定性来自锁文件和 frozen install；缓存友好来自包管理器缓存目录；失败可定位来自清晰的安装、检查、构建分步。

```yaml
steps:
  - run: corepack enable
  - run: pnpm install --frozen-lockfile
  - run: pnpm lint
  - run: pnpm test
  - run: pnpm build
```

不要在 CI 中默认执行无约束升级命令。CI 的职责是验证当前提交是否可靠，而不是在构建时改变依赖图。依赖升级应该通过明确的 PR、自动化机器人或人工维护流程进入项目。

依赖管理还要考虑开发依赖和生产依赖的边界。构建工具、测试框架、类型检查工具和 lint 工具通常属于开发依赖，但它们一旦出现漏洞或升级问题，也会影响构建链和发布链，所以不能简单地认为“devDependency 就不用管”。

对 monorepo 项目来说，依赖管理还会延伸到工作区复用、内部包版本策略和锁文件一致性。一个仓库里如果多个包各自维护一套依赖，很快就会出现版本漂移和重复安装。

CI 安装还要和缓存配合。缓存包管理器仓库可以加速安装，但不能缓存不可信的 `node_modules` 状态来跳过锁文件校验。速度和确定性之间，确定性优先。
