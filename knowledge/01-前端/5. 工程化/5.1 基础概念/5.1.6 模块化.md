## 模块边界

模块化的目标是把代码拆成有边界、可组合、可替换的单元。一个模块应该暴露清晰接口，隐藏内部实现。

```text
user/
  user.service.ts
  user.types.ts
  useUserList.ts
  UserTable.tsx
  index.ts
```

模块边界要按业务能力或技术职责划分，而不是只按文件类型划分。比如用户相关接口、类型、Hook、组件可以聚合在用户模块内，再通过统一入口向外暴露。

边界清楚的模块应该能回答三个问题：它提供什么能力，外部怎么使用，内部哪些东西不能被依赖。只拆目录不定义入口，外部仍然会到处深层导入，模块边界就只是表面结构。

## 导入导出

ES Modules 使用 `import` 和 `export` 表达依赖关系。命名导出适合多个能力，默认导出适合模块主能力。

```ts
export type User = {
  id: string;
  name: string;
};

export function getUserName(user: User) {
  return user.name;
}
```

```ts
import { getUserName, type User } from "./user";
```

统一导出入口可以降低外部依赖内部路径的风险。

```ts
export * from "./user.types";
export * from "./user.service";
export * from "./useUserList";
```

但公共入口不要无脑 `export *` 所有文件。暴露太多内部能力，会让模块失去边界。

导入导出还会影响 Tree Shaking。入口文件如果执行副作用，或者把大量无关模块聚合到一个大入口，构建工具可能很难安全裁剪。公共入口要尽量保持纯导出。

## 公共入口

公共入口是模块对外的门面。它能减少外部直接引用内部文件，也能让后续重构更安全。

```ts
// user/index.ts
export { UserTable } from "./UserTable";
export { useUserList } from "./useUserList";
export type { User } from "./user.types";
```

```ts
import { UserTable, useUserList } from "@/modules/user";
```

公共入口应该稳定、克制。不要把临时函数、内部工具、测试辅助都导出去。一个模块暴露的内容越多，后续修改越困难。

模块化不是为了拆文件，而是为了控制复杂度。拆分后如果依赖更乱、命名更散、入口更多，就不是好的模块化。

公共入口可以理解为模块契约。契约越稳定，内部越自由；契约越混乱，任何内部重构都会影响外部调用方。
## 工程边界

工程化里的模块化不只是 ES Module 语法，而是把项目拆成可理解、可测试、可复用、可替换的单元。模块边界越清晰，构建、测试、发布和协作越稳定。

```text
业务模块
  -> 组件
  -> 状态
  -> 接口
  -> 工具
  -> 样式
```

模块化的目标不是“文件很多”，而是让每个文件、目录、包都有明确职责。

工程边界还要体现在测试上。模块如果只能通过完整页面测试，说明边界可能太大；模块如果可以单独测试输入输出，说明它的职责更清楚。

## 依赖方向

模块之间应该有清晰依赖方向。基础能力可以被业务依赖，业务模块不应该反向污染基础层。

```text
shared -> entities -> features -> pages
```

如果 `shared` 依赖具体页面，说明层级被倒置了。依赖方向稳定，后续抽包、测试和构建都会更容易。

依赖方向可以通过路径规则约束。例如禁止 `shared` import `features`，禁止 `entities` import `pages`。靠口头约定很难长期保持，工具约束会更可靠。

## 公共模块

公共模块应该承载真正通用的能力，例如请求封装、日期处理、基础组件、设计 token、日志工具。不要把“两个地方刚好用了”立刻抽成公共模块。

| 可以公共化 | 谨慎公共化 |
|---|---|
| 请求客户端 | 某个业务弹窗 |
| 基础按钮 | 某个活动页组件 |
| 日期格式化 | 临时业务规则 |
| 权限判断基础函数 | 特定页面判断 |

过早公共化会让模块变成垃圾场。公共模块一旦被很多地方依赖，修改成本会迅速上升。

公共模块要先稳定再抽取。重复一次不急，重复两次观察，重复三次且边界一致时再公共化，通常比一看到重复就抽象更稳。

## 入口设计

模块应有清晰入口，外部通过入口访问，不直接依赖内部文件。

```typescript
// features/order/index.ts
export { OrderList } from './ui/OrderList';
export { useOrderQuery } from './model/useOrderQuery';
```

```typescript
import { OrderList } from '@/features/order';
```

入口文件是模块的公开 API。内部结构可以调整，只要入口稳定，外部影响就可控。

入口设计也适合配合别名路径。比如外部只允许从 `@/features/order` 导入，而不是从 `@/features/order/ui/OrderList` 导入。这样目录调整不会扩散到全项目。

## 循环依赖

循环依赖是模块化的常见坏味道。它通常意味着两个模块职责互相缠绕，或者抽象层级不清。

```text
A -> B -> C -> A
```

循环依赖可能导致初始化顺序异常、测试难写、构建警告和运行时 undefined。解决方式通常是抽出共同依赖、反转依赖方向或重新划分边界。

```text
处理循环依赖：
1. 抽出公共类型或工具
2. 把双向调用改成事件或参数注入
3. 重新划分业务模块
4. 把上层流程移动到更高层
```

不要只靠把 import 改成动态导入来“消除警告”。如果业务职责仍然互相缠绕，问题只是被藏起来了。

## 包级模块化

当目录边界不足以支撑协作时，可以升级到包级模块化，例如 Monorepo 中的 `packages/ui`、`packages/utils`、`apps/admin`。

```text
packages
├─ ui
├─ utils
└─ config
apps
└─ admin
```

包级模块化更强，但成本也更高：版本、构建、发布、依赖关系和测试都要管理。不要为了“看起来高级”过早拆包。

包级模块化适合多人协作、跨应用复用、独立发布和边界强约束。小项目如果只是为了目录好看就拆包，会增加构建、发布和调试成本。

## 构建影响

模块化会影响 tree shaking、代码分割、缓存和包体积。如果模块入口有副作用，或者把所有东西都从一个大入口导出，构建工具很难优化。

```typescript
// 更利于按需导入
export { Button } from './Button';
export { Modal } from './Modal';
```

模块化和 [[6.4.5 依赖分析|依赖分析]] 是互相影响的：依赖图越清晰，包体积问题越容易定位。

构建层面还要避免“桶文件”带来的副作用。如果一个入口导出了所有组件，并且每个组件又引入样式或注册逻辑，按需引入就可能失效。模块越清晰，构建优化越容易。
