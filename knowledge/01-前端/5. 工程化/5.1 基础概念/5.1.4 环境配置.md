## 配置目标

环境配置用于管理不同运行环境下的差异，例如接口地址、日志级别、监控开关、构建模式、CDN 地址、功能开关和鉴权回调地址。

```text
同一套代码
  -> local
  -> test
  -> staging
  -> production
```

环境配置的目标是让差异显式、可验证、可追踪，而不是把 `if` 散落在业务代码中。

环境配置最怕两件事：一是配置太散，二是配置语义不清。比如同一个项目里既有 `.env`、又有运行时注入、又有远程配置，如果没有统一优先级，最后谁覆盖谁就会变成猜谜。

环境配置应该有明确优先级。比如基础配置提供默认值，环境文件覆盖部署差异，运行时配置覆盖同产物多环境，远程配置控制灰度开关。优先级一旦写清，排查配置问题就会快很多。

```text
base config
  -> mode config
  -> runtime config
  -> remote feature flags
```

## 配置来源

配置来源可以是环境变量、配置文件、远程配置、构建参数和运行时注入。

| 来源 | 适合场景 |
|---|---|
| 环境变量 | 构建和部署差异 |
| `.env` 文件 | 本地开发 |
| 远程配置 | 功能开关、灰度 |
| 运行时注入 | 同产物多环境 |
| 代码常量 | 不随环境变化的固定值 |

不要把所有配置都放进 `.env`。真正稳定的业务常量写在代码里更清晰。

并不是所有“可变内容”都应该放环境配置。页面文案、业务枚举、固定阈值如果本质上不随环境变化，直接写在代码或单独配置模块里会更清楚。环境变量适合放环境差异，不适合把整个项目都伪装成“可配置系统”。

配置来源越多，越要集中读取。业务代码不应该到处直接读 `import.meta.env` 或 `process.env`，最好通过统一 `config` 模块暴露已经校验过的结果。

## 配置分层

配置可以按基础配置、环境覆盖、运行时覆盖分层。

```typescript
const baseConfig = {
  requestTimeout: 8000,
  enableDebugPanel: false,
};

const envConfig = {
  production: {
    enableDebugPanel: false,
  },
  development: {
    enableDebugPanel: true,
  },
};
```

分层可以避免每个环境重复写完整配置，也能明确哪些值是默认值、哪些值是环境差异。

分层还可以帮助排查问题。启动时先看基础配置，再看环境覆盖，最后看运行时注入，基本就能知道某个值是在哪一层被改掉的。没有分层，调试环境问题时往往只能一层层翻代码。

```ts
export const config = {
  apiBase: import.meta.env.VITE_API_BASE,
  release: import.meta.env.VITE_RELEASE,
  enableMock: import.meta.env.VITE_ENABLE_MOCK === "true",
};
```

对外暴露布尔值、数字和枚举时，应该在配置层完成转换，不要让业务页面自己判断字符串。

## 配置校验

配置缺失应该在启动或构建阶段失败，而不是上线后才在某个页面报错。

```typescript
function assertConfig(config: Record<string, unknown>) {
  if (typeof config.apiBase !== 'string') {
    throw new Error('missing apiBase');
  }
}
```

配置校验适合放在应用初始化和 CI 构建验证中。越早失败，越容易修。

校验不只是检查“有没有值”，还要检查值是否合理。比如接口地址格式、开关类型、端口范围、CDN 前缀、主题名是否合法，都应该尽量在启动时暴露，而不是等用户打开页面后再报错。

可以用 schema 工具或手写函数校验配置。关键是失败要早、错误要清楚。比如缺少 `VITE_API_BASE` 时，构建阶段直接失败，比线上请求发到 `undefined/api` 好得多。

## 公开与私有

前端配置必须区分公开配置和私有配置。公开配置可以进入浏览器，私有配置必须留在服务端。

| 公开配置 | 私有配置 |
|---|---|
| API base URL | 数据库密码 |
| release | 第三方 Secret |
| feature flag | 服务端 token |
| 监控 DSN 公共部分 | 签名密钥 |

配置不是因为写在 `.env` 里就安全。是否安全取决于它是否进入客户端产物。

公开配置和私有配置的分界，最好在工程层面就写清楚。什么可以被前端读取、什么只能在服务端使用、什么必须通过中转接口暴露，这些边界越明确，安全风险越低。

如果需要让前端使用第三方能力，尽量使用公开 key、临时凭证或服务端代理，不要把长期密钥注入前端。前端能看到的配置，都应该被当成公开信息。

## 功能开关

功能开关是环境配置的重要应用。它可以控制新功能是否启用、灰度人群、降级路径和紧急关闭。

```typescript
if (config.features.newCheckout) {
  renderNewCheckout();
} else {
  renderLegacyCheckout();
}
```

功能开关要有生命周期。长期不清理的开关会让代码分支越来越复杂，最后变成维护负担。

功能开关适合灰度、回滚和实验，但不适合永久分叉业务逻辑。一个开关如果已经稳定上线并且长期不再切换，就应该考虑收敛掉旧分支，避免代码越来越难读。

功能开关要配套命名和清理计划。比如 `newCheckoutEnabled` 比 `flag1` 清楚，开关上线后要记录负责人和预计清理时间。否则项目里会沉积大量没人敢删的分支。

## 部署关系

环境配置和部署流程要对齐。部署到哪个环境，就应该加载对应配置，并在产物或监控中标记环境。

```text
build artifact
  -> environment config
  -> deployment
  -> monitoring context
```

环境配置和 [[5.9.2 环境变量|环境变量]]、[[5.7.3 构建验证|构建验证]] 紧密相关：变量提供输入，配置组织输入，构建验证确认输入正确。

如果项目同时有本地开发、预发、灰度和生产，最好让环境名称和部署平台术语一致。命名不一致会让大家在排查问题时来回翻译，最后连“哪个环境出了问题”都说不清。

部署后还要把环境信息写入监控上下文。错误、性能、接口失败如果能按环境、版本、灰度批次筛选，排查就不会把预发和生产混在一起。
