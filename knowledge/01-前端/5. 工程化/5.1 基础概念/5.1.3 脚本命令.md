## 命令入口

`package.json` 的 `scripts` 是前端项目最重要的协作入口。它把开发、构建、测试、校验、预览、发布等动作封装成统一命令，让团队不必记住底层工具参数。

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "lint": "eslint src",
    "typecheck": "tsc --noEmit",
    "test": "vitest run"
  }
}
```

脚本命名要稳定。`dev` 应该总是启动本地开发，`build` 应该总是产出可交付文件，`test` 应该总是运行测试，`lint` 应该总是检查代码风格或潜在问题。同一个命令在不同项目里含义漂移，会增加协作成本。

脚本还应该把“常用动作”和“底层工具”隔开。团队成员只需要记住 `pnpm dev`、`pnpm verify`、`pnpm build`，底层到底是 Vite、Webpack、Vitest 还是 Playwright，可以由脚本隐藏。

## 分层设计

脚本要按使用频率和执行成本分层。高频命令要短、快、反馈清楚；低频命令可以更严格，交给 CI 或发布流程执行。

| 层级 | 命令 | 目标 |
| --- | --- | --- |
| 开发 | `dev`、`test:watch` | 快速反馈 |
| 本地校验 | `lint`、`typecheck` | 提交前发现问题 |
| CI 验证 | `verify`、`build` | 稳定阻断 |
| 发布 | `release`、`deploy` | 权限和环境更严格 |

不要让 `dev` 默认执行大量全量检查，也不要让 `build` 依赖开发者本地未提交文件。命令越清晰，问题越容易定位。

一个常见结构是：`dev` 追求快，`verify` 追求全面，`ci` 追求可复现，`release` 追求安全。不同命令目标不同，就不会互相拖累。

## 环境变量

脚本经常需要区分开发、测试、预发和生产环境。环境变量要显式、可复现，并考虑跨平台差异。Windows、macOS、Linux 对 shell 语法和环境变量写法并不完全一致。

```json
{
  "scripts": {
    "dev:mock": "cross-env MOCK=true vite",
    "build:staging": "vite build --mode staging",
    "build:prod": "vite build --mode production"
  }
}
```

环境变量不要承载敏感密钥。前端构建时注入的变量最终可能进入浏览器产物，不能把服务端密钥、数据库密码、私有 token 放进去。脚本只应该选择模式和开关，真正的敏感能力放在服务端。

环境脚本要避免依赖某个系统的 shell 写法。比如 `NODE_ENV=production vite build` 在 Windows 默认 shell 下可能不稳定，跨团队项目更适合用 `cross-env` 或工具自身的 `--mode`。

## 组合命令

组合命令适合表达固定流程，例如校验、构建前检查、发布前准备。组合时要注意失败即停止，避免前一步失败后继续执行后续危险动作。

```json
{
  "scripts": {
    "verify": "npm run lint && npm run typecheck && npm run test",
    "prebuild": "npm run verify",
    "build": "vite build"
  }
}
```

`prebuild`、`postbuild` 这类生命周期脚本会自动触发，适合稳定流程，但不要塞入隐蔽副作用。比如 `postinstall` 自动下载二进制、修改本地配置、启动服务，都可能让安装过程变得不可预测。

组合命令最好有清楚的失败边界。比如 `verify` 失败就不应该继续 `build`，发布命令失败就不应该继续上传产物。命令链越接近发布，越不能吞错误。

## 跨平台兼容

脚本越依赖 shell 特性，跨平台风险越高。路径分隔符、环境变量、删除命令、重定向、引号规则在不同系统上都可能不一致。

```json
{
  "scripts": {
    "clean": "rimraf dist",
    "dev:host": "vite --host 0.0.0.0"
  }
}
```

对于团队协作项目，优先使用跨平台工具，例如 `cross-env`、`rimraf`、`shx`，或者把复杂逻辑放到 Node 脚本里。简单命令直接写在 `scripts` 里，复杂流程不要硬挤成一行 shell 魔法。

当脚本超过一行、包含多层条件或需要读写文件时，通常应该提取成脚本文件。`package.json scripts` 适合做入口，不适合承载复杂业务逻辑。

## 工作区命令

Monorepo 中脚本命令还要考虑工作区。根目录命令负责全局编排，子包命令负责局部能力。不要让每个包都用完全不同的脚本命名。

```json
{
  "scripts": {
    "build": "pnpm -r build",
    "test": "pnpm -r test",
    "build:web": "pnpm --filter @app/web build"
  }
}
```

工作区命令要避免无意义全量执行。组件库改动可能不需要构建所有应用，文档改动可能不需要跑全部端到端测试。这里和 [[5.2.6 workspace|workspace]] 的边界相连：脚本是工作区协作的入口，依赖图决定哪些任务真的需要执行。

工作区脚本最好支持过滤和增量。比如只构建受影响包、只测试某个应用、只发布变更包。Monorepo 项目如果每次都全量执行，规模一大就会拖慢所有人。

## CI 对齐

本地命令和 CI 命令要尽量复用。CI 不应该有一套只有流水线知道的神秘命令，否则本地无法复现失败；本地也不应该绕过 CI 必跑检查。

```yaml
steps:
  - run: pnpm install --frozen-lockfile
  - run: pnpm verify
  - run: pnpm build
```

当 CI 失败时，开发者应该能在本地运行同一个脚本复现。脚本命令的价值就在这里：它把“怎么验证项目”变成仓库内可执行的约定，而不是散落在口头说明里。

CI 对齐还意味着脚本输出要清晰。失败时应该能看出是 lint、类型、测试还是构建失败，而不是一个巨大命令报一屏日志。分步执行比一个黑盒命令更利于定位。

## 安全边界

脚本命令拥有本地文件系统和环境变量访问能力，不能把它当成无害文本。尤其是 `postinstall`、`prepare`、`release`、`deploy` 这类命令，要审查它们是否会访问网络、修改文件、读取密钥或影响发布。

```json
{
  "scripts": {
    "release": "npm run verify && npm run build && changeset publish"
  }
}
```

对开源依赖和内部包都要关注安装脚本风险。依赖治理不仅是版本问题，也包括脚本执行边界，这部分会影响 [[5.1.5 依赖管理|依赖管理]] 和 [[1.6.7 依赖安全|依赖安全]]。

高风险脚本要减少自动触发。比如 `deploy`、`release`、`publish` 不应该被普通安装或构建间接触发，最好需要明确命令和权限。脚本越靠近外部服务，越要显式。
