## 核心模型

pnpm 的核心特点是内容寻址存储、硬链接复用和严格的 `node_modules` 结构。它不会像传统 npm 那样为每个项目复制一份完整依赖，而是把依赖内容放入全局 store，再通过链接组织到项目中。

```text
全局 store
  -> 硬链接到项目 node_modules/.pnpm
  -> 符号链接形成依赖可访问结构
```

这个模型带来的直接收益是安装更快、磁盘占用更少、依赖边界更清晰。多个项目使用同一个版本的依赖时，pnpm 可以复用已经下载和解压过的内容；每个项目仍然拥有自己的依赖视图，不会因为共享 store 而混在一起。

pnpm 的“快”不是魔法，而是减少重复下载、重复解压和重复存储。对单个小项目来说差异可能不夸张；对多个应用、多个包、频繁 CI 安装的团队来说，收益会明显放大。

```text
npm/yarn 传统思路：每个项目安装一份依赖
pnpm 思路：内容进入 store，项目通过链接形成依赖视图
```

## 内容寻址存储

内容寻址存储不是按“项目”保存依赖，而是按“包内容”保存依赖。同一个包的同一个版本在机器上通常只需要存一份，项目里的 `node_modules` 只是指向这份内容。

```bash
pnpm store path
pnpm store prune
```

`pnpm store path` 可以查看 store 位置，`pnpm store prune` 可以清理不再被项目引用的包内容。团队排查“为什么磁盘突然变大”时，可以先区分项目的 `node_modules` 和全局 store，不要简单删除所有项目依赖再重装。

内容寻址也让缓存更稳定。CI 中可以缓存 pnpm store，而不是直接缓存整个 `node_modules`。前者更通用，后者更容易因为平台、Node 版本或锁文件变化而失效。

## node_modules 结构

pnpm 的 `node_modules` 更严格。依赖不能随意访问没有声明的包，这能暴露“幽灵依赖”问题。

```text
幽灵依赖：代码 import 了某个包，但 package.json 没有声明它
```

传统扁平化 `node_modules` 可能因为间接依赖刚好存在，让项目在本地能跑；换机器、升级依赖或进入 CI 后就失败。pnpm 的严格结构能更早发现这种问题。

```javascript
// 如果 left-pad 没有写入当前包的 package.json，pnpm 下更容易暴露问题
import leftPad from "left-pad";
```

如果项目从 npm 或 Yarn 迁移到 pnpm 后报“找不到包”，通常不是 pnpm 出错，而是原项目依赖声明不完整。正确做法是把真实使用的包补进对应 package 的 `dependencies` 或 `devDependencies`。

幽灵依赖暴露出来通常是好事。它说明项目原本依赖了“刚好被别的包带进来”的间接依赖。pnpm 让这种隐患更早失败，而不是等到依赖升级或 CI 环境变化时才炸。

## 工作区

pnpm 的 workspace 能管理 Monorepo 里的多个包。根目录通过 `pnpm-workspace.yaml` 声明哪些目录属于工作区。

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

```text
apps/admin        应用
apps/mobile       应用
packages/ui       组件库
packages/utils    工具库
```

工作区让本地包之间可以直接互相依赖，不需要先发布再安装。比如 `apps/admin` 依赖 `packages/ui` 时，可以使用 workspace 协议表达本地依赖关系。

```json
{
  "dependencies": {
    "@company/ui": "workspace:*"
  }
}
```

这类本地链接和 Monorepo 工作区是同一条线：包管理器负责识别包、链接依赖、统一安装，任务编排工具再负责按依赖图运行构建和测试。

`workspace:*` 还能防止误装 registry 上的同名包。内部包如果没有用 workspace 协议，可能在某些情况下被解析成远端版本，导致本地联调和 CI 行为不一致。

## 常用命令

pnpm 的基础命令和 npm 类似，但在 workspace 场景下更强。

| 命令 | 作用 |
| --- | --- |
| `pnpm install` | 安装依赖 |
| `pnpm add react` | 安装运行依赖 |
| `pnpm add -D vite` | 安装开发依赖 |
| `pnpm remove lodash` | 移除依赖 |
| `pnpm run build` | 执行当前包脚本 |
| `pnpm -r build` | 对工作区内所有包递归执行 build |
| `pnpm --filter admin dev` | 只在匹配包执行命令 |

```bash
pnpm --filter @company/admin dev
pnpm --filter @company/ui build
pnpm -r test
```

`--filter` 不只是“按名字筛选”，也可以在大型仓库中缩小任务范围。真实项目里通常会把它和变更检测、缓存、CI 矩阵组合使用，避免每次提交都全量构建。

```bash
pnpm --filter @company/ui... build
pnpm --filter "...@company/ui" test
```

过滤语法可以表达依赖和被依赖关系。组件库改动时，通常不仅要构建组件库，也要验证依赖它的应用。

## 锁文件

pnpm 使用 `pnpm-lock.yaml` 锁定完整依赖图。锁文件记录直接依赖、间接依赖、解析版本和完整性信息，保证本地、同事机器和 CI 安装出一致结果。

```bash
pnpm install --frozen-lockfile
```

CI 中通常使用 `--frozen-lockfile`，如果 `package.json` 与 `pnpm-lock.yaml` 不一致，就让流水线失败。这比“自动更新锁文件继续构建”更安全，因为依赖漂移会让问题隐藏到上线之后。

锁文件冲突时，不要直接删除 `pnpm-lock.yaml`。正确做法是确认 `package.json` 的依赖意图，重新执行安装生成一致锁文件，再跑测试和构建。删锁文件会让整个依赖图重新解析，风险更大。

## 依赖类型

pnpm 不改变 npm 依赖类型的语义，但严格结构会让依赖类型错误更容易暴露。

| 字段 | 适合内容 | 常见问题 |
| --- | --- | --- |
| `dependencies` | 运行时需要的包 | 写到 `devDependencies` 后发布缺包 |
| `devDependencies` | 构建、测试、类型检查工具 | 被运行时代码 import |
| `peerDependencies` | 插件、组件库要求宿主提供的包 | 版本范围过窄导致安装冲突 |
| `optionalDependencies` | 可选能力依赖 | 没有兜底逻辑导致运行失败 |

组件库、插件库尤其要认真处理 `peerDependencies`。例如 React 组件库通常不应该把 React 打进自己的运行依赖里，而是要求业务项目提供 React，避免页面中出现多个 React 副本。

pnpm 对 peer 依赖也更敏感。peer 范围过窄会导致安装警告或重复实例，范围过宽又可能隐藏不兼容。组件库发布前应该在多个宿主版本下验证 peer 依赖。

## 脚本编排

pnpm 支持递归执行脚本，适合在 Monorepo 中统一构建、测试和发布。

```json
{
  "scripts": {
    "build": "pnpm -r build",
    "test": "pnpm -r test",
    "lint": "pnpm -r lint"
  }
}
```

```bash
pnpm --filter @company/ui build
pnpm --filter "...[origin/main]" test
```

脚本编排和 [[5.8.4 任务编排|任务编排]]、[[5.8.5 版本发布|版本发布]] 是一条线：pnpm 负责执行，工作区负责聚合，发布工具负责版本化。项目变大后，通常会继续接入 Turborepo、Nx 或 CI 缓存，让“只跑受影响任务”成为默认策略。

pnpm 自身能完成递归执行，但它不负责高级缓存和远程任务调度。大型仓库通常让 pnpm 管安装和 workspace，让 Turborepo 或 Nx 管任务缓存，这样职责更清楚。

## 选择边界

pnpm 适合依赖多、项目多、希望安装更快并控制幽灵依赖的团队。对于 Monorepo，它通常比传统 npm 更舒服，因为工作区、本地链接和严格依赖模型能一起发挥作用。

迁移到 pnpm 前要重点检查三件事：第一，代码是否依赖未声明的包；第二，构建脚本是否假设了扁平化 `node_modules`；第三，CI 是否固定了包管理器版本。可以在根 `package.json` 中声明 `packageManager`，让团队和流水线使用一致的 pnpm 版本。

```json
{
  "packageManager": "pnpm@9.15.0"
}
```

如果项目非常小、没有多包协作、团队也没有幽灵依赖困扰，npm 已经足够；如果项目进入多应用、多包、多团队协作阶段，pnpm 的收益会更明显。

迁移 pnpm 时建议先在分支上跑完整链路：安装、开发启动、类型检查、单元测试、构建、E2E、发布预览。尤其要关注构建脚本是否假设扁平 node_modules，以及某些老工具是否能正确解析符号链接。
