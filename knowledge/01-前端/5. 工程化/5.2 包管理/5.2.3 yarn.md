## 版本体系

Yarn 不是只有一个形态。Yarn Classic 通常指 Yarn 1，Modern Yarn 通常指 Yarn 2+。它们在安装模型、配置文件、Workspace 能力和 Plug'n'Play 支持上差异明显。

| 版本 | 特点 |
|---|---|
| Yarn 1 | 使用传统 `node_modules`，生态兼容强 |
| Yarn 2+ | 默认支持 PnP、Zero-Installs、约束和更强 Workspace |

项目里选择 Yarn 时，首先要明确团队使用的是哪个大版本。很多命令和配置在 Yarn 1 与 Yarn 2+ 中并不完全相同。

Yarn 1 的优势是稳定、兼容强、迁移成本低；Yarn 2+ 的优势是 workspace、PnP、约束和可复现能力更强。两者名字相同，但工程体验差异很大，团队文档和 CI 必须写清具体版本。

## 安装模型

Yarn 现代版本支持多种安装模型，其中最有代表性的是 `node_modules` 和 Plug'n'Play。

```yaml
nodeLinker: node-modules
```

```yaml
nodeLinker: pnp
```

PnP 不再生成传统巨大 `node_modules`，而是通过加载器让工具直接解析依赖位置。它速度快，也能暴露幽灵依赖，但部分工具需要额外适配。

如果团队使用很多老工具、脚手架插件或依赖直接扫描 `node_modules` 的工具，PnP 可能需要额外配置。此时可以选择 Yarn 现代版本的 `node-modules` 模式，在保留新版 Yarn 能力的同时降低兼容成本。

## 锁文件

`yarn.lock` 用来锁定依赖解析结果，保证团队和 CI 安装一致。

```bash
yarn install --immutable
```

`--immutable` 会在锁文件需要变更时失败，适合 CI 环境。它能防止“本地没更新锁文件，CI 却悄悄重新解析依赖”的问题。

Yarn 现代版本还常配合 Corepack 固定包管理器版本。这样团队不需要全局手动安装某个 Yarn 版本，仓库可以通过 `packageManager` 声明自己的工具链。

```json
{
  "packageManager": "yarn@4.5.0"
}
```

## Workspaces

Yarn Workspaces 允许在一个仓库中管理多个包，并共享一份锁文件。

```json
{
  "private": true,
  "workspaces": [
    "packages/*",
    "apps/*"
  ]
}
```

工作区包之间可以互相依赖：

```json
{
  "dependencies": {
    "@acme/ui": "workspace:*"
  }
}
```

`workspace:` 协议表达的是“使用当前工作区里的包”，这比手动 `link` 更稳定，也更适合 monorepo。

Yarn workspace 适合多包仓库统一依赖、统一脚本和统一发布。大型仓库里，它的约束能力可以帮助团队避免内部包版本漂移。

## Zero-Installs

Zero-Installs 是 Yarn 现代版本的一个重要实践：把 `.yarn/cache` 等安装产物提交到仓库，让拉取代码后几乎不需要重新下载依赖。

```text
仓库
├─ .yarn/cache
├─ .pnp.cjs
└─ yarn.lock
```

它的优点是 CI 更快、安装更可复现；代价是仓库会变大，依赖升级会产生更多二进制缓存变更。是否启用要看团队规模、CI 成本和代码仓库管理习惯。

Zero-Installs 适合对安装确定性和离线能力要求很高的团队，但不是所有项目都需要。小团队如果不想让仓库变大，使用普通锁文件和 CI 缓存也完全可以。

## 依赖约束

Yarn 现代版本支持约束和规则，用来统一 Workspace 内依赖版本、字段和包约定。

```text
约束目标：
1. 所有包使用同一 React 版本
2. 每个包都有 license
3. 禁止依赖某些已废弃库
```

这类能力适合大型 monorepo。小项目不一定需要，但当包数量变多后，自动约束比人工 review 稳定得多。

约束能把“团队约定”变成可执行规则。比如禁止多个 React 版本、要求所有包都有 `type` 字段、要求内部包统一使用 workspace 协议。包越多，约束越有价值。

## 常用命令

```bash
yarn install
yarn add react
yarn remove lodash
yarn workspace web build
yarn workspaces foreach --all run test
```

Yarn 2+ 中许多 npm 相关命令位于 `yarn npm` 命名空间下，例如发布包时使用 `yarn npm publish`。跨版本项目要格外注意命令差异。

```bash
yarn workspaces foreach -A run build
yarn workspaces foreach --since run test
```

现代 Yarn 的 workspace 命令适合做批量构建和变更范围执行，但具体参数和版本有关，项目里最好统一封装成 `package.json scripts`。

## 选择边界

Yarn、pnpm、npm 都能完成包管理。选择 Yarn 的常见理由是团队已有 Yarn 基础、需要 PnP/Zero-Installs、或希望在 workspace 里使用更强的约束能力。

| 场景 | 判断 |
|---|---|
| 老项目稳定运行 | Yarn 1 可继续维护 |
| 现代 monorepo | Yarn 2+ 或 pnpm |
| 强依赖兼容性 | `node_modules` 模式更稳 |
| 极致可复现 | PnP + Zero-Installs |

包管理工具不是孤立选择，它会影响 [[5.7.1 流水线|流水线]]、缓存策略、依赖安全和 monorepo 任务编排。

如果项目已经稳定使用 Yarn 1，不一定要为了“现代”立刻迁移；如果项目准备建设大型 monorepo、希望更强约束和可复现安装，Yarn 现代版本值得评估。选型关键不是工具名，而是安装模型、团队习惯和工程链路是否匹配。
