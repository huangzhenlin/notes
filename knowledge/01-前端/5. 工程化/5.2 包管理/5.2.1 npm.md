## 工具定位

npm 同时指 npm registry、npm CLI 和 Node 包生态。前端项目使用 npm 来安装依赖、运行脚本、发布包和管理锁文件。

```text
package.json
  -> npm install
  -> package-lock.json
  -> node_modules
```

npm 是最基础的包管理工具，理解它有助于再理解 pnpm、yarn 和 monorepo 工具。

npm 的优势是默认、通用、生态兼容性强。Node 安装后通常自带 npm，几乎所有前端工具都会优先保证 npm 可用。即使团队最终使用 pnpm 或 Yarn，也应该理解 npm 的依赖字段、semver、锁文件和脚本生命周期，因为这些是整个 Node 包生态的共同基础。

```text
npm 负责：
1. 解析依赖版本
2. 安装 node_modules
3. 运行 scripts
4. 发布包到 registry
5. 执行安全审计
```

## package.json

`package.json` 是项目依赖和脚本的核心描述文件。

```json
{
  "name": "web-app",
  "version": "1.0.0",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest"
  },
  "dependencies": {
    "react": "^19.0.0"
  },
  "devDependencies": {
    "typescript": "^5.0.0"
  }
}
```

`dependencies` 是运行时依赖，`devDependencies` 是开发和构建依赖。前端构建依赖虽然不进浏览器运行，但会参与 CI 和产物生成，仍然有供应链风险。

依赖字段要表达真实使用位置。运行时代码会 import 的包放 `dependencies`；只在构建、测试、类型检查、代码生成时使用的包放 `devDependencies`；组件库和插件库通常还要认真声明 `peerDependencies`，避免把宿主框架打包成多份。

```json
{
  "peerDependencies": {
    "react": ">=18"
  },
  "devDependencies": {
    "react": "^19.0.0"
  }
}
```

这里 `peerDependencies` 表达使用方必须提供 React，`devDependencies` 表达组件库自身开发和测试也需要 React。

## 锁文件

`package-lock.json` 锁定实际安装版本，保证安装结果可复现。

```bash
npm ci
```

CI 中应优先使用 `npm ci`，它会根据锁文件安装，并在锁文件和 `package.json` 不一致时失败。

| 命令 | 适合场景 |
|---|---|
| `npm install` | 本地新增或更新依赖 |
| `npm ci` | CI 和干净安装 |

`npm ci` 会删除现有 `node_modules` 后重新安装，适合 CI、容器构建和可复现环境。本地日常新增依赖时使用 `npm install 包名`，因为它会更新 `package.json` 和 `package-lock.json`。

```bash
npm install axios
npm install -D vitest
npm uninstall lodash
```

不要在 CI 里用无约束的 `npm install` 来“顺便更新锁文件”。CI 的职责是验证当前提交，不应该改变依赖图。

## 语义化版本

npm 依赖版本常用 semver 范围。

| 写法 | 含义 |
|---|---|
| `1.2.3` | 固定版本 |
| `^1.2.3` | 允许 minor/patch 升级 |
| `~1.2.3` | 允许 patch 升级 |
| `*` | 任意版本 |

版本范围影响安装解析，锁文件影响最终安装结果。不要只看 `package.json`，还要看锁文件变化。

`^` 是 npm 默认常见写法，但并不代表绝对安全。很多包虽然遵守 semver，但次版本仍可能改变默认行为。核心框架、构建工具、路由、状态管理、组件库升级时，即使只是 minor，也应该阅读 release notes 并跑完整验证。

## 脚本生命周期

npm 支持脚本和生命周期钩子，例如 `preinstall`、`postinstall`、`prepare`。

```json
{
  "scripts": {
    "prepare": "husky",
    "build": "vite build"
  }
}
```

生命周期脚本能力很强，也有安全风险。新增依赖时，如果它带有 install 脚本，要额外留意。

生命周期脚本也会影响团队体验。比如 `prepare` 常用于 Husky 初始化，`postinstall` 常用于补丁或生成文件，但它们会在安装时自动执行。如果脚本访问网络、写文件或依赖本机环境，安装就会变得不可预测。

```text
适合生命周期：轻量初始化、生成必要类型
谨慎生命周期：下载二进制、修改配置、启动服务
```

## workspaces

npm 也支持 workspaces，用于管理多包仓库。

```json
{
  "workspaces": [
    "packages/*",
    "apps/*"
  ]
}
```

```bash
npm run build --workspace=web
npm install react --workspace=web
```

对于复杂 monorepo，pnpm/yarn/Turborepo 可能提供更强能力；但 npm workspace 已经能覆盖基础多包管理。

npm workspaces 适合基础多包协作，例如一个应用加一个组件库、工具包和配置包。它能统一安装、统一锁文件、本地链接工作区包，但在大规模任务过滤、缓存和依赖图执行方面通常还会配合其他工具。

## audit

npm 提供漏洞扫描：

```bash
npm audit
npm audit fix
```

`audit fix` 不应盲目执行，尤其是会升级大版本时。修复漏洞要结合实际触发路径、破坏性变更和测试结果。

审计结果要区分运行时依赖和构建链依赖。一个开发依赖漏洞不一定进入浏览器，但构建链依赖被攻击可能污染产物。安全处理不能只看“高危/中危”标签，也要看依赖是否可达、是否有替代版本、升级是否破坏现有功能。

## 发布包

npm 包发布需要确认入口、类型、files、版本和访问权限。

```json
{
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "files": [
    "dist"
  ]
}
```

发布前可以使用：

```bash
npm pack --dry-run
```

检查最终会发布哪些文件。npm 和 [[5.8.5 版本发布|版本发布]]、[[1.6.7 依赖安全|依赖安全]] 是一条完整链路。

发布包前还要确认 `.npmignore`、`files`、`exports`、`types` 和构建产物是否一致。很多包发布事故不是代码错，而是把源码、测试文件、私有配置或缺失类型声明一起发布出去了。

```bash
npm publish --access public
npm deprecate my-package@"<2.0.0" "请升级到 2.x"
```

发布是不可轻视的动作，尤其是公共包和内部基础包，一旦被多个项目依赖，错误版本会迅速扩散。
