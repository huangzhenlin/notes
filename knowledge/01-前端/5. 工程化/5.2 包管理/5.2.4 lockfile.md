## 锁定依赖图

lockfile 用来记录真实安装结果。`package.json` 只声明版本范围，lockfile 会记录具体解析到哪个版本、下载地址、完整性校验和完整依赖树。

```text
package.json  描述版本范围
lockfile      锁定实际安装结果
node_modules  安装后的物理结果
```

`"react": "^18.2.0"` 表示允许兼容升级，但 lockfile 会记录当前实际安装的具体版本。没有 lockfile 时，同一份 `package.json` 在不同时间安装，可能得到不同依赖版本。

lockfile 锁定的不只是直接依赖，还包括所有间接依赖。很多“代码没改却突然构建失败”的问题，本质上就是某个间接依赖在没有锁文件保护时被重新解析到了新版本。lockfile 的作用就是把这种不确定性压到最低。

```text
直接依赖：项目自己声明的包
间接依赖：这些包继续依赖的包
lockfile：把两层以及更深层全部固定下来
```

## 常见文件

不同包管理器有不同 lockfile。

| 包管理器 | lockfile |
| --- | --- |
| npm | `package-lock.json` |
| pnpm | `pnpm-lock.yaml` |
| Yarn Classic | `yarn.lock` |
| Yarn Berry | `yarn.lock` |
| Bun | `bun.lockb` 或 `bun.lock` |

同一个项目应只使用一种包管理器和一种 lockfile。混用会造成依赖解析不一致，也会让团队不知道到底该用哪个工具安装。

## 提交策略

应用项目应该提交 lockfile。这样能保证团队和 CI 使用一致依赖树。

```text
应用项目：提交 lockfile
Monorepo：提交根 lockfile
库源码：通常提交，用于开发和 CI
模板项目：视目标而定
发布到 npm 的包：使用方安装不依赖库自己的 lockfile
```

lockfile 不是“自动生成就不用管”的文件，而是依赖图变更记录。依赖升级应作为明确变更审查，而不是安装时悄悄发生。

审查 lockfile 变化时，不需要逐行读懂每个字段，但要重点看是否出现核心框架升级、解析来源变化、大量重复版本、新增安装脚本依赖，或无关范围的依赖树抖动。

```text
重点关注：
1. React / Vue / TS / 构建工具版本变化
2. 下载来源是否异常
3. 是否多出大量间接依赖
4. 是否出现多个关键库版本并存
```

## 可重复安装

CI 中应使用严格安装命令，确保 lockfile 和 `package.json` 一致。

```bash
npm ci
pnpm install --frozen-lockfile
yarn install --immutable
```

这些命令不会随意更新 lockfile。如果 `package.json` 和 lockfile 不一致，CI 应失败，提醒开发者提交正确锁文件。

本地如果想验证“在干净环境里是否还能装通”，也可以主动删除 `node_modules` 后执行严格安装。这样能提前暴露锁文件遗漏、包管理器版本不一致或安装脚本依赖本地环境的问题。

## 依赖漂移

没有 lockfile 时，同一份 `package.json` 在不同时间安装可能得到不同依赖树。

```json
{
  "dependencies": {
    "some-lib": "^1.2.0"
  }
}
```

今天可能安装 `1.2.3`，下周可能安装 `1.3.0`。如果新版本有 bug，项目会出现“代码没变但构建坏了”的问题。

依赖漂移并不总是立刻表现为报错。很多时候它表现为样式细节变化、类型报错数量变化、测试偶发失败、打包体积波动，或者某个浏览器兼容行为变化。lockfile 的价值就在于让这些变化发生时，我们至少知道“确实换过依赖图”。

## 冲突处理

lockfile 冲突不应该随手删掉重装。

```text
处理顺序：
1. 理解两个分支改了哪些依赖
2. 保留 package.json 中真实依赖变更
3. 用当前包管理器重新 install
4. 运行测试和构建
5. 审查 lockfile 的核心变化
```

删除 lockfile 会导致整个依赖图刷新，可能引入大量无关变更。除非明确要升级依赖树，否则不要轻易重生成全量锁文件。

发生 lockfile 冲突时，最好让真正修改过依赖的分支为主，再在合并后重新 install。这样 lockfile 的变化会尽量贴近真实意图，而不是把两个分支的整个依赖树一起重新洗牌。

## 安全校验

lockfile 中通常包含 integrity 信息，用于校验下载包是否被篡改。

```yaml
resolution:
  integrity: sha512-...
```

这不是完整供应链安全方案，但能提供基础完整性校验。依赖审计、私有 registry、锁文件审查仍然很重要。

完整性校验只能说明“下载到的包和发布时记录的一致”，不能说明这个包本身就安全。所以 lockfile 是基础防线，不是全部安全方案。

## Monorepo

Workspace 项目通常在根目录维护一个统一 lockfile。

```text
repo/
  pnpm-lock.yaml
  apps/web/package.json
  packages/ui/package.json
```

统一 lockfile 能保证整个仓库依赖解析一致，也让跨包 CI 缓存更稳定。子包不要各自维护独立 lockfile，除非它们真的是独立项目。

统一 lockfile 还能帮助发现跨包版本漂移。比如 UI 包升级了 React peer 范围，应用是否一起适配、测试是否一起通过，都能在同一份依赖图里更早暴露。

## 排查路径

遇到依赖相关问题时，可以按 lockfile 反查：

```text
1. package.json 是否声明了预期版本
2. lockfile 是否解析到正确版本
3. node_modules 是否和 lockfile 一致
4. CI 是否使用 frozen install
5. 是否存在多个 lockfile
```

lockfile 的价值是让依赖问题可复现、可审查、可回滚。它和 [[5.1.5 依赖管理|依赖管理]] 是同一套工程稳定性的基础。

如果一个项目没有提交 lockfile，或者频繁无原因大范围重写 lockfile，就意味着依赖图基本不可追踪。这样的项目往往在 CI 稳定性、供应链审计和线上回滚上都会更脆弱。
