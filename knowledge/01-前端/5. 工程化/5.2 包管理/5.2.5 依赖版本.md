## 版本固定

核心工具链有时适合固定版本，例如 TypeScript、构建工具、测试工具、代码格式化工具。

```json
{
  "devDependencies": {
    "typescript": "5.5.4",
    "prettier": "3.3.3"
  }
}
```

这些工具即使小版本变化，也可能影响类型报错、构建产物或格式化结果。固定版本能减少协作差异，再通过定期升级统一推进。

固定版本最适合“输出会直接影响仓库内容或 CI 结果”的工具。比如 TypeScript 版本变化会影响类型推导，Prettier 会改写格式，ESLint 会改变规则判定，Vite/Webpack 插件版本变化会影响构建链。对于这些工具，稳定通常比自动跟新更重要。
## 版本语义

依赖版本通常遵循 SemVer：主版本、次版本、修订版本。

```text
1.2.3
主版本：1
次版本：2
修订版本：3
```

主版本通常表示破坏性变更，次版本表示向后兼容的新能力，修订版本表示 bug 修复。现实中不是所有包都严格遵守，所以升级仍然要验证。

SemVer 是约定，不是法律。很多库虽然标了 patch 或 minor，但仍然可能改默认值、删边缘行为或收紧类型。依赖版本的判断不能只看数字，还要看这个包在项目里的重要程度。

## 范围符号

`package.json` 中的版本范围决定包管理器可以选择哪些版本。

| 写法 | 含义 |
|---|---|
| `1.2.3` | 固定版本 |
| `^1.2.3` | 允许 `1.x.x` 内升级 |
| `~1.2.3` | 允许 `1.2.x` 内升级 |
| `>=1.2.3` | 大于等于 |
| `*` | 任意版本 |

`^` 是最常见默认范围，但对于构建工具、编译器、核心框架，大版本和小版本都可能带来行为差异，需要更谨慎。

一个实用策略是：应用项目的业务运行时依赖可以适度使用 `^`，但构建链、编译链、测试链更适合固定版本或至少更保守的范围。风险高的工具链一旦抖动，影响的是整个团队。

## 锁文件

版本范围描述“允许哪些版本”，锁文件记录“实际安装哪个版本”。

```text
package.json: react ^19.0.0
lockfile: react 19.0.2
```

团队协作和 CI 必须依赖锁文件保证可复现。锁文件变化应被 review，因为它可能引入大量间接依赖变更。

依赖版本管理里，`package.json` 表达的是“允许什么”，lockfile 表达的是“这次具体用了什么”。两者必须一起看，不能只盯着其中一份文件。

## 依赖类型

不同依赖类型表达不同运行边界。

| 字段 | 用途 |
|---|---|
| `dependencies` | 运行时依赖 |
| `devDependencies` | 开发、构建、测试依赖 |
| `peerDependencies` | 由使用者提供的依赖 |
| `optionalDependencies` | 可选依赖 |

组件库通常把 React/Vue 放到 `peerDependencies`，避免把框架打进库产物，造成多个运行时实例。

`optionalDependencies` 也要谨慎使用。它适合平台相关能力、可选优化器或某些失败后可以降级的依赖；如果没有兜底逻辑，把关键能力放进 optional 只会把问题延后到运行时。

## peerDependencies

`peerDependencies` 表示“我需要你提供这个依赖，并且版本要满足范围”。

```json
{
  "peerDependencies": {
    "react": "^18.0.0 || ^19.0.0"
  }
}
```

它适合插件、组件库、框架扩展。版本范围要写得既准确又不过度保守，否则使用者会遇到无意义警告。

peer 范围太窄会抬高接入成本，太宽又可能掩盖真实不兼容。比如只测试过 React 18 却宣称支持 React 17-20，看起来兼容范围很大，实际风险也更高。peer 范围最好和真实验证范围一致。

## 版本升级

依赖升级要按风险分层。

| 升级 | 风险 |
|---|---|
| patch | 通常低 |
| minor | 中等，可能有行为变化 |
| major | 高，需要迁移 |
| 预发布版本 | 高，需明确目的 |

升级后要跑构建、类型检查、单测和关键 E2E。安全升级也不能绕过验证。

升级时最好按类别拆分提交。比如先升级 lint/format 工具，再升级测试工具，再升级运行时库，最后升级框架和组件库。这样出问题时更容易回滚和定位。

## 重复版本

同一个依赖出现多个版本，会增加包体积，也可能造成运行时问题。

```text
react@18
react@19
```

对 React、Vue、状态库、样式运行时这类单例敏感依赖，要特别避免重复版本。可以通过 lockfile、overrides/resolutions、包边界治理来解决。

重复版本不只是体积问题，也可能是运行时问题。React 多实例、样式运行时多实例、状态库多副本都可能导致 hooks 异常、上下文失效或样式重复注入。

## 固定策略

是否固定版本取决于项目风险。

| 场景 | 策略 |
|---|---|
| 应用项目 | 范围 + lockfile |
| 基础设施工具 | 更谨慎，可固定 |
| 组件库 peer | 合理范围 |
| 安全敏感依赖 | 审查后升级 |

依赖版本和 [[1.6.7 依赖安全|依赖安全]]、[[6.4.5 依赖分析|依赖分析]] 紧密相关：版本影响安全，也影响包体积和运行行为。

版本策略最终要服务项目目标。小项目可以更保守，优先稳定；基础设施项目可以定期批量升级，保持生态兼容；组件库则要特别认真地维护 peer 范围和宿主版本支持矩阵。
