## 工作区目标

Workspace 用于在一个仓库中管理多个包或应用。它让本地包可以互相依赖、统一安装依赖、共享锁文件，并支持批量执行脚本。

```text
repo
├─ apps
│  └─ web
└─ packages
   ├─ ui
   └─ utils
```

Workspace 是 monorepo 的基础能力，但它本身不等于完整 monorepo 工程。任务编排、版本发布、包边界还需要额外设计。

可以把 Workspace 理解成“包管理器层面的多包组织能力”。它解决的是安装、链接和脚本执行问题；而完整 monorepo 还要继续解决缓存、依赖边界、影响分析、版本发布和团队协作问题。不要因为用了 workspace，就默认工程已经具备 monorepo 治理能力。

Workspace 最直接的收益是把多个应用和内部包放进同一个依赖图里。这样组件库、工具包、配置包和应用可以一起演进，不需要每次都先发布再安装。

## 包发现

不同包管理器通过配置声明哪些目录属于工作区。

```yaml
packages:
  - 'apps/*'
  - 'packages/*'
```

```json
{
  "workspaces": [
    "apps/*",
    "packages/*"
  ]
}
```

包必须有自己的 `package.json`，并通过 `name` 暴露包名。

包发现范围要尽量收敛。不要把临时目录、构建产物目录或示例目录随意纳入 workspace，否则包管理器可能会把不该安装的目录也当成项目包处理，增加安装时间和依赖混乱风险。

一个实用原则是：只有“要参与安装、脚本执行和依赖关系”的目录才进入 workspace。demo、sandbox、docs 示例目录如果不是真正的工作区包，就不要为了图省事一起扫进去。

## 本地依赖

工作区包之间可以使用 workspace 协议声明本地依赖。

```json
{
  "dependencies": {
    "@acme/ui": "workspace:*"
  }
}
```

这表示开发时使用仓库内的 `@acme/ui`，发布时再转换成合适版本。它比手动 `npm link` 更稳定。

本地依赖的优势是调试直接：修改内部包后，应用可以立刻使用最新代码。但这也意味着内部包的构建输出、类型声明和入口配置必须稳定，否则应用会遇到“源码能改，消费不了”的问题。

内部包最好像真正可发布的包一样维护入口、类型和构建产物。即使它暂时不发布到 npm，这种约束也能降低未来拆包或独立发布的成本。

## 脚本执行

Workspace 支持针对单个包或全部包执行脚本。

```bash
pnpm --filter web build
pnpm -r test
yarn workspace web build
npm run build --workspace=web
```

批量执行要考虑依赖顺序。简单 workspace 只负责运行命令，复杂依赖拓扑更适合配合 Turborepo、Nx 等任务编排工具。

脚本执行还要区分“单包执行”和“按依赖拓扑执行”。如果 `app` 依赖 `ui`，构建时就应该先构建 `ui` 再构建 `app`。包管理器能帮你定位包，但不一定自动理解所有任务依赖。

工作区脚本最好统一命名。比如每个包都约定有 `build`、`test`、`lint`、`typecheck`，根目录再统一编排。命名越统一，自动化工具越容易接入，团队也越少猜测。

## 依赖提升

不同包管理器对依赖提升和 `node_modules` 布局处理不同。依赖提升可能让未声明依赖“刚好能用”，也可能造成幽灵依赖。

```text
包 A 没声明 lodash
但根 node_modules 有 lodash
代码仍然能运行
```

每个包都应该在自己的 `package.json` 中声明真实依赖。不要依赖根目录或其他包间接提供的依赖。

幽灵依赖是 workspace 里很常见的问题。本地开发能跑，不代表发布后的包也能跑，因为发布后它离开了根目录依赖环境。每个包都声明自己的真实依赖，才能保证独立构建、独立测试和独立发布。

根目录依赖也要克制。不是所有公共依赖都应该只装在根上。构建工具可以在根上统一，真正被某个包运行时代码使用的依赖，还是应该写进那个包自己的 `package.json`。

## 版本发布

Workspace 中的包可能独立发布，也可能统一版本。选择不同，发布流程也不同。

| 模式 | 适合场景 |
|---|---|
| 独立版本 | 工具包、组件库 |
| 固定版本 | 强耦合套件 |
| 只内部使用 | 应用内部包 |

如果包要发布到 npm，需要关注 `files`、`exports`、`types`、`peerDependencies` 和 changelog。

内部包如果只在仓库内使用，也仍然需要版本意识。即使不发布到 npm，包的 API 变化也会影响消费方。对高频内部包，最好也维护变更记录和迁移说明。

版本策略还会影响协作方式。固定版本适合强耦合套件，独立版本适合通用工具包。没有标准答案，关键是包之间是否真的要同步发布和同步升级。

## 边界治理

Workspace 让包之间互相引用变容易，也容易让边界变模糊。要明确哪些包可以被哪些包依赖。

```text
apps -> packages/ui
apps -> packages/utils
packages/ui -> packages/utils
packages/utils 不应依赖 apps
```

Workspace 和 [[5.8.3 包边界|包边界]]、[[5.8.4 任务编排|任务编排]] 是配套的：workspace 提供包组织，包边界控制依赖，任务编排提升执行效率。

如果 workspace 里每个包都能随便引用任何包，短期很方便，长期会把仓库变成一团强耦合代码。真正可维护的 workspace，一定要有清楚的依赖方向和公共能力沉淀规则。

Workspace 最后要落到治理：哪些目录允许成为包，哪些包可以被应用消费，哪些包只服务内部构建，哪些脚本必须在根执行，哪些包可以独立发布。规则越早明确，仓库越不容易长成“大家都能用但谁都不敢动”的形状。
