## 检查目标

ESLint 用于发现 JavaScript、TypeScript、React、Vue 等代码中的潜在问题，并统一团队代码风格。它的核心价值不是“让代码看起来一样”，而是把容易遗漏的错误前移到编辑器、提交和 CI 阶段。

```text
源码
  -> ESLint 解析
  -> 规则检查
  -> 自动修复
  -> 报告问题
```

ESLint 适合检查未使用变量、错误依赖、Hook 规则、可疑条件、无效导入和团队约定，不适合替代类型检查、测试和人工设计评审。

ESLint 的价值通常体现在“把容易漏掉的问题提早暴露”。比如 React Hooks 依赖数组、未处理的 Promise、重复导入、危险的条件判断，很多都是编辑器里能提前发现的低级错误。

它最适合解决“肉眼不容易稳定发现，但规则能稳定发现”的问题。比如条件分支里误用赋值、忘记清理依赖、异步函数没有正确处理返回值，这些问题如果等到测试或线上再发现，成本会明显更高。

## Flat Config

ESLint 新版本推荐 flat config，用 `eslint.config.js` 描述配置。

```javascript
import js from '@eslint/js';

export default [
  js.configs.recommended,
  {
    files: ['**/*.js'],
    rules: {
      'no-console': 'warn',
    },
  },
];
```

Flat config 的配置顺序很重要，后面的配置会覆盖前面的同名规则。不同文件类型可以使用不同配置片段。

Flat config 也更容易按文件类型拆分规则。比如源码、测试文件、配置文件、文档中的代码块可以分别制定不同约束，避免“一把尺子量所有文件”。

这对大型仓库特别重要。业务源码、脚本、构建配置、测试文件、示例代码往往处在不同约束环境里，如果共用一套规则，误报会很多，最终团队只会越来越依赖 `disable`。

## 规则等级

ESLint 规则有三个常见等级：关闭、警告、错误。

| 等级 | 含义 | 适合场景 |
|---|---|---|
| `off` | 不检查 | 与项目不匹配的规则 |
| `warn` | 提示但不阻断 | 迁移期、低风险问题 |
| `error` | 报错并可阻断 CI | 明确质量底线 |

团队不要把所有规则都设成 error。高噪音规则会让大家习惯性忽略 lint 结果。

更好的做法通常是先让高价值规则落地，再逐步把团队能接受的规则从 `warn` 升级到 `error`。规则不是越严越好，而是越能持续执行越好。

一个常见判断标准是：

| 更适合 `error` 的规则 | 更适合 `warn` 的规则 |
| --- | --- |
| 明确会引发 bug 的问题 | 团队还在迁移中的风格问题 |
| 框架运行机制约束 | 需要人工判断上下文的问题 |
| 能稳定自动修复或明确判定的问题 | 争议较大的偏好型约束 |

## TypeScript 集成

TypeScript 项目通常使用 `typescript-eslint`，让 ESLint 能理解 TS 语法和部分类型信息。

```javascript
import tseslint from 'typescript-eslint';

export default [
  ...tseslint.configs.recommended,
  {
    files: ['**/*.ts', '**/*.tsx'],
    rules: {
      '@typescript-eslint/no-explicit-any': 'warn',
    },
  },
];
```

有些规则需要类型信息，检查更准，但速度也更慢。可以把重规则放到 CI，编辑器里保留快速反馈。

类型感知规则适合发现“语法上合法、逻辑上可疑”的问题，但它们会明显增加 lint 开销。大型项目里，编辑器快速反馈和 CI 深度检查分层是更稳的做法。

这也是为什么很多团队会把 lint 分成两层：

```text
本地 / 编辑器：
快速规则，优先保证反馈速度

CI：
类型感知规则、全量扫描、严格门禁
```

这样既不会拖慢日常开发，也不会因为追求速度而放弃深度检查。

## 框架规则

React、Vue、Next 等框架通常有专门规则集，用于检查框架特有约束。

```text
React：Hooks 调用规则、依赖数组
Vue：模板语法、组件命名、组合式 API
Next：页面约定、性能和可访问性建议
```

框架规则比通用 JS 规则更贴近真实 bug。例如 React Hooks 不能放在条件分支里，这不是格式问题，而是运行机制要求。

这也是为什么框架项目通常会搭配专门的 ESLint 插件。工具不是为了“管得更多”，而是为了把框架运行时的约束提前翻译成静态规则。

例如 React 的 Hooks 规则、Next 的页面能力约束、Vue 的模板和响应式写法规则，本质上都在帮助开发者少踩运行机制上的坑。越接近框架内部约束的规则，往往越有实际价值。

## 自动修复

部分规则支持自动修复。

```bash
eslint . --fix
```

自动修复适合格式、导入排序、简单语法替换。不适合依赖人工判断的设计问题。提交前可以配合 lint-staged 只修复 staged 文件。

如果自动修复覆盖面太大，反而可能让代码变动和业务改动混在一起，PR 更难审。把自动修复限定在可机械处理的范围内，通常更稳。

更推荐的做法是：格式、导入排序、简单语法替换交给自动修复；需要理解业务语义的规则仍然通过报错提示开发者手动修改。这样 lint 才是在提效，而不是偷偷重写代码。

## 忽略边界

忽略规则要尽量小范围，并说明原因。

```typescript
// eslint-disable-next-line @typescript-eslint/no-explicit-any -- 第三方 SDK 类型缺失
function handleMessage(payload: any) {}
```

不要在文件顶部大面积关闭规则。大量 disable 往往说明规则配置不适合项目，或代码边界需要重构。

`eslint-disable-next-line` 最适合局部、可解释、可复查的例外场景。比如第三方 SDK 类型缺失、兼容旧接口、临时代码迁移；如果它反复出现，就该考虑补类型、改封装或调整规则。

换句话说，`disable` 应该被当成“例外申请”，而不是默认解决方案。一个项目里如果大量出现整段关闭规则，通常说明规则边界、代码结构或迁移策略至少有一项出了问题。

## CI 门禁

ESLint 应接入 CI 和本地 hooks。

```json
{
  "scripts": {
    "lint": "eslint .",
    "lint:fix": "eslint . --fix"
  }
}
```

ESLint 和 [[5.5.5 Git Hooks|Git Hooks]]、[[5.7.1 流水线|流水线]] 是一条质量链路：编辑器即时提示，本地提交前快速检查，CI 做最终门禁。

这条链路越完整，团队越不依赖个人自觉。编辑器负责即时反馈，hooks 负责拦住低级问题，CI 负责兜底，三者各有位置。

从排查角度看，如果 ESLint 结果和预期不一致，可以优先检查：

```text
1. 当前文件是否命中了正确的配置片段
2. 规则是否被后面的配置覆盖
3. 是否启用了类型信息，但 parser / tsconfig 指向错误
4. 编辑器插件、命令行和 CI 使用的配置是否一致
```

很多“为什么本地不报、CI 才报”或“编辑器报错但命令行不报”的问题，本质上都来自配置来源不一致。
