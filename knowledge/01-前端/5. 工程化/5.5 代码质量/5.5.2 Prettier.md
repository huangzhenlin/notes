## 工具定位

Prettier 是代码格式化工具，负责统一缩进、换行、空格、引号等格式。

```txt
Prettier: 怎么排版
ESLint: 代码质量和潜在问题
Stylelint: 样式质量和规则
```

它的价值不是让每个人喜欢同一种风格，而是让团队不再在格式问题上反复讨论。

Prettier 解决的是“怎么排版”，不是“怎么写得更好”。当格式自动统一后，PR 里更容易看出真正的逻辑变化。

这件事对协作效率的影响非常直接。格式不统一时，review 常常被无意义 diff 淹没；格式统一后，讨论才能回到命名、边界、抽象和行为变化本身。

## 基础配置

```json
{
  "semi": true,
  "singleQuote": false,
  "printWidth": 100,
  "trailingComma": "all"
}
```

配置应尽量少。Prettier 的设计就是减少可争论选项，过度配置会削弱它的价值。

如果团队对格式有强烈偏好，通常不应该靠疯狂调 Prettier 参数来满足，而应该尽量接受它的默认行为。配置越多，越容易回到“争论格式”的老路。

Prettier 的核心价值之一，就是主动压缩“可争论空间”。如果所有人都还能继续围绕空格、换行和逗号争论，那它的意义就被削弱了。

## 忽略文件

`.prettierignore` 用于排除不需要格式化的文件。

```txt
dist
coverage
node_modules
pnpm-lock.yaml
*.min.js
```

构建产物、依赖目录、覆盖率报告、压缩文件都不应该格式化。lockfile 通常由包管理器维护，也不建议手动格式化。

对于知识库类文档，是否让 Prettier 全量接管 Markdown，要看文档里有没有大量手工排版、表格或 Obsidian 语法。有时局部格式化比全量格式化更稳。

这也是文档仓库和应用源码仓库最大的区别之一。源码更适合强一致格式化，知识文档则要同时考虑阅读节奏、表格布局、代码块展示和双链语法是否被破坏。

## 脚本集成

```json
{
  "scripts": {
    "format": "prettier \"src/**/*.{ts,tsx,vue,css,md}\" --write",
    "format:check": "prettier \"src/**/*.{ts,tsx,vue,css,md}\" --check"
  }
}
```

`--write` 用于本地修复，`--check` 用于 CI 检查。CI 中不应自动改代码，只应失败并提示需要格式化。

这样做的好处是职责清楚：本地负责改，CI 负责验。否则 CI 里自动重写代码，容易把格式问题和真正的问题混在一起。

如果 CI 自动改代码，再把改动推回仓库，虽然看起来省事，实际上会让提交历史变脏，也会让“谁改了什么”变得不清楚。格式修复最好始终发生在开发者本地。

## 编辑器集成

团队应统一编辑器保存时格式化行为。

```json
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode"
}
```

如果有人保存自动格式化，有人不格式化，PR 中会出现大量无关 diff。编辑器集成能把格式问题提前解决在本地。

团队最好统一保存时的格式化器，否则同一段代码在不同编辑器里会被反复改动，PR 变得很吵。

尤其在多人协作和 monorepo 场景里，编辑器行为不一致会放大这种问题。一个人保存后重排了整段 JSON、Markdown 或样式，另一个人再保存又换成另一种换行策略，历史会非常难看。

## 与 ESLint

Prettier 和 ESLint 可能有格式规则重叠。现代项目通常让 Prettier 负责格式，让 ESLint 关注质量。

```txt
关闭 ESLint 中与格式冲突的规则
保留 no-unused-vars、hooks、imports 等质量规则
```

不要让 ESLint 和 Prettier 对同一段格式给出相反意见。工具职责清楚，开发体验才稳定。

实际落地时通常会关闭与 Prettier 冲突的 ESLint 格式规则，再保留真正有质量意义的规则。这样格式统一和质量检查才能各自发挥作用。

如果工具职责不清，很容易出现下面这种循环：

```text
Prettier 改了一次
  -> ESLint 认为格式不对
  -> 再修一次
  -> Prettier 又改回去
```

这种互相打架的问题，本质上不是某个工具不好，而是职责边界没有划清。

## Markdown 格式化

Prettier 可以格式化 Markdown，但技术笔记项目要谨慎控制范围。

```bash
prettier "docs/**/*.md" --write
```

如果 Markdown 中有特殊换行、表格、Obsidian 语法或手写排版，格式化前要确认不会破坏阅读体验。知识库文档不一定必须全量格式化。

对文档类内容，格式一致固然重要，但可读性更重要。只要排版不会破坏双链、表格和代码块，局部使用 Prettier 就足够了。

如果 Markdown 中有大量需要人为控制节奏的内容，比如对照表、代码解释、嵌套引用或特殊段落，最好先小范围验证格式化效果，再决定是否全量启用。

## CI 与 pre-commit

```txt
编辑器保存格式化
pre-commit 检查暂存文件
CI 检查全量格式
```

pre-commit 适合快速阻止明显问题，CI 是最终保障。大型仓库中，可以只对变更文件做本地格式化，CI 再做完整检查。

如果格式化范围太大，本地钩子会变慢，开发者就更容易绕开它。把本地动作控制在“快且能拦住明显问题”的范围内，通常更可持续。

对于大仓库，更推荐“保存即格式化 + pre-commit 检查暂存文件 + CI 做全量 check”的组合。这样既能降低手动成本，也不会让一次提交因为全仓格式检查而变得过慢。

## 使用边界

| 适合 Prettier | 不适合 Prettier 决定 |
| --- | --- |
| 缩进 | 架构设计 |
| 换行 | 命名质量 |
| 引号风格 | 依赖边界 |
| 尾逗号 | 性能问题 |
| Markdown 表格基础格式 | 文档内容质量 |

Prettier 解决的是格式统一，不解决代码是否好。它应该和 lint、test、review 一起组成质量体系。

判断 Prettier 是否接入得合理，可以看三个信号：

| 信号 | 说明 |
| --- | --- |
| PR 中格式噪音明显减少 | 说明它真正起到了统一作用 |
| 开发者几乎不用手动调格式 | 说明集成顺畅 |
| 很少出现工具互相打架 | 说明职责边界清楚 |
