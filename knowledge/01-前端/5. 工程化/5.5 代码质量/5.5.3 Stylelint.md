## 工具定位

Stylelint 是 CSS 代码质量工具，用于检查样式语法、规则顺序、命名、兼容性和团队约定。

```txt
CSS
SCSS
Less
CSS Modules
Vue/React 中的样式块
```

它和 ESLint 分工不同：ESLint 管 JavaScript/TypeScript，Stylelint 管样式。

Stylelint 更适合管“样式边界”。比如是否允许重复属性、选择器是否过深、是否直接写裸色值、CSS Modules 命名是否规范，这些都很适合交给它。

样式问题的一个特点是“能显示出来，不代表容易维护”。页面今天看起来正常，不代表下次加一个类名、切一个主题、换一个断点后不会崩。Stylelint 的价值就在于尽量把这类维护风险前移。

## 基础配置

常见配置从标准规则集开始。

```js
export default {
  extends: ["stylelint-config-standard"],
  rules: {
    "color-hex-length": "short",
    "declaration-block-no-duplicate-properties": true,
  },
};
```

项目使用 SCSS、Vue、CSS Modules 时，需要加入对应 parser 或 config。不要直接复制配置而不确认语法环境。

样式工具链经常混用 SCSS、Less、PostCSS、CSS Modules 和组件内联样式。配置前先确认项目到底用了哪种语法，否则规则可能根本没生效。

如果仓库同时存在多种样式形态，最好分文件类型或目录配置。比如基础样式、组件局部样式、主题样式和第三方覆盖样式往往不该共用完全同一套限制。

## 脚本集成

```json
{
  "scripts": {
    "lint:style": "stylelint \"src/**/*.{css,scss,vue}\"",
    "lint:style:fix": "stylelint \"src/**/*.{css,scss,vue}\" --fix"
  }
}
```

`--fix` 可以自动修复部分问题，但不应替代代码审查。规则设计要能帮助维护，而不是制造大量低价值噪音。

对于样式代码，自动修复最适合处理格式和简单重复问题；真正的层叠、结构和设计 token 问题，还是要靠人判断。

也就是说，Stylelint 更适合扮演“守门员”，不适合替代样式设计本身。它能拦住明显错误和不符合约定的写法，但不能替团队决定层级结构、组件边界和视觉表达。

## 与 Prettier

Prettier 负责格式化，Stylelint 负责质量规则。两者职责要分开。

```txt
Prettier: 缩进、换行、空格
Stylelint: 禁止重复属性、限制选择器、检查命名和兼容性
```

如果两者规则冲突，应关闭 Stylelint 中纯格式化规则，交给 Prettier 处理。

这样可以避免“格式化工具”和“质量工具”抢同一件事。职责越清楚，团队越容易持续使用。

对样式来说，工具打架会特别烦。因为 CSS 一旦格式和规则相互覆盖，改动常常看似只是排版变化，实际却可能把选择器顺序、覆盖关系和阅读节奏都弄乱。

## 规则类型

Stylelint 规则大致可以分为：

| 类型 | 示例 |
| --- | --- |
| 错误规则 | 重复属性、无效语法 |
| 风格规则 | 十六进制长度、命名格式 |
| 架构规则 | 限制选择器深度 |
| 兼容规则 | 禁止不支持属性 |
| 约定规则 | design token、颜色变量 |

团队应优先启用能减少真实问题的规则，再逐步补充风格和架构约束。

如果一开始就上太多限制，样式开发会很痛。先管重复属性、明显错误、过深选择器和设计 token，再逐步收紧细节，通常更容易落地。

样式规范最怕“一步到位式重约束”。尤其在旧项目里，如果基础结构本来就有很多层叠和历史包袱，过早上大量严格规则，开发者只会不断写忽略说明，长期反而失控。

## 选择器约束

限制选择器复杂度能减少层叠和覆盖问题。

```js
export default {
  rules: {
    "selector-max-id": 0,
    "selector-max-compound-selectors": 4,
  },
};
```

深选择器、ID 选择器、过度嵌套会让样式难以覆盖。组件化项目通常更偏向低优先级、局部类名。

这类约束对设计系统和组件库尤其重要。样式规则越清晰，后续主题切换、覆盖和定制成本越低。

选择器复杂度本质上反映了样式耦合程度。选择器越深、优先级越高、覆盖路径越长，组件就越难复用，也越难在后续改版中安全调整。

## 设计系统约束

Stylelint 可以配合团队约定限制颜色、字号、间距等。

```js
export default {
  rules: {
    "color-no-hex": true,
  },
};
```

如果项目要求使用 CSS 变量或设计 token，就可以限制直接写裸色值。规则要与设计系统成熟度匹配，过早强限制会影响开发效率。

Stylelint 在这里的作用不是“强迫所有人写同一份样式”，而是把设计约束变成可自动检查的规则，避免设计 token 被绕过。

当设计系统已经形成统一 token、语义色和间距体系后，Stylelint 很适合用来守住底线。例如禁止直接写十六进制颜色、限制使用未登记变量、要求统一层级策略等。

## CI 与编辑器

Stylelint 应同时接入编辑器、pre-commit 和 CI。

```txt
编辑器：即时反馈
pre-commit：阻止明显问题
CI：保证主分支质量
```

CI 是最终防线。编辑器配置不统一时，CI 能保证规则真正执行。

如果项目里存在多种样式写法，比如 `.css`、`.scss`、`.vue`、CSS Modules，最好按文件类型分别配置，避免误报和漏报。

排查 Stylelint 误报时，可以优先看：

```text
1. 文件语法是否被正确解析
2. 当前规则是否真的适用于该类样式文件
3. 是否和 Prettier、构建器或 CSS Modules 规则冲突
4. 是否把设计系统约束错误地套到了临时覆盖样式上
```

很多看似“规则太严格”的问题，本质上其实是规则作用范围没有分层。
