## 检查目标

TypeScript 检查用于在编译阶段发现类型错误、接口不一致、空值风险和重构破坏。它不替代测试，但能在代码运行前拦住大量低级问题。

```text
源码
  -> 类型分析
  -> 诊断错误
  -> 阻止提交或构建
```

类型检查的价值不只是“没有红线”，而是让模块边界、函数签名和数据结构更稳定。

类型检查最适合拦住“重构后签名变了但调用方没改”“接口字段可能为空但页面直接读取”“组件 props 传错类型”这类问题。它不能证明业务逻辑一定正确，但能把大量低级错误提前到编码和 CI 阶段暴露。

```text
类型检查负责：
1. 数据结构一致
2. 函数调用合法
3. 空值风险可见
4. 模块边界清楚
```

它尤其适合做“工程放大镜”。项目规模越大、调用链越长、复用越多，类型检查带来的收益越明显。一个公共函数签名变化，在没有类型系统时可能要等到运行时才暴露；有类型系统时，受影响位置通常会立刻亮出来。

## noEmit

前端项目通常把类型检查和构建输出分开。`tsc --noEmit` 只做检查，不生成文件。

```bash
tsc --noEmit
```

Vue 项目常用：

```bash
vue-tsc --noEmit
```

Vite、SWC、esbuild 等工具转译很快，但它们通常不做完整类型检查。因此 CI 中应单独跑 typecheck。

这也是很多项目需要同时存在 `build` 和 `typecheck` 的原因。构建成功只代表代码能被转换成产物，不一定代表类型完全正确。尤其是 Vite 项目，如果只跑 `vite build`，可能漏掉某些类型错误。

从职责上看，可以把两者理解成：

| 命令 | 主要目标 |
| --- | --- |
| `build` | 生成可交付产物 |
| `typecheck` | 验证静态边界和类型一致性 |

当团队把它们分开后，错误也会更容易归类，不会出现“构建挂了却不知道是打包问题还是类型问题”的混乱情况。

## 严格模式

`strict` 是 TypeScript 质量的关键开关。它会启用一组更严格的检查。

```json
{
  "compilerOptions": {
    "strict": true
  }
}
```

严格模式会让迁移初期更痛，但长期能减少 `any`、空值和隐式类型带来的隐患。老项目可以分阶段开启。

老项目开启严格模式时，不建议一次性把所有错误都压掉。更稳的方式是先从新模块开始严格，再按目录逐步收敛旧代码。否则大量 `as any` 会让 strict 只剩形式。

严格模式的难点从来不是“能不能开”，而是“开了之后是否愿意认真修”。如果只是为了把 CI 变绿而不断补断言和 `any`，类型系统提供的保护会迅速被削弱。

## 空值检查

`strictNullChecks` 能区分 `null`、`undefined` 和真实值。它可以避免大量运行时空指针错误。

```typescript
function formatName(user?: { name: string }) {
  return user?.name ?? '匿名';
}
```

如果关闭空值检查，很多潜在问题会被类型系统忽略。前端接口数据、DOM 查询、URL 参数都经常出现空值。

空值检查的重点是让“不确定”显式出现。接口返回值、路由参数、本地存储读取、DOM 查询结果都可能为空，代码应该通过判空、默认值或错误兜底处理，而不是依赖运行时侥幸。

这类检查对前端特别重要，因为前端天然会接触大量不受自己完全控制的数据源。用户输入、服务端返回、浏览器 API、第三方 SDK 都可能出现“类型定义里看着稳定，运行时却未必可靠”的情况。

## 增量检查

大型项目可以开启增量检查，加快后续 typecheck。

```json
{
  "compilerOptions": {
    "incremental": true,
    "tsBuildInfoFile": ".tsbuildinfo"
  }
}
```

增量检查依赖缓存文件。CI 中是否缓存 `.tsbuildinfo` 要看构建环境稳定性和收益。

增量检查适合大型项目和 monorepo，但缓存失效时也可能带来排查成本。CI 如果经常出现缓存污染或跨分支复用异常，可以先保证全量检查可靠，再逐步引入缓存。

换句话说，增量检查是性能优化手段，不是正确性前提。先建立一条稳定、可信的全量检查链路，再去追求缓存收益，通常更稳。

## 项目引用

Monorepo 或大型 TS 项目可以用 Project References 拆分类型检查边界。

```json
{
  "references": [
    { "path": "./packages/ui" },
    { "path": "./packages/utils" }
  ]
}
```

项目引用能让包之间类型关系更明确，也能提升增量构建效率。但它要求每个子项目配置更规范。

项目引用还可以帮助团队把类型边界拆开。比如 `packages/ui`、`packages/utils`、`apps/admin` 各自独立检查，问题定位会比整仓一次性检查更清楚。代价是 tsconfig、输出目录和声明文件要维护得更规范。

如果包之间经常直接跨目录引用内部文件，项目引用的收益会大打折扣。因为它依赖明确的包边界，而不是“仓库里都能随便 import”。

## CI 门禁

类型检查应该进入 CI，且失败时阻止合并或部署。

```yaml
- name: Type check
  run: pnpm typecheck
```

如果只在本地跑，团队很快会出现“我这里没跑”的差异。CI 是最终可信门禁。

CI 门禁最好和提交阶段检查分工。本地 hooks 可以快速拦截明显问题，CI 负责最终一致性。不要把全部类型检查都压到 pre-commit，否则大项目提交体验会很差，团队最后会绕过 hooks。

更合理的分层通常是：

```text
编辑器：
即时类型提示

本地 hooks：
必要时做轻量检查，避免提交体验过慢

CI：
跑完整 typecheck，作为最终门禁
```

## 错误治理

类型错误不要靠 `as any` 大面积压掉。更好的顺序是修正类型、补充边界判断、收窄 unknown，最后才考虑小范围断言。

| 问题 | 更稳处理 |
|---|---|
| 接口返回未知 | `unknown` + 类型守卫 |
| DOM 可能为空 | 显式判空 |
| 第三方无类型 | 补声明文件 |
| 旧代码 any 多 | 分模块迁移 |

TypeScript 检查和 [[1.5.12 类型断言|类型断言]] 是一组边界：检查负责发现不确定性，断言只用于你确实能保证的地方。

错误治理要有优先级。公共类型、接口 DTO、组件 props、工具函数签名属于高影响区域，应优先修；测试代码、历史边缘模块可以分阶段处理。只要边界清楚，类型质量就能逐步提高，而不是靠一次大迁移赌运气。

实际排查 TypeScript 检查问题时，可以优先按下面顺序定位：

```text
先看是类型声明不准
  -> 还是模块解析不一致
  -> 还是泛型/推导边界丢失
  -> 还是工具链对 tsconfig 的读取不一致
```

这样能避免一看到红线就无差别加断言，也更容易把问题修在真正的边界上。
