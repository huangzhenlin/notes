## 团队接入

Git Hooks 要保证新人克隆项目后能自动生效。常见方式是在 `prepare` 脚本中初始化 Husky。

```json
{
  "scripts": {
    "prepare": "husky"
  }
}
```

同时要在文档或脚本里保证包管理器一致，否则不同人安装依赖后 hook 行为可能不同。Hooks 的目标是减少协作摩擦，不应该变成环境问题的新来源。

Hooks 最适合拦住低成本、可机械判断的问题，比如格式、lint、提交信息和快速类型检查。它不适合承载长时间任务，否则提交流程会变得很慢。

能否把 hooks 用好，关键不在于“挂了多少脚本”，而在于“它们是否稳定、快速、可预期”。如果一次提交要等很久，或者不同机器结果不一致，团队最终一定会想办法绕过它。
## 钩子目标

Git Hooks 用于在 Git 操作前后自动执行脚本，例如提交前检查格式、提交信息规范、推送前运行测试。它的目标是把低成本质量门禁前移到本地。

```text
git commit
  -> pre-commit
  -> commit-msg
  -> 提交成功
```

Hooks 不是 CI 的替代品。它适合快速反馈，CI 负责最终可信验证。

如果把所有检查都塞进 hooks，开发者很容易用 `--no-verify` 绕过。把 hooks 设计成“快、确定、常用”，才能真正提高质量。

Git Hooks 更像本地质量门卫，而不是最终裁判。它负责尽量早地发现低成本问题，但不应该承担所有质量责任。

## pre-commit

`pre-commit` 在创建提交前运行，适合执行格式化、lint、类型快速检查和针对 staged 文件的测试。

```bash
npx husky init
```

```bash
pnpm lint-staged
```

配合 lint-staged 可以只处理本次提交的文件，避免每次提交都跑全量检查。

这也是 hooks 最实际的价值之一：只处理改动文件，反馈快，阻力小。这样团队才更愿意一直用下去。

```json
{
  "lint-staged": {
    "*.{ts,tsx,vue,js}": [
      "eslint --fix",
      "prettier --write"
    ],
    "*.{md,json,css}": [
      "prettier --write"
    ]
  }
}
```

是否只检查暂存文件，是 hooks 体验的关键分水岭。全量 lint 和全量格式化在 CI 里没问题，但在本地提交流程里常常过重。

## commit-msg

`commit-msg` 用于校验提交信息，例如 Conventional Commits。

```text
feat: add payment entry
fix: handle token refresh failure
docs: update api usage
```

提交信息规范能帮助生成 changelog、识别版本类型和追踪变更。它和 monorepo 版本发布尤其相关。

这一步看似很小，却是让提交历史持续保持可读的关键。如果提交规范只靠大家“自觉遵守”，一段时间后通常会逐渐失效。

## pre-push

`pre-push` 在推送前运行，适合执行更重一点的检查，例如单元测试或类型检查。

```bash
pnpm typecheck
pnpm test
```

不要把过慢的 E2E 全量测试放进 pre-push，否则开发者会倾向于绕过 hooks。重检查更适合 CI。

pre-push 比 pre-commit 稍重一些，但也不宜过度。适合放类型检查、快速单测，不适合放太慢的端到端测试。

一个实用的判断方式是：如果某项检查超过了团队可接受的日常等待时间，它更适合进 CI，而不是留在 pre-push。

## 绕过风险

Git Hooks 可以被 `--no-verify` 绕过，所以不能把它当作唯一门禁。

```bash
git commit --no-verify
```

所有关键检查仍要在 CI 中执行。Hooks 用来提升本地反馈速度，CI 用来保证主干质量。

这两层一起用，才能兼顾体验和可靠性。只有 hooks 没有 CI，质量不稳；只有 CI 没有 hooks，反馈太慢。

所以 hooks 的定位从来不是“保证一切万无一失”，而是“把能早发现的问题尽量提前”。越早暴露，修复成本越低。

## 团队一致性

Hooks 脚本要放进仓库，安装方式要清晰，依赖版本要锁定。否则不同开发者本地行为不一致。

```json
{
  "scripts": {
    "prepare": "husky"
  }
}
```

如果项目使用 pnpm/yarn/npm，要让 hooks 命令和项目包管理器一致。不要在 pnpm 项目里混用全局 npm 命令。

安装方式也要统一。否则新人第一次拉项目后，hook 没生效会直接破坏整个质量链路。

如果团队里经常有人 hook 不生效，优先检查 `prepare` 是否执行、依赖是否正确安装、包管理器是否统一，以及仓库是否有被跳过安装脚本的情况。

## 执行边界

Hooks 应该快、稳定、可解释。常见边界如下：

| 阶段 | 适合任务 |
|---|---|
| pre-commit | 格式化、lint staged |
| commit-msg | 提交信息校验 |
| pre-push | 类型检查、快速单测 |
| CI | 全量构建、E2E、发布校验 |

Git Hooks 和 [[5.7.1 流水线|流水线]] 的关系很简单：本地拦低级错误，CI 拦最终风险。

如果团队已经把本地质量门禁做得比较完整，CI 里就可以更专注于全量构建、集成测试和发布校验，而不是重复做低价值检查。

比较稳的 hooks 设计通常符合下面几个特征：

| 特征 | 说明 |
| --- | --- |
| 快 | 不拖慢日常提交 |
| 稳 | 不依赖脆弱的本地环境差异 |
| 清楚 | 失败信息能直接指导修复 |
| 分层 | 本地和 CI 各做自己最合适的事 |

排查 hooks 问题时，也可以优先看这几类原因：

```text
1. Husky / hook 安装未生效
2. 命令依赖全局环境，导致不同机器结果不一致
3. 检查范围过大，提交体验太慢
4. 本地和 CI 执行的命令不一致
```

只要把这几个问题控制住，Git Hooks 往往会成为质量体系里成本最低、收益最稳定的一环。
