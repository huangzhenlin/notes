## 规范目标

提交规范用于让 Git 历史可读、可检索、可生成 changelog，并能服务版本发布。好的提交信息能说明“为什么改”和“影响什么”，而不是只写“修改了代码”。

```text
feat: add user profile page
fix: handle expired token refresh
docs: update deployment guide
```

提交规范不是形式主义。它让团队在回溯问题、生成版本说明、定位回滚范围时更省力。

规范化提交最大的好处是可追踪。一个问题到底是功能、修复、重构还是文档更新，历史一眼能看出来。

提交规范真正提升的不是“格式统一”，而是信息密度。未来排查 bug、查版本、做回滚、写发布说明时，提交历史能不能快速读懂，差别会非常明显。

## Conventional Commits

Conventional Commits 是常见提交格式：

```text
<type>(<scope>): <description>

<body>

<footer>
```

示例：

```text
feat(auth): support refresh token rotation
```

`type` 描述变更类型，`scope` 描述影响范围，`description` 简要说明行为变化。

如果团队已经有清晰的模块划分，scope 会非常有用。比如 `feat(auth)`、`fix(router)`、`chore(release)`，都能让变更定位更快。

scope 不是必须写，但一旦项目规模上来，它会变得越来越有价值。特别是在 monorepo、组件库、多应用仓库里，没有 scope 的提交信息很难帮助团队快速判断影响范围。

## 类型划分

常见 type 如下：

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修复 bug |
| `docs` | 文档 |
| `style` | 格式，不影响逻辑 |
| `refactor` | 重构 |
| `test` | 测试 |
| `chore` | 工具、依赖、脚手架 |
| `perf` | 性能优化 |
| `build` | 构建系统 |
| `ci` | CI 配置 |

type 要描述用户或工程影响，不要把所有变更都写成 `chore`。

如果 type 乱用，自动生成 changelog 和版本判断也会失真。最常见的问题就是把新功能、修复和重构都写成 `chore`，最后历史看不出重点。

实际使用时，`type` 最好优先表达“变更性质”，而不是作者心情或工作阶段。比如“调一下”“继续改”“再修一次”这类描述虽然真实，但对后续维护几乎没有帮助。

## scope

scope 用来标记影响范围，例如模块、包、页面、能力或目录。

```text
fix(router): preserve query when redirecting
feat(ui): add loading state to button
ci(release): upload source maps
```

在 monorepo 中，scope 可以使用包名或应用名，让变更更容易被定位。

scope 也要避免过细。如果每次都写到某个极小函数、某个临时页面或某个一次性脚本，历史会变得很碎，不利于检索。更合适的是使用模块、包、页面域或能力域这一层粒度。

## 破坏性变更

破坏性变更可以使用 `!` 或 footer 标记。

```text
feat(api)!: remove legacy user endpoint
```

```text
BREAKING CHANGE: remove support for old token format
```

破坏性变更应该写清迁移方式。否则版本号升级了，使用者仍然不知道怎么改。

对于库、SDK、接口层或配置层的破坏性变更，迁移说明比标题更重要。否则提交规范虽然完整，真正接收方还是不知道怎么处理升级。

这也是破坏性变更必须慎重标记的原因。`!` 或 `BREAKING CHANGE` 不只是为了触发 major 版本，更是在告诉维护者和使用者：“这次升级需要你主动评估影响。”

## commitlint

commitlint 可以在提交时校验提交信息。

```javascript
// commitlint.config.js
export default {
  extends: ['@commitlint/config-conventional'],
};
```

配合 Husky：

```bash
pnpm commitlint --edit "$1"
```

本地校验能减少无效提交信息进入仓库，但关键分支仍应由 CI 或合并规则兜底。

如果项目后续要接 changesets 或 semantic-release，这套提交信息约定会直接影响版本和 changelog 的生成质量。

即使当前还没自动发版，也建议先把提交规范打好。因为一旦未来接入自动 changelog 或版本策略，历史质量会直接决定这些工具是否真正可用。

## 变更日志

规范提交可以自动生成 changelog，也能帮助 changesets、semantic-release 等工具判断版本升级类型。

```text
feat -> minor
fix -> patch
BREAKING CHANGE -> major
```

不是所有项目都要自动发版，但提交信息规范化会让发布说明更容易整理。

即使不做全自动发版，规范提交也能让 release note 更容易写，回滚范围更容易找，问题定位更容易看。

对于多人协作来说，提交规范还是一层沟通协议。你不一定认识每个提交者，但你可以通过提交历史快速看懂这次改动是修 bug、加能力、还是只动了构建链。

## 合并策略

Squash merge、merge commit、rebase merge 对提交历史影响不同。

| 策略 | 特点 |
|---|---|
| Squash | 历史简洁，PR 作为一个变更 |
| Merge commit | 保留分支结构 |
| Rebase | 线性历史 |

如果团队使用 squash，PR 标题也要符合提交规范，因为最终进入主干的可能是 PR 标题。

合并策略要和提交规范一起设计，不然单个 commit 规范了，最终进入主干的却是随意的 PR 标题，效果会打折扣。

如果团队主要使用 squash merge，那么 PR 标题本身就应该纳入规范；如果保留分支提交历史，则要保证中间提交至少不至于完全失真。最终原则只有一个：进入主干的历史必须可读。

判断提交规范是否真正落地，可以看这些信号：

| 信号 | 说明 |
| --- | --- |
| release note 整理成本明显下降 | 说明历史结构更清楚了 |
| 回滚时能快速定位范围 | 说明 type 和 scope 有价值 |
| 很少出现无意义提交标题 | 说明规范不仅写了，还被执行了 |
