## 泄露边界

前端代码天然会交给用户浏览器执行，所以任何打进前端产物里的信息，都应该默认可被用户看到。敏感信息泄露不是只发生在接口返回里，也可能来自源码、构建产物、日志、URL、错误提示、Source Map、环境变量和第三方工具。

这也是前端安全里最容易被误判的地方。很多人会觉得“我没把密码写在源码里就没问题”，但只要构建产物、网络响应、日志或调试文件里出现了不该暴露的内容，泄露就已经发生了。

```text
写进前端代码 = 可能被用户看到
写进网络请求 = 可能被抓包看到
写进 URL = 可能被日志和历史记录保存
```

因此前端安全的第一条边界是：不要把真正的密钥、私有凭证、后台权限、数据库连接信息放进浏览器。

更准确地说，凡是泄露后会直接导致账户接管、数据读取、支付滥用或后台访问的内容，都不应该进入前端产物。前端可以持有“可公开标识”和“短期令牌”，但不应该持有长期秘密。

前端里常见的“看起来像密钥但其实可公开”的值包括地图 SDK key、埋点项目 ID、公开 Firebase 配置、Sentry DSN 等。它们不一定需要保密，但必须在服务端或供应商后台限制来源、权限和配额。真正危险的是把后端私钥、云服务 AK/SK、数据库密码、支付私钥、管理员 token 当成环境变量打进 bundle。

```text
可公开配置：API Base URL、环境名、公开项目 ID
短期可见凭证：短期 access token、一次性上传签名
绝不可进前端：服务端私钥、数据库密码、云服务永久密钥
```

判断标准很直接：如果用户复制这个值后能绕过你的服务端直接访问核心资源，它就不应该出现在前端。

## 环境变量

构建工具里的前端环境变量只是“构建时替换”，不是安全存储。

```ts
const apiBase = import.meta.env.VITE_API_BASE_URL;
```

这类变量适合放公开配置，比如接口域名、环境标识、公开的埋点 key。它不适合放服务端密钥、支付私钥、云服务永久 token。只要变量被打进 bundle，用户就能从产物中找到。

前端环境变量本质上是构建阶段注入的字符串替换，不是安全边界。开发时看起来像“私有配置”的值，构建后只要进入 bundle，就和写死在代码里没有本质区别。

很多构建工具会通过前缀区分“允许暴露给前端”的变量，例如 Vite 默认只暴露 `VITE_` 前缀变量。这是一种防误用机制，不是加密机制。一旦变量被允许暴露，它就会进入客户端代码。

```ts
console.log(import.meta.env.VITE_PUBLIC_ANALYTICS_ID);
```

如果某个能力需要服务端密钥，例如调用云服务管理 API、生成支付签名、访问私有数据库，就应该通过服务端接口代理。前端发起业务请求，服务端校验用户身份和权限后，再用私密凭证调用第三方服务。

```text
浏览器
  -> 业务接口
  -> 服务端校验
  -> 服务端使用私钥调用第三方
  -> 返回最小结果
```

## Token 存储

身份凭证要尽量减少暴露面。

| 位置 | 特点 | 风险 |
| --- | --- | --- |
| 内存 | 页面刷新丢失 | 体验复杂 |
| `HttpOnly` Cookie | JS 读不到 | 要处理 CSRF |
| `localStorage` | 使用简单 | XSS 后容易被读取 |
| URL 参数 | 传递方便 | 极易泄露 |

如果必须在前端持有 token，要缩短有效期、限制权限、配合刷新机制和异常退出。能用服务端会话解决的场景，不要为了“前后端分离感”强行把长期凭证暴露给浏览器。

前端保存 token 的风险不只是被人打开控制台看见，还包括 XSS、浏览器扩展、共享设备、自动化脚本和误复制。越容易被脚本读到的位置，越不适合放高价值凭证。

如果 token 必须被 JavaScript 读取，应该尽量缩短有效期、限制 scope，并避免把 refresh token 放进同样位置。access token 泄露后的影响应该是分钟级，而不是长期可用。

```json
{
  "scope": "profile:read order:create",
  "expires_in": 900
}
```

登出时要清理所有相关位置：内存状态、本地存储、会话存储、查询缓存、Service Worker 缓存和正在排队的请求。多账号切换尤其要注意，不要让上一个用户的数据留在当前页面状态里。

## URL 泄露

URL 会出现在浏览器历史、Referer、服务器日志、监控系统和截图里，所以不要把敏感信息放在查询参数里。

```text
不推荐：/reset-password?token=secret
更稳妥：短期 token + 一次性使用 + 服务端校验 + 跳转后清理
```

有些业务必须通过 URL 承载短期 token，比如邮箱验证或密码重置，这时要限制有效期、一次性使用、绑定场景，并在使用后立即失效。

如果 token 出现在跳转链接里，还要注意 Referer、浏览器历史和页面分享。使用后最好及时跳转并清理地址栏，避免后续页面继续携带这个值。

短期 token 出现在 URL 中时，最好使用后立即换成普通地址。前端可以在服务端校验成功后调用 `history.replaceState` 清理地址栏，避免用户复制、截图或跳转时继续带着敏感参数。

```ts
const url = new URL(location.href);

if (url.searchParams.has("token")) {
  url.searchParams.delete("token");
  history.replaceState(null, "", url.toString());
}
```

重置密码、邮箱验证、邀请链接这类场景，还要让 token 一次性使用，并绑定具体用途。不能让同一个 URL token 同时完成登录、改密码、绑定账号等多个高风险动作。

## 日志与埋点

前端日志经常会把用户输入、接口响应、错误对象一起上报。这里最容易泄露手机号、邮箱、身份证、token、订单号和内部错误栈。

```ts
function maskPhone(phone: string) {
  return phone.replace(/(\d{3})\d{4}(\d{4})/, "$1****$2");
}
```

上报前要做脱敏，尤其是错误监控和行为分析工具。第三方监控平台属于外部系统，不能默认它适合保存所有业务数据。

脱敏最好在采集端完成，而不是只在后台展示时打码。因为一旦原始数据被发出，落到第三方系统或日志平台里，后面就很难完全收回来。

错误对象也可能携带敏感信息。比如请求失败时直接上报完整 config，里面可能包含 `Authorization`、Cookie、请求体、用户输入和内部接口地址。封装请求库时，应该在上报前统一过滤。

```ts
function sanitizeHeaders(headers: Record<string, string>) {
  const result = { ...headers };
  delete result.Authorization;
  delete result.Cookie;
  return result;
}
```

埋点字段要遵循最小化原则：能上传枚举就不要上传原文，能上传长度区间就不要上传完整内容，能在服务端关联就不要在前端拼接个人信息。第三方平台的权限、保留时间和导出能力也要纳入数据治理。

## Source Map

生产环境 Source Map 能帮助定位问题，也可能暴露源码结构、接口路径和内部注释。

```text
公开访问的 source map
  -> 调试方便
  -> 源码暴露风险更高
```

如果要保留生产 Source Map，最好上传到受控监控平台，不直接公开到静态资源目录。对于安全敏感项目，可以只在内部环境或受权限控制的系统里使用。

Source Map 的风险不只是“别人能看到源码”，还包括内部模块关系、接口路径、注释和文件组织方式都可能暴露。对外站点如果没有强需求，通常应尽量避免公开发布可直接访问的 map 文件。

如果需要生产问题定位，可以把 Source Map 上传到错误监控平台，然后从公开静态目录删除。这样线上错误仍然能映射源码，但普通用户无法直接下载完整源码映射。

```text
构建产物生成 source map
  -> CI 上传到监控平台
  -> 静态资源发布时排除 .map
```

同时要检查 source map 里是否包含源码内容。某些配置会把完整源码嵌入 map 文件，暴露程度比只暴露映射关系更高。安全敏感项目发布前应明确 source map 策略，而不是沿用脚手架默认值。

## 接口响应

接口不要因为“前端暂时不用”就返回全量数据。返回越多，泄露面越大。

```json
{
  "id": "u_1",
  "name": "Ada"
}
```

比起返回完整用户对象后让前端挑字段，更好的方式是后端按页面需要返回最小数据集。隐藏字段不是安全措施，浏览器网络面板里能看到完整响应。

这条原则同样适用于错误响应。不要把调试堆栈、数据库表名、内部服务名和实现细节直接透给前端。错误要能帮助定位问题，但不应该把内部结构一并送出去。

接口响应应按页面场景设计 DTO，而不是把数据库实体原样返回。数据库字段经常包含内部状态、风控标记、权限位、删除标记和审计信息，这些字段前端不一定需要，也不应该默认暴露。

```json
{
  "id": "order_1",
  "status": "paid",
  "amount": 12900,
  "displayNo": "202607300001"
}
```

分页、搜索和导出接口也要小心。导出文件常常比页面响应包含更多字段，一旦权限校验或字段过滤复用不当，就可能成为批量泄露入口。

## 处理原则

| 场景 | 推荐处理 |
| --- | --- |
| 前端环境变量 | 只放公开配置 |
| 身份凭证 | 短期、最小权限、减少 JS 可读 |
| URL token | 短期、一次性、使用后失效 |
| 日志埋点 | 脱敏后再上报 |
| Source Map | 受控存储，不公开散发 |
| 接口数据 | 最小字段返回 |

敏感信息防护的核心不是“藏得更巧”，而是不要让它进入不该进入的地方。浏览器端永远不是保密容器，前端应该默认自己处在公开环境里。

实战里可以把信息分成三类：可公开信息、短期可见信息、绝对不可暴露信息。前者可以进入前端，第二类要严格控制生命周期和上下文，第三类应完全留在服务端或受控后台。

上线前可以按“产物、网络、存储、日志”四条线检查：构建产物里是否有密钥，网络响应是否返回多余字段，浏览器存储里是否有高价值凭证，日志和埋点是否带个人信息。任何一条线泄露，都不能靠“代码混淆”解决。

```text
构建产物：bundle、source map、静态配置
网络链路：请求、响应、重定向、Referer
浏览器存储：Cookie、localStorage、IndexedDB、Cache
观测系统：日志、埋点、错误监控、录屏
```

前端安全里的敏感信息治理，本质上是数据生命周期管理。进入前端前要问是否必要，进入后要问在哪里保存，发送出去前要问是否脱敏，使用结束后要问是否清理。只要这几个问题形成习惯，泄露风险会下降很多。
