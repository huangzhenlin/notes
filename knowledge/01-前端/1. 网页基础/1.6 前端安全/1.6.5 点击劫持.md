## 攻击方式

点击劫持（Clickjacking）是把目标页面放进透明或伪装的 `iframe` 里，诱导用户在不知情的情况下点击真实页面上的敏感按钮。用户看到的是 A，实际点到的是 B。

```html
<iframe src="https://bank.example/transfer"></iframe>
```

它的核心不是“页面被嵌了就危险”，而是“被嵌后用户的点击意图被篡改了”。这类问题最适合用浏览器层限制，而不是靠前端按钮遮挡。

因为攻击者不需要读内容，只需要借用户的手点到敏感按钮，所以点击劫持通常发生在“用户信任页面”的场景里，比如银行、支付、管理后台和账户设置页。

典型攻击页面会把目标站点 iframe 放在按钮下方，再用透明度、定位、诱导文案让用户点击。用户以为自己点的是“领取奖励”，实际点击的是目标站点里的“确认转账”。

```html
<style>
  iframe {
    position: absolute;
    inset: 0;
    width: 100%;
    height: 100%;
    opacity: 0.01;
    z-index: 2;
  }

  .fake-button {
    position: absolute;
    top: 240px;
    left: 120px;
    z-index: 1;
  }
</style>

<button class="fake-button">领取奖励</button>
<iframe src="https://target.example/account/delete"></iframe>
```

如果目标页面仍保持登录态，并且敏感按钮不需要二次确认，攻击者就可能把用户意图和真实点击错位。点击劫持攻击的重点不是读取页面，而是操纵交互。

## 防护指令

最常用的防护是 `frame-ancestors` 和 `X-Frame-Options`。

```http
Content-Security-Policy: frame-ancestors 'none'
X-Frame-Options: DENY
```

`frame-ancestors` 更灵活，`X-Frame-Options` 兼容性更老牌。实际项目里通常优先 CSP，再视兼容情况补 `X-Frame-Options`。

如果业务里根本不需要被嵌入，最简单的策略就是直接拒绝所有嵌入；如果确实需要合作方嵌入，也要把允许来源写成白名单，而不是放开给整个互联网。

`frame-ancestors` 的匹配对象是“谁能嵌入当前页面”，不是“当前页面能嵌入谁”。它必须由被保护页面的响应头下发，而不是攻击页面自己决定。

```http
Content-Security-Policy: frame-ancestors 'self' https://partner.example
```

`X-Frame-Options` 只支持 `DENY` 和 `SAMEORIGIN` 等较简单策略，不能表达多个合作方来源。新项目优先用 CSP；如果要兼容旧环境，可以两者同时设置，但要避免策略互相矛盾。

```http
Content-Security-Policy: frame-ancestors 'none'
X-Frame-Options: DENY
```

## SameSite 辅助

`SameSite` Cookie 也能在一定程度上缓解点击劫持，因为很多认证态在 `iframe` 中不会携带 Cookie。

但它的帮助是间接的。真正决定页面能不能被嵌进去的，还是 `frame-ancestors` 或旧的 `X-Frame-Options`。所以不要把 `SameSite` 当成点击劫持的主要防线。

```http
Set-Cookie: session=abc; Path=/; Secure; HttpOnly; SameSite=Lax
```

但它不是点击劫持专用方案，也不是所有业务都靠得住。页面是否能被嵌入，最好还是交给 `frame-ancestors` 明确声明。

`SameSite` 的价值是降低 iframe 中登录态可用性，但它受业务登录方式、浏览器策略和 Cookie 属性影响。比如某些跨站嵌入业务本来就需要 `SameSite=None; Secure`，此时 Cookie 可能仍会在第三方上下文中携带。安全设计不能假设 Cookie 一定不会出现。

如果页面是支付确认、账户删除、权限授权这类高风险操作，即使 Cookie 因 `SameSite` 没被带上，也应该用 `frame-ancestors` 明确禁止嵌入。安全策略越明确，排查越简单。

## 防御层次

```text
浏览器禁止嵌入
  -> Cookie 降低可利用性
  -> 页面上避免高风险无确认操作
```

如果某些页面必须被嵌入，比如支付 SDK、预览页、广告组件，就要对允许嵌入的来源做白名单，而不是全部开放。

同时，高风险操作最好要求页面内再次确认，例如二次密码、显式提交、倒计时确认或跳转到顶层窗口。即使浏览器层防线漏了一层，页面层也还能再兜一下。

页面层兜底不能依赖“检测自己是否在 iframe 中然后跳出”作为主防线。过去常见的 frame busting 脚本容易被 sandbox、浏览器限制或攻击页面技巧绕过。

```js
if (window.top !== window.self) {
  window.top.location = window.self.location;
}
```

这类代码最多作为兼容兜底，不应该替代响应头。浏览器安全策略由浏览器在嵌入阶段执行，比页面脚本加载后再自救更可靠。

高风险操作还可以要求用户在当前页面输入一段确认文本、重新输入密码或进行二次验证。这不是点击劫持的第一防线，但能减少“单次误点即完成”的危险。

## 沙盒限制

`iframe` 自身也可以配合 `sandbox` 收紧能力。

```html
<iframe
  src="/preview"
  sandbox="allow-scripts allow-same-origin"
></iframe>
```

`sandbox` 更像“被嵌入内容的能力开关”，而 `frame-ancestors` 更像“允许谁来嵌”。两个方向不同，但放在一起时效果最好。

如果你维护的是对外开放的内容页，允许嵌入与禁止嵌入往往会按页面区分，而不是按整个站点一刀切。比如预览页可嵌，账户页不可嵌，这样策略更贴近业务。

`sandbox` 的权限组合要小心。`allow-scripts` 允许脚本执行，`allow-same-origin` 允许 iframe 保持同源身份；两者同时出现时，如果嵌入的是同源页面，页面可能移除 sandbox 或恢复较高能力。对不可信内容预览，最好放到独立域名，并严格限制 sandbox 权限。

```html
<iframe
  src="https://preview.example/file/123"
  sandbox="allow-scripts"
></iframe>
```

如果只是展示静态预览，不一定需要 `allow-forms`、`allow-popups`、`allow-top-navigation`。iframe 权限越少，被嵌内容越难影响宿主页面。

## 判断边界

| 情况 | 是否需要防护 |
| --- | --- |
| 登录后可修改资料 | 需要 |
| 重要支付/转账页 | 强烈需要 |
| 公开内容展示页 | 视业务而定 |
| 仅做静态预览嵌入 | 需要受控白名单 |

点击劫持看起来像 UI 问题，实际是浏览器信任边界问题。要把它当成“页面是否允许在别人的上下文里运行”的策略来处理。

排查时可以先看响应头里有没有 `frame-ancestors` 或 `X-Frame-Options`，再确认是否存在第三方嵌入需求。很多“页面为什么在某些站点里打不开”的问题，其实是安全策略生效了，而不是页面本身坏了。

真实项目里可以按页面分类制定策略：账户、支付、后台、授权页默认禁止嵌入；公开内容页按业务决定；合作方嵌入页单独列白名单；预览和沙盒页放到隔离域名。这样比全站一个策略更精确，也更容易和产品需求协调。

验证时不需要复杂工具，写一个本地 HTML 嵌入目标页面即可。如果 iframe 加载失败并出现 CSP 或 X-Frame-Options 相关错误，说明策略生效；如果能正常嵌入，就要确认这是否符合预期。
