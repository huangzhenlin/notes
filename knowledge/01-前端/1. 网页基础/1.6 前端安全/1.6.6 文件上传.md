## 风险入口

文件上传是前端安全里最容易被低估的入口，因为它看起来只是“把文件交给服务器”。实际风险包括恶意脚本、伪造类型、超大文件、压缩炸弹、路径穿越、敏感数据泄露和存储桶权限错误。

```html
<input type="file" accept="image/png,image/jpeg" />
```

`accept` 只能改善用户选择体验，不能作为安全校验。攻击者可以绕过浏览器限制直接构造请求，所以真正的校验必须在服务端完成。

前端在这里的角色是“减少误操作”和“尽早提示风险”，而不是“最终放行”。所以不要把文件上传当成一个普通表单项，它本质上是一个受控的数据入口。

文件上传的风险通常不是单点发生，而是贯穿选择、上传、存储、处理、访问和删除整个生命周期。比如用户上传了伪装成图片的 SVG，上传接口本身可能没问题，但后续如果被当成同源资源直接打开，就可能执行脚本；用户上传了超大压缩包，上传时只是一个文件，解压或扫描时才可能消耗大量资源。

```text
选择文件
  -> 上传请求
  -> 临时存储
  -> 校验/扫描/转码
  -> 业务绑定
  -> 对外访问
  -> 删除归档
```

前端要把“文件已上传”和“文件已通过安全处理”区分开。业务页面展示的应该是服务端确认后的文件状态，而不是浏览器刚选中的本地文件。

## 类型校验

前端可以做预校验，但服务端要重新验证扩展名、MIME、文件头和内容。

```ts
function isAllowedImage(file: File) {
  const allowTypes = ["image/png", "image/jpeg", "image/webp"];
  const maxSize = 2 * 1024 * 1024;

  return allowTypes.includes(file.type) && file.size <= maxSize;
}
```

这段代码能减少误传和无效请求，但不能证明文件一定安全。比如攻击者可以伪造 MIME，或者把脚本藏进可被错误解析的文件里。

前端校验的价值主要体现在体验和成本控制：用户能更早知道文件太大、类型不对、尺寸不合适，减少无效上传；真正的可信判断仍然要看服务端。

文件类型不能只看扩展名或 `file.type`。浏览器给出的 MIME 可能为空，也可能来自操作系统或文件名推断。服务端通常要结合魔数、MIME、扩展名和解析结果判断。

```ts
async function readHeader(file: File) {
  const buffer = await file.slice(0, 12).arrayBuffer();
  return [...new Uint8Array(buffer)]
    .map((byte) => byte.toString(16).padStart(2, "0"))
    .join(" ");
}
```

前端读取文件头可以用于更友好的提示，但不要把它当成可信结论。真正的安全校验必须在服务端重新读取文件内容完成。

图片上传还要考虑尺寸和像素数量。一个文件体积不大，但分辨率极高，也可能在解码、缩放、生成缩略图时消耗大量内存。

```ts
function getImageSize(file: File) {
  return new Promise<{ width: number; height: number }>((resolve, reject) => {
    const url = URL.createObjectURL(file);
    const image = new Image();

    image.onload = () => {
      URL.revokeObjectURL(url);
      resolve({ width: image.naturalWidth, height: image.naturalHeight });
    };

    image.onerror = () => {
      URL.revokeObjectURL(url);
      reject(new Error("Invalid image"));
    };

    image.src = url;
  });
}
```

## 文件名处理

用户上传的文件名不要直接用于服务端存储路径。

```text
用户文件名：../../shell.php
安全存储名：2026/07/uuid.webp
展示名称：保留原文件名作为普通文本
```

服务端应该生成新的文件名，把原始文件名只当作展示字段，并且输出时按普通文本处理。路径、扩展名、目录结构都不应该由用户决定。

文件名还可能包含控制字符、超长字符串、同形字符、多个扩展名和容易误导的后缀，例如 `avatar.png.php`、`report.pdf.exe`。展示原始文件名时，要限制长度并按文本输出；下载时要谨慎设置 `Content-Disposition`。

```http
Content-Disposition: attachment; filename="report.pdf"; filename*=UTF-8''report.pdf
```

如果需要保留用户文件名作为下载名，也应该由服务端清洗后再写响应头，避免换行注入或头部污染。存储名和展示名分离，是文件上传里非常基础但很重要的边界。

## 预览处理

图片预览常见写法是 `URL.createObjectURL`。

```ts
const previewUrl = URL.createObjectURL(file);
image.src = previewUrl;

image.onload = () => {
  URL.revokeObjectURL(previewUrl);
};
```

预览不等于可信。即使前端能正常显示，也不能说明这个文件可以安全入库或公开访问。对于 SVG、HTML、PDF 等可能带脚本或复杂解析行为的格式，更要谨慎。

如果预览需要展示给其他用户看，最好在服务端完成转码或生成安全缩略图，而不是把原始文件直接公开给浏览器。很多上传漏洞不是发生在“上传”，而是发生在“后续访问”。

SVG 要特别谨慎。它是图片格式，但本质上是 XML，可以包含脚本、外链资源和事件属性。如果业务只是头像或普通图片，通常不应该允许 SVG；如果必须允许，最好服务端净化并通过独立域名、下载方式或受限 CSP 展示。

PDF、Office 文档也类似。浏览器预览、第三方预览服务和下载行为都有不同风险。对不可信文档，建议通过转图片、转 PDF、沙盒 iframe 或隔离域名展示，避免让它以主站同源身份运行。

```http
Content-Type: application/octet-stream
Content-Disposition: attachment
X-Content-Type-Options: nosniff
```

`nosniff` 可以减少浏览器把文件按错误类型解析的风险，但它不能替代正确的 `Content-Type` 和访问控制。

## 上传策略

```text
选择文件
  -> 前端大小/类型预校验
  -> 上传到受控接口或对象存储
  -> 服务端重新校验
  -> 重命名与隔离存储
  -> 扫描或转码
  -> 返回受控访问地址
```

图片类文件常见做法是服务端重新编码成标准格式，既能压缩，也能去掉潜在元数据和异常结构。文档类文件则更适合走扫描、隔离和权限控制。

上传完成后还要考虑生命周期管理。临时附件、草稿附件、已删除附件、历史版本附件是否需要保留，保留多久，谁能访问，这些都要在产品和后端层提前定义。

上传链路最好有明确状态机，而不是上传成功就立即公开。

```text
pending
  -> uploaded
  -> scanning
  -> ready
  -> rejected
```

前端展示时可以根据状态给用户明确反馈：上传中、处理中、审核失败、可使用。这样能避免用户拿到一个尚未扫描或尚未绑定业务的文件地址就开始传播。

分片上传还要处理重复分片、乱序分片、取消上传和过期清理。服务端合并前必须确认每个分片属于同一用户、同一任务、同一文件，不要让攻击者借分片接口拼接任意内容。

## 对象存储

前端直传对象存储时，不要把永久密钥放到浏览器里。应该由服务端签发短期、范围受限的上传凭证。

```text
前端请求上传凭证
  -> 服务端校验用户和业务权限
  -> 返回短期签名 URL
  -> 前端直传
  -> 服务端确认文件归属和状态
```

签名 URL 要限制过期时间、路径范围、文件大小和内容类型。上传成功后，还要让服务端记录文件归属，否则对象存储里可能出现“传上去了但业务上没人管”的孤儿文件。

如果上传链路支持断点续传或分片上传，前端还要额外处理进度、重试和取消。这里最重要的是把“上传状态”和“业务提交状态”分开，不要上传完就默认业务也成功。

签名 URL 权限应该尽量窄：只允许上传到某个用户或业务前缀，只允许指定方法，只在短时间内有效，只允许合理大小和类型。如果把对象存储写权限做得太宽，前端泄露一个签名就可能被批量滥用。

```text
user-uploads/{userId}/{uploadId}/original
```

对象默认不要公开读。公开访问应该由业务状态决定，例如头像审核通过后才生成公开 URL，私有附件则通过后端鉴权后短期签名下载。

## 风险边界

| 风险 | 防护重点 |
| --- | --- |
| 伪造类型 | 服务端校验文件头和内容 |
| 超大文件 | 前后端同时限制大小 |
| 路径穿越 | 服务端重命名和隔离目录 |
| 恶意脚本 | 禁止可执行目录，必要时转码 |
| 隐私泄露 | 控制访问权限和生命周期 |

文件上传的原则是：前端负责体验和早期拦截，服务端负责最终可信判断，存储层负责隔离和权限。

如果业务允许用户上传敏感内容，建议再加一层审核或病毒扫描，并在展示前控制访问权限。这样即使文件本身安全，误上传带来的业务风险也能降低。

前端实现上传组件时，最好把这些限制变成显式配置：允许类型、最大大小、最大数量、是否多选、是否需要裁剪、是否支持断点续传、失败后是否可重试。组件只负责表达规则和交互，不应该把安全结论写死在浏览器里。

```ts
type UploadPolicy = {
  accept: string[];
  maxSize: number;
  maxCount: number;
  multiple: boolean;
};
```

服务端返回的错误也要足够具体，例如文件过大、类型不支持、扫描失败、权限不足、签名过期。安全失败不应该都显示“上传失败”，否则用户和开发者都很难判断问题发生在哪一层。
