## 责任边界

前端说的“鉴权”，通常混着两个概念：认证（Authentication）和授权（Authorization）。认证是确认“你是谁”，授权是确认“你能做什么”。很多安全问题不是认证没做，而是认证之后的权限边界没守住。

从实现上看，认证更接近登录态建立，授权更接近资源访问控制。也就是说，前端页面看到“用户已登录”只说明身份被识别，不代表这个用户可以访问任何页面或任何数据。

```text
登录 -> 获取会话或令牌 -> 请求接口 -> 服务端校验身份 -> 判断权限 -> 执行操作
```

前端能做的更多是承载流程、展示状态和减少误操作，真正的权限判断必须放在服务端。否则只改按钮隐藏、路由守卫或前端条件分支，安全上都不够。

一个常见误区是把“路由守卫通过”当成“用户有权限”。路由守卫只能控制页面入口，不能保护接口和数据。用户可以绕过前端直接发请求，也可以修改本地状态让按钮出现。真正的权限判断必须在服务端根据身份、角色、资源归属和业务规则重新计算。

```tsx
if (canDelete) {
  return <button onClick={() => deleteUser(user.id)}>删除</button>;
}
```

这段代码可以改善体验，但 `DELETE /users/:id` 仍然必须检查当前用户是否真的能删除目标用户。前端隐藏按钮是“减少误点”，不是“阻止越权”。

## 会话方式

前端常见的身份承载方式有 Cookie 会话、Token 和短期凭证。

| 方式 | 优点 | 风险点 |
| --- | --- | --- |
| Cookie 会话 | 浏览器自动携带，适合传统站点 | 需要处理 CSRF |
| Token | 更适合前后端分离 | 存储位置要谨慎 |
| 短期凭证 + 刷新 | 风险更可控 | 实现更复杂 |

Cookie 适合让浏览器帮你传递身份，但也更容易受 CSRF 影响；Token 更灵活，但如果随意放在 `localStorage` 里，又会被 XSS 放大风险。两者没有绝对优劣，关键是匹配架构。

如果是传统站点和服务端渲染，Cookie 会话通常更自然；如果是前后端分离、移动端、跨端应用，短期 token 加刷新机制会更灵活。选型时不要只看“技术新不新”，要看安全边界、运维成本和业务形态是否匹配。

Cookie 会话的优势是凭证可以放进 `HttpOnly` Cookie，脚本读不到；代价是要认真处理 [[1.6.2 CSRF|CSRF]]。Token 的优势是适合多端和 API 调用；代价是前端一旦能读取 token，XSS 后就可能被窃取。短期 access token 配合 refresh token 可以降低单个 token 泄露后的影响，但刷新流程也必须防重放、防并发覆盖和异常循环。

```text
用户登录
  -> 服务端签发短期 access token
  -> 服务端设置 refresh cookie
  -> access token 过期
  -> 前端调用刷新接口
  -> 服务端校验 refresh cookie 并轮换凭证
```

刷新接口是高价值目标。它通常需要 `HttpOnly`、`Secure`、`SameSite`、CSRF 防护、设备绑定或刷新令牌轮换。否则攻击者拿到刷新能力后，就能长期维持会话。

## 登录状态

```tsx
function Avatar({ user }: { user: { name: string } | null }) {
  if (!user) {
    return <a href="/login">登录</a>;
  }

  return <span>{user.name}</span>;
}
```

前端展示登录态主要是体验问题，不是安全判断。即使页面显示“已登录”，接口仍然必须做服务端校验；即使前端禁用了按钮，攻击者也可以直接调接口。

因此登录态组件、头像菜单、退出入口都只是“视觉表达”。真正的会话状态应由服务端权威决定，前端只负责展示、跳转和过期处理。

前端本地的用户信息应该被看作缓存，而不是权威数据。页面初始化时可以先展示缓存减少闪烁，但关键操作前仍要以接口返回为准。尤其是角色、套餐、组织成员身份这类权限相关字段，不应该只依赖本地持久化值。

```tsx
async function loadCurrentUser() {
  const response = await fetch("/api/me", {
    credentials: "include",
  });

  if (response.status === 401) {
    return null;
  }

  return response.json();
}
```

登录态失效时，要统一清理内存状态、缓存用户信息、正在排队的请求和敏感页面数据。只跳转登录页但不清理旧状态，可能导致用户短暂看到过期数据，或者多账号切换时展示错账号信息。

## 权限判断

权限通常分成页面级、功能级、数据级三层。

| 层级 | 例子 | 落点 |
| --- | --- | --- |
| 页面级 | 是否能进入管理页 | 路由 + 接口 |
| 功能级 | 是否能看到删除按钮 | 展示控制 + 服务端 |
| 数据级 | 是否能改别人的资料 | 接口鉴权最关键 |

前端可以减少越权操作的入口，但不能作为最终防线。一个常见错误是“看不到按钮就等于不能操作”，这在抓包工具面前通常不成立。

更稳的设计是让页面权限和数据权限同时成立：页面决定入口是否可见，接口决定数据是否可改。这样即便前端被篡改，服务端也能兜住。

权限模型常见有 RBAC、ABAC 和资源归属校验。RBAC 按角色授权，适合后台菜单和功能入口；ABAC 按属性和条件授权，适合更细粒度的业务规则；资源归属校验则是最容易被漏掉的一层，比如“只能编辑自己创建的文档”。

```typescript
type Permission = "user:create" | "user:delete" | "article:publish";

function hasPermission(permissions: Permission[], permission: Permission) {
  return permissions.includes(permission);
}
```

前端可以用权限点控制显示，但权限点命名要和后端保持一致。不要一个页面写 `isAdmin`，另一个页面写 `canManage`，第三个页面写 `role === 1`。权限表达越分散，越容易出现展示和接口规则不一致。

## 存储位置

如果身份信息要在前端保存，优先考虑最小暴露。

```text
会话 Cookie（HttpOnly + Secure + SameSite）
  > 短期内存状态
  > 必要时的受控 token
  > 尽量少放 localStorage
```

`HttpOnly` 能减少脚本读取 Cookie 的风险，`Secure` 能限制传输到 HTTPS，`SameSite` 能缓和跨站请求。它们不是替代品，而是一起工作。

存储策略还要看威胁模型。如果应用容易遭受 XSS，能放进 `HttpOnly` Cookie 的身份信息就不要放进可被脚本读取的位置；如果业务必须把短期令牌交给前端脚本读取，那就要缩短有效期并加强刷新机制。

不要把敏感信息和用户偏好混在一起存。主题色、语言、折叠菜单可以放本地存储；access token、refresh token、身份证号、完整手机号、权限密钥不应该随意放进 `localStorage`。如果确实需要前端保存短期 token，优先放内存，并在刷新、关闭标签页、登出时清理。

```typescript
let accessToken: string | null = null;

export function setAccessToken(token: string | null) {
  accessToken = token;
}

export function getAccessToken() {
  return accessToken;
}
```

内存 token 的代价是刷新页面会丢失状态，需要通过刷新接口恢复。这是体验和安全之间的取舍，不能只从“实现方便”决定。

## 失效处理

前端还要处理登录态失效、权限变更和多端并发登录。

```tsx
if (response.status === 401) {
  redirectToLogin();
}

if (response.status === 403) {
  showForbiddenPage();
}
```

`401` 更像“身份没了或没认证成功”，`403` 更像“身份有，但权限不够”。把这两类状态分清楚，错误页、跳转策略和重试逻辑才会更自然。

除了 401/403，很多产品还会遇到 419、440 之类的会话过期状态。前端最好把这些状态统一抽象成“需要重新登录”“权限不足”“账号异常”三类，而不是让页面直接依赖某个 HTTP 数字。

刷新 token 时要避免“并发刷新风暴”。多个请求同时收到 401，如果每个请求都发刷新接口，可能造成状态覆盖或触发风控。更稳的做法是把刷新过程收敛成单飞请求：第一个请求负责刷新，其他请求等待结果。

```typescript
let refreshing: Promise<void> | null = null;

async function refreshOnce() {
  if (!refreshing) {
    refreshing = refreshSession().finally(() => {
      refreshing = null;
    });
  }

  return refreshing;
}
```

刷新失败后要统一退出登录，而不是无限重试。无限刷新循环会让页面卡死，也可能把服务端打满。

## 前后端边界

| 问题 | 前端能做 | 服务端必须做 |
| --- | --- | --- |
| 识别用户 | 展示登录状态 | 验证身份 |
| 控制入口 | 隐藏按钮、路由拦截 | 拒绝非法请求 |
| 防止越权 | 提示当前用户 | 检查资源归属 |
| 降低风险 | 规范存储方式 | 设置会话策略 |

真正可靠的鉴权，不是让前端看起来像安全系统，而是让前端只负责表达状态，让服务端负责裁决。

如果项目里还有路由守卫、按钮权限和接口拦截，最好把它们都当作同一套鉴权体系的不同表现层，而不是三套各自维护的逻辑。这样权限变更、角色调整或接口升级时，才不会到处漏改。

前端鉴权代码的目标是“体验一致、失败可控、状态清晰”。体验一致，是指菜单、按钮、路由、错误页使用同一份权限数据；失败可控，是指 401/403/会话过期都有明确处理；状态清晰，是指本地缓存、内存状态和服务端状态不会互相打架。

```text
服务端权限结果
  -> 前端权限模型
  -> 路由入口
  -> 菜单按钮
  -> 接口错误处理
```

任何一个环节都不能替代服务端校验，但它们可以让用户少走弯路，也能让越权尝试以明确错误结束。安全不是把所有逻辑都堆到前端，而是让前端在正确边界内把体验做好。
