## 供应链本质

前端项目依赖多、更新快、构建链路长，所以依赖安全不是“装包时看一眼”就结束。风险可能来自直接依赖、间接依赖、构建插件、脚手架、CI 脚本、CDN 脚本甚至开发机环境。

```text
业务代码 -> 直接依赖 -> 间接依赖 -> 构建插件 -> 发布产物
```

攻击者不一定要改你的代码，只要污染你信任的依赖或构建过程，就可能进入最终产物。

这就是为什么依赖安全不只是“漏扫漏洞”，而是整个供应链可信度的问题。脚手架、插件、脚本、镜像源、CI runner 都可能成为入口。

前端供应链有一个特点：很多依赖只在构建时运行，却能影响最终产物。比如 Vite 插件、Babel 插件、PostCSS 插件、代码生成器、GitHub Action，它们不一定进入浏览器 bundle，但运行时拥有读取源码、环境变量和文件系统的能力。攻击者污染这类依赖，可能直接把恶意代码注入产物或窃取发布密钥。

```text
安装依赖
  -> 执行 install/postinstall
  -> 构建插件读取源码
  -> 注入或改写产物
  -> CI 发布到线上
```

所以依赖安全要同时看“浏览器运行路径”和“构建执行路径”。开发依赖不一定低风险，尤其当它能在 CI 中执行脚本时。

## 版本锁定

锁文件是依赖安全和可复现构建的基础。

```text
package.json
package-lock.json / pnpm-lock.yaml / yarn.lock
```

`package.json` 描述版本范围，锁文件记录实际安装版本。没有锁文件，今天安装和明天安装可能得到不同依赖树，排查问题会很痛苦，也更容易引入未审查的版本。

锁文件还承担了安全审计的基础作用。它让团队知道“线上构建到底装了什么”，否则同一个提交在不同机器上的产物都可能不一样。

版本范围也会影响风险。`^1.2.3` 允许升级到同一大版本内的新版本，`~1.2.3` 通常只允许补丁级变化，精确版本最可控但维护成本更高。锁文件能固定当前安装结果，但新增安装、更新锁文件和 CI 缓存仍然要纳入审查。

```json
{
  "dependencies": {
    "example-lib": "^1.2.3"
  }
}
```

不要手工随意改锁文件来“解决冲突”。锁文件变化应该通过包管理器生成，并在代码评审里关注新增包、版本跃迁、依赖来源和体积变化。锁文件很长，但它是供应链变更清单。

## 风险扫描

常见扫描包括包管理器审计、平台安全提醒、SCA 工具和 CI 检查。

```bash
npm audit
pnpm audit
```

扫描结果要看可利用条件，而不是看到告警就机械升级。有些漏洞只影响服务端运行，有些只存在于开发依赖，有些需要特定 API 才能触发。真正的判断要结合项目使用方式。

如果漏洞只出现在测试工具、生成器或未启用的代码路径里，优先级通常会低一些；如果漏洞存在于浏览器运行路径、构建插件或发布脚本里，就要更严肃地处理。

扫描告警可以按几个问题判断优先级：漏洞依赖是否进入生产产物，是否在构建时执行，是否可被外部输入触发，是否已有修复版本，是否存在临时缓解手段。一个高危告警如果只影响未使用的 CLI 子命令，优先级可能低于一个中危但会进入用户浏览器的漏洞。

```text
漏洞包
  -> 直接依赖还是间接依赖
  -> 生产依赖还是开发依赖
  -> 运行时路径还是构建路径
  -> 当前代码是否调用风险 API
  -> 是否能最小升级修复
```

审计报告不是结论，而是排查入口。真正重要的是形成“谁评估、谁修复、多久内关闭”的流程，否则告警会越积越多，最后团队只能选择忽略。

## 升级策略

```text
安全告警
  -> 判断是否在运行路径
  -> 查看修复版本
  -> 小版本优先升级
  -> 跑测试和构建
  -> 必要时临时替换或隔离
```

不要为了清空告警盲目大版本升级。大版本可能带来 API 变更，反而引入功能风险。更稳的方式是先升级最小可修复版本，再通过测试和构建验证。

升级前最好看一下依赖是否还维护、是否有替代方案、是否被更深层的包间接依赖。很多时候最危险的不是一个已知漏洞，而是“明知道有风险却一直没人处理”。

间接依赖漏洞有时不能直接升级目标包，需要升级上游依赖，或者使用包管理器的 override/resolution 临时固定版本。

```json
{
  "pnpm": {
    "overrides": {
      "vulnerable-package": "1.2.4"
    }
  }
}
```

这种覆盖要谨慎：它可能让上游包在未测试版本下运行。最好只作为短期缓解，并在备注或 issue 中记录原因、影响范围和移除条件。长期方案仍然是升级上游包或替换不维护依赖。

依赖升级后不能只看安装成功。至少要跑类型检查、单元测试、构建和关键页面冒烟；如果是构建工具、路由、状态管理、组件库这类核心依赖，还要重点检查产物体积、运行兼容和 SSR/CSR 行为差异。

## 第三方脚本

CDN 脚本、统计脚本、客服脚本、广告脚本都属于依赖，只是它们不一定在 `package.json` 里。

```html
<script
  src="https://cdn.example.com/sdk.js"
  integrity="sha384-..."
  crossorigin="anonymous"
></script>
```

如果脚本内容固定，可以使用 SRI 校验资源完整性；如果脚本需要频繁动态更新，就要考虑 CSP、域名白名单、权限隔离和最小化加载范围。

第三方脚本风险最大的地方在于它们天然具有“站点身份”影响力。只要脚本被劫持，它就能读取页面内容、发请求、改 UI，所以即使是统计脚本，也不应该无限制地放入所有页面。

SRI 适合内容固定的 CDN 资源。如果资源地址返回的脚本会动态变化，SRI 会频繁失效；如果不用 SRI，又要依赖供应商域名和传输链路可信。对于动态第三方脚本，更现实的做法是限制加载页面、降低权限、配合 [[1.6.3 CSP|CSP]] 和数据最小化。

```html
<script
  src="https://cdn.example.com/sdk@1.2.3/index.js"
  integrity="sha384-..."
  crossorigin="anonymous"
></script>
```

第三方脚本不要默认进入登录、支付、账户设置、管理后台等敏感页面。即使业务上需要监控，也要选择尽量少的数据字段和更受控的采集方式。

## 构建插件

构建插件有很高权限，能读取源码、改产物、访问环境变量。安装插件前要看维护状态、下载量、仓库活跃度、issue 质量和权限边界。

```text
脚手架插件
Vite / Webpack 插件
Babel / SWC 插件
PostCSS 插件
CI Action
```

这些工具运行在开发和 CI 环境里，经常能接触 token、环境变量和构建产物，风险不低于运行时依赖。

尤其是自动化发布插件和 GitHub Action，一旦权限过大，就可能直接接触密钥和发布产物。安装前最好确认维护者、发布频率和最小权限原则，而不是只看“大家都在用”。

安装新插件前可以做轻量审查：仓库是否开源、最近是否维护、发布者是否可信、是否有异常 postinstall、依赖数量是否异常、是否请求不必要权限、issue 中是否有供应链风险反馈。不是每个小工具都值得引入依赖，几十行脚本能解决的事情，未必需要装一个高权限包。

```bash
npm view package-name scripts
npm view package-name dependencies
```

CI Action 尽量 pin 到具体版本或提交，而不是浮动 `main`。浮动引用会让未来某次上游变更直接进入你的发布链路，审查和回滚都更困难。

## 治理习惯

| 做法 | 价值 |
| --- | --- |
| 保留锁文件 | 保证依赖树可复现 |
| 定期升级 | 降低长期积累风险 |
| 审查新增依赖 | 防止小功能引入大风险 |
| CI 安全扫描 | 让问题尽早暴露 |
| 最小化第三方脚本 | 减少运行时攻击面 |

依赖安全的目标不是“永远没有漏洞”，而是让漏洞可见、可判断、可修复。一个项目依赖越多，越需要把依赖升级和安全扫描纳入日常工程流程。

如果团队已经有定期升级窗口，建议把“新增依赖审批”和“高风险依赖复查”一起纳入。这样依赖新增不会失控，安全修复也不至于堆到年底一次性爆发。

治理上可以把依赖分层：核心运行时依赖、构建链路依赖、开发体验依赖、一次性脚本依赖。核心依赖升级要更谨慎，开发体验依赖可以更频繁更新，但构建链路依赖要特别关注权限。

```text
新增依赖
  -> 是否已有实现可复用
  -> 是否进入生产产物或 CI
  -> 维护状态是否健康
  -> 体积和权限是否可接受
  -> 是否有替代方案
```

最好的依赖安全不是每天手动看告警，而是把锁文件、审计、自动升级 PR、CI 校验、人工评估连起来。自动化负责发现和验证，人负责判断风险和取舍。
