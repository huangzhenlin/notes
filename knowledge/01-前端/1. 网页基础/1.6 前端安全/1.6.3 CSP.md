## 工作机制

CSP（Content Security Policy）是浏览器根据响应头执行的一套资源和行为限制策略。它主要用来约束页面允许加载哪些脚本、样式、图片、连接和嵌入资源，最核心的价值是降低 XSS 的可利用性。

```http
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-r4nd0m'
```

当 CSP 配得足够严格时，就算攻击者把脚本注入到了页面里，浏览器也可能不会执行它。它不是替代 XSS 防护，而是和输出编码、净化一起构成防线。

CSP 更像运行时护栏：代码层犯错时，它可以降低漏洞被利用的概率；代码层没有犯错时，它也能限制第三方资源和浏览器能力的边界。它的收益来自“默认拒绝，显式允许”。

浏览器接收到 CSP 后，会在加载资源和执行敏感行为前检查策略。违反策略的资源会被阻止，并在控制台记录信息；如果配置了上报端点，还可以把违规报告发给服务端。它不是构建时检查，而是每个页面响应都要携带的运行时策略。

```http
Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'
```

`default-src 'none'` 是更严格的起点：默认全拒绝，再按资源类型逐项放开。它适合安全要求较高、资源来源清晰的页面；普通业务可以从 `default-src 'self'` 开始逐步收紧。

## 核心指令

```text
default-src
script-src
style-src
img-src
connect-src
frame-ancestors
upgrade-insecure-requests
```

不同指令负责不同资源类型。最容易出效果的通常是 `script-src` 和 `frame-ancestors`，前者控制脚本执行，后者控制页面是否能被嵌入到别人的 `iframe` 里。

实际配置时可以从 `default-src 'self'` 开始，再逐个放开必须的资源来源。不要一上来写一串宽泛通配符，否则策略看起来存在，实际却没有收紧攻击面。

常用指令可以按资源类型理解：

| 指令 | 控制对象 | 常见影响 |
| --- | --- | --- |
| `script-src` | 脚本加载和执行 | XSS 利用、第三方脚本 |
| `style-src` | 样式来源 | CSS 文件、内联样式 |
| `img-src` | 图片来源 | CDN、头像、data URL |
| `connect-src` | 网络连接 | API、WebSocket、埋点 |
| `font-src` | 字体来源 | Web Font、图标字体 |
| `frame-src` | 页面能嵌入谁 | 支付 iframe、视频 |
| `frame-ancestors` | 页面能被谁嵌入 | 点击劫持防护 |

指令粒度越细，越能把风险限制在必要范围。比如允许图片来自 CDN，不代表脚本也应该来自 CDN；允许上报域名出现在 `connect-src`，也不代表它应该出现在 `script-src`。

## 资源控制

```http
Content-Security-Policy: default-src 'self'; img-src 'self' https://cdn.example
```

这种配置会限制页面只能从指定来源加载资源。它的意义不只是“更严格”，而是把第三方资源使用范围变成显式白名单，避免脚本、图片、样式、接口调用在项目里悄悄失控。

`connect-src` 对现代前端尤其重要，因为接口、WebSocket、SSE、监控上报都属于连接来源。配置它可以防止被注入脚本把数据偷偷发往陌生域名，虽然不能替代后端权限校验，但能减少数据外传渠道。

第三方资源是 CSP 落地时最容易扩散的地方。统计、客服、A/B 测试、广告、错误监控往往都要加载脚本或发起连接。如果不做治理，策略很快会变成一串供应商域名，难以判断哪个还在使用。

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://analytics.example;
  connect-src 'self' https://api.example https://rum.example;
  img-src 'self' https://cdn.example data:;
```

给第三方放行时要尽量按页面和能力拆分。不是所有页面都需要客服脚本，也不是所有页面都需要支付 iframe。越敏感的页面，越应该减少第三方脚本，因为第三方脚本一旦被污染，等价于在你的页面里执行高权限代码。

## 运行脚本

严格 CSP 下，内联脚本、事件属性和 `eval()` 都可能被禁止。

```html
<script nonce="r4nd0m">
  console.log("allowed");
</script>
```

非得允许内联脚本时，通常应该优先考虑 `nonce` 或 `hash`，而不是直接放开 `unsafe-inline`。一旦开口太大，CSP 的价值会迅速下降。

`nonce` 要做到每个响应随机生成，并且只给可信脚本使用。把固定 nonce 写死在模板里，等于给攻击者一个长期可复用的通行证。`hash` 更适合内容稳定的内联脚本，一旦脚本内容变化，hash 也要同步更新。

严格 `script-src` 下，最好逐步移除内联事件和字符串执行：

```html
<button onclick="submitForm()">提交</button>
```

```js
document.querySelector("#submit").addEventListener("click", submitForm);
```

`onclick` 这类内联事件需要 `unsafe-inline` 才能执行，而 `unsafe-inline` 会明显削弱 CSP。把事件绑定移到独立脚本里，既更利于维护，也更利于启用严格策略。

`eval`、`new Function`、某些模板编译器和开发工具也可能触发 CSP 限制。如果生产环境必须开启 `unsafe-eval`，要查清楚是哪一个依赖需要它，是否能通过构建配置、预编译或升级依赖移除。

## 嵌入限制

CSP 还可以通过 `frame-ancestors` 限制页面被谁嵌入。

```http
Content-Security-Policy: frame-ancestors 'none'
```

这和 [[1.6.5 点击劫持|点击劫持]] 的关系非常直接。相比旧的 `X-Frame-Options`，CSP 的控制更细，但在一些兼容场景里，两者也可以一起用。

需要被合作方嵌入的页面不要简单写成全部允许。应该列出明确来源，例如 `frame-ancestors 'self' https://partner.example`，并把可嵌入页面和高风险账户页面分开。

`frame-ancestors` 不能写在 `<meta http-equiv>` 里，必须通过 HTTP 响应头下发。因为浏览器需要在页面被嵌入前就知道策略，等 HTML 解析到 meta 时已经太晚。部署点击劫持防护时，要确认网关、CDN、应用服务是否真的把响应头加到了目标页面上。

```http
Content-Security-Policy: frame-ancestors 'self' https://partner.example
```

如果历史系统还要兼容旧浏览器，可以同时设置 `X-Frame-Options: DENY` 或 `SAMEORIGIN`，但新项目优先使用 CSP，因为它能表达多个允许来源。

## 部署方式

| 方式 | 适合场景 |
| --- | --- |
| `Content-Security-Policy` | 已验证策略，正式环境 |
| `Content-Security-Policy-Report-Only` | 先观察，不阻断 |
| `nonce` | 动态页面、SSR 页面 |
| `hash` | 静态脚本、稳定模板 |

很多团队第一次上 CSP 会直接报一堆控制台错误，所以更稳的做法是先用 `Report-Only` 观察，再逐步收紧。这样能先看清楚页面到底依赖了哪些外部资源。

上线策略通常分三步：先收集报告，整理真实资源清单；再在低风险页面启用阻断；最后扩展到登录、支付、账户等关键页面。这样既能减少误伤，也能避免策略永远停留在观察阶段。

`Report-Only` 适合发现问题，但不要长期只观察不阻断。否则 CSP 会变成控制台噪音。比较稳的做法是给策略设置版本，按页面或路由逐步推进。

```http
Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m';
  report-to csp-endpoint
```

收集报告时要过滤浏览器插件、运营商注入、用户脚本等噪音。不是每一条违规都代表业务资源缺失；但如果同一个页面持续报告某个生产域名被阻止，就说明策略和真实依赖没有对齐。

## 常见误区

| 误区 | 问题 |
| --- | --- |
| 只配首页 | 其他页面仍然暴露 |
| 直接放开 `unsafe-inline` | 保护能力大幅下降 |
| 忽略第三方脚本 | 供应链脚本仍有风险 |
| 只靠 CSP 防 XSS | 防护链条不完整 |

CSP 最像“浏览器侧白名单”，而不是“代码层修复”。它最好的位置，是在你已经把输出编码和组件默认转义做好之后，再为剩余风险加一道硬约束。

如果项目使用 SSR、微前端或第三方 SDK，CSP 要和构建产物一起维护。每新增一个脚本域、样式域或上报域，都应该问清楚它为什么需要、影响哪些页面、能否被更小范围地允许。

常见失败模式是“为了让页面先跑起来，临时加了 `*`、`unsafe-inline`、`unsafe-eval`，后来没人收回”。这类临时策略应该有明确过期时间和责任人。否则 CSP 头虽然存在，实际安全收益会接近于零。

```http
Content-Security-Policy: default-src * 'unsafe-inline' 'unsafe-eval' data: blob:
```

这类配置几乎把主要入口都打开了，不应作为正式策略。真正有效的 CSP 是可解释的：每个来源为什么存在，每个危险关键字为什么暂时需要，什么时候可以删除。
