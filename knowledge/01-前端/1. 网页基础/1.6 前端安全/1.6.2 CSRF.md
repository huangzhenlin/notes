## 攻击原理

CSRF（Cross-Site Request Forgery）是指攻击者诱导用户的浏览器，在用户已经登录的前提下，向受信任站点发出非本人意图的请求。浏览器会自动携带 Cookie，所以如果服务端只认“有没有带登录态”，就可能把攻击请求当成正常请求。

```html
<form action="https://bank.example/transfer" method="POST">
  <input type="hidden" name="amount" value="10000" />
  <input type="hidden" name="to" value="attacker" />
</form>
<script>document.forms[0].submit()</script>
```

这个攻击能成立，前提是目标站点用 Cookie 维持会话，而且敏感操作没有额外校验。它和 [[1.6.4 鉴权|鉴权]] 关系很近，但不等于鉴权本身出了问题，而是“认证已经完成，后续请求没再确认是不是本人发起”。

CSRF 的特殊之处在于攻击者不需要读取响应内容，只要能让浏览器把请求发出去就可能造成状态变化。也正因为如此，CORS 不等于 CSRF 防护：CORS 主要控制跨站脚本能不能读取响应，而 CSRF 关注的是请求是否已经被发出并被服务端执行。

CSRF 和 XSS 的攻击方向不同。XSS 是让恶意脚本进入目标站点执行；CSRF 是让用户浏览器从攻击站点向目标站点发请求。前者更像“站内代码被污染”，后者更像“站外页面借用了用户登录态”。如果站点存在 XSS，CSRF Token 也可能被读取并滥用，所以两类风险要一起考虑。

攻击者通常无法读取跨站响应，但这不影响某些操作成功，例如提交表单、触发退出登录、修改偏好、发起关注。只要服务端执行了状态变更，攻击就已经达成。

## 适用条件

CSRF 通常依赖以下条件：

| 条件 | 说明 |
| --- | --- |
| 使用 Cookie 会话 | 浏览器会自动带上 Cookie |
| 有状态变更接口 | 比如转账、改密码、绑定邮箱 |
| 缺少二次验证 | 没有 token、没有来源校验、没有风控 |
| 接口允许跨站发送 | 没有限制同站请求或方法 |

如果接口只是查询数据，通常风险会小很多；但只要能引起状态变化，就要当成敏感操作看待。

常见敏感接口包括修改密码、绑定邮箱、发起支付、关注/取消关注、修改收货地址、退出登录。即使单次操作看起来不严重，只要能被批量诱导执行，也应该纳入防护范围。

接口方法也很关键。`GET` 应该保持只读，不应该承担状态变更。如果 `GET /delete?id=1` 这类接口存在，图片、链接、预加载、爬虫都可能触发它，CSRF 风险会被放大。

```html
<img src="https://example.com/api/delete?id=1" />
```

把状态变更改成 `POST`、`PUT`、`PATCH`、`DELETE` 并不自动安全，但它至少让接口语义更清楚，也方便服务端对写操作统一套 token、来源校验和风控。

## Token 校验

最经典的防御是 CSRF Token。服务端生成一个随机、不可预测的 token，页面提交时一并带回，服务端再比对。

```html
<meta name="csrf-token" content="abc123" />
<script>
  const token = document.querySelector('meta[name="csrf-token"]').content;

  fetch("/api/profile", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-CSRF-Token": token
    },
    body: JSON.stringify({ nickname: "Ada" })
  });
</script>
```

token 要由服务端生成和验证，前端只是传递。把 token 存在 `localStorage` 或随便暴露在可被脚本读取的地方，并不等于一定不安全，但一旦发生 XSS，保护强度会明显下降，所以还是要结合整体架构判断。

Token 校验的重点是“攻击站点猜不到、拿不到、自动带不上”。如果 token 和 Cookie 一样会被浏览器自动跨站带上，那就失去了防护意义。更常见的做法是把 token 放在页面、响应体或专门接口里，由同站脚本读取后放进自定义请求头。

自定义请求头还有一个实际效果：跨站页面无法用普通 HTML 表单设置 `X-CSRF-Token`，而跨站 `fetch` 带自定义头会触发预检，服务端可以拒绝不可信来源。但不要把“会触发预检”当成唯一防线，真正的核心仍然是 token 随机、绑定会话、服务端验证。

```js
async function postJson(url, body) {
  const token = document.querySelector('meta[name="csrf-token"]')?.getAttribute("content");

  if (!token) {
    throw new Error("Missing CSRF token");
  }

  return fetch(url, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-CSRF-Token": token,
    },
    credentials: "same-origin",
    body: JSON.stringify(body),
  });
}
```

如果前端采用 BFF 或 SSR，token 通常可以由服务端模板注入；如果是纯 SPA，也可以提供一个同站接口返回 token。无论哪种方式，token 都应该和会话相关，并且在登出、会话更新、权限变化时重新评估有效性。

## SameSite Cookie

`SameSite` 是浏览器层的补充手段，常和服务端 token 一起使用。

```http
Set-Cookie: session=abc; Path=/; Secure; HttpOnly; SameSite=Lax
```

`Lax` 和 `Strict` 都能减少跨站请求里自动携带 Cookie 的机会，但它们不是万能的。对于复杂登录流程、老浏览器兼容、跳转回链等场景，`SameSite` 只能算一层缓冲，不能替代服务端校验。

`SameSite=None` 必须配合 `Secure`，否则现代浏览器通常不会接受。需要第三方嵌入、跨站登录回调、统一认证域时，Cookie 策略会变复杂，这时更不能只靠浏览器默认行为，要把敏感接口的服务端校验补上。

`SameSite=Lax` 通常允许顶层导航场景携带 Cookie，但会限制很多跨站子资源请求；`Strict` 更严格，跨站跳转回来也可能不带 Cookie，用户体验上可能影响登录回跳、支付回调或外部链接进入。选择时要结合业务路径测试，而不是统一设成最严。

```http
Set-Cookie: session=abc; Path=/; Secure; HttpOnly; SameSite=Lax
```

对大多数普通 Web 应用，`Lax` 是兼顾体验和安全的起点；账户管理、后台管理、支付确认等高风险页面，可以结合更严格的来源校验和二次确认。

## 请求判定

```text
登录态 Cookie
  -> 同站请求校验
  -> CSRF Token 比对
  -> 必要时加二次确认
  -> 通过后再执行状态变更
```

如果接口是高风险操作，比如转账、改邮箱、解绑设备，建议额外加短信、密码、验证码或二次确认。这种场景里，安全边界不能只交给前端。

来源校验可以辅助判断 `Origin`、`Referer`，但不能把它们当成唯一依据。某些浏览器、隐私插件、企业代理可能会裁剪这些头；同时服务端也要确认请求方法、内容类型和 token 是否符合预期。

`Origin` 比 `Referer` 更适合做来源判断，因为它不包含完整路径，隐私暴露更少。对于写操作，服务端可以优先检查 `Origin` 是否为允许来源；缺失时再谨慎回退到 `Referer`。但来源头可能缺失，所以它更适合做防线之一，而不是唯一依据。

```text
写请求进入服务端
  -> 方法是否允许
  -> Cookie 会话是否有效
  -> Origin / Referer 是否可信
  -> CSRF Token 是否匹配
  -> 风险等级是否需要二次确认
```

前端能做的是规范请求头和错误处理，服务端才是最终裁决者。不要把 token 校验写成“前端拦截器里有就发，没有就跳过”，后端必须拒绝缺 token 或 token 不匹配的敏感请求。

## 防护组合

| 手段 | 作用 |
| --- | --- |
| CSRF Token | 确认请求确实来自当前站点页面 |
| `SameSite` | 降低跨站自动携带 Cookie 的概率 |
| `HttpOnly` | 避免会话 Cookie 被脚本直接读走 |
| 来源校验 | 辅助识别可疑跨站请求 |
| 二次确认 | 给高风险操作加最后一道门 |

CSRF 之所以常被忽视，是因为它不需要攻击者拿到密码，只要诱导用户访问一个页面就有机会成立。真正稳妥的做法，是让“跨站发起的请求”天然过不了服务端门槛。

实践上可以把接口分层：只读接口尽量无副作用；普通写接口要求 CSRF Token；高风险写接口再叠加二次确认或风控。这样既不会让所有操作都变得笨重，也能把真正危险的入口拦住。

如果应用改用 `Authorization: Bearer <token>` 并且 token 只保存在内存里，传统 Cookie 型 CSRF 风险会下降，因为浏览器不会自动给跨站请求加这个头。但这并不代表整体更安全：token 如果放在 `localStorage`，XSS 后更容易被直接读走；如果刷新 token 仍靠 Cookie，也要继续保护刷新接口。

安全选型不要只问“用 Cookie 还是 token”，而要看请求凭证是否会被浏览器自动跨站携带、攻击站点能否构造同样的请求、敏感操作是否有服务端二次校验。只要这三个问题回答清楚，CSRF 防线就不会停留在口号上。
