## 同步与异步

同步代码会按顺序直接进入调用栈执行；异步代码会把后续工作交给宿主环境，等条件满足后再回来执行。

```javascript
console.log('start');

setTimeout(() => {
  console.log('timer');
}, 0);

console.log('end');
```

输出通常是：

```text
start
end
timer
```

异步不是“开新线程直接跑 JS”，而是把等待网络、定时器、用户事件这类耗时操作从同步调用栈里拆出去。

JavaScript 主线程一次只能执行一段同步代码。异步的意义是把“等待”交给宿主环境，让主线程先继续处理其他工作。网络请求、计时器、用户事件、文件读取这些能力通常由浏览器或 Node.js 宿主提供，回调再按事件循环规则回到 JavaScript 调用栈。

## 回调函数

回调是最基础的异步表达方式：把“完成后要做什么”作为函数传进去。

```javascript
function loadScript(src, callback) {
  const script = document.createElement('script');
  script.src = src;
  script.onload = () => callback(null);
  script.onerror = () => callback(new Error(`加载失败：${src}`));
  document.head.append(script);
}
```

回调的问题不是“不能用”，而是容易嵌套、错误分散、流程难读。

```javascript
loadUser((user) => {
  loadOrders(user.id, (orders) => {
    loadDetail(orders[0].id, (detail) => {
      render(detail);
    });
  });
});
```

Promise 和 async/await 的出现，本质上是为了让异步流程更容易组合和阅读。

回调仍然适合一些底层事件模型，例如 DOM 事件、Node 风格 API、订阅系统。问题不是回调本身，而是当流程存在顺序依赖、错误传播和资源清理时，单纯嵌套回调会让控制流分散。Promise 把“未来结果”变成值，async/await 再让基于 Promise 的流程更接近同步代码的阅读方式。

## 任务队列

异步回调执行前，通常会先进入任务队列，等同步代码和当前轮次的调度规则完成后再执行。

```javascript
console.log('A');

Promise.resolve().then(() => console.log('B'));

setTimeout(() => console.log('C'), 0);

console.log('D');
```

通常输出是：

```text
A
D
B
C
```

Promise 回调通常比定时器更早执行，因为它们会进入微任务队列。更完整的调度模型可以继续看 [[1.4.2 事件循环|事件循环]]。

微任务也不能无限堆积。大量连续 `Promise.then`、`queueMicrotask` 或框架内部更新如果一直追加微任务，可能让浏览器迟迟没有机会进入渲染和用户事件处理。微任务适合处理当前任务之后必须立刻收尾的逻辑，不适合承载长时间循环。

## 串行与并行

多个异步任务如果互相依赖，就应该串行；如果彼此独立，就应该并行。

```javascript
// 串行：订单依赖用户 ID
const user = await fetchUser();
const orders = await fetchOrders(user.id);
```

```javascript
// 并行：两个请求彼此独立
const [profile, settings] = await Promise.all([
  fetchProfile(),
  fetchSettings(),
]);
```

把独立请求写成串行，会拖慢页面；把依赖请求写成并行，会让数据关系混乱。异步代码最重要的判断，就是先看依赖关系。

还有一种常见场景是“有限并发”。比如要请求 100 个资源，全部串行太慢，全部并行又可能压垮服务或触发浏览器连接限制。此时应该做并发池，而不是简单 `Promise.all`。

```javascript
async function runWithLimit(tasks, limit) {
  const results = [];
  const executing = new Set();

  for (const task of tasks) {
    const promise = Promise.resolve().then(task);
    results.push(promise);
    executing.add(promise);
    promise.finally(() => executing.delete(promise));

    if (executing.size >= limit) {
      await Promise.race(executing);
    }
  }

  return Promise.all(results);
}
```

## 取消与过期

异步任务开始后，不一定都应该等结果。输入框搜索、页面切换、组件卸载时，都要考虑取消旧任务。

```javascript
const controller = new AbortController();

fetch('/api/search?q=html', {
  signal: controller.signal,
});

controller.abort();
```

有些请求不一定能真正中断底层网络，但至少要防止旧结果覆盖新结果。

```javascript
let requestId = 0;

async function search(keyword) {
  const currentId = ++requestId;
  const result = await fetchSearch(keyword);

  if (currentId === requestId) {
    render(result);
  }
}
```

取消和过期是两个不同问题。`AbortController` 关注“让任务尽量停止”，请求 ID 关注“即使旧任务完成，也不要采用旧结果”。搜索建议、路由切换、组件卸载往往两个都需要：能取消就取消，不能取消也要忽略过期结果。

## 错误传播

异步错误不能只靠“看控制台”，要让调用方知道发生了什么。

```javascript
async function submit() {
  try {
    await saveForm();
    showSuccess();
  } catch (error) {
    showError(error);
  }
}
```

如果把错误吞掉，问题只会延后暴露。

```javascript
fetchUser().catch((error) => {
  reportError(error);
  throw error;
});
```

异步错误处理的目标不是“一个都不能报”，而是让可恢复错误能恢复，让不可恢复错误能被正确暴露。

不同层级的错误处理职责也不同。请求封装层适合把 HTTP 状态、网络错误、解析错误标准化；业务层适合决定是否重试、降级或提示；页面层适合展示用户能理解的反馈。把所有错误都在底层吞掉，会让上层误以为流程成功。

```javascript
async function request(url) {
  const response = await fetch(url);

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }

  return response.json();
}
```

让错误带着足够上下文向上传播，通常比在底层直接弹提示更容易维护。
