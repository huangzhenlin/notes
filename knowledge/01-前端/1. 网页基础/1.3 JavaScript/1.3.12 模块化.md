## 模块边界

模块化的目标是按职责拆分代码，让依赖关系显式化。一个模块只暴露外部真正需要的接口，内部实现保持封闭。

```javascript
// math.js
export function sum(a, b) {
  return a + b;
}

function normalize(value) {
  return Number(value) || 0;
}
```

模块边界带来的收益是：命名冲突更少、依赖更清晰、测试更容易、重构更安全。

```javascript
// user-cache.js
const cache = new Map();

export function getCachedUser(id) {
  return cache.get(id);
}
```

模块作用域天然私有。只要不 `export`，外部就不能直接访问内部变量。

模块边界也是工程协作边界。一个模块暴露什么，外部就会依赖什么；暴露越多，未来可自由修改的空间越小。写模块时不要只问“这个函数能不能导出”，还要问“它是否应该成为长期稳定 API”。

## 导出语义

ES Module 通过 `export` 暴露接口。常见导出方式有命名导出和默认导出。

```javascript
export const version = '1.0.0';

export function createClient() {}

export default class Client {}
```

命名导出适合一个模块暴露多个稳定能力；默认导出适合模块只有一个核心对象或函数。

```javascript
export {
  createClient,
  parseResponse,
};
```

导出是模块公开 API 的设计动作，不是把内部变量随手暴露出去。公共模块的导出越随意，后续重构成本越高。

导出命名最好表达能力而不是实现细节。`fetchUser`、`formatCurrency`、`createStore` 比 `helper1`、`utils`、`handleData` 更容易被调用方理解。模块 API 一旦被大量使用，重命名和拆分成本会快速上升。

## 导入语义

`import` 用于引入模块。ES Module 的导入是静态的，这让工具可以在执行前分析依赖图。

```javascript
import { sum } from './math.js';
import Client from './client.js';
```

导入绑定是只读的“活绑定”。导出方的变量变化会反映到导入方，但导入方不能直接重新赋值。

```javascript
// counter.js
export let count = 0;

export function inc() {
  count += 1;
}
```

```javascript
import { count, inc } from './counter.js';

inc();
console.log(count); // 1
```

静态导入必须写在模块顶层，不能放在条件语句里。需要运行时按需加载时，使用动态 `import()`。

静态导入的好处是工具能提前建立依赖图，进行 tree shaking、代码分割、循环依赖分析和类型检查。代价是它不能根据运行时条件临时决定是否加载。只要模块是核心路径依赖，静态导入通常更清晰；只有低频、重型、条件化能力才考虑动态导入。

## 命名导出

命名导出最适合公共工具库和多人协作项目。它的优点是重命名更安全，模块接口也更清晰。

```javascript
export function formatDate(date) {}
export function parseDate(text) {}
```

调用方通常这样使用：

```javascript
import { formatDate, parseDate } from './date.js';
```

如果模块需要多个相关能力，命名导出比默认导出更容易随着功能增长保持稳定。

```javascript
import { formatDate as format } from './date.js';
```

需要避免的是一个文件导出几十个互不相关的函数。那通常说明模块边界已经太宽。

命名导出还有一个工程优势：调用方导入的名字通常和导出名一致，搜索、重构、自动导入都更稳定。公共工具库、业务 API、状态模块更适合命名导出，因为它们往往包含多个清晰能力。

## 默认导出

默认导出适合模块只提供一个核心能力的场景，例如一个类、一个配置工厂或一个页面组件。

```javascript
export default function createStore() {}
```

默认导出可以在导入方随意起名，但过度使用会降低一致性。

```javascript
import makeStore from './store.js';
import createStore from './store.js';
```

上面两个名字都能工作，但团队搜索和重构时会变得不统一。公共工具模块里更推荐命名导出；页面组件、框架约定入口里默认导出更常见。

默认导出最大的问题是调用方可以随意命名，长期会造成同一个模块在不同文件里名字不一致。它适合“这个文件本身就是一个核心对象”的场景，例如一个页面组件、一个类、一个配置入口；不适合工具函数集合。

## 重新导出

重新导出可以把多个模块的能力集中到一个入口，常用于公共包的对外出口。

```javascript
export { sum } from './math.js';
export * from './format.js';
export * as utils from './utils/index.js';
```

入口文件适合统一暴露 API，但不要把所有内部实现都无脑 re-export，否则边界会变模糊。

```javascript
// index.js
export { createButton } from './button.js';
export { createDialog } from './dialog.js';
```

入口文件应该像产品橱窗，只摆出外部应该使用的能力，而不是把仓库内部通道全部暴露出去。

重新导出还会影响 tree shaking 和依赖可见性。`export *` 很方便，但如果入口过于宽泛，调用方很容易依赖原本不该公开的模块。公共包最好明确列出稳定 API，让内部文件仍然可以自由调整。

## 循环依赖

模块依赖图如果出现环，就可能遇到初始化顺序问题。ES Module 支持循环依赖，但要小心访问时机。

```javascript
// a.js
import { b } from './b.js';
export const a = 'a';
console.log(b);
```

```javascript
// b.js
import { a } from './a.js';
export const b = 'b';
console.log(a);
```

循环依赖不一定是错误，但通常说明职责切分不够清晰。状态模块、工具模块、常量模块之间互相引用时，最容易出现隐性循环。

常见处理方式是把公共依赖抽到第三个模块，或者把互相调用改成参数注入。

```javascript
// shared.js
export const config = {};
```

循环依赖最危险的地方是“访问时机”。ES Module 的活绑定能让某些循环正常工作，但如果在模块初始化阶段就读取对方尚未完成初始化的值，仍然可能报错或拿到不可用状态。循环依赖不是必然错误，但通常是架构信号：两个模块可能边界不清。

## 动态加载

`import()` 可以在运行时按需加载模块，常用于路由页面、重型组件和低频能力。

```javascript
button.addEventListener('click', async () => {
  const { openEditor } = await import('./editor.js');
  openEditor();
});
```

动态加载和 [[6.4.2 代码分割|代码分割]] 紧密相关。它把“什么时候加载”从构建阶段延后到运行阶段，适合延迟首屏不需要的重型模块。

```javascript
async function loadChart() {
  const { createChart } = await import('./chart.js');
  return createChart();
}
```

动态 `import()` 返回 Promise，因此要处理加载失败、重复触发、竞态和用户等待状态。

动态加载通常要配合 UI 状态：加载中、加载失败、重试、预加载。比如点击“打开编辑器”时再加载编辑器模块，如果加载很慢，用户需要看到反馈；如果连续点击多次，也要避免重复创建多个加载流程。

```javascript
let editorPromise;

function loadEditor() {
  editorPromise ??= import('./editor.js');
  return editorPromise;
}
```

缓存动态导入 Promise 可以避免重复加载同一个模块。

## 浏览器模块

浏览器里的模块脚本和普通脚本不同。模块默认启用严格模式，顶层变量属于模块作用域，HTML 中需要 `type="module"`。

```html
<script type="module" src="/main.js"></script>
```

模块脚本默认延迟执行，并且要遵守 CORS、MIME 类型和路径解析规则。相对路径通常要写清楚后缀。

```javascript
import { start } from './app.js';

start();
```

模块化不只是语法风格，而是工程组织方式。它会影响打包、缓存、测试、循环依赖和发布边界。

浏览器原生模块还要求正确的 MIME 类型和 CORS 策略。直接在本地用 `file://` 打开模块页面常会失败，通常需要通过本地服务器访问。构建工具在开发阶段帮你处理这些细节，但理解原生约束有助于排查生产环境模块加载失败。

## 模块设计

一个稳定模块通常有三个特点：职责清楚、导出克制、依赖单向。

```javascript
// api/user.js
export async function fetchUser(id) {
  const response = await fetch(`/api/users/${id}`);
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  return response.json();
}
```

```javascript
// pages/profile.js
import { fetchUser } from '../api/user.js';

export async function renderProfile(id) {
  const user = await fetchUser(id);
  render(user);
}
```

底层模块不应该反向依赖页面模块；公共模块不应该偷偷依赖具体业务状态。模块边界越清晰，项目越能长久维护。

模块设计可以按依赖方向检查：基础工具不依赖业务，API 层不依赖页面，状态层暴露明确读写入口，页面层组合各种能力。只要底层开始反向依赖上层，复用、测试和重构都会变得困难。

```text
utils -> api -> state -> page
```

这不是绝对分层模型，而是提醒依赖尽量单向。单向依赖越稳定，模块越容易替换。
