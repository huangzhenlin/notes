## 高频事件

滚动、窗口缩放、输入框输入、鼠标移动都可能在短时间内触发大量事件。如果每次事件都执行昂贵逻辑，页面就容易卡顿。

```javascript
window.addEventListener('resize', () => {
  console.log(window.innerWidth);
});
```

防抖和节流解决的是“高频触发如何降频执行”，但策略不同。它们不是性能银弹，只是把执行频率控制到业务真正需要的程度。

高频事件的成本不一定来自事件本身，而是来自事件里做了什么：读写 DOM、发请求、复杂计算、更新状态、触发渲染都可能变贵。防抖和节流只能减少执行次数，不能让一次昂贵执行变便宜。真正优化时，要同时看执行频率和单次执行成本。

## 触发模式

防抖和节流都可以分成首次立即执行、末次执行、两端都执行等模式。实际选择时，先想清楚用户是更需要“停下来后再执行”，还是“持续操作也要稳定反馈”。

```text
leading: 开始时立即执行
trailing: 停止后补最后一次
```

搜索建议通常需要 trailing；按钮防重复点击可能需要 leading；滚动上报可能两者都要根据业务选。

触发模式本质上是在选择用户感知。`leading` 让用户马上看到反馈，但可能丢掉最后一次变化；`trailing` 保留最后结果，但用户会感到延迟；两端都执行适合既要立即反馈又要补最终状态的场景，但实现更复杂，也更容易重复执行。

## 防抖

防抖是在事件连续触发时，只在停止触发一段时间后执行一次。

```javascript
function debounce(fn, delay) {
  let timer;

  return function (...args) {
    clearTimeout(timer);

    timer = setTimeout(() => {
      fn.apply(this, args);
    }, delay);
  };
}
```

它适合搜索输入、窗口 resize、表单自动保存这类“等用户停下来再执行”的场景。

```javascript
const search = debounce((keyword) => {
  fetch(`/api/search?keyword=${encodeURIComponent(keyword)}`);
}, 300);

input.addEventListener('input', (event) => {
  search(event.target.value);
});
```

如果用户持续输入，防抖会不断推迟执行。

防抖的体验取决于延迟时间。搜索框常见 200ms 到 500ms，太短会接近没防抖，太长会让用户觉得页面迟钝。自动保存可以更长一些，但最好配合“保存中 / 已保存”的状态提示，让用户知道系统没有丢失输入。

## 节流

节流是在事件持续触发时，限制函数最多每隔一段时间执行一次。

```javascript
function throttle(fn, interval) {
  let lastTime = 0;

  return function (...args) {
    const now = Date.now();

    if (now - lastTime >= interval) {
      lastTime = now;
      fn.apply(this, args);
    }
  };
}
```

它适合滚动、拖拽、鼠标移动、实时位置上报这类“持续触发但需要固定频率响应”的场景。

```javascript
const reportScroll = throttle(() => {
  console.log(window.scrollY);
}, 200);

window.addEventListener('scroll', reportScroll);
```

节流关注的是固定频率，防抖关注的是最后一次触发。先判断业务要哪种时间语义，再写实现。

节流适合需要持续反馈的场景，例如滚动进度、拖拽位置、鼠标轨迹、窗口尺寸采样。它不会等用户停下来，而是在操作过程中保持一个可控频率。频率越高，反馈越实时，成本也越高；频率越低，性能更稳，但可能显得不跟手。

## `leading` 与 `trailing`

实际项目里经常需要控制首次是否立即执行、结束后是否补最后一次。

```javascript
function debounce(fn, delay, { leading = false } = {}) {
  let timer;

  return function (...args) {
    const shouldCallNow = leading && !timer;
    clearTimeout(timer);

    timer = setTimeout(() => {
      timer = undefined;
      if (!leading) fn.apply(this, args);
    }, delay);

    if (shouldCallNow) {
      fn.apply(this, args);
    }
  };
}
```

按钮防重复点击常常可以用 `leading` 防抖，但更稳定的做法通常是提交期间直接禁用按钮。

```javascript
submitButton.disabled = true;
try {
  await submit();
} finally {
  submitButton.disabled = false;
}
```

防重复提交不要只靠时间窗口。网络慢时，用户可能在防抖时间过后再次点击；网络快时，固定时间又可能让按钮无意义地不可用。提交中状态、幂等接口、请求锁和服务端防重一起设计，才比单纯防抖可靠。

## 取消执行

防抖函数常常需要取消能力，尤其是在组件卸载时。

```javascript
function debounce(fn, delay) {
  let timer;

  function debounced(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  }

  debounced.cancel = () => clearTimeout(timer);

  return debounced;
}
```

React、Vue 组件里使用防抖时，要在卸载时取消，避免组件销毁后仍然执行回调。

取消能力还适合“用户主动清空或切换上下文”的场景。比如搜索框清空后，之前排队的防抖请求不应该再发出；弹窗关闭后，排队的自动保存也不应该继续写入旧状态。防抖函数如果没有 cancel，生命周期就不完整。

## `requestAnimationFrame`

和视觉更新相关的高频事件，可以用 `requestAnimationFrame` 对齐浏览器渲染节奏。

```javascript
function rafThrottle(fn) {
  let ticking = false;

  return function (...args) {
    if (ticking) return;

    ticking = true;

    requestAnimationFrame(() => {
      ticking = false;
      fn.apply(this, args);
    });
  };
}
```

它适合滚动位置读取、拖拽视觉更新、动画相关计算。它不是替代所有节流的方案，接口请求和日志上报仍然更适合时间间隔节流。

`requestAnimationFrame` 的优势是和浏览器绘制节奏对齐。视觉更新如果比屏幕刷新还频繁，用户也看不到更多细节，只会增加主线程压力。滚动中读取位置、更新 transform、绘制 canvas 这类任务通常适合 raf 节流。

## 选择边界

| 场景 | 推荐 |
|---|---|
| 搜索输入 | 防抖 |
| 自动保存草稿 | 防抖 |
| 窗口 resize 后重排版 | 防抖 |
| 滚动位置上报 | 节流 |
| 拖拽过程更新 | `raf` 节流 |
| 防重复提交 | `leading` 防抖或按钮禁用 |

防抖关心“最后一次”，节流关心“固定频率”。如果你不先判断业务语义，就很容易把代码写对了，体验却不对。

还有一类情况不该使用防抖节流：核心输入反馈。例如输入框本身的显示、按钮按下态、焦点样式不能被防抖，否则用户会感觉界面不响应。应该把“即时反馈”和“昂贵副作用”拆开：输入立即更新，搜索请求防抖；拖拽立即跟手，日志上报节流。

## 异步请求

防抖只能减少请求次数，不能自动解决竞态。旧请求仍然可能晚于新请求返回。

```javascript
let requestId = 0;

const search = debounce(async (keyword) => {
  const currentId = ++requestId;
  const result = await fetchSearch(keyword);

  if (currentId === requestId) {
    render(result);
  }
}, 300);
```

搜索场景通常需要“防抖 + 竞态保护”。如果底层支持取消请求，也可以进一步结合 `AbortController`。

```javascript
let controller;

const search = debounce(async (keyword) => {
  controller?.abort();
  controller = new AbortController();

  const result = await fetchSearch(keyword, {
    signal: controller.signal,
  });

  render(result);
}, 300);
```

防抖节流控制的是触发频率，竞态保护控制的是结果归属，两者解决的问题不一样。

如果请求可以取消，最好把防抖、取消和结果归属一起考虑。防抖减少请求数量，`AbortController` 尽量终止旧请求，请求 ID 防止旧结果覆盖新结果。三者不是互斥方案，而是分别处理“少发、停掉、别误用结果”。
