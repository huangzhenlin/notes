## 引擎定位

V8 是 Google 开源的 JavaScript 和 WebAssembly 引擎，Chrome、Node.js、Electron 等环境都使用它。它负责解析、编译、执行 JavaScript，并管理内存。

```text
JavaScript 源码
  -> 解析
  -> 字节码
  -> 解释执行
  -> 热点优化
  -> 机器码
```

前端学习 V8，不是为了手写引擎，而是为了理解为什么某些写法更容易被优化，为什么对象形状变化会变慢，以及为什么运行时性能不只看语法。

V8 只负责执行 JavaScript 和 WebAssembly，不负责 DOM 渲染、CSS 布局、网络请求和浏览器 UI。前端性能问题经常跨越多层：JS 执行慢可能是 V8 热路径问题，页面卡顿可能是布局绘制问题，请求慢可能是网络问题。理解 V8 是为了知道“JS 引擎这一层可能发生了什么”，不是把所有性能问题都归因于引擎。

## 解析与编译

V8 会先把源码解析成 AST，再生成字节码执行。热点代码会被优化编译器进一步优化成更高效的机器码。

```javascript
function add(a, b) {
  return a + b;
}

for (let i = 0; i < 100000; i += 1) {
  add(i, i + 1);
}
```

频繁执行的函数更容易成为优化目标。运行时收集到的类型反馈，会帮助引擎做优化判断。

```javascript
function sum(list) {
  let total = 0;
  for (const item of list) total += item;
  return total;
}
```

热点代码越稳定，越容易被优化；反复变化的数据形态越多，优化越难稳定。

V8 的执行大致经历解释执行和优化执行。解释执行启动快，适合刚加载的代码；热点函数在运行中积累类型反馈，优化编译器再尝试生成更快代码。这意味着性能不是只由源码静态决定，也和运行时传入的数据形态有关。

## 隐藏类

V8 会为对象创建隐藏类，用来描述对象属性结构。相同形状的对象更容易被优化。

```javascript
function createUser(name, age) {
  return {
    name,
    age,
  };
}
```

如果对象属性总是按同样顺序创建，隐藏类更稳定。频繁给对象动态增删属性，会让优化变困难。

```javascript
const user = {};
user.name = 'Ada';
user.age = 28;
delete user.age;
```

不是说不能动态属性，而是性能敏感路径里要尽量避免对象形状过度变化。

```javascript
function makePoint(x, y) {
  return { x, y };
}
```

统一初始化顺序、统一字段集合，通常比在热路径上边跑边补属性更好。

隐藏类不是开发者直接操作的 API，而是引擎内部为了快速访问属性建立的结构描述。相同字段、相同添加顺序的对象更容易共享隐藏类；如果某些对象后续不断增删字段，同一个访问点就会遇到更多形状，优化会变难。

```javascript
// 更稳定
function createUser(name, age) {
  return {
    name,
    age,
    role: 'member',
  };
}

// 热路径里再补字段，形状更容易变化
const user = { name: 'Ada' };
user.age = 28;
user.role = 'member';
```

## 内联缓存

内联缓存用于加速属性访问和函数调用。引擎会记录某个访问点通常遇到什么对象形状。

```javascript
function getName(user) {
  return user.name;
}
```

如果 `getName` 总是接收相同形状对象，访问会更容易优化；如果同一位置不断传入完全不同结构，解释器就要处理更多分支。

内联缓存越稳定，性能通常越好。多态太多时，优化收益会下降。

内联缓存可以理解为“这个属性访问点见过哪些对象形状”。如果 `getName(user)` 总是拿到相似对象，引擎可以更快定位 `name`；如果一会儿传用户对象，一会儿传配置对象，一会儿传 DOM 节点，同一个访问点就会越来越难优化。

## 优化与去优化

V8 会根据运行时反馈优化热点代码，但如果假设被打破，也会去优化。

```javascript
function double(value) {
  return value * 2;
}

double(1);
double(2);
double('3');
```

前两次可能让引擎以为 `value` 是数字，后来传入字符串会让优化假设失效。业务代码不必为了 V8 写得奇怪，但稳定的数据形态通常更利于性能。

```javascript
function normalizeUser(user) {
  return {
    id: String(user.id),
    name: user.name,
  };
}
```

优化和去优化提醒我们：热路径里最好保持输入类型稳定。比如列表渲染函数里，字段最好提前规范化；计算函数里不要混用数字和字符串；对象结构不要在循环中反复变化。普通业务无需微优化，但数据形态稳定通常同时提升可读性和性能。

## 垃圾回收

V8 会自动管理内存。对象不再可达后，会在某次 GC 中被回收。常见 GC 策略会区分新生代和老生代。

```text
新生代：短生命周期对象，回收频繁
老生代：存活较久对象，回收成本更高
```

大量短生命周期对象通常能较快回收；长期缓存、大对象、全局状态如果持续增长，就会进入更昂贵的回收路径。

这也解释了为什么“创建对象”本身不一定可怕。现代引擎对短命对象很擅长；真正危险的是创建了大量对象，又让它们意外长期可达。性能敏感路径里要关注分配频率，但更要关注对象生命周期是否符合预期。

## 增量回收

为了减少主线程停顿，现代引擎会使用增量标记、并发标记、并行回收等策略，把一次很长的暂停拆成更小的工作片段。

```text
传统长暂停
  -> 增量拆分
  -> 并发处理
  -> 降低卡顿
```

即便引擎很聪明，大量内存分配和长期保留对象仍然会造成压力。

GC 优化的目标是减少停顿，但不是消除成本。对象越多、引用图越复杂、老生代越大，GC 仍然需要工作。页面表现为偶发卡顿时，除了查 JS 长任务，也要查内存分配和 GC 时间。

## Node 与浏览器

V8 只是执行 JavaScript 的引擎，浏览器还提供 DOM、BOM、网络、事件循环等宿主能力；Node.js 提供文件、进程、网络等服务端能力。

```text
V8：执行 JS
浏览器：DOM / 网络 / 渲染
Node：文件 / 进程 / 服务端网络
```

```javascript
typeof document; // 浏览器里是 "object"，Node 里通常是 "undefined"
```

所以 `document`、`window`、`fs` 都不是 V8 本身提供的能力，而是宿主环境提供的 API。

事件循环也属于宿主与引擎协作的边界。V8 执行回调函数，但定时器、网络、DOM 事件、渲染时机由浏览器调度；Node.js 则有自己的 libuv 事件循环和系统 API。相同 JavaScript 语法在不同宿主里能做的事不同。

## 性能判断

理解 V8 后，写代码时可以重点关注几个方向：

| 方向 | 意义 |
|---|---|
| 数据结构稳定 | 更容易优化 |
| 避免无意义大对象 | 降低 GC 压力 |
| 少在热路径动态改形状 | 减少去优化 |
| 用性能工具验证 | 避免凭感觉优化 |

V8 知识要和 [[1.4.2 事件循环|事件循环]]、[[1.3.15 垃圾回收|垃圾回收]]、[[6.3.1 渲染流程|渲染流程]] 放在一起理解：引擎执行 JS，宿主调度任务，渲染链路负责把结果显示出来。

```text
代码写法
  -> 引擎优化
  -> GC 行为
  -> 页面体感
```

如果只凭直觉判断性能问题，不看热路径、对象形状、GC 和宿主调度，通常很难真正定位根因。

V8 相关优化应该建立在测量上。先用 Performance、Memory、Node profiling 或浏览器 DevTools 找到热路径，再判断是否是对象形状、类型不稳定、GC 压力或算法复杂度问题。不要为了“可能让 V8 更喜欢”把普通代码写得难懂；可读、稳定的数据结构通常已经是最好的基础优化。
