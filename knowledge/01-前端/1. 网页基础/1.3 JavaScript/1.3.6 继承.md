## `class extends`

JavaScript 里最常见的继承写法是 `class extends`。它让子类看起来像在继承父类，但底层依然是原型链。

```javascript
class Animal {
  constructor(name) {
    this.name = name;
  }

  move() {
    return `${this.name} is moving`;
  }
}

class Dog extends Animal {
  bark() {
    return `${this.name} says woof`;
  }
}

const dog = new Dog('Lucky');
dog.move();
dog.bark();
```

`Dog` 实例既能访问自己的方法，也能沿原型链访问 `Animal.prototype` 上的方法。理解继承，还是要回到 [[1.3.5 原型|原型]]。

`extends` 建立了两条关系：实例方法通过子类原型链访问父类原型，静态方法通过构造函数之间的原型关系访问。也就是说，继承不只是让实例能用父类方法，也会让子类本身可以继承父类静态方法。

## 原型继承

在 `class` 出现之前，常见做法是用 `Object.create` 或手动设置构造函数原型来建立继承关系。

```javascript
const animal = {
  move() {
    return `${this.name} is moving`;
  },
};

const dog = Object.create(animal);
dog.name = 'Lucky';
dog.move();
```

这种写法更贴近 JavaScript 的对象本质：对象直接继承对象。它适合简单委托场景，但在大型业务里通常不如 `class` 清晰。

对象委托适合表达“这个对象基于另一个对象扩展一点能力”。它不需要构造函数，也不需要类层级。缺点是团队可读性不一定好，尤其是大量对象通过 `Object.create` 串起来时，来源和初始化路径不如 class 直观。

## 构造函数继承

构造函数继承常用于初始化实例属性，配合原型继承共享方法。

```javascript
function Animal(name) {
  this.name = name;
}

Animal.prototype.move = function () {
  return `${this.name} is moving`;
};

function Dog(name) {
  Animal.call(this, name);
}

Dog.prototype = Object.create(Animal.prototype);
Dog.prototype.constructor = Dog;
```

这套写法能解释 `class extends` 背后的行为：调用父构造函数初始化实例，再连接原型链共享方法。

旧式继承最容易出错的地方是只借用构造函数、不连接原型，或者只连接原型、不初始化实例属性。前者会导致父类方法不可用，后者会导致实例数据缺失。`class extends` 的价值之一，就是把这些样板细节收起来。

## `class` 语法

`class` 把构造函数、原型方法和继承关系放到更清晰的语法里。

```javascript
class User {
  constructor(name) {
    this.name = name;
  }

  rename(name) {
    this.name = name;
  }
}
```

类方法默认不可以枚举，类内部默认严格模式。`class` 不是新对象模型，只是更清楚的表达方式。

```javascript
const user = new User('Ada');
```

如果函数只是做工具处理，不需要实例状态，那么模块函数通常比 `class` 更简单。

类适合表达“多个实例共享行为，并且每个实例有自己的状态”。如果逻辑只是纯计算、格式化、请求封装、数据转换，用普通函数或模块对象往往更直接。不要为了“看起来面向对象”给所有工具都套 class。

## `super`

`super` 用于调用父类构造函数或父类方法。子类构造函数中，在访问 `this` 之前必须先调用 `super()`。

```javascript
class Admin extends User {
  constructor(name, role) {
    super(name);
    this.role = role;
  }

  rename(name) {
    super.rename(name.trim());
  }
}
```

`super` 不是父类对象本身，而是按当前继承关系去访问父类构造函数或原型方法。继承链越复杂，`super` 越要谨慎使用。

子类构造函数里必须先调用 `super()` 才能访问 `this`，因为父类构造过程负责初始化实例的基础部分。方法里调用 `super.method()` 时，`this` 仍然是当前实例，不是父类实例。

```javascript
class Dog extends Animal {
  move() {
    return `${super.move()} quickly`;
  }
}
```

这里 `super.move()` 调用的是父类原型方法，但方法里的 `this.name` 仍然来自当前 `dog` 实例。

## 静态继承

静态属性和静态方法属于类本身，不属于实例。

```javascript
class User {
  static fromJSON(json) {
    const data = JSON.parse(json);
    return new User(data.name);
  }
}
```

子类也可以继承父类静态方法。

```javascript
class Admin extends User {}

Admin.fromJSON('{"name":"Ada"}');
```

静态方法适合工厂函数、类型工具和类级别配置，不要把依赖具体实例状态的逻辑写成 static。

静态继承适合让子类复用创建逻辑，但也要注意返回的实例类型。如果父类静态工厂方法里写死 `new User()`，子类调用时可能仍然返回父类实例；如果使用 `new this()`，则会根据调用的类创建实例。这类写法更灵活，但也更要求构造参数保持一致。

```javascript
class User {
  static create(name) {
    return new this(name);
  }
}

class Admin extends User {}

const admin = Admin.create('Ada');
console.log(admin instanceof Admin); // true
```

## 组合优先

继承表达的是“子类是父类的一种”。如果关系只是“拥有某种能力”，组合通常更清晰。

```javascript
function withLogger(service) {
  return {
    ...service,
    log(message) {
      console.log(message);
    },
  };
}
```

组合可以把能力拆成更小模块，避免继承层级越来越深。

```javascript
const userService = withLogger({
  createUser(data) {
    return request('/users', data);
  },
});
```

在前端业务里，组件组合、函数组合、Hook 组合都比深层继承更常见。

组合的优势是能力可以横向拼装，而不是纵向层层继承。比如“可记录日志”“可缓存”“可重试”“可取消”这些更像能力，不像身份。它们用函数包装、中间件、Hook、组件插槽通常比继承更自然。

## 继承边界

继承的风险通常不是语法，而是耦合。

| 风险 | 表现 |
|---|---|
| 层级过深 | 调用链难追踪 |
| 父类过大 | 子类继承了不需要的能力 |
| 重写过多 | 行为不稳定 |
| 状态共享不清 | 初始化顺序复杂 |

如果子类不断覆盖父类方法，或者父类为了兼容多个子类不断加判断，通常就说明继承已经不自然了。

继承还会把初始化顺序变复杂。父类构造函数、子类字段、子类构造函数、重写方法之间如果互相依赖，很容易出现“父类初始化时调用了子类尚未准备好的方法”这类问题。继承层级越深，这种风险越难排查。

## 选择判断

可以用几个简单问题判断是否适合继承：

1. 子类是否真的是父类的一种？
2. 是否需要共享实现而不是共享接口？
3. 子类是否会长期稳定复用父类行为？
4. 是否可以用组合更清楚地表达关系？

如果答案不够明确，先考虑组合，再考虑继承。很多前端代码里，组合比继承更容易维护。

一个实用判断是：如果关系可以自然说成“它是某种东西”，继承可能合理；如果关系更像“它拥有某种能力”或“它需要某个步骤增强”，组合通常更合适。前端业务变化快，组合的局部替换成本通常低于继承层级重塑。
