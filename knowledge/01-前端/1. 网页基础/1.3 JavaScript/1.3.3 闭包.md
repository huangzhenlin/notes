## 词法环境保留

闭包是“函数”和“函数创建时能访问的外层变量”的组合。它不是特殊语法，而是词法作用域的自然结果。

```javascript
function createPrinter(message) {
  return function print() {
    console.log(message);
  };
}

const printHello = createPrinter('Hello');
printHello(); // Hello
```

`createPrinter` 执行结束后，`message` 没有被释放，因为返回的 `print` 函数仍然引用它。只要内部函数还可能被调用，它引用的外层变量就需要继续存在。

闭包要解决的不是“函数套函数”的形式问题，而是“某段逻辑需要带着上下文继续执行”的问题。

所以判断一个函数是否形成闭包，不要只看有没有嵌套函数，而要看内部函数是否引用了外层变量，并且这个内部函数是否在外层执行结束后仍可能被调用。闭包让局部变量拥有比调用栈更长的生命周期，这是能力，也是需要管理的资源。

## 私有状态

闭包可以保存外部无法直接访问的私有状态。

```javascript
function createCounter() {
  let count = 0;

  return {
    increment() {
      count += 1;
      return count;
    },
    reset() {
      count = 0;
    },
  };
}

const counter = createCounter();
counter.increment(); // 1
counter.increment(); // 2
```

外部不能直接修改 `count`，只能通过返回的方法影响它。函数工厂、缓存器、模块封装都经常用这种模式。

#### 状态封装边界

闭包适合表达“少量状态 + 少量操作”。如果状态越来越多、操作越来越复杂，就应该考虑对象、类、模块或框架状态管理，而不是把所有逻辑塞进一个闭包里。

```javascript
function createToggle(initial = false) {
  let value = initial;

  return {
    get() {
      return value;
    },
    set(next) {
      value = Boolean(next);
    },
  };
}
```

闭包隐藏状态的能力很强，但隐藏得太深也会降低可测试性。判断是否适合闭包时，可以问一句：调用方是否只需要一个简单接口，而不需要直接观察内部状态？

闭包封装状态时，最好同时提供明确的读取、更新和清理入口。只暴露一个会改变内部状态的函数，短期很方便，长期可能让状态变化难以追踪。计数器、一次性执行、限流器、缓存器这类小状态非常适合闭包；复杂业务流程则更适合显式对象或状态机。

## 回调上下文

异步回调会保留创建时能够访问的变量。

```javascript
function delayLog(value) {
  setTimeout(() => {
    console.log(value);
  }, 1000);
}

delayLog('Ada');
```

一秒后仍然能打印 `value`，是因为回调函数形成了闭包。事件监听、Promise 回调、定时器、请求回调都依赖这种能力。

```javascript
function fetchAndRender(url) {
  let loading = true;

  fetch(url)
    .then((res) => res.json())
    .then((data) => {
      loading = false;
      render(data);
    });
}
```

这里的 `loading` 只是局部变量，但回调仍然能修改它。闭包让异步代码“记住当时的上下文”，这也是 [[1.3.8 异步|异步]] 编程能表达连续流程的重要基础。

异步闭包还要注意“旧上下文覆盖新结果”。搜索框、自动补全、分页加载里，旧请求可能比新请求更晚返回。如果回调闭包里没有判断当前上下文是否仍然有效，就可能把过期结果渲染到页面上。

## 循环绑定

经典闭包问题常出现在 `var` 循环中，因为 `var` 是函数作用域。

```javascript
for (var i = 0; i < 3; i += 1) {
  setTimeout(() => {
    console.log(i);
  }, 0);
}

// 3 3 3
```

多个回调引用的是同一个 `i`，等回调执行时，循环已经结束，`i` 已经变成 `3`。

使用 `let` 可以为每次循环创建新的块级绑定。

```javascript
for (let i = 0; i < 3; i += 1) {
  setTimeout(() => {
    console.log(i);
  }, 0);
}

// 0 1 2
```

这里不是定时器的问题，而是绑定复用的问题。只要多个函数共享同一个可变变量，就可能出现类似结果。

`let` 的每轮绑定解决的是循环变量问题，但不代表所有闭包问题都自动消失。如果循环里捕获的是同一个外部对象，多个回调仍然会共享这个对象。要判断捕获的是“每次新的绑定”，还是“同一个可变引用”。

```javascript
const state = { value: 0 };

for (let i = 0; i < 3; i += 1) {
  setTimeout(() => {
    state.value += 1;
  }, 0);
}
```

## 缓存与记忆化

闭包可以保存缓存，避免重复计算。

```javascript
function memoize(fn) {
  const cache = new Map();

  return function memoized(input) {
    if (cache.has(input)) {
      return cache.get(input);
    }

    const result = fn(input);
    cache.set(input, result);
    return result;
  };
}

const double = memoize((value) => value * 2);
```

这种写法适合纯函数、格式化、昂贵计算和稳定输入。它的问题也很明显：缓存如果不清理，就会一直增长。

#### 缓存失效

真实项目里的缓存闭包通常要考虑大小限制、过期时间、手动清理或弱引用。

```javascript
function createLimitedCache(limit = 100) {
  const cache = new Map();

  return {
    get(key) {
      return cache.get(key);
    },
    set(key, value) {
      if (cache.size >= limit) {
        const oldestKey = cache.keys().next().value;
        cache.delete(oldestKey);
      }
      cache.set(key, value);
    },
  };
}
```

闭包保存缓存很自然，但它不应该变成没有边界的全局仓库。

记忆化还要求函数最好接近纯函数：相同输入得到相同输出，且没有隐藏副作用。如果函数依赖时间、随机数、全局状态、接口返回值，就要重新考虑缓存键和失效策略。否则闭包缓存会把“不稳定结果”保存下来，制造更隐蔽的 bug。

## 事件监听

事件监听器经常借助闭包保留配置、状态和 DOM 引用。

```javascript
function bindClick(button, options) {
  let count = 0;

  function handleClick() {
    count += 1;
    if (count >= options.max) {
      button.disabled = true;
    }
  }

  button.addEventListener('click', handleClick);

  return function cleanup() {
    button.removeEventListener('click', handleClick);
  };
}
```

这个例子里，`handleClick` 需要访问 `count`、`options` 和 `button`。如果监听器不移除，这些值也会被保留。闭包和 [[1.3.11 事件|事件]] 绑定在一起使用时，清理函数通常比绑定函数本身更重要。

事件监听里的闭包最好形成“绑定函数返回解绑函数”的习惯。这样调用方不需要知道内部捕获了哪些变量，只要在组件卸载、页面切换或功能关闭时调用 cleanup，就能释放监听器和相关引用。

```javascript
const cleanup = bindClick(button, { max: 3 });

// 页面离开或组件销毁时
cleanup();
```

## 框架状态

React Hooks、Vue 组合式函数和其他前端框架里经常出现闭包。事件处理函数、effect 回调、订阅函数都会捕获某一次渲染或某一次初始化时的变量。

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const timer = setInterval(() => {
      console.log(count);
    }, 1000);

    return () => clearInterval(timer);
  }, []);
}
```

这里定时器里的 `count` 会一直是初次渲染时的值，因为 effect 只执行了一次。解决方式取决于真实意图：把 `count` 加入依赖、使用函数式更新、使用 `ref` 保存最新值，或者重新设计状态流。

闭包在框架里既是能力，也是陷阱。它能让事件处理、缓存、订阅写得很自然，也会让“看起来是最新值，实际是旧值”的问题很隐蔽。

框架里的闭包问题通常不是语言本身错了，而是渲染模型和闭包生命周期不一致。一次渲染会产生一组新的变量和函数，旧 effect、旧事件处理器、旧定时器可能仍然引用旧变量。理解这一点后，依赖数组、ref、函数式更新这些工具就不再像框架魔法，而是在管理闭包捕获。

## 生命周期与内存

闭包会延长变量生命周期。只要闭包仍然可达，它引用的对象就不能被垃圾回收。

```javascript
function bindLargeObject() {
  const largeData = new Array(100000).fill('*');

  return function read(index) {
    return largeData[index];
  };
}
```

闭包本身不是内存泄漏，问题在于不再需要的闭包仍然被事件监听、全局变量、缓存容器或订阅系统持有。

```javascript
function createHandler() {
  const state = { count: 0 };
  return () => {
    state.count += 1;
    return state.count;
  };
}
```

如果返回的函数被长期保存，`state` 也会长期存在。判断闭包是否安全，关键不是“有没有闭包”，而是“闭包的生命周期是否符合预期、引用的数据是否应该继续存在”。

内存排查时，可以沿引用链思考：谁持有这个函数，函数又捕获了哪些变量，这些变量里有没有 DOM、巨型数组、缓存 Map、订阅对象。闭包通常只是链条中的一环，真正泄漏的是“已经不需要的闭包仍然可达”。

## 使用边界

闭包适合封装少量状态、保留上下文、延迟执行逻辑和实现局部缓存。不适合承载过大的共享状态，也不适合替代清晰的数据流。

```javascript
function createOnce(fn) {
  let called = false;
  let result;

  return function once(...args) {
    if (!called) {
      called = true;
      result = fn(...args);
    }
    return result;
  };
}
```

好的闭包通常满足三个条件：捕获的数据少，生命周期清楚，对外接口简单。只要其中一个条件失控，就要重新评估是否应该换成模块、类、状态管理或显式参数传递。

闭包不是越少越好，也不是越多越高级。它是一种把上下文和行为打包的方式。用得好，代码会非常清晰；用得失控，状态会藏得太深。写闭包时先问“谁会持有返回函数、持有多久、如何释放”，通常就能避开大多数问题。
