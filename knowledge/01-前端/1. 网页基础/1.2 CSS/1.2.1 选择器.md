## 选择目标

CSS 选择器用于把样式规则匹配到 HTML 元素。选择器写得好，样式可读、可维护；选择器写得过深，后续覆盖和重构会很痛苦。

```css
.card-title {
  font-size: 20px;
  line-height: 1.3;
}
```

选择器的核心问题不是“能不能选中”，而是“是否稳定、是否容易覆盖、是否表达真实结构关系”。一个能工作的选择器不一定是好选择器，尤其在多人协作和组件化项目里，过深、过强、过依赖 DOM 的选择器会让样式变成隐形耦合。

```css
/* 不稳定：依赖过多 DOM 层级 */
.page .main .content .list .item .title {
  color: #111;
}

/* 更稳定：表达组件内的明确部位 */
.list-item-title {
  color: #111;
}
```

判断选择器是否合适，可以看三点：它是否描述了当前元素的角色，它是否会因为 DOM 小调整而失效，它是否容易被更局部的样式覆盖。

选择器本质上是样式和结构之间的契约。契约越依赖页面偶然结构，重构成本越高；契约越贴近组件角色，维护成本越低。比如 `.product-card-title` 表达的是组件部位，`.page > div:nth-child(2) h3` 表达的是当前 DOM 偶然长相。前者可以随着内部结构演进，后者很容易在加一层容器后失效。

## 基础选择器

基础选择器包括类型、类、ID、属性和通配选择器。工程中最常用的是类选择器和属性选择器；ID 选择器因为优先级高，通常更适合定位脚本入口或页面锚点，不适合大量用于组件样式。

```css
button {
}

.primary-button {
}

#app {
}

[data-state='active'] {
}

* {
  box-sizing: border-box;
}
```

| 选择器 | 示例 | 适合场景 | 风险 |
|---|---|---|---|
| 类型选择器 | `button` | 基础重置、元素默认样式 | 范围较大 |
| 类选择器 | `.button` | 组件、工具类、状态类 | 命名需要稳定 |
| ID 选择器 | `#app` | 根节点、锚点 | 优先级过高 |
| 属性选择器 | `[disabled]` | 状态、数据属性、表单 | 过度依赖属性结构 |
| 通配选择器 | `*` | 全局重置 | 范围极大 |

属性选择器在组件状态里很常见，尤其适合配合 `data-*` 表达 UI 状态。

```html
<button class="tab" data-active="true">概览</button>
```

```css
.tab[data-active='true'] {
  color: #1677ff;
  border-bottom-color: currentColor;
}
```

这种写法比为了状态不断拼类名更直观，但要保持状态命名一致，不要在同一项目里混用 `is-active`、`active`、`data-selected`、`data-state` 多套表达。

属性选择器特别适合表达状态和值，例如 `data-state="open"`、`aria-current="page"`、`aria-expanded="true"`。它的好处是状态含义写在 DOM 上，样式、测试和无障碍都能共享同一个信号。风险是状态命名一旦漂移，样式就会变成“看起来统一，实际各写各的”。

## 组合选择器

组合选择器用于表达元素之间的结构关系。它们适合描述“这个元素在某个上下文中”“这个元素是直接子元素”“这个元素紧跟在另一个元素后面”等关系。

```css
.card .title {
}

.card > .title {
}

h2 + p {
}

h2 ~ p {
}
```

后代选择器范围较宽，子代选择器更精确。层级过深会让样式强绑定 DOM 结构，组件内部稍微调整就可能破坏样式。

```html
<article class="article">
  <h2>标题</h2>
  <p>第一段正文。</p>
  <p>第二段正文。</p>
</article>
```

```css
.article h2 + p {
  margin-top: 0.5em;
}
```

这个选择器表达的是“标题后的第一段正文有更紧密的间距”，它比给第一段单独加类更贴近内容结构。但如果样式是组件稳定部位，例如卡片标题、按钮图标、列表项文本，通常直接使用类会更安全。

| 组合符 | 含义 | 常见用途 |
|---|---|---|
| 空格 | 任意后代 | 文章内容基础样式 |
| `>` | 直接子代 | 组件一层结构 |
| `+` | 紧邻兄弟 | 标题后首段、表单项间距 |
| `~` | 后续兄弟 | 状态影响后续元素 |

## 伪类

伪类用于选择某种状态、位置或逻辑条件。交互状态应优先使用语义明确的伪类，例如 `:hover`、`:focus-visible`、`:disabled`、`:checked`。

```css
button:hover {
  background: #f5f5f5;
}

input:focus-visible {
  outline: 2px solid #1677ff;
}

button:disabled {
  cursor: not-allowed;
  opacity: 0.5;
}
```

`:focus-visible` 特别适合保留键盘焦点样式，又避免鼠标点击时出现不必要轮廓。焦点样式和 [[1.1.7 无障碍|无障碍]] 直接相关，不要为了“视觉干净”把它完全移除。

位置伪类适合处理列表、表格和重复结构。

```css
.table-row:nth-child(even) {
  background: #fafafa;
}

.nav-item:first-child {
  margin-left: 0;
}
```

逻辑伪类能减少重复选择器：

```css
.form-field:has(input:invalid) .error {
  display: block;
}

.button:not(:disabled):hover {
  transform: translateY(-1px);
}
```

`:has()` 很强，但也更容易把父子结构耦合在一起。它适合表达“父元素样式依赖子元素状态”的场景，比如表单项错误、卡片是否包含封面图；不适合替代清晰的状态类。

```css
.field:has(input:focus-visible) {
  border-color: #1677ff;
}

.card:has(.card-cover) {
  grid-template-rows: auto 1fr;
}
```

这类写法读起来很自然，因为父元素状态确实来自子元素。但如果选择器开始描述复杂业务条件，就应该回到组件层输出明确状态。CSS 选择器适合表达结构和视觉状态，不适合承担业务判断。

## 伪元素

伪元素用于选择元素的一部分或生成装饰内容。常见伪元素包括 `::before`、`::after`、`::first-line`、`::first-letter`、`::selection`。

```css
.badge::before {
  content: '';
  display: inline-block;
  width: 6px;
  height: 6px;
  border-radius: 999px;
  background: currentColor;
}

p::first-line {
  font-weight: 600;
}
```

伪元素适合装饰，不适合承载关键文本信息。`content` 生成的内容对可访问性支持不稳定，重要信息应写在 HTML 中。

```css
/* 不推荐：关键文案藏在 CSS 里 */
.required::after {
  content: '必填';
}
```

更稳的方式是在 HTML 中放真实文本，再用 CSS 控制视觉：

```html
<label for="email">
  邮箱
  <span class="required-text">必填</span>
</label>
```

## 优先级

CSS 优先级由选择器类型决定。可以粗略理解为：ID 高于类、属性、伪类，高于类型、伪元素。

| 选择器 | 示例 | 权重倾向 |
|---|---|---|
| ID | `#app` | 高 |
| 类/属性/伪类 | `.card`、`[disabled]`、`:hover` | 中 |
| 类型/伪元素 | `button`、`::before` | 低 |

优先级越高，越难覆盖。不要为了解决一个样式问题不断加深选择器，这会制造新的维护问题。

```css
/* 不推荐：用更强的选择器压过去 */
.page .card .button.primary:hover {
  color: red;
}

/* 更推荐：调整样式归属或降低原选择器权重 */
.button-primary:hover {
  color: red;
}
```

选择器和 [[1.2.2 优先级|优先级]] 是一体两面：选择器负责“匹配谁”，优先级负责“冲突时谁赢”。工程里要尽量让选择器保持低权重，这样组件覆盖、主题切换和页面局部调整才不会层层加码。

## :is 与 :where

`:is()` 和 `:where()` 可以减少重复选择器。区别是 `:is()` 的优先级取参数中最高者，`:where()` 自身优先级为 0。

```css
:is(h1, h2, h3) {
  line-height: 1.2;
}

:where(.article h1, .article h2, .article h3) {
  margin-block: 1em 0.5em;
}
```

`:where()` 很适合写低优先级基础样式，方便后续组件覆盖。

```css
:where(button, input, textarea, select) {
  font: inherit;
}
```

`:is()` 更适合把多组选择器合并起来，减少重复。

```css
.card :is(h2, h3, p) {
  margin-block-start: 0;
}
```

这两个伪类的价值不是“写得更短”，而是帮助控制选择器复杂度。基础样式尽量用 `:where()` 降低权重；真正需要保留参数优先级时，再使用 `:is()`。

在文章正文、富文本、Markdown 渲染区里，`:where()` 很有价值。它可以给大量元素设置基础排版，又不会把权重抬高到组件难以覆盖的程度。

```css
.prose :where(h1, h2, h3, p, ul, ol, blockquote) {
  margin-block: 0;
}
```

如果未来某个组件嵌在 `.prose` 里，需要覆盖段落间距，低权重基础样式就不会成为阻碍。

## 工程边界

工程中选择器要避免过深、过强、过依赖 DOM。越靠近基础层，选择器越应该低权重；越靠近组件层，选择器越应该稳定清晰；越靠近页面层，越要避免影响到其他页面。

```css
/* 基础层：低优先级、容易覆盖 */
:where(a) {
  color: inherit;
  text-decoration-thickness: 0.08em;
}

/* 组件层：明确组件部位 */
.card-title {
  font-size: 1.125rem;
}

/* 状态层：表达状态而不是 DOM 位置 */
.card[data-selected='true'] {
  border-color: #1677ff;
}
```

选择器设计可以按这个顺序思考：

| 问题 | 判断 |
|---|---|
| 这是全局基础样式吗 | 用低权重选择器，避免污染组件 |
| 这是组件内部部位吗 | 用稳定类名或组件作用域 |
| 这是状态变化吗 | 用状态类、属性或语义伪类 |
| 这是内容结构关系吗 | 可用组合选择器 |
| 这是一次性覆盖吗 | 先找样式归属，而不是加深选择器 |

在 CSS Modules、Scoped CSS、CSS-in-JS、原子化 CSS 中，选择器策略会不同，但底层原则不变：匹配范围越清楚，权重越低，后续维护越轻松。

## 作用域选择

选择器要先明确作用域，再写匹配规则。全局选择器适合重置、排版和基础元素；组件选择器适合封装局部 UI；页面选择器适合一次性布局调整。混用作用域，是 CSS 失控的常见起点。

```css
/* 全局基础层 */
:where(button, input, textarea, select) {
  font: inherit;
}

/* 组件层 */
.product-card {
  border: 1px solid #e5e7eb;
}

/* 页面层 */
.home-page .product-card {
  margin-block-start: 24px;
}
```

页面层选择器不应反向污染组件设计。比如一个页面为了临时需求修改 `.button` 全局样式，就可能让其他页面按钮全部变形。更稳的做法是给当前页面或当前容器限定作用域。

## 状态选择

状态选择器要表达“状态”，不要表达“结构巧合”。常见状态可以用伪类、状态类、ARIA 属性或 `data-*` 属性表达。

```css
.button:hover {
  background: #f3f4f6;
}

.button[aria-pressed="true"] {
  background: #1677ff;
  color: white;
}

.tab[data-state="active"] {
  border-bottom-color: currentColor;
}
```

如果状态来自真实交互语义，例如选中、展开、当前页，优先考虑 `aria-*` 或原生伪类；如果状态只是组件内部视觉状态，可以用 `data-state` 或状态类。不要让状态散落成多个命名体系。

## 选择器性能

现代浏览器选择器匹配已经很快，绝大多数页面不需要为“选择器性能”过度优化。真正需要关注的是选择器复杂度带来的维护成本，以及在超大 DOM、频繁状态切换、动画场景中的匹配范围。

```css
/* 可读性和范围都不理想 */
.page .layout .content .panel ul li a span {
  color: red;
}

/* 更明确 */
.article-link-label {
  color: red;
}
```

选择器性能问题通常不是因为用了类选择器还是属性选择器，而是因为 DOM 太大、重排太频繁、样式影响范围太广。先优化结构和渲染，再考虑选择器微调。

## 命名策略

类名命名要稳定、可读、能表达角色。常见策略有 BEM、语义类、工具类、组件作用域类。没有一种命名适合所有项目，关键是同一项目保持一致。

```css
/* BEM 风格 */
.card {}
.card__title {}
.card--featured {}

/* 状态类 */
.is-active {}
.is-disabled {}
```

如果项目已经使用 CSS Modules 或 Scoped CSS，类名可以更短；如果是全局 CSS，类名就要更强调命名空间和语义。选择器命名的目标不是“看起来高级”，而是让后续维护者能立刻知道这条规则属于哪里。
