## 计算模型

CSS 优先级解决的是同一个元素、同一个属性被多条规则命中时，哪条声明最终生效。它不是孤立规则，而是层叠过程中的一个环节：先看来源和层级，再看优先级，再看出现顺序。

```css
button {
  color: black;
}

.primary-button {
  color: blue;
}
```

```html
<button class="primary-button">提交</button>
```

这里按钮最终是蓝色，因为 `.primary-button` 的优先级高于 `button`。如果只看“下面那条覆盖上面那条”，会误判很多 CSS 冲突；只有优先级相同时，后出现的规则才更靠后生效。

```text
是否同一属性
  -> 是否同一层叠来源和层
  -> 是否 important
  -> 比较选择器优先级
  -> 优先级相同看书写顺序
```

优先级和 [[1.2.6 层叠|层叠]] 紧密相关。学习时可以先把它理解成“选择器权重”，但实际排查时要把来源、层、`!important`、内联样式都一起看。

一个实用的判断是：优先级解决的是“谁赢”，层叠解决的是“在哪一层赢”，顺序解决的是“同层同权重时谁后写谁赢”。三者一起看，才能解释为什么某条规则明明写了却没有效果。

## 权重组成

选择器优先级通常可以用三列数字理解：ID 数量、类/属性/伪类数量、类型/伪元素数量。数值从左到右比较，左侧更重要。

| 选择器 | ID | 类/属性/伪类 | 类型/伪元素 |
|---|---:|---:|---:|
| `button` | 0 | 0 | 1 |
| `.button` | 0 | 1 | 0 |
| `.button:hover` | 0 | 2 | 0 |
| `form .button` | 0 | 1 | 1 |
| `#submit` | 1 | 0 | 0 |

```css
button.primary {
  color: blue;
}

.primary {
  color: red;
}
```

`button.primary` 的权重是 `0-1-1`，`.primary` 是 `0-1-0`，所以前者更高。即使 `.primary` 写在后面，也不会覆盖 `button.primary`。

类型选择器的权重虽然低，但堆叠很多类型选择器仍会增加复杂度。

```css
/* 权重不高，但结构耦合很重 */
main article section ul li a {
  color: red;
}
```

工程里真正危险的往往不是单个选择器，而是大量“为了覆盖而叠加”的选择器组合。

这也是为什么很多项目最终会回到“基础样式、组件样式、状态样式、页面覆盖”分层治理。只要层级清晰，大多数样式冲突根本不需要比到很高的权重。

## 相同优先级

当两条规则的层叠来源、层、重要性和优先级都相同时，后出现的声明生效。

```css
.button {
  color: blue;
}

.button {
  color: red;
}
```

最终是红色。这个规则常用于组件默认样式和后续主题覆盖，但不能滥用。多个文件打包后顺序可能被构建工具、导入顺序、CSS 提取策略影响，因此工程里要尽量让样式归属清楚，而不是依赖“某个文件刚好在后面”。

```css
/* 基础按钮 */
.button {
  color: #222;
}

/* 主题按钮，语义更明确 */
.button[data-variant='primary'] {
  color: #fff;
  background: #1677ff;
}
```

如果你发现必须不断调整 import 顺序才能让样式生效，通常说明样式边界或选择器权重已经不够清晰。

排序依赖尤其容易在 CSS 拆包、按路由加载、组件异步加载后失真。开发阶段看起来“写在后面的文件覆盖了前面的文件”，到了构建产物里顺序可能变了。真正可靠的方式不是背文件顺序，而是让规则本身的权重和归属更明确。

## :where

`:where()` 的特殊点是自身优先级为 0。它非常适合写基础样式、重置样式和范围样式，让后续组件轻松覆盖。

```css
:where(button, input, textarea, select) {
  font: inherit;
}

.form-button {
  font-weight: 600;
}
```

即使 `:where()` 里包含复杂选择器，它仍然不增加优先级。

```css
:where(.article h1, .article h2, .article h3) {
  margin-block: 1em 0.5em;
}
```

这很适合文章正文、富文本区域、基础排版。使用 `:where()` 的目的不是炫语法，而是把基础层权重压低，避免未来覆盖时被迫写更强选择器。

## :is 与 :not

`:is()`、`:not()`、`:has()` 本身不会像普通伪类那样简单增加一份权重，它们的优先级通常取参数中最高的选择器权重。

```css
:is(.button, #submit) {
  color: red;
}
```

这条规则会因为参数里包含 `#submit` 而拥有较高权重。写起来很短，但可能让覆盖变困难。

```css
.card:not(.is-disabled) {
  cursor: pointer;
}
```

`not()` 适合排除状态，但不要把它写成复杂业务逻辑。选择器越像条件表达式，越容易难以维护。

```css
/* 不推荐：选择器承载太多逻辑 */
.card:not(.is-disabled):has(.cover):not([data-loading='true']) {
  transform: translateY(-2px);
}
```

如果状态复杂，更适合在组件里输出明确状态类或 `data-state`。

## important

`!important` 会改变普通声明的比较顺序。它适合少数必须跨层覆盖的场景，例如工具类、用户样式、第三方样式修正，但不应该作为日常覆盖手段。

真正需要 `!important` 的场景通常很少，而且通常是“外部规则比你更强”或者“工具类必须无条件生效”。如果一个业务样式也开始频繁用 `!important`，说明样式治理已经从设计问题退化成了权重搏斗。

```css
.hidden {
  display: none !important;
}
```

工具类使用 `!important` 可以接受，因为它的语义就是“强制隐藏”。但业务样式里频繁使用 `!important`，会让后续覆盖只能继续加 `!important`，形成权重军备竞赛。

| 场景 | 是否适合 |
|---|---|
| 工具类强制隐藏 | 可以 |
| 覆盖第三方内联样式 | 谨慎 |
| 修复局部业务样式 | 不推荐 |
| 主题系统常规覆盖 | 不推荐 |

遇到样式不生效，优先检查选择器、层叠顺序和样式归属，不要第一反应用 `!important`。

## 内联样式

HTML 的 `style` 属性具有很高优先级，常见于 JS 动态样式、组件库运行时样式、拖拽尺寸、动画中间状态。

```html
<div class="panel" style="width: 320px;">内容</div>
```

普通外部 CSS 很难覆盖内联样式。如果第三方库通过内联样式写入尺寸，通常更适合使用库提供的 API、变量或配置，而不是硬写覆盖规则。

```css
/* 不推荐：为了覆盖内联样式继续加码 */
.panel {
  width: 400px !important;
}
```

内联样式适合表达动态数值，不适合承载可复用设计规则。颜色、间距、字体这类设计系统内容，应优先放在 CSS 类或变量里。

很多组件库会在运行时写入内联样式来表达尺寸、位移、定位或动画状态，这时更好的修复方式通常是查组件库提供的 API、变量或插槽，而不是在外层不断加 `!important`。如果必须覆盖第三方库，优先找它的主题入口、配置入口或插槽接口。

## 降低冲突

优先级治理的目标不是“算得很熟”，而是让你少算。好的 CSS 架构会让大多数样式冲突在设计上避免，而不是事后靠权重压制。

```css
/* 基础层：低权重 */
:where(a) {
  color: inherit;
}

/* 组件层：稳定类名 */
.nav-link {
  color: #333;
}

/* 状态层：明确状态 */
.nav-link[aria-current='page'] {
  color: #1677ff;
}
```

降低冲突可以从这些方向入手：

| 方法 | 价值 |
|---|---|
| 基础样式用 `:where()` | 降低默认样式权重 |
| 组件样式用稳定类名 | 减少 DOM 结构耦合 |
| 状态用属性或状态类 | 避免写复杂组合选择器 |
| 避免 ID 写样式 | 降低覆盖成本 |
| 避免无限嵌套 | 减少权重膨胀 |
| 使用 cascade layers | 明确层级覆盖关系 |

如果项目里有 CSS Modules、Scoped CSS 或原子化 CSS，它们可以降低全局命名冲突，但不能消除优先级问题。组件内部写出过强选择器，照样会难以覆盖。

## 调试方法

样式不生效时，不要靠猜。浏览器 DevTools 的 Styles 和 Computed 面板能直接告诉你哪条规则被覆盖、来自哪个文件、优先级如何。

排查顺序可以这样走：

```text
确认元素是否被选择器命中
  -> 确认属性是否被划掉
  -> 查看被哪条规则覆盖
  -> 比较 important、来源、层、优先级、顺序
  -> 判断是选择器问题还是样式归属问题
```

常见现象和处理方式：

| 现象 | 可能原因 | 处理方向 |
|---|---|---|
| 规则没出现在 DevTools | 选择器没命中或文件没加载 | 检查 DOM、类名、构建输出 |
| 属性被划掉 | 被更高优先级覆盖 | 降低原规则权重或调整归属 |
| 写在后面仍不生效 | 前者优先级更高 | 比较权重，不只看顺序 |
| 加 `!important` 才生效 | 样式架构冲突 | 找到原样式来源 |
| 组件库样式覆盖不了 | 样式注入顺序或内联样式 | 查组件库覆盖机制 |

真正稳定的修复通常不是“再写一条更强规则”，而是把样式放回正确层级：基础样式归基础层，组件样式归组件层，状态样式归状态层，页面覆盖归页面边界。

当你在 DevTools 里反复比较同一属性时，可以顺手问三个问题：这条样式属于基础还是组件，属于状态还是结构，属于页面覆盖还是全局规则。很多冲突其实不是 CSS 写错，而是样式职责放错地方。

## 层叠来源

优先级只在同一层叠来源、同一层、同一重要性下比较。浏览器默认样式、用户样式、作者样式、内联样式、动画和过渡都会参与层叠。

```text
浏览器默认样式
用户样式
作者样式
作者 important
用户 important
过渡样式
```

日常开发主要写的是作者样式，但调试时会看到浏览器默认样式、组件库注入样式、内联样式一起出现。不要只盯选择器权重，先确认冲突来自哪一层。

## cascade layer

`@layer` 可以显式声明样式层级，让覆盖顺序从“文件顺序和选择器硬碰硬”变成“先按层级排序”。

```css
@layer reset, base, components, utilities;

@layer reset {
  :where(*) {
    box-sizing: border-box;
  }
}

@layer components {
  .button {
    color: white;
  }
}

@layer utilities {
  .text-red {
    color: red;
  }
}
```

同一层内部仍然比较优先级和顺序，但不同层之间，后声明的层优先级更高。层叠层适合设计系统、组件库、业务覆盖、工具类同时存在的项目。

## 低权重策略

好维护的 CSS 通常不是靠高优先级取胜，而是靠低权重、清晰层级和明确作用域减少冲突。

```css
@layer base {
  :where(a) {
    color: inherit;
  }
}

@layer components {
  .nav-link {
    color: #374151;
  }
}

@layer utilities {
  .text-primary {
    color: #1677ff;
  }
}
```

基础层尽量低权重，组件层表达结构和状态，工具层提供明确覆盖。这样后续改样式时，更多是在正确层级里调整，而不是不断加 ID、嵌套和 `!important`。

## 冲突案例

样式冲突可以按“来源、层、重要性、优先级、顺序”一步一步排。

```css
@layer base {
  .button {
    color: black;
  }
}

@layer components {
  button {
    color: blue;
  }
}
```

虽然 `.button` 的选择器权重高于 `button`，但如果 `components` 层在 `base` 层之后，`button` 可能仍然赢。引入 `@layer` 后，调试思路必须从“只算选择器”升级到“先看层，再算权重”。

## 设计系统

设计系统里优先级治理尤其重要。基础 token、组件默认样式、主题样式、业务覆盖、工具类如果没有层次，就会互相抢控制权。

```text
推荐顺序：
1. reset
2. base
3. tokens / theme
4. components
5. pages
6. utilities
```

这个顺序不是固定标准，但要有明确约定。没有约定时，CSS 会靠“谁写得更强”获胜；有约定时，CSS 会靠“谁属于更合适的层”获胜。
