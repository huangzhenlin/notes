## transition

`transition` 用于在属性变化时生成过渡动画。

```css
.button {
  opacity: 0.8;
  transition: opacity 160ms ease, transform 160ms ease;
}

.button:hover {
  opacity: 1;
  transform: translateY(-2px);
}
```

它适合 hover、展开收起、状态切换这类“从一个状态到另一个状态”的动画。`transition` 的好处是简单，适合绝大多数轻量交互反馈。

```css
.panel {
  transition: max-height 240ms ease, opacity 240ms ease;
}
```

如果动画只是为了反馈状态变化，尽量优先用 transition。能不写复杂时间线，就不要把问题拖成动效工程。

`transition` 最适合“属性已经有两个状态，只需要让状态切换更柔和”的场景，例如按钮 hover、开关选中、卡片聚焦、抽屉进入。它不适合表达复杂阶段，也不适合解决显示隐藏的所有问题。比如元素从 `display: none` 变成 `display: block` 本身不能过渡，通常需要用 opacity、transform、visibility 或组件状态配合处理。

## keyframes

`@keyframes` 用于定义更完整的动画过程。

```css
@keyframes fade-in {
  from {
    opacity: 0;
    transform: translateY(8px);
  }
  to {
    opacity: 1;
    transform: translateY(0);
  }
}

.panel {
  animation: fade-in 240ms ease both;
}
```

`both` 表示动画前后应用对应关键帧样式，能避免动画开始或结束时闪动。

```css
@keyframes pulse {
  0%,
  100% {
    transform: scale(1);
  }
  50% {
    transform: scale(1.03);
  }
}
```

`keyframes` 适合加载态、强调态、持续循环态，但循环动画不要太多，否则会干扰阅读。

关键帧动画更适合有明确过程的动效，例如进入页面的轻微位移、骨架屏闪烁、加载 spinner、成功反馈。它的风险是容易被写成“页面一直在动”。持续循环动画要格外克制，特别是正文附近、表单附近和用户需要长时间阅读的区域。

## 合成友好属性

高频动画优先使用 `transform` 和 `opacity`。

```css
.drawer {
  transform: translateX(100%);
  transition: transform 240ms ease;
}

.drawer.is-open {
  transform: translateX(0);
}
```

动画 `width`、`height`、`top`、`left` 更容易触发布局和绘制，可能造成卡顿。并不是完全不能用，而是不要用于每帧高频动画。

```css
.card {
  will-change: transform;
}
```

`will-change` 只能偶尔用来提示浏览器优化，不要长期滥用。提前占用资源并不等于真正更快。

性能友好的动画通常遵循一个朴素原则：尽量不要每一帧都重新计算布局。`transform` 和 `opacity` 往往可以由合成线程处理，而 `width`、`height`、`top`、`left`、`margin` 这类属性更容易牵动布局和绘制。不是说它们绝对不能动画，而是要避免把它们用于高频、长时间、大面积的动效。

## easing

缓动函数决定动画节奏。

```css
.modal {
  transition: transform 220ms cubic-bezier(0.2, 0, 0, 1);
}
```

线性动画适合匀速移动，界面反馈通常更适合 ease 或自定义 cubic-bezier。动画要服务于状态变化，不要只追求炫。

```css
.toast {
  transition-timing-function: ease-out;
}
```

不同交互适合不同节奏：进入动画可以更快些，退出动画可以更柔和些。关键不是“用了什么曲线”，而是曲线有没有帮助用户理解变化方向。

缓动也会影响用户对界面的信任感。过慢的动画让操作显得迟钝，过弹的动画让业务系统显得不稳，过强的位移让用户失去空间定位。一般界面反馈控制在一两百毫秒更适合高频操作，页面级进入动效可以略长，但不应拖慢用户开始阅读和操作。

## 动画中断

用户可能快速重复触发动画，例如连续打开关闭菜单。动画要能处理中断。

```css
.menu {
  transition: opacity 160ms ease, transform 160ms ease;
}

.menu[data-open="false"] {
  opacity: 0;
  pointer-events: none;
  transform: translateY(-4px);
}
```

用状态驱动样式，比在 JS 中手动维护多个定时器更稳定。复杂动画可以交给 Web Animations API 或动画库。

```css
.dialog {
  transition: opacity 180ms ease, transform 180ms ease;
}

.dialog[hidden] {
  display: none;
}
```

当组件快速切换显示状态时，要考虑动画是否会被打断、状态是否还能回到正确位置。

中断处理的关键是让样式由“当前状态”决定，而不是由“上一次动画流程”决定。比如弹窗打开和关闭都应该只依赖 `data-open`、`hidden`、`aria-expanded` 等状态，而不是依赖某个定时器刚好跑完。只要状态源清楚，动画被用户快速打断时，也更容易回到正确样式。

## 减少动态效果

要尊重用户的系统动效偏好。

```css
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```

对眩晕敏感用户来说，大幅位移、缩放、视差动画可能造成不适。动效是体验增强，不应阻碍使用。

```css
@media (prefers-reduced-motion: reduce) {
  .carousel {
    scroll-behavior: auto;
  }
}
```

如果你的页面依赖滚动动画，也应给减少动态效果用户一个更平静的路径。

减少动态效果不等于把界面反馈全部取消。更合理的做法是保留必要状态变化，但减少大幅移动、缩放、视差和长时间循环。比如弹窗可以直接淡入，轮播可以关闭自动播放，滚动定位可以改成立即跳转。目标是减少不适，而不是让页面突然失去可理解反馈。

## JS 动画

需要逐帧控制时，可以使用 `requestAnimationFrame`。

```js
function animate() {
  updatePosition();
  requestAnimationFrame(animate);
}

requestAnimationFrame(animate);
```

JS 动画容易受主线程长任务影响。能用 CSS 完成的简单过渡，不必用 JS；需要手势联动、物理动画、复杂时间线时，再考虑 JS 动画。

```js
let start = performance.now();
function tick(now) {
  const progress = Math.min((now - start) / 300, 1);
  update(progress);
  if (progress < 1) requestAnimationFrame(tick);
}
requestAnimationFrame(tick);
```

JS 动画更适合精确控制进度，但也更需要你自己处理性能和中断。

JS 动画还要避免和布局读写交错。连续读取布局信息再写样式，会强制浏览器同步计算布局，容易造成卡顿。需要手势联动或拖拽动画时，可以把读取、计算、写入放进明确流程里，尽量批量更新，并用 `requestAnimationFrame` 对齐浏览器绘制节奏。

## 调试性能

```txt
优先 transform/opacity
避免大面积 box-shadow/filter 动画
检查是否触发布局
用 Performance 面板看掉帧
低端设备真机验证
```

动画是否流畅，要看目标设备。桌面浏览器流畅不代表移动端 WebView 也流畅。

调试动画时不要只看“肉眼顺不顺”，还要看主线程是否有长任务、是否频繁 Layout/Paint、是否产生大面积图层、是否因为阴影和滤镜导致绘制成本过高。尤其是移动端和低端机，轻微的阴影、模糊、背景滤镜都可能比想象中更贵。

| 现象 | 可能原因 | 排查方向 |
| --- | --- | --- |
| 动画卡顿 | 触发布局或大面积重绘 | 换成 transform/opacity |
| 动画闪烁 | 起止状态不连续 | 检查关键帧和初始样式 |
| 动画无法中断 | 状态机不清晰 | 用状态驱动样式 |
| 动画太晕 | 位移/缩放过强 | 尊重 reduced motion |

## 关键帧组织

`@keyframes` 不只是做循环，也可以配合状态切换、加载反馈、强调效果。

```css
@keyframes slide-in {
  from {
    opacity: 0;
    transform: translateY(12px);
  }
  to {
    opacity: 1;
    transform: translateY(0);
  }
}
```

组织动画时要先想清楚“进入、停留、退出”三个阶段。只写一个漂亮的中间过程，往往不足以支撑真实交互。

进入动画要让用户知道新内容从哪里来，退出动画要让用户知道内容去了哪里，停留阶段要尽量安静。动效设计如果只关注进入效果，常会忽略关闭、取消、快速切换、加载失败这些真实状态。

## 动画边界

动画的目标是帮助用户理解状态变化，而不是制造存在感。能少则少，能清楚就够。

判断一个动画是否值得保留，可以问三个问题：它是否解释了空间关系，它是否反馈了操作结果，它是否让等待过程更可感知。如果三个问题都答不上来，这个动画大概率只是装饰。装饰动画可以有，但不应该牺牲交互速度、阅读稳定和无障碍偏好。
