## 流式基础

响应式布局的基础是让内容随容器变化，而不是固定在某个设备宽度。先保证流式，再谈断点。

```css
.page {
  width: min(100%, 960px);
  margin-inline: auto;
  padding-inline: 16px;
}
```

固定最大宽度 + 自适应宽度，是很多页面主体容器的基本写法。不要把页面整体写成固定 1200px。

```css
.content {
  max-width: 68ch;
}
```

正文容器限宽能保持可读性，这和 [[1.2.11 文本样式|文本样式]] 里的行宽控制是同一件事。

流式布局的关键是先让页面“在任意宽度下不坏掉”。比如主体容器用 `width: min(100%, 960px)`，图片用 `max-width: 100%`，网格用 `minmax()`，文本用合理行宽，这些都不是某个断点里的补丁，而是页面默认就应该具备的弹性。断点应该用于结构切换，而不是修复一堆固定宽度造成的溢出。

## 媒体查询

媒体查询用于在不同视口条件下应用不同样式。

```css
.grid {
  display: grid;
  grid-template-columns: 1fr;
}

@media (min-width: 768px) {
  .grid {
    grid-template-columns: repeat(3, 1fr);
  }
}
```

断点应该来自内容需要，而不是死记设备尺寸。当卡片在某个宽度下拥挤，就在那里调整布局。

```css
@media (min-width: 1024px) {
  .layout {
    grid-template-columns: 240px 1fr;
  }
}
```

媒体查询不只是宽度，还可以判断高度、分辨率、颜色方案、打印等条件。

```css
@media (prefers-color-scheme: dark) {
  body {
    background: #111;
    color: #f5f5f5;
  }
}
```

媒体查询还要注意“条件含义”。`max-width` 更像向下覆盖，`min-width` 更像向上增强；`orientation` 判断横竖屏，但不等于判断设备类型；`hover` 和 `pointer` 判断输入能力，但混合设备可能同时支持触摸和鼠标。不要把媒体查询写成“某个手机型号的 if 判断”，它应该描述能力或空间条件。

## 移动优先

移动优先是先写小屏默认样式，再用 `min-width` 增强大屏。

```css
.sidebar {
  display: none;
}

@media (min-width: 1024px) {
  .sidebar {
    display: block;
  }
}
```

这种方式通常更符合移动端性能和布局思路。桌面优先也能做响应式，但容易在小屏上不断覆盖和修补。

```css
.card {
  padding: 16px;
}

@media (min-width: 768px) {
  .card {
    padding: 24px;
  }
}
```

移动优先的本质是先让最受限的环境可用，再逐步增强。这样样式层级和代码复杂度通常更稳定。

移动优先不等于“只照顾手机”。它更像一种渐进增强策略：默认样式满足小屏、慢网和触摸操作；屏幕变大后再增加侧栏、多列、悬停反馈和更高信息密度。这样即使某些增强样式没有加载，页面仍然保持基础可用。

## 弹性图片

图片和媒体资源要能在容器内收缩。

```css
img,
video {
  max-width: 100%;
  height: auto;
}
```

如果图片宽度超过容器，很容易造成横向滚动。复杂图片还应配合 `srcset`、`sizes` 和固定宽高减少加载和布局问题。

```html
<img
  src="/cover-800.jpg"
  srcset="/cover-400.jpg 400w, /cover-800.jpg 800w, /cover-1200.jpg 1200w"
  sizes="(max-width: 768px) 100vw, 800px"
  alt="课程封面"
/>
```

图片本身的响应式和 HTML 里的加载策略是一起看的，具体可以和 [[1.1.5 多媒体|多媒体]] 连起来理解。

响应式图片要同时考虑“显示尺寸”和“下载资源”。CSS 能让图片缩小，但如果 HTML 仍然只提供一张巨大原图，小屏用户还是会下载过大的资源。`srcset` 和 `sizes` 的意义就在于让浏览器根据实际显示宽度选择更合适的文件，而不是只靠 CSS 把大图压小。

## 容器查询

容器查询根据组件自身容器宽度调整样式，而不是只看 viewport。

```css
.card-list {
  container-type: inline-size;
}

@container (min-width: 520px) {
  .card {
    display: grid;
    grid-template-columns: 160px 1fr;
  }
}
```

同一组件可能出现在主内容区、侧栏、弹窗中。容器查询比全局 viewport 更能表达组件级响应式。

```css
.panel {
  container-type: inline-size;
}
```

容器查询适合组件复用度高的项目。组件不再只“看屏幕大小”，而是“看自己当前能有多宽”。

容器查询尤其适合卡片、列表项、侧栏面板、统计模块这些会被放到不同区域的组件。同一个组件在页面主栏里可能横排，在抽屉里可能竖排，在弹窗里可能压缩信息。用 viewport 媒体查询写这些规则时，页面越复杂，条件越容易互相打架；容器查询把判断放回组件自身，边界更清楚。

## clamp

`clamp` 适合响应式字号和间距。

```css
.title {
  font-size: clamp(24px, 6vw, 48px);
}

.section {
  padding-block: clamp(32px, 8vw, 96px);
}
```

它同时提供最小值和最大值，避免纯 `vw` 在极窄或极宽屏幕上失控。

```css
.page {
  padding-inline: clamp(16px, 4vw, 40px);
}
```

`clamp()` 的价值是把“跟随视口变化”变成一个有边界的连续变化，而不是突然跳变。

使用 `clamp()` 时要把三个值都想清楚：最小值保证小屏可读，中间值决定增长速度，最大值防止大屏失控。比如标题字号可以随视口增长，但不应该在超宽屏变成巨幅海报字；模块间距可以放大，但不能让内容之间离得像散架。

## 交互响应式

响应式不只关心宽度，还要关心输入方式。

```css
@media (hover: hover) {
  .card:hover {
    transform: translateY(-2px);
  }
}
```

触摸设备没有稳定 hover。桌面端 hover 效果不能成为移动端完成操作的唯一入口。

```css
@media (pointer: coarse) {
  .button {
    min-height: 44px;
  }
}
```

交互响应式的关注点还包括键盘、触摸、鼠标、打印和深色模式。布局能变，不代表交互语义也可以跟着变。

交互响应式还要避免“悬停专属信息”。桌面端可以用 hover 展示辅助说明，但移动端和键盘用户也应该有点击、聚焦或展开入口。响应式不是只让布局适配屏幕，也是让同一个任务在不同输入方式下都能完成。

## 响应式检查

| 检查项 | 说明 |
|---|---|
| 小屏是否横向溢出 | 常见于固定宽度和长文本 |
| 图片是否压缩合适 | 避免加载过大资源 |
| 触摸目标是否足够大 | 按钮和链接要易点 |
| 键盘是否遮挡输入 | 移动表单必须真机看 |
| 大屏是否过宽 | 文本行宽和内容密度 |
| 卡片是否在窄容器里还能读 | 组件级响应式 |

响应式的目标是让内容在不同空间里都可读、可操作、稳定，而不是只适配几个设备截图。

真正有效的响应式检查应该拖动视口连续观察，而不是只点几个预设尺寸。布局断裂往往发生在两个常见断点之间：导航刚好放不下、卡片刚好挤成奇怪宽度、表格刚好溢出、按钮刚好换行。连续检查能更早发现这些临界点。

## 断点策略

断点最好跟内容走，而不是跟设备型号走。页面在什么宽度开始拥挤、换行、对齐失衡，就在那里加断点。

```text
断点判断：
1. 卡片是否开始挤压
2. 导航是否需要折叠
3. 表格是否需要横向滚动
4. 侧栏是否该移到底部
```

与其背很多设备宽度，不如记住“内容出问题的临界点”。不同页面的断点完全可以不同。

## 版式切换

响应式不是只改列数，还包括间距、字号、对齐、可点击区域和信息密度。

```css
.layout {
  display: grid;
  grid-template-columns: 1fr;
  gap: 16px;
}

@media (min-width: 1024px) {
  .layout {
    grid-template-columns: 240px 1fr;
    gap: 24px;
  }
}
```

大屏不只是“更多列”，有时还意味着更多信息密度和更少折叠层级。小屏不只是“单列”，还意味着更大的触摸目标和更强的纵向优先级。

## 设备特性

媒体查询可以根据设备能力调整样式，而不只是宽度。

```css
@media (prefers-color-scheme: dark) {
  body {
    background: #111;
    color: #f5f5f5;
  }
}

@media (hover: hover) {
  .card:hover {
    transform: translateY(-2px);
  }
}
```

颜色方案、悬停能力、打印、横竖屏、分辨率和指针类型都可能影响体验。响应式不是“屏幕缩小版”，而是按当前环境重排信息和交互。

## 容器响应

当组件会出现在不同宽度区域时，容器查询比全局 viewport 更自然。

```css
.panel {
  container-type: inline-size;
}

@container (min-width: 480px) {
  .panel-card {
    display: grid;
    grid-template-columns: 160px 1fr;
  }
}
```

容器响应特别适合复用组件。一个卡片放在主内容区、侧栏、抽屉里时，组件应根据自己的容器宽度而不是整个屏幕决定排版。

## 测试维度

响应式测试不要只看几个常见分辨率，而要看布局在不同输入方式和信息密度下是否仍然稳定。

| 维度 | 关注点 |
| --- | --- |
| 小屏 | 是否可读、可点、无横滚 |
| 平板 | 是否适合中等信息密度 |
| 大屏 | 是否过宽、过散 |
| 横屏 | 是否出现断裂布局 |
| 高 DPI | 图片和细线是否清晰 |
| 深色模式 | 对比度和状态是否正常 |

如果项目里有大量图片、表格、卡片和侧边栏，响应式测试就不只是改几个媒体查询，而是要回头看信息结构本身是否支持多种宽度。

## 断点治理

断点多了以后，要避免每个组件各写一套毫无关系的尺寸。项目可以有一组基础断点，但具体组件仍然以内容临界点为准。

```css
:root {
  --breakpoint-sm: 640px;
  --breakpoint-md: 768px;
  --breakpoint-lg: 1024px;
}
```

CSS 自定义属性不能直接用于媒体查询条件，但可以作为设计文档和工具链配置的统一来源。实际项目常在 Sass、PostCSS、Tailwind、设计 token 或构建配置里维护断点。

断点治理的目标不是把所有组件锁在同一组尺寸上，而是让项目有共同语言。全局断点可以描述常见布局阶段，组件断点则由内容临界点决定。一个卡片组件在 520px 切换布局并不奇怪，前提是这个断点来自内容拥挤，而不是凭空新增。

## 组件响应

组件响应式的重点是“同一个组件在不同容器中仍然成立”。比如卡片在列表页是横向，在侧栏是纵向，在弹窗里可能更紧凑。

```css
.profile-card {
  container-type: inline-size;
}

@container (min-width: 560px) {
  .profile-card-inner {
    display: grid;
    grid-template-columns: 120px 1fr;
  }
}
```

这类写法能减少页面级媒体查询对组件内部结构的干预。组件越复用，越适合把响应逻辑放回组件容器。

## 表格响应

表格是响应式里最容易被处理坏的内容。宽表格可以横向滚动、隐藏低优先级列、拆分为多张表，也可以在移动端改成卡片，但要保留数据关系。

```css
.table-scroll {
  overflow-x: auto;
}

.table-scroll table {
  min-width: 720px;
}
```

如果用户主要任务是横向比较，不要轻易把表格改成卡片；如果用户主要任务是逐条查看记录，卡片化才更合适。

响应式表格最怕只追求“没有横向滚动”。有些数据天然需要横向比较，强行卡片化会让用户失去比较能力；有些数据主要按记录阅读，卡片化反而更清楚。选择方案前先问用户任务，而不是先问哪个样式更好看。

## 导航响应

导航从桌面到移动端，通常要处理横向空间不足、层级收纳和触摸目标。

```css
.nav {
  display: flex;
  gap: 16px;
}

@media (max-width: 767px) {
  .nav {
    display: none;
  }
}
```

隐藏导航时，必须提供等价入口，例如菜单按钮、底部导航或抽屉。响应式不能让功能在小屏上消失，只能改变入口形态。

## 内容优先级

小屏不是把桌面内容等比例缩小，而是要重新排列优先级。核心操作、标题、关键信息要更靠前，辅助信息可以折叠或下移。

```text
移动端优先展示：
1. 页面标题
2. 核心操作
3. 关键状态
4. 主内容
5. 辅助说明
```

如果内容层级不清楚，响应式样式会越写越复杂。很多响应式问题根源不是 CSS，而是信息架构没有主次。

## 真机验证

浏览器开发者工具只能模拟一部分场景。移动端还要看真实设备上的字体渲染、软键盘、滚动惯性、安全区、地址栏伸缩和触摸延迟。

```text
真机重点：
1. 输入框聚焦时是否被键盘遮挡
2. fixed 底栏是否避开安全区
3. 图片加载是否明显慢
4. 滚动是否卡顿
5. 横竖屏切换是否破版
```

响应式最终服务的是用户设备，而不是设计稿截图。只有在真实浏览器和真实输入方式里跑过，才算稳定。
