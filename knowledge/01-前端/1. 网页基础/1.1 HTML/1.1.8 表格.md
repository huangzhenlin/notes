## 表格结构

表格适合表达二维数据关系：行和列共同决定一个单元格的含义。课程表、财务报表、订单列表、权限矩阵、性能指标对比都适合使用表格；如果只是为了把图片和文字左右对齐，就不应该使用表格。

```html
<table>
  <caption>前端课程学习进度</caption>
  <thead>
    <tr>
      <th scope="col">课程</th>
      <th scope="col">章节数</th>
      <th scope="col">完成度</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">HTML</th>
      <td>8</td>
      <td>75%</td>
    </tr>
    <tr>
      <th scope="row">CSS</th>
      <td>12</td>
      <td>40%</td>
    </tr>
  </tbody>
</table>
```

`caption` 描述表格主题，`thead`、`tbody`、`tfoot` 描述表格区域，`th` 描述表头，`td` 描述普通数据。它们不是为了样式，而是为了让浏览器和辅助技术知道数据之间的关系。

| 元素 | 语义 | 常见用法 |
|---|---|---|
| `caption` | 表格标题 | 说明整张表的主题 |
| `thead` | 表头区域 | 放列标题或分组标题 |
| `tbody` | 主体区域 | 放主要数据行 |
| `tfoot` | 汇总区域 | 合计、平均值、备注 |
| `th` | 表头单元格 | 行标题或列标题 |
| `td` | 数据单元格 | 普通数据 |

表格和 [[1.1.3 语义化|语义化]] 的关系很直接：如果数据本身是二维关系，表格就是正确语义；如果只是为了页面布局，就应该使用 CSS 布局。

表格最适合的场景不是“看起来很规整”，而是“用户需要比较多个对象的多个字段”。比如订单、成绩、预算、权限、指标这些数据，用户往往是横向看列、纵向看行，再结合筛选和排序做判断。只要主任务是比较，表格就比卡片更高效。

表格要先组织数据关系，再考虑视觉效果。一个表格通常由标题、列头、行头、数据区和汇总区组成。

```html
<table>
  <caption>部门季度预算</caption>
  <colgroup>
    <col />
    <col span="2" class="number-col" />
  </colgroup>
  <thead>
    <tr>
      <th scope="col">部门</th>
      <th scope="col">预算</th>
      <th scope="col">实际支出</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">研发部</th>
      <td>120 万</td>
      <td>98 万</td>
    </tr>
  </tbody>
  <tfoot>
    <tr>
      <th scope="row">合计</th>
      <td>120 万</td>
      <td>98 万</td>
    </tr>
  </tfoot>
</table>
```

`colgroup` 可以表达列分组或辅助样式，但不要用它代替表头语义。真正说明列含义的仍然是 `th`。

## 表格标签

简单表格可以用 `scope` 建立表头关系。`scope="col"` 表示列标题，`scope="row"` 表示行标题。读屏器读到某个数据单元格时，可以结合对应行列标题理解它的含义。

```html
<table>
  <caption>各地区季度销售额</caption>
  <thead>
    <tr>
      <th scope="col">地区</th>
      <th scope="col">第一季度</th>
      <th scope="col">第二季度</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">华东</th>
      <td>120 万</td>
      <td>135 万</td>
    </tr>
  </tbody>
</table>
```

复杂表格则可以使用 `id` 和 `headers` 明确描述一个数据单元格对应哪些表头。

```html
<table>
  <caption>课程报名数据</caption>
  <thead>
    <tr>
      <th id="course">课程</th>
      <th id="signup">报名人数</th>
      <th id="finish">完课率</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th id="js" headers="course">JavaScript</th>
      <td headers="js signup">1500</td>
      <td headers="js finish">79%</td>
    </tr>
  </tbody>
</table>
```

复杂财务表、排班表、统计报表更需要明确表头关联。否则读屏器读到某个数值时，用户可能不知道它属于哪一行哪一列。

如果表格有分组列头，还可以在视觉上做多层表头，但结构上仍然要保持能被机器理解。不要为了版面把真实关系拆散成多个不连贯的表格，那样会让筛选、复制、导出和无障碍都更麻烦。

#### 合并与关联

`colspan` 和 `rowspan` 可以合并列或行，但合并会增加理解和维护成本。只有数据结构本身需要合并时才使用，不要为了视觉好看过度合并。

```html
<table>
  <caption>课程报名质量</caption>
  <thead>
    <tr>
      <th rowspan="2" scope="col">课程</th>
      <th colspan="2" scope="colgroup">报名数据</th>
    </tr>
    <tr>
      <th scope="col">人数</th>
      <th scope="col">完课率</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">JavaScript</th>
      <td>1500</td>
      <td>79%</td>
    </tr>
  </tbody>
</table>
```

合并表头时，要尤其关注表头和数据单元格的关联。简单合并可以继续使用 `scope`，复杂合并更适合 `headers`。如果为了美观把大量单元格合并，后续排序、筛选、导出、响应式展示都会变得困难。

合并单元格最好只出现在“数据本身有层级”的地方，例如部门合计、季度分组、分类汇总。纯粹为了视觉平衡做合并，往往会让表格变成难以维护的版式拼图。

## 表格呈现

表格样式应该增强可读性，而不是破坏语义。常见优化包括边框合并、单元格内边距、斑马纹、数值右对齐、表头固定和横向滚动。

```css
.data-table {
  width: 100%;
  border-collapse: collapse;
}

.data-table th,
.data-table td {
  padding: 8px 12px;
  border: 1px solid #ddd;
}

.data-table tbody tr:nth-child(even) {
  background: #f8f8f8;
}

.data-table .number {
  text-align: right;
  font-variant-numeric: tabular-nums;
}
```

数值列右对齐能让小数位和数量级更容易比较；`font-variant-numeric: tabular-nums` 可以让数字宽度更统一，报表阅读体验会更好。

```html
<td class="number">1,245.80</td>
<td class="number">98.12%</td>
```

表格排序、筛选、分页通常不只是 CSS 问题。如果点击列头能排序，应把按钮放进表头单元格里，避免把 `th` 变成难以操作的点击区域。

```html
<th scope="col">
  <button type="button" aria-sort="none">
    完成度
  </button>
</th>
```

`aria-sort` 应放在当前排序列上，并随排序状态更新。这样用户才能知道当前表格按哪一列、什么方向排序。

#### 响应式处理

宽表格在移动端很容易溢出。最稳妥的基础方案是外层容器横向滚动，保留表格结构和语义。

```html
<div class="table-scroll" tabindex="0" aria-label="可横向滚动的数据表格">
  <table class="data-table">
    <!-- table content -->
  </table>
</div>
```

```css
.table-scroll {
  overflow-x: auto;
  max-width: 100%;
}

.table-scroll table {
  min-width: 720px;
}
```

不要轻易把表格在移动端改成一堆 `div`，那会丢失行列关系。确实要卡片化时，应确认移动端主要阅读的是单条记录，而不是横向比较。

| 移动端方案 | 适合场景 | 代价 |
|---|---|---|
| 横向滚动 | 列很多，仍需横向比较 | 用户需要发现滚动 |
| 隐藏低优先级列 | 列有明显主次 | 信息可能不完整 |
| 卡片化 | 逐条查看记录 | 行列比较能力下降 |
| 拆分为多个表 | 指标分组清晰 | 页面更长 |

如果表格是关键数据入口，例如财务、订单、监控报表，移动端不应只追求“看起来不溢出”，还要保证用户能完成查找、比较、排序和复制数据。

#### 可访问性

可访问的表格要让用户知道表格主题、列含义、行含义和当前数据位置。至少应做到：有 `caption` 或可关联标题，表头使用 `th`，复杂关系使用 `scope` 或 `headers`，不要用空单元格制造视觉间距。

| 问题 | 影响 | 改法 |
|---|---|---|
| 表头用 `td` | 读屏器无法识别表头 | 使用 `th` |
| 没有标题说明 | 用户不知道表格主题 | 添加 `caption` 或关联标题 |
| 合并过度复杂 | 行列关系难理解 | 简化结构或加 `headers` |
| 用表格布局 | 语义错误、响应式困难 | 使用 CSS 布局 |
| 空单元格制造间距 | 数据关系被污染 | 用 CSS 控制间距 |

表格可访问性是 [[1.1.7 无障碍|无障碍]] 在二维数据里的具体落点。视觉用户可以靠位置理解数据，读屏器用户更依赖结构化关系，所以表头、标题和排序状态要比普通布局更严谨。


## 状态与操作

#### 排序与筛选

当表格支持排序时，表头里应该有可操作控件，而不是给整个 `th` 绑定点击事件。

```html
<th scope="col" aria-sort="ascending">
  <button type="button">完成度</button>
</th>
```

`aria-sort` 应只出现在当前排序列上，并且根据状态更新为 `ascending`、`descending`、`none` 或 `other`。筛选也应该提供可访问的控件和说明，不能只用图标颜色表示当前有筛选条件。

#### 空值与状态

表格里的空值要区分“没有数据”“不适用”“加载中”“权限不可见”。不要用空白单元格让用户猜。

| 显示 | 含义 |
| --- | --- |
| `-` | 暂无数据 |
| `不适用` | 当前项不适合该指标 |
| `加载中` | 数据尚未返回 |
| `无权限查看` | 数据存在但当前用户不可见 |

这些状态在报表、订单、权限矩阵里很重要。空白单元格看似干净，但会让用户无法判断是数据缺失、接口失败还是权限限制。

空值状态最好和业务含义绑定，而不是统一用一个符号糊过去。比如财务报表里的 `-`、权限矩阵里的 `无权限查看`、接口延迟里的 `加载中`，对应的解释都不同。把状态写清楚，用户就不会在“没数据”和“没权限”之间猜来猜去。

#### 数据密度

表格通常承载高密度信息，样式设计要帮助比较，而不是制造噪音。数值列右对齐、文本列左对齐、重要状态用文字加颜色，都会提升阅读效率。

```css
.data-table td.number {
  text-align: right;
  font-variant-numeric: tabular-nums;
}

.data-table td.status {
  white-space: nowrap;
}
```

高密度表格不一定要把所有信息都放进一张表。可以通过详情展开、列配置、分页、固定首列等方式控制复杂度。但无论怎么增强，原始数据关系都不应该被破坏。

表格和筛选、导出、批量操作经常连在一起。只要表格承担管理后台、报表或业务审核职责，就应该预留“选择行、查看详情、排序、筛选、分页、导出”这一整套操作，而不是只考虑静态展示。表格不是一个静态展示组件，而是高密度数据交互容器。

## 表格选择

不要把所有列表都做成表格。表格适合比较，卡片适合浏览，列表适合顺序阅读，描述列表适合术语说明。

```text
适合表格：
1. 多行多列比较
2. 数值统计
3. 权限矩阵
4. 报表数据

不适合表格：
1. 营销卡片
2. 图文信息流
3. 单列文章列表
4. 普通页面布局
```

当用户的主要任务是“比较多个对象的多个字段”，表格通常是正确选择；当用户的主要任务是“逐条阅读内容”，卡片或列表可能更合适。

做表格无障碍时也可以先抓主任务：用户是否能知道当前表格主题、是否能理解每列含义、是否能判断当前排序状态、是否能移动到需要的单元格。只要这些问题清楚，后面再优化斑马纹、固定表头和移动端重排就会轻很多。
