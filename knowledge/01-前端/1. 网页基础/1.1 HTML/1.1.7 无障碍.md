## 语义基础

语义化 HTML 是无障碍的基础。浏览器、读屏器、键盘导航和其他辅助技术都依赖元素语义理解页面结构。页面不是只有“看起来像”按钮、导航、标题就够了，而是要真的使用对应元素。

```html
<header>站点头部</header>
<nav aria-label="主导航">
  <a href="/courses">课程</a>
  <a href="/articles">文章</a>
</nav>
<main>
  <h1>订单详情</h1>
  <section aria-labelledby="summary-title">
    <h2 id="summary-title">订单概览</h2>
    <p>订单状态：待支付</p>
  </section>
</main>
```

优先使用原生语义元素，而不是给 `div` 强行加交互。按钮用 `button`，链接用 `a`，表单控件用对应输入元素。这比手写 ARIA 更可靠，也更容易保持和浏览器默认行为一致。

| 场景 | 推荐元素 | 价值 |
|---|---|---|
| 站点导航 | `nav` | 让用户快速定位跳转区域 |
| 页面主体 | `main` | 明确当前页面核心内容 |
| 独立文章 | `article` | 表示可单独分发的内容块 |
| 章节分组 | `section` | 表示带主题的内容区域 |
| 辅助内容 | `aside` | 表示侧边、补充、相关推荐 |

如果页面结构本身不清楚，后面再补 ARIA 也很难救回来。无障碍不是“加标签”，而是先把语义做对，这一点和 [[1.1.3 语义化|语义化]] 的底层目标一致。

很多无障碍问题不是“有没有标签”，而是“用户能不能按自己的方式完成任务”。比如同样是打开筛选面板，鼠标用户可以点图标，键盘用户要能 Tab 到触发按钮并看到焦点，读屏器用户要能听到当前状态是展开还是收起。先想任务，再想交互，最后再看标签，通常比先堆 ARIA 更有效。

## 键盘可达性

可交互元素必须能通过键盘访问。用户应该可以用 Tab 移动焦点，用 Enter 或 Space 触发操作。对于只用鼠标的开发者来说，这一层最容易被忽略，但对依赖键盘、开关控制、语音控制的用户却是基本能力。

```html
<button type="button">保存</button>
<a href="/orders">查看订单</a>
```

不要用 `div` 模拟按钮：

```html
<!-- 不推荐 -->
<div onclick="submit()">保存</div>
```

如果确实必须自定义交互元素，需要补充角色、焦点和键盘事件，但这通常比直接使用原生控件更容易出错。

```html
<!-- 原生按钮自带焦点、键盘触发和禁用语义 -->
<button type="button" aria-pressed="false">
  收藏
</button>
```

键盘可用性常见问题包括：点击元素没有焦点、只能按鼠标操作、弹窗打开后焦点丢失、菜单展开后方向键不能移动、对话框关闭后焦点回不到触发按钮。对自定义组件，至少要明确“打开、关闭、切换、确认、取消”这些动作是否都能键盘完成。

如果一个交互只能用鼠标完成，就意味着它在焦点管理上还不完整。最常见的补救不是给元素加更多样式，而是回到原生元素、表单语义和焦点流。很多看起来复杂的无障碍问题，最后都会落到“这个元素到底应该是按钮、链接还是输入框”这个基础判断上。

#### 焦点管理

焦点告诉键盘用户当前操作位置。弹窗、抽屉、菜单、路由切换和步骤表单都需要关注焦点。焦点样式可以被设计得更好看，但不能被隐藏。

```css
button:focus-visible,
a:focus-visible,
input:focus-visible {
  outline: 2px solid #1677ff;
  outline-offset: 2px;
}
```

不要粗暴移除 `outline`。如果视觉设计不接受浏览器默认样式，可以重写为统一的焦点样式，但必须让用户在 Tab 移动时知道自己在哪里。

```html
<button id="delete-button" type="button">删除</button>

<dialog aria-labelledby="confirm-title">
  <form method="dialog">
    <h2 id="confirm-title">确认删除</h2>
    <p>删除后无法恢复。</p>
    <button value="cancel">取消</button>
    <button value="confirm">确认删除</button>
  </form>
</dialog>
```

浮层焦点管理通常包含三件事：打开时焦点进入浮层，浮层内 Tab 不应跳到页面背后，关闭后焦点回到触发元素。否则键盘用户会在页面里“迷路”。在单页应用中，路由切换后也要考虑把焦点移到新页面标题或主内容区域。

## 表单无障碍

表单控件需要可感知的标签。`placeholder` 不能替代 `label`，因为用户输入后 placeholder 会消失，而且它对辅助技术来说不是稳定的名称。

```html
<label for="email">邮箱</label>
<input id="email" name="email" type="email" autocomplete="email" />
```

错误提示要和控件关联：

```html
<label for="password">密码</label>
<input id="password" type="password" aria-describedby="password-error" />
<p id="password-error">密码至少 8 位</p>
```

更完整的标注还包括组标题和辅助说明：

```html
<fieldset>
  <legend>联系信息</legend>

  <label for="phone">手机号</label>
  <input id="phone" name="phone" inputmode="tel" aria-describedby="phone-hint" />

  <p id="phone-hint">用于接收短信通知。</p>
</fieldset>
```

这里的核心不是“写了标签就行”，而是要让用户知道这个控件是什么、该怎么填、填错后哪里出问题。表单无障碍和 [[1.1.4 表单|表单]] 直接相关，标签、错误、必填、自动填充都会影响可用性。

表单类页面最适合做端到端无障碍检查：标签是否能读出字段名称，错误是否能被定位，自动填充后内容是否仍能理解，提交失败后焦点是否回到错误摘要。只要表单能被完整走一遍，很多其他页面的问题也能顺带暴露出来。

## 辅助技术适配

#### ARIA 边界

ARIA 用来补充语义，不是替代语义。能用原生 HTML 表达时，不要优先使用 ARIA。

```html
<!-- 推荐 -->
<button type="button">关闭</button>

<!-- 不推荐 -->
<div role="button" tabindex="0">关闭</div>
```

常见 ARIA 用法包括 `aria-label`、`aria-labelledby`、`aria-describedby`、`aria-expanded`、`aria-controls`。它们适合增强复杂组件状态表达，例如可折叠面板、菜单、树形控件、分页器和选项卡。

```html
<button aria-expanded="false" aria-controls="menu">
  菜单
</button>
<ul id="menu" hidden>
  <li><a href="/profile">个人资料</a></li>
  <li><a href="/settings">设置</a></li>
</ul>
```

ARIA 不会自动赋予行为。`role="button"` 只是告诉辅助技术“这像按钮”，但仍然要自己补焦点、键盘事件、按下态和禁用态。能用原生元素，就尽量不要手搓角色。

| 做法 | 风险 | 更好的选择 |
|---|---|---|
| `div role="button"` | 需要手动补键盘与焦点 | `button` |
| 只写 `aria-label` | 可见文本缺失，维护成本高 | 可见文本优先 |
| 滥用 `aria-hidden` | 可能误隐藏重要信息 | 只隐藏装饰内容 |
| 滥用 `aria-live` | 频繁打断用户 | 只播报关键动态 |

#### 可访问名称

可访问名称是辅助技术读出一个控件或区域时使用的名称。按钮、链接、输入框、图片、区域都需要能被准确命名。

```html
<button type="button" aria-label="关闭弹窗">×</button>

<label for="search">搜索课程</label>
<input id="search" name="keyword" type="search" />
```

优先使用可见文本作为名称。只有图标按钮、无可见文字控件、复杂组合区域，才考虑 `aria-label` 或 `aria-labelledby`。如果可见文字和无障碍名称不一致，用户听到的内容和看到的内容会产生偏差。

#### 颜色对比

文本与背景要有足够对比度。只用颜色表达状态是不够的，因为色弱用户、高对比模式用户、低亮度屏幕用户都可能无法区分。

```html
<p class="error">
  <span aria-hidden="true">!</span>
  邮箱格式错误
</p>
```

```css
.error {
  color: #b42318;
  border-left: 4px solid currentColor;
  padding-left: 12px;
}
```

错误状态可以同时使用颜色、图标、文字和边框。颜色是增强信息，不应该是唯一信息。

| 信息类型 | 推荐表达 |
|---|---|
| 错误提示 | 颜色 + 文案 + 图标 |
| 必填字段 | 星号 + 文案说明 |
| 成功状态 | 颜色 + 文字反馈 |
| 警告状态 | 图标 + 说明文本 |

如果页面支持深色模式，不能只检查浅色主题下的对比度。按钮、正文、边框、图标、禁用态、占位文本都应分别验证。

#### 状态表达

组件状态要能被看见，也要能被辅助技术理解。例如展开、选中、禁用、当前页、排序方向都不是纯视觉信息。

```html
<button aria-expanded="false" aria-controls="filter-panel">
  筛选条件
</button>
<section id="filter-panel" hidden>
  ...
</section>
```

```html
<a href="/docs/html" aria-current="page">HTML</a>
```

`aria-expanded`、`aria-selected`、`aria-current`、`aria-pressed` 等状态属性应随交互实时更新。状态不更新，比不写更危险，因为它会给辅助技术错误信息。

## 动态内容与交互

异步加载、Toast、校验错误、步骤切换等动态内容，需要考虑辅助技术是否能感知变化。视觉上出现一条提示，并不代表读屏器用户能知道发生了什么。

```html
<div role="status" aria-live="polite">
  保存成功
</div>
```

`aria-live` 适合非阻塞通知。错误、警告和关键状态要谨慎使用，避免频繁打断读屏器用户。

动态内容不要只考虑“播报”，还要考虑“是否能被发现”。比如加载完成后新增一段列表、展开更多内容、切换分页、显示后台校验错误，这些变化有时更适合通过焦点移动、标题变化或区域状态更新来表达，而不只是依赖实时播报。

| 场景 | 适合方式 |
|---|---|
| 表单提交成功 | `role="status"` 或 `aria-live="polite"` |
| 重要错误 | 可聚焦错误摘要 + 字段错误关联 |
| 装饰性更新 | 不必播报 |
| 倒计时、价格跳动 | 慎用播报，避免噪音 |

很多动态更新更适合“更新焦点位置”而不是“语音播报所有变化”。例如表单提交失败时，把焦点移到错误摘要区，通常比连续播报每个字段更清楚。

#### 弹窗交互

弹窗、抽屉、下拉菜单是无障碍问题高发区。它们会改变页面焦点、视觉层级和交互范围。

```html
<dialog aria-labelledby="dialog-title">
  <form method="dialog">
    <h2 id="dialog-title">确认删除</h2>
    <p>删除后无法恢复。</p>
    <button value="cancel">取消</button>
    <button value="confirm">确认删除</button>
  </form>
</dialog>
```

弹窗打开时，焦点应该进入弹窗；弹窗关闭时，焦点应该回到触发按钮；弹窗打开期间，键盘不应跳到背后的页面内容。视觉层级、DOM 顺序和焦点顺序要一起考虑。

#### 检查路径

无障碍检查可以从几个具体问题开始：

| 检查项 | 判断 |
|---|---|
| 键盘能否完成操作 | 不使用鼠标也能走完核心流程 |
| 焦点是否可见 | Tab 移动时位置清楚 |
| 图片是否有替代文本 | 信息型图片有 `alt` |
| 表单是否有标签 | 输入项能被读屏器识别 |
| 颜色是否唯一表达 | 状态不只靠颜色 |
| 浮层是否可关闭 | 键盘能进入、操作、退出 |
| 页面是否有主内容入口 | 能快速进入主区域 |

可以按“结构、交互、表单、视觉、动态反馈”的顺序检查：先看语义结构是否正确，再看键盘和焦点是否可用，然后检查表单、颜色和提示，最后看异步内容和浮层是否能被辅助技术理解。

无障碍不是额外工作，它和 [[1.1.6 SEO|SEO]] 有很多共同基础：结构越清楚，机器和人越容易理解页面。页面越接近原生语义，后续补可访问性就越省力。

如果时间有限，可以优先保核心路径：登录、搜索、提交、付款、关闭弹窗、切换选项卡、打开菜单、查看详情。把这些高频动作先做顺，通常比在低频页面上花很多时间更有价值。

#### 测试方法

无障碍测试不能只依赖自动化工具。自动化能发现缺失标签、对比度不足、ARIA 使用错误，但发现不了所有交互体验。

```text
基本手测：
1. 只用键盘走完核心流程
2. 打开读屏器听主要页面结构
3. 放大页面到 200% 检查布局
4. 关闭图片看内容是否仍可理解
5. 检查深色模式和高对比模式
```

如果时间有限，至少保证核心路径可用：登录、搜索、提交表单、下单、支付、查看详情、关闭弹窗。这些路径不能只服务鼠标用户。

## 媒体无障碍

#### 图片替代

图片的 `alt` 要描述图片在当前上下文中的作用。不是所有图片都要长描述，也不是所有图片都能空 `alt`。

| 图片角色 | 推荐处理 |
| --- | --- |
| 商品图 | 描述商品或关键外观 |
| 图标按钮 | 描述按钮动作 |
| 数据图表 | 提供关键结论或表格替代 |
| 装饰图 | `alt=""` |
| 复杂流程图 | 正文补充详细说明 |

复杂图表不要试图把所有信息塞进 `alt`。更好的方式是在图表旁边提供文字总结或数据表，让用户能用文本理解核心信息。
