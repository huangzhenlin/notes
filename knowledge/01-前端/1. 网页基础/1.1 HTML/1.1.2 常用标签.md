## 文本层级

文本标签的重点不是默认样式，而是内容意义。标题表示层级，段落表示完整语义单元，强调标签表达重要性或语气，行内容器用于局部包裹。

```html
<article>
  <h1>HTML 常用标签</h1>
  <p>HTML 通过标签组织页面内容。</p>
  <p>请先阅读 <strong>重点说明</strong>，再继续操作。</p>
  <p>这个词需要 <em>语气强调</em>，不是单纯变斜。</p>
  <p>价格：<span class="price">¥99</span></p>
</article>
```

#### 标题标签

`h1` 到 `h6` 表示六级标题。它们应该描述内容结构，而不是充当字号工具。标题跳级会让文档轮廓断裂，尤其影响屏幕阅读器按标题导航。

标题的数量没有固定答案，但层级要能解释得通。文章页通常只有一个页面主标题，下面按内容层次展开；后台页面可能有页面标题、卡片标题和表单分组标题。只要标题能组成清晰大纲，就比“视觉上像标题但结构上是 `div`”更可靠。

#### 段落与换行

`p` 表示段落，适合承载一段独立文字。不要用多个 `<br>` 制造段落间距，段落间距应该由 CSS 控制。

```html
<!-- 不推荐 -->
第一段文字<br><br>
第二段文字

<!-- 推荐 -->
<p>第一段文字</p>
<p>第二段文字</p>
```

`br` 不是绝对不能用，它适合地址、歌词、诗歌、短格式文本这类“换行本身就是内容”的场景。普通正文、说明文字、卡片描述则更适合用多个段落，让结构和样式分开。

#### 强调与视觉

`strong` 表示重要内容，`em` 表示语气强调；`b` 和 `i` 更偏视觉或约定俗成的文本标记。只想改变字体粗细时，优先用 CSS；内容确实重要时，才用 `strong`。

强调标签要少用。一个段落里如果到处都是 `strong`，用户反而不知道重点在哪里。真正重要的条件、风险、限制可以用 `strong`；单纯品牌词、视觉高亮、价格颜色，通常用样式类更合适。

文本层级里还要注意“可读性”和“可检索性”。比如在文章正文里，术语第一次出现时可以用普通文本配合上下文解释，不必反复上强调标签；而在产品说明、协议条款、警告信息里，`strong` 更适合表达“这里一定要注意”。如果只是为了让文字显粗，后续改版时会很难分辨到底是视觉需求还是语义需求。

| 标签 | 语义 | 典型场景 | 不适合 |
| --- | --- | --- | --- |
| `h1` ~ `h6` | 标题层级 | 页面标题、章节标题 | 单纯控制字号 |
| `p` | 段落 | 正文、说明、摘要 | 包复杂布局 |
| `strong` | 重要 | 警告、关键条件 | 只为了加粗 |
| `em` | 强调语气 | 语气变化、重点词 | 只为了斜体 |
| `span` | 无语义行内容器 | 局部样式、脚本挂点 | 替代段落或按钮 |
| `br` | 换行 | 地址、诗歌、短格式文本 | 制造段落间距 |

## 代码与引用

技术文档、教程和产品说明经常需要展示代码、键盘输入、引用和补充说明。HTML 提供了专门的文本标签，不必全部用 `span`。

```html
<p>运行 <code>npm run dev</code> 启动项目。</p>
<pre><code>const message = "hello";</code></pre>
<p>按 <kbd>Ctrl</kbd> + <kbd>S</kbd> 保存文件。</p>
<blockquote cite="https://example.com">
  <p>这是一段引用内容。</p>
</blockquote>
```

`code` 表示短代码片段，`pre` 保留空白和换行，二者经常组合展示多行代码。`kbd` 表示用户输入，`blockquote` 表示块级引用，`q` 表示行内引用。

| 标签 | 语义 | 适合场景 |
| --- | --- | --- |
| `code` | 代码片段 | 命令、变量、函数名 |
| `pre` | 预格式化文本 | 多行代码、日志片段 |
| `kbd` | 用户输入 | 快捷键、终端输入 |
| `blockquote` | 块级引用 | 引用说明、摘录 |
| `q` | 行内引用 | 短句引用 |

这些标签不负责语法高亮。高亮通常由 CSS 或前端代码完成，HTML 先负责把内容角色表达清楚。

多行代码通常用 `pre > code`，这样既保留换行和缩进，又表达内容是代码。不要把代码块直接放进普通段落里，否则空白会被折叠，复制体验和阅读体验都会变差。

技术文档里还经常会遇到“命令”“输出”“错误信息”这三类内容。命令适合用行内 `code`，终端输出和报错更适合放在 `pre` 里，必要时再在外层补一个说明句，告诉读者这一段是在什么条件下出现的。这样比把所有内容都放进一整块截图更利于搜索和复制。

## 列表结构

列表用于表达“同类项集合”。只要内容天然是一个个条目，就比连续的 `div` 更清楚。列表语义能告诉用户当前有多少项、每项在哪里，也更利于样式和脚本统一处理。

```html
<ul>
  <li>HTML</li>
  <li>CSS</li>
  <li>JavaScript</li>
</ul>

<ol>
  <li>搭建页面结构</li>
  <li>添加样式</li>
  <li>补充交互</li>
</ol>

<dl>
  <dt>HTML</dt>
  <dd>负责页面结构和语义。</dd>
</dl>
```

`ul` 用于无顺序集合，`ol` 用于步骤、排名、时间线这类顺序会影响理解的内容，`dl` 用于术语解释、属性说明、键值信息。

```html
<dl>
  <dt>charset</dt>
  <dd>声明文档字符编码。</dd>
  <dt>viewport</dt>
  <dd>控制移动端布局视口和缩放。</dd>
</dl>
```

列表不是只能显示圆点或数字。默认样式可以去掉，但结构不要丢：

```css
.nav-list {
  display: flex;
  gap: 16px;
  padding: 0;
  list-style: none;
}
```

| 结构 | 使用场景 | 判断标准 |
| --- | --- | --- |
| `ul` | 菜单、功能点、标签、卡片集合 | 顺序不改变含义 |
| `ol` | 操作步骤、排名、教程目录 | 顺序会影响理解 |
| `dl` | 术语解释、配置说明、元数据 | 名称与说明成对出现 |

列表也适合做导航和卡片集合。比如菜单项、商品卡片、搜索结果、文章目录都天然是一组同类项，即使最终视觉上是网格或横向排列，结构上仍然可以使用 `ul` / `ol`。

列表里也要区分“集合”和“描述”。如果一组内容只是多个彼此独立的卡片，用 `ul` 更自然；如果每一项都在回答同一个问题，例如“名称是什么、取值是什么”，`dl` 更合适；如果每一项的顺序不能打乱，例如教程步骤、内容目录、操作流程，就用 `ol`。这种判断比“看起来像不像列表”更重要。

## 区块容器

区块标签用于组织页面区域。`div` 是无语义容器，适合纯布局；`main`、`section`、`article`、`nav`、`header`、`footer` 等结构标签则表达内容角色。

```html
<main>
  <section>
    <h2>课程介绍</h2>
    <p>这里是课程摘要。</p>
  </section>

  <article>
    <h2>学习笔记</h2>
    <p>这是一篇可以独立阅读的内容。</p>
  </article>
</main>
```

#### 通用容器

`div` 适合做样式包裹、布局网格、脚本挂载点。它没有语义，所以不要用它替代按钮、链接、列表、标题、表格等原生结构。

#### 结构容器

`section` 应该有明确主题，通常配合标题；`article` 表示可独立分发或复用的内容；`main` 表示当前页面主体；`nav` 表示主要导航链接组。

| 标签 | 结构角色 | 简单判断 |
| --- | --- | --- |
| `div` | 通用容器 | 只是为了布局或样式 |
| `section` | 主题分区 | 能加一个概括标题 |
| `article` | 独立内容 | 单独拿出去仍成立 |
| `main` | 页面主体 | 当前页面最核心内容 |
| `nav` | 导航区域 | 一组重要跳转链接 |
| `header` / `footer` | 头尾信息 | 区块介绍、作者、版权、辅助链接 |

结构容器和 [[1.1.3 语义化|语义化]] 是同一条线：先用正确标签描述内容，再用 CSS 决定布局，不要反过来由视觉决定标签。

`section` 和 `div` 的边界可以用标题判断：如果这块内容能有一个合理标题，它更可能是 `section`；如果只是为了包一层样式、加背景或做网格布局，`div` 更合适。语义元素不是越多越好，选对比堆满更重要。

在组件化页面里，`main`、`section`、`article` 还常常和卡片、弹窗、面板一起出现。判断时不要只看视觉块，而要问它是不是页面主体、是不是可独立阅读、是不是只是主题分区。比如文章详情页适合 `article`，商品列表页的每一张卡片也可以是 `article`，而一个仅用于排版的容器就不必强行加语义。

## 链接

链接的核心语义是“导航到另一个资源”。`href` 是链接成立的关键，如果只是执行当前页面动作，应优先使用 `button`。

```html
<a href="/html">学习 HTML</a>
<a href="https://developer.mozilla.org/" target="_blank" rel="noopener noreferrer">
  打开 MDN
</a>
```

链接文本应该脱离上下文也能说明去向，“查看 HTML 表单示例”比“点击这里”更清楚。新窗口打开外链时，通常配合 `rel="noopener noreferrer"`，避免新页面通过 `window.opener` 影响原页面。

```html
<!-- 不推荐：链接文本缺少信息 -->
<a href="/forms">点击这里</a>

<!-- 推荐 -->
<a href="/forms">查看 HTML 表单示例</a>
```

`download` 可以提示浏览器下载资源，`target="_blank"` 可以新窗口打开，但它们都不应该滥用。用户是否离开当前页面、是否下载文件，都属于交互预期的一部分。

```html
<a href="/files/report.pdf" download>下载报告 PDF</a>
```

链接还要注意可读文本。自动化测试、屏幕阅读器和搜索引擎都会读链接文本，“点击这里”在脱离上下文时没有意义；“下载年度报告 PDF”就清楚得多。

链接不只是跳转页面，也可以是邮箱、电话、锚点和文件资源。`mailto:`、`tel:`、`#id`、下载链接都属于链接语义的自然扩展。真正需要警惕的是“长得像链接，但其实要做动作”的场景，这时通常应该换成按钮或拆成更清晰的交互。

```html
<a href="#comments">跳到评论区</a>
<a href="mailto:support@example.com">联系支持邮箱</a>
<a href="tel:+8613800138000">拨打客服电话</a>
```

锚点链接要求目标元素有对应 `id`；邮箱和电话链接在桌面端、移动端、不同应用环境里的表现可能不同，所以文案要让用户知道会发生什么。比如“拨打客服电话”比“联系我们”更明确。

## 图像

图像不仅是视觉资源，也会影响可访问性、布局稳定性和页面性能。

```html
<img
  src="/images/html-logo.png"
  alt="HTML 标志"
  width="160"
  height="160"
  loading="lazy"
/>
```

`alt` 描述图片在当前语境中的作用，不是机械重复文件名。装饰图可以用空 `alt=""`，让辅助技术跳过；承载信息的图片则必须提供等价文本。

| 图片类型 | `alt` 写法 | 示例 |
| --- | --- | --- |
| 信息图 | 描述关键信息 | `alt="移动端视口与布局视口示意图"` |
| 操作图标 | 描述动作 | `alt="搜索"` |
| 装饰背景 | 空文本 | `alt=""` |
| 商品图 | 描述对象 | `alt="黑色机械键盘正面图"` |

给图片写 `width` 和 `height` 可以帮助浏览器提前预留空间，减少布局跳动。非首屏图片可以考虑 `loading="lazy"`；首屏关键图不要盲目懒加载，否则可能拖慢最大内容绘制。

```html
<img
  src="/hero.webp"
  alt="课程首页主视觉"
  width="1200"
  height="630"
  fetchpriority="high"
/>
```

图像细节会继续进入 [[1.1.5 多媒体|多媒体]]，加载策略则会影响 [[1.4.7 页面加载|页面加载]] 和 [[6.2.6 图片优化|图片优化]]。

图片标签的关键是“当前语境”。同一张图在商品详情里可能需要描述商品，在背景装饰里可能应该空 `alt`，在按钮图标里则要表达动作。不要机械地把文件名塞进 `alt`。

如果页面需要在不同分辨率下适配清晰度，可以继续配合 `srcset` 和 `sizes`；如果需要优先加载首屏大图，再考虑 `fetchpriority`。这些写法都建立在“图片本身是内容的一部分”这个前提上，而不是单纯做装饰。图片是否该懒加载、是否该预留尺寸、是否该作为首屏关键资源，应该由页面角色决定。

```html
<img
  src="/covers/course-800.webp"
  srcset="/covers/course-400.webp 400w, /covers/course-800.webp 800w, /covers/course-1200.webp 1200w"
  sizes="(max-width: 600px) 100vw, 600px"
  alt="HTML 课程封面"
  width="800"
  height="450"
/>
```

`srcset` 负责告诉浏览器有哪些候选图片，`sizes` 负责告诉浏览器图片在不同视口下大约显示多宽。没有 `sizes` 时，浏览器很难准确选择资源，可能在小屏上下载过大的图。

## 交互入口

常见标签里最容易混淆的是 `a` 和 `button`。判断方式很简单：会改变当前位置或打开资源，用链接；在当前页面触发动作，用按钮。

```html
<a href="/settings">进入设置页</a>
<button type="button">打开设置弹窗</button>
```

按钮要注意 `type`。在表单里，`button` 默认可能参与提交；如果只是普通动作，应显式写 `type="button"`。

```html
<form>
  <button type="submit">提交</button>
  <button type="button">取消</button>
</form>
```

不要为了样式统一把所有交互都写成 `div`。原生链接和按钮已经带有键盘、焦点、语义和默认行为，重新模拟不仅麻烦，还容易破坏 [[1.1.7 无障碍|无障碍]]。

如果一个控件既能跳转又能执行动作，要先拆清交互意图。比如“查看详情”通常是链接，“收藏商品”通常是按钮，“提交搜索”可以是表单按钮。标签选错时，后面补事件和样式只是在修补错误语义。

在设计系统或组件库里，这个判断尤其重要。一个看起来完全相同的视觉块，底层可能分别是链接、按钮或菜单项；它们的键盘交互、默认行为和可访问名称都不一样。先定语义，再定样式，后面封装组件时才不会把一堆交互揉成一个万能 `div`。

```html
<!-- 跳转资源 -->
<a class="primary-action" href="/checkout">去结算</a>

<!-- 当前页面动作 -->
<button class="primary-action" type="button">加入购物车</button>
```

两者视觉上可以完全一致，但语义不能混用。用户长按、右键、新标签打开、回车触发、空格触发等行为，都来自元素本身的默认语义。

## 标签选择

选择标签时可以按这个顺序判断：

1. 这段内容是标题、段落、列表、引用、链接、按钮，还是普通容器。
2. 是否有原生标签能表达这个角色。
3. 默认行为是否符合用户预期。
4. 是否需要额外的属性补充语义、目标、尺寸或安全边界。
5. 样式能否通过 CSS 实现，而不是换错标签。

HTML 的基础标签不是“记住越多越好”，而是要知道每个标签的角色边界。标签选对后，CSS、JavaScript、SEO、无障碍和自动化测试都会更自然。

学习标签时可以少背默认样式，多记角色边界：标题组织结构，段落承载正文，列表表达集合，链接导航资源，按钮触发动作，表单采集输入，图片提供视觉或信息。这个判断比记住几十个标签名更有用。

如果真要做日常检索，可以按“结构类、文本类、交互类、媒体类”去记，而不是按默认外观去背。结构类解决页面骨架，文本类解决阅读，交互类解决操作，媒体类解决信息承载。这个分法比单纯列标签名更容易在实际写页面时想起来。
