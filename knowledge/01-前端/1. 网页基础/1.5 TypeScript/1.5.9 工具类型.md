## 类型转换

TypeScript 工具类型用于基于已有类型生成新类型。它们不是运行时代码，而是类型层面的转换工具。

```typescript
type User = {
  id: string;
  name: string;
  age: number;
};

type UserDraft = Partial<User>;
```

工具类型的价值在于减少重复声明，让类型关系保持同步。字段变化时，派生类型会自动跟着变化。

工具类型本质上是“类型复用的计算工具”。它适合从同一个领域模型派生表单值、接口 payload、展示模型、权限映射等结构，避免一处字段改名后，多份手写类型悄悄漂移。

```typescript
type User = {
  id: string;
  name: string;
  email: string;
  passwordHash: string;
  createdAt: string;
};

type PublicUser = Omit<User, 'passwordHash'>;
type UserCard = Pick<User, 'id' | 'name'>;
type UserPatch = Partial<Pick<User, 'name' | 'email'>>;
```

但工具类型不是越多越好。如果一个类型需要嵌套三四层工具才能读懂，往往说明它应该被单独命名，或者业务模型本身需要拆开。

## `Partial`

`Partial<T>` 会把对象类型的所有属性变成可选。

```typescript
type UserPatch = Partial<User>;

function updateUser(id: string, patch: UserPatch) {
  return request(`/users/${id}`, {
    method: 'PATCH',
    body: JSON.stringify(patch),
  });
}
```

它适合更新接口、表单草稿、局部配置。不要滥用于所有业务对象，否则原本必须存在的字段会变得不可信。

`Partial` 只会处理第一层属性，不会递归处理深层对象。

```typescript
type Settings = {
  theme: {
    color: string;
    fontSize: number;
  };
};

type SettingsPatch = Partial<Settings>;
```

这里 `theme` 可以整体缺失，但一旦传了 `theme`，里面仍然需要完整的 `color` 和 `fontSize`。如果业务需要深层局部更新，可以单独设计 patch 类型，或者谨慎使用自定义 `DeepPartial`。深层可选会让数据结构非常松，适合测试数据和配置覆盖，不一定适合正式接口。

## `Required`

`Required<T>` 会把所有可选属性变成必选。

```typescript
type Config = {
  apiBase?: string;
  timeout?: number;
};

type ResolvedConfig = Required<Config>;
```

它适合默认值合并后的配置类型。

```typescript
function resolveConfig(config: Config): ResolvedConfig {
  return {
    apiBase: config.apiBase ?? '/api',
    timeout: config.timeout ?? 8000,
  };
}
```

`Required` 很适合表达“输入可以省略，解析后一定完整”。这类类型经常出现在组件 props 默认值、SDK 初始化配置、构建工具配置里。

```typescript
type ButtonProps = {
  size?: 'small' | 'medium' | 'large';
  disabled?: boolean;
};

type ResolvedButtonProps = Required<ButtonProps>;

function resolveButtonProps(props: ButtonProps): ResolvedButtonProps {
  return {
    size: props.size ?? 'medium',
    disabled: props.disabled ?? false,
  };
}
```

不要把 `Required` 用在外部输入上假装字段已经存在。它只改变类型，不会自动填默认值。必须先有运行时代码把值补齐，再把结果标成完整类型。

## `Pick` 与 `Omit`

`Pick<T, K>` 从对象类型中挑选部分字段，`Omit<T, K>` 排除部分字段。

```typescript
type UserCard = Pick<User, 'id' | 'name'>;
type CreateUserPayload = Omit<User, 'id'>;
```

`Pick` 适合组件只需要部分字段的场景；`Omit` 适合创建、复制、隐藏敏感字段。

```typescript
function renderUserCard(user: Pick<User, 'id' | 'name'>) {
  return `${user.id}: ${user.name}`;
}
```

`Pick` 和 `Omit` 的选择可以看稳定性：当你只需要少数字段时，用 `Pick` 更安全；当你需要“大部分字段，只排除几个”时，用 `Omit` 更省事。敏感字段过滤通常更推荐显式 `Pick`，因为后续新增字段不会自动暴露出去。

```typescript
type SafeUserResponse = Pick<User, 'id' | 'name' | 'email'>;
```

如果用 `Omit<User, 'passwordHash'>`，将来 `User` 新增 `phone`、`address`、`token` 等字段时，它们会自动进入返回类型。自动同步有时是优点，有时是风险，关键看这个派生类型是否代表对外边界。

## `Record`

`Record<K, T>` 用于声明键和值的映射关系。

```typescript
type Role = 'admin' | 'editor' | 'guest';

const permissions: Record<Role, string[]> = {
  admin: ['create', 'delete'],
  editor: ['create'],
  guest: [],
};
```

`Record` 比普通对象更能约束键集合。新增角色时，如果忘记补权限，编译器会提醒。

`Record` 常和字面量联合、`as const`、`keyof typeof` 配合使用，把配置对象变成类型来源。

```typescript
const tabs = ['home', 'profile', 'settings'] as const;

type TabKey = (typeof tabs)[number];

const tabLabels: Record<TabKey, string> = {
  home: '首页',
  profile: '资料',
  settings: '设置',
};
```

如果键集合来自接口数据或用户输入，`Record<string, T>` 只能说明值的类型，不能说明某个 key 一定存在。开启 `noUncheckedIndexedAccess` 后，动态读取会得到 `T | undefined`，更符合运行时事实。

```typescript
const label = tabLabels['home'];
```

## `ReturnType`

`ReturnType<T>` 可以提取函数返回值类型，适合从工厂函数、hook、工具函数中复用返回类型。

```typescript
function createUserStore() {
  return {
    user: null as null | User,
    setUser(user: User) {
      this.user = user;
    },
  };
}

type UserStore = ReturnType<typeof createUserStore>;
```

当返回结构由实现决定，且外部需要复用时，`ReturnType` 能避免手写重复类型。

`ReturnType` 特别适合工厂函数和 hook。很多时候实现里的返回对象会随着需求增长而变化，手写返回类型容易落后。

```typescript
function usePagination(total: number) {
  return {
    page: 1,
    pageSize: 20,
    total,
    next() {},
    prev() {},
  };
}

type PaginationState = ReturnType<typeof usePagination>;
```

如果返回值是对外公共 API，是否使用 `ReturnType` 要看稳定性。内部复用可以让实现驱动类型；对外发布的库 API 则常常需要显式返回类型，避免内部实现变化意外影响使用者。

## `Parameters`

`Parameters<T>` 可以提取函数参数元组。

```typescript
function track(eventName: string, payload: Record<string, unknown>) {}

type TrackArgs = Parameters<typeof track>;
```

它适合包装函数、事件转发和中间层代理。

```typescript
function safeTrack(...args: Parameters<typeof track>) {
  try {
    track(...args);
  } catch {
    // ignore
  }
}
```

`Parameters` 会保留参数元组，包括可选参数和剩余参数。它适合做日志包装、权限包装、错误兜底、节流防抖等高阶函数。

```typescript
function withLog<T extends (...args: never[]) => unknown>(fn: T) {
  return (...args: Parameters<T>): ReturnType<T> => {
    console.log('call with', args);
    return fn(...args) as ReturnType<T>;
  };
}
```

这类高阶函数一旦写对，调用方能保持原函数参数提示。但如果泛型约束写得过宽或过窄，也会让类型丢失。包装函数时要优先保留原函数的参数和返回值，而不是把它们改成 `any[]` 和 `unknown`。

## `Exclude` 与 `Extract`

`Exclude<T, U>` 从联合类型中排除成员，`Extract<T, U>` 从联合类型中提取成员。

```typescript
type Status = 'idle' | 'loading' | 'success' | 'error';

type FinalStatus = Exclude<Status, 'idle' | 'loading'>;
type ErrorStatus = Extract<Status, 'error'>;
```

它们适合状态机、权限枚举和事件类型拆分。

在可辨识联合类型里，`Extract` 可以按字段提取某一种分支，比手写重复类型更稳。

```typescript
type RequestState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: string[] }
  | { status: 'error'; error: Error };

type SuccessState = Extract<RequestState, { status: 'success' }>;
type FailedState = Extract<RequestState, { status: 'error' }>;
```

`Exclude` 则适合表达“除了某些状态之外都可以”。比如一个按钮只在非加载状态可点击，可以从联合类型里排除 `loading`。这类写法会随着联合成员变化自动更新，但要给派生类型起清楚名字，否则阅读者很难一眼看出业务含义。

## `NonNullable`

`NonNullable<T>` 会排除 `null` 和 `undefined`。

```typescript
type MaybeUser = User | null | undefined;
type SafeUser = NonNullable<MaybeUser>;
```

它适合类型转换，但运行时仍然要判空。工具类型不能替代真实数据校验。

`NonNullable` 常用于在已经做过过滤后表达结果类型。比如数组里可能有空值，过滤后再进入渲染逻辑。

```typescript
const users = [
  { id: 'u1', name: 'Ada' },
  null,
  undefined,
];

function isPresent<T>(value: T): value is NonNullable<T> {
  return value !== null && value !== undefined;
}

const safeUsers = users.filter(isPresent);
```

如果只是写 `users.filter(Boolean)`，运行时能过滤一些假值，但 TypeScript 不一定能得到足够精确的类型，而且会把空字符串、`0` 这类合法值也过滤掉。类型守卫能把运行时行为和类型结果对应起来。

## 组合使用

工具类型可以组合，但不要追求炫技。类型表达应该帮助理解，而不是让同事读不懂。

```typescript
type PublicUser = Pick<User, 'id' | 'name'>;
type UserUpdate = Partial<Omit<User, 'id'>>;
```

工具类型和 [[1.5.2 类型推断|类型推断]] 关系紧密：很多高级推断都建立在已有类型的变换上。写类型时，先表达业务边界，再考虑抽象复用。

组合工具类型时，要注意“派生方向”。比如从数据库实体派生前端展示类型时，可以用 `Pick`；从表单值派生提交 payload 时，可能需要转换而不是简单 `Omit`。如果两个结构只是长得像，但语义不同，不要强行从一个派生另一个。

```typescript
type UserEntity = {
  id: string;
  firstName: string;
  lastName: string;
  birthday: string;
};

type UserViewModel = {
  id: string;
  displayName: string;
  ageText: string;
};
```

这种情况下，`UserViewModel` 不应该用工具类型硬凑，因为它不是字段裁剪，而是业务转换结果。工具类型擅长维护“同源结构”的关系，不擅长表达“经过业务计算后的新模型”。

内置工具类型背后很多都依赖映射类型、条件类型和 `infer`。日常使用不必一开始就展开实现，但理解它们是类型层面的计算，有助于判断边界：类型能帮你减少重复，不能替你校验数据、不能自动生成运行时代码，也不能替代清晰的模型命名。
