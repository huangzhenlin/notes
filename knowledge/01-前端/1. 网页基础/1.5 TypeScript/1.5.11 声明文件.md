## 声明文件作用

声明文件 `.d.ts` 用来描述已经存在的 JavaScript 代码、第三方库或者运行时全局对象的类型外形。它只提供类型信息，不会生成运行时代码。

```typescript
declare function track(eventName: string, payload?: Record<string, unknown>): void;
```

它最常见的价值有三类：给老 JS 项目补类型、给没有类型的第三方包补类型、给运行时全局变量补类型。它和 [[1.5.1 基础类型|基础类型]]、[[1.5.6 接口类型|接口类型]]、[[1.5.9 工具类型|工具类型]] 一起，构成了“把真实世界的 JS 代码翻译成类型系统能理解的形式”的那部分能力。

#### 全局声明

全局声明会把类型暴露到整个项目作用域，常用于浏览器全局对象、环境变量或第三方脚本注入的内容。

```typescript
declare global {
  interface Window {
    __APP_VERSION__: string;
  }
}

export {};
```

`export {}` 的作用是让当前文件变成模块，避免全局声明无意污染别的文件。全局声明要尽量克制，只放真正共享的运行时全局，否则项目会越来越像“到处都能用，但没人知道从哪来的”。

浏览器项目里，全局声明最常见的是构建时注入的变量、第三方脚本挂到 `window` 上的 SDK、或者框架约定的环境对象。写声明时要和真实注入时机对齐：如果脚本可能还没加载完成，类型上就不应该声明成永远存在。

```typescript
declare global {
  interface Window {
    analytics?: {
      track(event: string, payload?: Record<string, unknown>): void;
    };
  }
}

export {};
```

这里把 `analytics` 写成可选属性，是为了提醒调用方先判断再使用。声明文件不应该把不稳定的运行时事实伪装成稳定 API，否则类型越“舒服”，运行时越容易报错。

```typescript
window.analytics?.track("page_view", {
  path: location.pathname,
});
```

如果确实由 HTML 模板保证脚本先加载，也可以在初始化层做一次显式校验，再把不确定性挡在应用入口外面。这样比在所有业务代码里到处写非空断言更集中。

#### 模块声明

模块声明描述一个可以被 `import` 的模块，即使这个模块本身没有现成的类型文件。

```typescript
declare module "some-untyped-module" {
  export function createClient(baseUrl: string): {
    get(path: string): Promise<unknown>;
  };
}
```

这类声明通常用于第三方库缺少类型、私有包暂时没发类型、或者迁移过程里先补最小可用边界。写法上要优先保证 API 轮廓准确，而不是急着把所有内部细节都翻译出来。

模块声明不要一上来写成 `any`。`any` 虽然能让报错消失，但也会让所有调用方失去保护。更好的过渡方式是先用 `unknown` 接住不确定返回值，再给稳定参数和稳定方法补类型。

```typescript
declare module "legacy-report-sdk" {
  export interface ReportClient {
    send(name: string, payload?: Record<string, unknown>): Promise<void>;
    getConfig(): unknown;
  }

  export function createReportClient(appId: string): ReportClient;
}
```

当第三方库有默认导出、命名导出和 CommonJS 混用时，声明要贴近真实导入方式。比如运行时代码是 `module.exports = createClient`，项目里却想用 `import createClient from "pkg"`，就要同时确认 `esModuleInterop`、构建工具和声明写法是否匹配。类型声明能描述 API，但不能改变模块系统的真实行为。

静态资源导入也常靠模块声明补类型。比如 Vite 项目里导入 SVG、CSS Module、图片时，运行时由构建工具处理，TypeScript 需要知道导入结果是什么。

```typescript
declare module "*.module.css" {
  const classes: Record<string, string>;
  export default classes;
}

declare module "*.svg?component" {
  import type { ComponentType, SVGProps } from "react";

  const Component: ComponentType<SVGProps<SVGSVGElement>>;
  export default Component;
}
```

这类声明要和构建插件保持一致。如果插件实际返回 URL，声明却写成组件，代码就会在运行时出错。

#### 类型发布

发布 npm 包时，声明文件最好和运行时代码一起发布，并且入口、子路径、导出路径都保持一致。

```json
{
  "name": "@acme/sdk",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts"
}
```

如果包暴露多个入口，还要保证对应子路径也能找到声明文件。很多“包能跑但没提示”的问题，本质上就是运行时入口和类型入口没有对齐。

现代包经常通过 `exports` 控制入口，这时类型入口也要放进对应条件里，不能只写顶层 `types`。如果用户通过 `@acme/sdk/react` 导入，而 `exports` 没有暴露这个子路径的类型，编辑器就会找不到声明。

```json
{
  "name": "@acme/sdk",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    },
    "./react": {
      "types": "./dist/react.d.ts",
      "import": "./dist/react.js"
    }
  }
}
```

对外发布的声明应该尽量表达“公共契约”，而不是泄露内部实现。比如内部用了很多辅助类型，可以在生成声明后检查是否把内部路径暴露给使用者。如果用户的类型提示里出现 `dist/internal/*`，说明包的类型边界可能需要重新整理。

#### 外部类型

外部库的类型来源大体有三种：包内自带、`@types` 社区包、自己编写。

| 来源 | 适合场景 | 特点 |
| --- | --- | --- |
| 包内自带 | 现代库、维护中的官方库 | 运行时和类型同仓库 |
| `@types` | 老库、第三方库 | 社区维护，覆盖面广 |
| 自己编写 | 私有库、过渡期项目 | 最贴近业务，但维护成本高 |

一般顺序是先找包内类型，再找 `@types`，最后才自己补。这样最省成本，也最不容易和库的真实行为脱节。

`types` 和 `typeRoots` 会影响全局类型的引入范围。默认情况下，TypeScript 会自动查找 `node_modules/@types` 下的类型；一旦配置了 `types`，就变成白名单，只引入列出的类型包。这在测试环境里很有用，可以避免 `jest`、`vitest`、`node` 的全局类型互相污染。

```jsonc
{
  "compilerOptions": {
    "types": ["vitest/globals", "node"]
  }
}
```

`typeRoots` 更底层，通常只在团队有统一的内部类型目录时使用。它配置不当很容易让默认的 `@types` 查找失效，所以普通项目优先用 `types` 或直接把声明文件放进 `include` 覆盖范围。

```text
src/
  env.d.ts
types/
  legacy-report-sdk.d.ts
```

如果声明文件没有生效，排查顺序通常是：文件是否被 `include` 覆盖、是否含有顶层 `export` 导致作用域变化、模块名是否和 import 完全一致、`types` 白名单是否排除了它、编辑器是否读取了正确的 `tsconfig`。

#### 生成方式

对于已有 JS 项目，可以通过编译或 JSDoc 逐步生成 `.d.ts`，适合迁移期和库项目。

```json
{
  "compilerOptions": {
    "declaration": true,
    "emitDeclarationOnly": true,
    "allowJs": true
  }
}
```

```typescript
/**
 * @param {string} name
 * @returns {number}
 */
export function lengthOfName(name) {
  return name.length;
}
```

自动生成的声明通常只是起点，不是终点。它可能过宽，也可能把内部实现泄露出去，所以发布前最好检查一遍 API 是否真的适合对外公开。

JSDoc 迁移的价值在于“不立刻把所有 JS 改成 TS，也能先获得类型反馈”。这对老项目特别友好：先给关键函数写参数和返回值，再逐步打开 `checkJs`，最后再迁移核心模块。

```jsonc
{
  "compilerOptions": {
    "allowJs": true,
    "checkJs": true,
    "declaration": true,
    "emitDeclarationOnly": true
  },
  "include": ["src/**/*.js"]
}
```

```javascript
/**
 * @typedef {{ id: string, name: string }} User
 */

/**
 * @param {User[]} users
 * @param {string} id
 * @returns {User | undefined}
 */
export function findUser(users, id) {
  return users.find((user) => user.id === id);
}
```

这类生成适合公共工具函数、SDK、组件库迁移。业务页面代码如果强行生成声明，收益通常不高，因为页面更多是应用入口，不是稳定 API。

#### 发布入口

声明文件发布时，要确保入口文件、子路径、导出格式和 `types` 指向一致。

```typescript
// index.d.ts
export * from "./client";
export * from "./helpers";
```

一个好的声明文件应该做到三件事：让用户知道有哪些 API、让编辑器能给出真实提示、尽量贴近运行时行为而不过度暴露内部实现。它和 [[1.5.2 类型推断|类型推断]]、[[1.5.5 类型收窄|类型收窄]] 配合起来，才能让外部调用在写代码阶段就尽量接近真实运行结果。

声明文件维护时有一个很实用的原则：类型越靠近真实运行边界，越应该保守；类型越靠近内部实现，越可以精确。比如接口响应、浏览器全局对象、第三方 SDK 返回值，最好先用 `unknown`、可选字段、联合类型表达不确定性；而内部纯函数、组件 props、工具方法，则可以用泛型和工具类型表达更精细的约束。

```typescript
// 对外入口：保守描述外部输入
export interface RequestOptions {
  headers?: Record<string, string>;
  body?: unknown;
}

// 内部实现：可以更精确地约束状态
export interface NormalizedRequestOptions {
  headers: Record<string, string>;
  body: string | FormData | undefined;
}
```

声明文件不是“让 TypeScript 不报错”的补丁，而是运行时契约的文字化。写得过宽，调用方失去保护；写得过窄，正常用法会被误伤；写得和运行时不一致，最危险，因为它会给团队一种已经安全的错觉。
