## 断言含义

类型断言是告诉 TypeScript：“我比你更清楚这个值的类型”。它只影响编译期，不会改变运行时值。

```typescript
const input = document.querySelector("input") as HTMLInputElement;
input.value = "hello";
```

如果实际查到的是 `null`，或者根本不是输入框，运行时照样会出错。断言不是类型转换，也不是安全检查，只是让编译器放行。

#### as 语法

现代 TypeScript 更推荐 `as`。

```typescript
const value = unknownValue as string;
```

在 `.tsx` 文件里，尖括号断言容易和 JSX 冲突，所以通常统一使用 `as`。写法统一之后，团队里的代码会少很多语义歧义。

`as` 只能在类型系统允许的范围内移动。比如把 `string | number` 断言成 `string` 可以，因为它们有重叠；把 `string` 直接断言成完全无关的对象类型，TypeScript 通常会提醒“如果你确定，先转成 `unknown`”。这个提醒不是语法刁难，而是在告诉你：这已经不是普通断言，而是在主动绕开类型系统。

```typescript
type User = {
  id: string;
  name: string;
};

const raw = '{"id":"u1","name":"Ada"}';
const user = JSON.parse(raw) as User;
```

上面这段代码很常见，但它没有验证 JSON 结构。`JSON.parse` 返回 `any`，`as User` 只是让后续访问看起来安全。更稳的方式是在解析后做结构判断，或者用运行时 schema 工具统一校验。类型断言适合跨过编译器看不见的小沟，不适合跨过外部数据这条河。

#### 空值断言

非空断言 `!` 用来告诉编译器某个值不是 `null` 或 `undefined`。

```typescript
const app = document.querySelector("#app")!;
```

它很方便，但也最容易埋雷。只有在你能确定运行时一定存在时才该用，比如页面固定挂载点、框架初始化后已保证存在的引用。否则更稳妥的方式还是显式判断。

```typescript
const app = document.querySelector("#app");

if (!app) {
  throw new Error("missing app root");
}
```

非空断言还常见于类属性初始化。开启 `strictPropertyInitialization` 后，如果属性不是在构造函数里赋值，TypeScript 会要求说明它什么时候有值。

```typescript
class DialogController {
  private root!: HTMLElement;

  mount(root: HTMLElement) {
    this.root = root;
  }

  open() {
    this.root.hidden = false;
  }
}
```

这段代码能通过检查，但调用者如果在 `mount` 前调用 `open`，仍然会运行时报错。更可靠的设计是把依赖放进构造函数，或者在方法里显式判断初始化状态。非空断言解决的是“编译器不知道”，不是“程序一定正确”。

```typescript
class SafeDialogController {
  constructor(private readonly root: HTMLElement) {}

  open() {
    this.root.hidden = false;
  }
}
```

#### 双重断言

双重断言常见写法是 `value as unknown as Target`。

```typescript
const user = value as unknown as User;
```

它能绕过很多限制，但也意味着你主动放弃了大部分类型保护。除非是在处理非常特殊的边界，比如历史遗留数据、极少数第三方类型缺口，否则不应该把它当成默认方案。

双重断言真正适合的场景通常很窄：库类型声明比真实版本滞后、框架内部泛型暂时无法表达、迁移期间需要把历史对象接到新类型边界上。即便使用，也最好把它封装在一个小函数里，把不安全集中起来，而不是散落在业务代码里。

```typescript
type LegacyUser = {
  user_id: string;
  user_name: string;
};

type User = {
  id: string;
  name: string;
};

function normalizeUser(value: LegacyUser): User {
  return {
    id: value.user_id,
    name: value.user_name,
  };
}
```

如果可以通过转换函数解决，就不要用 `as unknown as User`。转换函数多几行代码，但它把字段映射、默认值、兼容逻辑都写在运行时，后续接口变更时也更容易定位。

#### DOM 断言

DOM API 返回值往往比较宽，比如 `querySelector` 可能返回 `Element | null`。这时要先确认空值，再缩窄到具体元素类型。

```typescript
const button = document.querySelector("button");

if (button instanceof HTMLButtonElement) {
  button.disabled = true;
}
```

这种写法比直接断言更稳，因为它同时包含运行时检查和类型收窄。对于表单元素、SVG 元素、列表项这类场景，优先用显式判断会更可靠。

如果页面结构由当前组件完全控制，直接断言可以接受；如果选择器依赖后端模板、CMS 内容、第三方脚本或用户输入，就应该优先做检查。DOM 断言的风险不在语法，而在页面结构经常比类型假设更脆。

```typescript
function getRequiredElement<T extends Element>(
  selector: string,
  constructor: { new (...args: never[]): T }
): T {
  const element = document.querySelector(selector);

  if (!(element instanceof constructor)) {
    throw new Error(`Missing element: ${selector}`);
  }

  return element;
}

const form = getRequiredElement("#login-form", HTMLFormElement);
```

这类辅助函数把“查询失败应该怎么处理”固定下来，比每个地方手写 `as HTMLFormElement` 更容易维护。需要注意的是，`instanceof` 对跨 iframe 的 DOM 对象可能有边界问题，普通单页面应用里通常足够可靠。

#### unknown 边界

外部输入应该先落到 `unknown`，再通过判断变成具体类型，而不是直接断言成业务对象。

```typescript
function isUser(value: unknown): value is { id: string; name: string } {
  return (
    typeof value === "object" &&
    value !== null &&
    "id" in value &&
    "name" in value
  );
}

const data: unknown = await response.json();

if (isUser(data)) {
  console.log(data.name);
}
```

接口响应、`localStorage`、URL 参数、`postMessage`、第三方 SDK 返回值都属于这类边界。先接住不确定性，再通过守卫或校验收窄，通常比一开始就断言成业务类型更安全。

类型守卫要检查到业务真正依赖的字段，而不是只检查“看起来像对象”。例如页面只展示用户名，检查 `name` 也许够用；如果后续要拿 `id` 调接口，就必须同时检查 `id`。守卫的精度应该跟使用场景匹配。

```typescript
type User = {
  id: string;
  name: string;
  roles: string[];
};

function isStringArray(value: unknown): value is string[] {
  return Array.isArray(value) && value.every((item) => typeof item === "string");
}

function isUser(value: unknown): value is User {
  if (typeof value !== "object" || value === null) {
    return false;
  }

  const record = value as Record<string, unknown>;

  return (
    typeof record.id === "string" &&
    typeof record.name === "string" &&
    isStringArray(record.roles)
  );
}
```

当校验逻辑变复杂时，可以用运行时 schema 库把检查集中化。TypeScript 的类型在编译后会消失，所以凡是来自网络、存储、跨窗口消息的值，都需要运行时证据，而不是只需要一个漂亮的类型名字。

#### satisfies

`satisfies` 用来检查值是否满足某个类型，同时保留更具体的字面量信息。

```typescript
const routes = {
  home: "/",
  detail: "/detail/:id",
} satisfies Record<string, string>;
```

它适合配置对象、映射表和常量表。和 `as` 相比，`satisfies` 更像“校验是否合格”，而不是“强行规定成某个类型”。在很多场景里，它其实比断言更适合表达意图。

`satisfies` 的优势在路由表、权限表、主题 token、接口映射这类配置里很明显。它既能发现缺字段、错字段，又不会把字面量全部抹平成宽类型。

```typescript
type RouteConfig = {
  path: string;
  auth: "public" | "private";
};

const routes = {
  home: { path: "/", auth: "public" },
  profile: { path: "/profile", auth: "private" },
} satisfies Record<string, RouteConfig>;

type RouteName = keyof typeof routes;
```

如果写成 `as Record<string, RouteConfig>`，`home`、`profile` 这些具体键名和更细的字面量信息更容易被抹掉。`satisfies` 不会改变表达式本身的推断结果，因此适合“检查结构，但保留具体信息”的场景。

`as const` 也是断言家族里常见的一种，它会把对象或数组尽量收窄成只读字面量。

```typescript
const statusList = ["idle", "loading", "success", "error"] as const;

type Status = (typeof statusList)[number];
```

`as const` 适合稳定常量，不适合后续还要频繁修改的对象。它会让属性变成只读，数组变成只读元组，因此更像“把配置冻结成类型来源”。

#### 使用边界

类型断言适合补足 TypeScript 无法推断但开发者能确认的边界，不适合掩盖模型设计问题。

| 场景 | 建议 |
| --- | --- |
| 固定 DOM 容器 | 可用非空断言或显式判断 |
| 外部 JSON | 用 `unknown` + 类型守卫 |
| 配置常量 | 优先 `satisfies` |
| 推断不出来的小范围边界 | 可用窄断言 |
| 大面积 `any` 转业务类型 | 尽量避免 |

断言和 [[1.5.5 类型收窄|类型收窄]] 是互补关系：收窄负责证明，断言负责在你已经知道答案时告诉编译器答案是什么。前者更安全，后者更直接，真正好的代码通常先想收窄，实在不行再断言。

判断是否该用断言，可以先问三个问题：这个值是否来自外部边界、是否能用运行时判断证明、断言失败后是否会造成明显后果。来自外部边界且失败后影响大的值，不应该直接断言；来自内部稳定结构、编译器只是推断不到的值，可以局部断言。

```typescript
function assertUser(value: unknown): asserts value is User {
  if (!isUser(value)) {
    throw new Error("Invalid user payload");
  }
}

const payload: unknown = await response.json();
assertUser(payload);

console.log(payload.roles.join(","));
```

断言函数 `asserts value is User` 适合入口校验、测试工具、框架适配层。它的语义是“如果函数正常返回，后面的代码可以认为类型成立”。这比在业务深处反复写 `as User` 更清楚，也更容易统一错误处理。

在代码评审里，看到断言不要只问“能不能编译”，还要问“为什么编译器不知道”“有没有运行时证据”“能不能把不确定性收口到边界层”。好的断言是小范围的、有理由的、靠近边界的；坏的断言则是大面积的、为了消除报错的、把真实问题藏起来的。
