## 对象结构

`interface` 最常见的用途是描述对象形状。它适合 API 入参、组件 props、服务对象、领域实体、配置项这类结构稳定、名字重要的对象。

```typescript
interface User {
  id: string;
  name: string;
  age: number;
}

const user: User = {
  id: 'u1',
  name: 'Ada',
  age: 28,
};
```

TypeScript 关注的是结构兼容，而不是声明名本身。只要对象具备所需字段，就可以满足接口要求。

```typescript
function printUser(user: User) {
  return `${user.name} (${user.age})`;
}

printUser({ id: 'u1', name: 'Ada', age: 28 });
```

接口的可读性好，适合给团队协作中的公共结构命名。

结构兼容也意味着“额外字段”在不同位置会有不同表现。对象字面量直接传参时，TypeScript 会做额外属性检查；先赋值给变量再传入，则会按结构兼容判断。

```typescript
interface User {
  id: string;
  name: string;
}

function saveUser(user: User) {}

saveUser({
  id: 'u1',
  name: 'Ada',
  role: 'admin',
});

const admin = {
  id: 'u1',
  name: 'Ada',
  role: 'admin',
};

saveUser(admin);
```

第一种写法会提醒 `role` 不在 `User` 里，因为对象字面量很可能是调用处写错字段；第二种写法允许通过，因为 `admin` 至少具备 `User` 所需结构。理解这一点后，就不会误以为 TypeScript 的对象类型是“精确对象类型”。如果要表达严格白名单，通常需要借助泛型约束、校验函数或 lint 规则。

## 可选属性

属性后加 `?` 表示可选。它适合字段可能不存在的场景，例如后端字段渐进上线、表单草稿、局部配置。

```typescript
interface Product {
  id: string;
  title: string;
  description?: string;
}

const text = product.description ?? '暂无描述';
```

如果字段一定存在，只是值可能为空，应写成 `string | null` 或 `string | undefined`，语义更清楚。

```typescript
interface UserProfile {
  nickname: string | null;
}
```

可选属性和空值属性不要混用，否则调用方会多判断一层。

开启 `exactOptionalPropertyTypes` 后，可选属性会更接近“属性可以不存在”，而不是“属性可以是 `undefined`”。这对接口设计很重要：补丁对象里 `nickname?: string` 可以表示“不修改昵称”，而 `nickname: string | null` 可以表示“明确清空昵称”。

```typescript
interface UserPatch {
  nickname?: string;
  avatarUrl?: string | null;
}

function applyPatch(userId: string, patch: UserPatch) {
  if ('nickname' in patch) {
    // 调用方显式传入了 nickname
  }

  if (patch.avatarUrl === null) {
    // 明确删除头像
  }
}
```

接口字段设计最好提前区分三种状态：不存在、存在但为空、存在且有值。后端 API、表单草稿、缓存数据里，这三种状态常常代表完全不同的业务含义。

## 只读属性

`readonly` 表示属性不能被重新赋值，适合配置、实体标识、路由信息、不可变标记。

```typescript
interface RouteConfig {
  readonly path: string;
  readonly title: string;
}
```

`readonly` 是类型层面的约束，不等于运行时冻结。

```typescript
interface AppState {
  readonly user: {
    name: string;
  };
}
```

如果要表达深层不可变，需要继续使用只读数组、只读对象或状态管理约束。

`readonly` 更适合表达“调用方不应该改”，而不是表达“对象永远不会变”。比如组件 props、路由配置、领域实体 id 可以只读；但如果对象内部仍然被状态管理库更新，类型上只读并不会阻止底层引用变化。

```typescript
interface MenuItem {
  readonly id: string;
  readonly children: readonly MenuItem[];
}

const menus: readonly MenuItem[] = [
  {
    id: 'home',
    children: [],
  },
];
```

只读数组没有 `push`、`splice` 这类修改方法，适合配置表和常量列表。真正需要运行时不可变时，还要配合 `Object.freeze`、不可变数据结构或框架状态更新规范。

## 函数接口

接口也可以描述函数形状。当函数本身还带属性时，接口比普通函数类型更方便。

```typescript
interface Validator {
  (value: string): string | null;
}

const validateEmail: Validator = (value) => {
  return value.includes('@') ? null : '邮箱格式不正确';
};
```

```typescript
interface RequestClient {
  (url: string): Promise<unknown>;
  baseURL: string;
}
```

这种写法适合“既是函数，又有静态属性”的工具对象。如果没有属性，普通函数类型往往更轻。

函数接口还可以表达可调用对象的多种签名，但要谨慎使用。比如一个请求客户端既可以直接请求 URL，也可以通过 `.get`、`.post` 方法发请求。

```typescript
interface HttpClient {
  <T>(url: string): Promise<T>;
  get<T>(url: string): Promise<T>;
  post<TBody, TResult>(url: string, body: TBody): Promise<TResult>;
}
```

这类接口适合 SDK、插件系统、可扩展工具对象。普通业务函数如果没有额外属性，用 `type Handler = (event: Event) => void` 更直观。

## 索引签名

索引签名用于描述动态 key，适合字典、缓存、错误映射、国际化文案等键名不固定的对象。

```typescript
interface Dictionary {
  [key: string]: string;
}

const messages: Dictionary = {
  required: '必填',
  email: '邮箱格式不正确',
};
```

索引签名会放宽对象结构。能枚举具体 key 时，优先使用联合类型或 `Record`。

```typescript
type ErrorCode = 'required' | 'email';
type ErrorMessages = Record<ErrorCode, string>;
```

如果同一个对象既有固定字段又有索引签名，要注意固定字段类型必须兼容索引签名。

索引签名会影响所有同类 key。下面这个例子会出问题，因为 `id` 也是字符串 key，它的类型必须兼容索引签名的值类型。

```typescript
interface BadMap {
  id: number;
  [key: string]: string;
}
```

更合理的做法是把固定字段和动态字段拆开，避免动态结构污染核心结构。

```typescript
interface FormState {
  id: number;
  fields: Record<string, string>;
}
```

动态 key 如果有固定集合，优先用联合类型配合 `Record`；只有键名真的无法枚举时，再使用索引签名。这样能避免把“所有字符串都合法”扩得太开。

## 接口继承

接口可以继承接口，用于扩展对象结构。

```typescript
interface Entity {
  id: string;
  createdAt: string;
}

interface User extends Entity {
  name: string;
}
```

多层继承在稳定模型里很好用，但不要为了省字段重复而把领域对象继承得过深。一次性组合有时用交叉类型更直接。

```typescript
interface Timestamped {
  updatedAt: string;
}

interface AuditedUser extends User, Timestamped {}
```

接口继承适合表达“是某种更具体的对象”。比如 `AdminUser extends User` 比较自然，因为管理员用户仍然是用户；但 `UserForm extends User` 就未必合适，因为表单草稿可能缺字段、字段类型也可能不同。此时用 `Pick`、`Partial` 或单独建模更清晰。

```typescript
interface User {
  id: string;
  name: string;
  email: string;
}

type UserFormValues = Pick<User, 'name' | 'email'>;
```

继承越深，越容易把上层模型的约束带到不该出现的地方。前端里后端实体、表单值、展示模型、提交 payload 经常相似但不相同，接口继承不能替代清晰建模。

## 声明合并

`interface` 支持声明合并，同名接口会被合并。这在扩展第三方库、全局对象、框架类型时很有用。

```typescript
interface Window {
  analytics?: {
    track(event: string): void;
  };
}

window.analytics?.track('page_view');
```

声明合并很强，但也要克制。随意扩展全局接口会让类型来源变得难追踪。只有在确实是在扩展宿主环境或第三方库能力时才使用。

声明合并常用于扩展框架或运行时类型，例如给 `Window` 增加构建变量、给 Express/Vite/第三方库增加自定义字段。它的关键是放在合适的声明文件里，并确保文件被 `tsconfig` 收进来。

```typescript
declare global {
  interface Window {
    __APP_ENV__: 'dev' | 'test' | 'prod';
  }
}

export {};
```

如果声明写了却不生效，优先检查文件是否在 `include` 范围内、是否因为没有 `export {}` 导致作用域和预期不同、是否存在同名属性类型冲突。声明合并和 [[1.5.11 声明文件|声明文件]] 的边界非常接近，适合集中放在 `env.d.ts` 或 `types` 目录里维护。

## `interface` 与 `type`

`interface` 和 `type` 都能描述对象，但能力侧重点不同。

| 能力 | interface | type |
|---|---|---|
| 对象结构 | 适合 | 适合 |
| 声明合并 | 支持 | 不支持 |
| 联合类型 | 不适合 | 适合 |
| 交叉类型 | `extends` 或组合 | 适合 |
| 基础类型别名 | 不支持 | 支持 |

公共对象结构、可扩展 API、库对外类型常用 `interface`；联合、映射、条件、工具类型组合常用 `type`。团队保持一致，比争论谁更高级更重要。

如果对象结构会继续派生出更多变体，通常会和 [[1.5.4 泛型|泛型]]、[[1.5.3 联合交叉|联合交叉]] 配合使用。

一个实用判断是：如果你在给一个“对象契约”命名，优先考虑 `interface`；如果你在做“类型表达式”，优先考虑 `type`。组件 props、服务接口、插件协议通常适合 `interface`；状态联合、工具类型组合、字面量枚举通常适合 `type`。

```typescript
interface ButtonProps {
  type?: 'button' | 'submit';
  disabled?: boolean;
}

type RequestState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: unknown }
  | { status: 'error'; error: Error };
```

两者不是竞争关系，而是不同表达工具。真正需要避免的是在同一目录里一会儿用 `interface User`，一会儿用 `type User`，或者为了某个小差异来回转换，导致团队看不出命名背后的设计意图。
