## 配置入口

`tsconfig.json` 是 TypeScript 项目的总配置入口，决定编译器看哪些文件、怎么解析模块、输出什么语法、启用哪些类型检查规则。它不是“写给编译器看的一个小文件”这么简单，而是整个工程里 TypeScript、编辑器、测试工具、构建工具共同读取的约定。

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "strict": true
  },
  "include": ["src"]
}
```

在前端项目里，`tsconfig` 往往影响的不只是 `tsc`。编辑器补全、类型提示、测试环境、路径别名、声明文件查找，很多都要靠它提供统一边界。它和 [[1.5.2 类型推断|类型推断]]、[[1.5.5 类型收窄|类型收窄]] 一起，决定“编译器能看见什么”和“能把什么判断出来”。

#### 文件范围

`include`、`exclude`、`files` 这几项决定了项目边界。

```json
{
  "include": ["src/**/*.ts", "src/**/*.tsx"],
  "exclude": ["node_modules", "dist"],
  "files": ["src/main.ts"]
}
```

`include` 适合描述源码目录，`exclude` 适合排除构建产物和依赖目录，`files` 则更像白名单，适合非常小的项目或特殊声明文件。大多数前端项目只要把源码和测试目录纳入清楚，其他内容就会更稳定。

| 项目项 | 作用 | 适合场景 |
| --- | --- | --- |
| `include` | 选中需要参与编译的文件 | 常规应用、库项目 |
| `exclude` | 排除不参与编译的文件 | 排除 `dist`、`node_modules` |
| `files` | 显式列出参与编译的文件 | 小项目、特殊入口 |

`exclude` 只会影响 `include` 自动扫描出来的文件，不会阻止一个文件被 `import` 进项目。也就是说，如果 `src/main.ts` 引用了 `../scripts/build.ts`，即使 `scripts` 在 `exclude` 里，TypeScript 仍然可能为了类型分析把它纳入图里。排查“为什么这个文件也被检查了”时，可以用 `tsc --explainFiles` 看文件进入编译图的原因。

```bash
tsc --noEmit --explainFiles
```

测试文件是否放进同一个配置，要看团队想要的反馈方式。如果应用构建不需要测试文件，可以让 `tsconfig.app.json` 只包含业务源码，`tsconfig.test.json` 再包含测试目录和测试框架类型。这样可以避免 `vitest`、`jest`、`node` 这些全局类型污染浏览器应用配置。

#### 目标语法

`target` 决定输出到什么 JavaScript 语法版本，`lib` 决定类型层面能用哪些内建 API。

```json
{
  "compilerOptions": {
    "target": "ES2020",
    "lib": ["DOM", "DOM.Iterable", "ES2020"]
  }
}
```

这两个选项经常被一起讨论，但职责不同。`target` 影响生成代码的语法形态，`lib` 影响编译器知道哪些全局类型。浏览器项目通常需要 `DOM`，而 Node 项目往往不需要；如果 `lib` 没配对，`document`、`HTMLElement`、`fetch` 之类的类型就会缺失。

`target` 不等于兼容性承诺。它只决定 TypeScript 自己会把部分语法降到什么程度，很多新 API 不会因为降低 `target` 自动补 polyfill。例如 `Array.prototype.at`、`Promise.any`、`structuredClone` 这类 API，类型层面可能来自 `lib`，运行时是否存在还要看浏览器、Babel、core-js 或构建工具策略。真正做兼容时，要把 `target`、`lib`、Browserslist、Babel/esbuild/SWC 配置一起看。

```jsonc
{
  "compilerOptions": {
    "target": "ES2020",
    "lib": ["DOM", "DOM.Iterable", "ES2020"]
  }
}
```

如果项目里出现“类型提示说能用，低版本浏览器却报错”，优先检查这三个问题：类型库是否过高、转译工具是否负责该语法、运行时 API 是否需要 polyfill。TypeScript 负责类型和有限语法降级，不负责完整运行时兼容。

#### 模块解析

`module` 和 `moduleResolution` 决定模块输出和查找方式。

```json
{
  "compilerOptions": {
    "module": "ESNext",
    "moduleResolution": "Bundler"
  }
}
```

现代前端构建工具常见的是 `ESNext + Bundler` 这一类组合。TypeScript 负责类型和静态分析，真正的打包、转译、路径重写由 Vite、Webpack、Next 之类工具完成。这里最容易出问题的是“类型能过，运行时报错”，尤其是路径别名、扩展名解析和包导出字段不一致的时候。

`moduleResolution` 要跟运行环境匹配。浏览器应用交给 Vite、Webpack、Rspack 这类工具处理时，`Bundler` 更贴近现代包的 `exports`、`imports` 字段；Node ESM 项目更常用 `NodeNext`，因为它要尊重 Node 对扩展名、`type: "module"` 和条件导出的规则。库项目如果既要给浏览器用，又要给 Node 用，最好单独设计构建配置，不要试图用一个 `tsconfig` 同时表达所有运行时。

```jsonc
{
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext"
  }
}
```

当导入第三方包报类型错误时，不要只盯着当前文件。要同时看第三方包的 `package.json` 是否声明了 `types`、`exports` 是否屏蔽了子路径、当前配置是否启用了匹配的模块解析策略。很多 “Cannot find module” 并不是文件不存在，而是当前解析规则不允许这样访问。

#### 严格检查

`strict` 是一组严格检查的总开关，建议新项目默认开启。

```json
{
  "compilerOptions": {
    "strict": true
  }
}
```

开启后，`null`、`undefined`、隐式 `any`、函数参数、返回值等问题会被更早暴露。老项目迁移时可以分阶段打开，但新代码尽量不要依赖“编译器先放过我”这种侥幸。

`strict` 背后是一组具体选项，例如 `noImplicitAny`、`strictNullChecks`、`strictFunctionTypes`、`strictBindCallApply`、`strictPropertyInitialization` 等。老项目迁移时，可以先打开 `noImplicitAny` 和 `strictNullChecks` 这类收益最大的检查，再逐步收紧函数和类相关规则。迁移的重点不是追求一次全绿，而是让新增代码不再继续制造宽类型。

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true
  }
}
```

`noUncheckedIndexedAccess` 会让数组索引和对象动态读取多出 `undefined`，更贴近运行时事实；`exactOptionalPropertyTypes` 会区分“属性不存在”和“属性存在但值是 `undefined`”。它们会让代码一开始写起来更严格，但能暴露很多接口数据、配置对象和动态字典里的真实风险。

#### 路径别名

`baseUrl` 和 `paths` 用来配置路径别名。

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

这类配置最常见的误区是只改了 `tsconfig`，却没同步改构建工具和测试工具。TypeScript 只负责类型层面的解析，真正运行时还要让 bundler、测试框架、Node 解析器都认识同样的别名。

路径别名适合隐藏稳定边界，不适合掩盖混乱依赖。比如 `@/components/Button` 比 `../../../../components/Button` 更清晰，但如果所有目录都用 `@/*` 互相引用，反而会削弱模块层次。大型项目更适合设置少量语义别名，例如 `@app/*`、`@shared/*`、`@features/*`，让依赖方向在路径上也能看出来。

```jsonc
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@app/*": ["src/app/*"],
      "@shared/*": ["src/shared/*"],
      "@features/*": ["src/features/*"]
    }
  }
}
```

如果别名只在编辑器里生效，运行时报错，说明运行链路没有同步。Vite 要配 `resolve.alias`，Jest/Vitest 要配模块映射，Node 脚本可能还要靠 `tsx`、`ts-node` 或运行时 loader 支持。路径别名越多，同步成本越高。

#### 输出控制

`noEmit` 常用于“只做类型检查，不负责产物输出”的项目。

```json
{
  "compilerOptions": {
    "noEmit": true
  }
}
```

很多前端项目都把编译和产物生成交给构建工具，TypeScript 只负责校验。CI 里用 `tsc --noEmit` 做类型检查，是一种很常见也很稳妥的做法。

库项目则经常需要 `declaration`、`declarationMap` 和 `emitDeclarationOnly`。应用项目主要关心运行产物，库项目还要把类型作为公共 API 发布出去。生成声明文件时，最好把内部目录、实验性 API、私有类型隔离好，否则用户会在自动补全里看到一堆本不该依赖的内部细节。

```jsonc
{
  "compilerOptions": {
    "declaration": true,
    "declarationMap": true,
    "emitDeclarationOnly": true,
    "outDir": "dist/types"
  }
}
```

`declarationMap` 会让使用者从 `.d.ts` 跳回源码位置，适合开源库和内部共享库。发布到 npm 时，还要确认 `package.json` 的 `types` 或 `exports` 类型入口指向正确，这部分和 [[1.5.11 声明文件|声明文件]] 的发布边界直接相关。

#### 继承配置

`extends` 适合把公共配置提到基础层，子项目只保留差异部分。

```json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "jsx": "react-jsx"
  },
  "include": ["src"]
}
```

Monorepo 或多包项目里，这种方式特别有价值。基础配置负责统一规范，应用配置负责补齐环境差异，比如 React、Node、测试、库发布等。

继承配置要避免“基础层过度全能”。如果 `tsconfig.base.json` 同时塞进 DOM、Node、测试框架、构建脚本类型，所有子项目都会得到一堆不属于自己的全局能力，类型检查反而变松。更稳的方式是基础层只放通用严格规则，环境相关内容放到应用层。

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  }
}
```

`skipLibCheck` 常用于大型前端项目减少第三方声明文件检查成本，但它不是修复类型问题的万能开关。它会跳过库声明内部的一些检查，不能解决业务代码和库 API 调用不匹配的问题。新项目可以谨慎使用，库项目发布前则要更严格地检查对外类型。

#### 配置组合

常见项目里，`tsconfig` 往往会按职责拆成几层：基础层、应用层、测试层、发布层。这样做的好处不是“文件多看起来专业”，而是让不同环境各取所需，减少互相干扰。

```text
tsconfig.base.json
tsconfig.app.json
tsconfig.node.json
tsconfig.test.json
```

如果项目里经常出现“编辑器提示正常、构建失败”或“测试环境缺类型”，先看 `tsconfig` 是否真的和工具链同步了。`tsconfig` 不是单点配置，而是工程契约的一部分。

一个常见的前端应用组合可以这样划分：`tsconfig.json` 做入口和引用，`tsconfig.app.json` 负责浏览器源码，`tsconfig.node.json` 负责构建脚本，测试配置按测试框架单独维护。

```jsonc
// tsconfig.json
{
  "files": [],
  "references": [
    { "path": "./tsconfig.app.json" },
    { "path": "./tsconfig.node.json" }
  ]
}
```

```jsonc
// tsconfig.app.json
{
  "extends": "./tsconfig.base.json",
  "compilerOptions": {
    "jsx": "react-jsx",
    "lib": ["DOM", "DOM.Iterable", "ES2022"],
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "noEmit": true
  },
  "include": ["src"]
}
```

项目引用 `references` 适合 Monorepo 或多包库，可以让 TypeScript 理解包之间的构建顺序，也能配合增量构建减少重复检查。它不是所有项目都需要，但当多个包互相依赖、类型检查越来越慢时，项目引用比简单扩大 `include` 更可控。

排查 `tsconfig` 问题时，最有用的不是凭感觉改选项，而是把编译器最终看到的配置打印出来。

```bash
tsc --showConfig
```

`--showConfig` 可以发现很多隐藏问题：继承后的选项是否被覆盖、`include` 是否过宽、`types` 是否引入了意外的全局类型、`moduleResolution` 是否和构建工具不一致。配置文件本身不长，但它连接的是编辑器、编译器、测试、构建和发布链路，越早建立清晰边界，后面排查成本越低。
