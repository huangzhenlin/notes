## 渲染成本

重排和重绘是浏览器渲染页面时产生的成本。重排关注元素几何信息，重绘关注像素绘制。理解它们，可以解释为什么某些 DOM 和样式操作会让页面卡顿。

```text
样式变化
  -> 可能重新布局
  -> 可能重新绘制
  -> 可能重新合成
```

不是所有样式变化成本都相同。修改 `width` 和修改 `opacity` 对浏览器的影响完全不同。

重排、重绘、合成不是孤立优化口诀，而是渲染流水线不同阶段的成本。优化时要先判断瓶颈在哪：布局频繁说明几何关系变化太多，绘制慢说明像素效果或面积太重，合成慢可能是图层和纹理成本过高。不同瓶颈要用不同手段处理。

## 重排

重排也叫回流，发生在浏览器需要重新计算元素位置和尺寸时。

| 操作 | 原因 |
|---|---|
| 修改宽高 | 几何变化 |
| 修改字体大小 | 文本换行和尺寸变化 |
| 插入删除节点 | 结构变化 |
| 改变窗口大小 | 视口变化 |
| 读取布局属性 | 可能强制刷新布局 |

重排可能只影响一个元素，也可能影响整个文档。影响范围取决于布局关系，文档流越复杂，连锁影响越大。

```javascript
const height = element.offsetHeight;
element.style.height = `${height + 20}px`;
```

重排范围可以通过布局隔离降低。例如组件内部尺寸变化不应该影响整页时，可以考虑更稳定的布局边界、固定容器尺寸、虚拟列表或 CSS containment。不是所有场景都需要 `contain`，但它能帮助浏览器缩小某些计算范围。

重排和 [[1.4.1 渲染流程|渲染流程]] 里的布局阶段直接对应。

## 重绘

重绘发生在元素外观变化但几何不变时。

| 操作 | 影响 |
|---|---|
| 改变颜色 | 重新绘制像素 |
| 改变背景 | 重新绘制背景 |
| 改变阴影 | 重新绘制阴影 |
| 改变边框颜色 | 重新绘制边框 |

重绘通常比重排轻，但复杂阴影、滤镜、大背景、半透明叠层也可能很贵。大面积视觉变化会让绘制成本明显上升。

绘制成本常被低估。`box-shadow`、`filter: blur()`、大面积渐变、背景图叠加、透明遮罩都可能让低端设备掉帧。视觉效果越靠近滚动区域和动画区域，越要谨慎评估绘制面积。

## 合成

某些属性可以由合成阶段处理，例如 `transform` 和 `opacity`。这类变化通常不需要重新布局。

```css
.panel {
  transform: translateX(0);
  transition: transform 200ms ease;
}

.panel.open {
  transform: translateX(100px);
}
```

动画尽量使用合成友好的属性。不要用 `left`、`top` 做高频位移动画。

```css
.fade {
  opacity: 0;
  transition: opacity 200ms ease;
}
```

合成友好不等于没有成本。图层过多会增加内存和合成开销。

合成层适合少数需要独立移动、淡入淡出或固定显示的元素。把大量卡片都提升成独立图层，可能让内存和纹理上传成本变高。动画性能要平衡布局、绘制、合成三者，不是只追求“走合成”。

## 强制布局

JavaScript 写样式后立刻读布局属性，可能迫使浏览器马上完成布局。

```javascript
box.style.width = '200px';
const height = box.offsetHeight;
```

这种模式在循环里尤其危险。应尽量先批量读取，再批量写入。

```javascript
const heights = items.map((item) => item.offsetHeight);

items.forEach((item, index) => {
  item.style.height = `${heights[index] + 10}px`;
});
```

常见会触发布局计算的读取包括 `offsetWidth`、`offsetHeight`、`clientWidth`、`scrollTop`、`getBoundingClientRect()` 和 `getComputedStyle()`。

强制布局最常见于“循环里读写交错”。如果每次循环都先改样式再读尺寸，浏览器可能反复同步布局。更稳的模式是先收集所有需要的尺寸，再统一写入样式；或者把计算放到一次 `requestAnimationFrame` 中批处理。

## 批量更新

批量更新能减少渲染成本。常见方式包括切换 class、使用 `DocumentFragment`、把视觉更新放进 `requestAnimationFrame`。

```javascript
requestAnimationFrame(() => {
  element.classList.add('active');
});
```

大量 DOM 插入可以先放进片段，再一次性插入。

```javascript
const fragment = document.createDocumentFragment();

for (const item of data) {
  const li = document.createElement('li');
  li.textContent = item.title;
  fragment.append(li);
}

list.append(fragment);
```

如果列表规模很大，还应考虑虚拟列表、分页或按需渲染，而不是只靠批量 DOM 操作硬扛。

批量更新也要控制可见范围。一次性创建一万个 DOM 节点，即使用了 DocumentFragment，插入后浏览器仍然要为它们计算样式和布局。虚拟列表的本质是减少实际参与渲染的节点，而不只是优化插入方式。

## 图层权衡

提升图层可以减少某些动画的重绘，但图层不是越多越好。过多图层会增加内存和合成成本。

```css
.moving {
  will-change: transform;
}
```

`will-change` 应用于即将变化的元素，动画结束后可以移除。长期大量使用会适得其反。

```javascript
element.addEventListener('transitionend', () => {
  element.style.willChange = 'auto';
});
```

如果页面在低端设备上动画掉帧，既要看 JS 长任务，也要看图层数量、绘制面积和图片尺寸。

图层问题也可以从 DevTools 的 Layers、Rendering 和 Performance 面板观察。不要只看 FPS 数字，要看掉帧时主线程在做 JS、Layout、Paint 还是 Composite。定位到阶段，优化才不会变成猜。

## 排查工具

Chrome DevTools Performance 面板可以看到 Layout、Paint、Composite 和 Long Task。排查卡顿时，优先录制一次真实交互。

| 面板线索 | 说明 |
|---|---|
| Layout 很长 | 布局计算重 |
| Paint 很长 | 绘制面积或效果重 |
| Long Task | JS 阻塞主线程 |
| FPS 下降 | 动画或滚动不流畅 |

排查顺序可以从主线程开始，再定位到布局、绘制、合成和 JS。

```text
确认是否有 Long Task
  -> 看 Layout 是否频繁
  -> 看 Paint 面积是否过大
  -> 看 Composite 和图层
  -> 回到具体 DOM / CSS / JS 代码
```

重排重绘不是“优化口诀”，而是浏览器工作的结果。真正要优化的是导致它们过于频繁、范围过大或出现在关键交互路径上的代码。

一个实用原则是：首屏和交互路径优先优化，非关键区域按需优化。后台隐藏页签、折叠面板、非首屏列表，即使有重排重绘，也不一定值得复杂化代码。性能优化要服务用户体感，而不是追求理论上每一步都最少。
