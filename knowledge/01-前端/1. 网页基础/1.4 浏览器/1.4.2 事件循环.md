## 调度目标

事件循环用于协调 JavaScript 执行、异步回调、微任务、渲染和用户交互。浏览器主线程一次只能执行一个任务，事件循环决定下一个执行什么。

```text
执行一个任务
  -> 清空微任务
  -> 可能渲染
  -> 执行下一个任务
```

理解事件循环可以解释为什么 Promise 通常比 `setTimeout` 更早执行，为什么长任务会阻塞点击，为什么 `requestAnimationFrame` 适合动画。

事件循环不是 JavaScript 语言本身单独完成的机制，而是浏览器宿主环境和 JS 引擎协作的调度模型。V8 负责执行回调，浏览器负责把计时器、网络、用户输入、渲染等工作安排到合适时机。理解这个边界，能避免把所有异步行为都归结为 Promise 或线程。

## 任务队列

任务也常被称为宏任务。常见来源包括脚本执行、`setTimeout`、`setInterval`、用户事件、网络回调等。

```javascript
setTimeout(() => {
  console.log('timeout');
}, 0);

console.log('script');
```

同步代码会先执行，定时器回调进入后续任务队列。任务队列不是简单的“等待列表”，而是浏览器调度主线程执行入口的一部分。

## 微任务

微任务会在当前任务结束后、浏览器进入下一轮任务或渲染前执行。常见来源包括 Promise、`queueMicrotask`、`MutationObserver`。

```javascript
console.log('start');

Promise.resolve().then(() => {
  console.log('microtask');
});

setTimeout(() => {
  console.log('task');
});

console.log('end');
```

输出顺序通常是：

```text
start
end
microtask
task
```

微任务优先级高，但如果连续创建大量微任务，也会阻塞渲染。Promise 链写得很深时，尤其要注意。

微任务适合当前任务结束后的收尾，例如 Promise 后续处理、状态批处理、MutationObserver 回调。它不适合长时间计算。如果微任务里继续不断排微任务，浏览器会一直清空微任务队列，渲染和用户输入就会被推迟。

## 渲染时机

浏览器通常会在任务结束、微任务清空后，选择合适时机进行渲染。不是每轮事件循环都一定渲染，浏览器会根据页面状态和帧预算决定。

```text
Task
  -> Microtasks
  -> Rendering
  -> Next Task
```

如果一个任务执行很久，浏览器无法及时处理输入和绘制，用户会感觉卡顿。

```javascript
function blockMainThread() {
  const start = performance.now();
  while (performance.now() - start < 120) {}
}
```

长任务不仅影响动画，也影响点击、输入和滚动响应。

长任务对 INP 这类交互指标影响很直接。用户点击后，如果主线程正在执行大循环、复杂渲染或大量 JSON 解析，事件回调就无法及时运行。优化交互响应时，先找长任务，再看能否拆分、延迟、缓存或移到 Worker。

## `requestAnimationFrame`

`requestAnimationFrame` 会在下一次绘制前执行，适合读取动画状态和更新视觉。

```javascript
function animate() {
  box.style.transform = `translateX(${x}px)`;
  requestAnimationFrame(animate);
}

requestAnimationFrame(animate);
```

它比 `setInterval` 更适合动画，因为浏览器可以和刷新率对齐，并在页面不可见时降低执行频率。

`requestAnimationFrame` 里也不应该做重计算。它的定位是“下一帧绘制前更新视觉状态”，不是给你一段无限制执行时间。复杂计算可以提前完成，帧回调里只做必要的 DOM/CSS 更新。

## `requestIdleCallback`

`requestIdleCallback` 适合执行低优先级任务，例如预计算、日志整理、非关键缓存。

```javascript
requestIdleCallback(() => {
  warmupCache();
});
```

空闲回调不适合关键逻辑，因为浏览器不保证它马上执行。兼容性也要注意，必要时需要降级方案。

空闲任务要能被延迟甚至跳过。预加载非关键数据、建立低优先级索引、清理日志、预计算推荐都比较适合；提交表单、展示错误、响应点击这类用户等待的逻辑绝不应该依赖空闲回调。

## 长任务

超过 50ms 的主线程任务通常会被视为 Long Task。长任务会阻塞输入响应和渲染。

```javascript
function heavyWork(items) {
  for (const item of items) {
    expensiveCompute(item);
  }
}
```

可以通过分片执行降低阻塞。

```javascript
function chunkWork(items) {
  const task = items.splice(0, 100);
  task.forEach(expensiveCompute);

  if (items.length > 0) {
    setTimeout(() => chunkWork(items), 0);
  }
}
```

如果任务本身不能拆，至少要把它移出首屏关键路径，或者放到空闲时执行。

分片执行还要考虑用户是否能看到中间状态。大列表处理可以分批渲染，搜索索引可以后台构建，导入大文件可以显示进度。把长任务拆开，不只是为了浏览器喘气，也是为了让用户知道系统仍在工作。

## `async/await`

`async/await` 本质上基于 Promise。`await` 后面的代码会在 Promise resolved 后作为微任务继续。

```javascript
async function run() {
  console.log('a');
  await Promise.resolve();
  console.log('b');
}

run();
console.log('c');
```

输出通常是：

```text
a
c
b
```

`await` 不会阻塞整个页面，只是暂停当前 async 函数后半段的执行。异步链复杂时，要记住“await 之后的继续执行”仍然是微任务。

因此 `await` 不是性能优化开关。如果 await 的 Promise 已经 resolved，后续代码仍会进入微任务；如果 await 前后做的是同步重计算，主线程依然会被阻塞。异步能让等待变非阻塞，但不能让 CPU 密集型计算自动变快。

## 排查顺序

页面卡顿或响应延迟时，可以按这个顺序排查：

```text
是否有长任务
  -> 微任务是否过多
  -> 是否阻塞渲染
  -> 是否在动画帧里做重计算
  -> 是否在交互回调里做同步大循环
```

事件循环和 [[1.3.17 V8|V8]]、[[1.4.1 渲染流程|渲染流程]] 是连在一起的：V8 执行 JS，浏览器事件循环调度任务，渲染流水线把结果显示出来。

排查时可以用 Performance 面板看主线程火焰图：长任务在哪里，微任务是否密集，渲染是否被推迟，输入事件是否等待太久。事件循环问题最好用时间线验证，单靠输出顺序只能解释一小部分。
