## 缓存层级

浏览器缓存不是单一机制，而是一组层级：内存缓存、磁盘缓存、HTTP 缓存、Service Worker 缓存、预加载缓存和应用自定义缓存。

```text
资源请求
  -> 内存缓存
  -> 磁盘缓存
  -> HTTP 缓存校验
  -> Service Worker
  -> 网络请求
```

真实命中顺序会受到浏览器实现、页面状态、请求方式和 Service Worker 的影响。学缓存时，重点是理解 HTTP 缓存语义和发布策略，而不是背某个 DevTools 里显示的命中顺序。

缓存解决的是“资源是否需要重新下载”。它和 [[1.4.7 页面加载|页面加载]]、静态资源部署、Service Worker 更新策略是同一个问题的不同侧面。

缓存还要区分“浏览器缓存”和“中间层缓存”。CDN、代理、网关、Service Worker、浏览器 HTTP 缓存都可能保存资源。线上缓存问题经常不是某一层单独错，而是 HTML、静态资源、CDN TTL、Service Worker 更新和回滚策略没有对齐。

## 强缓存

强缓存表示浏览器在缓存有效期内直接使用本地副本，不向服务器确认。

```http
Cache-Control: public, max-age=31536000, immutable
```

带 hash 的静态资源最适合强缓存：

```text
assets/main.abc123.js
assets/style.f91a20.css
```

文件名变了就代表内容变了，旧文件可以放心长期缓存。强缓存的关键前提是“URL 能代表内容版本”。如果 URL 不变但内容变了，长期强缓存就会让用户拿到旧资源。

因此静态资源强缓存通常必须配合内容 hash。不要给 `/app.js` 这种固定 URL 配一年强缓存，除非你能保证更新时 URL 一定变化。强缓存越强，发布系统越要保证版本化、旧资源保留和回滚路径。

## 协商缓存

协商缓存表示浏览器会先向服务器确认资源是否更新。常见头是 `ETag` 和 `Last-Modified`。

```http
ETag: "abc123"
Last-Modified: Tue, 22 Jul 2025 10:00:00 GMT
```

再次请求时，浏览器会带上条件头：

```http
If-None-Match: "abc123"
If-Modified-Since: Tue, 22 Jul 2025 10:00:00 GMT
```

如果资源未变，服务器返回 `304 Not Modified`，浏览器继续使用本地副本。协商缓存适合内容可能变化，但不值得每次完整下载的资源。

```http
HTTP/1.1 304 Not Modified
```

协商缓存减少响应体传输，但仍然有一次网络往返。对 HTML 入口来说这是常见取舍：既保证能发现新版本，又避免每次完整下载；对带 hash 静态资源来说，协商反而不如长期强缓存直接。

## `Cache-Control`

`Cache-Control` 是现代 HTTP 缓存的核心控制头。

| 指令 | 含义 |
|---|---|
| `max-age` | 缓存有效秒数 |
| `no-cache` | 使用前必须校验 |
| `no-store` | 不存储 |
| `public` | 可被共享缓存保存 |
| `private` | 仅浏览器私有缓存 |
| `immutable` | 有效期内内容不会变 |

`no-cache` 不是不缓存，`no-store` 才是不存储。敏感页面更适合 `no-store`。

```http
Cache-Control: no-store
```

用户私有信息、一次性票据、支付结果这类页面，不应该被浏览器或中间缓存长期保存。

`private` 和 `public` 的边界也很重要。`private` 表示只适合浏览器私有缓存，不应被共享缓存保存；`public` 则允许 CDN 或代理缓存。用户相关 API 和页面通常不要让共享缓存保存，除非明确做了按用户、权限或 Vary 维度隔离。

## `ETag`

`ETag` 是资源版本标识，通常由服务器根据内容或版本生成。

```http
ETag: "main-abc123"
```

当资源过期后，浏览器会把旧 ETag 放进 `If-None-Match` 请求头，让服务器判断内容是否变化。相比时间戳，ETag 通常更精确。

```http
If-None-Match: "main-abc123"
```

在分布式部署里，要保证不同节点生成的 ETag 规则一致，否则缓存会失效得很频繁。ETag 不只是缓存校验，也常用于并发编辑冲突判断。

ETag 如果包含节点信息、时间戳或不稳定构建信息，就可能导致同一资源在不同服务器上反复被认为变化。CDN 和多实例服务里，ETag 生成策略要稳定，否则协商缓存会形同虚设。

## `Last-Modified`

`Last-Modified` 用时间表示资源最后修改时间。

```http
Last-Modified: Tue, 22 Jul 2025 10:00:00 GMT
```

它实现简单，适合静态文件和发布时间明确的资源。它的精度和一致性通常不如 ETag，因此更多是和 ETag 搭配使用。

```http
HTTP/1.1 200 OK
Last-Modified: Tue, 22 Jul 2025 10:00:00 GMT
ETag: "abc123"
```

## HTML 策略

HTML 通常不适合长时间强缓存，因为它负责引用最新的静态资源版本。更常见的做法是让 HTML 走短缓存或协商缓存。

```http
Cache-Control: no-cache, private
```

如果 HTML 是个性化页面，还应避免被共享缓存保存。资源与入口页的策略通常是分开的：HTML 保持新鲜，带 hash 的 JS/CSS 长期缓存。

HTML 是版本入口。它决定加载哪些 JS/CSS chunk、预加载哪些资源、注入哪些运行时配置。HTML 过度强缓存会让用户长期停留在旧应用版本；HTML 完全不缓存则会增加每次导航成本。多数应用会选择短缓存或协商缓存。

## 资源版本

前端发布最常见的策略是：HTML 短缓存，hash 静态资源长缓存，旧资源保留一段时间。

```text
index.html -> no-cache
app.[hash].js -> max-age=31536000, immutable
```

这样可以避免用户拿到旧 HTML 却请求不到旧 chunk。缓存策略和 [[5.9.1 静态资源部署|静态资源部署]] 是同一个问题的两面。

```text
用户缓存旧 index.html
  -> 请求 app.old.js
  -> 服务器已删除旧 chunk
  -> 页面白屏
```

发布时保留旧 chunk 是非常关键的线上稳定策略。因为用户可能打开着旧 HTML、Service Worker 可能还缓存旧入口、CDN 节点可能还没全部刷新。只删除最新版本之外的所有资源，很容易制造白屏。

## Service Worker

Service Worker 可以拦截请求并自定义缓存策略，常用于 PWA、离线缓存和资源预缓存。

```javascript
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      return cached || fetch(event.request);
    }),
  );
});
```

Service Worker 很强，也很容易出事故。缓存策略写错后，用户可能长期拿到旧页面，所以发布时一定要设计更新和回滚。

```javascript
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((keys) => {
      return Promise.all(
        keys.filter((key) => key !== 'static-v2').map((key) => caches.delete(key)),
      );
    }),
  );
});
```

Service Worker 缓存不是 HTTP 缓存的替代品，而是更靠近应用层的缓存控制。

Service Worker 更新也有生命周期：install、activate、fetch。新 SW 不一定立刻接管所有页面，旧页面可能还由旧 SW 控制。PWA 更新策略要考虑用户是否需要刷新、旧缓存何时删除、失败时如何回滚。它很强，但也比普通 HTTP 缓存更需要治理。

## 调试缓存

Chrome DevTools Network 面板可以看资源来自 memory cache、disk cache、304 还是 Service Worker。

| 现象 | 可能原因 |
|---|---|
| `from memory cache` | 当前会话内存缓存 |
| `from disk cache` | 磁盘缓存命中 |
| `304` | 协商缓存命中 |
| chunk 404 | HTML 与资源版本不一致 |
| 更新不生效 | HTML/CDN/SW 缓存未刷新 |

排查缓存问题时，要同时看浏览器缓存、CDN 缓存、Service Worker 和部署顺序。很多“浏览器缓存问题”其实是某一层没对齐。

调试时可以先确认请求是否真的发出，再看响应头，再看 DevTools 是否显示 from disk/memory cache、Service Worker、304 或 CDN 命中。不要只按一次刷新结果判断缓存策略；普通刷新、强制刷新、禁用缓存、无痕窗口、清 SW 都可能得到不同结果。

## 选择策略

| 资源 | 推荐策略 |
|---|---|
| HTML 入口 | `no-cache, private` 或短缓存 |
| hash 静态资源 | `max-age=31536000, immutable` |
| 需要校验的资源 | `no-cache` + `ETag` |
| 敏感页面 | `no-store` |
| 离线应用资源 | Service Worker + HTTP 缓存组合 |

缓存不是越强越好，而是要和发布方式匹配。只要资源版本、缓存头和回滚策略三者一致，缓存就会变成加速器；一旦其中一环不一致，就会变成线上故障源。

最终可以用一句话检查缓存策略：入口文件要能尽快发现新版本，版本化静态资源要能长期复用，敏感内容不能被不该缓存的地方保存，应用层缓存必须能更新和回滚。四件事同时成立，缓存才算可靠。
