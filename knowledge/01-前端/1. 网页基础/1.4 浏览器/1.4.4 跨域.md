## 同源边界

同源策略是浏览器的安全边界。协议、域名、端口三者完全一致，才算同源。

```text
https://app.example.com:443
协议：https
域名：app.example.com
端口：443
```

跨域并不是“服务器收不到请求”，而是“浏览器不让前端脚本读响应”。这点很重要，因为很多跨域问题的表象是请求发出去了，控制台却读不到结果。

```text
浏览器发出请求
  -> 服务器返回响应
  -> 浏览器检查 CORS
  -> 不允许则 JS 读不到响应
```

同源策略主要限制的是脚本读取跨源数据。图片、脚本、样式等资源加载各自还有单独规则，不能简单理解成“跨域都不行”。

同源策略是浏览器保护用户数据的基础。没有它，任意网站都可以用用户浏览器里的登录态读取银行、邮箱或后台系统的数据。跨域限制看起来麻烦，但它本质上是在阻止恶意页面读取其他站点的私有响应。

## CORS

CORS 是服务器主动声明允许哪些来源访问资源的机制。

```http
Access-Control-Allow-Origin: https://app.example.com
```

如果需要携带 Cookie，还要同时允许凭证：

```http
Access-Control-Allow-Credentials: true
```

前端请求也要显式开启凭证：

```javascript
fetch('https://api.example.com/profile', {
  credentials: 'include',
});
```

带凭证时，`Access-Control-Allow-Origin` 不能是 `*`，必须是明确来源。跨站登录、会话恢复和受限资源访问都需要把这几个条件一起看。

服务器还应该设置 `Vary: Origin`，避免共享缓存把某个 Origin 对应的 CORS 响应错误复用给另一个 Origin。只要响应会根据 Origin 动态变化，缓存层就需要知道 Origin 是响应变化维度。

## 简单请求

简单请求不会触发预检。它需要满足方法、请求头和 `Content-Type` 等条件。

| 条件 | 示例 |
|---|---|
| 方法 | GET、HEAD、POST |
| 请求头 | 只使用安全列表头 |
| Content-Type | `text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded` |

JSON POST 通常会触发预检，因为 `application/json` 不属于简单请求范围。

```javascript
fetch('https://api.example.com/users', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ name: 'Ada' }),
});
```

简单请求不是“安全请求”。它只是浏览器认为可以不预检的请求。比如普通表单 POST 可以跨站发出，所以 CSRF 防护不能依赖预检是否存在。安全判断仍然要靠服务端鉴权、SameSite、CSRF token 等机制。

## 预检请求

预检请求会先发 `OPTIONS`，先确认服务器是否允许真正请求。

```http
OPTIONS /api/profile
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization
```

服务器需要返回允许的来源、方法和头：

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: content-type, authorization
```

预检失败时，真正请求通常不会发出。调试跨域时一定要看 `OPTIONS` 响应，而不是只盯业务接口。

```http
Access-Control-Max-Age: 600
```

预检结果可以缓存一段时间，但缓存时长要和安全要求、接口变化频率一起权衡。

预检失败时，浏览器控制台常常只给出 CORS 错误，但真正原因可能是 OPTIONS 路由不存在、网关没放行请求头、后端没返回允许方法、认证中间件拦截了预检。预检请求本身通常不应该要求业务登录态，否则浏览器还没发真正请求就被拦住。

## 凭证模式

`fetch` 的 `credentials` 会影响 Cookie 是否发送和接收。

| 选项 | 含义 |
|---|---|
| `omit` | 不发送凭证 |
| `same-origin` | 仅同源发送 |
| `include` | 跨域也发送 |

跨站登录问题通常同时涉及 `credentials`、Cookie `SameSite` 和 CORS 响应头。

```http
Set-Cookie: session=abc; SameSite=None; Secure
```

跨站携带 Cookie 通常需要 `SameSite=None; Secure`，并且请求必须走 HTTPS。

Cookie 能不能发送由多层共同决定：请求的 `credentials`、Cookie 的 `SameSite/Secure/Domain/Path`、浏览器第三方 Cookie 策略、CORS 是否允许凭证。只改前端 `credentials: 'include'`，如果服务端 Cookie 属性不对，仍然不会成功。

## 代理方案

开发环境常用代理绕过浏览器跨域限制，本质是让浏览器请求同源开发服务器，再由开发服务器转发给后端。

```typescript
// vite.config.ts
export default {
  server: {
    proxy: {
      '/api': 'https://api.example.com',
    },
  },
};
```

代理解决的是开发体验，不代表生产环境也可以绕过跨域。生产环境还是要正确配置 CORS、网关或后端转发。

生产代理也可以作为架构方案，例如前端同源请求 BFF 或网关，由网关再请求后端服务。这样浏览器视角是同源，跨服务通信在服务端完成。它和开发代理的区别是：生产代理要承担鉴权、限流、日志、错误转换和安全边界。

## JSONP

JSONP 利用 `<script>` 不受同源策略限制的特性获取数据，只支持 GET，而且安全性较弱。

```html
<script src="https://api.example.com/jsonp?callback=handle"></script>
```

现代项目优先使用 CORS。JSONP 的问题在于脚本会被直接执行，不能像普通 JSON 一样只当作数据读取。

```javascript
function handle(data) {
  render(data);
}
```

如果服务端返回恶意脚本，页面会直接执行它。这就是 JSONP 风险高的根本原因。

JSONP 也无法像 CORS 一样细粒度控制方法、请求头和凭证模式。它是历史兼容方案，不适合承载现代受保护 API。现在遇到 JSONP，更多是维护老系统或接入老接口时需要知道风险。

## 安全关系

CORS 不是鉴权。允许某个来源读取响应，不代表这个来源天然可信。服务端仍然要校验登录态、权限和 CSRF。

```text
CORS：谁能被浏览器允许读取响应
鉴权：谁能访问资源
CSRF：谁能伪造用户操作
```

跨域要和 [[1.6.2 CSRF|CSRF]]、[[1.6.4 鉴权|鉴权]] 一起看。CORS 放宽了暴露面，鉴权缺失则会直接泄露数据。

排查跨域时可以按顺序看：请求是否发出，是否有预检，预检是否成功，正式响应是否带允许来源，是否需要凭证，Cookie 是否真的发送，服务端是否通过鉴权。跨域问题常常不是单点配置，而是浏览器、网关、后端和 Cookie 策略共同决定的结果。
