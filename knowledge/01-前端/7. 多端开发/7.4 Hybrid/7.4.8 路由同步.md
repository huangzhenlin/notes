## 双路由模型

Hybrid 应用里通常同时存在 Native 路由和 H5 路由。Native 管 Activity、ViewController、容器页面和系统返回；H5 管 WebView 内部路径、浏览器 history、页面标题和业务状态。

```text
Native 栈：HomeActivity -> WebViewActivity -> PayActivity
H5 栈：/home -> /product/1001 -> /checkout
```

如果两套路由没有同步协议，就会出现标题不一致、返回错乱、登录后跳转丢失、分享链接不完整、埋点页面名错误等问题。路由同步的目标是让容器和 Web 对“当前页面是谁”形成一致认知。

双路由模型最难的是两边都认为自己有控制权。Native 觉得系统返回应该关闭容器，H5 觉得应该先退内部 history；Native 觉得标题由容器控制，H5 觉得路由 meta 才是标题来源。同步协议就是用来消除这种“各管各的”。

路由同步的本质，不是把两套路由硬拼在一起，而是明确谁负责容器级导航、谁负责页面级导航、谁在关键时刻拥有最终决定权。规则一旦清楚，很多看似复杂的返回和标题问题都会简单很多。

## 同步内容

路由同步不只是同步 URL。容器往往还需要知道标题、返回按钮状态、右上角菜单、页面来源、是否允许下拉刷新、是否拦截返回、埋点页面标识等信息。

```ts
bridge.call("setNavigationBar", {
  title: "商品详情",
  showBack: true,
  actions: [{ key: "share", text: "分享" }],
});
```

这些信息应该由页面进入或路由变化时主动声明，而不是让 Native 侧通过解析 URL 猜。URL 表达资源位置，导航栏和行为策略更适合用结构化协议表达。

同步内容还要区分“页面状态”和“容器状态”。页面状态包括当前 path、query、业务 ID；容器状态包括标题、返回按钮、右侧菜单、沉浸式样式、是否允许关闭。两者可以一起上报，但不要混成一个无法演进的大字符串。

同步内容越结构化，后续扩展越稳。今天同步标题和返回，明天同步分享和埋点，后天同步主题和沉浸式样式，如果一开始就是一个结构清晰的协议，后面的演进成本会低很多。

## Web 到 Native

H5 内部跳转后，需要通知 Native 更新容器状态。单页应用尤其需要处理这一点，因为浏览器地址变化不一定会让 Native 容器感知到。

```ts
router.afterEach((to) => {
  bridge.call("routeChanged", {
    url: location.href,
    path: to.path,
    title: to.meta.title,
    canGoBack: window.history.length > 1,
  });
});
```

通知要避免过于频繁。查询参数变化、锚点变化、页面内部 tab 切换是否算“路由变化”，要根据业务定义。否则 Native 标题栏和埋点可能被无意义更新刷屏。

单页应用尤其要在路由守卫或全局 after hook 中统一通知 Native，避免每个页面自己写一套同步逻辑。否则有的页面忘记同步标题，有的页面重复上报，有的页面返回状态不准，问题会很分散。

统一同步入口还能顺手收口埋点、分享信息和页面级容器配置。只要路由变化是系统级事件，就尽量不要让业务页面各自处理一遍。

## Native 到 Web

Native 返回键、导航栏返回按钮、关闭按钮、系统手势都可能触发路由行为。Native 侧不能直接关闭 WebView，而应该先询问 H5 是否可以处理。

```ts
window.__handleNativeBack = function () {
  if (window.history.length > 1) {
    window.history.back();
    return true;
  }

  return false;
};
```

如果 H5 返回 true，说明它已经处理了内部返回；如果返回 false，Native 再关闭容器页。这个协议要明确超时策略，避免 H5 异常时 Native 返回卡死。

Native 到 Web 的返回询问要有硬超时。H5 脚本异常、Bridge 失效或页面正在加载时，如果 Native 一直等待，就会造成返回键失效。超时后通常应该按容器默认策略关闭或返回上一原生页面。

Native 到 Web 的控制消息最好保持少而稳定。返回、关闭、刷新、前台恢复这类少量强语义事件，通常已经足够支撑大部分容器交互；消息越多，双端越容易进入彼此实现细节。

## 返回策略

返回策略要区分“回退 H5 history”“关闭 WebView”“跳到 Native 首页”“退出流程”。支付、登录、开户、表单编辑这类流程不能简单使用浏览器默认返回。

```ts
function beforeBack() {
  if (hasUnsavedDraft()) {
    bridge.call("confirm", {
      title: "离开页面",
      message: "未保存内容将丢失",
    });
    return true;
  }

  return false;
}
```

返回拦截要克制。能用标准 history 解决的页面不要定制；只有数据丢失、关键流程、身份状态变化这类场景才需要特殊策略。否则用户会觉得返回行为不可预测。

表单编辑、支付确认、实名认证这类流程可以拦截返回，但拦截后要给用户明确选择。最差的体验是点返回没有反应，用户不知道页面卡了还是不允许离开。返回策略本质上是交互协议，不只是技术逻辑。

返回策略真正要统一的是“默认行为”和“例外条件”。默认情况下按系统预期返回，只有确实会丢数据、断流程、损坏状态时才做特殊拦截，这样用户对 Hybrid 页面才会保有稳定预期。

## 分享恢复

Hybrid 页面常需要分享给外部用户。分享链接必须能恢复页面所需状态，而不能依赖 Native 临时栈或内存缓存。

```ts
bridge.call("setShareInfo", {
  title: "夏季活动",
  url: `https://m.example.com/activity?id=${activityId}`,
  image: shareImage,
});
```

如果页面状态来自登录后缓存、Native 入参或上一个页面传递，分享后打开就会丢失。可分享页面要把关键状态放入 URL、服务端短链或可查询资源 ID 中。

分享恢复要按照“冷启动”设计。接收分享的人可能没有登录、没有当前 App 栈、没有本地缓存，也可能从浏览器或微信外部进入。只要分享链接无法独立恢复核心内容，就不是一个可靠分享页。

这也是为什么分享链接最好承载可恢复状态，而不是承载当前内存状态。分享的本质是把页面从当前栈里解耦出来，变成一个能被外部重新打开的入口。

## 登录回跳

登录是路由同步最常见的复杂场景。H5 发现未登录后跳转登录，登录可能由 Native 页面完成，也可能由 H5 页面完成。完成后需要回到原始目标页。

```ts
function requireLogin(targetUrl: string) {
  bridge.call("openLogin", {
    redirect: encodeURIComponent(targetUrl),
  });
}
```

redirect 要校验来源，只允许站内路径或白名单页面。登录回跳还要处理 H5 history，避免用户登录成功后返回又回到登录页。

登录回跳还要处理多入口：用户可能从分享进入、从 Native 页面进入、从 H5 内部跳转进入。最好把目标页编码成受控 redirect，并在登录成功后替换历史记录，而不是简单 push 一个新页面。

登录回跳一旦没设计好，用户会非常容易迷路：登录后去了不该去的页、返回又回到登录页、原始目标页丢失、参数消失。这类问题看起来像局部 bug，根上其实都是路由协议不完整。

## 协议版本

路由同步协议要有版本。H5 和 Native 不是总能同时发布，新 H5 可能运行在旧 App 中，旧 H5 也可能运行在新 App 中。

```ts
bridge.call("routeChanged", {
  protocolVersion: 2,
  path: "/product/1001",
  title: "商品详情",
  canGoBack: true,
});
```

协议字段要向后兼容。新增字段可以可选，删除字段要谨慎，行为变化要有能力探测或版本判断。这里和 [[7.4.5 热更新|热更新]] 的版本匹配是同一个风险面。

路由协议最好有默认行为。旧容器不认识新字段时，至少能保持基本标题和返回；新容器遇到旧页面时，也不应该要求页面必须上报所有字段。默认行为越稳，热更新和灰度发布越安全。

协议版本的目标不是让每次变更都必须双端同步，而是让不同版本组合时依然能维持一个足够可用的基础行为。只要标题、返回和基础路径还能工作，大多数页面就不会彻底失控。

## 异常兜底

路由同步失败不能让页面不可用。Bridge 超时、Native 未实现、H5 脚本异常、history 状态混乱时，都需要兜底策略。

```ts
async function safeBridgeCall(name: string, payload: unknown) {
  try {
    await bridge.call(name, payload, { timeout: 1000 });
  } catch (error) {
    console.warn("bridge failed", name, error);
  }
}
```

关键原则是：同步失败可以导致标题不准，但不应该导致交易流程中断；返回判断失败可以回退到关闭容器，但不能无限卡住。路由同步要服务体验，而不是让容器和 Web 互相绑死。

异常兜底也要进入监控。标题同步失败、返回询问超时、分享信息设置失败、登录回跳丢失，都应该以低成本日志记录下来。它们未必立刻造成白屏，但会持续破坏 Hybrid 体验。

路由同步真正成熟的状态，是同步成功时几乎无感，同步失败时也不会让主流程崩掉。它应该像基础设施一样默默工作，而不是每次异常都直接暴露给用户。
