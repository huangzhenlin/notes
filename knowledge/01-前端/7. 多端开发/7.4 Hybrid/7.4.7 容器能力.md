## 能力分层

Hybrid 容器能力是原生 App 提供给 H5 的平台能力集合，通常通过 JSBridge 暴露。

```txt
H5 页面
  -> Bridge API
  -> 容器能力层
  -> iOS/Android 系统能力
```

容器能力应按业务封装，而不是把所有原生 API 原样暴露给 H5。

能力分层的目的，是让 H5 调用的是稳定业务能力，而不是不同平台的实现细节。比如 H5 需要的是“选择头像”，而不是知道 iOS 用哪个相册 API、Android 用哪个权限弹窗。平台差异应尽量被容器能力层吸收。

能力分层做得越好，H5 页面就越接近“调用业务服务”，而不是“操作原生设备”。这会直接影响页面可维护性，也会影响后续换容器、换宿主和做灰度时的稳定性。

## 常见能力

| 能力 | 示例 |
| --- | --- |
| 导航 | 打开原生页、关闭 WebView、设置标题 |
| 设备 | 获取系统信息、网络状态 |
| 媒体 | 相机、相册、扫码 |
| 用户 | 登录、获取用户状态 |
| 支付 | 唤起原生支付 SDK |
| 分享 | 唤起系统或平台分享 |
| 存储 | 安全存储、缓存 |
| 通知 | 推送、订阅状态 |

这些能力很多涉及权限、隐私和安全，不能只从前端调用便利性设计。

常见能力要按敏感程度分级。设置标题、关闭页面属于低风险能力；扫码、相册、定位属于需要用户授权的能力；支付、账号、文件、安全存储属于高风险能力。风险等级越高，越需要来源校验、参数校验和服务端配合。

能力分级的价值，在于决定治理强度。低风险能力可以更偏前端体验，高风险能力必须更偏安全和审计。不是所有容器能力都值得用同一套轻重策略来对待。

## 能力注册

容器应维护能力白名单。

```json
{
  "chooseImage": {
    "minVersion": "2.3.0",
    "permissions": ["album"]
  },
  "payOrder": {
    "minVersion": "3.1.0",
    "permissions": ["login"]
  }
}
```

H5 调用前可以探测能力是否存在，容器执行前也要校验版本、权限、域名和参数。

能力注册表最好由原生维护，并暴露给 H5 做探测。这样页面可以在展示入口前就判断是否可用，而不是等用户点击后才失败。对灰度能力、实验能力和平台差异能力，这种探测尤其重要。

注册表不仅是“有哪些方法”的清单，也是“哪些能力能在哪些条件下使用”的约束源。只要注册信息足够完整，H5 的展示逻辑、服务端的资源下发和原生的权限判断就能围绕同一份事实工作。

## 参数协议

Bridge 参数应有明确 schema。

```ts
type ShareParams = {
  title: string;
  url: string;
  imageUrl?: string;
};
```

容器不能相信 H5 传入的数据。URL、文件路径、订单号、跳转地址都要做合法性校验。

参数协议还应明确返回结构。比如 `chooseImage` 返回本地临时文件、上传后的文件 ID，还是二者都返回；`payOrder` 返回支付完成、用户取消、处理中，还是只返回成功失败。返回语义不清，会让页面逻辑被迫写大量猜测分支。

参数协议越业务化，页面越容易稳定复用。H5 不应该频繁关心 iOS 和 Android 各自返回什么底层字段，而是应该拿到一个对业务足够清楚的统一结果。

## 版本兼容

H5 发布速度通常快于 App。新 H5 调用旧容器不存在的能力，是 Hybrid 常见线上问题。

```ts
if (bridge.canIUse("shareProduct", "2.1.0")) {
  bridge.call("shareProduct", { productId });
} else {
  copyShareLink(productId);
}
```

容器能力需要版本号和降级方案。服务端下发 H5 资源时，也可以按 App 版本做灰度。

版本兼容不能只靠前端判断。服务端下发页面资源、容器暴露能力、H5 展示入口三处都要保持一致：服务端不要把新页面发给旧 App，容器不要让旧协议误调新能力，H5 不要在能力不可用时显示无法完成的入口。

真正稳定的兼容，不是某一层单独做得聪明，而是三层一起保守：服务端控制资源范围，容器控制能力暴露，H5 控制入口展示。任何一层放松，线上都可能出现“页面看得见但做不完”的断链体验。

## 权限与隐私

相机、相册、定位、通讯录、通知等能力都涉及用户授权。

```txt
H5 发起业务请求
容器解释权限用途
系统弹窗授权
原生返回结果或拒绝原因
H5 展示后续 UI
```

权限拒绝不是普通失败。H5 需要知道是用户取消、系统拒绝、设备不支持，还是容器版本不支持。

权限说明最好靠近用户动作。用户点击“查看附近门店”时解释定位用途，比页面启动时直接弹定位授权更容易被理解。权限失败后也要有手动兜底，例如手动选择城市、手动上传图片、复制链接分享。

权限设计如果只考虑“怎么调起系统弹窗”，最后通常会损失转化。更好的做法是把权限当成完整交互流程的一部分：为什么需要、拒绝后怎么办、以后如何再次开启，都要在页面和容器层一起说明清楚。

## 安全边界

| 风险 | 防护 |
| --- | --- |
| XSS 调用敏感能力 | 域名白名单、CSP、参数校验 |
| 任意跳转 | URL 白名单 |
| 旧 H5 调新能力 | 版本探测 |
| 支付参数篡改 | 服务端签名和校验 |
| 文件路径攻击 | 路径限制 |

容器能力越强，安全边界越重要。Bridge 层应默认拒绝未知方法和未知参数。

安全边界要同时存在于 H5、Bridge 和原生三层。H5 做输入约束是体验优化，Bridge 做 schema 校验是协议约束，原生做权限和来源校验才是最后防线。不能因为 H5 已经校验过，就让原生跳过安全判断。

容器能力越强，越不能相信“调用方已经处理好了”。在 Hybrid 体系里，H5 永远只是半可信环境，真正的最终判断必须留在宿主能力层。

## 调试与监控

容器能力应记录调用日志。

```txt
method
params 摘要
appVersion
bridgeVersion
resultCode
duration
```

线上排查时，Bridge 调用失败率、耗时、错误码分布很关键。没有监控的容器能力很难治理。

监控里不要记录完整敏感参数，但要保留可定位问题的摘要信息，例如方法名、参数类型、结果码、耗时、App 版本、Bridge 版本、页面来源和包版本。这样既能保护隐私，也能定位故障。

容器能力治理到后面，监控会变得和协议本身一样重要。没有监控，就很难知道哪些能力最常失败、哪些版本最不稳定、哪些页面经常误用能力，团队也就无法持续收敛复杂度。
