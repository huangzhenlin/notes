## 能力边界

React Native 原生模块用于把 iOS/Android 原生能力暴露给 JavaScript，例如蓝牙、定位、相机、文件、加密、系统设置。

```txt
JavaScript 调用 -> 原生模块 -> 系统 SDK -> 返回结果
```

不是所有能力都应该自己写原生模块。优先评估成熟社区库；只有业务定制、性能要求或平台能力缺口明确时，再自定义模块。

原生模块最适合“JS 无法直接完成、但业务又必须依赖”的事情，比如调用系统 SDK、访问硬件能力、对接设备特性。

自定义原生模块的成本不只是一段 iOS/Android 代码，还包括双端实现、权限声明、构建配置、CI 环境、升级兼容和测试矩阵。只要社区库稳定覆盖需求，就不要轻易重写；但涉及内部 SDK、合规能力或强业务协议时，自定义模块会更可控。

原生模块的门槛不在“会不会写一段 Swift 或 Kotlin”，而在“后续能不能长期维护双端一致性”。一旦模块进入项目，它就会跟着 RN 版本、系统版本、权限策略和依赖库一起长期演化。

## JS 调用形态

在 JS 侧，原生模块应该被封装成业务化 API。

```ts
import { NativeModules } from "react-native";

const { DeviceSecurityModule } = NativeModules;

export async function isDeviceSecure() {
  return DeviceSecurityModule.isDeviceSecure();
}
```

页面不应该直接到处调用 `NativeModules.xxx`。封装一层可以统一类型、错误处理、平台差异和降级策略。

```ts
export async function scanQRCode() {
  try {
    const result = await NativeModules.Scanner.scan();
    return normalizeScanResult(result);
  } catch (error) {
    throw normalizeNativeError(error);
  }
}
```

封装层最好输出业务语义，例如 `scanQRCode`、`payOrder`、`chooseAvatar`，而不是暴露底层模块名。这样后续替换社区库、改原生实现或迁移新架构时，页面代码不需要大范围修改。

对页面来说，原生模块最好像一个稳定服务，而不是一组裸露的宿主能力。只要页面直接依赖底层模块名和平台返回结构，后面任何一次原生改造都会放大成业务层变更。

## iOS 与 Android

同一个 JS API 背后通常需要两套原生实现。

```txt
DeviceSecurityModule.ts
  ├─ iOS: Swift / Objective-C
  └─ Android: Kotlin / Java
```

两端返回值、错误码和权限处理要保持一致。不要让 JS 层分别判断一堆 iOS/Android 特有返回结构。

如果平台差异不可避免，最好在原生层统一成同一种返回契约，再交给 JS 层消费。

iOS 与 Android 还可能在权限弹窗、后台行为、文件 URI、图片压缩、系统设置入口上不同。JS 层可以知道平台差异存在，但不应该被迫理解每个平台的底层细节。跨端一致性要尽量在模块边界内解决。

双端一致性不是指实现方式一样，而是指 JS 看到的契约尽量一样。只有契约稳定，RN 页面和组件层才能真正复用，而不会慢慢退化成“一个界面里藏着两套平台分支”。

## 异步返回

原生能力通常通过 Promise 返回。

```ts
try {
  const result = await scanQRCode();
  setCode(result.code);
} catch (error) {
  showError(normalizeNativeError(error));
}
```

原生模块要区分取消、权限拒绝、设备不支持、系统错误。全部返回一个 `failed` 会让业务无法做正确提示。

```ts
type NativeError =
  | { code: "cancelled" }
  | { code: "permission_denied" }
  | { code: "unsupported" }
  | { code: "system_error"; message: string };
```

异步返回还要处理超时和页面销毁。用户扫码时退出页面、支付 SDK 长时间不回调、权限弹窗后应用切后台，这些都会让 Promise 处于尴尬状态。模块封装应明确超时、取消和重复调用策略。

原生模块一旦没有定义清楚取消和超时语义，页面就只能自己补救，最后会出现各页面各写一套 loading、重复点击锁和异常兜底，复杂度很快失控。

## 权限处理

相机、相册、定位、蓝牙、通知等能力都涉及权限。

| 权限结果 | UI 处理 |
| --- | --- |
| 首次询问 | 解释用途后触发系统授权 |
| 用户拒绝 | 展示原因和重试入口 |
| 永久拒绝 | 引导到系统设置 |
| 设备不支持 | 隐藏入口或展示替代方案 |

权限逻辑不要只写在原生侧。JS 层也要知道用户是否可以继续当前流程。对于表单、扫码、拍照、地图这类能力，权限状态本身就是业务流程的一部分。

权限请求最好由用户动作触发，而不是页面打开就弹系统授权。先说明用途，再调用系统权限，失败后提供设置入口或替代方案。权限处理如果只交给原生弹窗，用户很容易不知道为什么要授权。

权限本质上是用户流程的一部分，而不是模块内部的小细节。原生模块负责能力接入，RN 页面仍然要负责把授权理由、失败兜底和后续动作讲清楚。

## 线程与调用频率

高频调用的模块要特别注意线程切换和性能成本。原生调用如果每次都穿过一层重协议，可能会让页面响应变差。

```txt
高频能力示例：
1. 传感器读取
2. 位置更新
3. 蓝牙状态轮询
4. 小动画驱动
```

能批量就批量，能事件推送就别轮询，能在原生侧一次处理完就别每帧都跨桥。

传感器、定位、蓝牙和设备状态这类模块，通常更适合由原生侧控制采样频率，再按业务需要推送聚合结果。JS 侧如果不断轮询，不仅耗电，也会加重桥接通信和 JS 线程负担。

高频原生模块如果没有频率治理，问题往往不仅是性能，还会扩展到电量、发热和后台稳定性。越靠近设备层的能力，越要把调用频率当成设计问题，而不是简单实现问题。

## 新架构影响

React Native 新架构下，Turbo Modules 和 JSI 能减少旧 Bridge 的序列化和异步通信成本。

```txt
旧架构：JS -> Bridge -> Native
新架构：JS -> JSI/TurboModule -> Native
```

性能敏感、调用频繁、需要同步能力的模块更可能受益。但普通业务模块不必为了“新架构”过早重写，先确认项目 RN 版本、库兼容性和团队原生能力。

新架构迁移要看依赖链。一个项目能不能启用 Turbo Modules，不只取决于自研模块，也取决于导航、手势、动画、图片、地图、推送等第三方库是否兼容。迁移前先列清楚依赖清单和回归范围。

原生模块是否值得为新架构重写，也要看实际收益。低频、稳定、能力简单的模块未必是优先项；高频、性能敏感、调用链长的模块通常更值得优先评估。

## 测试重点

原生模块测试不能只测 happy path。至少要覆盖：

- 权限拒绝
- 用户取消
- 设备不支持
- 原生 SDK 抛错
- 页面销毁后回调返回

这些异常路径比成功路径更能体现模块封装质量。

测试还要覆盖双平台一致性。同一个 JS API 在 iOS 和 Android 上应该返回同样结构、同样错误码和相近行为；如果必须不同，文档和类型里要明确说明。否则线上问题会变成“只在某个平台偶现”。

原生模块测试的价值，不只是证明 happy path 能跑通，而是尽早暴露“某个平台某种权限状态下行为不同”这类最难在线上补救的问题。

## 选型判断

如果现成社区库已经覆盖业务需求，优先用成熟库；如果功能需要和业务深度绑定、权限链路复杂、或者要和内部原生 SDK 协同，才考虑自定义原生模块。原生模块不是 RN 的默认答案，它是边界清晰时的加法。

选型时还要看维护状态、RN 新架构支持、平台覆盖、issue 活跃度和原生依赖体积。移动端库一旦接入原生层，升级和排障成本会明显高于普通 JS 包。

原生模块不是默认选项，而是明确边界后的工具。真正值得接入的模块，通常要么能补足 RN 自身能力缺口，要么能稳定封装业务强依赖的原生 SDK，要么能在性能上带来明显收益。
