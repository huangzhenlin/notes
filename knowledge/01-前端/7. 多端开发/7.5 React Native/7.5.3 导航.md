## 原生导航协同

React Native 项目有时会和原生页面共存。此时要处理 RN 页面栈和原生页面栈的关系，尤其是返回、弹窗、tab 切换和登录页。

如果两个导航系统各自维护状态，就容易出现返回错页、重复打开页面或关闭当前容器后状态丢失。

原生导航协同的关键，是约定谁负责最外层页面栈，谁负责 RN 内部页面栈。混合应用里，通常由原生控制应用级入口、登录、支付和系统能力页面，RN 控制业务模块内部的列表、详情、表单和局部流程。

只要这个边界没定清楚，导航问题就会层出不穷。页面明明跳转成功了，但返回链路、关闭行为、登录回跳和原生弹窗又各走各的，最后用户感知到的就是“这个应用有时候不按常理返回”。
## 导航模型

React Native 本身不内置完整导航框架，项目通常使用 React Navigation 或原生导航方案。导航不是简单的页面跳转，它要处理页面栈、底部标签、抽屉、深链、参数、返回手势、状态恢复和原生生命周期。

```text
NavigationContainer
  -> Stack Navigator
    -> HomeScreen
    -> DetailScreen
  -> Tab Navigator
    -> FeedScreen
    -> ProfileScreen
```

移动端导航要尊重平台习惯：iOS 常见右滑返回和底部 Tab，Android 有系统返回键，复杂业务还会有登录拦截、深链进入和多栈切换。

导航层应该被当作应用架构的一部分，而不是 UI 组件。它决定页面能否从通知、分享、推送、原生入口和冷启动恢复，也决定页面参数和状态管理边界。

导航一旦进入真实项目，问题就不再是“这个按钮点了去哪里”，而是“用户从任何入口进来后，能不能走完流程、能不能返回正确位置、进程被回收后能不能恢复”。这就是为什么导航要被当成基础设施，而不是纯页面跳转工具。

## Stack 导航

Stack 导航模拟移动端页面栈。进入详情页是 `push` 或 `navigate`，返回上一页是 `goBack`。页面参数应该保持可序列化，避免把函数、大对象或临时状态塞进路由。

```tsx
import { createNativeStackNavigator } from '@react-navigation/native-stack';

type RootStackParamList = {
  Home: undefined;
  Detail: { id: string };
};

const Stack = createNativeStackNavigator<RootStackParamList>();

export function AppNavigator() {
  return (
    <Stack.Navigator>
      <Stack.Screen name="Home" component={HomeScreen} />
      <Stack.Screen name="Detail" component={DetailScreen} />
    </Stack.Navigator>
  );
}
```

```tsx
function HomeScreen({ navigation }) {
  return (
    <Button
      title="查看详情"
      onPress={() => navigation.navigate('Detail', { id: '1001' })}
    />
  );
}
```

路由参数适合放资源 ID、过滤条件、来源标记这类轻量信息。详情数据应由页面根据 ID 请求或从状态缓存读取，否则页面恢复、深链进入和刷新都会变得困难。

`navigate` 和 `push` 的差异也要清楚。`navigate` 更偏向“到达某个路由”，可能复用已有页面；`push` 更偏向“压入一个新实例”。同一个详情页连续打开不同商品时，如果用错 API，可能出现页面没更新或栈层级异常。

栈导航最容易出问题的地方，就是页面实例语义没想清楚。到底是回到已有页面，还是新开一个页面实例，应该由流程语义决定，而不是哪个 API 看起来更顺手。

## Tab 导航

Tab 导航适合承载应用的一一级入口，如首页、消息、我的。每个 Tab 通常有自己的 Stack，这样用户在某个 Tab 内进入详情后，切换到其他 Tab 再回来仍能保留页面栈。

```tsx
const Tab = createBottomTabNavigator();

function MainTabs() {
  return (
    <Tab.Navigator screenOptions={{ headerShown: false }}>
      <Tab.Screen name="FeedStack" component={FeedStack} />
      <Tab.Screen name="ProfileStack" component={ProfileStack} />
    </Tab.Navigator>
  );
}
```

Tab 不适合放过多入口。移动端底部 Tab 通常控制在 3 到 5 个，更多功能应放入二级页面、个人中心或业务分组里。

每个 Tab 是否保留自己的 Stack，会直接影响用户体验。资讯页进入详情后切到“我的”，再切回资讯页，通常应该还停留在详情；但某些强任务型应用可能希望切回时重置到 Tab 首页。这类行为要作为产品和架构约定，而不是默认交给框架。

Tab 导航设计得成熟时，用户对每个主入口都会形成稳定预期：切出去再回来时会回到哪里、是否保留滚动位置、是否保留详情栈。只要这些行为漂移，应用会显得不可靠。

## 类型约束

TypeScript 项目应给导航参数建模。这样页面跳转时传错参数、读取不存在字段都能在编译阶段暴露。

```tsx
import type { NativeStackScreenProps } from '@react-navigation/native-stack';

type RootStackParamList = {
  Home: undefined;
  Detail: { id: string; from?: 'feed' | 'search' };
};

type DetailProps = NativeStackScreenProps<RootStackParamList, 'Detail'>;

function DetailScreen({ route }: DetailProps) {
  const { id, from } = route.params;
  return <Text>{`${id} from ${from ?? 'unknown'}`}</Text>;
}
```

导航类型不只是代码提示，它能约束跨页面协议。多人协作时，页面参数相当于页面之间的接口，应该像组件 props 一样被认真维护。

类型约束还可以减少深链和通知入口的隐患。只要页面声明了参数类型，打开页面的地方就必须提供必需字段；可选字段也能通过类型提示明确默认逻辑。路由参数越稳定，页面越容易独立测试。

导航类型本质上是在给“页面之间的协议”加约束。页面不是孤立组件，它们之间通过参数和状态链接起来，所以这层协议越明确，协作和重构越安全。

## 深链进入

深链让用户从通知、短信、网页或其他 App 直接进入应用内指定页面。深链配置要把 URL 路径映射到导航树中的页面。

```tsx
const linking = {
  prefixes: ['myapp://', 'https://example.com/app'],
  config: {
    screens: {
      Home: '',
      Detail: 'goods/:id',
    },
  },
};

export function Root() {
  return (
    <NavigationContainer linking={linking}>
      <AppNavigator />
    </NavigationContainer>
  );
}
```

深链进入时，应用可能还没登录、数据缓存为空、导航状态尚未恢复。因此详情页必须能只凭 `id` 完成加载，不能依赖“用户一定从列表点进来”。

深链还要处理非法参数和过期资源。商品下架、活动结束、用户无权限、登录态失效时，页面要能展示合理兜底，而不是因为参数解析失败停在空白页。深链页面天然是外部入口，必须比普通内部跳转更健壮。

能被深链打开的页面，应该默认按“冷启动页面”来设计。它不能假设前一个页面一定存在，也不能假设本地缓存一定齐全，更不能假设用户已经完成登录和初始化。

## 返回行为

Android 有系统返回键，iOS 有导航栏返回和侧滑手势。React Native 项目要明确哪些页面允许返回、哪些页面返回时要确认、哪些页面返回时要清理临时状态。

```tsx
import { BackHandler } from 'react-native';
import { useFocusEffect } from '@react-navigation/native';

function EditScreen() {
  useFocusEffect(() => {
    const subscription = BackHandler.addEventListener('hardwareBackPress', () => {
      // 有未保存内容时拦截返回。
      return true;
    });

    return () => subscription.remove();
  });
}
```

返回拦截要慎用。拦截系统返回却不给用户明确提示，会让应用显得“卡住”。表单、支付、上传这类不可中断流程才适合增加确认。

Android 返回键要和导航栈、弹窗、底部面板、选择器一起协调。常见优先级是先关闭弹层，再退出当前编辑态，再执行页面返回，最后才退出应用。所有返回都直接 `goBack`，会让复杂页面体验很粗糙。

返回设计得好的应用，用户几乎不会注意到它；返回设计得差的应用，用户会频繁感到困惑。系统返回、导航栏返回、手势返回、弹层关闭其实都是同一套交互决策链。

## 状态恢复

移动系统可能在后台回收应用进程。导航状态恢复可以让用户回到之前页面，但前提是路由参数可序列化，页面能根据参数恢复数据。

| 不稳定做法 | 更稳做法 |
|---|---|
| 路由传完整商品对象 | 只传 `id`，页面重新加载 |
| 路由传回调函数 | 使用全局事件或状态管理 |
| 页面依赖上一个页面内存状态 | 从缓存或接口恢复 |

React Native 导航和 [[7.5.4 原生模块|原生模块]] 也有关：通知点击、分享回跳、支付回调这类原生入口，最终都要落到可恢复的导航路径上。

状态恢复还要求页面副作用可重复执行。应用从后台恢复后，页面可能重新挂载，也可能只恢复导航状态；请求、订阅、计时器和缓存读取都要能适应这两种情况。只把数据存在组件内存里，进程被杀后就无法恢复。

导航恢复真正可用的前提，是页面本身具备“按参数自恢复”的能力。只要页面高度依赖前一页传来的完整对象、函数回调或瞬时内存状态，进程恢复和深链进入都会变得很脆弱。
