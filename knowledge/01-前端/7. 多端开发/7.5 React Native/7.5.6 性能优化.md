## 列表虚拟化

长列表优先使用 `FlatList`、`SectionList`，并提供稳定 key。

```tsx
<FlatList
  data={messages}
  keyExtractor={(item) => item.id}
  renderItem={({ item }) => <MessageItem message={item} />}
  initialNumToRender={12}
  windowSize={7}
  removeClippedSubviews
/>
```

`initialNumToRender`、`windowSize`、`maxToRenderPerBatch` 会影响首屏速度、滚动流畅度和内存占用。不要盲目调大，应该结合真实设备测试。列表过长时，优先考虑虚拟化而不是一次性渲染。

列表优化要先确认卡顿来自哪里：首屏渲染慢，可能是初始渲染数量过多；滚动掉帧，可能是 item 过重或图片解码；快速滑动空白，可能是窗口太小或批量渲染太慢。不同现象对应不同参数，不要一套配置到处复制。

列表优化最怕从参数开始调。更稳的顺序通常是先把 item 做轻、把图片做稳、把状态范围收小，再去调窗口和批量参数。否则即使参数调对了，复杂 item 仍然会把性能吃掉。

## 组件重渲染

列表项和复杂组件要避免因父组件状态变化而全部重渲染。

```tsx
const MessageItem = memo(function MessageItem({
  message,
}: {
  message: Message;
}) {
  return <Text>{message.text}</Text>;
});
```

`memo` 只有在 props 稳定时才有价值。如果每次渲染都创建新对象、新数组、新函数，仍然会触发更新。先稳定数据结构，再考虑缓存组件。对列表场景来说，重渲染往往比很多人以为的更贵。

组件重渲染要结合状态归属看。页面级状态变化如果传给每个列表项，会让所有 item 都收到新 props；把 item 需要的字段裁剪清楚，能减少无关更新。`memo` 是最后一道优化，不是替代状态设计的万能工具。

很多 RN 性能问题本质上不是“框架太慢”，而是状态边界没收好。只要父组件一动，整棵子树都跟着抖，后面再靠 `memo` 和缓存补救，收益通常有限。

## 图片资源

移动端图片会直接影响内存、网络和滚动性能。

| 问题 | 优化方向 |
| --- | --- |
| 原图过大 | 服务端裁剪或 CDN 参数 |
| 列表图片闪烁 | 占位图、缓存、固定尺寸 |
| 内存上涨 | 控制同时展示数量 |
| 加载慢 | WebP/AVIF、渐进加载、预取 |

图片组件要有稳定宽高，避免加载后布局跳动。图片列表还要避免一次性渲染过多远程图片。Android 和 iOS 对图片解码、内存回收和动画流畅度的表现并不完全一致。

图片优化最好从资源源头开始：服务端裁剪到展示尺寸，CDN 根据 DPR 输出合适资源，客户端固定容器比例，列表中显示缩略图，详情页再加载大图。只在前端压缩或隐藏大图，网络和解码成本仍然已经发生。

图片是 RN 页面里最容易同时拖慢首屏、滚动和内存的一类资源。只要列表、卡片流和详情页都依赖大量远程图片，图片策略就应该被当成架构问题，而不是某个组件的小优化。

## JS 线程

JS 线程承担 React 渲染、业务逻辑和部分事件处理。长时间同步计算会造成点击迟钝、动画卡顿。

```tsx
const visibleItems = useDeferredValue(keyword)
  ? filterItems(items, keyword)
  : items;
```

大型筛选、JSON 处理、加密压缩、复杂图表计算都要谨慎。可以考虑分页、懒计算、后台线程、原生能力或减少同步工作量。JS 线程一旦被占满，页面看起来就会“掉帧”和“按了没反应”。

JS 线程问题通常会表现为点击延迟、输入卡顿、导航切换慢和动画不跟手。排查时可以先用真机录屏和性能工具确认是否有长任务，再决定是拆分计算、延后执行、移到原生侧，还是减少一次性渲染量。

RN 优化时不要只盯着 JS。很多卡顿其实来自渲染树过大、列表项过重、图片解码或不必要的组件重渲染。JS 线程只是最显眼的一层。

JS 线程优化真正有效的时候，通常不是“把一段代码写得更聪明”，而是减少本来就不该在这一层发生的工作。筛选、加密、批量转换和高频事件聚合都要先问一句：一定要同步发生在 JS 线程里吗。

## 动画性能

动画尽量使用能在 UI 线程执行的方案，例如 Reanimated。频繁依赖 JS 线程驱动的动画更容易被业务计算阻塞。

```tsx
const animatedStyle = useAnimatedStyle(() => ({
  transform: [{ translateY: offset.value }],
}));
```

手势、拖拽、联动动画要重点关注低端 Android 设备。只在模拟器或高端机上验证，容易低估卡顿。React Native 的动画性能通常不是“动画 API 不够”，而是“渲染频率和线程分工没有设计好”。

手势联动动画尤其要避免每帧经过 JS 状态更新。拖拽、吸附、卡片滑动、底部面板这类交互，如果依赖 JS 线程实时计算，一旦页面同时请求数据或更新列表，就容易掉帧。优先使用能在 UI 线程执行的动画方案。

手势复杂的页面，最好减少同时进行的数据请求和状态更新。交互正在进行时如果又触发了大规模列表刷新，JS 和 UI 线程都会更吃紧。

动画能不能顺，不只取决于动画库，也取决于页面当时是不是还在做别的重活。很多“动画卡”的根因，其实是动画发生时同时做了大渲染、大请求或大计算。

## 原生配合

有些重任务更适合交给原生模块、图像库或专门的本地能力。

```text
JS 负责交互
原生负责解码、压缩、批量计算或复杂绘制
```

如果一段逻辑既重又频繁，还在 JS 线程里做，优化空间通常比想象中大。性能优化不是一定要“更聪明”，有时只是把任务放到更合适的线程和层级。

原生配合也要控制边界。把所有逻辑都丢给原生，会让调试和迭代变慢；只把重计算、系统 SDK、图片处理、加密压缩和高频设备能力下沉，才能在性能和维护性之间保持平衡。

如果某个能力频繁触发且逻辑稳定，适合下沉；如果能力变化快、和页面状态强耦合，就不适合过早搬到原生。边界感比“尽量原生化”更重要。

性能优化里的原生配合，目标不是追求“越多原生越好”，而是把最重、最稳定、最靠近设备的工作放到更合适的位置。下沉得对，性能会上来；下沉得乱，维护成本会先上来。

## 性能定位

优化前先定位瓶颈。常用线索包括 React DevTools Profiler、RN 性能监控、原生平台 profiler、日志和真机录屏。

```txt
是否首屏慢
是否滚动掉帧
是否点击响应慢
是否内存持续增长
是否只在某个平台发生
```

不同问题对应不同方向。首屏慢关注包体、初始化和请求；滚动卡关注列表、图片和渲染；点击慢关注 JS 线程和同步任务。先确认问题在 JS、UI 还是原生层，再动手改代码。

RN 的性能验证一定要看真机，而且最好看低端机。模拟器和高端设备都可能把问题掩盖掉。

性能优化完成后要用同一设备、同一路径、同一数据量复测。React Native 性能非常依赖真机、数据规模和平台差异，只在模拟器或开发环境里看结果，很容易误判优化效果。

性能定位做到位时，团队会先回答“慢在哪一层、哪种设备最明显、是偶发还是稳定复现”，再决定优化手段。只要问题还没被归类清楚，就不要急着堆优化技巧。
