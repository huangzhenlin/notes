## 组件模型

React Native 的核心思想，是用 JavaScript 或 TypeScript 描述界面，再把这些界面映射到原生视图。对前端来说，它保留了 React 的组件思维，但渲染目标不再是 DOM，而是 iOS 和 Android 的原生组件。

React Native 组件写起来像 React，但不能把它当成“移动端浏览器”。没有 DOM、没有完整 CSS、没有浏览器事件模型，布局、文本、图片、滚动、输入和触摸都有对应原生组件与平台差异。

```txt
React 组件树
  -> React Native 渲染器
  -> 原生视图树
  -> iOS / Android UI
```

这种模型的优势是复用 React 的组件组织方式，同时获得更接近原生的交互体验；代价是开发者必须理解移动平台、原生视图和 Bridge / JSI 等运行边界。

对 Web 前端来说，最需要调整的心智不是 JSX 写法，而是“组件最终会落到什么宿主上”。同样是 `<View>`、`<Text>`、`<Image>` 这些声明，背后对应的是原生视图树和移动系统行为，而不是浏览器排版和 DOM 事件。

## View

`View` 是 React Native 中最基础的容器组件，类似 Web 中的 `div`，但它渲染到原生视图而不是 DOM。

```tsx
import { View, Text, StyleSheet } from "react-native";

export function ProfileCard() {
  return (
    <View style={styles.card}>
      <Text style={styles.title}>Ada Lovelace</Text>
      <Text style={styles.description}>移动端开发者</Text>
    </View>
  );
}

const styles = StyleSheet.create({
  card: {
    padding: 16,
    borderRadius: 12,
    backgroundColor: "#fff",
  },
  title: {
    fontSize: 18,
    fontWeight: "600",
  },
  description: {
    marginTop: 4,
    color: "#666",
  },
});
```

`View` 适合做页面容器、卡片、布局区域和交互区域。不要把它用成万能组件：文本必须放在 `Text` 里，长列表要用列表组件，点击区域要用 `Pressable` 或合适的触摸组件。

`View` 和 Web 里的 `div` 只是“角色上相似”，不是“能力上相同”。它没有 DOM 属性、没有浏览器默认布局语义，也没有很多 Web 上顺手可用的细节能力，所以组件抽象时要从原生视图约束出发，而不是从 Web 习惯出发。

## Text

所有文本都必须放在 `Text` 组件中，不能像 Web 一样把字符串直接放到任意容器里。

```tsx
<Text>
  你好，<Text style={{ fontWeight: "700" }}>React Native</Text>
</Text>
```

`Text` 可以嵌套，用于局部加粗、变色或增加链接样式。文本样式不会像 Web 那样通过普通容器自然继承到所有后代，写样式时要按 RN 的规则验证。

文本还要考虑系统字体、动态字体、换行、省略和可访问性。商品标题、按钮文字、错误提示、协议链接这些内容，不仅要显示出来，还要在不同字号、语言长度和系统字体设置下保持可读。

文本组件在移动端往往比 Web 更敏感。字号放大、系统语言切换、无障碍字体、按钮宽度限制、长文案省略都会直接影响布局，所以文本不只是“样式”，也是布局系统的一部分。

## Image

`Image` 用于展示本地或远程图片。远程图片通常需要明确宽高。

```tsx
import { Image } from "react-native";

<Image
  source={{ uri: "https://example.com/avatar.png" }}
  style={{ width: 64, height: 64, borderRadius: 32 }}
/>
```

本地图片通过 `require` 引入。

```tsx
<Image source={require("./assets/logo.png")} />
```

图片性能和加载体验在移动端很重要。列表中的大量图片要考虑尺寸裁剪、缓存、占位图和懒加载策略。远程图片最好由服务端或 CDN 提供适合当前设备的尺寸，不要把原图直接塞进长列表。

图片在 RN 里经常同时影响流量、解码、内存和滚动性能。页面看起来像“列表有点卡”，根因却可能是图片体积过大、尺寸不稳定或组件频繁重绘，所以图片策略最好从一开始就和列表方案一起设计。

## ScrollView 与 FlatList

`ScrollView` 会一次性渲染所有子元素，适合内容较少的滚动页面；长列表优先使用 `FlatList`。

```tsx
import { FlatList } from "react-native";

<FlatList
  data={products}
  keyExtractor={(item) => item.id}
  renderItem={({ item }) => <ProductCard product={item} />}
/>
```

`FlatList` 支持虚拟化，只渲染屏幕附近的内容。商品列表、聊天消息、动态流这类场景不要用 `ScrollView` 硬撑。列表性能通常取决于 item 是否轻量、key 是否稳定、图片是否合理、是否避免在滚动时触发大量状态更新。

如果列表项高度固定，可以提供 `getItemLayout` 减少测量成本；如果列表项复杂，可以把 item 组件拆小，并避免把整个页面状态传给每一项。

长列表优化最怕一开始就用 `ScrollView` 图省事，后面再补救会越来越难。只要数据规模有增长可能，优先按 `FlatList` 的心智来组织 item、key、分页和图片加载，后续扩展空间会更大。

## Pressable

`Pressable` 是更灵活的触摸组件，可以根据按压状态改变样式。

```tsx
import { Pressable, Text, StyleSheet } from "react-native";

<Pressable
  onPress={submit}
  style={({ pressed }) => [
    styles.button,
    pressed && styles.buttonPressed,
  ]}
>
  <Text style={styles.buttonText}>提交</Text>
</Pressable>
```

移动端交互要考虑按压反馈、禁用状态、可点击区域和无障碍标签。不要只把 Web 的点击思路搬过来。一个看起来像按钮的组件，应同时具备视觉反馈、禁用逻辑、加载状态和可访问性语义。

```tsx
<Pressable
  accessibilityRole="button"
  accessibilityLabel="提交订单"
  disabled={submitting}
  onPress={submit}
>
  <Text>{submitting ? "提交中..." : "提交订单"}</Text>
</Pressable>
```

触摸组件不只是“把点击接上”。它还承担按压反馈、禁用态、手势竞争、可访问性语义和可点击热区这些责任。移动端里一个按钮是否好用，很多时候不取决于视觉，而取决于这些细节有没有一起做好。

## TextInput

`TextInput` 用于输入文本、手机号、搜索词和验证码。它和 Web 的 `<input>` 类似，但键盘、焦点、自动填充、输入法和平台样式差异更明显。

```tsx
import { TextInput } from "react-native";

<TextInput
  value={phone}
  onChangeText={setPhone}
  keyboardType="phone-pad"
  textContentType="telephoneNumber"
  placeholder="请输入手机号"
/>
```

移动输入要和键盘避让、表单校验、自动填充一起考虑。验证码、手机号、金额和搜索框适合设置不同的 `keyboardType`，但最终合法性仍然要由业务校验保证。

`TextInput` 的难点也往往不在“能不能输入”，而在输入法、焦点、键盘、自动填充和平台差异叠在一起后的整体体验。登录页、搜索页、地址表单、验证码页都应该在真机上单独过一遍输入路径。

## Modal

`Modal` 用于展示覆盖当前界面的弹层。它在移动端更接近原生弹窗或全屏覆盖层，而不是 Web 里随便放一个绝对定位元素。

```tsx
import { Modal, View, Text, Button } from "react-native";

<Modal visible={visible} animationType="slide" onRequestClose={close}>
  <View style={{ flex: 1, padding: 24 }}>
    <Text>确认提交？</Text>
    <Button title="关闭" onPress={close} />
  </View>
</Modal>
```

Android 上 `onRequestClose` 很重要，因为系统返回键需要知道如何关闭弹窗。弹窗里还要处理焦点、遮罩、返回、滚动和安全区，否则容易出现无法关闭、内容被遮挡或返回行为混乱。

Modal 在移动端比 Web 更接近“真正的界面层级切换”。它不仅遮住内容，还可能改变返回行为、焦点顺序和系统手势体验，所以弹层设计要同时考虑平台返回和宿主导航。

## Platform

同一组件在 iOS 和 Android 上可能需要差异化处理。

```tsx
import { Platform } from "react-native";

const shadowStyle = Platform.select({
  ios: {
    shadowColor: "#000",
    shadowOpacity: 0.12,
    shadowRadius: 8,
  },
  android: {
    elevation: 4,
  },
});
```

平台分支要收口在少数地方。大量散落的 `Platform.OS` 会让组件难以维护，也容易造成两个平台行为漂移。更好的方式是封装平台适配组件、主题变量或能力函数，让业务组件尽量保持一致。

平台差异不可避免，但不应该无序扩散。只要 `Platform.OS` 到处都是，组件很快就会从“跨平台组件”退化成“一个文件里塞了两套实现”，后续测试和维护成本都会上升。

## 组合方式

React Native 依然强调组件组合。界面应该拆成可复用、职责单一的组件，数据通过 props 传递，事件通过回调或状态管理流转。

和 Web 不同的是，组件树最终会被转换为原生视图树，布局和性能问题会更多地受原生侧影响。一个界面需要大量原生级交互时，React Native 的组件模型通常比 WebView 更接近宿主体验，但也要求开发者理解原生组件边界。

组件拆分时要关注三件事：输入是否清楚、输出事件是否稳定、内部状态是否局部。页面级导航、请求编排和业务状态不应该塞进通用 UI 组件；而卡片、列表项、表单项、空状态和弹层适合做成可复用组件。

React Native 组件体系写得成熟时，页面更像业务编排层，组件更像原生友好的 UI 单元。这样无论后面接状态管理、导航、原生模块还是性能优化，边界都会更稳定。
