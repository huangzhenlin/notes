## 桥接职责

原生桥接负责让 JavaScript 和原生平台互相调用。它连接的是两套运行时，而不是普通函数调用。

```txt
JavaScript Runtime <-> Bridge/JSI <-> Native Runtime
```

桥接适合访问平台能力、复用原生 SDK、处理性能敏感逻辑。普通业务状态和页面逻辑不应该下沉到原生层。桥接越轻，JS 和 Native 的责任边界就越清楚。

判断一个能力是否需要桥接，可以看三个问题：Web/JS 是否做不了，是否强依赖系统或原生 SDK，是否对性能和线程有特殊要求。扫码、支付、蓝牙、相机、文件、加密和设备安全适合桥接；普通表单校验、页面状态、数据格式化不应该为了“看起来原生”下沉。

桥接层最重要的不是“能连通”，而是“边界清楚”。只要普通业务逻辑开始顺手往原生里塞，后面双端发布、联调、测试和回滚的复杂度就会迅速上升。

## 版本协议

桥接接口要有版本意识。页面代码、原生容器和业务 SDK 可能处在不同版本，如果没有协议兼容，就会出现新页面调用旧容器能力失败的问题。

常见做法是给桥接能力增加能力检测或版本检测，而不是默认所有接口都存在。

```ts
if (NativeModule?.version >= 2) {
  NativeModule.openPicker({ multiple: true });
}
```

如果协议会演进，最好先定义向后兼容原则：新增字段默认可选、旧字段保留一段时间、错误码可扩展但不随意重命名。桥接协议一旦不稳定，后续联调和回滚都会很痛苦。

版本协议最好和能力检测一起出现。只比较版本号容易被灰度包、渠道包和热修复打破；按能力探测则更接近真实可用性。JS 调用前知道能力是否存在，原生执行前再校验参数和权限，双侧都能更稳。

版本协议真正要解决的是“新 JS 跑在旧容器上还能不能安全工作”。只要这个问题没提前考虑，线上迟早会出现页面升级后某个原生能力突然不可用的事故。

## 通信成本

旧架构 Bridge 需要序列化数据并跨线程通信，频繁调用会有成本。

```ts
for (const item of items) {
  NativeModule.trackItem(item);
}
```

这种逐条调用应该改成批量调用。

```ts
NativeModule.trackItems(items);
```

桥接设计要减少调用次数、控制数据体积、避免高频同步依赖。小数据、高频次、强实时的场景最容易暴露通信成本。

通信成本不只来自数据大小，也来自调用频率和线程切换。埋点、传感器、滚动位置、蓝牙状态这类高频场景，应优先批量、节流或由原生侧聚合后再通知 JS。每帧跨桥传数据通常都是危险信号。

桥接性能问题经常不是单次调用太慢，而是“看起来每次都不重，但数量太多”。只要高频路径里不断发生跨桥，页面交互迟早会开始掉帧或迟钝。

## 数据协议

桥接参数应使用简单、可序列化、稳定的结构。

```ts
type SharePayload = {
  title: string;
  url: string;
  imageUrl?: string;
};
```

不要传复杂类实例、函数、循环引用或平台特有对象。JS 和原生之间要像接口协议一样设计类型。

```text
建议：
1. 只传必要字段
2. 参数名语义稳定
3. 错误码可枚举
4. 返回值可序列化
```

数据协议还要控制“平台差异泄漏”。比如 iOS 和 Android 的相机返回字段不同，最好在原生层归一化成同一个 JS 契约。否则 JS 业务层会散落大量平台判断，后续维护会越来越像写两套应用。

协议如果没有在模块边界内统一，复杂度就会流到页面层。页面越知道原生细节，跨端组件和业务逻辑就越难保持一致，最后 React Native 的“跨平台”优势会被一点点吃掉。

## 错误处理

原生错误需要转成 JS 可理解的错误码。

```ts
try {
  await NativePayment.pay({ orderId });
} catch (error) {
  if (error.code === "PAY_CANCELLED") {
    return;
  }

  showToast("支付失败");
}
```

取消、权限拒绝、设备不支持、SDK 初始化失败、网络失败要区分。统一错误码能让业务层稳定降级。

如果错误全部被折叠成一个“失败”，业务就只能靠猜。桥接层应该承担一部分“翻译错误语义”的责任。

错误语义要服务用户路径。用户取消支付通常不需要弹错误，权限拒绝需要授权引导，设备不支持需要隐藏入口或展示替代方案，SDK 初始化失败则要上报并允许重试。错误码越清晰，页面越不需要写脆弱的字符串判断。

桥接层成熟时，页面看到的应该是“能直接参与业务判断的错误语义”，而不是一堆来自原生 SDK 的模糊异常文本。只有这样，JS 侧才能把用户体验和监控都做稳定。

## 线程边界

原生模块可能运行在不同线程。耗时任务不要阻塞 UI 线程，回调 JS 时也要注意线程切换。

```txt
UI 操作 -> 主线程
文件/网络/计算 -> 后台线程
结果回调 -> JS 可接收的线程上下文
```

原生桥接问题经常表现为卡顿、闪退或回调丢失。设计时就要明确线程和生命周期。

生命周期也属于线程边界的一部分。页面已经卸载、应用进入后台、原生 Activity/Controller 被销毁后，迟到的回调不应该再更新已不存在的 JS 状态。桥接封装要能取消请求、清理监听，并在页面失焦时停止高频事件。

线程边界一旦处理不好，问题通常不会表现成“接口不通”，而是更隐蔽的卡顿、偶发闪退、回调丢失和页面卸载后仍然更新状态。这类问题越往后修，成本越高。

## 新架构迁移

Turbo Modules 和 JSI 改变了桥接方式，但协议设计仍然重要。

| 关注点 | 旧架构 | 新架构 |
| --- | --- | --- |
| 通信 | Bridge | JSI/TurboModule |
| 类型 | 手动约定 | Codegen 更强 |
| 性能 | 序列化成本较高 | 更直接 |
| 迁移成本 | 低 | 依赖库兼容 |

迁移前要盘点自定义模块、第三方原生库、构建脚本和测试覆盖。不要只打开开关就上线。

新架构能改善一部分通信模型，但不会自动修复糟糕协议。方法太多、参数不稳、错误码混乱、权限缺失这些问题，在新架构下依旧存在。迁移前先把协议边界理清，迁移才不会变成“换了底层但复杂度还在”。

所以迁移新架构时，最值得先整理的往往不是代码生成开关，而是桥接 API 本身：哪些方法真的需要保留，哪些参数该收敛，哪些错误语义该统一，哪些能力该改成模块边界内吸收平台差异。

## 设计判断

如果一个能力是“高频、跨平台、协议简单”的，桥接可以做得更薄；如果一个能力是“低频、复杂、强依赖原生”，桥接层就要多承担校验、封装和兼容责任。桥接的好坏，不看它有多炫，而看它能不能把复杂性关在最小范围内。

好的桥接层应该让业务页面像调用普通异步函数一样使用原生能力，同时让原生侧保留安全、权限、线程和版本控制。JS 不应该知道太多原生细节，原生也不应该把不可信参数直接执行。

桥接设计最终衡量的不是“做了多少原生封装”，而是“有没有把复杂性稳定关在最小边界里”。这一点做好了，RN 页面写起来才会真的像前端开发，而不是像在远程操控两套原生应用。
