## 发布对象

Electron 打包需要分别面向 Windows、macOS、Linux 生成不同产物。

发布对象不只是“系统”，还包括“用户安装习惯”和“分发场景”。面向企业内部分发，可能更关心静默安装、代理和签名；面向公众分发，则更关心安装包体积、自动更新和首次启动体验。

```txt
Windows: exe / msi / nsis
macOS: dmg / pkg
Linux: AppImage / deb / rpm
```

不同平台的安装方式、签名要求、自动更新机制都不一样。桌面发布不是把 Web 资源压缩一下这么简单。发布前要先确认目标平台、CPU 架构、分发渠道和更新方式。

同一套代码打包成不同产物时，真正变化的不只是文件后缀，还有安装目录、快捷方式、启动参数和权限模型。比如 macOS 的公证、Windows 的 UAC、Linux 的桌面文件和包管理器行为，都会影响最终发布策略。

如果项目同时面向个人用户和企业客户，发布对象还会继续细分成在线安装包、离线安装包、便携版、商店版等不同形态。不同形态背后的更新方式、依赖预装、安装权限、日志采集策略都可能不同，所以发布目标最好在项目早期就定清楚。

## 构建内容

打包产物通常包含 Electron 运行时、主进程代码、渲染进程资源、preload、原生依赖和配置。

构建内容要按职责分层看：主进程负责生命周期和系统能力，preload 负责安全桥接，渲染资源负责界面，原生依赖负责少量底层能力。任何一层出问题，表现出来都可能是“打不开”“白屏”“菜单没反应”“更新失败”，所以排障时要先分层定位。

```txt
main.js
preload.js
renderer assets
package metadata
native modules
icons
```

构建时要区分主进程和渲染进程。前端构建成功，不代表 Electron 主进程入口、preload、原生依赖都能正常打包。很多问题只会在安装包里出现，例如 preload 路径错误、资源路径错误、原生模块缺失。

很多团队会在 CI 里同时产出至少两类检查结果：一类是构建产物本身，一类是安装后的启动验证。前者检查有没有漏文件，后者检查能不能真正跑起来。只看 `npm run build` 远远不够。

如果使用 Vite、Webpack 之类工具构建渲染层，还要明确主进程和 preload 是否走同一套构建链。它们的目标环境、模块格式、产物路径常常不同，混用后最容易出现“开发能跑、打包白屏”的问题。

## 签名与权限

桌面应用常涉及代码签名、权限声明和安全校验。尤其 macOS 和 Windows，对未签名应用可能有明显提示或限制。

签名系统不是形式主义，它直接影响用户是否愿意安装、系统是否允许更新、企业管控是否放行。很多时候应用本身没问题，卡住的是证书链、时间戳、证书过期或构建机上的签名工具配置。

| 平台 | 关注点 |
| --- | --- |
| macOS | Developer ID、notarization、公证 |
| Windows | 代码签名证书、SmartScreen |
| Linux | 包格式和仓库信任 |

签名不是最后一步才考虑的事情。证书、CI 环境、密钥管理和发布流程要提前设计。签名也影响自动更新、企业分发和用户信任。

如果项目里有多个发布渠道，最好把签名证书、发布仓库、更新服务和构建参数一起纳入版本管理。否则一旦某个渠道证书失效，回溯起来会非常痛苦。

签名链路还要和构建环境隔离开。最怕的是开发机手工签过一次能用，到了 CI 或换了构建机器就彻底跑不通。真正可维护的发布流程应该能稳定复现签名、公证、上传和校验结果，而不是依赖某台“神奇电脑”。

## 环境差异

打包后的应用和开发环境差异很大：

- 文件路径不同
- 资源位置不同
- 调试工具受限
- 自动更新逻辑生效
- 系统权限更真实

所以打包后必须做安装包级别验证。开发环境里能打开页面，不代表打包后 `app.asar`、资源路径、用户数据目录和原生模块都正常。

尤其要注意相对路径和工作目录。开发时很多路径看起来是相对当前项目，打包后却是相对安装目录或资源目录。最稳的做法是把“静态资源”“运行时数据”“临时文件”分别定位到各自的系统路径。

环境差异还体现在系统权限和安全策略上。开发时你常常以管理员身份、在完整开发环境里运行；用户机器上却可能是普通权限、受公司策略限制、没有调试工具、甚至离线。打包验证的意义，就是提前把这些差异暴露出来。

## 原生依赖

Electron 项目如果使用原生 Node 模块，打包时要特别注意 ABI、平台架构和重编译问题。开发环境能运行，不代表打包后在所有系统上都能运行。

原生依赖最大的风险是“看起来只是一个 npm 包，实际却和平台强绑定”。一旦依赖编译失败、ABI 不匹配或系统缺少运行库，问题会在用户机器上直接爆出来。

需要重点验证：

- Windows、macOS、Linux 是否都能安装
- x64、arm64 架构是否兼容
- 原生模块是否正确随包分发
- 安装目录和运行权限是否正常

原生依赖越多，发布矩阵越复杂。能用纯 JS 或系统 API 解决的能力，不要轻易引入难维护的原生模块。

如果不得不使用原生模块，最好把它们收敛到少数能力上，并在启动阶段提前探测可用性。这样当模块缺失时，可以给出明确错误，而不是让应用在深层调用时才崩掉。

## 自动更新

桌面应用通常需要自动更新能力。更新流程要包含版本检测、下载、校验、安装和回滚。

发布到生产环境以后，更新链路本身就是产品的一部分。它不只是“拉个新包”，而是用户能否平稳从旧版本迁到新版本的核心路径。

```txt
检查版本 -> 下载更新包 -> 校验签名 -> 提示或静默安装 -> 重启生效
```

自动更新必须使用 HTTPS 和签名校验。更新包一旦被篡改，风险相当于分发恶意桌面程序。自动更新还要和版本、渠道、灰度和回滚一起设计，不能只看“能下载新包”。

还要考虑用户是否正在编辑文档、导入文件或进行关键操作。桌面端比网页更容易出现“重启更新导致未保存内容丢失”的问题，所以更新时机最好由应用掌握，而不是固定死在某个时间点。

如果应用面向企业环境，还要准备自动更新失败时的备用方案，例如离线安装包、管理员集中分发或内网镜像源。把更新链路完全押在公网自动下载上，通常扛不住真实企业环境的复杂性。

## 资源路径

开发环境和打包环境的路径不同。不要依赖相对路径猜测资源位置。

资源路径问题几乎是 Electron 打包里的高频坑。开发时 `__dirname`、Vite 的静态资源路径、preload 的加载路径都能跑，打包后只要有一层路径不对，就会出现白屏、图标丢失或 preload 不生效。

```ts
const preloadPath = path.join(__dirname, "preload.js");
```

读写用户数据应使用 `app.getPath("userData")` 等系统路径。不要把运行时数据写进安装目录，尤其是 macOS 和 Windows 受权限限制时会失败。渲染资源、preload、图标、配置和用户数据要分清“随包资源”和“运行时数据”。

如果应用支持多用户或多配置文件，`userData` 下也要继续分层，不要把所有状态写到一个大 JSON 里。缓存、日志、配置、最近文件和草稿最好分开，方便清理和迁移。

图标、语言包、预置模板、数据库初始化文件这类资源也要尽量统一寻址。最怕的是有些资源走打包路径，有些资源走开发路径，最后排查时完全不知道当前进程到底读的是哪一份文件。

## 发布流程

发布通常包括构建、签名、安装验证、上传、灰度、更新和回滚。桌面应用不像网页那样部署即生效，用户版本分布会长期存在。

桌面发布更像“软件交付链路”，而不是“静态资源发布”。只要某个版本安装到了用户机器上，它就会长期存在，所以发布前的验证质量直接决定后续支持成本。

```text
构建产物
签名与公证
安装验证
上传发布通道
灰度放量
监控崩溃和启动
必要时回滚
```

每个版本都应能追溯源码提交、构建环境、签名证书、发布通道和更新元数据。没有版本链路，线上问题会很难定位。

建议至少保留三类记录：构建日志、安装包清单、更新服务版本表。这样当用户反馈“更新后打不开”时，能快速确认是构建问题、签名问题还是更新服务问题。

## 发布验证

发布前要在真实系统上安装验证。

验证不只是“能不能装上”，还要看安装后能不能卸载、能不能升级、能不能保留用户数据、能不能恢复旧版。桌面应用的发布问题很多都出在生命周期后半段。

```txt
首次安装
覆盖安装
自动更新
卸载清理
离线启动
文件关联
权限弹窗
杀毒软件拦截
```

Electron 应用的很多问题只在打包后出现，例如路径、签名、preload 加载、原生模块和自动更新。只跑开发环境不够。发布验证应该覆盖全新安装、旧版本升级、无网启动、低权限用户和多系统架构。

如果项目允许，最好在一台干净机器或虚拟机里做发布冒烟测试。这样能更接近真实用户环境，也更容易发现“构建机上没暴露、安装后才出现”的问题。

验证时还可以把“崩溃恢复”和“错误可解释性”一起纳入检查。也就是说，不只是确认功能成功时能走通，还要确认签名失败、更新失败、目录不可写、配置损坏时，应用能不能给出可理解的提示和可执行的下一步。
