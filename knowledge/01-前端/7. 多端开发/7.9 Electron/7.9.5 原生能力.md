## 能力入口

Electron 的原生能力主要由主进程提供，例如文件、菜单、托盘、通知、剪贴板、系统对话框、协议唤起、自动更新。渲染进程不应该直接拥有 Node.js 和系统权限，通过主进程封装能力，再由 preload 暴露安全 API，是更稳的边界。

原生能力越强，越不能把它当成“页面 API”。一旦渲染进程能随意触达文件系统、剪贴板或外部链接，应用就会从“网页壳”退化成“带浏览器的系统权限入口”。更稳的方式是按业务场景拆能力，例如“导出报告”“打开本地文件”“打开系统设置”，而不是直接暴露 `readFile`、`writeFile` 这类底层方法。

```ts
import { dialog, ipcMain } from "electron";

ipcMain.handle("file:open", async () => {
  const result = await dialog.showOpenDialog({
    properties: ["openFile"],
  });

  return result.filePaths[0] ?? null;
});
```

原生能力的设计原则是“用户明确触发、主进程受控执行、渲染进程只拿业务结果”。不要为了方便让页面拿到底层系统 API。

如果能力会影响系统状态，就要补充两层约束：一层是参数校验，一层是权限收口。前者解决“传什么”，后者解决“谁能传”。例如同样是打开文件，业务上可能只允许当前工作区内的目录，或者只允许特定扩展名。能力入口越少，后续审计和排障也越轻松。

判断一个原生能力该不该暴露时，可以先问三个问题：它是不是必须依赖桌面系统、它能否在主进程完全闭环完成、它是否能被收敛成单一业务动作。只要其中有一项答不上来，就说明当前接口可能还拆得不够稳。

## 文件系统

文件能力是 Electron 桌面应用最常见也最容易出风险的能力。读取、写入、导入、导出都要明确路径范围和用户授权。

文件相关能力通常分成三步：先让用户选，再让主进程校验，最后再执行读写。不要让页面直接拼一个路径给主进程。路径、文件名、后缀、大小、编码、覆盖策略，这些都属于不可信输入。

```ts
ipcMain.handle("file:readText", async (_event, filePath: string) => {
  assertAllowedPath(filePath);
  return fs.promises.readFile(filePath, "utf-8");
});
```

常见原则是：用户主动选择文件，不默认扫描敏感目录，写入前明确提示，失败时保留可恢复路径。不要让渲染进程直接拼路径请求主进程读写任意位置。

导入和导出最好分别设计。导入更像“读取外部输入并解析”，需要容错和格式校验；导出更像“把业务结果落盘”，需要默认目录、覆盖提示和文件扩展名校验。两者的错误处理也不同，导入失败要告诉用户哪里坏了，导出失败要告诉用户能否重试或换目录。

路径校验、扩展名限制、大小限制都应在主进程完成。页面传入的路径、文件名和导出格式都要当作不可信输入。

如果文件能力还要配合拖拽、最近打开、自动保存，就要把“临时数据”和“持久数据”分开。临时预览可以先落到缓存目录，真正保存再写入用户选择的路径，这样回退和撤销更容易。

对于文档类应用，还可以进一步区分“业务文件”和“应用内部状态”。前者是用户真正关心的产物，后者是窗口布局、最近列表、缓存索引这类辅助数据。把两者混在一起，后续迁移、备份和权限治理都会变得很乱。

## 系统对话框

打开文件、保存文件、确认操作应使用系统对话框。系统对话框能把用户意图和系统权限结合起来，比页面自己拼路径更可靠。

系统对话框的价值不只是“好看”，更重要的是让用户在操作前有明确的上下文。比如保存时系统会自然呈现目录、文件名和覆盖行为，用户更容易判断自己到底在保存什么。

```ts
const result = await dialog.showSaveDialog({
  title: "导出报告",
  defaultPath: "report.pdf",
});
```

对话框返回的是用户选择，不代表操作一定安全。保存前仍要校验文件类型、写入权限、覆盖提示和异常情况。导出类能力最好由主进程根据业务 ID 生成内容，而不是让页面传任意内容和路径。

在多个平台上，对话框返回值的细节可能不一致，例如取消、空路径、单选多选、过滤器行为都可能不同。业务代码不要假设“只要弹过框就一定有结果”，而是把取消视为正常分支处理。

如果应用支持批量导入、导出目录、拖拽文件夹这类操作，也要提前定义失败策略。比如导入 20 个文件时，是遇到第 1 个坏文件就整体失败，还是跳过坏文件继续导入；这些行为最好在界面和日志里都体现清楚。

## 剪贴板与通知

剪贴板和通知是常见桌面能力。

这类能力的共同点是“轻量但高打扰”。剪贴板会影响别的应用，通知会抢占系统注意力，所以它们非常适合做结果反馈，不适合做后台自动动作。

```ts
import { clipboard, Notification } from "electron";

clipboard.writeText("复制内容");

new Notification({
  title: "导出完成",
  body: "文件已保存到本地",
}).show();
```

通知要控制频率，剪贴板写入要由明确用户操作触发。后台静默频繁写剪贴板会造成很差的用户体验，也可能触发安全审查。通知内容还要避免泄露敏感信息，因为它可能显示在系统通知中心或锁屏界面。

如果通知里包含文件名、账号、路径或片段内容，最好做脱敏处理。剪贴板也要避免在非预期时机覆盖用户已有内容，尤其是多窗口应用里，用户可能正在别的程序里复制别的东西。

## 系统集成

托盘、菜单、快捷键、协议唤起、通知都属于桌面系统集成能力。它们能提升桌面体验，但也会增加平台差异和用户打扰。

系统集成的关键不是“能不能做”，而是“做了以后用户是否知道它在做什么”。托盘和全局快捷键如果没有明确说明，很容易让用户觉得应用在偷偷运行；协议唤起如果没有参数确认，也很容易把外部输入直接带进应用内部。

全局快捷键要避免和系统或其他应用冲突，通知要避免高频打扰，协议唤起要校验参数来源。系统集成越深，越要设计关闭入口、权限说明和错误兜底。

协议唤起尤其要谨慎。外部应用或浏览器可能通过自定义协议启动桌面应用，所有参数都必须校验，不能把协议参数直接当成文件路径、命令或跳转地址。

菜单和托盘还经常承担“主窗口不可见时的入口”角色，这就要求它们的行为保持一致。比如托盘点击打开窗口、菜单里的“检查更新”、最近文件列表、窗口聚焦逻辑，最好都复用同一套业务入口，而不是各自拼一段实现。

## 外部链接

打开外部链接应通过 `shell.openExternal`，并先校验 URL。

这里最重要的是协议白名单。`https:` 通常是安全默认值，`http:` 是否允许要看业务场景，`file:`、`javascript:` 和任意自定义协议都应该默认拒绝，除非你明确知道它的用途和边界。

```ts
import { shell } from "electron";

function openExternalUrl(url: string) {
  const parsed = new URL(url);

  if (!["https:"].includes(parsed.protocol)) {
    throw new Error("Unsupported protocol");
  }

  return shell.openExternal(url);
}
```

不要让页面传入任意协议，例如 `file:`、`javascript:` 或系统特定协议。外部链接是高风险入口。应用内窗口只应该加载可信页面，不可信页面交给系统浏览器处理。

如果业务上要从应用内跳转到第三方站点，最好把“跳转动作”和“跳转地址”分开传递。页面传一个业务标识，主进程根据白名单映射成真实 URL，这样就不会把完全开放的跳转能力暴露给渲染层。

## 权限收口

| 能力 | 收口方式 |
| --- | --- |
| 文件读写 | 用户选择路径 + 白名单 |
| shell 打开 | URL 协议校验 |
| 系统命令 | 尽量避免，必要时严格参数化 |
| 剪贴板 | 用户触发 |
| 通知 | 用户授权和频率控制 |
| 自动更新 | 签名校验和回滚 |

Electron 的原生能力要按最小权限暴露。渲染进程只拿业务 API，不拿底层系统 API。每新增一个能力，都应该同步检查 preload API、IPC 校验、主进程权限和日志脱敏。

一个实用的检查顺序是：先确认是否真的需要系统权限，再确认是否能在主进程里做，再确认是否能只暴露结果而不是过程。能不开放给页面的，就不要开放；能只开放单一动作的，就不要开放成通用接口。

当原生能力越来越多时，最好维护一份内部能力清单，至少记录“能力名、触发入口、主进程通道、参数约束、平台差异、失败提示”。这不是额外文档负担，而是为了后续迭代时能看清哪些能力已经过度开放，哪些能力还缺少收口。
