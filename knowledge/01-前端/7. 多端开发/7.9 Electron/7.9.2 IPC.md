## 超时与取消

IPC 调用可能因为系统弹窗、文件操作、网络代理或原生异常长时间不返回。渲染进程侧应该有超时和取消策略，避免页面一直等待。

主进程侧也要处理窗口销毁后请求仍在执行的情况，避免回调写入不存在的窗口。

超时不是为了“快点失败”，而是为了让页面可恢复。打开文件、导出报表、检查更新、下载资源这类能力都可能被系统环境卡住；渲染进程应该能提示重试、取消或回到安全状态。

IPC 的超时语义一旦缺失，页面就很容易进入“按钮点了但一直没反应”的灰区。桌面应用里这类体验尤其糟，因为用户往往会继续重复操作，最终把状态搞得更乱。

## 多窗口通信

多窗口应用里，IPC 还可能承担窗口之间的消息转发。此时要明确消息目标窗口和来源窗口，避免一个窗口的敏感事件广播给所有窗口。

多窗口通信还要注意窗口身份。设置页、登录页、主窗口、弹窗窗口的权限不应该完全相同。主进程转发消息时要确认来源窗口和目标窗口，避免低权限窗口触发高权限动作。

多窗口一多，IPC 就不只是“进程间通信”，还变成了“窗口间权限边界”。只要来源和目标不区分，某个本该低权限的窗口就可能借消息通道触发不该有的能力。
## 通信职责

IPC 是 Electron 主进程和渲染进程之间的通信机制。它负责跨进程传递消息，不应该成为随意暴露系统能力的通道。

```txt
Renderer -> preload -> ipcRenderer -> ipcMain -> Main
```

渲染进程通过 preload 暴露的安全 API 发起调用，主进程执行高权限操作并返回结果。

通信职责要保持单向清晰：渲染进程提出业务请求，preload 限制可调用 API，主进程执行系统能力并返回受控结果。任何绕过 preload 直接暴露 IPC 的设计，都会让安全边界变薄。

IPC 最怕的不是通道多，而是职责乱。页面既能随意发消息、又能自己决定通道、还能碰到系统能力时，后面几乎不可能再补出清晰的安全边界。

## invoke 与 handle

请求响应式通信推荐使用 `ipcRenderer.invoke` 和 `ipcMain.handle`。

```ts
// preload
contextBridge.exposeInMainWorld("fileApi", {
  openFile: () => ipcRenderer.invoke("file:open"),
});
```

```ts
// main
ipcMain.handle("file:open", async () => {
  const result = await dialog.showOpenDialog({
    properties: ["openFile"],
  });

  return result.filePaths[0] ?? null;
});
```

这种模式比手动维护 requestId 更清晰，适合打开文件、读取配置、获取系统信息等一次性调用。

`invoke/handle` 适合请求响应式任务，但不适合高频进度事件。下载进度、更新状态、日志流这类持续事件，更适合使用订阅式通道，并提供取消订阅函数。

把一次性请求和持续事件分开，是 IPC 设计里最基础的结构化动作。只要两者混在一起，页面层和主进程层都会越来越难判断什么时候该等待结果，什么时候该取消监听。

## 事件推送

主进程也可以向渲染进程推送事件，例如下载进度、更新状态、系统通知。

```ts
mainWindow.webContents.send("download:progress", {
  percent: 42,
});
```

preload 中再包装订阅接口。

```ts
onDownloadProgress(callback) {
  const listener = (_event, payload) => callback(payload);
  ipcRenderer.on("download:progress", listener);

  return () => ipcRenderer.removeListener("download:progress", listener);
}
```

订阅必须提供取消函数，避免窗口重复进入时监听器累积。

事件推送要避免无差别广播。更新进度可以发给主窗口，调试日志可以只发给开发工具窗口，账号变更则可能需要通知多个窗口。每个事件都应该知道自己的目标范围。

事件推送设计成熟时，主进程会很清楚哪个事件该发给谁，而不是“先全发出去再让页面自己判断”。这样多窗口场景里的行为才更稳定，也更容易审计。

## 参数校验

IPC 参数来自渲染进程，主进程必须校验。

```ts
ipcMain.handle("file:read", async (_event, payload) => {
  if (!isValidReadFilePayload(payload)) {
    throw new Error("Invalid payload");
  }

  assertAllowedPath(payload.path);
  return fs.promises.readFile(payload.path, "utf-8");
});
```

不要相信前端页面传入的路径、URL、命令或文件名。Electron 中 XSS 可能进一步变成主进程能力滥用。

参数校验最好使用明确 schema，而不是零散 `if`。文件路径、URL、导出格式、命令参数都要限制范围；敏感操作还要结合用户授权或系统对话框结果，而不是只靠页面传参。

参数校验的目标不只是防止恶意输入，也是防止页面层误用接口。Electron 项目里很多事故不是黑客攻击，而是业务代码把不该传的东西顺手传进了高权限通道。

## 通道命名

IPC 通道应该按领域命名，并保持白名单。

```txt
file:open
file:read
app:getVersion
update:check
download:progress
```

避免使用 `message`、`callNative`、`execute` 这类过于泛化的通道。通道越泛化，越难做权限和参数校验。

通道命名也影响审计效率。看到 `file:open`、`update:check`、`app:getVersion`，就能快速判断能力范围；看到 `execute`，则必须追代码才知道它到底能做什么。

通道名称越贴近领域语义，后面越容易定位调用关系、限制权限和做日志审计。名称含糊，复杂度就会一路扩散到调试和安全排查里。

## 安全边界

| 风险 | 防护 |
| --- | --- |
| 暴露 ipcRenderer | 只通过 contextBridge 暴露业务 API |
| 任意文件读取 | 路径白名单和用户授权 |
| 任意 URL 打开 | 协议与域名校验 |
| 监听器泄漏 | 返回取消订阅函数 |
| 参数注入 | schema 校验 |

IPC 是 Electron 安全设计的核心。主进程能力越强，IPC 越要严格。

IPC 的设计原则可以概括为：通道固定、参数受限、结果稳定、错误可区分、监听可取消。只要这五点守住，Electron 的桌面能力会更容易维护和审计。

IPC 真正写得好的状态，是页面层把它当作稳定服务来用，主进程把它当作受限接口来管。两边都不需要越权，复杂度自然也更容易被控制住。
