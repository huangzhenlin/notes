## 能力分类

鸿蒙应用可以调用设备、系统和平台能力，例如网络、文件、相机、定位、传感器、通知、剪贴板、窗口和后台任务。前端开发者学习原生能力时，最重要的不是记 API 名，而是先区分能力类型、权限要求和调用时机。

如果把这些能力都看成“工具函数”，就很容易忽略它们的代价。原生能力通常意味着权限、兼容性、系统资源和用户打扰，因此学习时应该先看风险，再看 API。

| 能力类型 | 常见场景 | 关注点 |
| --- | --- | --- |
| 设备能力 | 相机、扫码、传感器、定位 | 权限申请、用户授权、设备兼容 |
| 系统能力 | 通知、剪贴板、窗口、后台任务 | 系统限制、生命周期、打断恢复 |
| 数据能力 | 文件、数据库、偏好存储 | 沙箱路径、容量、隐私数据 |
| 网络能力 | HTTP、WebSocket、上传下载 | 超时、证书、弱网、重试 |
| 平台能力 | 账号、支付、分享 | 平台审核、回调安全、幂等处理 |

一个能力越接近用户隐私和系统资源，越不能只按“能不能调用”来设计，而要同时考虑授权解释、失败兜底和数据最小化。

这也是为什么能力封装不能只返回原始结果。页面通常更需要知道“权限是否已拒绝”“设备是否不支持”“是否需要引导用户去设置页”，而不是系统底层错误码。对业务来说，语义比细节更重要。

## 设备差异

同一个 API 在不同设备上的可用性可能不同。手机有相机和定位，大屏可能更重视遥控器和焦点，车机可能受安全策略限制。

所以原生能力设计时，最好把“设备能力探测”当成正式流程的一部分，而不是出错后的补丁。页面进入时先判断能力是否可用，再决定展示完整功能还是降级视图，会比事后捕获异常更平稳。

因此原生能力封装要返回清晰的不可用原因，而不是只返回一个通用失败。页面层看到的应该是“设备不支持、权限拒绝、系统失败、用户取消”这类语义，而不是一串底层错误。

设备差异还会影响交互预期。比如手机扫码通常是直接调起相机，大屏设备则可能更适合通过文件上传、遥控输入或与手机协同完成。如果能力封装只考虑“API 能不能调”，却不考虑当前终端的交互方式，最终体验往往会非常别扭。

## 权限模型

权限是原生能力的第一道边界。涉及位置、相机、麦克风、通知、通讯录等敏感能力时，应用需要在配置中声明权限，并在运行时请求用户授权。

```typescript
import abilityAccessCtrl from '@ohos.abilityAccessCtrl';

async function requestLocationPermission(context: Context) {
  const manager = abilityAccessCtrl.createAtManager();
  const result = await manager.requestPermissionsFromUser(context, [
    'ohos.permission.LOCATION',
  ]);

  return result.authResults.every((status) => status === 0);
}
```

权限申请前要让用户知道“为什么需要”。例如定位权限不要在应用启动时直接弹，而是在用户点击“附近门店”时说明用途再申请。授权失败也要能继续使用核心流程，只是降级为手动选择城市。

在鸿蒙里，权限说明和功能入口最好保持一致。也就是说，只有当用户确实触发相关能力时，再引导授权，这样用户更容易理解权限和功能之间的关系，也更容易接受授权请求。

权限流程还要考虑“拒绝后怎么办”。如果用户已经拒绝一次，下一次是再次弹窗、引导去系统设置，还是直接走手动流程，都要提前定清楚。好的权限设计不是弹到用户同意，而是即使用户不同意，应用也仍然能给出可理解的替代路径。

## 能力封装

业务代码不应该到处直接调用系统 API。更稳妥的做法是封装一层平台能力模块，把权限、异常、兼容和日志统一处理。

```typescript
export async function getCurrentLocation(context: Context) {
  const granted = await requestLocationPermission(context);

  if (!granted) {
    return {
      ok: false,
      reason: 'permission_denied',
    };
  }

  try {
    const location = await locateOnce();
    return {
      ok: true,
      data: location,
    };
  } catch (error) {
    return {
      ok: false,
      reason: 'system_error',
      error,
    };
  }
}
```

封装后的返回值最好使用明确的成功/失败结构，而不是让上层业务捕获各种系统异常。这样页面只需要判断业务语义：未授权、设备不可用、系统错误、超时，而不需要理解底层 API。

封装层还可以顺手做三件事：统一埋点、统一超时、统一降级。例如相机扫描失败时，可以返回“是否建议重试”“是否建议切换手动输入”，这样页面就不需要自己判断一堆条件。

封装层最好再区分“能力适配”和“业务组合”。前者解决调用哪个 API、怎么申请权限、怎么兜底；后者解决这个能力在订单、登录、内容发布等业务里如何被串起来。两层分开后，既便于复用，也更容易测试和替换。

## 文件访问

文件能力要关注沙箱路径、用户选择、缓存清理和隐私边界。应用自己的缓存文件可以自动管理，用户主动选择的文件则需要明确来源和权限。

```typescript
async function saveCacheText(context: Context, filename: string, content: string) {
  const path = `${context.cacheDir}/${filename}`;
  const file = await fs.open(path, fs.OpenMode.READ_WRITE | fs.OpenMode.CREATE);

  try {
    await fs.write(file.fd, content);
  } finally {
    await fs.close(file);
  }

  return path;
}
```

缓存目录适合临时图片、接口缓存和可重建数据；文档、用户生成内容和离线资料要更谨慎地选择存储位置。缓存不能假设永久存在，业务逻辑必须能在缓存丢失后重新恢复。

如果应用要处理敏感文件，最好把临时文件和用户文件分目录保存，并在退出或切换账号时清理临时数据。这样既方便维护，也更符合隐私最小化原则。

文件访问还要考虑编码、文件大小和失败恢复。导入文本、图片、压缩包、离线资源时，它们的校验方式完全不同。不要把“拿到路径”当成操作完成，真正稳定的实现会继续验证格式、容量、可读性和后续解析结果。

## 通知能力

通知是高打扰能力，适合订单状态、消息提醒、任务完成这类明确需要用户感知的场景。不要把通知当成普通运营弹窗，否则用户很快会关闭权限。

```typescript
async function notifyOrderPaid(orderNo: string) {
  await notificationManager.publish({
    content: {
      contentType: notificationManager.ContentType.NOTIFICATION_CONTENT_BASIC_TEXT,
      normal: {
        title: '支付成功',
        text: `订单 ${orderNo} 已完成支付`,
      },
    },
  });
}
```

通知要设计点击后的落点。用户点击通知进入应用时，应能恢复到具体订单、聊天或任务页，而不是只打开首页。这会牵涉 [[7.10.2 页面路由|页面路由]] 和启动参数解析。

通知内容还要考虑系统展示空间。标题要短，正文要把最关键的信息放前面，长文本和敏感字段尽量避免直接展示，否则用户在锁屏或系统通知中心里会看到太多细节。

## 网络能力

网络请求属于最常用的原生能力，但移动端网络不是稳定管道。鸿蒙应用也要处理弱网、超时、重试、取消和证书策略。

```typescript
async function requestWithTimeout(url: string, timeout = 8000) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeout);

  try {
    return await fetch(url, {
      signal: controller.signal,
    });
  } finally {
    clearTimeout(timer);
  }
}
```

接口调用要按业务重要性设计重试。查询类请求可以有限重试，创建订单、支付、领取权益这类写操作必须依赖幂等键或服务端状态校验，不能简单重复提交。

对于移动端网络，还要考虑切换网络、后台挂起和应用恢复后的重新同步。很多“网络失败”其实不是接口本身失败，而是请求过程被系统挂起、超时或中断了。

如果应用存在离线阅读、草稿编辑、拍照上传等场景，网络层还应当支持任务排队、断点续传或稍后同步。否则用户一旦在地铁、电梯或后台切换时触发操作，数据就容易停在半途，页面层也很难解释当前到底成功了没有。

## 调用审计

敏感能力调用应有日志和审计。至少要记录能力名称、调用页面、失败原因和设备信息，方便定位“某个设备能用、某个设备不能用”的问题。

审计不只是给研发排障用，也给产品和运营看趋势用。比如某个设备型号上权限拒绝率特别高，说明授权时机可能不对；某个能力调用失败很多，可能是设备兼容问题，也可能是入口设计不合理。

审计日志不能泄漏隐私数据。比如可以记录“定位失败原因是权限拒绝”，但不应该把用户经纬度、身份证、完整文件路径直接打进普通日志。

## 兼容边界

原生能力会受设备型号、系统版本、权限策略和应用形态影响。写代码时要把“能力不可用”当作正常路径，而不是异常路径。

```typescript
type CapabilityResult<T> =
  | { ok: true; data: T }
  | { ok: false; reason: 'unsupported' | 'permission_denied' | 'system_error' };
```

这种返回结构能逼迫业务显式处理失败分支。平台能力越复杂，越要在封装层沉淀统一错误码、埋点和降级策略，否则页面层会堆满重复判断。

如果平台能力未来还会被别的页面复用，最好把接口做成“查询能力是否可用 + 发起能力调用 + 统一处理结果”三段式。这样既方便测试，也方便后续替换具体实现。

兼容边界写得越清楚，后续跨端复用越轻松。业务层只需要知道“这个能力现在能不能用、失败后怎么走替代流程”，而不必理解每一种设备差异。这也是平台封装真正的价值所在。
