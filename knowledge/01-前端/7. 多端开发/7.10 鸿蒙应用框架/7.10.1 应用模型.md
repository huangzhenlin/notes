## 工程结构

鸿蒙应用工程通常会把页面、组件、资源、配置和能力声明放在明确位置。对前端来说，最需要适应的是：它不是一个单纯由路由和组件组成的 Web 项目，应用配置和平台能力声明会直接影响运行结果。

这意味着“能不能运行”不只取决于代码，还取决于配置是否声明完整、模块是否被正确编译、页面入口是否被系统识别。前端开发者如果还沿用 Web 的思维，只盯着页面文件，很容易忽略应用级元数据。

因此项目结构要同时服务两件事：

- 让页面和组件易于维护
- 让平台配置、权限和资源可追踪

一个实用的判断方式是：凡是和平台生命周期、权限、资源加载、模块分发有关的内容，都不要散落在页面里；凡是和 UI 呈现、局部交互有关的内容，尽量留在页面或组件里。这样工程结构才不会把“能跑”与“好维护”混在一起。

如果团队同时维护 Web、小程序和鸿蒙端，最好在目录层就把“跨端通用逻辑”和“鸿蒙平台特有逻辑”分开。这样一来，业务模型、接口层、校验逻辑还能保持一定复用，而 Ability、资源声明、系统能力这些平台差异点也不会混进通用代码里。

## 应用包结构

鸿蒙应用的工程结构围绕应用包、模块和页面组织。前端开发者可以把它理解为“一个应用包含多个能力模块，每个模块再声明自己的页面、资源和运行能力”。这种结构比传统单页面 Web 更接近原生应用，也更强调系统能力、权限和生命周期。

```text
App
├─ entry 模块
│  ├─ UIAbility
│  ├─ pages
│  ├─ resources
│  └─ module.json5
├─ feature 模块
│  ├─ pages
│  └─ module.json5
└─ app.json5
```

`app.json5` 描述应用级信息，`module.json5` 描述模块级能力和页面入口。前端常见的 `src/pages` 目录只能描述页面文件，而鸿蒙还需要在配置中声明这些页面与能力的关系。

这也是鸿蒙应用模型和普通前端项目最大的差异之一。页面文件的存在并不自动意味着可访问，系统要先知道它属于哪个模块、能否被导入、是否具有入口能力。也就是说，路由不只是代码层的跳转，而是配置、编译和运行时共同决定的结果。

## Ability 模型

Ability 是鸿蒙应用对外提供能力的基本单元。常见的 UI 页面能力由 `UIAbility` 承载，它负责窗口创建、页面入口加载、前后台切换等工作。

```typescript
import UIAbility from '@ohos.app.ability.UIAbility';
import window from '@ohos.window';

export default class EntryAbility extends UIAbility {
  onWindowStageCreate(windowStage: window.WindowStage) {
    windowStage.loadContent('pages/Index', (error) => {
      if (error.code) {
        console.error(`load page failed: ${JSON.stringify(error)}`);
      }
    });
  }
}
```

前端视角下，可以把 `UIAbility` 看成“页面路由容器 + 生命周期边界 + 系统交互入口”。页面不是孤立启动的，而是先创建 Ability，再创建窗口，最后加载 ArkUI 页面。

这层边界的价值在于：系统事件、窗口状态和页面 UI 不再混在同一个对象里。比如应用切到后台、窗口尺寸变化、启动参数变化，都应该优先由 Ability 接住，再把需要的状态传给页面层处理。

理解 Ability 的一个好方法，是把它看成比“页面”更靠近操作系统、比“应用进程”更贴近单次界面交互的中间层。很多刚从前端切过来的同学习惯把所有启动逻辑塞进首页组件里，但在鸿蒙里，Ability 往往才是处理冷启动、热启动、拉起来源和窗口恢复的更合适位置。

## 页面入口

ArkUI 页面通常由配置声明和页面文件共同组成。页面文件负责 UI 与交互，配置负责告诉系统这些页面是否属于当前模块、能否被路由加载。

```json
{
  "module": {
    "pages": "$profile:main_pages",
    "abilities": [
      {
        "name": "EntryAbility",
        "srcEntry": "./ets/entryability/EntryAbility.ets",
        "exported": true
      }
    ]
  }
}
```

如果页面文件存在但配置未声明，路由可能无法找到页面；如果配置存在但路径错误，应用启动或跳转时会失败。鸿蒙里的页面治理更接近“声明式入口管理”，不是单纯文件系统路由。

所以新增页面时，不能只创建文件，还要同步检查页面声明、模块配置和入口引用。否则调试时会出现“文件明明在，系统却找不到”的错觉，这类问题在迁移前端项目时尤其常见。

页面入口设计还会影响后续模块拆分。早期如果把所有页面都挂在单一入口模块下，短期看最省事，但后面一旦要做按业务域拆模块、按能力拆包或按终端做差异化分发，迁移成本会很高。

## 资源体系

鸿蒙资源体系用于管理字符串、颜色、媒体、设备差异和国际化内容。相比把常量散落在代码里，资源文件可以让主题、语言、屏幕规格和平台能力更容易统一。

```typescript
Text($r('app.string.app_name'))
  .fontColor($r('app.color.primary_text'))
  .fontSize(18)
```

资源引用看似只是语法变化，本质上是把“会随环境变化的值”从业务逻辑中抽离出来。多语言、深浅色主题、不同设备尺寸和品牌定制都更适合落在资源体系里，而不是到处写硬编码。

资源体系还影响可维护性。把文本、颜色、图标尺寸和间距放进资源后，UI 调整就不必挨个改页面代码。对需要适配多设备的鸿蒙应用来说，这种集中治理比 Web 项目里随手写常量更重要。

进一步看，资源体系其实也是“平台设计语言”的承载层。字号层级、语义色、圆角、间距、暗色模式差异，只要先进入资源体系，页面代码就能更多聚焦在结构和交互上，而不是被大量视觉细节淹没。

## 生命周期边界

鸿蒙应用模型里至少有三层生命周期：应用进程、Ability 和页面组件。它们的作用不同，放错位置会造成重复初始化或状态丢失。

| 层级 | 关注点 | 典型逻辑 |
| --- | --- | --- |
| 应用进程 | 全局运行环境 | 日志、崩溃监控、基础配置 |
| UIAbility | 窗口与系统交互 | 页面入口、前后台、系统参数 |
| ArkUI 组件 | UI 状态与交互 | 页面数据、组件状态、事件响应 |

登录态恢复、启动参数解析、权限预检查更适合靠近 Ability；列表数据、表单状态、按钮交互更适合留在页面组件。这个边界也会影响 [[7.10.4 状态管理|状态管理]] 的职责划分。

如果把全局状态塞到页面组件里，页面一切换就容易丢；如果把纯 UI 状态放到应用进程里，又会让数据流过度集中，测试和复用都变差。鸿蒙的应用模型其实是在提醒前端：状态归属要尽量贴近使用者，而不是贴近实现习惯。

做边界判断时，可以优先问“这个状态随谁生灭”。跟窗口和系统事件强相关的，更接近 Ability；跟当前页面展示强相关的，更接近组件；跨页面共享但不依赖单个界面的，则可以再上收到应用级状态层。这个思路在复杂应用里会比“看起来哪里方便就放哪里”稳定得多。

## 迁移判断

从 Web 或跨端框架迁移到鸿蒙应用框架时，要先判断哪些能力能复用：

- 业务状态和接口模型通常可复用
- 设计语言和组件拆分思路可复用
- 页面生命周期、系统能力和发布流程需要重新适配

如果只把它当成“换一种语法写页面”，后续会在权限、路由和发布上不断踩坑。

迁移时最好先选一条完整业务链路做验证，例如首页 -> 详情页 -> 权限申请 -> 本地保存 -> 再次启动恢复。只要这一条链路能跑通，就能很快看出应用模型、配置和页面状态之间是否协调。

迁移顺序也很关键。通常先迁页面结构和数据流，再迁系统能力和发布链路，会比一开始就全面对齐所有平台特性更稳。因为只要数据流和页面组织方式没理顺，后面加再多权限和能力封装，也只是在给混乱结构叠平台复杂度。

## 模块边界

鸿蒙应用可以拆成 entry、feature、shared 等模块。模块拆分不是为了目录好看，而是为了管理功能边界、编译产物、依赖关系和发布形态。

| 模块类型 | 作用 | 适合内容 |
| --- | --- | --- |
| entry | 应用主入口 | 首页、主流程、基础初始化 |
| feature | 独立功能模块 | 订单、会员、活动页等业务域 |
| shared | 共享能力 | 工具函数、组件、资源、网络封装 |

模块之间要避免循环依赖。共享模块可以被业务模块依赖，但共享模块不应该反向依赖某个具体业务模块。这个原则和前端 Monorepo 的包边界类似，能降低后续编译、测试和发布成本。

如果模块边界不清晰，后面很容易出现“一个页面改动牵出一堆模块”的情况。较稳的做法是先按业务域拆，再按能力抽 shared，最后只让入口模块负责组装，而不是让入口模块替所有功能兜底。

真正拆模块时，还要把“谁拥有入口权”单独想清楚。不是每个模块都应该能直接成为入口，也不是每个功能都适合单独做成模块。业务耦合高、资源共享重、生命周期强绑定的部分，可以先放在同一模块内稳定下来，再考虑继续拆分。
