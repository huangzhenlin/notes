## 页面栈模型

鸿蒙应用中的页面导航也可以理解为页面栈：进入新页面是压栈，返回是出栈。

```txt
HomePage -> DetailPage -> EditPage
返回后：HomePage -> DetailPage
```

页面栈模型适合理解普通前进、返回、替换、清空栈等导航行为。业务流程越复杂，越需要明确返回路径。

对前端来说，页面栈最重要的价值是可预测。用户点一次进入、点一次返回，页面状态如何变化，应该能从栈里直接推出来。只要返回路径开始依赖“临时变量”“随机跳转”或“当前缓存是否存在”，导航就会变得很难维护。

页面栈模型还能帮助你设计“这个页面该不该存在”。如果某个中间页既没有独立状态，也没有独立返回价值，只是为了从 A 去 B 临时过渡，那它更适合做成弹层、分步区域或局部状态，而不一定非要占一个完整页面节点。

## 多设备入口

鸿蒙应用可能运行在手机、平板、大屏等不同设备形态上。页面路由不能只按手机单窗口思路设计，还要考虑不同入口、不同窗口尺寸和不同交互方式。

例如同一个详情页，在手机上可能全屏打开，在大屏上可能作为分栏区域出现。路由设计要尽量表达业务目标，而不是写死某一种页面展示方式。

这也意味着路由不该只关心“去哪个页面”，还要关心“以什么展示策略去到那里”。同一个业务页在不同设备上可能走不同布局，但路由参数和业务语义应该尽量保持一致，这样后续才能统一处理埋点、缓存和返回。

如果未来还要接入卡片、服务入口、外部分享拉起等场景，路由入口就更不能只围着页面按钮点击来设计。较稳的做法是先把“业务目标”抽象出来，再决定这个目标在不同终端、不同窗口中怎么呈现。

## Navigation 组件

ArkUI 中常用 `Navigation` 和相关能力组织页面导航。

```ts
@Entry
@Component
struct Index {
  build() {
    Navigation() {
      Text("首页")
    }
    .title("首页")
  }
}
```

`Navigation` 不只是视觉导航栏，也承载页面结构、标题、返回行为等导航语义。复杂应用应统一封装导航入口，避免每个页面自己拼跳转。

统一封装还有一个好处：你可以把权限判断、登录拦截、参数清洗、埋点和异常兜底放在同一个跳转入口里，而不是让每个页面自己重复一遍。页面层只表达“要去哪里”，封装层决定“能不能去、怎么去”。

这类统一封装最好保持轻量。它应该解决路由规则一致性，而不是演化成庞大的“全能导航管理器”。一旦里面塞满页面专属逻辑，后面新增页面时就会被迫改公共层，导航本身反而会变成耦合源头。

## 路由参数

页面跳转通常传递稳定参数，例如 id、类型、来源。

```ts
router.pushUrl({
  url: "pages/ProductDetail",
  params: {
    id: "p1",
  },
});
```

详情页通过参数获取 id 后，再请求数据或读取缓存。不要传递大型对象，避免序列化、过期和恢复困难。

参数设计最好遵循“少而稳定”的原则。像列表筛选条件、搜索词、页面来源这些信息适合放在参数里，因为它们可以帮助恢复上下文；但真正的大对象、编辑草稿或临时计算结果，更适合放在状态管理或本地缓存里。

参数还要尽量语义化。例如 `productId`、`source`、`tab` 这类名字，远比单纯的 `id`、`type`、`flag` 更利于维护。因为路由参数不是只给当前页面看，还会进入日志、埋点、异常恢复和外部拉起链路里。

## 返回处理

返回行为要区分普通返回、流程完成返回、登录后返回和支付后返回。

```txt
普通详情 -> 返回上一页
编辑成功 -> 返回并刷新上一页
登录完成 -> 回到原始目标页
支付完成 -> 替换到结果页
```

如果所有场景都只使用默认返回，页面栈容易残留中间页，用户会在返回时走到不该看到的流程页。

复杂业务里尤其要区分“返回上一页”和“返回到业务结束页”。例如表单提交成功后，通常不能再回到仍可编辑的页面；支付成功后，也不应继续回到待支付状态页。路由策略要和业务状态保持一致。

如果一个流程里既有手动返回，也有系统返回键或手势返回，就更要提前统一规则。否则用户从按钮返回和从系统手势返回会进入两个不同分支，问题很隐蔽，但线上体验会很差。

## 状态恢复

页面被系统回收、应用切到后台、外部入口重新拉起时，都可能涉及状态恢复。路由参数、页面状态和全局状态之间要有清晰边界。

关键页面应明确：

- 哪些状态来自路由参数
- 哪些状态可以重新请求
- 哪些状态需要本地保存
- 哪些状态失效后应该回到入口页

这样页面在多终端和多生命周期场景下更稳定。

如果状态恢复依赖缓存，最好再加一个失效时间或版本号。否则应用升级后，旧缓存可能把用户带回一个已经不存在的流程节点，表现出来就是“页面能进但状态不对”。

恢复策略还要考虑“是否值得恢复”。比如确认页、支付结果页、一次性成功页，很多时候并不适合原样恢复；更合理的做法是回到入口页或详情页，再用提示告诉用户刚刚发生了什么。不是所有页面都值得被持久化。

## 模块化路由

大型应用可以按业务模块维护页面路径常量和跳转函数。

```ts
export const ProductRoutes = {
  detail(id: string) {
    return {
      url: "pages/ProductDetail",
      params: { id },
    };
  },
};
```

集中管理路由能减少路径字符串散落，也方便后续调整页面路径、埋点、鉴权和参数校验。

在大型项目里，路由集中管理通常还能顺带解决两个问题：一是避免硬编码路径到处复制，二是让页面跳转和业务动作解耦。页面看到的是 `ProductRoutes.detail(id)`，而不是满屏字符串。

如果项目分模块开发，还可以把“模块内部页面跳转”和“跨模块跳转”分开设计。前者更关注本模块自洽，后者更关注公共约定、参数稳定性和升级兼容。把两类跳转混在一起，后续模块演进会非常受限。

## 路由边界

路由负责“用户在哪里”，不负责保存所有业务状态。

| 数据 | 是否适合路由 |
| --- | --- |
| 商品 id | 适合 |
| 搜索关键词 | 适合 |
| 完整商品对象 | 不适合 |
| 表单草稿 | 不适合 |
| 登录后重定向地址 | 适合 |

能通过 id 恢复的数据，路由只放 id。页面内部编辑状态、临时输入、长表单草稿应由页面状态、缓存或持久化层管理。

判断边界时可以用一个简单问题：这个值如果丢了，用户是否还能靠重新加载或重新请求恢复？能恢复的，就可以考虑放到路由或查询参数里；不能恢复的，通常就不该塞进路由。

再进一步说，路由更适合表达“地址语义”，状态层更适合表达“运行时语义”。地址语义强调可定位、可恢复、可共享，运行时语义强调临时性、交互过程和页面内部变化。两者分清之后，页面结构会稳定很多。

## 跨端类比

鸿蒙页面路由和其他声明式应用框架有相似模型。

| 概念 | 鸿蒙 | 类比 |
| --- | --- | --- |
| 页面栈 | 路由栈 | Flutter Navigator |
| 路由参数 | params | 小程序 options / Web query |
| 导航容器 | Navigation | React Navigation / NavigationView |
| 返回行为 | back | 浏览器 history back |

类比能帮助理解，但具体 API、生命周期和系统返回键行为必须按鸿蒙平台验证。

特别是在返回行为上，不同平台对“返回键”“手势返回”“关闭窗口”的处理都不完全一样。迁移时如果只看类比，不看平台实测，往往会在多设备场景里遇到意料之外的返回链路。
