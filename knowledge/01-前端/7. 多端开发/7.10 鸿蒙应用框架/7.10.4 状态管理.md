## 异步状态

接口请求、原生能力调用和权限申请都会带来异步状态。页面需要明确 loading、success、empty、error、unauthorized 等状态，不要只用一个布尔值表达所有情况。

异步状态越清晰，页面在弱网、拒绝权限、设备不支持时越容易降级。

对鸿蒙应用来说，异步状态还经常和生命周期交织在一起。页面发起请求后，应用可能切到后台、权限弹窗可能打断流程、设备能力可能返回不可用。状态模型如果只考虑“请求成功或失败”，就会漏掉取消、恢复、重试和过期这些常见分支。

```typescript
type AsyncState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'empty' }
  | { status: 'error'; message: string }
  | { status: 'unauthorized' };
```

这种结构比 `isLoading + data + error` 更适合复杂页面，因为每个状态都是互斥的。页面渲染时只需要按状态分支展示，不容易出现“既有数据又显示错误”的矛盾 UI。

对于列表、搜索和分页场景，还可以把“首次加载”和“增量加载”继续拆开。首次加载决定整页骨架屏和错误页，增量加载决定底部加载更多、局部重试和是否保留已有数据。两者混在一起时，用户很容易在翻页过程中看到整页闪烁。

## 多端状态一致性

如果应用同时覆盖手机、平板、大屏等设备形态，同一业务状态在不同布局下可能对应不同 UI。状态设计应尽量表达业务语义，而不是绑定某个具体组件是否展示。

例如“当前选中的商品 id”是业务状态，“右侧详情面板是否展开”是布局状态。手机上点击商品可能进入新页面，平板上可能更新右侧面板，但它们共享的仍然是商品选择状态。如果把状态命名成 `isDetailPanelOpen`，迁移到手机布局时就会变得别扭。

这也是为什么多端状态设计要尽量避免写死“某个控件当前是不是显示”。真正稳定的做法，是先描述业务对象和业务阶段，再让不同终端把这些状态映射成各自的页面结构和组件组合。

## 状态层级

鸿蒙 ArkUI 的状态管理不是单一 API，而是一组围绕组件树、父子通信、跨组件共享和持久化场景设计的能力。前端开发者可以先按“状态活多久、被谁使用、是否需要跨页面”来划分。

| 状态范围 | 典型能力 | 适合数据 |
|---|---|---|
| 组件内部 | `@State` | 输入框值、开关状态、局部展开收起 |
| 父子传递 | `@Prop`、`@Link` | 表单项、受控组件、父子同步 |
| 后代共享 | `@Provide`、`@Consume` | 主题、上下文、局部业务模型 |
| 应用共享 | AppStorage / LocalStorage | 登录信息、全局配置、页面级共享状态 |
| 持久保存 | PersistentStorage | 用户偏好、低频设置 |

状态范围越大，越要谨慎。能放组件内部的，不要过早放全局；需要持久化的，也要区分是否真能跨版本、跨设备长期保存。

状态层级的判断可以先看生命周期，再看共享范围。短生命周期、单组件消费的状态放局部；跨页面但不需要重启保留的状态放应用共享；需要重启恢复、且不包含敏感临时数据的状态再考虑持久化。这个顺序能避免“所有东西一上来就全局化”。

## 局部状态

`@State` 是组件内部响应式状态。它适合描述只由当前组件拥有的数据，状态变化会驱动 UI 重新渲染。

```typescript
@Entry
@Component
struct CounterPage {
  @State count: number = 0;

  build() {
    Column() {
      Text(`count: ${this.count}`)
        .fontSize(20)

      Button('增加')
        .onClick(() => {
          this.count += 1;
        })
    }
    .padding(16)
  }
}
```

`@State` 不适合承载从多个页面共享的数据。比如用户信息、购物车数量、主题配置如果散落在多个组件的 `@State` 中，就会出现同步困难。

局部状态最适合描述 UI 内部瞬时变化，例如输入内容、折叠面板、当前 tab、列表选中项。它的优势是简单，缺点是离开组件就消失。因此凡是需要页面返回后继续存在的状态，都要额外考虑缓存、路由参数或更高层状态。

一个常见误区是把请求结果也长期放在局部状态里。短期看最直接，长期看却会在返回恢复、跨页面共享和多设备同步时频繁重写。更稳的判断是：只要这个数据不再属于“纯粹的当前组件瞬时状态”，就应该开始考虑提升状态层级。

## 父子同步

父组件向子组件传值时，可以用 `@Prop` 表示单向输入，用 `@Link` 表示父子双向同步。设计组件时要优先选择单向数据流，只有子组件确实需要修改父组件状态时才使用双向绑定。

```typescript
@Component
struct NameEditor {
  @Link name: string;

  build() {
    TextInput({ text: this.name })
      .onChange((value: string) => {
        this.name = value;
      })
  }
}

@Entry
@Component
struct ProfilePage {
  @State nickname: string = 'Ada';

  build() {
    Column() {
      NameEditor({ name: $nickname })
      Text(`当前昵称：${this.nickname}`)
    }
  }
}
```

双向同步很方便，但也容易让数据修改来源变模糊。表单组件、开关组件、选择器组件适合 `@Link`；展示型卡片、列表项、标签组件更适合 `@Prop`。

如果一个子组件既接收 `@Link`，又内部维护很多派生状态，就要特别小心同步时机。更稳的写法是让子组件只负责编辑当前值，把提交、校验和保存交给父组件或表单模型处理。

父子同步还要避免“链式双向绑定”过长。组件树一深，某个值从祖先一路通过 `@Link` 传到很深的子树，再被多层子组件改回去，排查来源会非常困难。层级太深时，更适合改成上下文共享或集中状态入口。

## 上下文共享

当状态需要跨多层组件传递，但又不适合全局化时，可以使用 `@Provide` 和 `@Consume`。它类似前端框架里的依赖注入，能避免层层透传 props。

```typescript
@Component
struct ThemeProvider {
  @Provide themeColor: string = '#0A59F7';

  build() {
    Column() {
      Header()
      Content()
    }
  }
}

@Component
struct Header {
  @Consume themeColor: string;

  build() {
    Text('首页')
      .fontColor(this.themeColor)
  }
}
```

适合放进上下文的状态一般具有“局部全局”特征：它在某棵组件子树里稳定有效，但不一定属于整个应用。例如主题、当前页面模式、局部表单上下文。

上下文共享不适合放频繁变化的大数据。比如滚动位置、输入框每次输入、列表每项状态，如果都放进上下文，刷新范围和调试复杂度都会升高。上下文更适合稳定、低频、被多层组件读取的状态。

## 应用共享

应用级共享状态适合承载跨页面、跨组件都要读取的数据。这里要特别区分“内存共享”和“持久保存”：内存共享解决运行期同步，持久保存解决应用重启后的恢复。

```typescript
AppStorage.SetOrCreate('token', '');

@Entry
@Component
struct UserBar {
  @StorageLink('token') token: string = '';

  build() {
    Row() {
      Text(this.token ? '已登录' : '未登录')
      Button('退出')
        .onClick(() => {
          this.token = '';
        })
    }
  }
}
```

全局状态要控制写入口。登录、退出、刷新用户信息最好封装成明确的业务方法，而不是让任意组件直接修改存储值。否则问题会变成“谁把 token 改掉了”，调试会很痛苦。

应用共享状态还要区分“可恢复”和“必须重新拉取”。用户 token 可以持久化，但用户资料、权限列表、配置开关往往需要启动后重新同步。持久化不是为了省请求，而是为了让应用在启动、离线或短暂异常时有基础可用状态。

如果应用里有多账号切换、工作区切换或角色切换，还要把共享状态继续分域。比如 token、当前组织、权限缓存、最近访问记录不一定总属于同一个存储命名空间。边界分得越清楚，退出登录和切换环境时越不容易残留脏数据。

## 状态选择

选择状态方案时，可以用三个问题判断：

| 问题 | 结论 |
|---|---|
| 只有当前组件使用吗 | 优先 `@State` |
| 只在父子之间同步吗 | `@Prop` 或 `@Link` |
| 跨多层但限定在子树内吗 | `@Provide` / `@Consume` |
| 跨页面共享吗 | AppStorage / LocalStorage |
| 重启后还要保留吗 | PersistentStorage 或数据库 |

状态管理的核心不是“用哪个装饰器”，而是让数据所有权清晰。谁创建、谁修改、谁消费、什么时候清理，这四个问题回答清楚，API 选择就自然了。

如果状态选择仍然纠结，可以先从最小范围开始写。等确实出现跨组件复用、跨页面同步或重启恢复需求，再逐步提升状态层级。过早全局化会让简单页面变复杂，过晚抽离则会造成状态复制，两者都要靠业务边界来平衡。

最后再补一个判断标准：状态方案不是一劳永逸的。页面刚开始可能只需要 `@State`，随着功能增加才需要共享、持久化和恢复。只要结构清晰、写入口集中，后续把状态逐步上提通常并不困难；真正困难的是一开始就把所有状态混成一团。
