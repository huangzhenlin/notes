## 组件模型

鸿蒙应用框架下的组件体系要从宿主平台理解。HarmonyOS 不只是多一个 UI 库，而是一个统一的设备开发与分布式能力环境。前端关注点在于：页面、组件、布局和交互最终如何映射到平台组件与能力。

这套组件体系更像“面向设备形态的声明式 UI 语言”，而不只是按钮、文本和容器的集合。前端如果只按 Web 组件库的思路去理解，就会忽略它背后的平台约束、生命周期和能力接入方式。

```text
页面结构
组件抽象
布局适配
跨设备交互
能力边界
```

真正适合放进前端知识体系的，不是每个鸿蒙组件的具体 API，而是平台形态、宿主能力和 UI 组织方式。这样后面学 [[7.1.6 原生平台|原生平台]] 和多端框架时，才会知道边界在哪里。

也就是说，这里要学的不只是“怎么摆组件”，还要学“组件为什么能在不同设备上复用”。一旦理解了宿主平台和 UI 组织方式，后面看布局、路由、状态和原生能力时会顺很多。

## 基础容器

常见布局容器包括 `Column`、`Row`、`Stack`、`Flex` 等。

```ts
Column({ space: 12 }) {
  Row() {
    Text("商品名称")
    Blank()
    Text("￥99")
  }

  Button("加入购物车")
}
.width("100%")
.padding(16)
```

`Column` 适合纵向排列，`Row` 适合横向排列，`Stack` 适合层叠。复杂页面应由多个小组件组合，而不是把所有 UI 写在一个 `build` 中。

组件拆分到合适粒度后，布局问题会更好判断：顶层决定信息层级，中层决定区域关系，底层决定单个控件的状态和交互。这样一来，页面适配不同设备时，只需要调整少数容器，而不是重写整页。

容器选择本质上是在表达信息结构，而不是在“拼样式”。如果一个区域天然是上下阅读，就优先用 `Column`；如果它需要主次并列，就考虑 `Row` 或分栏；如果它强调覆盖关系，再考虑 `Stack`。先把结构想清楚，后续适配和状态更新都会自然很多。

## 基础组件

鸿蒙也有文本、图片、容器、按钮、列表、输入等基础组件。不同的是，这些组件更多依赖平台设计规范和设备形态。

```text
常见基础能力：
文本与图像展示
布局容器
按钮与列表
输入和表单
弹窗与导航
```

如果把鸿蒙页面直接按移动 Web 的习惯去写，会忽略设备多形态、系统交互和分布式场景。组件设计要先确认目标设备，再决定布局和交互。

例如同样是列表页，手机上更适合单列滚动，平板上可能要左右分栏，大屏上甚至可以把筛选区固定在侧边。组件体系如果没有从设备形态出发，后续就会一直在“改样式补丁”里打转。

基础组件的使用还要尽量保持语义一致。按钮就负责触发动作，列表项负责承载单元信息，输入框负责表达输入边界。不要因为页面赶工，就把一个 `Row` 临时拼成按钮、把一个 `Text` 临时当链接、把一个容器临时当卡片。语义越模糊，后续无障碍、焦点、埋点和交互反馈都会越来越难统一。

## 状态装饰器

ArkUI 通过装饰器描述状态来源和传递关系，例如 `@State`、`@Prop`、`@Link`。

| 装饰器 | 作用 |
| --- | --- |
| `@State` | 组件内部状态 |
| `@Prop` | 父向子单向传递 |
| `@Link` | 父子双向同步 |
| `@Provide` / `@Consume` | 跨层级依赖传递 |

状态装饰器决定了数据更新后哪些组件会刷新。组件设计时要先判断状态归属，再选择传递方式。

这部分和 React 的 props/state、Vue 的响应式和插槽思路有相似之处，但 ArkUI 的装饰器更强调声明式数据依赖。理解它的关键不是记住装饰器名字，而是知道“谁持有状态、谁消费状态、谁负责同步”。

组件设计里最容易犯的错，不是装饰器不会用，而是状态归属没想清楚。一个组件如果既想自己管状态，又想让父组件控制，又想在外部缓存，就很容易出现更新不同步。先决定组件是“受控”还是“自持有”，再选装饰器，通常比反过来更稳。

## 组件拆分

可复用 UI 应拆成独立组件，通过参数传入数据，通过事件回调通知外部。

```ts
@Component
struct ProductCard {
  title: string;
  price: number;
  onBuy: () => void;

  build() {
    Column() {
      Text(this.title)
      Text(`￥${this.price}`)
      Button("购买").onClick(this.onBuy)
    }
  }
}
```

子组件不应该直接修改父组件的业务状态。它通过回调表达用户意图，父组件决定如何更新状态或发起请求。

如果组件既要展示，又要负责发起请求，最好把“展示数据”和“交互动作”拆开传入。这样组件复用时才不会被某个业务流程绑死，也更容易做单元测试。

判断一个组件是否拆得合适，可以看它有没有清晰的输入和输出。输入通常是数据、配置、样式变体，输出通常是点击、选择、提交、关闭这类事件。如果一个组件的输入越来越多、输出越来越乱、内部还开始知道很多页面上下文，那通常就是拆分边界需要重新调整的信号。

## 布局差异

鸿蒙设备可能覆盖手机、平板、折叠屏、车机、大屏和 IoT 场景。布局不能只按手机屏幕去想。

对多设备场景来说，布局不是“缩放一下就行”，而是信息层级、交互方式和可触达区域都可能改变。输入方式从触摸变成遥控器或鼠标后，按钮大小、焦点顺序和可访问性也要一起考虑。

```text
布局关注点：
尺寸变化
窗口协同
分栏和主次信息
手势和遥控输入
安全区和系统栏
```

当设备横屏、分屏或多窗口时，组件不只是缩放，而是可能需要重新组织信息层级。对于前端而言，这种布局思维和响应式布局、跨端适配是连着的。

所以组件设计时最好预留一些弹性，比如支持可折叠区域、可切换布局和可复用的内容块。这样页面从手机扩展到平板时，才不至于从头重做。

如果一个组件从一开始就把宽高、边距、按钮数量和内容排布写死，那么设备一变化，它就会变成整个页面的阻塞点。更好的做法是让组件保留少量布局策略输入，例如密度、方向、是否分栏、是否展示附加区块，而不是只允许一种固定外观。

## 能力接入

鸿蒙的一个重要特征是设备协同和分布式能力。前端不一定直接写底层分布式逻辑，但要理解页面和组件可能调用的系统能力。

这类能力最怕散落在各个页面里。更好的方式是把能力探测、权限申请和失败兜底放到一层统一封装，让页面只关心“是否可用”和“结果是什么”。

```ts
type DeviceCapability = {
  share: boolean;
  clipboard: boolean;
  camera: boolean;
  storage: boolean;
};
```

当组件依赖系统能力时，应该把能力探测、权限申请和失败兜底封装在较靠近平台的一层，而不是散落在每个页面里。

如果某个组件在没有摄像头、蓝牙或存储权限时也能正常显示，那它就更适合复用；如果组件一进来就强依赖某种设备能力，就要把这种依赖明确写进边界说明，避免误用。

组件和能力的关系最好保持“声明依赖、延迟使用”。也就是说，组件可以表达自己需要拍照、定位或分享，但真正调用能力的动作最好仍然由页面或平台封装层触发。这样既保留了组件复用性，也不会让组件直接长出一堆系统耦合代码。

## 跨端类比

从前端视角看，鸿蒙组件体系与其他声明式 UI 框架有相似的学习路径。

| 概念 | 鸿蒙 ArkUI | 类比 |
| --- | --- | --- |
| 声明式组件 | `@Component` | React Component / Flutter Widget |
| 内部状态 | `@State` | React state / Flutter State |
| 父子传值 | `@Prop` | props |
| 双向同步 | `@Link` | 受控值 + 回调 |
| 布局容器 | `Column`、`Row` | Flex / Flutter Row Column |

类比能帮助入门，但不能替代平台文档。涉及生命周期、路由、权限、原子化服务和系统能力时，仍然要按鸿蒙平台规则实现和验证。

如果团队里同时有 Web、Flutter 和鸿蒙开发者，这种类比尤其有用，因为它能帮助大家快速对齐“数据从哪来、UI 怎么变、能力怎么接”。但最后落到代码时，还是要回到平台自己的语义，不要把类比当成实现依据。

## 开发验证

HarmonyOS 的官方开发环境提供组件定制、代码编译、可视化调试和分布式特性支持。组件体系设计时，要配合 DevEco 之类工具的调试能力来验证。

组件验证时，最好同时看三个层面：单组件状态是否正确、页面组合后布局是否稳定、真机和多设备场景下是否仍然可交互。只看设计器里的静态预览，很容易漏掉焦点、触摸区域和系统栏遮挡的问题。

```text
调试重点：
组件层级
页面布局
不同设备尺寸
系统交互
真机性能
```

如果组件只在单一设备上看起来正常，而没有在平板、折叠屏和车机等形态验证，就不能算成熟。

对于经常复用的组件，建议再补一套最小示例页，用来单独验证状态、布局和能力接入。这样后续改组件时，就有一个固定的回归入口，不必每次都在业务页面里排查。

验证时还要关注交互细节是否一致，例如点击反馈、焦点移动、长按、滑动冲突、系统返回后的状态恢复。组件真正难的地方往往不在静态样式，而在这些边界交互是否稳定。
