## 构建产物

鸿蒙应用发布前需要经过构建、签名、配置校验、包体检查和分发流程。前端开发者不能只关注页面是否能运行，还要理解最终交付给设备和应用市场的是经过配置、资源、代码和签名整合后的安装包。

发布阶段其实是在回答两个问题：这个包是否能被系统接受，和这个包是否适合当前发布环境。前者关乎构建和签名，后者关乎渠道和灰度。

```text
源码与资源
  -> 编译构建
  -> 生成应用包
  -> 签名
  -> 安装测试
  -> 提交审核
  -> 灰度与发布
```

构建失败通常不只是语法问题，也可能来自权限声明、页面配置、资源引用、模块依赖、签名配置或目标设备版本不匹配。

所以鸿蒙发布的排查顺序应该尽量分层：先看构建日志，再看配置文件，再看签名和版本，最后才看页面代码。这样能避免一上来就在业务页面里兜圈子。

## 环境区分

发布前要明确开发、测试、预发和生产环境的配置差异。接口域名、日志开关、权限声明、调试能力和证书信息都不能混用。

如果环境配置靠手工切换，发布风险会很高。更稳妥的方式是让构建流程显式选择环境，并在产物中保留版本和环境标识。

环境标识最好不仅体现在接口地址上，还体现在应用的页面角标、日志级别和埋点标签上。这样一旦测试包误发或灰度包混入正式环境，能更快识别出来。

如果团队有多个发布分支，还要明确“哪个分支对应哪个环境”。很多发布事故并不是构建脚本出错，而是测试分支误打成生产包、或者生产代码误带测试开关。环境边界越早固化进流程，后面越不依赖人工记忆。

## 环境配置

正式发布前要确保环境变量、接口域名、埋点开关、日志级别和调试入口都切换到正确环境。移动应用一旦发出去，修复成本比 Web 高，因此发布前配置检查非常重要。

```typescript
export const runtimeConfig = {
  apiBaseUrl: BuildProfile.env === 'prod'
    ? 'https://api.example.com'
    : 'https://staging-api.example.com',
  enableDebugPanel: BuildProfile.env !== 'prod',
};
```

生产包不应该保留测试域名、调试面板、明文 token、内部账号入口和过量日志。灰度包可以保留诊断能力，但也要确保只有内部用户能触发。

很多线上问题并不是“代码写错”，而是“调试入口忘了关”。因此发布前最好把调试能力、测试账号、模拟数据和日志开关列成固定清单。

还可以把“配置自检”做成启动时的只读校验，例如在开发环境打印当前环境名、接口地址和调试状态，在生产环境禁止出现这些调试提示。这样即使某次构建配置有偏差，也能更早暴露出来。

## 应用签名

签名用于证明应用包来源可信，并让系统识别安装包是否属于同一个应用。调试签名用于本地开发，发布签名用于正式分发，两者不能混淆。

签名本身不只是“能装”，还关系到升级链路能否持续。如果签名配置乱了，用户可能会遇到无法覆盖安装、无法升级或安装包被系统判定为不同应用的问题。

| 签名类型 | 使用阶段 | 风险 |
|---|---|---|
| 调试签名 | 本地调试、真机安装 | 不应用于正式发布 |
| 发布签名 | 应用市场、正式包 | 泄露会影响应用安全 |
| 测试分发签名 | 内测、灰度渠道 | 需要控制分发范围 |

签名资料要纳入团队密钥管理，不应该放进普通代码仓库。CI/CD 中使用签名时，也应通过密钥系统注入，而不是把密码写在脚本里。

如果团队多人协作发布，签名证书和发布权限最好分角色管理。这样即使某个账号失效，也不至于把整个发布链路卡死。

签名问题通常不是上线当天才会暴露，而是在接近发布时集中爆发。所以只要项目已经确定会正式分发，就应该尽早把签名、公证和权限流程跑通一次，避免最后阶段把所有风险都堆到一起。

## 多设备验证

鸿蒙应用如果目标包含多种设备形态，发布验证不能只在一种手机上完成。至少要按目标设备覆盖页面布局、路由返回、输入方式、权限申请、原生能力调用和异常恢复。

多设备验证时，建议优先挑差异最大的设备做对比，比如手机和平板、触屏和非触屏、大屏和车机。差异越大，越容易暴露布局和交互上的隐藏问题。

多设备发布的难点不只是构建成功，而是体验和能力边界是否一致。

验证时还要留意“系统级行为”是否一致，例如返回键、窗口切换、后台恢复、通知跳转和权限弹窗。页面布局往往是最容易看到的问题，系统行为差异常常更隐蔽，但线上代价也更高。

## 版本策略

版本发布需要同时关注展示版本和构建版本。展示版本面向用户，例如 `1.8.0`；构建版本面向系统和发布平台，用于判断升级顺序。

如果版本策略不统一，后面做灰度、回滚和用户支持时会很麻烦。用户看到的是展示版本，系统判断用的是构建版本，两者都要可追踪。

```json
{
  "app": {
    "versionName": "1.8.0",
    "versionCode": 10800
  }
}
```

`versionCode` 必须单调递增，否则应用市场或设备可能拒绝升级。`versionName` 则应该和产品发布节奏一致，避免用户看到混乱版本号。

对于经常灰度的小版本，最好在版本备注里同步记录修复内容和风险范围。这样用户、测试和客服看到版本号时，能更快知道这次升级改了什么。

## 发布检查

发布检查不是“最后跑一下能不能打开”，而是围绕安装、启动、登录、权限、核心流程、异常恢复和回滚能力做闭环确认。

检查清单最好和业务流程绑定，而不是只看技术动作。比如登录后首页是否能正常进入、订单页能否完成支付、通知能否跳转到指定页、离线场景是否有提示，这些都比“能打开”更重要。

| 检查项 | 重点 |
|---|---|
| 安装升级 | 覆盖安装、低版本升级、高版本回退限制 |
| 首次启动 | 冷启动、权限弹窗、隐私协议 |
| 核心链路 | 登录、支付、分享、消息、离线恢复 |
| 兼容设备 | 不同系统版本、屏幕尺寸、性能档位 |
| 异常路径 | 弱网、权限拒绝、接口失败、应用切后台 |
| 可观测性 | 崩溃上报、关键埋点、日志脱敏 |

发布前最好用清单化方式确认，而不是靠经验记忆。移动端问题往往只在特定设备、特定系统版本或特定权限状态下出现。

如果团队有自动化真机或模拟器矩阵，发布前至少跑一轮核心链路；如果没有，也要保留人工冒烟清单。发布的目标不是“看起来差不多”，而是尽量提前暴露设备差异。

## 灰度发布

灰度发布用于降低新版本风险。它可以按用户比例、地区、账号名单、设备类型或渠道逐步放量。对于涉及支付、登录、通知、原生能力的版本，灰度比一次性全量更安全。

灰度不是为了拖慢发布，而是为了把风险从“全体用户”降到“可控人群”。特别是涉及设备能力、权限和系统交互时，灰度能帮你尽早发现兼容性差异。

```text
内部验证 -> 1% 灰度 -> 10% 灰度 -> 50% 灰度 -> 全量
```

每个阶段都要观察崩溃率、启动成功率、接口错误率、关键业务转化和用户反馈。如果指标异常，应暂停放量并回滚或修复。

如果灰度期间某个设备型号、系统版本或区域异常明显，应该优先按这个维度止损，而不是盲目全量或继续扩大范围。发布数据越细，回滚决策越稳。

灰度期间最好把版本、渠道、设备型号和系统版本一起打到监控维度里。这样当问题只出现在某一批设备上时，可以快速确认是平台兼容问题、配置问题，还是业务本身的问题。

## 回滚方案

移动端回滚不如 Web 直接。用户已经安装的新包不能瞬间撤回，因此发布前要准备服务端开关、远程配置、入口限制、服务端兼容和必要的重新发版路径。

真正的回滚方案不是“出事以后再想”，而是“在发版前就知道哪些开关能关、哪些接口能兼容、哪些页面可以退回旧流程”。这样出问题时，处理动作会非常明确。

发布方案里应提前说明哪些问题可以靠远程配置处理，哪些问题必须重新发版，哪些问题需要下架或暂停放量。

| 风险 | 回滚思路 |
|---|---|
| 新入口异常 | 远程配置关闭入口 |
| 新接口失败 | 保留旧接口兼容 |
| 原生能力异常 | 降级到普通流程 |
| 页面崩溃 | 服务端下发禁用开关 |

真正可靠的发布方案不是“永远不出错”，而是在出错后能把影响范围收住。打包发布和 [[7.10.5 原生能力|原生能力]] 的关系尤其紧密，因为系统权限、设备能力和平台审核都可能影响发布结果。

如果应用的某些能力是依赖远程配置打开的，回滚时最好能一键关掉高风险入口，比如相机、支付、文件导入或通知推送。这样即使新版本已经分发出去，也能先把伤害面收窄。

回滚预案最好提前演练过一次。哪怕只是内部环境里模拟“关闭入口配置”“切回旧接口”“禁用某项原生能力”，都比线上第一次真实操作时再摸索要稳得多。回滚不是纸面方案，必须能执行。
