## 兼容目标

Taro 的 API 兼容目标，是让开发者用相对统一的方式调用不同端能力。它会封装常见平台 API，但并不保证所有能力在所有端都完全一致。

```text
兼容的不是名字，而是可用行为
```

如果某个能力在目标端不存在，项目要么降级，要么显式分支处理，而不是假装所有端都原生支持。

兼容的本质不是“名字统一”，而是“在可用范围内提供接近的行为”。如果两个端的语义已经明显不同，就不应该强行包成同一个接口，否则业务层会在错误假设上继续往下写。

这也是 API 兼容最需要克制的地方。统一接口不是目标本身，统一可预期行为才是目标。如果行为无法真正对齐，明确拆分反而比伪统一更稳。

## 能力差异

常见差异包括登录授权、支付、分享、文件、位置和设备能力。某些能力在小程序端很自然，在 H5 端就需要降级方案或替代实现。

```text
常见差异：
登录与授权
支付
分享
文件与存储
位置与设备
系统设置页
```

API 兼容的第一步不是调用，而是判断目标端是否支持。只有确认可用，才进入业务流程。

能力差异往往不是少一个函数，而是整个流程都不同。比如登录、支付、分享、文件和设备能力，某些端可能有完整宿主支持，某些端则需要服务端兜底或者根本不支持，因此入口设计本身就应该按端处理。

一旦能力差异进入完整业务流程，就不能只在调用点补一个 `if`。入口是否展示、用户如何感知、失败后怎么兜底，都应该一起设计，否则兼容层只会把问题往后拖。

## 能力检测

`Taro.canIUse()` 可以用来判断当前版本是否支持某个 API、参数、组件或属性。它适合在入口阶段做能力探测，而不是用户点了按钮才发现不支持。

```ts
if (Taro.canIUse("openBluetoothAdapter")) {
  // 支持蓝牙
}
```

能力检测适合决定入口、流程和降级方案。例如是否展示某按钮、是否启用某交互、是否切换到替代方案。

能力检测最好在页面进入时做完，而不是等用户点击才失败。这样可以减少“点了没反应”的感知，也能让页面提前隐藏不支持的功能入口。

能力检测的真正价值，是让页面能在渲染阶段就做出正确选择，而不是让用户在交互阶段才发现端不支持。越靠近入口做检测，体验越稳定。

## 统一封装

项目里最好再封一层业务 API，把平台差异、错误码和降级逻辑收拢起来。业务页面不应该到处写平台判断。

```ts
export async function openSharePanel() {
  if (!Taro.canIUse("showShareMenu")) {
    return fallbackShare();
  }

  return Taro.showShareMenu();
}
```

统一封装的价值在于把不同平台的差异集中处理，调用方只关心业务语义。例如“分享商品”“打开设置”“获取定位”，而不是“微信小程序怎么调、H5 怎么调、哪个端不能调”。

封装层还能统一错误结构、权限引导和降级路径。页面层只需要接收成功、取消、失败三类结果，再根据业务做下一步，而不用到处写平台判断。

统一封装的意义，不只是复用代码，而是把平台行为翻译成业务语义。页面知道的是“分享成功/取消/失败”，而不是微信小程序和 H5 各自返回了什么底层对象。

## 降级策略

兼容不是所有端都做同一件事，而是在不能完全一致时给出可接受替代。

```text
降级方式：
隐藏入口
替代流程
提示用户切换端
使用服务端兜底
```

降级策略最好提前设计，不要等线上报错再临时补。某些能力，比如蓝牙、文件系统、支付、系统权限，失败后的兜底设计常常比主流程更重要。

降级不是把功能删掉，而是让用户在不能用高级能力时仍然能完成核心任务。例如无法定位就让用户手动选城市，无法分享就复制链接，无法访问文件系统就走上传页面或服务器中转。

降级设计如果提前做好，兼容问题就会从“线上故障”变成“体验差异”。这两者差别很大，前者会中断流程，后者通常还能把用户留在主路径里。

## 分层兼容

API 兼容可以分成三层：框架统一 API、项目业务适配层、平台特化层。越靠近页面，越不应该看到平台细节。

| 层级 | 作用 |
| --- | --- |
| 框架 API | 提供统一写法 |
| 业务适配层 | 封装错误和降级 |
| 平台特化层 | 处理真正差异 |

不要把所有差异都压进统一 API，也不要把平台强差异硬钉在业务页面。兼容的意义是降低心智成本，不是抹平所有平台现实。

分层兼容还意味着责任边界要清楚：框架层提供常见 API，业务适配层负责异常和降级，平台特化层负责真正不能统一的差异。这样后续新增端时，只需要补少量适配，而不是重写整个业务面。

分层兼容最怕边界模糊。只要平台特化逻辑开始散落在业务页面里，后面不管是补新端还是调整老端，都很容易变成大范围连锁修改。

## 判断原则

判断一个 API 是否应该统一，关键不是命名，而是行为是否满足业务。若两个端语义差异太大，就应该明确拆分，而不是伪装成同一个能力。

```text
优先统一：
系统信息
网络请求
基础弹窗
常见选择器

谨慎统一：
支付
分享
权限
文件系统
设备特性
```

Taro API 兼容的真正价值，是把可统一的能力统一，把不可统一的能力显式分支处理。

判断一个 API 是否要统一，关键不是名称像不像，而是业务行为是否足够接近。若两个端语义差异太大，就应该明确拆分，而不是伪装成同一个能力。

真正好的兼容策略，会让团队很清楚哪些能力是真统一、哪些能力是假统一、哪些能力必须显式分端。只有这三类边界清楚，业务层的心智成本才不会持续上升。
