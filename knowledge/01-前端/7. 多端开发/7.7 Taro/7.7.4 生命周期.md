## 生命周期映射

Taro 生命周期需要同时理解框架自身模型和目标平台模型。页面在小程序端会映射到小程序页面生命周期，在 H5 端则更接近 Web 和框架路由生命周期。

```text
小程序页生命周期：onLoad / onShow / onHide / onUnload / onReady
Taro 页面 Hooks：useLoad / useReady / useDidShow / useDidHide / usePullDownRefresh
```

生命周期越接近页面入口，越适合做初始化；越接近显示阶段，越适合刷新数据；越接近隐藏阶段，越适合收尾。

Taro 生命周期的关键，不是记住每个钩子叫什么，而是知道它和目标端生命周期的映射关系。小程序、H5、不同宿主的表现并不完全一致，所以跨端页面要把“首次进入”“再次显示”“切后台”“卸载”分开处理。

跨端生命周期最容易出问题的地方，是把某一个端的触发习惯误当成通用规律。页面在微信小程序里返回时会怎样、在 H5 里前进后退时会怎样、在 tab 页切换时会怎样，这些都应该按场景验证，而不是靠经验猜。

## 页面入口

`useLoad` 和 `onLoad` 适合读取路由参数、初始化页面数据、发起首屏请求。它们不应该承载大量同步任务。

```tsx
import { useLoad, useDidShow } from "@tarojs/taro";

function Index() {
  useLoad((options) => {
    console.log("page params", options.id);
  });

  useDidShow(() => {
    refreshList();
  });

  return <View />;
}
```

首屏逻辑要尽量轻。初始化越重，页面越慢。需要等待的请求可以拆分成首屏关键数据和非首屏次要数据。

入口阶段最适合做参数校验、关键状态初始化和首屏必要请求，不适合做大量同步计算、复杂格式化或全局副作用。页面越靠近首屏，越应该把逻辑拆成“必须先有”和“可以稍后补”的两部分。

入口阶段设计得清楚，后面的性能和恢复问题会简单很多。只要一进页面就把所有事情都一起做，用户看到的通常就是首屏慢、返回慢和分享进入恢复不稳定。

## 显示与隐藏

`useDidShow`、`useDidHide` 适合处理切入前台、切出后台或页面再次显示的逻辑。返回列表后刷新、恢复草稿、暂停轮询都可以放这里。

```tsx
useDidHide(() => {
  stopPolling();
});

useDidShow(() => {
  resumePolling();
});
```

不要把所有逻辑都塞进一个生命周期。首次加载、返回刷新、前后台切换、卸载清理应该分开写。

显示/隐藏阶段特别容易出问题：如果返回页面时又重新开了轮询，但隐藏时没有停掉，就会出现重复请求；如果页面切后台后没有暂停播放或计时器，就会浪费资源。生命周期写清楚后，调试会省很多时间。

显示与隐藏的语义，通常比“是否重新创建页面”更重要。很多跨端页面并不会每次重新进来都重建实例，所以刷新逻辑、恢复逻辑和暂停逻辑必须明确分层。

## 下拉与触底

下拉刷新和触底加载是典型的页面级生命周期。它们的业务意义很明确，但也容易和普通数据请求混在一起。

```tsx
usePullDownRefresh(() => {
  return reloadList();
});
```

下拉刷新通常要重置分页、重新拉首屏数据、结束刷新状态；触底加载更多则要判断是否还有下一页。两者不要混写成一个统一刷新函数，否则状态会很乱。

触底加载还要处理“有没有下一页”和“当前是否正在请求中”。如果没有这两个锁，很容易因为快速滚动或重复触发导致分页错乱。下拉刷新则要重置分页、清空缓存和恢复首屏状态，两者的业务含义本来就不同。

下拉和触底最容易被误写成“都去拉一次数据”。但实际上一个是重新获取首屏真相，一个是向后继续扩展数据，两者的分页、loading 和错误处理语义都应该分开。

## 组件副作用

页面生命周期和组件副作用不是一回事。页面的显示、隐藏、卸载对应页面层任务；组件内部的定时器、事件订阅、DOM 监听和异步请求，要在组件自身生命周期里清理。

```tsx
useEffect(() => {
  const timer = setInterval(refresh, 30_000);
  return () => clearInterval(timer);
}, []);
```

页面卸载不代表组件副作用一定自动正确。长连接、音视频、定位、消息订阅、滚动监听等都要检查清理逻辑。

跨端项目里最常见的泄漏问题，就是把页面级副作用写进组件效果里，却没在销毁阶段清理。组件副作用是否正确，应该作为代码审查和测试的一部分，而不是等线上才发现。

副作用管理做得成熟时，页面级逻辑和组件级逻辑会自然分开：页面负责路由和流程，组件负责局部交互和短生命周期资源。混在一起时，生命周期问题就会越来越难排查。

## 平台差异

小程序、H5、tab 页、分享页、后台切换等场景下，生命周期触发顺序和次数可能不同。跨端代码不要把某一个端的行为当成统一标准。

```text
重点测试：
首进页面
分享进入
返回页面
tab 切换
前后台切换
页面卸载
```

对关键流程，最好在真机和真实容器里验证。生命周期看起来像“框架钩子”，实际经常直接影响业务正确性。

不同端的触发顺序不一定完全一致，所以验证时要重点看“是否触发”“触发几次”“返回后是否恢复”。只在某个端上验证一次，很容易错把平台特性当成通用规律。

平台差异并不意味着生命周期没法统一，而是意味着统一时要更看重语义而不是时机细节。只要页面逻辑是围绕“首次进入、再次显示、隐藏暂停、彻底离开”来组织，就更容易适配不同端。

## 清理原则

离开页面时，应释放页面级资源；切到后台时，应暂停昂贵任务；返回前台时，再恢复关键任务。并不是所有任务都应该在隐藏时立刻取消。

```text
隐藏时适合暂停：
轮询
动画
定位
音视频

卸载时适合清理：
订阅
定时器
事件监听
临时对象
```

生命周期写得越明确，页面越不容易出现重复请求、资源泄露和返回后状态错乱。

清理原则可以落到一个简单判断：离开页面时停掉正在消耗资源的东西，卸载时释放所有与页面绑定的对象，回到前台时再恢复必要任务。这样页面会更像一个状态明确的容器，而不是一团混在一起的副作用。

生命周期管理最后要落到稳定行为：页面进入时知道要初始化什么，显示时知道要恢复什么，隐藏时知道要暂停什么，离开时知道要释放什么。只要这四件事清楚，跨端页面的大多数副作用问题都会收敛很多。
