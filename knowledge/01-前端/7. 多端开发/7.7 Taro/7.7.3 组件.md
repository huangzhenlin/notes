## 组件抽象

Taro 组件体系以跨端基础组件为核心。开发者使用 `@tarojs/components` 提供的 `View`、`Text`、`Image`、`Button`、`ScrollView`、`Input` 等组件组织页面，再由 Taro 编译到小程序、H5、React Native 等目标端。

```tsx
import { View, Text, Image, Button } from "@tarojs/components";

export function ProductCard({ product, onBuy }) {
  return (
    <View className="product-card">
      <Image className="cover" src={product.cover} mode="aspectFill" />
      <Text className="title">{product.title}</Text>
      <Button size="mini" onClick={() => onBuy(product.id)}>
        购买
      </Button>
    </View>
  );
}
```

这些组件更接近小程序组件模型，而不是浏览器 DOM。不要把 `div`、`span`、`img` 的使用习惯直接迁移到 Taro 页面中，否则跨端编译和端侧行为会变得不可控。

组件抽象的目标是把稳定 UI 和交互沉淀下来，而不是追求所有端完全同一份视觉。只要组件内部能把平台差异收口，对外保持稳定 props 和事件，跨端复用就有价值。

组件抽象做得好的关键，不是“端差异一点都看不见”，而是“业务层几乎不需要感知端差异”。只要 props、事件和状态语义稳定，内部实现有适当分支是完全合理的。

## 基础组件

基础组件用于构建稳定页面结构。`View` 是通用容器，`Text` 承载文本，`Image` 处理图片，`Button` 处理按钮交互，`ScrollView` 承载局部滚动。统一组件名降低了跨端心智负担，但不保证所有端表现完全一致。

```tsx
import { ScrollView, View, Text } from "@tarojs/components";

export function OrderList({ orders }) {
  return (
    <ScrollView scrollY className="order-list">
      {orders.map((order) => (
        <View key={order.id} className="order-row">
          <Text>{order.title}</Text>
        </View>
      ))}
    </ScrollView>
  );
}
```

长列表、嵌套滚动、固定底部操作栏是最需要真机验证的区域。H5 模拟器里顺滑，不代表小程序或低端 Android WebView 中也顺滑。

基础组件还要尊重目标端能力。比如 `Button` 在小程序里可能承载开放能力，`Image` 的裁剪模式和懒加载表现受端影响，`ScrollView` 的滚动边界和触底事件也不完全等同 Web。封装组件时要把这些端侧行为写进测试清单。

统一组件名不等于统一行为。组件层最大的职责，是把这些行为差异变成可预期、可测试的适配结果，而不是假装所有端都完全相同。

## 事件对象

Taro 使用 React 风格绑定事件，但事件对象会适配目标端。表单值、触摸点、dataset、滚动位置等字段要以 Taro 和目标端文档为准，不能完全按浏览器事件理解。

```tsx
import { Input } from "@tarojs/components";

function SearchInput({ value, onChange }) {
  return (
    <Input
      value={value}
      placeholder="搜索"
      onInput={(event) => onChange(event.detail.value)}
    />
  );
}
```

组件封装时不要把原始事件对象一路传给业务层。更好的做法是把事件转换成稳定语义，例如 `onChange(value)`、`onReachBottom()`、`onUploadSuccess(file)`，让平台差异停在组件内部。

事件对象越往业务层传，平台差异越容易扩散。组件层可以知道 `event.detail.value`、dataset、触摸点这些细节，业务层最好只接收语义化结果。这样 H5、小程序和其他端的事件差异不会污染业务逻辑。

这也是跨端组件最重要的抽象原则之一：把端细节留在组件边界内。业务层知道的是“值变了”“用户选中了”“滚动到底了”，而不是某个平台事件对象长什么样。

## 受控输入

表单组件在 Taro 中同样要区分受控和非受控。受控输入适合搜索、筛选、表单校验和联动；非受控或局部状态适合临时输入、性能敏感输入或端侧特殊控件。

```tsx
function LoginForm() {
  const [phone, setPhone] = useState("");

  return (
    <View>
      <Input value={phone} type="number" onInput={(e) => setPhone(e.detail.value)} />
      <Button disabled={phone.length !== 11}>登录</Button>
    </View>
  );
}
```

输入框要验证软键盘、输入法、光标、自动聚焦和页面滚动。跨端表单问题经常不在状态逻辑，而在宿主输入行为。

受控输入在不同端的性能和光标行为可能不同。搜索框、验证码、金额输入可以受控；长文本输入、频繁输入或端侧特殊控件要谨慎，必要时把输入中状态留在局部，提交时再同步到业务状态。

输入组件的跨端问题经常不在“状态有没有同步”，而在“同步时机对不对”。只要同步太频繁、太早或和端侧输入法行为冲突，体验就会先出问题。

## 样式边界

Taro 支持 CSS、Sass 等写法，但最终会编译到不同端。小程序端选择器能力、样式隔离、单位转换、层级覆盖、原生组件样式都有自己的限制。

```scss
.product-card {
  padding: 24px;
  border-radius: 16px;
  background: #fff;
}

.cover {
  width: 100%;
  height: 240px;
}
```

跨端样式要避免过深选择器和浏览器特有能力。滚动容器、固定定位、动画、遮罩层和弹窗层级要在目标端真机验证。样式越贴近基础布局能力，跨端成本越低。

样式边界也包括单位和隔离。设计稿里的 px 不一定适合所有端，组件内部样式也不应该依赖页面外部深层覆盖。越基础的组件，越应该提供明确 class、props 或主题变量，而不是让使用者穿透内部结构。

样式边界清楚以后，组件才真正可维护。只要组件外部必须通过复杂选择器去修内部样式，这个组件的跨端稳定性通常已经开始下降。

## 平台差异

组件差异无法完全消除。地图、视频、相机、开放能力按钮、文件选择、分享等组件强依赖平台能力，通常需要单独适配。

```tsx
// 业务层只关心选择图片，平台差异放到适配层
export async function chooseImage() {
  const result = await Taro.chooseImage({
    count: 1,
    sourceType: ["album", "camera"],
  });

  return result.tempFilePaths[0];
}
```

如果组件确实只在某些端可用，要在组件 API 中表达清楚，而不是让运行时静默失败。可以提供降级 UI、禁用状态或平台提示。

平台差异最好集中在适配层。比如选择图片、分享、支付、订阅消息可以封装成独立能力函数；组件只调用能力函数并处理成功、取消、失败三种结果，而不是在 JSX 里到处判断端。

平台差异不可避免，但不应该无序扩散。只要组件知道太多端细节，业务页面最终也会被迫知道太多端细节，跨端复用收益就会被一点点吃掉。

## 组件复用

适合跨端复用的组件通常是卡片、标签、表单项、空状态、列表项、业务状态展示等结构稳定组件；不适合强行复用的通常是相机、地图、视频、复杂手势和依赖开放能力的组件。

```text
复用优先级：
业务模型和类型
纯展示组件
轻交互组件
平台能力适配
强原生体验组件
```

Taro 组件设计和 [[4.1.1 组件原则|组件原则]] 的目标一致：把稳定部分沉淀，把差异部分隔离。不要为了“一份组件跑所有端”把组件写成条件编译迷宫。

复用组件越底层，越要稳定；越靠近平台能力，越要允许差异。纯展示组件可以高度复用，强端能力组件则更适合“统一 API + 平台实现”。这样既能复用业务心智，又不牺牲端侧体验。

复用的重点不是“所有端都共用一份实现”，而是“所有端都共用一份业务语义”。底层展示组件更适合实现复用，强平台能力组件更适合接口复用。

## 调试验证

Taro 组件至少要经过编译检查、H5 预览、小程序开发者工具、真机测试四层验证。组件越依赖滚动、输入、媒体、权限和原生能力，越不能只停留在 H5。

```text
验证清单：
事件参数是否一致
样式是否溢出
滚动是否顺滑
输入是否被键盘遮挡
异常状态是否可恢复
目标端是否支持所用组件
```

跨端组件的质量不取决于“能编译通过”，而取决于目标端用户是否能稳定使用。

调试验证还要覆盖异常状态：无数据、弱网、权限拒绝、图片失败、输入法切换、滚动到底、重复点击。跨端组件真正难的是边界一致，而不是正常路径能显示出来。

跨端组件真正通过验收的标准，不是 H5 页面里长得差不多，而是目标端用户在真实交互和异常场景下都能顺利完成操作。能编译只是起点，稳定使用才是交付标准。
