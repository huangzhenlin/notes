## 页面注册

Taro 路由首先来自页面注册。小程序端需要在应用配置里声明页面路径，框架再把这些页面编译成目标平台能识别的页面入口。新增页面时，文件路径、配置路径和跳转路径必须一致。

```ts
export default defineAppConfig({
  pages: [
    "pages/index/index",
    "pages/product/detail",
    "pages/user/profile",
  ],
  tabBar: {
    list: [
      {
        pagePath: "pages/index/index",
        text: "首页",
      },
      {
        pagePath: "pages/user/profile",
        text: "我的",
      },
    ],
  },
});
```

页面注册决定了运行时能不能打开这个页面。H5 端更接近浏览器路由，小程序端更依赖页面栈和配置声明；所以跨端项目不要把路由当成纯前端字符串拼接问题。

页面注册还会影响分包、tabBar、分享入口和 H5 部署路径。新增页面时如果只改文件、不改配置，某些端可能能编译但无法进入；如果只改小程序配置、不考虑 H5 fallback，刷新和分享又可能失败。

页面注册在 Taro 里不是单纯“把路径列出来”，而是在声明多端页面入口。注册结构是否稳定，会直接影响后面的分包治理、分享恢复、H5 部署和真机调试。

## 跳转动作

Taro 常见跳转动作包括 `navigateTo`、`redirectTo`、`switchTab`、`navigateBack`、`reLaunch`。它们看起来都是“跳页面”，但对页面栈的影响不同。

| API | 页面栈行为 | 适合场景 |
| --- | --- | --- |
| `navigateTo` | 保留当前页，打开新页 | 列表到详情 |
| `redirectTo` | 关闭当前页，打开新页 | 登录后替换中间页 |
| `switchTab` | 切换 tabBar 页 | 底部导航 |
| `navigateBack` | 返回上一层或多层 | 详情返回列表 |
| `reLaunch` | 清空页面栈后打开 | 退出登录、重置流程 |

```ts
import Taro from "@tarojs/taro";

Taro.navigateTo({
  url: "/pages/product/detail?id=p1001",
});
```

不要用 `navigateTo` 跳转 tabBar 页面，小程序端通常需要 `switchTab`。如果封装路由工具，可以在路由表里标记某个页面是否为 tab 页面，避免业务代码到处判断。

跳转动作应该按“页面栈意图”选择，而不是按“能不能打开”。列表到详情保留返回路径，适合 `navigateTo`；登录成功后不希望回到登录页，适合 `redirectTo` 或 `reLaunch`；切主导航必须走 `switchTab`。这些差异如果散落在按钮里，后续很难统一调整。

一旦跳转动作只是“哪个 API 好像能用就用哪个”，页面栈很快就会失控。路由真正要管理的是流程，而不是单次打开动作。

## 参数传递

简单参数可以放在 query 中，复杂对象不适合直接塞进 URL。页面参数要经过编码，并在接收侧做类型校验。不要默认认为路由参数一定存在，因为分享进入、扫码进入、外部链接进入都可能缺少上下文。

```ts
Taro.navigateTo({
  url: `/pages/product/detail?id=${encodeURIComponent(productId)}`,
});
```

```tsx
import { useRouter } from "@tarojs/taro";

export default function ProductDetail() {
  const router = useRouter();
  const id = router.params.id;

  if (!id) {
    return <ErrorView message="缺少商品 ID" />;
  }

  return <ProductDetailView productId={id} />;
}
```

跨端项目里，路由参数最好保持扁平、可序列化、可恢复。复杂状态可以放到全局 Store、缓存或服务端查询中，但要处理刷新和分享后状态丢失的问题。

参数接收侧要把路由参数当作外部输入。分享、扫码、H5 刷新、通知点击都可能让参数缺失或格式不对，所以详情页应该能展示缺参兜底，而不是直接假设上一个页面一定传了完整上下文。

能独立恢复的页面，参数通常都比较克制。只传能定位资源和恢复流程的信息，复杂对象交给缓存或接口层去补，页面跨端表现才更稳。

## 页面栈

小程序端有页面栈限制，连续 `navigateTo` 会不断压栈，栈太深会导致跳转失败或返回体验异常。业务流程越长，越要设计页面栈，而不是让用户每点一步就压一层。

```ts
// 流程完成后替换当前页，而不是继续压栈
Taro.redirectTo({
  url: "/pages/order/success?orderId=o1001",
});
```

页面栈也影响返回逻辑。比如用户从分享卡片进入详情页，页面栈里可能没有列表页；这时点击“返回”不能简单调用 `navigateBack`，而要兜底跳到首页或列表页。

```ts
function safeBack(fallbackUrl = "/pages/index/index") {
  const pages = Taro.getCurrentPages();

  if (pages.length > 1) {
    Taro.navigateBack();
  } else {
    Taro.switchTab({ url: fallbackUrl });
  }
}
```

页面栈设计还要考虑业务流程长度。下单、支付、实名、表单填写这类流程如果每一步都压栈，返回体验会很混乱；流程完成后通常需要替换或重置到结果页，避免用户返回到已经失效的中间页。

栈设计得好的项目，返回行为会很自然；设计得差的项目，用户会经常遇到“怎么又回到这一步了”或者“为什么这里退不回去”。这不是单页 bug，而是流程语义没有被路由层表达清楚。

## 登录拦截

路由封装层适合处理登录拦截、权限校验、参数序列化和错误兜底。业务页面只表达“去哪里”，不要每个按钮都复制一遍登录判断。

```ts
const authPages = new Set(["/pages/order/confirm", "/pages/user/profile"]);

export async function navigate(url: string) {
  const path = url.split("?")[0];

  if (authPages.has(path) && !isLoggedIn()) {
    const redirect = encodeURIComponent(url);
    return Taro.navigateTo({
      url: `/pages/login/index?redirect=${redirect}`,
    });
  }

  return Taro.navigateTo({ url });
}
```

登录后回跳要校验 redirect 是否属于站内页面，避免把用户带到非预期位置。移动端路由安全虽然不像 Web 开放跳转那么典型，但仍然要避免把外部输入直接当作跳转目标。

登录拦截还要和页面栈配合。用户从详情页进入登录，登录成功后应该回到原目标页，而不是把登录页留在栈里。否则用户点返回时可能再次回到登录页，形成很别扭的路径。

登录拦截最怕分散在各个按钮里。真正稳的做法，是在路由层统一判断、统一记录目标页、统一回跳，这样多端路径才能保持一致。

## Tab 页面

Tab 页面是 Taro 路由里最容易踩坑的部分。小程序 tabBar 页面不能用普通 `navigateTo` 打开，也不能随便带复杂 query；切换 tab 后，页面是否刷新要由页面生命周期或状态管理决定。

```ts
Taro.switchTab({
  url: "/pages/index/index",
});
```

如果需要从详情页切到首页并刷新列表，可以通过全局事件、状态标记或 URL 之外的轻量缓存完成。不要依赖“返回时一定重新创建页面”这种假设，不同端的页面缓存和生命周期可能不同。

Tab 页面还要谨慎处理参数。小程序 tabBar 页面通常不适合承载复杂 query，H5 端却可能依赖 URL 表达状态。跨端项目里，Tab 页更适合保存稳定入口状态，复杂筛选和详情流程放到普通页面。

Tab 页更像一级入口，不像流程节点。只要把复杂过程硬塞进 Tab，返回、刷新和状态恢复就都会变得别扭。

## H5 差异

H5 端路由会受到浏览器历史记录、部署路径、刷新行为和服务端 fallback 影响。一个在小程序端正常的路由，在 H5 刷新时可能因为服务端没有配置 fallback 而 404。

```text
H5 路由关注点：
base 路径
history/hash 模式
刷新 fallback
浏览器返回行为
分享链接可恢复性
```

如果项目同时发布小程序和 H5，路由封装层要把“页面路径”和“H5 URL”区分开。页面内部也要能从 URL 参数恢复关键状态，否则分享链接只在小程序端可用，在 H5 端不可复现。

H5 差异还会影响部署。history 模式需要服务端 fallback，hash 模式分享路径更简单但地址语义弱；如果应用部署在子路径，还要处理 base 路径。Taro 路由不能只在开发服务器里验证。

多端路由里，H5 往往是最容易在“刷新”和“外部进入”时暴露问题的端。只在小程序内验证成功，不代表 H5 的直接访问、浏览器返回和分享恢复就一定成立。

## 封装边界

路由封装不是把所有 Taro API 包一层名字，而是统一处理跨端差异。建议维护一份路由表，集中声明路径、是否需要登录、是否 tab 页面、参数规则和兜底策略。

```ts
const routes = {
  productDetail: {
    path: "/pages/product/detail",
    auth: false,
    tab: false,
  },
  profile: {
    path: "/pages/user/profile",
    auth: true,
    tab: true,
  },
} as const;
```

这样做的价值是让路由成为工程约定，而不是散落在页面里的字符串。它和 [[7.7.6 多端编译|多端编译]] 有实际联系：编译目标不同，最终路由行为可能不同，但业务层应该尽量只依赖稳定抽象。

路由表还可以承载埋点名、页面标题、权限要求和分享策略。这样页面跳转、登录拦截、导航栏设置和统计口径可以使用同一份页面元信息，减少“路径改了但埋点没改”的漂移。

路由封装真正的价值，不是少写几次字符串，而是把页面元信息、页面栈意图和跨端差异收口到一个稳定入口。只要这一层稳定，后面换端、改路径、做登录守卫都会轻松很多。
