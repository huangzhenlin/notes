## 核心能力

PWA 是 Progressive Web App 的缩写，强调 Web 应用逐步获得接近原生应用的体验。它不是一个单独框架，而是一组 Web 能力的组合。

```text
Web App Manifest + Service Worker + HTTPS
```

典型 PWA 能力包括可安装到桌面或主屏幕、离线或弱网可用、通过 Service Worker 控制缓存、通过 Manifest 提供应用名称和图标，并在部分平台支持推送通知等能力。

“Progressive”的重点是渐进增强：普通浏览器访问时页面仍然可用，支持更多能力的平台再获得安装、离线、推送等增强体验。因此 PWA 不应该把核心业务建立在某个不稳定能力上，而应该把安装和离线当作体验加分项。

PWA 最适合的心态不是“把网站变成 App”，而是“让已经成熟的 Web 应用在支持的平台上拥有更像应用的体验”。如果基础 Web 体验本身还不稳定，先把页面、性能、缓存和登录链路打稳，通常比急着加安装入口更重要。

## Manifest

Web App Manifest 描述应用名称、图标、启动方式和显示模式。

```json
{
  "name": "Todo App",
  "short_name": "Todo",
  "start_url": "/",
  "display": "standalone",
  "icons": [
    {
      "src": "/icons/icon-192.png",
      "sizes": "192x192",
      "type": "image/png"
    }
  ]
}
```

Manifest 决定用户添加到桌面后的体验。图标、名称、启动地址、主题色都要按真实产品配置。`start_url` 还要考虑登录态、灰度版本和渠道参数，不要让用户从桌面入口进入一个无法恢复状态的页面。

`display: "standalone"` 会让页面更像原生应用，但也意味着地址栏可能消失，返回、分享、刷新等能力要在产品设计里重新考虑。`scope` 决定哪些 URL 属于这个应用范围，配置过大容易把不相关页面也纳入 PWA，配置过小又可能导致跳转后退出应用体验。

Manifest 还会影响安装后的“应用感”。图标裁剪、启动页背景色、主题色、横竖屏策略、应用名称长度都要真实测试，否则用户装到桌面后看到的可能是被截断名称、模糊图标或颜色不一致的启动体验。

## Service Worker

Service Worker 可以拦截请求并实现缓存策略。

```ts
self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      return cached || fetch(event.request);
    }),
  );
});
```

Service Worker 权限很大，错误缓存会导致用户长期拿到旧资源。发布时必须设计版本更新和缓存清理。它和普通 HTTP 缓存不同：普通缓存主要由浏览器和响应头控制，Service Worker 可以在脚本中接管请求，因此也更容易制造“缓存事故”。

Service Worker 只能在 HTTPS 或本地开发环境中工作，这不是形式要求，而是安全边界：它可以拦截页面请求，如果在不安全传输下被篡改，影响会非常大。注册时也要控制作用域，避免一个目录下的 worker 意外接管过多页面。

```javascript
if ("serviceWorker" in navigator) {
  window.addEventListener("load", async () => {
    const registration = await navigator.serviceWorker.register("/sw.js", {
      scope: "/",
    });

    console.log("Service Worker scope:", registration.scope);
  });
}
```

Service Worker 最大的价值，是让缓存和离线能力从“浏览器帮你猜”变成“应用自己治理”。但也因为它能接管请求，所以每条缓存规则都要像写线上逻辑一样谨慎。

## 缓存策略

不同资源适合不同缓存策略。

| 资源 | 策略 |
| --- | --- |
| HTML 入口 | 网络优先，失败兜底 |
| JS/CSS hash 文件 | 缓存优先 |
| 图片 | 缓存优先或 stale-while-revalidate |
| API 数据 | 按业务决定 |
| 离线页 | 预缓存 |

不要把所有请求都一股脑缓存。登录态接口、支付结果、库存数据通常需要新鲜数据。PWA 的缓存策略要和 [[6.2.5 缓存策略|缓存策略]] 保持一致：静态资源可以激进，业务数据要谨慎。

缓存策略应该按“是否可变、是否关键、是否可离线”拆分。HTML 入口决定版本入口，通常要网络优先；带 hash 的静态资源内容不可变，可以缓存优先；头像、封面图适合 stale-while-revalidate；订单、余额、库存这类业务数据通常不能简单离线复用。PWA 的缓存不是越多越好，而是要让用户在弱网下拿到“正确的可用内容”。

如果缓存策略设计得太激进，用户最常见的感受不是“离线好用”，而是“怎么我看到的页面和别人不一样”“为什么修复了 bug 我这里还没生效”。PWA 项目的难点，很多时候都在缓存一致性，而不在注册代码本身。

## 更新机制

Service Worker 更新不是刷新页面立即生效。新 worker 可能处于 waiting 状态，直到旧页面关闭。

```text
install -> waiting -> activate
```

应用要设计更新提示，例如“新版本已准备好，点击刷新”。强制立即接管要谨慎，避免用户正在填写表单时页面被刷新。

```ts
// 示例：发现新版本后提示用户，而不是无声刷新
function notifyUpdateReady() {
  showToast("新版本已准备好，刷新后生效");
}
```

真正的难点不是“注册成功”，而是版本变更、旧缓存清理、离线页面兜底和失败恢复。PWA 做得好是体验增强，做得不好会变成线上排查最难的缓存层。

更新机制要有产品策略。工具类应用可以提示用户刷新，内容站可以静默等待下次打开生效，交易类页面则要避免在用户提交表单或支付过程中切换版本。`skipWaiting()` 和 `clients.claim()` 能加快新版本接管，但也可能让正在运行的页面突然处在“旧 HTML + 新 JS”或“新 worker + 旧页面”的混合状态。

因此更新提示最好和业务状态联动。用户正在支付、编辑、上传或填写长表单时，不应贸然刷新；用户停留在首页、列表页或空闲状态时，再提示更新会更安全。

## 适用场景

PWA 更适合这些场景：

- 内容型站点希望提升复访体验
- 工具型 Web 应用需要安装入口
- 弱网环境下仍需要基础可用
- 不想完全依赖应用商店发版

它不适合用来替代所有原生应用能力。涉及深度系统能力、复杂后台任务或强平台集成时，仍然要评估原生或跨端方案。

PWA 适合“Web 已经能完成主要业务，只是希望增强复访、弱网和安装体验”的产品。它不适合把 Web 包装成万能 App：后台常驻、复杂蓝牙能力、深度系统权限、强消息触达和应用商店生态，仍然可能需要 [[7.4 Hybrid|Hybrid]]、[[7.5 React Native|React Native]] 或原生方案配合。

如果一个产品核心诉求是“快速访问、内容浏览、轻度互动、离线兜底”，PWA 非常有价值；如果核心诉求是“深度系统接入、复杂后台能力、强平台生态分发”，PWA 往往只是补充方案。

## 平台差异

PWA 在不同平台支持程度不同，尤其是 iOS 和部分内置 WebView。

| 能力 | 注意 |
| --- | --- |
| 添加到桌面 | 浏览器支持差异 |
| 推送通知 | iOS/浏览器版本限制 |
| 后台同步 | 支持不一致 |
| 存储配额 | 平台差异 |
| WebView | 可能不完整支持 |

把 PWA 当增强能力更稳妥。基础功能仍应在普通浏览器访问时可用，不要把核心业务完全绑定到某个 PWA 能力上。

平台差异还体现在调试和发布上。桌面 Chrome 的 Lighthouse 通过，不代表 iOS Safari、Android WebView 或微信内置浏览器都能获得同样体验。上线前要至少验证安装入口、离线兜底、缓存更新、登录恢复、推送权限和存储清理这些关键路径。

PWA 的平台差异不只是“某个 API 支不支持”，还包括安装提示出现方式、桌面图标行为、缓存配额、后台更新时机、推送权限策略和宿主浏览器限制。把它当成跨平台增强能力，而不是统一标准，心态会更稳。
