## 输入环境

移动端输入和桌面端最大的差异，是软键盘会改变可视区域，并且输入类型会影响键盘布局。表单体验做得好不好，经常直接决定移动页面的转化率。

```text
常见问题：
键盘遮挡输入框或按钮
数字键盘不出现
邮箱键盘缺少 @
输入后页面抖动
自动聚焦打断浏览
```

移动端输入不能只在模拟器里测，真机、不同系统版本、不同 WebView 和 Hybrid 容器里表现会有差异。

输入体验的难点不是“能不能输入”，而是用户能否在最少切换、最少遮挡、最少修正的情况下完成任务。手机号、验证码、金额、地址、搜索、备注这些字段看起来都只是 `<input>`，但它们对键盘、自动填充、校验时机和错误反馈的要求完全不同。

移动端输入做不好，页面往往不是“不能提交”，而是用户在半路就放弃了。转化率下降、验证码输错、地址填不全、支付页跳失，很多时候都和输入链路细节有关。

## 键盘类型

`type`、`inputmode` 和 `autocomplete` 可以同时改善输入体验。`type` 负责语义和校验，`inputmode` 负责提示虚拟键盘，`autocomplete` 负责自动填充线索。

```html
<input type="tel" inputmode="numeric" autocomplete="tel" />
<input type="email" autocomplete="email" />
```

MDN 明确说明，`inputmode` 只是提示键盘类型，不会强制校验输入值。需要验证输入合法性时，仍然应该选择合适的 `type`，并在提交时做完整校验。

`type="number"` 不适合所有数字输入。手机号、验证码、银行卡号虽然由数字组成，但它们不是数学数字，不应该出现科学计数法、步进按钮或小数处理。更常见的做法是使用 `type="text"` 搭配 `inputmode="numeric"`，再用业务规则做格式化和校验。

```html
<label>
  验证码
  <input
    type="text"
    inputmode="numeric"
    autocomplete="one-time-code"
    maxlength="6"
  />
</label>
```

不同字段可以这样理解：

| 字段类型 | 更常见写法 | 这样做的原因 |
| --- | --- | --- |
| 手机号 | `type="tel"` 或 `text + inputmode="numeric"` | 需要数字键盘，但不需要数学运算语义 |
| 验证码 | `text + inputmode="numeric"` | 便于控制长度和粘贴 |
| 邮箱 | `type="email"` | 键盘更容易输入 `@` 和 `.` |
| 金额 | `text + inputmode="decimal"` | 需要控制小数和格式化 |
| 搜索 | `type="search"` | 键盘和回车动作更贴近搜索语义 |

## 视口变化

软键盘弹出会改变可视区域，尤其会影响底部按钮、固定定位元素和聊天输入框。页面最好避免把关键按钮强依赖在容易被遮挡的位置。

```css
.submit-bar {
  position: sticky;
  bottom: 0;
  padding-bottom: env(safe-area-inset-bottom);
}
```

在 iOS Safari、Android Chrome 和微信 WebView 中，键盘对 viewport 的影响可能不同。触发输入后要观察输入框、按钮、滚动容器和安全区是否还可用。

底部固定按钮最容易被键盘影响。表单页可以把提交按钮放在内容流末尾，键盘弹出时让用户自然滚动到按钮；如果必须固定到底部，要结合 `visualViewport`、安全区和容器滚动一起测试。只靠 `100vh` 经常会在移动端产生被地址栏或键盘遮挡的问题。

如果一个页面里既有长表单又有底部固定 CTA，通常要提前决定策略：是输入时把 CTA 推上来，还是在输入阶段临时折叠 CTA。两种都可以，但不能既想固定又不处理键盘，否则最终就是挡住输入区或挡住按钮。

## 聚焦策略

自动聚焦不是默认推荐。它很容易直接拉起键盘，打断用户浏览节奏，也可能在某些 WebView 里被系统限制。只有登录页、验证码页、搜索页这类明确需要立即输入的场景，才值得考虑。

```html
<input autofocus />
```

如果页面同时有底部固定 CTA、弹窗表单和长列表，自动聚焦更容易引发布局跳动。更稳妥的方式通常是让用户主动点击输入框。

聚焦还要考虑时机。页面刚进入就聚焦会抢走浏览节奏；弹窗打开后立即聚焦可能触发布局抖动；验证码输入框自动跳格虽然看起来顺滑，但如果处理不好粘贴、删除和输入法组合输入，会让用户更难纠错。

输入法组合输入也是常见坑。中文输入、联想输入、语音转文字并不是一个字符一个字符稳定到达的，如果在 `input` 过程中立刻格式化、截断或跳格，往往会破坏输入体验。涉及复杂输入时，要正确处理组合事件或在确认输入后再格式化。

## 表单优化

移动端表单应该尽量减少手动输入成本。能选就不要填，能自动补全就不要重复输入，错误提示要靠近输入项，提交按钮不要被键盘遮住。

```text
优化顺序：
选择器优先
自动填充优先
分组填写优先
输入中即时提示
提交前完整校验
```

金额、手机号、验证码等字段要使用更合适的键盘类型和 `autocomplete` 值。`autocomplete` 的实际支持会受浏览器和系统影响，因此关键表单仍要真机验证。

错误提示不要只在提交后统一弹 toast。移动端屏幕小，用户可能看不到出错字段；更好的方式是在字段附近展示具体原因，并保留用户已经输入的内容。对身份证号、手机号、邮箱这类字段，可以在失焦或输入达到长度后提示，避免用户每输入一个字符都被打断。

表单优化的重点不是“校验越早越好”，而是“提示出现得恰到好处”。格式明显错误可以早点提示，业务依赖服务端判断的内容则不要过早打断用户。手机号、验证码、密码、地址的提示策略通常应该分别设计，而不是一套通用逻辑全部套上去。

## 触控适配

移动输入经常和触控区一起出问题。可点击区域太小、输入框与按钮太近、软键盘弹起后列表错位，都会让用户误触。

```css
.field {
  min-height: 44px;
}

.action {
  min-height: 44px;
  touch-action: manipulation;
}
```

输入框和按钮布局要考虑手指点击、单手操作和拇指活动范围。靠近底部的输入区域，尤其需要关注安全区和键盘弹出后的空间重排。

触控适配还包括光标定位和文本选择。输入框太小会导致用户难以移动光标，清除按钮太靠近提交按钮会导致误触，验证码倒计时按钮如果状态不明显会造成重复点击。输入控件应该把可点击区、文本区、辅助操作区分开，而不是把所有元素挤在一行里。

对单手操作场景尤其要敏感。页面底部区域更容易触达，但也更容易被键盘和安全区影响；页面顶部输入框则更容易让用户在键盘弹出后来回移动视线。输入链路设计时，要同时考虑触达成本和可见性。

## 容器差异

如果页面运行在 Hybrid 容器里，还要额外确认宿主是否对键盘弹出、沉浸式状态栏和安全区做了额外处理。Web 页面本身看起来没问题，不代表嵌进 App 后还能正常使用。

```text
真机检查：
键盘弹出后按钮是否被遮挡
输入框是否自动滚动到可视区域
页面是否发生无意义抖动
焦点切换后是否丢失输入法状态
```

移动端输入的目标不是“能输入”，而是“输入成本低、遮挡少、反馈准、恢复快”。这和 [[1.1.4 表单|表单]] 的设计原则是同一件事。

如果页面嵌在 App 内，输入问题还可能来自原生层：键盘避让策略、沉浸式状态栏、WebView resize 模式、输入法兼容、Bridge 弹窗和原生导航栏都可能改变可视空间。排查时要同时记录浏览器页面 URL、容器版本、系统版本和键盘类型，避免只在 H5 代码里绕圈。

很多输入问题最终都不是某个 `<input>` 标签写错了，而是视口、滚动容器、固定布局、键盘策略和表单节奏叠在一起造成的。移动端输入优化，往往要把页面结构、交互反馈和宿主容器一起看。
