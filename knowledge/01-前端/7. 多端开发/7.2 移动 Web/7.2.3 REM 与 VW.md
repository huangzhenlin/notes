## 单位模型

`rem` 和 `vw` 都是相对单位，但相对对象不同。`rem` 相对根元素 `font-size`，适合建立一套可控的比例系统；`vw` 相对视口宽度，适合让模块直接跟随屏幕宽度变化。移动端适配不能只问“用 rem 还是 vw”，更应该问“哪些尺寸需要等比缩放，哪些尺寸需要保持可读”。

`rem` 更适合统一缩放一整套视觉系统，`vw` 更适合直接跟随屏幕宽度变化。两者的差别，本质上是“基于字号缩放”和“基于视口缩放”。

```css
html {
  font-size: 16px;
}

.title {
  font-size: 1.25rem;
}

.hero {
  width: 100vw;
}
```

`px` 也不是不能用。边框、图标细节、固定点击区域、字号下限经常需要稳定值。移动端适配的目标是让布局舒适，而不是把所有数值机械转换成相对单位。

很多项目最后都会回到混合方案：大块结构用相对单位，小细节保留 px。完全依赖单一单位，通常会让适配变得别扭。

如果页面是营销活动、落地页、全屏视觉页，`vw` 往往更直接；如果页面是业务表单、商品详情、文章阅读、后台模块，完全按视口缩放就容易把可读性带偏，这时 `rem`、`px`、`clamp()` 的组合通常更稳。

## rem 换算

早期移动 H5 常用动态 `rem` 方案：根据设计稿宽度和当前视口宽度设置根字号，再把设计稿尺寸换算成 `rem`。例如 375px 设计稿中，约定 `1rem = 37.5px`，那么 150px 宽按钮就是 `4rem`。

```javascript
function setRootFontSize() {
  const designWidth = 375;
  const base = 37.5;
  const width = Math.min(document.documentElement.clientWidth, 540);
  document.documentElement.style.fontSize = `${(width / designWidth) * base}px`;
}

setRootFontSize();
window.addEventListener("resize", setRootFontSize);
```

这种方案的优点是设计稿还原成本低，缺点是依赖运行时脚本和构建换算。大屏手机、折叠屏、横屏和平板上，如果不限制最大宽度，页面会被等比放大到不舒适。

rem 方案适合设计稿固定、页面主要面向移动端的场景；如果要同时覆盖平板和桌面，它通常还需要额外断点兜底。

rem 的优点是整套比例关系稳定。比如卡片圆角、按钮高度、标题字号、内容间距会一起按根字号变化，视觉系统不容易散。但它的代价是根字号成为“总开关”，一旦算法不合理，整页都会被一起放大或缩小。

```css
.product-card {
  padding: 0.32rem;
  border-radius: 0.24rem;
}

.product-card__title {
  font-size: 0.4rem;
  line-height: 1.4;
}
```

如果根字号会在运行时变化，首屏还要注意闪动问题。根字号脚本执行前后的差异，可能造成页面第一次渲染和最终渲染尺寸不一致。

## vw 换算

`vw` 直接来自视口宽度，`1vw` 等于视口宽度的 1%。如果设计稿是 375px，设计稿里的 150px 可以换算成 `40vw`，因为 `150 / 375 * 100 = 40`。

```css
.banner {
  width: 100vw;
  height: 56.25vw;
}

.button {
  width: 40vw;
}
```

`vw` 很适合横幅、活动页视觉块、等比例卡片，但不适合无脑控制所有字号。字号完全跟随视口时，小屏可能太小，大屏可能太大。现代 CSS 可以用 `clamp()` 限制范围。

`clamp()` 的价值是给响应式尺寸加上下限，避免极端屏幕下字号或间距失控。

```css
.headline {
  font-size: clamp(20px, 6vw, 32px);
}
```

vw 的问题通常出在“跟得太紧”。它会随着视口实时变化，所以横屏、平板、桌面容器、分屏模式里，某些尺寸会被放大到不合理。只要某个尺寸需要稳定下限或上限，就不该裸用 vw 到底。

```css
.hero-title {
  font-size: clamp(24px, 7vw, 40px);
}

.hero-actions {
  gap: clamp(12px, 3vw, 20px);
}
```

## 视口变化

移动端视口不是固定矩形。浏览器地址栏展开/收起、横竖屏切换、安全区、软键盘弹出都会改变可见区域。传统 `100vh` 在移动端经常导致底部被遮挡或出现跳动，新视口单位 `svh`、`lvh`、`dvh` 能更精确表达不同视口状态。

```css
.full-screen {
  min-height: 100dvh;
}

.bottom-bar {
  padding-bottom: env(safe-area-inset-bottom);
}
```

`dvh` 表示动态视口高度，适合真正跟随可见区域变化；`svh` 偏保守，适合避免内容被浏览器 UI 挡住；`lvh` 偏最大视口，适合沉浸式视觉。具体使用要结合页面类型测试。

移动端视口单位最容易踩坑的地方，就是浏览器 UI 和键盘会改变可见区域。只靠 `100vh` 往往不够稳。

旧方案里常见的 `height: calc(var(--vh) * 100)` 本质上也是在手动修复移动端高度问题。现在如果环境支持 `dvh`，优先用原生单位；如果要兼容旧容器，再用 CSS 变量或 `visualViewport` 做降级补丁。

## 内容可读性

内容型页面不应该追求严格等比还原设计稿。阅读体验更依赖字号、行高、行宽、段落间距和触控区域。正文可以保持相对稳定字号，布局用弹性方式适配。

```css
.article {
  max-width: 42rem;
  margin-inline: auto;
  padding-inline: clamp(16px, 4vw, 32px);
  font-size: 16px;
  line-height: 1.75;
}
```

设计稿中的尺寸只是参考。真实设备里要确认文字是否可读，按钮是否容易点击，表单是否被键盘遮挡，横屏是否仍能操作。这和 [[7.2.7 移动端输入|移动端输入]] 的体验问题会相互影响。

内容可读性优先时，字号和行高应保守一点，不要为了还原设计稿牺牲可读性。

尤其不要把正文、表单标签、按钮文字全部按 `vw` 缩放。页面宽一点并不代表用户就愿意看更大的字，页面窄一点也不代表字可以无限变小。可读内容更适合稳定在一个合理区间内。

## 混合策略

实际项目通常混合使用多种单位。布局容器用百分比、Flex、Grid；大视觉块用 `vw`；字号和间距用 `rem` 或 `clamp()`；边框和细节用 `px`；最大宽度用 `max-width` 限制。

```css
.page {
  max-width: 540px;
  margin-inline: auto;
  padding: 0 clamp(16px, 4vw, 24px);
}

.card {
  border: 1px solid #e5e7eb;
  border-radius: 12px;
  padding: 1rem;
}
```

如果页面只面向移动端活动营销，`vw` 或 rem 等比方案会更高效；如果页面要覆盖手机、平板、桌面，应该更多依赖断点、容器宽度和响应式布局，而不是单一缩放。

单位方案的判断重点，不是“哪个更先进”，而是“页面的适配目标有多宽”。目标越广，越要用布局和断点兜底。

下面这个组合在移动业务页里很常见：

| 内容类型 | 常见单位策略 |
| --- | --- |
| 页面外边距 | `clamp()` 或少量 `vw` |
| 卡片内间距 | `rem` 或 `px` |
| 正文字号 | `px` 或受控 `rem` |
| 沉浸式视觉区 | `vw` / `dvh` |
| 边框与细线 | `px` |

这样做的原因不是“混搭更高级”，而是不同元素对稳定性和缩放敏感度不同。正文、表单和按钮更怕失控，视觉块和横幅更适合弹性变化。

## 工程落地

工程里常见做法是通过 PostCSS 插件把 `px` 自动转成 `rem` 或 `vw`。这能减少手算，但必须配置排除规则，否则第三方组件、1px 边框、字体和不该缩放的尺寸也会被转换。

```javascript
export default {
  plugins: {
    "postcss-px-to-viewport": {
      viewportWidth: 375,
      unitPrecision: 5,
      propList: ["*"],
      exclude: [/node_modules/],
    },
  },
};
```

自动转换适合统一视觉稿还原，不适合替代响应式设计判断。团队要约定哪些文件参与转换、哪些属性不转换、最大宽度如何处理、平板和横屏如何兜底。移动适配最终还是要在真机上验证，而不是只看浏览器模拟器。

如果项目里同时有组件库和业务页，转换规则还要区分组件内样式和页面样式，否则很容易把不该缩放的基础组件一起转坏。

工程里还要特别注意这几个点：

| 关注点 | 为什么重要 |
| --- | --- |
| 第三方样式是否排除 | 避免把外部组件尺寸转换坏 |
| `1px` 边框是否转换 | 容易出现边线失真 |
| 字号是否全部参与转换 | 可能破坏可读性 |
| 最大宽度是否限制 | 平板和桌面可能被过度放大 |

最终判断单位方案是否合适，最简单的方法不是看配置，而是拿真实页面过一遍：窄屏下文字会不会太小，宽屏下卡片会不会过散，输入时键盘会不会把关键区域顶坏，横屏时布局是否还能成立。
