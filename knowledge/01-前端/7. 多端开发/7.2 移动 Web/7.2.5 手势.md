## 手势语义

手势是在触摸事件或 Pointer Events 之上识别出来的交互语义。滑动、拖拽、缩放、长按、轻扫都不是浏览器自动给你的完整业务动作，而是由事件序列组合出来的结果。

```text
pointerdown / touchstart
pointermove / touchmove
pointerup   / touchend
```

前端做手势时，重点不是监听到了多少事件，而是能否稳定识别用户意图。简单点击交给 `click` 即可，拖拽、滑动、缩放、长按才需要直接处理触摸或指针事件。

手势识别通常要经历“记录起点、判断方向、确认阈值、收尾复位”四步。不要在 `touchstart` 阶段就下结论，因为很多动作一开始都像点击，只有移动距离、持续时间和方向逐渐明确后，才能区分点击、滑动和长按。

手势识别最怕过早抢占。还没确认用户意图就阻断页面滚动或点击，体验通常会很差。先观察、再判断、最后执行，往往比一开始就拦截更稳。

很多手势体验不好的根因不是算法太弱，而是语义设计不清。一个区域到底是“点击进入详情”“横滑露出操作”“长按进入编辑”还是“拖拽排序”，如果交互目标本身就重叠，再好的识别也会让用户犹豫。

## 常见手势

| 手势 | 识别依据 | 常见场景 |
| --- | --- | --- |
| 点击 | 短时间、短距离触摸 | 按钮、列表项 |
| 长按 | 按住超过阈值 | 菜单、复制、拖拽入口 |
| 滑动 | 单方向位移超过阈值 | 轮播、返回、抽屉 |
| 拖拽 | 持续跟随触点移动 | 排序、面板调整 |
| 缩放 | 多触点距离变化 | 图片预览、地图 |

手势识别通常要设置时间阈值、距离阈值和方向阈值，避免轻微抖动就触发动作。

这些阈值不应该写成固定答案。轮播图、图片预览、卡片删除、地图拖动对距离和速度的容忍度不同。更稳的做法是同时看距离和时间：距离够大时直接判定，距离不够但速度很快时也可以判定；如果距离短又很慢，那更像犹豫或误触。

手势要尽量贴近场景心理模型。用户在图片预览里默认期待双指缩放和拖动，在聊天列表里期待左滑露出操作，在地图里期待拖拽和缩放；如果把某个手势放到用户没有预期的区域，就算技术上能实现，也不一定好用。

## 滑动判断

左右滑动可以通过起点和终点差值判断。

```ts
let startX = 0;
let startY = 0;

element.addEventListener("touchstart", (event) => {
  const touch = event.touches[0];
  startX = touch.clientX;
  startY = touch.clientY;
});

element.addEventListener("touchend", (event) => {
  const touch = event.changedTouches[0];
  const dx = touch.clientX - startX;
  const dy = touch.clientY - startY;

  if (Math.abs(dx) > 40 && Math.abs(dx) > Math.abs(dy)) {
    console.log(dx > 0 ? "向右滑" : "向左滑");
  }
});
```

判断手势时要设置阈值，避免轻微抖动被识别成滑动。还要比较横向和纵向距离，避免和页面滚动冲突。

如果交互区域既支持横滑又支持纵向滚动，最好再加入方向锁定。方向锁定前不要抢占滚动，锁定后再跟随手势变化。这样可以避免用户只是想往下滑看内容，却被组件误判为横向操作。

方向锁定的前提是给手势足够的容忍区间。阈值太小会误判，阈值太大又会让交互迟钝。轮播、图片预览、抽屉返回这类场景，要针对用户习惯单独调。

除了距离阈值，很多滑动还会加入速度判断。例如列表左滑删除，如果用户快速甩出一个短距离动作，也可以判定为有效；如果用户慢慢移动但距离不够，则更像试探。距离和速度一起看，通常比单看位移更符合直觉。

## 滚动冲突

移动端手势最难的是冲突。横向轮播嵌在纵向页面里，既要允许页面上下滚动，又要让横向滑动可用。

```css
.carousel {
  touch-action: pan-y;
}
```

常见策略是先判断移动方向，未超过阈值前不抢占，明确组件区域的 `touch-action`，避免全局拦截所有触摸事件。能用 CSS 解决的手势冲突，不要全部用 `preventDefault` 硬拦截。

手势冲突还和容器层级有关。页面里同时存在 `body` 滚动、弹窗内部滚动、横向滑动区域和下拉刷新时，手势归属会变得复杂。更稳的设计是减少嵌套滚动容器，横向手势区域只占必要高度，并通过 `touch-action`、方向锁定和边界回弹共同控制。

当组件到了边界时，是否把后续手势交还给外层容器，也是体验的一部分。比如轮播滑到第一张继续右滑时，要不要触发页面返回手势；列表滚到顶部继续下拉时，要不要交给页面刷新，这些都属于手势边界设计。

## 长按

长按通常通过定时器实现，并在移动或抬起时取消。

```ts
let timer: number | undefined;

element.addEventListener("touchstart", () => {
  timer = window.setTimeout(() => {
    openContextMenu();
  }, 600);
});

element.addEventListener("touchmove", () => clearTimeout(timer));
element.addEventListener("touchend", () => clearTimeout(timer));
```

长按要考虑系统默认菜单、文字选择、图片保存等行为。涉及 WebView 或小程序时，还要看容器是否拦截了长按。

长按不是“等够时间就行”。手指移动超过阈值、触点取消、页面切后台、弹窗关闭时，都应该清理定时器，否则用户只是滚动了一下列表，也可能在半秒后突然弹出菜单。

长按菜单要尽量和系统菜单行为区分开，尤其在 WebView 里。如果页面本身也支持文字选择、图片保存或复制，长按策略就要更谨慎。

如果长按只是为了补充一个次级操作入口，最好同时提供可见操作入口。把重要能力完全藏在长按里，会增加学习成本，也不利于跨端一致性。

## 交互反馈

手势必须有及时反馈。拖拽时元素跟手、长按时出现状态变化、滑动时有位移或阻尼，都能让用户知道系统正在响应。

| 手势 | 反馈 |
| --- | --- |
| 点击 | 按压态、按钮禁用 |
| 滑动 | 跟手移动、阈值提示 |
| 长按 | 触觉或视觉提示 |
| 拖拽 | 占位、吸附、边界 |

没有反馈的手势会让用户不确定是否生效。手势越隐蔽，反馈越重要。复杂手势不要轻易从零实现，图片缩放、惯性滚动、拖拽排序这类能力更适合使用成熟组件或专门库。

反馈要和结果强度匹配。轻微横滑可以只显示操作按钮，达到阈值后再出现颜色变化或震动反馈；拖拽排序要显示占位位置；图片缩放要有边界阻尼。用户需要在动作过程中看到“现在发生了什么”，而不是等松手后才知道结果。

手势实现完成后，最好在真机上对横向、纵向、混合滚动和边缘滑动分别试一遍。很多问题只在真实触摸条件下才会暴露。

如果一个手势必须依赖教程说明用户才会用，通常说明它不够直观。移动端里真正高频、可持续的手势，往往都有清晰反馈、明确边界和自然的心理预期。
