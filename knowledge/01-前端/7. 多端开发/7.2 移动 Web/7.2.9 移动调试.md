## 调试困难

移动 Web 调试比桌面 Web 更复杂，因为问题经常只在真实设备、真实网络和真实 WebView 中出现。桌面浏览器模拟视口只能发现布局问题，不能完全代表移动端行为。

常见移动端问题包括：

- 某个系统版本样式异常
- 软键盘导致布局错乱
- WebView 和浏览器表现不同
- 弱网下资源加载顺序变化
- 真机触摸和滚动不流畅

移动端问题还经常具有“偶发”和“组合触发”的特点：只在某个系统版本、某个 App 容器、某个网络条件、某个输入法、某个屏幕比例下出现。调试时不要急着改代码，先把复现环境收窄到可描述、可重复、可对比。

真正难的不是“怎么开调试工具”，而是怎么把用户口中的“偶尔会卡”“有时候点不动”“某些手机会白屏”转成可以复现的具体条件。移动调试的第一步通常不是写代码，而是收集环境。

## 真机验证

移动 Web 至少要覆盖几类真实环境：

- 主流 Android 浏览器和系统 WebView
- iOS Safari 和内嵌 WebView
- 不同屏幕比例和像素密度
- 弱网、断网、切后台恢复

只在桌面模拟器里通过，不代表移动端真正可用。

真机验证最好建立基础矩阵：一台较新的 iPhone、一台较新的 Android、一台低端 Android、一个目标 App WebView。如果业务主要来自微信、支付宝、企业微信或内嵌浏览器，还要把这些容器纳入必测范围。低端机不是“极端情况”，它经常代表真实用户的性能下限。

真机验证不是每次都要全量覆盖所有设备，而是要有一组稳定的基线设备和容器。只要这组基线持续可用，很多回归问题就能在发版前被更早发现。

## 日志与埋点

线上移动端问题很难让用户打开 DevTools，所以需要前置日志能力：

- JavaScript 错误日志
- 资源加载失败
- 页面白屏检测
- 关键接口耗时
- 设备、系统和容器版本信息

如果缺少设备和容器版本，很多兼容性问题会很难复现。

日志要能回答三个问题：页面跑在什么环境、发生了什么错误、错误前后做了什么操作。移动端日志里至少应包含 URL、构建版本、UA、系统版本、容器版本、网络类型、页面可见性变化和关键请求 trace id。

如果没有版本号和容器信息，很多日志几乎不可用。移动端线上问题常常不是“这个页面错了”，而是“某个版本的某个 WebView 容器在某种网络下错了”，上下文不全就很难定位。

## 调试顺序

移动端问题可以按下面顺序排查：

1. 先确认是否只在某类设备或容器出现。
2. 再看网络和资源加载是否异常。
3. 再看控制台错误和接口返回。
4. 最后看布局、键盘、触摸和性能录制。

移动调试的关键是缩小范围，不要一上来就猜是框架问题。

排查时可以用“替换法”快速定位：同一页面换设备、同一设备换浏览器、同一浏览器换网络、同一网络换账号、同一账号清缓存。如果问题跟着设备走，多半是兼容或性能；跟着网络走，多半是资源或接口；跟着账号走，则要看数据规模、权限和服务端返回。

调试顺序的核心，是先缩小变量，再深入具体层级。设备、系统、容器、网络、账号、版本这些变量如果不先压缩，后面看到的异常现象往往会互相干扰。
## 真机优先

移动 Web 调试必须重视真机。桌面浏览器模拟器只能覆盖 viewport 和部分触摸行为，无法完整模拟 WebView、键盘、安全区、系统权限和性能。

```txt
桌面模拟 -> 快速布局检查
真机浏览器 -> 触摸、键盘、性能
App WebView -> 容器、Bridge、离线包
微信/支付宝内置浏览器 -> 平台限制
```

问题只在真机出现很常见，尤其是输入框、滚动、fixed 定位、视频、上传和支付。

桌面模拟器适合快速调整布局断点和初步检查响应式样式，真机适合验证触摸、滚动、输入、视频、上传、定位、支付和分享。两者不是替代关系，而是先快筛、再实测的关系。

如果问题和键盘、视频、权限、文件上传、分享、支付、定位有关，几乎都应该默认上真机。模拟器可以帮你提速，但不能替你证明真实体验成立。

## 远程调试

Android Chrome 可以通过远程调试查看移动端页面。

```txt
手机开启 USB 调试
连接电脑
Chrome 打开 chrome://inspect
选择目标页面 Inspect
```

iOS Safari 可以通过 Web Inspector 调试 Safari 或 WKWebView 页面。

```txt
iPhone 开启 Web 检查器
Mac Safari 开启开发菜单
连接设备后选择页面
```

远程调试能查看 Console、Network、Elements、Performance，是定位移动端问题的基础工具。

远程调试时要注意页面是否真的加载的是同一份资源。开发环境、测试环境、离线包、灰度版本和 CDN 缓存都可能让你看到“看似同一个页面，实际不是同一份代码”。调试前先确认页面 URL、构建版本和资源 hash。

远程调试拿到工具面板后，优先看三类信息：Console 是否报错、Network 是否有失败和重试、Elements 里最终渲染的 DOM/CSS 是否和预期一致。先抓大方向，再做细节录制，效率通常更高。

## WebView 调试

Hybrid 页面需要容器允许调试。Android 通常要开启 WebView debugging，iOS 要使用可调试构建。

```txt
确认当前加载 URL
确认离线包版本
查看 JS 错误
查看资源请求
查看 Bridge 调用日志
```

WebView 白屏不要只看 H5 代码。容器拦截、离线包损坏、HTTPS 证书、域名白名单、Bridge 初始化失败都可能导致白屏。

Hybrid 调试要同时看 H5 日志和原生日志。H5 侧看到的只是页面内部错误，原生侧才可能看到 WebView 创建失败、资源拦截失败、证书校验失败、Bridge 注入时机异常等问题。涉及 [[7.4.2 JSBridge|JSBridge]] 的页面，还要确认 Bridge 是否在业务代码调用前已经完成注入。

WebView 问题最怕只从单侧视角看。页面白屏、点击无响应、上传失败、支付不回调，既可能是 H5 逻辑问题，也可能是容器没初始化好、宿主拦截了请求，或者原生回调没有按协议返回。

## 网络排查

移动端网络问题常来自弱网、代理、证书、跨域、缓存和域名配置。

| 工具 | 用途 |
| --- | --- |
| Chrome DevTools Network | 请求与资源加载 |
| Charles / Proxyman | 抓包、弱网、Mock |
| 平台日志 | WebView/原生错误 |
| 服务端日志 | 接口真实响应 |

抓包 HTTPS 时要安装证书，并注意部分 App 或系统会限制用户证书。线上问题要结合请求 id 或 trace id 定位。

弱网排查不要只看接口是否成功，还要看资源加载顺序、超时策略和重试行为。移动网络下 DNS、TLS、首包时间和丢包都会放大首屏问题；如果页面依赖多个首屏接口串行返回，弱网下就会比桌面环境慢很多。

抓包时还要注意缓存命中和容器层改写。有些请求在 DevTools 里看起来正常，但实际上被 Service Worker、离线包、中间代理或宿主容器二次处理过，最终行为和浏览器直连并不完全一样。

## 性能排查

移动端性能要关注首屏、长任务、滚动、图片和内存。

```txt
Performance 面板看长任务
Lighthouse 看基础指标
真机录屏看交互卡顿
Network 看资源体积
Memory 看泄漏趋势
```

低端 Android 设备是非常重要的验证环境。只在桌面模拟器和高端手机上流畅，不代表真实用户体验稳定。

性能排查要区分加载慢、执行慢和渲染慢。加载慢看 Network 和缓存，执行慢看长任务和脚本拆分，渲染慢看滚动、动画、图片解码、布局抖动和图层合成。移动端性能优化最终要回到真实设备上的录制结果，而不是只看本机开发环境的数字。

移动调试真正有效的时候，不是你开了多少工具，而是你能把问题稳定归类到某一层：资源、脚本、渲染、容器、系统还是网络。归类一旦清楚，后面的修复路径通常就会快很多。
