## viewport 影响

正确设置 viewport 是消除点击延迟的基础。

```html
<meta
  name="viewport"
  content="width=device-width, initial-scale=1"
/>
```

如果页面仍按桌面宽度缩放，浏览器可能保留双击缩放判断。移动端页面首先要确保 viewport 配置正确。现代页面里，很多“点击慢”的问题，本质上不是浏览器天生慢，而是页面缩放、布局和手势判断没有被正确配置。

如果页面允许用户缩放，不代表一定会出现点击延迟；如果页面设置了标准 viewport，也不代表所有容器都没有点击问题。内置 WebView、旧系统浏览器、第三方容器和手势库都可能重新引入延迟感，所以排查时要先确认运行环境，而不是只看代码里有没有 viewport。

从工程角度看，viewport 更像点击体验的前置条件，而不是最终答案。它解决的是浏览器要不要继续等待双击缩放判断，但解决不了业务代码自己造成的迟缓。

## touch-action

`touch-action` 可以告诉浏览器某个元素允许哪些默认触摸行为。

```css
.button {
  touch-action: manipulation;
}
```

`manipulation` 通常表示允许平移和缩放相关的常规操作，同时减少双击缩放等待。它适合按钮、链接、可点击卡片等元素。

```css
a,
button,
.tap-target {
  touch-action: manipulation;
}
```

对于有拖拽、滑动、地图、画布等复杂手势的区域，`touch-action` 更应该按区域单独控制，而不是全局一刀切。

`touch-action` 的价值在于让浏览器提前知道交互意图。它不是性能魔法，也不能替代事件逻辑；如果组件仍然在主线程里做重计算，点击看起来还是会慢。按钮、Tab、开关这类明确点击控件可以使用 `manipulation`，滑动区域则更适合声明 `pan-x`、`pan-y` 或按场景组合。

很多点击体验差的页面，其实是把“点一下”变成了“点一下后还要等 JS 决定下一步”。浏览器默认行为越明确，主线程判断越少，用户就越容易感知到即时响应。

## pointer 事件

现代浏览器支持 Pointer Events，可以统一鼠标、触摸、手写笔输入。

```js
button.addEventListener("pointerup", () => {
  submit();
});
```

但普通按钮点击仍然优先使用 `click`，因为它和键盘、辅助技术、默认可访问性行为配合更好。只有自定义手势或高响应需求时，再直接处理 pointer/touch。

如果用 `pointerup` 自己模拟点击，要补齐很多原生行为：键盘触发、焦点管理、禁用态、表单提交、辅助技术语义、拖出元素后的取消逻辑。普通按钮直接使用 `<button>` 往往比手写指针事件更可靠。

这也是为什么自定义组件库里要特别谨慎。一个“看起来只是更快一点”的自定义点击实现，可能悄悄损失掉原生按钮几十个细节行为，后续再一项项补回来的成本非常高。

## fastclick 历史

过去常用 FastClick 之类库消除 300ms 延迟。现代项目通常不再需要。

```txt
现代浏览器 + 正确 viewport -> 通常无点击延迟
旧 WebView / 特殊缩放 -> 可能仍需兼容
```

引入这类库前要确认真实问题存在。多余的 touch/click 兼容层可能带来双触发、阻止默认行为和表单问题。

老项目里如果已经引入 fastclick 类库，迁移时不要直接删除。更稳妥的做法是先统计目标浏览器和 WebView 版本，建立一组点击、输入框、滚动、弹窗的回归用例，再逐步移除并观察是否出现双击缩放、输入聚焦或点击穿透问题。

这类兼容库的价值主要属于历史阶段。现在更常见的问题，已经不是浏览器统一存在 300ms 延迟，而是少数旧容器、老 WebView 或业务自己叠加的事件处理把问题重新制造出来。

## 双触发问题

同时监听 `touchend` 和 `click` 容易导致同一操作执行两次。

```js
element.addEventListener("touchend", submit);
element.addEventListener("click", submit);
```

如果必须兼容 touch 和 click，要做统一封装和去重。普通按钮不要同时绑两套事件。

双触发常见于“touchend 里立即执行动作，同时浏览器随后又派发 click”。处理方式不是到处加布尔锁，而是统一事件入口：普通控件只监听 `click`，手势组件只在识别成功后阻止或吞掉后续兼容事件，并把去重逻辑封装在组件内部。

如果项目里同一个组件既监听 `touchend` 又监听 `click`，还混入了框架层的合成事件，排查时就要特别小心事件顺序。很多“偶现重复提交”其实就是多套点击链路叠在一起。

## 可访问性

为了追求触摸响应，不要破坏键盘和辅助技术。

```html
<button type="button">提交</button>
```

原生 `button` 天然支持键盘、焦点、禁用、语义。自定义 `div` 按钮需要额外处理 role、tabindex、键盘事件，成本更高。

```text
更稳的顺序：
1. 先用原生语义元素
2. 再补 viewport 和 touch-action
3. 再排查主线程和任务阻塞
4. 最后才考虑手势兼容层

移动页面并不只被手指使用。外接键盘、读屏软件、车机浏览器、平板触控笔都会触发不同输入路径。点击优化如果牺牲语义，短期看是“快了”，长期会让测试、无障碍和跨端适配一起变难。
```

按钮的“快”不只是触发快，还包括反馈快。按下态、加载态、禁用态、错误提示都属于点击体验的一部分。只解决了事件延迟，但没有解决用户对状态变化的感知，整体体验仍然会显得迟钝。

## 排查路径

```txt
确认 viewport
确认浏览器或 WebView 版本
检查是否允许双击缩放
检查是否同时绑定 touch 和 click
检查是否有第三方 fastclick
真机录制点击响应
```

点击慢不一定是 300ms 延迟，也可能是主线程长任务、请求阻塞、按钮防抖、React/Vue 状态更新或 WebView 容器处理慢。移动端点击优化的关键，是先区分“事件触发慢”和“页面响应慢”。

用户感知里的“慢”通常包括三段：按下后没有反馈、业务动作迟迟不开始、页面状态很久不更新。第一段靠视觉按压态解决，第二段靠减少主线程阻塞和去重事件解决，第三段靠请求状态、骨架屏或乐观更新解决。不要把所有问题都归因到点击延迟。

这也是移动点击问题最容易被误诊的地方。用户说“点不动”时，可能是事件没触发、触发了但被防抖吞掉、请求发出去了但按钮没反馈、页面更新了但用户没感知到。先把“哪一段慢”拆出来，修复才不会跑偏。

## 判断边界

如果点击延迟只发生在某个旧 WebView 或特定机型上，优先看容器和兼容配置；如果所有设备都慢，优先看主线程、渲染和业务逻辑。不要一上来就加兼容库，先找真正的延迟来源。
