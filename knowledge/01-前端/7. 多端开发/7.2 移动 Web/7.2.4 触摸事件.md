## 输入模型

移动 Web 的主要输入方式是触摸。触摸和鼠标不同：一个手势可能包含多个触点，也可能产生滑动、缩放、长按等复杂交互。写移动端交互时，不能把触摸事件简单理解成“移动端的鼠标事件”，而要把它看成一段连续输入流。

早期移动端常见 `touchstart`、`touchmove`、`touchend`、`touchcancel`；现代 Web 也会使用 Pointer Events，用统一模型处理鼠标、触摸笔和触摸屏。只有目标环境存在旧 WebView 兼容问题时，才需要回到 Touch Events 做兜底。

| 事件体系 | 代表事件 | 适合场景 | 注意点 |
|---|---|---|---|
| Touch Events | `touchstart`、`touchmove`、`touchend` | 移动端滑动、手势、拖拽 | 要处理多指、滚动冲突和默认行为 |
| Mouse Events | `mousedown`、`mousemove`、`click` | 桌面点击、兼容兜底 | 移动端可能同时触发兼容鼠标事件 |
| Pointer Events | `pointerdown`、`pointermove`、`pointerup` | 跨输入设备组件 | 需要结合 `pointerType` 判断来源 |

触摸交互的关键不是监听了多少事件，而是能否从事件流中稳定识别用户意图：轻触应该触发点击，横向滑动不应该抢走纵向滚动，多指缩放不应该误触业务手势，系统中断时组件状态也要能恢复。

如果把触摸事件只当成“点击的前置版本”，后面几乎一定会遇到滚动冲突、拖拽抖动和双触发问题。移动端输入更像一段连续过程，而不是一次孤立事件。

## Touch 对象

触摸事件对象里最关键的是三组触点集合：`touches`、`targetTouches` 和 `changedTouches`。它们不是同义词，混用会导致多指手势和滑动结束时取错坐标。

| 属性 | 含义 | 常见用途 |
|---|---|---|
| `touches` | 当前屏幕上的所有触点 | 判断是否存在多指操作 |
| `targetTouches` | 当前目标元素上的触点 | 组件内部手势识别 |
| `changedTouches` | 本次事件发生变化的触点 | 在 `touchend` 中读取离开的手指 |

```javascript
const state = {
  startX: 0,
  startY: 0,
};

const card = document.querySelector(".card");

card.addEventListener(
  "touchstart",
  (event) => {
    const touch = event.changedTouches[0];
    state.startX = touch.clientX;
    state.startY = touch.clientY;
  },
  { passive: true },
);

card.addEventListener(
  "touchend",
  (event) => {
    const touch = event.changedTouches[0];
    const deltaX = touch.clientX - state.startX;
    const deltaY = touch.clientY - state.startY;

    if (Math.abs(deltaX) > 60 && Math.abs(deltaX) > Math.abs(deltaY)) {
      console.log(deltaX > 0 ? "向右滑动" : "向左滑动");
    }
  },
  { passive: true },
);
```

`touchend` 时手指已经离开屏幕，`touches[0]` 可能不存在，因此结束阶段通常读取 `changedTouches[0]`。如果组件支持多指，还要用 `identifier` 追踪同一个触点，不能默认数组第一个触点永远对应同一根手指。

```javascript
const activeTouches = new Map();

surface.addEventListener("touchstart", (event) => {
  for (const touch of event.changedTouches) {
    activeTouches.set(touch.identifier, {
      startX: touch.clientX,
      startY: touch.clientY,
    });
  }
});

surface.addEventListener("touchend", (event) => {
  for (const touch of event.changedTouches) {
    const snapshot = activeTouches.get(touch.identifier);
    if (!snapshot) continue;
    activeTouches.delete(touch.identifier);
  }
});
```

这类写法在双指缩放、双指旋转、自定义画布输入里更稳，因为它不会把多个触点混成一个状态。

## 坐标体系

触摸点常见坐标有 `clientX`、`pageX`、`screenX`。移动端页面存在滚动、缩放、软键盘和视口变化时，坐标选择会直接影响计算结果。

| 坐标 | 参照系 | 使用场景 |
|---|---|---|
| `clientX/clientY` | 视口左上角 | 判断元素内拖动、滑动方向 |
| `pageX/pageY` | 文档左上角 | 需要考虑页面滚动距离的定位 |
| `screenX/screenY` | 设备屏幕左上角 | 较少用于 Web 业务 |

写手势组件时，通常使用 `clientX/clientY` 计算移动距离，因为它不受文档滚动距离影响，更符合用户在当前屏幕上的动作感知。涉及元素命中、吸附位置或绝对页面位置时，再结合 `getBoundingClientRect()`、滚动位置和 [[7.2.1 视口|视口]] 变化一起判断。

坐标问题在移动端特别容易和滚动混淆。页面一旦发生滚动、回弹、键盘顶起、地址栏收缩，仅凭某一个坐标系就下结论，往往会导致吸附位置漂移或拖拽终点不准。

## 默认行为

触摸事件常和浏览器默认行为冲突，例如页面滚动、双指缩放、下拉刷新、文本选择和系统返回手势。处理这类问题时不能随意 `preventDefault()`，否则可能破坏页面滚动、缩放能力和可访问性。

CSS 的 `touch-action` 可以提前告诉浏览器某个区域允许哪些触摸行为，比在高频 `touchmove` 中临时阻止默认行为更稳定：

```css
.horizontal-slider {
  touch-action: pan-y;
  overflow: hidden;
}
```

`touch-action: pan-y` 表示浏览器可以处理纵向滚动，横向手势交给页面逻辑处理。它和 [[7.2.6 点击延迟|点击延迟]] 一样，都是通过提前声明交互意图来减少浏览器猜测和兼容成本。

下面几种默认行为最常见：

| 默认行为 | 常见触发场景 | 是否应轻易阻止 |
| --- | --- | --- |
| 页面滚动 | 列表、正文页 | 不应轻易阻止 |
| 双击缩放 | 老容器、非标准 viewport | 优先用配置避免 |
| 文本选择 | 长按文字 | 视场景决定 |
| 下拉刷新 | 顶部回弹 | 先看宿主是否支持配置 |

## 滚动冲突

移动端手势最棘手的问题是横向滑动组件与页面纵向滚动冲突。直接在 `touchmove` 中调用 `preventDefault()` 虽然能阻止滚动，但会破坏页面滚动体验，也可能触发浏览器关于 passive listener 的警告。

```javascript
let startX = 0;
let startY = 0;
let locked = false;

slider.addEventListener(
  "touchstart",
  (event) => {
    const touch = event.changedTouches[0];
    startX = touch.clientX;
    startY = touch.clientY;
    locked = false;
  },
  { passive: true },
);

slider.addEventListener(
  "touchmove",
  (event) => {
    const touch = event.changedTouches[0];
    const deltaX = touch.clientX - startX;
    const deltaY = touch.clientY - startY;

    if (!locked) {
      locked = Math.abs(deltaX) > Math.abs(deltaY) && Math.abs(deltaX) > 8;
    }

    if (locked) {
      event.preventDefault();
      slider.style.transform = `translateX(${deltaX}px)`;
    }
  },
  { passive: false },
);
```

这段代码体现了两个边界：方向锁定前不要急着拦截滚动，真正需要 `preventDefault()` 的监听器不能声明为 passive。实际项目里还要在 `touchend` 和 `touchcancel` 中释放锁定状态，否则一次异常中断可能让组件一直停留在拖拽态。

复杂页面里，滚动冲突通常不是单个组件的问题，而是多个滚动容器和多个手势区叠在一起导致的。排查时要先确认谁应该拥有滚动权，再看手势是否越界抢占。

## Pointer Events

Pointer Events 把鼠标、触摸和触控笔统一成 `pointerdown`、`pointermove`、`pointerup`。它的优势是代码路径更少，也能通过 `pointerType` 识别输入来源，并通过 `setPointerCapture()` 在拖拽时持续接收当前指针事件。

```javascript
const box = document.querySelector(".drag-box");
let activePointerId = null;
let x = 0;
let y = 0;

box.addEventListener("pointerdown", (event) => {
  if (event.button !== 0) return;
  activePointerId = event.pointerId;
  box.setPointerCapture(event.pointerId);
});

box.addEventListener("pointermove", (event) => {
  if (event.pointerId !== activePointerId) return;
  x += event.movementX;
  y += event.movementY;
  box.style.transform = `translate(${x}px, ${y}px)`;
});

box.addEventListener("pointerup", (event) => {
  if (event.pointerId !== activePointerId) return;
  box.releasePointerCapture(event.pointerId);
  activePointerId = null;
});
```

组件库里的拖拽、滑块、画布和手势组件，更适合优先考虑 Pointer Events。普通按钮、链接、表单控件不要为了“移动端优化”绕开原生点击模型，因为原生控件已经处理了键盘、辅助技术和焦点语义。

如果项目同时面向桌面端和平板、手机，Pointer Events 的统一收益会更明显。它能减少 mouse/touch 两套逻辑并存导致的状态分叉，也更适合做跨端组件库。

## 性能边界

触摸移动事件触发频率很高，不适合在每次回调里做重计算、同步布局读取或大量 DOM 操作。滚动、拖拽、手势动画通常要配合节流、`requestAnimationFrame` 和合成层属性。

```javascript
let latestX = 0;
let ticking = false;

slider.addEventListener(
  "touchmove",
  (event) => {
    latestX = event.changedTouches[0].clientX;

    if (!ticking) {
      requestAnimationFrame(() => {
        slider.style.transform = `translateX(${latestX}px)`;
        ticking = false;
      });
      ticking = true;
    }
  },
  { passive: true },
);
```

触摸体验不好，不一定是事件写错，也可能是主线程被长任务占住、图片解码阻塞、滚动容器层级过深或同步布局读写交替触发重排。排查卡顿时要把手势代码放回 [[6.3.2 长任务优化|长任务优化]] 和 [[6.3.6 重排与重绘|重排与重绘]] 的链路里看。

手势代码最怕在 `touchmove` 里同时做这几件事：读布局、改样式、发请求、算业务状态。只要其中一件偏重，用户感知就会从“跟手”变成“拖着走”。移动手势优化的第一原则，是把高频输入路径变短。

## 手势边界

手势不是越灵敏越好。滑动阈值、方向锁定、惯性距离、取消条件都会影响用户体验。常见边界包括：

| 边界 | 现象 | 处理方式 |
|---|---|---|
| 抖动 | 手指轻微移动触发滑动 | 设置最小移动阈值 |
| 斜滑 | 横向组件抢占纵向滚动 | 根据 `deltaX/deltaY` 判断主方向 |
| 多指 | 双指缩放误触业务手势 | `touches.length > 1` 时退出 |
| 取消 | 系统中断触摸流程 | 监听 `touchcancel` / `pointercancel` |

移动 Web 中的触摸事件和 [[7.1.5 适配体系|适配体系]] 有直接关系：不同设备像素比、视口宽度和 WebView 行为会改变用户实际触发区域，因此可点击区域、拖拽阈值和滚动容器都要用真实设备验证。

真实项目里，手势边界最好写成组件约定，而不是散落在各页面里。阈值、方向判断、取消策略和默认行为处理越统一，跨端适配越稳，也更不容易出现“这个列表能滑，那个列表一滑就卡”的体验割裂。
