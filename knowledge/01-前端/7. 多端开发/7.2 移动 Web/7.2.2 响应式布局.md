## 目标核心

响应式布局的目标，是让同一份 Web 页面在不同屏幕宽度、比例和输入方式下保持可读、可操作和结构稳定。它不是简单把页面等比缩小，而是让内容根据空间重新组织。

响应式布局不是“缩放页面”，而是“重排内容”。内容优先、结构重组和操作可达性，比单纯视觉还原更重要。

```text
常见变化：
单列与多列切换
图片和视频宽度自适应
导航从横向菜单变成抽屉或底部栏
表格、卡片、表单在窄屏下重新排列
```

响应式布局解决的是“空间变了，内容怎么排”的问题。它和移动适配、容器尺寸、触控区、键盘遮挡、内容优先级是联动的。

真正好的响应式布局，不会让用户明显感到“这是同一页被硬挤到了小屏上”。用户看到的应该是自然重组后的信息结构，而不是勉强保留桌面排版痕迹的缩小版。

## 视口基础

响应式布局首先要设置正确的 viewport。

```html
<meta name="viewport" content="width=device-width, initial-scale=1" />
```

`width=device-width` 让布局视口匹配设备宽度，`initial-scale=1` 保持初始缩放正常。没有这个配置，移动端页面可能会按桌面宽度缩放，导致字体、间距和点击区域都变得不可控。

视口配置正确后，媒体查询和布局规则才有机会按真实设备宽度工作。

如果团队里有人反馈“断点都写了还是不对”，先不要急着改样式，先确认视口是否正确、容器是否有固定宽度、页面是否被宿主容器缩放过。很多看似是布局问题，根因其实在视口或容器层。

## 媒体查询

媒体查询是响应式布局最基础的工具。断点不要只按设备型号设置，更应该根据内容何时放不下、何时可读性下降来设置。

```css
.cards {
  display: grid;
  grid-template-columns: repeat(3, 1fr);
}

@media (max-width: 768px) {
  .cards {
    grid-template-columns: 1fr;
  }
}
```

真正的分界点应该来自内容，而不是从某个设备规格表里抄一个数字。比如导航菜单在某个宽度开始挤压、表格在某个宽度开始难读、卡片在某个宽度开始放不下，这些都可以成为断点。

断点越贴近内容压力，布局越稳定。硬记设备型号，不如记住“什么时候页面开始失衡”。

除了 `width`，响应式布局有时还要关注这些条件：

| 条件 | 适合判断什么 |
| --- | --- |
| `hover` | 当前设备是否适合悬停交互 |
| `pointer` | 指针是否精细，是否更偏鼠标 |
| `orientation` | 横竖屏切换后的布局重组 |
| `prefers-reduced-motion` | 是否减少动画和位移 |

```css
@media (hover: hover) and (pointer: fine) {
  .menu-item:hover {
    background: #f5f5f5;
  }
}
```

## 弹性布局

Flex 和 Grid 是现代响应式布局的基础。Flex 适合一维排列，比如按钮组、导航、表单行；Grid 适合二维布局，比如卡片区、相册、仪表盘。

```css
.page {
  display: grid;
  grid-template-columns: 280px minmax(0, 1fr);
  gap: 24px;
}

@media (max-width: 960px) {
  .page {
    grid-template-columns: 1fr;
  }
}
```

不要在响应式布局里过度依赖固定宽高。固定像素写得越多，跨设备表现越容易失控。更稳的做法是使用百分比、弹性轨道、最大宽度和最小宽度约束。

响应式布局追求的是约束，而不是死尺寸。`max-width`、`minmax()` 和弹性盒通常比固定宽高更适合多设备。

很多响应式问题并不是“少了一个断点”，而是父容器缺少 `minmax(0, 1fr)`、子项没有 `min-width: 0`、图片没有限制最大宽度，导致内容一挤就溢出。布局系统如果约束没写好，断点再多也只是补漏洞。

```css
.layout {
  display: grid;
  grid-template-columns: 240px minmax(0, 1fr);
}

.content {
  min-width: 0;
}

img,
video {
  max-width: 100%;
  height: auto;
}
```

## 内容优先

响应式布局的起点是内容优先。窄屏下不是所有信息都必须硬塞进去，有些信息应该折叠、简化、延后显示，或者换一种结构表达。

```text
内容处理方式：
主信息优先展示
次要操作折叠到菜单
表格转卡片
横向复杂图表提供滚动或摘要
```

如果只是做媒体查询，页面可能“看起来能排下”，但点击区域太小、文本拥挤、按钮遮挡、视觉层次混乱，实际还是差。响应式更关注空间重组，而不是仅仅缩放。

响应式布局要和交互适配一起看。页面排得下，不代表点得舒服、看得清楚、滑得顺畅。

尤其是表格、筛选、图表和后台页面，不能只是简单缩成手机宽度。更合理的做法往往是拆成摘要卡片、关键指标优先、次级筛选折叠、复杂明细横向滚动或单独详情页承接。

## 常见误区

响应式布局和移动端适配不是一回事。响应式更关注内容如何随空间变化；移动端适配还包括触控、键盘、安全区、系统能力和性能档位。

```text
只做媒体查询的风险：
触控区过小
输入框被键盘遮挡
底部按钮被安全区盖住
布局变了但可读性没提升
```

如果只做媒体查询，页面可能“看起来能排下”，但点击区域太小、输入框被键盘挡住、底部按钮被安全区盖住，依旧不是合格的移动体验。

还有几个常见误区：

| 误区 | 实际问题 |
| --- | --- |
| 所有端都追求完全同构视觉 | 会牺牲可读性和操作效率 |
| 断点越多越专业 | 规则更碎，维护更难 |
| 所有内容必须完整保留 | 窄屏下信息密度会失控 |
| 桌面交互可以直接平移到移动端 | hover、右键、拖拽经常失效 |

## 断点选择

断点应该从内容和布局压力出发，而不是从设备型号硬背。

```css
@media (max-width: 1024px) { ... }
@media (max-width: 768px) { ... }
@media (max-width: 480px) { ... }
```

通常可以先围绕“导航是否还能横排”“表格是否还能读”“卡片是否还能并列”“表单是否还能并行”这几个问题设置断点，再逐步优化。断点越少，维护越简单；断点越准确，布局越稳定。

断点不是越多越好。过多断点会让布局规则碎片化，维护和调试都更困难。

一个实用做法是先只设少量主断点，再围绕少数局部组件做容器内调整。先保证页面级结构稳定，再处理局部精修，比一上来写大量全局断点更稳。

## 组合单位

响应式布局通常会组合多种单位和约束：`max-width` 控制阅读宽度，`minmax()` 和 `fr` 处理弹性轨道，`clamp()` 控制字号或间距，`rem`/`vw` 处理缩放，`env()` 处理安全区。

```css
.article {
  max-width: 42rem;
  margin-inline: auto;
  padding-inline: clamp(16px, 4vw, 32px);
}
```

移动 Web 的布局和 [[7.2.3 REM 与 VW|REM 与 VW]] 是配套关系：单位决定怎么缩放，布局决定怎么重新排布。只改单位，不改结构，通常不够。

真正好的响应式方案，通常是“布局重组 + 合理单位 + 适当断点”三者一起用，而不是依赖单一技巧。

```css
.dashboard {
  display: grid;
  grid-template-columns: repeat(12, minmax(0, 1fr));
  gap: clamp(12px, 2vw, 24px);
}

.summary {
  grid-column: span 4;
}

.chart {
  grid-column: span 8;
}

@media (max-width: 768px) {
  .summary,
  .chart {
    grid-column: 1 / -1;
  }
}
```

这个思路的重点不是记住某种写法，而是学会先定义“桌面时如何分区，窄屏时如何回落成单列”，再用单位和断点把它落下来。
