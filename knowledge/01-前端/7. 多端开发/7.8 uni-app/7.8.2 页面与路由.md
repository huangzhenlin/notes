## 页面栈差异

uni-app 输出到不同端后，页面栈行为会受到目标平台影响。小程序端更接近宿主页面栈，H5 端更接近浏览器历史记录，App 端还会涉及原生容器和页面生命周期。

因此同一段跳转逻辑，要重点验证：

- 返回按钮是否符合预期
- tab 页面是否能正确进入
- 登录拦截后能否回到来源页
- 分享或外部入口进入后返回是否合理

路由封装如果不理解目标端页面栈，只做 API 包装，往往会把问题藏得更深。

页面栈差异会直接影响返回、刷新和登录回跳。跨端路由的核心不是统一 API 名称，而是让每个端都能得到符合用户预期的返回路径。

页面栈设计得不清楚时，问题通常不会立刻暴露，而是会在分享进入、登录回跳、tab 切换和长流程返回时集中爆发。路由语义一开始就要按真实用户路径设计，而不是只按开发调试路径设计。

## 页面缓存

不同端对页面缓存和组件保留的策略不同。返回页面时，是重新加载、恢复旧状态，还是触发显示生命周期，需要按目标端验证。

涉及表单、筛选条件、滚动位置和分页列表时，页面缓存策略尤其重要。

页面缓存要提前设计。列表页返回后是否保留滚动位置、筛选条件是否保留、详情页编辑后列表是否刷新，这些都不应该靠偶然生命周期触发来决定。

缓存策略如果没有明确约定，返回体验会很不稳定。有时保留状态，有时重建页面，有时列表不刷新，用户会明显感到应用“没有固定规律”。
## pages 配置

uni-app 页面需要在 `pages.json` 中声明。页面路径、导航栏标题、下拉刷新、背景色等页面级配置都可以在这里维护。

```json
{
  "pages": [
    {
      "path": "pages/index/index",
      "style": {
        "navigationBarTitleText": "首页"
      }
    },
    {
      "path": "pages/product/detail",
      "style": {
        "navigationBarTitleText": "商品详情"
      }
    }
  ]
}
```

页面文件和配置路径要一致。新增页面后如果没有写入 `pages.json`，运行时无法通过路由进入。

`pages` 的顺序和配置也会影响默认首页、分包结构和部分平台的入口行为。页面新增、移动、重命名后，必须同步检查路径、tabBar、分包和跳转代码。

`pages.json` 在 uni-app 里既是页面注册表，也是路由元信息入口。路径、标题、刷新能力、tabBar 关系一旦漂移，问题通常不是局部的，而会影响多个目标端。

## 页面文件

一个页面通常是一个 `.vue` 文件。

```txt
pages/
  index/
    index.vue
  product/
    detail.vue
```

页面组件负责路由参数、页面生命周期、请求装配和业务组件组合；可复用卡片、按钮、表单项应放到组件目录中。

页面文件不要承担所有 UI 细节。更好的结构是页面负责流程和数据，业务组件负责展示和局部交互，服务层负责请求和格式转换。这样页面路由变化时，不会牵动大量 UI 代码。

页面写得太重，路由层的问题和业务层的问题就会缠在一起。把页面控制在“流程编排层”，后面做返回刷新、登录守卫和参数恢复时会轻松很多。

## 跳转 API

uni-app 使用 `uni.navigateTo`、`uni.redirectTo`、`uni.switchTab`、`uni.navigateBack` 等 API 管理页面跳转。

```ts
uni.navigateTo({
  url: "/pages/product/detail?id=p1",
});
```

不同 API 对页面栈影响不同。

| API | 作用 | 适合场景 |
| --- | --- | --- |
| `navigateTo` | 保留当前页，打开新页 | 列表到详情 |
| `redirectTo` | 替换当前页 | 登录后替换中间页 |
| `switchTab` | 跳转 tabBar | 首页、我的 |
| `navigateBack` | 返回上级页面 | 详情返回列表 |
| `reLaunch` | 关闭所有页面重新打开 | 登出、重置流程 |

页面栈是小程序和 App 端都要关注的模型。不要所有跳转都用 `navigateTo`，否则返回路径会变得混乱。

跳转 API 应该按场景选择：列表到详情保留返回，用 `navigateTo`；登录成功替换中间页，用 `redirectTo`；回首页或主导航，用 `switchTab`；退出登录或重置流程，用 `reLaunch`。

路由 API 的区别本质上是页面栈区别。只要栈语义没想清楚，业务层再怎么封装，也只是把问题推迟到返回和恢复阶段才暴露。

## 参数读取

页面可以在 `onLoad` 中读取 URL 参数。

```ts
import { onLoad } from "@dcloudio/uni-app";
import { ref } from "vue";

const productId = ref("");

onLoad((options) => {
  productId.value = String(options?.id ?? "");
});
```

路由参数适合传 id、类型、来源等小而稳定的数据。完整业务对象应通过 id 查询或从缓存恢复，不适合序列化塞进 URL。

参数读取时要把参数当成不可信输入。扫码、分享、H5 刷新、外部跳转都可能造成参数缺失或格式异常，页面应提供错误态或兜底跳转，而不是直接进入空白。

一个可恢复的页面，通常只依赖少量稳定参数。参数一旦开始承担整块业务对象或临时状态，分享和刷新路径就会变得很脆弱。

## tabBar 页面

tabBar 页面需要在 `pages.json` 中配置，并通过 `switchTab` 跳转。

```json
{
  "tabBar": {
    "list": [
      {
        "pagePath": "pages/index/index",
        "text": "首页"
      },
      {
        "pagePath": "pages/user/index",
        "text": "我的"
      }
    ]
  }
}
```

tabBar 页面通常是应用主入口，不适合承载过深的业务路径。详情、编辑、支付等页面应使用普通页面栈。

tabBar 页面也不适合承担复杂 query 状态。主入口应保持稳定，复杂筛选、详情和流程页放到普通页面里，必要时通过全局状态或缓存传递刷新信号。

tabBar 更像一级导航，不像流程节点。把深流程和复杂参数塞进 tab 页，最终通常会把刷新、返回和分享路径一起搞乱。

## 分包页面

大型应用可以通过分包降低主包体积。

```json
{
  "subPackages": [
    {
      "root": "packages/order",
      "pages": [
        {
          "path": "list",
          "style": {
            "navigationBarTitleText": "订单"
          }
        }
      ]
    }
  ]
}
```

分包页面适合低频业务、大型模块、活动页。公共组件和基础工具应放在主包可访问的位置，避免分包之间复制依赖。

分包设计要同时看包体和访问路径。如果用户几乎每次都会进入某个页面，它就不一定适合放分包；如果一个页面低频但依赖很重，分包收益会更明显。

分包和路由本来就是一起设计的。页面放在哪个包里，不只是体积问题，也会直接影响首次进入、分享冷启动和页面切换体验。

## H5 路由差异

uni-app 编译到 H5 时，路由还会受到浏览器 URL、部署 base、刷新兜底影响。

```txt
小程序端：页面栈
H5 端：浏览器 history 或 hash
App 端：原生容器 + 页面栈
```

跨端路由要同时验证小程序页面栈、H5 刷新、App 返回键。只在一个端跑通，不代表路由模型完全可靠。

H5 路由还要考虑部署 base、history fallback、刷新 404 和分享链接恢复。小程序能打开的路径，不代表 H5 刷新后服务端也能正确返回入口文件。

跨端项目里，H5 往往是最容易在“刷新”和“外部进入”时出问题的端。只在小程序里验证通过，并不能证明这套路由已经真正稳定。

## 返回刷新

从编辑页返回列表页时，列表页通常不需要重新创建，但可能需要刷新数据。

```ts
import { onShow } from "@dcloudio/uni-app";

const needRefresh = ref(false);

onShow(() => {
  if (needRefresh.value) {
    reloadList();
    needRefresh.value = false;
  }
});
```

不要在每次 `onShow` 都无条件请求。更好的方式是明确刷新信号，例如编辑成功、支付完成、授权变化。

返回刷新可以通过事件、状态标记或缓存版本号触发。关键是让“为什么刷新”有明确来源，而不是把 `onShow` 当作万能刷新入口。

页面返回后要不要刷新，应该由业务语义决定，而不是由生命周期碰运气决定。只有刷新触发条件清楚，列表、表单和详情页的行为才能长期稳定。
