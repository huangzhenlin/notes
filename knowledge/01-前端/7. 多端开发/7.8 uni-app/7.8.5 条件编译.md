## 编译标记

uni-app 条件编译用于按平台保留或移除代码。它发生在编译阶段，不是运行时 `if`。

```ts
// #ifdef MP-WEIXIN
uni.showShareMenu();
// #endif

// #ifdef H5
console.log("H5 only");
// #endif
```

目标平台之外的代码不会进入对应产物。这个特性适合处理少量平台特有逻辑，而不是做大规模业务分叉。

条件编译的核心价值是“让不同端共享一套业务结构，但允许少量差异下沉到编译期”。如果把大量业务规则都切成平台块，后面维护会非常痛苦。

条件编译最适合处理少量、明确、端差异很大的逻辑，例如分享菜单、平台样式、某端专有能力。它不是业务分叉工具，越往业务层走越容易失控。

条件编译最危险的误用，就是把它当成长期业务分治的主手段。代码短期能跑，长期会逐渐演变成“一个文件里塞了几套平台逻辑”，后续谁都不敢轻易改。

## 常见平台

条件编译可以用于 JS、模板、样式等位置。常见平台标记包括 H5、小程序、App。

| 标记 | 含义 |
| --- | --- |
| `H5` | H5 平台 |
| `APP-PLUS` | App 平台 |
| `MP-WEIXIN` | 微信小程序 |
| `MP-ALIPAY` | 支付宝小程序 |
| `MP` | 小程序泛平台 |

使用泛平台标记时要确认各小程序能力真的一致。支付、分享、订阅、地图等能力通常需要具体平台判断。

如果平台差异只是一个小分支，条件编译比运行时判断更干净；如果差异已经影响整个页面结构，最好拆文件或拆平台实现，而不是继续堆条件块。

平台标记越多，越要小心收口位置。能集中在适配层解决的问题，不要扩散到页面层；能拆成平台文件的，不要在一个组件里堆满编译块。

## API 封装

条件编译不要大量散落在页面中。更好的方式是封装平台能力。

```ts
export function shareProduct(productId: string) {
  // #ifdef MP-WEIXIN
  return shareInWeixin(productId);
  // #endif

  // #ifdef H5
  return copyShareLink(productId);
  // #endif
}
```

页面只调用 `shareProduct`，不关心当前平台差异。这样平台逻辑可以集中测试和维护。业务代码看到的是一个统一接口，平台差异被收口到了单个封装层。

编译期封装的好处是目标端不存在的代码根本不会进产物。这样可以减少无效依赖和平台冲突，但前提是封装层足够清楚，不要把太多业务规则藏进条件块。

封装层真正的价值，是让业务页面看不见平台判断。页面只表达“我要分享”“我要扫码”“我要支付”，平台差异由封装层和编译层共同吸收。

## 样式差异

样式也可以条件编译，但要控制范围。

```css
.safe-bottom {
  padding-bottom: 24rpx;
}

/* #ifdef H5 */
.safe-bottom {
  padding-bottom: env(safe-area-inset-bottom);
}
/* #endif */
```

如果样式差异越来越多，可以拆平台组件或平台样式文件。大量条件块会让样式难以阅读。

样式条件编译最好只用在少量平台特有差异，比如安全区、按钮间距、原生组件覆盖。主布局一旦处处条件编译，后续维护会很困难。

样式编译块如果开始主导布局结构，通常就说明组件抽象已经出了问题。越基础的布局越应该保持统一，越特化的细节才值得条件编译。

## 使用边界

| 场景 | 是否适合条件编译 |
| --- | --- |
| 平台 API 能力不同 | 适合 |
| 小段样式差异 | 适合 |
| 整个页面结构差异巨大 | 更适合拆文件或拆页面 |
| 业务规则不同 | 谨慎，优先服务端配置 |
| 权限和支付差异 | 适合封装后条件编译 |

条件编译是跨端差异的手术刀，不是业务分叉工具。用得太多，项目会逐渐变成多个平台代码混在一个文件里。

判断条件编译是否合理，可以先问：这段代码是不是只有编译期才能裁掉、运行时是否根本不需要、是否能通过一个更小的适配层解决。如果答案都是否定的，通常就该拆文件。

条件编译真正适合的是“差异明确、范围小、目标端不存在时应彻底移除”的逻辑。只要差异已经深入到业务流程，通常就不该继续靠条件编译硬撑。

## 可测试性

条件编译最大的问题是某些分支只在特定目标端存在。如果缺少对应构建和测试，代码可能长期处于“看起来没问题，实际从没跑过”的状态。

因此每个被声明支持的端，都应该至少有一次构建验证和关键路径验证。

条件编译还要求有明确的测试矩阵。否则某个分支可能长期没有任何人跑过，直到线上才发现语法、样式或 API 差异。编译通过不等于逻辑正确。

```text
建议流程：
1. 编译目标端
2. 检查产物是否裁掉不该出现的分支
3. 真机或模拟器回归核心流程
4. 对比平台差异是否符合预期
```

测试矩阵的价值，是让每个被声明支持的分支至少真的跑过一次。否则条件编译只是在制造“看起来有人照顾了这个端”的错觉。

## 调试技巧

条件编译最容易犯的错，是在错误的平台块里写了核心逻辑。调试时可以直接把平台分支抽成小函数，方便单独阅读和单测。越是条件编译多的地方，越要减少逻辑嵌套。

调试条件编译时，最有效的办法往往不是继续加判断，而是把平台分支抽成小函数或独立文件。这样每个端的行为更可读，排查也更直接。

条件编译越多，越要反向追问：是不是已经到了该拆分实现的时候。好的调试技巧，往往不是继续加注释，而是把端差异边界重新收紧。
