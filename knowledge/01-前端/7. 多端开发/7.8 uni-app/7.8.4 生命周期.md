## 应用周期

uni-app 应用生命周期描述整个应用从启动、进入前台、进入后台到发生全局错误的过程。它适合处理初始化配置、读取缓存、恢复登录态、启动埋点、监听网络变化等全局动作。

```ts
export default {
  onLaunch() {
    console.log("应用启动");
  },
  onShow() {
    console.log("应用进入前台");
  },
  onHide() {
    console.log("应用进入后台");
  },
};
```

`onLaunch` 不应该塞入过多阻塞逻辑。启动阶段越重，首屏越慢。可以先初始化必要配置，再把非关键任务延后，例如预取数据、上报设备信息、加载非核心资源。

应用生命周期适合做全局初始化，但不适合承载具体页面业务。登录态恢复、配置读取、埋点启动可以放在应用层；订单详情、列表刷新、表单草稿这类页面状态应留在页面或状态层，否则应用启动会变得越来越重。

应用周期最容易被滥用成“全局兜底入口”。只要所有事情都往 `onLaunch` 和 `onShow` 里堆，首屏启动、前后台恢复和问题排查都会越来越重。全局层应该只做真正全局的事。

## 页面周期

页面生命周期描述页面加载、显示、隐藏、卸载等阶段。`onLoad` 通常用于读取页面参数和首次请求；`onShow` 可能多次触发，适合从其他页面返回时刷新；`onHide` 和 `onUnload` 适合暂停任务和清理资源。

```ts
export default {
  onLoad(options) {
    this.productId = options.id;
    this.fetchProduct();
  },
  onShow() {
    this.refreshIfNeeded();
  },
  onHide() {
    this.stopPolling();
  },
  onUnload() {
    this.dispose();
  },
};
```

不要把所有逻辑都放在 `onShow`。如果每次页面显示都重新请求，用户从详情返回列表时可能丢失滚动位置，也可能产生重复请求。首次加载、返回刷新和手动刷新应该分开建模。

页面周期要区分首次加载和再次显示。`onLoad` 更适合读取参数和初始化，`onShow` 更适合根据明确标记刷新。只要把所有请求都塞进 `onShow`，页面返回体验和性能都会变得不可控。

跨端页面最容易犯的错，就是把“页面可见”直接等同于“页面应重置”。这样做短期看起来最安全，长期会让列表滚动位置、分页状态和返回体验一起变差。

## 组合式写法

Vue 3 项目中可以使用组合式 API 风格的生命周期辅助函数。这样更适合把页面逻辑拆成 Hook，例如订单详情、页面埋点、轮询任务、权限检查。

```ts
import { onLoad, onShow, onHide } from "@dcloudio/uni-app";

export function useProductPage() {
  onLoad((options) => {
    console.log("商品 ID", options.id);
  });

  onShow(() => {
    console.log("页面显示");
  });

  onHide(() => {
    console.log("页面隐藏");
  });
}
```

组合式写法的好处是逻辑聚合，但也要避免一个 Hook 隐式注册太多生命周期副作用。Hook 名称应该能说明它负责什么，例如 `usePageAnalytics`、`useOrderPolling`、`useAuthGuard`。

组合式 Hook 最好保持单一职责。一个 Hook 既做请求、又做埋点、又做权限、又做轮询，会让生命周期副作用隐藏得很深。拆成多个语义清晰的 Hook，反而更容易调试。

组合式写法的优势在于把副作用按语义聚拢，而不是把所有生命周期钩子重新换个地方堆在一起。Hook 越清楚，生命周期问题越容易定位。

## 组件周期

组件生命周期关注组件自身的创建、挂载、更新和卸载。组件中如果启动定时器、订阅事件、监听网络或创建观察器，就必须在卸载时清理。

```ts
import { onMounted, onUnmounted } from "vue";

export function useInterval(callback: () => void, delay: number) {
  let timer: ReturnType<typeof setInterval> | undefined;

  onMounted(() => {
    timer = setInterval(callback, delay);
  });

  onUnmounted(() => {
    if (timer) clearInterval(timer);
  });
}
```

跨端项目里，组件可能因为条件渲染、页面切换、分包加载而频繁创建和销毁。没有清理的计时器和订阅，会造成重复请求、内存增长和后台耗电。

组件周期尤其要关注长期资源：定时器、WebSocket、上传任务、音视频实例、地图实例、全局事件订阅都不应该跟着组件残留。组件越通用，越要保证销毁时能自己清理干净。

组件级副作用如果没有收口，页面越复杂、条件渲染越多、端差异越大，问题就越容易被放大。跨端项目里，这类泄漏通常比普通页面更隐蔽。

## 数据请求

生命周期里最常见的逻辑是请求数据。推荐把“首次加载”“显示刷新”“下拉刷新”“触底加载更多”拆开，而不是让一个函数承担所有场景。

```ts
async function loadInitial() {
  page.value = 1;
  list.value = await fetchList({ page: 1 });
}

async function loadMore() {
  const nextPage = page.value + 1;
  const next = await fetchList({ page: nextPage });
  list.value.push(...next);
  page.value = nextPage;
}
```

请求还要处理竞态。用户快速进入又退出页面时，旧请求返回后不应该更新已卸载页面；用户连续触发刷新时，旧结果不应该覆盖新结果。

请求竞态可以通过请求序号、取消任务或页面存活标记处理。关键是让“最后一次有效请求”更新页面，而不是让最慢返回的旧请求覆盖新状态。

请求设计得成熟时，生命周期和数据流会自然配合：什么时候初始化、什么时候刷新、什么时候取消、什么时候忽略过期结果，都有明确边界，而不是靠偶然时序成立。

## 前后台切换

App、小程序和 H5 对前后台切换的处理不完全一致。进入后台时适合暂停轮询、定位、音视频、动画和耗电任务；回到前台时适合检查登录态、刷新关键数据、恢复未完成任务。

```ts
export default {
  onShow() {
    refreshTokenIfNeeded();
    syncPendingActions();
  },
  onHide() {
    saveDraft();
    stopExpensiveTasks();
  },
};
```

不要把后台当成页面完全销毁。很多平台会缓存页面状态，回到前台时原页面还在。也不要假设后台任务一定能继续执行，系统可能随时限制或回收。

前后台切换要按照资源成本分级处理：高成本任务暂停，关键状态保存，必要状态恢复。比如定位、音视频和轮询可以暂停；草稿、未完成操作和登录态要保存或重新校验。

前后台切换的核心不是“全部停掉”或“全部保留”，而是根据任务性质决定：哪些任务适合暂停，哪些状态必须保留，哪些能力回前台后必须重新确认。

## 端侧差异

生命周期在 H5、小程序、App 上触发时机可能不同。Tab 切换、返回上一页、扫码进入、分享进入、App 前后台切换，都可能导致不同组合的生命周期执行。

```text
需要真机验证：
首次打开页面
从详情页返回列表
tabBar 切换
分享链接进入
App 前后台切换
弱网请求未完成时离开页面
```

涉及支付、登录、扫码、定位、上传等流程时，生命周期差异会直接影响业务正确性。这里和 [[7.8.1 uni-app架构|uni-app架构]] 的能力适配有关：页面周期、平台 API 和业务状态要一起设计。

端侧差异最好用真实路径验证：扫码进入、分享进入、从支付页返回、App 切后台再恢复、弱网请求未完成时离开页面。生命周期问题经常只在这些组合场景里出现。

生命周期差异真正危险的地方在于组合触发。单独测一个 `onShow` 往往没问题，但和分享进入、tab 切换、后台恢复叠在一起时，问题才会暴露。

## 清理策略

生命周期的收尾和初始化同样重要。定时器、订阅、文件临时路径、上传任务、WebSocket、音视频实例、地图实例都需要明确清理时机。

```ts
let uploadTask;

function startUpload(filePath: string) {
  uploadTask = uni.uploadFile({
    url: "/api/upload",
    filePath,
    name: "file",
  });
}

function cancelUpload() {
  uploadTask?.abort?.();
}
```

清理不是越早越好。页面隐藏时是否取消任务，要看任务是否还需要后台继续；页面卸载时通常要释放页面级资源；应用隐藏时要暂停高成本任务。生命周期代码要表达这些边界，而不是简单“离开就全部清掉”。

清理策略要和业务结果一致。上传、支付、同步草稿这类任务可能需要继续或保存进度；轮询、动画、定位这类高消耗任务更适合暂停。生命周期代码写清楚这些边界，线上问题会少很多。

生命周期真正写得好的项目，离开页面、切后台、再次进入这三类动作都会有稳定表现，而不是每个页面都靠各自经验补一套清理逻辑。
