## uni API

uni-app 通过 `uni` 命名空间提供跨端能力，例如请求、路由、存储、媒体、设备和权限。

```ts
uni.chooseImage({
  count: 1,
  success(result) {
    console.log(result.tempFilePaths);
  },
});
```

这些 API 会适配不同平台，但具体能力、参数和限制仍然可能不同。使用前要确认目标端支持情况。

原生能力调用的核心不是“统一调用”，而是“统一业务语义”。页面应该关心的是选择图片、发起支付、获取定位、打开分享，而不是每个平台具体怎么调系统 API。

这也是跨端能力设计最重要的抽象点。页面看到的是业务动作，平台细节留在适配层；只有这样，后续补端、改插件和做降级时，业务代码才能保持稳定。

## Promise 封装

回调式 API 可以封装成 Promise，方便组合业务流程。

```ts
function chooseOneImage() {
  return new Promise<string>((resolve, reject) => {
    uni.chooseImage({
      count: 1,
      success(result) {
        resolve(result.tempFilePaths[0]);
      },
      fail: reject,
    });
  });
}
```

封装层可以统一错误处理、权限引导和平台差异。页面不要直接处理所有底层细节。

Promise 封装还能让业务流程更线性。比如先选图，再上传，再提交表单，链路会比回调式写法清晰很多；但封装时也要保留取消、失败和权限拒绝三种稳定结果。

封装层不要只把回调改成 Promise 就结束了。真正有价值的是同时把错误语义、权限分支和平台差异也整理成稳定返回，这样业务流程才不会每次都重新处理底层细节。

## 权限处理

相机、相册、定位、蓝牙、通知等能力都涉及权限。

```ts
async function chooseAvatar() {
  try {
    const image = await chooseOneImage();
    return uploadImage(image);
  } catch (error) {
    showPermissionOrFailureMessage(error);
  }
}
```

用户拒绝授权、设备不支持、系统权限关闭、平台 API 不存在，都应该有不同降级路径。

权限处理要和用户意图一起设计。不要页面一打开就弹权限，而要在用户点击明确动作时再请求；失败后提供设置入口或替代方案，避免把用户直接卡死。

权限请求如果脱离用户动作，很容易同时伤害转化和体验。跨端项目里，这类问题更明显，因为不同端的授权弹窗和失败反馈本来就不一致。

## 降级设计

原生能力调用失败时，要给出明确降级路径。例如定位失败时允许手动选择城市，扫码失败时允许手动输入，分享不可用时提供复制链接。

多端应用不能假设每个端都能调用同一套能力，降级体验应该是能力设计的一部分。能力越接近系统底层，越要把失败当成正常分支设计。

降级路径可以是手动输入、跳转网页、服务端中转、隐藏入口或提示切换端。关键不是有没有降级，而是降级后用户还能不能继续完成核心任务。

降级设计真正成熟时，失败就不再是流程中断，而只是体验退一级。对跨端项目来说，这往往比主流程本身更能体现架构质量。

## App 原生插件

App 端可能通过原生插件扩展能力，例如推送、地图、支付、蓝牙、硬件设备。

```txt
Vue 页面 -> JS 封装 -> uni 原生插件 -> iOS/Android SDK
```

原生插件要关注版本兼容、权限声明、隐私合规和真机测试。插件更新可能影响 App 打包，不像 H5 资源那样随时发布。

App 原生插件最好和业务层解耦。Vue 层只拿稳定 API，原生侧处理平台差异和 SDK 对接，这样插件升级、权限变更和平台政策变化都更容易控制。

原生插件接入的难点，不只是今天能不能调通，而是后续如何升级、怎么回归、哪些能力受平台政策影响。只要插件边界不清，跨端项目后面会越来越重。

## 平台差异封装

平台能力差异应封装成领域函数。

```ts
export async function scanCode() {
  // #ifdef H5
  return scanByWebCamera();
  // #endif

  // #ifndef H5
  return scanByUniApi();
  // #endif
}
```

页面调用 `scanCode`，不关心当前运行端。差异集中后，后续补平台、加降级、改错误码都会更容易。

适配层应该同时处理成功、取消和失败。这样业务页面只接收统一结果，不需要知道当前是在 H5、微信小程序还是 App 端调用的能力。

平台差异封装做得好，页面层根本不需要知道当前运行在哪个端。它看到的是统一的动作结果，而不是某端临时拼出来的一段兼容代码。

## 调试验证

原生能力必须在目标端验证。

| 能力 | 验证方式 |
| --- | --- |
| 相机/相册 | 真机 |
| 定位 | 真机 + 权限场景 |
| 支付 | 沙箱/测试商户 |
| 推送 | 真机 + 厂商通道 |
| 文件系统 | App 端真实路径 |

浏览器或模拟器只能覆盖一部分行为。越接近系统能力，越不能省略真机测试。

原生能力验证最好和权限、环境、版本一起做。相机、定位、蓝牙、推送这些能力在不同系统版本和不同机型上差异很大，真机矩阵比“开发者工具里能用”更有意义。

原生能力调用最后一定要回到真实设备和真实流程里验证。能编译、能预览、能在开发工具里点通，都不等于用户在目标端里真的能稳定完成这条能力链路。
