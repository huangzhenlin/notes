## 组件体系

uni-app 组件体系包括内置组件、自定义组件和生态组件。内置组件提供跨端基础能力，自定义组件封装业务 UI，生态组件补充常见场景。组件名称统一不代表端表现完全一致，尤其是滚动、输入、视频、地图、相机等强平台能力组件。

```vue
<template>
  <view class="product-card">
    <image class="cover" :src="product.cover" mode="aspectFill" />
    <text class="title">{{ product.title }}</text>
    <button size="mini" @click="addToCart">加入购物车</button>
  </view>
</template>
```

这里的 `view`、`image`、`text`、`button` 会映射到不同目标端的组件能力。不要把它们完全当作 HTML 的 `div`、`img`、`span` 和 `button` 使用。

组件体系的核心是“通用部分复用，差异部分隔离”。一个组件越基础，越应该保持稳定和跨端；一个组件越依赖原生能力，越应该允许平台实现不同。

uni-app 组件真正的价值，不是让所有端看起来完全一样，而是让业务层尽量面对统一语义。只要对外的 props、事件和状态边界稳定，内部有适度分端实现是合理的。

## 基础组件

基础组件承担页面结构和常见交互。`view` 负责容器，`text` 负责文本，`image` 负责图片，`button` 负责按钮，`scroll-view` 负责可滚动区域。它们是跨端页面最稳定的基础。

```vue
<template>
  <scroll-view scroll-y class="list">
    <view v-for="item in list" :key="item.id" class="row">
      <text>{{ item.name }}</text>
    </view>
  </scroll-view>
</template>
```

长列表不要简单依赖一次性 `v-for` 渲染大量数据。小程序和 App 端对节点数量、滚动性能、内存都有压力，数据量大时要分页、懒加载或使用更适合的列表方案。

基础组件也要注意平台边界。`scroll-view`、`swiper`、`button`、`image` 在不同端的事件、样式和性能表现不完全一致，不能只在 H5 预览里判断组件质量。

统一组件名只是起点，不是终点。基础组件是否真能跨端复用，最终还是要看目标端里的滚动、点击、图片解码和开放能力行为是否足够稳定。

## 表单组件

表单组件包括 `input`、`textarea`、`radio`、`checkbox`、`picker`、`switch` 等。它们的事件对象更接近小程序模型，输入值通常从 `event.detail.value` 读取，而不是 Web DOM 的 `event.target.value`。

```vue
<template>
  <input :value="keyword" placeholder="搜索商品" @input="onInput" />
  <button @click="submit">提交</button>
</template>

<script setup>
import { ref } from "vue";

const keyword = ref("");

function onInput(event) {
  keyword.value = event.detail.value;
}

function submit() {
  console.log(keyword.value);
}
</script>
```

跨端表单要特别验证键盘弹出、光标位置、输入法组合、自动聚焦、固定底部按钮遮挡等问题。这些问题往往不是语法错误，而是宿主平台行为差异。

表单组件最好把输入值、校验结果和错误提示封装清楚。手机号、验证码、金额、搜索框的键盘类型和校验时机不同，不要把所有输入组件写成一个粗糙的万能输入框。

表单组件最怕追求“一个组件处理所有输入场景”。跨端输入问题本来就多，如果再把语义完全混在一起，后续调整键盘、校验和异常提示会非常痛苦。

## 媒体组件

`image`、`video`、`camera`、`map` 等组件依赖平台能力更强。它们在不同端的权限、层级、样式覆盖、事件回调和性能表现可能不同。

```vue
<image
  class="cover"
  :src="coverUrl"
  mode="aspectFill"
  @error="onImageError"
/>
```

图片要处理加载失败、占位图和尺寸比例；视频要处理自动播放限制、全屏、暂停、页面隐藏；地图和相机要处理权限、真机调试和平台审核。媒体组件不能只在浏览器模拟器里验证。

媒体组件还要考虑层级和性能。地图、视频、相机这类组件在某些端可能是原生组件，层级覆盖、遮罩、弹窗和样式控制会和普通组件不同，必须真机确认。

媒体组件一旦进入原生层级，很多 Web 经验就会失效。遮罩盖不住、弹窗压不住、滚动冲突和权限回调时机不同，都是这类组件高发的问题。

## 自定义组件

自定义组件适合封装稳定业务结构，例如商品卡片、表单项、空状态、订单状态标签、弹窗内容。组件 Props、事件和插槽要保持清晰，避免端差异泄漏到业务页面。

```vue
<template>
  <view class="field">
    <text class="label">{{ label }}</text>
    <slot />
    <text v-if="error" class="error">{{ error }}</text>
  </view>
</template>

<script setup>
defineProps({
  label: String,
  error: String,
});
</script>
```

跨端组件越通用，越要少依赖平台特有 API。需要端能力时，可以让组件调用适配层，或者拆成平台版本，而不是在一个组件里堆大量条件编译。

自定义组件的 API 要保持稳定。Props 表达输入，事件表达输出，slot 表达扩展点。只要组件内部把平台差异处理掉，业务页面就能保持干净。

组件 API 稳定，比组件内部统一更重要。业务页面如果始终面对同一套输入输出协议，后面即使内部改成分端实现，整体工程仍然是可控的。

## 样式边界

uni-app 支持常见 CSS 写法和 `rpx` 等单位，但目标端样式能力不完全一致。复杂选择器、固定定位、滚动容器、层级覆盖、阴影、滤镜、字体等都要按端验证。

```css
.safe-footer {
  padding-bottom: env(safe-area-inset-bottom);
}

.card {
  border-radius: 16rpx;
  background: #fff;
}
```

组件样式要尽量简单、局部、可预测。不要依赖过深选择器覆盖子组件内部结构，也不要假设所有平台的层叠和原生组件覆盖方式一致。

样式边界还包括单位选择和安全区。底部按钮、弹窗、输入栏、全屏页面都要考虑不同端状态栏、底部手势区和键盘遮挡，不能只按单一设计稿写死尺寸。

样式边界清楚以后，跨端组件才真正能长期维护。否则每次出现一点端差异，就只能继续往外部样式里补丁，最终越来越难收拾。

## 事件通信

组件通信优先使用 Props 和事件。父组件向子组件传数据，子组件通过事件通知父组件变化。复杂状态再交给状态管理或业务容器，不要让兄弟组件互相读取内部状态。

```vue
<template>
  <Counter :value="count" @change="count = $event" />
</template>

<script setup>
import { ref } from "vue";

const count = ref(0);
</script>
```

跨端组件的事件参数要保持稳定。不要直接把平台原始事件对象传给业务层，否则 H5、小程序、App 的差异会扩散到所有调用方。

事件通信最好转换成业务语义。例如输入组件抛 `change(value)`，上传组件抛 `success(file)`，选择器抛 `select(option)`。平台原始事件留在组件内部，业务层会更可维护。

事件设计的关键是把平台事件翻译成业务事件。业务层知道“用户选中了什么”，而不是知道 `event.detail.value` 在某个端长什么样。

## 复用判断

适合复用的组件通常结构稳定、交互通用、平台能力依赖少；不适合强行复用的组件通常深度依赖端能力，例如地图、扫码、支付、分享、复杂原生插件 UI。

```text
优先复用：
卡片、标签、表单项、空状态、列表项

谨慎复用：
地图、相机、视频、富文本、文件上传
```

复用的目标不是“一份组件跑所有端”，而是让通用部分沉淀，差异部分有边界。这个思路和 [[4.1.1 组件原则|组件原则]] 一致：复用要服务维护，而不是制造更难维护的万能组件。

判断组件是否值得复用，可以看它的结构是否稳定、交互是否通用、平台能力依赖是否少。如果一个组件为了跨端写满条件编译，它可能已经不适合做成同一份组件。

复用不是目的，稳定维护才是目的。只要一个组件已经因为跨端分支变成“条件编译迷宫”，继续强行复用往往比适当拆分更贵。
