## 配置隔离

不同端的配置要隔离管理，例如 AppId、接口域名、地图 Key、支付配置、统计 SDK 和渠道信息。配置混用会导致非常隐蔽的线上问题。

发布前最好能自动输出当前构建使用的端、环境、版本和关键配置摘要，方便排查。

多端发布的第一原则不是一次构建覆盖所有平台，而是每个目标端都有独立产物、独立验证和独立回滚。只有把配置、版本和构建结果分开，问题才容易定位。

```txt
构建产物至少要能区分：
1. 平台
2. 环境
3. 版本
4. 提交号
5. 关键配置
```

配置隔离做得越清楚，线上问题越容易追。最怕的是多个端共用一套模糊配置，最后出现“只在某个端、某个环境、某个构建里才会错”的隐蔽问题。

## 发布对象

uni-app 多端发布不是一次构建投到所有平台。不同端有不同产物、审核、配置和回滚方式。

| 平台 | 发布对象 |
| --- | --- |
| H5 | 静态资源或 SSR 服务 |
| 微信小程序 | 小程序代码包 |
| App | iOS/Android 安装包 |
| App 热更新 | wgt/资源包 |
| 其他小程序 | 对应平台代码包 |

发布前要明确当前改动影响哪些端。只改 H5 样式，不代表小程序端不会受条件编译或公共组件影响。

发布对象越多，越要先做影响面分析。一个公共组件、一个适配层、一个条件编译分支都可能同时影响多个端，所以发布前要明确哪些端是主目标，哪些端只是兼容验证。

多端发布最容易被低估的，不是构建命令数量，而是“同一份改动到底影响了哪些产物”。只有影响面清楚，测试和灰度资源才知道应该投到哪里。

## 环境配置

多端发布要区分开发、测试、预发、生产环境。

```ts
const baseURL = import.meta.env.VITE_API_BASE_URL;
```

接口域名、资源域名、AppKey、支付配置、分享回调都可能按端和环境不同。配置要集中管理，避免在页面里写死。

如果某个端的配置需要额外覆盖，最好在构建阶段完成，而不是在运行时散落判断。运行时分支越多，排错越难。

环境配置最好集中管理为端和环境两个维度。接口域名、资源域名、地图 Key、支付配置、统计 SDK、渠道信息都要清楚知道“哪个端用哪个值”，否则线上问题很难复现。

环境配置如果不能稳定追踪，就很难解释“为什么测试环境没问题，生产环境某个端出了问题”。端和环境的双维度管理，本质上是在给后续排障留证据。

## 构建检查

发布前至少完成目标端构建和核心流程验证。

```txt
H5: 构建产物、路由刷新、资源路径
小程序: 包体积、分包、权限、预览二维码
App: 真机安装、原生插件、权限、启动页
```

跨端项目常见问题不是语法错误，而是某个平台运行时能力差异、资源路径差异或配置遗漏。

构建检查要和目标端特性绑定。H5 要看刷新、路由和资源路径；小程序要看包体、分包和权限；App 要看安装、原生插件和启动页。检查项不同，发布成功的定义也不同。

构建检查不该只是“能不能打包成功”。真正要确认的是产物是否能在对应平台的真实运行边界里正常工作，包括路由、权限、资源、插件和首屏体验。

## 审核与灰度

小程序和 App 都可能涉及平台审核。H5 发布最快，但也最需要灰度和监控。

| 发布方式 | 风险控制 |
| --- | --- |
| H5 全量 | CDN 回滚、错误监控 |
| 小程序发布 | 体验版、审核、灰度 |
| App 发布 | TestFlight/内测、应用商店审核 |
| 热更新 | 版本匹配、灰度、回滚 |

支付、登录、隐私权限、用户数据采集相关改动，要特别关注平台审核规则和线上风险。对于高风险改动，先灰度再放量，比一次全量更稳。

审核与灰度可以理解成不同层次的风险控制。审核主要看平台规则，灰度主要看真实用户反馈和监控指标。改动越接近支付、隐私和登录，就越不适合直接全量。

灰度真正的价值，不是“发布慢一点”，而是给高风险改动留出观察窗口。只要改动碰到登录、支付、权限、原生插件和资源加载，先灰度往往比全量后抢修更划算。

## 版本管理

多端版本要能追踪源码、构建产物和线上版本。

```json
{
  "appVersion": "2.8.0",
  "h5Version": "2026.07.28.1",
  "miniProgramVersion": "1.12.0",
  "commit": "abc123"
}
```

线上问题定位时，需要知道用户使用的是哪个端、哪个 App 版本、哪个资源版本、哪个构建提交。没有版本链路，回滚和排查都会变慢。

版本管理最好保留源码提交号和资源版本号的对应关系。这样出现问题时，可以快速回到具体构建，而不是只知道“线上有个版本出问题了”。

版本链路越完整，回滚就越果断。知道用户正在运行哪个端、哪个资源版本、哪个提交构建出来的产物，很多线上问题定位速度会快一个量级。

## 发布后监控

发布完成后要观察错误率、白屏率、接口失败率、性能指标和关键业务漏斗。

```txt
白屏率
JS 错误率
接口错误率
首屏时间
支付/登录/下单转化
平台维度分布
```

多端发布的监控要能按平台拆分。H5 正常不代表小程序正常，Android 正常也不代表 iOS 正常。

发布后监控应持续看首屏、错误率、登录、支付、下单和页面白屏。每个平台各自看自己的核心指标，比只看总体平均值更有价值。

多端监控如果只看总体平均值，很容易把局部平台问题淹没掉。真正有价值的做法，是按平台、版本、环境和关键流程拆开看，这样异常才会尽早显出来。

## 回滚策略

发布不是最后一步，回滚能力才是最终兜底。H5 可以通过 CDN 和路由配置快速回滚，小程序和 App 则要提前准备版本切换、灰度撤回和配置回退。多端项目里，发布能力本身就是工程能力的一部分。

回滚策略也要按平台准备。H5 可以快速切回旧资源，小程序和 App 则要有版本回退、配置回退或灰度撤回方案。没有回滚，就不能算真正完成发布设计。

发布能力成熟的标志，不是“可以发出去”，而是“出问题时能在多快时间内撤回来”。多端项目里，回滚速度往往比发布速度更能决定最终风险。
