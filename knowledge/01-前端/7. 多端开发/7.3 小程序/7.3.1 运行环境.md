## 宿主容器

小程序不是运行在标准浏览器标签页里，而是运行在微信等宿主 App 提供的容器中。宿主负责账号、支付、分享、扫码、位置、文件、网络和生命周期等能力，同时也限制了页面能力边界。

| 能力 | 普通 Web | 小程序 |
|---|---|---|
| DOM 操作 | 可直接访问 DOM | 不直接操作 DOM |
| 路由 | History / Hash | 页面栈 API |
| 网络 | `fetch` / XHR | `wx.request`，域名需配置 |
| 存储 | Cookie / LocalStorage / IndexedDB | 小程序本地缓存 |
| 系统能力 | 浏览器能力有限 | 宿主提供扫码、支付、分享等 |

前端开发者进入小程序后，最需要转换的思维是：页面不是浏览器页面，API 不是 Web API，渲染也不是 DOM 渲染。很多能力需要通过宿主接口获得。

宿主容器同时带来能力和约束。能力包括统一账号体系、支付、分享、扫码、订阅消息、位置和文件；约束包括域名白名单、包体积、页面栈、审核规则、基础库版本和平台策略。小程序开发经常不是“代码能跑就行”，还要考虑能力是否被允许、是否需要用户授权、是否能通过审核。

和浏览器页面相比，小程序更像“运行在超级 App 里的应用片段”。宿主给了很多能力，但也意味着你的页面从一开始就不再拥有完整自主权，开发、调试、上线和回滚都要跟着宿主规则走。

## JavaScript 环境

小程序逻辑层运行 JavaScript，但它不是完整浏览器环境。通常不能依赖 `window`、`document`、`localStorage` 这类 Web 全局对象，也不能直接使用依赖 DOM 的库。

```javascript
// 不推荐：依赖浏览器对象
const width = window.innerWidth;

// 小程序中应使用宿主 API
wx.getSystemInfo({
  success(res) {
    console.log(res.windowWidth, res.pixelRatio);
  },
});
```

选择第三方库时，要判断它是否依赖 DOM、BOM、Canvas、Web Worker 或浏览器存储。纯计算库通常可以直接使用，UI 库和浏览器增强库往往不能直接迁移。

常见可直接复用的是日期处理、数据校验、加密摘要、状态工具和纯算法库；常见不能直接复用的是依赖 DOM 的拖拽库、浏览器路由库、富文本编辑器、图表库和文件上传封装。引入库前先看它是否访问 `window`、`document`、`location`、`navigator`，比引入后再排兼容问题更省时间。

小程序里的 JavaScript 不是“阉割版浏览器 JS”，而是另一种宿主环境。只要项目里还把“小程序页面”当成“不能访问 DOM 的 H5 页面”，很多抽象都会写偏，例如把浏览器路由、浏览器缓存、浏览器事件系统硬搬进来。

## 渲染环境

小程序渲染层使用 WXML 和 WXSS。它看起来像 HTML/CSS，但并不等同于浏览器 DOM。组件、事件、样式隔离、选择器支持和布局能力都受小程序规范约束。

```xml
<view class="card" bindtap="openDetail">
  <image class="cover" src="{{item.cover}}" mode="aspectFill" />
  <text class="title">{{item.title}}</text>
</view>
```

```css
.card {
  display: flex;
  gap: 16rpx;
  padding: 24rpx;
}

.cover {
  width: 160rpx;
  height: 160rpx;
  border-radius: 12rpx;
}
```

`rpx` 是小程序常用的响应式单位，会根据屏幕宽度换算。它适合做移动端等比适配，但并不意味着所有尺寸都要使用 `rpx`。边框、文字、最小点击区域仍要结合真实设备体验判断。

渲染层和逻辑层之间存在通信成本。频繁 `setData`、一次传递大对象、在列表里更新整棵数据，都会让页面变慢。小程序性能优化里很大一部分工作，就是减少逻辑层到渲染层的数据同步范围，这一点和浏览器里直接操作 DOM 的优化思路不同。

这也是为什么小程序里很多性能问题最终都落在“数据更新粒度”上，而不是单纯样式或循环写法。浏览器里常见的优化思路是减少 DOM 变更，小程序里还要额外控制逻辑层和视图层之间的数据桥接成本。

## API 边界

小程序 API 通常分为界面、网络、存储、媒体、位置、设备、开放能力等类别。使用 API 时要同时关注权限、平台版本、异步回调和失败路径。

```javascript
wx.getLocation({
  type: 'gcj02',
  success(location) {
    console.log(location.latitude, location.longitude);
  },
  fail(error) {
    wx.showToast({
      title: '定位失败，请手动选择城市',
      icon: 'none',
    });
  },
});
```

不要只写 `success`。用户拒绝授权、系统定位关闭、网络异常、基础库版本过低都会进入失败路径。小程序的运行环境越接近原生，就越需要把权限和降级当作正常业务分支。

API 调用还要区分“业务失败”和“能力失败”。例如支付接口返回失败，可能是用户取消、支付密码错误、网络异常、宿主版本不支持，也可能是服务端订单状态不合法。页面提示应该尽量让用户知道下一步能做什么，而不是统一显示“操作失败”。

小程序 API 的另一个特点是“平台能力和业务流程强耦合”。分享、登录、手机号、支付、订阅消息这些能力往往并不是一个独立功能点，而是整个业务转化链路中的关键步骤，所以失败分支一定要当成正常产品流程来设计。

## 基础库版本

小程序能力与基础库版本相关。新 API、新组件和新属性不是所有用户都可用，因此正式项目要检查最低基础库版本，并为关键能力做兼容判断。

```javascript
if (wx.canIUse('button.open-type.chooseAvatar')) {
  // 使用新能力
} else {
  // 降级到普通头像上传流程
}
```

基础库兼容不是“老用户少就不管”。如果一个新能力影响登录、支付、下单、授权这类核心路径，就必须有明确降级方案。

正式项目可以把基础库检查放进启动阶段或能力封装层中，不要在业务页面到处散落 `canIUse`。这样当最低支持版本调整时，只需要修改一处能力判断和降级策略，页面仍然按照“有能力”和“无能力”两种结果处理。

版本兼容的关键不是会不会写 `canIUse`，而是是否形成统一能力层。页面只关心“这个能力现在能不能用”，至于为什么不能用，是基础库低、平台不支持还是用户未升级，最好由底层封装统一处理。

## 调试差异

开发者工具、真机预览和线上版本可能存在差异。开发者工具更方便调试，但它无法完全模拟真实网络、系统权限、WebView 性能和宿主行为。

| 环境 | 作用 | 限制 |
|---|---|---|
| 开发者工具 | 快速编码、断点、查看数据 | 性能和权限不完全等同真机 |
| 真机预览 | 验证交互、扫码、定位、支付等 | 仍不是线上版本 |
| 体验版 | 接近发布环境 | 需要配置体验成员 |
| 正式版 | 用户真实环境 | 需要监控和回滚预案 |

涉及性能、权限、支付、分享、扫码、蓝牙、地图这类能力时，必须真机验证。运行环境的差异会直接影响 [[7.3.3 生命周期|生命周期]] 和页面状态恢复。

调试时要特别注意“开发者工具可用，但真机不可用”的情况。开发者工具可能放宽了部分安全限制，也可能没有真实系统权限弹窗；真机预览接近真实环境，但仍可能和线上正式版在域名配置、体验权限、灰度基础库上不同。上线前至少要走一遍体验版验收。

这也是小程序开发里很容易低估的一点：你写的并不是“本地运行的前端页面”，而是“运行在平台治理体系里的页面”。代码正确只是第一步，能力开通、权限配置、版本兼容、审核规则和真机表现同样决定最终能不能上线和稳定运行。
