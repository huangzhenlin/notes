## API 形态

微信小程序 API 是宿主平台开放能力的入口。它覆盖网络、存储、媒体、位置、设备、登录、支付、分享等能力。

这些 API 和 Web API 不同，它们由微信运行时提供，并受到平台权限、用户授权、基础库版本和审核规则约束。

```js
wx.request({
  url: "https://api.example.com/products",
  method: "GET",
  success(response) {
    console.log(response.data);
  },
  fail(error) {
    console.error(error);
  },
});
```

很多 API 是回调风格。现代项目通常会封装成 Promise，以便统一错误处理、loading 状态和登录态处理。

调用小程序 API 时要把它分成两类：一类是普通能力调用，例如请求、存储、剪贴板；另一类是强平台能力，例如登录、支付、授权、订阅消息。前者可以比较通用地封装，后者必须保留清晰业务语义和失败分支。

API 调用最大的误区，是把所有平台能力都包装成“普通工具函数”。请求和缓存可以高度通用，但登录、支付、授权、分享这类能力天生带着业务和平台约束，封装过度反而会把风险藏起来。

## 请求封装

接口请求不应该散落在页面里。可以封装基础 request，再按业务模块组织 API。

```js
function request(options) {
  return new Promise((resolve, reject) => {
    wx.request({
      ...options,
      success(response) {
        if (response.statusCode >= 200 && response.statusCode < 300) {
          resolve(response.data);
        } else {
          reject(response);
        }
      },
      fail: reject,
    });
  });
}
```

业务 API：

```js
export function getProductDetail(id) {
  return request({
    url: `${API_BASE_URL}/products/${id}`,
  });
}
```

这样页面只关心业务数据，不关心 statusCode、错误归一化、token 注入等底层细节。

请求封装通常还要处理超时、重复提交、登录过期和接口错误码。页面不应该到处写“如果 401 就重新登录”，而应该由请求层统一识别登录态失效，再让业务层决定跳转登录页、静默刷新 token 还是提示用户重新进入。

```javascript
async function requestWithAuth(options) {
  const token = wx.getStorageSync("token");
  const data = await request({
    ...options,
    header: {
      ...options.header,
      Authorization: token ? `Bearer ${token}` : undefined,
    },
  });

  if (data.code === "TOKEN_EXPIRED") {
    await relogin();
    return requestWithAuth(options);
  }

  return data;
}
```

请求封装的目标，是让普通业务请求路径变得稳定，而不是让所有异常都“自动消失”。真正关键的流程仍然要让页面或业务层知道当前发生了什么，比如用户取消登录、订单状态失效、支付前签名失败，这些都不该被悄悄吞掉。

## 权限授权

定位、相册、相机、通知等 API 涉及授权。调用前要设计清楚用户拒绝后的路径。

```js
wx.getSetting({
  success(res) {
    if (!res.authSetting["scope.userLocation"]) {
      wx.authorize({
        scope: "scope.userLocation",
        success: getLocation,
        fail: showPermissionGuide,
      });
    }
  },
});
```

权限不是简单的 API 调用失败。用户可能首次拒绝、永久拒绝、系统关闭权限，不同情况要有不同提示。权限也不是纯技术问题，还关系到产品解释和平台规范。

权限引导要解释“为什么需要”，而不是只让用户去设置页打开开关。定位用于附近门店、相机用于扫码、相册用于上传凭证，用户理解用途后更容易授权。对于非核心权限，应提供手动输入或跳过路径，避免把用户卡死。

权限请求最好和用户动作绑定，而不是在页面一进入就批量索取。用户点击“选择地址”时再请求定位，点击“扫码登录”时再请求相机，通常比一上来弹一串授权框更容易被接受。

## 网络边界

小程序网络请求通常受域名白名单、协议和平台规则限制。上线前要确认请求域名配置、HTTPS、超时、错误处理和登录态。

前端不要把小程序网络请求完全等同于浏览器 `fetch`。它的运行环境、Cookie 处理和安全约束都有平台差异。接口层应明确 token 注入、重试策略、登录过期和业务错误码。

域名白名单是小程序网络排查里的高频问题。开发环境可用不代表线上可用，体验版和正式版也可能因为配置不同产生失败。上线前要确认接口域名、上传下载域名、WebSocket 域名、HTTPS 证书和跨环境配置都已经同步。

网络边界还包括弱网和宿主限制。小程序运行在平台容器里，请求时机、并发行为、缓存命中、重试体验和浏览器环境并不完全一样，所以请求层最好从一开始就明确超时、重试和兜底策略。

## 存储 API

本地存储适合保存轻量偏好、缓存标记、草稿等，不适合保存敏感信息。

```js
wx.setStorageSync("theme", "dark");
const theme = wx.getStorageSync("theme");
```

token、手机号、身份证等敏感数据要谨慎。即使存储在本地，也要考虑设备丢失、调试环境、日志泄漏等风险。

存储还要考虑容量和过期。缓存列表数据、城市选择、用户偏好时，最好记录版本和时间戳；接口结构变化后可以主动清理旧缓存，避免旧数据污染新页面。对敏感数据，优先缩短本地保存时间，并避免写入调试日志。

本地存储最容易的问题不是“不会用”，而是“越存越多、越存越久、谁都能读”。一旦没有版本、过期和清理策略，缓存就会慢慢从优化手段变成线上隐患。

## 错误归一化

平台 API 的错误形式不完全一致，项目应统一成业务可理解的错误结构。

```js
function normalizeWxError(error) {
  if (String(error.errMsg).includes("auth deny")) {
    return { code: "PERMISSION_DENIED", message: "用户拒绝授权" };
  }

  return { code: "UNKNOWN", message: "操作失败" };
}
```

统一错误码后，页面才能稳定展示重试、授权引导、降级入口，而不是到处判断 `errMsg` 字符串。

错误归一化不要抹平全部细节。页面需要知道这是网络失败、权限失败、用户取消、业务拒绝还是系统不支持。统一结构可以包含 `code`、`message`、`retryable`、`cause`，既方便展示，也保留排查线索。

真正有用的错误归一化，不是把所有失败都变成一句“操作失败”，而是把失败整理成页面和日志都能消费的结构。页面知道怎么提示用户，日志知道该怎么定位根因，这样封装才算完整。

## 封装边界

业务项目通常会封装 API 层，统一处理 loading、错误提示、登录态失效、请求重试和数据格式转换。

封装的目标是屏蔽重复逻辑，而不是把所有平台差异藏到看不见。对权限、支付、登录这类强平台能力，仍然要保留清晰边界。页面应知道自己在请求业务数据、发起授权还是调用平台能力，这三类失败路径不应该被混成一个普通错误弹窗。

好的封装应该让常规场景更简单，让复杂场景仍然可控。比如普通请求可以自动 loading 和错误提示，但支付、登录、授权必须让调用方显式处理结果；普通业务错误可以 toast，关键流程错误则可能需要弹窗、重试、联系客服或回到安全页面。

API 层如果边界清楚，页面写起来会很顺：普通请求像普通请求，权限像权限，支付像支付，登录像登录。不同类型的能力有不同失败语义，封装层应该帮助页面看见这些差异，而不是把它们抹平。
