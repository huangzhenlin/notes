## 平台定位

微信小程序运行在微信客户端内，提供接近原生体验的轻应用能力。它不是普通 H5，也不是完整原生 App，而是微信生态里的受控运行环境。

```txt
微信客户端
  ├─ 小程序运行环境
  ├─ 小程序基础库
  ├─ 微信开放能力
  └─ 页面与组件
```

微信小程序的价值来自宿主能力和平台生态：微信登录、支付、分享、扫码、订阅消息、位置和地图、文件和媒体、小程序跳转和场景值。这些能力让小程序特别适合交易、服务、内容分发和轻量工具类场景。

小程序的优势不是“像 Web 一样轻”，而是“在微信生态里足够顺手”。如果业务天然依赖微信入口、支付和分享，小程序的转化链路通常会比单独 App 更短。

开发时要同时理解前端语法、小程序运行机制和微信平台规则。支付、登录、分享、订阅消息、隐私授权都与微信生态强相关，不是写一段前端代码就能完整解决。

微信小程序真正的壁垒不在模板语法，而在“平台生态 + 宿主能力 + 业务流程”三者的结合。只会写页面还不够，还要知道页面最终要运行在怎样的平台规则里。

## 基础库

小程序能力由微信客户端和基础库版本共同决定。新 API 可能需要较高基础库版本。

```js
if (wx.canIUse("getPrivacySetting")) {
  wx.getPrivacySetting({ success: handlePrivacy });
}
```

使用新能力前要做兼容判断。不要只在最新版开发者工具中验证，因为用户微信版本可能落后。涉及登录、支付、授权、隐私弹窗这类核心路径时，基础库兼容必须有降级方案。

基础库判断最好集中在能力封装层，而不是散落在页面代码里。页面只关心“当前是否支持某能力”和“不可用时怎么降级”，具体基础库版本和 `canIUse` 判断由能力层处理。

基础库兼容要尽量前置到设计阶段。只要某个能力对业务至关重要，就要先看当前最低可支持的微信版本，再决定要不要提供替代流程。

兼容问题越晚发现，返工越大。尤其是登录、支付、隐私弹窗、用户信息收集这类核心能力，如果上线前才发现某些版本不支持，补救空间会很小。

## 登录流程

微信登录通常通过 `wx.login` 获取临时 code，再交给服务端换取业务登录态。

```js
wx.login({
  success(res) {
    if (res.code) {
      loginByCode(res.code);
    }
  },
});
```

前端不应该直接处理 openid、unionid、session_key 等敏感凭证。code 换登录态、用户绑定、权限校验应由服务端完成。前端拿到的应该是业务 token、用户基础状态和下一步流程。

登录流程还要处理 code 过期、用户未绑定手机号、服务端会话失效、微信态和业务态不一致等情况。不要把 `wx.login` 等同于“用户已经登录业务系统”，它只是微信侧身份换取流程的一步。

登录态和业务态最好分开设计。微信态负责平台身份，业务态负责你自己的用户体系、权限和会话，这样后续换绑、解绑和多端登录才不会乱。

把微信登录理解成“平台身份入口”，而不是“业务登录终点”，后面的账号体系、绑定关系和权限控制就会清楚很多。平台身份只是入口，业务身份才决定用户在你系统里能做什么。

## 开放能力

微信小程序提供分享、支付、订阅消息、手机号授权、位置、扫码等开放能力。

| 能力 | 关注点 |
| --- | --- |
| 支付 | 服务端下单、签名、支付回调、订单状态校验 |
| 分享 | path 参数可恢复、分享来源可统计 |
| 订阅消息 | 用户主动授权、模板用途合规 |
| 手机号 | 用户主动触发、服务端解密、隐私说明 |
| 位置 | 权限说明、拒绝降级、手动选择兜底 |
| 扫码 | 场景值解析、异常码、跳转安全 |

这些能力通常不能只靠前端完成。涉及安全、签名、回调、隐私的数据处理，要放在服务端。前端负责发起能力、展示授权说明、处理用户取消和失败兜底。

开放能力最容易踩坑的是“以为页面里调用一下就行”。支付、手机号、位置、隐私授权这些能力都应该按合规流程来，用户授权、文案说明和服务端校验都不能省。

开放能力越强，越不能只从前端视角看。很多能力成功与否，取决于服务端签名、类目资质、平台配置、审核规则和用户操作路径是否完整，而不是单个 API 是否调用成功。

## 生态约束

微信小程序受平台规则约束，常见约束包括提审与发布流程、域名和安全要求、用户隐私与权限规范、包体积限制、部分能力需要资质或类目支持。

这些约束会影响技术方案。比如某些能力不是写代码就能用，还需要平台配置、审核或业务资质；某些页面可以在开发版里访问，但正式版因为域名、类目或隐私协议配置不完整而无法通过审核。

小程序开发里，平台约束不是上线后的附加检查，而是设计时就要考虑的边界。业务流程越依赖平台能力，越要先确认资质、类目、隐私和域名配置。

```txt
新增权限 -> 更新隐私说明
新增支付 -> 确认类目和商户配置
新增订阅消息 -> 确认模板用途
新增 WebView -> 确认业务域名
新增用户信息收集 -> 确认最小必要原则
```

生态约束不是上线前才处理的附加事项。设计方案时就要确认能力是否可用、是否需要资质、是否影响审核、是否需要服务端配合，否则代码写完后才发现平台不允许，会造成很大返工。

这也是为什么小程序项目经常需要产品、前端、后端和运营一起对齐。平台规则不只是技术细节，它会直接改变页面流程、授权文案、支付链路和发布节奏。

## 开发模型

微信小程序开发模型由页面和组件、App/Page/Component 生命周期、WXML、WXSS、JavaScript、JSON、小程序 API、分包和发布配置组成。

学习时不要只记 API 名称，更要理解平台为什么用页面栈、为什么限制包体积、为什么很多能力需要授权。页面栈影响返回和状态恢复，包体积影响启动，授权影响用户路径，基础库影响能力兼容，这些都属于小程序开发模型的一部分。

小程序的分包、页面栈和生命周期会直接影响代码组织。页面不要写成一个大壳子，而是应把公共能力、业务状态和页面逻辑分开。

微信小程序和 [[7.3.1 运行环境|运行环境]]、[[7.3.4 路由|路由]]、[[7.3.8 API 调用|API 调用]] 是连续的知识链：先理解宿主容器，再理解页面栈和生命周期，最后才能把开放能力稳定接入业务。

真正学会微信小程序，往往不是记住了多少 API，而是能把页面、组件、路由、生命周期、开放能力和平台规则串成一套完整运行模型。这样写出来的页面才会更接近真实线上环境，而不是只在开发者工具里成立。

## 调试发布

微信小程序开发通常经历开发者工具、真机预览、体验版、审核、发布。

```txt
本地开发 -> 真机预览 -> 体验版验证 -> 提交审核 -> 灰度/全量发布
```

真机验证很重要。开发者工具无法完全模拟权限、支付、性能、系统键盘、WebView 和部分原生组件表现。体验版接近发布环境，但正式版仍可能受到审核配置、灰度基础库和用户设备差异影响。

很多小程序问题只在真机或特定微信版本上出现，比如输入框遮挡、页面返回、支付回跳、分享参数和 WebView 打开限制。开发者工具只能做基础验证，不能替代真机回归。

发布前要特别检查登录、支付、分享、订阅消息、隐私授权、域名配置、分包加载和关键页面白屏。微信小程序的风险往往不在语法，而在平台能力、用户路径和发布配置的组合。

发布链路越接近真实用户路径，越容易提前发现问题。开发者工具通过、真机预览通过、体验版通过并不代表正式发布就一定没问题，所以关键流程最好在接近正式环境的条件下完整走一遍。

## 适用场景

微信小程序适合高频微信生态入口、支付和交易闭环、轻量服务工具、内容和活动承接、不希望用户安装独立 App 的业务。

它不太适合完全替代复杂重交互 App。对于强性能、复杂后台任务、深系统能力、长时间音视频处理、重型编辑器或强平台定制场景，仍然要评估原生、Hybrid、React Native、Flutter 或其他跨端方案。

判断是否选择微信小程序，可以看四个问题：用户是否主要在微信生态里，业务是否依赖微信开放能力，交互复杂度是否适合受控容器，发布审核和平台规则是否能接受。如果答案大多是肯定，小程序会很有优势；如果核心诉求是高度自由的系统能力和复杂交互，单靠小程序就会吃力。

如果同时需要 H5 承接、微信入口和后端统一登录态，小程序常常是一个很好的中间方案。但如果业务重在复杂编辑、长时任务或强系统权限，还是要谨慎评估是否适合只用小程序。

是否选择微信小程序，最终还是一个业务判断：如果你的用户、入口和能力都高度依赖微信生态，小程序会非常顺手；如果核心竞争力在复杂系统能力或长时重交互，单靠小程序往往不够。
