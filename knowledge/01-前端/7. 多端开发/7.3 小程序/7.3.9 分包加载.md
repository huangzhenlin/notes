## 包体约束

微信小程序分包加载的目标，是把非首屏、非核心页面拆到独立包里，减少主包体积并提升首屏启动速度。分包不是为了把目录拆得更漂亮，而是为了让用户先下载必须的部分。

```text
主包：
启动页
tabBar 页
公共基础代码
首屏必须资源

分包：
低频业务页
大型功能模块
活动页
设置页
```

主包越大，启动压力越大；分包拆得越合理，页面跳转时的等待越可控。分包的目标是启动快、跳转顺、包体稳定，而不是单纯追求主包最小。

拆分前要先识别“首屏必须”和“后续可达”。tabBar、启动页、登录兜底、公共基础组件通常需要留在主包；订单中心、活动页、会员页、管理工具、低频设置更适合分包。把首屏一定会用的代码拆进分包，反而会让用户启动后马上遭遇二次加载。

分包的重点不是“拆得越细越高级”，而是“让下载时机更符合用户路径”。用户还没走到的代码先不下，用户一定会立刻用到的代码不要拆走，这才是分包真正的价值。

## 配置结构

分包配置通常在 `app.json` 中声明。目录结构和路由配置要保持一致，否则页面无法正确进入。

```json
{
  "pages": ["pages/index/index"],
  "subpackages": [
    {
      "root": "packages/order",
      "pages": ["list/index", "detail/index"]
    }
  ]
}
```

路径组织建议和分包边界一致，例如订单、用户、活动、管理后台可以各自成为独立子包。分包一旦划分好，页面路径、资源路径和依赖关系都应该围绕它组织。

配置结构要和团队约定绑定。页面移动目录、改包名、改路由路径时，需要同步检查 `app.json`、跳转路径、分享路径、预加载配置和监控埋点。分包不是只改目录，还是一套路由和资源边界。

一旦进入分包阶段，目录结构就不再只是“代码放哪里”的问题，而会直接影响路由、资源引用、监控、灰度和调试体验。所以包边界最好尽量稳定，不要频繁来回调整。

## 依赖边界

分包可以依赖主包里的公共资源，但主包不应该直接依赖分包内部模块。否则分包就失去了“延迟加载”的意义。

```txt
主包 common -> 分包可用
分包 order -> 主包不要直接引入
```

公共工具、样式、接口封装、基础组件适合放在主包公共目录；分包里的页面、局部组件和低频逻辑则留在分包内部。边界清晰后，包体和依赖关系才容易治理。

依赖边界最怕“公共目录越来越胖”。一旦把低频业务组件、活动素材、重型 SDK 都放进公共目录，主包就会重新膨胀。判断是否放公共目录时，可以问一句：启动页或多个高频页面是否真的需要它？如果只是某个分包使用，就应该留在分包内部。

分包治理到后面，真正难的不是第一次拆包，而是持续防止依赖回流到主包。只要公共目录缺少边界意识，主包体积通常会慢慢反弹。

## 预加载

预加载可以改善分包首次进入的等待体验。用户高概率会访问的页面，适合在合适时机提前加载。

```json
{
  "preloadRule": {
    "pages/index/index": {
      "packages/order": {
        "network": "wifi",
        "packages": ["packages/order"]
      }
    }
  }
}
```

预加载不是越多越好。预加载会消耗网络和内存，如果覆盖面太大，反而会抵消分包对首屏的收益。应该只预加载高概率会访问的页面或模块。

预加载应该和用户路径绑定。例如首页点击“我的订单”的概率很高，可以在首页稳定后预加载订单分包；活动入口只有少量用户点击，就不适合全量预加载。弱网或低端机上，预加载过多还可能影响当前页面体验。

预加载本质上是在“等待未来可能要用”与“保护当前正在用”的资源之间做平衡。预测越准，收益越大；预测越差，浪费越多。

## 触发时机

预加载的时机通常来自首页后、列表页后、导航入口点击前、弱网空闲时。什么时候预加载，取决于用户路径是否可预测。

```text
适合预加载：
首页后详情页
登录后业务页
活动页入口

不适合预加载：
低概率页面
体积很大的重模块
网络不稳定时的非关键资源
```

如果一个分包几乎总是用户一进来就要访问，那它可能不应该继续留在分包里，而应该重新评估包边界。

触发时机还要避开首屏关键路径。首页刚进入时已经在下载资源、请求数据和渲染首屏，如果此时立刻预加载多个分包，可能让首屏变慢。更合适的时机通常是首屏稳定后、用户停留后、即将点击入口前或网络条件较好时。

很多分包预加载效果不佳，不是功能本身没用，而是时机选错了。把它放到首屏最忙的时候，它就会和当前页面争资源；把它放到用户即将进入下一个模块之前，它才真正像一次“提前准备”。

## 体积控制

分包能不能发挥效果，取决于你有没有真的把大资源和低频依赖拆出去。

```text
检查项：
主包是否包含大图和大组件
公共库是否被重复打入多个包
页面是否引用了不必要的重依赖
分包是否过度碎片化
```

分包越多，并不一定越好。过多分包会增加路由和资源管理复杂度，首屏虽然变小了，但跳转链路可能变重。最好的分包策略是把“低频且重”的模块独立出去。

体积治理要看真实产物，而不是只看源码目录。公共依赖可能被多个包重复打入，图片和字体可能占据主要体积，某个组件库可能因为按需引入失败进入主包。每次新增重依赖，都应该确认它落在哪个包里。

分包后的体积治理要持续做，而不是拆完就结束。每次引入新组件库、图表库、地图 SDK、富文本能力或大图资源时，都要重新检查它对主包和目标分包的影响。

## 路由体验

分包页面进入时会产生加载等待，因此路由体验要做好过渡。可以通过骨架屏、loading、提前预热和更合理的页面拆分减少体感卡顿。

```tsx
Page({
  onLoad() {
    this.setData({ loading: true });
    this.loadData().finally(() => this.setData({ loading: false }));
  },
});
```

如果分包进入时等待明显，先看包体、静态资源和首屏依赖，而不是先盲目加 loading。loading 只能缓解感知，不能替代体积治理。

分包页面也要有首屏策略。进入分包后，不要再串行加载大量接口和图片；可以先展示页面骨架和核心信息，再逐步加载扩展模块。分包只解决“代码什么时候下载”，不自动解决“页面什么时候可用”。

用户感知里只有“这个页面开得快不快”，不会区分你是在下载代码、等接口还是解码图片。所以分包页面也需要像普通首屏一样设计展示顺序，而不是以为拆了包就自然会快。

## 适用边界

分包适合低频、大模块、体积敏感、路径明确的场景，不适合把所有页面都切得很碎。

```text
适合分包：
订单中心
活动专区
设置页
帮助中心

慎重分包：
首屏必达页
tab 页
高度共享的基础页面
```

分包加载和 [[7.3.4 路由|路由]]、[[7.3.2 页面结构|页面结构]] 是配套的。路由怎么走、页面怎么组织、资源怎么拆，三者需要一起设计。

如果某个页面既是分享入口又在低频分包里，要额外验证冷启动路径。用户从分享直接进入分包页面时，小程序需要先加载主包再加载目标分包，页面必须有明确 loading、参数校验和失败兜底，不能只按“从首页点进来”的路径设计。

分包设计成熟时，团队通常能回答这几个问题：哪些页面必须首屏可达，哪些页面可以延迟下载，哪些依赖必须留主包，哪些模块值得预加载，哪些入口需要额外冷启动兜底。回答清楚这些问题，分包才算真正服务了体验，而不是只服务了目录结构。
