## 绑定模型

小程序的数据绑定连接的是逻辑层和视图层。页面或组件的 `data` 提供视图状态，WXML 用 Mustache 语法读取这些状态，用户交互再通过事件回到逻辑层更新数据。它不是直接操作 DOM，而是通过框架同步数据让视图重新渲染。

```js
Page({
  data: {
    count: 1,
    user: {
      name: "Ada",
    },
  },
});
```

```xml
<view>{{user.name}}</view>
<text>数量：{{count}}</text>
```

这种模型的好处是 UI 和状态关系清楚，坏处是开发者必须理解同步成本。`data` 不是普通内存对象的展示副本，它会参与跨层通信，只应该放视图真正需要的数据。

可以把 `data` 理解成“视图状态协议”：逻辑层把需要展示的数据通过协议发给视图层，视图层按模板渲染。临时变量、请求控制器、缓存 Map、未展示的原始响应都不应该默认塞进 `data`，否则每次更新都会增加跨层同步成本。

理解这件事之后，很多写法会自然变得克制。不是所有数据都值得进入视图层，只有真正参与展示、交互反馈和条件判断的字段，才值得为它付出同步成本。

## setData 同步

更新视图必须使用 `setData`。直接修改 `this.data` 只会改变逻辑层对象，不会把变化同步到视图层。

```js
Page({
  data: {
    count: 1,
  },

  increase() {
    this.setData({
      count: this.data.count + 1,
    });
  },
});
```

`setData` 的本质是把变更从逻辑层发送到视图层。传输数据越大、频率越高，性能压力越明显。滚动、拖拽、输入这类高频交互里尤其要克制。

`setData` 也不是越少调用越好。如果为了减少调用次数，把互不相关的大量字段合并成一次巨大更新，同样会造成卡顿。更合理的目标是“少传无关数据、少做高频同步、让一次更新只包含本次视图真正变化的字段”。

`setData` 可以理解成一次跨层消息发送。字段越多、结构越深、频率越高，这条消息就越重。小程序里很多性能问题最终都不是算法复杂，而是这条消息发得太大、太频繁。

## 路径更新

只更新变更字段，而不是整个大对象，是小程序性能优化里最基础的一步。列表或对象某个字段变化时，可以用路径语法精确更新。

```js
this.setData({
  "user.name": "Grace",
  "items[2].checked": true,
});
```

如果每次勾选列表项都把整个 `items` 数组重新传给视图层，数据量会随着列表增长快速变大。路径更新能减少同步体积，但路径要可读，过度拼接动态路径也会让代码难维护。

路径更新特别适合列表项状态变化，例如勾选、点赞、展开、局部 loading。复杂路径可以集中封装成小函数，避免页面里到处手写字符串路径。这样既能减少同步体积，也能降低路径写错导致视图不更新的风险。

路径更新的核心价值，不是“语法更炫”，而是让你只同步真正变化的局部。列表越长、对象越深，这个差异带来的性能收益就越明显。

## 模板表达式

WXML 表达式适合简单读取、三元判断和轻量格式化，不适合承载复杂业务逻辑。复杂逻辑应该在 JS 中提前计算成视图模型。

```xml
<text>{{isVip ? "会员" : "普通用户"}}</text>
```

```js
this.setData({
  displayUser: {
    name: user.name,
    levelText: user.isVip ? "会员" : "普通用户",
    avatar: user.avatar || "/assets/default-avatar.png",
  },
});
```

把复杂格式化放在逻辑层，能让模板更清楚，也能减少重复计算。模板越像声明结构，后续维护越轻松。

视图模型还可以把多个后端字段合并成页面语义。例如接口返回 `price`、`stock`、`status`，页面可以提前生成 `priceText`、`disabled`、`statusText`。模板只关心展示结果，业务规则集中在 JS 中更容易测试和复用。

模板越纯，页面越稳。模板里如果堆满判断和拼接，后面无论是改接口、改文案还是加埋点，都会变成一边改结构一边改规则，维护成本很快就会上升。

## 条件渲染

`wx:if` 会根据条件创建或销毁节点，`hidden` 更接近切换显示状态。两者都能让内容不可见，但成本和状态表现不同。

```xml
<view wx:if="{{hasPermission}}">
  管理面板
</view>

<view hidden="{{!expanded}}">
  详情内容
</view>
```

频繁切换且内部结构复杂的区域，可以考虑 `hidden`；条件很少变化、且不需要保留内部状态的区域，用 `wx:if` 更合适。选择时要看节点创建成本、状态保留和初始渲染成本。

弹窗、折叠面板、Tab 内容区都要根据状态保留来选择。`wx:if` 会销毁并重建节点，适合权限分支、空状态和一次性内容；`hidden` 会保留节点，适合频繁切换且内部状态需要保留的区域，但保留太多隐藏节点也会增加页面负担。

这里没有绝对答案，关键是先想清楚“我想保留什么”。如果希望保留输入内容、滚动位置、内部组件状态，通常不能轻易销毁；如果希望切换时彻底重置状态，销毁反而更干净。

## 列表渲染

列表渲染要设置稳定 `wx:key`。稳定 key 能帮助框架识别列表项，减少不必要的重建，也能避免输入框、选中状态在列表变化时错位。

```xml
<view wx:for="{{items}}" wx:key="id">
  <text>{{item.name}}</text>
</view>
```

不要用数组下标作为长期 key，除非列表永远不会插入、删除或排序。真实业务列表经常会分页、刷新、筛选、插入置顶项，稳定业务 ID 更可靠。

列表渲染还要控制单项复杂度。一个列表项里嵌太多图片、按钮、倒计时和自定义组件，会让节点数和通信成本一起上升。长列表要优先做分页、图片懒加载、字段裁剪，再考虑更复杂的虚拟列表方案。

列表卡顿经常不是因为“循环本身很慢”，而是因为每一项都太重、每次更新范围太大、图片和子组件太多。先把每一项做轻，再考虑更激进的优化手段，通常收益更稳定。

## 视图模型

`data` 里不一定要放完整业务对象。更好的做法是把接口数据转换成视图模型，只保留页面展示和交互需要的字段。

```js
function toProductView(product) {
  return {
    id: product.id,
    title: product.name,
    priceText: `￥${(product.price / 100).toFixed(2)}`,
    soldOut: product.stock <= 0,
  };
}

this.setData({
  products: list.map(toProductView),
});
```

这样能减少 `setData` 体积，也能把价格格式化、库存状态、默认图等逻辑集中起来。接口模型变化时，页面模板不需要到处调整。

视图模型不等于复制一份接口数据。它应该只保留当前页面需要渲染和交互的字段。接口返回的权限、埋点、调试字段、冗余嵌套对象如果不用于视图，就不应该进入页面 `data`。

视图模型做得好，后面的数据绑定、事件处理和组件属性都会更轻。页面不会反复在模板里“现场解释后端数据”，而是提前把后端数据整理成适合当前页面消费的形态。

## 性能边界

小程序数据绑定的主要性能边界是数据量、更新频率和节点数量。常见问题是把大对象放进 `data`、在滚动中频繁 `setData`、列表项过多、每次更新整个页面状态。

```text
优化顺序：
减少 data 字段
缩小 setData 粒度
降低高频更新次数
拆分组件和列表
使用分页或虚拟列表方案
```

如果页面既有大量列表，又有高频输入或滚动联动，应该先做真实设备测试。小程序的逻辑层和视图层通信模型，决定了它和浏览器直接更新 DOM 的性能特征不同，这也是 [[7.3.6 事件系统|事件系统]] 里高频事件需要谨慎处理的原因。

性能排查可以从 `setData` 入手：看一次更新的数据大小，看更新频率，看是否每次都更新大数组，看是否在滚动或触摸中同步视图。很多卡顿不需要复杂优化，只要把不展示的数据移出 `data`，把整块更新改成路径更新，就能明显改善。

数据绑定写得成熟时，页面状态会更像一个经过整理的“展示层状态树”，而不是把所有业务数据原样塞进来。这样不仅性能更稳，页面结构、组件边界和调试体验也都会更清晰。
