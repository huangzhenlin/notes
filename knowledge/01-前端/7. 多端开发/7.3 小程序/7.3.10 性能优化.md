## 优化方向

小程序性能优化主要关注启动、渲染、通信和包体积。它和移动 Web 有相似之处，但因为小程序有逻辑层和视图层分离、包体积限制、宿主 API 等特点，优化重点并不完全一样。

常见性能目标包括更快启动、更少白屏、更顺滑滚动、更低 `setData` 成本和更合理的分包加载。

小程序性能优化要先分清问题发生在哪里：启动慢看主包和初始化，首屏慢看接口与渲染，滚动卡看节点和图片，交互慢看 `setData` 和主线程任务，跳转慢看分包和目标页首屏。不同问题对应的优化手段完全不同。

性能优化最重要的不是“把所有指标都压低”，而是先找出用户最能感知的慢点。小程序里很多问题不是单点慢，而是启动、通信和渲染叠在一起慢。

小程序性能优化最怕一上来就堆技巧。先分层定位问题发生在启动、数据同步、节点渲染、图片资源还是分包加载，再对症处理，通常比到处加缓存、节流和预加载更有效。

## 启动性能

启动阶段要控制主包体积和初始化工作量。

```text
下载主包 -> 初始化运行时 -> 加载页面 -> 请求数据 -> 首屏渲染
```

常见做法包括减少主包无关页面和资源、非首屏逻辑延后执行、使用分包承接低频页面、首页数据请求并行化、避免启动时同步做重计算。启动慢不一定是框架问题，常常是主包过大、初始化过重或首屏接口串行造成的。

启动阶段不要把所有全局初始化都塞进 `onLaunch`。埋点、配置、登录态恢复、AB 实验、地理位置、用户资料如果全部串行完成后才进入首页，用户会看到更长白屏。更好的方式是区分“首屏必须”和“可延后”：必须项先完成，可延后项在首页可见后再补。

启动优化时，最好把首屏必须的数据和非首屏数据拆开。首屏先渲染壳子和关键内容，次要能力等页面稳定后再补，能明显减少白屏感。

启动阶段更适合做“必要初始化”，而不是“完整初始化”。只要首页已经可用，很多非关键逻辑都可以延后；反过来，如果用户还没看到首屏就已经做了一堆全局准备，再精细的局部优化也很难掩盖体感上的慢。

## setData 成本

`setData` 是小程序性能优化里的重点。它会触发逻辑层到视图层的数据同步，如果频繁或数据量过大，会造成明显卡顿。

```js
this.setData({
  "list[0].checked": true,
});
```

优化原则是只传视图需要的数据、避免整块列表重复更新、在高频事件里减少 `setData`、不要把大对象直接放进页面 `data`。滚动、拖拽、输入时频繁更新，体验很容易变差。

排查 `setData` 成本时，可以关注一次更新的数据量、调用频率和更新范围。输入框每个字符更新整个表单对象、滚动时更新整个列表、倒计时每秒更新所有列表项，都是常见性能陷阱。局部路径更新和组件内局部状态通常更稳。

`setData` 还要避免在高频事件里重复触发。比如滚动、拖拽、输入联动时，最好做节流、合并或者局部更新，否则逻辑层和视图层之间会频繁同步。

很多页面交互不顺，不是因为渲染层本身太慢，而是逻辑层不断往视图层推送大更新。只要把高频路径里的大更新缩成局部更新，很多卡顿会立刻缓和。

## 列表渲染

长列表要分页加载，避免一次性渲染过多节点。

```js
Page({
  data: {
    list: [],
    page: 1,
  },
  async loadNextPage() {
    const nextList = await productApi.list({ page: this.data.page });

    this.setData({
      list: this.data.list.concat(nextList),
      page: this.data.page + 1,
    });
  },
});
```

列表项字段也要精简，只传渲染需要的数据。接口返回的大对象可以在 service 层裁剪。对于复杂列表，是否需要虚拟列表、是否需要分包列表页，也要一起判断。

列表页还要控制图片尺寸、组件数量和分页策略。每个列表项如果都有倒计时、复杂自定义组件、多个图片和状态计算，分页也可能卡。可以先把列表项变成轻量视图模型，再把非首屏按钮、标签、营销信息延迟展示。

如果列表真的很长，可以进一步考虑分段加载和骨架占位，而不是一次性塞大量节点。小程序里节点数和渲染复杂度都很容易放大卡顿。

列表优化通常要按优先级来做：先减少单项复杂度，再减少单次渲染数量，再控制图片与组件开销，最后才考虑更复杂的虚拟化或特殊渲染手段。越靠前的优化，收益越稳定，也越不容易引入副作用。

## 图片与资源

图片是小程序性能问题的高发点。

| 问题 | 优化 |
| --- | --- |
| 图片过大 | CDN 裁剪、压缩 |
| 首屏图片多 | 懒加载、占位图 |
| 列表滚动卡 | 固定尺寸、减少同时展示 |
| 格式不合适 | WebP 等更合适格式 |

图片组件要设置明确宽高，避免加载完成后页面跳动。列表图应使用缩略图，不要直接加载原图。

图片优化不能只靠压缩。业务上要区分封面图、头像、详情大图、富文本图和本地静态图：封面图使用 CDN 裁剪，头像可缓存，详情大图可懒加载，富文本图要限制最大宽度，本地静态图要避免放进主包造成启动压力。

图片优化也要兼顾分辨率和尺寸。如果列表里只展示缩略图，就不要把原图直接下发给列表组件；详情页再加载高清图，通常更合理。

图片往往既影响流量，也影响解码和渲染。页面看起来像“滚动卡”，实际根因可能是图片体积过大、尺寸不稳定或列表里同时出现过多图片节点，所以资源优化和渲染优化要一起看。

## 分包与预加载

分包能降低主包体积，预下载能减少进入分包时的等待。

```json
{
  "preloadRule": {
    "pages/index/index": {
      "network": "wifi",
      "packages": ["packages/order"]
    }
  }
}
```

预加载要结合用户路径。高概率进入的分包值得预下载，低频分包不应过早占用流量。

如果分包页面首屏仍然慢，要继续看目标页面自己的首屏：是否入口包下载完后又串行请求多个接口，是否首屏加载了大图，是否初始化了重型组件。分包只能降低启动包体积，不能替代页面级渲染优化。

分包策略应该围绕用户路径设计。高频入口尽量留在主包，低频重页面放分包；如果用户一打开就要走到某个页面，再把那个分包做预下载更划算。

分包优化如果没有结合真实路径，很容易出现“主包变小了，但用户进入目标页还是慢”。只有把下载时机、页面首屏和用户路径放在一起看，分包收益才会真正落到体验上。

## 体验监控

优化要结合开发者工具、真机和线上监控。

```txt
启动耗时
首屏时间
setData 体积
页面节点数
接口耗时
JS 错误和白屏
```

开发者工具表现不等于真机表现。低端 Android、弱网、老基础库版本都要纳入验证范围。性能优化真正要看的不是“代码改了多少”，而是用户是否真的少等了、少卡了。

监控指标最好能按设备、基础库版本、网络类型、页面路径和版本号拆分。平均值经常掩盖问题：高端机很快、低端机很慢时，平均值看起来可能还行；Wi-Fi 正常、弱网白屏时，也需要按网络分组才能看出来。

小程序性能验证最好真机、低端机、不同微信版本都跑一遍。开发者工具里的结果只能算初筛，不能代表真实上线表现。

监控的价值，不只是证明“我们优化过了”，而是持续发现哪一类设备、哪一种网络、哪一个页面仍然慢。能持续定位慢点，比一次性做一轮优化更重要。
