## 事件链路

小程序事件系统负责把视图层交互传递到逻辑层。用户点击、输入、滚动、触摸时，视图层产生事件，框架把事件对象传给页面或组件方法，逻辑层再决定是否更新数据、调用 API 或触发业务流程。

```xml
<button bindtap="handleSubmit">提交</button>
```

```js
Page({
  handleSubmit(event) {
    console.log("submit", event.type);
  },
});
```

事件处理函数应该表达业务意图，而不是直接堆一串 UI 操作。复杂流程可以拆成“读取参数、校验状态、执行动作、更新视图”几个步骤。

事件链路里最容易混乱的是“视图事件”和“业务动作”混在一起。点击按钮只是触发条件，真正的业务动作可能是校验、请求、导航、埋点和状态更新。把事件处理拆成小函数，能让页面逻辑更接近业务流程。

事件处理函数越短越好，但不是为了形式上的短，而是为了让“输入是什么、判断了什么、最终做了什么”一眼可见。这样后面排查重复提交、误触、漏埋点时也更容易定位。

## bind 与 catch

`bind` 绑定的事件会继续冒泡，`catch` 绑定的事件会阻止冒泡。弹层、列表项、嵌套按钮是最容易混淆的场景。

```xml
<view class="mask" bindtap="closeDialog">
  <view class="dialog" catchtap="noop">
    <button bindtap="confirm">确认</button>
  </view>
</view>
```

点击遮罩需要关闭弹窗，点击弹窗内部不能关闭弹窗，因此内部容器用 `catchtap` 阻止事件继续冒泡。不要为了省事到处用 `catch`，否则父级无法感知必要交互。

`catch` 适合阻断明确不应该向外传播的交互，例如弹窗内容区域、嵌套按钮、滑动操作区域。列表项内部如果有收藏按钮，按钮可以阻止冒泡，避免同时触发打开详情；但列表项整体点击仍应该用普通 `bindtap`，让父级保持可感知。

事件冒泡是否中断，背后其实是在定义交互边界。页面和组件都应该清楚：哪些点击属于当前节点自己消费，哪些点击应该继续交给外层去理解。

## target 与 currentTarget

`target` 表示事件源组件，`currentTarget` 表示当前绑定事件的组件。嵌套结构中，如果要读取绑定节点上的 `data-*`，通常应该使用 `currentTarget.dataset`。

```xml
<view data-id="{{item.id}}" bindtap="openDetail">
  <text>{{item.name}}</text>
</view>
```

```js
Page({
  openDetail(event) {
    const id = event.currentTarget.dataset.id;
    wx.navigateTo({ url: `/pages/detail/index?id=${id}` });
  },
});
```

如果使用 `event.target.dataset.id`，点击内部 `text` 时可能拿不到外层 `view` 的数据。这个问题在复杂卡片和列表项中非常常见。

可以把 `target` 理解成“用户真正点到的节点”，把 `currentTarget` 理解成“当前处理函数绑定的节点”。读取 `data-*` 参数时，大多数业务场景应该使用 `currentTarget`，因为参数通常挂在绑定事件的业务节点上。

这个差异在列表、卡片、嵌套按钮场景里尤其关键。用户可能点到图片、标题、角标，但业务真正要处理的是整个卡片或按钮节点本身。

## dataset 传参

`data-*` 适合传递字符串、数字、布尔值等简单信息。复杂对象不建议放进 dataset，因为可读性差、序列化不可控，也会让模板变重。

```xml
<button data-id="{{product.id}}" bindtap="handleBuy">
  购买
</button>
```

```js
handleBuy(event) {
  const { id } = event.currentTarget.dataset;
  const product = this.data.products.find((item) => item.id === id);
  this.buy(product);
}
```

业务上要传复杂对象时，更推荐传 ID，再从状态或缓存里查完整数据。事件参数越简单，页面越容易维护。

dataset 传参还要注意命名会被转换，`data-product-id` 在事件里通常通过 `dataset.productId` 读取。不要在 dataset 里放过多字段，否则模板会被数据细节污染，事件处理也会变成“从 DOM 上凑业务对象”。

dataset 最适合传业务定位信息，例如 `id`、`index`、`type`、`status`。只要开始往里面塞整块业务对象，模板就会越来越重，后面调试事件来源也会变麻烦。

## detail 数据

表单和自定义组件事件常通过 `detail` 携带值。输入框、选择器、开关等组件的值通常不在 `target.value`，而在 `event.detail.value`。

```xml
<input value="{{keyword}}" bindinput="handleInput" />
```

```js
handleInput(event) {
  this.setData({
    keyword: event.detail.value,
  });
}
```

封装自定义组件时，也应该通过 `triggerEvent` 抛出稳定的 `detail`，让父组件不需要知道子组件内部结构。

```js
this.triggerEvent("change", {
  value: nextValue,
});
```

组件事件的 `detail` 应该保持稳定结构。比如表单组件统一抛出 `{ value, valid }`，选择器统一抛出 `{ value, option }`，父级就不需要关心子组件内部用了按钮、输入框还是滑块实现。

`detail` 更像组件对外的事件协议。结构一旦稳定，父级页面就可以把组件当成一个黑盒能力来使用，而不用随着组件内部重构一起改事件读取逻辑。

## 触摸事件

触摸事件包含 `touches` 和 `changedTouches`，适合处理滑动、拖拽、手势等交互。它们的频率很高，不适合每次触发都执行重计算或大量 `setData`。

```js
touchMove(event) {
  const touch = event.touches[0];
  this.currentX = touch.clientX;
}
```

拖拽过程中可以把临时位置保存在实例字段中，必要时节流更新视图。只有最终状态需要持久展示时，再写入 `data`。这和 [[7.3.7 数据绑定|数据绑定]] 的性能边界是一体的。

触摸事件里最忌讳频繁 `setData` 大对象。拖拽跟手可以先把坐标保存在实例字段，配合节流或动画能力更新局部样式；只有用户松手后的最终位置、排序结果、选择结果才需要写入 `data`。

高频触摸的关键，是把“跟手反馈”和“最终提交”拆成两段。前者追求顺滑和低成本，后者才负责把结果写入页面状态或发给服务端。

## 事件命名

页面事件可以按动作命名，例如 `handleSubmit`、`openDetail`、`closeDialog`；组件事件更适合按语义命名，例如 `change`、`confirm`、`cancel`、`select`。

```xml
<price-stepper value="{{count}}" bind:change="handleCountChange" />
```

事件名不要暴露内部实现，例如 `bindtapplusbutton` 这类命名会让父组件依赖子组件结构。父组件关心的是数量变化，不是用户点了哪个内部按钮。

事件命名还要避免过度具体。`change` 适合值变化，`select` 适合选择某项，`submit` 适合提交动作，`close` 适合关闭状态。名称越贴近语义，组件内部实现越容易调整。

如果父级一看到事件名就知道“这代表什么业务动作”，说明命名就是成功的；如果父级还得去翻子组件代码确认“用户到底点了哪里”，说明事件命名还停留在实现层。

## 高频边界

滚动、触摸、输入都是高频事件。高频事件里要避免同步大数据、频繁请求、复杂计算和反复创建对象。需要实时反馈时，可以节流、延迟、局部更新或使用组件自身能力。

```js
function throttle(fn, delay) {
  let timer = null;
  return function (...args) {
    if (timer) return;
    timer = setTimeout(() => {
      timer = null;
      fn.apply(this, args);
    }, delay);
  };
}
```

事件系统的关键不是“能不能绑定”，而是事件发生后是否能用最小成本完成必要状态变化。小程序页面越复杂，越要把高频事件和重型状态更新隔离开。

高频事件如果必须触发请求或复杂计算，应该增加明确的节流、防抖或提交时机。输入框搜索可以在停止输入后请求，滚动加载可以在接近底部时触发一次，拖拽排序可以在松手后提交结果。事件越高频，越要把“实时反馈”和“业务提交”拆开。

事件系统写得成熟时，页面不会因为“能监听到一切”而变复杂，反而会因为“只在必要时做必要的事”而变得更清晰。视图事件负责把用户动作送上来，业务层再决定哪些动作需要立即反馈、哪些动作应该延迟提交、哪些动作只做本地状态更新。
