## 组件定位

小程序组件用于封装可复用 UI 和局部逻辑，例如商品卡片、弹窗、表单项、标签、列表项。

```txt
components/
  product-card/
    product-card.wxml
    product-card.wxss
    product-card.js
    product-card.json
```

页面负责业务装配，组件负责局部展示和交互。不要让组件直接依赖具体页面路径和页面数据结构。

组件抽取的判断标准不是“这段 WXML 出现了两次”，而是它是否有稳定边界。商品卡片、筛选项、空状态、弹窗、表单控件都有相对固定的输入、输出和内部交互，适合组件化；一次性业务流程、页面级权限判断、路由跳转则更适合留在页面层。

组件化的目标不是把页面拆碎，而是把稳定的局部能力沉淀下来。能长期复用、边界清晰、输入输出明确的内容越多，页面层就越能专注于业务流程本身。

## 组件注册

页面或组件需要在 JSON 中注册自定义组件。

```json
{
  "usingComponents": {
    "product-card": "/components/product-card/product-card"
  }
}
```

注册后可在 WXML 中使用。

```xml
<product-card product="{{item}}" bind:select="handleSelect" />
```

组件注册路径建议统一使用绝对路径或项目约定的别名，避免页面层级变化导致相对路径混乱。公共组件如果被多个分包使用，还要考虑它放在主包还是分包：主包组件复用方便，但会增加主包体积；分包组件更轻，但跨包复用受限制。

组件目录规划本身也是工程边界的一部分。真正跨业务复用的基础组件、业务中台组件、页面私有组件，最好从目录和命名上就区分开，否则后面很容易出现“看起来是公共组件，实际只给某一页定制”的情况。

## properties

组件通过 `properties` 接收外部数据。

```js
Component({
  properties: {
    product: {
      type: Object,
      value: null,
    },
  },
});
```

properties 类似 props，应视为外部输入。组件内部不要直接修改外部传入对象，应该通过事件通知页面更新。

组件属性最好保持“窄输入”。不要把整个页面对象传给组件，只传组件展示和交互真正需要的数据。属性越宽，组件越容易依赖外部数据结构，后续改接口或复用到其他页面时成本越高。

属性设计越克制，组件越稳定。把整个对象直接传进去虽然一开始更省事，但很容易让组件偷偷依赖一堆它其实不该知道的字段，最后外部一改接口，组件就跟着一起碎。

## data

组件内部状态放在 `data` 中。

```js
Component({
  data: {
    expanded: false,
  },
  methods: {
    toggle() {
      this.setData({
        expanded: !this.data.expanded,
      });
    },
  },
});
```

只影响组件内部显示的状态可以留在组件中。跨页面或跨组件共享状态不应塞进某个组件内部。

组件内部状态适合保存展开收起、当前选中、输入草稿、动画状态这类局部信息。订单状态、用户信息、购物车数量这类业务真相不应该藏在某个组件里，否则其他页面或组件很难知道它已经变化。

一个简单判断是：如果这个状态在组件销毁后应该消失，通常适合放组件内部；如果它在页面切换、列表刷新、其他组件联动时仍然应该保持一致，就不该只放在组件 `data` 里。

## methods

组件事件处理和对外方法写在 `methods` 中。

```js
Component({
  methods: {
    handleTap() {
      this.triggerEvent("select", {
        id: this.properties.product.id,
      });
    },
  },
});
```

组件通过 `triggerEvent` 通知父级发生了什么。父级决定跳转、请求或更新状态。

组件事件应该描述语义而不是描述内部实现。`select`、`change`、`confirm`、`cancel` 比 `tapTitle`、`clickRightButton` 更稳定，因为父级关心的是业务结果，而不是用户点了组件内部哪个节点。

组件方法也应该尽量围绕能力来命名，而不是围绕内部节点来命名。这样即使组件内部结构调整，外部协作方式也能保持稳定。

## observers

`observers` 可以监听 properties 或 data 变化。

```js
Component({
  observers: {
    "product.id"(id) {
      this.loadExtraInfo(id);
    },
  },
});
```

监听器适合少量同步逻辑，但不要把复杂业务流程都放进 observers。很多派生值可以在模板或方法中计算。

`observers` 适合做属性变化后的轻量同步，例如根据 `value` 更新内部选中态。它不适合发起复杂请求、修改多个外部状态或触发导航，因为这些副作用会让组件变得难预测。需要请求时，可以由页面传入完整数据，或把加载动作明确封装成组件方法。

很多组件难维护，不是因为生命周期太多，而是因为 `observers` 被当成了万能副作用入口。只要属性一变就自动发请求、自动改状态、自动通知父级，久而久之组件行为就很难推断。

## 生命周期

组件有自己的生命周期，例如 created、attached、detached。

```js
Component({
  lifetimes: {
    attached() {
      this.start();
    },
    detached() {
      this.stop();
    },
  },
});
```

定时器、订阅、长连接要在 detached 中清理。组件被页面卸载时，内部资源也应释放。

如果组件会在列表中反复出现，生命周期清理尤其重要。列表滚动、条件渲染、分页追加都会导致组件实例创建和销毁；如果每个实例都留下定时器或事件订阅，很快就会变成性能和内存问题。

组件生命周期要和组件职责一起设计。展示型组件通常很轻，关注属性变化即可；交互型组件、媒体组件、弹层组件、副作用组件则必须明确什么时候启动、什么时候暂停、什么时候彻底释放。

## 样式隔离

小程序组件默认有样式隔离策略，可以减少组件样式互相污染。

```js
Component({
  options: {
    styleIsolation: "isolated",
  },
});
```

组件库开发要特别关注样式隔离。公共组件不应依赖页面全局样式才能正常显示。

样式隔离也会影响主题定制。业务组件可以适当暴露 class、slot 或 CSS 变量风格的定制入口，但不要要求使用者写复杂选择器穿透内部结构。组件内部结构一旦调整，外部穿透样式就会失效。

样式可定制和样式可穿透不是一回事。健康的组件应该主动暴露少量稳定的定制点，而不是逼着页面使用者去猜内部类名和层级。

## 设计边界

| 内容 | 放在组件 | 放在页面 |
| --- | --- | --- |
| 卡片展示 | 适合 | 不优先 |
| 点击后发出 select | 适合 | 处理结果 |
| 页面跳转 | 不优先 | 适合 |
| 接口装配 | 不优先 | 适合 |
| 纯 UI 状态 | 适合 | 视情况 |
| 跨页面业务状态 | 不适合 | Store/全局 |

组件越通用，越应该通过 properties 和 events 与外部交互，而不是直接知道业务流程。

判断一个组件是否健康，可以看它是否能被单独阅读：输入是什么，内部状态是什么，输出事件是什么，是否有资源清理，是否依赖页面路径。如果这些问题都清楚，组件就更容易复用、测试和迁移。

组件设计真正成熟时，页面和组件之间的关系会很清楚：页面告诉组件“你现在展示什么、当前状态是什么”，组件告诉页面“用户做了什么、局部状态发生了什么”，双方都不替对方做决定。
