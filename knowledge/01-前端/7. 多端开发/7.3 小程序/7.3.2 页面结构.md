## 页面组成

小程序页面结构通常由页面文件、页面配置、模板、样式和逻辑组成。它不像浏览器页面那样直接围绕 DOM 展开，而是围绕小程序运行时的页面模型组织。

```text
pages/
  index/
    index.wxml
    index.js
    index.json
    index.wxss
```

页面和组件的分工要清楚：页面负责路由入口、数据获取和页面级状态；组件负责局部 UI 和交互；配置负责标题、窗口、下拉刷新和页面能力。

页面目录最好围绕业务入口组织，而不是围绕技术层组织。一个页面文件夹里放齐 WXML、WXSS、JS、JSON，可以让路由、结构、样式和配置一起演进。跨页面复用的 UI 再放到 `components`，跨页面复用的请求和数据处理再放到 `services` 或 `utils`。

页面结构写得好，后续很多问题都会简单一些。因为小程序页面天然就是路由入口、生命周期入口和配置入口，结构如果一开始就混乱，后面请求、组件、样式和权限配置都会被迫缠在一起。

## 模板层

WXML 是模板层，负责把逻辑层的数据渲染成视图结构。模板适合表达结构和简单绑定，不适合堆复杂业务逻辑。

```xml
<view class="page">
  <view wx:if="{{loading}}">加载中...</view>
  <view wx:elif="{{error}}">加载失败</view>
  <view wx:else>
    <view wx:for="{{items}}" wx:key="id">
      {{item.title}}
    </view>
  </view>
</view>
```

模板最好尽量声明式，让页面结构一眼可读。复杂格式化、状态派生和业务分支，提前放到 JS 中处理会更稳。

WXML 里可以写条件和循环，但不适合承载复杂表达式。列表项是否禁用、价格如何格式化、按钮文案如何组合，通常应该在逻辑层转换成模板可直接消费的数据。这样模板更接近“状态展示”，而不是把业务规则散落在结构里。

模板层越干净，页面越容易排查。真实项目里，如果一眼看过去全是嵌套判断、三元表达式和多层循环，后面改动某个展示条件时就很容易改出副作用。模板更适合表达“有哪些状态”，不适合推导“为什么是这个状态”。

## 配置层

页面 JSON 配置负责窗口标题、下拉刷新、导航样式等页面级行为。

```json
{
  "navigationBarTitleText": "商品详情",
  "enablePullDownRefresh": true,
  "backgroundTextStyle": "dark"
}
```

配置层是页面结构里很容易被忽略的部分，但它直接决定页面的宿主行为。对于 tab 页、登录页、表单页、详情页，不同配置会影响用户体验。

例如列表页启用下拉刷新后，要在请求结束时调用停止刷新；沉浸式导航栏需要额外处理状态栏高度；页面标题如果依赖接口数据，则要在数据返回后更新。配置层不是静态背景，它会和页面生命周期、布局适配和用户操作产生联动。

很多小程序页面体验问题其实不是样式问题，而是配置和结构没有一起设计。例如页面需要分享却没补分享入口，需要下拉刷新却没处理结束状态，需要自定义导航栏却没处理安全区，这些都属于页面结构的一部分。

## 样式层

WXSS 负责页面样式，尽量保持页面结构清晰、选择器简单、层级稳定。小程序样式隔离和组件样式覆盖规则跟 Web 不完全一样，所以不要把复杂覆盖逻辑写进页面样式里。

```css
.page {
  padding: 24rpx;
}

.title {
  font-size: 32rpx;
  line-height: 1.5;
}
```

如果样式和逻辑强耦合，页面会越来越难维护。更好的方式是把可复用样式提取成组件或公共样式资源。

小程序样式要避免过深选择器和过度依赖父级结构。组件内部样式越依赖页面容器，组件越难复用；页面样式越频繁穿透组件，组件边界越容易失效。对于可复用卡片、按钮、弹窗和表单项，优先让组件通过属性控制状态，而不是由页面外部强行覆盖样式。

样式层的稳定性直接影响后续组件复用。页面为了赶进度直接覆盖组件内部类名，看起来暂时省事，但后面组件一升级、结构一调整、平台样式一变化，就很容易出现大面积连锁回归。

## 逻辑层

JS 逻辑层负责页面初始化、事件处理、请求数据和状态更新。它通常拥有页面生命周期和少量页面级业务状态。

```js
Page({
  data: {
    loading: false,
    items: [],
  },

  async onLoad() {
    this.setData({ loading: true });
    const items = await fetchItems();
    this.setData({ loading: false, items });
  },
});
```

逻辑层应该尽量只保留页面需要的最小状态。大对象、临时计算和非展示数据尽量别放进 `data`，以免同步成本过高。

`data` 的定位是“需要渲染层感知的数据”。请求中的临时变量、节流状态、定时器 id、缓存 Map、未展示的原始响应都不适合放进 `data`。这些数据可以挂在页面实例上，减少无意义的渲染层同步。

小程序页面逻辑层最容易膨胀的地方，就是把所有状态都丢进 `data`。一开始看起来方便，后面就会出现 `setData` 范围过大、列表更新抖动、调试时难以判断哪些字段真正参与渲染的问题。

## 页面职责

页面应该承担“组织数据和流程”的职责，而不是把所有 UI、请求、校验和事件都写成一个巨型脚本。

```text
页面职责：
读取路由参数
发起首次请求
协调组件交互
维护页面级状态
处理页面生命周期
```

需要共享的 UI 结构和复杂交互，应该下沉到组件。需要跨页面共享的数据，应该交给状态层或缓存层。

页面代码增长到难维护时，通常不是因为行数多，而是职责混在一起：请求、格式化、权限判断、弹窗状态、组件事件、埋点和导航都写在同一层。更稳的拆分方式是把请求封装到 service，把展示片段拆成组件，把纯计算抽成函数，把页面保留为流程编排层。

页面最适合做的，是把“用户来到这个入口后会经历什么流程”组织清楚，而不是承接所有实现细节。只要页面开始变成一个什么都管的总控脚本，后面任何一个局部改动都会影响整页行为。

## 与组件的边界

页面结构和组件结构要分清。页面级标题、请求、分页、分享、下拉刷新等逻辑通常在页面里；可复用卡片、筛选条、空状态、表单项则应该抽成组件。

```text
适合页面：
路由入口
数据拉取
页面级生命周期

适合组件：
卡片
列表项
筛选条
空状态
表单项
```

页面结构理解清楚后，路由、生命周期、数据绑定和事件系统就会连起来。它也是小程序与 Web 最大的心智差异之一。

组件边界也影响性能。列表页里如果每个列表项都是复杂组件，渲染层通信和组件实例数量会增加；但如果全部写在页面里，又会让结构不可维护。真实项目中要在复用性、可读性和渲染成本之间取平衡，核心是让组件承担稳定、内聚、可复用的交互单元。

页面结构的成熟度，往往就体现在这里：页面是否真的只做页面级编排，组件是否真的只封装局部交互。边界清楚以后，后面的 [[7.3.5 组件|组件]]、[[7.3.7 数据绑定|数据绑定]] 和性能优化才更容易统一起来。
