## 页面栈

小程序路由的核心不是 URL，而是页面栈。用户打开页面、跳转详情、返回列表、切换 tab，都在影响页面栈结构。

```text
页面栈示例：
Home -> List -> Detail
```

理解页面栈后，很多“为什么不能这样返回”的问题就清楚了。小程序不是浏览器历史记录模型，它有自己的页面实例生命周期和栈深限制。

页面栈决定了页面实例是否保留，也决定了返回后是否会重新触发生命周期。列表页进入详情页后，列表页通常还在栈里；登录页 `redirectTo` 到首页后，登录页会被替换；`reLaunch` 会清空原有栈。路由问题如果只看 URL，很容易忽略页面实例和状态保留。

小程序路由最容易和 Web 混淆的地方就在这里。浏览器页面更强调地址和历史记录，小程序页面更强调“当前栈里有哪些页面实例、这些实例是否还活着、返回后会恢复到什么状态”。只要先把页面栈想清楚，很多返回链路和刷新时机就不再靠猜。

## 跳转方式

常见跳转 API 包括 `navigateTo`、`redirectTo`、`switchTab`、`reLaunch`、`navigateBack`。不同 API 的页面栈行为不同。

```xml
<!-- WXML 里不会写跳转逻辑，跳转由 JS 发起 -->
```

```js
wx.navigateTo({ url: "/pages/detail/index?id=1" });
wx.redirectTo({ url: "/pages/login/index" });
wx.switchTab({ url: "/pages/home/index" });
```

`navigateTo` 保留当前页，适合列表到详情；`redirectTo` 替换当前页，适合登录成功后进入新页；`switchTab` 用于 tabBar 页面；`navigateBack` 用于回退；`reLaunch` 用于重置流程。

真实业务里可以按流程选择跳转方式：普通详情使用 `navigateTo`，登录成功后不希望返回登录页则使用 `redirectTo` 或 `reLaunch`，切换主导航必须使用 `switchTab`，支付成功页如果需要阻断返回链路，通常要重置或替换当前流程。跳转 API 选错，往往不是立刻报错，而是用户返回路径变得奇怪。

可以把这些 API 理解成几种不同语义：

| API | 更像什么语义 | 常见场景 |
| --- | --- | --- |
| `navigateTo` | 进入下一层 | 列表到详情、详情到编辑 |
| `redirectTo` | 当前页替换 | 登录成功、流程页切步 |
| `switchTab` | 切主入口 | 首页、订单、我的 |
| `navigateBack` | 回到上一步 | 详情返回列表 |
| `reLaunch` | 重开流程 | 登录失效、支付完成回首页 |

如果路由 API 只是被当成“能跳过去就行”的工具，后面通常会出现页面返回路径不稳定、重复页面入栈、状态恢复错位这些问题。

## Tab 页面

tabBar 页面是路由里最容易踩坑的部分。tab 页面不能随便用普通跳转打开，也不应该承载深层详情流程。

```ts
wx.switchTab({
  url: "/pages/home/index",
});
```

如果需要从非 tab 页面返回 tab 页，最好通过 `switchTab` 或统一的路由封装处理，而不是依赖历史栈碰运气。

tab 页面通常是应用的主入口，不适合承载深层参数状态。比如商品详情不应该做成 tab 页，订单列表可以是 tab 页但订单详情应该是普通页面。否则从分享、通知或扫码进入时，页面栈和 tab 状态会混在一起，返回体验很难统一。

tab 页面更像应用骨架，而不是业务流程节点。把骨架和流程拆开，后面的分享进入、登录跳转、支付完成回落和返回兜底都会更稳定。

## 参数传递

路由参数适合传递简单、可序列化、可恢复的信息。复杂对象、临时 UI 状态和大数据不适合直接放在 query 里。

```ts
wx.navigateTo({
  url: `/pages/detail/index?id=${productId}`,
});
```

页面接收参数后要做校验，不能默认参数一定存在。分享进入、扫码进入、冷启动进入都可能让参数缺失。

参数还要注意编码。标题、回调地址、搜索词这类值如果直接拼 URL，可能因为特殊字符导致解析错误。更稳的做法是只在路由里传 ID 或短参数，复杂数据放到缓存、事件通道或服务端上下文里恢复。

```javascript
const query = encodeURIComponent(JSON.stringify({ keyword: "手机 壳" }));
wx.navigateTo({
  url: `/pages/search/index?query=${query}`,
});
```

路由参数应该尽量承担“定位页面”的职责，而不是承担“搬运整段业务数据”的职责。页面真正需要的大对象，通常更适合由页面自己根据参数再去获取，或者通过状态层恢复。

## 返回兜底

返回行为要有兜底。用户从外部分享直接进入详情页时，可能没有上一页，这时不能假设 `navigateBack` 一定有效。

```ts
function safeBack() {
  const pages = getCurrentPages();
  if (pages.length > 1) {
    wx.navigateBack();
  } else {
    wx.reLaunch({ url: "/pages/home/index" });
  }
}
```

有未保存内容的页面，还要在返回前提示用户确认。返回逻辑越接近业务关键路径，越不能写成纯跳转封装。

外部入口尤其需要兜底。用户可能从分享卡片、二维码、订阅消息、搜索结果直接进入深层页面，此时页面栈里没有你以为的列表页。详情页的返回按钮应该根据页面栈决定返回上一页还是回到首页，而不是无条件 `navigateBack`。

返回按钮如果没有兜底，用户最直接的感受就是“点返回没反应”或者“返回到了一个莫名其妙的页面”。这类问题往往不是单个页面 bug，而是整套路由语义没有统一。

## 页面恢复

页面重新进入时，不能总是假设会重新创建。缓存、返回栈和页面实例保留都会影响 `onLoad`、`onShow`、`onHide` 的触发方式。

```ts
Page({
  onShow() {
    this.refreshIfNeeded();
  },
});
```

很多“返回后数据显示不对”的问题，本质是页面状态没在返回时正确刷新。路由与生命周期要一起看，不能只看页面地址。

页面恢复还要考虑数据来源。如果列表页只是需要局部更新，可以通过事件通道标记某一项变更；如果数据可能被其他端修改，则应该在 `onShow` 做轻量刷新；如果页面数据很重，就要结合缓存时间和用户操作判断是否重新请求。

这里真正要判断的不是“要不要刷新”，而是“哪些状态必须恢复真相，哪些状态应该保留用户上下文”。筛选条件、滚动位置、输入草稿通常应该保留，订单状态、库存状态、登录状态则更需要在适当时机重新校准。

## 协议设计

如果小程序和宿主 App 或 H5 共用一套路由模型，最好统一导航语义。比如“返回首页”“打开详情”“关闭当前页”“打开 tab 页”应当有清晰命名，而不是只传一个裸 URL。

```text
推荐语义：
openDetail
openTabHome
closeCurrent
relaunchHome
```

语义化路由封装能减少页面间互相猜测。它和 [[7.4.8 路由同步|路由同步]] 的思路一致：路由不是单纯字符串，而是一套页面行为协议。

路由封装不只是把 `wx.navigateTo` 包一层。它应该统一路径常量、参数编码、登录拦截、返回兜底、错误提示和埋点。这样页面只表达“打开商品详情”这样的业务意图，具体走 `navigateTo`、`redirectTo` 还是 `switchTab` 由路由层根据目标页面和当前栈决定。

路由协议越清晰，页面之间的耦合就越低。页面不需要知道对方是不是 tab 页、需不需要替换当前页、是否要求登录，只需要发出明确的导航意图，剩下的交给统一路由层判断。
