## 状态边界

Flutter 状态管理解决的是界面如何响应数据变化。状态可能来自用户输入、接口请求、页面参数、全局登录态或本地缓存。

状态管理的目标不是“选一个最强工具”，而是让数据变化和 UI 更新保持清晰关系。状态影响范围越小，方案就应该越轻；状态影响范围越大，才需要更明确的共享和约束。

状态管理最重要的先验，不是工具，而是归属。先分清哪些状态只影响局部，哪些状态会被多个组件共享，哪些状态需要持久化或跨页面恢复，再决定用什么方案。工具只是把归属关系表达得更清楚。

Flutter 状态管理最容易被带偏的地方，就是一开始先讨论库，再讨论状态。真正稳定的顺序应该反过来：先认清状态是什么、影响谁、生命周期多长，再决定需不需要 Provider、Riverpod 或 Bloc。

## 局部状态

Flutter 中最小的状态管理方式是 `StatefulWidget + setState`。它适合组件内部的临时状态。

```dart
class CounterButton extends StatefulWidget {
  const CounterButton({super.key});

  @override
  State<CounterButton> createState() => _CounterButtonState();
}

class _CounterButtonState extends State<CounterButton> {
  int count = 0;

  @override
  Widget build(BuildContext context) {
    return ElevatedButton(
      onPressed: () {
        setState(() {
          count += 1;
        });
      },
      child: Text("点击 $count 次"),
    );
  }
}
```

如果状态只影响当前组件或很小的子树，`setState` 是足够清晰的。不要因为项目用了状态管理库，就把所有局部状态都全局化。

局部状态适合输入框、展开收起、收藏按钮、临时开关、短动画这类只影响当前组件的场景。把这些状态全局化通常只会增加样板代码和重建范围，得不偿失。

`setState` 被误用的常见情况，不是“它太简单”，而是“本来应该局部的状态被写成了页面全局变量”。只要状态仍然只影响一个很小的可见区域，局部管理通常就是最清晰的方案。

## 状态提升

当兄弟 Widget 需要共享状态时，可以把状态提升到共同父级。

```dart
class SearchPage extends StatefulWidget {
  const SearchPage({super.key});

  @override
  State<SearchPage> createState() => _SearchPageState();
}

class _SearchPageState extends State<SearchPage> {
  String keyword = "";

  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        SearchInput(
          value: keyword,
          onChanged: (value) => setState(() => keyword = value),
        ),
        SearchResult(keyword: keyword),
      ],
    );
  }
}
```

状态提升解决的是近距离共享。跨页面、跨模块或需要持久化的状态，再考虑更完整的 Store 方案。状态提升的代价是父组件会承担更多渲染责任，所以它适合“共享很近、逻辑很轻”的场景。

状态提升本身不是坏事，关键是别提升过头。只要父级已经开始同时承担布局、请求、筛选、弹层、列表和多个子组件交互，继续把更多状态往上抬，页面就会越来越重。

## 共享状态

当状态需要跨组件、跨页面共享时，就需要更明确的状态管理方案。常见方向包括父组件传递、InheritedWidget 机制、Provider、Riverpod、Bloc 等。

不同方案关注点不同：有的轻量，有的强调单向数据流，有的强调事件和状态分离。选择前先看状态是否跨页面、是否需要持久化、是否需要测试、团队是否能维护对应复杂度。

选状态方案时还要看是否需要和 API 请求、缓存、路由、表单、离线恢复一起工作。很多状态问题并不是“状态库不够强”，而是没有把服务端数据、客户端临时状态和 UI 状态拆开。

共享状态设计得成熟时，页面不需要知道所有数据都从哪里来，只需要依赖一个稳定的读取和更新入口。状态库的价值，不是替代业务判断，而是把依赖关系组织清楚。

## InheritedWidget

`InheritedWidget` 是 Flutter 依赖传递的底层机制，Theme、MediaQuery、Provider 等都与它有关。

```dart
final theme = Theme.of(context);
final size = MediaQuery.sizeOf(context);
```

你不一定需要手写 `InheritedWidget`，但要理解它的意义：下层 Widget 可以通过 `BuildContext` 找到上层提供的数据，并在依赖变化时重建。`InheritedWidget` 的价值是把“向下传递数据”变成框架机制。

理解 `InheritedWidget` 很重要，因为很多上层方案本质上都建立在这套依赖传递机制之上。你即使不直接手写它，也会不断通过 Theme、MediaQuery、Provider 这些能力间接使用它。

## Provider

Provider 是 Flutter 生态中常见的状态管理方案，适合把状态对象提供给子树。

```dart
ChangeNotifierProvider(
  create: (_) => CartModel(),
  child: const CartPage(),
);
```

```dart
class CartModel extends ChangeNotifier {
  final List<CartItem> items = [];

  int get totalCount => items.length;

  void addItem(CartItem item) {
    items.add(item);
    notifyListeners();
  }
}
```

组件中读取：

```dart
final totalCount = context.watch<CartModel>().totalCount;
```

`watch` 会订阅变化，`read` 只读取不订阅。误用 `watch` 会扩大重建范围。性能敏感区域可以拆小监听范围，或者只监听派生字段。Provider 的常见误区不是不会写，而是监听范围太大。

Provider 最容易出现的问题，不是 API 学不会，而是“图方便把整个页面都包在一个大监听里”。只要监听范围收不住，局部改动就会不断触发大范围重建。

## Riverpod 与 Bloc

复杂应用中也常见 Riverpod、Bloc 等方案。

| 方案 | 特点 | 适合场景 |
| --- | --- | --- |
| setState | 简单直接 | 局部状态 |
| Provider | 概念适中 | 中小型共享状态 |
| Riverpod | 类型和测试友好 | 模块化、可测试状态 |
| Bloc | 事件与状态分离 | 流程复杂、团队约束强 |

Riverpod 更强调声明式依赖和可测试性，Bloc 更强调事件输入和状态输出的约束。两者都能处理复杂业务，但复杂度也更高。

复杂方案并不天然更好。它们适合有明确边界的中大型项目：多模块协作、异步流程多、状态来源复杂、测试要求高。如果只是几个页面的局部交互，用这些方案反而会让样板代码上升。

选复杂方案前，最好先确认团队是不是真的会长期用到它的约束能力。否则很容易出现“库很重，但大家只用到最浅一层能力”，最后复杂度先上去了，收益却没有跟上。

## 三类状态

实际工程里，很多状态最好直接拆成三类：UI 临时状态、业务持久状态、服务端数据状态。先拆这三类，再讨论是否需要 Provider、Riverpod 或 Bloc，通常会少走很多弯路。

| 状态类型 | 例子 | 适合位置 |
| --- | --- | --- |
| UI 临时状态 | 输入、展开、选中 | 局部组件 |
| 业务持久状态 | 登录态、购物车 | 页面上层或全局 Store |
| 服务端数据状态 | 列表、详情、配置 | 数据层 / 缓存层 |

把状态先拆成这三类，很多争论会自然消失。局部 UI 状态不必硬塞进全局库，服务端数据也不该和按钮展开状态混在一起，登录态和购物车这类业务状态则应该有更稳定的持有位置。

## 常见问题

状态管理常见问题包括状态放得太高导致不必要重建、局部状态误放全局、异步请求回来时页面已销毁、多处同时修改同一状态来源不清。

状态边界清晰，比工具选择更重要。工具只能帮助组织状态，不能替你决定状态归属。

状态管理做得好的项目，代码里会自然呈现出一种秩序：局部状态留在局部，共享状态有稳定入口，服务端数据有明确缓存策略，页面不会因为一个小交互把整棵树带着抖动。
