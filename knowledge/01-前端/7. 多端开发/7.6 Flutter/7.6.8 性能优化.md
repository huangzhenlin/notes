## 帧预算

Flutter 性能优化首先要理解帧预算。60Hz 设备每帧约 16ms，120Hz 设备每帧约 8ms。Flutter 一帧通常涉及 UI 线程构建和 Raster 线程栅格化，任一部分超预算都可能造成卡顿。

```text
UI 线程：执行 Dart、构建 Widget、布局、生成 Layer Tree
Raster 线程：把 Layer Tree 栅格化并交给 GPU 显示
```

优化不要只凭肉眼感受，要在 profile 模式和真机上看帧图。debug 模式下的性能不能代表 release 表现，很多断言、调试信息和热重载机制都会影响结果。

帧预算还要结合设备刷新率看。60Hz 设备还有约 16ms，120Hz 设备只剩约 8ms，高刷设备对动画和滚动更敏感。优化时要选目标用户真实设备，而不是只看开发机。

性能优化一开始就要确定目标设备，不然“在我手机上挺流畅”的结论几乎没有意义。Flutter 页面在高端机和低端机上的容错空间差很多，优化优先级也会跟着变。

## 重建范围

Flutter 的 Widget 重建本身很快，但不必要的大范围重建仍会累积成本。状态应该尽量靠近真正依赖它的子树，静态部分可以拆成独立 Widget 或使用 `const`。

```dart
class CounterText extends StatelessWidget {
  const CounterText({super.key, required this.count});

  final int count;

  @override
  Widget build(BuildContext context) {
    return Text("当前计数：$count");
  }
}
```

不要在顶层 `setState` 后让整页所有区域都重建。列表、动画、输入、计时器这类高频变化，要把状态边界缩小到局部。

静态 Widget 尽量使用 `const`，能让 Flutter 更容易跳过不必要的重建。复杂页面可以先拆出稳定区域，再把频繁变化的部分放到更小的子树里。重建不是洪水猛兽，但无关重建一定会累积成本。

重建范围控制得好，很多后续优化都能少做。只要局部状态一直拖着整页重建，图片、列表、动画和布局都会一起被连累，页面体感很难真正稳定下来。

## build 纯度

`build` 方法应该描述 UI，不应该执行重计算、网络请求、文件读取、复杂排序或创建大量临时对象。`build` 可能被频繁调用，里面的重逻辑会直接进入帧预算。

```dart
@override
Widget build(BuildContext context) {
  final visibleItems = items.where((item) => item.visible).toList();
  return ListView.builder(
    itemCount: visibleItems.length,
    itemBuilder: (context, index) => ItemTile(item: visibleItems[index]),
  );
}
```

上面这种写法在小列表里问题不大，但大列表或高频重建时会浪费。更好的做法是把过滤结果放到状态更新阶段、Selector、ViewModel 或缓存层中。

build 纯度也影响可预测性。只要 build 里有请求、日志副作用、随机数或时间依赖，界面就可能因为一次普通重建表现不同。纯 build 更容易测试，也更容易被框架优化。

build 方法越接近纯函数，页面就越容易推断。性能优化很多时候并不是“让 build 更快”，而是先让 build 不再承担它本来不该承担的事情。

## 列表性能

长列表要使用惰性构建，例如 `ListView.builder`、`GridView.builder` 或 `SliverList`。一次性创建所有子项会增加构建、布局和内存压力。

```dart
ListView.builder(
  itemCount: products.length,
  itemBuilder: (context, index) {
    return ProductListItem(product: products[index]);
  },
);
```

列表项要控制图片尺寸、避免复杂阴影和裁剪，滚动过程中不要频繁触发全局状态更新。列表中如果每个 item 都订阅同一个大状态，状态变化可能导致整屏甚至整列表重建。

列表性能要关注 item 本身是否稳定。`ListView.builder` 只是惰性构建，不会自动解决 item 过重、图片过大、状态订阅过宽的问题。长列表优先保证 item 轻、key 稳、图片合适、状态局部。

列表优化真正有效时，通常不是只改一个参数，而是把 item 结构、图片策略、状态范围和惰性加载一起整理。只调 builder 参数而不减轻 item，本质上还是在让重内容慢慢滚动。

## 图片资源

图片过大、解码过重、缓存策略不合理都会造成卡顿和内存压力。移动端显示 100x100 的缩略图时，不应该下载和解码 3000x3000 的原图。

```dart
Image.network(
  imageUrl,
  width: 120,
  height: 120,
  fit: BoxFit.cover,
  cacheWidth: 240,
);
```

`cacheWidth`、缩略图服务、占位图、预缓存都能改善体验。图片列表要特别关注内存峰值，低端设备比开发机更容易暴露问题。

图片优化最好从源头做，不要在客户端下载大图后再缩小显示。服务端裁剪、CDN 参数、合理缓存宽度和占位图配合起来，才能同时降低网络、解码和内存压力。

图片是 Flutter 页面里最容易同时拖慢启动、滚动和内存的资源。只要页面以图为主，图片治理就不应该被当成局部修修补补，而应该被当成整体性能策略的一部分。

## 绘制成本

有些视觉效果会增加 GPU 或 Raster 线程压力，例如大量阴影、模糊、裁剪、透明叠加、`saveLayer`、复杂 Path。它们不是不能用，而是要限制范围和频率。

```dart
RepaintBoundary(
  child: ComplexChart(data: data),
);
```

`RepaintBoundary` 可以把复杂绘制区域隔离出来，避免父级变化导致它重复重绘。但不是越多越好，过多边界会增加图层管理成本。只有复杂、相对独立、重绘频率不同的区域才值得加。

绘制成本最怕“看起来只是一个小效果”。模糊、阴影、半透明叠加和裁剪在低端设备上可能很贵。视觉效果越复杂，越要在真实设备上看 Raster 线程，而不是只看设计稿还原度。

很多视觉优化和性能优化并不是对立的，但前提是你知道哪个效果代价最高。只要不知道成本在哪，就很容易为了一个局部质感牺牲整个页面流畅度。

## 动画流畅

动画卡顿通常来自每帧做了太多构建、布局或绘制。动画期间要避免请求、解析、复杂计算和大范围状态更新。能交给 Flutter 动画系统的，不要用定时器手动刷新。

```dart
AnimatedOpacity(
  opacity: visible ? 1 : 0,
  duration: const Duration(milliseconds: 200),
  child: const Text("提示内容"),
);
```

复杂动画要拆分静态和动态部分，减少每帧变化范围。首帧动画卡顿还可能和 shader 编译有关，需要结合目标平台和 Flutter 渲染器策略验证。

动画性能的核心是每帧只做必要变化。能用内置隐式动画解决的，不要用定时器手动刷新；能只改变 transform/opacity 这类轻量属性的，就不要每帧重新布局大块内容。

动画卡顿通常不是“动画 API 不行”，而是动画期间同时发生了太多别的事情。只要滚动、请求、重建和复杂绘制叠在一起，任何动画系统都会吃力。

## DevTools 定位

Flutter DevTools 的 Performance View 可以查看 Flutter frames chart、UI/Raster 耗时、jank 帧、Timeline 事件、Widget build、layout、paint 等信息。优化时先定位瓶颈属于 UI 线程还是 Raster 线程。

```text
UI 线程高：Dart 代码、build、layout、状态更新
Raster 线程高：绘制、图层、图片、阴影、裁剪、GPU 压力
内存高：图片、缓存、对象保留、列表未释放
```

不要一上来就改代码。先在 profile 模式复现，再用 DevTools 选中慢帧，看它慢在哪里。能测量的问题才值得优化，不能测量的优化很容易变成玄学。

DevTools 定位时要留意两个方向：慢帧发生在用户操作期间，还是页面加载期间。前者优先看重建、布局和绘制，后者还要看初始化、资源加载、接口等待和首屏图片。

真正高效的定位，不是把所有指标都看一遍，而是先明确“慢发生在什么阶段”。交互慢和首屏慢很少是同一类问题，用同一套优化手段处理通常不会高效。

## 发布验证

Flutter 性能要在目标设备、目标构建模式和真实数据下验证。模拟器、debug 模式、小数据集都可能掩盖问题。

```bash
flutter run --profile
```

上线前至少验证启动时间、核心列表滚动、关键动画、图片密集页面、低端设备内存、弱网加载。性能优化的目标不是让某台开发机流畅，而是让目标用户的设备稳定。

发布验证最好保留性能基线。每次升级 Flutter、引入新插件、改列表结构、增加图片资源后，都用同一套设备和路径复测。性能退化越早发现，修复成本越低。

性能优化最终一定要回到真实发布路径。profile 模式、目标设备、真实数据量和核心用户操作路径一起验证，才能说明这次优化是真的对用户有价值，而不是只对开发环境好看。
