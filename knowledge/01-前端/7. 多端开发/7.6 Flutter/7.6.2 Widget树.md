## Widget 树

Flutter 的界面是通过 Widget 树描述出来的。父 Widget 组合子 Widget，多层组合后形成完整页面。

```text
MaterialApp
  Scaffold
    AppBar
    Column
      Text
      Button
```

Widget 树描述的是“界面应该长什么样”，而不是“界面已经是什么样”。这也是 Flutter 和命令式 UI 的核心差异之一。

树的意义不只是“把组件摆出来”，而是把界面的结构、职责和更新边界表达清楚。树写得清楚，后面的状态提升、局部刷新、性能排查都会更容易落点。

## 三棵树

Flutter 中经常提到 Widget Tree、Element Tree 和 Render Tree。

| 树 | 职责 |
| --- | --- |
| Widget Tree | 描述 UI 配置 |
| Element Tree | 连接 Widget 与实际实例 |
| Render Tree | 负责布局、绘制与命中测试 |

Widget 是不可变配置，Element 负责生命周期和复用，RenderObject 才真正参与布局和绘制。理解这三棵树，才能理解为什么 Flutter 需要频繁重建 Widget 却仍然高效。

这三棵树一起看，很多看似反直觉的现象就会顺了：为什么 Widget 可以频繁新建、为什么局部状态能被保留、为什么布局和绘制不直接发生在 Widget 上。它们本来就不在同一层承担责任。

## build 描述

Widget 的核心工作是实现 `build()`，它返回下一级 Widget。`build()` 应该尽量纯，不要做副作用、网络请求、文件读取或复杂耗时计算。

```dart
@override
Widget build(BuildContext context) {
  return const MaterialApp(
    home: Scaffold(
      body: Center(
        child: Text("Hello World"),
      ),
    ),
  );
}
```

Flutter 会在需要时重新调用 build，并通过树 diff 找出最小变更。build 越纯，框架越容易高效复用已有对象。把请求、监听、缓存初始化放进 build，通常都会让行为变得不稳定。

`build` 的纯度越高，树就越像一个可预测结果。只要它开始偷偷做副作用，重建次数和执行时机就会变成潜在风险源，后面很多“偶尔执行两次”“为什么这里反复请求”之类的问题都会出现。

## 复用机制

Widget 重建不等于整棵树重画。Flutter 会尝试复用 Element 和 RenderObject，只替换发生变化的部分。

```text
状态变化 -> 重新 build Widget
Widget 对比 -> 复用 Element
需要时更新 RenderObject
```

这也是为什么 Widget 很轻量。开发者可以频繁创建新 Widget 而不用担心对象创建本身太重，但前提是 build 里别塞复杂逻辑。

Widget 的轻量是为了让你放心地“重新描述界面”，不是为了让你把所有重活都塞进 `build`。真正昂贵的通常是布局、绘制、图片解码和不必要的大范围重建，而不是几个配置对象本身。

## 树层级

Widget 树越清晰，后续维护越容易。不要让一个巨大 build 方法塞满所有视觉和状态逻辑，复杂区域应该拆成更小的 Widget。

```dart
class ProductCard extends StatelessWidget {
  const ProductCard({super.key, required this.title});

  final String title;

  @override
  Widget build(BuildContext context) {
    return const Padding(
      padding: EdgeInsets.all(16),
      child: Text("标题"),
    );
  }
}
```

清晰的树结构也有助于性能定位。你可以更快地判断是哪一块 Widget 在频繁重建。遇到莫名抖动或输入框状态错位时，先看是否有不稳定的树层级和 Key。

树层级设计得好时，页面会自然形成几块稳定区域：头部、内容区、列表区、底部操作区、弹层。这样无论是状态更新还是问题排查，都更容易找到具体边界。

## Key 作用

Key 用于帮助框架识别节点身份。在列表、排序、动态插入删除等场景下，稳定 key 可以减少状态错位。

```dart
ListView(
  children: items
      .map((item) => ListTile(
            key: ValueKey(item.id),
            title: Text(item.title),
          ))
      .toList(),
);
```

Key 的思路和 React/Vue 里类似：用稳定身份告诉框架谁是谁。没有 key 或 key 不稳定，列表中输入框焦点、动画状态和局部状态都可能错位。

Key 不只是列表里才有用。任何会在同一位置反复切换不同内容的区域，只要内部带状态，就值得认真考虑 Key 的稳定性。

Key 真正解决的是“身份连续性”问题，而不是“让框架别报错”。只要一个区域在视觉上看起来像同一个位置、但业务上在切换不同对象，就应该问自己要不要显式告诉框架谁是谁。

## 状态分层

Widget 树里最好把状态尽量放在真正依赖它的地方。局部状态放低，页面状态放中，应用状态放高。

```text
App
  Page
    Section
      Item
```

越靠近状态使用点，重建范围越小；越往上，状态共享越方便，但重建范围也越大。这个取舍和 [[7.6.3 布局系统|布局系统]] 一样，都需要看边界。

如果一个 Widget 只影响局部视觉，就把状态放在局部；如果多个子组件都依赖同一状态，再考虑提升状态层级。不要为了“统一管理”把所有状态都提到最上层。

状态分层做得好，Widget 树的更新范围就会自然收敛。状态一旦提升过头，整棵树会因为一点局部变化频繁重建；状态一旦压得太低，又会出现同步困难和数据漂移。
