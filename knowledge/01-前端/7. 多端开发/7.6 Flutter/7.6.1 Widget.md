## Widget 模型

Flutter 的核心是 Widget。界面、布局、样式、手势、动画，很多内容都可以通过 Widget 描述。对前端来说，Widget 有点像组件，但它不是 DOM 节点，也不是最终绘制对象。

Flutter 应用本质上是由一棵 Widget 树描述出来的。Widget 更像“当前界面应该长什么样”的配置，真正参与更新的还包括 Element 和 RenderObject。

对 Web 前端来说，最需要先放下的习惯是“组件最终会变成 DOM 节点”。在 Flutter 里，Widget 更像是一层描述语言，它本身不是最终 UI，也不是长期可变对象，而是框架用来组织界面的一份声明。

## 声明式界面

Flutter 使用声明式 UI 思路：状态变化后重新描述界面，框架负责计算差异并更新渲染结果。

```dart
class CounterText extends StatelessWidget {
  const CounterText({super.key, required this.count});

  final int count;

  @override
  Widget build(BuildContext context) {
    return Text("当前计数：$count");
  }
}
```

当 `count` 变化时，Flutter 会重新执行 `build`，得到新的 Widget 描述，再由框架比较并更新底层结构。学习 Flutter 时要先接受这个模型：你不是手动修改某个文本节点，而是重新描述界面。

声明式界面的好处是状态和 UI 的关系更直接，坏处是如果你在 `build` 里塞了副作用、复杂计算或网络请求，就会把本来清晰的模型搞乱。Widget 适合描述结果，不适合承载重逻辑。

Flutter 里很多“为什么一改状态就乱了”的问题，根上都和这个原则有关：`build` 是描述当前结果，不是执行流程的地方。只要把副作用、请求和重计算混进来，声明式模型就会开始失真。

## StatelessWidget

`StatelessWidget` 适合只依赖外部输入的组件。它自身不保存可变状态。

```dart
class UserCard extends StatelessWidget {
  const UserCard({
    super.key,
    required this.name,
    required this.avatarUrl,
  });

  final String name;
  final String avatarUrl;

  @override
  Widget build(BuildContext context) {
    return Row(
      children: [
        CircleAvatar(backgroundImage: NetworkImage(avatarUrl)),
        const SizedBox(width: 12),
        Text(name),
      ],
    );
  }
}
```

只要组件结果完全由构造参数决定，就优先使用 `StatelessWidget`。这类组件更容易复用、测试，也更不容易产生生命周期问题。它们适合做展示卡片、标签、头像、列表项和静态布局片段。

`StatelessWidget` 的价值不只是“代码更短”，而是它把依赖关系说得很清楚：输入变了，界面才变；输入不变，组件本身没有额外状态要维护。这样的组件越多，整棵树的行为越稳定。

## StatefulWidget

`StatefulWidget` 适合拥有内部可变状态的场景，例如输入内容、动画控制、局部展开状态。

```dart
class LikeButton extends StatefulWidget {
  const LikeButton({super.key});

  @override
  State<LikeButton> createState() => _LikeButtonState();
}

class _LikeButtonState extends State<LikeButton> {
  bool liked = false;

  @override
  Widget build(BuildContext context) {
    return IconButton(
      icon: Icon(liked ? Icons.favorite : Icons.favorite_border),
      onPressed: () {
        setState(() {
          liked = !liked;
        });
      },
    );
  }
}
```

`setState` 的作用是告诉 Flutter：这个 State 依赖的数据变了，需要重新构建当前子树。不要在 `build` 中调用 `setState`，否则容易造成重复构建甚至循环。

Stateful 并不代表可以随意堆状态。能下沉的状态尽量下沉，局部状态只放在真的需要局部重建的地方，否则整个组件树会越来越难控制。

`StatefulWidget` 真正适合的是“这个局部自己就能管理好”的状态，比如展开收起、输入内容、Tab 切换、动画控制器。只要状态已经变成页面级、跨组件共享或需要统一恢复，就不该继续堆在局部 State 里。

## 组合原则

Flutter 鼓励用小 Widget 组合复杂界面。拆分 Widget 的目标是让结构清晰、状态边界明确，而不是把每一行都拆出去。

```dart
Container(
  padding: const EdgeInsets.all(16),
  decoration: BoxDecoration(
    color: Colors.white,
    borderRadius: BorderRadius.circular(12),
  ),
  child: const Text("订单已提交"),
);
```

`Container`、`Padding`、`DecoratedBox`、`Text` 都是 Widget。复杂界面不是写一个巨大 Widget，而是把它拆成清晰的小 Widget。组合得当时，布局和交互逻辑也更容易复用。

拆分 Widget 时可以按职责拆，而不是按行数拆：头部、内容区、空状态、操作区、列表项各自独立，后续状态变化和测试都会更稳。

Flutter 的 Widget 组合很细，但不意味着要机械拆分。拆得好的标准不是文件更多，而是结构更清楚、状态边界更明白、后续变更时影响范围更可控。

## Widget 树

Widget 树描述的是界面结构。Widget 树变化后，Flutter 会尽量复用已有 Element 和 RenderObject，而不是每次都全量重建。

```dart
ListView(
  children: todos.map((todo) {
    return TodoItem(
      key: ValueKey(todo.id),
      todo: todo,
    );
  }).toList(),
);
```

`Key` 用于帮助 Flutter 在 Widget 树变化时识别“谁是谁”。列表重排、插入、删除时尤其重要。没有稳定 Key 时，Flutter 可能按位置复用 Element，导致输入框内容、动画状态或局部状态错位。

Widget 树的复用不是玄学，而是身份识别的问题。只要同一位置上出现的 Widget 身份不稳定，框架就很难复用正确的实例。列表项、表单项和带动画的组件尤其要认真处理 Key。

很多“输入框内容串了”“动画状态跑错了”“列表重排后局部状态乱了”的问题，最终都会回到身份识别。对 Flutter 来说，树结构和 Key 决定了谁才是“同一个组件”。

## 学习边界

理解 Widget 时，要记住它是“配置描述”，不是最终绘制对象。真正参与布局和绘制的还有 Element、RenderObject 等更底层结构。

先把 Widget、Element、RenderObject 的职责分清，再看布局、状态和性能，Flutter 的很多设计才会顺起来。Widget 解决“长什么样”，Element 解决“实例怎么复用”，RenderObject 解决“怎么测量和绘制”。

Widget 学习到这里，最关键的收获不是记住几个类名，而是建立一套分层认知：描述层、实例层、渲染层各自负责什么。后面遇到状态、布局、性能和原生交互问题时，判断就会清楚很多。
