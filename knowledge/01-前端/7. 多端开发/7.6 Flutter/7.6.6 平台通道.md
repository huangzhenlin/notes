## 通道定位

Flutter 平台通道用于 Dart 与原生平台通信，访问 Flutter SDK 没有直接提供的 iOS/Android 能力。

```txt
Dart -> MethodChannel -> Android/iOS -> 系统 SDK
```

常见场景包括调用原生 SDK、读取系统能力、接入支付、蓝牙、地图、推送等。平台通道适合承载“Flutter SDK 没有直接覆盖，但业务又必须依赖”的能力。

平台通道的边界要尽量小。能用现成插件就不要自己再封一层通道；必须自定义时，也要保持接口稳定、参数清晰、错误可读。

平台通道最容易被滥用成“万能出口”。只要页面一遇到原生能力就直接新开通道，项目很快就会积累出一堆零散协议和双端维护负担。边界越早收紧，后面越稳。

## MethodChannel

`MethodChannel` 是最常见的调用方式，适合 Dart 主动调用原生方法并等待结果。

```dart
const channel = MethodChannel("app.device/security");

Future<bool> isDeviceSecure() async {
  final result = await channel.invokeMethod<bool>("isDeviceSecure");
  return result ?? false;
}
```

通道名称要稳定且有命名空间，方法名要业务化。不要把大量零散系统 API 直接暴露给 Dart。好的通道命名应该能看出业务边界，例如 `app.device/security`、`app.pay/order`、`app.network/status`。

命名空间能帮助区分不同能力域，也方便后续版本扩展。一个通道最好只负责一个能力域，而不是把支付、分享、定位、设备信息全塞在一起。

通道设计得像接口设计一样严谨，会给后面的协作省很多力。页面知道该去哪个能力域里找方法，原生知道某个通道只负责什么范围，协议自然更容易稳定。

## 参数与返回值

平台通道支持基础可序列化类型，例如字符串、数字、布尔、列表、Map。

```dart
await channel.invokeMethod("shareProduct", {
  "title": product.title,
  "url": product.shareUrl,
});
```

参数结构要像接口一样设计。复杂对象应转成明确 Map，不要依赖平台侧猜测字段含义。通道参数还要考虑可演进，字段新增应保持向后兼容，返回值结构尽量稳定。

如果通道参数频繁变化，建议加版本字段或能力探测，不要让 Dart 和原生双方都默认“对方一定懂最新参数”。

参数协议越稳定，页面层就越不需要理解平台差异。真正好的平台通道，不是把平台细节原样搬上来，而是把它们在边界内整理成一套更像业务接口的调用方式。

## 错误处理

原生侧错误会以 `PlatformException` 回到 Dart。

```dart
try {
  await channel.invokeMethod("payOrder", {"orderId": orderId});
} on PlatformException catch (error) {
  if (error.code == "PAY_CANCELLED") {
    return;
  }

  showError(error.message ?? "支付失败");
}
```

错误码要稳定。取消、权限拒绝、设备不支持、SDK 异常应区分，否则 Dart 层无法给出正确 UI。错误处理最好同时区分“用户行为”和“系统行为”。

平台通道里的错误最好能映射成 Flutter 层统一错误模型，这样业务页面才能用同一套提示和降级逻辑处理不同原生问题。

错误模型清楚之后，页面才能真正把平台能力当成可用服务，而不是一个“可能成功也可能抛奇怪异常”的黑盒。取消、拒绝、超时、不可用和系统错误最好从一开始就分开。

## EventChannel

持续事件流适合用 `EventChannel`，例如传感器、定位、网络状态、扫码结果。

```dart
const eventChannel = EventChannel("app.network/status");

Stream<NetworkStatus> watchNetworkStatus() {
  return eventChannel.receiveBroadcastStream().map(parseNetworkStatus);
}
```

事件流要处理订阅开始、取消订阅和页面销毁。否则原生侧可能继续推送，造成资源泄漏。`EventChannel` 适合低频但持续的状态变化，不适合高频画面驱动。

如果事件较频繁，应该评估是否真的要通过平台通道跨回 Dart。高频数据更适合原生渲染或更贴近底层的采集方式，否则桥接开销会比较明显。

持续事件流的难点，不是“能不能收到”，而是“收到以后会不会把 Dart 层拖慢”。定位、传感器、网络状态、扫码流这类能力都要同时考虑订阅频率和页面生命周期。

## 插件封装

可复用平台能力应封装成 Flutter plugin，而不是只在业务项目里写散乱通道。

```txt
plugin/
  lib/
  android/
  ios/
  example/
```

插件要提供 Dart API、Android 实现、iOS 实现和示例。跨项目复用时，插件边界比直接复制通道代码更稳定。插件化的好处是把平台通道封装成可发布、可测试、可版本化的产物。

插件还应该提供最小可运行示例，方便确认通道权限、生命周期和错误处理是否正常。很多原生问题只有在真机示例里才容易暴露。

插件化的意义，不只是为了复用代码，更是为了把平台通道从业务页面里剥离出来，变成有版本、有示例、有测试边界的独立能力单元。

## 设计边界

| 场景 | 是否适合平台通道 |
| --- | --- |
| Flutter 已有成熟插件 | 优先用插件 |
| 业务定制原生 SDK | 适合 |
| 高频实时数据 | 谨慎，考虑 EventChannel 或原生渲染 |
| 普通 UI 状态 | 不适合 |
| 安全敏感能力 | 适合但要严格校验 |

平台通道是跨运行时边界，调用成本和维护成本都比普通 Dart 代码高。只有确实需要原生能力时再使用。评估平台通道时可以先问：现成插件是否足够、原生能力是否真的必要、调用频率是否足够低。

如果平台能力已经被频繁调用，说明这个能力可能不适合继续停留在通道层，而是应该抽成更稳定的插件或原生组件。边界越清楚，后续维护越轻松。

平台通道写得成熟时，业务层看到的是少量稳定、语义清楚的能力；原生层看到的是有限、可验证、可监控的协议。它不应该成为项目里任何“暂时没地方放的原生调用”的收纳箱。
