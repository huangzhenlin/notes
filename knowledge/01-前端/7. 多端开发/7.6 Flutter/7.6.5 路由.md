## 导航模型

Flutter 路由负责页面切换和页面栈管理。它和浏览器 URL 历史不同，更像原生应用里的导航栈。常见操作包括打开页面、返回页面、替换页面和清空栈重新进入。

路由的本质不是“跳转 API”，而是页面生命周期和页面栈的管理。跳转方式选错，往往不是马上报错，而是返回错乱、状态丢失、深链恢复失败、登录后回不到正确页面。

Flutter 路由和 Web 路由最大的差异，在于它首先服务的是移动应用流程，而不是浏览器历史。页面如何入栈、何时出栈、返回后恢复什么状态，往往比路径字符串本身更重要。

## Navigator 栈

Flutter 提供 `Navigator` 管理路由栈。页面可以通过 push 进入新页面，通过 pop 返回上一页。

```dart
Navigator.of(context).push(
  MaterialPageRoute(
    builder: (context) => const DetailPage(),
  ),
);
```

```dart
Navigator.of(context).pop();
```

`push` 会把新页面压入栈顶，`pop` 会移除栈顶页面。普通移动应用的页面前进、返回都可以先用这个模型理解。如果页面只是查看详情，`push`/`pop` 就够了；如果页面会替换原页面流程，比如登录成功后进入首页，通常要考虑替换或清空栈。

栈语义清楚以后，很多“为什么这里返回不对”就能更快定位。问题通常不是某个按钮没写对，而是整个流程本来就不该继续留着前一页的历史。

## 返回行为

移动应用的返回体验很重要。Flutter 项目要处理系统返回键、页面内返回按钮、弹层关闭、登录拦截后的回退。

如果返回栈设计不清，用户很容易进入无法返回或返回位置错误的状态。页面内部弹层和整页路由要区分处理，避免一个返回动作把用户带离当前上下文。

复杂页面里常常有多个返回层次：弹窗、底部面板、内页、外层容器。建议返回逻辑按优先级处理，先关局部浮层，再退当前页面，最后才交给系统或宿主。

返回体验做得好的应用，用户几乎不会注意到它；做得差的应用则会频繁让用户困惑“为什么这次退不回去”“为什么一下退多层”。这本质上是导航语义没设计清楚。

## 参数传递

页面跳转通常需要传递 id，而不是传递整块复杂对象。

```dart
Navigator.of(context).push(
  MaterialPageRoute(
    builder: (context) => ProductDetailPage(productId: product.id),
  ),
);
```

详情页拿到 `productId` 后再读取缓存或请求接口。这样列表页和详情页不会共享同一个可变对象，刷新、深链和状态恢复也更容易处理。参数传递应该尽量保持可序列化、可分享、可恢复。

路由参数如果承担了太多临时状态，页面就会越来越难恢复。一个健康的页面应该尽量能靠少量参数独立打开，而不是依赖上一个页面当时的内存环境。

## 返回结果

`push` 返回一个 `Future`，可以接收下一页 `pop` 时带回的结果。

```dart
final changed = await Navigator.of(context).push<bool>(
  MaterialPageRoute(
    builder: (context) => const EditProfilePage(),
  ),
);

if (changed == true) {
  reloadProfile();
}
```

编辑页保存成功后：

```dart
Navigator.of(context).pop(true);
```

这种方式适合“编辑完成后刷新上一页”这类短链路。复杂跨页面状态同步更适合放到状态管理或数据缓存层。返回结果最好表达清楚“是否需要刷新”和“刷新什么”。

返回结果的价值在于把一次短流程闭环讲清楚，而不是把大量业务状态都塞回上一页。只要结果开始变复杂，通常就说明它已经不适合继续依赖 `pop` 返回值来传递。

## 命名路由

命名路由适合集中管理路径，但参数类型和复杂导航会变得不够直观。

```dart
MaterialApp(
  routes: {
    "/": (context) => const HomePage(),
    "/settings": (context) => const SettingsPage(),
  },
);
```

```dart
Navigator.of(context).pushNamed("/settings");
```

小项目可以使用基础命名路由；中大型项目、深链、嵌套路由、Web URL 同步通常会选择更完整的路由库。命名路由的边界在于可维护性，规模一大就更需要集中管理。

命名路由的问题不在“能不能用”，而在“规模变大后是否还能稳定演进”。路径一多、参数一复杂、重定向一出现，集中约束和类型建模的价值就会迅速上升。

## go_router

`go_router` 是 Flutter 生态中常用的声明式路由方案，适合路径化、重定向和深链。

```dart
final router = GoRouter(
  routes: [
    GoRoute(
      path: "/products/:id",
      builder: (context, state) {
        final id = state.pathParameters["id"]!;
        return ProductDetailPage(productId: id);
      },
    ),
  ],
);
```

```dart
MaterialApp.router(routerConfig: router);
```

当应用需要浏览器地址、登录重定向、多 Tab 嵌套路由时，声明式路由比手写 Navigator 栈更容易维护。声明式路由的价值在于“状态驱动导航”。

声明式路由更适合把“当前应用应该处在哪个页面状态”表达清楚，而不是在各个按钮里手动拼栈。复杂应用一旦出现登录守卫、深链恢复和多层嵌套，声明式方案通常会更稳。

## 路由边界

路由负责页面位置和跳转，不应该承载大量业务状态。筛选条件可以进入 URL，表单草稿和接口缓存通常不适合直接塞进路由参数。

| 数据 | 是否适合路由参数 | 原因 |
| --- | --- | --- |
| 商品 id | 适合 | 可分享、可恢复 |
| 搜索关键词 | 适合 | 影响页面结果 |
| 完整商品对象 | 不适合 | 体积大，容易过期 |
| 表单输入中内容 | 通常不适合 | 临时状态 |
| 登录后跳转地址 | 适合 | 导航流程需要 |

路由边界可以记成一句话：能恢复的放路由，临时的放状态，重的数据放缓存或请求层。这样页面打开、刷新、分享和系统回收时都更容易恢复。

这条边界一旦守住，很多架构问题会自然收敛。页面可以从分享打开、从后台恢复、从通知跳转，仍然能走回统一的恢复路径，而不是依赖脆弱的上一页上下文。

## 状态恢复

移动系统可能在后台回收应用进程。导航状态恢复可以让用户回到之前页面，但前提是路由参数可序列化，页面能根据参数恢复数据。

| 不稳定做法 | 更稳做法 |
|---|---|
| 路由传完整商品对象 | 只传 `id`，页面重新加载 |
| 路由传回调函数 | 使用全局事件或状态管理 |
| 页面依赖上一个页面内存状态 | 从缓存或接口恢复 |

React Native 导航和 [[7.5.4 原生桥接|原生桥接]] 也有关：通知点击、分享回跳、支付回调这类原生入口，最终都要落到可恢复的导航路径上。

导航恢复真正稳定的前提，是页面具备“按参数自恢复”的能力。只要页面严重依赖前一页传来的完整对象、回调函数或瞬时状态，系统回收、深链进入和跨端入口都会变得很脆弱。
