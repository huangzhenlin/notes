## 形态差异

多端开发中的发布形态，决定了同一套业务会以什么方式到达用户。常见形态包括 H5、原生 App、桌面客户端、小程序、混合容器和跨端框架产物。

```text
同一业务
  -> 浏览器网页
  -> 小程序
  -> 原生 App
  -> 桌面端
  -> 混合容器
```

发布形态不同，限制不同：浏览器更开放，原生更强但发布慢，小程序更依赖平台审核，桌面端要考虑安装与更新，混合容器要考虑桥和内核。

发布形态会反向影响技术架构。更新越慢，越需要兼容和灰度；能力越强，通常发布和审核成本也越高。

## H5

H5 适合传播快、更新快、入口轻的场景，例如活动页、资讯页、分享落地页和轻量业务页。

| 优势 | 限制 |
|---|---|
| 迭代快 | 受浏览器能力限制 |
| 分享方便 | 离线和系统能力较弱 |
| 无需安装 | 依赖网络和容器质量 |

H5 适合快速试错，但在支付、蓝牙、后台任务、复杂通知等场景里，能力边界明显。它最强的地方是分发和迭代，不是系统能力。

H5 的另一个优势是可以和搜索、分享、营销投放天然结合。只要业务强调传播和短周期活动，H5 往往是最轻的形态。

## 小程序

小程序介于 H5 和原生之间，适合轻量业务、强入口分发、平台生态内复用。

| 优势 | 限制 |
|---|---|
| 入口强 | 平台规则限制多 |
| 安装成本低 | 宿主 API 有边界 |
| 开发体验接近前端 | 调试和发布受平台约束 |

小程序适合在平台生态里承接高频轻业务，但对于深度系统能力、复杂性能和重交互应用，仍有边界。

小程序还要考虑平台差异。微信、支付宝、抖音等平台 API、审核规则、包体限制和调试工具都不完全相同。

## 原生 App

原生 App 适合高性能、强系统能力、复杂交互和深度硬件集成场景。

```text
相机、定位、蓝牙、推送、后台任务
  -> 原生更有优势
```

原生的代价是开发链路和发布链路更重，但它在性能、系统集成和 UI 控制上更完整。很多“必须原生”的判断，不是技术偏好，而是平台能力需求。

如果需求依赖后台定位、蓝牙稳定连接、复杂音视频、系统级推送或深度文件能力，原生方案通常更可靠。

## 桌面端

桌面端适合办公、编辑、可视化、IDE 类应用。它强调窗口、多任务、文件、快捷键和系统托盘等能力。

| 场景 | 适合 |
|---|---|
| 文件处理 | 桌面端 |
| 实时协作编辑 | 桌面端或 Web |
| 深度系统调用 | 桌面端 |
| 轻量查看 | H5 或小程序 |

桌面端发布还要考虑安装包、更新、签名和权限。它不像 Web 那样能随时刷新，也不像移动端那样天然受应用商店约束统一。

桌面端还要适配不同操作系统的文件路径、快捷键、窗口行为和权限模型，这些都不是普通 Web 页面会遇到的问题。

## 混合容器

Hybrid 是把 Web 内容放进原生容器里，通过 JSBridge 补齐系统能力的方案。它适合已有 Web 资产、又需要部分原生能力的业务。

```text
页面用 Web 写
能力靠原生补
```

Hybrid 的关键不是“能不能包起来”，而是桥、内核、容器和资源发布是否可控。桥不稳，混合容器就会出现白屏、卡顿、能力不可用等问题。

Hybrid 特别适合已有 Web 资产复用，但如果原生能力调用越来越多，Bridge 协议和容器版本治理会变成核心工程能力。

## 选择判断

发布形态不应该凭感觉选，而应该根据业务约束判断。

| 业务约束 | 倾向形态 |
|---|---|
| 更新极快、入口轻 | H5 |
| 平台生态分发 | 小程序 |
| 重性能、强系统能力 | 原生 App |
| 文件和窗口能力 | 桌面端 |
| 已有 Web 资产复用 | Hybrid |

```text
判断顺序：
1. 先看用户入口在哪
2. 再看业务是否依赖系统能力
3. 再看发布节奏和审核成本
4. 最后看团队现有资产
```

发布形态和 [[7.1.5 适配体系|适配体系]] 紧密相关。先定义目标用户和能力需求，再决定发布形态，通常比先定技术栈更稳。

如果一个业务同时需要快迭代和强能力，可以考虑组合形态：核心能力在 App，活动和运营在 H5，平台入口用小程序承接。

## 形态策略

一个项目不一定只有一种发布形态。很多团队会用 H5 承接活动页，用小程序承接平台流量，用原生 App 承接深度能力，再用 Hybrid 或跨端框架复用部分逻辑。真正重要的是把不同形态的边界划清，而不是强求“一套代码跑所有地方”。

组合形态下最重要的是统一账号、路由、埋点、错误监控和业务协议，否则用户在不同入口之间切换时体验会割裂。
