## 屏幕适配

屏幕适配的核心是让布局在不同宽度和比例下保持结构稳定。移动 Web 常见手段包括响应式布局、弹性盒、网格布局、媒体查询、`rem`、`vw`、安全区域和动态视口单位。

适配的目标不是让每个端看起来一模一样，而是让每个端都在自己的约束里保持可用、可读、可操作。

```css
.product-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(160px, 1fr));
  gap: 12px;
}

.action-bar {
  position: fixed;
  left: 0;
  right: 0;
  bottom: 0;
  padding: 12px 16px calc(12px + env(safe-area-inset-bottom));
  background: #fff;
}
```

`auto-fit + minmax()` 适合商品卡片、工具入口和内容卡片，因为它让每列最小可读宽度固定，剩余空间自动分配。底部按钮则要考虑安全区域，否则在全面屏设备上可能被系统手势条遮挡。

安全区和视口单位经常一起出现。全面屏、刘海屏、折叠屏和横竖屏切换都可能影响布局边界，所以适配体系要同时看尺寸和可点击区域。

## 交互适配

交互适配关注用户如何输入。触屏需要更大的点击区域和滑动容错；桌面端需要 hover、右键、快捷键和焦点可见；TV 或车机这类终端更依赖方向键和焦点管理。

```css
.tap-target {
  min-width: 44px;
  min-height: 44px;
}

.button:focus-visible {
  outline: 2px solid #1677ff;
  outline-offset: 2px;
}

@media (hover: hover) {
  .card:hover {
    transform: translateY(-2px);
  }
}
```

不要把 hover 当成唯一反馈，也不要把滑动当成唯一操作入口。移动端可以支持左滑删除，但仍应提供显式删除按钮；桌面端可以提供快捷键，但也要保留可见操作。

交互适配本质上是在不同输入方式之间做冗余。可点击、可滑动、可键盘操作、可触摸焦点，能覆盖的越多，终端越稳。

## 能力适配

多端开发经常遇到“某个平台没有这个 API”的问题。能力适配不是在每个页面写一堆 `if`，而是建立统一能力层：检测、调用、降级和错误语义都收敛到一个模块里。

```typescript
type ShareResult =
  | { ok: true }
  | { ok: false; reason: 'unsupported' | 'cancelled' | 'failed' };

export async function sharePage(title: string, url: string): Promise<ShareResult> {
  if (navigator.share) {
    try {
      await navigator.share({ title, url });
      return { ok: true };
    } catch {
      return { ok: false, reason: 'cancelled' };
    }
  }

  await navigator.clipboard.writeText(url);
  return { ok: false, reason: 'unsupported' };
}
```

能力适配要让业务看到稳定语义，而不是看到平台细节。页面只需要知道分享成功、用户取消、不支持或失败，不需要知道当前运行在浏览器、WebView 还是小程序。

当能力缺失时，适配层还应返回明确降级结果，而不是直接抛出平台错误。这样业务层才能决定是提示用户、切换方案还是隐藏入口。

## 数据适配

不同端的数据保存能力差异很大：浏览器有 Cookie、LocalStorage、IndexedDB，小程序有本地缓存，原生应用有沙箱文件和数据库，桌面端还可能有本地文件系统。数据适配要关注容量、同步、过期、加密和清理。

数据适配最容易出问题的地方是“同一个字段在不同端保存方式不同，但业务以为它一致”。比如 token、草稿、下载文件和接口缓存都要有明确生命周期。

| 数据类型 | 适合位置 | 注意点 |
|---|---|---|
| 登录 token | 安全存储或受控缓存 | 过期刷新、退出清理、避免明文泄漏 |
| 页面草稿 | 本地缓存 | 版本兼容、用户主动清除 |
| 大型离线数据 | IndexedDB / 文件 / SQLite | 容量、索引、增量更新 |
| 接口缓存 | 内存 + 持久缓存 | 失效策略、弱网兜底 |

数据适配和 [[7.1.4 发布形态|发布形态]] 相关：同一业务如果既有 H5 又有小程序和 App，就要提前定义哪些数据可以跨端同步，哪些只能留在端内。

## 工程适配

工程适配是把多端差异纳入构建、测试和发布流程。常见做法包括环境变量、条件编译、平台目录、适配层、端到端测试矩阵和灰度发布。

```text
业务页面
  -> 通用组件
  -> 平台能力层
  -> Web / 小程序 / App / 桌面实现
```

平台差异越多，越要控制分叉位置。业务层应尽量保持通用，差异集中在能力层和少量平台组件里。否则项目会从“多端复用”退化成“多个端混在一个仓库里”。

工程适配越成熟，平台判断就越少出现在业务页面里。页面只关心业务状态，平台判断应该沉到构建、适配层和少量入口组件里。

## 验证矩阵

适配最终要靠验证闭环。只在开发者自己的手机上测试，无法覆盖真实用户环境。一个合理的多端验证矩阵至少包括高低端设备、不同系统版本、不同屏幕比例、弱网、深色模式、权限拒绝和升级路径。

| 维度 | 示例 |
|---|---|
| 设备 | 小屏手机、大屏手机、折叠屏、平板、桌面窗口 |
| 系统 | iOS、Android、HarmonyOS、Windows、macOS |
| 容器 | 浏览器、WebView、小程序、桌面客户端 |
| 状态 | 首次安装、升级、清缓存、离线、弱网 |
| 权限 | 授权、拒绝、仅本次允许、系统关闭 |

适配体系的目标不是“穷尽所有设备”，而是用有限成本覆盖最容易出问题的组合。每次线上事故都应该反向补到验证矩阵里，让经验沉淀为流程。

如果某个设备、系统或容器在验证矩阵里总是出问题，就应该把它当成高优先级兼容项，而不是每次发布都临时赌运气。
