## 容器类型

渲染容器决定前端代码运行在哪里、由谁负责渲染、能访问哪些能力。多端开发中常见容器包括浏览器、WebView、小程序容器、React Native 宿主、Flutter Engine、Electron Chromium 和鸿蒙 ArkUI。

| 容器 | 渲染方式 | 典型能力 |
|---|---|---|
| 浏览器 | HTML/CSS/JS | 标准 Web API |
| WebView | 嵌入式浏览器内核 | Web + 原生桥 |
| 小程序 | 宿主双线程渲染 | 宿主 API |
| React Native | JS 驱动原生组件 | 原生组件和模块 |
| Flutter | Skia/Impeller 自绘 | Flutter 组件体系 |
| Electron | Chromium + Node | 桌面能力 |

容器不是外壳名称，而是运行时边界。它决定页面加载、渲染、通信、调试和发布方式。

同一段业务逻辑放进不同容器，能访问的 API、能承受的性能压力、能使用的调试工具都会不同。容器选择是多端架构的第一层约束。

很多后续问题其实都能追溯回容器选择。容器一旦决定，渲染模型、通信方式、能力边界和发布形态都会跟着收敛。

## 浏览器容器

浏览器容器最标准，前端直接使用 DOM、CSSOM、Fetch、Storage、History、Service Worker 等 Web API。

```text
HTML -> DOM
CSS -> CSSOM
JS -> 操作 DOM / 调用 Web API
```

浏览器适合开放 Web、搜索引擎收录、分享传播和快速迭代。它的限制是系统能力受限，无法像原生应用一样深度调用设备能力。

浏览器容器最大的优势是标准化和分发成本低。只要用户能打开链接，就能访问页面；但权限、后台运行、系统集成和离线能力会受到限制。

浏览器容器适合把“内容和流程尽快送到用户面前”，不适合承担太多系统级能力承诺。只要业务强依赖系统权限和后台稳定性，就要谨慎只靠浏览器解决。

## WebView 容器

WebView 是原生 App 内嵌的浏览器容器。它能复用 Web 页面，同时通过 JSBridge 补齐部分原生能力。

```text
Web 页面
  -> WebView
  -> JSBridge
  -> 原生能力
```

WebView 的复杂点在于内核版本、桥注入时机、缓存、白屏治理和宿主生命周期。网页在浏览器里正常，不代表在 WebView 里一定正常。

WebView 还要关注宿主 App 版本。不同 App 版本可能注入不同 Bridge、不同 UA、不同缓存策略，导致同一个 H5 页面表现不同。

所以 WebView 问题常常不是“前端代码错了”，而是“页面、Bridge、容器配置和宿主版本之间有一个环节没对齐”。定位时必须把容器版本一起带上。

## 小程序容器

小程序容器通常采用逻辑层和渲染层分离的模型。开发者写类 Web 语法，但不能直接操作 DOM，能力由宿主平台控制。

```text
逻辑层 JS
  -> setData
  -> 渲染层
  -> 用户事件
  -> 逻辑层
```

这种模型能增强平台控制和安全隔离，但也带来通信成本。频繁大对象 `setData` 会影响性能。

小程序容器里的“类 Web”不等于浏览器 Web。不能直接操作 DOM，也不能假设所有 Web API 都存在，平台 API 和生命周期才是核心边界。

把小程序当浏览器写，是很多性能和兼容问题的起点。理解它是平台宿主容器，而不是开放浏览器，会让很多判断更准确。

## 原生组件容器

React Native 使用 JavaScript 描述 UI，但最终渲染到原生组件。它不是 WebView，也没有浏览器 DOM。

```tsx
<View>
  <Text>Hello</Text>
</View>
```

这意味着 Web CSS、DOM API、浏览器事件模型不能直接迁移。RN 的性能和体验更多受原生组件、Bridge/JSI、列表渲染和线程调度影响。

如果团队从 Web 切到 RN，要重新理解布局、手势、导航和原生模块，不要把 RN 当作“移动端浏览器”。

RN 里很多“为什么这里不像 Web”并不是框架缺陷，而是因为它本来就不在浏览器模型里运行。越早接受这点，方案设计会越稳。

## 自绘容器

Flutter 这类框架通常由自己的渲染引擎绘制 UI。它不依赖系统原生控件或 DOM，而是维护自己的组件、布局和绘制体系。

```text
Dart Widget
  -> Element / RenderObject
  -> Engine
  -> GPU 绘制
```

自绘容器的优势是跨平台一致性强，缺点是包体积、原生生态接入和平台体验细节需要额外处理。

Flutter 适合追求视觉一致性和复杂交互的应用，但如果项目需要大量平台原生能力，也要评估插件生态和原生开发投入。

Flutter 的优势是跨平台 UI 一致，但代价是你要接受它自己的渲染体系和工程链路。它更像“自成一套平台”，而不是 Web 的直接延伸。

## 桌面容器

Electron 使用 Chromium 渲染页面，并通过主进程提供桌面能力。它把 Web 技术带到桌面，但也引入安全和体积成本。

```text
Renderer
  -> Preload
  -> IPC
  -> Main Process
  -> OS
```

桌面容器的关键不是“能用网页做桌面”，而是进程隔离、自动更新、文件权限、窗口管理和系统集成。

Electron 的渲染进程和主进程边界必须清楚。把 Node 能力直接暴露给页面会带来明显安全风险。

桌面容器的危险在于，它看起来像网页，实际上却握着很多系统能力。越是方便暴露能力的地方，越要明确边界和权限。

## 选择判断

选择渲染容器要看业务目标，而不是只看团队熟悉什么。

| 需求 | 倾向容器 |
|---|---|
| 快速传播和 SEO | 浏览器 |
| App 内复用 Web | WebView |
| 平台生态入口 | 小程序 |
| 高原生体验 | React Native / 原生 |
| 强一致跨端 UI | Flutter |
| 桌面文件和窗口能力 | Electron |

渲染容器和 [[7.1.3 通信模型|通信模型]]、[[7.1.5 适配体系|适配体系]] 是一组基础概念。容器决定运行边界，通信决定能力交换，适配决定体验如何落到不同终端。

选容器时可以先问：目标用户从哪里进入、需要哪些系统能力、性能要求多高、发布是否受审核、团队是否能维护对应工具链。

容器是否选对，可以反过来看几个问题：

| 问题 | 说明 |
| --- | --- |
| 关键能力是否能自然接入 | 能力边界是否匹配 |
| 主要性能瓶颈是否在容器可控范围内 | 性能模型是否匹配 |
| 调试和发布链路是否能被团队长期维护 | 工程成本是否可控 |
