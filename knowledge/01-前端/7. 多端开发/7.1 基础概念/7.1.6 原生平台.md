## 对前端的影响

原生平台会直接影响前端的这些判断：

1. 该用什么容器承载页面。
2. 能否快速更新页面资源。
3. 哪些能力必须走宿主桥接。
4. 页面栈、返回和恢复应该怎么设计。
5. 是否需要按平台做特化体验。

如果这些边界不清楚，后续在 [[7.4 Hybrid|Hybrid]]、[[7.5 React Native|React Native]]、[[7.6 Flutter|Flutter]]、[[7.9 Electron|Electron]] 里的很多设计都会显得“为什么这里这么麻烦”。

原生平台知识对前端的价值，主要在于帮助你判断哪些能力可以靠 Web/容器解决，哪些必须依赖宿主层。

## 学习边界

前端理解原生平台，目标不是成为原生开发者，而是做到两件事：

- 知道哪些问题属于前端自己能解决，哪些需要宿主配合
- 知道不同方案为什么会在能力、性能、发布和适配上出现差异

到这一步，原生平台知识就已经足够支撑后面的框架学习了。

不需要一开始就深入每个平台 SDK，但要理解生命周期、权限、容器和发布机制这些共同约束。
## 平台范围

前端学习原生平台，不是为了立刻转成 Android、iOS 或 HarmonyOS 开发，而是理解多端方案背后的宿主环境。页面运行在哪里，决定了生命周期、权限、导航、性能、调试和发布方式。

```text
移动系统：Android、iOS、HarmonyOS
桌面系统：Windows、macOS、Linux
新终端：车机、TV、大屏、IoT、可穿戴设备
宿主容器：WebView、小程序容器、App 内嵌容器、桌面 WebView
```

这些平台都可能承载前端代码，但承载方式不同。H5 在浏览器里运行，Hybrid 在 App WebView 里运行，小程序在平台容器里运行，React Native 和 Flutter 则通过自己的运行时或渲染体系接入原生能力。

这些平台不只是“更多目标端”，还意味着不同的生命周期、权限系统、更新机制和硬件形态。前端方案如果不理解宿主平台，就很难解释为什么某些端会特别麻烦。

## Android

Android 生态开放，设备形态和系统版本分布更碎片化。前端在 Android 上最常遇到的问题包括 WebView 版本差异、机型兼容、权限弹窗、返回键、软键盘遮挡、状态栏和导航栏适配。

```text
Android 前端关注点：
WebView 内核版本
物理返回键与页面返回栈
软键盘 resize / overlay 行为
文件选择与相机权限
厂商系统对后台、通知、定位的限制
```

在 Hybrid 或小程序场景中，很多“页面 bug”其实来自宿主容器配置。例如 WebView 是否允许混合内容、是否开启调试、是否注入 Bridge、是否处理文件上传回调。前端排查时要同时看页面代码和宿主配置。

Android 端最常见的不是单纯页面逻辑问题，而是 WebView 版本碎片化和宿主接入差异。前端要学会把问题拆成“页面问题”和“容器问题”。

## iOS

iOS 生态相对统一，但系统安全模型更严格。前端常见问题包括 WKWebView 行为、Safari 与内嵌 WebView 差异、输入框聚焦限制、滚动回弹、安全区、权限说明和 App 审核规则。

```css
.page {
  padding-bottom: env(safe-area-inset-bottom);
}
```

安全区不是视觉细节，而是不同设备形态下的布局边界。刘海屏、灵动岛、底部 Home Indicator 都会影响页面可点击区域。移动 Web、Hybrid、小程序都要明确安全区策略，否则底部按钮和固定导航很容易被遮挡。

iOS 容器通常对滚动、焦点、输入和键盘行为更敏感。很多看似简单的输入框问题，其实是 WebView 和系统交互方式导致的。

## HarmonyOS

HarmonyOS 对前端的意义不只是“多一个系统”，而是移动、平板、车机、穿戴和 IoT 场景之间的协同能力更强。前端团队即使不写原生 ArkTS，也要理解它可能改变应用分发、页面容器和设备协同方式。

```text
HarmonyOS 关注点：
设备形态更多
应用能力可能跨设备流转
权限与分发规则独立
Web 容器和原生容器需要分别验证
```

国内业务如果覆盖华为生态，不能只按 Android WebView 经验判断。尤其是支付、定位、分享、推送、文件访问等能力，要以平台文档和真实设备验证为准。

HarmonyOS 场景下，多设备协同会让“一个页面在多终端流转”的需求更常见。前端如果只按单设备 App 思路设计，可能会漏掉跨设备状态和恢复逻辑。

## 桌面系统

桌面平台对前端的影响主要体现在窗口、多进程、本地文件、系统菜单、快捷键、托盘、自动更新和安全沙箱。Electron 把 Web 技术带到桌面，但它不是“浏览器页面套壳”这么简单。

```text
桌面前端关注点：
窗口生命周期
主进程与渲染进程通信
本地文件权限
自动更新与签名
系统快捷键和菜单
崩溃日志与本地诊断
```

桌面应用用户停留时间更长，对稳定性和资源占用更敏感。内存泄漏、长任务、无限日志、后台定时器在浏览器页面里可能只是卡顿，在桌面应用里会变成长期资源消耗。

桌面端还要考虑单实例、文件打开、深链路、系统托盘和热更新。它比纯 Web 更接近一个完整应用，而不是一个页面。

## 新终端

车机、TV、大屏、IoT、可穿戴设备的共同特点是交互方式和使用场景发生变化。它们不一定以触摸为主，可能依赖遥控器、旋钮、语音、方向键、手势或传感器。

```text
新终端适配维度：
输入方式
观看距离
网络稳定性
性能预算
离线能力
系统权限
应用分发
```

这类场景里，响应式布局只是基础。更重要的是信息密度、焦点导航、弱网容错、字体大小、操作确认和异常恢复。前端不能只把手机页面放大或缩小到新屏幕上。

新终端最重要的不是“屏幕更大/更小”，而是交互距离和反馈方式变了。适配时要重新思考焦点、导航和内容密度。

## 生命周期

原生平台都有自己的生命周期：应用启动、进入前台、退到后台、页面切换、进程回收、权限变化、网络变化。Web 页面在浏览器中也有生命周期，但在宿主 App 和小程序容器里，生命周期会被平台进一步包装。

```ts
function onAppResume() {
  refreshTokenIfNeeded();
  syncPendingTasks();
}

function onAppPause() {
  saveDraft();
  stopExpensivePolling();
}
```

如果不理解生命周期，页面很容易出现返回后数据过期、后台轮询耗电、草稿丢失、登录态失效、音视频未暂停等问题。多端项目应该把生命周期事件抽象成清晰的应用事件，而不是每个页面各写一套判断。

生命周期处理不好，会直接影响草稿、登录态、音视频、轮询和后台任务。前端和宿主的责任边界必须明确。

## 前端边界

前端需要知道哪些问题能自己解决，哪些必须让宿主配合。布局、安全区、资源加载、页面状态通常能在前端侧处理；相机、定位、通知、文件、支付、分享、蓝牙等能力往往需要宿主权限、原生模块或平台 API。

这也是 [[7.1.1 多端开发|多端开发]] 里选择路线的前置知识：如果核心能力都依赖原生，纯 H5 会很吃力；如果核心诉求是内容展示和快速发布，强原生方案可能过重。清楚原生平台边界，才能避免在错误层级解决问题。

清楚边界之后，很多方案取舍会变得明显：如果核心能力多数要靠宿主，就不该把纯 Web 当成唯一方案；如果核心能力只是展示和交互，过重的原生改造也没必要。
