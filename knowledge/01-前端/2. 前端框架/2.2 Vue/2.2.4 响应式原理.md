## 响应式追踪

Vue 的响应式系统会把普通对象转换成可追踪的响应式对象。读取和修改会被纳入依赖收集与触发更新链路中。

它解决的是“数据变了，谁需要知道”的问题。Vue 不需要手动告诉每个视图怎么更新，而是通过依赖追踪自动找到受影响的地方，这也是它和命令式 DOM 更新最大的不同。

```ts
const state = reactive({
  count: 0,
  user: {
    name: "Ada",
  },
});
```

它的核心不是“自动魔法”，而是“谁读了谁，谁改了谁，就记下来”。组件渲染时读取到的响应式值，会被记录为依赖，后续值变化时再触发更新。

所以响应式系统的关键并不在“数据对象变没变”，而在“读取和修改是不是经过了可追踪的代理层”。这也是为什么直接替换原始对象、乱做解构或脱离响应式上下文，都会让更新链路失效。

Vue 3 的响应式主要基于 `Proxy`。读取属性时收集依赖，写入属性时触发依赖更新。可以把它理解成一张关系表：某段渲染或计算读取过哪个字段，字段变化后就通知对应执行单元重新运行。

```text
组件渲染读取 state.count
  -> 记录“当前组件依赖 count”
  -> state.count 修改
  -> 找到依赖 count 的组件
  -> 重新渲染相关部分
```

依赖收集发生在读取时，而不是声明时。一个字段如果从未被渲染、计算属性或 watcher 读取，它变化时也不会触发无关更新。这种按需追踪是 Vue 响应式的核心优势。

## `reactive`

`reactive` 更适合对象和数组。

```ts
const form = reactive({
  profile: {
    name: "",
    email: "",
  },
});
```

它适合对象结构明确、字段经常一起变化的场景。大对象里如果只关心少数字段，也可以再拆得更细一点。

`reactive` 更像结构化状态容器，适合表单、配置对象、详情页模型这类整体性强的数据。对单个原始值来说，`ref` 往往更自然，也更容易在模板和脚本之间保持一致。

`reactive` 返回的是代理对象，原始对象本身并不会变成响应式入口。后续读写应该始终经过代理对象，而不是继续操作原始对象。

```ts
const raw = { count: 0 };
const state = reactive(raw);

state.count += 1;
```

如果把 `reactive` 对象整体重新赋值给另一个普通对象，原来的依赖不会自动迁移。需要替换整体状态时，通常更适合用 `ref` 包对象，或者逐字段更新 `reactive` 对象。

```ts
const profile = ref({ name: "Ada" });
profile.value = { name: "Grace" };
```

## `ref`

`ref` 更适合原始值，也能包装对象。

```ts
const count = ref(0);
count.value += 1;
```

在模板里 `ref` 会自动解包，但在 JavaScript 里要通过 `.value` 访问。把这个差异记牢，很多“模板正常、脚本不正常”的问题就会少很多。

如果在组合函数或工具函数里传递 `ref`，要特别留意是否已经解包。很多 bug 并不是响应式失效，而是 `.value` 访问时机不对，导致拿到的始终不是预期值。

`ref` 在模板中会自动解包，在响应式对象中也有一些解包行为，但在数组、集合和普通 JavaScript 逻辑里仍然需要 `.value`。学习 Vue 响应式时，最容易混淆的就是“哪里会自动解包，哪里不会”。

```ts
const count = ref(0);
const list = reactive([count]);

console.log(count.value);
console.log(list[0].value);
```

组合函数返回 `ref` 是常见做法，因为调用方可以继续保持响应式。如果组合函数直接返回普通值，调用方拿到的可能只是某一刻的快照。

```ts
function useCounter() {
  const count = ref(0);
  const increment = () => {
    count.value += 1;
  };

  return { count, increment };
}
```

## 依赖收集

```ts
const total = computed(() => state.count * 2);
```

组件渲染或计算属性执行时会读取响应式值，Vue 会记录依赖。之后值一变，对应的计算或渲染就会重新执行。

依赖收集不是全局扫描，而是“当前执行过程中读到了什么就记什么”。所以响应式代码写得越局部、越明确，Vue 需要追踪的依赖就越少，调试也越容易。

`computed` 会缓存结果，只有依赖变化时才重新计算。它适合纯派生值，不适合在内部做请求、写状态或修改 DOM。

```ts
const fullName = computed(() => {
  return `${firstName.value} ${lastName.value}`;
});
```

如果派生值只是模板里一小段简单表达式，可以直接写；如果逻辑复用、计算较重或需要命名表达业务含义，用 `computed` 更清楚。不要把 `computed` 当成“异步任务容器”，异步和副作用应该交给 `watch`、生命周期或数据层。

## 深层响应

默认情况下，响应式对象会递归追踪嵌套结构。

```ts
const profile = reactive({
  info: {
    name: "",
    email: "",
  },
});
```

但这不代表越大越好。大对象、超深层结构和服务端整包返回的数据，不一定都适合直接塞进一个 `reactive`。

深层响应式带来的成本不只是性能，还包括更新边界更难看清。大对象一旦被多个视图读取，后续哪个字段改动会触发哪些组件，就不再那么直观了。

对于大型不可变数据、第三方实例、地图对象、编辑器实例、图表实例，不一定需要深层响应。可以使用 `shallowRef`、`shallowReactive` 或 `markRaw` 控制响应式深度，避免 Vue 递归代理不需要追踪的对象。

```ts
const chart = shallowRef<ChartInstance | null>(null);

onMounted(() => {
  chart.value = createChart();
});
```

这类对象通常由第三方库自己管理内部状态，Vue 只需要知道实例引用是否存在，不需要追踪实例内部每个字段。响应式不是越深越好，应该追踪真正会影响视图的部分。

## 响应式陷阱

| 问题 | 说明 |
| --- | --- |
| 解构丢失响应式 | 直接解构会丢依赖 |
| 混用 `ref` 和 `reactive` | 容易搞乱访问方式 |
| 替换整个对象 | 可能影响依赖追踪 |
| 大对象整包响应 | 可能让边界太宽 |

如果需要解构后保持响应式，可以用 `toRefs`。

这类工具的意义，是让“结构拆分”与“响应式保留”同时成立。对需要拆字段单独传递给子组件的场景尤其有用，否则一不小心就把响应式链路断开了。

```ts
const state = reactive({ count: 0 });
const { count } = toRefs(state);
```

解构丢响应式的根因是：解构拿到的是当前属性值，而不是带有 get/set 追踪能力的代理访问。`toRef` 和 `toRefs` 会把属性包装成 ref，让拆出去的字段仍然能回到原响应式对象。

```ts
const state = reactive({
  name: "Ada",
  age: 28,
});

const name = toRef(state, "name");
name.value = "Grace";
```

如果只是把响应式对象传给函数并在函数内部读取属性，不一定需要解构。过度 `toRefs` 也会让代码充满 `.value`，要根据传递边界决定。

## 选择边界

| 场景 | 推荐 |
| --- | --- |
| 基本值 | `ref` |
| 对象与集合 | `reactive` |
| 解构后保留响应式 | `toRefs` |
| 复杂派生值 | `computed` |

响应式系统的目标是让“数据变了，界面知道”。理解这个依赖链，后面的组合式 API 才会真正顺。

如果你把 Vue 响应式和 React 的 state 对比来看，会更容易理解它们的差别：Vue 更偏自动追踪依赖，React 更偏显式触发更新。两者都在解决 UI 与状态同步，只是机制不同。

实践里选择 `ref` 还是 `reactive`，可以遵循一个朴素规则：基本值和可能整体替换的对象用 `ref`，结构稳定且字段一起维护的对象用 `reactive`。团队里最好形成统一习惯，否则一会儿 `.value`、一会儿深层对象代理，会让组合函数边界变得难读。

响应式调试时，先确认三件事：读取是否发生在响应式上下文中，修改是否经过代理或 ref，解构或传参时是否丢失了响应式连接。多数“Vue 没更新”的问题，都能在这三条里找到原因。
