## 数据流向

组件通信首先要看数据归属：谁拥有状态，谁负责修改，谁只是展示。通信方式选错，组件很快会互相牵线。

通信方式不是越高级越好。父子关系能解决，就不要上 store；只是布局内容定制，就不要用 ref 调方法；跨层配置能用 provide/inject，就不用把 props 一层层透传到每个中间组件。先判断数据生命周期和共享范围，再选择 API。

```text
父拥有状态 -> props 下发，emits 回传
组件自己拥有状态 -> 内部 ref/reactive
跨层稳定上下文 -> provide/inject
跨页面共享 -> store
命令式动作 -> 组件 ref
```

这样选型会比“哪个 API 新就用哪个”稳定得多。

## props 与 emits

最基础、最稳定的父子通信方式是 props + emits。

```vue
<UserCard :user="user" @select="handleSelect" />
```

```ts
defineProps<{ user: User }>();
defineEmits<{ (e: "select", id: string): void }>();
```

props 向下传数据，emits 向上通知变化。单向数据流越清楚，组件边界越容易维护。

props 应该被看作只读输入。子组件如果需要修改父组件传来的值，应通过事件表达“发生了什么”，让父组件决定如何更新。

```vue
<script setup lang="ts">
const props = defineProps<{ user: User }>();
const emit = defineEmits<{ (e: "rename", id: string, name: string): void }>();

function rename(name: string) {
  emit("rename", props.user.id, name);
}
</script>
```

事件名最好表达业务语义。`rename`、`submit`、`select` 比 `change`、`callback` 更容易让父组件理解意图。

## `v-model`

`v-model` 是父子组件之间常见的双向绑定语法。

```vue
<Child v-model="value" />
```

它本质上仍然是 `modelValue` 和 `update:modelValue`。

```vue
<Child
  :model-value="value"
  @update:model-value="value = $event"
/>
```

适合输入框、开关、选择器这类“父组件持有值，子组件通知变化”的场景。

自定义组件的 `v-model` 本质上仍然是受控组件模式。父组件持有值，子组件通过 `update:modelValue` 通知变化。

```vue
<script setup lang="ts">
defineProps<{ modelValue: string }>();
const emit = defineEmits<{ (e: "update:modelValue", value: string): void }>();
</script>

<template>
  <input
    :value="modelValue"
    @input="emit('update:modelValue', ($event.target as HTMLInputElement).value)"
  />
</template>
```

不要在子组件内部同时维护一份完全独立的值，除非你明确需要“提交前草稿”。否则父子两份状态很容易不同步。

## 多模型

复杂输入可以使用多个 `v-model`。

```vue
<RangePicker v-model:start="start" v-model:end="end" />
```

每个模型都应该有明确业务含义，不要只为了省代码滥用。

多个 `v-model` 适合范围选择器、颜色选择器、分页组件这类有多个独立受控值的组件。但如果模型之间强关联，可能更适合传一个对象，或者设计更明确的提交事件。

```vue
<RangePicker
  v-model:start="startDate"
  v-model:end="endDate"
/>
```

如果 `start` 和 `end` 必须一起校验、一起提交，就要在组件内部处理它们的关系，而不是让父组件在两个更新事件之间猜测状态是否完整。

## `provide/inject`

`provide/inject` 适合跨层传递上下文。

```ts
provide("theme", theme);
const theme = inject("theme");
```

主题、表单上下文、布局配置、注册器都适合这种方式。高频变化的业务状态更适合 store 或明确的数据流。

`provide/inject` 最适合“祖先提供能力，后代按需使用”的场景，例如表单上下文注册字段、弹窗组共享配置、主题和国际化。为了类型安全，真实项目里通常会把 key 抽成 `InjectionKey`。

```ts
const ThemeKey: InjectionKey<Ref<"light" | "dark">> = Symbol("theme");

provide(ThemeKey, theme);

const theme = inject(ThemeKey);
```

它会让依赖变得不如 props 显式，所以不适合普通业务数据到处传。使用时要保证提供者和消费者的层级关系稳定，否则组件单独复用时可能拿不到注入值。

## 插槽通信

插槽适合内容分发，不适合承载复杂数据流。

```vue
<Modal>
  <template #footer>
    <button>确认</button>
  </template>
</Modal>
```

它更像“把内容交给子组件摆放”，而不是“让组件互相同步状态”。

作用域插槽可以让子组件把一部分状态暴露给插槽内容，用于表格列、列表项、弹窗底部等可定制结构。

```vue
<DataList :items="users">
  <template #item="{ item }">
    <UserCard :user="item" />
  </template>
</DataList>
```

插槽适合结构定制，不适合承载复杂业务流程。如果插槽传出的数据越来越多，调用方需要理解子组件内部状态机，说明组件 API 可能已经过度抽象。

## 组件 ref

父组件可以通过 ref 调用子组件暴露的方法。

```vue
<Child ref="childRef" />
```

这种方式适合少量命令式能力，比如重置表单、滚动到指定位置、打开弹窗。不要把它当成常规通信方式。

在 `<script setup>` 中，子组件需要通过 `defineExpose` 显式暴露给父组件，否则父组件不应该依赖内部实现。

```vue
<script setup lang="ts">
const inputRef = ref<HTMLInputElement | null>(null);

function focus() {
  inputRef.value?.focus();
}

defineExpose({ focus });
</script>
```

命令式调用适合聚焦、滚动、重置、播放控制这类动作。状态同步仍然优先 props、emits 和 store，否则父组件会变成操纵子组件内部细节的脚本。

## Store 通信

跨页面、跨路由、跨多个组件共享的状态，可以使用 Pinia 或其他 store。

```ts
const userStore = useUserStore();
```

store 适合身份、权限、购物车、偏好设置这类真正跨域共享的状态。局部父子通信仍然优先 props / emits。

Store 通信要避免成为“全局事件总线”。如果两个相邻组件只是父子关系，用 store 反而会隐藏数据流。Pinia 这类 store 更适合跨路由、跨布局、跨业务模块共享的状态，或者需要持久化、调试、派生 getter 的状态。

```ts
const cartStore = useCartStore();
cartStore.add(productId);
```

服务端数据也不一定都要放 store。接口列表、详情缓存、分页结果更像服务端状态，可能更适合请求缓存库或页面数据层。store 适合前端拥有的客户端状态。

## 选择边界

| 场景 | 推荐 |
| --- | --- |
| 父子通信 | props / emits |
| 表单双向值 | `v-model` |
| 跨层上下文 | provide / inject |
| 内容分发 | 插槽 |
| 少量命令式调用 | ref |
| 全局共享状态 | store |

先看数据归属，再选通信方式。API 很多，但真正要守住的是数据流。

如果通信链路开始绕，可以用两个问题重新整理：这份数据的权威来源在哪里，变化应该由谁发起。权威在父组件，就 props/emits；权威在子组件但父组件需要命令式触发，就 ref；权威在跨页面客户端状态，就 store；权威在服务端，就数据请求层。

组件通信不是为了让任意两个组件随便说话，而是让状态沿着可解释的路径流动。路径清楚，后续调试和重构才不会变成猜谜。
