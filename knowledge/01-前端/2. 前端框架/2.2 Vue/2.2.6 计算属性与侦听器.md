## 派生状态

计算属性和侦听器都依赖响应式系统，但职责完全不同。一个负责“算出结果”，一个负责“在变化时做事”。

判断时可以先看结果是不是“可以直接由现有状态推出来”。如果是，就更偏向 `computed`；如果它会触发请求、写本地存储、同步标题、改路由、打埋点，那通常就已经进入 `watch` 的职责范围了。

## `computed`

`computed` 适合从响应式数据派生新值。

计算属性的核心价值是声明派生关系。依赖不变时复用缓存，依赖变化时重新计算，它适合纯函数式结果。

```ts
const fullName = computed(() => `${firstName.value} ${lastName.value}`);
```

它有缓存，依赖不变时不会重复执行。格式化、过滤、聚合、拼接、布尔派生，都很适合放这里。

`computed` 最适合承接模板层不该继续堆放的那部分展示逻辑。例如“当前列表是否为空”“按钮是否可点”“筛选后的结果集”“当前步骤标题”这类值，都很适合作为派生状态存在，而不是每次在模板里临时算一遍。

## 缓存机制

```ts
const filteredList = computed(() =>
  items.value.filter((item) => item.visible),
);
```

计算逻辑轻时，缓存收益可能不明显；但当逻辑涉及过滤、排序、分组或格式化时，`computed` 通常很值。

如果结果只是模板里展示的一小段，直接写表达式也可以；如果同一个结果会被多处复用，`computed` 更有意义。

缓存机制的重点不只是“省性能”，还在于“把派生关系固定下来”。只要这个值在多个地方被读取，提成 `computed` 往往会比复制同一段表达式更稳，因为后续规则变了，只需要改一个地方。

## 可写计算

`computed` 也可以提供 setter。

```ts
const fullName = computed({
  get: () => `${firstName.value} ${lastName.value}`,
  set: (value: string) => {
    const [first = "", last = ""] = value.split(" ");
    firstName.value = first;
    lastName.value = last;
  },
});
```

这种写法适合组合输入和拆分显示，但不要滥用成复杂状态同步机制。

可写计算适合像“全名”这类双向语义清楚的场景，不适合复杂表单同步。setter 里一旦有太多条件，代码就会难推理。

一个实用判断是：如果 setter 只是把一个展示值拆回几个基础字段，它通常还算自然；如果 setter 已经开始做校验、请求、状态联动、错误处理，那它多半已经超出可写计算的合理边界了。

## `watch`

`watch` 适合观察某个响应式源，并在变化时触发副作用。

`watch` 的核心是源明确、动作明确。它适合发请求、存草稿、同步路由、记录埋点这类“值变化后要做事”的场景。

```ts
watch(searchText, (value) => {
  fetchList(value);
});
```

它更像“变化回调”，适合请求、埋点、路由同步和显式监听。

`watch` 的优势在于源足够明确。你能很清楚地知道“是谁变了”“变化后要做什么”，这对于调试和维护都很重要。复杂页面里，显式依赖通常比自动收集更可控。

## `watchEffect`

`watchEffect` 会自动收集依赖并立即执行。

`watchEffect` 适合快速同步简单依赖，但它的边界不如 `watch` 显式。依赖越来越复杂时，通常还是 `watch` 更可控。

```ts
watchEffect(() => {
  document.title = title.value;
});
```

它写起来更省，但依赖不够显式。复杂逻辑里，`watch` 往往更可控。

`watchEffect` 更像“快速把副作用挂上去”的工具，适合依赖很少、逻辑很短、阅读成本低的场景。只要 effect 体越来越长，或者内部开始有分支和异步，一般就该收回到 `watch` 里。

## 即时与深度

```ts
watch(
  () => route.params.id,
  (id) => loadUser(id),
  { immediate: true },
);
```

```ts
watch(form, saveDraft, { deep: true });
```

`immediate` 适合初次进入就要执行一次的场景；`deep` 适合监听对象结构，但不要滥用，否则会把范围搞得太宽。

`deep` 监听对象很方便，但对象越大越容易把不相关变化也算进去。能监听具体字段，就不要动不动监听整个对象。

同样地，`immediate` 也不只是“顺手开一下”。它意味着这个侦听器既负责初始化，又负责后续变化。如果初始化逻辑和更新逻辑已经开始分叉，通常就该拆开，而不是继续塞在同一个 `watch` 回调里。

## 选择判断

| 场景 | 推荐 |
| --- | --- |
| 纯派生值 | `computed` |
| 需要缓存 | `computed` |
| 需要副作用 | `watch` |
| 初始化即执行并追踪依赖 | `watchEffect` |
| 监听明确源 | `watch` |

更简单的记法是：结果放 `computed`，动作放 `watch`，短小自动同步放 `watchEffect`。只要你开始犹豫，就先问自己这段代码产出的到底是“值”还是“动作”。

## 清理

监听器和副作用通常需要清理。

```ts
watchEffect((onCleanup) => {
  const timer = setInterval(() => {}, 1000);
  onCleanup(() => clearInterval(timer));
});
```

派生状态和侦听器一起看，最容易理解“数据变化”和“副作用触发”的分界。

一个好记的顺序是：结果用 `computed`，动作用 `watch`，临时自动收集用 `watchEffect`。先选语义，再选 API。

清理阶段尤其容易暴露边界是否选对了。如果一个 effect 需要管理很多定时器、监听器、并发请求和取消逻辑，往往说明副作用已经变复杂，继续依赖自动收集就会很难维护。这个时候宁可多写一点显式代码，也比后期排查副作用泄漏轻松。
