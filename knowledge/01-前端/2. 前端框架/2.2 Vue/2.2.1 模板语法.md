## 模板表达

Vue 模板是声明式 UI 语法。它的目标不是把业务逻辑写进模板，而是清楚描述“数据如何映射成界面”。

模板最重要的价值是把 UI 的结构和数据关系显式化。看模板时应该优先关注“有哪些状态”“哪些内容是动态的”“哪些行为依赖事件”，而不是把它当成一段普通 HTML。

模板本质上仍然是 Vue 组件的一部分，只是 Vue 把常见绑定和结构控制语法包装得更接近 HTML。它适合表达“什么展示什么”，不适合替代脚本层承担全部规则。

```vue
<template>
  <h1>{{ title }}</h1>
  <p>{{ count + 1 }}</p>
</template>
```

模板里可以写表达式，但不适合写复杂计算。越接近“显示结果”，越适合放在模板；越接近“业务规则”，越应该放进脚本层。

这条边界很关键。模板里的表达式应该更像“轻量展示逻辑”，比如拼接文本、判断状态、选择类名；像格式化、筛选、聚合、权限判断、流程控制这类逻辑，最好提前放到计算属性或方法里。

判断一段逻辑该不该留在模板里，可以问一个简单问题：它是在描述界面结果，还是在推导业务规则。前者适合模板，后者更适合 `computed`、方法或组合函数。这个判断一旦稳定下来，Vue 模板就会明显更清爽。

## 插值表达式

双大括号会把值作为文本输出。

```vue
<template>
  <p>Hello, {{ userName }}</p>
</template>
```

这类写法适合文本展示、状态提示和简单拼接。复杂格式化更适合放到计算属性或方法里。

如果插值内容可能来自用户输入，仍然应该依赖 Vue 的默认转义，而不是手动拼 HTML。模板插值本身更适合“安全文本展示”，不适合做富文本注入。

插值里可以写轻量表达式，但不要把业务规则塞得太深。比如简单三元、拼接、取值可以接受，复杂筛选、聚合、权限判断更适合移到计算属性或方法里。

如果某个插值已经长到需要换行，往往就说明它不该继续留在模板里了。把它提炼成一个有语义的计算属性，不仅更好读，也更方便以后复用和测试。

## 属性绑定

动态属性用 `v-bind` 或简写 `:`.

```vue
<template>
  <img :src="avatarUrl" :alt="username" />
</template>
```

绑定可以作用于属性、类名、样式和布尔状态。只要值来自变量，就应该通过绑定进入模板，而不是手写字符串拼接。

属性绑定的意义不只是动态，它还能把“值”和“语义”分开。比如 `:disabled="submitting"`、`:aria-busy="submitting"` 这种绑定，能让可访问性和状态表达同时成立。

动态绑定的优势在于“值和语义分离”。例如 `:class="{ active: selected }"` 远比 `class="btn active"` 更能说明状态来源，也更容易跟随数据更新。

属性绑定还经常承担“把组件状态暴露给 DOM”的任务。表单禁用、错误态、当前步骤、可展开区域这些信息，只要能稳定映射成属性或 class，模板结构和样式规则就更容易保持一致。

## 事件绑定

事件用 `v-on` 或简写 `@`.

```vue
<button @click="handleClick">提交</button>
```

模板里尽量只保留轻量调用，复杂逻辑放进脚本层。这样模板会更像视图描述，而不是半个业务层。

如果事件处理里要做多步动作，例如校验、请求、埋点、提示，通常就该先抽到脚本函数里，再由模板调用。这样模板可读，脚本也更容易测试和复用。

事件绑定最适合表达“用户动作入口”。模板负责接线，脚本负责动作链。逻辑一复杂，就别继续往模板里堆。

一个常见坏味道是模板里直接写很长的内联表达式，比如先改状态、再调接口、再埋点、再阻止默认行为。这种写法短期省事，长期会让模板变成半个控制器，维护成本很高。

## 条件与列表

```vue
<template>
  <div v-if="loading">加载中</div>
  <ul v-else>
    <li v-for="user in users" :key="user.id">{{ user.name }}</li>
  </ul>
</template>
```

`v-if` 适合互斥状态，`v-for` 适合重复结构。过滤和排序最好先在计算属性里处理，再交给模板渲染。

`v-if` 和 `v-for` 都很常见，但不要在同一个节点上滥用它们。复杂列表先在脚本里整理出最终数据，再交给模板循环，会比在模板里同时写过滤、排序和渲染清楚很多。

`v-if` 和 `v-for` 还要考虑生命周期。`v-if` 会创建和销毁节点，适合低频切换；`v-show` 只是切换显示，适合菜单、面板这类频繁开关。选择的关键不是“哪个更高级”，而是“这个区域隐藏时应不应该保留状态和 DOM”。

列表渲染的另一个重点是稳定 `key`。一旦 `key` 不稳定，输入框焦点、过渡动画、子组件内部状态都可能错位。模板语法本身不复杂，真正难的是你是否清楚每个节点在数据里的身份。

## 动态 class 和 style

Vue 对 class 和 style 的动态绑定支持很自然。

```vue
<template>
  <button :class="{ active: selected, disabled: isDisabled }">
    保存
  </button>
</template>
```

```vue
<template>
  <div :style="{ color, fontSize: size + 'px' }"></div>
</template>
```

这类写法适合状态驱动的视觉变化，但如果规则越来越复杂，最好先在脚本里整理出语义更清晰的状态值。

当 class 或 style 绑定开始依赖很多布尔值时，通常意味着业务状态可以再抽象一层，比如“选中”“禁用”“危险”“强调”。状态值越有语义，模板越不容易写成条件拼盘。

class 绑定适合有限状态组合，style 绑定适合少量动态值。不要在模板里拼很长的样式字符串，那会让样式来源分散，也不利于和设计系统对齐。

如果某一块视觉规则需要很多运行时判断，优先考虑抽成语义 class，而不是把所有值都硬塞进 `:style`。前者更利于和主题、设计 token、响应式规则结合，后者更适合少量动态尺寸或颜色值。

## 模板边界

| 写法 | 适合 | 不适合 |
| --- | --- | --- |
| 插值 | 文本展示 | 复杂计算 |
| 属性绑定 | 动态状态 | 动态拼接危险属性 |
| 事件绑定 | 用户交互 | 大段业务流程 |
| 条件渲染 | 简单分支 | 复杂状态机 |
| 列表渲染 | 结构重复 | 无稳定 `key` 的集合 |

模板最好的状态是“清楚但不拥挤”。它负责表达 UI，真正的规则应该放在脚本里。

如果一个模板已经开始频繁出现嵌套条件、字符串拼接和临时变量，通常就该把这些逻辑上移到 `computed`、方法或组合函数里。模板不是业务层，尽量保持它的可扫读性。

一个好模板通常满足三点：状态入口清楚、表达式短、结构层次和页面层次一致。它负责表达 UI，不负责承担所有业务推理。

从工程角度看，模板边界越清楚，后续做组件拆分、无障碍增强、测试和重构就越顺。因为你能很清楚地知道：模板负责展示关系，脚本负责数据来源和行为规则，样式负责视觉落地。
