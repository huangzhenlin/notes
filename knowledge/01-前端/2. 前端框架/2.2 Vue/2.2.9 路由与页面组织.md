## 页面入口

路由负责把 URL 映射到页面组件。它应该回答“去哪里”和“进入前需要什么条件”，不应该承载大量业务逻辑。

一个好的路由结构应该让 URL、页面组件、菜单和权限边界互相对应。用户刷新页面、复制链接、从外部进入时，页面都能根据 URL 恢复核心状态，而不是依赖上一个页面临时传参。

```text
/users
/users/:id
/settings/profile
/settings/security
```

路由是应用的信息架构，不只是组件加载表。路径命名、嵌套层级和参数设计会直接影响页面可分享性、权限控制和后续维护。

一个稳定的路由入口通常还能帮助团队对齐页面边界。什么算列表页、什么算详情页、什么算流程页、什么算设置页，都会通过路径结构被长期固化下来，所以路径设计最好一开始就尽量贴近业务认知，而不是只求能跳转。

## 动态路由

动态路由适合详情页、用户页、文章页这类路径参数变化的页面。

```ts
// /users/:id
```

路由参数应和数据加载逻辑直接对应。详情页通常从路由拿 `id`，再由页面或数据层读取实际数据。

动态参数来自 URL，类型上通常是字符串。即使业务 id 是数字，也要在页面入口做解析和校验，不要假设路由参数一定合法。

```ts
const route = useRoute();
const userId = computed(() => String(route.params.id));
```

如果参数非法，页面应该进入明确的错误或 404 状态，而不是带着 `undefined` 去请求接口。路由参数是外部输入，处理方式和表单输入一样需要边界校验。

对于可选参数和多个参数组合，也要尽量让语义稳定。例如 `/users/:id` 适合唯一标识详情页，而筛选、排序、分页更适合放 query。路径参数更像资源定位，query 更像视图状态，分工清楚后页面恢复会容易很多。

## 嵌套路由

嵌套路由适合父子页面结构。

```ts
const routes = [
  {
    path: "/settings",
    component: SettingsLayout,
    children: [
      { path: "profile", component: ProfileSettings },
    ],
  },
];
```

父路由负责布局和导航，子路由负责具体内容，页面层级会更清楚。

嵌套路由适合共享布局和局部导航，例如设置页、后台详情页、多标签工作台。父组件通常放侧边栏、面包屑、公共请求或权限上下文，子组件只处理具体页面内容。

```vue
<template>
  <SettingsSidebar />
  <RouterView />
</template>
```

如果父子页面没有共享布局，只是路径看起来相似，不一定要强行嵌套。路由嵌套应该服务于 UI 层级和数据上下文，而不是只服务于 URL 字符串。

嵌套路由还要控制层级深度。路径可以很长，但页面层级不一定要一直向下嵌。嵌套太深时，布局、权限、缓存和调试都会变复杂，很多时候两到三层已经足够表达页面结构。

## 懒加载

路由组件可以按需加载，减少首屏体积。

```ts
const UserPage = () => import("./pages/UserPage.vue");
```

后台系统、报表页、图表页、富文本编辑器都适合拆出去。懒加载不是越多越好，但页面多、依赖重时收益明显。

懒加载的收益在于减少首屏 bundle，但它会带来异步加载状态。页面切换时要考虑 loading、错误重试和预加载策略。

```ts
const ReportPage = () => import("./pages/report/ReportPage.vue");
```

对于用户很可能马上进入的页面，可以在鼠标悬停菜单、登录后空闲时或首屏完成后预加载。懒加载和预加载结合，才能在首屏体积和页面切换体验之间取得平衡。

懒加载还要看页面依赖特征。图表、富文本、地图、可视化编辑器这类重依赖页面，拆出去收益很明显；而登录页、首页、主导航容器这类高频入口页面，通常不值得过度拆分。

## 路由守卫

路由守卫适合登录校验、权限判断、标题和埋点。

```ts
router.beforeEach((to) => {
  if (to.meta.requiresAuth && !isLoggedIn()) {
    return "/login";
  }
});
```

守卫适合做跳转决策，不适合塞大量业务逻辑。复杂权限和数据预取最好拆到服务或页面层。

全局守卫适合处理登录态、基础权限和通用埋点；路由独享守卫适合页面特定条件；组件内逻辑适合依赖页面数据后的判断。不要把所有规则都塞进 `beforeEach`，否则路由文件会变成业务规则中心。

```ts
router.beforeEach((to) => {
  if (!to.meta.requiresAuth) return true;

  if (!authStore.loggedIn) {
    return {
      path: "/login",
      query: { redirect: to.fullPath },
    };
  }

  return true;
});
```

前端守卫只负责体验和入口控制，真正权限仍然要由服务端接口判断。隐藏页面入口不能替代接口鉴权。

守卫里最好只保留少量、稳定、全局性的规则。像“未登录跳登录”“根据 meta 设置标题”“记录页面进入埋点”都比较适合；而需要依赖接口结果、页面上下文或复杂表单状态的判断，通常更适合留在页面层或数据层处理。

## `meta`

`meta` 可以承载页面级元信息。

```ts
{
  path: "/dashboard",
  meta: { title: "仪表盘", requiresAuth: true }
}
```

它适合放标题、权限、缓存策略，不适合放页面业务数据。

`meta` 字段要保持小而稳定。常见内容包括 `title`、`requiresAuth`、`roles`、`keepAlive`、`layout`。如果把接口参数、页面表单默认值、业务开关都塞进 `meta`，路由配置会越来越难维护。

```ts
{
  path: "/admin",
  component: AdminPage,
  meta: {
    title: "管理后台",
    requiresAuth: true,
    roles: ["admin"],
  },
}
```

`meta` 更像页面级声明，不是页面数据仓库。动态数据仍然应该来自接口、store 或页面自身逻辑。

如果团队已经约定了 `meta` 字段集合，例如 `title`、`requiresAuth`、`keepAlive`、`layout`、`roles`，最好继续保持收敛。字段越稳定，守卫、布局和页面壳层逻辑就越容易共享。

## 目录组织

页面目录最好和路由结构接近。

```text
pages/
  users/
    index.vue
    detail.vue
  settings/
    profile.vue
    security.vue
```

URL、页面文件、菜单入口如果能对应起来，新成员会更容易定位代码。

目录组织还要考虑复用层级。页面专属组件可以放在页面目录下，共享组件放到公共组件目录。这样既不会把所有组件都堆进全局 `components`，也不会让复用组件散落在页面里。

```text
pages/
  users/
    UserListPage.vue
    UserDetailPage.vue
    components/
      UserFilter.vue
      UserTable.vue
components/
  AppButton.vue
  AppDialog.vue
```

页面目录表达业务结构，公共组件目录表达跨页面复用。边界清楚后，重构和查找都会轻很多。

目录组织还可以顺手表达“页面专属逻辑放哪”。例如当前页面专用的表格、筛选器、弹窗、hooks 和样式，都可以优先放在页面目录旁边；只有真正跨页面复用后，再提升到公共层。这样能减少过早全局化。

## 状态恢复

可刷新、可分享、可从外部进入的页面，应该能通过路由参数恢复核心状态。

```text
适合放路由：id、分页、筛选、搜索词
不适合放路由：完整对象、临时草稿、弹窗内部状态
```

路由状态越清楚，页面越不依赖“必须从某个上游点进来”。

列表页的筛选、分页和排序通常适合放进 query，因为它们影响当前页面数据视图，并且用户可能希望复制链接给别人。

```ts
router.replace({
  query: {
    keyword: keyword.value || undefined,
    page: String(page.value),
  },
});
```

不要把完整对象、敏感信息和大量临时草稿放进 URL。URL 会进入浏览器历史、日志、Referer 和截图，适合表达可分享的轻量状态，不适合保存私密或复杂数据。

路由状态和组件状态要避免双向循环：watch 路由更新表单，watch 表单又更新路由，如果没有去重和节流，很容易造成重复导航。更稳的做法是明确一个方向：初始化从路由读，用户操作后集中写回路由。

真正稳定的页面恢复，不是把所有状态都塞进 URL，而是只恢复“用户重新进入时最在意的那部分”。比如当前筛选条件、分页位置、详情 id、当前 tab 往往值得保留；一次性弹窗、局部 hover、临时输入中间态就没必要强行路由化。
