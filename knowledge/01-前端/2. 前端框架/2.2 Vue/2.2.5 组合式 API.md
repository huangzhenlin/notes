## 逻辑组织

组合式 API 的重点是按能力组织逻辑，而不是按选项散开。它让相似的状态、派生值、副作用和复用逻辑放在一起。

它真正改变的是代码组织方式。以前同一件事可能散在 `data`、`computed`、`methods`、`watch` 里，组合式 API 则让相关逻辑可以按“业务能力”聚在一起，比如搜索、表单、权限、主题、列表加载。

```ts
const displayName = computed(() => `${user.value.firstName} ${user.value.lastName}`);
```

组合式 API 的组织单位通常是“一个能力闭环”：它包含状态、派生值、方法、副作用和清理。比如搜索能力可以包含关键词、结果、加载状态、请求方法和取消逻辑；表单能力可以包含字段值、校验、提交和错误状态。

```ts
function useSearch() {
  const keyword = ref("");
  const loading = ref(false);
  const results = ref<Result[]>([]);

  async function search() {
    loading.value = true;
    try {
      results.value = await fetchResults(keyword.value);
    } finally {
      loading.value = false;
    }
  }

  return { keyword, loading, results, search };
}
```

这样调用方看到返回值，就能理解这个逻辑单元提供了什么能力，而不需要翻组件内部的多个选项。

## `setup`

`setup` 是组合式 API 的入口，适合组织初始化逻辑和响应式状态。

`setup` 里写的内容应该尽量围绕“初始化什么、依赖什么、返回什么”展开，而不是把所有生命周期、请求和计算都堆在一起。它越像入口函数，后续逻辑越容易拆出去。

```ts
onMounted(() => {
  loadData();
});
```

它让“声明输入、组织状态、注册副作用、返回视图所需内容”变成同一条线。

在 `<script setup>` 中，顶层变量和函数可以直接暴露给模板，写法更简洁，但边界仍然要清楚。不要因为没有显式 `return`，就把所有逻辑都堆在文件顶层。

```vue
<script setup lang="ts">
const count = ref(0);
const doubled = computed(() => count.value * 2);

function increment() {
  count.value += 1;
}
</script>

<template>
  <button @click="increment">{{ doubled }}</button>
</template>
```

`setup` 执行时组件实例还没有完成挂载，因此需要访问 DOM 的逻辑要放到 `onMounted`，依赖服务端渲染的项目还要注意浏览器对象是否存在。

## 复用逻辑

组合式 API 很适合抽离成可复用函数。

```ts
function useToggle(initial = false) {
  const value = ref(initial);
  const toggle = () => (value.value = !value.value);
  return { value, toggle };
}
```

这类函数通常叫组合函数，命名习惯上以 `useXxx` 开头。它们适合封装状态、请求、表单、权限、主题等逻辑单元。

组合函数最好的形态是“输入明确、输出明确、可单独复用”。如果它内部还依赖很多外部隐式状态，后面就会变得很难测试，也很难在别的组件里复用。

组合函数可以接收普通值、ref、getter 或配置对象。为了让调用方更灵活，可以用 `toValue` 这类工具统一读取输入，但不要让 API 过度聪明到看不出依赖。

```ts
function useUser(userId: Ref<string>) {
  const user = ref<User | null>(null);

  watch(
    userId,
    async (id) => {
      user.value = await fetchUser(id);
    },
    { immediate: true },
  );

  return { user };
}
```

这里 `userId` 是显式输入，组合函数内部根据它加载用户。比起在函数里直接读取路由参数，这种写法更容易测试，也更容易在不同组件里复用。

## 生命周期

生命周期钩子可以和逻辑放在一起组织。

```ts
onMounted(() => {
  loadData();
});
```

这样相关逻辑更集中，不需要在多个选项之间来回跳。

生命周期钩子和组合函数配合起来，往往能把“初始化、订阅、清理”这三件事围在一起写清楚。这样后面看代码时，不需要在文件里四处找同一个功能的不同部分。

组合函数内部也可以注册生命周期。调用组件使用这个组合函数时，生命周期会绑定到当前组件实例。

```ts
function useEventListener(target: Window, event: string, handler: EventListener) {
  onMounted(() => {
    target.addEventListener(event, handler);
  });

  onUnmounted(() => {
    target.removeEventListener(event, handler);
  });
}
```

这类封装特别适合窗口事件、媒体查询、可见性监听、WebSocket 连接等需要清理的逻辑。创建什么，就在同一个组合函数里清理什么，调用方才不会遗漏资源释放。

## `props` 与 `emits`

组件输入输出要显式声明。

```ts
const props = defineProps<{ value: string }>();
const emit = defineEmits<{ (e: "update:value", value: string): void }>();
```

越复杂的组件，越需要把“输入值”“变更事件”“完成事件”“错误状态”分清楚，而不是只靠一个模糊事件名撑住所有变化。

这种显式边界对组件复用特别重要。父组件看见 `props` 就知道传什么，看见 `emit` 就知道能收到什么，不需要翻完整个实现才能确认交互协议。

`defineProps` 得到的 props 是只读的，子组件不应该直接修改。需要变更时，通过 `emit` 通知父组件，或者使用 `v-model` 约定。

```ts
const props = defineProps<{ modelValue: string }>();
const emit = defineEmits<{ (e: "update:modelValue", value: string): void }>();

function update(value: string) {
  emit("update:modelValue", value);
}
```

复杂组件要把事件语义拆清楚：`update:modelValue` 表示值变化，`submit` 表示提交意图，`success` 表示提交成功，`error` 表示失败结果。不要用一个 `change` 承担所有业务含义。

## 使用边界

| 逻辑类型 | 适合位置 |
| --- | --- |
| 可复用状态 | 组合函数 |
| 页面初始化 | `setup` / `onMounted` |
| DOM 交互 | `onMounted` + `ref` |
| 服务端请求 | 组合函数或数据层 |
| 纯派生值 | `computed` |

组合式 API 的价值是让同类逻辑彼此靠近。真正需要的是“更好组织”，不是“把所有东西塞进 setup”。

`watch` 和 `computed` 的边界也要明确。`computed` 表达纯派生值，有缓存且不应该有副作用；`watch` 用来观察变化并执行副作用，例如发请求、写存储、同步第三方实例。

```ts
const fullName = computed(() => `${firstName.value} ${lastName.value}`);

watch(locale, (nextLocale) => {
  localStorage.setItem("locale", nextLocale);
});
```

如果一个 `watch` 只是为了把 A 算成 B 再存起来，多半应该改成 `computed`。如果一个 `computed` 里开始写请求或修改状态，就说明它承担了副作用。

## 何时拆出

如果某段逻辑在多个组件里复用，而且能独立测试、输入输出清晰，就适合抽成组合函数。

| 适合抽出 | 不太适合抽出 |
| --- | --- |
| 跨组件复用 | 只在单组件使用 |
| 包含副作用清理 | 纯模板拼装 |
| 输入输出明确 | 深度耦合模板 |
| 与 UI 无关 | 强依赖当前模板结构 |

组合式 API 是 Vue 的组织方式，不是模板的替代品。模板依然负责展示，组合函数负责逻辑。

如果组合式 API 用得太激进，把一切逻辑都抽成超长 `useXxx`，代码也会重新变得难读。真正好的组合式写法，仍然是让一个逻辑单元清楚、短小、可复用，而不是无限抽象。

拆组合函数时，不要只按“代码行数”拆，而要按“业务能力”拆。比如 `useUserList`、`useUserSearch`、`useSelection` 可以分别代表列表数据、搜索条件、选中状态；但 `usePageEverything` 这种函数只是把组件复杂度搬到另一个文件。

一个好的组合函数通常满足四点：输入参数少而明确，返回值能直接用于模板，内部副作用有清理，名字能说明业务能力。它不是 Vue 里的工具函数合集，而是组件逻辑的可复用单元。
