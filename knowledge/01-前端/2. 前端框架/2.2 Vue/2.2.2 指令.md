## 指令作用

Vue 指令是以 `v-` 开头的特殊属性，用来在模板里描述条件、循环、绑定和行为。

```vue
<div v-show="visible">内容</div>
```

指令的价值在于把常见 UI 逻辑写成声明式语法，而不是手动拼 DOM。模板负责描述结果，逻辑负责决定结果。

指令的作用是把常见 DOM 控制语义写进模板语言里，让开发者不必为每个节点手动写命令式代码。

学指令时不要只记名字，更要理解它们是在帮你表达哪类界面关系。`v-if` 表达分支，`v-for` 表达集合，`v-model` 表达输入同步，`v-bind` 表达属性依赖。把语义抓住以后，模板就不会写成“哪儿能跑就往哪儿塞”。

## 条件显示

`v-if` 和 `v-show` 是最常见的一对。

这两个指令的选择，关键不只是“谁快”，而是“谁更符合生命周期”。隐藏时需要释放资源、停止订阅、销毁实例，常常更适合 `v-if`；只是暂时收起、以后马上再显示，通常更适合 `v-show`。

```vue
<p v-if="error">{{ error }}</p>
<p v-show="menuOpen">菜单</p>
```

`v-if` 会真正创建和销毁节点，适合低频切换；`v-show` 只是切换 `display`，适合高频显隐。

| 指令 | 行为 | 适合场景 |
| --- | --- | --- |
| `v-if` | 创建 / 销毁节点 | 权限、状态分支 |
| `v-show` | 切换 CSS 显隐 | 菜单、面板、频繁切换 |

除了性能差异，还要关注副作用差异。`v-if` 对应的子组件会重新走挂载和卸载流程，里面的请求、订阅、动画、表单状态都可能重建；`v-show` 则通常会保留这些内部状态。所以选哪一个，本质上是在选“这个区域隐藏时要不要继续活着”。

## 列表渲染

`v-for` 用于渲染集合，`key` 应稳定且唯一。

`v-for` 最好的输入是已经整理好的最终集合，而不是一边循环一边在模板里做大量判断。先在脚本里过滤、排序、分组，模板会更清楚。

```vue
<li v-for="item in items" :key="item.id">
  {{ item.name }}
</li>
```

不要用数组索引当 `key` 去处理会重排的列表，否则输入框、动画和内部状态都可能错位。

如果列表项本身已经足够复杂，通常还要继续把它抽成子组件。这样 `v-for` 只负责渲染集合结构，列表项组件负责自己的展示和交互，模板层次会清楚很多。

## 属性绑定

`v-bind` 常用于动态 class、style 和布尔属性。

`v-bind` 表达的是“这个属性跟随响应式状态变化”，所以它在 aria、disabled、readonly、hidden 这类属性上尤其重要。

```vue
<button :disabled="submitting" :class="{ active: selected }">保存</button>
```

对象语法和数组语法都很常见，适合状态驱动的样式切换。

`v-bind` 还有一个很重要的用途，是把状态同步到无障碍属性和组件输入上。像 `aria-expanded`、`aria-selected`、`tabindex`、`disabled` 这些属性一旦和状态脱节，组件看起来能用，实际体验却会很割裂。

## 事件处理

事件绑定可以直接接收参数，也可以搭配修饰符。

```vue
<button @click="handleClick(item.id)">选择</button>
<button @click.stop="select(item)">选择</button>
```

`.stop`、`.prevent`、`.once` 这类修饰符让常见行为更简洁，但不要用它们掩盖结构问题。

修饰符是语法糖，不是业务建模工具。模板里如果到处都是 `.stop`、`.prevent`，通常说明事件边界还可以再整理。

事件修饰符更适合解决浏览器层面的默认行为和冒泡问题，而不是替代组件通信设计。真正的组件边界还是要靠清晰的输入、输出和职责划分来保证。

## 双向绑定

`v-model` 是表单和受控状态的核心。

```vue
<input v-model="keyword" />
```

它本质上是 `:value` 加 `@input` 的语法糖。多模型绑定时，要明确每个模型对应的业务含义，而不是把它当省代码工具。

`v-model` 的重点不是“双向”，而是“父持有值，子发出更新”。这个协议统一后，表单和受控组件会更容易设计。

```vue
<RangePicker v-model:start="start" v-model:end="end" />
```

在业务组件里使用 `v-model` 时，最好先想清楚这个值是否真的需要由父组件掌控。输入框、开关、选择器很适合；但如果一个组件内部状态只服务自己，不一定非要暴露成双向绑定接口。

## 自定义指令

自定义指令适合处理直接操作 DOM 的场景，比如聚焦、权限显隐和点击外部关闭。

```ts
const focus = {
  mounted(el: HTMLInputElement) {
    el.focus();
  },
};
```

如果逻辑需要复杂状态、跨组件通信或较多副作用，更适合做成组件或组合函数。

自定义指令适合单点增强，比如聚焦、点击外部关闭、权限显隐。它们直接作用于 DOM，所以应该保持职责单一。

写自定义指令时还要考虑生命周期清理。事件监听、观察器、定时器如果只在挂载时添加、不在卸载时移除，后面很容易造成泄漏或重复触发。自定义指令看起来小，但它和原生 DOM 直接打交道，边界反而更要收紧。

## 指令选择

| 场景 | 推荐 |
| --- | --- |
| 条件显示 | `v-if` / `v-show` |
| 集合渲染 | `v-for` |
| 表单输入 | `v-model` |
| 样式切换 | `:class` / `:style` |
| 直接 DOM 操作 | 自定义指令 |

指令不是“模板里的万能 API”，而是把常见交互写得更顺手的一层语法。

判断是否用指令，可以先看它是不是只解决一个小的 DOM 问题。只要开始涉及复杂状态、跨组件通信或多步副作用，就更适合组件或组合函数。

一个稳妥的思路是：先用指令表达模板层关系，再用组件和组合函数承接复杂逻辑。这样模板会保持声明式优势，脚本层也不会被拆得支离破碎。
