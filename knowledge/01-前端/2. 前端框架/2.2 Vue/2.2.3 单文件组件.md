## 组件边界

单文件组件（SFC）把模板、逻辑和样式放在同一个 `.vue` 文件里。它的目标不是把一切塞进一个文件，而是让一个 UI 单元的结构更完整。

SFC 的重点是“按组件为单位组织理解成本”。当模板、脚本和样式围绕同一个组件聚在一起时，读代码的人不需要在多个目录之间跳转，也更容易理解这个 UI 单元的整体边界。

```vue
<script setup lang="ts">
const props = defineProps<{ title: string }>();
</script>

<template>
  <h2>{{ props.title }}</h2>
</template>
```

SFC 适合组件内部逻辑清楚、视图结构紧密的场景。一个文件对应一个组件，读起来通常比模板、脚本、样式散在多个地方更顺。

但 SFC 并不意味着什么都往单个文件里堆。它更适合“一个组件的一组相关内容”，而不是把页面级流程、多个子模块和大量业务逻辑一起塞进一个巨文件。

判断一个 SFC 是否健康，可以看三块内容是否围绕同一个 UI 单元：模板描述这个单元的结构，脚本管理这个单元的状态和行为，样式服务这个单元的视觉。如果三者已经分别对应多个业务模块，这个文件就该拆。

## `script setup`

`<script setup>` 是 Vue 3 里最常用的写法之一，能让组件代码更直接。

```vue
<script setup lang="ts">
const props = defineProps<{ title: string }>();
</script>
```

它的优点是少样板、少样板、少样板，编译后也更接近“声明输入、组织状态、输出模板”。

`script setup` 让 `props`、`emit`、`ref`、`computed` 和生命周期调用更贴近顶部组织方式，代码从上到下读起来更像“先声明数据，再声明行为，再交给模板展示”。

`script setup` 是编译期语法糖，顶层声明会暴露给模板，但不等于所有变量都应该放在顶层。推荐顺序通常是：导入依赖、声明 props/emits、声明状态、声明计算属性、声明方法、注册生命周期。顺序稳定后，团队阅读成本会低很多。

```vue
<script setup lang="ts">
const props = defineProps<{ userId: string }>();
const loading = ref(false);
const user = ref<User | null>(null);

const displayName = computed(() => user.value?.name ?? "未知用户");

async function loadUser() {
  loading.value = true;
  user.value = await fetchUser(props.userId);
  loading.value = false;
}

onMounted(loadUser);
</script>
```

## `defineProps` 与 `defineEmits`

组件输入输出最好显式声明。

```vue
<script setup lang="ts">
const props = defineProps<{ value: string }>();
const emit = defineEmits<{ (e: "change", value: string): void }>();
</script>
```

`props` 表示外部输入，`emits` 表示组件对外发出的事件。边界越清楚，组件越容易复用。

如果一个组件既接收大量 props，又触发很多事件，通常说明它已经开始承担过多责任。这个时候要么拆分职责，要么把一部分逻辑上移给父组件。

`defineProps` 和 `defineEmits` 不只是类型声明，也是组件契约。props 越像外部输入，emits 越像业务事件，组件越容易被别人正确使用。

```ts
const emit = defineEmits<{
  (e: "submit", value: FormValue): void;
  (e: "cancel"): void;
}>();
```

如果事件名只是 `change`、`click`、`callback`，调用方往往还要翻源码确认含义。组件越通用，输入输出越要清楚。

## `scoped`

`scoped` 可以把样式限制在当前组件内。

```vue
<style scoped>
.title {
  color: #222;
}
</style>
```

它适合局部组件，但不是绝对隔离。遇到第三方组件、深层子元素或主题化需求时，还是要谨慎看样式穿透和作用域边界。

`scoped` 更适合业务页面里的局部样式收口，而不是复杂的设计系统。需要跨组件一致性的主题变量、全局基础样式和布局规范，通常还是要单独设计。

`scoped` 的实现通常依赖给元素追加作用域属性选择器，因此它能减少样式串扰，但不是完全隔离。子组件根节点、深度选择器、第三方组件内部结构都可能让样式边界变复杂。

```vue
<style scoped>
:deep(.third-party-button) {
  border-radius: 8px;
}
</style>
```

深度选择器要少用。它意味着当前组件开始依赖子组件或第三方组件内部结构，后续升级时更容易失效。

## CSS Modules

CSS Modules 通过局部作用域减少类名冲突。

```vue
<script setup lang="ts">
import styles from "./Card.module.css";
</script>

<template>
  <div :class="styles.card">内容</div>
</template>
```

它更偏工程化，适合大型项目和组件库；`scoped` 更轻，适合普通业务组件。

两者的选择本质上是在平衡“局部隔离”和“样式组织成本”。项目越大，越需要明确哪些样式是组件私有的，哪些样式是全局规范，哪些样式应该靠设计变量统一管理。

CSS Modules 更适合需要显式类名映射、跨文件组合和组件库封装的场景。它让类名成为脚本里可引用的对象，类型和编辑器支持也更容易做起来。

```vue
<template>
  <section :class="$style.card">
    内容
  </section>
</template>

<style module>
.card {
  padding: 16px;
}
</style>
```

普通业务组件用 `scoped` 已经足够，组件库或大型工程再考虑 CSS Modules、原子 CSS、设计 token 等更系统的方案。

## 组件拆分

当一个 SFC 同时出现很多分支、很多请求和很多样式块时，就该考虑拆分。

| 信号 | 说明 |
| --- | --- |
| `template` 很长 | 视图职责过重 |
| `script` 很复杂 | 逻辑需要下沉 |
| `style` 很分散 | 结构需要分层 |
| 子区域可独立命名 | 适合拆成子组件 |

SFC 的目标是把一个 UI 单元写完整，而不是把所有事情写进一个文件。它和 [[2.2.1 模板语法|模板语法]]、[[2.2.2 指令|指令]] 是天然一组。

如果某个 SFC 的 `template` 已经明显比同层组件更长，通常就说明它开始承担过多展示职责了。最稳的拆分方式往往是先拆出可复用子组件，再考虑把逻辑提到组合函数里。

拆分 SFC 时可以按两个方向走：视图重复或区域独立时拆组件，逻辑重复或副作用成组时拆组合函数。不要把模板结构拆进组合函数，也不要把纯逻辑硬塞进子组件。

```text
长模板 -> 拆展示组件
重复请求逻辑 -> 拆组合函数
复杂样式块 -> 拆子组件或样式层
多个业务流程 -> 拆页面区域
```

SFC 的理想大小不是固定行数，而是“一个文件讲清一个组件”。读完文件后能说清这个组件的输入、输出、状态、样式边界，就说明它还在健康范围内。
