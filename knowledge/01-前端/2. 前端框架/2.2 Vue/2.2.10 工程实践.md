## 工程分层

Vue 项目里最重要的工程实践，是把组件、组合函数、API 层、页面层和状态层分清楚。

| 层级 | 责任 |
| --- | --- |
| 组件 | 视图和局部交互 |
| 组合函数 | 可复用逻辑 |
| API 层 | 请求与数据转换 |
| 页面 | 组合、路由、布局 |
| Store | 跨页面共享状态 |

分层不是为了显得复杂，而是为了让变化有地方去。

分层的意义在于把变化快的东西和变化慢的东西拆开。UI 和交互变化快，接口和数据模型相对慢；拆开后，需求改动通常只会影响一层。

这也是为什么工程分层本质上不是目录问题，而是职责问题。哪怕目录暂时没有拆得很细，只要组件不直接写请求细节、页面不直接承担全局状态、组合函数不偷偷改路由，整体结构就会比“目录很漂亮但职责混乱”稳得多。

## 状态归属

状态先按作用域归属。

```text
只影响一个组件 -> 组件本地
影响一个页面多个区域 -> 页面共享
跨页面、跨路由 -> store
```

很多工程问题不是库不好用，而是状态放得太高或太散。

状态归属要和 Vue 的组合式写法一起看。能留在组件里的就别进 store，能由页面组合的就别跨路由共享。全局状态应该少而稳定。

一个好用的判断标准是：谁最关心这个状态，谁就应该优先拥有它。输入框值、弹窗开关、局部筛选项通常离组件更近；页面查询条件、局部分页和组合后的展示结果更靠近页面；登录态、主题、权限、用户偏好才更接近全局。

## 请求封装

接口请求建议统一封装，处理 baseURL、错误、鉴权、超时和重试。

```ts
async function request<T>(url: string): Promise<T> {
  const response = await fetch(url);
  return response.json();
}
```

组件里不要散落请求细节。页面应该关心业务含义，而不是每个接口怎么拼 header。

请求层最好统一处理 baseURL、错误、鉴权、超时、重试和返回值归一化。页面只关心“拿到什么数据、失败怎么提示”，不关心具体请求实现。

如果项目开始出现“同一个接口在三个页面各写一遍”“每个页面都要自己处理登录过期”“错误提示风格不一致”这些现象，通常就说明请求层还没有真正收拢起来。请求封装的价值不在于包一层函数，而在于把重复的网络规则沉淀下来。

## 路由组织

路由、页面目录和导航入口最好保持认知一致。

```text
pages/
  users/
  settings/
  reports/
```

当目录结构、URL 和菜单能互相对应时，维护成本会小很多。

路由和页面目录最好按业务域组织，而不是按技术能力组织。用户、订单、设置、报表这种域通常比“components1、components2”更容易维护。

工程里一旦出现“找页面要靠全局搜索路径字符串”，通常说明路由组织已经开始失衡。让目录、菜单、路由命名和页面职责尽量同频，后续定位问题、接手维护和做权限治理都会轻松很多。

## 类型约束

Vue 3 + TypeScript 项目里，props、emits、router meta、store 和接口返回值都应该尽量有类型。

```ts
type User = { id: string; name: string };
```

类型不是为了炫技，而是为了让页面、接口和组件边界更明确。

Vue 3 + TypeScript 里，props、emits、route meta、store 和接口返回值这几个点最值得优先补类型。它们是边界层，越早补越能减少后续返工。

从收益角度看，最该优先补类型的不是实现细节，而是边界输入输出。因为一旦边界稳定，IDE 提示、重构、联调和新人接手都会顺很多；反过来，如果边界全是 `any`，项目规模一大就很难靠经验兜住。

## 样式策略

样式可以分成局部样式、主题变量和设计 token。

```text
局部样式：组件内部
主题变量：全局统一
设计 token：多组件共享
```

不要把所有样式都塞进 SFC，也不要一上来就全部全局化。不同层级要有不同职责。

样式层次最好和业务层次一致：组件内部样式只影响当前组件，主题变量影响整个应用，token 影响多个组件和页面。

样式实践真正困难的地方，不是选 `scoped` 还是 CSS Modules，而是能不能稳定表达“什么属于组件、什么属于页面、什么属于品牌主题”。只要这层边界清楚，具体技术方案通常都能落得稳。

## 质量门禁

常见质量门禁包括 lint、typecheck、测试和构建。

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

如果一个页面经常返工，优先检查状态归属、组件边界和路由组织，而不是先怀疑某个 API 不好用。

工程实践里也要看可维护性信号，比如单文件是否越来越大、请求逻辑是否分散、store 是否膨胀、路由是否难找页面。它们往往比“代码能不能跑”更能说明项目是否健康。

质量门禁最好进入日常流程，而不是只在发版前想起来跑一次。提交前的本地检查、合并前的 CI 校验、上线前的构建验证，这三层一旦稳定，很多“明明早就能发现”的问题就不会拖到最后一刻。

## 维护判断

| 信号 | 可能问题 |
| --- | --- |
| 页面文件越来越大 | 组件和组合函数没拆清 |
| 请求散在各处 | API 层缺失 |
| store 过度膨胀 | 局部状态被全局化 |
| 路由难找页面 | 目录和路由不一致 |
| 样式互相覆盖 | 样式分层不清 |

工程实践的目标不是“统一到死”，而是让项目变大以后仍然知道每段代码应该放在哪里。

日常工程约定最好落成 lint、typecheck、测试和构建，而不是只靠口头习惯。只要分层、类型、路由和请求层稳定，Vue 项目规模变大后仍然能保持可维护。

真正好的工程实践，通常不会让人时刻意识到它的存在。它更像是一个稳定的默认轨道：写组件知道放哪，写接口知道放哪，写状态知道放哪，出问题也知道先从哪一层排查。这种“可预期”本身就是工程价值。
