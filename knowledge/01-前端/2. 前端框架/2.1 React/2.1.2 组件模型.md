## 组件边界

React 的基本单位是组件。组件本质上是一个把输入转换成 UI 的函数，输入通常来自 `props`、`children`、上下文和本地状态，输出则是可渲染的界面描述。

```tsx
function Button({ label, disabled }: { label: string; disabled?: boolean }) {
  return <button disabled={disabled}>{label}</button>;
}
```

组件模型的重点不是“把页面切成很多文件”，而是把一段 UI 里变化原因不同的部分拆开，让每一层只负责自己该负责的事。

组件边界通常来自变化原因，而不是视觉区域。两个东西长在同一个卡片里，但一个随用户输入变化、一个随接口数据变化、一个只是静态装饰，它们就可能需要不同边界。反过来，视觉上分开的区域如果共享同一份交互状态，也可能应该由同一个容器协调。

```tsx
function UserPanel({ userId }: { userId: string }) {
  return (
    <section>
      <UserHeader userId={userId} />
      <UserActions userId={userId} />
      <UserActivity userId={userId} />
    </section>
  );
}
```

这里三个子组件都围绕 `userId` 工作，但它们的数据加载、交互和刷新频率不同，拆开后每个组件可以独立演进。组件拆分的目标是降低变化互相影响的概率，而不是追求文件数量。

## 输入输出

组件的最重要原则之一是输入清晰、输出确定。

```tsx
type CardProps = {
  title: string;
  children: React.ReactNode;
};

function Card({ title, children }: CardProps) {
  return (
    <section className="card">
      <h3>{title}</h3>
      {children}
    </section>
  );
}
```

只要输入不变，输出就应该尽量稳定。这样组件才容易复用、测试和排查问题。

“输出确定”并不代表组件不能有状态，而是同一轮渲染里不要偷偷依赖外部可变值。比如在渲染时直接读取 `Date.now()`、`Math.random()`、全局变量，都会让 UI 难以复现。

```tsx
function BadBadge() {
  return <span>{Math.random()}</span>;
}
```

如果确实需要生成一次性值，应把它放到状态初始化或稳定引用里。

```tsx
function Badge() {
  const [id] = React.useState(() => crypto.randomUUID());
  return <span>{id}</span>;
}
```

组件越接近纯函数，越容易测试。给定 props，断言输出；触发事件，断言回调或状态变化。复杂组件也可以通过拆分，把纯展示层和有副作用的容器层分开。

## 状态归属

决定一个值放 `props` 还是 `state`，通常看它是谁拥有、谁修改、谁负责展示。

```tsx
function Counter() {
  const [count, setCount] = React.useState(0);

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

如果一个值会随着用户交互或异步结果变化，而且变化后需要重新渲染，就更适合放进状态。纯展示数据则尽量通过 props 下发。

状态归属的常见判断是“谁需要读，谁负责改”。如果只有一个输入框需要值，把状态放在输入组件内部；如果兄弟组件都需要读同一个值，把状态提升到最近公共父组件；如果跨很多页面共享，再考虑 Context 或状态管理库。

```tsx
function FilterableList() {
  const [keyword, setKeyword] = React.useState("");

  return (
    <>
      <SearchInput value={keyword} onChange={setKeyword} />
      <ResultList keyword={keyword} />
    </>
  );
}
```

不要过早把所有状态放到全局。全局状态看似方便，实际会扩大更新范围，也会让组件复用变难。局部状态、上提状态、上下文、外部 store 应该按共享范围逐级选择。

## 组合优先

React 更强调组合而不是继承。组合的意思是把 UI 拆成小部件，再通过 props 和 `children` 拼起来。

```tsx
function Page() {
  return (
    <Layout>
      <UserCard />
    </Layout>
  );
}
```

这种方式让布局、容器和内容分离得更明显。继承式复用在 UI 里往往不如组合自然，因为界面变化通常不是“父子类关系”，而是“结构拼装关系”。

组合可以通过 `children`、具名插槽式 props、渲染函数和组件参数表达不同层次的可定制性。简单容器优先用 `children`，需要多个区域时可以用具名 props。

```tsx
function Dialog({
  title,
  footer,
  children,
}: {
  title: React.ReactNode;
  footer: React.ReactNode;
  children: React.ReactNode;
}) {
  return (
    <section role="dialog">
      <header>{title}</header>
      <main>{children}</main>
      <footer>{footer}</footer>
    </section>
  );
}
```

不要把所有差异都做成布尔 props。`primary`、`danger`、`withIcon`、`showFooter`、`compact` 一路叠加后，组件会变成内部条件迷宫。结构差异很大时，用组合比继续加开关更健康。

## 纯渲染

组件渲染阶段最好保持纯净，也就是不要在渲染时做副作用。

```tsx
function Greeting({ name }: { name: string }) {
  return <p>Hello, {name}</p>;
}
```

渲染阶段的职责只是根据当前输入计算 JSX。像修改全局变量、发请求、改 `document.title` 这类动作，更适合放到事件处理器或副作用里。

纯渲染还要求不要在渲染过程中修改传入对象。props 应该被看作只读输入，子组件不能为了方便直接改父组件传来的数组或对象。

```tsx
function BadList({ items }: { items: string[] }) {
  items.sort();
  return <ul>{items.map((item) => <li key={item}>{item}</li>)}</ul>;
}
```

这会修改父组件持有的数据。更稳妥的方式是创建副本。

```tsx
function List({ items }: { items: string[] }) {
  const sortedItems = [...items].sort();
  return <ul>{sortedItems.map((item) => <li key={item}>{item}</li>)}</ul>;
}
```

这种写法让数据流保持单向，也避免多个组件共享同一个引用时互相影响。

## 组合方式

常见组合手段有 `children`、条件分支、列表和插槽式参数。

| 方式 | 适合场景 |
| --- | --- |
| `children` | 布局、卡片、弹窗 |
| 条件渲染 | 视图状态切换 |
| 列表渲染 | 重复结构 |
| 传入组件 | 可定制结构 |

组件边界划分清楚后，页面会更像“一个个稳定积木的组合”，而不是“一大坨逻辑混在一起”。

传入组件适合复杂定制，但要控制粒度。比如表格列渲染、列表空状态、弹窗底部操作区都适合交给调用方定制；但如果一个组件要求调用方传入十几个渲染函数，说明它可能已经承担了太多场景。

```tsx
function EmptyState({ action }: { action?: React.ReactNode }) {
  return (
    <div>
      <p>暂无数据</p>
      {action}
    </div>
  );
}
```

好的组合 API 应该让默认场景简单，复杂场景可扩展。不要为了少写两个组件，把所有定制能力都塞进同一个组件参数表。

## 组件层级

一个组件通常只应该承担一层职责：展示、交互、数据获取、布局组织、容器编排，不要全部混在一个函数里。

```tsx
function UserCard({ user }: { user: { name: string; email: string } }) {
  return (
    <Card title={user.name}>
      <p>{user.email}</p>
    </Card>
  );
}
```

当一个组件开始同时负责很多条件分支、很多请求和很多状态时，通常不是“这个组件很强”，而是它已经太重了。

可以把组件大致分成几类：展示组件负责渲染结构和样式，容器组件负责数据和状态，布局组件负责页面区域，交互组件负责可复用行为。这个分类不是硬规则，但能帮助判断当前组件是否混入了太多责任。

```tsx
function UserCardView({ user }: { user: User }) {
  return <Card title={user.name}>{user.email}</Card>;
}

function UserCardContainer({ userId }: { userId: string }) {
  const user = useUser(userId);
  return user ? <UserCardView user={user} /> : <Skeleton />;
}
```

展示层更容易复用和测试，容器层更贴近业务和数据。拆分后，性能优化也更自然：数据变化只影响容器和必要展示组件。

## 设计判断

| 问题 | 更好的方向 |
| --- | --- |
| 逻辑太多 | 拆子组件 |
| 状态太乱 | 上提或下放 |
| 结构复用多 | 用组合 |
| 表现差异大 | 用参数控制 |
| 副作用混杂 | 移到 hook 或事件 |

组件模型的目标是让 UI 的变化点更可控。边界清晰，后面的 Hooks、性能优化和状态管理才会更顺。

实际拆组件时，可以先不急着抽象“通用组件”。如果一段 UI 只是当前页面独有，把它拆成局部子组件就足够。等多个页面出现相似结构，并且变化点也稳定，再考虑沉淀成共享组件。过早通用化会让简单需求被迫适配复杂 API。

一个健康的组件模型通常有三个特征：数据从上到下流动，用户动作通过回调向上表达，副作用集中在边界层。只要这三条保持清楚，组件树就不会轻易变成难以追踪的状态网。
