## 状态归属

React 状态管理首先要解决的不是“用什么库”，而是“这份状态应该归谁拥有”。状态放得太低，兄弟组件难以共享；放得太高，又会扩大渲染影响范围。

```tsx
function Page() {
  const [selectedId, setSelectedId] = React.useState<string | null>(null);

  return (
    <>
      <UserList selectedId={selectedId} onSelect={setSelectedId} />
      <UserDetail id={selectedId} />
    </>
  );
}
```

状态提升应该停在“最近共同父组件”。如果为了两个很远的组件通信一路提到应用根部，通常说明组件边界或状态类型需要重新审视。

React 状态可以先按范围分层：组件内部状态、父子共享状态、跨页面客户端状态、服务端缓存状态、URL 状态。不同状态的生命周期和同步方式不同，混在一起会让项目越来越难维护。

```text
输入框内容 -> 组件内部
筛选条件 -> URL 或页面容器
主题语言 -> Context
用户列表 -> 服务端状态库
登录用户 -> 会话层 / Context
```

状态管理真正困难的地方不是保存值，而是决定值的来源、失效时机和更新影响范围。

## 本地状态

本地状态适合只影响当前组件或很小子树的交互。

```tsx
function Accordion() {
  const [open, setOpen] = React.useState(false);

  return (
    <section>
      <button onClick={() => setOpen((value) => !value)}>展开</button>
      {open && <div>内容</div>}
    </section>
  );
}
```

弹窗开关、输入框值、标签页选中项、折叠状态这类内容，如果没有跨页面共享需求，通常不需要进入全局 store。

本地状态越靠近使用点，组件越容易复用。比如一个下拉菜单的展开状态应该在菜单组件内部，而不是进入全局 store。否则页面上每个菜单的展开都会变成全局事件，调试和性能都变复杂。

```tsx
function Dropdown({ label, children }: { label: string; children: React.ReactNode }) {
  const [open, setOpen] = React.useState(false);

  return (
    <div>
      <button onClick={() => setOpen((value) => !value)}>{label}</button>
      {open && <div>{children}</div>}
    </div>
  );
}
```

只有当外部确实需要控制这个状态时，才把它提升成受控 props。不要因为“以后可能用到”提前全局化。

## `useReducer`

当状态更新规则集中、动作类型多、字段联动多时，`useReducer` 比多个 `useState` 更清楚。

```tsx
type State = { count: number };
type Action = { type: "inc" } | { type: "dec" };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "inc":
      return { count: state.count + 1 };
    case "dec":
      return { count: state.count - 1 };
  }
}
```

它适合复杂表单、编辑器、购物车、筛选条件这类“动作驱动状态变化”的场景。优势不是代码更短，而是状态转移规则集中。

`useReducer` 让状态更新更像事件日志。每个 action 表达发生了什么，reducer 负责从旧状态计算新状态。这对字段联动和复杂状态特别有价值。

```tsx
type CartState = {
  items: Record<string, number>;
};

type CartAction =
  | { type: "add"; id: string }
  | { type: "remove"; id: string }
  | { type: "clear" };

function cartReducer(state: CartState, action: CartAction): CartState {
  switch (action.type) {
    case "add":
      return {
        items: {
          ...state.items,
          [action.id]: (state.items[action.id] ?? 0) + 1,
        },
      };
    case "remove": {
      const next = { ...state.items };
      delete next[action.id];
      return { items: next };
    }
    case "clear":
      return { items: {} };
  }
}
```

如果 reducer 开始处理异步请求、路由跳转、埋点等副作用，就要重新划边界。reducer 应该保持纯函数，副作用放在事件处理器、effect 或外部数据层里。

## Context

Context 适合跨层传递低频、全局、配置型数据。

```tsx
const ThemeContext = React.createContext<"light" | "dark">("light");
```

主题、语言、当前用户信息、布局配置适合放 Context。输入框内容、鼠标位置、高频列表筛选通常不适合，因为 Context 更新会影响订阅它的子树。

Context 的常见误区是把它当成轻量全局 store。Context 擅长传递值，不擅长高频更新和精细订阅。一个 Context value 如果每次渲染都创建新对象，所有消费它的组件都可能跟着更新。

```tsx
const ThemeContext = React.createContext<{
  theme: "light" | "dark";
  setTheme: (theme: "light" | "dark") => void;
} | null>(null);
```

实践中可以把“状态值”和“更新函数”拆分 Context，或保证 value 稳定。但如果需求已经涉及复杂派生、订阅粒度、开发工具和跨页面共享，外部状态库可能比继续堆 Context 更合适。

## 服务端状态

服务端状态来自接口、缓存和同步结果，和本地 UI 状态不是一类问题。

```tsx
function UserPage() {
  const [users, setUsers] = React.useState<User[]>([]);

  React.useEffect(() => {
    fetch("/api/users").then((r) => r.json()).then(setUsers);
  }, []);

  return <UserList users={users} />;
}
```

服务端状态更关心缓存、失效、重试、去重、刷新和同步。列表数据、详情数据、分页、搜索结果都属于这一类。复杂项目通常会把它交给专门的数据请求库，而不是只靠本地 state。

服务端状态和客户端状态的区别在于“权威来源”。服务端状态的权威在后端，前端只是缓存副本；客户端状态的权威在当前界面，例如弹窗是否打开、当前输入框内容、选中的标签页。

```text
服务端状态：用户列表、订单详情、库存、通知数量
客户端状态：弹窗开关、表单草稿、当前 tab、侧边栏折叠
```

把服务端状态手写进普通 state 时，马上会遇到几个问题：什么时候重新请求，多个组件请求同一数据是否去重，修改后如何让列表和详情同步，离开再回来是否使用缓存。这些问题正是 React Query、SWR、Relay、Apollo 这类工具要解决的边界。

本地 state 不是不能存接口数据，而是适合简单页面或一次性数据。只要数据需要跨组件复用、后台刷新、乐观更新或缓存失效，就应该考虑服务端状态层。

## 外部状态库

当状态需要跨页面、跨组件、跨生命周期共享，或者需要订阅粒度、派生能力和调试工具时，可以考虑外部状态库。

```text
本地 state
  -> 状态提升
  -> Context
  -> 服务端状态库
  -> 外部客户端状态库
```

这条顺序不是强制，但能帮你避免一开始就把所有状态放进全局。真正的全局状态应该少而稳定。

外部客户端状态库适合保存“前端自己拥有、但多个地方都要用”的状态，例如复杂编辑器状态、跨页面草稿、全局播放队列、应用级偏好、低频会话展示信息。它不应该替代服务端缓存，也不应该成为所有临时 UI 状态的垃圾桶。

```text
是否需要外部 store
  -> 多个远距离组件共享？
  -> 更新频率是否高？
  -> 是否需要派生选择器？
  -> 是否需要持久化或调试工具？
  -> 是否真的不是服务端状态？
```

如果只是父子组件通信，用 props；如果只是跨几层传配置，用 Context；如果是接口数据，优先服务端状态库；如果是复杂客户端状态，再考虑 Zustand、Redux、Jotai 等工具。这里会和 `3. 状态管理` 章节继续衔接。

## 渲染影响

状态变更最终都会影响渲染范围。谁订阅了状态，谁就可能在状态变化时重新渲染。

| 状态类型 | 常见归属 |
| --- | --- |
| 输入框值 | 当前表单组件 |
| 弹窗开关 | 使用弹窗的局部组件 |
| 主题语言 | Context |
| 接口列表 | 服务端状态层 |
| 登录用户 | Context 或全局状态 |

正确的状态管理不是“放得越统一越好”，而是放在最合适的层级。更完整的工具选型可以放到 [[3.1.1 状态归属|状态归属]] 继续展开。

状态影响渲染，还影响调试路径。状态离 UI 太远，组件为什么变化会难追踪；状态离 UI 太近，共享又会困难。好的状态设计应该让“谁改了状态、谁读了状态、状态什么时候失效”都能说清。

实际排查 React 状态问题时，可以按顺序问：这个值是否能由现有 props/state 推导，是否需要保存；这个值的权威来源在哪里；这个值变化后哪些组件必须更新；这个值离开页面后是否还要保留。问完这几句，很多“要不要上状态库”的争论会自然变小。
