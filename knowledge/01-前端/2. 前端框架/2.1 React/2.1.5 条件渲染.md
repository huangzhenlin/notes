## 分支模型

条件渲染就是根据不同状态展示不同 UI。它看起来只是语法问题，但其实是在整理“页面到底有哪些状态”。

如果一个页面的条件渲染写得清楚，说明它的状态模型通常也更清楚。反过来，如果 JSX 里塞满了嵌套判断，往往意味着页面状态没有被好好拆分。

条件渲染的第一步不是选 `if`、三元还是 `&&`，而是列出页面状态。比如一个用户详情页可能有：参数缺失、加载中、加载失败、无权限、用户不存在、加载成功。状态列清楚后，代码自然会更接近业务流程。

```text
invalidParams
  -> loading
  -> error
  -> forbidden
  -> notFound
  -> success
```

如果只用几个布尔值描述这些状态，很容易出现矛盾组合，例如 `loading=true` 同时 `error` 也存在。复杂页面更适合用状态枚举或联合类型。

## 提前返回

提前返回适合处理加载、权限、空值和错误等互斥状态。

```tsx
function UserPanel({ user, loading }: { user?: User; loading: boolean }) {
  if (loading) return <Spinner />;
  if (!user) return <Empty />;

  return <UserCard user={user} />;
}
```

这种写法能让主路径保持干净，避免 JSX 里嵌套太多层。

提前返回尤其适合“先判断能不能渲染，再决定渲染什么”的场景。比如权限不足、数据未加载、请求失败、参数非法，这些状态本质上都在阻止主流程继续往下走，没必要和主流程混在一起写。

提前返回的顺序要从“阻断主流程的状态”到“正常主流程”。这样读代码时就像过闸门：参数不对先退出，没权限先退出，加载失败先退出，最后才看成功内容。

```tsx
function UserPage({ state }: { state: RequestState<User> }) {
  if (state.status === "loading") return <Spinner />;
  if (state.status === "error") return <ErrorBanner message={state.error} />;
  if (state.status === "success" && !state.data) return <Empty />;

  return <UserProfile user={state.data} />;
}
```

如果提前返回太多，也可以把状态视图抽成 `RequestView`，但不要把所有分支重新塞回一个复杂三元表达式里。

## 三元表达式

三元表达式适合分支都很短的场景。

```tsx
{isLoggedIn ? <UserMenu /> : <LoginButton />}
```

如果任一分支开始变长，通常就该提取成变量或子组件，而不是继续堆在一行里。

三元表达式最怕一边展示按钮、一边展示复杂表单。那样不仅难读，还会让后续维护时很难判断 UI 哪部分属于主路径，哪部分属于临时状态。

三元表达式适合局部替换：文案、图标、小块 UI。如果两个分支共享大部分结构，可以把变化点放到结构里面；如果两个分支结构完全不同，拆变量或子组件更好。

```tsx
const action = isEditing ? (
  <button type="submit">保存</button>
) : (
  <button type="button" onClick={startEdit}>编辑</button>
);

return <footer>{action}</footer>;
```

这样主 JSX 只看到 `action`，不会被分支细节打断。

## 逻辑与

`&&` 适合“条件成立才展示”的情况。

它在 React 里很常见，但也最容易忽略“左边不是布尔值”的问题。像计数、长度、索引这类值如果直接放在左边，可能会把 `0` 渲染出来，造成看起来像“条件满足但内容错了”的假象。

```tsx
{error && <ErrorBanner message={error} />}
```

要注意 `0` 的问题。如果左侧可能是数字长度，最好显式写成比较表达式。

```tsx
{items.length > 0 && <List items={items} />}
```

逻辑与还要注意右侧组件是否有副作用。条件从 true 变 false 时，组件会卸载，对应 effect 会清理；条件再变 true 时，会重新挂载。对于播放器、地图、富文本编辑器、WebSocket 面板这类组件，这意味着外部实例也会反复创建和销毁。

如果只是想隐藏但保留内部状态，可以考虑 CSS 隐藏或组件内部状态控制；如果确实想释放资源，条件卸载就是合适选择。条件渲染不仅影响显示，也影响组件生命周期。

## 空渲染

返回 `null` 表示不渲染任何内容。

```tsx
function AdminOnly({ isAdmin, children }: { isAdmin: boolean; children: React.ReactNode }) {
  if (!isAdmin) return null;
  return <>{children}</>;
}
```

它适合权限隐藏、条件开关、占位挂载等场景。需要用户知道“为什么没有内容”时，应该展示明确状态，而不是悄悄返回 `null`。

`null` 更像“这个位置暂时不需要任何内容”，而不是“这里报错了”。如果用户需要知道发生了什么，应该渲染空状态、错误提示或说明文案，而不是让区域无声消失。

权限场景要特别小心。隐藏按钮可以减少误操作，但不能作为权限防护。比如非管理员不显示删除按钮，接口仍然必须在服务端校验权限。条件渲染解决的是界面表达，不是安全裁决。

```tsx
function DeleteUserButton({ canDelete }: { canDelete: boolean }) {
  if (!canDelete) return null;

  return <button type="button">删除用户</button>;
}
```

这类组件最好命名清楚，让调用方知道它是在控制 UI 可见性，而不是完成后端授权。

## 状态枚举

复杂页面更适合用状态枚举而不是一堆布尔值。

```tsx
type RequestState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: string };
```

这种结构能避免 `loading=true` 同时又有 `error` 的非正常组合。它和 [[1.5.3 联合交叉|联合类型]]、[[1.5.5 类型收窄|类型收窄]] 的思路是一致的：先把状态讲清楚，再去渲染。

一旦页面状态数量开始变多，最好让“状态名”本身就带有业务语义，比如 `unauthorized`、`empty`、`expired`、`submitting`，而不是永远停留在 `loading/error/success` 这三个词。语义越明确，分支越不容易写错。

状态枚举还可以让 TypeScript 帮你做穷尽检查。

```tsx
function assertNever(value: never): never {
  throw new Error(`Unexpected state: ${value}`);
}

function renderState(state: RequestState<User>) {
  switch (state.status) {
    case "idle":
      return null;
    case "loading":
      return <Spinner />;
    case "success":
      return <UserCard user={state.data} />;
    case "error":
      return <ErrorBanner message={state.error} />;
    default:
      return assertNever(state);
  }
}
```

新增状态后，如果忘记处理，编译器会提醒。页面状态越复杂，这种建模收益越明显。

## 结构拆分

如果分支多到已经很难一眼看懂，就该拆成独立组件。

```tsx
function RequestView({ state }: { state: RequestState<User[]> }) {
  switch (state.status) {
    case "loading":
      return <Spinner />;
    case "error":
      return <ErrorBanner message={state.error} />;
    case "success":
      return <UserList users={state.data} />;
    default:
      return null;
  }
}
```

把分支拆成独立组件以后，每个状态的 UI、样式和交互都更容易单独演进。

这对复杂页面尤其有用，比如列表页里的空态、错误态、分页态、筛选态都可以单独成组件。它们虽然都属于“条件渲染”，但视觉和交互要求往往不同，硬写在一个返回值里会越来越难维护。

拆分时不要只为了“让当前文件变短”。更好的拆分边界是：这个分支有没有独立文案、独立交互、独立样式、独立测试价值。比如 `EmptySearchResult` 和 `PermissionDenied` 就是两个语义完全不同的状态组件。

```tsx
function SearchResultView({ state }: { state: SearchState }) {
  if (state.status === "empty") {
    return <EmptySearchResult keyword={state.keyword} />;
  }

  if (state.status === "success") {
    return <ResultList items={state.items} />;
  }

  return null;
}
```

## 常见判断

| 分支情况 | 建议 |
| --- | --- |
| 两个很短的分支 | 三元表达式 |
| 单个条件显示 | `&&` |
| 多个互斥状态 | 提前返回或 `switch` |
| 状态复杂 | 枚举 + 拆组件 |

条件渲染本质上是在建模页面状态。状态越清楚，UI 越不会乱。

写条件渲染时可以先问一句：这个分支是“数据决定的”，还是“用户操作决定的”，还是“权限/环境决定的”。把决定因素想清楚，代码通常就不会乱。

还要注意 SSR 和客户端状态差异。如果服务端渲染时不知道浏览器宽度、登录本地缓存或当前时间，而客户端首次渲染又根据这些条件展示不同内容，就可能出现 hydration 不一致。需要依赖浏览器环境的条件，通常放到客户端挂载后再判断，或用框架提供的客户端边界处理。
