## 核心能力

Hooks 让函数组件拥有状态、副作用、上下文和其他 React 能力。它的本质不是“函数里也能写一些魔法”，而是把组件逻辑拆成更小、更可复用的状态单元。

Hooks 之所以重要，不只是因为语法更现代，而是因为它把“逻辑复用”从类组件时代的继承、混入和高阶组件，转成了更细粒度的函数组合。这个变化直接影响了组件拆分、状态管理和副作用组织方式。

```tsx
function Counter() {
  const [count, setCount] = React.useState(0);

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

Hooks 的价值在于把同类逻辑聚合起来，而不是把所有逻辑都塞进组件函数。状态、订阅、请求、派生值、DOM 引用，各有各的位置。

从运行模型看，函数组件每次渲染都会重新执行，Hooks 保存的状态并不是存在函数局部变量里，而是由 React 按调用顺序挂在组件对应的内部记录上。组件函数只是在每次渲染时“读取当前状态并返回 UI 描述”。这也是为什么不要把 Hooks 理解成普通函数调用，它们是 React 渲染机制的一部分。

```tsx
function Counter() {
  const [count, setCount] = React.useState(0);

  function increment() {
    setCount((current) => current + 1);
  }

  return <button onClick={increment}>{count}</button>;
}
```

状态更新如果依赖上一次状态，优先使用函数式更新。这样事件处理器即使捕获了旧闭包，也能从 React 提供的最新状态继续计算。

## 常用能力

React 最常见的 Hooks 可以粗略分成几类。

| Hook | 作用 |
| --- | --- |
| `useState` | 维护可触发渲染的状态 |
| `useEffect` | 处理副作用 |
| `useRef` | 保存不触发渲染的可变值 |
| `useMemo` | 缓存计算结果 |
| `useCallback` | 缓存函数引用 |
| `useContext` | 读取上下文 |

这些 Hook 的职责不同，不建议为了“统一写法”硬套同一种思路。比如状态该用 `useState`，副作用该用 `useEffect`，DOM 引用该用 `useRef`。

一个简单的判断是：会触发重新渲染的值用状态，不触发渲染但需要跨渲染保存的值用 `useRef`，需要同步外部世界的动作用副作用，需要减少重复计算的结果再考虑缓存。

常见 Hook 的边界可以再细一点：`useState` 适合局部交互状态，`useReducer` 适合状态转移复杂且事件类型明确的场景，`useContext` 适合跨层传递稳定上下文，`useSyncExternalStore` 适合订阅外部 store，`useId` 适合生成 SSR/CSR 稳定一致的表单关联 id。

```tsx
function Field() {
  const id = React.useId();

  return (
    <label htmlFor={id}>
      用户名
      <input id={id} />
    </label>
  );
}
```

`useId` 不是用来生成列表 key 的。列表 key 应该来自数据本身，因为 key 要表达数据身份；`useId` 更像组件实例内的可访问性关联标识。

## 规则约束

Hooks 只能在 React 函数组件或自定义 Hook 的顶层调用，不能写在条件、循环或普通函数里。

```tsx
function Profile({ enabled }: { enabled: boolean }) {
  const [count, setCount] = React.useState(0);

  if (!enabled) {
    return null;
  }

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

如果条件决定逻辑是否执行，不要条件调用 Hook，而是把条件放进 Hook 内部。React 依赖 Hook 调用顺序来匹配状态槽位，顺序乱了，状态就会错位。

这也是为什么 Hooks 规则看起来有点“死板”。它的约束换来的，是组件每次渲染都能稳定地对应到同一组状态槽位。只要调用顺序不变，React 就能正确地恢复之前的状态。

违反规则最容易出现的问题是状态错位。下面这种条件调用看起来只是“有需要才用”，但下一次渲染条件变化后，后面的 Hook 会对应到不同槽位。

```tsx
function BadProfile({ enabled }: { enabled: boolean }) {
  if (enabled) {
    React.useEffect(() => {
      document.title = "Enabled";
    }, []);
  }

  const [name, setName] = React.useState("");
  return <input value={name} onChange={(event) => setName(event.target.value)} />;
}
```

正确做法是始终调用 Hook，把条件放到 Hook 内部。

```tsx
function Profile({ enabled }: { enabled: boolean }) {
  React.useEffect(() => {
    if (!enabled) return;

    document.title = "Enabled";
  }, [enabled]);

  const [name, setName] = React.useState("");
  return <input value={name} onChange={(event) => setName(event.target.value)} />;
}
```

eslint 的 Hooks 规则不是形式主义，它是在帮团队提前发现调用顺序、依赖遗漏和闭包问题。真正项目里不要关闭这类规则来“让代码先过”。

## 自定义 Hook

自定义 Hook 用来封装可复用的 React 逻辑。

```tsx
function useDocumentTitle(title: string) {
  React.useEffect(() => {
    document.title = title;
  }, [title]);
}
```

好的自定义 Hook 通常会把“订阅、清理、同步、派生”这些重复逻辑收进去，让调用方只拿结果，不关心内部怎么协调。

自定义 Hook 最有价值的地方，是把“和 React 生命周期强相关的逻辑”集中封装。比如窗口尺寸、页面可见性、网络请求、表单联动、主题变化，都很适合抽成 Hook，因为它们都需要订阅和清理。

一个自定义 Hook 应该像普通函数一样有清晰输入和输出，但内部可以使用其他 Hook。比如窗口尺寸 Hook，调用方只关心尺寸，订阅和清理由内部处理。

```tsx
function useWindowSize() {
  const [size, setSize] = React.useState(() => ({
    width: window.innerWidth,
    height: window.innerHeight,
  }));

  React.useEffect(() => {
    function handleResize() {
      setSize({
        width: window.innerWidth,
        height: window.innerHeight,
      });
    }

    window.addEventListener("resize", handleResize);
    return () => window.removeEventListener("resize", handleResize);
  }, []);

  return size;
}
```

如果项目有 SSR，还要注意 `window` 在服务端不存在。此时初始化值不能直接读取浏览器对象，或者要把 Hook 限定在客户端组件里使用。Hooks 封装的不是“能跑就行”的片段，而是一段可复用的运行边界。

## 组合边界

Hooks 适合复用逻辑，不适合把 UI 结构也一起封装掉。

| 场景 | 适合 Hook | 不太适合 Hook |
| --- | --- | --- |
| 订阅窗口尺寸 | 是 |  |
| 维护请求状态 | 是 |  |
| 复用输入校验逻辑 | 是 |  |
| 页面布局结构 |  | 是 |
| 纯计算工具 |  | 是 |

如果一段逻辑本身不依赖 React 生命周期，也不需要状态槽位，通常就不该硬做成 Hook。

换句话说，Hook 不是“任何复用都要做成 Hook”。如果只是一个纯计算函数，或者一个和 React 毫无关系的工具方法，普通函数通常更简单，也更容易测试。

Hook 的命名以 `use` 开头，不只是约定，也是工具识别它是否遵守 Hooks 规则的方式。自定义 Hook 的返回值也要尽量稳定：如果返回对象里包含函数，调用方可能会把它作为 effect 依赖或传给子组件，这时要考虑是否需要稳定引用，或者把 API 设计得更简单。

```tsx
function useBoolean(initial = false) {
  const [value, setValue] = React.useState(initial);

  return {
    value,
    setTrue: () => setValue(true),
    setFalse: () => setValue(false),
    toggle: () => setValue((current) => !current),
  };
}
```

上面这种 Hook 适合局部复用，但如果它被大量传递到深层组件，返回对象每次渲染都会变成新引用，可能影响 `memo` 判断。是否优化要看实际调用链，不要为了“完美稳定”一开始就把简单 Hook 写复杂。

## 使用判断

可以先问三个问题：

1. 这段逻辑是否要和组件生命周期绑定。
2. 这段逻辑是否需要保存可变状态。
3. 这段逻辑是否值得在多个组件里复用。

如果答案都是否定的，普通函数往往更简单。

如果答案是“是”，也不一定立刻写成 Hook。还要继续判断它是否依赖组件树、是否需要跨组件共享、是否需要暴露给多个页面。Hooks 的目标是让状态和副作用更可组合，不是把所有逻辑都包装进 Hook 名字里。

还可以用“数据是否属于 UI 生命周期”判断。比如格式化金额、计算折扣、排序数组，这些逻辑可以离开 React 单独测试，普通函数更好；监听页面可见性、订阅媒体查询、同步 URL 查询参数，这些逻辑依赖组件挂载和卸载，Hook 更自然。

```tsx
function formatPrice(value: number) {
  return `￥${value.toFixed(2)}`;
}

function usePageVisibility() {
  const [visible, setVisible] = React.useState(!document.hidden);

  React.useEffect(() => {
    function handleVisibilityChange() {
      setVisible(!document.hidden);
    }

    document.addEventListener("visibilitychange", handleVisibilityChange);
    return () => document.removeEventListener("visibilitychange", handleVisibilityChange);
  }, []);

  return visible;
}
```

两者都能复用，但边界不同。把纯函数写成 Hook，会让它只能在组件里用；把生命周期逻辑写成普通函数，又会丢掉清理和状态更新能力。

## 与其他能力的关系

Hooks 不是为了取代组件模型，而是补充组件模型的表达能力。状态相关的逻辑通常要配合 [[2.1.2 组件模型|组件模型]]、[[2.1.8 副作用|副作用]] 和 [[2.1.9 Ref|Ref]] 一起看，才能分清“谁负责展示，谁负责同步，谁负责记忆”。

如果把组件比作一块 UI 外壳，那 Hooks 就是在外壳里组织“状态、引用和同步”的方式。理解这层关系以后，再去看 `useEffect` 的依赖、`useRef` 的稳定引用和 `useMemo` 的缓存，就不会只剩语法记忆了。

React 官方文档近几年反复强调一个方向：先用渲染表达 UI，事件处理器响应用户动作，effect 只同步外部系统。Hooks 学习的重点也应该沿着这个边界走，而不是背 API 清单。真正写项目时，大部分问题都能归到三类：状态放错位置、effect 做了不该做的事、缓存工具掩盖了组件设计问题。
