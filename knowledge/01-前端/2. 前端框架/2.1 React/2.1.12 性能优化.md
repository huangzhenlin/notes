## 更新范围

React 性能优化最先看的通常不是 `memo`，而是状态归属和更新范围。状态越靠近真正使用它的组件，受影响的渲染范围越小。

```tsx
function Page() {
  return (
    <>
      <SearchBar />
      <Results />
    </>
  );
}
```

如果搜索输入只影响搜索栏，就不要把它放到整页父组件里。先控制状态归属，再考虑缓存工具，通常更有效。

React 的一次更新会从状态所在组件开始重新渲染它的子树。重新渲染不等于真实 DOM 一定更新，但组件函数会重新执行，昂贵计算和大列表仍然可能造成主线程压力。因此性能优化的第一步通常是让状态离使用它的地方更近，或者把不相关的 UI 拆成子组件。

```tsx
function Page() {
  return (
    <Layout>
      <SearchPanel />
      <StaticSidebar />
    </Layout>
  );
}
```

如果搜索状态放在 `Page`，`StaticSidebar` 也会跟着重新渲染；如果状态只放在 `SearchPanel`，更新范围会自然缩小。很多时候，正确拆组件比加 `memo` 更有效，也更容易维护。

## `React.memo`

`React.memo` 可以在 props 没变化时跳过子组件重复渲染。

```tsx
const UserItem = React.memo(function UserItem({ user }: { user: User }) {
  return <li>{user.name}</li>;
});
```

它适合渲染代价高、props 稳定、列表项多的组件。不要把所有组件都 memo，维护成本可能比收益更高。

`React.memo` 做的是浅比较。props 里如果每次都传新对象、新数组、新函数，memo 很可能失效。

```tsx
const UserItem = React.memo(function UserItem({
  user,
  onSelect,
}: {
  user: User;
  onSelect: (id: string) => void;
}) {
  return <button onClick={() => onSelect(user.id)}>{user.name}</button>;
});
```

要让它生效，父组件需要尽量传稳定数据，或者把对象创建移动到更合适的位置。不过不要为了 memo 把所有东西都 `useMemo/useCallback` 一遍。先用 Profiler 确认子组件确实昂贵，再优化引用稳定性。

## `useMemo`

`useMemo` 适合缓存昂贵计算结果。

```tsx
const filteredUsers = React.useMemo(() => {
  return users.filter((user) => user.name.includes(keyword));
}, [users, keyword]);
```

如果计算很轻，`useMemo` 可能只是增加复杂度。它解决的是昂贵计算和引用稳定问题，不是“让代码自动变快”的开关。

`useMemo` 的成本包括依赖比较、缓存保存和理解成本。适合使用它的场景通常有两个：计算确实昂贵，或者结果引用需要稳定传给 memo 子组件。

```tsx
const visibleRows = React.useMemo(() => {
  return rows
    .filter((row) => row.name.includes(keyword))
    .sort((a, b) => a.createdAt.localeCompare(b.createdAt));
}, [rows, keyword]);
```

如果 `rows` 本身每次渲染都是新数组，`useMemo` 也会每次重算。优化时要看依赖链，而不是只看当前这一行。

## `useCallback`

`useCallback` 用来稳定函数引用，尤其适合传给 `memo` 子组件或作为 effect 依赖。

```tsx
const handleSelect = React.useCallback((id: string) => {
  setSelectedId(id);
}, []);
```

如果没有引用比较链路，它通常不会带来实际收益。不要为了“看起来优化过”到处包 `useCallback`。

`useCallback(fn, deps)` 本质上接近 `useMemo(() => fn, deps)`。它不会阻止函数内部执行，也不会让事件处理更快，只是让函数引用在依赖不变时保持稳定。

```tsx
const handleSelect = React.useCallback((id: string) => {
  setSelectedId(id);
}, []);
```

如果函数只传给普通 DOM 元素，通常不需要 `useCallback`。如果它传给 `React.memo` 子组件、作为 context value 的一部分，或者作为 effect 依赖导致重复订阅，就值得考虑稳定引用。

## 列表优化

长列表优化通常按顺序来。

```text
分页或懒加载
稳定 key
拆分列表项
减少单项渲染成本
虚拟滚动
```

虚拟列表适合大量 DOM 节点造成卡顿的场景，但它会引入滚动、测量、可访问性和动态高度等额外复杂度。

列表性能要先确认瓶颈来自哪里：是数据请求慢、过滤排序慢、单项组件重、DOM 节点太多，还是图片加载和布局抖动。不同瓶颈对应不同方案。

```text
请求慢 -> 分页、预加载、缓存
计算慢 -> 索引、memo、Web Worker
组件重 -> 拆分、memo、减少 props 变化
DOM 多 -> 虚拟列表
图片重 -> 懒加载、尺寸占位、压缩
```

虚拟列表不是默认答案。它适合几百上千项同时渲染造成 DOM 压力的场景；如果列表只有几十项，问题可能在单项组件、图片或状态更新范围。

## 并发能力

React 的并发能力可以改善交互流畅度，但不能替代状态设计。

```tsx
const [isPending, startTransition] = React.useTransition();

function handleChange(value: string) {
  setKeyword(value);
  startTransition(() => {
    setFilter(value);
  });
}
```

`startTransition` 适合把低优先级更新延后，比如搜索结果刷新、复杂列表过滤、图表重算。输入本身仍然应该优先响应。

并发能力改变的是更新优先级和可中断性，不会减少总工作量。如果列表过滤本身要跑 500ms，`startTransition` 可以让输入更跟手，但最终计算仍然要执行。真正耗时的任务可能还需要分页、缓存、Web Worker 或服务端搜索。

```tsx
function SearchPage() {
  const [input, setInput] = React.useState("");
  const [query, setQuery] = React.useState("");
  const [isPending, startTransition] = React.useTransition();

  function handleChange(event: React.ChangeEvent<HTMLInputElement>) {
    const value = event.target.value;
    setInput(value);
    startTransition(() => {
      setQuery(value);
    });
  }

  return (
    <>
      <input value={input} onChange={handleChange} />
      {isPending && <span>更新结果中...</span>}
      <SearchResults query={query} />
    </>
  );
}
```

这里输入值和查询值分开，用户输入优先响应，结果列表可以稍后更新。它改善交互节奏，但不能替代算法和数据层优化。

## 延迟值

`useDeferredValue` 适合把高频输入和低优先级结果分开。

```tsx
const deferredKeyword = React.useDeferredValue(keyword);
```

它能让输入先跟手，再慢慢刷新重计算结果。搜索、筛选、复杂图表和大列表都可能用到。

`useDeferredValue` 适合“同一个值有两种消费速度”的场景。输入框需要立刻显示最新值，结果区域可以滞后一点。它比手写防抖更贴近 React 更新调度，但语义不同：防抖是延迟触发，deferred value 是允许低优先级渲染落后。

```tsx
function SearchBox({ items }: { items: Item[] }) {
  const [keyword, setKeyword] = React.useState("");
  const deferredKeyword = React.useDeferredValue(keyword);

  return (
    <>
      <input value={keyword} onChange={(event) => setKeyword(event.target.value)} />
      <ResultList keyword={deferredKeyword} items={items} />
    </>
  );
}
```

如果每次输入都会发请求，仍然要处理请求取消、缓存和防抖。`useDeferredValue` 主要影响渲染，不是网络请求管理工具。

## 副作用优化

很多性能问题来自 effect 写得太多或依赖不稳定。

```tsx
React.useEffect(() => {
  document.title = title;
}, [title]);
```

能在事件里完成的逻辑，不要放进 effect；能在渲染时直接算出的值，不要先存 state 再同步一次。React 性能问题常常不是 React 慢，而是状态和副作用让更新链路变长。

一个常见性能坏味道是 effect 里 setState 形成二次渲染。

```tsx
React.useEffect(() => {
  setFullName(`${firstName} ${lastName}`);
}, [firstName, lastName]);
```

这类派生值直接在渲染阶段计算即可。少一次状态同步，就少一次渲染链路，也少一个依赖数组维护点。

```tsx
const fullName = `${firstName} ${lastName}`;
```

如果 effect 用来订阅外部系统，则要保证清理完整、依赖稳定。重复订阅和未清理资源会让页面越用越慢。

## 验证方式

优化前先定位瓶颈，优化后再验证收益。

| 工具 | 用途 |
| --- | --- |
| React DevTools Profiler | 看组件渲染耗时 |
| 浏览器 Performance | 看主线程和长任务 |
| 真实设备测试 | 看实际交互体感 |
| 日志计数 | 简单确认渲染次数 |

如果优化后代码更复杂，但没有明显收益，就应该回退。性能优化的目标是更快、更稳，而不是把所有工具都用上。

验证时要区分开发环境和生产环境。开发环境有额外检查、源码映射和 Strict Mode 行为，不能直接代表生产性能。React DevTools Profiler 可以定位组件提交耗时，浏览器 Performance 面板可以观察长任务、布局和脚本执行。两者结合，才能分清是 React 渲染慢，还是浏览器主线程被其他任务占满。

```text
先复现卡顿
  -> Profiler 找组件耗时
  -> Performance 找主线程瓶颈
  -> 小范围修改
  -> 对比优化前后
```

性能优化最怕“凭感觉改”。如果没有基线，就不知道优化是否有效；如果没有回退标准，就容易把简单代码改成复杂代码。好的优化应该能说清：慢在哪里、为什么这个改动能减少工作、改完后指标有什么变化。
