## 输入边界

Props 是父组件传给子组件的数据和回调。它们更像一张快照：传给子组件时通常应该保持相对稳定，而不是被子组件随意改写。

```tsx
type ButtonProps = {
  label: string;
  disabled?: boolean;
};

function Button({ label, disabled }: ButtonProps) {
  return <button disabled={disabled}>{label}</button>;
}
```

组件设计的第一个原则通常是“输入清晰，输出确定”。props 越稳定，组件越容易复用、测试和维护。

Props 是只读输入，子组件不应该修改它。即使传入的是对象或数组，技术上可以改引用里的内容，也不应该这么做，因为这会破坏 React 的单向数据流。

```tsx
function BadTags({ tags }: { tags: string[] }) {
  tags.push("new");
  return <span>{tags.join(",")}</span>;
}
```

需要新增、删除或排序时，应创建新数据，或者通过回调告诉父组件更新。

```tsx
function Tags({ tags, onChange }: { tags: string[]; onChange: (tags: string[]) => void }) {
  return (
    <button onClick={() => onChange([...tags, "new"])}>
      添加标签
    </button>
  );
}
```

## 回调 Props

父组件常通过回调把事件处理交给自己。

```tsx
type TodoItemProps = {
  id: string;
  title: string;
  onToggle: (id: string) => void;
};

function TodoItem({ id, title, onToggle }: TodoItemProps) {
  return <button onClick={() => onToggle(id)}>{title}</button>;
}
```

回调命名最好表达业务意图，比如 `onSubmit`、`onSelectUser`、`onClose`，而不是只叫 `callback`。

回调 props 最好表达“发生了什么”，而不是要求子组件知道父组件要“怎么做”。比如 `onDeleteUser(id)` 比 `setUsers(...)` 更适合作为子组件 API，因为前者是业务事件，后者暴露了父组件内部状态结构。

```tsx
type UserItemProps = {
  user: User;
  onDeleteUser: (id: string) => void;
};
```

如果回调需要返回 Promise，要明确子组件是否关心异步结果。比如弹窗确认按钮需要等待父组件提交完成再关闭，就应该把返回类型写出来，并处理 loading 和错误。

```tsx
type ConfirmDialogProps = {
  onConfirm: () => Promise<void>;
};
```

## children

`children` 适合承载组件内容，尤其适合布局、卡片、弹窗和容器类组件。

```tsx
type CardProps = {
  title: string;
  children: React.ReactNode;
};

function Card({ title, children }: CardProps) {
  return (
    <section className="card">
      <h3>{title}</h3>
      {children}
    </section>
  );
}
```

它让组件把“外壳”和“内容”分开，调用方负责内容，组件负责结构。

`children` 的类型通常写成 `React.ReactNode`，因为它可以接收字符串、数字、元素、数组、`null` 等可渲染内容。不要轻易写成 `JSX.Element`，否则会把正常的文本、多个节点和条件空值排除掉。

```tsx
type PanelProps = {
  title: string;
  children: React.ReactNode;
};
```

如果组件必须只接收一个特定子组件，才需要更严格的类型和运行时约束。多数容器组件不应该过度限制 children，否则组合能力会下降。

## 默认值

默认值通常在参数解构时给出。

```tsx
type ButtonProps = {
  variant?: "primary" | "secondary";
  disabled?: boolean;
};

function Button({ variant = "primary", disabled = false }: ButtonProps) {
  return <button className={`btn-${variant}`} disabled={disabled} />;
}
```

默认值应该是业务上真的合理，而不是为了省掉判断随便塞一个。像权限、金额、用户身份这种字段，默认值往往会掩盖问题。

默认值适合视觉变体、开关状态、尺寸这类低风险字段。对于业务身份、权限、接口数据，宁可让调用方显式传入，也不要给一个“看起来能用”的默认值。

```tsx
type PriceProps = {
  amount: number;
  currency?: "CNY" | "USD";
};

function Price({ amount, currency = "CNY" }: PriceProps) {
  return <span>{currency} {amount}</span>;
}
```

这里 `currency` 有业务默认值可以接受，但 `amount` 不能默认成 `0`。如果金额缺失却显示成 0，用户会以为商品免费或订单无金额，这比直接报错更危险。

## 对象 Props

多个字段属于同一个实体时，可以用对象 props。

```tsx
type UserCardProps = {
  user: {
    id: string;
    name: string;
    email: string;
  };
};

function UserCard({ user }: UserCardProps) {
  return <div>{user.name}</div>;
}
```

如果组件只需要少数字段，可以用 `Pick` 缩小边界，避免把整个大对象传进来。

```tsx
type UserCardProps = {
  user: Pick<User, "id" | "name">;
};
```

对象 props 的边界取决于组件职责。展示用户卡片只需要 `id` 和 `name`，就不应该把完整用户对象传入；详情页容器确实要协调多个子组件，传完整对象可能更自然。

```tsx
type UserAvatarProps = {
  user: Pick<User, "name" | "avatarUrl">;
};
```

缩小 props 有两个好处：组件更容易复用，敏感字段更不容易误传到子组件。尤其是用户对象、订单对象、权限对象，经常包含页面不该展示的字段。

## 受控与非受控

受控 props 表示状态由父组件持有，子组件只负责触发变更。

```tsx
type ToggleProps = {
  checked: boolean;
  onCheckedChange: (checked: boolean) => void;
};

function Toggle({ checked, onCheckedChange }: ToggleProps) {
  return (
    <button onClick={() => onCheckedChange(!checked)}>
      {checked ? "开" : "关"}
    </button>
  );
}
```

非受控组件则把状态放在内部。业务组件通常不需要一开始就设计成“可控 + 不可控”双模式，太早复杂化只会让 API 变厚。

组件库里的基础组件有时需要同时支持受控和非受控，例如 `Dialog` 既可以由外部传 `open` 控制，也可以内部维护开关。但业务组件通常先选择一种模式就够了。

```tsx
type DialogProps = {
  open: boolean;
  onOpenChange: (open: boolean) => void;
};

function Dialog({ open, onOpenChange }: DialogProps) {
  if (!open) return null;
  return <button onClick={() => onOpenChange(false)}>关闭</button>;
}
```

受控组件的优势是父组件完全掌握状态，适合弹窗、筛选、分页、开关这类需要外部协调的场景。非受控组件优势是使用简单，适合内部临时交互。不要混用到调用方分不清谁拥有状态。

## 设计原则

| 问题 | 判断 |
| --- | --- |
| 这个字段真的是外部要控制的吗 | 再决定是否做成 props |
| 字段组合是否容易出错 | 是否该收敛成对象 |
| 回调是否表达业务动作 | 是否该改命名 |
| 默认值是否会掩盖错误 | 是否该改成必填 |

props 的边界越清楚，组件就越像一个可靠的黑盒。和 [[2.1.2 组件模型|组件模型]] 配合起来，界面会更容易拆解，也更容易复用。

设计 props 时，可以优先避免三类坏味道：布尔开关过多、透传大对象、命名过于技术化。布尔开关过多会制造组合爆炸，大对象会模糊依赖，技术化命名会让调用方不知道业务含义。

```tsx
// 不如 onConfirm 清楚
type Props = {
  callback: () => void;
};
```

好的 props API 通常读起来像一句业务描述：`<ConfirmDialog open={open} title="删除用户" onConfirm={deleteUser} />`。调用方不用打开组件源码，也能大概知道这个组件需要什么、会在什么时候通知外部。
