## 列表结构

列表渲染是把数据集合转成重复 UI 结构的过程。React 里最常见的方式就是 `map`。

```tsx
function UserList({ users }: { users: User[] }) {
  return (
    <ul>
      {users.map((user) => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}
```

列表渲染的核心不是“把数组变成一堆标签”，而是让数据驱动界面，并保证每一项的身份稳定。

列表通常是前端复杂度最容易累积的地方，因为它同时涉及数据获取、过滤排序、空状态、分页、选择、批量操作和性能。写列表时要先区分“数据集合”和“单项交互”：容器负责集合逻辑，项组件负责单项展示和动作。

```tsx
function UserList({ users, onSelect }: { users: User[]; onSelect: (id: string) => void }) {
  return (
    <ul>
      {users.map((user) => (
        <UserListItem key={user.id} user={user} onSelect={onSelect} />
      ))}
    </ul>
  );
}
```

这种拆法看起来多了一个组件，但它让列表容器不会被每一项的细节淹没。

## `key`

`key` 用来让 React 识别列表项身份，影响复用、移动、插入和删除时的状态保留。

```tsx
{todos.map((todo) => (
  <TodoItem key={todo.id} todo={todo} />
))}
```

优先使用稳定业务 ID。数组索引只适合静态、不重排、不插入删除的简单列表。

`key` 的错误不仅影响性能，还会影响状态归属。假设列表项里有输入框，用索引作为 key 时，在列表头部插入新项，原来第一个输入框的内部状态可能被复用到新数据上。

```tsx
{items.map((item, index) => (
  <EditableItem key={index} item={item} />
))}
```

如果数据没有天然 ID，应在数据进入前端时生成稳定 ID，而不是每次渲染时调用 `crypto.randomUUID()`。每次渲染都变的 key 会让 React 认为所有项都是新元素，导致状态全部丢失。

```tsx
const itemsWithId = rawItems.map((item) => ({
  ...item,
  clientId: crypto.randomUUID(),
}));
```

这段生成应该发生在数据初始化或入库阶段，而不是 JSX 的 `map` 里。

## 预处理

过滤、排序和分组通常先在数据层处理，再交给 JSX 渲染。

```tsx
const visibleUsers = users.filter((user) => user.enabled);

return <UserList users={visibleUsers} />;
```

这样可以让 JSX 保持更像结构描述，而不是混杂大量处理逻辑。

过滤、排序要注意不要修改原数组。`sort` 会原地修改数组，如果 props 里的数组被直接排序，父组件数据也会被改变。

```tsx
const visibleUsers = [...users]
  .filter((user) => user.enabled)
  .sort((a, b) => a.name.localeCompare(b.name));
```

如果预处理很昂贵，或者数据量大、输入频繁变化，可以结合 `useMemo`。但先确认计算确实是瓶颈，不要把每个 `filter` 都包起来。

```tsx
const visibleUsers = React.useMemo(() => {
  return users.filter((user) => user.name.includes(keyword));
}, [users, keyword]);
```

## 拆分项组件

列表项有交互、状态或复杂样式时，最好单独拆成组件。

```tsx
function TodoItem({ todo, onToggle }: { todo: Todo; onToggle: (id: string) => void }) {
  return (
    <li>
      <label>
        <input
          type="checkbox"
          checked={todo.done}
          onChange={() => onToggle(todo.id)}
        />
        {todo.title}
      </label>
    </li>
  );
}
```

拆分后，列表容器负责数据集合，列表项负责单项展示和交互，职责会更清楚。

列表项组件还可以帮助控制渲染范围。比如父组件里搜索框变化时，如果每一项 props 没变，配合 `React.memo` 可以减少昂贵项的重复渲染。但前提是 key 稳定、props 稳定，并且列表项确实有渲染成本。

```tsx
const TodoItem = React.memo(function TodoItem({
  todo,
  onToggle,
}: {
  todo: Todo;
  onToggle: (id: string) => void;
}) {
  return <li>{todo.title}</li>;
});
```

不要把所有项组件都 memo。普通文本列表通常不需要，复杂卡片、富交互项、大量项才值得验证。

## 空列表

空列表不要悄悄什么都不显示，最好给出明确状态。

```tsx
if (users.length === 0) {
  return <Empty description="暂无用户" />;
}
```

空状态既是体验，也是信息反馈。用户看到空页面时，应该知道是没数据、在加载，还是权限不足。

空列表要和加载状态、筛选结果为空区分开。初始没有数据、搜索无结果、权限不可见、接口失败，它们都是“列表没东西”，但用户需要的反馈完全不同。

```tsx
if (loading) return <Spinner />;
if (error) return <ErrorBanner message="加载失败" />;
if (keyword && users.length === 0) return <Empty description="没有匹配结果" />;
if (users.length === 0) return <Empty description="暂无用户" />;
```

这种分支看似啰嗦，但能避免所有情况都显示同一个“暂无数据”，让用户不知道下一步该做什么。

## 性能边界

长列表要考虑渲染成本。

```text
先优化顺序：
1. 减少不必要的重渲染
2. 保持 key 稳定
3. 避免列表项过重
4. 再考虑虚拟列表
```

不要一上来就给所有列表套虚拟滚动。只有当列表数量、渲染成本和交互频率真的成为瓶颈时，才值得引入额外复杂度。

虚拟列表会改变 DOM 结构：屏幕外的项不在 DOM 中，浏览器查找、滚动定位、辅助技术和自动聚焦都可能受影响。动态高度、展开项、拖拽排序、表格合并单元格也会让虚拟列表复杂度上升。

优化长列表可以按层次做：先分页或服务端筛选减少数据量，再减少每项渲染成本，再稳定 key 和 props，最后才引入虚拟滚动。虚拟滚动解决的是 DOM 数量问题，不解决慢接口、慢计算和图片过大。

## 事件传递

列表项事件通常要带上当前项 ID。

```tsx
function TodoList({ todos, onToggle }: { todos: Todo[]; onToggle: (id: string) => void }) {
  return (
    <ul>
      {todos.map((todo) => (
        <TodoItem key={todo.id} todo={todo} onToggle={onToggle} />
      ))}
    </ul>
  );
}
```

事件放在项组件还是容器组件，主要看状态归属。状态在父层，就让事件往上抛；状态在项内，就让项自己处理。

批量操作场景里，选中状态通常属于列表容器，因为工具栏、分页、全选按钮和每一项都要读它。

```tsx
function UserList({ users }: { users: User[] }) {
  const [selectedIds, setSelectedIds] = React.useState<Set<string>>(() => new Set());

  function toggle(id: string) {
    setSelectedIds((current) => {
      const next = new Set(current);
      next.has(id) ? next.delete(id) : next.add(id);
      return next;
    });
  }

  return users.map((user) => (
    <UserItem
      key={user.id}
      user={user}
      selected={selectedIds.has(user.id)}
      onToggle={toggle}
    />
  ));
}
```

注意这里每次都创建新的 `Set`，而不是直接修改旧集合。React 状态更新仍然需要不可变思路。

## 设计判断

| 问题 | 处理方式 |
| --- | --- |
| 项结构重复 | 用 `map` |
| 逻辑太多 | 拆项组件 |
| 列表太长 | 先减渲染量 |
| 需要空状态 | 单独处理 |
| 需要排序过滤 | 先处理数据再渲染 |

列表渲染看起来简单，但它往往是界面复杂度最先放大的地方。把结构、身份和状态边界理顺，后面会轻很多。

列表设计可以先问四个问题：每项的稳定身份是什么，列表为空时显示什么，单项状态归谁管理，数据量变大后怎么办。把这四件事想清楚，列表后续增加搜索、分页、排序、选择、拖拽时就不容易推倒重来。
