## 事件边界

React 事件处理器接收的是合成事件对象。它的意义不只是“接一下点击”，而是把用户交互转成明确的业务动作。

```tsx
function SearchForm() {
  function handleSubmit(event: React.FormEvent<HTMLFormElement>) {
    event.preventDefault();
    console.log("submit");
  }

  return <form onSubmit={handleSubmit}>...</form>;
}
```

表单提交、链接跳转、菜单展开、拖拽开始这些行为，通常都要先明确：这是浏览器默认行为，还是组件自己的业务行为。React 事件处理就是这个分界点。

React 事件处理器不是模板字符串里的脚本，而是传入函数引用。不要在渲染时直接调用函数，否则组件渲染时就会执行动作。

```tsx
// 错误：渲染时立即执行
<button onClick={submitForm()}>提交</button>

// 正确：点击时执行
<button onClick={submitForm}>提交</button>
```

需要带参数时，用包装函数表达用户动作。

```tsx
<button onClick={() => deleteUser(user.id)}>删除</button>
```

如果这个按钮在大列表里，并且列表项很重，再结合 `React.memo` 和 `useCallback` 判断是否需要优化；普通场景下，先保证意图清楚比过早优化更重要。

## 阻止默认

`preventDefault` 用来阻止浏览器默认行为，比如表单提交、链接跳转。

```tsx
function LinkLike() {
  function handleClick(event: React.MouseEvent<HTMLAnchorElement>) {
    event.preventDefault();
    console.log("custom navigation");
  }

  return <a href="/docs" onClick={handleClick}>文档</a>;
}
```

不要依赖 `return false`。在 React 里，它不会自动阻止默认行为，也不会阻止事件传播。

`preventDefault` 只阻止浏览器默认行为，不会阻止事件继续冒泡。比如链接点击时调用它，浏览器不会跳转，但父元素的 `onClick` 仍然可能执行。

```tsx
function CardLink() {
  return (
    <div onClick={() => console.log("card")}>
      <a
        href="/docs"
        onClick={(event) => {
          event.preventDefault();
          console.log("link");
        }}
      >
        文档
      </a>
    </div>
  );
}
```

如果既要阻止跳转又要阻止父级点击，需要同时使用 `preventDefault` 和 `stopPropagation`。两者解决的问题不同，不能互相替代。

## 事件传播

事件会从目标元素向外冒泡。需要阻止父级处理时，使用 `stopPropagation`。

```tsx
function Row() {
  return (
    <div onClick={() => console.log("row")}>
      <button
        onClick={(event) => {
          event.stopPropagation();
          console.log("button");
        }}
      >
        操作
      </button>
    </div>
  );
}
```

传播控制很有用，但不要滥用。表格行、弹窗、菜单、列表卡片这些复杂交互里，过多的阻止传播会让事件链难以理解。

复杂交互里更推荐让事件层级表达清楚，而不是靠大量 `stopPropagation` 补洞。比如表格行点击进入详情，行内按钮执行操作，这种确实需要阻止冒泡；但如果父子元素都有模糊的点击区域，最好重新设计交互边界。

```tsx
function UserRow({ user }: { user: User }) {
  return (
    <tr onClick={() => openDetail(user.id)}>
      <td>{user.name}</td>
      <td>
        <button
          type="button"
          onClick={(event) => {
            event.stopPropagation();
            deleteUser(user.id);
          }}
        >
          删除
        </button>
      </td>
    </tr>
  );
}
```

阻止传播应该出现在“子元素确实有独立业务动作”的地方，而不是作为默认习惯。

## 状态更新

事件处理器是更新状态最常见的地方。

```tsx
function Counter() {
  const [count, setCount] = React.useState(0);

  return <button onClick={() => setCount((value) => value + 1)}>{count}</button>;
}
```

当新状态依赖旧状态时，优先使用函数式更新，避免闭包拿到旧值。

```tsx
setCount((prev) => prev + 1);
```

React 会批量处理同一个事件中的多次状态更新。直接使用当前闭包里的 `count` 连续更新，可能不会得到预期的累加结果。

```tsx
setCount(count + 1);
setCount(count + 1);
```

如果想基于上一次结果连续更新，要用函数式写法。

```tsx
setCount((current) => current + 1);
setCount((current) => current + 1);
```

这和 Hooks 里的闭包问题是一条线：事件处理器捕获的是某次渲染的值，函数式更新则把计算交给 React 在更新队列中按顺序执行。

## 异步操作

异步事件里要处理重复点击、加载中和错误状态。

```tsx
function SubmitButton() {
  const [submitting, setSubmitting] = React.useState(false);

  async function handleSubmit() {
    if (submitting) return;

    setSubmitting(true);
    try {
      await submitForm();
    } finally {
      setSubmitting(false);
    }
  }

  return (
    <button disabled={submitting} onClick={handleSubmit}>
      {submitting ? "提交中" : "提交"}
    </button>
  );
}
```

如果异步动作和组件生命周期绑定很强，后面再结合 [[2.1.8 副作用|副作用]] 一起看会更自然。

异步事件还要考虑错误是否属于用户可恢复。比如保存草稿失败可以提示重试，删除资源失败要恢复按钮状态，支付失败要给出明确原因。不要只在控制台打印错误。

```tsx
async function handleDelete() {
  if (!confirm("确认删除？")) return;

  setDeleting(true);
  setError(null);

  try {
    await deleteUser(userId);
  } catch {
    setError("删除失败，请稍后重试");
  } finally {
    setDeleting(false);
  }
}
```

如果组件可能在请求返回前卸载，且请求结果会 setState，就要结合取消标记、AbortController 或数据请求库处理。用户点击触发的请求放在事件里，但生命周期清理仍然可能需要 effect。

## 命名方式

组件内可以保留 DOM 风格事件名，对外 props 更适合业务语义。

```tsx
type ModalProps = {
  onClose: () => void;
  onConfirm: () => void;
};
```

`onClick` 更像按钮自身事件，`onDeleteUser`、`onSubmitOrder` 更像业务动作。命名越贴近业务，调用方越容易读懂。

组件内部事件处理器可以叫 `handleClick`、`handleSubmit`，因为它们离 DOM 很近；组件对外暴露的回调应该提升到业务层。

```tsx
type DeleteButtonProps = {
  onDelete: () => void;
};

function DeleteButton({ onDelete }: DeleteButtonProps) {
  return <button onClick={onDelete}>删除</button>;
}
```

如果组件本身就是一个基础按钮，对外用 `onClick` 合理；如果组件表达业务动作，对外用业务动词更清楚。命名本身就是组件边界的一部分。

## 事件边界

| 场景 | 更合适的放置位置 |
| --- | --- |
| 简单点击 | 组件内事件处理器 |
| 需要共享状态 | 上提到父组件 |
| 与请求绑定 | 事件处理器 + 状态 |
| 与生命周期绑定 | 副作用或自定义 hook |

事件处理器最适合做“用户意图入口”。只要把输入、状态和副作用边界分清，交互会稳定很多。

用户事件和副作用最大的区别是“原因”。用户点击导致提交，应该在事件处理器里；某个外部连接需要随 `roomId` 改变而重连，应该在 effect 里。把原因写对，代码自然更好读。

事件处理也要尊重原生语义。能用 `<button>` 就不要用 `<div onClick>` 模拟按钮；必须模拟时，要补键盘事件、角色和焦点处理。交互不只是鼠标点击，也包括键盘、屏幕阅读器和移动端触摸。
