## 同步职责

副作用是组件和外部系统同步的地方，比如网络请求、订阅、定时器、手动 DOM 操作、第三方实例初始化和页面标题更新。

```tsx
React.useEffect(() => {
  const timer = window.setInterval(() => {
    console.log("tick");
  }, 1000);

  return () => window.clearInterval(timer);
}, []);
```

渲染阶段只负责根据输入计算 UI，副作用则负责“开始连接”和“断开连接”。这条边界如果混乱，组件就会越来越难维护。

React 的渲染阶段应该保持纯净：相同的 props、state、context 输入，应当得到相同的 JSX 输出。读取时间、修改 DOM、发请求、订阅事件、写本地存储，这些都会把组件和外部世界连接起来，因此应该放到事件处理器或 effect 中。

```tsx
function BadCounter({ count }: { count: number }) {
  localStorage.setItem("count", String(count));
  return <span>{count}</span>;
}
```

这类写法把外部写入放进渲染阶段，未来在严格模式、并发渲染或重复渲染下都可能产生意外。更合适的做法是让渲染只描述 UI，副作用负责同步。

```tsx
function Counter({ count }: { count: number }) {
  React.useEffect(() => {
    localStorage.setItem("count", String(count));
  }, [count]);

  return <span>{count}</span>;
}
```

## 创建与清理

`useEffect` 最重要的习惯是和清理函数成对出现。

```tsx
React.useEffect(() => {
  function handleResize() {
    setSize({ width: window.innerWidth, height: window.innerHeight });
  }

  handleResize();
  window.addEventListener("resize", handleResize);

  return () => window.removeEventListener("resize", handleResize);
}, []);
```

创建什么，就清理什么。订阅什么，就退订什么。定时器、事件监听、WebSocket、第三方实例都属于这类资源。

开发环境下 React Strict Mode 可能会让 effect 执行“挂载 -> 清理 -> 再挂载”的额外检查，用来暴露清理不完整的问题。看到 effect 执行两次时，不要立刻用 ref 绕过，而要先检查这个 effect 是否具备幂等和清理能力。

```tsx
React.useEffect(() => {
  const connection = createConnection(roomId);
  connection.connect();

  return () => {
    connection.disconnect();
  };
}, [roomId]);
```

如果清理函数完整，这种重复检查不会造成资源泄露。反过来，如果没有清理，WebSocket、事件监听、定时器很快就会出现重复连接和重复回调。

## 依赖数组

依赖数组应该反映 effect 真正使用到的外部值。

```tsx
React.useEffect(() => {
  document.title = `${count} - Dashboard`;
}, [count]);
```

不要为了“少执行几次”刻意删依赖。少写依赖往往只是把问题藏起来，等值变化后再用旧数据出错。

依赖数组表达的是 effect 读取了哪些响应式值。组件内的 props、state、上下文值、组件内定义的函数和对象，只要在 effect 中使用，就应该进入依赖考虑范围。真正要减少依赖时，应该调整代码结构，而不是手动删除依赖。

```tsx
React.useEffect(() => {
  const options = {
    roomId,
    serverUrl,
  };

  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, [roomId, serverUrl]);
```

如果对象只在 effect 内部使用，就把对象创建放进 effect 内部，避免外部对象每次渲染都变成新引用。依赖问题通常是结构问题，不是数组语法问题。

## 请求逻辑

数据请求可以放在 effect 里，但要处理竞态和卸载。

```tsx
React.useEffect(() => {
  let cancelled = false;

  async function load() {
    const response = await fetch("/api/users");
    const data = await response.json();

    if (!cancelled) {
      setUsers(data);
    }
  }

  load();

  return () => {
    cancelled = true;
  };
}, []);
```

如果请求是由用户操作触发，通常放在事件处理器里更自然；如果是页面进入就要加载的数据，effect 更合适。

请求 effect 要考虑竞态、取消、错误和加载状态。只处理成功路径，会让页面在快速切换筛选条件、路由变化或组件卸载时出现旧数据覆盖新数据。

```tsx
React.useEffect(() => {
  const controller = new AbortController();

  async function load() {
    setLoading(true);

    try {
      const response = await fetch(`/api/users?keyword=${keyword}`, {
        signal: controller.signal,
      });
      setUsers(await response.json());
    } catch (error) {
      if (!controller.signal.aborted) {
        setError(error);
      }
    } finally {
      if (!controller.signal.aborted) {
        setLoading(false);
      }
    }
  }

  load();

  return () => controller.abort();
}, [keyword]);
```

真实项目里，如果请求涉及缓存、重试、去重、分页、预加载和服务端状态同步，通常会交给 React Query、SWR、框架数据层或路由加载器，而不是每个组件手写 effect。effect 能做请求，但不代表它是所有数据获取的最佳抽象。

## 同步边界

很多 effect 其实是在同步派生值，而不是做真正副作用。

```tsx
const fullName = `${firstName} ${lastName}`;
```

能直接在渲染阶段算出来的值，就不要再同步到 state。只有当逻辑确实依赖外部系统时，才值得使用 effect。

派生状态同步是 effect 滥用的高发区。下面写法会多一次渲染，并且容易在依赖遗漏后得到旧值。

```tsx
const [fullName, setFullName] = React.useState("");

React.useEffect(() => {
  setFullName(`${firstName} ${lastName}`);
}, [firstName, lastName]);
```

如果值只由当前 props/state 推导，直接计算即可。

```tsx
const fullName = `${firstName} ${lastName}`;
```

只有当推导非常昂贵时，才考虑 `useMemo`。即使使用 `useMemo`，它仍然是渲染阶段的计算缓存，不是副作用。

## 失效处理

effect 里经常要处理旧请求晚于新请求返回的问题。

```tsx
React.useEffect(() => {
  let active = true;

  async function load() {
    const response = await fetch(`/api/items?filter=${filter}`);
    const data = await response.json();

    if (active) {
      setItems(data);
    }
  }

  load();

  return () => {
    active = false;
  };
}, [filter]);
```

如果一个 effect 里同时有很多依赖、很多条件和很多同步动作，通常说明逻辑该拆分了。

effect 最好按同步目标拆分，而不是把“组件挂载后要做的事”全塞进一个 effect。同步标题、订阅窗口、请求数据、初始化第三方实例，分别对应不同外部系统，依赖和清理方式也不同。

```tsx
React.useEffect(() => {
  document.title = title;
}, [title]);

React.useEffect(() => {
  window.addEventListener("resize", handleResize);
  return () => window.removeEventListener("resize", handleResize);
}, [handleResize]);
```

拆分后，每个 effect 的触发原因更清楚，调试时也更容易判断是哪条同步链路出了问题。

## 不该使用

| 场景 | 更好的选择 |
| --- | --- |
| 渲染时就能算出来 | 普通变量 |
| 纯派生状态 | `useMemo` 或直接计算 |
| 用户点击触发 | 事件处理器 |
| 持久连接 | effect |
| DOM 读写同步 | effect + ref |

把副作用和纯计算分开，React 组件会更稳定，也更容易推理。

还有一类逻辑不该放进 effect：由用户事件直接触发的动作。比如点击按钮后提交表单、选择商品后加入购物车、上传文件后显示进度，这些动作发生的原因是事件，而不是“组件渲染到了某种状态”。

```tsx
function BuyButton({ productId }: { productId: string }) {
  async function handleClick() {
    await buyProduct(productId);
  }

  return <button onClick={handleClick}>购买</button>;
}
```

如果把这类逻辑写成“state 改变后 effect 自动提交”，代码会更绕，也更容易因为重复渲染或状态恢复产生重复请求。事件处理器表达意图，effect 表达同步关系，这条边界非常关键。

## 与 Ref 的关系

effect 常常和 [[2.1.9 Ref|Ref]] 一起出现：effect 负责同步外部系统，ref 负责保存不触发渲染的对象或节点。两者配合好，组件会干净很多。

ref 还能用来保存外部实例，例如播放器、图表、地图对象。effect 创建实例并清理，ref 保存实例引用，事件处理器再通过 ref 调用实例方法。

```tsx
function Chart({ data }: { data: number[] }) {
  const containerRef = React.useRef<HTMLDivElement | null>(null);
  const chartRef = React.useRef<ChartInstance | null>(null);

  React.useEffect(() => {
    if (!containerRef.current) return;

    chartRef.current = createChart(containerRef.current);
    return () => {
      chartRef.current?.destroy();
      chartRef.current = null;
    };
  }, []);

  React.useEffect(() => {
    chartRef.current?.setData(data);
  }, [data]);

  return <div ref={containerRef} />;
}
```

这个例子里，初始化和数据同步是两个不同 effect。这样比一个 effect 里同时创建实例、更新数据、处理销毁更清楚，也更不容易误触发重建。
