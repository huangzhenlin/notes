## App 目录

Next.js App Router 以 `app` 目录组织页面、布局和接口。目录结构本身就是路由结构的一部分。

这意味着目录设计不是纯整理问题，而是功能边界问题。`app` 下的每一层目录，都会直接影响页面、布局、加载态和错误边界的组合方式。

```text
app/
  page.tsx
  layout.tsx
  users/
    page.tsx
```

目录存在不代表路由公开，只有当目录里有 `page.tsx` 或 `route.ts` 时，它才会成为页面或接口入口。这种设计让页面、布局和局部文件可以按功能聚合在一起。

App Router 的目录结构同时承担三件事：URL 结构、渲染边界、体验边界。比如在某个目录下放 `loading.tsx`，就是给这个路由段设置加载边界；放 `error.tsx`，就是给这个路由段设置错误边界。目录不是单纯的文件夹，而是 Next 运行模型的一部分。

```text
app/
  products/
    layout.tsx
    loading.tsx
    page.tsx
    [id]/
      page.tsx
```

这意味着目录设计越清楚，后续数据获取、加载态和错误处理越容易落到正确位置。

## 特殊文件

App Router 通过特殊文件表达页面能力。

| 文件 | 作用 |
| --- | --- |
| `page.tsx` | 页面入口 |
| `layout.tsx` | 共享布局 |
| `loading.tsx` | 路由段加载状态 |
| `error.tsx` | 路由段错误边界 |
| `not-found.tsx` | 404 页面 |
| `route.ts` | 路由接口 |

这些文件会形成嵌套层级。父 `layout` 包裹子路由，`loading` 和 `error` 也会尽量只影响当前路由段，避免整页都被阻塞。

项目结构设计时，最重要的是让“页面入口”“共享壳层”“局部状态”分别待在该待的位置里。这样后面加新路由、改布局或插入 loading/error 时，影响面会更可控。

这些特殊文件可以按职责理解：`page` 负责“这里有什么内容”，`layout` 负责“这片区域共享什么壳”，`loading` 负责“等待时看到什么”，`error` 负责“失败时如何局部恢复”，`not-found` 负责“资源不存在时如何结束”，`route` 负责“这个路径是否提供 HTTP 接口”。

不要把这些职责混在一个文件里。比如在 `page.tsx` 里手写一堆加载状态和错误兜底，有时能工作，但路由段级体验就不如约定文件清楚。

## 路由分组

路由组用括号目录组织代码，但不影响 URL。

```text
app/
  (marketing)/
    page.tsx
  (dashboard)/
    layout.tsx
    users/
      page.tsx
```

它适合把营销页、后台页、认证页分开管理，同时为不同区域使用不同布局和中间策略。

路由组的价值还在于让代码阅读和 URL 结构解耦。URL 保持干净，目录则按业务域、权限域或交互域组织，这对大型项目特别有帮助。

路由组常见的划分方式有三类：按布局体系分，比如 `(marketing)` 和 `(dashboard)`；按权限域分，比如 `(public)` 和 `(protected)`；按业务域分，比如 `(shop)` 和 `(account)`。选择哪种，要看项目里最稳定的边界是什么。

```text
app/
  (public)/
    login/
      page.tsx
  (protected)/
    dashboard/
      page.tsx
```

路由组不改变 URL，也不自动提供权限隔离。权限仍然需要在页面、服务端数据层或 Middleware 中明确处理。

## 静态资源

`public` 用于放静态资源。

```text
public/
  logo.svg
  favicon.ico
```

这些资源会以站点根路径直接访问。需要参与打包、压缩或模块引用的资源，应该放到源码目录里。

`public` 里的资源不会经过模块打包，也不会自动获得基于内容哈希的引用管理。适合 favicon、robots.txt、公开图片、下载模板这类稳定静态文件；组件中引用并希望构建工具处理的图片，更适合放进源码并通过 import 使用。

```tsx
import logo from "@/assets/logo.svg";
```

如果资源需要权限控制，就不应该直接放在 `public`。`public` 的资源默认可以被知道路径的人访问。

## 源码目录

`src` 是可选的源代码根目录。

```text
src/
  app/
  components/
  lib/
```

大项目通常会把 `components`、`features`、`lib`、`server`、`styles` 等目录放在 `src` 下，减少根目录混乱。

如果项目还包含 `services`、`hooks`、`types`、`config` 之类目录，也应该尽量保持职责稳定。目录名不求多，但求一眼能看出是页面、组件、工具还是服务端能力。

Next 项目里经常会有服务端专用代码和客户端可用代码。建议在目录上明确边界，例如 `server` 放数据库、鉴权、内部 API 调用；`lib` 放环境无关工具；`components` 放 UI；`features` 放业务模块。不要让客户端组件误导入服务端文件。

```text
src/
  app/
  components/
  features/
  lib/
  server/
```

如果服务端文件包含数据库连接、私钥读取或 Node 专属 API，就应该避免被客户端边界导入。目录命名和导入规则越清楚，越不容易发生 bundle 泄露或构建失败。

## Server 与 Client

App Router 默认是 Server Component。只有需要浏览器能力时，才使用 `use client`。

```tsx
"use client";

export function SearchBox() {
  return <input onChange={(event) => console.log(event.target.value)} />;
}
```

能留在服务端的逻辑就尽量留在服务端，这样可以减少客户端 JavaScript，也能避免把数据库凭证、私有逻辑暴露给浏览器。

项目结构上也要服务这个原则。交互组件可以放在 `components/client` 或靠近页面的局部目录里，服务端数据组件可以留在页面目录或 `server` 能力附近。关键不是目录名一定怎么叫，而是团队能一眼看出哪些文件会进入浏览器。

## 结构判断

| 文件 | 应该放什么 |
| --- | --- |
| `page.tsx` | 当前路由的主体内容 |
| `layout.tsx` | 共享壳层 |
| `loading.tsx` | 进入中的过渡状态 |
| `error.tsx` | 局部错误兜底 |
| `route.ts` | API/Route Handler |

Next 的项目结构本质上是“按路由组织代码”。路由边界越清楚，后面的导航、渲染和数据获取就越顺。

所以在 Next 里，先搭结构往往比先堆业务代码更重要。结构一旦清楚，后面每个页面该放哪类文件、哪些逻辑能上移、哪些交互要下沉，都会更自然。

一个实用判断是：如果某段代码和 URL 强相关，放在 `app` 对应路由附近；如果它跨多个页面复用，放到 `components`、`features` 或 `lib`；如果它只能在服务端运行，放到明确的服务端目录。Next 的结构不是为了追求层级多，而是为了让运行位置和业务边界可见。
