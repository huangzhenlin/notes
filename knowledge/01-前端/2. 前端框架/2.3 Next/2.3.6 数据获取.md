## 获取策略

Next 的数据获取重点不只是“在哪里 fetch”，还包括缓存、失效、同步和首屏体验。

真正需要先想的不是语法，而是数据生命周期。首屏必需数据、用户操作后刷新数据、低频缓存数据、私有敏感数据，通常会落在不同层。

同一个接口，在服务端获取、客户端获取、Route Handler 中转，体验和风险都不同。服务端获取更利于首屏和隐藏敏感信息，客户端获取更适合交互后的局部更新，Route Handler 更适合封装边界。

数据获取位置应该跟数据权威、缓存时机和用户体验绑定。首屏必须出现的公开内容，优先服务端获取；用户点击后才需要的数据，客户端获取更自然；需要隐藏后端密钥或聚合多个服务时，Route Handler 更合适。

## 服务端获取

在 Server Component 中可以直接 `await fetch`。

```tsx
export default async function Page() {
  const res = await fetch("https://api.example.com/posts");
  const posts = await res.json();

  return <PostList posts={posts} />;
}
```

这能把数据获取和首屏渲染放在一起，减少客户端补请求。

服务端获取尤其适合首屏必须展示的数据，比如文章详情、商品信息、公开列表和 SEO 页面。浏览器拿到 HTML 时已经有主要内容，不需要等客户端 JS 再发一次请求。

如果服务端拿到的数据还要继续传给客户端组件，记得这部分数据也会成为边界的一部分。越接近服务端，越适合做权限和敏感信息处理。

服务端获取时可以先裁剪数据，只把客户端需要展示或交互的字段传下去。

```tsx
export default async function Page() {
  const user = await getCurrentUser();

  return (
    <ProfileClient
      user={{
        id: user.id,
        name: user.name,
      }}
    />
  );
}
```

不要把完整数据库实体直接传给客户端组件。它可能包含权限位、内部状态、审计字段或敏感信息。

## 缓存与重验证

Next 在服务端会对 `fetch` 做缓存和重验证支持。页面是静态还是动态，常常不只是由组件决定，也由请求策略决定。

```tsx
await fetch("https://api.example.com/posts", {
  next: { revalidate: 60 },
});
```

数据频繁变化时，要考虑重新验证；数据稳定时，可以更积极地利用缓存。

缓存策略要和业务语义绑定。商品详情可能允许短暂缓存，库存和价格可能需要更频繁刷新，用户私有数据通常不应该被公共缓存错误复用。不要把所有请求都写成同一种缓存策略。

Next 的 `fetch` 缓存和页面动态性会互相影响。带有用户身份、Cookie、请求头或实时变化的数据，往往不适合静态缓存；公开且变化低频的数据，可以使用 `revalidate` 降低后端压力。

```tsx
await fetch("https://api.example.com/products", {
  next: { revalidate: 300 },
});

await fetch("https://api.example.com/me", {
  cache: "no-store",
});
```

同一个页面里也可能同时存在可缓存数据和不可缓存数据，关键是给它们设不同边界，而不是整页一刀切。

## 客户端获取

如果页面不需要预渲染，或者数据会频繁变化，也可以在客户端获取。

```tsx
useEffect(() => {
  fetch("/api/users").then((res) => res.json()).then(setUsers);
}, []);
```

客户端获取更适合局部刷新、强交互页面和无需 SEO 的区域，但通常会更依赖加载状态。

例如搜索建议、实时筛选、仪表盘局部刷新、用户操作后的重新拉取，都更适合客户端获取。它的代价是需要处理 loading、error、empty、retry，以及组件卸载后的取消。

客户端获取不要只写成功路径。用户快速切换筛选条件、网络失败、组件卸载、重复点击都会影响结果。复杂场景可以使用 SWR、React Query 或框架数据层处理缓存、去重和重试。

```tsx
React.useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${keyword}`, { signal: controller.signal })
    .then((response) => response.json())
    .then(setResults)
    .catch((error) => {
      if (!controller.signal.aborted) {
        setError(error);
      }
    });

  return () => controller.abort();
}, [keyword]);
```

## 路由接口

数据也可以先经由 Route Handler 再返回给客户端。

```ts
export async function GET() {
  return Response.json({ ok: true });
}
```

这种方式适合统一封装、复用逻辑、保护后端接口或做中间层适配。

Route Handler 还适合隐藏真实后端地址、注入服务端凭证、聚合多个接口和统一错误格式。但它不是万能代理，如果只是简单转发，也要评估是否增加了不必要的链路延迟。

Route Handler 运行在服务端边界，适合承接前端不能暴露的能力，例如签名上传、支付回调适配、第三方 API 调用、统一鉴权。

```ts
export async function POST(request: Request) {
  const body = await request.json();
  const result = await createOrder(body);

  return Response.json(result);
}
```

它仍然需要做权限校验和输入校验。不要因为文件在 `app/api` 下，就默认它是安全的内部函数；它对外就是 HTTP 接口。

## 选择方式

| 场景 | 推荐 |
| --- | --- |
| 首屏需要数据 | 服务端获取 |
| 数据更新频繁 | 重验证或客户端获取 |
| 无需 SEO | 客户端获取 |
| 统一接口适配 | Route Handler |

选择数据获取位置时，可以先问三件事：这份数据是否影响首屏，是否包含敏感凭证，是否需要用户交互后频繁刷新。三个答案基本能决定它更适合服务端、客户端还是中间层。

另一个实用问题是：这份数据错一次会影响多大范围。如果错一次影响整页首屏，最好上服务端和缓存策略；如果错一次只影响局部控件，客户端获取通常就够了。

还可以按数据类型划分：公开内容适合缓存，用户私有数据适合请求时动态获取，交互临时数据适合客户端状态，提交后的结果需要触发缓存失效或重新获取。

## 流程

```text
页面初始化
  -> 服务端获取或客户端获取
  -> 缓存/重验证
  -> 渲染
  -> 交互时局部刷新
```

## 判断标准

不要只问“能不能 fetch”，而要问“这份数据应该在哪一层拿、在哪一层缓存、谁来负责失效”。

如果页面出现“刷新后数据旧”“切换路由数据没变”“客户端又补请求一次”这类问题，通常要回到数据获取策略，而不是只盯着组件渲染。Next 的数据问题很大一部分其实是缓存边界问题。

实践里最容易忽略的是服务端与客户端重复拉同一份数据。能在一个层拿完并往下传的，就不要上下一起 fetch，不然会造成重复请求和状态漂移。

数据更新后要考虑失效路径。创建订单、修改资料、发布文章之后，哪些页面和组件的缓存应该刷新，是否需要乐观更新，是否需要跳转后重新获取，这些都属于数据获取设计的一部分。只写 `fetch` 不处理失效，页面迟早会出现“保存成功但列表还是旧数据”的问题。
