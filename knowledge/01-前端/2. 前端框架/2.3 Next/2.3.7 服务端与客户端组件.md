## 组件边界

Next App Router 的默认组件是服务端组件。只有需要状态、事件、生命周期或浏览器 API 时，才使用客户端组件。

从工程角度看，这种默认值也让你更容易控制边界。需要交互的地方显式声明 `"use client"`，其余地方默认保持服务端，这样不会在无意中把整页拖进浏览器。

这个默认值很重要：Next 不是让所有 React 代码都跑在浏览器里，而是优先把不需要交互的部分留在服务器。这样可以减少客户端 bundle，也能把数据获取和权限判断放在更安全的位置。

```tsx
"use client";

export function SearchBox() {
  return <input onChange={(event) => console.log(event.target.value)} />;
}
```

服务端和客户端组件不是视觉层级，而是运行环境边界。一个页面可以大部分在服务端，只有几个按钮、输入框、弹窗在客户端。真正要避免的是为了一个交互点把整棵页面树都放进客户端。

## 服务端组件

服务端组件适合数据获取、访问密钥、减少客户端 JS 和分流渲染。

服务端组件不能使用浏览器事件，也不能直接使用 `useState`、`useEffect` 这类客户端 Hook。它的优势是运行在服务器，能访问后端资源，能把渲染结果以更轻的形式传给客户端。

因此服务端组件很适合做“数据整形”和“权限分流”：先拿到原始数据，再按页面需要裁剪成可传递的内容。客户端只接收最终可展示、可交互的结果。

```tsx
export default async function Page() {
  const data = await getData();
  return <div>{data.title}</div>;
}
```

服务端组件可以直接访问服务端环境变量、数据库客户端和内部接口，但返回给客户端组件的数据必须经过裁剪。不要把“服务端能读到”误解成“都可以传下去”。

```tsx
const user = await getUser();

return <UserMenu user={{ id: user.id, name: user.name }} />;
```

这类裁剪不只是为了序列化成功，也是为了边界更清楚。客户端组件通常并不需要完整后端模型，只需要完成交互所需的最小字段。数据传得越少，安全性、调试性和可维护性通常越好。

## 客户端组件

客户端组件适合状态、事件、浏览器 API 和自定义 Hook。

一旦文件顶部写了 `"use client"`，这个文件及其客户端依赖都会进入浏览器侧边界。因此客户端组件应该尽量小，最好只包住真正需要交互的部分。

如果一个组件只是为了用到一个小 Hook 就变成客户端组件，通常是不划算的。更好的方式是把那段交互拆到最小粒度，再把其余内容留在服务端。

```tsx
"use client";

export default function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

客户端组件应该尽量靠近交互点。比如商品详情页里，正文、价格说明、规格说明可以是服务端组件，收藏按钮和加入购物车按钮是客户端组件。这样能减少 hydration 和浏览器 JS 成本。

客户端组件还要谨慎对待第三方库。图表、地图、编辑器、播放器这类库往往体积大、依赖浏览器对象强，更适合被限制在很小的交互区域里，必要时再结合动态加载，而不是一开始就把整页拖进客户端。

## 边界传递

服务端组件可以把数据通过 props 传给客户端组件。

```tsx
<LikeButton likes={post.likes} />
```

传过去的 props 需要能被序列化，不能随便传函数、类实例或不可序列化对象。

这条规则背后是运行环境不同：服务端组件的结果需要跨边界传到客户端。如果一个值无法稳定序列化，客户端就无法正确恢复它。日期、Map、类实例、函数、数据库连接都要特别注意。

如果遇到序列化问题，先想“这个值真的需要传过去吗”。很多时候真正需要传的是 id、状态码或精简后的展示数据，而不是完整对象。

日期、Map、Set、类实例、函数、数据库模型对象都容易在边界上出问题。把它们转换成字符串、数组或普通对象，再传给客户端组件，会更稳定。

```tsx
<EventCard
  event={{
    id: event.id,
    startTime: event.startTime.toISOString(),
  }}
/>
```

边界数据越简单，客户端越容易接收，缓存和调试也更清楚。

一个很实用的习惯是把传给客户端的 props 当成一份“公开传输协议”来看待。只暴露最小字段、最稳定结构，后面无论是重构服务端实现，还是替换客户端组件，成本都会更低。

## 子树嵌套

服务端组件也可以作为子树传入客户端组件。

```tsx
<Modal>
  <Cart />
</Modal>
```

这很适合“外壳客户端、内容服务端”的组合模式。

例如一个 Modal 需要开关状态，所以外壳是客户端组件；但弹窗里的商品详情可以来自服务端组件。这样既保留交互，又不会把整块内容都打进客户端 JS。

这种组合模式也很适合列表页、抽屉页和详情浮层。页面外壳负责控制交互，内容区域尽量服务端化，整体体验通常会更轻。

这种模式可以理解成“客户端组件提供交互容器，服务端组件提供内容”。它让弹窗开关、tab 切换、抽屉展开这些交互留在浏览器，同时避免把内容获取和渲染全部客户端化。

这类嵌套特别适合做“交互壳 + 服务端内容块”。例如搜索面板、筛选抽屉、侧边详情栏、购物车弹窗，外壳负责显隐和局部状态，内容本身仍然可以利用服务端数据获取和缓存优势。

## 选择原则

| 能力 | 适合组件 |
| --- | --- |
| 数据获取 | 服务端 |
| 浏览器事件 | 客户端 |
| 密钥和令牌 | 服务端 |
| 交互表单 | 客户端 |
| 纯展示 | 服务端 |

判断时可以把问题变成一句话：这段代码是否需要浏览器。如果不需要，先放服务端；如果需要，再把最小区域切成客户端组件。这个顺序通常比先写客户端再优化更稳。

更细的判断可以看四件事：是否需要事件处理，是否需要浏览器 API，是否需要本地状态，是否依赖客户端 Hook。只要命中其中之一，就需要客户端边界；否则优先服务端。

再进一步看，很多组件其实不是非黑即白。页面主体可以是服务端，局部表单是客户端；弹窗壳是客户端，弹窗内容可以继续是服务端；布局是服务端，主题切换按钮是客户端。理解“按区域切边界”比死记规则更重要。

## 误区

| 误区 | 问题 |
| --- | --- |
| 一点交互就整页客户端化 | JS 太大 |
| 把秘密放进客户端组件 | 可能泄露 |
| 传不可序列化值 | 边界失败 |

服务端和客户端的分界，最终目标是让每段逻辑都在它最适合的环境里运行。

判断一个组件该放哪边时，可以先看它是否需要浏览器事件、是否需要本地状态、是否需要直接访问窗口对象。三个答案都是否定时，通常就没必要放客户端。

最常见的坏味道是“页面顶部为了一个按钮写了 `use client`”。这会让整页都变成客户端边界，既增加 JS，也让原本能在服务端完成的数据和权限逻辑被迫迁移。更好的做法是把按钮抽成小组件。

另一个坏味道是把第三方客户端库放到服务端组件里直接导入。图表、地图、富文本编辑器、播放器通常依赖浏览器对象，应该放进客户端组件，并必要时动态加载。否则构建或运行时可能因为 `window is not defined` 失败。

还有一个常见误区是把服务端和客户端组件的划分当成“文件夹划分”。真正重要的不是目录长什么样，而是每段代码运行在哪、依赖什么、会不会进浏览器 bundle。只要运行边界清楚，目录反而容易慢慢整理稳定。
