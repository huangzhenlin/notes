## 入口逻辑

Next Middleware 会在请求进入路由之前执行，适合做入口级判断，例如登录重定向、语言识别、A/B 实验、灰度流量和请求改写。

```ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  const loggedIn = request.cookies.has("session");

  if (!loggedIn) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  return NextResponse.next();
}
```

它像“门口的检查员”，适合做轻量、快速、全局的入口决策，不适合承载复杂业务主流程。

Middleware 的价值在于“尽早分流”。比如未登录用户不必进入后台页面渲染，语言前缀可以在路由前规范化，灰度实验可以在请求入口决定版本。但越靠前的逻辑越应该轻，因为它会影响所有匹配请求。

可以把 Middleware 理解成“全站入口层”，而不是“迷你后端”。它更适合快速判断请求下一步应该往哪走，而不是在这里完成完整业务处理。只要逻辑开始依赖复杂上下文、重型查询或细粒度资源判断，就说明它已经不太适合继续停留在入口层了。

## 执行位置

Middleware 在路由处理之前执行，所以它能影响后续请求流向。

```text
浏览器请求
  -> Middleware
  -> 路由匹配
  -> 页面 / Route Handler
  -> 响应
```

这种位置让它很适合做重定向和改写，但也意味着它一旦变慢，就会拖慢所有匹配请求。中间件里不要做重型数据库查询、复杂计算或大量外部网络请求。

Middleware 的运行环境和普通 Node 服务端代码不完全一样，很多场景接近 Edge Runtime。不要默认可以使用所有 Node API，也不要把数据库客户端、文件系统读取、重型加密计算放进去。复杂判断应该下沉到服务端页面、Route Handler 或后端服务。

执行位置越靠前，对响应延迟的放大就越明显。页面里慢一次可能只影响一个路由，请求入口慢一次往往会影响整批匹配路径。所以 Middleware 的第一原则通常不是“功能能不能实现”，而是“这件事是否值得放在所有请求最前面做”。

## 路径匹配

`matcher` 用于限制 Middleware 生效范围。

```ts
export const config = {
  matcher: ["/dashboard/:path*", "/settings/:path*"],
};
```

不要默认让所有静态资源、图片、脚本、API 都穿过 Middleware。匹配范围越精确，性能和行为越可控。

`matcher` 应该尽量排除静态资源和不需要处理的路径。否则图片、字体、脚本等请求也会经过中间件，带来额外开销和意外行为。

```ts
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

更好的方式是只匹配真正需要入口判断的业务路径，例如 `/dashboard/:path*`、`/settings/:path*`。

路径匹配设计得越精确，中间件越稳定。很多线上性能问题并不是逻辑本身多复杂，而是 matcher 过宽，导致本来不该经过入口层的请求也被拦了一遍。先缩范围，往往比继续优化中间件代码更有效。

## 重定向与改写

重定向会改变浏览器地址，改写则在服务端内部把请求交给另一个路径处理。

```ts
export function middleware(request: NextRequest) {
  const url = request.nextUrl.clone();

  if (url.pathname === "/old") {
    url.pathname = "/new";
    return NextResponse.redirect(url);
  }

  return NextResponse.next();
}
```

重定向适合登录、迁移旧地址、规范化路径；改写适合灰度、区域化内容、内部代理。

重定向会让浏览器地址栏变化，适合用户应该知道目标已变的场景；改写不会改变地址栏，适合内部路由到不同实现。灰度、A/B 实验、区域化内容经常使用 rewrite。

```ts
if (bucket === "b") {
  url.pathname = `/variant-b${url.pathname}`;
  return NextResponse.rewrite(url);
}
```

选择 redirect 还是 rewrite，要看 URL 是否应该成为用户可见事实。

一个简单判断是：如果用户应该知道自己已经去了新地址，就用 redirect；如果只是服务器内部想把同一个入口分流到不同实现，而不希望用户感知，就更偏向 rewrite。这个区分在多语言、灰度和旧地址迁移里尤其常见。

## Cookie 与 Header

Middleware 可以读取 Cookie，也可以调整请求或响应头。

```ts
export function middleware(request: NextRequest) {
  const locale = request.cookies.get("locale")?.value ?? "zh-CN";
  const response = NextResponse.next();

  response.headers.set("x-locale", locale);
  return response;
}
```

这类能力适合上下文注入，但要避免把敏感信息写进可被客户端读取的 header。身份凭证、内部 token、权限细节仍然应该保持服务端私有。

Middleware 可以设置响应 Cookie 或读取请求 Cookie，但不要在这里做完整会话系统。比如刷新 token、细粒度权限、资源归属校验，这些通常需要更可靠的服务端逻辑和审计。

```ts
const response = NextResponse.next();
response.cookies.set("locale", locale, {
  path: "/",
  sameSite: "lax",
});
```

Cookie 和 Header 更适合作为“上下文传递工具”，而不是“权限真相本身”。比如语言、来源标记、实验桶、轻量追踪信息适合在这里处理；真正的登录态可信校验、资源归属和高敏感凭证仍然应该交给更靠后的服务端层处理。

## 鉴权入口

Middleware 可以做粗粒度登录拦截。

```ts
export function middleware(request: NextRequest) {
  const token = request.cookies.get("session")?.value;

  if (!token && request.nextUrl.pathname.startsWith("/dashboard")) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  return NextResponse.next();
}
```

但细粒度权限仍然要在服务端接口或页面数据层检查。Middleware 可以判断“有没有票”，不能只靠它判断“这张票能不能操作某条具体数据”。

例如 `/projects/123/settings` 是否能访问，不只是用户有没有登录，还要看用户是否属于项目 123、是否有管理权限。这类资源级授权通常需要查服务端数据，应该在页面数据层或 API 层再次判断。

因此更稳的做法通常是“两段式”：Middleware 负责粗筛，比如未登录先拦；页面或接口再做细查，比如这个用户是否真的能访问某个项目、某条订单、某个组织。这样既保留入口体验，也不会把最终权限判断做轻了。

## 适用边界

| 场景 | 是否适合 |
| --- | --- |
| 登录入口拦截 | 适合 |
| 多语言重定向 | 适合 |
| A/B 分流 | 适合 |
| 复杂权限表查询 | 不适合 |
| 大量数据聚合 | 不适合 |

Middleware 越轻越好。它的价值是提前改变请求方向，而不是替代页面、接口和后端服务的业务判断。

可以把 Middleware 的边界记成三句话：适合入口级、适合轻量级、适合无状态或弱状态判断。不适合复杂业务、不适合重查询、不适合替代最终鉴权。只要它开始像一个完整后端服务，就说明边界已经过重了。

从排障角度看，也建议把“入口问题”和“业务问题”分开定位。先确认中间件是否把请求正确送到了目标路径，再确认页面或接口内部的权限、数据和渲染是否正确。这样出问题时不会一上来就在多个层里来回猜。
