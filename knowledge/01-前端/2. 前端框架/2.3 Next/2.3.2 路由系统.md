## 文件路由

Next.js App Router 用文件系统组织页面。`page.tsx` 决定一个路径是否真正对外可访问。

文件路由的优点是结构直观：目录就是 URL，文件就是路由能力。但这也意味着目录设计会直接影响学习成本和维护成本，不能把所有页面随手塞进一层目录。

```text
app/
  page.tsx
  users/
    page.tsx
```

只有目录下存在 `page` 或 `route` 文件时，这个段才会公开。文件结构和路由结构是一一对应的。

这条规则能帮助判断“为什么目录存在但访问不到”。普通目录只是组织代码，只有特定约定文件才会让路由对外暴露。

App Router 里除了 `page.tsx`，还有一组约定文件共同定义路由段行为：`layout.tsx` 定义共享布局，`loading.tsx` 定义加载态，`error.tsx` 定义错误边界，`not-found.tsx` 定义 404，`route.ts` 定义接口处理。理解这些文件，比只记页面路径更重要。

```text
app/
  dashboard/
    layout.tsx
    loading.tsx
    error.tsx
    page.tsx
```

一个路由段可以同时拥有页面、布局、加载和错误边界，这使得 Next 的路由结构天然和用户体验边界绑定在一起。

## 动态段

动态路由适合详情页、用户页和文章页。

```tsx
app/users/[id]/page.tsx
```

```tsx
export default function Page({ params }: { params: { id: string } }) {
  return <div>{params.id}</div>;
}
```

路径参数应该对应资源标识，而不是把完整对象塞进 URL。可分享、可刷新、可从外部进入的状态，才适合放到动态段。

动态段的重点是可恢复。只要拿到 URL，页面就应该能重新获取对应资源，而不是依赖上一个页面传来的内存对象。

动态段参数本质上来自外部输入，应该在页面入口校验。即使路径看起来是 `/users/123`，也不能假设 `id` 一定存在、格式一定正确、资源一定可访问。

```tsx
import { notFound } from "next/navigation";

export default async function Page({ params }: { params: { id: string } }) {
  const user = await getUser(params.id);

  if (!user) {
    notFound();
  }

  return <UserProfile user={user} />;
}
```

URL 负责定位资源，服务端负责确认资源是否存在和当前用户是否有权访问。

## 嵌套段

嵌套路由适合父子页面结构。

```tsx
const routes = [
  {
    path: "/settings",
    component: SettingsLayout,
    children: [
      { path: "profile", component: ProfileSettings },
    ],
  },
];
```

父层负责骨架和导航，子层负责具体内容。这样页面结构会更稳定。

嵌套路由最适合管理“共享框架 + 局部内容”的场景，比如后台设置、课程详情、商品管理。共享布局不应该在每个子页面重复写，否则路由切换时状态保留和加载体验都会变差。

`layout.tsx` 会包住子路由，并在同层路由切换时尽量保留。适合放导航、侧边栏、面包屑、页面框架和稳定上下文；不适合放只属于某个子页面的数据和状态。

```tsx
export default function SettingsLayout({ children }: { children: React.ReactNode }) {
  return (
    <section>
      <SettingsNav />
      {children}
    </section>
  );
}
```

如果布局里放了过多动态数据，可能会让本来可缓存的子页面受到影响。共享布局越稳定，路由切换越顺。

## 路由组

路由组用括号目录整理结构，不改变 URL。

```text
app/(marketing)/page.tsx
app/(shop)/cart/page.tsx
```

它适合把不同业务域拆开，同时保留更简洁的访问路径。

路由组常用于营销页、后台页、认证页等不同布局体系。它不改变 URL，却能让文件结构更有业务边界，适合大型项目整理目录。

路由组还可以让不同区域拥有不同根布局。例如 `(marketing)` 使用公开站点布局，`(dashboard)` 使用后台布局，但 URL 不必带上 `marketing` 或 `dashboard`。

```text
app/
  (marketing)/
    layout.tsx
    page.tsx
  (dashboard)/
    layout.tsx
    dashboard/
      page.tsx
```

它是目录组织工具，不是权限边界。后台页面是否可访问仍然要靠服务端鉴权和路由守卫式逻辑判断。

## 并行与拦截

并行路由和拦截路由适合复杂交互，比如弹窗详情、局部切换和同页多视图。

```text
@modal
(..)photo
```

这类能力很强，但也会提升理解成本。普通项目不要一开始就用到最复杂的路由形态。

并行和拦截路由适合照片弹窗、购物车侧栏、同屏多区域更新等复杂体验。如果只是普通页面跳转，用基础嵌套路由通常更清楚。

并行路由适合一个页面同时展示多个相对独立的区域，例如主内容和弹窗槽位；拦截路由适合“从列表点开详情时显示弹窗，直接访问详情 URL 时显示完整页面”。这类能力的价值在于让 URL 和交互状态同时成立。

```text
app/
  feed/
    page.tsx
    @modal/
      (..)photo/[id]/page.tsx
```

使用前要确认团队能维护这套模型。并行与拦截很强，但会让目录语义和跳转行为更复杂，不适合为普通弹窗滥用。

## 路由边界

| 数据 | 适不适合放路由 |
| --- | --- |
| `id` | 适合 |
| 搜索词 | 适合 |
| 分页页码 | 适合 |
| 完整对象 | 不适合 |
| 临时草稿 | 不适合 |

如果某个状态需要分享、刷新后保留、从外部链接进入，就更适合进入 URL；如果某个状态只在当前页面短暂存在，就更适合留在组件状态或缓存里。

搜索词、分页、排序、筛选通常适合 query，因为它们描述当前列表视图。弹窗输入草稿、未提交表单、临时展开状态不适合放 URL，因为它们只属于当前交互过程。

```tsx
import { redirect } from "next/navigation";

export default function Page({ searchParams }: { searchParams: { page?: string } }) {
  const page = Number(searchParams.page ?? "1");

  if (!Number.isInteger(page) || page < 1) {
    redirect("/users?page=1");
  }

  return <UserList page={page} />;
}
```

URL 参数同样要校验。能被用户手动编辑的东西，就不能直接信任。

## 设计原则

路由负责位置，页面负责内容，数据层负责状态。只要这三层不混，路由系统就会很好用。

Next 路由设计不要只看“路径怎么写”，还要看页面是否需要共享布局、是否需要加载态、是否需要错误边界、是否会影响数据缓存。这些都和 `app` 目录结构绑定在一起。

一个实用设计顺序是：先确定业务 URL，再确定共享布局，再确定加载和错误边界，最后决定是否需要路由组、并行路由或拦截路由。先用简单结构覆盖主要路径，只有交互模型真的需要时再引入高级路由能力。
