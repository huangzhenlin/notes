## Route Handler

Next App Router 使用 `route.ts` 定义接口路由，也叫 Route Handler。它让同一个 Next 项目既能提供页面，也能提供轻量 API、Webhook、BFF 聚合层或代理层。

```text
app/
  api/
    users/
      route.ts
```

```ts
export async function GET() {
  return Response.json({ ok: true });
}
```

Route Handler 运行在服务端，不会打进浏览器 bundle，因此适合访问环境变量、服务端 SDK、数据库连接和内部接口。但它不是“所有数据获取都必须经过的一层”，Server Component 能直接访问的数据，不一定要绕一圈调用自己的接口。

Route Handler 的定位更像“前端项目里的服务端边界”。它适合给浏览器提供受控接口、接收 Webhook、做 BFF 聚合、隐藏第三方凭证；但如果页面服务端组件本来就能直接调用数据库或内部服务，再请求自己的 `/api` 反而会多一层 HTTP 成本。

```text
Server Component -> 直接调用 server 函数
Client Component -> 调用 Route Handler
外部系统 -> 调用 Webhook Route Handler
```

先判断调用方是谁，再决定是否需要 Route Handler。不要为了“统一走接口”让服务端内部也绕远路。

## 请求方法

`route.ts` 通过导出同名函数处理不同 HTTP 方法。

```ts
export async function GET() {
  const users = await listUsers();
  return Response.json(users);
}

export async function POST(request: Request) {
  const body = await request.json();
  const user = await createUser(body);
  return Response.json(user, { status: 201 });
}
```

常见方法包括 `GET`、`POST`、`PUT`、`PATCH`、`DELETE`。接口语义最好和资源操作对应：查询用 `GET`，创建用 `POST`，整体替换用 `PUT`，局部修改用 `PATCH`，删除用 `DELETE`。

方法语义会影响缓存、重试和安全策略。`GET` 应该无副作用，浏览器、代理和预取机制都可能重复触发它；状态变更必须使用写方法，并做鉴权、CSRF 或来源校验。

```ts
export async function DELETE(
  _request: Request,
  { params }: { params: { id: string } },
) {
  await deletePost(params.id);
  return new Response(null, { status: 204 });
}
```

写接口返回状态码要清楚：创建成功用 `201`，删除成功可以用 `204`，参数错误用 `400`，未认证用 `401`，无权限用 `403`，资源不存在用 `404`。

## 请求对象

Route Handler 接收 Web 标准 `Request` 对象，也可以使用 Next 扩展的 `NextRequest`。

```ts
import { NextRequest } from "next/server";

export async function GET(request: NextRequest) {
  const keyword = request.nextUrl.searchParams.get("q") ?? "";
  return Response.json({ keyword });
}
```

查询参数适合分页、筛选、搜索；请求体适合提交表单、创建资源、批量操作。不要把敏感信息放进 URL 查询参数里，URL 会进入浏览器历史、服务端日志和监控系统。

请求体一定要校验。TypeScript 类型只在开发期存在，外部请求进来时仍然是不可信数据。可以使用 schema 校验库，也可以手写最小校验。

```ts
type CreateUserBody = {
  name: string;
  email: string;
};

function isCreateUserBody(value: unknown): value is CreateUserBody {
  if (typeof value !== "object" || value === null) return false;

  const record = value as Record<string, unknown>;
  return typeof record.name === "string" && typeof record.email === "string";
}
```

不要直接 `const body = await request.json() as CreateUserBody` 后进入业务逻辑。断言不是校验，接口入口必须有运行时证据。

## 响应对象

响应可以用标准 `Response`，也可以用 `NextResponse`。

```ts
return new Response("Created", { status: 201 });
```

```ts
import { NextResponse } from "next/server";

return NextResponse.json({ message: "ok" });
```

接口响应要明确状态码。不要所有失败都返回 `200` 再在 body 里写 `success: false`，这样会让调用方、监控、重试和缓存都难以判断真实结果。

响应体也要控制字段。Route Handler 经常位于客户端和后端之间，应该在这里做字段裁剪和错误归一化，不要把后端内部错误、数据库字段或堆栈直接返回给浏览器。

```ts
try {
  const user = await createUser(body);
  return Response.json({ id: user.id, name: user.name }, { status: 201 });
} catch {
  return Response.json({ message: "create failed" }, { status: 500 });
}
```

错误信息要能帮助前端展示和排查，但不能泄露内部表名、服务名、SQL、密钥或完整堆栈。

## 参数路由

Route Handler 也可以使用动态段。

```text
app/api/users/[id]/route.ts
```

```ts
export async function GET(
  _request: Request,
  { params }: { params: { id: string } },
) {
  const user = await getUser(params.id);

  if (!user) {
    return Response.json({ message: "not found" }, { status: 404 });
  }

  return Response.json(user);
}
```

动态段适合资源标识，查询参数适合筛选条件。把两者分清，接口路径会更稳定。

动态参数同样要校验。比如 id 是否符合格式、资源是否存在、当前用户是否有权访问，都应该在 Route Handler 或底层服务中确认。

```ts
if (!/^[a-zA-Z0-9_-]+$/.test(params.id)) {
  return Response.json({ message: "invalid id" }, { status: 400 });
}
```

不要把路径参数直接拼进数据库查询或第三方 URL。所有外部输入都要先经过格式检查和权限判断。

## 鉴权边界

Route Handler 可以做鉴权和权限检查，但要注意它是服务端入口，不是前端展示逻辑。

```ts
export async function DELETE(
  _request: Request,
  { params }: { params: { id: string } },
) {
  const session = await getSession();

  if (!session) {
    return Response.json({ message: "unauthorized" }, { status: 401 });
  }

  const allowed = await canDeleteUser(session.userId, params.id);
  if (!allowed) {
    return Response.json({ message: "forbidden" }, { status: 403 });
  }

  await deleteUser(params.id);
  return new Response(null, { status: 204 });
}
```

`401` 表示未认证，`403` 表示已认证但无权限。这个边界和 [[1.6.4 鉴权|鉴权]] 是同一件事在服务端入口的落点。

Route Handler 的鉴权要按接口能力决定强度。只读公开接口可以无需登录；用户私有数据要确认会话；修改、删除、支付、上传签名这类高风险接口要额外检查资源归属和业务权限。

```text
请求进入
  -> 校验会话
  -> 校验请求体
  -> 校验资源归属
  -> 执行业务动作
  -> 返回最小响应
```

前端按钮隐藏、Middleware 登录拦截都不能替代这里的最终校验。

## BFF 聚合

Route Handler 很适合做 BFF（Backend For Frontend）：把多个后端接口聚合成更适合页面使用的数据。

```ts
export async function GET() {
  const [profile, orders, notifications] = await Promise.all([
    getProfile(),
    getRecentOrders(),
    getNotifications(),
  ]);

  return Response.json({
    profile,
    orders,
    notifications,
  });
}
```

这种方式能减少客户端多次请求，也能把后端字段转换、权限过滤、错误兜底集中到服务端处理。它适合页面视角的数据聚合，不适合把所有业务逻辑都塞进 Next 项目。

BFF 聚合要以页面需求为中心，而不是简单把后端接口再包一层。它可以减少浏览器请求次数、隐藏内部服务结构、统一错误格式，也可以根据当前用户裁剪字段。

```ts
export async function GET() {
  const session = await getSession();

  if (!session) {
    return Response.json({ message: "unauthorized" }, { status: 401 });
  }

  const dashboard = await getDashboardData(session.userId);
  return Response.json({
    profile: dashboard.profile,
    unreadCount: dashboard.unreadCount,
  });
}
```

如果聚合逻辑开始包含复杂事务、跨系统一致性、重试补偿和领域规则，就应该回到后端服务设计，而不是继续堆在 Next Route Handler 里。

## 使用边界

| 场景 | 是否适合 Route Handler |
| --- | --- |
| Webhook 接收 | 适合 |
| BFF 聚合 | 适合 |
| 保护内部接口 | 适合 |
| Server Component 内部取数 | 不一定需要 |
| 重业务事务处理 | 通常交给后端服务 |

Route Handler 最好的定位是“前端应用的服务端边界”。它能补齐页面项目里的轻量服务能力，但不应该变成没有边界的后端大杂烩。

还要注意运行时选择。有些 Route Handler 可以跑在 Edge Runtime，适合轻量、低延迟、无 Node 依赖的场景；涉及数据库驱动、文件系统、复杂 SDK 的接口通常更适合 Node.js 运行时。运行时能力和依赖要匹配，否则部署后才会暴露兼容问题。

```ts
export const runtime = "nodejs";
```

接口路由上线前至少检查：方法语义是否正确，输入是否校验，鉴权是否在服务端完成，响应字段是否最小化，错误状态码是否准确，是否误把重业务逻辑塞进了前端项目。
