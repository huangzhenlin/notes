## 部署方式

Next.js 可以部署到托管平台、Node.js 服务、Docker 容器，也可以在特定条件下做静态导出。选择部署方式时，要先看项目是否依赖服务端渲染、Route Handler、Middleware、图片优化和运行时环境变量。

```json
{
  "scripts": {
    "build": "next build",
    "start": "next start"
  }
}
```

```bash
npm run build
npm run start
```

能不能部署成功只是第一步，更重要的是缓存策略、运行时能力、错误回退和监控是否匹配业务。

部署前要先确认项目实际使用了哪些 Next 能力。只要用了 SSR、Route Handler、Middleware、图片优化、动态缓存、服务器环境变量，就不能按纯静态站点思路处理。不同部署平台对 Node Runtime、Edge Runtime、文件系统、环境变量和缓存的支持也不完全一样。

```text
页面类型
  -> 静态页面
  -> 动态 SSR 页面
  -> Route Handler
  -> Middleware
  -> 静态资源
```

每种类型的运行位置和缓存策略都要明确，否则线上问题会集中出现在“本地能跑，部署后行为不一样”。

## Node 服务

Node 部署适合需要完整 Next 服务端能力的项目。

```text
请求
  -> 负载均衡
  -> Node Next 服务
  -> 页面 / Route Handler / 静态资源
```

这种方式对 SSR、动态渲染、接口路由和中间件支持更完整。缺点是需要自己处理进程管理、日志、扩容、健康检查和滚动发布。

Node 服务部署时，要关注启动方式、健康检查、进程守护和反向代理。`next start` 适合运行 Next 构建产物，但生产环境还需要 Nginx、负载均衡、PM2、systemd、容器编排或平台服务来保证进程稳定。

```text
CDN
  -> 反向代理
  -> Next Node 服务
  -> 后端 API / 数据库
```

如果 SSR 响应变慢，不能只看前端 bundle，也要看服务端接口、数据库、缓存命中和 Node 实例资源。

## Docker 容器

Docker 适合统一运行环境，尤其适合企业内部平台、Kubernetes 或多环境交付。

```dockerfile
FROM node:20-alpine AS runner
WORKDIR /app

ENV NODE_ENV=production

COPY .next ./.next
COPY public ./public
COPY package.json ./package.json

CMD ["npm", "run", "start"]
```

真实项目里还要处理依赖安装、构建阶段、运行阶段、非 root 用户、镜像体积和环境变量注入。Docker 的价值是可复现，不是把所有问题都打包带走。

Docker 更推荐多阶段构建：构建阶段安装依赖并执行 `next build`，运行阶段只复制运行所需产物。Next 可以配合 standalone 输出减少镜像体积。

```js
// next.config.js
const nextConfig = {
  output: "standalone",
};

module.exports = nextConfig;
```

运行镜像里不要带完整源码、测试文件和开发依赖。镜像越小，拉取更快，攻击面也更小。

## 静态导出

静态导出适合纯静态站点、文档站、营销页或不依赖服务端能力的页面。

```js
// next.config.js
const nextConfig = {
  output: "export",
};

module.exports = nextConfig;
```

如果项目依赖动态 SSR、Route Handler、Middleware 或运行时接口能力，静态导出就不合适。不要为了部署简单牺牲真实需求。

静态导出适合内容稳定、无需服务端运行时的项目，例如文档、活动页、作品集。它的优势是部署简单、CDN 友好；限制是无法使用需要服务器参与的能力。选择静态导出前，要确认页面数据是否能在构建时确定，以及表单、鉴权、接口是否有外部服务承接。

## 缓存策略

部署优化离不开缓存。静态资源、页面 HTML、接口响应、图片资源的缓存策略都不同。

| 资源 | 常见策略 |
| --- | --- |
| 带 hash 静态资源 | 长缓存 |
| HTML | 短缓存或按渲染策略控制 |
| API 响应 | 按数据新鲜度控制 |
| 图片 | CDN 缓存 + 格式优化 |

缓存不是越久越好，而是要匹配数据变化频率。商品价格、库存、支付结果这类数据要谨慎；文档、图标、构建产物可以更积极。

带 hash 的静态资源可以长缓存，因为文件内容变了文件名也会变；HTML 和 RSC payload 则要跟渲染策略匹配。CDN、浏览器、Next 数据缓存和后端缓存叠在一起时，要明确哪一层负责新鲜度。

```http
Cache-Control: public, max-age=31536000, immutable
```

这类策略适合 hash 静态资源，不适合用户私有 HTML 或接口响应。缓存配置错一次，可能表现为“发布了但用户还看到旧页面”。

## 环境变量

Next 项目要区分构建时变量和运行时变量，也要区分服务端变量和客户端变量。

```text
服务端私有：DATABASE_URL、API_SECRET
客户端公开：NEXT_PUBLIC_ANALYTICS_ID
```

以 `NEXT_PUBLIC_` 开头的变量会进入客户端代码，不能放密钥。这个边界和 [[1.6.8 敏感信息|敏感信息]] 直接相关。

构建时变量和运行时变量也要区分。进入客户端 bundle 的变量在构建时就固化了，容器运行后再改环境变量不会改变已经生成的静态 JS。服务端运行时读取的变量，则取决于部署环境。

```text
NEXT_PUBLIC_* -> 客户端可见，构建时注入
服务端变量 -> 只在服务端读取，运行时可变取决于平台
```

如果同一个镜像要部署到多个环境，尤其要设计好运行时配置方式，避免为每个环境重新构建，或误把私密变量打进客户端。

## 构建产物

上线前要看构建输出，关注路由类型、包体积、静态资源和动态渲染提示。

```bash
npm run build
```

如果某个页面意外变成动态渲染，或者客户端 bundle 明显变大，要回头检查数据获取、`use client` 边界和第三方依赖。

`next build` 输出会提示路由是静态、动态还是使用了运行时能力。上线前应该把这些变化纳入审查：某个页面从静态变动态，可能意味着缓存失效、成本上升或首屏变慢；某个客户端包变大，可能是误导入了大型库。

```bash
npm run build
```

构建产物检查不是为了追求所有页面静态化，而是确认每个页面的运行方式符合预期。

## 监控与回滚

部署后的优化不只看上线成功，还要看运行质量。

```text
需要关注：
构建是否稳定
首屏指标是否退化
接口错误率是否升高
SSR 响应是否变慢
静态资源是否 404
```

回滚策略也要提前准备。前端部署最怕“能发不能退”，尤其是缓存、资源 hash、接口兼容和灰度流量混在一起时。

监控至少要覆盖三类信号：用户体验指标、服务端运行指标、前端错误指标。比如 LCP、INP、CLS 反映用户体验，SSR 响应时间和 Route Handler 错误率反映服务端质量，浏览器错误和资源加载失败反映前端发布质量。

```text
体验：LCP / INP / CLS
服务端：SSR 延迟 / API 错误率 / 冷启动
前端：JS 错误 / 资源 404 / hydration 错误
```

回滚时要考虑静态资源兼容。HTML 指向的新 hash 资源如果已经发布到 CDN，但回滚后接口协议不兼容，可能出现半新半旧状态。发布和回滚都要保证前后端接口向后兼容一段时间。

## 交付检查

| 检查项 | 目的 |
| --- | --- |
| `next build` 通过 | 确认构建稳定 |
| 关键路由可访问 | 确认页面入口正常 |
| 环境变量正确 | 避免线上配置缺失 |
| 静态资源正常 | 避免样式、图片、脚本丢失 |
| 监控已接入 | 方便上线后定位 |

部署优化的核心是把渲染模式、运行环境、缓存和监控串起来。一个 Next 项目不是“build 完就结束”，而是要确保每种页面在正确的地方、用正确的方式运行。

交付前可以按路径抽查：公开静态页、登录后动态页、Route Handler、Middleware 跳转、图片资源、错误页、加载态、刷新和回退。Next 项目的部署质量，不只由构建结果决定，还由真实路由在生产环境里的行为决定。

```text
构建通过
  -> 路由抽查
  -> 环境变量校验
  -> 缓存头检查
  -> 监控告警确认
  -> 回滚路径确认
```

部署优化最终要回答三个问题：用户是否更快看到正确内容，服务端是否稳定可扩展，出了问题是否能快速定位和回退。
