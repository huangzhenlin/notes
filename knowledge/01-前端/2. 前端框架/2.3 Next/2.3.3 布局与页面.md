## 页面职责

`page.tsx` 对应具体页面内容，负责当前路由的主体展示。

页面组件最好是“当前路由的组合层”：它读取参数、拿数据、组合区块，但不应该塞进过多底层 UI 细节。这样页面文件会更像业务入口，而不是巨大的组件实现。

```tsx
export default function Page() {
  return <main>Home</main>;
}
```

页面应该专注于当前路由的业务主体，不承担整站壳层职责。它可以读取路由参数、发起服务端数据获取、组合页面内部组件。

如果多个页面都重复出现相同壳层，就应该考虑上移到 layout；如果某个区块只服务当前页面，就留在 page 或页面内部组件里。这个边界能减少重复。

`page.tsx` 最好像一个页面编排入口：读取参数、调用服务端数据函数、组合页面区块。底层按钮、卡片、表格、表单细节不一定都要塞在页面文件里。

```tsx
export default async function UserPage({ params }: { params: { id: string } }) {
  const user = await getUser(params.id);

  return (
    <main>
      <UserHeader user={user} />
      <UserProfile user={user} />
    </main>
  );
}
```

这样页面文件表达业务结构，子组件表达具体 UI。

## 共享布局

`layout.tsx` 用于共享壳层，比如导航栏、侧边栏和页脚。

```tsx
export default function Layout({ children }: { children: React.ReactNode }) {
  return (
    <>
      <Header />
      {children}
    </>
  );
}
```

布局会包裹子路由，并在路由切换时尽量保留状态。适合放稳定 UI 框架，不适合放每个页面都不同的业务逻辑。

比如侧边栏展开状态、顶部导航、用户信息栏适合放在 layout；而商品详情、订单表单、搜索结果这种随页面变化的内容不适合放进共享布局。

布局的保留特性会影响状态。放在 layout 中的客户端组件，在同一布局下切换子页面时可能不会卸载，因此适合导航展开、主题切换、播放器这类跨页面保留的状态。不想保留的状态，就不要放到共享 layout。

## Server Component

默认情况下，页面和布局都是 Server Component。

```tsx
export default async function Page() {
  const data = await getData();
  return <div>{data.title}</div>;
}
```

能留在服务端的逻辑优先留在服务端，这样可以减少客户端 JavaScript，也更利于访问私有资源。

页面和布局默认是服务端组件，所以它们适合处理数据获取、权限判断和元信息生成。只有局部交互才需要下沉到客户端组件。

布局也可以是异步服务端组件，用来获取共享数据，例如当前用户、导航菜单、组织信息。但要注意共享布局的数据会影响其下所有页面的动态性和缓存策略。共享得越上层，影响面越大。

```tsx
export default async function DashboardLayout({ children }: { children: React.ReactNode }) {
  const currentUser = await getCurrentUser();

  return (
    <>
      <Sidebar user={currentUser} />
      {children}
    </>
  );
}
```

## Client Component

需要状态、事件或浏览器 API 时，才使用 Client Component。

```tsx
"use client";
```

按钮、表单、动画、交互区通常更适合客户端组件。不要为了一个按钮把整页都改成客户端组件。

一旦 layout 被标记为客户端组件，它下面大量内容都可能进入客户端边界。通常更好的做法是在服务端 layout 里嵌入小的客户端交互组件。

客户端 layout 不是不能用，但要非常克制。比如整站主题切换、客户端侧边栏折叠、拖拽布局可能需要客户端能力；但通常可以只把交互部分拆成小组件，而不是让整个 layout 变成客户端组件。

## `loading`

`loading.tsx` 处理当前路由段的加载状态。

```tsx
export default function Loading() {
  return <div>Loading...</div>;
}
```

更好的 loading 往往是骨架屏或结构近似的占位，而不是一段空文本。

加载态最好和真实布局保持接近，这样用户感知会更稳定，也能减少页面内容突然跳动。对慢数据区域，可以把 loading 放在更靠近该路由段的位置。

`loading.tsx` 会在对应路由段等待时自动显示，常用于页面级骨架。如果只有页面内部某块数据慢，可以使用 `Suspense` 给局部区域设置等待边界，避免整页 loading。

```tsx
<Suspense fallback={<ChartSkeleton />}>
  <SlowChart />
</Suspense>
```

## `error`

`error.tsx` 是路由段级错误边界。

```tsx
"use client";

export default function Error() {
  return <div>出错了</div>;
}
```

它可以把失败限制在局部，不让整页一起崩掉。复杂页面和异步区域尤其需要。

错误边界的意义是把失败限定在一个路由段。比如推荐区域失败，不应该让整个商品页白屏；详情核心数据失败，才需要更高层错误页介入。

`error.tsx` 必须是客户端组件，因为它需要接收错误和重试函数。错误页应该给用户可理解的反馈，并提供重试或返回路径，而不是只输出错误对象。

```tsx
"use client";

export default function Error({ reset }: { reset: () => void }) {
  return <button onClick={reset}>重试</button>;
}
```

## `template`

`template.tsx` 会在导航时重新渲染，适合需要每次进入都重置的场景。

```tsx
export default function Template({ children }: { children: React.ReactNode }) {
  return <>{children}</>;
}
```

如果 `layout` 偏向保留，`template` 就偏向重置。两者结合能更精细地控制页面状态。

比如同一个 layout 下多个页面切换时希望保留导航状态，就用 layout；如果每次进入都希望重新播放动画、重置内部状态，就可以考虑 template。

`template` 每次导航都会创建新实例，因此适合页面进入动画、统计曝光、需要重置的表单壳层。不需要重置时，优先用 layout，因为 layout 的保留能减少重复渲染和状态丢失。

## 选择判断

| 组件 | 作用 |
| --- | --- |
| `page` | 当前页面内容 |
| `layout` | 共享壳层 |
| `loading` | 进入中的过渡 |
| `error` | 局部兜底 |
| `template` | 导航时重置 |

页面和布局分清后，数据获取和导航体验会更好设计。

实际设计时可以先画出页面壳层，再决定哪些路由段共用 layout，哪些路由段需要单独 loading/error。这个顺序比先写页面再抽布局更稳定。

页面和布局设计的关键，是把“稳定壳层”和“变化内容”分开。稳定壳层上移，变化内容留在 page，局部失败用 error，等待体验用 loading，状态重置再考虑 template。这样 App Router 的约定文件会自然形成页面体验结构。
