## 渲染边界

Next 的渲染模式决定页面在服务器还是客户端生成，以及什么时候能拿到内容。App Router 里最常见的默认模式是服务器先渲染，再把交互补到客户端。

渲染模式还会影响调试和部署。服务端渲染更接近请求时状态，客户端渲染更依赖浏览器执行结果，所以定位问题时要先分清“首屏 HTML 是什么”和“hydration 后变成了什么”。

理解渲染模式时，不要只问“SSR 还是 CSR”。在 Next App Router 里，一个页面往往同时包含服务端组件、客户端组件、缓存数据、动态数据和流式片段。真正要判断的是：每一块 UI 应该在哪里生成、什么时候生成、要不要缓存、是否需要浏览器能力。

Next 的渲染模式可以拆成四个问题：这段 UI 在服务器还是浏览器执行，数据在构建时还是请求时获取，结果是否缓存，交互是否需要 hydration。很多问题不是“SSR/SSG/CSR 选错”，而是其中某个问题没有拆开。

```text
运行位置：Server / Client
生成时机：Build / Request / Interaction
缓存策略：Static / Revalidate / Dynamic
交互恢复：Hydration / No Hydration
```

## SSR 与流式

服务端渲染会在请求时生成 HTML。

```text
请求 -> 服务器生成 HTML -> 浏览器展示 -> 客户端 hydration
```

App Router 还会按路由段流式输出，让页面更早显示骨架或部分内容。

流式渲染的价值在于把“全部等完再展示”改成“能展示的先展示”。对首屏来说，导航、布局和骨架可以先出来，慢数据区域再逐步补齐。这和传统整页 SSR 最大的体验差异在于等待边界更细。

这对复杂页面特别有用，因为不是所有数据都一样慢。商品详情、推荐列表、评论、统计图可以分批输出，用户会更早觉得页面“活了”。

流式渲染通常和 `loading.tsx`、`Suspense` 一起工作。它让慢区域有自己的等待边界，而不是拖住整个页面。

```tsx
import { Suspense } from "react";

export default function Page() {
  return (
    <>
      <ProductSummary />
      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews />
      </Suspense>
    </>
  );
}
```

等待边界设计得越细，用户越早看到可用内容；但边界过碎也会让页面闪动变多。要按用户感知的重要区域拆，而不是每个组件都包一层。

流式边界设计时，最好优先围绕“用户先想看到什么”来拆。导航、标题、价格、摘要这种关键内容往往值得先出来；推荐、评论、扩展信息可以稍后流入。顺序对了，用户会觉得页面响应很快。

## Server Components

默认情况下，页面和布局都是 Server Components。

```tsx
export default async function Page() {
  const data = await getData();
  return <div>{data.title}</div>;
}
```

它适合数据获取、访问秘密信息、减少客户端 JS 和提升首屏可见性。

服务端组件还天然适合访问数据库、内部接口和环境变量，因为这些代码不会直接进入浏览器 bundle。只要逻辑不需要点击事件、浏览器 API 或客户端状态，就应该优先考虑留在服务端。

如果把本来能放服务端的逻辑提前丢到客户端，不仅 bundle 变大，还会把私有资源访问权限一并搬过去。渲染模式因此不只是性能问题，也是边界问题。

Server Components 还能减少客户端 hydration 工作。纯展示和服务端数据逻辑不需要在浏览器重新执行，这对大内容页、文档站、电商详情页和后台首页很有价值。

但服务端组件也有边界：不能使用事件处理器，不能访问 `window`，不能保存浏览器本地状态。只要逻辑需要用户交互，就要把那一小块拆到客户端组件。

服务端组件还有一个重要优势，是更容易和缓存策略绑定。公开内容、详情数据、布局级共享数据如果能稳定留在服务端，再配合重验证或标签失效，通常会比客户端自己拉取后再管理缓存更自然。

## Client Components

需要状态、事件或浏览器 API 时，才声明客户端组件。

```tsx
"use client";
```

只要有一个文件标记了 `use client`，它导入和渲染链上的客户端边界就会扩大，所以要尽量把客户端能力切得小而准。

这也是 Next 性能优化里非常重要的一条：不是页面有交互就整页客户端化，而是把交互组件切出来。比如搜索框、收藏按钮、弹窗开关可以是客户端组件，文章正文、商品详情和推荐列表仍然可以是服务端组件。

`"use client"` 是文件级边界。一个文件声明为客户端组件后，它导入的子组件和依赖会进入客户端图。最常见的性能问题，就是在页面顶层加了 `"use client"`，导致本来可服务端渲染的大量内容都进入浏览器 bundle。

```tsx
// 更推荐：只让按钮是客户端组件
export default async function ProductPage() {
  const product = await getProduct();

  return (
    <>
      <ProductContent product={product} />
      <FavoriteButton productId={product.id} />
    </>
  );
}
```

## 混合渲染

最常见的模式是：页面主体在服务器，少量交互组件在客户端。

```tsx
<Layout>
  <Search />
  <Content />
</Layout>
```

这样能兼顾首屏和交互，不必为了一个按钮把整页都变成客户端渲染。

混合渲染的判断重点是“交互边界”。静态内容、服务端数据、权限判断和元信息适合服务端；输入、点击、动画、浏览器存储和实时状态适合客户端。边界切得越小，客户端 JS 越少。

你可以把它理解成“页面外壳在服务器，用户动作在浏览器”。这条分工清楚后，Next 的大部分模式选择其实就不再复杂了。

混合渲染还要注意传递边界。服务端组件可以把可序列化数据传给客户端组件，但不能把数据库连接、函数、类实例直接传过去。传输边界越小，客户端组件越轻。

```tsx
<AddToCartButton productId={product.id} stock={product.stock} />
```

比起传完整 `product` 对象，只传按钮真正需要的字段更安全，也更利于控制客户端 bundle。

## 选择判断

| 需求 | 更适合 |
| --- | --- |
| 需要 SEO | 服务端渲染 |
| 需要交互 | 客户端组件 |
| 需要减少 JS | 服务端组件 |
| 需要流式展示 | App Router 流式渲染 |

如果页面既需要 SEO，又需要局部强交互，可以让页面主体服务端渲染，再把强交互区域拆成客户端组件。不要把渲染模式理解成单选题，它更像页面分层策略。

如果实在拿不准，就先从默认服务端开始，再把必须依赖浏览器的局部区域切成客户端组件。这通常比先整页客户端化、后面再一点点往回拆更稳，也更符合 App Router 的默认思路。

私有用户数据通常会让页面更动态，因为它依赖请求时的身份和权限。公开内容则更适合缓存和重验证。渲染模式要跟数据性质绑定，而不是跟页面名称绑定。

## 误区

| 误区 | 问题 |
| --- | --- |
| 一律客户端化 | JS 体积变大 |
| 一律服务端化 | 交互能力受限 |
| 只看首屏 | 忽略切换体验 |

渲染模式不是“选一个就结束”，而是按页面区域拆分。静态的留服务端，交互的放客户端，通常是更稳的方案。

如果同一个页面在不同环境下首屏差异很大，通常就是渲染模式、缓存策略或客户端边界里有一项没对齐。把这三件事分开看，问题会清楚很多。

排查渲染问题时可以从三个方向看：页面是否因为动态数据被迫动态渲染，客户端边界是否意外扩大，缓存策略是否和业务实时性冲突。很多 Next 问题不是 API 不会用，而是运行位置和缓存时机没想清楚。

如果出现 hydration mismatch，通常要检查服务端和客户端首次渲染是否读了不同值，比如当前时间、随机数、浏览器尺寸、本地存储、用户时区。服务端不知道浏览器环境，这类值要么延后到客户端挂载后渲染，要么由请求头或服务端可知信息统一生成。

另一个常见误区是把渲染模式和数据获取策略绑死。实际上同样是服务端组件，有的数据适合静态缓存，有的数据适合按请求动态生成，有的数据适合提交后刷新。渲染位置和缓存时机虽然相关，但不是同一件事。
