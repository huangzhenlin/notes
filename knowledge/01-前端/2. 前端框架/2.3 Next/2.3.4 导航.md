## 页面导航

Next 的导航围绕路由跳转、参数同步和加载体验展开。良好的导航体验会尽量减少突兀跳白。

导航不是简单地从 A 到 B，而是要处理历史栈、数据刷新、加载过渡、滚动位置和用户是否还能返回。页面越复杂，导航就越像状态管理的一部分。

Next 导航还要考虑服务端组件和缓存。一次跳转可能不只是换 URL，还可能触发新的服务端渲染、读取缓存、展示 loading、复用 layout。用户感受到的是页面切换，框架内部处理的是路由树更新。

## `Link`

`Link` 是推荐的页面跳转方式。

```tsx
import Link from "next/link";

<Link href="/users">用户列表</Link>;
```

它适合普通跳转、列表页链接和预取场景。相比原生 `a` 标签，`Link` 更符合 Next 的路由模型。

对于站内跳转，优先用 `Link`。原生 `a` 更适合下载、外链、打开新窗口等浏览器原生行为。混用时要明确跳转目标是不是 Next 路由。

`Link` 的 `href` 应该表达可恢复的目标。列表项进入详情时，优先传资源路径，而不是依赖点击前把完整对象写进全局状态。

```tsx
<Link href={`/users/${user.id}`}>{user.name}</Link>
```

这样用户刷新详情页、复制链接或从外部打开时，都能通过 URL 重新加载资源。

如果列表页还带筛选、分页或排序，进入详情时也可以考虑把“返回后仍然需要恢复的那部分状态”保留在 URL 里，而不是只靠内存状态记住用户刚才看到了哪里。导航体验好不好，很多时候就体现在这种返回可恢复性上。

## `useRouter`

客户端可以用 `useRouter` 做编程式导航。

```tsx
"use client";

import { useRouter } from "next/navigation";
```

```tsx
const router = useRouter();
router.push("/dashboard");
router.replace("/login");
router.back();
router.refresh();
```

`push` 会保留历史，`replace` 会替换当前记录。登录、提交和重定向后的场景，通常要想清楚历史栈是否应该保留。

例如登录成功后通常用 `replace`，避免用户返回登录页；从列表进入详情通常用 `push`，因为用户需要返回列表。历史栈设计会直接影响用户体感。

`router.refresh()` 会重新请求当前路由的服务端数据，并保留客户端状态。它适合提交后刷新服务端组件数据，但不要把它当成所有状态同步的万能按钮。能精确失效缓存或局部更新时，优先选择更小范围的方式。

```tsx
async function handleSave() {
  await saveProfile(form);
  router.refresh();
}
```

`push`、`replace` 和 `refresh` 的选择，本质上是在决定“用户路径怎么记录、服务端数据怎么重取、客户端局部状态要不要保留”。把这三件事分开想，很多导航细节就不容易混淆。

## `redirect`

`redirect` 适合服务端或路由处理中的直接跳转。

```ts
redirect("/login");
```

当用户没有权限或数据不存在时，服务端直接跳转通常比先渲染再隐藏更清楚。

服务端跳转也能避免敏感页面先闪一下再跳走。权限、登录、资源不存在这类判断如果能在服务端完成，体验和安全边界都会更清晰。

`redirect` 会中断当前渲染流程，所以适合明确的分流结果。比如未登录跳登录页、旧地址迁移到新地址、非法参数规范化。用户交互后的导航如果发生在客户端组件里，仍然用 `useRouter` 更自然。

如果一个页面必须先拿到服务端数据或身份信息才能决定能不能进，优先在服务端分流通常会比客户端先渲染再跳转更稳。这样不仅避免闪烁，也更符合“敏感页面默认不先暴露”的原则。

## 查询参数

`searchParams` 适合保存筛选、排序、分页等状态。

```tsx
export default function Page({
  searchParams,
}: {
  searchParams: { q?: string };
}) {
  return <div>{searchParams.q}</div>;
}
```

可分享、可刷新、可从外部进入的状态，优先放 URL。

搜索词、排序、分页、筛选条件都适合放在 `searchParams` 里。这样用户复制链接、刷新页面、分享给别人时，页面状态仍然能恢复。

写入查询参数时要避免每次输入都立刻导航，尤其是搜索框。可以在提交、失焦、防抖后更新 URL，避免制造过多历史记录和请求。

```tsx
const params = new URLSearchParams(searchParams);
params.set("q", keyword);
router.replace(`/users?${params.toString()}`);
```

筛选条件更新通常用 `replace` 更合适，因为用户不一定希望每输入一个字符都能回退一步。

查询参数最好尽量保持语义稳定，比如 `q`、`page`、`sort`、`tab` 这些都很适合作为可恢复状态；而临时展开项、弹窗开关、局部 hover 这类瞬时状态通常不值得放进 URL。不是所有状态都应该路由化。

## 预取

`Link` 默认会预取可见链接资源。

```tsx
<Link href="/dashboard" prefetch>
  仪表盘
</Link>
```

预取能提升切换速度，但在超长列表和高频动态页里也要关注额外流量。

如果页面里有大量可见链接，预取可能带来额外请求压力。对不常点击或成本较高的链接，可以显式调整预取策略，避免“优化体验”变成“浪费资源”。

预取更适合用户大概率会访问的链接，例如导航菜单、列表首屏可见详情、下一步流程。无限滚动列表、超多详情链接、权限变化频繁的页面，要谨慎评估预取成本。

如果某些链接背后会触发较重的数据准备或用户访问概率很低，可以考虑关闭或延后预取。预取不是越多越好，它的目标是把“很可能发生的下一步”提前准备，而不是把整站所有页面都提前请求一遍。

## 体验状态

导航体验不只是“能跳”，还包括过渡、加载和中断。

```text
常见体验：
1. 点击后显示过渡
2. 切换时保留部分页面内容
3. 搜索参数变化时局部刷新
```

`loading.tsx`、局部 skeleton 和按钮 pending 状态可以一起配合。

导航中的等待感最好分层处理：页面级切换用路由段 loading，局部操作用按钮 pending，慢区域用 skeleton。不要所有等待都用一个全屏 loading。

客户端导航中的 pending 状态可以配合 `useTransition` 或表单提交状态。比如点击保存后按钮进入提交中，路由跳转时保留页面骨架，用户会更清楚当前发生了什么。

导航体验最怕两种情况：一种是点了没反应，用户不知道是不是卡住了；另一种是全屏闪白，用户感觉整页被重置。局部 loading、按钮 pending 和稳定的 layout 复用，正是在解决这两个问题。

## 选择方式

| 场景 | 优先方案 |
| --- | --- |
| 普通页面跳转 | `Link` |
| 交互完成后的跳转 | `useRouter` |
| 服务端条件跳转 | `redirect` |
| URL 状态同步 | `searchParams` |
| 页面加载过渡 | `loading.tsx` 或 skeleton |

导航不是单纯的跳转动作，而是把历史、状态和体验一起处理好。

如果用户经常在返回时回到错误位置、筛选条件丢失或页面闪白，就说明导航状态还没设计好。先判断哪些状态应该进入 URL，哪些状态应该留在页面，体验通常会自然很多。

导航设计的底层原则是：URL 表达可恢复状态，历史栈表达用户路径，loading 表达等待边界，refresh 表达服务端数据重新同步。把这四件事分清，Next 导航就不会只剩 API 调用。

真正稳定的导航设计通常有一个共同点：用户离开页面、刷新页面、复制链接、从外部再次进入时，核心路径都还能走通。只要这一点成立，App Router 的很多 API 选择都会顺着变得清楚。
