## 框架适配

组件库必须先匹配框架，再谈体验。React、Vue、Svelte、原生模板对组件库的接入方式和心智模型都不一样。

```text
先确认：
1. 框架支持
2. 版本兼容
3. TypeScript 支持
4. SSR / CSR 兼容
5. 社区是否在持续维护
```

选型前先看项目的实际技术栈，不要把“别人能用”当成“我们也好用”。如果项目已经围绕 Vue 生态建立了路由、状态、测试和构建体系，再引入强 React 绑定的库，迁移成本会远高于收益。

框架适配不只是“有没有 React 版或 Vue 版”。还要看库是否适配当前主版本、是否支持组合式 API 或 Hooks 写法、是否提供完整类型、是否能在 SSR 场景下稳定工作。一个库如果只在纯客户端页面表现正常，但服务端渲染时样式注入顺序、随机 ID、Portal 挂载点或 hydration 行为不稳定，就不适合 Next、Nuxt 这类框架的核心页面。

在大型项目里，还要确认组件库是否和现有状态管理、路由守卫、权限系统、埋点系统自然配合。比如弹窗和通知组件如果只能通过全局单例调用，就要提前判断它是否会影响多实例应用、微前端或服务端渲染。

框架适配还要看团队日常写法。React 团队如果大量使用受控组件、Hooks 和服务端组件，就要确认组件库是否支持这些模式；Vue 团队如果大量使用组合式 API、`v-model`、slot 和 Nuxt，就要看库是否顺着这些语义设计。

也就是说，生态匹配不只是技术上“能装能跑”，更是开发习惯上“顺不顺手”。一个库如果总要求团队绕开自己熟悉的范式去写代码，长期使用成本通常会比最初预估高很多。

## 工程链路

组件库不只是组件，还影响构建、按需加载、样式编译和测试。

| 环节 | 需要确认 |
| --- | --- |
| 构建 | 是否支持 Tree Shaking |
| 样式 | 是否支持主题变量 |
| 测试 | 是否易于模拟交互 |
| SSR | 是否能安全渲染 |
| 类型 | 是否有完整声明 |

有些库本身很好，但和项目构建链路不兼容，比如样式加载顺序、CSS Modules、SSR hydration 或按需引入策略冲突。生态匹配不只是“能安装”，而是“能稳定跑在当前工程里”。

工程链路里最容易被低估的是“默认配置”。如果一个库必须依赖额外 Babel 插件、Vite 插件、样式预处理器、全局 CSS 顺序或运行时 Provider，团队就要把这些成本写进模板工程里。否则不同项目各接一套，后面升级和排查会很痛。

组件库还会影响测试方式。复杂组件经常包含异步渲染、Portal、虚拟滚动和键盘交互，测试时可能需要额外处理容器挂载、焦点切换和计时器。如果测试工具很难稳定模拟这些行为，组件库带来的不仅是开发成本，还有质量保障成本。

工程链路验证最好在真实项目模板中做，而不是新建一个空项目。真实模板里通常有路由、状态、测试、主题、lint、构建分析和部署配置，更容易暴露冲突。

很多“空项目里没问题”的组件库，一进真实项目才开始暴露问题。因为真实工程里往往已经有自己的 Provider 层、主题层、请求层和构建约束，生态兼容性的真正考验是在这些约束叠起来以后。

## 生态插件

很多项目会依赖表单、图表、表格、日期、上传、编辑器等外围生态。选组件库时也要看这些生态是否好接。

```text
外围生态：
1. 表单库
2. 图表库
3. 查询库
4. 路由库
5. SSR 框架
6. 权限和国际化方案
```

如果组件库和这些生态搭配很差，后续就会出现“主库还行，周边都要手工补”的情况。真正的大型项目里，外围生态往往和核心组件库一样重要。

表单是最典型的生态交叉点。一个输入组件不仅要展示值，还要和校验、错误信息、禁用态、重置、默认值、动态字段、服务端错误回填协作。如果组件库的表单模型和团队已有请求、状态、校验工具相冲突，就会让页面代码变得绕。

表格和图表也是重灾区。表格要关心排序、筛选、固定列、虚拟滚动、行选择、批量操作和服务端分页；图表要关心主题、尺寸监听、懒加载和导出。选型时要看这些高频组合能不能自然接起来，而不是只看单个组件是否存在。

外围生态还要看版本协同。比如日期组件依赖 dayjs、date-fns 或 moment，图表依赖 echarts 或其他渲染库，表格依赖虚拟滚动或拖拽库，这些依赖是否和项目现有依赖冲突，也会影响长期维护。

外围生态越多，越要留意“谁才是主导者”。如果组件库强依赖一套表单模型、日期方案或图表接法，而项目里已经有另一套稳定方案，就要判断是统一切换，还是做好边界适配。两套方案长期并行往往最贵。

## 设计协同

如果团队已经有设计系统，要确认组件库是否能匹配设计 token、色板、字号和间距规范。

```text
对齐项：
1. 颜色
2. 圆角
3. 阴影
4. 间距
5. 状态色
6. 动效节奏
```

一个库如果默认视觉风格很强，但 token 暴露不足，后期就很难和设计体系统一。对于强设计协同团队，生态匹配不仅是技术问题，也是组织协作问题。

设计协同还包括设计工具和代码之间的映射。如果设计稿使用的是 Figma 组件、变量和样式库，前端组件库最好能找到对应的 token、组件状态和命名体系。否则设计里叫 `primary/hover`，代码里叫 `brand-active`，长期会产生大量翻译成本。

如果组件库提供官方设计资源、主题编辑器或 token 导出能力，设计和前端之间会少很多重复沟通。反过来，如果只能靠截图和手写覆盖样式对齐，组件体系会越来越难维护。

设计协同最好用真实设计稿验证，而不是只调主色。至少要验证按钮、表单、表格、弹窗、空态、错误态、暗色模式和密集布局。只有这些场景都能被 token 和组件 API 支撑，才能说组件库和设计体系匹配。

设计协同的重点不是“能不能改得像”，而是“能不能稳定地一直像”。如果每次新增一个组件状态都要靠手工样式覆盖，那就说明生态匹配停留在表面，而没有真正建立起设计到代码的稳定映射。

## 组织约束

大公司或多团队协作时，组件库还要考虑组织内部规范、权限流程、审查标准和文档治理。

如果组件库支持统一规范、可审计变更和稳定升级，跨团队协作会轻松很多；反之，组件库再好看，也可能因为治理成本太高而不适合组织规模。

```text
组织里真正重要的不是“好不好看”，而是：
1. 规范能不能统一
2. 升级能不能控住
3. 问题能不能定位
4. 多团队能不能协作
```

组织规模越大，越不能只看单个项目的接入体验。统一组件库通常还要配套 changelog、升级指南、破坏性变更说明、设计验收规则和问题反馈渠道。如果这些治理机制缺失，组件库会慢慢变成“每个业务线自己 fork 一份”的状态。

组织约束还包括安全和合规。上传、弹窗、表单、输入框、通知这类组件可能承载敏感数据，组件库和封装层要能支持脱敏、权限控制、审计埋点和错误提示规范。

组织规模越大，越需要把这些约束前置到选型阶段。因为一旦组件库成为团队基础设施，它影响的就不只是页面开发效率，还包括设计治理、质量治理、安全治理和升级治理。

## 版本兼容

库版本升级会影响生态插件和业务封装。先确认主版本升级是否会影响已有主题、类型和运行时依赖。

```text
升级前要确认：
旧 API 是否废弃
主题变量是否变化
样式类名是否变化
插件是否跟着升级
```

生态匹配的本质，是让组件库可以自然融入项目，而不是让项目围着库改造。一个真正适合的库，不仅组件够用，还要能和现有工程链路、设计规范和组织协作一起工作。

版本兼容最好在选型阶段就做一次模拟升级：从当前版本安装到最新版本，跑构建、跑关键页面、跑核心测试，记录警告和破坏性变更。这个动作成本不高，却能快速暴露库的升级质量。

如果库已经有多个主版本共存，或者社区迁移案例里普遍反馈升级困难，就要把这一点写入选型风险。组件库不是一次性工具，它会跟着项目维护很多年。

版本兼容本质上是在评估“未来负债”。今天接入顺手不代表长期便宜，真正值得选的库，应该在未来一年、两年里仍然有可预期的升级路径，而不是每次升级都像一次小型迁移。
