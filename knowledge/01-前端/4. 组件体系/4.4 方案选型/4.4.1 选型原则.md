## 业务优先级

选型的第一原则不是“哪个库最火”，而是“这个项目最需要什么”。中后台、营销页、移动端、设计系统、原型工具的优先级完全不同。

```text
先问：
1. 项目要快交付，还是要强定制？
2. 视觉是否要高度统一？
3. 是否需要复杂表单和表格？
4. 团队是否熟悉现有技术栈？
5. 是否有长期维护和升级要求？
```

如果是后台管理系统，表单、表格、弹窗和权限态通常是高频热区，组件库的“默认完整度”会非常重要；如果是营销活动页或品牌官网，视觉控制和动效表达往往比组件齐全更重要；如果是移动端 H5，轻量、触控体验和主题切换会比桌面端那套重组件更关键。选型先看项目类型，再看库本身。

更实用的判断方式，是把候选库放进真实业务场景里比一轮，而不是抽象地谈“好不好”。一个库在 Button、Input、Modal 上看起来都不错，不代表它在复杂筛选、批量表格编辑、异步表单校验和空态处理上也合适。

选型时可以先列出项目的“高频页面模型”。比如后台项目通常是查询表单、结果表格、批量操作、弹窗编辑、详情抽屉；移动端项目通常是列表、详情、底部操作、弹层选择、表单提交。组件库能不能自然覆盖这些模型，比单个组件是否漂亮更重要。

```text
后台样板：筛选表单 + 表格 + 弹窗 + 批量操作
移动样板：列表 + 下拉刷新 + 底部按钮 + 弹层选择
官网样板：响应式布局 + 主题视觉 + 动效区域
```

这一步的本质，是把“选组件库”转成“选页面模型支持度”。一旦页面模型清楚，很多争论会自动变少，因为大家讨论的不再是主观印象，而是库能不能自然支撑真实业务结构。

## 团队匹配

组件库会影响开发习惯、学习成本和协作方式。团队如果已经熟悉 Vue，就不必为了“流行”强换 React 生态里的库，反过来也一样。

| 团队特征 | 关注点 |
| --- | --- |
| 新团队 | 上手快、文档清楚 |
| 成熟团队 | 约束是否足够、定制是否方便 |
| 多人协作 | 命名一致、组件稳定 |
| 设计驱动 | 主题和 token 能否收敛 |

选型不是技术负责人一个人的拍板。设计、前端、测试、业务都应该参与样板页验证。

如果团队里已经有人长期维护某个生态的表单方案、校验方案或表格方案，那套组合本身也是选型的一部分。很多时候“库”的成本不只来自组件库本身，还来自配套生态和团队经验。团队熟悉的方案，往往能更快落地，也更容易形成统一写法。

如果团队成员分布在多个小组，更要看是否容易形成一致的封装规范。组件库如果太自由，最后会出现“每个团队都能用，但每个团队用法都不一样”的情况，后续维护和排查都会变重。

团队匹配还包括测试和设计协作能力。一个组件库如果只有前端觉得好用，但设计侧没有资源、测试侧不好定位元素、业务侧难以理解交互规则，也很难长期推广。

所以团队匹配不能只看“开发快不快”，还要看“协作成本高不高”。一个库即使单个前端写起来顺手，如果设计映射困难、测试用例难稳定、评审沟通成本高，它在团队层面就未必是低成本方案。

## 成熟度

不要只看 star，更要看文档、发布节奏、社区案例、问题响应和长期兼容性。

```text
检查项：
1. 是否长期维护
2. 是否有活跃 release
3. 是否有清晰升级记录
4. 是否有真实生产案例
5. 是否有明确的破坏性变更说明
```

一个库如果短期很流行，但版本升级频繁、文档滞后、问题响应慢，就会把成本转嫁给业务团队。

成熟度还体现在“有没有把复杂问题说清楚”。比如表单校验、国际化、主题切换、暗黑模式、无障碍、SSR、按需加载，这些问题如果官方文档本身就解释得模糊，后面就会在项目里反复踩坑。

对长期项目来说，版本策略比“功能多不多”更重要。一个库即使今天足够好，如果它的破坏性变更太密、迁移指南太少、社区回答太零散，后续升级就会变成一次次重写。

成熟度还可以通过 issue 和 release 看出来：bug 是否有人响应，破坏性变更是否提前说明，文档示例是否跟随版本更新，官方是否提供迁移指南。一个库的“长期安全感”，往往来自这些看似琐碎的维护细节。

很多组件库在演示层看起来差异不大，真正拉开差距的往往就是这些维护细节。因为业务项目真正难的不是把第一版页面搭起来，而是两年后还能不能稳定升级、还能不能快速定位问题、还能不能继续招新人接手。

## 风险边界

选型时要提前承认风险：视觉是否会被库绑住、未来升级成本是否可控、是否会和现有设计系统冲突。

```text
风险越高，越要先做样板页。
```

如果项目已经有统一设计语言，而组件库默认风格很强，后续改造往往会把大量时间花在样式覆盖上。

风险边界还包括团队边界。如果前端、设计、测试、产品对同一组件的理解不一致，后期就会出现“页面看起来像对了，但交互和状态并不对”的情况。样板页不只是验证视觉，也是在提前统一认知。

真正危险的不是“这个库有风险”，而是“风险被延后发现”。越晚发现不适配，迁移和返工的代价越高。

风险可以提前分级。视觉风格不完全匹配通常是中风险；表单模型不适配、SSR 不稳定、主题能力不足、复杂表格性能不够，通常是高风险。高风险项必须用样板页验证，而不是靠讨论决定。

风险分级还有一个作用，是帮助团队决定验证顺序。高风险项先验证，低风险项后讨论；一旦高风险项不过线，后面的细节优化意义就不大了。这样选型过程会比“所有问题一起争”更高效。

## 验证样板

最靠谱的选型方式，是拿真实页面做一个最小样板，而不是只看官网截图。

```text
样板页建议包含：
1. 表单
2. 表格
3. 弹窗
4. 列表
5. 主题切换
6. 错误态
7. 异步加载
```

样板页要用真实业务数据和真实交互。这样才能尽早暴露表单、表格、弹窗、主题和可访问性的真实成本。

如果项目有权限、国际化、暗黑模式、复杂筛选或批量操作，样板页里也应该提前放进去。否则选型时觉得“没问题”，上线后才发现权限态没有统一入口，或者国际化切换时大量组件要单独修。

样板页最好同时做功能验证和验收验证：功能验证看能不能实现，验收验证看是否符合设计、是否容易复用、是否和工程链路冲突。

样板页完成后要留下结论，而不是只留代码。结论至少要说明：哪些场景顺手，哪些场景需要封装，哪些场景需要绕过，哪些风险不能接受。

```text
样板结论：
1. 表格能力是否够
2. 表单校验是否顺
3. 主题覆盖是否稳定
4. 弹层和焦点是否可靠
5. 包体和性能是否可接受
```

如果样板页只证明“能做出来”，那它的价值只完成了一半。更重要的是把过程中暴露出来的摩擦点显式记录下来，这样后续选型讨论才不会重复回到主观印象。

## 评分模型

| 维度 | 权重建议 |
| --- | --- |
| 业务匹配 | 高 |
| 团队熟悉度 | 高 |
| 定制成本 | 高 |
| 生态兼容 | 中 |
| 包体积 | 中 |
| 长期维护 | 高 |

评分不是为了制造“科学感”，而是为了把争议落到具体维度上。

评分最好配合一句最终结论，而不是只给分数。比如“适合中后台、适合移动端、适合强设计定制、适合长期维护”。这样后续回看时，大家能直接知道为什么选它，而不是只看到一张表。

最终判断时，通常不要追求“全面最优”，而是追求“对当前项目最稳”。如果一个库在业务匹配、团队熟悉度和长期维护上明显占优，即使它在包体积或默认风格上不是最漂亮，也可能是更合理的选择。

评分模型的意义是减少拍脑袋。最终选择时可以把“必须满足”和“加分项”分开：必须满足项不过线直接淘汰，加分项再用于排序。比如 SSR 稳定、主题可覆盖、表格可用可能是必须项；默认视觉更好、文档更漂亮则是加分项。

最终产出的不应该只有“我们选了哪个库”，还应该有“为什么选它、它适合什么项目、不适合什么项目”。这份判断本身就是团队资产，后续换项目、换团队、换框架时都还能复用。
