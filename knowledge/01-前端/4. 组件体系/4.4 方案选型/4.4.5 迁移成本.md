## API 差异

迁移成本通常首先体现在 API 差异上。组件名、属性名、事件名和插槽结构不同，都会带来改造工作。

```text
迁移对象：
1. 组件名
2. 属性名
3. 事件名
4. 插槽结构
5. 表单校验方式
6. 主题变量
```

迁移前要先做 API 差异表，而不是直接打开代码替换。很多组件表面看起来名字相同，但受控模式、默认值、事件时机和错误处理都完全不同。

API 差异要从高频组件开始看，而不是平均扫描所有组件。Button、Input、Form、Table、Modal、Select、DatePicker、Upload 这些组件出现频率最高，它们的差异会决定迁移主体成本。低频组件即使差异大，也可以逐页处理。

表单迁移尤其要谨慎。不同组件库的表单模型可能在字段注册、校验触发、错误展示、默认值、嵌套字段和动态数组上完全不同。表单 API 看似只是替换组件，实际可能会影响业务数据结构和提交逻辑。

迁移差异表最好按高频组件排序。先统计项目里 Button、Input、Select、Form、Table、Modal、DatePicker、Upload 的使用数量，再决定迁移优先级。不要平均用力。

这一步其实是在找“迁移杠杆点”。高频基础组件的差异，往往会放大到几十上百个页面；优先看清这些差异，才能避免后面在低频组件上花了很多时间，却没真正推动主体迁移。

## 样式迁移

样式迁移不只是 class 替换，还包括布局、间距、断点和主题 token 的重做。

```text
常见成本：
1. 类名替换
2. 布局重调
3. 主题重构
4. 图标与反馈重接
5. 视觉回归重测
```

如果旧组件库和新组件库设计语言差异很大，迁移后页面可能会“功能能跑，但视觉全变”。这类风险要通过样板页和视觉回归提前暴露。

样式迁移最怕“局部看没问题，整体不统一”。比如按钮圆角、表单 label 间距、表格行高、弹窗宽度、提示颜色这些细节如果没有统一规则，页面迁完后会显得拼接。迁移前最好先建立主题 token 映射，再处理页面。

如果旧项目里有大量覆盖组件库内部 class 的样式，迁移前要先检索这些覆盖点。它们往往不是显式依赖，却会在替换库之后直接失效。

样式迁移最好先做 token 映射，再做页面替换。比如先统一主色、文字色、圆角、表单间距、表格行高、弹窗宽度，再替换具体组件。否则每个页面会各自调一遍样式。

这也是为什么样式迁移不能只靠“页面修一修”。没有统一 token 映射时，每个页面都会自己解释新库风格，最后即使迁完，整体视觉也容易变成一组局部最优而非系统最优。

## 业务组件改造

如果项目里已经有大量业务封装组件，迁移时要确认这些封装是否继续可用，还是要一起重写。

```tsx
// 业务层最好依赖领域组件，而不是到底层组件库
<UserSelector value={userId} onChange={setUserId} />
```

如果业务页面都直接使用底层组件库，迁移就会扩散到大量页面；如果已经有领域组件，迁移可以优先替换封装内部实现。

迁移前可以把页面依赖分成三层：基础组件库、业务通用组件、具体页面。最理想的迁移路径是先让业务通用组件适配新库，再让页面保持原有业务语义。如果页面大量直接写底层组件库 API，就需要先抽出高频业务组件，否则迁移会变成全站散点修改。

```tsx
// 页面层只表达业务意图
<OrderStatusSelect value={status} onChange={setStatus} />

// 封装层决定底层组件库实现
function OrderStatusSelect(props: Props) {
  return <Select {...props} options={orderStatusOptions} />;
}
```

这种隔离不会让迁移“没有成本”，但能把成本集中到少数可控位置。

如果还没有业务组件层，迁移前反而可以先补一层高频封装。比如先抽 `UserSelect`、`OrderTable`、`ConfirmDeleteDialog`，再在封装内部切换底层库。这样迁移会慢一点开始，但后期影响范围更可控。

从长期看，这类“先补适配层再迁移”的策略通常更稳。它看起来前置成本更高，但能显著降低后面散点替换、回归困难和跨页面不一致的风险。

## 渐进迁移

不要企图一次切完。更现实的顺序是先选一个页面或一个业务域试点。

```text
建议顺序：
1. 新页面先切
2. 低风险页面试点
3. 高复用组件先改
4. 核心业务页最后动
```

渐进迁移要给新旧组件库划清边界。可以按路由、业务域或组件层分界，不要在同一个复杂页面里随意混用两套基础组件。混用会带来样式冲突、层级冲突、主题冲突和交互不一致，最后比一次性迁移还难排查。

试点页面要选择“有代表性但风险可控”的页面。太简单的页面暴露不了问题，太核心的页面又不适合先动。一个包含表单、表格、弹窗、请求状态和权限态的普通业务页，通常更适合做试点。

渐进迁移期间要建立新旧边界。例如按业务域迁移，或按路由迁移，或按组件层迁移。最怕的是同一个页面里新旧基础组件混用，最终出现两套主题、两套弹层层级、两套表单规则。

边界一旦定义清楚，迁移期间的协作就会顺很多。大家知道哪些页面还能继续用旧库，哪些组件必须走新封装，哪些场景禁止混用，迁移就不会演化成“每个人按自己的判断推进”。

## 成本评估

| 成本项 | 容易被忽略的部分 |
| --- | --- |
| 样式 | 视觉回归、断点、暗黑模式 |
| 交互 | 焦点、键盘、表单行为 |
| 数据 | 受控模式、状态同步 |
| 业务 | 封装组件和页面模板 |
| 测试 | 快照、E2E、无障碍验证 |

迁移评估应该包含开发、测试、设计验收和灰度成本，而不仅仅是替换组件的时间。

评估时要把成本拆成一次性成本和长期成本。一次性成本是迁移本身，长期成本是之后每次维护、升级和新增页面的成本。如果新库能显著降低长期维护成本，较高的一次性迁移成本可能是值得的；如果只是“换一个更流行的库”，但长期收益不明确，就要谨慎。

```text
迁移收益也要写清：
1. 是否减少重复封装
2. 是否提升设计一致性
3. 是否降低维护成本
4. 是否改善性能或可访问性
5. 是否提升团队开发效率
```

成本评估还要把“停止迁移”的条件写清。如果试点发现表单模型严重不适配、主题覆盖成本过高、性能无法接受，就应该暂停，而不是因为已经开始就硬推到底。

这条很关键。迁移不是必须成功的政治任务，而应该是一个可验证、可终止的工程决策。试点的意义不只是证明可行，也是在尽早发现“不值得继续”的信号。

## 双栈共存

迁移期间双栈共存很常见，但要明确边界，避免新旧库混用。

```text
双栈共存规则：
1. 新页面优先新库
2. 旧页面不随意混用
3. 公共业务组件先改适配层
```

双栈共存期间要特别关注全局样式和弹层容器。两套库可能都修改 `body`、注入 reset、使用 Portal、管理 z-index，如果没有统一约束，弹窗遮罩、下拉层级和滚动锁定很容易出问题。

如果项目允许双栈共存，最好明确结束条件。比如“核心业务组件迁完后禁止新增旧库使用”“下个版本移除旧库依赖”。没有结束条件的双栈，最后往往会变成长期双倍维护。

双栈共存最怕的不是暂时混乱，而是变成常态。只要新增代码还在持续进入旧栈，迁移进度就会永远被新增需求抵消。结束条件越明确，双栈阶段越容易真正收口。

双栈共存还需要 lint 或 review 规则约束新增代码。否则旧库虽然说要下线，但新页面还在继续引入，迁移永远追不上新增。

## 回滚策略

迁移必须考虑回滚。

```text
回滚方式：
1. 保留旧组件入口
2. 按页面开关切换
3. 新旧实现共用数据协议
4. 核心流程先灰度
```

如果迁移后只有样式错乱，通常还能快速修；如果表单提交、权限校验、支付流程或无障碍行为变了，就必须有明确回退方案。

回滚策略越靠近业务开关越安全。纯代码回滚依赖重新发版，页面级开关或路由级开关可以更快止损。对关键流程来说，迁移期间保留旧实现入口并不浪费，它是风险控制的一部分。

迁移完成后也要做清理。旧库依赖、旧主题变量、旧样式覆盖、兼容适配层如果长期保留，会让项目变得更重。迁移不是把新库接进来就结束，而是要把旧路径逐步移除。

迁移复盘也很重要。迁移结束后要记录哪些组件最难迁、哪些封装最有效、哪些样式覆盖最脆弱。下一次升级或换库时，这些经验会直接降低成本。

真正完整的迁移，不是“新库上线了”，而是“旧库被安全移除、经验被沉淀下来、团队后续能继续沿着新约定推进”。只有做到这一步，迁移成本才算真正闭环。
