## 定制层级

定制成本通常从低到高分为：配置项、主题 token、样式覆盖、组件封装、源码改造。

```text
从低到高：
配置 -> token -> 覆盖 -> 封装 -> 改源码
```

选型时要先判断需求能停在哪一层。如果只是颜色、圆角、字号、间距，理想情况应该停在 token 层；如果要改变交互流程、DOM 结构或状态机，成本会明显升高。

定制层级越深，越接近组件库内部实现，也越容易被版本升级击穿。配置项和 token 通常是公开契约，升级时比较稳定；内部 class、DOM 结构和未公开状态则不是稳定契约，一旦依赖它们，后续每次升级都要重新验证。

一个实用判断是：如果 80% 的视觉和交互都能通过公开 API 完成，这个库还算匹配；如果一开始就要大量穿透样式、改 DOM 结构、重写交互，说明库和项目设计语言可能并不合适。

选型时可以把定制需求逐条标注层级。比如品牌色是 token 层，按钮埋点是封装层，弹窗焦点模型变化是交互层。层级越深，越要谨慎。

```text
低风险：主题色、圆角、字号
中风险：组件默认值、业务封装、局部样式
高风险：DOM 结构、状态机、键盘模型、源码改造
```

这种分层方式的价值，在于它能把“感觉改得动”变成“知道改到哪一层”。一旦大部分需求都落在高风险层级，就该重新考虑库是否真的适合，而不是默认后续都能靠工程手段补回来。

## 主题变量

如果组件库的主题变量足够丰富，很多定制可以停留在 token 层，不需要深入组件内部。

```tsx
<ConfigProvider theme={{ token: { colorPrimary: "#0f766e" } }}>
  <App />
</ConfigProvider>
```

主题变量要看覆盖范围。只支持主色不够，真实项目还会关心文本色、边框色、错误色、禁用态、圆角、阴影、间距、字体、暗色模式等。token 越完整，越容易和 [[4.2.1 设计令牌|设计令牌]] 对齐。

主题变量还要看粒度。全局 token 适合统一品牌色和基础尺寸，组件级 token 适合微调 Button、Input、Table、Modal 等组件的细节。只有全局 token 时，细节差异常常会滑向样式覆盖；组件级 token 越完整，越能把定制控制在可维护范围内。

暗色模式和多品牌主题要提前验证。很多库支持“换主色”，但不一定支持运行时主题切换、多租户主题、暗色模式和高对比度主题。如果业务未来会做品牌化或白标系统，主题能力就是核心选型指标。

主题变量还要看“可覆盖但是否可治理”。变量太少会逼业务写覆盖样式；变量太多但命名混乱，也会让使用方不知道该改哪个。好的主题系统应该能用语义名称表达设计意图。

真正好的主题系统，不只是能改颜色，而是能形成设计语言到实现语言的一致映射。业务改的是语义，而不是一堆零散数值。这样后续换品牌、扩深色模式、加租户主题时，成本才不会线性爆炸。

## 二次封装

二次封装适合统一默认值、埋点、权限、业务文案和特定交互。

```tsx
type PrimaryButtonProps = ButtonProps & {
  trackName?: string;
};

function PrimaryButton({ trackName, onClick, ...props }: PrimaryButtonProps) {
  return (
    <Button
      type="primary"
      size="large"
      {...props}
      onClick={(event) => {
        if (trackName) trackClick(trackName);
        onClick?.(event);
      }}
    />
  );
}
```

封装要表达业务语义，而不是把组件库所有 props 原样再包一层。比如 `SubmitButton`、`PermissionButton`、`UserPicker` 比 `MyButton` 更有价值。

好的二次封装会隔离组件库变化，让业务层依赖稳定的领域接口。比如业务层只关心“选择用户”，不需要知道底层是 Select、Cascader 还是弹窗表格。这样未来替换组件库时，改动可以集中在封装层，而不是扩散到每个页面。

封装也要克制。如果只是把 `ButtonProps` 原样透传一遍，又没有统一默认值、业务语义或治理价值，就会增加一层无意义抽象。组件封装真正该解决的是复用、约束和一致性，不是为了“所有东西都要包一下”。

二次封装最适合放高频、有业务语义、需要统一默认值的组件。比如 `PermissionButton`、`UserSelector`、`PageTable`、`ConfirmDialog` 都有明确收益；而 `MyButton` 如果只是原样转发，价值就很低。

封装是否值得做，可以看它能不能同时解决三个问题中的至少一个：减少重复、统一约束、屏蔽底层变化。三个都做不到的封装，通常只是新增维护层，而不是新增价值。

## 样式覆盖

样式覆盖成本高于 token，但有时是必经之路。问题在于覆盖越深，升级时越容易失效。

```css
.order-form :where(.ant-form-item-label) {
  font-weight: 600;
}
```

覆盖样式要尽量局部化，并避免依赖组件库内部不稳定 class。全局覆盖虽然快，但很容易影响其他页面，尤其是弹窗、表单、表格这类复用频率高的组件。

样式覆盖最好有明确边界：页面级覆盖只服务当前页面，业务组件覆盖只服务该业务组件，基础组件覆盖必须经过统一评审。越靠近全局，影响范围越大，越需要谨慎。

如果不得不覆盖内部结构，至少要把原因写在代码附近，并在升级清单里标记出来。这样后续升级组件库时，团队知道哪些地方必须重点回归，而不是等线上样式错乱后再反查。

样式覆盖最好统一入口。比如只允许在业务组件样式里覆盖，不允许页面散写深层选择器；或者用特定命名空间包住覆盖范围。这样升级时可以用搜索快速找到风险点。

统一入口的另一个好处是能集中治理“脆弱定制”。只要覆盖规则散在几十个页面里，没人能真正回答哪些地方依赖了内部 class、哪些页面最容易被升级打断。集中管理至少能让风险可见。

## 交互定制

交互定制通常比样式定制更贵，因为它会影响状态机、焦点、键盘和可访问性。

例如把一个普通 Select 改成“远程搜索 + 多选 + 分组 + 虚拟滚动 + 键盘导航”的组件，成本已经不只是改样式，而是重做输入状态、请求状态、选中状态、加载状态和可访问性语义。

交互定制要优先判断组件库是否提供扩展点。公开的 render prop、slot、custom render、受控状态、事件回调都属于可维护扩展；直接监听内部 DOM、手动改 class、绕过组件状态则属于脆弱扩展。

复杂交互最好先封装成领域组件，再暴露稳定接口。比如远程用户选择器可以只暴露 `value`、`onChange`、`departmentId`、`disabled`，内部再处理搜索、防抖、加载和错误态。这样页面不会被组件库细节污染。

交互定制还要考虑可访问性。弹窗、菜单、下拉、日期选择器这些组件一旦重写交互，就要重新验证焦点、键盘、读屏和关闭路径。样式定制失败通常只是不好看，交互定制失败会让组件不可用。

这也是为什么交互定制的成本通常被低估。因为它表面上看只是“改一下行为”，实际上连带的是状态机、可访问性、测试用例、边界事件和回归范围的整体增加。

## 升级成本

定制越深，升级越难。每次主版本升级都可能重新检查覆盖选择器、主题变量和内部结构。

```text
升级检查：
主题 token 是否变更
内部 class 是否变更
组件 API 是否废弃
二次封装是否仍然兼容
视觉回归是否通过
```

如果一个库必须通过大量样式覆盖才能满足设计稿，升级成本会被长期放大。选型阶段就应该把这个成本算进去。

升级成本最好被显式纳入代码管理。比如把主题变量集中在一个文件，把二次封装集中在组件目录，把样式覆盖集中在可检索的命名空间下。分散在页面里的定制，短期最快，长期最难维护。

对于长期项目，组件库升级不应依赖“全员记忆”。更稳的方式是维护迁移清单：哪些组件被封装、哪些页面有深度覆盖、哪些业务流程依赖特殊交互。这样升级时能先回归高风险区域。

升级成本也可以通过封装层降低。页面越少直接依赖底层库 API，升级时越容易集中修改。反过来，如果页面到处直接使用组件库并穿透样式，升级就会变成全站排雷。

所以定制成本和升级成本其实是一体两面。今天为了赶进度随手加的覆盖、直接透传的 props、绕过公开 API 的写法，最后都会在升级时重新收你一次账。

## 设计匹配

如果设计稿和组件库风格差异很大，定制成本会急剧上升。此时要提前判断是不是应该换更贴近设计目标的库。

组件库默认风格越强，越适合沿用它的设计语言；越想做独特品牌表达，越需要关注 token 能力、无样式组件、headless 方案或自研组件体系。

设计匹配不能只看首页截图，还要看异常状态和边缘状态：错误、警告、禁用、加载、空数据、长文本、密集布局、移动端窄屏。很多组件库在常规状态很好看，但一到真实业务状态就需要大量补样式。

如果项目希望形成自己的视觉品牌，选择“可主题化能力强”的库通常比选择“默认样式最漂亮”的库更稳。默认样式越强，越容易让产品长得像组件库官网。

设计匹配最好用真实状态检查：默认、hover、focus、disabled、loading、error、empty、dark。只比较正常态，会低估定制成本。

很多组件库在默认态很漂亮，但一进入真实业务状态就开始暴露问题。定制成本评估如果不包含这些边缘状态，得到的往往只是“演示页成本”，不是“生产环境成本”。

## 决策边界

| 定制需求 | 推荐层级 |
| --- | --- |
| 颜色、圆角、间距 | token |
| 默认值、文案 | 封装 |
| 个别样式微调 | 覆盖 |
| 交互流程变化 | 封装或自研 |
| 结构完全不同 | 谨慎选型 |

定制不是坏事，但要尽量停留在最浅层。层级越深，长期维护越重。

如果某个需求必须长期停留在深层覆盖或源码改造上，通常应该重新考虑选型，或者把这块能力自研。不要把组件库用成“到处打补丁的半成品”。

最终最值得追求的，不是“什么都能改”，而是“绝大多数需求都能停留在浅层定制”。只有这样，组件库才是在帮项目降低长期成本，而不是把复杂度换一种方式藏起来。
