## 视觉决策的变量化

设计令牌是把颜色、字号、间距、圆角、阴影、动效时长等设计决策抽象成稳定变量。它不是简单的 CSS 变量命名，而是把“为什么这样设计”沉淀成可复用的系统语言。

如果组件直接写 `#1677ff`、`16px`、`8px`，短期看很快，长期会让主题切换、品牌定制和视觉统一变得困难。令牌的价值在于让组件依赖语义，而不是依赖某个具体数值。

```css
:root {
  --color-brand-600: #1677ff;
  --color-text-primary: #1f2329;
  --color-border-default: #dcdfe6;
  --radius-control-md: 6px;
  --space-control-x: 12px;
  --duration-fast: 120ms;
}

.button {
  color: #fff;
  border-radius: var(--radius-control-md);
  padding-inline: var(--space-control-x);
  background: var(--color-brand-600);
  transition: background var(--duration-fast) ease;
}
```

设计令牌通常服务于 [[4.2.3 主题系统|主题系统]] 和 [[4.2.6 组件封装与发布|组件封装与发布]]：前者通过替换令牌改变视觉，后者通过稳定令牌降低业务二次覆盖成本。

令牌化不是把所有值都变成变量。真正值得令牌化的是会被复用、会被主题切换、会影响一致性的视觉决策。一次性页面里的特殊偏移，如果强行做成令牌，反而会污染体系。

设计令牌越靠近底层，越应该稳定；越靠近组件，越可以服务具体状态。比如品牌色、文本色、间距阶梯是底层约束，按钮危险态背景色、输入框聚焦边框色则是组件状态的表达。

令牌还要考虑跨端一致性。Web 可以用 CSS 变量，React Native、Flutter、iOS、Android 则可能需要映射成各自平台的资源或常量。设计令牌越结构化，越容易从一套源头生成多端可用的输出。

```text
设计源
 -> Web: CSS Variables
 -> RN: JS Constants / Theme Object
 -> Android: colors.xml / dimens.xml
 -> iOS: asset / plist / constants
```

如果团队有多品牌或白标产品，令牌命名还要支持品牌覆盖与灰度发布。此时“语义令牌 + 组件令牌”的层级会比单纯色值表更稳。

## 原始令牌与语义令牌

原始令牌描述具体值，语义令牌描述使用意图。组件层更应该依赖语义令牌，因为组件关心的是“主按钮背景色”“危险状态边框色”，而不是“蓝色 600”或“红色 500”。

| 类型 | 示例 | 适合位置 | 变化风险 |
| --- | --- | --- | --- |
| 原始令牌 | `--blue-600`、`--gray-100`、`--space-8` | 设计系统底层 | 可能随品牌色板调整 |
| 语义令牌 | `--color-primary-bg`、`--color-error-border` | 组件样式 | 更稳定，表达业务含义 |
| 组件令牌 | `--button-primary-bg`、`--input-hover-border` | 具体组件 | 最贴近组件状态 |

一套可维护的令牌通常会形成三层映射：

```text
原始值
  -> 原始令牌：blue-600
  -> 语义令牌：color-primary-bg
  -> 组件令牌：button-primary-bg
```

这样做的好处是，当品牌主色从蓝色换成绿色时，按钮、链接、焦点环等组件不需要逐个修改，只需要调整语义令牌的映射。

```css
:root {
  --color-brand-600: #1677ff;
  --color-primary-bg: var(--color-brand-600);
  --button-primary-bg: var(--color-primary-bg);
}
```

组件令牌并不意味着组件内部完全封闭。它更像“默认映射层”，方便某个组件在局部品牌或主题下覆盖，而不会波及整套语义色板。

原始令牌适合描述色板和尺寸刻度，语义令牌适合描述使用意图，组件令牌适合描述组件细节。三层之间不要混用得太随意，否则后续会很难判断一个变量到底是设计资产，还是某个组件的实现细节。

当令牌数目增长时，最好建立校验规则，检查是否有未被使用的令牌、重复命名的令牌、映射缺失的语义值。否则设计资产会越来越像“没人敢删的散落常量”。

```text
检查项：
1. 是否被组件引用
2. 是否有重复语义
3. 是否已覆盖浅色/深色
4. 是否可生成多端资源
```

令牌系统的目标不是“看起来高级”，而是让设计决策可维护、可迁移、可审查。

## 颜色、间距与状态

颜色令牌不能只覆盖品牌色，还要覆盖文本、边框、背景、状态和遮罩。组件库里最容易失控的是状态色：默认、悬停、聚焦、激活、禁用、危险、成功等状态如果各自随意写值，会造成同一状态在不同组件上表现不一致。

```css
:root {
  --color-control-bg: #ffffff;
  --color-control-bg-hover: #f5f7fa;
  --color-control-border: #dcdfe6;
  --color-control-border-focus: var(--color-brand-600);
  --color-control-disabled-bg: #f2f3f5;
  --color-control-disabled-text: #a8abb2;
}
```

间距令牌要优先服务布局节奏，而不是把所有像素值都令牌化。常见做法是保留一组有限刻度，例如 `4 / 8 / 12 / 16 / 24 / 32`，再为控件内部空间定义语义变量。

```css
.input {
  min-height: 32px;
  padding-inline: var(--space-control-x);
  border: 1px solid var(--color-control-border);
}

.form-item + .form-item {
  margin-block-start: var(--space-section-y);
}
```

状态令牌要特别注意对比度。错误、警告、成功、信息这些状态不能只追求“颜色看起来对”，还要保证文字和背景、边框和背景、焦点环和页面底色之间有足够区分。组件库越底层，越不能把可读性问题留给业务页面。

设计令牌最好同时包含状态层级。比如表单输入的默认、悬停、聚焦、禁用、错误状态都应该有可重复使用的颜色和阴影表达。这样按钮、输入、选择器就不会各画各的状态。

```css
:root {
  --color-focus-ring: #91caff;
  --color-error-bg: #fff1f0;
  --color-error-border: #ff4d4f;
  --color-success-bg: #f6ffed;
}
```

同一状态在不同组件里可以强弱不同，但语义应该一致。比如 `danger` 在按钮上可能是填充背景，在文字链接上可能只是文本色，但它表达的都是风险更高的动作。

## 命名稳定性

令牌命名比令牌数量更重要。名称一旦进入组件实现和业务覆盖代码，就会变成公共契约。好的命名应该表达用途，避免表达视觉结果。

```text
推荐：--color-text-primary
避免：--color-black-85

推荐：--button-danger-bg
避免：--button-red-bg

推荐：--space-control-x
避免：--padding-12
```

如果令牌名称里包含具体颜色、具体像素或临时业务词，很容易在视觉调整后失真。比如 `--color-blue-primary` 在品牌色换成绿色后就会变成历史包袱，而 `--color-brand-primary` 仍然成立。

命名还要保持同一维度的顺序一致。比如颜色可以统一为 `color-role-state`，间距可以统一为 `space-scope-direction`，组件令牌可以统一为 `component-part-state-property`。命名规则越稳定，使用方越容易猜到正确变量。

## 组件落地方式

组件中使用令牌时，要把令牌作为默认值，而不是禁止业务覆盖。对于需要长期维护的组件库，推荐暴露少量稳定 CSS 变量，并用类名、状态属性或 data 属性表达状态。

```css
.button {
  --button-bg: var(--color-primary-bg);
  --button-text: var(--color-primary-text);

  color: var(--button-text);
  background: var(--button-bg);
}

.button[data-variant="danger"] {
  --button-bg: var(--color-danger-bg);
  --button-text: var(--color-danger-text);
}
```

这样封装的组件既能保持默认设计一致，又允许业务在局部场景覆盖 `--button-bg`，不需要依赖高优先级选择器或侵入组件内部 DOM。

组件落地时要避免直接依赖原始令牌。比如 Button 不应该直接写 `--blue-600`，而应该使用 `--button-primary-bg` 或 `--color-primary-bg`。这样组件不关心品牌色到底是什么，只关心自己处于什么语义状态。

```css
[data-theme="dark"] {
  --color-primary-bg: #4096ff;
  --color-text-primary: #f5f5f5;
}
```

主题切换时，最好保留“不切断语义”的原则。品牌色可以变，语义不应变；比如“主按钮背景色”应该始终代表主操作，“危险色”始终代表高风险动作。

## 令牌交付格式

设计令牌最终需要在设计工具、代码仓库和构建产物之间流转。为了避免“设计稿一套、代码一套”，令牌最好使用结构化格式维护，再生成 CSS 变量、Sass 变量、JSON 或平台代码。

```json
{
  "color": {
    "brand": {
      "primary": {
        "$type": "color",
        "$value": "#1677ff"
      }
    }
  },
  "radius": {
    "control": {
      "md": {
        "$type": "dimension",
        "$value": "6px"
      }
    }
  }
}
```

结构化令牌的价值在于可校验、可转换、可追踪。比如设计侧修改品牌色后，代码侧可以通过构建生成 CSS 变量，而不是手动同步多份值。

如果设计团队使用 Figma Tokens、Tokens Studio 或类似工具，建议把生成流程固定下来：设计源 -> 结构化文件 -> 代码生成 -> 组件消费。这样可以减少手工同步和版本漂移。

```text
设计改动
  -> token JSON
  -> 代码生成脚本
  -> 组件样式引用
  -> 预览 / 回归
```

令牌的交付格式越统一，后续做主题切换、品牌定制、跨端映射就越轻松。

如果团队同时维护 Web、移动端、小程序或跨端应用，结构化令牌会更重要。它可以被转换成 CSS 变量、Sass 变量、TypeScript 常量、Android 资源或 iOS 资源，让不同端共享同一套设计决策。

## 令牌版本

令牌变化也需要版本意识。新增令牌通常安全，修改语义令牌映射可能影响全站视觉，删除令牌则可能破坏业务覆盖。

```text
新增原始色板：低风险
调整语义色映射：中风险
删除组件令牌：高风险
改变间距阶梯：高风险
```

如果令牌已经被业务项目引用，删除前应提供替代名称和迁移周期。令牌不是内部实现细节，而是主题系统和业务定制之间的公共契约。

令牌版本最好和组件版本一起管理。组件新增状态时，可能也要新增状态令牌；主题新增品牌时，可能要验证所有组件令牌是否覆盖完整。令牌和组件分开演进但不相互校验，很容易出现“组件有状态、主题没有值”的断层。

版本管理还要给业务足够的迁移时间。删除或重命名令牌之前，最好先提供 alias 或兼容层，保证旧组件和旧主题还能跑一段时间。

```css
:root {
  --color-primary-bg: var(--color-brand-600);
  --button-primary-bg: var(--color-primary-bg);
  /* 旧名保留一段时间 */
  --button-bg-primary: var(--button-primary-bg);
}
```

令牌一旦成为公共契约，修改它就不只是改一个值，而是在改一批组件的默认语义。
