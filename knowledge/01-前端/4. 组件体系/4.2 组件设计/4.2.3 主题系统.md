## 主题变量

主题系统是把一组视觉决策切换为另一组视觉决策的机制。它依赖 [[4.2.1 设计令牌|设计令牌]]，但不等于令牌本身：令牌提供变量，主题系统负责变量的注入、覆盖、隔离和切换。

最简单的主题系统可以基于 CSS 变量实现。

```css
:root {
  --color-bg-page: #ffffff;
  --color-text-primary: #1f2329;
  --color-primary-bg: #1677ff;
}

[data-theme="dark"] {
  --color-bg-page: #101418;
  --color-text-primary: #f2f3f5;
  --color-primary-bg: #4096ff;
}

body {
  color: var(--color-text-primary);
  background: var(--color-bg-page);
}
```

CSS 变量的优势是可以在运行时切换，不需要重新编译样式。它也支持局部主题，例如某个后台应用嵌入到门户中，只在容器节点上覆盖变量即可。

主题系统除了颜色，还常常要覆盖字体、圆角、阴影、动效和间距。真正成熟的主题，不是只有深色和浅色，而是能保持组件语义、可访问性和品牌一致性。

```html
<main data-theme="brand-a">
  <button class="button">品牌 A 按钮</button>
</main>
```

主题系统真正难的地方，不是把颜色切换掉，而是确保切换后组件状态仍然合理。比如按钮、输入框、弹窗、提示、表格这些组件在浅色和深色下都要保持对比度、层级和可读性一致。

这也是为什么主题系统不能只由设计稿颜色表驱动。颜色值只是结果，真正需要管理的是语义关系，例如“页面背景”“表单边框”“危险文本”“悬浮背景”“主按钮默认态”。语义关系稳定，主题切换才会稳定。

## 暗色模式

暗色模式不是把颜色反转。暗色主题需要重新处理背景层级、边框透明度、文字对比度、阴影表达和状态色亮度。浅色主题中依赖阴影区分层级，暗色主题中往往要更多依赖背景色差和边框。

```css
:root {
  color-scheme: light;
}

[data-theme="dark"] {
  color-scheme: dark;
}
```

`color-scheme` 可以让浏览器原生控件、滚动条和表单控件更贴近当前主题，但组件本身的颜色仍然要由令牌控制。对于复杂表单和弹窗，暗色模式还要检查焦点环、禁用态和错误态的可读性。

```text
浅色主题：白底 -> 灰底层级 -> 深色文字 -> 彩色强调
暗色主题：深底 -> 亮度层级 -> 浅色文字 -> 降饱和强调
```

暗色模式不要只看首页或按钮。真正容易出问题的是表单帮助文本、表格边框、选择器弹层、阴影层级和半透明遮罩。很多组件在浅色下没问题，一切换主题就会露出对比度不足或层级不清的情况。

主题切换最好做视觉验证。页面顶部和基础组件往往好改，真正难的是复杂页面里的表格、弹层、空态和错误态。暗色主题上线前，至少要抽样检查表单、列表、对话框、导航和文本密集区域。

如果项目支持运行时切换主题，还要关注切换过程本身是否平滑。颜色变化、图标反色、阴影消失、局部容器未同步这些问题，往往不是静态截图能发现的，必须在真实交互里验证。

## 品牌定制

品牌定制通常有两种路径：全局替换主题变量，或只为少数组件开放组件级变量。前者适合统一品牌换肤，后者适合业务局部定制。

```css
[data-brand="finance"] {
  --color-primary-bg: #0f766e;
  --color-primary-bg-hover: #0d9488;
  --button-primary-radius: 999px;
}

.button[data-variant="primary"] {
  border-radius: var(--button-primary-radius, var(--radius-control-md));
  background: var(--color-primary-bg);
}
```

组件库不应该鼓励业务通过深层选择器覆盖内部 DOM。

```css
/* 不推荐：依赖内部结构，组件升级后容易失效 */
.my-page .button > span:first-child {
  margin-right: 10px;
}
```

更稳定的方式是暴露明确插槽、属性或组件级变量。这会让主题能力和 [[4.2.6 组件封装与发布|组件封装与发布]] 的 API 契约保持一致。

品牌定制最好优先通过主题系统完成，而不是在页面里局部硬改。局部硬改可以救急，但如果同一个品牌有大量页面都在重复覆盖，说明主题边界没有收紧，后续维护会越来越散。

品牌定制时也要考虑“局部品牌”与“全局品牌”的区别。企业门户可能整站一个品牌，但运营活动页、嵌入式小模块、子品牌页面可能只需要局部主题。主题系统能否覆盖容器级别，是判断它是否足够实用的重要标准。

局部品牌能力还直接影响微前端、嵌入模块和白标场景。只支持全局换肤的主题系统，通常很难在一个页面里同时容纳多个视觉域；而能按容器注入变量的主题系统，会更适合复杂产品矩阵。

## 主题边界

主题系统应该明确哪些内容可以改，哪些内容不建议改。颜色、圆角、字号、间距通常可配置；交互逻辑、焦点顺序、错误提示结构不应该被主题覆盖。

| 可主题化 | 谨慎主题化 | 不应通过主题修改 |
| --- | --- | --- |
| 品牌色、背景色、文字色 | 控件高度、动画时长 | 表单校验逻辑 |
| 圆角、阴影、边框 | 断点、栅格间距 | 键盘交互方式 |
| 组件状态色 | 字体族、字号阶梯 | 可访问性语义 |

如果主题能力过度开放，业务会把主题当成“万能覆盖层”，最终导致组件外观看似统一，行为却不可预测。

主题边界越清楚，组件库越稳定。一个比较健康的原则是：主题负责“看起来像什么”，组件负责“行为是什么”，业务负责“为什么要这么用”。三者不要互相替代。

主题系统不应该改写业务逻辑。例如通过主题控制是否允许提交、是否显示某些字段，这种做法会让视觉配置变成行为开关。主题只能影响表达，不能替代规则。

一旦主题开始承担行为开关，就会破坏系统可预测性。页面看起来换的是颜色，实际却顺手改了交互和流程，后续排查时很难分清问题到底来自设计配置还是业务规则。

## 注入顺序

主题系统还要处理样式注入顺序。默认主题、品牌主题、业务局部覆盖、用户偏好如果顺序混乱，就会出现同一组件在不同页面表现不一致。

```text
组件默认变量
  -> 产品主题变量
  -> 品牌主题变量
  -> 页面局部变量
  -> 用户偏好变量
```

局部覆盖应该只影响当前容器。比如后台主应用使用企业主题，嵌入的营销模块可以在自己的根节点覆盖变量，但不应污染全局。

注入顺序最好有明确层次，否则不同页面之间会出现“同一个组件在这个页面是这种颜色，在另一个页面是另一种颜色”的混乱。层次越明确，排查主题问题越容易。

如果项目同时支持系统主题和用户主题，优先级也要明确：系统偏好只是默认值，用户手动选择通常应覆盖系统偏好，页面局部覆盖则只作用于局部容器。优先级不清会让切换结果不可预测。

优先级清楚以后，主题系统才真正像“规则系统”而不是“样式碰碰运气”。用户在设置页里选了深色主题，页面就不应该又被系统浅色偏好改回去；局部容器做了品牌覆盖，也不应该顺手污染全站。

## 主题持久化

用户手动切换主题后，通常需要持久化到本地存储或服务端偏好。持久化时要注意首屏闪烁：如果页面先按默认主题渲染，再切换到用户主题，用户会看到明显闪动。

```html
<script>
  const theme = localStorage.getItem("theme") || "light";
  document.documentElement.dataset.theme = theme;
</script>
```

这段脚本通常应尽早执行，放在应用主脚本之前。SSR 项目还要考虑服务端输出的主题与客户端 hydration 是否一致。

主题持久化还要考虑系统偏好。很多用户会希望默认跟随系统深色模式，再允许在应用内手动覆盖。这个优先级如果没有定义好，用户切换主题后会被系统设置覆盖，或者反过来导致页面和系统表现不一致。

```text
优先级示例：
用户手动设置 > 页面局部覆盖 > 系统偏好 > 默认主题
```

主题初始化最好放到尽早执行的位置，避免首屏先渲染默认主题再闪到目标主题。这个小闪动在视觉上很明显，也很容易被误认为是性能问题。

如果项目有 SSR 或静态预渲染，主题初始化脚本应该尽量前置，否则首屏闪烁会很明显。主题系统的体验好坏，往往就差在这一下。

从工程角度看，主题系统的成熟度通常体现在三件事上：主题变量是否语义化，注入顺序是否可控，首屏切换是否无闪烁。只要这三件事稳定，后续再扩品牌、扩暗色、扩局部主题时才不会推倒重来。
