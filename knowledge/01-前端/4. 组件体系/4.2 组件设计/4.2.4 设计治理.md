## 治理机制

设计治理的核心不是“多几个流程”，而是明确谁对规范、视觉、破坏性变更和回收负责。没有治理，组件会在不同项目里悄悄漂移。

```text
常见角色：
1. 设计负责人
2. 组件库维护者
3. 前端负责人
4. 使用方代表
```

如果没有所有权，组件规范会在不同团队、不同版本和不同页面里逐渐变形。治理机制的第一步，就是把责任和决策边界写清楚。

治理机制要解决三个问题：谁能新增组件、谁能修改规范、谁负责推动旧方案回收。没有这些边界时，组件体系表面上很自由，实际上会让每个业务线都长出自己的按钮、弹窗和表单规则。

治理不等于审批变慢。好的治理应该让常规需求有快速通道，让破坏性变更有充分评审，让重复需求能被沉淀为公共能力。

治理机制最好配合设计规范、代码规范和版本发布一起看。只靠会议评审不够，必须有可执行的检查点，比如类型约束、Storybook 演示、视觉回归、废弃标记和迁移说明。

```text
日常修复：维护者评审
新增组件：设计 + 前端联合评审
破坏性变更：提案 + 迁移方案 + 试点
大范围视觉调整：主题验证 + 视觉回归
```

这样既不会让小修小补被流程拖慢，也不会让影响全站的改动悄悄进入业务项目。

## 变更流程

组件设计的变化不应该直接悄悄改在业务项目里。更稳妥的路径是提案、评审、试点、发布和通知。

```text
提案 -> 评审 -> 样板验证 -> 发布 -> 通知使用方
```

变更流程要区分小变更和大变更。文案调整、样式微调、补充 token 可以走轻量流程；组件交互模型、默认行为、DOM 结构、关键 API 变化则必须经过样板验证和迁移评估。

样板验证最好覆盖真实业务页面，而不是只改 Storybook 里的 demo。组件在 demo 里通常很干净，但到业务页面会遇到长文本、权限态、异步数据、错误态、低端设备和复杂布局。

组件治理还应关注“谁来做最后决定”。如果设计、前端、产品对冲突意见没有决策机制，组件规范会在评审里拖很久。治理的目标是减少反复争论，而不是把每个问题都交给群聊临时拍板。

## 版本演进

组件设计会持续演进，不能假设一套规范永远不变。

| 类型 | 例子 | 处理方式 |
| --- | --- | --- |
| 新增 | 新增 `variant` | 小版本 |
| 调整 | 文案、默认值、变量映射 | 小版本或补丁 |
| 破坏性 | 删除 prop、改 DOM 结构 | 大版本 |

版本演进要让使用方能预期风险。补丁版本不应该改变交互语义，小版本可以新增能力但不应破坏旧用法，大版本才适合移除旧 API 或调整基础结构。即使不是发布 npm 包，内部组件库也应该遵守类似的版本边界。

如果多个业务项目共用组件库，版本演进还要考虑“升级窗口”。并不是所有项目都能马上升级，维护者需要在一定时间内保留兼容层，让业务项目有节奏地迁移。

对于大型组件库，版本演进最好和 changelog、migration guide、codemod 一起发。这样使用方不仅知道变了什么，也知道怎么改。

```text
Changelog：说明变化
Migration：说明迁移步骤
Codemod：自动迁移重复代码
Deprecation：给旧 API 留缓冲期
```

版本治理的目标是让升级可预期，而不是每次升级都像拆盲盒。

## 质量闭环

规范不只是写完就结束，而是要能被执行、验证和回收。

```text
闭环：
1. 规范文档
2. 代码实现
3. 样板验证
4. 使用反馈
5. 回收旧方案
```

质量闭环的关键是“规范和实现一致”。如果设计稿、文档、代码和线上行为不一致，使用方会不知道该信谁。组件体系应该把 demo、设计资源、代码示例和变更记录尽量同步更新。

可以把质量拆成几类检查：视觉一致性、交互一致性、无障碍、类型约束、单元测试、视觉回归和真实页面试用。不是每个组件都需要同样重的检查，但高频基础组件和复杂组件必须更严格。

治理闭环里还应该有“回收结果”。旧 API 标记废弃后，是否真的减少使用、是否真的移除、是否出现绕过组件体系的临时实现，这些都要回看。

```text
发布前：测试和示例通过
发布后：收集接入问题
迁移期：统计旧 API 使用量
截止后：删除兼容层
```

没有回收动作的治理，最后会变成“新旧方案并存”。组件体系最怕的不是没有新能力，而是旧能力永远删不掉。

## 决策记录

重要设计决策应当可追溯，比如为什么选择某种状态模型、为什么保留某个 API、为什么不支持某种定制方式。

```text
记录内容：
1. 问题背景
2. 备选方案
3. 最终选择
4. 代价与风险
```

决策记录不是为了写文档而写文档，而是为了避免半年后团队重复争论同一个问题。尤其是“为什么不做某个能力”，比“做了什么”更值得记录。拒绝支持一个高度定制需求，可能是为了保护组件长期稳定性。

如果决策会影响业务接入方式，就要写清迁移影响和替代路径。否则使用方只看到结果，看不到权衡，后续会更容易绕过组件体系。

决策记录不需要长篇大论，但至少要足够让后来者知道：为什么不是别的方案、这个方案的代价是什么、什么时候要重新评估。这样组件体系才能持续演进，而不是靠记忆维持。

```text
例如：
不开放 Button 内部 span class 覆盖。
原因：内部 DOM 会随图标、loading、国际化变化。
替代：提供 icon、children、variant、CSS 变量。
```

把“不支持什么”写清楚，比只写“支持什么”更能保护组件边界。

## 废弃策略

废弃不是直接删除，而是先标记、再迁移、最后回收。

```text
废弃顺序：
1. 标记 deprecated
2. 提供替代 API
3. 迁移样板
4. 给出截止版本
5. 再移除
```

废弃策略要给使用方可执行路径。只写“这个 API 已废弃”不够，还要说明替代 API、迁移示例、影响范围和最后移除时间。否则废弃会长期停留在警告里，旧代码永远不会真正减少。

对高频组件来说，最好配套 codemod、lint 规则或迁移脚本。人工迁移容易漏，工具化迁移能把重复劳动降下来，也能减少风格漂移。

废弃策略还要避免“永久 deprecated”。如果旧 API 一直留着，维护者就必须同时支持两套语义，测试矩阵和文档都会变复杂。废弃应该有明确窗口和移除版本。

## 反馈机制

治理要有反馈入口，让使用方能把问题回传给维护者。

```text
反馈来源：
1. 文档评论
2. 使用问题单
3. 设计评审
4. 代码评审
```

好的治理不是增加阻力，而是让组件设计长期保持可预期、可维护、可回收。

反馈机制要能闭环到版本计划。使用方反馈的问题如果只停留在聊天记录里，很快就会丢失；如果能进入 issue、需求池或版本路线图，就能被排序、评审和跟踪。治理的价值，就是把零散经验变成可复用资产。

反馈还要分类处理。Bug、文档缺口、设计不一致、API 不足、性能问题和无障碍问题的处理路径不同，不能全部堆在一个“组件库问题”池子里。

```text
Bug：尽快修复并补回归
API 缺口：先找重复场景再设计
设计漂移：回到规范和令牌
性能问题：补 benchmark 或真实页面验证
```

分类清楚以后，组件维护者才能判断哪些问题应该立即修，哪些问题需要进入下一轮设计。
