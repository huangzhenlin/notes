## 基础组件

基础组件是最底层的 UI 原子，比如 Button、Input、Icon、Badge、Space、Modal 的底层壳。

```text
特点：
1. 面向原子能力
2. 尽量少业务语义
3. 可复用范围最广
```

基础组件应该尽量稳定、单一、可预测。它们负责视觉和交互原语，而不是业务判断。

基础组件的职责是“把最小但最常用的能力做对”。比如按钮要处理禁用态、加载态、点击态和键盘可达性，输入框要处理焦点、占位符、清空、禁用和错误态。越底层的组件，越不能轻易掺进业务文案、接口请求或页面级流程。

如果基础组件开始频繁出现特例，通常说明设计系统还不稳定，或者组件本身被做得太大了。此时应该先拆分共性，再补特性，而不是继续往一个组件里塞条件分支。

基础组件层最怕“为了复用而复用”。一个 Button 如果已经开始同时承担权限、埋点、表单提交、路由跳转和业务文案，它表面上还是基础组件，实际上已经偷偷长成了业务组件。

## 组合组件

组合组件由多个基础组件拼装而成，比如表单行、筛选栏、表格工具条、详情头部。

```tsx
<SearchBar />
<ActionToolbar />
```

组合组件负责把基础组件和常见交互组合成更高层次的可复用单元。它们通常有明确的交互模式，但不应该带业务领域语义。

组合组件是最容易积累工程价值的一层。它能把表单行、工具条、搜索区、筛选区、列表头这些常见结构沉淀下来，让页面不再重复拼装这些基础布局。

这一层最重要的是“模式稳定”。如果一个组合组件在不同页面都长得差不多，才值得抽出来；如果每个页面都差很多，硬抽只会增加分支。

组合组件的价值，通常来自页面结构的重复而不是视觉像不像。搜索栏、筛选区、工具条、分页头、空态区这些模式一旦稳定，就能显著减少页面重复拼装，也能顺带统一交互细节。

## 业务组件

业务组件包含明确领域语义，比如 `UserStatusTag`、`OrderSummaryCard`、`PermissionPanel`。

```text
业务组件的特点：
1. 面向某个业务域
2. 可能依赖接口数据
3. 复用范围较小但价值高
```

业务组件最重要的不是“通用”，而是“语义清楚”。当某块 UI 在多个页面都出现，但含义始终属于同一业务领域时，就适合抽成业务组件。

业务组件和领域模型往往更接近。比如用户状态、订单摘要、权限面板、组织选择器这类组件，复用价值不一定比基础组件高，但语义很明确，也更能减少页面代码里的重复判断。

业务组件通常会依赖接口数据，但它不应该自己承担完整的数据获取责任。更稳妥的做法，是让页面或上层容器负责请求，业务组件负责展示和局部交互。

这条边界能明显降低耦合。只要业务组件自己偷偷发请求、自己决定缓存、自己处理路由，后面复用时就会发现它并不是“领域组件”，而是“一个绑着特定页面上下文的小页面模块”。

## 页面模块

页面模块通常包含布局、请求、状态和多个业务组件的组合。

```tsx
<PageLayout>
  <FilterPanel />
  <ResultTable />
</PageLayout>
```

它更像一个页面的组装层，而不是一个基础组件。页面模块负责路由级组织和数据拼装，不应该再去做低层原语封装。

页面模块的核心价值是把“请求、状态、权限、布局、业务组件”组织成一个完整页面。它不应该再追求极致复用，而是追求清晰和可维护。很多页面级重复，实际上更适合被提到业务组件层，而不是继续往页面模块里复制。

如果页面模块越来越厚，通常说明组件层拆分不足，或者数据流没有分层。此时优先检查是不是该把某些表单区、查询区、操作区和结果区抽成更高层的组合组件。

页面模块厚并不可怕，可怕的是它同时承担原语封装、业务语义、请求编排和局部交互。只要这些职责全部堆在一起，页面很快就会变成重构最困难、测试最脆弱的一层。

## 分层边界

| 层级 | 职责 |
| --- | --- |
| 基础组件 | 最小交互和视觉原语 |
| 组合组件 | 组装常见模式 |
| 业务组件 | 领域语义封装 |
| 页面模块 | 路由级组织 |

如果基础组件里出现接口请求，或者业务组件里暴露太多底层 DOM 细节，分层就开始失效了。

分层边界不是教条，而是为了减少耦合。基础组件越底层，越应该少知道业务；页面模块越上层，越应该少关心具体原语。只要职责清楚，团队就更容易知道问题该改哪里。

如果一个需求跨越多层，通常应该从上到下传递意图，而不是从下往上穿透实现。例如页面需要一个“可搜索的用户选择器”，合理路径通常是页面使用业务组件，业务组件组合基础输入和下拉，而不是页面直接操作底层 DOM。

这也是为什么分层不只是目录约定，而是沟通约定。页面说“我要一个用户选择器”，业务组件说“我会提供这个语义”，组合组件说“我来拼交互模式”，基础组件说“我负责最小原语”。层层职责清楚，团队协作会轻松很多。

分层还能帮助控制测试粒度。基础组件测交互原语，组合组件测模式拼装，业务组件测领域语义，页面模块测路由流程。每层都测自己的职责，失败时更容易定位。

```text
基础组件：点击、键盘、焦点、样式状态
组合组件：插槽、布局、联动规则
业务组件：字段映射、权限、领域文案
页面模块：请求、路由、完整流程
```

如果所有测试都写成页面 E2E，问题定位会很重；如果只测基础组件，又覆盖不到业务流。分层测试能让质量成本更可控。

## 目录映射

目录结构最好和分层保持一致，这样新成员能快速知道该在哪一层找组件。

```text
components/base
components/composed
components/business
pages
```

如果目录命名和分层没有对齐，后面最先乱的往往不是代码，而是大家对“这个组件应该放哪”的理解。

目录映射最好让新成员一眼能看懂。基础组件目录里放最通用的原语，组合组件目录里放高频模式，业务组件目录里放领域封装，页面目录里放路由页或页面容器。这样检索和维护都更直观。

目录如果和分层不一致，最常见的问题就是“大家都把东西放到最顺手的地方”。短期看没问题，长期就会出现基础组件目录越来越杂、业务组件目录越来越散、页面目录里夹杂大量可复用片段。

```text
components/base/Button
components/composed/SearchBar
components/business/UserPicker
pages/user/UserListPage
```

目录命名不一定非要完全一样，但要让团队对“放哪一层”有共同答案。

目录一旦和分层认知脱节，最先出问题的往往不是构建，而是协作。每个人都能找到一个“看起来差不多”的地方放组件，久而久之基础层会越来越杂，业务层会越来越难搜，重构成本也会跟着上升。

## 依赖方向

| 方向 | 允许吗 |
| --- | --- |
| 业务组件依赖基础组件 | 允许 |
| 页面模块依赖业务组件 | 允许 |
| 基础组件依赖业务逻辑 | 不允许 |

底层组件一旦开始向上引用，就会破坏长期演进能力。分层的价值，是让复用和演进都更可控。

依赖方向一旦反过来，常见后果是：基础组件越来越重、业务逻辑越来越隐蔽、页面改一点东西要牵动很多地方。分层越清晰，后续重构和替换就越容易。

一条实用原则是：越底层越少依赖，越上层越能组合。基础组件不依赖业务组件；组合组件只依赖基础组件；业务组件可以依赖基础和组合；页面模块可以依赖全部，但不反向暴露底层细节。

```text
允许：Page -> Business -> Composed -> Base
不允许：Base -> Business
不建议：Composed -> Page
```

如果依赖方向需要破例，通常说明分层命名或组件职责需要重新检查。

依赖方向清楚以后，替换成本也会明显下降。你可以替换基础组件实现，而不必重写业务组件语义；也可以重组页面模块，而不必推翻基础层。这种可替换性本身就是分层设计的重要收益。

## 复用判断

判断某个东西该不该抽成组件，可以问三件事：是否有稳定语义、是否存在重复使用、是否能脱离当前页面理解。答案都不够成立，就别急着拆。

还可以再加一个判断：如果这个东西未来会被多个页面以相同方式使用，抽出来的收益就更高；如果它只是一次性场景，过早抽象通常会增加认知负担。

组件是否要抽象，也要看“变化是稳定重复，还是偶然重复”。偶然重复可能只是当前页面碰巧相似，真正抽出来后很快就会因为第二个页面的差异而加一堆特例。稳定重复才适合提升为组件层能力。

```text
稳定重复：多个页面相同结构、相同交互、相同边界
偶然重复：视觉相似，但业务规则和变化点不同
```

复用判断不是看复制了几行代码，而是看抽象后能否减少未来决策。

一个很实用的信号是：抽出来以后，调用方是否会变得更简单、更一致、更少分支。如果抽完之后每个页面还要继续传一堆特例参数，说明抽象时机可能还没到，或者抽象层级选错了。
