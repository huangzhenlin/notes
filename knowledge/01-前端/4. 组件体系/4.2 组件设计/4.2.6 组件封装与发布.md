## 封装边界

组件封装的核心是确定什么应该被隐藏，什么必须被暴露。封装不是把 DOM 包起来，而是把稳定的使用方式、状态规则和视觉契约交给组件维护。

一个好的组件应该隐藏内部结构，暴露可理解的能力。

```tsx
type AlertProps = {
  type?: "info" | "success" | "warning" | "error";
  title: string;
  description?: string;
  closable?: boolean;
  onClose?: () => void;
};
```

这里暴露的是告警的语义，而不是内部图标、颜色、间距和 DOM 层级。业务调用方只需要表达“这是错误提示，允许关闭”，不需要关心具体结构。

封装边界要避免两个极端：过度封装会让组件难以适配真实场景，封装不足又会让业务到处覆盖内部实现。组件应该提供少量稳定扩展点，例如插槽、渲染函数、样式变量和受控属性。

封装时最好把“稳定 API”和“实验性能力”分开。稳定 API 可以长期承诺兼容，实验性能力可以先做内部试点，等使用情况明确再正式公开。

```text
公开面：Button variant / size / disabled
内部面：实验性动画、debug 标记、临时适配钩子
```

这样能避免组件库一开始就把所有可能性都暴露给使用方。

## API 契约

组件 API 是长期契约。命名、默认值、事件时机、受控模式、可访问性语义都会影响使用方。API 设计要优先表达业务意图，而不是暴露实现细节。

```tsx
type DialogProps = {
  open: boolean;
  title?: React.ReactNode;
  children: React.ReactNode;
  onOpenChange: (open: boolean) => void;
};
```

`open` 和 `onOpenChange` 构成受控 API，使用者可以把弹窗状态交给路由、表单或外部状态管理。这个模式和 [[4.1.5 受控模式|受控模式]] 一致，适合弹窗、抽屉、下拉框、分页器等需要外部协调的组件。

API 契约还要写清事件时机。例如 `onChange` 是输入中触发，还是失焦后触发；`onOpenChange` 是点击触发还是状态真正变化后触发。这个细节直接关系到表单联动和异步状态收口。

API 设计时要特别注意布尔属性膨胀。

```tsx
// 不推荐：多个布尔值容易组合出非法状态
<Button primary danger ghost />

// 推荐：用枚举表达互斥关系
<Button variant="danger" appearance="ghost" />
```

当多个属性之间存在互斥或依赖关系时，类型系统应该尽量帮助约束，而不是把所有组合都留到运行时。

## 文档示例

组件文档不能只列属性表。使用方真正需要的是：什么时候用、怎么用、边界是什么、错误用法是什么。示例要从最小用法开始，再展示常见组合和复杂场景。

```tsx
<Button variant="primary">保存</Button>

<Button variant="primary" loading>
  提交订单
</Button>

<Button variant="danger" onClick={handleDelete}>
  删除
</Button>
```

好的示例应该能直接复制运行，并且覆盖状态差异。对于复杂组件，示例比 API 表更重要，因为它展示了多个属性如何协同。

```text
基础示例：最小可用
状态示例：loading、disabled、error
组合示例：和表单、弹窗、列表协同
边界示例：长文本、空数据、异步失败
```

文档还要同步说明可访问性行为，例如键盘如何打开菜单、焦点关闭后回到哪里、错误信息如何被读屏识别。这些内容不能只留给实现者理解。

文档示例最好覆盖最小用法、受控用法、组合用法和边界用法。只放最简单的 demo，业务方会在复杂场景里自己踩坑；只放复杂 demo，又不利于新人上手。

## 构建产物

组件库发布时通常要同时考虑 ESM、CJS、类型声明和样式产物。现代前端项目优先使用 ESM，因为它更利于 Tree Shaking；但如果使用方仍有 Node 或旧构建链需求，可能还需要 CJS。

```json
{
  "name": "@acme/ui",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "sideEffects": [
    "**/*.css"
  ],
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

样式产物要明确导入方式：是全量 CSS、按组件 CSS、CSS-in-JS，还是基于原子类。不同方案会影响 [[4.4.4 体积性能|体积性能]] 和主题定制方式。

发布产物还要尽量可预测。入口文件、样式路径、类型声明、子路径导出和副作用范围最好固定，不要让每次发版都改包结构。包结构一旦不稳定，升级和按需加载都会受影响。

## 版本发布

组件库发布要遵循语义化版本。对于公共组件来说，破坏性变化不只包括 TypeScript 类型不兼容，也包括 CSS 变量删除、类名变化、DOM 结构调整和默认交互改变。

```text
1. 修复缺陷：补丁版本
2. 新增兼容能力：小版本
3. 移除或改变旧能力：大版本
```

发布说明要写清楚“影响谁”和“如何迁移”。如果只写“优化 Button 样式”，使用方很难判断是否需要升级。

发布记录里还应该说明“是否需要同步设计稿或样板”。如果某次改动会影响视觉稿、主题变量或使用示例，最好一并写到发布说明里，避免设计和开发版本脱节。

```text
Button

修复：`loading` 状态下仍可触发点击的问题。
废弃：`primary` 布尔属性，请使用 `variant="primary"`。
移除计划：下一大版本将移除 `primary` 属性。
```

## 按需加载

按需加载的目标是让使用方只打包实际用到的组件和样式。组件库要避免入口文件产生无关副作用，否则构建工具很难安全裁剪代码。

```ts
// 推荐：独立导出，便于 Tree Shaking
export { Button } from "./button";
export { Input } from "./input";

// 谨慎：入口直接执行全局注册或注入样式，会形成副作用
registerAllComponents();
```

样式按需加载也需要规划。如果组件 JS 可以裁剪，但 CSS 始终全量引入，最终体积仍然会偏大。常见做法是每个组件维护自己的样式入口，再由构建工具或插件按需导入。

```ts
import { Button } from "@acme/ui/button";
import "@acme/ui/button/style.css";
```

按需加载不应该牺牲使用体验。对于内部业务组件库，可以先提供稳定的全量入口，再逐步补充按需入口；对于面向多项目的通用组件库，则应该从一开始就设计好模块边界和样式边界。

如果组件库同时支持全量引入和按需引入，必须保证两种方式行为一致。按需引入不应该漏样式、漏副作用或漏类型，否则使用方会因为导入方式不同得到不同体验。

## 自动化测试

组件库测试要覆盖逻辑、交互、可访问性和视觉稳定性。不同测试类型关注不同风险，不应该只靠快照测试证明组件可靠。

| 测试类型 | 关注内容 | 适合组件 |
| --- | --- | --- |
| 单元测试 | 状态变化、事件回调、边界属性 | Button、Input、Tabs |
| 交互测试 | 点击、键盘、焦点、异步提交 | Modal、Select、Form |
| 可访问性测试 | 语义、名称、ARIA、键盘路径 | Dialog、Menu、Tooltip |
| 视觉回归 | 尺寸、颜色、间距、主题差异 | 全部公共组件 |

文档示例也应该能参与测试。示例如果长期不可运行，文档会逐渐变成静态说明，无法保证和真实组件同步。

测试还应该覆盖主题、语言、无障碍和不同密度模式。很多组件在默认主题下通过了，但一切换暗色模式、紧凑模式或高对比模式，就会出现视觉和交互问题。

## 发布清单

发布前应该有固定清单，确保组件、样式、类型、文档和迁移说明同步完成。

```text
类型声明已生成
样式入口可导入
ESM 与 CJS 产物符合预期
组件示例可运行
破坏性变化已标记
废弃 API 有迁移说明
包体变化已检查
```

发布清单可以很轻量，但要固定。组件库影响多个项目，发布质量越稳定，业务团队越愿意升级。

如果发布涉及破坏性变化，最好同时准备迁移文档、示例 diff 和回滚策略。这样出问题时不至于靠口头解释排查。
