## 原生能力

表单组件应该尽量保留原生 input、select、textarea 的行为，包括键盘输入、焦点、提交、自动填充和可访问性语义。

```tsx
<input type="email" autoComplete="email" />
```

表单组件最常见的误区，是把“样子像输入框”当成“能正常工作”。实际上，正确的光标行为、移动端键盘类型、浏览器自动填充和回车提交都很重要。

如果为了美化把原生能力完全重做，后续验证、移动端输入法和辅助技术都会更难处理。

表单组件不是单纯的输入框外壳，它还承担信息收集、校验、提示、提交和错误恢复。设计表单组件时，除了外观，还要考虑它如何和 label、help、error、required、disabled、loading 这些外围信息协作。

如果组件只是“长得像表单”，但没有和原生表单行为对齐，后续在 Enter 提交、自动填充、回车换行、移动端键盘切换上都可能掉坑。

原生能力还包括正确的 `name`、`type`、`autoComplete`、`inputMode` 和 `disabled`。这些属性会影响浏览器自动填充、移动端键盘、表单提交和辅助技术识别。

```tsx
<label htmlFor="email">邮箱</label>
<input
  id="email"
  name="email"
  type="email"
  autoComplete="email"
  inputMode="email"
/>
```

自定义组件封装时要把这些能力透传到底层输入元素。不要只暴露 `value` 和 `onChange`，否则业务页面遇到自动填充、测试定位、无障碍关联时会很难补。

## 校验时机

表单校验通常有三种时机：输入时、失焦时、提交时。

```text
输入时：即时反馈
失焦时：减少打扰
提交时：最终兜底
```

不同字段适合的校验时机不同。邮箱格式、密码强度适合即时提示；身份证、地址这类长文本更适合失焦或提交时校验。

校验时机还要看用户成本。越短、越规则明确的字段，越适合即时校验；越长、越依赖上下文的字段，越适合延后校验。否则用户一边输入一边报错，很容易被打断。

| 字段类型 | 推荐时机 | 原因 |
| --- | --- | --- |
| 邮箱、手机号 | 输入或失焦 | 规则简单 |
| 用户名唯一性 | 失焦或提交 | 需要请求 |
| 长文本 | 失焦或提交 | 即时提示打扰大 |
| 密码强度 | 输入时 | 反馈能指导输入 |

校验时机还要区分“提示”和“阻止”。输入时可以展示轻提示，但不一定要立即阻止用户继续输入；提交时则必须做最终校验。比如密码强度可以边输入边提示，但邮箱格式最好等用户输入完成或失焦后再显示错误。

```text
输入中：帮助用户发现趋势
失焦后：提示字段级错误
提交时：统一阻止无效提交
```

这样能减少“用户还没输完就报错”的挫败感，也能保证最终提交不会漏校验。

## 错误反馈

表单错误反馈应该足够明确，告诉用户错在哪里、为什么错、怎么改。

```tsx
<input aria-invalid={hasError} aria-describedby="email-error" />
<p id="email-error" role="alert">
  邮箱格式不正确
</p>
```

错误提示位置、颜色、文案和关联字段应该统一，不要每个表单都重新设计一套。

好的错误反馈至少满足：

1. 字段和错误能对应。
2. 文案能指导修正。
3. 屏幕阅读器能感知状态。
4. 提交失败后焦点能引导到错误区域。

错误信息最好能绑定到字段，而不是只放在页面顶部。顶部错误适合说明整体失败，例如“保存失败，请稍后重试”；字段错误适合说明具体修改方式，例如“邮箱格式不正确”。

```tsx
<Field label="邮箱" error={errors.email}>
  <input
    aria-invalid={Boolean(errors.email)}
    aria-describedby={errors.email ? "email-error" : undefined}
  />
</Field>
```

提交失败后，如果存在字段错误，可以把焦点移动到第一个错误字段。这样键盘用户和读屏用户都能快速知道下一步该修改哪里。

## 异步校验

唯一性检查、服务端规则校验、地址联想都属于异步校验。

```ts
let checkId = 0;

async function validateUsername(name: string) {
  const currentId = ++checkId;
  const available = await api.checkUsername(name);

  if (currentId !== checkId) return null;
  return available ? null : "用户名已存在";
}
```

异步校验要处理竞态和过期结果，避免旧请求覆盖新输入。还要避免每次敲字都请求服务端，可以结合防抖、失焦触发或提交前统一校验。

异步校验还要考虑“校验结果有效期”。用户名在当前输入值下可用，不代表用户改了一个字符后仍然可用。校验结果必须和当时的输入值绑定。

```ts
const validatedName = ref("");
const usernameError = ref("");

async function checkUsername(name: string) {
  validatedName.value = name;
  const available = await api.checkUsername(name);

  if (validatedName.value !== name) return;
  usernameError.value = available ? "" : "用户名已存在";
}
```

如果异步校验依赖服务端，提交时仍然要让服务端再做一次权威校验。前端校验用于体验，不应该成为安全边界。

## 提交流程

表单提交要收口到一个明确流程：校验、提交、加载、成功、失败、回滚或跳转。

```tsx
async function handleSubmit() {
  if (!isValid()) return;

  setSubmitting(true);
  try {
    await saveForm(data);
  } finally {
    setSubmitting(false);
  }
}
```

完整表单通常还要考虑：

```text
1. 提交中禁用重复点击
2. 失败后保留用户输入
3. 成功后清理或跳转
4. 部分字段错误回填
5. 网络失败时允许重试
```

提交流程越清晰，组件越不容易把业务状态和界面状态混在一起。

一个常见做法是把表单提交拆成“预校验、提交中、成功、失败、重试”几个状态，这样页面就能统一处理按钮禁用、loading、错误提示和成功跳转。状态越清晰，表单越不容易写成一堆嵌套 if。

如果表单依赖服务端返回错误，最好把服务端错误映射回具体字段，而不是只给一个顶部通用提示。字段级错误能让用户更快修正，也更符合表单的预期。

```ts
async function handleSubmit() {
  const result = validateClient(data);
  if (!result.valid) {
    setErrors(result.errors);
    return;
  }

  setSubmitting(true);
  try {
    await api.save(data);
    resetForm();
  } catch (error) {
    const normalized = normalizeFormError(error);
    setErrors(normalized.fieldErrors);
    setFormError(normalized.message);
  } finally {
    setSubmitting(false);
  }
}
```

表单提交过程中不要清空用户输入，除非成功提交且业务明确需要重置。失败后保留输入，可以让用户直接修正，而不是重新填写。

## 组合接口

好的表单组件通常要支持基础输入、错误状态、禁用、帮助文案和插槽扩展，而不是只暴露一个 `value`。

```tsx
type FieldProps = {
  label: string;
  error?: string;
  help?: string;
  required?: boolean;
  children: React.ReactNode;
};
```

表单组件不是单纯的输入框，而是一整套交互和反馈系统。设计时要同时考虑 `label`、`help`、`error`、`required`、`disabled`、`loading`、`prefix`、`suffix` 这些外围信息如何组合。

复杂表单还应和 [[4.1.5 受控模式|受控模式]] 配合，让外部能统一收集值、校验错误和提交状态。

表单组件还要处理动态字段、条件显示和局部联动。比如某个字段的可见性依赖另一个字段的值，或者多个字段需要共享一个异步校验结果，这些都说明表单已经不是单个输入控件，而是一套状态协调系统。

如果一个表单区域经常复用，最好把它抽成组合组件而不是复制页面代码。比如地址表单、联系人表单、支付方式表单，都很适合先做成可配置的局部模块。

一个常见结构是 `Form` 负责整体数据和提交，`Field` 负责标签、帮助、错误和布局，具体输入组件只负责值变化。

```tsx
<Form onSubmit={handleSubmit}>
  <Field label="邮箱" error={errors.email} required>
    <Input
      value={form.email}
      onChange={(email) => setForm({ ...form, email })}
      autoComplete="email"
    />
  </Field>
  <Button type="submit" loading={submitting}>保存</Button>
</Form>
```

这样拆分后，错误样式、必填标识、帮助文案和提交状态都有统一入口，页面只需要关心字段和业务流程。
