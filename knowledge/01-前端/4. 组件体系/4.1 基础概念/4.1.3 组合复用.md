## Props 组合

Props 适合传递数据和少量配置。基础组件通过 props 暴露可控变化点。

```tsx
type ButtonProps = {
  variant?: 'primary' | 'danger';
  disabled?: boolean;
  children: React.ReactNode;
};
```

Props 不适合无限膨胀。如果一个组件有几十个 props，通常说明它承担了太多场景，或者应该通过 slot/render props/组合子组件表达结构。

Props 组合的关键，是让变化保持在“参数层”而不是“实现层”。按钮的类型、尺寸、禁用态、加载态适合通过 props 控制；但如果开始用 props 控制复杂布局、内部多块内容和完全不同的交互流程，组件就会越来越像一个不易理解的开关机。

判断 props 是否还合适，可以看调用方是否仍能一眼看懂。一个组件如果需要同时传 10 个以上和行为相关的 props，通常说明它已经不是单一原子能力，而是该拆分或改用更高层的组合方式。

Props 组合适合“少量、稳定、可枚举”的变化点。比如按钮的尺寸、颜色语义、加载状态、禁用状态都是稳定变化；但弹窗底部按钮布局、表单项内部结构、表格单元格渲染，往往更适合 slot 或子组件组合。

```tsx
// Props 适合
<Button variant="danger" size="sm" loading>
  删除
</Button>

// Props 开始吃力
<Dialog
  footerAlign="between"
  footerLeftText="无法恢复"
  primaryDanger
  secondaryGhost
/>
```

当 props 开始描述结构时，就该考虑把结构交回调用方。

## Slot 组合

Slot 适合把 UI 片段交给调用方。它常用于布局、弹窗、表格、列表和卡片。

```vue
<BaseCard>
  <template #header>订单信息</template>
  <OrderSummary />
</BaseCard>
```

Props 传数据，Slot 传结构。这个边界很重要：如果调用方需要控制一块 UI 的内容和布局，slot 往往比 props 更合适。

Slot 的好处是保持组件主体稳定，同时把局部变化暴露给调用方。对于卡片、抽屉、弹窗、表单项包装器这类组件，标题区、内容区、底部按钮区经常适合 slot 化处理。这样基础组件不用认识业务语义，但调用方仍然能自由组织内容。

Slot 过多也会让组件难读，所以一般只把真正不同的“区域”做成 slot，而不是把每个小文本、每个 icon 都 slot 化。区域太碎，调用方就会被迫写很多模板，反而不如 props 直观。

Vue 中 slot 还可以传递作用域数据，让调用方在组件控制的数据上下文里自定义展示。例如表格组件常见的单元格渲染，就是组件负责数据遍历和状态，调用方负责局部 UI。

```vue
<DataTable :rows="orders">
  <template #cell-status="{ row }">
    <StatusTag :status="row.status" />
  </template>
</DataTable>
```

这种方式比给表格组件加 `statusColorMap`、`statusTextMap`、`statusIconMap` 更灵活，也更不容易把业务规则塞进基础组件。

## 子组件组合

复杂组件可以拆成一组协作子组件，例如 Tabs、Menu、Form、Table。

```tsx
<Tabs defaultValue="profile">
  <Tabs.List>
    <Tabs.Trigger value="profile">资料</Tabs.Trigger>
    <Tabs.Trigger value="security">安全</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Content value="profile">...</Tabs.Content>
  <Tabs.Content value="security">...</Tabs.Content>
</Tabs>
```

这种组合方式让结构更自然，也避免一个组件用大量 props 控制所有区域。

子组件组合最适合表达层级关系明确的 UI 结构，比如 Tabs、Menu、Tree、Form、Table。父组件负责状态和协调，子组件负责局部显示与交互，这样结构和行为的边界都比较清楚。

如果调用方必须同时控制“结构”和“状态”，子组件组合往往比单一组件的 props 列表更可维护。它也更接近 HTML 原生语义，学习成本通常更低。

子组件组合的关键是共享上下文。Tabs 的 Trigger 和 Content 需要知道当前激活项，FormItem 需要知道表单校验状态，MenuItem 需要知道选中路径。父组件可以通过 Context、provide/inject 或内部注册机制把这些状态传给子组件。

```tsx
<Form value={form} onChange={setForm}>
  <Form.Item name="email" label="邮箱">
    <Input />
  </Form.Item>
  <Form.Error name="email" />
</Form>
```

这种写法让调用方看到的结构接近业务布局，而内部状态同步由组件组完成。比一个巨大 `Form` 组件接收字段配置数组更适合复杂自定义页面。

## 逻辑复用

逻辑复用可以使用 hooks、composable、工具函数或状态模块。UI 复用和逻辑复用要区分。

```typescript
export function useDisclosure(initial = false) {
  const open = ref(initial);

  return {
    open,
    show: () => (open.value = true),
    hide: () => (open.value = false),
  };
}
```

如果复用的是状态和行为，用组合函数；如果复用的是视觉结构，用组件；如果复用的是纯计算，用普通函数。

逻辑复用要避免把 UI 和行为绑死。比如“打开/关闭”“复制”“防抖”“远程搜索”“权限判断”这类能力，本质上都更适合抽成 hook/composable；一旦做成组件，调用方只能通过渲染去间接控制，灵活度反而下降。

好的逻辑复用应该能单独测试。这样当多个组件共享一套行为时，问题定位会更快，也更容易在不改 UI 的情况下复用能力。

逻辑复用要避免把渲染细节带进去。比如 `useRemoteSearch` 可以暴露 keyword、results、loading、search 方法，但不应该决定用 Select、Table 还是 List 展示结果。

```ts
export function useRemoteSearch<T>(fetcher: (keyword: string) => Promise<T[]>) {
  const keyword = ref("");
  const results = ref<T[]>([]);
  const loading = ref(false);

  async function search() {
    loading.value = true;
    try {
      results.value = await fetcher(keyword.value);
    } finally {
      loading.value = false;
    }
  }

  return { keyword, results, loading, search };
}
```

这样同一套搜索逻辑可以被 Select、命令面板、列表筛选复用，UI 不需要跟逻辑绑定。

## 受控与非受控

组件复用常见边界是受控和非受控。受控组件状态由外部传入，非受控组件自己维护内部状态。

```tsx
<Input value={value} onChange={setValue} />
```

受控适合表单、复杂联动和外部状态管理；非受控适合简单内部交互。高级组件通常同时支持两种模式，但实现要小心状态同步。

受控和非受控并不是“二选一的宗教问题”。在组件设计里，更常见的是默认非受控、关键场景可受控，或者两者兼容。比如输入框既可以自己维护内部值，也可以暴露 `value` 和 `onChange` 让外层接管。

如果组件既支持受控又支持非受控，必须明确优先级：外部值优先还是内部状态优先、受控切换时如何同步、默认值何时生效、清空和重置如何处理。这些规则如果不清楚，组件很容易出现状态漂移。

兼容受控和非受控时，可以用“是否传入 value”判断控制权。传了 `value` 就由外部负责，没传就使用内部状态；`defaultValue` 只在初始化时生效，不应该在每次 props 变化时覆盖用户输入。

```tsx
function useControllableState<T>({
  value,
  defaultValue,
  onChange,
}: {
  value?: T;
  defaultValue: T;
  onChange?: (value: T) => void;
}) {
  const [innerValue, setInnerValue] = useState(defaultValue);
  const controlled = value !== undefined;
  const currentValue = controlled ? value : innerValue;

  function setValue(nextValue: T) {
    if (!controlled) setInnerValue(nextValue);
    onChange?.(nextValue);
  }

  return [currentValue, setValue] as const;
}
```

这个模式在 Input、Switch、Tabs、Dialog、Select 里都很常见。

## 组合优先

组合优先不代表永远不封装，而是先把稳定能力拆成小块，再组合成复杂组件。

| 需求 | 更适合 |
|---|---|
| 可替换 UI 片段 | Slot / children |
| 共享状态逻辑 | Hook / composable |
| 统一视觉规范 | 基础组件 |
| 强业务流程 | 业务组件 |

组合复用和 [[4.1.6 继承边界|继承边界]] 是相邻主题：组件体系里应尽量通过组合扩展能力，避免继承式层级越来越深。

组合优先不是鼓励无限拆碎，而是鼓励“把变化放到正确层级”。底层负责稳定能力，上层负责业务组合，中间层负责常见模式。这样既不会让基础组件长出业务逻辑，也不会让页面里堆满重复实现。

组合复用还有一个反向边界：不要为了复用把本来清楚的页面拆成难懂的抽象。如果两个页面只是刚好长得像，但业务规则不同，强行抽一个万能组件会让 props 和 slot 同时膨胀。

```text
值得复用：稳定结构 + 重复出现 + 变化点清楚
暂不复用：只出现两次 + 业务差异大 + 未来方向不确定
```

组件复用的目标不是减少文件数量，而是减少重复决策。能让调用方少想、少写、少踩坑的复用，才是有效复用。
