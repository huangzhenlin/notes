## 组件目标

可访问性不是附加项，而是组件设计的一部分。一个组件如果不能被键盘、屏幕阅读器或辅助技术正常使用，就算视觉上完成了，也还不算完整。

对组件体系来说，可访问性会影响 API 设计、状态设计和交互设计。比如弹窗必须管理焦点，输入组件必须能关联错误，图标按钮必须有可读名称。

可访问性在组件体系里不是“最后补 ARIA”，而是从命名、结构、交互到测试都要一起考虑。一个组件如果默认可以被键盘操作、可被读屏识别、可正确聚焦，后面业务接入时的风险会小很多。

很多可访问性问题不是高深问题，而是组件封装时把原生语义拿掉了。比如把按钮写成 div、把 label 和输入拆散、把错误提示放在看不见的地方，都会让辅助技术失去上下文。

组件体系里的可访问性应该默认内建，而不是靠业务页面逐个补救。基础组件一旦缺少键盘行为或语义属性，所有使用它的业务页面都会继承这个问题。反过来，基础组件默认做好，业务页面只需要补充具体文案和上下文。

```text
Button 默认可聚焦、可键盘触发
Dialog 默认管理焦点和 aria 属性
Input 默认关联 label、help、error
Tabs 默认声明 selected 状态和键盘切换
```

这也是为什么可访问性应该进入组件 API 设计，而不是最后检查视觉稿时才想起来。

## 原生优先

能用原生语义实现的就优先用原生语义。按钮就用 `button`，链接就用 `a`，输入就用 `input`。

```tsx
<button type="button">保存</button>
```

原生元素天然带有角色、状态、键盘交互和可访问名称。自己重做时，这些能力都要重新补齐。

```tsx
// 不推荐：需要自己补齐大量语义和键盘行为
<div onClick={onSave}>保存</div>
```

原生优先并不排斥自定义视觉。更好的方式是保留原生元素的语义和交互，再用样式增强外观；而不是先抹掉语义，再用大量 JS 和 ARIA 补回来。

ARIA 的原则是“能不用就不用，能用原生就用原生”。比如按钮不要用 `div role="button"` 代替，链接跳转不要用 `span` 加点击事件代替。自定义角色意味着你要自己补齐键盘、焦点、禁用、名称和状态。

```tsx
// 推荐
<button type="button" disabled={disabled}>提交</button>

// 只有在无法使用 button 时才考虑补 role 和键盘行为
<div role="button" tabIndex={0}>提交</div>
```

大多数基础组件都能在保留原生元素的前提下完成视觉定制。

## 键盘模型

组件必须支持键盘操作，包括 Tab、Enter、Space、方向键等常见行为。

```text
常见要求：
1. 可聚焦
2. 可操作
3. 可退出
```

菜单、弹窗、下拉、标签页、表格工具栏这些常见组件，都应该在没有鼠标时仍然可用。

| 组件 | 常见键盘行为 |
| --- | --- |
| Button | Enter / Space 激活 |
| Dialog | Esc 关闭，Tab 循环 |
| Tabs | 方向键切换 |
| Menu | 方向键移动，Enter 选择 |

键盘模型最好和浏览器及平台习惯保持一致，而不是自造一套新规则。用户已经习惯 Tab 负责焦点切换、Esc 负责关闭、方向键负责局部移动，组件如果反着来，会显著增加学习成本。

复杂组件还要区分“Tab 顺序”和“组件内部导航”。Tab 通常负责在页面可聚焦元素之间移动；方向键负责在 Tabs、Menu、RadioGroup 这类组件内部移动。不要让一个组件内部塞进过多 Tab 停靠点，否则键盘用户会很难快速穿过页面。

```text
Tabs：Tab 进入组件，方向键切换标签
Menu：Tab 进入菜单，方向键移动选项
Dialog：Tab 在弹窗内部循环
```

键盘模型越接近用户已有习惯，组件越容易被不同输入设备使用。

## 焦点管理

弹窗、菜单、下拉、抽屉等组件要处理焦点进入、焦点循环和焦点返回。

```tsx
dialogRef.current?.focus();
```

弹窗打开时把焦点移入，关闭后把焦点还给触发按钮，这是用户最容易感知的基础体验之一。

如果组件打开后焦点还停留在背景区域，键盘用户可能完全不知道弹窗已经出现。

焦点管理还要处理嵌套场景。比如弹窗里再打开下拉、抽屉里再开确认框、表格单元格里编辑输入，焦点顺序和返回路径都要尽量明确。焦点丢失往往意味着交互边界没设计好。

弹窗类组件通常要保存触发元素，打开后把焦点移到弹窗内部，关闭后再把焦点还回触发元素。这样用户不会在关闭弹窗后“掉”到页面顶部或不可见区域。

```tsx
const triggerRef = useRef<HTMLButtonElement | null>(null);

function closeDialog() {
  setOpen(false);
  triggerRef.current?.focus();
}
```

焦点陷阱也要有出口。`Esc`、关闭按钮、取消按钮都应该能让用户离开弹层，且关闭后焦点位置可预测。

## 状态描述

视觉状态需要有语义状态对应，例如 `aria-expanded`、`aria-selected`、`aria-invalid`。

```tsx
<button aria-expanded={open}>菜单</button>
```

如果界面上有加载中、错误、选中、展开、只读这些视觉状态，最好都能找到对应的语义表达。

```tsx
<input aria-invalid={hasError} aria-describedby="email-error" />
```

状态描述的价值，不只是给读屏器用，也能帮助前端自己统一状态模型。比如 `aria-expanded`、`aria-selected`、`aria-invalid` 这些属性，本质上是在告诉组件和调用方：这个状态是公开且应被理解的。

语义状态要和视觉状态同步。按钮看起来禁用时，底层也应该有 `disabled` 或 `aria-disabled`；输入框显示错误时，应该设置 `aria-invalid` 并关联错误说明；折叠面板展开时，触发按钮应该有 `aria-expanded`。

```tsx
<button aria-expanded={open} aria-controls="menu-panel">
  更多操作
</button>
<div id="menu-panel" hidden={!open}>
  ...
</div>
```

如果视觉和语义不一致，鼠标用户、键盘用户、读屏用户会得到不同体验，测试也更难稳定。

## 名称计算

图标按钮、无文字按钮和复合控件要有可读名称，不能只靠视觉图标表达。

```tsx
<button aria-label="关闭弹窗" />
```

没有可读名称的按钮，屏幕阅读器用户几乎无法知道它的作用。

如果组件有可见标题，优先用可见文本；如果没有可见文本，再补 `aria-label` 或 `aria-labelledby`。

名称计算要尽量避免只靠图标传达意思。像关闭、删除、展开、更多这类图标按钮，如果没有名称，既影响读屏，也会让自动化测试和埋点识别更困难。

可访问名称应该优先来自可见文本。只有图标按钮、纯视觉控件或文本被隐藏时，才使用 `aria-label`。如果页面上已经有标题或说明，可以用 `aria-labelledby` 或 `aria-describedby` 建立关系。

```tsx
<h2 id="delete-title">删除项目</h2>
<p id="delete-desc">删除后不可恢复。</p>
<Dialog aria-labelledby="delete-title" aria-describedby="delete-desc" />
```

名称和描述分开很重要：名称回答“这是什么”，描述回答“它有什么补充信息”。

## Props 设计

可访问性最好从 Props 层就被设计进去，而不是最后补 ARIA。

```tsx
type DialogProps = {
  title: string;
  onClose: () => void;
  "aria-label"?: string;
};
```

例如提供 `aria-label`、`aria-describedby`、`id`、`htmlFor` 这类入口，会比事后硬塞更自然。

组件封装时要避免吞掉调用方传入的 `aria-*` 和 `data-*`，否则业务场景很难补充必要语义。

对于基础组件，最好默认支持把无障碍属性透传到底层原生元素。这样业务层可以在需要时补充 `aria-label`、`aria-describedby`、`role`、`aria-controls` 等属性，而不必改组件实现。

Props 设计还要避免用视觉文案替代语义名称。比如 IconButton 可以要求必须传入 `aria-label` 或 `label`，这样调用方不会忘记给无文字按钮命名。

```tsx
type IconButtonProps = {
  icon: React.ReactNode;
  "aria-label": string;
} & React.ButtonHTMLAttributes<HTMLButtonElement>;
```

对于 Dialog、Drawer、Popover 这类组件，标题、描述、关闭按钮名称都应该有明确入口。否则组件越复用，可访问性缺口越会被放大。

## 测试检查

组件开发后，要做键盘测试、焦点测试和辅助技术检查。如果一个组件离开鼠标就不好用，通常说明设计还不完整。

可访问性测试可以很朴素：

1. Tab 一遍。
2. 回车和空格操作一遍。
3. 打开关闭弹窗看焦点是否返回。
4. 错误提示是否能被读到。

很多问题其实不用复杂工具就能提前发现。可访问性和 [[1.1.7 无障碍|无障碍]] 是同一条知识线，只是在组件体系里要落到每个 API 和交互细节上。

如果团队资源允许，最好把键盘测试和读屏检查纳入高频组件的回归流程。对按钮、表单、弹窗、菜单、标签页这些基础交互组件来说，这类检查的收益非常高。

自动化测试可以覆盖一部分可访问性问题，例如使用 Testing Library 按角色查询元素、用 `userEvent.keyboard` 测试键盘路径、用 axe 检查明显违规。但自动化不能替代人工键盘检查。

```tsx
expect(screen.getByRole("button", { name: "关闭弹窗" })).toBeInTheDocument();

await user.keyboard("{Escape}");
expect(onClose).toHaveBeenCalled();
```

组件库里越基础、复用越频繁的组件，越值得把可访问性行为写进测试。因为一个底层组件修好，整个业务都会受益。
