## 继承问题

继承的问题在于强耦合。子组件依赖父组件内部实现，父组件修改会影响所有子组件。

| 问题 | 表现 |
|---|---|
| 层级过深 | 找行为要一路向上 |
| 覆盖复杂 | 子类不断重写父类 |
| 隐式依赖 | 父类内部状态影响子类 |
| 复用困难 | 只能沿继承链扩展 |

组件库里如果大量依赖继承，后续需求变化会越来越难处理。

UI 组件里的继承尤其容易制造隐式行为。子组件看起来只是改了一点样式，但实际可能继承了父组件的状态、生命周期、副作用和默认交互。等需求变化时，维护者需要同时理解父类、子类和覆盖关系，成本会快速上升。

继承最大的问题不是语法本身，而是它把“复用”和“分类”绑在一起。很多 UI 需求只是想复用一段结构或逻辑，并不存在稳定的 is-a 关系，用继承表达就会显得过重。

前端组件面对的是高频变化的交互和视觉，而继承更适合稳定层级。设计规范一变，子类可能都要改；父类生命周期一变，所有子类都会受影响。这种影响链在 UI 里往往比普通业务模型更难控制。

```text
继承链变化：父类改一个默认行为，所有子类一起变化
组合式变化：替换一个局部能力，只影响使用该组合的地方
```

所以组件体系通常默认组合，只有在模型抽象非常稳定时才考虑继承。

## 组合替代

组合更适合 UI。把基础能力拆成 props、slot、children、hook/composable，再组合成新组件。

```tsx
<Card>
  <Card.Header>订单</Card.Header>
  <Card.Body>
    <OrderSummary />
  </Card.Body>
</Card>
```

这种方式让结构由调用方决定，基础组件只负责提供稳定能力。

组合替代继承的核心，是把变化点显式暴露出来。调用方可以选择传入 children、slot、render 函数或组合子组件，而不是通过覆盖父类方法去改变内部行为。变化越显式，组件就越容易读懂和测试。

组合也更适合多维变化。一个按钮可能同时变化尺寸、颜色、图标、权限、加载状态和埋点，如果用继承，很容易产生 `DangerIconLoadingButton` 这类爆炸式层级；如果用组合，可以把这些能力分别组合起来。

```tsx
<Button variant="danger" loading={submitting} icon={<TrashIcon />}>
  删除
</Button>
```

这里视觉、加载和图标都是可组合能力，不需要分别创建多个继承子类。变化维度越多，组合的优势越明显。

## Props 扩展

简单变化可以通过 props 表达。

```tsx
<Button variant="danger" size="small">
  删除
</Button>
```

Props 适合有限、明确、稳定的变化。如果 props 越加越多，说明组件可能需要拆分或改用组合。

Props 扩展应该描述组件允许的变化，而不是暴露所有内部实现。比如 `variant`、`size`、`disabled` 是稳定语义；`innerWrapperClassName`、`labelContainerStyle` 这类属性如果大量出现，可能说明组件边界不够好，调用方正在穿透内部结构。

如果一个 props 只有某一个页面使用，而且改变了组件主要行为，就要考虑它是否应该放在业务组件里，而不是污染基础组件。

Props 扩展也有边界。如果新增 prop 只是为了绕过组件内部限制，比如 `ignoreDisabledStyle`、`forceCloseWhenLoading`，说明组件模型可能没设计好。与其继续加开关，不如重新审视状态枚举或组合结构。

```tsx
type ButtonState = "idle" | "loading" | "disabled";
```

把互斥状态收敛成一个模型，比不断加布尔开关更接近组件设计。

## Slot 扩展

Slot 或 children 适合扩展结构。

```vue
<BaseModal>
  <template #title>确认删除</template>
  <p>删除后不可恢复</p>
</BaseModal>
```

当变化点是“一块 UI”，slot 比继承和配置对象更自然。

Slot 的优势是能扩展结构，但仍保留父组件的外壳和协调能力。比如 Modal 可以固定遮罩、层级、焦点管理和关闭行为，同时允许标题、主体、底部按钮由调用方决定。这样既保留一致性，也避免继承带来的强耦合。

```vue
<BaseModal>
  <template #header>
    <h2>邀请成员</h2>
  </template>
  <InviteMemberForm />
  <template #footer>
    <Button>发送邀请</Button>
  </template>
</BaseModal>
```

Slot 扩展适合“外壳稳定、内部变化”的组件。父组件仍然负责弹层、焦点、关闭和布局，业务层只决定内容。

## Hook 扩展

逻辑复用可以用 hook/composable，而不是继承基类。

```typescript
function useSelection<T>() {
  const selected = ref<T[]>([]);

  return {
    selected,
    toggle(item: T) {},
  };
}
```

这让逻辑可以被多个组件组合使用，而不强制它们共享同一父类。

Hook/composable 适合承载可复用行为，比如选择、展开、分页、复制、拖拽、远程搜索和弹窗开关。它们不关心最终 UI 怎么渲染，因此可以被不同组件复用，也可以单独测试。

如果逻辑里依赖 DOM、网络请求和全局状态，仍然要保持边界清晰。可复用逻辑应该暴露稳定输入输出，而不是让组件调用方知道内部所有细节。

Hook/composable 也比继承更容易组合多个能力。一个表格可以同时组合分页、选择、排序和远程加载，而不需要继承 `SelectableSortablePaginatedRemoteTable` 这种层级。

```ts
const selection = useSelection<Row>();
const pagination = usePagination();
const sorting = useSorting();
```

这些能力可以单独测试、单独替换，也不会强迫所有表格共享同一父类。

## 允许继承

继承并非绝对不能用。稳定的非 UI 模型、错误类型、抽象协议、测试基类有时适合继承。

| 可以考虑 | 不建议 |
|---|---|
| Error 子类 | UI 组件层级继承 |
| 抽象服务类 | 业务组件继承业务组件 |
| 测试夹具基类 | 为了复用样式继承 |

UI 组件优先组合，底层模型按实际需要判断。

继承适合稳定抽象，而不是频繁变化的 UI。比如自定义错误类型继承 `Error`，或者测试夹具共享初始化逻辑，通常比 UI 组件继承更合理。原因是这些模型的层级关系更稳定，变化点也更少。

如果确实使用继承，要控制层级深度，并避免子类依赖父类的隐式状态。继承链越深，越难判断一个行为到底来自哪里。

允许继承的场景通常有两个特征：抽象稳定，变化方向单一。比如错误类型继承 `Error` 是为了统一异常语义；抽象服务类定义协议是为了约束实现；测试基类复用初始化是为了降低重复 setup。这些场景的层级关系比 UI 组件稳定得多。

```ts
class HttpError extends Error {
  constructor(
    message: string,
    public status: number,
  ) {
    super(message);
  }
}
```

这类继承和 UI 组件继承不是一回事，不应该因为“继承有问题”就一概否定。

## 设计判断

判断是否应该继承，可以问：

| 问题 | 如果答案是是 |
|---|---|
| 是否只是复用一块 UI | 用组合 |
| 是否只是复用逻辑 | 用 hook/composable |
| 是否需要替换局部结构 | 用 slot/children |
| 是否存在稳定 is-a 关系 | 可以考虑继承 |

继承边界和 [[4.1.3 组合复用|组合复用]] 是同一个设计原则：优先让能力可组合，而不是把变化绑进层级。

实际设计时可以先默认不继承，只有当概念上存在稳定的 is-a 关系，并且组合会显著增加复杂度时，再考虑继承。这个默认选择能让组件体系更扁平，也更适合前端界面快速变化的特点。

在组件评审里，可以把问题换成更具体的判断：这是要复用视觉结构、复用交互逻辑、复用数据模型，还是表达真实的类型层级？前三种通常优先组合，只有最后一种才可能适合继承。

```text
复用视觉结构：children / slot
复用交互逻辑：hook / composable
复用状态模型：store / context
表达稳定类型：继承或接口
```

这样判断能避免把“我想少写点代码”误判成“这里需要继承”。
