## 状态归属

受控模式的核心是状态由外部持有，组件只负责展示和通知变化。

```tsx
type ToggleProps = {
  checked: boolean;
  onCheckedChange: (checked: boolean) => void;
};
```

受控模式的本质，是让“当前值”只有一个权威来源。这样外部可以统一做校验、联动、持久化和提交。

```tsx
function Page() {
  const [checked, setChecked] = useState(false);

  return <Toggle checked={checked} onCheckedChange={setChecked} />;
}
```

受控模式最适合外部需要知道每一次变化的组件，例如输入框、开关、标签页、弹窗、下拉选择、日期范围、分页器。外部持有状态后，可以统一做 URL 同步、表单校验、跨组件联动和持久化。

```tsx
<Tabs value={activeTab} onValueChange={setActiveTab} />
<Dialog open={open} onOpenChange={setOpen} />
```

组件内部仍然可以维护一些临时状态，比如 hover、动画阶段、测量结果，但业务值本身应该来自外部。

## 成对接口

受控组件通常成对提供 `value/onChange` 或 `checked/onCheckedChange`。

```tsx
type InputProps = {
  value: string;
  onChange: (value: string) => void;
};
```

成对接口能让“谁控制状态”一眼看明白。这类接口最适合输入、勾选、下拉、滑块和复合表单控件。

组件库里常见的命名约定：

| 值类型 | 常见接口 |
| --- | --- |
| 文本 | `value / onChange` |
| 开关 | `checked / onCheckedChange` |
| 展开 | `open / onOpenChange` |
| 选中项 | `selectedKey / onSelectionChange` |

成对接口的命名要保持体系一致。React 生态常见 `value/onChange`，Radix 风格常见 `open/onOpenChange`，选择类组件可能用 `selectedKey/onSelectionChange`。无论选哪一种，组件库内部都应该统一。

事件参数最好直接给“下一个值”，而不是原始 DOM 事件。这样调用方不用知道底层是 input、button 还是自定义结构。

```tsx
type SwitchProps = {
  checked: boolean;
  onCheckedChange: (checked: boolean) => void;
};
```

如果调用方确实需要原始事件，可以额外提供，但不要让业务代码依赖底层 DOM 结构。

## 非受控模式

非受控模式把状态放在组件内部，外部只在需要时读取。

```tsx
type InputProps = {
  defaultValue?: string;
};
```

非受控更适合简单场景、文件输入、第三方库集成和快速原型。

```tsx
function FilePicker() {
  const inputRef = useRef<HTMLInputElement | null>(null);

  function submit() {
    const file = inputRef.current?.files?.[0];
  }

  return <input ref={inputRef} type="file" />;
}
```

非受控的优点是低成本，缺点是外部很难实时知道组件内部发生了什么。需要即时联动的业务，通常还是受控更清楚。

非受控特别适合文件输入，因为浏览器出于安全限制不允许脚本随意设置文件值。它也适合一次性读取的简单表单，或者第三方富文本编辑器这类内部状态很重的控件。

```tsx
function SimpleForm() {
  const formRef = useRef<HTMLFormElement | null>(null);

  function submit() {
    const data = new FormData(formRef.current!);
    console.log(data.get("email"));
  }

  return (
    <form ref={formRef}>
      <input name="email" defaultValue="" />
      <button type="button" onClick={submit}>读取</button>
    </form>
  );
}
```

非受控不是低级写法，只是它把读取时机推迟到了需要的时候。只要业务不需要实时联动，它可以很简洁。

## 默认值

受控和非受控都可能有默认值，但默认值的归属不同。

```tsx
<input defaultValue="Ada" />
<input value={value} onChange={...} />
```

如果既想默认又想受控，要明确初始状态来源，不然很容易出现切换警告或状态失真。

默认值只应该影响初始化，不应该在组件运行过程中反复覆盖内部状态。

很多 bug 来自把 `defaultValue` 当成“每次 props 改变都同步”。实际上 `defaultValue` 只代表初始值；如果需要外部持续控制，就应该使用 `value`。

```tsx
// 初始值，后续内部维护
<Input defaultValue="Ada" />

// 外部持续控制
<Input value={name} onChange={setName} />
```

如果业务需要“外部点击重置”，不要试图反复改 `defaultValue`，而应该暴露明确的 `reset` 行为，或通过改变 key 重新创建组件。

## 混合风险

不要在同一个组件里同时让外部控制又让内部偷偷改状态。

```text
风险：
1. 外部 value 和内部 state 冲突
2. 初始化与受控切换混乱
3. 调试时不知道谁是事实来源
```

如果一个组件既能受控又能非受控，接口一定要非常明确地说明优先级和切换条件，否则调用方很容易踩坑。

最安全的规则是：组件首次渲染时如果传入 `value`，就按受控处理；没有传入 `value`，就按非受控处理。运行过程中不要在两种模式之间切换。

```tsx
const isControlled = value !== undefined;
const [innerValue, setInnerValue] = useState(defaultValue);
const mergedValue = isControlled ? value : innerValue;
```

如果确实允许切换，也要明确同步策略，并准备好测试。多数情况下，禁止受控与非受控切换反而更可靠。

## 表单联动

复杂表单联动、校验和条件渲染通常更适合受控模式，因为外部能完整掌握状态变化。

```tsx
<TextField value={name} onChange={setName} />
```

在表单系统里，受控模式更像“可预测的输入管道”，方便做联动、校验和提交前收口。

```tsx
const canSubmit = name.length > 0 && email.includes("@");
```

受控模式也适合字段联动。比如选择国家后更新省份列表，选择配送方式后计算运费，勾选发票后显示发票抬头。外部持有完整表单值，联动规则就能集中表达。

```tsx
const provinceOptions = getProvinceOptions(country);

<Select value={country} onChange={setCountry} />
<Select value={province} options={provinceOptions} onChange={setProvince} />
```

如果每个输入组件都把值藏在内部，联动就只能通过 ref 或额外事件绕出来，复杂度会更高。

## 组件封装

封装输入类组件时，要先决定它是“完全受控”，还是“默认可受控”。不要把两种模式写成难以预测的混合体。

```tsx
type ControllableInputProps = {
  value?: string;
  defaultValue?: string;
  onChange?: (value: string) => void;
};
```

如果需要同时支持默认值、受控值和回填值，最好在文档和类型上把三者关系写清楚，避免初始化后切换引发警告。

受控模式的关键不是多写几个 props，而是让状态来源和更新路径始终可追踪。

封装时可以抽一个 `useControllableState`，让受控和非受控逻辑集中在一个地方。这样 Input、Tabs、Dialog、Switch 都能复用同一套边界判断。

```tsx
function useControllableState<T>({
  value,
  defaultValue,
  onChange,
}: {
  value?: T;
  defaultValue: T;
  onChange?: (value: T) => void;
}) {
  const [innerValue, setInnerValue] = useState(defaultValue);
  const controlled = value !== undefined;
  const current = controlled ? value : innerValue;

  function setCurrent(next: T) {
    if (!controlled) setInnerValue(next);
    onChange?.(next);
  }

  return [current, setCurrent] as const;
}
```

这个抽象的价值不是省代码，而是让所有支持双模式的组件遵守同一套规则。
