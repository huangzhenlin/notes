## 输入契约

Props 是组件的输入契约。它决定组件接受什么数据、触发什么行为、允许哪些扩展方式。

```tsx
type ButtonProps = {
  label: string;
  onClick?: () => void;
};
```

Props 越明确，组件越容易理解。不要让调用方猜测某个 prop 是必须的、可选的，还是只在某些模式下有效。

输入契约一旦发布，就会被业务代码依赖。组件内部可以重构，但 Props 的语义最好稳定。尤其是基础组件，Props 改动会扩散到大量页面，所以设计时要先想清楚哪些变化是长期稳定的，哪些只是当前页面的临时需求。

如果某个 prop 只服务一个页面，而且语义明显属于业务，就不应该轻易放进基础组件。更好的做法是放到业务组件里，或者通过组合方式让页面自行处理。

设计 Props 时要把“组件稳定能力”和“业务临时需求”分开。比如 `Button` 支持 `variant` 是稳定能力，支持 `isOrderExpired` 就是业务泄漏。基础组件一旦吸收业务 prop，后续会不断被不同页面追加特殊规则。

```tsx
// 不推荐：基础按钮认识订单业务
<Button isOrderExpired={order.expired}>续费</Button>

// 推荐：业务层决定按钮状态
<Button disabled={order.expired}>续费</Button>
```

Props 是公开 API，越底层的组件越要保守。业务组件可以更贴近具体场景，基础组件则应该保持语义通用。

## 数据属性

数据属性描述组件内容，例如文本、图标、图片、尺寸、状态和标题。

```tsx
type AvatarProps = {
  name: string;
  src?: string;
  size?: "sm" | "md" | "lg";
};
```

数据属性应该尽量直接表达业务语义，而不是暴露实现细节。

数据属性要尽量避免把展示实现绑死。比如头像组件用 `size` 比用 `width`、`height` 更接近设计系统；状态标签用 `tone` 或 `status` 比直接传 `color` 更能保持视觉一致。底层可以由组件把语义映射成具体样式。

```tsx
type StatusTagProps = {
  status: "draft" | "running" | "failed" | "finished";
};
```

这种写法让调用方传业务状态，组件内部决定颜色、文案和图标，避免每个页面重复维护一套映射。

数据属性还要避免“半语义、半样式”。比如 `color="red"` 看似灵活，但会让每个页面都重新选择色彩；`tone="danger"` 表达的是语义，组件可以映射到当前主题下的危险色。

```tsx
type TagProps = {
  tone?: "neutral" | "success" | "warning" | "danger";
  children: React.ReactNode;
};
```

当设计系统需要换主题时，语义属性能保持业务代码稳定；直接色值则会把视觉决策扩散到所有调用方。

## 行为属性

行为属性通常是回调，例如点击、提交、关闭、选择、清除。

```tsx
type ModalProps = {
  onClose: () => void;
  onConfirm: () => void;
};
```

好的行为属性命名应接近业务动作，而不是 DOM 事件名的简单复制。

行为属性要说明“何时触发”和“传什么参数”。比如 `onChange` 是输入过程中触发，还是确认选择后触发；`onClose` 是点关闭按钮触发，还是遮罩、Esc、提交成功都会触发。事件时机不清楚，会直接影响状态同步。

对于复杂组件，可以把事件拆得更明确。例如弹窗可以有 `onOpenChange`、`onConfirm`、`onCancel`，表格可以有 `onSortChange`、`onPageChange`、`onSelectionChange`。事件越贴近业务动作，调用方越不容易误用。

行为属性还要保持单向数据流。组件触发事件，调用方决定是否更新外部状态；组件不应该在内部猜测外部状态一定会变化。尤其是受控组件，`onChange` 只是请求变更，不是状态已经变更的证明。

```tsx
<Switch
  checked={enabled}
  onCheckedChange={(nextChecked) => {
    if (canEdit) setEnabled(nextChecked);
  }}
/>
```

这里 Switch 只表达用户意图，真正是否更新由外部决定。这个模式能让权限、校验、异步确认都更容易接入。

## 布尔属性

布尔属性适合表达简单开关，但不要滥用。大量布尔值组合起来，往往会制造非法状态。

```tsx
type AlertProps = {
  loading?: boolean;
  disabled?: boolean;
  closable?: boolean;
};
```

如果多个布尔值彼此关联，改成状态枚举通常更清楚。

布尔属性最容易制造不可理解的组合。例如 `primary`、`danger`、`ghost` 同时出现时，到底谁优先并不直观。互斥状态应该用枚举，独立开关才适合布尔值。

```tsx
type ButtonProps = {
  variant?: "primary" | "secondary" | "danger" | "ghost";
  loading?: boolean;
  disabled?: boolean;
};
```

这里 `variant` 是互斥视觉风格，`loading` 和 `disabled` 是可叠加状态，边界就更清楚。

布尔属性适合表达独立、简单、可叠加的状态，例如 `disabled`、`loading`、`required`、`readOnly`。一旦几个布尔值之间有优先级或互斥关系，就应该改成枚举或联合类型。

```tsx
type UploadProps =
  | { mode: "single"; maxCount?: 1 }
  | { mode: "multiple"; maxCount?: number };
```

类型能把非法组合挡在编译期，比在运行时写一堆 `if` 再报警告更可靠。

## 默认值

默认值应当是业务上合理的初始状态，而不是“随便填一个方便写代码的值”。

```tsx
function Button({ variant = "primary" }: { variant?: "primary" | "secondary" }) {
  return <button className={`btn-${variant}`}>按钮</button>;
}
```

默认值能减少调用方负担，但也要避免把关键业务字段默认掉。

默认值应该服务常见场景，而不是掩盖必填信息。像按钮尺寸、弹窗宽度、分页页码可以有默认值；但用户 ID、订单状态、权限范围这类业务关键字段，不应该用默认值让错误静默发生。

默认值还要稳定。基础组件默认值一旦变化，可能导致全站视觉和交互发生连锁变化，所以默认值调整也应该被当成组件 API 变化对待。

默认值不要制造隐藏行为。比如弹窗默认点击遮罩关闭是否合理，要看业务风险；删除确认、支付确认这类高风险场景，默认可关闭可能会导致误操作或状态丢失。基础组件可以给出保守默认值，业务组件再明确覆盖。

```tsx
<ConfirmDialog closeOnOverlayClick={false} />
```

越是可能影响数据安全或用户确认的默认值，越不应该只为了“交互方便”而放松。

## children

`children` 让组件有内容插槽，是组合能力的重要入口。

```tsx
function Card({ title, children }: { title: string; children: React.ReactNode }) {
  return (
    <section>
      <h3>{title}</h3>
      {children}
    </section>
  );
}
```

`children` 适合布局组件、容器组件、弹窗和卡片。

`children` 的价值是表达结构，而不是传递配置。如果一个组件需要接收一整块可变 UI，`children` 往往比很多字符串和开关 prop 更自然。比如 Card、Layout、Modal、Popover 都适合让调用方决定主体内容。

但 `children` 也不是万能入口。组件如果需要控制子元素数量、顺序和状态关系，就要考虑子组件组合或 slot 命名，否则调用方很容易传入不符合预期的结构。

当内容区域很多时，可以用具名子组件或具名 slot 替代单个 `children`。这样调用方仍然能组合结构，组件也能识别区域语义。

```tsx
<Card>
  <Card.Header>订单信息</Card.Header>
  <Card.Body>
    <OrderSummary />
  </Card.Body>
  <Card.Footer>
    <Button>确认</Button>
  </Card.Footer>
</Card>
```

这种写法比 `headerText`、`footerButtonText`、`showDivider` 等多个 props 更能表达复杂结构。

## 属性透传

属性透传适合把原生属性往底层节点传递，例如 `className`、`style`、`aria-*`、`data-*`。

```tsx
type InputProps = React.InputHTMLAttributes<HTMLInputElement> & {
  label: string;
};
```

透传能增加灵活性，但要避免把底层实现完全暴露给调用方。

透传属性要优先保留 `aria-*`、`data-*`、`id`、`className` 这类常见扩展能力。它们对测试、可访问性、埋点和样式定位很重要。组件如果吞掉这些属性，业务层会很难补充外围能力。

同时也要控制透传边界。基础组件可以透传原生属性，业务组件则不一定应该把所有底层属性暴露出去。暴露得越多，未来替换底层实现时越难保持兼容。

属性透传要注意冲突优先级。比如组件内部需要控制 `disabled`，调用方也传了 `disabled`，最终以谁为准必须明确。一般来说，业务限制应该优先于调用方样式自由；可访问性属性则尽量不要被覆盖掉。

```tsx
function Button({ disabled, loading, ...rest }: ButtonProps) {
  return <button disabled={disabled || loading} {...rest} />;
}
```

如果透传顺序写反，调用方可能绕过组件内部约束。底层组件尤其要小心这类细节。

## 类型约束

Props 最好能被类型系统约束。这样参数缺失、非法值和错误组合都能在编译期暴露。

```tsx
type BadgeProps = {
  tone: "success" | "warning" | "danger";
  text: string;
};
```

组件设计时，Props 就是最重要的公共 API。API 越稳定，组件越耐用。 

类型约束不只是为了避免拼写错误，也能表达组件状态模型。比如某些 props 只能在特定模式下出现，可以用联合类型约束，而不是依赖运行时判断。

```tsx
type DialogProps =
  | { mode: "confirm"; onConfirm: () => void; onClose: () => void }
  | { mode: "notice"; onClose: () => void };
```

这种写法能让非法组合在编码阶段暴露出来，减少运行时分支和文档解释成本。

类型约束还可以表达“某个 prop 出现时，另一个 prop 必须出现”。比如异步按钮进入 loading 时可能需要 `loadingText`，链接按钮需要 `href`，普通按钮需要 `onClick`。

```tsx
type ButtonProps =
  | { as: "button"; onClick: () => void; href?: never }
  | { as: "a"; href: string; onClick?: never };
```

Props 类型越能表达真实约束，组件运行时需要兜底的分支就越少，调用方也越容易在编辑器里获得正确提示。
