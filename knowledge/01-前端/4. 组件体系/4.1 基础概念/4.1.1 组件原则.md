## 职责边界

一个好组件通常只负责一件事：展示、交互、容器、输入、状态管理或局部布局，而不是全部混在一起。

```tsx
function Card({ title, children }: { title: string; children: React.ReactNode }) {
  return (
    <section className="card">
      <h3>{title}</h3>
      {children}
    </section>
  );
}
```

职责越清楚，组件越容易复用、测试和替换。命名也会更稳定：`UserCard`、`SearchInput`、`ConfirmDialog` 都比 `UserPanelWithFormAndList` 更容易维护。

```text
一个组件先回答一个问题：
它负责展示什么，还是处理什么交互？
```

如果一个组件同时处理请求、列表、表单、弹窗、权限和布局，通常已经是页面模块，而不是基础组件。

组件原则的核心不是“组件越小越好”，而是“边界要清楚”。有些组件天然会比按钮大，比如日期选择器、筛选器、弹窗表单，但它们仍然应该围绕一个明确职责展开，而不是把多个不相关能力揉在一起。

判断组件是否合理，可以看它能不能在不看实现的情况下被理解。名字、Props、槽位和默认行为如果都能清楚表达意图，这个组件通常就已经走在正确方向上了。

职责边界也决定组件放在哪一层。基础组件不应该知道业务接口，业务组件不应该复刻底层按钮样式，页面组件才适合串联请求、状态和路由。

```text
Button：表达按钮语义和视觉状态
UserCard：展示用户摘要信息
UserPage：请求用户数据并组织页面结构
```

如果 `Button` 里出现用户权限判断，或者 `UserCard` 里直接发请求，说明组件层级已经混了。层级混乱短期能省一次传参，长期会让组件难以复用，也会让测试不得不准备很多无关上下文。

## 组合能力

组件优先通过组合扩展，而不是通过继承扩展。组合意味着把外壳、内容、行为和状态拆开，按需拼装。

```tsx
<Card title="用户">
  <UserInfo />
</Card>
```

常见组合方式包括：

| 组合方式 | 例子 | 适合场景 |
| --- | --- | --- |
| `children` | 卡片包内容 | 容器、布局 |
| Slot | 弹窗头部、尾部 | 多区域布局 |
| 回调 props | 列表项点击 | 交互回传 |
| 组合函数 | 表单逻辑、请求逻辑 | 状态和副作用 |

组合点是显式的。你能看见谁包裹了谁、谁把什么内容传进来，这比继承层级更容易调试。

组合能力还意味着“替换局部而不推翻整体”。比如卡片里替换底部操作区、表单里替换错误提示、弹窗里替换 footer，通常都比重新造一个新组件更稳。组合越自然，后续扩展和回收就越轻。

组合的另一层价值是保留调用方的表达能力。比如弹窗组件如果只提供 `confirmText`、`cancelText`、`showFooter`，一旦业务需要“左侧提示 + 右侧两个按钮 + 异步提交状态”，props 会很快膨胀。改成 footer slot 或 children 后，基础弹窗只负责结构和无障碍，业务按钮由调用方组合。

```tsx
<Dialog title="删除项目">
  <p>删除后不可恢复。</p>
  <Dialog.Footer>
    <Button variant="secondary">取消</Button>
    <Button variant="danger">确认删除</Button>
  </Dialog.Footer>
</Dialog>
```

组件组合不是为了炫技，而是为了把变化留给最懂场景的位置。

## 默认行为

好的组件会尽量保留原生行为，并在此基础上增强体验，而不是重写一套全新的交互逻辑。

```tsx
<button type="button">保存</button>
```

按钮、输入框、链接、表单这些基础元素都有默认语义、键盘行为和浏览器能力。如果为了统一视觉完全重做，后续无障碍、移动端输入法、自动填充和测试都会更难。

例如下拉框、日期选择器、文件上传这类组件，视觉可以重做，但语义、键盘和屏幕阅读器支持不能缺。

对表单类组件来说，原生能力还包括浏览器自动保存、自动填充、回车提交和输入法适配。很多看起来“只是个样式问题”的组件，其实一旦抹掉原生行为，业务层就会开始补各种兼容逻辑。

如果组件设计里必须改造原生行为，最好明确指出你牺牲了什么、补回了什么。这样后续做可访问性、移动端适配和测试时才不会踩空。

原生行为尤其体现在表单组件上。一个自定义按钮如果没有 `type="button"`，放进表单里可能会意外提交；一个自定义输入框如果不转发 `name`、`disabled`、`required`，表单序列化和校验都会受影响。

```tsx
function IconButton(props: React.ButtonHTMLAttributes<HTMLButtonElement>) {
  return <button type="button" {...props} />;
}
```

组件体系越靠底层，越应该尊重浏览器原生语义。视觉统一可以覆盖样式，但不应该抹掉键盘、焦点、表单和可访问性能力。

## 状态归属

组件内部状态适合短生命周期、局部交互和展示细节；需要跨组件共享的状态，应该提升到父组件、上下文或 Store。

```text
组件内部状态：hover、展开、临时输入
共享状态：选中项、表单提交态、全局偏好
```

判断状态归属时，可以先问：

1. 这个状态是否只影响当前组件。
2. 组件卸载后状态是否应该消失。
3. 是否有多个组件需要同时读取或修改。
4. 是否需要持久化或参与提交。

这和 [[3.1.3 归属|状态归属]] 是同一条原则：先局部，后提升。

状态归属还应该看变化频率。频繁变化但只影响局部展示的状态，留在组件内部更合适；变化频率低但需要跨页面一致的状态，才适合提升。这个判断能减少不必要的全局状态，也能避免局部交互被做得过重。

组件内部状态还要区分“可丢弃”和“应提交”。比如输入中内容、展开面板、hover 是可丢弃状态；表单提交后的实体、用户选择的筛选条件可能具有业务意义。可丢弃状态不应该污染外层 Store，应提交状态则要有明确写回入口。

```tsx
function SearchBox({ onSearch }: { onSearch: (keyword: string) => void }) {
  const [draft, setDraft] = useState("");

  return (
    <form onSubmit={(event) => {
      event.preventDefault();
      onSearch(draft.trim());
    }}>
      <input value={draft} onChange={(event) => setDraft(event.target.value)} />
    </form>
  );
}
```

这里 `draft` 是组件内部草稿，`onSearch` 才是向外提交的业务事件。这个边界清楚，调用方就不会被每次输入变化打扰。

## 可扩展边界

组件扩展时要控制 API 的增长。能通过 `children`、插槽、render props、组合函数扩展的，就不要一口气暴露大量布尔开关。

```text
优先顺序：
1. 组合
2. 插槽 / children
3. 少量 props
4. 最后才是复杂模式切换
```

一个稳妥的经验是：先提供少量清晰配置，再观察真实使用场景。等扩展点真的被重复使用后，再把它正式提升为 API。

大量布尔值很容易产生非法组合：

```tsx
<Dialog primary danger ghost simple />
```

这类写法会让调用方猜不出最终状态。更好的方向是用明确的模式、变体或组合结构。

如果组件的状态本质上是互斥的，优先用枚举而不是多个布尔值。例如 `variant="primary | danger | ghost"` 往往比 `primary danger ghost` 更好理解，也更容易做类型约束和设计对齐。

扩展边界还要考虑“默认可组合，特殊可覆盖”。比如基础组件可以提供 `variant`、`size`、`disabled` 这些稳定 API，同时保留 `className`、`style`、`aria-*` 和 slot，让业务在特殊场景有出口。完全封死会逼业务绕路，完全敞开又会破坏一致性。

```tsx
type ButtonProps = {
  variant?: "primary" | "secondary" | "danger";
  size?: "sm" | "md" | "lg";
} & React.ButtonHTMLAttributes<HTMLButtonElement>;
```

API 的扩展应该从真实重复需求里长出来，而不是把“未来可能会用”全部预留成 props。组件越底层，API 越要稳定克制。

## 可测试性

组件应该能被独立测试。输入清楚、输出稳定、交互边界明确的组件更容易写单测、交互测试和视觉测试。

```tsx
render(<Button disabled onClick={handleClick}>保存</Button>);
```

测试最好围绕组件行为，而不是围绕内部实现。比如“点击后触发回调”“输入后显示错误”“禁用时不可点击”，都比“某个 class 名称存在”更接近用户体验。

可测试组件通常有几个特点：

1. Props 输入明确。
2. 状态来源清楚。
3. DOM 语义稳定。
4. 副作用可隔离。

测试友好的组件往往也更容易维护，因为它们通常会避免把核心逻辑藏在难以观察的内部状态里。对高频组件来说，测试能反过来帮助稳定 API 设计。

组件测试可以分层：基础组件测试语义和交互，业务组件测试数据状态，页面测试关键流程。不要用快照测试替代行为测试。快照能发现 DOM 结构变化，但不一定能说明用户行为是否正确。

```tsx
render(<Button disabled onClick={handleClick}>保存</Button>);

await user.click(screen.getByRole("button", { name: "保存" }));

expect(handleClick).not.toHaveBeenCalled();
```

这个测试关注的是“禁用按钮不可触发点击”，比断言 class 名更接近组件契约。

## 设计一致性

同一体系里的组件应该共享一致的尺寸、间距、状态、交互和命名风格。这样用户学会一个组件后，能更容易迁移到其他组件。

一致性不仅是视觉，还包括：

1. 命名风格一致。
2. 状态命名一致。
3. 反馈时机一致。
4. 默认值策略一致。
5. 无障碍策略一致。

如果同一个体系里有的组件用 `size`，有的用 `scale`，有的用 `type`，调用方的学习成本会明显上升。

组件体系的目标不是“做出很多组件”，而是做出一组可以稳定组合、持续演进的 UI 原语。

一致性还会影响设计协作。设计师、前端、测试和业务方如果对“同一个状态”的理解不同，后面就会在边距、色值、交互时机和禁用态上反复拉扯。组件一致性越高，沟通成本越低。

一致性最好通过设计令牌、组件规范和示例沉淀下来，而不是依赖口头约定。比如同一个 `danger` 状态，在按钮、提示、标签和弹窗里应该有一致的色彩语义和文案强度；同一个 `disabled` 状态，也应该有一致的鼠标、键盘和可访问性表现。

```text
视觉一致：颜色、字号、圆角、间距
交互一致：hover、focus、loading、disabled
语义一致：success、warning、danger、info
代码一致：props 命名、事件命名、插槽命名
```

当组件体系能让调用方少做选择、少猜规则、少复制代码时，它才真正提升了效率。
